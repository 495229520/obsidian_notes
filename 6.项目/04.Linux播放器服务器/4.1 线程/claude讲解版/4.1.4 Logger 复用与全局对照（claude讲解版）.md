# 第4讲：Logger 复用与全局对照（claude讲解版）

> [!abstract]
> 本篇把前三讲落回真实场景：日志服务器如何**复用 `CThread`**，并借它引出全项目最关键的一组对照——
> **线程池"传指针"（只能同进程） vs 日志"传数据"（可跨进程）。**
> 最后给出 `main` 测试入口与面试串讲。
> 上级索引：[[4.1.0 线程体系总览与学习路线（claude讲解版）]]

## 1. 知识定位

属于 **后台线程 + 生产者消费者 + IPC 边界**。它复用 [[4.1.2 CThread pthread 封装（claude讲解版）]]，并与 [[4.1.3 CThreadPool socket+epoll 线程池（claude讲解版）]] 形成"传数据 vs 传指针"的关键对照；底层进程概念见 [[3.Linux/11. 进程/11.1 进程简介]]。

## 2. Logger 复用 CThread —— 证明 CThread 是"基础设施"

`CLoggerServer` 不是线程池，而是**单后台线程的专用消费者**（`Logger.h:54`）：

```cpp
CLoggerServer() : m_thread(&CLoggerServer::ThreadFunc, this) { ... }
```

它和 `CThreadPool` 唯一的共同点：**都把 `CThread` 当承载体**。

| | CThreadPool | CLoggerServer |
|---|---|---|
| 线程数 | N 个 worker | 1 个专用线程 |
| 线程做什么 | 等任务 socket → 执行任意任务 | 等日志 socket → 写文件 |
| 底座 | `CThread` | `CThread` |

这恰说明第2讲的 `CThread` 是**可复用基础设施**，不是线程池私有零件。

## 3. 🔑 全项目最关键的对照：传数据 vs 传指针

两者都用"本地 socket + epoll + CThread"，但**穿过 socket 的东西根本不同**：

| | CThreadPool | CLoggerServer |
|---|---|---|
| socket 里传的是 | `CFunctionBase*` **指针值（8字节）** | `LogInfo` 序列化的**真实数据**（`Logger.h:34` `operator Buffer()`） |
| 通信范围 | **必须同进程**（地址才有意义） | **可跨进程**（数据自带内容） |
| 实际部署 | worker 与生产者同进程 | 日志服务器跑在**独立子进程** `proclog`，业务进程经 `./log/server.sock` 连过来 |

```cpp
// Logger.h:116 —— Trace 是 static，任何进程/线程都能调
static void Trace(const LogInfo& info) {
    static thread_local CSocket client;        // 又是 TLS 免锁（同第3讲剖析1）
    if (client == -1) { client.Init(".../server.sock"); client.Link(); }
    client.Send(info);                         // info 隐式转 Buffer：发的是"内容"
}
```

**为什么 Logger 敢跨进程而 ThreadPool 不敢？** 回到 [[4.1.3 CThreadPool socket+epoll 线程池（claude讲解版）]] 剖析3 的铁律：跨进程地址无意义，所以**跨进程通信必须传可序列化数据，不能传指针**。Logger 传日志文本字节，子进程收到照样写文件；ThreadPool 传堆地址，出了进程就废。

> [!important]
> 这一组对照，把「进程 vs 线程 / 地址空间 / IPC vs 线程内通道」四个八股点一次性焊死——面试时这是最该讲的一段。

## 4. 生产者-消费者 + 文件句柄集中

日志为什么天生适合"后台单线程"模型？

- **业务线程是生产者**：`TRACEI(...)` → `Trace()` 把日志**发出去就返回**，不等磁盘 I/O，业务路径不被 `fwrite`/`fflush` 拖慢。
- **日志线程是唯一消费者**：只有 `ThreadFunc` → `WriteLog`（`Logger.h:219`）碰那个 `FILE*`。**文件句柄被收敛到单线程**，于是多线程写日志**天然不会交错、也不用给文件加锁**。

> [!tip]
> 这是"用线程归属代替锁"的又一例，和第3讲 `thread_local` 同一种思想：**消除共享 = 消除竞争**。

## 5. 顺带看懂两个 C++ 小技巧

### 流式日志 `LOGE << 100 << "x"`

`LogInfo::operator<<`（`Logger.h:37`）每次把参数 `stringstream` 成串、`+=` 进 `m_buf`，返回 `*this` 支持链式；最后 `operator Buffer()` 隐式转换交给 `Send`。

```cpp
template<typename T>
LogInfo& operator<<(const T& data) {
    std::stringstream stream; stream << data;
    m_buf += stream.str().c_str();
    return *this;                 // 链式关键
}
```

### 宏自动抓调用现场

```cpp
#define TRACEI(...) CLoggerServer::Trace(LogInfo(__FILE__, __LINE__, __FUNCTION__, \
                    getpid(), pthread_self(), LOG_INFO, __VA_ARGS__))
```

宏在**展开点**捕获 `__FILE__/__LINE__/__FUNCTION__/getpid()/pthread_self()`——所以日志能精确打印"哪个文件哪行哪个线程"。**这就是日志库为什么常用宏而非函数：函数拿不到调用者的 `__LINE__`。**

## 6. main 测试入口：三种执行方式的"递进"

```cpp
int main() {
    CProcess proclog, procclients;
    proclog.SetEntryFunction(CreateLogServer, &proclog);
    proclog.CreateSubProcess();      // ① 先拉起独立日志子进程

    LogTest();                       // ② 主线程同步执行    —— 普通函数调用
    CThread thread(LogTest);         // ③ 单独线程异步执行  —— 第2讲 CThread
    thread.Start();

    CThreadPool pool;                // ④ 线程池 worker 异步 —— 第3讲 CThreadPool
    pool.Start(4);
    pool.AddTask(LogTest);           //    投 4 个任务给 4 个 worker
    pool.AddTask(LogTest);
    pool.AddTask(LogTest);
    pool.AddTask(LogTest);
    getchar();
    pool.Close();
}
```

三种方式对应课程从浅到深的演进：

```text
LogTest()                  // 主线程同步
CThread thread(LogTest)    // 单独线程异步
pool.AddTask(LogTest)      // 线程池 worker 异步
```

而 `proclog` 在最前创建，所以上面三种方式打的日志**全部通过本地 socket 汇聚到那个子进程写文件**——这就在测试里真正跑通了第3节的"跨进程传数据"。

## 7. 这份日志还不是生产级

| 缺口 | 生产做法 |
|---|---|
| 无界通道 | 有界队列，避免日志暴增撑爆内存 / socket 缓冲 |
| 退出不保证 flush | 进程退出前显式 drain + flush |
| 不做级别过滤 | `LogLevel` 已采集但 `ThreadFunc` 未按级别过滤，应加阈值 |
| 文件无限增长 | 按大小/时间做日志轮转 |

## 8. 面试串讲：30 秒讲清整个线程体系

> 易播的线程体系分四层：`CFunction` 用**模板+多态**把任意可调用体统一成 `operator()()`；`CThread` 用 **static 蹦床函数 + this 偷渡**把 pthread 对象化；`CThreadPool` 最特别——它不用队列和条件变量，而是用**本地 socket 当任务通道、`epoll_wait` 当休眠点、`EPOLLIN` 当唤醒信号**，本质是 self-pipe trick；`CLoggerServer` 复用 `CThread` 做单线程日志消费者。
>
> 最值得讲的权衡是：线程池**传 `CFunctionBase*` 裸指针，所以只能同进程**；而日志**传序列化数据，所以能跨进程**到独立的日志子进程。这一点把进程/线程地址空间的区别讲活了。
>
> 工程上我会指出它的教学痕迹：用信号停线程不满足异步信号安全（应换 `eventfd`/`stop_token`）、N 个 worker 抢一个 epoll 有惊群和竞态（应换 one-loop-per-thread 或 `EPOLLEXCLUSIVE`）、裸指针穿 socket 破坏了 RAII（应换 `unique_ptr` + 真正的 MPMC 队列）。

## 9. 全四讲知识闭环

```text
第1讲 Function    模板适配差异 + 多态统一接口 → base 是"堆地址"
                       │
第2讲 CThread     static蹦床+this偷渡 pthread → EMC++ Item37 空析构 / jthread+stop_token
                       │
第3讲 ThreadPool  socket=队列 / epoll=cond_wait / EPOLLIN=signal
                  thread_local免锁 + 裸指针所有权流转(同进程铁律) + 共享epoll惊群
                       │
第4讲 Logger      复用CThread + 【传数据⇒跨进程】对照【传指针⇒同进程】 + 生产者消费者免锁
```

## 10. 延伸思考

1. **相关概念**：`CProcess::SendFD/RecvFD`（fd 传递）——这是"跨进程传句柄"的正解，和本篇"跨进程必须传数据/句柄、不能传指针"是同一原理的延伸。
2. **面试常见问题**：
   - Q：为什么线程间能共享指针，进程间不行？
   - A：线程共享同一虚拟地址空间，一个线程 `new` 的堆对象另一个线程用同地址可访问；进程地址空间独立，地址值传过去没有意义。跨进程要用管道/消息队列/socket 序列化协议/共享内存。
