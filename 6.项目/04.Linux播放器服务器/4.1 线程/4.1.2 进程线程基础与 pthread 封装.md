# 进程线程基础与 pthread 封装

> [!abstract]
> 本篇解释易播线程体系为什么必须先理解进程和线程的地址空间差异。
> 重点连接 `CFunctionBase*` 指针传递、同进程线程共享堆、`pthread_create` 的 C 风格入口和 C++ 对象封装。
> 
> 上级索引：[[4.1.1 易播服务器线程体系详解|易播服务器线程体系总览]]

## 4. 进程 vs 线程：为什么这里必须理解地址空间

`[[3.Linux/11. 进程/11.1 进程简介]]` 里最重要的一句话是：**进程是资源分配的基本单位**。每个进程有自己的虚拟地址空间、文件描述符表、堆、全局变量等资源边界。`[[3.Linux/12. 线程/12.1 线程简介]]` 里最重要的一句话是：**线程是操作系统调度的最小单位**。同一个进程内的多个线程共享进程的地址空间和文件描述符，但每个线程有自己的栈、寄存器和执行流。

这两个概念直接决定了易播线程池的一个关键实现是否成立：

```cpp
CFunctionBase* base = new CFunction< _FUNCTION_, _ARGS_...>(func, args...);
Buffer data(sizeof(base));
memcpy(data, &base, sizeof(base));
ret = client.Send(data);
```

这里通过 socket 发送的是 `base` 指针的二进制值。这个做法看起来很危险，但在当前线程池设计中它能工作，原因是：

- `base` 不是任务数据本身，而是任务对象在当前进程堆内存中的地址。假设 `base = 0x12345678`，这个值的含义是“到当前进程的堆里找这个 `CFunction` 对象”。
- `AddTask()` 的调用者和 `TaskDispatch()` 的 worker 线程属于同一个进程。
- 同一进程内的线程共享堆空间。
- `new CFunction(...)` 得到的堆对象地址，对同进程内所有线程都有意义。也就是说，调用者线程看到 `0x12345678` 指向某个 `CFunction` 对象，worker 线程用同一个地址值也能找到同一个对象。
- 本地 socket 在这里不是跨进程序列化通道，而是一个同进程内的任务通知和数据搬运通道。

如果把这段逻辑改成跨进程通信，立刻就会失效。因为父进程里的地址 `0x12345678`，传到子进程后只是一个普通数字。子进程有自己的虚拟地址空间，这个地址可能没有映射，也可能映射到别的内容；即使地址值碰巧相同，也不是父进程里 `new` 出来的那块堆内存。

所以跨进程要传任务，不能直接传普通 C++ 对象指针，而应该传**可序列化数据**，例如任务类型、函数编号、参数内容、JSON 或自定义二进制协议；如果确实要共享内存中的对象，也必须使用**共享内存 + 同步机制**，并且专门设计对象布局和生命周期。

> [!important]
> 这就是项目代码和八股知识的连接点：面试里问“进程和线程的区别”不是背概念而已。这个区别会直接决定 `CFunctionBase*` 能不能这样传、socket 在这里到底是 IPC 还是线程内任务通道。

## 5. pthread 八股与 CThread 对应表

`CThread` 基本就是一份 pthread 八股题的项目化答案：

| pthread 八股点 | 标准理解 | 项目代码位置 | 项目里的作用 |
|---|---|---|---|
| `pthread_create` | 创建线程，入口必须是 `void* (*)(void*)` | `CThread::Start()` | 创建新线程，并把 `this` 作为参数传给静态入口 |
| 线程入口函数 | 普通成员函数不能直接传给 pthread | `static ThreadEntry(void*)` | 静态函数接住 `void*`，再转回 `CThread*` |
| 参数传递 | pthread 只能传一个 `void*` 参数 | `pthread_create(..., this)` | 用 `this` 间接带出整个对象上下文 |
| `joinable` | 线程结束后需要被 join 回收 | `pthread_attr_setdetachstate` | 创建时设置为 `PTHREAD_CREATE_JOINABLE` |
| `pthread_join` | 等待线程结束并回收资源 | `pthread_timedjoin_np` | `Stop()` 中限时等待线程自然退出 |
| `detach` | 分离后线程结束自动回收，不能再 join | `pthread_detach` | 超时或线程结束时转成分离状态 |
| `pthread_exit` | 当前线程主动退出 | `ThreadEntry()`、`Sigaction()` | 业务执行完或收到退出信号后结束线程 |
| 信号控制线程 | 可以向指定线程发信号，但要注意安全性 | `pthread_kill`、`SIGUSR1`、`SIGUSR2` | 用于暂停和退出，教学意义大于生产推荐 |

面试时可以这样回答 `CThread` 的封装思想：

> `pthread_create` 只能接收 C 风格线程入口，所以 C++ 封装时通常把入口函数做成 `static void* ThreadEntry(void*)`，再把当前对象 `this` 作为参数传进去。线程启动后，静态入口把 `void*` 转回对象指针，调用对象内部保存的任务函数。易播的 `CThread` 就是这个模式，只是它进一步用 `CFunctionBase` 把任意函数和参数包装成统一的 `operator()()`。

### 为什么要用 `static ThreadEntry(void*)`

`pthread_create` 是 C 接口，它只认一种线程入口函数类型：

```cpp
void* (*)(void*)
```

也就是说，线程入口必须是一个**普通函数指针**：接收一个 `void*` 参数，返回一个 `void*`。普通 C++ 成员函数不能直接传进去，因为成员函数天然依赖某个对象，背后有一个隐藏的 `this` 参数。

例如表面上写的是：

```cpp
thread.Run();
```

可以理解成编译器实际需要：

```cpp
Run(&thread);
```

所以普通成员函数的类型并不是 `void* (*)(void*)`，它和 pthread 要求的函数指针类型对不上。`static` 成员函数不绑定具体对象，没有隐藏的 `this` 参数，所以可以伪装成普通 C 函数入口。

### `ThreadEntry + this` 的转接流程

`CThread::Start()` 创建线程时，大致做了这件事：

```cpp
pthread_create(&m_thread, &attr, &CThread::ThreadEntry, this);
```

可以按下面的流程理解：

```text
主线程调用 CThread::Start()
    -> pthread_create 创建新线程
    -> 新线程从 static ThreadEntry(void*) 开始执行
    -> pthread 把第四个参数 this 原样传给 ThreadEntry
    -> ThreadEntry 把 void* 转回 CThread*
    -> 通过 CThread 对象访问成员变量和任务函数
    -> 调用 CFunctionBase::operator()() 执行真正任务
```

典型写法接近这样：

```cpp
void* CThread::ThreadEntry(void* arg)
{
    CThread* self = static_cast<CThread*>(arg);
    if (self->m_function != nullptr) {
        (*self->m_function)();
    }
    pthread_exit(nullptr);
}
```

这里的关键点是：`pthread` 只负责把一个 `void*` 传进线程入口；至于这个 `void*` 里面到底是什么，完全由我们自己约定。项目里传的是 `this`，所以线程入口拿到它以后，就能重新回到 C++ 对象语境中。

### 生命周期相关的几个八股点

`joinable`、`join`、`detach`、`pthread_exit` 不是孤立概念，它们共同描述线程从创建到结束的资源回收过程：

- `PTHREAD_CREATE_JOINABLE`：线程结束后不会立刻完全释放资源，需要其他线程 `join` 它。
- `pthread_join`：等待目标线程结束，并回收它的线程资源。
- `pthread_timedjoin_np`：带超时的 join，项目里用于 `Stop()` 时等待线程自然退出。
- `pthread_detach`：把线程改成分离状态，之后线程结束会自动回收，但不能再 `join`。
- `pthread_exit`：当前线程主动退出，通常在线程入口函数执行完任务后调用。

易播的 `CThread` 把这些点串成了一个对象生命周期：`Start()` 负责创建线程，`ThreadEntry()` 负责进入任务，`Stop()` 尝试等待线程退出，超时后再结合 `detach` 和信号控制做兜底。

> [!warning]
> `pthread_kill` 给指定线程发信号可以展示“线程控制”的知识点，但生产代码里要谨慎使用。信号处理函数里能安全调用的函数很少，复杂的暂停/退出控制更推荐用条件变量、`eventfd`、原子变量或明确的控制消息。
