# SessionLog 审计日志系统

> [!abstract]
> `CSessionLog` 负责远控服务端的会话事件审计记录。
> 本笔记分析日志存储路径（`%LOCALAPPDATA%\AssistHost\sessions.log`）、TSV 格式（Timestamp/HelperName/PeerIp/EventType/Detail）、事件类型（connect_attempt/consent_shown/consent_approved/consent_denied/consent_timed_out/socket_error/session_started/session_extended/session_expired/session_ended_locally/session_disconnected）、字段转义机制、文件 I/O 实现、以及与 `HostMainDlg` 的集成方式。

---

## 1. 模块定位

![[图片/6.项目/06.远控服务端/6.3 会话管理/6_3_3_2_1.svg]]

**关键职责分工**：
- `CSessionLog`：纯静态工具类，负责日志文件的追加写入和读取，不持有任何状态
- `HostMainDlg::AppendSessionLog`：薄封装层，负责补全缺省的 `helperName` 和 `peerIp` 字段
- `HostMainDlg` 的各事件处理函数：决定**何时**记录**什么类型**的事件

## 2. 类设计

### 2.1 接口定义

```cpp
// SessionLog.h
class CSessionLog
{
public:
    // 追加一条事件到日志文件
    static void AppendEvent(
        const CString& helperName,   // 远程助手名称
        const CString& peerIp,       // 远程 IP 地址
        const CString& eventType,    // 事件类型字符串
        const CString& detail);      // 事件详情

    // 读取完整日志内容（用于 UI 展示）
    static CString ReadRecentSessions();

private:
    static CString GetLogPath();                    // 获取日志文件绝对路径
    static CString EscapeField(const CString& value);  // 字段转义
};
```

### 2.2 设计特征

| 特征 | 说明 |
|-----|------|
| **全静态方法** | 无实例状态，无需构造/析构，调用方直接 `CSessionLog::AppendEvent(...)` |
| **无锁设计** | 所有调用均发生在 UI 线程（MFC 消息泵保证串行化），不需要互斥锁 |
| **Fire-and-Forget** | `AppendEvent` 无返回值，写入失败静默忽略——审计日志不应阻断主业务流程 |
| **字符串类型事件** | 事件类型用 `CString` 传递而非枚举，灵活但缺少编译期检查 |

> [!tip] 为什么用全静态而不是单例？
> `CSessionLog` 没有任何成员变量，全部行为仅依赖参数和文件系统。静态方法是最简模型——无需管理生命周期，无需考虑初始化顺序问题。单例模式在此场景属于过度设计。

## 3. 日志存储路径

### 3.1 路径构建逻辑

```cpp
// SessionLog.cpp:70
CString CSessionLog::GetLogPath()
{
    TCHAR localAppData[MAX_PATH] = {};
    const DWORD length = ::GetEnvironmentVariable(
        _T("LOCALAPPDATA"), localAppData, _countof(localAppData));

    CString basePath = (length > 0 && length < _countof(localAppData))
        ? CString(localAppData)
        : CString(_T("."));    // 回退到当前目录

    if (!basePath.IsEmpty() && basePath[basePath.GetLength() - 1] != _T('\\'))
    {
        basePath += _T("\\");
    }

    return basePath + _T("AssistHost\\sessions.log");
}
```

**路径解析流程**：

```
GetEnvironmentVariable("LOCALAPPDATA")
  │
  ├─ 成功 → C:\Users\<用户名>\AppData\Local
  │          └─ + \AssistHost\sessions.log
  │          → C:\Users\<用户名>\AppData\Local\AssistHost\sessions.log
  │
  └─ 失败 → "."  (当前工作目录)
             └─ + \AssistHost\sessions.log
             → .\AssistHost\sessions.log
```

### 3.2 技术细节

| 要点 | 说明 |
|-----|------|
| **API 选择** | 使用 `GetEnvironmentVariable` 而非 `SHGetFolderPath` / `SHGetKnownFolderPath`，更轻量但不处理文件夹重定向的边缘情况 |
| **缓冲区大小** | `MAX_PATH`（260 字符），标准 Windows 路径上限。超长路径场景下可能截断 |
| **回退策略** | 环境变量不存在时回退到 `"."`（当前目录），确保程序不崩溃 |
| **尾部反斜杠** | 显式检查并补全 `\\`，防止路径拼接出错（如 `C:\Users\AdminAssistHost`） |

### 3.3 目录自动创建

```cpp
// SessionLog.cpp:27
const CString logPath = GetLogPath();
const int slashIndex = logPath.ReverseFind(_T('\\'));
if (slashIndex > 0)
{
    ::CreateDirectory(logPath.Left(slashIndex), nullptr);
}
```

`CreateDirectory` 的行为：
- 目录已存在 → 静默返回 `FALSE`，`GetLastError()` 为 `ERROR_ALREADY_EXISTS`，不影响后续操作
- 目录不存在 → 创建成功
- **局限**：只创建一层目录。如果 `%LOCALAPPDATA%` 不存在（极端情况），不会递归创建

> [!warning] 仅创建单层目录
> `CreateDirectory` 不是 `mkdir -p`。若 `%LOCALAPPDATA%\AssistHost` 中的 `%LOCALAPPDATA%` 本身不存在（理论上不可能但值得注意），创建会失败。实际 Windows 系统中 `%LOCALAPPDATA%` 始终由系统保证存在。

## 4. TSV 日志格式

### 4.1 格式规范

每行日志由 **5 个字段** 组成，以 **Tab (`\t`) 分隔**：

```
Timestamp           HelperName    PeerIp          EventType         Detail
────────────────    ──────────    ──────────────  ────────────────  ──────────────────────────
2026-06-05 14:30:45	JohnDoe	    192.168.1.100	connect_attempt   Incoming viewer connection
2026-06-05 14:30:46	JohnDoe	    192.168.1.100	consent_shown     Waiting for local approval
2026-06-05 14:30:50	JohnDoe	    192.168.1.100	consent_approved  Screen stream approved.
2026-06-05 14:30:51	JohnDoe	    192.168.1.100	session_started   Screen sharing active
2026-06-05 15:25:51	JohnDoe	    192.168.1.100	session_extended  Host extended the session by 15 minutes.
2026-06-05 15:30:51	JohnDoe	    192.168.1.100	session_ended_locally  Session ended locally.
```

### 4.2 字段说明

| 字段 | 类型 | 格式 | 来源 |
|-----|------|------|------|
| **Timestamp** | 本地时间 | `YYYY-MM-DD HH:MM:SS` | `GetLocalTime()` Windows API |
| **HelperName** | 助手标识 | 自由文本 | Viewer 在 Hello 握手中提供 |
| **PeerIp** | IP 地址 | `x.x.x.x` | `accept()` 后从 `sockaddr_in` 解析 |
| **EventType** | 事件标识 | snake_case 字符串 | 调用方硬编码 |
| **Detail** | 详情描述 | 自由文本 | 调用方提供 |

### 4.3 选择 TSV 而非 CSV/JSON 的理由

| 格式 | 优势 | 劣势 |
|-----|------|------|
| **TSV (当前)** | 实现极简，无需引号处理；Tab 在日志内容中极少出现 | 需自行转义 Tab/换行 |
| CSV | 广泛支持 | 需要处理逗号、引号、换行的嵌套转义（RFC 4180） |
| JSON | 结构化，易解析 | 追加写入不构成合法 JSON（需 JSON Lines 格式），实现更复杂 |
| Windows Event Log | 系统级审计 | 需要 Event Source 注册，部署复杂度高 |

> [!note] 设计权衡
> TSV 是"够用即可"的选择。对于本项目的审计需求（单进程、顺序写入、人类可读），TSV 的简洁性优于其他格式的结构化能力。

### 4.4 时间戳生成

```cpp
// SessionLog.cpp:6 — 匿名命名空间中的辅助函数
namespace
{
CString FormatTimestamp()
{
    SYSTEMTIME localTime = {};
    ::GetLocalTime(&localTime);

    CString timestamp;
    timestamp.Format(
        _T("%04u-%02u-%02u %02u:%02u:%02u"),
        localTime.wYear,
        localTime.wMonth,
        localTime.wDay,
        localTime.wHour,
        localTime.wMinute,
        localTime.wSecond);
    return timestamp;
}
}
```

**技术要点**：
- `GetLocalTime`：返回本机当前时区的时间，适合面向本地管理员的审计日志
- `SYSTEMTIME` 结构体：零初始化（`= {}`），防止未初始化字段
- 匿名命名空间：将函数限制在本编译单元（`SessionLog.cpp`），等效于 `static` 但更 Modern C++
- 秒级精度：对审计日志足够，无需毫秒

> [!tip] GetLocalTime vs GetSystemTime
> `GetLocalTime` 返回本地时区时间，适合单机审计。若需跨时区日志聚合（如集中式日志系统），应使用 `GetSystemTimeAsFileTime` 获取 UTC 时间。

## 5. 字段转义机制

### 5.1 实现

```cpp
// SessionLog.cpp:83
CString CSessionLog::EscapeField(const CString& value)
{
    CString escaped(value);
    escaped.Replace(_T("\r"), _T(" "));   // 回车 → 空格
    escaped.Replace(_T("\n"), _T(" "));   // 换行 → 空格
    escaped.Replace(_T("\t"), _T(" "));   // Tab  → 空格
    return escaped;
}
```

### 5.2 转义策略分析

**为什么要转义这三个字符？**

```
字符    在 TSV 中的角色        不转义的后果
────    ──────────────────    ────────────────────────────
\t      字段分隔符             一个字段被拆成两个，后续字段错位
\n      记录分隔符             一条日志被拆成两条，解析器混乱
\r      行尾符（Windows CRLF） 同 \n，且可能导致部分行被覆盖
```

**转义方式**：直接替换为空格，而非使用转义序列（如 `\\t`）。

优点：
- 实现极简，一行代码一个字符
- 替换后的文本仍然人类可读
- 不需要对应的"反转义"逻辑

缺点：
- **有损转换**——原始内容中的换行信息丢失，无法还原
- 若 `detail` 包含多行堆栈跟踪，换行会被压成一行

> [!warning] 有损转义
> `EscapeField` 是**有损**的。`"line1\nline2"` 转义后变为 `"line1 line2"`，无法区分原始内容是否包含空格还是换行。对于当前的审计场景（事件类型 + 简短描述），这不是问题。但若未来需要记录多行详情（如错误堆栈），需要改用可逆转义方案。

### 5.3 调用时机

`EscapeField` 对**除 Timestamp 外的全部四个字段**执行转义：

```cpp
// SessionLog.cpp:40
line.Format(
    _T("%s\t%s\t%s\t%s\t%s\n"),
    FormatTimestamp().GetString(),         // 不转义：格式固定，不含特殊字符
    EscapeField(helperName).GetString(),   // 转义：用户可控输入
    EscapeField(peerIp).GetString(),       // 转义：理论上格式固定但防御性处理
    EscapeField(eventType).GetString(),    // 转义：内部字符串但保持一致性
    EscapeField(detail).GetString());      // 转义：最可能包含特殊字符
```

> [!tip] 防御性编程
> 虽然 `peerIp` 和 `eventType` 理论上不包含换行/Tab，但统一对所有用户侧字段进行转义是正确的防御性做法。输入验证应在最靠近持久化的一层执行，而非假设上游已经清洗。

## 6. 文件 I/O 实现

### 6.1 AppendEvent — 追加写入

```cpp
// SessionLog.cpp:24
void CSessionLog::AppendEvent(
    const CString& helperName,
    const CString& peerIp,
    const CString& eventType,
    const CString& detail)
{
    const CString logPath = GetLogPath();

    // 1. 确保目录存在
    const int slashIndex = logPath.ReverseFind(_T('\\'));
    if (slashIndex > 0)
    {
        ::CreateDirectory(logPath.Left(slashIndex), nullptr);
    }

    // 2. 打开文件（追加模式）
    CStdioFile file;
    if (!file.Open(logPath,
        CFile::modeCreate |        // 文件不存在则创建
        CFile::modeNoTruncate |    // 已存在则不截断
        CFile::modeWrite |         // 写入模式
        CFile::typeText))          // 文本模式（CRLF 转换）
    {
        return;   // 静默失败
    }

    // 3. 定位到文件末尾
    file.SeekToEnd();

    // 4. 格式化并写入一行 TSV
    CString line;
    line.Format(
        _T("%s\t%s\t%s\t%s\t%s\n"),
        FormatTimestamp().GetString(),
        EscapeField(helperName).GetString(),
        EscapeField(peerIp).GetString(),
        EscapeField(eventType).GetString(),
        EscapeField(detail).GetString());
    file.WriteString(line);

    // 5. CStdioFile 析构自动 Close（RAII）
}
```

### 6.2 文件打开标志详解

```
modeCreate | modeNoTruncate | modeWrite | typeText
    │              │              │           │
    │              │              │           └── CRT 文本模式：
    │              │              │               写 \n → 磁盘 \r\n (Windows)
    │              │              │               读 \r\n → 内存 \n
    │              │              │
    │              │              └── O_WRONLY
    │              │
    │              └── 不截断已有内容
    │                  若不加此标志，modeCreate 会清空文件！
    │
    └── O_CREAT：文件不存在则创建
```

> [!danger] modeCreate 与 modeNoTruncate 必须组合使用
> `CFile::modeCreate` **单独使用**时等效于 `O_CREAT | O_TRUNC`，会**清空已有文件**。必须配合 `CFile::modeNoTruncate` 才能实现"存在则追加，不存在则创建"的语义。这是 MFC 文件操作中一个经典陷阱。

### 6.3 SeekToEnd 的必要性

```cpp
file.SeekToEnd();
```

虽然用了 `modeNoTruncate`，但 `modeWrite` 打开文件后**文件指针在开头**（不像 `fopen("a")` 自动定位到末尾）。如果不 `SeekToEnd`，`WriteString` 会**覆盖文件开头的内容**。

> [!danger] 不 SeekToEnd 就会覆盖！
> 这是 MFC `CFile` 与 C 标准库 `fopen("a")` 的关键差异。`fopen("a")` 模式下每次 write 都原子性地追加到末尾；而 `CFile::modeWrite | modeNoTruncate` 只是"不截断"，写入位置仍需手动设置。

下图对比"未 SeekToEnd"与"SeekToEnd 之后"两种写指针位置，直观呈现 `modeNoTruncate` 与 `SeekToEnd()` 必须配合使用的原因：

### 6.4 ReadRecentSessions — 全量读取

```cpp
// SessionLog.cpp:51
CString CSessionLog::ReadRecentSessions()
{
    CStdioFile file;
    if (!file.Open(GetLogPath(), CFile::modeRead | CFile::typeText))
    {
        return _T("No session history yet.");
    }

    CString content;
    CString line;
    while (file.ReadString(line))   // 逐行读取
    {
        content += line;
        content += _T("\r\n");      // 重新添加 Windows 换行符
    }

    return content.IsEmpty()
        ? _T("No session history yet.")
        : content;
}
```

**技术要点**：

| 要点 | 说明 |
|-----|------|
| **全量加载** | 将整个日志文件读入内存。日志增长无上限，长期运行后可能消耗大量内存 |
| **逐行拼接** | `CString::operator+=` 每次调用可能触发内存重分配，对大文件效率较低 |
| **CRLF 补回** | `ReadString` 会剥离行尾换行，这里用 `\r\n` 重新添加以适配 MFC `Edit` 控件的显示 |
| **UI 用途** | 结果直接通过 `SetDlgItemText(IDC_EDIT_RECENT_SESSIONS, ...)` 显示在多行编辑框中 |

> [!warning] 无日志轮转机制
> `ReadRecentSessions` 读取整个文件，`AppendEvent` 只追加不清理。长期运行的主机上，`sessions.log` 会持续增长。应考虑：
> - 按大小轮转（如超过 1MB 时截断/归档）
> - 按时间保留（如只保留最近 30 天）
> - 读取时只取最后 N 行（避免内存暴涨）

## 7. 事件类型全览

### 7.1 完整事件类型表

| 事件类型 | 触发位置 | 触发条件 | 典型 detail |
|---------|---------|---------|------------|
| `connect_attempt` | `OnServerEvent` / Listening | Viewer 建立 TCP 连接 | `"Incoming viewer connection"` |
| `consent_shown` | `OnServerEvent` / WaitingForConsent | Hello 验证通过，弹出同意对话框 | `"Waiting for local approval"` |
| `consent_approved` | `OnConsentRequest` | 主机用户点击 Allow | `"Screen stream approved."` |
| `consent_denied` | `OnConsentRequest` | 主机用户点击 Deny | `"Host denied screen sharing."` |
| `consent_timed_out` | `OnConsentRequest` | 30 秒倒计时超时 | `"Consent dialog timed out."` |
| `session_started` | `StartSession` | 同意后共享正式开始 | Payload detail |
| `session_extended` | `OnBnClickedExtendSession` | 主机用户点击延长 | `"Host extended the session by 15 minutes."` |
| `session_expired` | `OnTimer` / `StopSession` | 60 分钟时限到达 | `"60-minute session limit reached."` |
| `session_ended_locally` | `StopSession` | 主机主动终止 | `"Session ended locally."` |
| `session_disconnected` | `StopSession` | Viewer 意外断开 | `"Viewer disconnected."` |
| `socket_error` | `OnServerEvent` / Error | 网络错误 | 具体错误描述 |

### 7.2 事件生命周期

一次**完整正常会话**的事件序列：

```
connect_attempt          ← Viewer TCP 连入
    │
consent_shown            ← Hello 握手通过，弹出同意框
    │
consent_approved         ← 主机用户同意
    │
session_started          ← 共享正式开始
    │
session_extended (0..N)  ← 主机可选延长 N 次
    │
session_ended_locally    ← 主机主动结束
  或 session_expired     ← 时限到期
  或 session_disconnected← Viewer 断开
```

**异常场景的事件序列**：

```
场景 1：用户拒绝
  connect_attempt → consent_shown → consent_denied

场景 2：超时自动拒绝
  connect_attempt → consent_shown → consent_timed_out

场景 3：网络错误
  connect_attempt → socket_error

场景 4：会话中网络断开
  connect_attempt → consent_shown → consent_approved
  → session_started → session_disconnected
```

### 7.3 事件类型用字符串而非枚举

```cpp
// 当前设计：字符串字面量
AppendSessionLog(_T("consent_approved"), _T("Screen stream approved."));
AppendSessionLog(_T("session_expired"), _T("60-minute session limit reached."));
```

> [!warning] 缺少编译期检查
> 事件类型以硬编码字符串传递，拼写错误不会被编译器捕获。例如 `_T("sesion_started")`（少一个 s）会静默写入错误的事件类型。改进方案是定义常量或枚举：
> ```cpp
> // 改进建议
> namespace SessionEvent
> {
>     constexpr LPCTSTR ConnectAttempt   = _T("connect_attempt");
>     constexpr LPCTSTR ConsentApproved  = _T("consent_approved");
>     constexpr LPCTSTR SessionStarted   = _T("session_started");
>     // ...
> }
> ```

## 8. HostMainDlg 集成

### 8.1 AppendSessionLog 封装层

```cpp
// HostMainDlg.h:52 — 声明
void AppendSessionLog(
    const CString& eventType,
    const CString& detail,
    const CString& helperName = CString(),   // 默认空
    const CString& peerIp = CString());      // 默认空

// HostMainDlg.cpp:287 — 实现
void CHostMainDlg::AppendSessionLog(
    const CString& eventType,
    const CString& detail,
    const CString& helperName,
    const CString& peerIp)
{
    const CString logHelperName = helperName.IsEmpty()
        ? m_activeHelperName : helperName;
    const CString logPeerIp = peerIp.IsEmpty()
        ? m_activePeerIp : peerIp;
    CSessionLog::AppendEvent(logHelperName, logPeerIp, eventType, detail);
}
```

**设计意图**：

1. **参数默认值补全**：会话活跃期间（`session_started` 到 `session_ended`），`helperName` 和 `peerIp` 已存储在 `m_activeHelperName` / `m_activePeerIp` 成员变量中。调用方无需每次重复传递。

2. **显式覆盖**：在会话开始**之前**（如 `connect_attempt`、`consent_shown`）或结束**之后**，成员变量可能尚未设置或已清空，此时调用方通过参数显式传入。

### 8.2 调用方参数传递模式

| 场景 | helperName 参数 | peerIp 参数 | 实际来源 |
|-----|----------------|------------|---------|
| `connect_attempt` | `payload->helperName` | `payload->peerIp` | 显式从 Payload 传入 |
| `consent_shown` | `payload->helperName` | `payload->peerIp` | 显式从 Payload 传入 |
| `consent_approved/denied/timed_out` | `request->helperName` | `request->peerIp` | 显式从 ConsentRequest 传入 |
| `session_started` | 默认空 | 默认空 | 从 `m_activeHelperName/Ip`（刚在 `StartSession` 中赋值） |
| `session_extended` | 默认空 | 默认空 | 从 `m_activeHelperName/Ip` |
| `session_expired` (OnTimer) | 默认空 | 默认空 | 从 `m_activeHelperName/Ip` |
| `session_ended/disconnected` | `payload->helperName` | `payload->peerIp` | 显式传入（因为下方 `m_activeHelperName.Empty()` 会清空） |

> [!important] StopSession 中的顺序依赖
> `StopSession` 先调用 `AppendSessionLog`，然后才 `m_activeHelperName.Empty()`。若顺序颠倒，日志中的 helperName/peerIp 字段将为空。这是一个隐式的调用顺序约束。

## 9. StopSession 中的事件类型推导

`StopSession` 需要根据 `detail` 文本推导事件类型，这是最复杂的日志逻辑：

```cpp
// HostMainDlg.cpp:248
void CHostMainDlg::StopSession(const HostServerEventPayload& payload)
{
    const CString detail = payload.detail.IsEmpty()
        ? _T("Session ended.") : payload.detail;

    const CString eventType =
        detail == _T("Session expired.")
            ? _T("session_expired")
            : (detail == _T("Session ended locally.")
                ? _T("session_ended_locally")
                : _T("session_disconnected"));

    AppendSessionLog(eventType, detail, payload.helperName, payload.peerIp);
    // ... 清理代码 ...
}
```

**推导逻辑**：

```
payload.detail
    │
    ├── "Session expired."       → session_expired
    ├── "Session ended locally." → session_ended_locally
    └── 其他 (含空值)            → session_disconnected
```

> [!warning] 字符串匹配的脆弱性
> 事件类型推导依赖 `detail` 文本的**精确匹配**。如果任何调用 `EndSession` 的地方修改了文本（如加个句号或改大小写），推导就会错误地归类为 `session_disconnected`。这是"魔法字符串"反模式的典型案例。
>
> 改进方案：让 `HostServerEventPayload` 携带结构化的终止原因枚举，而非依赖 detail 文本推导。

## 11. 陷阱与警示

> [!danger] 陷阱 1：modeCreate 不加 modeNoTruncate 会清空文件
> `CFile::modeCreate` 单独使用等效于 `O_CREAT | O_TRUNC`。忘加 `modeNoTruncate` 会在每次写入时清空整个日志文件。这是 MFC 文件操作中最常见的错误之一。

> [!danger] 陷阱 2：SeekToEnd 遗漏导致覆盖
> `modeWrite | modeNoTruncate` 打开后文件指针在位置 0。不调用 `SeekToEnd()` 意味着 `WriteString` 从文件开头写入，覆盖已有日志。与 C 标准库 `fopen("a")` 行为完全不同。

> [!warning] 陷阱 3：无日志轮转
> `sessions.log` 只追加不清理。若 AssistHost 持续运行数月，日志文件和 `ReadRecentSessions` 返回的 `CString` 都会无限增长，最终导致内存压力和 UI 卡顿。

> [!warning] 陷阱 4：StopSession 的字符串匹配
> 事件类型推导依赖 `detail == _T("Session expired.")` 等精确字符串比较。修改任何 `EndSession` 调用的 detail 文本都可能导致事件分类错误。

> [!warning] 陷阱 5：有损转义不可逆
> `EscapeField` 将 `\r`、`\n`、`\t` 替换为空格，无法从转义后的文本恢复原始内容。对于当前简短 detail 文本不是问题，但若将来记录多行内容（如堆栈跟踪），信息会丢失。

> [!warning] 陷阱 6：CStdioFile 与并发写入
> 虽然当前所有写入都在 UI 线程，但 `CStdioFile` 不是线程安全的。若未来需要从多个线程写入日志，必须加锁保护或改用线程安全的日志库。

## 12. 设计决策分析

### 12.1 为什么用静态方法而不是实例方法？

**当前方案**：全静态方法，无成员变量
**替代方案**：实例化 `CSessionLog`，在 `HostMainDlg` 中持有成员

选择静态方法的原因：
1. 日志类没有需要维护的状态——路径是固定的，每次操作独立
2. 避免了"何时创建/销毁实例"的生命周期问题
3. 调用方一行代码即可使用，无需依赖注入

### 12.2 为什么写入失败时静默忽略？

```cpp
if (!file.Open(...))
{
    return;   // 静默失败，不抛异常、不弹框
}
```

审计日志是**辅助功能**，不应阻断核心业务（屏幕共享）。设计原则：
- 日志写入失败不影响用户体验
- 避免在文件系统异常时弹出错误对话框打断用户操作
- 符合"日志系统不应成为系统的 Single Point of Failure"原则

### 12.3 为什么 AppendSessionLog 是 HostMainDlg 的成员而非独立函数？

需要访问 `m_activeHelperName` 和 `m_activePeerIp` 成员变量来补全默认值。将它作为成员方法而非全局/静态函数是正确的封装——它依赖于对话框的会话状态。

### 12.4 为什么 ReadRecentSessions 读取全量而非最后 N 行？

当前实现简单直接。对于本项目的使用场景（桌面工具，非长期运行的服务器），日志量通常很小。如果需要优化：
- 方案 A：从文件末尾反向读取，只返回最后 N 行
- 方案 B：在 `AppendEvent` 中加入轮转逻辑，控制文件大小

## 13. 面试表达

> [!quote] 推荐表达
> "审计日志系统采用**全静态工具类**设计，`CSessionLog` 不持有任何状态，所有操作（追加写入、全量读取）都是独立的原子调用。
>
> 日志格式选用 **TSV**（Tab-Separated Values），每行 5 个字段：时间戳、助手名称、对端 IP、事件类型、详情。所有字段在写入前经过**有损转义**——将 `\r`、`\n`、`\t` 替换为空格，防止分隔符注入破坏日志结构。
>
> 文件 I/O 使用 MFC 的 `CStdioFile`，以 `modeCreate | modeNoTruncate | modeWrite` 组合打开，配合 `SeekToEnd()` 实现追加写入。这里有一个 MFC 特有的陷阱：`modeCreate` 单独使用会截断文件，必须搭配 `modeNoTruncate`；而且打开后文件指针在开头，必须手动 `SeekToEnd`——这与 C 标准库 `fopen("a")` 的自动追加行为不同。
>
> 系统共定义了 11 种事件类型，覆盖了会话完整生命周期：从连接尝试、同意流程、会话运行到终止。`HostMainDlg` 通过一个**薄封装方法** `AppendSessionLog` 桥接到 `CSessionLog`，自动从成员变量补全助手名称和 IP 地址等缺省字段。"

## 14. 已知局限

| 局限 | 说明 | 改进方向 |
|-----|------|---------|
| 无日志轮转 | 文件无限增长 | 添加按大小或按天轮转机制 |
| 全量读取 | `ReadRecentSessions` 加载整个文件 | 只读最后 N 行或最近 N 天 |
| 有损转义 | 换行信息不可恢复 | 改用 `\\n` 等可逆转义序列 |
| 字符串事件类型 | 无编译期拼写检查 | 定义 `constexpr` 常量或枚举 |
| 字符串匹配推导 | StopSession 依赖 detail 文本精确匹配 | 在 Payload 中添加结构化终止原因 |
| 无时区信息 | 时间戳为本地时间，无法跨时区对齐 | 使用 UTC + 时区偏移 |
| 单层目录创建 | `CreateDirectory` 不递归 | 实际场景中 `%LOCALAPPDATA%` 必然存在，风险极低 |
