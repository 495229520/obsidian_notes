# 12.7 条件变量与线程池

[[12.3 互斥量|互斥量]]解决的是“同一时刻谁能访问共享数据”，但很多多线程程序还需要解决另一个问题：**没有任务时线程应该睡眠，有任务时再被唤醒**。这就是条件变量要解决的问题。

---

## 1. 为什么只靠互斥量不够

假设有一个任务队列：

```text
producer 线程负责放任务
consumer 线程负责取任务
```

如果 consumer 一直循环检查队列是否为空：

```c
while (queue_empty()) {
    // 什么也不做，继续检查
}
```

这叫**忙等 (busy waiting)**。它会浪费 CPU，因为线程没有真正睡眠，只是在反复空转。

条件变量的作用是：

```text
队列为空 -> consumer 睡眠
producer 放入任务 -> 通知 consumer 醒来
consumer 被唤醒 -> 重新检查条件 -> 取任务
```

---

## 2. pthread_cond 基本 API

```c
#include <pthread.h>

int pthread_cond_init(pthread_cond_t *cond, const pthread_condattr_t *attr);
int pthread_cond_wait(pthread_cond_t *cond, pthread_mutex_t *mutex);
int pthread_cond_signal(pthread_cond_t *cond);
int pthread_cond_broadcast(pthread_cond_t *cond);
int pthread_cond_destroy(pthread_cond_t *cond);
```

| 函数 | 作用 |
|---|---|
| `pthread_cond_init` | 初始化条件变量 |
| `pthread_cond_wait` | 释放互斥锁并让线程睡眠，醒来后重新加锁 |
| `pthread_cond_signal` | 唤醒一个等待线程 |
| `pthread_cond_broadcast` | 唤醒所有等待线程 |
| `pthread_cond_destroy` | 销毁条件变量 |

最关键的是 `pthread_cond_wait`：它会**原子地释放 mutex 并睡眠**，被唤醒后又会先重新获得 mutex，再继续往下执行。

---

## 3. 标准使用模式

条件变量必须和互斥量一起使用：

```c
pthread_mutex_lock(&mutex);

while (condition_not_ready) {
    pthread_cond_wait(&cond, &mutex);
}

// 条件满足，访问共享数据

pthread_mutex_unlock(&mutex);
```

为什么是 `while` 而不是 `if`？

- 线程可能被**虚假唤醒 (spurious wakeup)**；
- 多个线程被唤醒后，条件可能已经被其他线程消耗；
- `while` 会重新检查条件，保证逻辑正确。

## 4. 生产者消费者示例

下面是一个固定大小队列的简化版本。它体现了三个核心动作：队列满时生产者等待，队列空时消费者等待，状态变化时互相通知。

```c
#include <pthread.h>
#include <stdio.h>
#include <unistd.h>

#define CAP 4

int queue[CAP];
int head = 0, tail = 0, count = 0;

pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t not_empty = PTHREAD_COND_INITIALIZER;
pthread_cond_t not_full = PTHREAD_COND_INITIALIZER;

void push(int value) {
    pthread_mutex_lock(&mutex);

    while (count == CAP) {
        pthread_cond_wait(&not_full, &mutex);
    }

    queue[tail] = value;
    tail = (tail + 1) % CAP;
    count++;

    pthread_cond_signal(&not_empty);
    pthread_mutex_unlock(&mutex);
}

int pop(void) {
    pthread_mutex_lock(&mutex);

    while (count == 0) {
        pthread_cond_wait(&not_empty, &mutex);
    }

    int value = queue[head];
    head = (head + 1) % CAP;
    count--;

    pthread_cond_signal(&not_full);
    pthread_mutex_unlock(&mutex);
    return value;
}

void *producer(void *arg) {
    for (int i = 0; i < 10; i++) {
        push(i);
        printf("produce %d\n", i);
    }
    return NULL;
}

void *consumer(void *arg) {
    for (int i = 0; i < 10; i++) {
        int value = pop();
        printf("consume %d\n", value);
    }
    return NULL;
}

int main(void) {
    pthread_t p, c;

    pthread_create(&p, NULL, producer, NULL);
    pthread_create(&c, NULL, consumer, NULL);

    pthread_join(p, NULL);
    pthread_join(c, NULL);
    return 0;
}
```

编译：

```bash
gcc cond_queue.c -o cond_queue -lpthread
```

## 5. 线程池解决什么问题

最朴素的服务器写法是：每来一个请求，就创建一个线程处理它。

```text
请求到来 -> pthread_create -> 处理请求 -> 线程退出
```

这个模型能跑，但不适合高并发：

| 问题 | 说明 |
|---|---|
| 创建销毁开销大 | `pthread_create` 和线程退出都需要内核参与，不适合每个请求都做一次 |
| 并发不可控 | 请求突然变多时，线程数量可能暴涨，导致上下文切换和内存压力 |
| 缺少排队边界 | 没有任务队列时，系统很难表达“忙不过来” |
| 退出流程混乱 | 临时线程分散存在，服务关闭时不好统一回收 |

线程池的做法是：**提前创建一批 worker 线程，让它们长期存在；请求来了以后，只把任务放进队列，worker 被唤醒后自己取任务执行**。

```text
main / I/O thread
-> push task into queue
-> signal condition variable
-> worker wakes up
-> pop task
-> unlock
-> execute task
```

这里最重要的分工是：

- `mutex` 保护任务队列；
- `cond` 负责“队列空时睡眠，有任务时唤醒”；
- `worker` 负责长期循环取任务；
- `stop` 标志负责关闭线程池。

## 6. 线程池结构图

![[图片/3.Linux/12. 线程/12.7 条件变量与线程池-01.svg]]

这张图里有两个关键路径：

- **提交任务路径**：I/O 线程或主线程把任务放入队列，然后调用 `pthread_cond_signal` 唤醒 worker。
- **执行任务路径**：worker 被唤醒后先抢锁，检查队列，取出任务，释放锁，然后执行任务。

注意：**耗时任务必须在释放锁之后执行**。锁只保护队列，不应该保护真正的业务处理。

## 7. 线程池的核心组件

一个最小线程池通常需要这些成员：

```c
typedef void (*task_fn)(void *);

typedef struct Task {
    task_fn func;
    void *arg;
    struct Task *next;
} Task;

typedef struct ThreadPool {
    pthread_t *threads;
    int thread_count;

    Task *head;
    Task *tail;
    int queue_size;
    int queue_capacity;

    int stop;

    pthread_mutex_t mutex;
    pthread_cond_t not_empty;
    pthread_cond_t not_full;
} ThreadPool;
```

各字段的含义：

| 字段 | 作用 |
|---|---|
| `threads` | 保存 worker 线程 ID，方便后续 `join` |
| `head` / `tail` | 任务队列，通常是链表或环形队列 |
| `queue_size` | 当前排队任务数量 |
| `queue_capacity` | 队列上限，用来形成背压 |
| `stop` | 关闭标志，告诉 worker 不要无限等待 |
| `mutex` | 保护队列和 `stop` |
| `not_empty` | 队列从空变成非空时唤醒 worker |
| `not_full` | 有界队列从满变成未满时唤醒提交者 |

> [!important]
> 条件变量本身不保存“条件是否成立”。真正的条件是 `queue_size > 0`、`queue_size < queue_capacity`、`stop == 1` 这些共享状态。条件变量只是让线程在条件不满足时睡眠，并在状态变化时被唤醒。

## 8. 提交任务：生产者逻辑

提交任务的一方通常是主线程、网络 I/O 线程或定时器线程。它的动作是：

```text
加锁
如果队列满，等待 not_full
如果线程池已经 stop，拒绝任务
把任务插入队列
通知 not_empty
解锁
```

简化代码如下：

```c
int thread_pool_add(ThreadPool *pool, task_fn func, void *arg) {
    Task *task = malloc(sizeof(Task));
    if (task == NULL) {
        return -1;
    }

    task->func = func;
    task->arg = arg;
    task->next = NULL;

    pthread_mutex_lock(&pool->mutex);

    while (!pool->stop && pool->queue_size == pool->queue_capacity) {
        pthread_cond_wait(&pool->not_full, &pool->mutex);
    }

    if (pool->stop) {
        pthread_mutex_unlock(&pool->mutex);
        free(task);
        return -1;
    }

    if (pool->tail == NULL) {
        pool->head = task;
        pool->tail = task;
    } else {
        pool->tail->next = task;
        pool->tail = task;
    }
    pool->queue_size++;

    pthread_cond_signal(&pool->not_empty);
    pthread_mutex_unlock(&pool->mutex);
    return 0;
}
```

这里有三个细节：

- 队列满时用 `while` 等待，因为醒来后队列可能仍然是满的；
- 插入任务后通知 `not_empty`，因为可能有 worker 正在睡眠；
- 如果 `stop` 已经置位，就不要再接受新任务。

## 9. worker 循环：消费者逻辑

worker 线程不是执行一次任务就退出，而是长期循环：

```text
while true:
    加锁
    while 队列为空 且 没有 stop:
        等待 not_empty
    如果 stop 且 队列为空:
        解锁并退出
    取出一个任务
    通知 not_full
    解锁
    执行任务
```

简化代码如下：

```c
void *worker_entry(void *arg) {
    ThreadPool *pool = (ThreadPool *)arg;

    while (1) {
        pthread_mutex_lock(&pool->mutex);

        while (!pool->stop && pool->queue_size == 0) {
            pthread_cond_wait(&pool->not_empty, &pool->mutex);
        }

        if (pool->stop && pool->queue_size == 0) {
            pthread_mutex_unlock(&pool->mutex);
            break;
        }

        Task *task = pool->head;
        pool->head = task->next;
        if (pool->head == NULL) {
            pool->tail = NULL;
        }
        pool->queue_size--;

        pthread_cond_signal(&pool->not_full);
        pthread_mutex_unlock(&pool->mutex);

        task->func(task->arg);
        free(task);
    }

    return NULL;
}
```

最关键的一点是：

```c
pthread_mutex_unlock(&pool->mutex);
task->func(task->arg);
```

取出任务后要先解锁，再执行任务。否则一个 worker 执行慢任务时会一直占着队列锁，其他 worker 无法取任务，提交者也无法继续放任务，线程池就退化成了单线程阻塞模型。

## 10. 关闭线程池：stop + broadcast

线程池关闭时不能只把主线程退出。否则 worker 可能还睡在：

```c
pthread_cond_wait(&pool->not_empty, &pool->mutex);
```

正确关闭流程通常是：

```text
加锁
stop = 1
broadcast 唤醒所有 worker
也 broadcast 唤醒可能卡在队列满的提交者
解锁
join 所有 worker
释放队列残留任务
销毁 mutex / cond
```

简化代码：

```c
void thread_pool_destroy(ThreadPool *pool) {
    pthread_mutex_lock(&pool->mutex);
    pool->stop = 1;
    pthread_cond_broadcast(&pool->not_empty);
    pthread_cond_broadcast(&pool->not_full);
    pthread_mutex_unlock(&pool->mutex);

    for (int i = 0; i < pool->thread_count; ++i) {
        pthread_join(pool->threads[i], NULL);
    }

    pthread_mutex_destroy(&pool->mutex);
    pthread_cond_destroy(&pool->not_empty);
    pthread_cond_destroy(&pool->not_full);
}
```

为什么关闭时用 `broadcast` 而不是 `signal`？

- `signal` 只唤醒一个 worker，其他 worker 可能继续睡眠，导致 `join` 卡住；
- `broadcast` 能让所有等待线程醒来，重新检查 `stop`，然后自行退出。

## 11. 线程池参数怎么设计

线程池不是只要能跑就行，工程上最重要的是控制边界。

| 参数 | 常见设计 | 影响 |
|---|---|---|
| worker 数量 | CPU 密集任务接近 CPU 核数，I/O 密集任务可以更多 | 影响并发度和上下文切换 |
| 队列容量 | 固定上限 | 决定排队延迟和内存上限 |
| 队列满策略 | 阻塞、拒绝、丢弃、降级 | 决定系统过载时怎么表现 |
| 关闭策略 | 等待队列清空或立即停止 | 决定退出时是否丢任务 |
| 任务抽象 | 函数指针 + `void*`，或 C++ 函数对象 | 决定封装灵活度 |

简单记：

```text
worker 数量控制并发
queue_capacity 控制排队
stop 控制退出
cond 控制睡眠和唤醒
```

## 12. 和 epoll 服务器的关系

[[13.4 epoll模型|epoll]] 解决的是“很多 socket fd 谁就绪了”；线程池解决的是“就绪后的慢任务交给谁做”。

```text
epoll_wait()
-> 发现 fd 可读
-> 读取请求并解析出 task
-> push 到线程池队列
-> worker 处理数据库、文件、CPU 计算或业务逻辑
-> 结果再交回 I/O 线程或响应队列
```

如果在 I/O 线程里直接执行慢任务，会出现两个问题：

- 其他 fd 的事件无法及时处理；
- 延迟抖动变大，吞吐也不稳定。

所以真实服务经常把 I/O loop 和 worker pool 分开。I/O 线程负责“快进快出”，worker 线程负责耗时业务。

## 13. 和 CUDA / LLM 推理的关系

在 [[AI Agent Native AI Infra GPU Performance Engineer 培养方案]] 这条路线里，条件变量和线程池对应的是 **host-side 推理调度**：

```text
请求进入
-> 网络线程读请求
-> CPU worker 做 tokenizer / 参数校验 / batch 拼装
-> GPU 调度线程发起 CUDA stream 或推理引擎 step
-> metrics 线程记录 TTFT / TPOT / TPS
```

几个工程判断：

| 判断点 | 为什么重要 |
|---|---|
| 队列要不要有上限 | 无界队列会把延迟和显存压力藏起来，最终表现为 OOM 或 TPOT 抖动 |
| worker 数量怎么设 | 太少会让 CPU 预处理拖慢 GPU，太多会造成上下文切换和锁竞争 |
| 是否在持锁时调用 GPU 同步 | 持锁等待 `cudaDeviceSynchronize()` 会把其他请求一起卡住 |
| 是否区分 prefill / decode 任务 | LLM 推理中两类任务耗时、显存和调度策略不同 |
| 指标从哪里打点 | TTFT 包含排队、预处理、prefill；TPOT 更关注 decode 稳定性 |

> [!important] 工程直觉
> CUDA kernel 慢不一定真是 kernel 慢。推理服务里一次请求的延迟可能被 CPU 队列、锁竞争、batch 调度、host-device 拷贝和 GPU kernel 共同决定。Linux 线程知识帮助你判断瓶颈到底在 host-side 还是 device-side。

## 14. 常见错误

| 错误 | 后果 | 修正 |
|---|---|---|
| 用 `if` 包住 `pthread_cond_wait` | 虚假唤醒后可能读空队列 | 用 `while` 重查条件 |
| 修改队列后忘记 `signal` | worker 永远睡眠 | 状态变化后通知 |
| 持锁执行耗时任务 | 其他线程无法访问队列 | 只在取任务 / 放任务时持锁 |
| 线程池没有 `stop` 标志 | 程序退出时 worker 卡住 | 设置 `stop` 并 `broadcast` |
| 关闭时只 `signal` 一个线程 | 其他 worker 仍然睡眠，`join` 卡住 | 使用 `pthread_cond_broadcast` |
| 队列无上限 | 内存和延迟不可控 | 使用有界队列或信号量做并发限制 |
| 任务对象生命周期不清楚 | worker 访问已释放内存 | 明确谁分配、谁执行、谁释放 |

---

## 15. 关键要点

1. **条件变量解决等待问题**：没有任务时睡眠，有任务时被唤醒。
2. **必须配合互斥量使用**：条件检查和队列操作都要在锁保护下完成。
3. **等待条件用 while**：防止虚假唤醒和条件被其他线程抢先消耗。
4. **线程池控制并发度**：复用 worker，避免为每个请求创建线程。
5. **任务执行不要持锁**：锁只保护任务队列，不保护真正的耗时业务。
6. **关闭要靠 stop + broadcast**：否则 worker 可能永远睡在条件变量上。
7. **推理服务中的价值**：帮助理解请求队列、CPU worker、GPU 调度、背压和 TTFT / TPOT 抖动。
