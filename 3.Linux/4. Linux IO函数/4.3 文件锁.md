两个进程同时往同一个日志文件追加，各自 `write()` 一条 200 字节的记录，最后文件里可能出现半条 A 接着半条 B。`write()` 对普通文件在同一个 `open` 描述上是原子的，但跨进程的「读出来、改一改、写回去」这三步之间，内核不会替你挡住任何人。

**文件锁**让内核记住「哪个进程正占着这个文件的哪一段」，这样第二个进程动手之前，要么被挡住，要么能查出是谁在占。它解决的是**跨进程**的协调，同一进程内的线程同步该用互斥量（一次系统调用比一次无竞争的 futex 贵两个数量级）。

Linux 上有三套接口：`flock()`、`fcntl()` 的 POSIX 记录锁、`fcntl()` 的 OFD 锁。三者的差别不在函数签名，而在**锁被挂到了哪个内核对象上**。

---

## 锁挂在哪个内核对象上

`fork` 之后子进程还持不持锁、`close` 掉一个不相干的 fd 会不会丢锁、两个线程能不能互斥，这些规则单独背很容易串。它们其实都是同一张对象图的推论。

![[图片/SVG/3_4_4_3_1.svg|1307]]

三句话概括上图：

- `flock()` 的锁挂在 **open file description**（内核里的 `struct file`）上。一次 `open()` 造一个，`fork()` 和 `dup()` 只是多一个 fd 指向它。
- POSIX 记录锁挂在 **(进程, inode)** 这个二元组上。它既不认 fd，也不认 open file description，只认「哪个 pid 在这个 inode 上占了哪些字节」。
- OFD 锁挂回 open file description，但保留了记录锁的字节区间能力。

由此推出的两条最容易踩的：

1. **POSIX 记录锁不被 `fork()` 继承。** 父进程加了锁，子进程一把都没有。跨 `execve()` 倒是保留。
2. **关闭指向该文件的任意一个 fd，本进程在该 inode 上的记录锁全部释放。** 哪怕那个 fd 是别处 `open` 出来的、跟你的锁毫无关系。

---

## 冲突怎么判：锁类型 × 字节区间

只有**区间重叠**、并且**至少一方是写锁**，请求才会被挡住。两条都满足才冲突，缺一条都放行。

![[图片/SVG/3_4_4_3_2.svg|1307]]

图 C 的四条请求里，进程 3 只在 `[150, 200)` 这 50 字节上撞到进程 1，整把锁就申请不下来。记录锁没有「锁到一半」这种中间状态：内核要么把你请求的整个区间都授予你，要么一个字节都不给。

`flock()` 是这套规则的退化情形，它永远只锁 `[0, EOF)`，所以任意两个写者必然重叠、必然互斥。

## flock()：整文件锁

```c
#include <sys/file.h>

int flock(int fd, int operation);
```

- **fd**：要锁定的[[4.1 打开、读取、写入、关闭#文件描述符（File Descriptor）|文件描述符]]。如果文件是 `fopen()` 打开的，用 [[6.2 高级文件操作函数#fileno() - 获取文件描述符|fileno()]] 取出 fd。`flock()` 不关心 fd 的打开模式，只读打开的 fd 一样能加排他锁。
- **operation**：

| 值 | 含义 |
|----|------|
| `LOCK_SH` | 共享锁。多个 open file description 可以同时持有 |
| `LOCK_EX` | 排他锁。同一时刻只有一个 open file description 能持有 |
| `LOCK_UN` | 释放 |
| `LOCK_NB` | 与前三者按位或。拿不到锁时立即返回 -1 并置 `errno = EWOULDBLOCK`，而不是睡下去 |

返回 0 表示成功。失败返回 -1，非阻塞冲突是 `EWOULDBLOCK`，被信号打断是 `EINTR`。

### 单实例守护进程

`flock()` 最常见的用途不是保护数据，而是保证一份程序不被同时启动两次。这个场景用 `LOCK_EX | LOCK_NB` 正好：

```c
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <errno.h>
#include <sys/file.h>

int main(void) {
    // 注意不能用 O_TRUNC：万一另一个实例正在跑，我们会把它的 pid 文件清空
    int fd = open("/var/run/myd.pid", O_RDWR | O_CREAT, 0644);
    if (fd == -1) { perror("open"); return 1; }

    // 非阻塞地抢排他锁。抢到 = 没有别的实例在跑
    if (flock(fd, LOCK_EX | LOCK_NB) == -1) {
        if (errno == EWOULDBLOCK) {
            fprintf(stderr, "已有一个实例在运行\n");
            return 1;
        }
        perror("flock");
        return 1;
    }

    // 抢到锁之后才截断并写入自己的 pid
    ftruncate(fd, 0);
    dprintf(fd, "%ld\n", (long)getpid());

    // 这里刻意不 close(fd)：整个生命周期都要握着这把锁
    // 进程退出时内核自动关 fd、自动释放锁，崩溃也一样
    // ... 主循环 ...
    return 0;
}
```

三个决定值得说清楚：

**为什么用 `LOCK_NB` 而不是阻塞版。** 启动第二份实例时，我们要的是「立刻报错退出」，不是「排队等第一份退出后接上」。阻塞版会让第二份进程一直挂在那儿，看起来像卡死。

**为什么截断放在加锁之后。** `open` 时如果带 `O_TRUNC`，文件在拿到锁之前就被清空了。此时真正在运行的实例的 pid 已经没了，而我们又抢锁失败退出，结果是把好好的状态搞坏。加锁成功意味着独占，之后 `ftruncate` 才安全。

**为什么故意不 `close`。** `flock` 的锁在最后一个引用该 open file description 的 fd 关闭时释放。进程正常退出、被 `kill`、段错误，内核都会关掉它的所有 fd，锁自动没。这比在信号处理函数里手动解锁可靠得多。

### 转换锁类型不是原子的

`flock(fd, LOCK_SH)` 之后再 `flock(fd, LOCK_EX)`，内核的做法是**先撤掉旧锁，再申请新锁**。这两步之间，别的进程排队的请求可能被满足。所以升级可能阻塞，加了 `LOCK_NB` 时可能直接失败，而且**失败之后原来那把共享锁也已经没了**。需要升级语义时，别指望这条路径。

## fcntl()：按字节区间上锁

```c
#include <fcntl.h>

int fcntl(int fd, int cmd, struct flock *lock);
```

| cmd | 行为 |
|-----|------|
| `F_SETLK` | 加锁或解锁，非阻塞。冲突时返回 -1 |
| `F_SETLKW` | 加锁，阻塞等待（W = Wait）。可被信号打断，返回 `EINTR` |
| `F_GETLK` | 只查询不加锁。若有冲突锁，把对方的信息填回 `lock` |

```c
struct flock {
    short l_type;    // F_RDLCK 读锁 / F_WRLCK 写锁 / F_UNLCK 解锁
    short l_whence;  // 区间起点的基准：SEEK_SET / SEEK_CUR / SEEK_END
    off_t l_start;   // 相对 l_whence 的偏移
    off_t l_len;     // 区间长度，0 表示「一直到文件末尾，含以后追加的部分」
    pid_t l_pid;     // 仅 F_GETLK 返回时有效：谁挡着你
};
```

与 `flock()` 不同，**记录锁检查 fd 的打开模式**：加 `F_RDLCK` 要求 fd 可读，加 `F_WRLCK` 要求 fd 可写，两种都要就 `O_RDWR` 打开。这是 `EBADF` 最常见的来源。

### 封一层再用

裸写 `struct flock` 每次五个字段，很容易漏填或者带进垃圾值。实践里都封一个小函数：

```c
#include <fcntl.h>
#include <errno.h>

// type: F_RDLCK / F_WRLCK / F_UNLCK
// len : 0 表示从 start 一直锁到文件末尾
// wait: 非 0 则阻塞等待，0 则拿不到就立即返回 -1
static int lock_region(int fd, int type, off_t start, off_t len, int wait) {
    struct flock fl = {0};      // 全零初始化，l_pid 之类的字段不带垃圾值进内核
    fl.l_type   = type;
    fl.l_whence = SEEK_SET;     // 固定用绝对偏移，见下文
    fl.l_start  = start;
    fl.l_len    = len;
    return fcntl(fd, wait ? F_SETLKW : F_SETLK, &fl);
}
```

**为什么固定 `SEEK_SET`。** `SEEK_CUR` 以当前文件偏移为基准，而文件偏移是 open file description 上的共享状态，同进程里任何一个线程做一次 `read()` 都会把它挪走。等你算好 `l_start` 再调 `fcntl()`，锁住的可能已经是另一段字节，而且不会报错。锁的区间必须是绝对的。

**为什么 `= {0}`。** `struct flock` 在不同平台上可能有 `l_pid` 之外的填充或扩展字段。局部变量不初始化就是栈上的残留数据，交给内核是自找麻烦。

调用方这样用：

```c
int fd = open("records.db", O_RDWR);

// 锁住第 2 条定长记录：偏移 100 起、长 100 字节
if (lock_region(fd, F_WRLCK, 100, 100, /*wait=*/1) == -1) {
    perror("lock");            // 阻塞版失败通常是 EINTR 或 EDEADLK
    return 1;
}

// ... 读改写这 100 字节，此间别的进程锁 [0,100) 或 [200,300) 都不受影响 ...

lock_region(fd, F_UNLCK, 100, 100, 0);   // 解锁用 F_SETLK 即可，不会阻塞
```

非阻塞版失败时的 errno 要注意：POSIX 允许 `F_SETLK` 在冲突时返回 `EACCES` **或** `EAGAIN`，Linux 上是 `EAGAIN`，但可移植的代码两个都要判：

```c
if (lock_region(fd, F_WRLCK, 100, 100, 0) == -1) {
    if (errno == EACCES || errno == EAGAIN) {
        // 有人占着，走降级路径
    } else {
        perror("fcntl");       // 真出错了
    }
}
```

### F_GETLK 用来诊断，不能用来「先查再锁」

```c
struct flock fl = {0};
fl.l_type   = F_WRLCK;         // 填上「我想加什么锁」，内核据此判断有无冲突
fl.l_whence = SEEK_SET;
fl.l_start  = 100;
fl.l_len    = 100;

if (fcntl(fd, F_GETLK, &fl) == -1) { perror("fcntl"); return 1; }

if (fl.l_type == F_UNLCK) {
    printf("这段没人占\n");           // 内核把 l_type 改成 F_UNLCK 表示无冲突
} else {
    printf("被 pid=%d 的 %s 挡着\n",
           fl.l_pid, fl.l_type == F_RDLCK ? "读锁" : "写锁");
}
```

注意 `fl` 是**传入传出**参数：进去时 `l_type` 是你想加的锁，出来时如果无冲突就被改写成 `F_UNLCK`，有冲突则整个结构体被替换成对方那把锁的描述。所以这个变量不能复用去做后续的 `F_SETLK`。

更要紧的是，`F_GETLK` 返回的是**调用那一瞬间**的状态。返回之后到你 `F_SETLK` 之前，对方可能已经解锁，也可能又冒出第三个进程。想加锁就直接 `F_SETLK`，让内核在一次系统调用里完成判断和加锁；`F_GETLK` 只适合排查「到底是谁卡住了」。

### 区间的合并、拆分与解锁

内核维护的是区间集合，不是「加锁计数」。同一进程在 `[0, 300)` 加了写锁，再在 `[100, 200)` 加读锁，结果是三段：`[0,100)` 写、`[100,200)` 读、`[200,300)` 写。解锁同理，`F_UNLCK` 一段中间区域会把原来那把锁劈成两半。

这也意味着记录锁**不可重入**：同一进程重复加锁不会累积，最后一次覆盖前面的；解一次就全没了。

## OFD 锁：修掉记录锁的两个坑

POSIX 记录锁那两条「不被 `fork` 继承」和「关任一 fd 就全丢」，在写库、写多线程程序时是实打实的地雷。Linux 3.15 加了 **OFD 锁**（open file description lock），把锁挂回 open file description，同时保留字节区间。

```c
#define _GNU_SOURCE      // 必须在所有 #include 之前，否则 glibc 不导出 F_OFD_* 常量
#include <fcntl.h>

struct flock fl = {0};
fl.l_type   = F_WRLCK;
fl.l_whence = SEEK_SET;
fl.l_start  = 0;
fl.l_len    = 100;
fl.l_pid    = 0;         // OFD 锁要求这个字段为 0，非 0 直接 EINVAL

if (fcntl(fd, F_OFD_SETLKW, &fl) == -1) { perror("F_OFD_SETLKW"); }
```

命令名把 `F_` 后面加上 `OFD_`：`F_OFD_SETLK`、`F_OFD_SETLKW`、`F_OFD_GETLK`，`struct flock` 的用法完全一样。

和 POSIX 记录锁的三点差别：

- **同一进程的两个 open file description 之间会冲突**。这正是它能给线程用的原因：每个线程各自 `open()` 一次，就有了各自的锁主体。POSIX 记录锁在这个场景下退化成无操作。
- **`fork()` 出来的子进程共享这把锁**，因为它们的 fd 指向同一个 open file description。
- **`F_OFD_SETLKW` 不做死锁检测**。POSIX 记录锁的阻塞版会检测环并返回 `EDEADLK`，OFD 锁不会，环形等待会一直挂着。

代价是不可移植：`F_OFD_*` 是 Linux 专有的，macOS 和 BSD 上没有。

## 建议性锁与强制性锁

上面所有的锁都是**建议性的**：内核只在你调用锁函数时去查那张表，`read()`/`write()` 路径根本不看。一个从不调用 `flock`/`fcntl` 的进程照样能把你锁住的字节改掉。

![[图片/SVG/3_4_4_3_3.svg|1307]]

**强制性锁**（`-o mand` 挂载 + set-GID 位开、group-execute 位关）曾经能让内核在 I/O 路径上强制检查，但它的实现一直有竞态。Linux 4.5 起被标为可选特性，**5.15 起实现已被完全删除**，`-o mand` 不再生效。写新代码时不必再考虑这条路。

结论就是：建议性锁的正确性依赖「所有访问这个文件的程序都遵守同一套约定」。跨语言、跨团队的场景里，把这个约定写进文档，比写进代码更重要。

图 B 那个 bug 值得单独记住：你在 `fd3` 上加了记录锁，随后调用了一个内部会 `open` 再 `close` 同一文件的工具函数，你的锁就没了，而且没有任何返回值提示你。修法只有两条，换成 OFD 锁，或者把该文件的 `open`/`close` 收进一个模块里、其余代码只能拿到句柄。

## 死锁

两个进程交叉持锁就会环形等待：

```
进程 A 持有 file1 的锁，去申请 file2 的锁
进程 B 持有 file2 的锁，去申请 file1 的锁
```

`F_SETLKW` 的 POSIX 记录锁在这种情况下会被内核检出，返回 `EDEADLK`。但这只覆盖能被内核看见的环，混进管道、套接字、用户态锁的复合环它认不出来。`flock()` 和 `F_OFD_SETLKW` 完全不做检测。

可靠的做法还是老三样：

- 全局约定一个加锁顺序（比如按 inode 号从小到大），所有代码遵守
- 用非阻塞版试探，失败就把已持有的锁全放掉、退避一小段随机时间再重来
- 需要超时就用 `alarm()` 或 `setitimer()` 让 `SIGALRM` 打断 `F_SETLKW`，它会返回 `EINTR`（信号处理函数不能设 `SA_RESTART`，否则会自动重启系统调用）

## 跨 NFS 的行为

`fcntl()` 记录锁在 NFS 上由服务端的锁管理器实现，跨机器有效。

`flock()` 从 Linux 2.6.12 起，在 NFS 挂载上被**模拟**成「锁整个文件的字节区间锁」。两个后果：一是 `flock()` 和 `fcntl()` 的锁在 NFS 上会互相冲突（本地文件系统上它们是两套独立的表，互不干扰）；二是要加排他锁，文件必须以可写方式打开，这和本地的行为不一样。挂载时加 `local_lock=flock` 之类的选项又会把它退回成纯客户端本地锁，等于跨机器失效。

需要跨 NFS 协调时，用 `fcntl()`。

## 看当前有哪些锁

`/proc/locks` 列出内核里所有的文件锁：

```
1: POSIX  ADVISORY  WRITE 3376 08:02:1048577 0 EOF
2: FLOCK  ADVISORY  WRITE 3376 08:02:1048577 0 EOF
3: OFDLCK ADVISORY  READ  -1   08:02:1048577 0 99
```

列的含义依次是：序号、锁的种类、建议性还是强制性、读锁还是写锁、持锁进程的 pid、`主设备号:次设备号:inode号`、区间起点、区间终点。OFD 锁的 pid 列固定是 `-1`，因为它不属于任何单个进程。

`util-linux` 里的 `lslocks` 把 inode 号翻译回路径，排查时更好用。定位「谁卡住了我」的顺序通常是：`lslocks` 找到 pid，`ls -l /proc/<pid>/fd` 看它开着哪些文件，`cat /proc/<pid>/stack` 或 `gdb` 看它卡在哪。

## 关键要点

- 三套接口的差别在**锁挂到哪个内核对象**上：`flock` 挂 open file description，POSIX 记录锁挂 (进程, inode)，OFD 锁挂 open file description 且带字节区间。`fork`/`dup`/`close`/多线程的所有行为都从这一条推出来。
- 冲突判定要两个条件同时成立：**区间重叠**且**至少一方是写锁**。
- POSIX 记录锁两颗地雷：子进程不继承；关闭指向该文件的任意一个 fd 会清掉本进程在该 inode 上的全部锁。
- Linux 3.15 起，需要区间粒度时优先 `F_OFD_SETLK`。只需要「整个文件一个写者」就用 `flock`，写起来最短。
- 强制性锁在 Linux 5.15 已被删除，只剩建议性锁；正确性靠全体参与者遵守约定。
- `F_GETLK` 只用来排查是谁挡着，它的结果返回即过期，不能拿来做「先查再锁」。
