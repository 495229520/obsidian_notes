# 3.6 常见 errno 错误码速查

> `errno` 是 Linux 系统调用报告异常的核心机制。它声明在 `<cerrno>` / `<errno.h>` 中，底层是一个**线程局部变量（Thread-Local Variable）**，每个线程独立维护一份，多线程并发读写完全线程安全。

---

## 1. 核心使用规则与调试手法

### 1.1 黄金准则

1. **只有系统调用返回值明确指示出错（如返回 `-1` 或 `NULL`）时，`errno` 才有意义**：
   系统调用成功时**绝不会主动把 `errno` 清零**。如果一个系统调用执行成功，此时去读 `errno`，读到的只是以前某个失败调用遗留的历史脏值。
2. **需要使用时立刻保存**：
   后续调用其他库函数甚至标准 I/O（比如看起来无害的 `printf`），其内部一旦触发系统调用失败，就会立刻冲掉之前的 `errno`。

### 1.2 打印错误文本的常用方式

```cpp
#include <cerrno>
#include <cstring>
#include <iostream>
#include <unistd.h>

// 方式 1：perror，直接向 stderr 输出带前缀的错误描述
int fd = open("/not_exist_file", O_RDONLY);
if (fd < 0) {
    perror("打开文件失败"); // 输出：打开文件失败: No such file or directory
}

// 方式 2：strerror_r（推荐，线程安全）
char errbuf[256];
strerror_r(errno, errbuf, sizeof(errbuf));
std::cerr << "操作失败: " << errbuf << " (errno=" << errno << ")\n";
```

在 Linux 终端命令行下快速反查错误码：
```bash
# 查看指定 errno 宏或数字的含义
$ errno 11
EAGAIN 11 Resource temporarily unavailable

$ errno ECONNREFUSED
ECONNREFUSED 111 Connection refused
```

## 2. 网络与 Socket 核心错误码（高频重点）

| 错误码（宏） | 典型触发场景 | 内核真实意图 | 应用程序正确应对策略 |
| :--- | :--- | :--- | :--- |
| **`EINPROGRESS`** | 非阻塞 [[8.12 非阻塞connect与健壮收发\|connect()]] | 三次握手已发出 SYN，网络往返中，尚未完成 | **绝非真错误**。将 fd 挂载至 epoll 监听可写事件（`EPOLLOUT`），触发后再用 `SO_ERROR` 确认结果 |
| **`EAGAIN`** /<br>**`EWOULDBLOCK`** | 非阻塞 `recv`、`send`、`accept` | 读缓冲区空、写缓冲区满或全连接队列无新连接，无法继续推进 | **绝非真错误**。立刻退出当前读写循环，交还 epoll 等待事件驱动，**严禁原地死循环忙等** |
| **`ECONNRESET`** | `read` / `recv` 时突然返回 `-1` | 对端异常崩溃直接退出，或对端进程强制发出了 **RST 报文** 斩断连接 | 连接已死。立即释放该连接占用的资源，关闭 fd（`close(fd)`），注销 epoll 事件 |
| **`EPIPE`** | 对端已关闭读通道后，本端执意调用 `send` / `write` | 管道/连接已破裂（Broken pipe）。内核同时会向当前进程发出 `SIGPIPE` 信号 | 默认会导致进程直接闪退！需设置 `signal(SIGPIPE, SIG_IGN)` 或改用 `send(..., MSG_NOSIGNAL)` |
| **`ECONNREFUSED`** | `connect()` 立即返回失败 | 目标主机存在，但目标端口**没有进程在监听**，或者被本地防火墙直接拒绝 | 检查服务是否挂掉、端口是否配置错误或防火墙安全策略阻断 |
| **`ETIMEDOUT`** | `connect()` 阻塞超时，或 TCP 保活/重传耗尽 | 目标主机不可达、关机、或中间网关直接静默丢弃 SYN，重传多次无响应 | 检查物理网络、路由可达性、安全组放行规则；业务层按需安排延迟重连 |
| **`EADDRINUSE`** | `bind()` 失败 | 端口已被其他进程占用；或本端刚重启，旧连接尚处于 `TIME_WAIT` 状态 | 开启 `SO_REUSEADDR` / `SO_REUSEPORT` 选项；排查是否有残留僵尸进程占用端口 |
| **`EADDRNOTAVAIL`** | 客户端 `connect` 或服务端 `bind` | 绑定的 IP 不是本机网卡真实 IP；或高并发频繁短连接下**客户端本地临时端口被全部耗尽** | 扩容系统临时端口范围（`ip_local_port_range`）或开启 `tcp_tw_reuse` |
| **`ENETUNREACH`** /<br>**`EHOSTUNREACH`** | `connect()` 或 `sendto()` | 本地没有到达目标网络的路由，或路由器回报主机不可达 | 检查系统默认网关配置与本地网络链路连接状态 |
| **`EMSGSIZE`** | UDP `sendto()` | 单个数据报文长度超过了 MTU 限制或套接字发送缓冲区上限 | 缩减 UDP 载荷大小，或在应用层切片分包；改用 TCP 传输大块数据 |
| **`EISCONN`** | 已连接的 socket 上再次调用 `connect()` | 套接字已经处于 Established 状态，不允许重复连接 | 检查客户端状态机逻辑，避免对同一个 fd 重复触发连接操作 |
| **`ENOTCONN`** | 在未连接的 socket 上调用 `getpeername()` 或发数据 | 尚未建立连接，无法提取对端元信息 | 确保连接就绪后再进行对端操作 |

## 3. 系统 I/O、资源与并发错误码

| 错误码（宏） | 典型触发场景 | 内核真实意图 | 应用程序正确应对策略 |
| :--- | :--- | :--- | :--- |
| **`EINTR`** | 慢系统调用（`read`、`epoll_wait` 等）中途被外部信号打断 | 进程收到操作系统信号（如 `SIGCHLD`、`SIGALRM`），内核优先处理信号中断了调用 | **绝非真错误，网络完好**。直接在循环中执行 `continue` 原地重试即可 |
| **`EMFILE`** | `accept()`、`open()`、`socket()` | **当前进程** 打开的文件描述符数量达到了限制上限（`ulimit -n`） | 生产高频事故！见下文高频排障四；排查是否有 fd 泄漏，或提升进程的 `nofile` 限制 |
| **`ENFILE`** | 同上 | **操作系统全局** 的文件描述符总数达到物理上限（`fs.file-max`） | 系统级瓶颈。排查全机所有进程的 fd 占用量，按需调大系统级限制 |
| **`EBADF`** | 任何传 `fd` 的系统调用 | 传入的整数不是合法的有效文件描述符，或者该 fd 已经被 `close()` 过了 | 代码中存在双重关闭（Double Close）、未初始化 fd 或多线程竞态破坏 fd |
| **`EFAULT`** | 传指针给系统调用（如 `read(fd, ptr, len)`） | 用户态指针 `ptr` 指向了非法内存区域（如 `nullptr`、野指针、越界地址） | 致命内存 BUG。检查指针分配、内存边界以及缓冲区合法性 |
| **`EINVAL`** | 各种系统调用（如 `epoll_ctl`、`bind`） | 传给内核的参数逻辑矛盾或不受支持（如长度不对、标志位冲突） | 仔细比对系统调用 man 手册，检查形参范围与结构体大小传递 |
| **`ENOMEM`** | `malloc`、`mmap`、内核创建对象 | 物理内存或虚拟地址空间耗尽，内核分配内存失败 | 检查进程是否存在严重内存泄漏；优化缓冲区分配策略；防范 OOM Killer |
| **`ENOSPC`** | `write()` 本地文件 | 磁盘存储空间已被彻底写满，无法再追加数据 | 业务排查日志滚动清理；监控磁盘容量预警 |

## 4. 权限与文件系统错误码

| 错误码（宏） | 典型触发场景 | 内核真实意图 | 应用程序正确应对策略 |
| :--- | :--- | :--- | :--- |
| **`EACCES`** /<br>**`EPERM`** | 普通用户 `bind` 1~1023 端口，或访问无权文件 | 权限受限。非 root 用户禁止绑定特权端口；文件只读但尝试写入 | 使用普通端口（≥1024）；为程序赋予 `CAP_NET_BIND_SERVICE` 权限或更改文件权限 |
| **`ENOENT`** | `open()`、`connect(AF_UNIX)` | 目标文件、目录或 Unix 域套接字文件路径不存在 | 检查文件绝对路径是否正确，注意相对路径是相对于进程的工作目录（CWD） |
| **`EEXIST`** | `mkdir()`、`open(O_CREAT | O_EXCL)` | 试图创建的文件或目录已经存在 | 按需使用 `O_CREAT` 覆盖模式，或先检查存在性 |
| **`EISDIR`** | 对目录执行 `read()` / `write()` | 传入的目标 fd 是目录，而不是常规可读写数据文件 | 路径逻辑错误，使用目录专用函数 `opendir` / `readdir` |
| **`EBUSY`** | 卸载挂载点、锁定已被占用的设备 | 目标资源当前正在被其他进程锁定或占用中 | 等待占用的句柄释放，或排查谁在占用（`lsof` / `fuser`） |

## 5. 四组高频排障经典对比

### 5.1 `EINTR` vs `EAGAIN`（立即重试 vs 退出交给 epoll）

```cpp
// 在非阻塞事件循环中，两者的处理逻辑截然相反：
if (n < 0) {
    if (errno == EINTR) {
        continue; // 信号打扰，链路完好，立刻重试
    }
    if (errno == EAGAIN || errno == EWOULDBLOCK) {
        break;    // 数据读干，不能重试（否则 100% 忙等烧 CPU），退回等 epoll
    }
    close(fd);    // 真实不可逆错误，关闭连接
}
```

### 5.2 `ECONNRESET` vs `EPIPE`（读时感知 vs 写时感知）

两者本质都是“对端连接断开了”，但感知路径不同：
- **`ECONNRESET`**：本端尝试 `read()`，结果收到对端发来的 RST 报文，读操作直接返回失败。
- **`EPIPE`**：对端已经发了 FIN/RST 关闭，本端未察觉依然调用 `write()` 写入。内核会立刻触发破裂管道异常，**默认投递 `SIGPIPE` 信号杀掉进程**。

### 5.3 `EADDRINUSE` vs `EADDRNOTAVAIL`（端口被占 vs 端口耗尽）

- **`EADDRINUSE`**（Address already in use）：常出现在**服务端 `bind`**。有别的进程正占着端口，或者自身重启时旧连接在 `TIME_WAIT`。
- **`EADDRNOTAVAIL`**（Cannot assign requested address）：常出现在**客户端高并发频繁短连接 `connect`**。本地可用临时端口（默认约 28000 个）全部耗尽，或者试图伪装绑定一个并不属于本机任何网卡的虚拟 IP。

### 5.4 `EMFILE` 在 epoll 水平触发（LT）下的“死循环陷阱”

当服务器文件描述符达到系统上限时，`accept()` 会返回 `-1` 且 `errno == EMFILE`：
1. 因为 fd 已满，`accept` 拿不出连接，已完成三次握手的客户端连接依然滞留在内核全连接队列中；
2. 在 epoll LT 模式下，全连接队列里有未处理的连接，会**无限次持续触发 `EPOLLIN`**；
3. 主线程每次被唤醒，调 `accept` 都返回 `EMFILE`，无法将连接取走，导致 CPU 瞬间 100% 陷入死循环卡死。

> **经典工业级解法（空闲 fd 占位法）**：
> 启动时预先打开一个无用的空闲 fd（如 `int idle_fd = open("/dev/null", O_RDONLY)`）。遇到 `EMFILE` 时，关闭 `idle_fd` 腾出一个名额，立即 `accept` 出这个连接并马上调用 `close` 礼貌断开对端，最后重新把 `idle_fd` 打开占位。
