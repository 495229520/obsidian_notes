## 1. 管道是什么

管道是最基础的[[11.2 进程间通信IPC|进程间通信]]方式：内核里的一块环形缓冲区，一端写、另一端读。它没有名字（匿名管道）或者用一个文件路径当名字（FIFO），但两种情况下数据都不落盘，只在内存里过一遍。

![[图片/3.Linux/11. 进程/3_11_11_3_1.svg|950]]

三个性质决定了它能干什么、不能干什么：

- **单向**。`pipe()` 给的两个 fd，`fd[0]` 只能读，`fd[1]` 只能写。要双向就开两个管道。教材里常说「半双工」，在 Linux 上更准确的说法是单向；POSIX 只要求单向，某些 Unix 上 `pipe` 是双向的，写可移植代码时按单向用。
- **字节流，没有消息边界**。写三次读一次，可能一次就把三次的内容全拿到；写一次读三次也可能。接收端要自己判断一条消息到哪里结束。
- **容量有限，满了就把写者拖住**。这不是缺陷，而是 shell 管道能处理 100 GB 文件却不撑爆内存的原因：下游慢，上游自动被反压。

## 2. 匿名管道

### 2.1 pipe()

```c
#include <unistd.h>

int pipe(int fd[2]);
```

| | 说明 |
| --- | --- |
| `fd[0]` | 读端，只能 `read` |
| `fd[1]` | 写端，只能 `write` |
| 返回值 | 成功 0，失败 -1 |

匿名管道没有名字，第三个进程无从找到它。它靠的是 [[11.1 进程简介|fork()]] 会复制文件描述符这一点：`pipe()` 在前、`fork()` 在后，父子手里就有了指向同一个管道的 fd。

![[图片/3.Linux/11. 进程/3_11_11_3_2.svg|1307]]

### 2.2 引用计数决定了一切

管道用错，八成错在没关掉用不到的那一端。

![[图片/3.Linux/11. 进程/3_11_11_3_3.svg|1307]]

内核为管道的读端和写端各维护一个引用计数，数的是**有多少个 fd 指着它**，不管这些 fd 在谁手里。由此得到两条最关键的规则：

- **写端引用计数归零时，`read()` 返回 0**。这是管道版本的 EOF。只要还有任何一个进程握着写端（哪怕它自己就是读数据的那个进程），`read()` 就会一直睡下去。
- **读端引用计数归零后再 `write()`，内核给写者发 `SIGPIPE`**。它的默认动作是终止进程，程序会一声不吭地消失。忽略这个信号之后，`write()` 才改为返回 -1、`errno = EPIPE`。

所以 `fork()` 之后的第一件事必须是：**读的一方关掉写端，写的一方关掉读端**。

### 2.3 代码示例

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>

#define BUF_SIZE 64

int main(void) {
    int fds[2];
    if (pipe(fds) == -1) { perror("pipe"); return 1; }

    pid_t pid = fork();
    if (pid == -1) { perror("fork"); return 1; }

    if (pid == 0) {
        close(fds[0]);                       // 子进程只写，立刻关掉读端
        const char *str = "hello, I am sub process!";
        write(fds[1], str, strlen(str));     // 用 strlen 而不是 sizeof
        close(fds[1]);                       // 写完就关，让父进程能收到 EOF
        _exit(0);
    }

    close(fds[1]);                           // 父进程只读，立刻关掉写端

    char buf[BUF_SIZE];
    ssize_t n;
    while ((n = read(fds[0], buf, sizeof(buf))) > 0) {
        fwrite(buf, 1, (size_t)n, stdout);   // read 不补 '\0'，按返回的字节数用
    }
    if (n == -1) perror("read");
    putchar('\n');

    close(fds[0]);
    wait(NULL);                              // 回收子进程，别留僵尸
    return 0;
}
```

四处值得说清楚：

**为什么两边都要 `close`。** 父进程如果不关 `fds[1]`，写端引用计数就永远至少是 1，子进程退出后 `read()` 依然认为「可能还有人要写」，于是一直睡。这是初学者最常撞的死锁，症状是程序看起来卡住了但 CPU 占用为 0。

**为什么用 `strlen` 而不是 `sizeof`。** `sizeof(str)` 在原来的数组写法里会把结尾的 `'\0'` 也发过去，读端打印时那个 `'\0'` 会混进输出；改成指针之后 `sizeof` 更是直接变成指针宽度 8。要传多少字节就写多少字节，别让编译器替你猜。

**为什么 `read` 要写成循环。** `read()` 返回的字节数可以少于你要的，管道尤其如此：写端分几次写，读端就可能分几次收到。只调一次 `read` 而假定拿全了，是字节流协议里的经典错误。循环到返回 0（EOF）才算读完。

**为什么用 `_exit(0)` 而不是 `return 0`。** 子进程是 `fork` 出来的，它继承了父进程 stdio 缓冲区的副本。`exit()` 会 flush 这些缓冲，把父进程还没输出的内容再打一遍。`_exit()` 直接进内核，不碰用户态缓冲。

### 2.4 双向通信要两个管道

```c
int fds1[2], fds2[2];
pipe(fds1);                    // 子 → 父
pipe(fds2);                    // 父 → 子

pid_t pid = fork();
if (pid == 0) {
    close(fds1[0]); close(fds2[1]);    // 子进程：写 1、读 2
    write(fds1[1], str1, strlen(str1));
    read(fds2[0], buf, sizeof(buf));
} else {
    close(fds1[1]); close(fds2[0]);    // 父进程：读 1、写 2
    read(fds1[0], buf, sizeof(buf));
    write(fds2[1], str2, strlen(str2));
}
```

```text
          fds1[1]              fds1[0]
    子进程 ──────────► 管道1 ────────► 父进程

          fds2[0]              fds2[1]
    子进程 ◄──────────  管道2 ◄──────── 父进程
```

> [!warning] 双向管道很容易互等
> 上面这段之所以不死锁，是因为顺序设计成了「子写 → 父读 → 父写 → 子读」。如果改成两边都先写一大块再读，而那一块超过 64 KB 缓冲区，两个进程就会同时卡在 `write()` 里等对方来读，谁也动不了。
>
> 两个方向都要传大量数据时，别用两个阻塞管道对着来，改用 `O_NONBLOCK` 加 `poll`，或者直接上 `socketpair()`（一个调用给你一对全双工的 fd，还能进 epoll）。

## 3. 命名管道 FIFO

### 3.1 mkfifo()

```c
#include <sys/types.h>
#include <sys/stat.h>

int mkfifo(const char *pathname, mode_t mode);
```

FIFO 在文件系统里有一个真实的 inode，`ls -l` 显示的类型字符是 `p`，任意进程 `open()` 这个路径就能接上，不需要有亲缘关系。但**文件里不存数据**：`ls -l` 看到的大小永远是 0，写进去的字节和匿名管道一样待在内核缓冲区里。

`mode` 是八进制权限，每一位对应文件所有者、同组用户、其他用户：

| 权限 | 二进制 | 八进制 | 含义 |
|------|--------|--------|------|
| `r` | `100` | `4` | 可读 |
| `w` | `010` | `2` | 可写 |
| `x` | `001` | `1` | 可执行 |

`0666` 拆成三段 `rw- rw- rw-`，三类用户都能读写。注意实际权限是 `mode & ~umask`，默认 `umask` 是 `022` 的话，写 `0666` 建出来的是 `0644`，别的用户就写不进去了。需要精确权限就在 `mkfifo` 之后补一句 `chmod()`。

```bash
mkfifo /tmp/myfifo          # 命令行创建
ls -l /tmp/myfifo           # prw-r--r--  ... 0 ... /tmp/myfifo
```

### 3.2 open() 会阻塞，这是特性不是 bug

这是 FIFO 最常见的「怎么卡住了」：

- `open(path, O_RDONLY)` 会**阻塞到有进程以写方式打开它**
- `open(path, O_WRONLY)` 会**阻塞到有进程以读方式打开它**

这个设计是为了让两端汇合：读者先启动也不会读到空，它会一直等到写者出现。加 `O_NONBLOCK` 可以改变行为，但两边不对称：`O_RDONLY | O_NONBLOCK` 立刻成功返回；`O_WRONLY | O_NONBLOCK` 在没有读者时直接失败，`errno = ENXIO`。

### 3.3 代码示例

**写入端 writer.c**：

```c
#include <stdio.h>
#include <string.h>
#include <errno.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/stat.h>

#define FIFO_PATH "/tmp/myfifo"

int main(void) {
    // 已经存在不算错误，别的进程可能先建好了
    if (mkfifo(FIFO_PATH, 0666) == -1 && errno != EEXIST) {
        perror("mkfifo"); return 1;
    }

    // 这一行会停在这里，直到有读者打开同一个 FIFO
    int fd = open(FIFO_PATH, O_WRONLY);
    if (fd == -1) { perror("open"); return 1; }

    char buffer[100];
    printf("输入要发送的消息: ");
    if (!fgets(buffer, sizeof(buffer), stdin)) { close(fd); return 1; }

    // 只写实际长度，不要把 buffer 里剩下的垃圾一起发过去
    if (write(fd, buffer, strlen(buffer)) == -1) perror("write");

    close(fd);
    return 0;
}
```

**读取端 reader.c**：

```c
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>

#define FIFO_PATH "/tmp/myfifo"

int main(void) {
    int fd = open(FIFO_PATH, O_RDONLY);      // 同样会等写者出现
    if (fd == -1) { perror("open"); return 1; }

    char buffer[100];
    ssize_t n;
    while ((n = read(fd, buffer, sizeof(buffer))) > 0) {
        fwrite(buffer, 1, (size_t)n, stdout);
    }
    // n == 0：写者全部关闭了，这才是真正读完
    close(fd);
    return 0;
}
```

两个改动和匿名管道同理：`write` 用 `strlen(buffer)` 而不是 `sizeof(buffer)`，避免把缓冲区里未初始化的 100 字节全发出去；`read` 用循环读到返回 0，而不是假定一次读全。

FIFO 用完之后文件还在，要 `unlink(FIFO_PATH)` 或 `rm` 掉。

## 4. Shell 里的管道符

```bash
ls -la | grep ".txt"
grep -c "error" file.txt        # 比 cat file.txt | grep "error" | wc -l 少两个进程
```

Shell 为每个 `|` 建一个匿名管道，然后 `fork` 出各级命令，用 `dup2()` 把子进程的标准输入或标准输出接到管道上。自己实现一遍就明白了：

```c
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {                       // 复刻 ls -la | wc -l
    int fd[2];
    if (pipe(fd) == -1) { perror("pipe"); return 1; }

    if (fork() == 0) {                 // 左边的 ls
        close(fd[0]);                  // 用不到读端
        dup2(fd[1], STDOUT_FILENO);    // 标准输出改指向管道写端
        close(fd[1]);                  // 关掉多余的那个写端 fd
        execlp("ls", "ls", "-la", NULL);
        perror("execlp ls"); _exit(127);
    }

    if (fork() == 0) {                 // 右边的 wc
        close(fd[1]);
        dup2(fd[0], STDIN_FILENO);     // 标准输入改指向管道读端
        close(fd[0]);
        execlp("wc", "wc", "-l", NULL);
        perror("execlp wc"); _exit(127);
    }

    close(fd[0]);                      // 父进程两端都用不到，两个都得关
    close(fd[1]);
    wait(NULL); wait(NULL);
    return 0;
}
```

**为什么 `dup2` 之后还要 `close(fd[1])`。** `dup2(fd[1], STDOUT_FILENO)` 让描述符 1 也指向管道写端，此时 `ls` 手里有**两个**写端 fd。`ls` 结束时内核会关掉它的所有 fd，这一步没问题；但如果中间还有第三级命令，多留的那个 fd 就会让下游收不到 EOF。养成 `dup2` 之后立刻关掉原 fd 的习惯，永远不会错。

**为什么父进程也要关两端。** 父进程手里的 `fd[1]` 同样计入写端引用数。不关的话 `wc` 会一直等着，`wait()` 也就永远返回不了，整个程序卡死。

**为什么 exec 失败后用 `_exit(127)`。** `exec` 成功就不会返回，能走到下一行说明失败了。这时候必须让这个子进程死掉，否则它会继续执行父进程的后半段代码，`fork` 出更多进程。用 `_exit` 是为了不 flush 继承来的 stdio 缓冲，127 是 shell 约定的「命令找不到」退出码。

## 5. 容量、原子性与反压

| 事实 | 数值 | 怎么查 / 怎么改 |
|------|------|-----------------|
| 管道缓冲区默认容量 | 65536 字节（16 页） | `fcntl(fd, F_SETPIPE_SZ, n)` 调整 |
| 单个管道容量上限 | 1048576 字节 | `/proc/sys/fs/pipe-max-size`，非特权进程受它约束 |
| 原子写的上限 `PIPE_BUF` | 4096 字节 | `<limits.h>` 里的常量 |

**原子性这一条在多写者场景下是硬要求。** 一次 `write()` 的长度不超过 `PIPE_BUF` 时，内核保证这批字节连续落进缓冲区，不会被另一个进程的写插进中间；超过之后就可能被切成几段。多个进程往同一个管道写日志时，把每条日志控制在 4096 字节以内，否则行与行之间会串。

**满了阻塞是反压，不是故障。** `yes | head -1` 之所以不会把内存写爆，就是因为 `head` 读够了就退出，`yes` 随即在 `write()` 里撞上 `SIGPIPE` 结束。整条流水线的速度自动被最慢的一级限住。

## 6. 管道里的 overlap

![[图片/3.Linux/11. 进程/11.3-管道overlap通用步骤.png|1307]]

管道最典型的 overlap 是**流水线并发**：左边一边写，右边一边读，右边不必等左边把全部输出生成完。

```text
时间轴:
生产者: 生成 chunk1 ── write() ── 生成 chunk2 ── write() ── 生成 chunk3
管道缓冲:          chunk1 可读      chunk2 可读      chunk3 可读
消费者:                 read() + 处理 chunk1 ── read() + 处理 chunk2
```

1. 父进程 `pipe(fd)` 建缓冲区，`fork()` 之后两边各关一端。
2. 写进程循环 `write(fd[1], buf, n)`，一小块一小块地放，而不是攒齐了再写。
3. 读进程循环 `read(fd[0], buf, sizeof(buf))`，读到多少就先处理多少。
4. 管道空时读进程睡，写进程继续生产；管道满时写进程睡，读进程继续消费。两种阻塞都是有意义的等待，CPU 会让给别人。
5. 不想在没数据时干等，就把 fd 设成非阻塞：

```c
int flags = fcntl(fd[0], F_GETFL);
fcntl(fd[0], F_SETFL, flags | O_NONBLOCK);

ssize_t n = read(fd[0], buf, sizeof(buf));
if (n > 0) {
    handle_chunk(buf, n);
} else if (n == -1 && errno == EAGAIN) {
    do_other_work();          // 暂时没数据，先干别的
} else if (n == 0) {
    /* 写端全关了，收工 */
}
```

注意这里必须区分 `n == 0` 和 `n == -1 && errno == EAGAIN`：前者是对方说完了，后者只是此刻没数据。原来那种 `if (n > 0) ... else 干别的` 的写法会把 EOF 当成「暂时没数据」，于是永远收不了工。

> [!tip] Shell 管道天生就是 overlap
> `grep "error" big.log | wc -l` 里，`wc` 不用等 `grep` 扫完整个文件才开始计数。管道的 64 KB 缓冲区就是那个让两级同时推进的中间层。

## 7. 匿名管道与命名管道

| 特性 | 匿名管道 | 命名管道 FIFO |
|------|----------|---------------|
| 创建 | `pipe()` | `mkfifo()` 或 `mkfifo` 命令 |
| 怎么找到对方 | 靠 `fork` 继承 fd，必须有亲缘关系 | 靠文件路径，任意进程都能 `open` |
| 文件系统里 | 不存在 | 有 inode，`ls -l` 类型是 `p`，大小恒为 0 |
| 数据在哪 | 内核缓冲区 | 同样是内核缓冲区，不落盘 |
| 打开时的行为 | `pipe()` 立刻返回 | `open()` 会等另一端也打开 |
| 生命周期 | 最后一个 fd 关闭时消失 | 文件一直在，要 `unlink` 删 |

两者在读写行为上完全一致：都是单向、都没有消息边界、都遵守上面那四条边界规则。

## 8. 关键要点

1. 管道是**单向字节流**，没有消息边界。双向要开两个，或者直接用 `socketpair()`。
2. 内核数的是**引用计数**：写端归零 `read` 才返回 0，读端归零写者才收到 `SIGPIPE`。`fork` 之后立刻关掉用不到的那一端，一句都不能省。
3. `read()` 必须写成循环读到返回 0；一次 `read` 假定读全是字节流协议的经典错误。
4. `write` 传的长度用 `strlen` 不用 `sizeof`，否则会把缓冲区里的垃圾一起发出去。
5. 缓冲区默认 64 KB，满了阻塞就是**反压**；`PIPE_BUF`（4096）以内的写是原子的，多写者场景下每条要控制在这个长度内。
6. FIFO 的 `open()` 会等另一端出现，这是特性；`O_WRONLY | O_NONBLOCK` 在无读者时返回 `ENXIO`。
7. Shell 的 `|` 就是 `pipe` + `fork` + `dup2`；`dup2` 之后要立刻关掉原来的 fd。
