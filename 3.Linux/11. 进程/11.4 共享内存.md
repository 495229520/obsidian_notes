## 1. System V IPC 简介

**System V IPC** 是 Unix/Linux 系统中一组经典的[[11.2 进程间通信IPC|进程间通信]]机制，主要包括三种：

| 机制 | 说明 | 主要用途 |
|------|------|----------|
| **共享内存** | 多个进程共享同一块物理内存 | 大量数据的高速交换 |
| **[[11.5 信号量\|信号量]]** | 用于进程同步的计数器 | 控制对共享资源的访问 |
| **[[11.6 消息队列\|消息队列]]** | 内核中的消息链表 | 异步消息传递 |

### 1.1 IPC 键值 (key)

System V IPC 使用**键值 (key)** 来标识 IPC 对象：

- 不同进程可以通过相同的 key 来访问同一个 IPC 对象
- `IPC_PRIVATE`（值为 0）创建私有的 IPC 对象，只有亲缘关系的进程能访问
- 通常使用 `ftok()` 函数生成唯一的 key

```c
#include <sys/types.h>
#include <sys/ipc.h>

key_t ftok(const char *pathname, int proj_id);
```

- `pathname`：一个存在的文件路径
- `proj_id`：项目 ID（只使用低 8 位）
- 返回值：成功返回 key，失败返回 -1

> [!warning] ftok 的两个坑
> **它认的是 inode，不是路径字符串。** `ftok(".", 'a')` 里的 `.` 是**当前工作目录**：两个进程从不同目录启动就会算出不同的 key，各建各的共享内存，症状是「共享内存怎么不生效」。所以要用绝对路径，而且那个文件在程序运行期间不能被删了重建，重建后 inode 变了，key 也就变了。
>
> **它会碰撞。** 生成的 key 只取了 inode 号的低 16 位、设备号的低 8 位和 `proj_id` 的低 8 位，不同文件算出同一个 key 完全可能。想确定地拿到一个 key，直接写死一个常量（例如 `0x1234ABCD`）比 `ftok` 更可控。

## 2. 共享内存原理

共享内存是**最快的 IPC 方式**：数据不在进程之间复制，多个进程直接读写同一批物理页。

准确地说，快的是**映射建好之后**的读写，那就是普通的访存指令，一次内核都不进。建立映射本身（`shmget` + `shmat`）仍然是系统调用，也有开销，所以共享内存适合「建一次、用很久、传很多」，不适合传一条几十字节的控制消息。

### 2.1 工作原理

![[图片/3.Linux/11. 进程/3_11_11_4_1.svg|760]]

1. 进程 A 调用 `shmget()` 创建一块共享内存
2. 进程 A 调用 `shmat()` 将共享内存映射到自己的[[1.3 进程的虚拟地址空间|虚拟地址空间]]
3. 进程 B 通过相同的 key 获取同一块共享内存
4. 进程 B 也将其映射到自己的地址空间
5. 两个进程可以像访问普通内存一样读写这块区域

### 2.2 优缺点

| 优点 | 缺点 |
|------|------|
| **速度最快**：映射建好后读写不进内核 | **需要同步机制**：必须配合[[11.5 信号量\|信号量]]等避免竞态条件 |
| **大容量**：适合传输大量数据 | **生命周期管理**：需要手动删除，进程崩溃也不会自动回收 |
| **灵活**：可以存储任意数据结构 | **不能存指针**：见下一节 |

### 2.3 共享内存里不能放指针

两个进程映射的是同一批物理页，但**映射到的虚拟地址通常不同**：进程 A 拿到 `0x7f3a…a000`，进程 B 拿到 `0x7f91…b000`。

![[图片/3.Linux/11. 进程/3_11_11_4_2.svg|1100]]

所以下面这个结构存进共享内存之后，B 读出来的 `next` 在 B 的地址空间里是个非法值：

```c
struct node {
    int          value;
    struct node *next;    // 存的是 A 的虚拟地址，B 解引用直接段错误
};
```

正确做法是存**相对于共享内存起始地址的偏移量**，用的时候再加上本进程的基址：

```c
struct node {
    int    value;
    size_t next_off;      // 相对偏移；约定 0 表示空
};

struct node *next = (n->next_off == 0)
                  ? NULL
                  : (struct node *)((char *)shmptr + n->next_off);
```

同样的道理，共享内存里也不能直接放 `std::string`、`std::vector` 或带虚函数的对象，它们内部都是裸指针。真要在共享内存里放容器，得用 Boost.Interprocess 那种配了自定义 allocator 的实现。

`shmat` 的第二个参数可以指定固定地址让两边映射到同一处，但那要求这段地址在每个进程里都恰好空着，很脆弱，工程上一般不这么做。

### 2.4 生命周期的三个事实

- **`shmat` 建立的映射会被 `fork` 继承**：父子指向同一批物理页，子进程不需要再 `shmat`。
- **`exec` 之后映射消失**：整个地址空间被换掉了，`exec` 后要重新 `shmget` + `shmat`。
- **`IPC_RMID` 只是打个标记**：标记之后 key 立刻失效，新的 `shmget` 再也拿不到它；但已经挂上的进程照常读写，直到最后一个进程 `shmdt` 或退出，内核才真正释放。

最后这条有个好用的模式：创建者建好、所有参与者 attach 完之后**立刻** `IPC_RMID`。之后谁都不会忘记删，最后一个人走的时候自动回收。否则进程崩溃时那块内存会一直挂在内核里直到重启，`ipcs -m` 里能看到一堆 `nattch` 为 0 的段。

## 3. 相关函数

### 3.1 shmget() - 创建/获取共享内存

```c
#include <sys/ipc.h>
#include <sys/shm.h>

int shmget(key_t key, size_t size, int shmflg);
```

| 参数 | 说明 |
|------|------|
| `key` | IPC 键值，用于标识共享内存。使用 `IPC_PRIVATE` 创建新的私有共享内存 |
| `size` | 共享内存的大小（字节）。实际分配会向上取整到页大小的倍数 |
| `shmflg` | 标志位，包括权限和选项 |
| 返回值 | 成功返回共享内存标识符 (shmid)，失败返回 -1 |

**常用标志位**：

| 标志 | 说明 |
|------|------|
| `IPC_CREAT` | 如果不存在则创建 |
| `IPC_EXCL` | 与 `IPC_CREAT` 一起使用，如果已存在则失败 |
| `0666` | 权限位（类似文件权限） |

**示例**：

```c
// 创建或获取共享内存
int shmid = shmget(key, 1024, IPC_CREAT | 0666);

// 创建新的共享内存（如果已存在则失败）
int shmid = shmget(key, 1024, IPC_CREAT | IPC_EXCL | 0666);

// 获取已存在的共享内存
int shmid = shmget(key, 0, 0);
```

获取已有共享内存时 `size` 传 `0` 最省事。传非 0 值时内核会检查它**不大于**已有段的实际大小，传大了返回 `EINVAL`。两个程序里各写死一个 `SHM_SIZE`、后来又只改了一边，后启动的那个就会莫名失败在这里。

### 3.2 shmat() - 映射共享内存

```c
void *shmat(int shmid, const void *shmaddr, int shmflg);
```

| 参数 | 说明 |
|------|------|
| `shmid` | `shmget()` 返回的共享内存标识符 |
| `shmaddr` | 指定映射地址，通常设为 `NULL` 让系统自动选择 |
| `shmflg` | 标志位 |
| 返回值 | 成功返回映射后的地址，失败返回 `(void *)-1` |

**常用标志位**：

| 标志 | 说明 |
|------|------|
| `0` | 默认（可读写） |
| `SHM_RDONLY` | 只读模式 |
| `SHM_RND` | 地址向下取整到页边界 |

**示例**：

```c
// 映射共享内存（系统自动选择地址）
char *ptr = (char *)shmat(shmid, NULL, 0);
if (ptr == (void *)-1) {
    perror("shmat failed");
    exit(1);
}
```

### 3.3 shmdt() - 解除映射

```c
int shmdt(const void *shmaddr);
```

| 参数 | 说明 |
|------|------|
| `shmaddr` | `shmat()` 返回的地址 |
| 返回值 | 成功返回 0，失败返回 -1 |

> **注意**：`shmdt()` 只是解除当前进程与共享内存的映射关系，并不会删除共享内存。共享内存会一直存在直到被显式删除或系统重启。

### 3.4 shmctl() - 控制共享内存

```c
int shmctl(int shmid, int cmd, struct shmid_ds *buf);
```

| 参数 | 说明 |
|------|------|
| `shmid` | 共享内存标识符 |
| `cmd` | 控制命令 |
| `buf` | `shmid_ds` 结构体指针，用于获取/设置信息 |
| 返回值 | 成功返回 0（或其他值），失败返回 -1 |

**常用命令**：

| 命令 | 说明 |
|------|------|
| `IPC_STAT` | 获取共享内存状态信息到 `buf` |
| `IPC_SET` | 设置共享内存属性（从 `buf` 读取） |
| `IPC_RMID` | 标记删除共享内存（当连接数为 0 时真正删除） |

**删除共享内存**：

```c
// 删除共享内存
shmctl(shmid, IPC_RMID, NULL);
```

### 3.5 POSIX 共享内存：shm_open + mmap

上面这套是 1983 年的 System V 接口：句柄不是文件描述符、靠 `ftok` 寻址、忘了删就一直留在内核里。今天新写代码通常用 POSIX 版本：

```c
#include <sys/mman.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <unistd.h>

int fd = shm_open("/myshm", O_CREAT | O_RDWR, 0666);   // 名字必须以 / 开头
ftruncate(fd, SHM_SIZE);                               // 新建对象大小为 0，得先定尺寸
void *p = mmap(NULL, SHM_SIZE, PROT_READ | PROT_WRITE,
               MAP_SHARED, fd, 0);                     // MAP_SHARED 才是共享
close(fd);                                             // 映射建好后 fd 就可以关

// ... 像普通内存一样读写 p ...

munmap(p, SHM_SIZE);
shm_unlink("/myshm");                                  // 对应 IPC_RMID
```

三处差别值得记住：

**`shm_open` 返回真正的 fd。** 能 `fstat` 查大小，能通过 Unix 域套接字的 `SCM_RIGHTS` 直接递给另一个进程，也能被 RAII 自动关掉。System V 的 `shmid` 只是个整数，这些都做不到。

**对象在 `/dev/shm/` 下以普通文件出现。** `ls -l /dev/shm` 就能看见，`rm` 就能删，不用记 `ipcrm -m`。忘了清理的后果也看得见，而不是藏在 `ipcs` 里。

**`mmap` 必须写 `MAP_SHARED`。** 写成 `MAP_PRIVATE` 会拿到一份写时复制的私有副本：自己改得挺欢，别人一个字节都看不到，而且**不会报任何错**。这是这套接口最容易踩的一脚。

`ftruncate` 那一步也别漏：`shm_open` 新建出来的对象长度是 0，直接 `mmap` 会成功，但访问时收到 `SIGBUS`。

glibc 2.34 之前编译要加 `-lrt`。

## 4. 代码示例

### 4.1 写入进程 (shm_write.c)

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/ipc.h>
#include <sys/shm.h>

#define SHM_SIZE 1024

int main(void) {
    key_t key;
    int shmid;
    char *shmptr;

    // 1. 生成 key
    key = ftok(".", 'a');
    if (key == -1) {
        perror("ftok failed");
        exit(1);
    }

    // 2. 创建共享内存
    shmid = shmget(key, SHM_SIZE, IPC_CREAT | 0666);
    if (shmid == -1) {
        perror("shmget failed");
        exit(1);
    }
    printf("共享内存创建成功，shmid = %d\n", shmid);

    // 3. 映射共享内存
    shmptr = (char *)shmat(shmid, NULL, 0);
    if (shmptr == (void *)-1) {
        perror("shmat failed");
        exit(1);
    }

    // 4. 写入数据
    strcpy(shmptr, "Hello from writer process!");
    printf("数据已写入: %s\n", shmptr);

    // 5. 解除映射（保留共享内存供其他进程读取）
    shmdt(shmptr);

    return 0;
}
```

### 4.2 读取进程 (shm_read.c)

```c
#include <stdio.h>
#include <stdlib.h>
#include <sys/ipc.h>
#include <sys/shm.h>

#define SHM_SIZE 1024

int main(void) {
    key_t key;
    int shmid;
    char *shmptr;

    // 1. 生成相同的 key
    key = ftok(".", 'a');
    if (key == -1) {
        perror("ftok failed");
        exit(1);
    }

    // 2. 获取已存在的共享内存
    shmid = shmget(key, SHM_SIZE, 0666);
    if (shmid == -1) {
        perror("shmget failed");
        exit(1);
    }
    printf("获取共享内存成功，shmid = %d\n", shmid);

    // 3. 映射共享内存
    shmptr = (char *)shmat(shmid, NULL, 0);
    if (shmptr == (void *)-1) {
        perror("shmat failed");
        exit(1);
    }

    // 4. 读取数据
    printf("读取到的数据: %s\n", shmptr);

    // 5. 解除映射
    shmdt(shmptr);

    // 6. 删除共享内存
    shmctl(shmid, IPC_RMID, NULL);
    printf("共享内存已删除\n");

    return 0;
}
```

> [!note] 为什么写进程用 `IPC_CREAT`，读进程不用？
> `IPC_CREAT | 0666` 的意思是：如果这个 `key` 对应的共享内存不存在，就创建；如果已经存在，就直接获取它。
>
> 在这个示例里，`shm_write.c` 被设计成先运行，负责创建共享内存并写入数据，所以它需要带 `IPC_CREAT`。`shm_read.c` 被设计成后运行，只需要通过相同的 `key` 找到已经存在的共享内存，所以只写 `0666`，表示按权限获取已有对象。
>
> 如果读进程也写成 `IPC_CREAT | 0666`，技术上也可能成功，但语义会变模糊：读进程可能在写进程还没创建共享内存时自己创建一块空共享内存，随后读到未初始化或无意义的数据。因此读进程通常不带 `IPC_CREAT`，这样一旦共享内存不存在，`shmget()` 会失败，能提醒你运行顺序或创建逻辑有问题。

### 4.3 编译和运行

```bash
# 编译
gcc -o shm_write shm_write.c
gcc -o shm_read shm_read.c

# 运行（先写后读）
./shm_write
./shm_read
```

> [!warning] 这个例子本身是有竞态的
> 两个程序靠「你先敲哪一条命令」来保证顺序。真实程序里没有这种保证：读进程完全可能在写进程的 `strcpy` 执行到一半时读走半截字符串，而且不会有任何报错。
>
> 共享内存不提供同步，也不提供「数据已就绪」的通知。上面这段只演示映射怎么建立，不能当模板抄。加同步的做法见 [[11.5 信号量]]。

## 5. 查看和管理共享内存

### 5.1 命令行工具

```bash
# 查看所有 System V IPC 对象
ipcs

# 只查看共享内存
ipcs -m

# 删除指定的共享内存
ipcrm -m <shmid>

# 删除所有共享内存（谨慎使用）
ipcrm -a
```

### 5.2 ipcs 输出示例

```
------ Shared Memory Segments --------
key        shmid      owner      perms      bytes      nattch     status
0x61012345 32769      user       666        1024       0
```

| 字段 | 说明 |
|------|------|
| `key` | IPC 键值 |
| `shmid` | 共享内存标识符 |
| `owner` | 创建者 |
| `perms` | 权限 |
| `bytes` | 大小（字节） |
| `nattch` | 当前连接的进程数 |

`status` 列出现 `dest` 表示这段已经被 `IPC_RMID` 标记，只等 `nattch` 归零就释放。

### 5.3 系统限制

| 限制 | 含义 | 查看 |
|------|------|------|
| `shmmax` | 单段共享内存的最大字节数 | `cat /proc/sys/kernel/shmmax` |
| `shmall` | 全系统共享内存的总页数上限 | `cat /proc/sys/kernel/shmall` |
| `shmmni` | 全系统共享内存段的最大数量 | `cat /proc/sys/kernel/shmmni` |

现代内核的 `shmmax` 默认已经很大，但一些发行版和容器镜像仍会调小。`shmget` 返回 `EINVAL` 而 `size` 看起来明明合理时，先来这里查一眼。

POSIX 共享内存不受这三个限制约束，它受 `/dev/shm` 这个 tmpfs 的容量约束，默认是物理内存的一半，用 `df -h /dev/shm` 查。容器里这个值常被设成 64 MB，跑 PyTorch DataLoader 之类靠 `/dev/shm` 传张量的程序时经常在这里翻车。

## 6. 共享内存与同步

共享内存本身**不提供同步机制**，多个进程同时读写可能导致数据不一致。通常需要配合以下机制：

| 同步方式 | 说明 |
|----------|------|
| **[[11.5 信号量\|信号量]]** | System V 信号量或 POSIX 信号量 |
| **互斥锁** | pthread_mutex（需要 `PTHREAD_PROCESS_SHARED`） |
| **文件锁** | `flock()` 或 `fcntl()` |

详细的同步机制请参考 [[11.5 信号量]]。

### 6.1 共享内存中的 overlap 实现过程

![[图片/3.Linux/11. 进程/11.4-共享内存双缓冲方案.png|778]]

---

![[图片/3.Linux/11. 进程/11.4-共享内存环形缓冲区方案.png|785]]

共享内存最适合做高吞吐 overlap，因为数据不需要在内核和用户空间之间反复复制。真正要解决的是：生产者写哪一块、消费者读哪一块、什么时候切换。

常用方案是 **双缓冲** 或 **环形缓冲区**：

```text
共享内存:
┌──────────────┬──────────────┐
│ buffer A     │ buffer B     │
│ 正在被写入     │  正在被读取   │
└──────────────┴──────────────┘

时间轴:
生产者: 写 A ── 通知 A 可读 ── 写 B ── 通知 B 可读
消费者:        读 A / 处理 A ──        读 B / 处理 B
```

实现过程：

1. 生产者用 `shmget()` 创建共享内存，并用 `shmat()` 映射到自己的地址空间。
2. 消费者用同一个 `key` 获取 `shmid`，也用 `shmat()` 映射同一块物理内存。
3. 共享内存中划分出多个槽位，例如 `slot[0]`、`slot[1]`，每个槽位保存一批数据和状态字段。
4. 生产者写 `slot[0]` 时，消费者可以处理上一轮已经写好的 `slot[1]`。
5. 生产者写完后，用 [[11.5 信号量|信号量]] 或事件通知消费者“这个槽位可读”。
6. 消费者读完后，再通知生产者“这个槽位可写”，避免覆盖未消费的数据。

环形缓冲区通常用两个指针和两个计数信号量来判断状态：

| 成员 | 作用 |
|------|------|
| `head` | 写指针，生产者下一次写入的槽位下标 |
| `tail` | 读指针，消费者下一次读取的槽位下标 |
| `empty_slot` | 空槽位数量，生产者写入前先等待它 |
| `full_slot` | 已写满槽位数量，消费者读取前先等待它 |

消费者不是扫描每一块共享内存来猜哪块可读，而是先 `wait(full_slot)`。只要这个等待成功，就说明至少有一个槽位已经由生产者写满；消费者随后读取 `tail` 指向的槽位。读完后把 `tail` 后移，并 `post(empty_slot)` 通知生产者“又空出一个槽位，可以继续写”。

生产者写完 `head` 指向的槽位后，先把该槽位状态标记为可读，再移动 `head`，最后 `post(full_slot)` 唤醒消费者。这里的 `post(full_slot)` 就是“通知消费者有数据可读”的动作。

伪代码结构：

```c
// producer
wait(empty_slot);
write(shared->slot[head], batch);
shared->slot[head].state = FULL;
head = (head + 1) % SLOT_COUNT;
post(full_slot);

// consumer
wait(full_slot);
read_and_process(shared->slot[tail]);
shared->slot[tail].state = EMPTY;
tail = (tail + 1) % SLOT_COUNT;
post(empty_slot);
```

> [!warning] overlap 不等于随便同时读写
> 共享内存没有消息边界，也没有自动同步。只有在“生产者写一个槽位，消费者读另一个槽位”且状态切换受同步机制保护时，overlap 才是正确的。

## 7. 关键要点

1. **快的是映射建好之后**：那时的读写就是普通访存指令，不进内核；建立映射本身仍然是系统调用，所以它适合「建一次、传很多」，不适合传一条控制消息
2. **使用流程**：`ftok()` → `shmget()` → `shmat()` → 读写 → `shmdt()` → `shmctl(IPC_RMID)`
3. **不能存指针**：两个进程映射到的虚拟地址不同，跨进程的引用要存**相对偏移**
4. **需要同步机制**：内核既不提供互斥，也不提供「数据已就绪」的通知，必须配合[[11.5 信号量|信号量]]
5. **生命周期**：进程崩溃不会自动回收；`IPC_RMID` 只打标记，等 `nattch` 归零才真正释放。attach 完立刻标记删除是最省心的模式
6. **`ftok` 认的是 inode 不是路径字符串**，用相对路径时会因为 cwd 不同而算出不同的 key
7. **新代码优先 `shm_open` + `mmap`**：句柄是 fd、在 `/dev/shm` 下看得见；但 `mmap` 一定要写 `MAP_SHARED`，写成 `MAP_PRIVATE` 不报错却完全不共享
8. **共享内存 overlap** 通常用双缓冲或环形缓冲区，让写下一批和读上一批同时推进
