# 11.7 僵尸进程

## 1. 什么是僵尸进程

[[11.1 进程简介#4. fork()：创建进程|fork()]] 出来的子进程终止时，它占的地址空间、文件描述符、物理内存都立刻还给了系统，但内核不会把它的**进程描述符**（`task_struct`）一起删掉。里面还留着退出状态、被哪个信号打死的、用了多少 CPU 时间这些信息，要等父进程用 `wait()` 或 `waitpid()` 来取。

在被取走之前，这个已经死掉但还没被清理的条目，就叫**僵尸进程（Zombie）**。

![[图片/SVG/3_11_11_7_1.svg|1307]]

### 1.1 为什么内核要留着它

道理很直白：**退出状态只有一份，而想看它的人还没来看**。

子进程退出时可能带回 0，也可能带回 42，也可能是被 `SIGSEGV` 打死的。这些信息只有它自己知道，一旦 `task_struct` 被删掉就永远查不到了。内核没法预判父进程要不要，只能先留着，等父进程明确说「我收下了」才敢扔。

所以僵尸不是异常状态，而是**每个子进程都必然经过的一站**。图 A 里从「运行中」到「彻底消失」中间那一格谁都得走一遍，区别只在停留多久：父进程早就阻塞在 `wait()` 上，那这一格几乎是瞬间穿过；父进程压根不管，才会一直卡在这里。

### 1.2 僵尸占着什么，不占什么

图 B 那三栏值得记住，因为传得最广的几句话恰好是错的：

- **不占内存**：地址空间在 `exit()` 那一刻就归还了，僵尸手里没有任何用户态内存
- **不占 CPU**：它没有任何代码可执行，调度器根本不会挑到它
- **占一个 PID 号**，以及内核里那一条 `task_struct`

危害全在 PID 上。`/proc/sys/kernel/pid_max` 默认是 32768，一个反复 `fork` 却从不回收的程序能把这个数字撑满，之后**整台机器**的 `fork()` 都会返回 `EAGAIN`，新进程一个也起不来。

### 1.3 孤儿进程不是僵尸

图 A 第 ③ 条路容易和僵尸混淆，其实结局正好相反。

父进程先退出的话，它的子进程会当场被过继给 PID 1，`getppid()` 从此返回 1。这叫**孤儿进程**。systemd 的主循环一直在 `wait`，所以孤儿死了立刻就被收走，反而不会堆积。

真正会出问题的只有图 A 第 ② 条：父进程活得好好的，还在不停 `fork`，就是不 `wait`。

有一个例外要留意：容器里的 PID 1 是你自己的应用进程，它多半没写回收循环。容器内的进程被托孤给它之后，僵尸照样会堆。`docker run --init` 和 tini 这类小 init 程序就是为了补这个洞。

### 1.4 怎么看，怎么清

僵尸在 `ps` 里的状态是 `Z`，命令名后面挂一个 `<defunct>`：

```bash
# 列出所有僵尸，同时看清它们的父进程是谁
$ ps -eo stat,pid,ppid,comm | awk 'NR==1 || $1 ~ /^Z/'
STAT   PID  PPID COMMAND
Z     4821  4810 a.out
```

**`kill -9 4821` 对它没有任何效果。** 信号是发给活着的进程去执行的，僵尸没有任何代码可执行，收到也没人处理。

真正的做法是对着 `PPID` 那一列下手：要么让父进程去 `wait`（改代码），要么直接杀掉父进程。父进程一死，这些僵尸立刻走图 A 第 ③ 条路，被 PID 1 接手并当场清理。

## 2. 销毁僵尸进程：wait() 函数

父进程用 `wait()` 等子进程终止，并把留在 `task_struct` 里的退出状态取走。

### 2.1 函数原型

```c
#include <sys/wait.h>

pid_t wait(int *status);
```

### 2.2 参数与返回值

| 项目 | 说明 |
|:---|:---|
| `status` | 输出参数，用于保存子进程的终止状态信息（可以为 NULL） |
| **返回值** | 成功时返回终止的子进程 PID；失败时返回 -1 |

返回 -1 有两种情况，得分开处理：

- `errno == ECHILD`：根本没有子进程了。这是循环回收的收尾条件，`while (wait(NULL) > 0);` 就是靠撞上它退出的
- `errno == EINTR`：阻塞期间被信号打断。这不是错误，要自己重试

### 2.3 status 状态解析宏

| 宏 | 说明 |
|:---|:---|
| `WIFEXITED(status)` | 子进程正常终止时返回真（true） |
| `WEXITSTATUS(status)` | 返回子进程的退出值（需要先用 `WIFEXITED` 判断） |
| `WIFSIGNALED(status)` | 子进程被信号终止时返回真 |
| `WTERMSIG(status)` | 返回导致子进程终止的信号编号 |
| `WIFSTOPPED(status)` | 子进程被暂停时返回真 |
| `WSTOPSIG(status)` | 返回导致子进程暂停的信号编号 |

括号里那句「需要先用 `WIFEXITED` 判断」不是客套话。**`status` 不是退出码本身**，`exit(42)` 之后它等于 10752，内核把「怎么死的」编在低字节、把「具体是多少」编在高字节。对一个被信号打死的 `status` 调 `WEXITSTATUS`，语法合法，读回来是 0，看着像执行成功。位布局的细节见 [[5.5 等待函数#5. status：先问死法，再取值|5.5 第 5 节]]。

### 2.4 wait() 的阻塞特性

调用 `wait()` 函数时：
- 如果**有子进程已终止**：函数立即返回，回收该子进程资源
- 如果**没有已终止的子进程**：函数会**阻塞**，直到有子进程终止
- 如果**一个子进程都没有**：立即返回 -1，`errno` 置 `ECHILD`

### 2.5 示例代码

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    int status;
    pid_t pid = fork();

    if (pid == 0) {
        // 子进程
        printf("子进程运行中...\n");
        sleep(3);
        return 10;  // 返回值 10，低 8 位返回给操作系统
    } else {
        // 父进程
        printf("父进程等待子进程终止...\n");
        pid_t child_pid = wait(&status);  // 阻塞等待

        if (WIFEXITED(status)) {
            printf("子进程 %d 正常终止，返回值: %d\n",
                   child_pid, WEXITSTATUS(status));
        }
    }
    return 0;
}
```

**输出示例**：
```
父进程等待子进程终止...
子进程运行中...
子进程 12345 正常终止，返回值: 10
```

前两行的先后顺序**每次运行都可能不同**，`fork()` 之后谁先被调度没有保证。第三行一定在 3 秒之后，因为父进程阻塞在 `wait()` 上。

代码里那句注释说的是：退出值只有 8 位，`return 10` 传出去的是 10，但 `return -1` 父进程读回来会变成 255。

子进程分支这里用 `return` 是能跑的，因为 `fork()` 之前没有任何没刷出去的输出，也没注册 `atexit()` 函数。**换成习惯写法应该是 `_exit()`**：`fork` 出来的子进程走 `exit()` 会把继承来的 stdio 缓冲区再刷一遍，父进程稍后又刷一次，同一段输出就打两遍（见 [[5.2 结束进程#何时使用 _exit()|5.2]]）。

## 3. 非阻塞等待：waitpid() 函数

`waitpid()` 提供了比 `wait()` 更灵活的控制，支持非阻塞模式和指定等待特定子进程。

### 3.1 函数原型

```c
#include <sys/wait.h>

pid_t waitpid(pid_t pid, int *status, int options);
```

### 3.2 参数说明

| 参数 | 说明 |
|:---|:---|
| `pid` | 指定要等待的子进程 |
| `status` | 同 `wait()` 的 status 参数 |
| `options` | 控制选项，可以实现非阻塞等待 |

### 3.3 pid 参数取值

| 值 | 含义 |
|:---|:---|
| `> 0` | 等待进程 ID 等于 pid 的子进程 |
| `== -1` | 等待任意子进程（等同于 `wait()`） |
| `== 0` | 等待与调用进程同一进程组的任意子进程 |
| `< -1` | 等待进程组 ID 等于 pid 绝对值的任意子进程 |

`wait(&status)` 就是 `waitpid(-1, &status, 0)`，写死了参数的那个特例。

### 3.4 options 选项

| 选项 | 说明 |
|:---|:---|
| `0` | 阻塞等待（默认行为） |
| `WNOHANG` | 非阻塞模式：如果没有已终止的子进程，立即返回 0 |
| `WUNTRACED` | 同时报告暂停状态的子进程 |

### 3.5 三种返回值要分开处理

| 返回值 | 含义 | 该做什么 |
|:---|:---|:---|
| `> 0` | 收到了，值是那个子进程的 PID | 解析 `status` |
| `== 0` | 只在带 `WNOHANG` 时出现，目标还活着 | 去干别的，等会儿再来 |
| `== -1` | 出错，看 `errno` | `ECHILD` 说明收完了，`EINTR` 要重试 |

把 0 和 -1 混在一起判断是写轮询循环时最常见的死循环来源。下面的示例把三个分支都写全了，可以当模板用。

### 3.6 示例：非阻塞等待

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    int status;
    pid_t pid = fork();

    if (pid == 0) {
        // 子进程
        sleep(5);
        return 20;
    } else {
        // 父进程：非阻塞轮询
        while (1) {
            pid_t result = waitpid(pid, &status, WNOHANG);

            if (result == -1) {
                perror("waitpid");
                break;
            } else if (result == 0) {
                // 子进程还在运行
                printf("子进程还在运行，父进程可以做其他事...\n");
                sleep(1);
            } else {
                // 子进程已终止
                if (WIFEXITED(status)) {
                    printf("子进程 %d 终止，返回值: %d\n",
                           result, WEXITSTATUS(status));
                }
                break;
            }
        }
    }
    return 0;
}
```

注释里的「父进程可以做其他事」是这段代码的用意，但它实际做的事是 `sleep(1)` 空转。查得勤就是烧 CPU，查得稀就是回收得晚，两头都不讨好。真要在等待期间干活，用下一节的 `SIGCHLD`。

## 4. 信号处理方式：signal() 函数

除了主动调用 `wait()`/`waitpid()`，还可以通过**注册信号处理函数**来自动回收僵尸进程。

### 4.1 SIGCHLD 信号

当子进程终止时，内核会向父进程发送 `SIGCHLD` 信号。父进程可以注册一个信号处理函数，在收到信号时调用 `wait()` 回收子进程。

这个信号的默认动作是**忽略**，所以不装处理函数的程序不会因为子进程退出而受影响，也正因为如此，僵尸才会一直堆着没人管。

### 4.2 signal() 函数原型

```c
#include <signal.h>

typedef void (*sighandler_t)(int);

sighandler_t signal(int signum, sighandler_t handler);
```

**函数原型的完整形式**：
```c
void (*signal(int signo, void (*func)(int)))(int);
```

### 4.3 参数说明

| 参数 | 说明 |
|:---|:---|
| `signum` | 信号编号（如 `SIGCHLD`、`SIGINT`、`SIGALRM` 等） |
| `handler` | 信号处理函数，或特殊值 `SIG_IGN`（忽略）、`SIG_DFL`（默认行为） |

### 4.4 返回值

- **成功**：返回之前的信号处理函数指针
- **失败**：返回 `SIG_ERR`

### 4.5 常用信号

| 信号 | 说明 |
|:---|:---|
| `SIGCHLD` | 子进程状态改变（终止或暂停）时发送给父进程 |
| `SIGALRM` | 由 `alarm()` 函数设置的定时器到期时触发 |
| `SIGINT` | 用户按下 `Ctrl+C` 时发送 |
| `SIGTERM` | 终止请求信号 |

### 4.6 signal() 的语义随平台变

![[图片/SVG/3_11_11_7_2.svg|1307]]

图 A 是学 `signal()` 时最该先知道的一件事：**这个函数在两套 Unix 传统里的行为不一样，而代码里看不出区别**。

System V 那套会在 handler 触发后把处置重置成 `SIG_DFL`，所以必须在 handler 里再 `signal()` 一次，而重置到重装之间的窗口里来一个信号就直接把进程干掉了。BSD 那套不重置、执行期间自动屏蔽同种信号、被打断的慢系统调用自动重启。

今天 Linux 上的 glibc 给的是 BSD 那套，所以本节的示例能正常跑。但这是 **glibc 的选择，不是标准的保证**，换一个 libc 就可能变回去。

`sigaction()` 的价值就在这里：`sa_flags` 和 `sa_mask` 把「要不要重启系统调用」「执行期间屏蔽谁」写成了显式参数，行为落在调用处，不看平台脸色。新代码一律用它，`signal()` 只留给 `signal(SIGPIPE, SIG_IGN)` 这种一句话的场合。

### 4.7 handler 里的三条约束

图 B 下半解释了另一件容易被忽略的事：处理函数不是凭空跑的，它抢的是主流程的执行流。

1. **必须循环 `waitpid`**。`SIGCHLD` 是标准信号，内核只用一个 pending 位记「有没有」，不记「有几个」。三个子进程在同一个调度间隙里退出，处理函数只会被调用一次，里面只 `wait` 一次就漏掉两个
2. **必须带 `WNOHANG`**。处理函数里不能阻塞，否则主流程被卡死
3. **进出各存一次 `errno`**。`waitpid` 失败会改写它，主流程正在检查的那个 `errno` 会被污染

另外 handler 里调 `printf` 只适合演示。它不是异步信号安全的函数，正式代码里不能用。

### 4.8 示例：使用信号自动回收僵尸进程

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <signal.h>
#include <sys/wait.h>

void sigchld_handler(int signo) {
    int status;
    pid_t pid;

    // 使用循环处理可能同时终止的多个子进程
    while ((pid = waitpid(-1, &status, WNOHANG)) > 0) {
        printf("子进程 %d 已回收\n", pid);
    }
}

int main(void) {
    // 注册 SIGCHLD 信号处理函数
    signal(SIGCHLD, sigchld_handler);

    pid_t pid = fork();

    if (pid == 0) {
        // 子进程
        printf("子进程 %d 运行中...\n", getpid());
        sleep(2);
        printf("子进程退出\n");
        exit(0);
    } else {
        // 父进程继续执行其他任务
        printf("父进程继续工作...\n");
        for (int i = 0; i < 5; i++) {
            printf("父进程工作中... %d\n", i);
            sleep(1);
        }
    }

    return 0;
}
```

跑这段会看到一个现象：五轮循环并没有花满 5 秒。子进程在第 2 秒退出，`SIGCHLD` 打断了父进程正在执行的 `sleep(1)`，而 **`sleep()` 被信号打断后是提前返回的，不会自己续上**，返回值是没睡完的秒数。这就是图 B 左边那张卡片说的事，`SA_RESTART` 对它也无效。

想睡满就得拿返回值再睡一次：

```c
unsigned int left = 1;
while ((left = sleep(left)) > 0)
    ;
```

`read`、`accept`、`waitpid` 这些慢系统调用是另一码事：带 `SA_RESTART` 时内核会自动重来，代码察觉不到；不带就返回 -1 并置 `EINTR`，必须自己重试。服务器代码不写这个分支，迟早会出偶发错误。

## 5. alarm() 定时器函数

`alarm()` 函数用于设置一个定时器，在指定秒数后向进程发送 `SIGALRM` 信号。

### 5.1 函数原型

```c
#include <unistd.h>

unsigned int alarm(unsigned int seconds);
```

### 5.2 参数与返回值

| 项目 | 说明 |
|:---|:---|
| `seconds` | 定时器时间（秒）。设为 0 可取消已设置的定时器 |
| **返回值** | 返回之前设置的定时器剩余秒数，如果之前没有设置则返回 0 |

### 5.3 特点

- 每个进程只有**一个** `alarm` 定时器，再调一次是重置而不是新增
- 正因为只有一个，库函数和业务代码抢着用会互相覆盖，写库时要格外小心
- `SIGALRM` 的默认动作是**终止进程**，所以设了定时器就必须配处理函数
- `fork()` 出来的子进程**不继承**父进程未到期的定时器
- 精度只到秒。要更细的粒度用 `setitimer()` 或 `timer_create()`

### 5.4 示例代码

```c
#include <stdio.h>
#include <unistd.h>
#include <signal.h>

void timeout_handler(int signo) {
    printf("定时器触发！\n");
    alarm(2);  // 重新设置定时器，实现周期性触发
}

int main(void) {
    signal(SIGALRM, timeout_handler);
    alarm(2);  // 2 秒后触发

    while (1) {
        printf("等待中...\n");
        sleep(1);
    }

    return 0;
}
```

`alarm()` 只响一次，所以要周期触发就得在 handler 里再设一次，这段代码就是这么做的。

主循环里的 `sleep(1)` 同样会被 `SIGALRM` 提前打断，现象和上一节完全一样。两个例子撞上的是同一件事：**只要装了信号处理函数，主循环里所有阻塞点都要考虑被打断的可能**。

## 6. 子进程回收中的 overlap 实现过程

这里说的 overlap 不是「传数据」，而是让父进程在子进程运行期间继续处理自己的任务，同时又能及时回收子进程。

### 6.1 阻塞等待的问题

如果父进程直接调用 `wait()`：

```c
pid_t pid = wait(&status);
```

那么父进程会停在这里，直到某个子进程退出。这种写法简单，但父进程无法同时执行其他工作，不适合服务器、任务调度器或交互式程序。

### 6.2 使用 waitpid(WNOHANG) 实现轮询式 overlap

```c
while (running) {
    handle_parent_work();  // 父进程继续处理请求、定时器或 IPC

    while ((pid = waitpid(-1, &status, WNOHANG)) > 0) {
        reap_child(pid, status);
    }
}
```

实现过程：

1. 父进程 `fork()` 创建子进程，把耗时任务交给子进程。
2. 父进程不调用阻塞式 `wait()`，而是在主循环中继续处理自己的工作。
3. 每轮循环调用 `waitpid(-1, &status, WNOHANG)` 检查是否有子进程退出。
4. 如果返回 `0`，说明暂时没有子进程退出，父进程继续工作。
5. 如果返回 `> 0`，说明某个子进程已结束，父进程立刻回收，避免僵尸进程堆积。

这个写法的前提是主循环本身在转。如果 `handle_parent_work()` 里阻塞在 `accept()` 上，那内层的回收循环就永远轮不到执行。

### 6.3 使用 SIGCHLD 实现事件驱动 overlap

更常见的服务器写法是注册 `SIGCHLD`：

```text
子进程退出 -> 内核给父进程发送 SIGCHLD -> handler 中 waitpid(WNOHANG) 回收
```

这样父进程平时可以阻塞在 `accept()`、`epoll_wait()` 或其他主循环中，只有子进程退出时才被信号打断并执行回收逻辑。

代价就是第 4.7 节那三条约束：循环收、带 `WNOHANG`、存好 `errno`。另外主循环那个 `accept()` 会被信号打断，`EINTR` 分支得自己补上。

> [!note] 回收 overlap 的核心
> 不要让父进程为了等待子进程退出而停止主业务。`WNOHANG` 和 `SIGCHLD` 的目标都是：子进程运行期间父进程继续工作，子进程结束时父进程再及时收尸。

## 7. 关键要点

1. **僵尸是每个子进程的必经站**，不是异常状态。内核留着 `task_struct` 是因为退出状态只有一份，而父进程还没来取
2. **僵尸不占内存也不占 CPU**，地址空间在 `exit()` 那一刻就还了。它占的是一个 PID 号和内核里那条记录，`pid_max` 默认 32768，撑满后全机 `fork` 返回 `EAGAIN`
3. **`kill -9` 清不掉僵尸**，它没有代码可执行。要对着 `PPID` 下手：让父进程 `wait`，或者杀掉父进程让它转投 PID 1
4. **孤儿不是僵尸**，父进程先死的子进程会被 PID 1 立刻收走。但容器里的 PID 1 是你的应用，未必写了回收循环
5. **`status` 不是退出码**，`exit(42)` 之后它等于 10752，必须先用 `WIF*` 判类型再取值
6. **`waitpid` 的 0 和 -1 要分开**：0 是「还没到时候」，-1 才是出错（`ECHILD` 收完了、`EINTR` 要重试）
7. **`signal()` 的语义随平台变**，glibc 给的是 BSD 那套但这不是标准保证。新代码用 `sigaction()`，把 `SA_RESTART` 和屏蔽集写成显式参数
8. **SIGCHLD 不排队**，handler 里必须 `while (waitpid(-1, &st, WNOHANG) > 0)` 循环收干净，并且进出各存一次 `errno`
9. **`sleep()` 被信号打断会提前返回**，`SA_RESTART` 救不了它；慢系统调用则取决于有没有这个标志
10. **`alarm()` 每个进程只有一个**，默认动作是终止进程，`fork` 出来的子进程不继承
11. **回收 overlap** 依赖 `WNOHANG` 或 `SIGCHLD`，让父进程继续主业务，同时异步回收子进程
