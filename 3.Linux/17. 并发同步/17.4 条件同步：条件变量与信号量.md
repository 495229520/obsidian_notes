# 17.4 条件同步：条件变量与信号量

> 锁解决"谁能访问"，条件同步解决"**何时访问**"——没有任务时睡眠、有任务时唤醒。
> 线程条件变量详见 [[12.7 条件变量与线程池]]，信号量详见 [[12.4 信号量]] 与 [[11.5 信号量]]。

---

## 1. 为什么需要"等待-通知"

忙等 (busy waiting) 是最朴素的做法：

```c
while (!condition) {
    // 什么也不做，反复检查
}
```

它浪费 CPU、造成不必要的缓存竞争，并且在高核心数下越来越慢。正确做法是让线程在条件不满足时**交出 CPU 进入睡眠**，由改变条件的一方**显式唤醒**。

POSIX 提供了两种机制来做这件事：**条件变量**和**信号量**。它们的设计哲学不同，各有适用场景。

---

## 2. 条件变量 (Condition Variable)

### 2.1 三件套：mutex + 条件变量 + 谓词 (predicate)

条件变量本身**不保存任何状态**。它只做一件事：让线程安全地睡眠和被唤醒。真正的"条件是否成立"由你用一个共享变量（谓词）来表达，并用 mutex 来保护。

三者缺一不可：

| 组件 | 作用 |
|------|------|
| `pthread_mutex_t` | 保护共享状态，使检查和修改条件为原子操作 |
| `pthread_cond_t` | 提供睡眠-唤醒机制 |
| 谓词（如 `queue_size > 0`） | 表达"到底在等什么" |

### 2.2 wait 的内部三步

`pthread_cond_wait(&cond, &mutex)` 做了三件事，且**前两步是原子的**——不存在"锁已释放但线程还没睡"的窗口：

![[图片/SVG/3_17_4_1.svg|760]]

这个原子性至关重要。如果释放锁和进入睡眠之间有间隙，通知线程可能在间隙中发出 signal，此时等待线程既没有持锁也还没睡，signal 就会丢失。

### 2.3 为什么必须用 `while` 而不是 `if`

```c
pthread_mutex_lock(&mutex);
while (queue_size == 0) {          // ← 必须是 while
    pthread_cond_wait(&cond, &mutex);
}
// 取任务...
pthread_mutex_unlock(&mutex);
```

用 `if` 只检查一次，但被唤醒后条件不一定仍然成立，原因有二：

**虚假唤醒 (spurious wakeup)**：POSIX 允许 `pthread_cond_wait` 在没有 signal/broadcast 的情况下返回。这是系统实现的自由度——底层使用 `futex` 时，信号中断或内核状态变化都可能导致提前返回。

**惊群 (thundering herd)**：`broadcast` 唤醒所有等待线程，但只有一个能抢到资源。其他线程醒来后发现条件已被先到者消耗，必须再次 `wait`。

`while` 在每次醒来后重新检查谓词，两种情况都能正确处理。

### 2.4 signal vs broadcast

| 操作 | 唤醒数量 | 典型场景 |
|------|---------|---------|
| `pthread_cond_signal` | 至少一个 | 只有一个等待者能获益（如入队一个任务） |
| `pthread_cond_broadcast` | 所有 | 状态变化对所有等待者都有意义（如关闭线程池、条件类型变化） |

**经验法则**：不确定用哪个时用 `broadcast`，只是可能多唤醒几个线程（它们在 `while` 中重新检查后会再次睡眠），不影响正确性。而误用 `signal` 可能导致该醒的线程没醒。

### 2.5 标准等待范式

等待方（消费者）：

```c
pthread_mutex_lock(&mutex);
while (!predicate) {
    pthread_cond_wait(&cond, &mutex);
}
// 条件已满足，持有锁，安全地修改共享状态
pthread_mutex_unlock(&mutex);
```

通知方（生产者）：

```c
pthread_mutex_lock(&mutex);
// 修改共享状态，使谓词变为 true
pthread_cond_signal(&cond);      // 或 broadcast
pthread_mutex_unlock(&mutex);
```

> [!important] signal 放在 unlock 前还是后?
> 放在 `unlock` **之前**（持锁 signal）是标准做法，语义最清晰。放在之后也能正确工作，但在某些实现上等待线程被唤醒后会立刻争锁失败再次睡眠（无谓的上下文切换）。

## 3. 信号量 (Semaphore)

### 3.1 计数信号量 vs 二元信号量

信号量内部维护一个**非负整数计数器**，两种操作围绕它工作：

| 操作 | 含义 |
|------|------|
| **P** (wait / sem_wait) | 计数 > 0 则 -1 并继续；= 0 则阻塞 |
| **V** (post / sem_post) | 计数 +1；若有线程阻塞则唤醒一个 |

- **计数信号量**：初值 > 1，表示多个可用资源（如连接池大小、缓冲区槽位数）。
- **二元信号量**：初值 = 1，功能类似互斥锁，但**没有所有权**——任何线程都能 post，不限于加锁者。

### 3.2 P/V 操作的原子性

`sem_wait` 和 `sem_post` 本身是原子的，**不需要**额外 mutex 保护。这让信号量的使用比条件变量简单，但也限制了它只能表达"计数 > 0"这一种条件。

### 3.3 信号量的"记忆"

这是信号量与条件变量最本质的区别：

- 条件变量的 `signal` **没有记忆**：若此刻没有线程在 wait，信号直接丢失。
- 信号量的 `post` **有记忆**：即使没有线程在 wait，计数仍然 +1 保留，下次 wait 立刻通过。

这意味着使用信号量时**不存在"唤醒丢失"问题**，而条件变量必须靠 `while + 谓词` 来间接防止。

## 4. 条件变量 vs 信号量 的取舍

![[图片/SVG/3_17_4_2.svg|760]]

对比总结：

| 维度 | 条件变量 | 信号量 |
|------|---------|--------|
| 内部状态 | 无 | 非负整数计数器 |
| 是否需配合锁 | 必须 | 不必 |
| 能表达的条件 | 任意谓词（`size>0 && !stop`） | 仅"计数 > 0" |
| 唤醒丢失 | 可能（signal 无记忆） | 不会（post 有记忆） |
| 批量唤醒 | broadcast | 不直接支持（需循环 post） |
| 典型场景 | 线程池、复杂生产者-消费者、状态机 | 资源池计数、并发槽位限制、简单 P-C |

**选择规则**：

- 等待条件是"某个计数 > 0"且不涉及其他共享状态 → **信号量**更简洁
- 等待条件涉及多个变量、或需要 broadcast、或需要 mutex 保护的复合判断 → **条件变量**

## 5. 生产者-消费者：两种实现对比

### 5.1 条件变量版（有界队列）

```c
pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  not_empty = PTHREAD_COND_INITIALIZER;
pthread_cond_t  not_full  = PTHREAD_COND_INITIALIZER;
int queue[CAP], head = 0, tail = 0, count = 0;

void push(int val) {
    pthread_mutex_lock(&mutex);
    while (count == CAP)
        pthread_cond_wait(&not_full, &mutex);
    queue[tail] = val;
    tail = (tail + 1) % CAP;
    count++;
    pthread_cond_signal(&not_empty);
    pthread_mutex_unlock(&mutex);
}

int pop(void) {
    pthread_mutex_lock(&mutex);
    while (count == 0)
        pthread_cond_wait(&not_empty, &mutex);
    int val = queue[head];
    head = (head + 1) % CAP;
    count--;
    pthread_cond_signal(&not_full);
    pthread_mutex_unlock(&mutex);
    return val;
}
```

### 5.2 信号量版（有界队列）

```c
sem_t empty_slots, filled_slots;
pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;
int queue[CAP], head = 0, tail = 0;

// 初始化
sem_init(&empty_slots,  0, CAP);   // 空槽位 = CAP
sem_init(&filled_slots, 0, 0);     // 已填充 = 0

void push(int val) {
    sem_wait(&empty_slots);             // P(empty)
    pthread_mutex_lock(&mutex);         // 保护队列本身
    queue[tail] = val;
    tail = (tail + 1) % CAP;
    pthread_mutex_unlock(&mutex);
    sem_post(&filled_slots);            // V(filled)
}

int pop(void) {
    sem_wait(&filled_slots);            // P(filled)
    pthread_mutex_lock(&mutex);
    int val = queue[head];
    head = (head + 1) % CAP;
    pthread_mutex_unlock(&mutex);
    sem_post(&empty_slots);             // V(empty)
    return val;
}
```

注意信号量版仍然需要 mutex——不是保护"等待-唤醒"，而是保护队列数组本身的一致性（head/tail 的读写）。两个信号量分别控制"有多少空槽位"和"有多少数据"，逻辑比条件变量版更直观。

## 6. 其他等待-通知原语

| 原语 | 层级 | 特点 |
|------|------|------|
| `futex` | Linux 内核 | 条件变量和信号量的底层实现；用户态快路径 + 内核慢路径 |
| `eventfd` | Linux 系统调用 | 可 poll/epoll 的计数器，适合跨线程唤醒 I/O 事件循环 |
| `std::condition_variable` | C++ 标准库 | RAII 封装，配合 `std::unique_lock`，支持 lambda 谓词 |
| `std::counting_semaphore` | C++20 | 标准化的计数信号量 |

`eventfd` 和 `futex` 的用法详见 [[13.7 eventfd、timerfd与跨线程唤醒]]。

## 7. 实践要点

1. **条件变量三件套不可缺**：mutex + cond + while(谓词)，少任何一个都是 bug。
2. **信号量有记忆，条件变量没有**：这是选择的核心判据。
3. **不确定用 signal 还是 broadcast 时选 broadcast**：正确性优先，多唤醒几个线程只是微小开销。
4. **signal 放在 unlock 之前**：语义清晰，避免无谓的唤醒-争锁-再睡眠。
5. **信号量版生产者-消费者仍需 mutex 保护队列**：信号量管"什么时候能操作"，mutex 管"操作时的一致性"。
6. **能用高层设施就别用 pthread**：`std::condition_variable` + `std::unique_lock` 自动管理锁，lambda 谓词一行搞定 while 循环，详见 [[17.8 Modern C++ 同步设施与实战并发模式]]。
