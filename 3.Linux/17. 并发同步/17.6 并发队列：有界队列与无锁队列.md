# 17.6 并发队列：有界队列与无锁队列

> 队列是线程间传递数据最常用的载体，是同步机制的**综合应用**。
> 综合了 [[17.3 锁机制、死锁与故障|锁]]、[[17.4 条件同步：条件变量与信号量|条件同步]]、[[17.5 无锁编程：CAS、乐观锁与悲观锁|无锁]]。
>

## 1. 生产者-消费者模型

并发队列的典型应用是**生产者-消费者模型**：一组线程生产数据放入队列，另一组线程从队列取出消费。队列在中间充当缓冲区，带来三大价值：

- **解耦**：生产者无需知道消费者是谁、有几个、处理多快；双方只依赖队列接口。
- **削峰**：突发流量先堆积在队列中缓冲，消费者按自身节奏处理，避免被瞬时高峰冲垮。
- **异步**：生产者投递后即可返回，不必等待消费完成。

> 线程池正是这一模型的经典落地：任务队列是生产者-消费者队列，工作线程是消费者。见 [[12.7 条件变量与线程池]]。

并发队列的实现可分两大流派：**基于锁的阻塞队列**（简单通用）与**无锁队列**（高吞吐低延迟）。下面分别展开。

---

## 2. 基于锁的阻塞队列 (BlockingQueue)

核心思想：用一把 `mutex` 保护内部容器，用**条件变量**让线程在"队列空/满"时阻塞等待，而非忙等轮询。

### 2.1 无界阻塞队列

只需一个条件变量 `notEmpty`：消费者在队列空时等待，生产者放入数据后唤醒。

```cpp
template <typename T>
class BlockingQueue {
public:
    void put(T x) {
        std::lock_guard<std::mutex> lock(mutex_);
        queue_.push_back(std::move(x));
        notEmpty_.notify_one();           // 唤醒一个等待的消费者
    }

    T take() {
        std::unique_lock<std::mutex> lock(mutex_);
        notEmpty_.wait(lock, [this] { return !queue_.empty(); });  // 谓词防虚假唤醒
        T front = std::move(queue_.front());
        queue_.pop_front();
        return front;
    }

private:
    std::mutex mutex_;
    std::condition_variable notEmpty_;
    std::deque<T> queue_;
};
```

要点：

- `wait` 必须配**谓词**（lambda 版本），自动循环检查条件，规避**虚假唤醒**（spurious wakeup）。见 [[17.4 条件同步：条件变量与信号量]]。
- "无界"意味着生产者从不阻塞——但若消费者跟不上，队列会**无限膨胀**，最终耗尽内存。这正是需要有界队列的原因。

### 2.2 有界阻塞队列 (BoundedQueue)

在无界版本上增加容量上限，并引入第二个条件变量 `notFull`：**队列满时阻塞生产者**。两个条件变量分工明确——

![[图片/3.Linux/17. 并发同步/3_17_6_1.svg]]

```cpp
template <typename T>
class BoundedQueue {
public:
    explicit BoundedQueue(size_t cap) : capacity_(cap) {}

    void put(T x) {
        std::unique_lock<std::mutex> lock(mutex_);
        notFull_.wait(lock, [this] { return queue_.size() < capacity_; });  // 满则等待
        queue_.push_back(std::move(x));
        notEmpty_.notify_one();
    }

    T take() {
        std::unique_lock<std::mutex> lock(mutex_);
        notEmpty_.wait(lock, [this] { return !queue_.empty(); });           // 空则等待
        T front = std::move(queue_.front());
        queue_.pop_front();
        notFull_.notify_one();            // 腾出空位，唤醒生产者
        return front;
    }

private:
    std::mutex mutex_;
    std::condition_variable notEmpty_;    // 队列非空 → 消费者可取
    std::condition_variable notFull_;     // 队列非满 → 生产者可放
    std::deque<T> queue_;
    const size_t capacity_;
};
```

**反压 (back pressure)**：有界队列最重要的工程价值。队列满时阻塞生产者，等于给上游施加"减速"压力，强制生产速率向消费速率收敛。这避免了无界队列在生产快于消费时的内存爆炸，是构建稳定流式系统的关键。

> 两个条件变量共用同一把 `mutex`。注意 `notify` 唤醒的是"对侧"角色：`put` 后唤醒消费者（`notEmpty_`），`take` 后唤醒生产者（`notFull_`）。

## 3. 无锁队列 (Lock-Free Queue)

锁队列在高并发下的瓶颈是**锁竞争**：所有线程争抢同一把锁，大量时间耗在阻塞与上下文切换。无锁队列改用**原子操作 + CAS** 协调，线程永不睡眠，靠重试推进，从而获得更高吞吐和更稳定的延迟。

代价是**实现难度陡增**：要精确处理内存序、ABA 问题与节点回收。先从最简单的 SPSC 讲起。

### 3.1 单生产者单消费者 (SPSC) 环形缓冲

只有**一个生产者**和**一个消费者**时，问题大大简化：读写各占一端，天然无写写冲突，因此**完全不需要 CAS**，仅靠一对 `acquire`/`release` 内存序即可正确同步。

实现用**环形缓冲（ring buffer）**：定长数组 + 两个下标 `head`（消费者读位）、`tail`（生产者写位），下标到末尾后回绕（取模）。

![[图片/3.Linux/17. 并发同步/3_17_6_2.svg]]

```cpp
template <typename T, size_t N>
class SpscRing {
public:
    bool push(const T& v) {
        const size_t t = tail_.load(std::memory_order_relaxed);
        const size_t next = (t + 1) % N;
        if (next == head_.load(std::memory_order_acquire))  // 满
            return false;
        buffer_[t] = v;                                     // ① 先写数据
        tail_.store(next, std::memory_order_release);       // ② 再发布新 tail
        return true;
    }

    bool pop(T& out) {
        const size_t h = head_.load(std::memory_order_relaxed);
        if (h == tail_.load(std::memory_order_acquire))     // 空
            return false;
        out = buffer_[h];                                   // 读数据
        head_.store((h + 1) % N, std::memory_order_release);
        return true;
    }

private:
    std::array<T, N> buffer_;
    std::atomic<size_t> head_{0};
    std::atomic<size_t> tail_{0};
};
```

**关键在 acquire/release 配对**：生产者**先写数据、后用 release 发布 tail**；消费者用 **acquire 读 tail**。release-acquire 建立 happens-before 关系，保证消费者一旦看到新的 `tail`，对应槽位的数据**必然已写完**——绝不会读到半成品。这是无锁正确性的基石，详见 [[17.2 原子性、可见性与内存序]]。

> 实际高性能实现还会做**缓存行对齐**：把 `head_` 与 `tail_` 分置不同缓存行（`alignas(64)`），避免生产者与消费者因**伪共享**（false sharing）互相拖累。

### 3.2 MPMC 队列

多生产者多消费者时，两端都有并发写，必须用 CAS 仲裁。经典方案是 **Michael-Scott 队列**（基于带哨兵节点的单链表）：

![[图片/3.Linux/17. 并发同步/3_17_6_3.svg]]

- **哨兵节点（dummy）**：链表始终保留一个空头节点，使空队列与非空队列的逻辑统一，简化边界处理。
- **入队**：在尾部用 `CAS(tail->next, nullptr → newNode)` 接入新节点，成功后再 CAS 推进 `Tail`。
- **出队**：用 `CAS(Head, head → head->next)` 推进头指针，返回原 `head->next` 的数据。
- CAS 失败说明有其他线程抢先，**重试**即可——无线程阻塞。

**两大难点**（详见 [[17.5 无锁编程：CAS、乐观锁与悲观锁]]）：

- **ABA 问题**：指针值从 A 变 B 又变回 A，单纯的 CAS 无法察觉中途的变化。解法：带版本号的**标签指针**（tagged pointer）。
- **内存回收**：一个线程要 `delete` 节点时，可能仍有别的线程持有该节点指针。不能裸 `delete`，需用 **hazard pointer**、**RCU** 或带标签指针等安全回收方案。

### 3.3 内存序的精细使用

无锁队列的正确性完全建立在**内存序**之上，需按"够用即可"的原则精细选择，既保证正确又不过度同步：

| 操作 | 推荐内存序 | 理由 |
|------|-----------|------|
| 读自己独占的下标 | `relaxed` | 单线程内无需同步 |
| 发布数据（store 标志/下标） | `release` | 确保此前的写对读者可见 |
| 读取对方发布的标志/下标 | `acquire` | 与 release 配对，建立 happens-before |
| 需要全局顺序的罕见场景 | `seq_cst` | 最强但最慢，非必要不用 |

> 原理详见 [[17.2 原子性、可见性与内存序]]。一句话：**relaxed 用于私有，release/acquire 用于配对发布，seq_cst 留给确实需要全局序的场合**。

## 4. 队列选型对比

| 队列 | 吞吐 | 延迟 | 实现难度 | 适用 |
|------|------|------|---------|------|
| 锁阻塞队列 | 中 | 中 | 低 | 通用、生产消费速率相近 |
| SPSC 无锁 | 高 | 低 | 中 | 严格单对单（如网络收发线程） |
| MPMC 无锁 | 高 | 低 | 高 | 高并发、多对多 |

**选型经验法则：**

1. **默认用锁阻塞队列**。绝大多数场景下它足够快、足够简单、不易出错。需要反压就用有界版。
2. 确认是**严格单生产者单消费者**且对延迟敏感 → SPSC 环形缓冲，性价比极高。
3. 只有在**实测证明锁竞争是瓶颈**、且并发度很高时，才考虑 MPMC 无锁队列——它的正确性极难验证，维护成本高。

> **不要为了"无锁"而无锁**。无锁不等于更快（CAS 重试在高竞争下也会浪费 CPU），更不等于无饥饿。先用锁队列跑通、压测，确有瓶颈再优化。
