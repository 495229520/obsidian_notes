# 17.8 Modern C++ 同步设施与实战并发模式

> 前面几节多用 pthread（C 风格）讲原理，便于看清底层机制。但**工程实践应使用 `<thread>` / `<mutex>` / `<atomic>` 等标准库设施**，并用 **RAII** 自动管理锁的生命周期；再把这些原语组合成可复用的**工程模式**——它们是高性能服务器的基石。
> 本节是 17 章的收尾：把原理落到 Modern C++ 写法与实战套路上。关联 [[13.6 Reactor模式与EventLoop]]。

---

## 一、Modern C++ 同步设施与 RAII

### 1. 为什么用 RAII 管理锁

手动 `mtx.lock()` / `mtx.unlock()` 有一个致命缺陷：**异常或提前 `return` 会跳过 `unlock`**，留下一把永不释放的锁，导致死锁。RAII（资源获取即初始化）把"解锁"绑定到栈对象的析构函数上——无论函数怎样退出（正常返回、`break`、抛异常），栈展开都会调用析构，锁必被释放。

![[图片/3.Linux/17. 并发同步/3_17_8_1.svg]]

```cpp
// ❌ 手动管理：异常路径泄漏锁
mtx.lock();
process();            // 若抛异常，下一行不执行 → 死锁
mtx.unlock();

// ✅ RAII：构造即加锁，析构（含异常栈展开）即解锁
{
    std::lock_guard<std::mutex> lk(mtx);
    process();        // 抛异常也会在离开作用域时自动解锁
}
```

> 这正是 *Effective Modern C++* 反复强调的：**让对象的生命周期替你管理资源**。锁、文件、socket 同理。

### 2. 锁包装器

标准库提供一族 RAII 锁包装器，按"需要多少控制力"选择——**能用 `lock_guard` 就别用 `unique_lock`**，越简单越不易错：

| 包装器 | 特点 | 典型场景 |
|--------|------|---------|
| `std::lock_guard` | 最简、不可移动、不可手动解锁 | 简单临界区 |
| `std::unique_lock` | 可延迟加锁 / 中途解锁 / 转移所有权 | 配合条件变量、需手动控制 |
| `std::scoped_lock` (C++17) | 一次锁多个互斥量，内部用免死锁算法 | 同时持有多把锁 |
| `std::shared_lock` (C++14) | 共享（读）锁 | 配合 `std::shared_mutex` |

```cpp
std::scoped_lock lk(mtxA, mtxB);   // 同时锁两把，自动避免 AB/BA 死锁
```

> `scoped_lock` 用统一加锁算法规避了"两个线程以相反顺序加锁"的经典死锁，见 [[17.3 锁机制、死锁与故障]]。

### 3. 互斥量家族

| 互斥量 | 用途 |
|--------|------|
| `std::mutex` | 最常用的基本互斥量 |
| `std::recursive_mutex` | 同一线程可重复加锁（应尽量避免——往往是设计有问题的信号） |
| `std::timed_mutex` | 支持 `try_lock_for` / `try_lock_until` 超时获取 |
| `std::shared_mutex` (C++17) | 读写锁：多读共享、写独占 |

### 4. 条件变量

`std::condition_variable` 必须配 `std::unique_lock`（因为 `wait` 内部要临时解锁再重新加锁）。**永远用带谓词的重载**，它自动循环检查条件，规避虚假唤醒：

```cpp
std::unique_lock<std::mutex> lk(mtx);
cv.wait(lk, [&]{ return !queue.empty(); });   // 谓词为真才返回
```

> 原理与"虚假唤醒""惊群"对照 [[17.4 条件同步：条件变量与信号量]]。

### 5. 原子与一次性初始化

- `std::atomic<T>`：无锁原子量，配合内存序使用，见 [[17.5 无锁编程：CAS、乐观锁与悲观锁]]。
- `std::call_once` + `std::once_flag`：保证某初始化**全程仅执行一次**，线程安全，是实现懒加载的利器。
- **C++20 协调原语**：`std::counting_semaphore`（计数信号量）、`std::latch`（一次性倒计时门闩）、`std::barrier`（可重复的栅栏，多线程在此集合后齐步前进）。

```cpp
std::once_flag flag;
void init() { std::call_once(flag, []{ /* 只执行一次 */ }); }
```

### 6. 任务级并发

不必事事手动开线程。`std::async` 把"启动任务"和"取回结果"封装好，`std::future` 负责异步取值：

```cpp
std::future<int> fut = std::async(std::launch::async, []{ return compute(); });
int result = fut.get();   // 阻塞直到结果就绪（异常也会在此处重新抛出）
```

- `std::promise` / `std::future`：手动设置/获取一个将来才有的值，可跨线程传递结果或异常。
- `std::packaged_task`：把可调用对象包装成"可投递到线程池执行、结果用 future 取回"的任务。

### 7. 对接项目规范

> 遵循仓库 `CLAUDE.md`：**RAII 优先、禁止裸 `new/delete`、用 `std::make_unique`/`nullptr`/`std::vector`、并发遵循 muduo 的 Reactor 模式**。本节所有示例均为此风格。

## 二、实战并发模式

> 把上面的原语组合成可复用的工程套路。核心心法只有一句：**能不共享就不共享，必须共享时把临界区压到最小。**

### 1. 生产者-消费者 / 线程池

最基础也最重要的并发结构：任务队列解耦生产与消费，工作线程池消费任务。它是 §6 异步、Reactor 多线程模型的底座。

> 完整实现见 [[12.7 条件变量与线程池]] 与 [[17.6 并发队列：有界队列与无锁队列]]——后者讨论了有界队列的**反压**与无锁队列的取舍。

### 2. 线程安全的单例

懒汉式单例的天真写法 `if (!instance) instance = new T;` 在多线程下是数据竞争。即便加上"双重检查锁定（DCLP）"，**朴素版本仍可能因指令重排出错**：`instance = new T` 实际分三步——分配内存、构造对象、把地址写入指针，编译器/CPU 可能把"写指针"重排到"构造"之前。

![[图片/3.Linux/17. 并发同步/3_17_8_2.svg]]

于是另一线程可能看到 `instance` 非空，却拿到一个**尚未构造完成**的对象，引发未定义行为。三种正确写法：

```cpp
// ✅ 推荐：C++11 magic static —— 局部静态变量的初始化由标准保证线程安全
Singleton& instance() {
    static Singleton inst;   // 首次进入时线程安全地初始化一次
    return inst;
}

// ✅ 备选：call_once
Singleton* g = nullptr;
std::once_flag flag;
Singleton& instance2() {
    std::call_once(flag, []{ g = new Singleton(); });
    return *g;
}
```

> **首选 magic static**：最简洁，零额外同步开销（编译器用高效的 guard 变量实现）。需要手写 DCLP 时，必须用 `std::atomic<T*>` 配 release/acquire 内存序，原理见 [[17.5 无锁编程：CAS、乐观锁与悲观锁]]。

### 3. 读多写少优化

当数据**读远多于写**时，让读者也去抢互斥锁非常浪费。几种递进的优化：

- **读写锁** `std::shared_mutex`：读用 `shared_lock` 并发、写用 `unique_lock` 独占。简单直接，但写者仍会阻塞所有读者，写频繁时反而更慢。
- **双缓冲 / `shared_ptr` 原子替换**：读者无锁地 `load` 当前快照的 `shared_ptr`；写者构造一份**新副本**，改完后**原子替换**指针。新读者看到新版，旧读者继续安全地读旧版，旧版在最后一个引用释放时自动回收。

![[图片/3.Linux/17. 并发同步/3_17_8_3.svg]]

```cpp
std::atomic<std::shared_ptr<const Config>> cfg;   // C++20 atomic<shared_ptr>

// 读者：无锁
auto snap = cfg.load();
use(*snap);

// 写者：拷贝—修改—原子换
auto next = std::make_shared<Config>(*cfg.load());
next->update();
cfg.store(next);
```

- **RCU（Read-Copy-Update）**：上述思想的极致形态，读侧几乎零开销，广泛用于内核。用户态可用专门库实现。

> 双缓冲的代价是写者一次完整拷贝，**适合配置热更新这类"读极多、写极少、可容忍读到稍旧数据"的场景**。

### 4. 每线程数据（Thread-Local）

**最好的同步是不共享**。把状态做成线程私有，就根本不需要锁：

- `thread_local`：声明线程局部存储，每个线程一份独立实例（如线程级日志缓冲、随机数引擎）。
- `pthread_key_t`：C 风格的等价物，现代代码优先用 `thread_local`。

```cpp
thread_local std::mt19937 rng{std::random_device{}()};   // 每线程独立，无需加锁
```

### 5. 无共享架构（Share-Nothing）

把"不共享"上升为架构原则：**每个线程独占一个 EventLoop**，连接被分发到固定线程上处理，线程间几乎不共享可变状态，自然消除了绝大部分锁。这就是 muduo 的 **one loop per thread** 模型。

```
                 ┌── EventLoop 线程 1 ── 连接 A、B …
   acceptor ────►├── EventLoop 线程 2 ── 连接 C、D …
                 └── EventLoop 线程 3 ── 连接 E、F …
```

> 详见 [[13.6 Reactor模式与EventLoop]]。跨线程协作时不直接加锁操作对方数据，而是用 `runInLoop`/任务队列把操作**派发回属主线程**执行。

### 6. 异步与 Future

用 `std::future` / `std::promise` 做任务编排，把"计算"和"取结果"解耦，避免回调层层嵌套的"回调地狱"。线程池配合 `std::packaged_task` 可实现"投递任务→拿 future→需要时再 `get`"的清爽风格。

### 7. 反模式与陷阱清单

| 反模式 | 后果 | 对策 |
|--------|------|------|
| 持锁调用用户回调 | 回调里再加锁 → 死锁；行为不可控 | 拷贝出数据后**先解锁再回调** |
| 持锁做耗时 IO / 阻塞调用 | 锁被长期占用，并发度暴跌 | 锁外做 IO，锁内只改内存 |
| 锁粒度过粗 / 过细 | 过粗失并发，过细易死锁且开销大 | 按数据划分，临界区只包"必须保护的" |
| 伪共享（false sharing） | 不同变量共享 cache line，跨核反复失效 | `alignas(64)` / padding 分行 |

伪共享尤其隐蔽——代码看不出任何共享，性能却莫名很差：

![[图片/3.Linux/17. 并发同步/3_17_8_4.svg]]

```cpp
struct alignas(64) Counter { std::atomic<long> n{0}; };  // 各占一条 cache line
Counter counters[N];   // 不同线程写 counters[i].n 互不干扰
```

> 一句话总结全节：**优先无共享（thread_local / share-nothing）；必须共享则用 RAII 锁把临界区压到最小；读多写少上读写锁或双缓冲；任何锁内都不要做 IO 或调用外部回调。**
