# 17.7 进程间同步

> 前面几节的锁、条件变量、原子量都默认作用于**同一进程内的多个线程**——因为它们天然共享同一片地址空间。一旦跨越进程边界，地址空间相互隔离，这些原语就不再"开箱即用"：同步状态必须被安置到**两个进程都能访问的地方**（内核对象或共享内存）。
> 本节承接 [[11.2 进程间通信IPC]]、[[11.4 共享内存]]、[[11.5 信号量]]、[[11.6 消息队列]]，从同步的视角把它们串起来。

---

## 1. 为什么进程间同步更难

线程间同步之所以简单，是因为同一进程的所有线程共享地址空间：一个放在堆或全局区的 `pthread_mutex_t`，每个线程都能直接寻址到同一个对象。进程则不同——各自拥有**私有的虚拟地址空间**，一个进程里普通变量的地址在另一个进程里毫无意义。

![[图片/SVG/3_17_7_1.svg]]

这带来两个必须正面解决的问题：

- **状态承载**：同步原语（锁、条件变量、信号量计数）的内部状态必须放在共享区——内核对象，或两进程都 `mmap` 的共享内存。普通 `pthread_mutex_t` 默认属性是 `PTHREAD_PROCESS_PRIVATE`，即使你把它放进共享内存，不改属性也无法跨进程工作。
- **崩溃健壮性**：线程崩溃通常整个进程一起退出，问题相对简单；而进程是独立的失败单元，**持锁进程可能突然崩溃**，留下一把永远不会被释放的锁，导致其他进程永久阻塞。因此跨进程锁还要考虑"持有者死亡"的善后（见 §3 的 robust mutex）。

> 一句话：进程间同步 = **找一块共享的地方放同步状态** + **处理某个进程中途死亡**。

---

## 2. 两套 API：System V vs POSIX

Linux 上的 IPC 同步设施有两套历史包袱不同的接口。它们功能重叠，但风格、命名、生命周期管理差别很大：

| 设施 | System V | POSIX |
|------|----------|-------|
| 信号量 | `semget` / `semop` | `sem_open` / `sem_wait` |
| 共享内存 | `shmget` / `shmat` | `shm_open` / `mmap` |
| 消息队列 | `msgget` / `msgsnd` | `mq_open` / `mq_send` |
| 命名方式 | 整数 `key`（常用 `ftok` 生成） | 文件式名字 `"/myobj"` |
| 生命周期 | 内核持久，需 `ipcrm` 手动清理 | 引用计数，`shm_unlink` 后无人引用即回收 |
| 查看工具 | `ipcs` / `ipcrm` | `ls /dev/shm` |

**经验上优先选 POSIX**：名字直观（类文件路径）、与 `mmap`/文件描述符体系一致、生命周期语义清晰、更易与现代代码集成。System V 接口设计古老（`semop` 的 `union semun` 还得自己定义），仅在维护老代码或特定平台约束时才用。

> 各设施的数据通信细节见 [[11.5 信号量]]、[[11.4 共享内存]]、[[11.6 消息队列]]；本节聚焦它们作为**同步原语**的用法。

## 3. 共享内存 + 进程共享 pthread 原语

这是最贴近线程编程心智模型的方案：把 `pthread_mutex_t` / `pthread_cond_t` **放进共享内存**，并显式设置 `PTHREAD_PROCESS_SHARED` 属性，于是两个进程就能像两个线程一样使用同一把锁。

![[图片/SVG/3_17_7_2.svg]]

关键在于：两个进程通过 `mmap` 把**同一块物理内存**映射进各自地址空间（虚拟地址可以不同），锁对象就活在这块共享物理页里。

```cpp
struct Shared {
    pthread_mutex_t mtx;
    pthread_cond_t  cond;
    int             ready;     // 受 mtx 保护的业务数据
};

// 创建者进程：建立共享内存并初始化同步原语（只做一次）
int fd = shm_open("/demo_sync", O_CREAT | O_RDWR, 0600);
ftruncate(fd, sizeof(Shared));
auto* sh = static_cast<Shared*>(
    mmap(nullptr, sizeof(Shared), PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0));

pthread_mutexattr_t ma;
pthread_mutexattr_init(&ma);
pthread_mutexattr_setpshared(&ma, PTHREAD_PROCESS_SHARED);  // ★ 跨进程关键
pthread_mutexattr_setrobust(&ma, PTHREAD_MUTEX_ROBUST);     // ★ 健壮锁
pthread_mutex_init(&sh->mtx, &ma);

pthread_condattr_t ca;
pthread_condattr_init(&ca);
pthread_condattr_setpshared(&ca, PTHREAD_PROCESS_SHARED);   // 条件变量同样要设
pthread_cond_init(&sh->cond, &ca);
```

其它进程只需 `shm_open` 同名对象并 `mmap`，**不再重复初始化**，直接 `pthread_mutex_lock(&sh->mtx)` 即可。

**健壮锁（robust mutex）解决崩溃问题**：设置 `PTHREAD_MUTEX_ROBUST` 后，若持锁进程死亡，下一个 `lock` 的进程会收到返回值 `EOWNERDEAD`——它得知"上一任持有者死在临界区里"，可以修复被破坏的共享数据，再调用 `pthread_mutex_consistent` 把锁恢复成可用状态：

```cpp
int rc = pthread_mutex_lock(&sh->mtx);
if (rc == EOWNERDEAD) {
    // 上一个持有者崩溃，共享数据可能处于不一致的中间态
    repair_invariants(sh);                 // 修复业务不变量
    pthread_mutex_consistent(&sh->mtx);    // 声明锁重新可用
}
```

> 不用 robust 锁时，持锁进程一崩溃，这把锁就**永久死锁**——这是进程间同步区别于线程间同步最容易踩的坑。

## 4. 内核信号量

若只需"计数型"协调（限制并发数、生产者-消费者配额），跨进程**信号量**比裸 mutex 更直接，且状态完全由内核维护，天然不受某个进程崩溃影响（计数仍在内核里）。

- **POSIX 命名信号量**：`sem_open("/name", O_CREAT, 0600, initVal)` 拿到一个跨进程可见的信号量，`sem_wait` / `sem_post` 即 P/V 操作，语义和线程信号量完全一致。
- **System V 信号量**：`semget` + `semop`，支持"信号量集合"和一次原子操作多个信号量，功能更强但接口繁琐。

```cpp
sem_t* sem = sem_open("/slots", O_CREAT, 0600, 3);  // 最多 3 个并发
sem_wait(sem);          // P：占用一个名额（不足则阻塞）
// ... 访问受限资源 ...
sem_post(sem);          // V：归还名额
```

原理与 P/V 语义详见 [[17.4 条件同步：条件变量与信号量]] 与 [[11.5 信号量]]；这里只需记住：**它是放在内核里的计数器，跨进程天然可见**。

## 5. 文件锁 (File Lock)

文件锁不依赖共享内存，而是借助**文件**这一所有进程都能命名的公共资源来协调。适合"多个进程协调访问同一文件/资源"的经典场景。

### 5.1 `flock`：整文件劝告锁

`flock(fd, LF_SH | LF_EX | LF_UN)` 对**整个文件**加共享锁（读锁）或排他锁（写锁），接口最简单。锁与**打开文件表项**关联，`dup` 出的 fd 共享同一把锁。注意它在 NFS 等网络文件系统上行为不可靠。

### 5.2 `fcntl` 记录锁：字节范围锁

`fcntl` 提供更细粒度的**记录锁（record lock）**：锁定文件的**某一段字节区间**而非整个文件，不同进程因此可以并发操作互不重叠的区间。

![[图片/SVG/3_17_7_3.svg]]

```cpp
struct flock fl{};
fl.l_type   = F_WRLCK;      // 写锁（排他）；读锁用 F_RDLCK
fl.l_whence = SEEK_SET;
fl.l_start  = 0;            // 起始偏移
fl.l_len    = 1024;         // 长度（0 表示到 EOF）

fcntl(fd, F_SETLKW, &fl);   // F_SETLKW 阻塞等待；F_SETLK 非阻塞（冲突即 EAGAIN）
// ... 安全访问 [0, 1024) 区间 ...
fl.l_type = F_UNLCK;
fcntl(fd, F_SETLK, &fl);    // 解锁
```

规则：**读锁可共享、写锁排他**；只有当区间**重叠且至少一方是写锁**时才冲突。

> ⚠️ **传统 `fcntl` 记录锁有个著名陷阱**：锁与"进程 + inode"绑定，而非与 fd 绑定。只要该进程**关闭了指向此文件的任意一个 fd**，所有锁就会全部释放——库代码不经意 `close` 一个无关 fd 就可能误删你的锁。Linux 后来引入 **OFD 锁**（`F_OFD_SETLK`，open file description lock）修正了这一点：锁与打开文件描述本身绑定，行为更符合直觉，新代码应优先使用。

### 5.3 劝告锁 vs 强制锁

- **劝告锁（advisory）**：内核只记录锁状态，**不强制**——只有同样主动检查锁的进程才会被挡住。绕过加锁直接读写文件完全可行。`flock` 和 `fcntl` 默认都是劝告锁，**依赖所有参与者的自觉约定**。
- **强制锁（mandatory）**：内核在 `read`/`write` 时强制检查。但实现历史包袱重、行为有竞态、需特殊挂载选项，现代内核已基本弃用，**不要依赖**。

> 实践中几乎总是用劝告锁，前提是所有访问方都遵守"先加锁再访问"的约定。

## 6. 其它跨进程协调手段

并非所有协调都需要"锁"——有时只需要一个**事件通知**：

- **`pipe` / `eventfd`**：一个进程写入、另一个进程在 `read` 上阻塞，天然实现"等待—唤醒"，还能轻松接入 `epoll` 事件循环。`eventfd` 比管道更轻量，专为事件计数设计。见 [[11.3 管道通讯]]。
- **信号（signal）**：`kill` 发送、信号处理器接收，可做最粗粒度的异步通知，但能携带的信息少、异步安全约束多，不适合高频或精细同步。
- **futex**：上层 `pthread`/信号量在 Linux 上的**底层基石**。它把"无竞争时纯用户态原子操作、有竞争时才陷入内核排队"结合起来。一般不直接用，了解其存在有助于理解上层原语为何高效。

## 7. 选型对比

| 方案 | 粒度 | 崩溃健壮性 | 适用场景 |
|------|------|-----------|---------|
| 共享内存 + pshared mutex/cond | 细（任意临界区） | 需 robust 锁兜底 | 高频、复杂临界区，最接近线程编程 |
| 内核信号量（POSIX/SysV） | 计数 | 好（状态在内核） | 限并发数、配额、生产消费 |
| `fcntl` / OFD 记录锁 | 文件字节区间 | 好（进程退出自动释放） | 多进程协调访问同一文件 |
| `pipe` / `eventfd` / 信号 | 事件通知 | 好 | 仅需"通知"而非"互斥" |

**经验法则：**

1. **只需通知** → 用 `eventfd`/管道，能接入事件循环，最简单。
2. **限制并发数 / 配额** → 用命名信号量，状态在内核、天生抗崩溃。
3. **复杂共享数据 + 高频互斥** → 共享内存 + `PTHREAD_PROCESS_SHARED` 锁，但**务必配 robust 锁**处理持有者死亡。
4. **协调访问文件** → `fcntl`/OFD 记录锁，进程退出自动释放，省心。

> 进程间同步的两大额外成本始终是**共享状态的承载**与**崩溃善后**。线程间不必操心的"持有者突然消失"，在进程间是常态，选型时优先考虑这一点。

---

## 关键要点

- 普通 `pthread_mutex` 默认 `PTHREAD_PROCESS_PRIVATE`，**不可跨进程**；放进共享内存并设 `PTHREAD_PROCESS_SHARED` 才生效。
- 进程是独立失败单元，**持锁崩溃**会留下死锁——用 **robust 锁**（`EOWNERDEAD` + `pthread_mutex_consistent`）兜底。
- 内核信号量状态在内核，跨进程可见且抗崩溃，适合计数型协调。
- `fcntl` 记录锁按**字节区间**加锁、读共享写排他；传统版有"关闭任意 fd 即释放"陷阱，新代码用 **OFD 锁**。
- 文件锁多为**劝告锁**，依赖所有参与方自觉先加锁。
- 仅需通知时，`eventfd`/管道/信号比锁更轻量。
