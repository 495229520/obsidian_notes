# 17.5 无锁编程：CAS、乐观锁与悲观锁

> 锁会带来阻塞、上下文切换、死锁风险。无锁 (lock-free) 编程用**原子操作**直接更新共享状态。
> 而**乐观锁 / 悲观锁不是某种具体的锁，而是两种处理并发冲突的"策略思想"**：悲观锁落地为互斥锁，乐观锁落地为 CAS / 版本号。无锁编程几乎都是乐观策略的指令级形态。
> 底层依赖 [[17.2 原子性、可见性与内存序]]。

## 一、乐观锁与悲观锁：两种冲突策略

### 1. 核心区别：对"冲突概率"的假设

| | 悲观锁 (Pessimistic) | 乐观锁 (Optimistic) |
|--|---------------------|--------------------|
| 基本假设 | **冲突经常发生** | **冲突很少发生** |
| 策略 | 先加锁，独占后再访问 | 不加锁，提交时**检测**冲突 |
| 访问前 | 阻塞等待获取锁 | 直接读取，记录版本 |
| 提交时 | 直接写，写完解锁 | 校验版本，未变才写，变了**重试** |
| 开销来源 | 加锁/解锁、阻塞、上下文切换 | 失败重试、CPU 自旋 |
| 适用 | 写多、冲突频繁、临界区长 | 读多写少、冲突罕见 |

> 一句话：**悲观锁"先防后用"，乐观锁"先用后查"。**

![[图片/3.Linux/17. 并发同步/3_17_5_1.svg]]

如图，悲观锁把"防冲突"前置到访问之前（加锁独占），乐观锁把"查冲突"后置到提交之时（校验版本）。注意它们都不是某个具体的锁类型，而是**面对并发冲突时的两种态度**，再分别落地为不同的机制。

### 2. 悲观锁 (Pessimistic Lock)

- **思想**：假设"只要不锁住，别人就会来捣乱"，所以访问共享资源前先独占。
- **并发编程中的体现**：[[17.3 锁机制、死锁与故障|互斥锁、自旋锁、读写锁]]、[[12.3 互斥量|pthread_mutex]] / `std::mutex`
- **数据库中的体现**：`SELECT ... FOR UPDATE`（行锁）、表锁，事务期间持锁，其他事务阻塞

> 编程里的 `lock_guard` 与数据库的 `FOR UPDATE` 本质同构：都是**进入临界区前先拿到独占权**，没拿到就阻塞等待。

### 3. 乐观锁 (Optimistic Lock)

- **思想**：假设"大概率没人跟我抢"，先不加锁地干，**提交时**再确认期间数据没被改过。

**(1) 版本号 / 时间戳（数据级）**
```text
读取: value, version
计算: new_value
提交: UPDATE ... SET value=new_value, version=version+1
      WHERE id=? AND version=旧version
      -> 影响行数=0 说明被人改过 -> 重试
```

下图是两个事务并发改同一行的典型时序：都读到 `version=5`，**先提交者成功并把版本推进到 6**，后提交者因 `WHERE version=5` 匹配不到行（影响 0 行）而失败、重试。

![[图片/3.Linux/17. 并发同步/3_17_5_2.svg]]

`UPDATE ... SET version=version+1 WHERE version=旧值` 这一句之所以可靠，是因为数据库保证它**原子**地完成"比较旧版本 + 写新值"——这正是 CAS 在数据层的等价物。

**(2) CAS（硬件级乐观锁）** —— `compare_exchange` 就是乐观锁的指令级形态（详见本节第二部分）

- **失败后的重试**：自旋重试 / 退避 (backoff) / 限次后转悲观

### 4. 如何选择

```text
读多写少、冲突罕见   -> 乐观锁（重试代价低）
写多、冲突频繁       -> 悲观锁（重试代价高，不如直接锁）
临界区很长/含阻塞IO  -> 悲观锁（自旋重试浪费 CPU）
临界区极短          -> 乐观锁 / 自旋
```

> **冲突率是分水岭**：乐观锁的总成本 ≈ 单次操作 × (1 + 平均重试次数)。冲突罕见时重试次数趋近 0，几乎零开销；一旦冲突频繁，重试次数飙升，大量 CPU 空转重算——此时不仅没省下锁开销，还可能多个线程互相"挤掉"对方的提交，进展极慢，逼近**活锁 (livelock)**。工程上常用**指数退避**或**限次后转悲观**来止损。

## 二、无锁编程与 CAS

> 无锁是乐观策略在指令级的落地：用 `std::atomic` + CAS 直接更新共享状态，不进内核。

### 1. 为什么要无锁

- 避免阻塞与上下文切换
- 无死锁、对实时性友好
- 代价：编程难度极高、易出错

### 2. 原子操作

- `std::atomic<T>`：对 `T` 的读、写、读-改-写都保证原子性，配合内存序控制可见性（见 [[17.2 原子性、可见性与内存序]]）。
- `is_lock_free()` / `is_always_lock_free`：判断该类型的原子操作是否由**硬件原子指令**实现，而非编译器偷偷加锁。
  - 整数、指针等"机器字大小"的类型几乎总是 lock-free；
  - 较大的结构体（超过一两个机器字）可能退化为带锁实现——此时"无锁编程"名存实亡，务必检查。

```cpp
static_assert(std::atomic<int>::is_always_lock_free);   // 编译期即可确认
```

### 3. CAS：比较并交换 (Compare-And-Swap)

CAS 是几乎所有无锁算法的基石：它把"比较旧值"和"写入新值"压成**一条不可分割的硬件指令**（x86 上是 `lock cmpxchg`），从而实现乐观锁的"提交时校验"。

#### 3.1 语义
```cpp
// 伪代码：整体原子完成
bool CAS(T* addr, T expected, T desired) {
    if (*addr == expected) { *addr = desired; return true; }
    return false;
}
```

C++ 的对应接口会在**失败时把 `expected` 更新为内存的当前值**，这一点是写 CAS 循环的关键：

```cpp
std::atomic<int> a;
// bool compare_exchange_strong(T& expected, T desired, ...);
// 成功: *this==expected 时写入 desired，返回 true
// 失败: 不写，且把 expected 改写为 *this 的当前值，返回 false
```

#### 3.2 `compare_exchange_weak` vs `strong`

| | `_strong` | `_weak` |
|--|-----------|---------|
| 语义 | 值匹配就一定成功 | 值匹配也**可能伪失败 (spurious fail)** |
| 来源 | 屏蔽底层 LL/SC 的伪失败 | 直接暴露 LL/SC，开销更低 |
| 用法 | 不在循环里时用它 | **写在循环里时优先用它** |

- **伪失败**：在 ARM、PowerPC 等用 **LL/SC**（Load-Linked / Store-Conditional）实现 CAS 的平台上，即使值没变，缓存行被其他核"碰过"也可能让 SC 失败。`weak` 不去额外屏蔽这种失败，因此单次更快。
- 既然循环本来就要重试，伪失败再转一圈即可——所以**循环内用 `weak`，单次判断用 `strong`**。在 x86 上两者生成的代码基本一致。

#### 3.3 CAS 循环更新范式

任何"读-改-写"都能改写成下面这个无锁范式：读当前值 → 算新值 → CAS 提交 → 失败就用刷新后的当前值重算。

![[图片/3.Linux/17. 并发同步/3_17_5_3.svg]]

```cpp
// 无锁地对 a 做任意复杂的更新 f
template <class T, class F>
void atomic_update(std::atomic<T>& a, F f) {
    T expected = a.load(std::memory_order_relaxed);
    T desired;
    do {
        desired = f(expected);                  // 基于"读到的旧值"计算
    } while (!a.compare_exchange_weak(           // 提交；失败时 expected 自动刷新
                 expected, desired,
                 std::memory_order_release,      // 成功：发布本次修改
                 std::memory_order_relaxed));    // 失败：仅需重新读取
}
```

> 注意 `compare_exchange_weak` 失败时**已经帮你把 `expected` 刷成最新值**，所以循环体里无需再手动 `load`，直接重算即可。

### 4. ABA 问题

CAS 只比较"值是否相等"，无法察觉"值是否被改动过又改回来"。若值在两次读取之间经历了 **A → B → A**，CAS 会误判"没变过"而成功提交。

![[图片/3.Linux/17. 并发同步/3_17_5_4.svg]]

- **危害场景**：纯数值计数器一般不受影响（值一样含义就一样）；ABA 真正致命的是**指针 + 内存复用**——典型如上图的无锁栈：被弹出的节点地址被分配器回收、再次分配给新节点，CAS 看到"还是那个地址"便成功，结果 `head` 指向了已释放或语义已变的内存。
- **解决思路**：
  1. **版本号 / tagged pointer**：把指针和一个单调递增的计数打包，每次修改都改变比较值（`A_v1` ≠ `A_v3`），用双字 CAS（`cmpxchg16b`）一次比较。
  2. **hazard pointer**：线程发布"我正在用这个指针"，其他线程在该指针被保护期间不得回收它，从根上消除"地址被复用"。
  3. **RCU / 延迟回收**：宽限期内不真正释放内存，等所有读者退出再回收。

### 5. 无锁 ≠ 无等待

"无锁"是一族进展性保证 (progress guarantee)，强弱有别：

| 级别 | 保证 | 含义 |
|------|------|------|
| **obstruction-free** | 最弱 | 若某线程**单独运行**（无干扰），它能在有限步内完成 |
| **lock-free** | 中 | **整个系统**总有线程在推进——单个线程可能饿死，但绝不全体卡死 |
| **wait-free** | 最强 | **每个线程**都能在有限步内完成，无饥饿 |

- 上文的 CAS 循环是典型的 **lock-free**：CAS 失败说明*别人成功了*（系统在前进），但当前线程理论上可能一直重试、被饿死。
- **wait-free** 要求人人有界，实现远更复杂、常数开销更大，仅在硬实时等场景才值得。
- 关键区别在于"无锁"指**没有互斥锁**，不等于"没有等待/重试"。

### 6. 进阶：内存回收难题

无锁数据结构最棘手的不是"怎么改链表"，而是**"什么时候能安全 `delete` 摘下来的节点"**——因为可能还有别的线程正持有指向它的指针。

- **hazard pointer（风险指针）**：每个线程把"当前正在访问的指针"登记到一张全局表；要回收某节点前先扫表，只要没人登记它才真正释放。
- **RCU (Read-Copy-Update)**：读者无锁进入临界区，写者先发布新版本、再等待一个"宽限期"（所有先前读者都已退出）后回收旧版本。Linux 内核大量使用，详见相关章节。

#### 示例：无锁计数器（最简单的 lock-free 结构）

```cpp
std::atomic<long> counter{0};
counter.fetch_add(1, std::memory_order_relaxed);   // 内部即一条原子加，天然无 ABA
```

> 计数器之所以无需 CAS 循环，是因为 `fetch_add` 本身就是单条原子读-改-写指令。

#### 示例：无锁栈的 push（CAS 循环的实战）

```cpp
template <class T>
class LockFreeStack {
    struct Node { T data; Node* next; };
    std::atomic<Node*> head_{nullptr};
public:
    void push(T value) {
        Node* node = new Node{std::move(value), head_.load(std::memory_order_relaxed)};
        // 反复尝试把 node 接到链表头，直到没人插队
        while (!head_.compare_exchange_weak(
                   node->next, node,                 // 失败时 node->next 自动刷成最新 head
                   std::memory_order_release,
                   std::memory_order_relaxed)) { }
    }
    // pop() 同理用 CAS 循环，但需配合 hazard pointer / 版本号处理 ABA 与回收
};
```

> `push` 相对安全，难点全在 `pop`：摘下节点后既要躲开 ABA，又要决定何时 `delete`——这正是上面两节"内存回收"要解决的问题。完整有界/无界队列实现见 [[17.6 并发队列：有界队列与无锁队列]]。

## 三、与其它概念的关系

- 乐观锁 ⊃ 无锁编程：无锁几乎都基于乐观策略
- 悲观锁 ⊃ [[17.3 锁机制、死锁与故障|死锁风险]]：加锁才可能死锁；乐观锁无死锁但可能活锁
- 自旋锁是"悲观地获取锁"，但用"乐观地自旋"实现 —— 二者可组合

---

## 关键要点

- **乐观/悲观是策略，不是锁类型**：悲观锁=先防后用（落地为 mutex / 行锁），乐观锁=先用后查（落地为 CAS / 版本号）。
- **选型看冲突率**：读多写少、冲突罕见用乐观；写多、临界区长、含阻塞用悲观。冲突高时乐观锁会因频繁重试逼近活锁。
- **CAS 是乐观锁的指令级形态**：把"读-改-写"的写步骤换成"带前置条件的原子写"，失败就用刷新后的当前值重算（循环内用 `_weak`）。
- **无锁 ≠ 无等待**：lock-free 保证系统整体推进、但单线程可能饿死；wait-free 才保证人人有界。
- **两大坑**：ABA（值绕回原值致 CAS 误判）与内存回收（何时能安全 delete），靠版本号 / hazard pointer / RCU 解决。
