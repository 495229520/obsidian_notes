# 17.2 原子性、可见性与内存序

> 这是理解一切同步机制的**底层基础**。锁、条件变量、无锁队列的正确性最终都建立在这三个概念之上。

---

## 1. 三大问题

并发程序的 bug 几乎都能归结到这三个相互独立的问题。三者缺一不可：只保证原子性不保证可见性，写出的值别的线程仍可能看不到；只保证可见性不保证有序性，指令重排会让你的逻辑顺序失效。

### 1.1 原子性 (Atomicity)

**原子操作**是不可被中途打断的操作：要么完整发生，要么完全没发生，其他线程观察不到中间状态。

`num++` **不是**原子操作，它在机器层面是三步「读-改-写 (read-modify-write)」：

```asm
mov  eax, [num]   ; ① load：把 num 读进寄存器
add  eax, 1       ; ② add ：寄存器加 1
mov  [num], eax   ; ③ store：写回 num
```

任意两步之间都可能被另一个线程插入，导致**更新丢失**：

![[图片/3.Linux/17. 并发同步/3_17_2_1.svg]]

如图，两个线程都先读到旧值 `0`，各自加 1 后写回，第二次写覆盖了第一次——本应 `+2`，实际只 `+1`。

> 解决：`std::atomic<int>` 的 `fetch_add` / `++` 把读-改-写压成一条不可分割的指令（x86 上是 `lock add`）。

### 1.2 可见性 (Visibility)

一个线程修改了共享变量，另一个线程**不保证**能马上看到新值。原因不是软件 bug，而是 CPU 为了性能引入的**多级缓存**：写可能只停在本核的缓存或写缓冲里，尚未传播到其他核。详见 [[#2.1 CPU 缓存与缓存一致性 (MESI)|第 2 节]]。

### 1.3 有序性 (Ordering)

源码里相邻的两条语句，**实际执行顺序可能被打乱**，来自两个层面：

| 重排来源 | 谁做的 | 例子 |
|---------|-------|------|
| 编译器重排 | 编译期优化 | 把不相关的 `store` 提前/延后 |
| CPU 乱序执行 | 运行期硬件 | 写缓冲使 `store` 延迟生效 |

单线程下重排不改变结果（编译器/CPU 保证 as-if-serial），但**多线程**下，别的线程可能观察到"乱序"的中间状态，从而破坏你预期的逻辑顺序。

---

## 2. 硬件视角

可见性与有序性的根，都在 CPU 的存储子系统里。理解了硬件，才知道内存屏障到底在屏蔽什么。

### 2.1 CPU 缓存与缓存一致性 (MESI)

每个核心有自己的 L1/L2 缓存。为了让多核看到"同一份"内存，硬件用 **MESI 协议**维护缓存行 (cache line) 的一致性，每行处于四种状态之一：

| 状态              | 含义                   |
| --------------- | -------------------- |
| **M** Modified  | 本核已改，且是唯一最新副本，内存里是旧的 |
| **E** Exclusive | 只有本核有副本，与内存一致        |
| **S** Shared    | 多核共享只读副本，与内存一致       |
| **I** Invalid   | 本核副本失效，需重新读取         |

核之间通过总线交换 `Read` / `Invalidate` 消息来切换状态。**理论上** MESI 已经能保证一致性——但如果每次写都同步等待所有核确认失效，CPU 会停顿太久，于是引入了下面两个异步缓冲。

### 2.2 Store Buffer 与 Invalidate Queue

- **Store Buffer（写缓冲）**：写操作先丢进 Store Buffer 就让 CPU 继续跑，不必等缓存行拿到写权限。后果——写**延迟**对其他核可见。
- **Invalidate Queue（失效队列）**：收到 `Invalidate` 消息先排进队列回个 ack，稍后再真正使缓存行失效。后果——其他核的写**延迟**被本核感知。

这两个异步缓冲，正是「可见性」问题的硬件来源：

![[图片/3.Linux/17. 并发同步/3_17_2_2.svg]]

CPU 0 写了 `x=1; flag=1`，但值还堵在 Store Buffer 里；CPU 1 即使在自旋等 `flag`，它的缓存（或失效队列）也可能还是旧值。于是出现"明明写了却读不到"的怪象。

### 2.3 内存屏障 (Memory Barrier / Fence)

屏障是一条特殊指令，**强制**处理器在此处排空缓冲、约束重排：

| 屏障类型 | 作用 |
|---------|------|
| **Store Barrier**（写屏障，`sfence`） | 排空 Store Buffer，保证屏障前的写先于屏障后的写可见 |
| **Load Barrier**（读屏障，`lfence`） | 排空 Invalidate Queue，保证屏障后的读看到最新值 |
| **Full Barrier**（全屏障，`mfence`） | 同时约束读和写，禁止跨屏障重排 |

C++ 的 `memory_order` 不直接写 `sfence`/`mfence`，而是由编译器**按需**把它们插到正确位置——这正是下一节的内容。

## 3. C++ 内存模型与内存序

C++11 起，标准用一套**与平台无关**的内存模型描述并发语义，核心是 `std::atomic` 配合 `memory_order` 参数。它把"硬件屏障"抽象成"建立 happens-before 关系"。

> **happens-before**：若操作 A happens-before 操作 B，则 A 的所有效果（包括它之前的普通写）对 B 可见。这是 C++ 并发可见性的**唯一**保证来源。

### 3.1 六种内存序

| memory_order | 含义 | 典型用途 |
|--------------|------|---------|
| `relaxed` | 仅保证原子性，不约束顺序与可见性 | 纯计数器（如统计） |
| `consume` | 弱化的 acquire（依赖传递），实践中少用 | 极少 |
| `acquire` | 读屏障：之后的读写不能上浮到它之前 | 加锁、出队的读 |
| `release` | 写屏障：之前的读写不能下沉到它之后 | 解锁、入队的写 |
| `acq_rel` | 兼具 acquire + release | 读改写（如 CAS） |
| `seq_cst` | 全局单一顺序一致（默认） | 默认安全选择 |

### 3.2 acquire-release 配对

最常用、性价比最高的模式。**release 的写**与**读到该值的 acquire 读**配对，形成跨线程的 happens-before：

```cpp
std::atomic<bool> ready{false};
int data = 0;

// 线程 A（生产者）
data = 42;                              // ① 普通写
ready.store(true, std::memory_order_release);   // ② release

// 线程 B（消费者）
while (!ready.load(std::memory_order_acquire)); // ③ acquire
assert(data == 42);                     // ④ 一定成立
```

![[图片/3.Linux/17. 并发同步/3_17_2_3.svg]]

- `release`（②）像一道闸：它**之前**的写（①）不能被重排到它之后；
- `acquire`（③）像另一道闸：它**之后**的读（④）不能被重排到它之前；
- 当 B 的 acquire **读到** A release 写入的 `true`，二者「synchronizes-with」，于是 `① → ② → ③ → ④` 拼成一条 happens-before 链，`data=42` 对 B 可见。

> 注意：只有"读到了 release 写入的值"才建立关系。若 B 没读到 `true` 就没有 happens-before，断言可能失败。

### 3.3 relaxed：只要原子，不要顺序

```cpp
std::atomic<long> counter{0};
counter.fetch_add(1, std::memory_order_relaxed);   // 多线程计数
```

`relaxed` 保证 `fetch_add` 本身原子（不丢更新），但**不**提供任何跨线程顺序/可见性保证。只适合各次操作之间没有依赖、最终只关心总数的场景。

### 3.4 seq_cst：默认但最贵

不带参数的 `atomic` 操作默认 `seq_cst`，它在 acq_rel 之上再加一条：**所有 `seq_cst` 操作存在一个全局一致的顺序**，所有线程看到的顺序相同。代价是 x86 上 store 需要 `mfence`/`lock` 级别的全屏障，开销最大。

---

## 4. 实践要点

- **先正确，后性能**：默认用 `seq_cst`，能跑对再说。出现性能瓶颈、且能想清楚 happens-before 时，才下放到 acquire/release。
- **acquire/release 成对出现**：release 配 acquire，单独一个没有意义。锁、无锁队列的核心就是这对配对。
- **relaxed 只用于无依赖的纯计数**：一旦计数结果会决定别的内存访问是否进行，就不能用 relaxed。
- **不要手写 `sfence`/`mfence`**：用 `std::atomic` + `memory_order`，让编译器按目标平台生成最优屏障。
- **能用高层设施就别碰原子**：`std::mutex`、`std::atomic<shared_ptr>` 已封装好正确的内存序，详见 [[17.8 Modern C++ 同步设施与实战并发模式]]。
