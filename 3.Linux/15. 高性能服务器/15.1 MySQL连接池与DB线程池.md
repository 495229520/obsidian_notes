## 1. 为什么数据库访问不能直接放在 EventLoop 中

在 [[13.6 Reactor模式与EventLoop|Reactor]] 服务器里，EventLoop 线程负责 `epoll_wait()`、事件分发、读写缓冲区和连接状态更新。它应该保持短小、快速、非阻塞。

MySQL 访问通常不是这样的操作：

- 建立连接需要 TCP 握手、认证、权限检查和初始化会话状态。
- SQL 执行可能被磁盘、锁等待、索引选择、网络 RTT、慢查询影响。
- 结果集读取和反序列化可能占用较长时间。
- 数据库连接数本身是稀缺资源，不能随请求无限增长。

如果在 EventLoop 中直接执行同步 MySQL 查询，后果是：一个慢 SQL 会拖住这个 loop 管理的所有连接。

> [!note] 核心定位
> MySQL 连接池解决的是“数据库连接如何复用和限流”；DB 线程池解决的是“阻塞式数据库任务交给哪些线程执行”。
>
> EventLoop 不应该等待数据库，应该把 DB 任务投递出去，结果完成后再投递回所属 EventLoop。

## 2. MySQL 连接池解决什么问题

最朴素的写法是每个请求都创建一个数据库连接：

```text
请求到来
    |
    |-- mysql_real_connect()
    |-- 执行 SQL
    |-- mysql_close()
```

这个模型在高并发下会有明显问题：

| 问题 | 说明 |
|:---|:---|
| 建连成本高 | TCP 连接、认证、初始化 session 都有成本 |
| 并发不可控 | 请求暴涨时可能把 MySQL 连接数打满 |
| 延迟抖动大 | 每次请求都把建连耗时放进主路径 |
| 资源释放复杂 | 异常路径上容易忘记关闭或归还连接 |

连接池的思路是：提前维护一组可复用连接，请求执行 SQL 时临时借用，执行完归还。

```text
初始化阶段：创建 N 个 MySQL 连接
请求阶段：acquire -> execute -> release
关闭阶段：停止接收任务，回收连接
```

### 2.1 连接池核心状态

一个最小连接池通常需要这些状态：

| 成员 | 作用 |
|:---|:---|
| idle connections | 空闲连接队列 |
| max connections | 最大连接数，防止打爆 MySQL |
| mutex / condition variable | 保护连接队列，空闲连接不足时等待或超时 |
| acquire timeout | 获取连接的最长等待时间 |
| health check | 检查连接是否断开、是否需要重连 |
| shutdown flag | 服务关闭时唤醒等待者并拒绝新任务 |

连接池本质上也是一个有界资源池，和 [[12.7 条件变量与线程池|线程池]] 的有界任务队列类似：没有资源时不能无限等待，也不能无限创建。

## 3. RAII：借出的连接必须自动归还

连接池最容易出错的地方是：业务代码执行到一半返回、抛异常或进入错误分支，忘记把连接归还给池。

因此借出的连接应该用 RAII guard 管理：

```cpp
class MysqlConnectionGuard {
public:
    MysqlConnectionGuard(ConnectionPool& pool, MysqlConn* conn)
        : pool_(pool), conn_(conn) {}

    ~MysqlConnectionGuard() {
        if (conn_ != nullptr) {
            pool_.release(conn_);
        }
    }

    MysqlConnectionGuard(const MysqlConnectionGuard&) = delete;
    MysqlConnectionGuard& operator=(const MysqlConnectionGuard&) = delete;

    MysqlConnectionGuard(MysqlConnectionGuard&& other) noexcept
        : pool_(other.pool_), conn_(other.conn_) {
        other.conn_ = nullptr;
    }

    MysqlConn* get() const { return conn_; }

private:
    ConnectionPool& pool_;
    MysqlConn* conn_;
};
```

这体现了《Effective C++》Item 13 的原则：用对象管理资源。这里的资源不是内存，而是“从连接池借出的 MySQL 连接”。

> [!warning] 不要把连接长期放在业务对象里
> MySQL 连接应该短时间借用、用完归还。
>
> 如果一个请求、一个会话或一个连接对象长期占有 DB 连接，连接池很快会被耗尽，后续请求只能排队或失败。

## 4. DB 线程池解决什么问题

MySQL C API 或常见同步数据库客户端通常会阻塞当前线程。如果把 SQL 放在网络 I/O 线程中执行，EventLoop 会被拖住。

DB 线程池的职责是：

```text
网络 I/O 线程解析出请求
    |
    |-- 构造 DBTask
    |-- push 到 DB 线程池有界队列
DB worker 线程
    |
    |-- 从连接池 acquire 连接
    |-- 执行 SQL
    |-- 生成结果
    |-- 投递回连接所属 EventLoop
```

和普通业务线程池相比，DB 线程池还受 MySQL 连接池约束：线程数、队列长度和连接数要一起设计。

| 参数 | 过小 | 过大 |
|:---|:---|:---|
| DB worker 数 | SQL 并发不足，请求排队 | 上下文切换变多，争抢连接 |
| 连接池大小 | worker 等连接，吞吐受限 | 打满 MySQL，影响其他服务 |
| DB 任务队列 | 容易拒绝请求 | 延迟隐藏在队列里，内存上涨 |

> [!tip] 经验规则
> DB worker 数不应该远大于连接池大小。
>
> 如果有 32 个 DB worker 但只有 8 个 MySQL 连接，大量 worker 会阻塞在 acquire 上；如果连接池过大，又可能把压力直接打到 MySQL。

## 5. 请求结果如何回到 EventLoop

DB worker 线程执行完 SQL 后，不能直接操作连接 fd 或 `TcpConnection` 内部状态。正确做法是把结果投递回这个连接所属的 EventLoop。

![[图片/3.Linux/15. 高性能服务器/15_1_2.svg|760]]

典型流程：

```text
EventLoop 线程
    |-- 收到请求并解析协议
    |-- 提交 DBTask，记录弱引用或连接标识

DB worker 线程
    |-- acquire MySQL 连接
    |-- execute SQL
    |-- release MySQL 连接
    |-- queueInLoop(sendResponse)

EventLoop 线程
    |-- 检查连接是否仍存在
    |-- 写入 output buffer
    |-- 必要时注册 EPOLLOUT
```

这和 [[13.7 eventfd、timerfd与跨线程唤醒|跨线程唤醒]] 是同一套模型：其他线程只投递任务，不直接修改连接状态。

同时还要结合 [[13.8 连接对象生命周期与RAII|连接对象生命周期]]：DB 任务执行期间，客户端可能已经断开，回调里要用 `weak_ptr` 或连接 ID 检查连接是否仍然有效。

## 6. 有界队列与反压

数据库通常是整条链路里最容易成为瓶颈的下游。如果网络层不断读入请求，而 DB 队列无限增长，系统表面上没有报错，但真实延迟会越来越大，最终内存和数据库都会被拖垮。

因此 DB 线程池队列应该有上限：

| 情况 | 常见策略 |
|:---|:---|
| 队列未满 | 接受任务，返回异步处理中 |
| 队列接近满 | 限流、降低读取速度、减少新请求接收 |
| 队列已满 | 快速失败，返回 busy / overload |
| 获取连接超时 | 释放任务上下文，返回数据库繁忙 |

这属于 [[8.12 非阻塞connect与健壮收发#7. 反压|反压]]：下游处理不过来时，上游不能无限制造工作。

> [!warning] 无界队列会隐藏故障
> 无界 DB 队列看似提高了“接收能力”，实际只是把过载变成排队延迟和内存增长。
>
> 高性能服务器更需要明确的队列上限、超时和拒绝策略。

## 7. 事务与连接复用

连接池复用的是物理连接，但 MySQL 连接上可能残留 session 状态：事务、临时表、变量、字符集、隔离级别等。

归还连接前要确保连接状态干净：

| 状态 | 风险 | 处理方式 |
|:---|:---|:---|
| 未提交事务 | 下一个请求继承旧事务 | 成功 commit，失败 rollback |
| session 变量 | 影响后续 SQL 行为 | 重置关键 session 状态 |
| 临时表 | 占用资源或污染后续逻辑 | 明确清理或限制使用 |
| 连接断开 | 下次借出才失败 | 借出前 ping 或失败后重连 |

> [!warning] 事务不要跨请求长期占用连接
> 一个事务应该在同一个 DB 任务或明确的事务上下文内完成。
>
> 如果把连接借出去后长期等待网络事件或用户下一步操作，会占住连接池资源，也容易造成锁等待和死锁放大。

## 8. 关键指标与排障方向

MySQL 连接池和 DB 线程池是否健康，不能只看 QPS，还要看排队和等待。

| 指标 | 含义 | 异常信号 |
|:---|:---|:---|
| pool idle / in-use | 空闲连接数和使用中连接数 | 长期 idle 为 0，说明连接池饱和 |
| acquire latency | 获取连接耗时 | 连接池太小或 SQL 太慢 |
| DB queue length | DB 任务排队长度 | 下游处理不过来，延迟开始堆积 |
| DB task latency | 从提交到完成的总耗时 | 包含排队、取连接、执行 SQL |
| SQL execution latency | 真正执行 SQL 的耗时 | 慢查询、锁等待、索引问题 |
| timeout / reject count | 超时和拒绝次数 | 系统进入过载保护 |

这些指标会在 [[15.2 压测、指标与线上排障]] 中继续用于压测和线上定位。

## 9. 常见工程陷阱

| 问题 | 后果 | 正确做法 |
|:---|:---|:---|
| EventLoop 中直接查 MySQL | 一个慢 SQL 阻塞整个 loop | 投递到 DB 线程池 |
| 每个请求新建 MySQL 连接 | 建连成本高，连接数不可控 | 使用连接池复用连接 |
| 借出连接后忘记归还 | 连接池耗尽 | 用 RAII guard 自动归还 |
| DB 队列无上限 | 延迟和内存不可控 | 有界队列、超时、拒绝策略 |
| DB worker 远多于连接数 | worker 阻塞在取连接上 | 线程数和连接池大小协同设计 |
| DB worker 直接写 socket | 跨线程操作连接，产生竞态 | 结果投递回所属 EventLoop |
| 连接归还前不清理事务 | 后续请求继承脏 session | commit / rollback 并重置状态 |
| 只看 SQL 执行耗时 | 忽略排队和取连接等待 | 分段打点：排队、acquire、execute、回写 |

## 10. 面试问法

| 问题 | 回答要点 |
|:---|:---|
| 为什么需要 MySQL 连接池？ | 复用连接、降低建连开销、限制数据库并发，避免请求暴涨时打满 MySQL。 |
| 为什么还需要 DB 线程池？ | 同步 SQL 会阻塞线程，不能放在 EventLoop 中执行，需要专门 worker 承接阻塞任务。 |
| 连接池和线程池是什么关系？ | 线程池执行 DBTask，连接池提供有限 MySQL 连接；两者都要有边界。 |
| DB worker 能直接操作 socket 吗？ | 不应该。应把结果投递回连接所属 EventLoop。 |
| 队列满了怎么办？ | 快速失败、限流、返回 busy，不能无界排队。 |
| 连接用完如何保证归还？ | 用 RAII guard 管理借出的连接，析构时自动 release。 |
| 连接池大小怎么估算？ | 结合 MySQL 最大连接数、SQL 平均耗时、目标 QPS、其他服务共享资源综合压测。 |
| 如何定位 DB 线程池瓶颈？ | 看队列长度、取连接耗时、SQL 执行耗时、超时/拒绝数和 MySQL 慢查询。 |

## 11. 关键要点

1. EventLoop 线程不能执行阻塞式 MySQL 查询。
2. MySQL 连接池复用连接，并限制数据库并发上限。
3. DB 线程池承接阻塞 SQL 任务，避免拖住网络 I/O 线程。
4. DB worker 执行完任务后，应把结果投递回连接所属 EventLoop。
5. 借出的连接要用 RAII guard 自动归还，避免连接池泄漏。
6. DB 队列必须有上限，过载时要限流、超时或快速失败。
7. 归还连接前要处理事务和 session 状态，避免污染下一个请求。
8. 排障时要区分排队耗时、取连接耗时、SQL 执行耗时和回写耗时。
