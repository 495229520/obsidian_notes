# 压测、指标与线上排障

## 1. 为什么压测不能只看 QPS

压测的目标不是证明“机器能打出一个漂亮 QPS”，而是找到系统在不同负载下的稳定边界。

只看 QPS 或平均延迟容易误判：

| 指标 | 容易隐藏的问题 |
|:---|:---|
| QPS | 吞吐高不代表尾延迟稳定，也不代表错误率可接受 |
| 平均延迟 | 少量慢请求会被平均值稀释，P99 可能已经很差 |
| CPU 使用率 | CPU 不高不代表系统没瓶颈，可能卡在 DB、锁、队列或网络 |
| 成功率 | 成功但排队很久，用户体验仍然很差 |

> [!note] 核心定位
> 压测要回答的是：系统在目标负载下是否稳定、瓶颈在哪里、过载后如何退化。
>
> 因此要同时看吞吐、分位延迟、错误率、队列长度、资源使用率和拒绝/超时数量。

## 2. 一次请求的分层耗时

高性能服务器的一次请求通常会穿过多层队列和资源边界。任何一层变慢，最终都会体现在客户端看到的 RT 上。

```text
客户端请求
    |
网络接入 / accept / read
    |
EventLoop 协议解析
    |
业务线程池 / DB 任务队列
    |
MySQL 连接池 acquire
    |
SQL execute
    |
queueInLoop 回到 EventLoop
    |
output buffer / EPOLLOUT 回写
    |
客户端收到响应
```

![[图片/3.Linux/15. 高性能服务器/15_2_1.svg|760]]

这些阶段对应的指标可以这样拆：

| 阶段 | 关键指标 | 常见异常信号 |
|:---|:---|:---|
| 客户端侧 | QPS、P50/P95/P99、错误率 | P99 飙升、超时增多 |
| EventLoop | loop latency、active channels、回调耗时 | I/O 线程被慢任务拖住 |
| 线程池队列 | queue length、wait time、reject count | 队列持续增长，等待时间变长 |
| MySQL 连接池 | pool idle/in-use、acquire latency | idle 长期为 0，取连接变慢 |
| SQL 执行 | SQL execution latency、慢查询数 | SQL 变慢、锁等待、索引失效 |
| 回写路径 | output buffer size、EPOLLOUT 次数 | 慢客户端导致输出积压 |

这和 [[15.1 MySQL连接池与DB线程池|MySQL 连接池与 DB 线程池]] 中的指标是同一套思路：不要只看最终 SQL 执行耗时，要把排队、取连接、执行、回写分开打点。

## 3. 压测场景怎么设计

压测前要先明确目标：验证吞吐、验证延迟、找极限、还是验证过载保护。不同目标对应不同场景。

| 场景 | 目的 | 观察重点 |
|:---|:---|:---|
| 稳态压测 | 验证目标 QPS 下是否稳定 | P95/P99、错误率、资源是否稳定 |
| 阶梯升压 | 找到系统拐点 | 哪个负载开始队列堆积、延迟上升 |
| 过载压测 | 验证限流和拒绝策略 | 是否快速失败，是否保护核心资源 |
| 长稳压测 | 验证长期运行 | 内存、fd、连接池、队列是否泄漏或膨胀 |
| 混合场景 | 模拟真实业务比例 | 慢接口是否拖累快接口 |

压测时要尽量固定变量：

1. 明确压测机数量和网络路径，避免压测机先成为瓶颈。
2. 区分短连接和长连接，固定连接数与并发数。
3. 准备稳定数据集，避免缓存命中率随机变化。
4. 先预热，再采集稳态数据。
5. 记录服务端和客户端两侧指标，避免只信一边。

> [!warning] 压测要包含过载表现
> 一个服务不仅要在正常负载下快，还要在下游变慢或请求暴涨时可控退化。
>
> 如果队列无上限、连接池无超时、错误没有计数，过载时就很难判断系统到底卡在哪里。

## 4. 指标分层

线上排障时，最怕所有问题都被说成“服务慢”。更好的方式是按层拆指标。

### 4.1 客户端与入口层

| 指标 | 含义 |
|:---|:---|
| QPS / RPS | 实际吞吐 |
| P50 / P95 / P99 | 延迟分布，尾延迟更能暴露抖动 |
| timeout count | 客户端超时数量 |
| error rate | 业务错误、5xx、连接失败比例 |
| connection count | 当前连接数、活跃连接数 |

### 4.2 EventLoop 与网络层

| 指标 | 含义 |
|:---|:---|
| loop latency | EventLoop 一轮循环是否被拖慢 |
| callback duration | 单个事件回调耗时 |
| input buffer size | 读入后未处理的数据是否堆积 |
| output buffer size | 慢客户端或下游慢导致响应堆积 |
| EPOLLOUT active count | 是否大量连接处于待写状态 |

`EPOLLOUT` 应该按需注册，不能常驻。相关原因见 [[13.4 epoll模型#13. EPOLLOUT 不要常驻|EPOLLOUT 不要常驻]]。

### 4.3 线程池与队列层

| 指标 | 含义 |
|:---|:---|
| queue length | 当前排队任务数 |
| queue wait time | 任务进入队列到被 worker 取走的时间 |
| worker busy ratio | worker 是否长期满负载 |
| reject count | 队列满后的拒绝数量 |
| task latency | 从提交到完成的总耗时 |

这些指标对应 [[12.7 条件变量与线程池|线程池]] 里的 `queue_capacity`、worker 数量和队列满策略。

### 4.4 DB 与下游层

| 指标 | 含义 |
|:---|:---|
| pool idle / in-use | MySQL 连接池是否饱和 |
| acquire latency | 获取连接等待时间 |
| SQL execution latency | 真正执行 SQL 的耗时 |
| slow query count | 慢查询数量 |
| lock wait | 锁等待、事务冲突 |
| timeout / retry | 下游超时、重试次数 |

如果 acquire latency 上升但 SQL execution latency 没变，可能是连接池太小或连接被长期占用；如果 SQL execution latency 上升，优先查慢查询、锁等待、索引和 MySQL 资源。

## 5. 常见瓶颈识别

| 现象 | 更可能的瓶颈 | 进一步检查 |
|:---|:---|:---|
| QPS 上不去，CPU 很高 | CPU 计算、序列化、锁竞争 | top、perf、回调耗时、锁等待 |
| QPS 上不去，CPU 不高 | DB、网络、队列等待 | DB queue、acquire latency、SQL latency |
| P99 升高，平均值变化小 | 少量请求排队或慢 SQL | 分位数、队列等待、慢查询 |
| DB queue 持续增长 | DB worker 不够或 SQL 慢 | worker busy、SQL execution latency |
| pool idle 长期为 0 | 连接池饱和 | acquire latency、连接占用时间 |
| output buffer 变大 | 客户端慢或回写受阻 | EPOLLOUT、发送缓冲区、慢连接 |
| 心跳超时增多 | EventLoop 被拖慢或网络抖动 | loop latency、定时器延迟、网络丢包 |
| reject count 增多 | 进入过载保护 | 队列容量、限流阈值、下游耗时 |

这类定位要结合 [[8.12 非阻塞connect与健壮收发#反压|反压]] 理解：下游慢时，上游继续无限接收只会把问题变成队列和内存膨胀。

## 6. 线上排障路径

线上排障不要从“猜原因”开始，而要先确认问题表现，再沿链路分层收敛。

```text
RT 升高 / 超时增多 / 错误率升高
    |
    |-- 客户端和服务端是否同时看到问题？
    |-- P99 变差还是整体变差？
    |-- 哪个队列开始堆积？
    |-- 是 EventLoop、线程池、DB、网络回写还是系统资源？
```

![[图片/3.Linux/15. 高性能服务器/15_2_2.svg|760]]

推荐顺序：

1. 先看入口：QPS、P95/P99、错误率、超时数是否同时变化。
2. 再看队列：线程池队列、DB 队列、output buffer 是否堆积。
3. 再拆耗时：queue wait、acquire latency、SQL execution latency、回写耗时分别是多少。
4. 再看资源：CPU、内存、fd 数、连接数、MySQL 连接数、磁盘 I/O。
5. 最后对照变更：近期配置、SQL、索引、发布、流量入口是否变化。

> [!tip] 先找“第一个变坏的指标”
> 例如 P99 变坏前，DB queue length 已经开始上涨，那根因更可能在 DB worker / SQL / 连接池，而不是网络发送。
>
> 排障的关键是找时间线上最早异常的那一层。

## 7. 常用命令与日志

| 工具 / 日志 | 用途 |
|:---|:---|
| `ss` | 查看连接状态、监听端口、连接数量、发送/接收队列 |
| `lsof` | 查看进程打开的 fd，辅助判断 fd 泄漏 |
| `top` / `htop` | 查看 CPU、线程、内存整体压力 |
| `pidstat` | 按进程或线程观察 CPU、I/O、上下文切换 |
| `tcpdump` | 抓包确认重传、RST、握手、响应是否真的发出 |
| MySQL 慢查询日志 | 定位慢 SQL、索引问题、锁等待 |
| 应用日志 | 关联 request id、排队耗时、SQL 耗时、错误码 |
| 指标面板 | 看趋势和时间线，定位第一个异常指标 |

这些工具不是替代指标体系，而是用来验证某一层的怀疑点。例如怀疑慢客户端时看 output buffer 和 `ss` 队列；怀疑 SQL 时看 acquire latency、慢查询日志和 MySQL 指标。

## 8. 常见误区

| 误区 | 问题 | 更好的做法 |
|:---|:---|:---|
| 只报 QPS，不报 P95/P99 | 看不到尾延迟和抖动 | 同时报吞吐、分位延迟和错误率 |
| 只看服务端平均耗时 | 客户端可能有网络或排队超时 | 客户端、服务端两侧都采集 |
| 队列无上限 | 过载被隐藏成排队延迟 | 有界队列、拒绝、限流、降级 |
| 只看 SQL 执行时间 | 忽略取连接和 DB 队列等待 | 分段记录 queue/acquire/execute |
| 在 EventLoop 打复杂日志 | 日志 I/O 反过来拖慢 loop | 异步日志或低开销采样 |
| 压测数据集不稳定 | 缓存命中率变化导致结论飘 | 固定数据集并记录缓存状态 |
| 单机压测直接外推线上 | 网络、LB、DB、缓存都可能不同 | 用分层指标确认瓶颈是否一致 |

## 9. 面试问法

| 问题 | 回答要点 |
|:---|:---|
| 压测为什么不能只看 QPS？ | QPS 不反映尾延迟、错误率和过载退化，需要看 P95/P99、队列长度和资源饱和。 |
| P99 突然升高怎么定位？ | 先看队列等待和下游耗时，再拆 EventLoop、线程池、DB、网络回写。 |
| 如何判断 DB 连接池是否是瓶颈？ | 看 idle 是否长期为 0、in-use 是否打满、acquire latency 是否上升。 |
| 如何判断线程池队列是否过载？ | 看 queue length、queue wait time、reject count 和 worker busy ratio。 |
| 为什么无界队列危险？ | 它把过载隐藏成排队延迟和内存增长，最终导致雪崩。 |
| 慢客户端会影响什么指标？ | output buffer 变大、EPOLLOUT 增多、写超时或连接关闭增多。 |
| 心跳误杀怎么排查？ | 看 EventLoop 是否被阻塞、timer callback 是否延迟、网络是否抖动。 |
| 线上排障先看什么？ | 先确认 QPS、P99、错误率和队列长度的时间线，找最早异常层。 |

---

## 10. 关键要点

1. 压测要同时看吞吐、分位延迟、错误率、队列长度和资源饱和点。
2. 平均延迟不够，P95/P99 更能暴露尾延迟和抖动。
3. 一次请求要拆成 EventLoop、队列、连接池、SQL、回写等分段耗时。
4. 有界队列和拒绝策略是过载保护，不是可选优化。
5. DB 排障要区分 DB queue wait、acquire latency 和 SQL execution latency。
6. 网络回写慢会体现在 output buffer、EPOLLOUT 和慢连接上。
7. 线上排障应先找时间线上第一个异常指标，再沿链路分层定位。
8. 压测结论必须说明场景、数据集、连接数、并发数、错误率和资源状态。
