# listen 和 accept 函数

## 概述

服务端的基本流程只有六步：

```
socket() → bind() → listen() → accept() → 数据收发 → close()
```

其中 `listen()` 和 `accept()` 最容易被误解。两句话先把它们摆正：

- **`listen()` 不是「开始监听」那么简单**，它把套接字从主动模式转成被动模式，并在内核里建起**两个**队列。
- **`accept()` 不是「接收数据」**，它只是从队列里取出一条**已经建好的**连接，顺便为它新开一个 fd。三次握手全程由内核完成，跟 `accept()` 无关。

---

## 两个队列

`listen()` 之后，内核为这个监听套接字维护两个队列。一条连接在握手过程中会从前者移到后者。

![[图片/SVG/3_7_7_7_1.svg|900]]

| 队列 | 装什么 | 对应 TCP 状态 |
|:---|:---|:---|
| 半连接队列（SYN queue） | 收到了 SYN、已回 SYN+ACK、还在等第三次 ACK 的连接 | SYN_RCVD |
| 全连接队列（accept queue） | 三次握手已完成、等着被 `accept()` 取走的连接 | ESTABLISHED |

理解这两个队列，能直接解释三个常见现象：

1. **`accept()` 慢不会导致握手失败**。握手是内核干的，应用再忙也不影响。只会让全连接队列越积越多。
2. **客户端 `connect()` 成功了，服务端却没响应**。全连接队列满时，内核默认丢弃第三次 ACK。客户端那边已经是 ESTABLISHED，服务端却当这条连接不存在，表现就是「连上了但一直没动静」。
3. **`ss -lnt` 里监听行的 `Recv-Q` 不为零**，说明全连接队列有积压。

## listen 函数

```c
#include <sys/socket.h>

int listen(int sockfd, int backlog);
```

| 参数 | 说明 |
|:---|:---|
| `sockfd` | 已经过 `bind()` 的套接字描述符 |
| `backlog` | 全连接队列的期望长度 |

成功返回 0，失败返回 -1 并设置 `errno`。

### backlog 到底控制什么

在 Linux 2.2 之后，`backlog` 指的是**全连接队列**的长度，不包括半连接队列。但它并不是最终生效的值：

```
实际队列长度 = min(backlog, /proc/sys/net/core/somaxconn)
```

两个值取小的那个，谁小谁生效。这带来两个方向的坑：

- 代码里写了 `listen(fd, 1024)`，但系统的 `somaxconn` 只有 128，实际就是 128。
- 运维把 `somaxconn` 调到了 65535，代码里还写着 `listen(fd, 5)`，那还是 5。**调内核参数却不改代码，等于白调。**

`somaxconn` 的默认值换过：**Linux 5.4 之前是 128，5.4 起改成了 4096**。写文档或排障时不要凭记忆断言，直接读：

```bash
cat /proc/sys/net/core/somaxconn        # 全连接队列上限
cat /proc/sys/net/ipv4/tcp_max_syn_backlog  # 半连接队列相关
```

半连接队列的长度主要受 `tcp_max_syn_backlog` 约束。开启 SYN cookies 后，队列满了也能继续建连接，不再是硬上限（代价见 [[7.5 TCP协议基础]] 的 SYN flood 一节）。

### 队列满了之后

| 哪个队列满 | 内核默认行为 | 客户端看到什么 |
|:---|:---|:---|
| 半连接队列 | 丢弃新来的 SYN | `connect()` 超时重试，最终失败 |
| 全连接队列 | 丢弃第三次 ACK | `connect()` 成功，但请求得不到响应 |

全连接队列那一行是最难查的：客户端认为连接正常，实际上服务端根本没这条连接。把 `net.ipv4.tcp_abort_on_overflow` 改成 1 可以让内核直接回 RST，让客户端快速失败而不是干等。这在排障时很有用，但生产上要慎用，因为流量尖峰时会把本来能扛过去的请求直接打掉。

积压次数可以直接读出来：

```bash
ss -lnt                              # Send-Q 是队列容量，Recv-Q 是当前积压
nstat -az TcpExtListenOverflows      # 全连接队列溢出的累计次数
nstat -az TcpExtListenDrops          # 因队列问题丢弃连接的累计次数
```

后两个数字长期增长，说明 `accept()` 的速度跟不上握手的速度。加大队列只是拖延，要去看处理线程为什么慢。参数调优的完整讨论见 [[8.13 TCP内核队列与参数调优]]。

## accept 函数

```c
#include <sys/socket.h>

int accept(int sockfd, struct sockaddr *addr, socklen_t *addrlen);
```

| 参数 | 说明 |
|:---|:---|
| `sockfd` | 监听套接字 |
| `addr` | 输出参数，填入客户端地址；不关心可以传 NULL |
| `addrlen` | 输入输出参数，进去时是缓冲区大小，出来时是实际地址长度 |

成功返回一个**新的**套接字描述符，失败返回 -1。

`addrlen` 是「值-结果」参数，每次循环调用前都要重新赋值。忘了重置的话，上一次的输出值会被当成这一次的缓冲区大小，地址可能被截断。

### 两种套接字

`accept()` 返回后，服务器手上有两类套接字，职责完全不同。

![[图片/SVG/3_7_7_7_2.svg|900]]

| 对比项 | listenfd | connfd |
|:---|:---|:---|
| 数量 | 整个进程一个 | 每条连接一个 |
| 五元组 | 只定死本地 IP 和端口，对端两项通配 | 五项全部确定 |
| 能收发数据吗 | 不能，`read()` 会返回 `EINVAL` | 能 |
| 活多久 | 从启动到进程退出 | 一条连接的时长，用完必须 `close()` |
| 谁创建的 | `socket()` + `bind()` + `listen()` | `accept()` 返回 |

所有 connfd 共用同一个端口号，靠五元组区分，这一点见 [[7.3 端口]]。

### accept4：多数情况下更该用的版本

```c
#define _GNU_SOURCE
#include <sys/socket.h>

int accept4(int sockfd, struct sockaddr *addr, socklen_t *addrlen, int flags);
```

`flags` 可以取 `SOCK_NONBLOCK` 和 `SOCK_CLOEXEC`（Linux 2.6.28 起）。两个都值得默认打开：

- **`SOCK_CLOEXEC`**：`exec()` 时自动关闭这个 fd。不加的话，服务进程 `fork` + `exec` 拉起子进程时，所有已连接的 fd 都会泄漏给子进程。后果不只是浪费描述符：子进程持有 fd 会让连接的引用计数不归零，即使父进程 `close()` 了，FIN 也发不出去。
- **`SOCK_NONBLOCK`**：省掉一次 `fcntl()` 调用。注意**监听套接字的非阻塞属性不会被 `accept()` 继承**，新 fd 默认是阻塞的，不显式设置就会在后续 `read()` 上卡住。

用 `accept4()` 一次搞定，比 `accept()` 之后再补两次 `fcntl()` 更不容易出错，也少两次系统调用。

### 必须处理的几种错误

`accept()` 返回 -1 时，`errno` 的几种取值要区别对待，不能一律 `continue`：

| errno | 含义 | 该怎么办 |
|:---|:---|:---|
| `EINTR` | 被信号打断 | 直接重试，不是错误 |
| `ECONNABORTED` | 客户端在 `accept` 前发了 RST，连接已作废 | 忽略这条，继续循环 |
| `EAGAIN` / `EWOULDBLOCK` | 非阻塞模式下队列为空 | 正常情况，回去等下一次事件 |
| `EMFILE` / `ENFILE` | 文件描述符耗尽 | **不能简单 continue**，见下 |

`EMFILE` 最麻烦。在 epoll 的水平触发模式下，连接还在队列里，`accept()` 一直失败，事件一直就绪，循环会空转到 100% CPU。一种经典处理是预留一个空闲 fd：

```c
// 启动时先占一个 fd
int idle_fd = open("/dev/null", O_RDONLY | O_CLOEXEC);

// 撞上 EMFILE 时：腾出这个 fd，接下来立刻关掉，再补一个
if (errno == EMFILE) {
    close(idle_fd);
    idle_fd = accept(listenfd, NULL, NULL);  // 取出这条连接
    close(idle_fd);                          // 立刻关闭，让客户端知道被拒
    idle_fd = open("/dev/null", O_RDONLY | O_CLOEXEC);
}
```

这样至少能把队列里的连接消化掉，并给客户端一个明确的关闭信号，而不是让它一直干等。

## 完整示例：一个迭代服务器

下面这段代码能跑，但它有一个重要的局限，读完代码再说。

```c
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <sys/socket.h>
#include <netinet/in.h>
#include <arpa/inet.h>

#define PORT        8080
#define BACKLOG     128
#define BUFFER_SIZE 1024

int main(void) {
    int listen_fd = socket(AF_INET, SOCK_STREAM, 0);
    if (listen_fd < 0) { perror("socket"); return 1; }

    // 允许在上一次连接的 TIME_WAIT 期间重新绑定，必须在 bind 之前设置
    int opt = 1;
    setsockopt(listen_fd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));

    struct sockaddr_in server_addr;
    memset(&server_addr, 0, sizeof(server_addr));
    server_addr.sin_family      = AF_INET;
    server_addr.sin_port        = htons(PORT);
    server_addr.sin_addr.s_addr = htonl(INADDR_ANY);

    if (bind(listen_fd, (struct sockaddr*)&server_addr, sizeof(server_addr)) < 0) {
        perror("bind"); close(listen_fd); return 1;
    }
    if (listen(listen_fd, BACKLOG) < 0) {
        perror("listen"); close(listen_fd); return 1;
    }
    printf("监听 %d，等待连接\n", PORT);

    for (;;) {
        struct sockaddr_storage client_addr;          // ① 用 storage，IPv6 也装得下
        socklen_t client_len = sizeof(client_addr);   // ② 每次循环都要重置

        int conn_fd = accept(listen_fd, (struct sockaddr*)&client_addr, &client_len);
        if (conn_fd < 0) {
            if (errno == EINTR || errno == ECONNABORTED) continue;  // ③ 可恢复
            perror("accept");
            break;                                                  // 其他错误退出
        }

        // ④ inet_ntop 而不是 inet_ntoa：后者返回静态缓冲区，多线程下会互相覆盖
        char ip[INET6_ADDRSTRLEN];
        struct sockaddr_in *sin = (struct sockaddr_in*)&client_addr;
        inet_ntop(AF_INET, &sin->sin_addr, ip, sizeof(ip));
        printf("客户端接入：%s:%d\n", ip, ntohs(sin->sin_port));

        // ⑤ 这里假设一次 read 就能拿到完整消息，只在演示时成立
        char buffer[BUFFER_SIZE];
        ssize_t n = read(conn_fd, buffer, sizeof(buffer) - 1);
        if (n > 0) {
            buffer[n] = '\0';
            printf("收到 %zd 字节：%s\n", n, buffer);
            const char *resp = "Hello from server!";
            write(conn_fd, resp, strlen(resp));
        }

        close(conn_fd);                               // ⑥ 不关就是 fd 泄漏
    }

    close(listen_fd);
    return 0;
}
```

逐条说明标号处：

① 用 `sockaddr_storage` 而不是 `sockaddr_in`，这样以后加 IPv6 支持时地址不会被截断。

② `client_len` 是值-结果参数，`accept()` 会改写它。放在循环体内声明是最简单的保证方式。

③ `EINTR` 和 `ECONNABORTED` 是可恢复的，重试即可；其他错误（如 `EBADF`）说明监听套接字本身出了问题，继续循环只会空转。

④ `inet_ntoa()` 把结果写在一块函数内的静态缓冲区里，两个线程同时调用会互相覆盖，连续调用两次也会让第一次的结果失效。`inet_ntop()` 要求调用者提供缓冲区，没有这个问题。相关讨论见 [[10.1 套接字选项]]。

⑤ **这是演示代码里最大的简化。** TCP 是字节流，一次 `read()` 拿到的可能是半条消息，也可能是一条半。真实代码必须按协议约定的边界反复读，直到凑齐一条完整消息。处理办法见 [[8.9 TCP的粘包和拆包]]。

⑥ 漏掉 `close(conn_fd)` 会同时造成两个后果：fd 泄漏，以及连接停在 CLOSE_WAIT 状态永不释放。

### 这段代码的局限：一次只能服务一个人

它是**迭代服务器**：`accept()` 取出一条连接后，要把这条连接的收发全部做完才回到循环顶部。这期间队列里的其他客户端只能干等。上面那张图的 C 区画的就是这件事。

只要有一个客户端发得慢（或者干脆连上不发），整个服务就停在那次 `read()` 上，所有人被一起拖住。三种破法：

| 方案 | 做法 | 适用场景 |
|:---|:---|:---|
| 多进程 | `accept()` 后 `fork()`，子进程处理这条连接 | 隔离性好，崩一个不影响别人；开销最大。见 [[11.8 基于多任务的多进程并发服务器]] |
| 多线程 | `accept()` 后起线程 | 比 `fork` 轻，但要自己处理数据竞争 |
| IO 多路复用 | 一个线程用 `epoll` 管所有 fd | 连接数上万时唯一撑得住的做法。见 [[13.1 IO复用简介]] |

三种方案的共同前提是**让 `accept()` 尽快返回去接下一个**。把耗时的业务处理留在 accept 循环里，加多少队列长度都没用。

## 惊群

多个进程或线程同时阻塞在**同一个** listenfd 上等连接时，一条连接到来会不会把它们全部唤醒？这就是惊群问题。分两种情况：

- **直接阻塞在 `accept()` 上**：Linux 内核早已修复，只唤醒一个，没有惊群。
- **用 epoll 等待同一个 listenfd**：默认会唤醒所有等待者，只有一个能 `accept()` 成功，其余拿到 `EAGAIN` 白忙一场。

两种解法：给 `epoll_ctl` 加 `EPOLLEXCLUSIVE` 标志（Linux 4.5 起），让内核只唤醒一个；或者用 `SO_REUSEPORT` 让每个进程各自建一个监听套接字绑同一个端口，由内核按连接做负载均衡，从根本上避开共享。后者还顺带解决了负载不均的问题，细节见 [[10.1 套接字选项]]。

## 关键要点

1. **`listen()` 建的是两个队列**：半连接队列装握手中的连接，全连接队列装握手完成待取的连接。
2. **实际队列长度是 `min(backlog, somaxconn)`**。只改内核参数不改代码等于白改；`somaxconn` 默认值在 Linux 5.4 从 128 变成了 4096。
3. **全连接队列满时默认丢弃第三次 ACK**，客户端以为连上了，服务端却没这条连接，是最难查的一类故障。
4. **`accept()` 不参与握手**，它只是取货。所以 `accept` 慢只会造成积压，不会让握手失败。
5. **`accept4()` 加上 `SOCK_CLOEXEC` 和 `SOCK_NONBLOCK`** 比事后补 `fcntl()` 更安全，还少两次系统调用。
6. **`EINTR` 和 `ECONNABORTED` 要重试，`EMFILE` 要特殊处理**，一律 `continue` 会导致 CPU 空转。
7. **迭代服务器一次只能服务一个客户端**，并发化的前提是让 `accept()` 尽快返回。
