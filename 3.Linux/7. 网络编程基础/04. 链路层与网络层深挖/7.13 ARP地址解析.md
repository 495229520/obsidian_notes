# 7.13 ARP 地址解析

## 1. 中间缺的那张表

发一个包出去，两层的要求对不上：

- 应用和 IP 层手里只有 IP 地址；
- [[7.10 以太网|Ethernet]] 帧头要填的是 MAC 地址。

ARP 就是把前者翻译成后者的那张表，加上维护这张表的一问一答。

有一句话必须先记住，后面所有细节都是它的推论：**ARP 解析的是下一跳，不是最终目标**。访问公网服务器时，ARP 问的是默认网关的 MAC；只有目标就在本网段时，问的才是目标本身。

> [!note] ARP 卡在两层之间
> 它不在 IP 层，因为 ARP 报文不封在 IP 数据报里，而是直接以 `EtherType = 0x0806` 封进以太帧；它也不算纯链路层，因为它要理解 IPv4 地址。RFC 826 干脆没给它定层，只说它是一个「地址解析协议」。
>
> 一个实际后果：ARP 报文不经过 IP 层，所以 iptables 的 `filter` 表拦不住它，要拦得用 `arptables` 或 `ebtables`。

## 2. 报文只有 28 字节

![[图片/SVG/3_7_7_13_1.svg|900]]

前 8 字节在说「我要把什么解析成什么」：`HTYPE=1` 表示硬件是 Ethernet，`PTYPE=0x0800` 表示协议地址是 IPv4，`HLEN=6`、`PLEN=4` 是这两种地址各自的字节数。实际代码里这四个字段基本是常量，收到时校验一下就过。

`OPER` 区分请求（1）和应答（2）。剩下 20 字节分成两组：**发送方**的 MAC + IPv4，和**目标**的 MAC + IPv4。请求时目标 MAC 全填 0，因为要问的就是它。

### 2.1 一个容易被问到的细节

Ethernet 帧头里已经有源 MAC 了，ARP 报文里为什么还要再写一遍 `SHA`？

因为两者是独立的。交换机只看帧头，不会去解 ARP 载荷；ARP 模块拿到的是剥掉帧头的载荷，必须自己自洽。代理 ARP、网桥转发这些场景里，两者本来就可以不同，接收方按 RFC 826 用的是 `SHA`。

这个分离也留下了口子：伪造 ARP 时只改 `SHA`、帧头源 MAC 写真的，只检查帧头的那类检测就抓不到。

### 2.2 帧长又是 42

14 字节帧头 + 28 字节 ARP = 42，比 [[7.10 以太网#6. MTU、最小帧长与填充|最小帧长 64]] 少一截，链路层要补 18 个 0。ARP 是日常最容易见到填充的帧，抓包时看到一串尾部零字节不用奇怪。

## 3. 一次解析的四步

![[图片/SVG/3_7_7_13_2.svg|900]]

### 3.1 请求广播，应答单播

请求只能广播：A 要是知道对方的 MAC，就不用问了。所以帧头目的 MAC 填 `ff:ff:ff:ff:ff:ff`，链路上每台机器都得收上来拆一眼，看 `TPA` 是不是自己。

应答可以单播，因为请求里带着 `SHA` 和 `SPA`，B 已经知道 A 是谁、在哪。

> [!tip] 一次问答填了两张表
> 常被忽略的一步：**B 也从请求里学到了 A 的映射**。RFC 826 规定，收到 ARP 报文时如果 `SPA` 已在缓存里就更新它；如果自己正是 `TPA`，那就无条件把 `SHA → SPA` 记下来。
>
> 这很合理：A 既然来问，接下来必定要给 B 发包，B 迟早要回。提前记下省掉一次反向解析。

### 3.2 缓存没命中的时候，包去哪了

不会被丢。Linux 会把待发的报文挂在这个邻居表项的队列上，一边发 ARP 请求，解析成功后再把队列里的包发出去。

要是解析失败（重试若干次后放弃），队列里的包被丢弃，正在等的 `send()` 或 `connect()` 拿到 `EHOSTUNREACH`。队列本身有上限，由 `unres_qlen_bytes` 控制，防止一个解析不出来的地址把内存耗光。

所以「第一个包延迟明显高于后续」这种现象，有一部分就是它：第一个包在等 ARP。

### 3.3 为什么 ARP 请求出不了本网段

ARP 请求是二层广播帧，路由器不转发广播。这也解释了跨网段时为什么必须先问网关：不是「不想」问目标的 MAC，是**问不到**。

判断走哪条路的逻辑在 IP 层：目标 IP 和本机 IP 分别与掩码相与，结果一致就是同网段，下一跳是目标本身；不一致就查路由表拿默认网关，下一跳是网关。ARP 拿到的永远是这个下一跳。

## 4. Linux 邻居表：不只是缓存

`ip neigh` 看到的不是一张简单的映射表，而是一台带状态机的邻居可达性检测器（NUD, Neighbour Unreachability Detection）。

| 状态 | 含义 | 怎么进来的 |
|:---|:---|:---|
| `INCOMPLETE` | 正在解析，还没答案 | 首次发包且表里没有 |
| `REACHABLE` | 确认可达，直接用 | 收到应答，或上层报告「对面有回应」 |
| `STALE` | 映射还在，但没最近确认过 | `REACHABLE` 超时；或收到未经请求的 ARP |
| `DELAY` | 先等一小会，看上层会不会自己确认 | `STALE` 表项被拿来发包 |
| `PROBE` | 等不到，主动发单播 ARP 探测 | `DELAY` 超时 |
| `FAILED` | 探测多次无应答 | `PROBE` 次数用尽 |
| `PERMANENT` | 手工写死，永不老化 | `ip neigh add ... nud permanent` |
| `NOARP` | 不需要解析 | 广播、组播地址，点对点接口 |

> [!important] `STALE` 不等于失效
> 这是读 `ip neigh` 输出时最容易误判的一点。`STALE` 表项照常拿来发包，只是内核会在用它的时候顺手安排一次验证（进 `DELAY`）。看到一屏 `STALE` 完全正常，不用去 flush。

### 4.1 上层反馈才是主力

`DELAY` 这个状态是整套机制的关键优化。表项从 `REACHABLE` 掉到 `STALE` 后再被使用时，内核不会立刻发探测，而是先等一小段时间，看上层协议会不会自己证明对方还在。

[[7.6 TCP协议基础|TCP]] 每收到一个推进发送窗口的 ACK，就相当于告诉内核「这个邻居活着」，表项直接回到 `REACHABLE`。结果是：一条繁忙的 TCP 连接上，几乎不会真的发出 ARP 探测报文。

这是个值得记的设计思路，**已有的上层信号是免费的，能用就别再花一个往返去问**。

### 4.2 几个参数

| 参数 | 默认值 | 作用 |
|:---|:---:|:---|
| `base_reachable_time_ms` | 30000 | `REACHABLE` 的基准时长，实际取值在它的 0.5～1.5 倍之间随机 |
| `gc_stale_time` | 60 | `STALE` 表项多久之后可以被回收 |
| `gc_thresh1` | 128 | 低于这个数量完全不回收 |
| `gc_thresh2` | 512 | 超过 5 秒仍高于此值就开始回收 |
| `gc_thresh3` | 1024 | 硬上限，超了立刻强制回收 |

路径在 `/proc/sys/net/ipv4/neigh/default/`，也可以按接口单独设。`REACHABLE` 时长要随机化，是为了避免整个网段的机器在同一时刻集体发探测。

大二层网络里如果同网段主机数逼近 `gc_thresh3`，内核日志会刷 `neighbour table overflow`，表现是随机丢包。这时该调大阈值，或者反思一下网段是不是划得太大了。

## 5. 免费 ARP 和代理 ARP

### 5.1 免费 ARP：SPA 和 TPA 填同一个地址

「免费」（gratuitous）指的是没人问它，自己主动发。特征是 `SPA == TPA`，都填自己的 IP。有三个用途：

- **地址冲突检测**：接口刚起来时问一句「谁是我这个地址」。要是有人应答，说明地址撞了。
- **高可用切换**：VIP 从主机漂到备机后，备机广播一次免费 ARP，把全网段缓存里的旧 MAC 刷掉。keepalived、VRRP 都靠这一下，不发的话客户端会一直往已经宕掉的那台发包，直到表项老化。
- **换网卡后通告**：MAC 变了，主动告诉别人别再用旧的。

RFC 5227 把冲突检测细分成两步，区别在 `SPA`：

| | `SPA` 填什么 | 目的 |
|:---|:---|:---|
| ARP Probe | `0.0.0.0` | 探测阶段。填 0 是为了万一地址真被占用，不去污染别人的缓存 |
| ARP Announcement | 自己的 IP | 确认没冲突后正式宣告 |

### 5.2 代理 ARP：路由器替别人答

`Proxy ARP` 让路由器对不属于自己的 IP 也做应答，填的是自己的 MAC，把流量吸引过来再转发。开关在 `/proc/sys/net/ipv4/conf/<接口>/proxy_arp`。

用途集中在几个场景：老式的子网划分、点对点 VPN 把远端地址映射进本地网段、部分容器网络方案。

代价是主机被蒙在鼓里，它以为目标就在本网段，实际隔着一跳。排障时看到「两个不同的 IP 解析出同一个 MAC」，多半就是代理 ARP。

## 6. ARP 完全没有认证

协议本身不带任何身份验证：谁都可以声称自己是任意 IP，收到的人无从核实。这就是 ARP 欺骗（投毒）的全部原理。

攻击者向 A 说「网关的 MAC 是我」，向网关说「A 的 MAC 是我」，两边的流量就都从他那儿过一遍，中间人成立。

> [!danger] Linux 的默认设置只挡住一半
> `/proc/sys/net/ipv4/conf/*/arp_accept` 默认是 0，含义是**不为表里没有的地址新建**表项。但表里已经有的表项，照样会被收到的免费 ARP 刷新。
>
> 也就是说，默认配置防的是「凭空插入」，防不住「篡改已有」。而真正在用的表项恰恰是已有的那些。

防御要分层看，越靠下越根本：

| 手段 | 在哪做 | 说明 |
|:---|:---|:---|
| 静态表项 `nud permanent` | 主机 | 只适合网关这类数量少又固定的地址 |
| DHCP Snooping + 动态 ARP 检测（DAI） | 交换机 | 交换机比对 ARP 报文和 DHCP 绑定表，对不上就丢。企业网的标准做法 |
| 端口隔离 / 私有 VLAN | 交换机 | 同网段主机之间根本不能直接通信 |
| `arpwatch` 之类的监控 | 旁路 | 只报警，不阻断 |
| TLS 等端到端加密 | 应用 | 流量被绕道也读不懂、改不了 |

最后一行才是根本。二层安全能提高门槛，但**只要攻击者在同一个广播域里，就不该假设链路是可信的**，这也是内网服务同样该上 TLS 的理由之一。

## 7. IPv6 那边没有 ARP

[[7.12 IPv6|IPv6]] 把这套活儿交给了 [[7.12 IPv6#7. NDP：ARP 的活它全包了|NDP]]（邻居发现协议），而 NDP 的报文属于 [[7.14 ICMP与ICMPv6|ICMPv6]]。

| | ARP（IPv4） | NDP（IPv6） |
|:---|:---|:---|
| 承载 | 直接封在以太帧，`EtherType 0x0806` | ICMPv6 报文，走 IPv6 |
| 请求方式 | 二层广播，全网段都要处理 | 组播到被请求节点地址，只有少数几台要处理 |
| 报文类型 | Request / Reply | Neighbor Solicitation / Advertisement（Type 135 / 136） |
| 顺带做的事 | 只做地址解析 | 还负责路由器发现、地址自动配置、重复地址检测、重定向 |
| 能不能加固 | 只能靠外部手段 | 可以用 SEND（RFC 3971）做加密认证，但实际部署极少 |

最值得注意的是**组播取代广播**。IPv6 把目标地址的低 24 位映射到一个「被请求节点组播地址」，只有低 24 位相同的机器才会收，其余主机的网卡在硬件层就过滤掉了。一个大网段里，这能省掉绝大部分无谓的中断。

代价是 NDP 依赖 ICMPv6。把 ICMPv6 一刀切屏蔽掉，IPv6 直接不能用，这一点在 [[7.14 ICMP与ICMPv6|ICMP 那篇]]里还会再提。

## 8. 在 Linux 上观察

### 8.1 命令

```bash
ip neigh show                 # 看全部邻居表项和状态
ip neigh show dev eth0

# 清掉某个接口的动态表项，下次发包会重新解析，方便抓一次完整过程
sudo ip neigh flush dev eth0

# 手工写死一条，状态是 PERMANENT，不参与老化
sudo ip neigh add 10.0.0.1 lladdr 52:54:00:12:34:56 dev eth0 nud permanent
sudo ip neigh del 10.0.0.1 dev eth0

# 主动发一个 ARP 请求，不经过 IP 层，用来测二层连通性
sudo arping -I eth0 -c 3 10.0.0.20
```

`arping` 值得单说：它绕过 IP 层，所以对方就算把 ICMP 全屏蔽了，`ping` 不通而 `arping` 通，说明机器活着、二层可达，问题出在更上面。

抓包看整个过程：

```bash
sudo tcpdump -i eth0 -e -n arp
# 请求：52:54:00:8f:1c:2a > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806),
#       length 42: Request who-has 10.0.0.20 tell 10.0.0.10
# 应答：52:54:00:12:34:56 > 52:54:00:8f:1c:2a, ethertype ARP (0x0806),
#       length 42: Reply 10.0.0.20 is-at 52:54:00:12:34:56
```

请求那行的目的 MAC 是广播、应答那行是单播，`length 42` 也和前面算的对得上。

### 8.2 自己发一个 ARP 请求

先定报文结构。ARP 是纯字节协议，结构体的内存布局必须和线上完全一致：

```cpp
#include <linux/if_ether.h>   // ETH_P_ARP、ETH_P_IP
#include <linux/if_packet.h>  // sockaddr_ll
#include <net/if.h>           // if_nametoindex
#include <sys/socket.h>
#include <arpa/inet.h>
#include <array>
#include <cstdint>
#include <cstring>

struct __attribute__((packed)) ArpPacket {
    std::uint16_t htype;                  // 1 = Ethernet
    std::uint16_t ptype;                  // 0x0800 = IPv4
    std::uint8_t  hlen;                   // 6
    std::uint8_t  plen;                   // 4
    std::uint16_t oper;                   // 1 = Request，2 = Reply
    std::array<std::uint8_t, 6> sha;
    std::array<std::uint8_t, 4> spa;
    std::array<std::uint8_t, 6> tha;
    std::array<std::uint8_t, 4> tpa;
};
static_assert(sizeof(ArpPacket) == 28, "ARP 报文必须正好 28 字节");
```

这个字段顺序**碰巧**不会产生对齐填充（两个 `uint8_t` 正好凑成一对），去掉 `packed` 算出来也是 28。但「碰巧」不该是协议代码的依据：字段一调整、类型一改就可能出洞，而这种 bug 在本机测试里往往发现不了。`packed` 加上 `static_assert` 才是把这件事钉死的写法，和 [[7.5 传输层协议：TCP与UDP|自定义协议]]那篇的结论一致。

然后填字段，注意哪些要转字节序：

```cpp
ArpPacket arp{};
arp.htype = htons(1);
arp.ptype = htons(ETH_P_IP);      // 0x0800
arp.hlen  = 6;
arp.plen  = 4;
arp.oper  = htons(1);             // Request
arp.sha   = my_mac;               // 本机 MAC，6 字节原样
arp.spa   = my_ip;                // inet_pton 得到的，已是网络字节序
arp.tha.fill(0);                  // 要问的就是它，留空
arp.tpa   = target_ip;
```

规则很简单：**单字节字段不用转，多字节的整数字段必须转**。`htype`、`ptype`、`oper` 是 `uint16_t`，要过 `htons`；MAC 和 IP 是字节序列而不是整数，`inet_pton` 出来就是网络序，直接拷贝。搞反了的典型症状是对端完全不应答，抓包一看 `OPER` 变成了 256。

最后封上帧头发出去：

```cpp
constexpr std::array<std::uint8_t, 6> kBroadcast{0xff, 0xff, 0xff, 0xff, 0xff, 0xff};

// 帧头三段就是 6 + 6 + 2，偏移直接写出来比再套一个结构体清楚
std::array<std::uint8_t, 14 + sizeof(ArpPacket)> frame{};
std::memcpy(frame.data() + 0,  kBroadcast.data(), 6);
std::memcpy(frame.data() + 6,  my_mac.data(),     6);
const std::uint16_t ethertype = htons(ETH_P_ARP);      // 0x0806
std::memcpy(frame.data() + 12, &ethertype,        2);
std::memcpy(frame.data() + 14, &arp,   sizeof(arp));

sockaddr_ll addr{};
addr.sll_family  = AF_PACKET;
addr.sll_ifindex = static_cast<int>(::if_nametoindex("eth0"));   // 从哪个网卡发
addr.sll_halen   = 6;
std::memcpy(addr.sll_addr, kBroadcast.data(), 6);

// fd 来自 socket(AF_PACKET, SOCK_RAW, htons(ETH_P_ARP))，需要 CAP_NET_RAW
::sendto(fd, frame.data(), frame.size(), 0,
         reinterpret_cast<sockaddr*>(&addr), sizeof(addr));
```

三点说明：

- **`sockaddr_ll` 这里只有 `sll_ifindex` 真正起作用。** 帧头是我们自己写的，内核不会再拿 `sll_addr` 去改目的 MAC。但该填的字段还是得填。
- **发出去的是 42 字节，线上是 60。** 填充由驱动或网卡补，应用这一层不用管。
- **收应答要另开一个循环。** `AF_PACKET` 套接字会收到该接口上所有匹配 `ETH_P_ARP` 的帧，包括别人之间的问答，得自己按 `TPA` 是不是本机来过滤。

例子省掉了错误检查和 `fd` 的 RAII 包装，真实代码里都得补上。

## 9. 常见误区

| 说法 | 实际 |
|:---|:---|
| 访问公网时会 ARP 公网服务器的 MAC | 只会 ARP 默认网关。ARP 请求是二层广播，出不了本链路 |
| ARP 应答也是广播 | 应答通常单播。请求里已经带了发送方的 MAC 和 IP |
| 只有发起方会更新缓存 | 被问的一方也从请求里学到了发起方的映射 |
| `ip neigh` 里的 `STALE` 是坏表项 | `STALE` 照常能用，只是下次使用时会顺带验证一次 |
| ARP 缓存靠定时重新解析来维持 | 主要靠上层反馈，TCP 的 ACK 就能把表项拉回 `REACHABLE` |
| 免费 ARP 没人问，所以没用 | 高可用切换全靠它刷新别人的缓存 |
| `arp_accept=0` 就防住 ARP 欺骗了 | 它只拦「新建表项」，已有表项照样会被刷新 |
| IPv6 也用 ARP，只是名字不同 | IPv6 用 NDP，报文属于 ICMPv6，而且是组播不是广播 |

## 10. 自测问题

1. 访问公网服务器时，主机为什么不会去 ARP 那台服务器的 MAC？
2. ARP 请求里已经带了发送方 MAC，Ethernet 帧头为什么还要再写一次源 MAC？
3. 免费 ARP 没有对应的请求，为什么仍然有用？
4. 一台机器的 `ip neigh` 输出里几乎全是 `STALE`，需要处理吗？

> [!question]- 参考答案
> 1. ARP 请求是二层广播帧，路由器不转发广播，请求根本到不了公网。IP 层判断目标不在本网段后把下一跳定为默认网关，ARP 解析的就是这个下一跳。
> 2. 两者相互独立：交换机只读帧头、不解 ARP 载荷；ARP 模块拿到的是剥掉帧头的载荷、必须自洽。代理 ARP 和网桥场景下两者本来就可能不同，接收方以 `SHA` 为准。
> 3. 它的作用是**主动刷新别人的缓存**，不是获取信息。VIP 漂移后备机广播一次免费 ARP，同网段主机就把旧 MAC 换掉了；否则客户端会一直往宕掉的那台发包，直到表项自然老化。它还用来做地址冲突检测。
> 4. 不需要。`STALE` 表示映射有效但最近没验证过，发包时照用，内核会顺带安排一次确认。真正需要关注的是 `FAILED` 和 `INCOMPLETE`。

## 11. 关键要点

1. **ARP 解析的永远是下一跳**：同网段问目标本身，跨网段问默认网关。
2. **报文 28 字节**，前 8 字节固定描述「IPv4 over Ethernet」，后 20 字节是发送方和目标两组地址；请求把目标 MAC 留空。
3. **请求广播、应答单播**，而且一次问答填了两张表，被问的一方也学到了发起方的映射。
4. **Linux 邻居表是状态机，不是简单缓存**：`STALE` 能用，`DELAY` 是给上层反馈留的窗口，TCP 的 ACK 能免掉真正的探测。
5. **免费 ARP 的关键特征是 `SPA == TPA`**，用于冲突检测和高可用切换后刷新全网缓存。
6. **ARP 没有认证，`arp_accept=0` 只拦新建不拦篡改**；二层加固能提高门槛，端到端加密才是根本。
7. **IPv6 用 NDP 而不是 ARP**，走 ICMPv6，用组播代替广播，还兼管路由器发现和地址自动配置。
8. **三条命令**：`ip neigh` 看表和状态，`arping` 测二层连通，`tcpdump -e -n arp` 看完整问答。
