# 7.1 网络分层模型

## 1. 为什么要分层

两台机器要通信，中间横着一堆互不相干的问题：电信号怎么调制、同一根网线上怎么区分是谁发的、包该往哪个方向转、丢了怎么重发、收到的字节流怎么解释成一条 HTTP 请求。

如果把这些问题揉在一个协议里，换一种物理介质（网线换光纤、有线换 Wi-Fi）就得重写整个协议栈。分层的做法是给每类问题划一层，层与层之间只约定接口：上层把数据交给下层，不关心下层怎么送；下层把数据送到对端的同一层，不关心里面装的是什么。

这带来三个实际后果：

- **换介质不用改上层**：从有线切到 Wi-Fi，只换了链路层和物理层，TCP 和 HTTP 一行代码都不动。
- **每一层可以独立演进**：HTTP/1.1 到 HTTP/2 只改了应用层的编码方式，TCP 没变；QUIC 换掉了传输层，HTTP 语义仍然沿用。
- **排障可以按层二分**：ping 通说明三层可达，telnet 端口不通说明四层被挡，这是网络问题最有效的定位方式。

代价是每层都要加自己的头部，这部分开销后面会具体算。

## 2. OSI 参考模型（七层）

OSI（Open Systems Interconnection，开放系统互连）是 ISO 在 1984 年定稿的参考模型，把通信划分成七层。

| 层次  |  名称   | 主要功能                               | 典型协议/设备                   |
| :-: | :---: | :--------------------------------- | :------------------------ |
|  7  |  应用层  | 为应用程序提供网络服务接口                      | HTTP, FTP, SMTP, DNS      |
|  6  |  表示层  | 数据格式转换、加密解密、压缩解压                   | SSL/TLS, JPEG, ASCII      |
|  5  |  会话层  | 建立、管理和终止会话连接                       | NetBIOS, RPC              |
|  4  |  传输层  | 端到端的可靠/不可靠数据传输                     | [[7.6 TCP协议基础\|TCP]], UDP |
|  3  |  网络层  | 路由选择、逻辑寻址（[[7.2 IP地址与CIDR\|IP地址]]） | IP, ICMP, IGMP            |
|  2  | 数据链路层 | 帧的封装与解封、物理寻址（MAC地址）                | Ethernet, PPP             |
|  1  |  物理层  | 比特流传输、物理介质规范                       | 网线、光纤、中继器                 |

### 2.1 数据封装与解封装

发送端从应用层往下走，每层在数据前面加上自己的头部；接收端从物理层往上走，每层剥掉对应的头部再交给上一层。两端的同一层看到的是同样的内容，这叫**对等层通信**。

![[图片/SVG/3_7_7_1_1.svg|1390]]

图的下半部分是这件事的实际成本。以太网上一个满载的 TCP 包：

```
以太网帧头 14 B + IP 头 20 B + TCP 头 20 B + 数据 1460 B + FCS 4 B = 1518 B
```

头部一共 58 字节，占 3.8%，可以接受。但头部大小和数据量无关，所以数据越小越亏：终端里敲一个键，1 字节的数据要用一个 64 字节的帧（以太网规定最小帧长 64 字节，不够要填充）送出去，有效载荷只有 1.6%。

这就是 [[10.3 Nagle算法|Nagle 算法]] 存在的理由：把连续的小写入攒成一个大包再发，用一点延迟换掉大部分头部开销。反过来说，程序里逐字节调用 `write()` 是最浪费带宽的写法。

> [!note] MSS 是怎么算出来的
> MSS（最大报文段长度）= MTU − IP 头 − TCP 头。以太网 MTU 是 1500，减掉两个 20 字节的头，得到 1460。超过 MSS 的数据由 TCP 自己切分，不会触发 IP 分片；而 UDP 不切分，一次 `sendto()` 超过 MTU 就会在 IP 层分片，任何一片丢了整个数据报都得重传。

## 3. TCP/IP 四层与五层模型

TCP/IP 是今天所有联网设备实际运行的协议栈。它把 OSI 的上三层合成应用层、下两层合成网络接口层，剩下四层。五层模型是教学上的折中：保留 TCP/IP 的应用层合并，但把链路层和物理层拆开，方便讲交换机和集线器的区别。

![[图片/SVG/3_7_7_1_2.svg|1390]]

| TCP/IP 层次 | 对应 OSI 层 | 主要协议 |
|:---:|:---:|:---|
| 应用层 | 应用层 + 表示层 + 会话层 | HTTP, SMTP, DNS, FTP, SSH |
| 传输层 | 传输层 | [[7.6 TCP协议基础\|TCP]], UDP |
| 网际层 | 网络层 | IP, ICMP, IGMP |
| 网络接口层 | 数据链路层 + 物理层 | 以太网, Wi-Fi, PPP |

### 3.1 五层模型的数据单元与设备

| 层次  |  名称   |               数据单元（PDU）               | 工作在该层的设备  |
| :-: | :---: | :-----------------------------------: | :-------- |
|  5  |  应用层  |             应用报文（message）             | 无（主机上的进程） |
|  4  |  传输层  | TCP 报文段（segment）/ UDP 用户数据报（datagram） | 无         |
|  3  |  网络层  |          IP 数据报（IP datagram）          | 路由器、三层交换机 |
|  2  | 数据链路层 |               帧（frame）                | 交换机、网桥、网卡 |
|  1  |  物理层  |               比特流（bit）                | 中继器、集线器   |

> [!warning] 别把路由器写在物理层
> 路由器要读 IP 头才能查路由表，所以它工作在第三层。物理层的设备只放大和转发信号，不理解任何头部，代表是中继器和集线器。集线器收到信号后向所有其他端口复制一份，这是它和交换机最本质的区别。

### 3.2 表示层和会话层去哪了

TCP/IP 里没有这两层，但它们负责的事情没有消失，只是挪进了应用层：

- **加密**：由 TLS 库（OpenSSL 等）实现，应用自己在 socket 之上套一层。
- **编码与压缩**：HTTP 用 `Content-Type`、`Content-Encoding` 这些头字段协商，双方各自处理。
- **会话管理**：HTTP 本身无状态，会话靠 Cookie 或 Session ID 维持。

所以「TCP/IP 只有四层」不等于「少了两层功能」，而是这些功能不再由独立的协议层承担。

## 4. 逐跳转发：中间设备只上到它需要的那一层

封装解封装那张图容易给人一个错觉，以为数据每经过一个设备都要走完七层。实际上只有两端主机会走完全程，中间设备各自停在不同高度。

![[图片/SVG/3_7_7_1_3.svg|1390]]

- **交换机**只解封装到帧头，读出目的 MAC，查 MAC 地址表决定从哪个口发出去。IP 头对它是不透明的载荷。
- **路由器**要多剥一层，读出目的 IP，按最长前缀匹配查路由表。转发前它会重写帧头（换成下一跳的 MAC）、把 TTL 减 1、重算 IP 头校验和。
- **集线器**什么头都不看，收到信号就往其余所有端口复制。

这三行里还藏着一个没交代的环节：路由器凭什么知道下一跳的 MAC 是多少？主机也一样——查完路由表只得到「下一跳是 192.168.1.1」这么一个 **IP**，可帧头要填的偏偏是 **MAC**。把这两者接起来的就是 [[7.13 ARP地址解析|ARP]]：

- **IP 决定「送到哪」**：目的 IP 从发出到收到全程不变，路由表拿它定方向。
- **MAC 决定「这一跳交给谁」**：它每跳都被重写，交换机只认它来转发。
- **ARP 把两者在每一跳连起来**：谁要发包，谁就拿「下一跳 IP」去问一次 ARP，换回「下一跳 MAC」填进帧头。

要紧的是**下一跳 IP 从不写进 IP 头**，它唯一的用途就是拿去问 ARP。于是整个过程就是「目的 IP 一路不变、MAC 一层一层换」地往前递进，直到最后一跳，目的 MAC 才终于是 B 自己。

由此得到一条贯穿整个网络排障的结论：

> **源和目的 IP 地址端到端不变；源和目的 MAC 地址每跳都被重写。**

理解了这句话，两件事就顺理成章：

1. 在本机抓包，看到目的 MAC 是网关而目的 IP 是某个公网地址，这是正常的，说明包要出本网段。
2. `traceroute` 之所以能打印出路径，是因为它把 TTL 从 1 开始逐次加一。TTL 减到 0 的那台路由器会回一个 ICMP 超时报文，报文的源 IP 就暴露了这一跳是谁。

最后补一句：如果两端之间是 TCP 连接，那么在发数据之前还有[[7.6 TCP协议基础#4. 三次握手|三次握手]]。但握手报文走的也是上面这套路径——握手是 IP 层**之上**的机制，而 ARP、查路由表、改帧头是每一跳**底下**都在发生的事。两者不在一个层面上，谁也不替代谁：三个握手报文同样要逐跳换 MAC，同样要靠 ARP 问出下一跳。

## 5. socket 落在哪一层

写网络程序时按 TCP/IP 四层来想最省事。[[7.7 套接字|socket]] API 正好架在应用层和传输层的边界上：

```
       你的业务代码           ← 应用层：自己定义的协议格式
    ────────────────────
       socket API            ← 系统调用边界
    ────────────────────
       TCP / UDP             ← 传输层：内核实现
       IP                    ← 网际层：内核实现
       网卡驱动               ← 网络接口层
```

这条边界决定了分工：**传输层往下全部由内核负责**，你不用写重传、不用管路由、不用算校验和；**边界往上的协议格式由你自己定**，包括怎么划分消息边界。TCP 只保证字节流按序不丢，不保证你 `write()` 三次对方就 `read()` 三次，这正是 [[8.9 TCP的粘包和拆包|粘包与拆包]] 问题的根源。

## 6. 关键要点

1. **分层的收益是解耦，代价是头部开销**。58 字节的固定头部在满载时只占 3.8%，在小包上却能占到 98%。
2. **一个包在网络里走一趟，只有两端走完全程**。交换机停在二层、路由器停在三层，这是它们转发得快的原因。
3. **IP 端到端不变，MAC 逐跳重写**。抓包分析、traceroute、ARP 相关的问题都从这条规则推导。
4. **物理层的设备是中继器和集线器，不是路由器**。设备工作在哪一层，取决于它需要读到哪一层的头部。
5. **写程序按 TCP/IP 四层想**。传输层以下是内核的事，应用层的协议格式和消息边界是你的事。
