# 7.5 传输层协议：TCP 与 UDP

## 1. 协议要回答的两个问题

协议是通信双方对**数据格式**和**交互流程**的约定。听起来很抽象，但落到实处，任何一个协议都必须回答两个问题：

1. **边界在哪**：收到一串字节，从第几个到第几个算一条完整消息？
2. **含义是什么**：这条消息里，每个字节分别代表什么？

第一个问题是绕不开的，因为 [[7.6 TCP协议基础|TCP]] 只保证字节按序到达，不保证「你发一次，对方就收一次」。第二个问题决定了双方能不能理解对方。两个问题都答好了，协议就成立了。

至于「协议是计算机的语言」这类比喻，帮助不大：真正要记住的是上面这两条，设计协议时逐条对照就行。

## 2. TCP 与 UDP：字段决定能力

传输层这两个协议的差别，直接写在头部里。TCP 头 20 字节，UDP 头 8 字节，多出来的 12 字节买到了三样东西。

![[图片/SVG/3_7_7_5_1.svg|1390]]

### 2.1 几个字段的作用

- **序号 seq（32 位）**：本报文段第一个字节在整条字节流中的位置。有了它，乱序到达的段可以重新排好，重复的段可以丢掉。
- **确认号 ack（32 位）**：告诉对方「你发的东西我收到这里了，下一个请从这个序号开始」。它是**累积确认**：ack=1100 表示 1099 及之前的字节全部收到。
- **窗口 win（16 位）**：接收方还能再收多少字节。发送方据此限制在途数据量，这就是流量控制。
- **数据偏移（4 位）**：以 4 字节为单位表示头部长度。4 位最大值 15，所以 TCP 头最长 60 字节，其中选项最多占 40 字节。
- **检验和（16 位）**：覆盖 TCP 头、数据和一个由 IP 地址拼出来的伪首部。带上伪首部是为了检出「送错主机」这种错误。

### 2.2 对比

| 特性 | [[7.6 TCP协议基础\|TCP]] | [[9.1 UDP原理\|UDP]] |
|:---|:---|:---|
| **头部开销** | 20 字节起，带选项最多 60 | 固定 8 字节 |
| **连接** | 三次握手建连，四次挥手断开 | 没有连接概念，直接发 |
| **可靠性** | 确认 + 超时重传，保证不丢不重不乱序 | 发出去就不管，丢了也不知道 |
| **消息边界** | 不保留，是字节流 | 保留，一次 sendto 对应一次 recvfrom |
| **流量控制** | 有，靠窗口字段 | 无，发多快全凭应用自觉 |
| **拥塞控制** | 有，网络拥塞时主动降速 | 无，网络越堵它发得越猛 |
| **首次通信延迟** | 至少多一个 RTT（握手） | 零，第一个包就带数据 |
| **典型场景** | HTTP、SSH、数据库连接 | DNS 查询、音视频流、游戏状态同步 |

> [!warning] 「UDP 比 TCP 快」需要限定条件
> UDP 快在两处，都是省掉的固定成本：建连少了一个 RTT，发送后不用等确认。但在丢包率高的链路上，UDP 未必更快，因为丢了的数据要么不管（业务受损），要么由应用自己重传，而应用层的重传通常不如内核的 TCP 实现高效。
>
> 准确的说法是：**UDP 把可靠性的决策权交给了应用**。需要可靠时，这些工作只是从内核挪到你的代码里，总开销不会凭空消失。QUIC 就是这么干的，它在 UDP 之上重新实现了一套更灵活的可靠传输。

## 3. 三种真实报文长什么样

抽象的定义看完了，来看三个具体协议怎么解决「边界」和「含义」这两个问题。这里只取够说明问题的部分，完整的报文结构见 [[7.4 应用层协议]]。

![[图片/SVG/3_7_7_5_2.svg|1390]]

### 3.1 HTTP：文本行协议

```http
GET /search?q=socket HTTP/1.1
Host: example.com
Connection: keep-alive
Content-Length: 17

name=alice&age=30
```

HTTP 同时用了两套边界机制：

- **头部**用 `\r\n` 分隔每一行，用一个**空行**表示头部结束。
- **实体**的长度由 `Content-Length` 这个头字段声明，读满这么多字节就是一条完整消息。

文本协议的好处是人能直接读、telnet 就能手工调试；代价是解析要逐字节扫描分隔符，比读一个定长整数慢，而且数字要在文本和二进制之间来回转换。

| 字段 | 说明 |
|:---|:---|
| `Host` | 目标主机名，同一个 IP 上区分多个站点靠它 |
| `Connection` | `keep-alive` 表示这条 TCP 连接复用，不要关 |
| `Content-Length` | 实体的字节数，接收方据此判断读到哪算完 |
| `Content-Type` | 实体的格式，如 `application/json` |
| `Accept-Encoding` | 客户端能解开哪些压缩格式 |
| `User-Agent` | 客户端标识 |

### 3.2 DNS：定长二进制头

DNS 的头部固定 12 字节，里面有四个计数字段（问题数、回答数、授权记录数、附加记录数）。接收方先读满 12 字节，就知道后面要解析几条记录，逐条读完即可。

这是**长度前缀**思路的一个变体：不直接给字节数，而是给条目数，每个条目自带长度。

### 3.3 SSH：长度前缀

SSH 的二进制包格式把长度放在最前面：

```c
// RFC 4253 定义的 SSH 二进制包格式（简化）
struct SshPacketHeader {
    uint32_t packet_length;   // 后面还有多少字节（不含本字段自己）
    uint8_t  padding_length;  // 其中有多少是填充
};
// 之后是 payload，再之后是随机填充，最后是 MAC
```

接收方先读 4 字节拿到 `packet_length`，再精确读那么多字节，一条消息就切出来了。这种做法不需要扫描，也不怕正文里出现特殊字节。

## 4. 设计自己的协议要当心什么

假设你要定一个私有协议，写出了这样的头部：

```cpp
struct MsgHeader {
    uint32_t total_len;   // 总长度
    uint8_t  version;     // 版本号
    uint8_t  msg_type;    // 消息类型
};

MsgHeader h{6, 1, MSG_LOGIN};
send(fd, &h, sizeof(h), 0);   // 这一行有两个坑
```

**坑一：`sizeof(h)` 不是 6，是 8。**

`uint32_t` 要求 4 字节对齐，编译器会在结构体末尾补 2 个字节，把总大小凑成 4 的倍数。你以为发了 6 字节，实际发了 8 字节，对端按 6 字节解析，从第二条消息开始全部错位。

两种解法：

```cpp
// 解法一：告诉编译器不要填充（编译器相关，且会带来非对齐访问）
#pragma pack(push, 1)
struct MsgHeader { uint32_t total_len; uint8_t version; uint8_t msg_type; };
#pragma pack(pop)

// 解法二（推荐）：手工序列化到字节缓冲区，不依赖结构体布局
std::array<std::byte, 6> buf{};
uint32_t len_be = htonl(total_len);
std::memcpy(buf.data(), &len_be, 4);
buf[4] = std::byte{version};
buf[5] = std::byte{msg_type};
```

解法二多写几行，但换来两个好处：跨编译器、跨平台的字节布局完全确定；顺手把字节序也处理了。

**坑二：`total_len` 没做字节序转换。**

x86 是小端，网络字节序是大端。直接把 `uint32_t` 拷进去发出去，对端如果是大端机器（或者只是老老实实按网络字节序解析），读到的就是一个天文数字。多字节整数在进缓冲区之前必须过一次 `htonl()` / `htons()`，取出来时过 `ntohl()` / `ntohs()`。字节序转换函数见 [[7.7 套接字1]]。

**还要定的几件事**：

| 要定的东西 | 为什么 |
|:---|:---|
| 长度字段的上限 | 对方声明 4 GB，你照着分配内存就被打垮了 |
| 版本号 | 协议总会改，留个字段才有平滑升级的余地 |
| 消息类型 | 一条连接上要跑多种消息，得能分辨 |
| 超时与心跳 | 对端进程被 kill 时不会发 FIN，只能靠心跳发现 |

完整的粘包处理和长度前缀协议的实现，见 [[8.9 TCP的粘包和拆包]]。

## 5. 常见协议与端口

应用层协议笔记 [[7.4 应用层协议]] 已经把 HTTP、HTTPS、SSH、DNS、FTP、SMTP 六个协议的端口、传输层选择和边界机制逐个拆过，每个协议都配了报文结构图。

其中 DNS 最能印证本篇开头那句话：同一个协议在 UDP 上不需要长度字段（数据报天然有边界），换到 TCP 上就必须在前面加两个字节的长度。边界问题是每个协议都躲不掉的，换个传输层也只是换个还法。

## 6. 关键要点

1. **协议就是回答两个问题**：一条消息从哪到哪，以及每个字节什么含义。
2. **TCP 头 20 字节买到的是序号、确认号、窗口三个字段**，对应排序去重、确认重传、流量控制三项能力。
3. **UDP 不是「更快的 TCP」**，它是把可靠性的决策权交给应用；需要可靠时开销只是换了个地方。
4. **定边界只有三种办法**：定长、分隔符、长度前缀。长度前缀最通用，但必须设上限。
5. **结构体不能直接 send**：有对齐填充，有字节序问题。手工序列化到字节缓冲区才安全。
6. **文本协议好调试，二进制协议好解析**，选哪种取决于你更在意排障成本还是吞吐。
