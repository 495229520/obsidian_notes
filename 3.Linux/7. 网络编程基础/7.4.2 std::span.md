# 7.4.2 `std::span`：不拥有数据的连续内存视图

在 [[7.4.1 RPC协议模板]] 中，RPC 处理函数经常写成这样：

```cpp
using Bytes = std::vector<std::byte>;

std::uint32_t ReadU32(std::span<const std::byte> input) {
    if (input.size() != sizeof(std::uint32_t)) {
        throw std::invalid_argument("uint32 field must be 4 bytes");
    }

    std::uint32_t wire = 0;
    std::memcpy(&wire, input.data(), sizeof(wire));
    return ntohl(wire);
}
```

这里的 `std::span<const std::byte>` 是理解 RPC 字节编解码的关键。它不是一个容器，也不会复制或拥有参数数据，而是对一段**连续内存**的临时观察窗口。

## 0. 读 RPC 源码前需要的 C++ 基础

前一篇 RPC 模板开头集中出现了几种现代 C++ 写法：

```cpp
using Bytes = std::vector<std::byte>;

inline constexpr std::uint16_t kMagic = 0x5243;
inline constexpr std::size_t kHeaderLen = 14;

enum class FrameType : std::uint8_t {
    Request = 1,
    Response = 2,
};

struct Frame {
    FrameHeader header;
    Bytes body;
};
```

这些写法分别解决不同问题：

| 写法 | 解决的问题 |
|---|---|
| `using` | 给复杂类型起一个有业务含义的别名 |
| `std::byte` | 表示原始二进制字节，而不是字符或普通整数 |
| `std::uint16_t`、`std::uint32_t` | 明确协议字段的宽度 |
| `inline constexpr` | 定义可以放进头文件的编译期协议常量 |
| `enum class` | 用强类型枚举表示有限状态 |
| `struct` | 组织一个数据记录，但不等于线路上的字节布局 |
| `std::array`、`std::vector` | 分别管理固定长度和动态长度的连续数据 |

下面把这些写法逐个拆开。

### 0.1 `using`：类型别名，不是新类型

```cpp
using Bytes = std::vector<std::byte>;
```

这行给 `std::vector<std::byte>` 起了一个更短、更符合业务语义的名字。它不会创建一个新的 C++ 类型：

```cpp
Bytes a;
std::vector<std::byte> b;

// a 和 b 的类型完全相同
```

所以 `Bytes` 只是“保存 RPC 字节数据的 vector”的别名。它让代码从：

```cpp
std::vector<std::byte> body;
```

变成：

```cpp
Bytes body;
```

读者看到 `Bytes`，马上知道这段 vector 在协议里代表消息体，而不必每次重新阅读模板参数。

RPC 源码中还有一种更有价值的别名：

```cpp
using Handler = std::function<Bytes(std::span<const std::byte>)>;
```

它把一个方法处理器的接口固定成：

```text
输入：只读的请求字节
输出：拥有结果数据的 Bytes
```

这样，`handlers_` 的类型就容易理解：

```cpp
std::unordered_map<std::uint16_t, Handler> handlers_;
```

这里的 `using` 不是为了少敲几个字符，而是把“方法号对应什么样的函数”写成一个可复用的协议概念。

它和 `struct`、`class`、`enum class` 不同：这些会定义新的类型，而 `using` 只给已有类型换一个名字。关于类型别名，可以继续看 [[2.3 类型别名与命名空间]]。

### 0.2 `std::byte`：把数据当作原始字节

```cpp
std::byte one = std::byte{0x12};
```

`std::byte` 用来表示一组原始二进制位。它表达的是：

> 这里是一字节存储空间，暂时不要把它当成字符或整数解释。

RPC 的消息体使用：

```cpp
using Bytes = std::vector<std::byte>;
```

因为消息体可能包含任意二进制内容，例如整数、字符串、图片片段或序列化对象。使用 `std::byte` 比使用 `char` 更能提醒读者：这是一段二进制协议数据，不是文本。

`std::byte` 是强类型的，不能直接参与整数运算：

```cpp
std::byte value = std::byte{0x12};

// value + 1;  // 编译错误
```

如果确实需要把它转换成整数，应明确表达转换意图：

```cpp
const auto number = std::to_integer<std::uint8_t>(value);
```

这可以避免把“原始字节”和“有数值意义的整数”混在一起。

在 RPC 编解码中，通常使用 `std::memcpy` 在字节和整数之间复制表示：

```cpp
std::uint32_t wire = 0;
std::memcpy(&wire, input.data(), sizeof(wire));
const std::uint32_t value = ntohl(wire);
```

这里先复制字节，再通过 `ntohl` 解释字节序；不要把 `std::byte*` 强行转换成 `std::uint32_t*` 后直接解引用，因为那会引入对齐和类型双关问题。

还要分清：

```text
std::byte
    表示一个原始字节，不强调数值运算

std::uint8_t
    表示一个 0 到 255 的无符号整数
```

### 0.3 固定宽度整数：协议先规定字节数

RPC 头部使用：

```cpp
std::uint16_t code;
std::uint32_t request_id;
std::uint32_t body_len;
```

`std::uint16_t` 明确表示 16 bit，也就是 2 字节；`std::uint32_t` 明确表示 32 bit，也就是 4 字节。

协议字段不应该使用大小依平台而变化的 `int`、`long` 或 `short`，因为客户端和服务端可能运行在不同平台，双方必须先对字段宽度达成一致。

但字段宽度和字节序是两个问题：

```text
std::uint32_t
    规定占 4 字节

htonl() / ntohl()
    规定这 4 个字节如何排列
```

所以 `std::uint32_t` 本身并不等于网络字节序。发送前仍然需要：

```cpp
const std::uint32_t wire = htonl(value);
```

`std::size_t` 主要表示本机内存中的数量和下标，例如：

```cpp
std::size_t offset = 0;
std::size_t body_size = body.size();
```

它适合做容器索引和内存长度，但不适合直接作为跨机器协议字段，因为它的宽度依平台而定。RPC 头部因此使用固定宽度的 `std::uint32_t body_len`，而本地循环中的 `offset` 使用 `std::size_t`。

### 0.4 `inline constexpr`：头文件中的协议常量

RPC 源码中的：

```cpp
inline constexpr std::uint16_t kMethodAdd = 1;
```

可以拆成三层：

```text
inline
    允许这个变量定义在头文件中，并在多个翻译单元中使用

constexpr
    值在编译期确定，可以作为编译期常量

std::uint16_t
    这个常量的类型是明确宽度的 16 位无符号整数
```

`constexpr` 表示这个值不能在运行时被修改，并且编译器可以在编译期使用它：

```cpp
inline constexpr std::size_t kHeaderLen = 14;

std::array<std::byte, kHeaderLen> raw_header{};
```

`kHeaderLen` 可以作为 `std::array` 的模板参数，说明它是编译期可确定的值。

`inline` 在这里不是“建议内联展开”的意思，而是 C++17 引入的 inline variable 语义。协议常量经常放在公共头文件：

```cpp
// protocol.hpp
inline constexpr std::uint16_t kMethodAdd = 1;
```

客户端和服务端都可以包含这个头文件，不需要在某个 `.cpp` 文件中额外提供变量定义。多个翻译单元看到的是同一个 inline 变量定义，不会因为头文件被多次包含而违反 ODR。

如果常量只写在一个 `.cpp` 文件里，`inline` 通常没有必要；这里同时写 `inline constexpr`，是因为它既是编译期协议常量，又适合放在客户端和服务端共享的协议头文件中。

常见的 RPC 常量包括：

```cpp
inline constexpr std::uint16_t kMagic = 0x5243;
inline constexpr std::uint8_t kVersion = 1;
inline constexpr std::size_t kHeaderLen = 14;
inline constexpr std::uint32_t kMaxBodyLen = 1024 * 1024;
```

它们把“魔数、版本、头部长度、消息上限”集中成一份协议定义，避免客户端和服务端各写一套容易漂移的数字。

### 0.5 `enum class`：有限状态的强类型表示

```cpp
enum class FrameType : std::uint8_t {
    Request = 1,
    Response = 2,
};
```

它定义了一个新类型 `FrameType`，可表示的命名值是 `FrameType::Request` 和 `FrameType::Response`。

`enum class` 使用作用域限定名称，不能把 `Request` 直接当成外层的普通名字使用，也不会轻易和整数混用：

```cpp
FrameType type = FrameType::Request;

// if (type == 1) { }  // 编译错误
```

冒号后的 `std::uint8_t` 指定底层整数类型。它说明这个枚举值适合用 1 字节表示，但这仍然不意味着可以直接把整个 C++ 对象发送到网络上。线路编码仍然要逐字段完成：

```cpp
out[3] = static_cast<std::byte>(h.type);
```

RPC 中的 `StatusCode` 也是同样的设计，只是它使用 `std::uint16_t` 作为底层类型。枚举用于限制“这个字段有哪些合法状态”，底层类型用于表达表示宽度。更多枚举基础见 [[15.9 枚举类]]。

### 0.6 `struct`：组织数据，不负责协议序列化

```cpp
struct Frame {
    FrameHeader header;
    Bytes body;
};
```

`struct` 适合表达一个数据记录。它的成员默认是 `public`，所以 `ReadFrame` 可以直接填充，调用者也可以读取：

```cpp
frame.header
frame.body
```

这里的 `Frame` 还体现了所有权关系：

```text
Frame
 ├── header：保存解析后的头部字段
 └── body：由 Bytes 拥有实际消息体
```

`Frame` 在内存中的布局不等于线路上的 14 字节头部。C++ 可能插入 padding，枚举和整数也有主机字节序问题，所以源码仍然使用 `EncodeHeader` 和 `DecodeHeader` 逐字段处理。

### 0.7 `std::array` 和 `std::vector`：固定长度与动态长度

固定长度的 RPC 头部使用：

```cpp
std::array<std::byte, kHeaderLen> raw_header{};
```

`std::array` 的长度是编译期固定的，数据直接存储在对象内部，不需要为了这 14 字节单独进行动态分配。

消息体使用：

```cpp
using Bytes = std::vector<std::byte>;
```

因为 body 长度由 `body_len` 决定，运行时才知道：

```cpp
frame.body.resize(frame.header.body_len);
```

可以这样区分：

```text
std::array<T, N>
    N 在编译期固定，适合固定头部和固定大小的临时缓冲区

std::vector<T>
    元素数量运行时决定，适合可变长度的消息体
```

两者都保证元素连续存储，因此都能转换成适合读取的 `std::span<const T>`。

### 0.8 `std::optional`：把“没有结果”写进类型

```cpp
std::optional<Frame> ReadFrame(int fd);
```

这个返回值有两种状态：

```text
有值：成功读取了一帧 Frame
无值：对端在下一帧开始前正常关闭连接
```

所以调用代码可以写成：

```cpp
while (auto frame = ReadFrame(fd)) {
    Serve(frame->header, frame->body);
}
```

这里的 `frame` 是循环条件中声明的局部变量。每次循环开始时，先调用 `ReadFrame`；有值就进入循环体，没有值就结束循环。

`std::optional<Frame>` 比返回一个特殊的空 `Frame` 更清楚，因为 `Frame` 本身不需要约定“某个字段为 0 就代表没有帧”。协议错误则通过异常报告，而不是伪装成空值。

### 0.9 `std::function`、lambda 和 `std::move`

服务端把方法号映射到处理函数：

```cpp
using Handler = std::function<Bytes(std::span<const std::byte>)>;
std::unordered_map<std::uint16_t, Handler> handlers_;
```

`std::function` 是一个类型擦除容器，可以保存满足相同调用签名的不同可调用对象，例如普通函数、lambda 或函数对象。

注册 `Add` 时使用 lambda：

```cpp
server.Register(kMethodAdd,
    [](std::span<const std::byte> args) {
        // 解析 args 并返回 Bytes
    });
```

`[]` 表示这个 lambda 不捕获外部变量，调用时只依赖参数 `args`。

注册函数内部：

```cpp
handlers_[method] = std::move(handler);
```

`handler` 是按值接收的 `std::function`。使用 `std::move` 后，程序把它内部保存的可调用对象资源转移给 map 中的目标，避免再做一次不必要的拷贝。

`std::move` 本身不移动数据，它只是把表达式转换成可以触发移动构造或移动赋值的右值。移动之后的 `handler` 仍然是一个有效对象，但不应再依赖它原来保存的具体目标。

这部分可以继续看 [[13.6.1 回调函数与Reactor事件分发]] 和 [[15.8 移动语义与右值引用&&]]。

### 0.10 结构化绑定、显式转换和边界工具

服务端分发时使用：

```cpp
auto [status, result] = Dispatch(method, args);
```

`Dispatch` 返回一个 `std::pair<StatusCode, Bytes>`。结构化绑定把 pair 中的两个成员分别命名为 `status` 和 `result`，比手动写 `.first`、`.second` 更直观。

协议编码中经常看到：

```cpp
static_cast<std::byte>(h.version)
static_cast<std::uint16_t>(status)
```

这是显式类型转换。网络协议代码不应该依赖隐式转换，因为字段的线路类型必须一眼可见。

对于 `std::byte` 转整数，优先使用：

```cpp
const auto value = std::to_integer<std::uint8_t>(input[0]);
```

它直接说明“我要把这个原始字节解释成一个整数”。

检查无符号整数溢出时使用：

```cpp
if (b > std::numeric_limits<std::uint32_t>::max() - a) {
    throw std::invalid_argument("uint32 addition overflow");
}
```

`std::numeric_limits<T>::max()` 根据类型给出可表示的最大值，比手写某个平台相关的数字更可靠。

### 0.11 异常类型和 `using` 继承构造函数

协议错误继承自标准运行时异常：

```cpp
class ProtocolError : public std::runtime_error {
public:
    using std::runtime_error::runtime_error;
};
```

这句 `using` 不是类型别名，而是把基类的构造函数引入派生类。于是可以直接写：

```cpp
throw ProtocolError("unexpected magic");
```

不需要为每一种字符串参数重新写构造函数。

远程错误的构造函数使用 `explicit`：

```cpp
explicit RemoteError(std::uint16_t status);
```

它禁止编译器把整数偷偷转换成 `RemoteError`，要求调用者明确构造错误对象。网络错误码这种语义重要的值，适合避免隐式转换。

源码中的 `try/catch` 还把不同层级的错误分开：

```text
std::invalid_argument
    预期的业务参数错误，转换为 INVALID_ARGUMENT

其他处理异常
    转换为 HANDLER_ERROR

ProtocolError
    协议损坏，交给连接所有者关闭连接
```

### 0.12 头文件和 `std::` 命名空间

RPC 源码在文件开头包含了很多标准库头文件。每个头文件负责声明一组设施：

| 头文件 | 源码中使用的内容 |
|---|---|
| `<array>` | `std::array` |
| `<cstddef>` | `std::byte`、`std::size_t` |
| `<cstdint>` | `std::uint8_t`、`std::uint16_t`、`std::uint32_t` |
| `<cstring>` | `std::memcpy` |
| `<functional>` | `std::function` |
| `<limits>` | `std::numeric_limits` |
| `<optional>` | `std::optional` |
| `<span>` | `std::span` |
| `<stdexcept>` | `std::runtime_error`、`std::invalid_argument` |
| `<system_error>` | `std::system_error` |
| `<unordered_map>` | `std::unordered_map` |
| `<utility>` | `std::move`、`std::pair` |
| `<vector>` | `std::vector` |

`std::` 是标准库的命名空间。例如：

```cpp
std::vector<std::byte> body;
std::span<const std::byte> input;
```

使用命名空间限定名可以避免项目自己的类型和标准库类型重名。RPC 源码没有写：

```cpp
using namespace std;
```

这样做更啰嗦一点，但每个名字的来源清楚，也避免把大量标准库名字引入当前作用域。网络库和协议代码通常值得保留这种明确性。

## 1. `std::span` 是什么

可以把 `std::span<T>` 粗略理解成两个信息的组合：

```text
起始地址 + 元素数量
```

它和“指向第一项的指针 + 这段内存有多少项”很接近，但 `std::span` 把这两个信息包装成了一个类型，并提供了切片、索引、长度查询等接口。它本身不负责分配和释放内存。

`std::span` 是 C++20 引入的类型，需要包含：

```cpp
#include <span>
```

它的模板形式可以先这样理解：

```cpp
template<class T, std::size_t Extent = std::dynamic_extent>
class span;
```

其中：

- `T` 是视图中每个元素的类型，例如 `std::byte`；
- `Extent` 是元素数量，可以是编译期固定值，也可以是运行时决定的 `std::dynamic_extent`。

在 RPC 代码中，消息体长度由帧头的 `body_len` 决定，所以通常使用动态长度：

```cpp
std::span<const std::byte> input;
```

它表示：

> `input` 观察一段只读的连续字节，具体有多少字节要到运行时通过 `input.size()` 得到。

## 2. 为什么 RPC 参数使用 `std::span`

先看这个函数：

```cpp
std::uint32_t ReadU32(std::span<const std::byte> input);
```

把它拆开：

```text
std::span
    表示一段连续内存的视图

const std::byte
    只能通过这个参数读取字节，不能修改字节

input
    视图变量本身
```

RPC 的消息体通常由 `std::vector<std::byte>` 保存，但解析函数并不需要拥有这段数据，也不需要修改它。它只需要：

1. 从某个地址开始读取；
2. 知道一共有多少字节；
3. 根据协议解释这些字节。

`std::span` 正好表达了这个需求。

### 2.1 不复制数据

下面的调用不会复制整个 `bytes`：

```cpp
Bytes bytes(4);
const std::uint32_t value = ReadU32(bytes);
```

传递的只是一个很小的视图描述信息。真正的数据仍然由 `bytes` 持有。

如果参数写成按值传递的 `Bytes`：

```cpp
std::uint32_t ReadU32(Bytes input);  // 会复制或移动一份消息体
```

就会改变所有权，可能产生复制成本，也容易让人误解函数会接管消息体。

使用 `const Bytes&` 可以避免复制：

```cpp
std::uint32_t ReadU32(const Bytes& input);
```

但它把函数限定为只能接收 `Bytes`，不能直接表达“我只需要任意一段连续字节”。`std::span` 的接口意图更准确。

### 2.2 可以接收不同的连续容器

`std::span<const std::byte>` 可以观察多种连续存储：

```cpp
Bytes dynamic_bytes(8);
Bytes four_bytes(4);
std::array<std::byte, 4> fixed_bytes{};

const auto a = ReadU32(four_bytes);
const auto b = ReadU32(fixed_bytes);
```

函数不需要为 `std::vector` 和 `std::array` 各写一份重载。

它也可以观察已有 `span` 的一部分：

```cpp
const std::span<const std::byte> bytes = dynamic_bytes;
const auto first_four = bytes.first(4);
const auto last_four = bytes.subspan(4, 4);
```

`first_four` 和 `last_four` 都只是新的视图，不会产生新的字节数组。

## 3. `std::span<const T>` 和 `std::span<T>`

这两个类型表达的权限不同：

```cpp
std::span<const std::byte> input;  // 只读视图
std::span<std::byte> output;       // 可写视图
```

只读解析函数使用：

```cpp
void Decode(std::span<const std::byte> input);
```

它不能通过 `input` 修改数据：

```cpp
input[0] = std::byte{0};  // 编译错误
```

需要填充输出缓冲区时，才使用可写视图：

```cpp
void Encode(std::span<std::byte> output) {
    if (output.size() < 4) {
        throw std::length_error("output buffer is too small");
    }

    output[0] = std::byte{0x12};
    output[1] = std::byte{0x34};
    output[2] = std::byte{0x56};
    output[3] = std::byte{0x78};
}
```

`std::span<const std::byte>` 中的 `const` 只限制当前函数通过这个视图写入数据。它不等于底层容器永远不会被其他代码修改。

## 4. RPC 示例中的 `span` 是怎样传递的

服务端读取一帧后，`Frame` 中的 body 由 `Bytes` 持有：

```cpp
struct Frame {
    FrameHeader header;
    Bytes body;
};
```

分发方法时：

```cpp
auto [status, result] = Dispatch(
    frame->header.code,
    frame->body
);
```

`frame->body` 可以转换成：

```cpp
std::span<const std::byte>
```

于是处理函数拿到的是同一段 body 的只读视图：

```cpp
server.Register(kMethodAdd,
    [](std::span<const std::byte> args) {
        if (args.size() != 8) {
            throw std::invalid_argument(
                "Add request must contain two uint32 values");
        }

        const std::uint32_t a = ReadU32(args.first(4));
        const std::uint32_t b = ReadU32(args.subspan(4, 4));
        return EncodeU32(a + b);
    });
```

这里的 `args.first(4)` 和 `args.subspan(4, 4)` 都只创建视图，不会复制 body。

```mermaid
flowchart LR
    A[Frame::body 持有字节] --> B[转换为 std::span<const std::byte>]
    B --> C[args.first(4)]
    B --> D[args.subspan(4, 4)]
    C --> E[ReadU32 读取 a]
    D --> F[ReadU32 读取 b]
```

真正拥有内存、负责释放内存的仍然是 `Frame::body`。处理函数返回后，`args` 这个视图也不应该继续被保存或使用。

## 5. 常用接口

### 5.1 查看长度和元素

```cpp
std::span<const std::byte> bytes = dynamic_bytes;

const std::size_t length = bytes.size();
const bool empty = bytes.empty();
const std::byte first = bytes[0];
```

`size()` 返回元素数量。对于 `std::span<const std::byte>`，一个元素就是一个字节，所以数量也就是字节数。

`operator[]` 不负责做边界检查。访问前需要先确认长度：

```cpp
if (bytes.size() < 4) {
    throw std::invalid_argument("at least 4 bytes are required");
}

const auto first_four = bytes.first(4);
```

### 5.2 创建子视图

```cpp
const auto prefix = bytes.first(4);
const auto suffix = bytes.last(4);
const auto middle = bytes.subspan(4, 4);
```

这些函数都不复制数据，只调整新视图的起始位置和长度。

源码中的：

```cpp
const std::uint32_t a = ReadU32(args.first(4));
const std::uint32_t b = ReadU32(args.subspan(4, 4));
```

等价于：

```text
args[0..3]  → a
args[4..7]  → b
```

这里的 `first(4)` 和 `subspan(4, 4)` 有前置条件：请求体必须至少包含对应范围。RPC 代码先检查 `args.size() == 8`，因此后面的切片才是安全的。

### 5.3 `data()`

```cpp
const std::byte* raw = bytes.data();
```

`data()` 返回底层内存的起始地址，通常用于调用需要指针的 C 或系统 API，例如 `std::memcpy`。

但只拿到 `data()` 不足以知道数据有多长，所以处理字节缓冲区时，长度必须和指针一起传递。`std::span` 正好把这两个信息放在一起。

## 6. 为什么函数参数通常按值传 `span`

推荐这样写：

```cpp
void Decode(std::span<const std::byte> input);
```

而不是：

```cpp
void Decode(const std::span<const std::byte>& input);
```

`std::span` 本身只是一个很小的视图对象，通常包含一个地址和一个长度。按值传递不会复制底层字节，只会复制这个小描述符。

按值传参还直接表达了“函数只借用这段连续内存”。如果函数需要保存这个视图，也必须额外考虑底层内存的生命周期；传引用并不能解决生命周期问题。

## 7. 生命周期：`span` 最容易出错的地方

`span` 不拥有数据，所以它的有效期不能超过底层数据。

下面的写法会产生悬空视图：

```cpp
std::span<const std::byte> MakeView() {
    Bytes temporary(8);
    return temporary;  // 错误：函数返回后 temporary 已经销毁
}
```

返回的 `span` 只保存了一个已经失效的地址。之后访问它属于未定义行为。

安全原则是：

```text
拥有数据的对象必须比 span 活得更久
```

在 RPC 服务端中，下面的调用是安全的：

```cpp
while (auto frame = ReadFrame(fd)) {
    Dispatch(frame->header.code, frame->body);
}
```

因为 `frame->body` 在整个 `Dispatch` 调用期间仍然存在。处理函数返回后，`span` 也就不应该继续被保存或使用。

不要把 `span` 保存到异步任务、成员变量或回调中，除非能保证原始 `Bytes` 在任务结束前一直存在。

## 8. 动态长度和固定长度

RPC body 通常是动态长度：

```cpp
std::span<const std::byte> body;
```

因为每次请求的长度由协议数据决定。

如果一段数据的长度在编译期就固定，可以使用固定 extent：

```cpp
using HeaderView = std::span<const std::byte, 14>;

void DecodeFixedHeader(HeaderView input);

std::array<std::byte, 14> raw_header{};
DecodeFixedHeader(raw_header);
```

固定 extent 可以把“必须是 14 字节”表达在类型中；动态 extent 更灵活，适合先接收、再根据协议检查长度的场景。

前一篇 RPC 示例中的 `DecodeHeader` 使用动态 `span`：

```cpp
FrameHeader DecodeHeader(std::span<const std::byte> input) {
    if (input.size() != kHeaderLen) {
        throw ProtocolError("invalid header size");
    }
    // ...
}
```

这是因为它要在函数内部统一检查输入长度，并把错误转换成协议错误。

## 9. `span` 能接收什么，不能接收什么

它要求数据在内存中连续排列，而且元素类型必须匹配。因此，对于
`std::span<const std::byte>`，可以接收：

```cpp
std::vector<std::byte>
std::array<std::byte, 8>
std::span<std::byte>
```

如果视图的元素类型是 `char`，则 `std::string` 和 `std::string_view` 也可以转换为：

```cpp
std::span<const char>
```

但它们不能直接转换为 `std::span<const std::byte>`，因为 `char` 和 `std::byte` 是不同的类型。

无论元素类型是什么，都不能直接观察节点分散存储的容器，例如：

```cpp
std::list<std::byte>
std::map<int, int>
```

因为这些容器没有一整段连续的字节区域。

可以这样记：

```text
vector  = 拥有一段动态数组
span    = 观察一段已有的连续数组
```

## 10. 在 RPC 编解码中的使用原则

可以按下面的规则设计函数：

```cpp
// 只读解析：使用 span<const T>
std::uint32_t ReadU32(std::span<const std::byte> input);

// 写入已有缓冲区：使用 span<T>
void EncodeU32(std::span<std::byte> output, std::uint32_t value);

// 需要拥有结果：返回 Bytes 或其他拥有数据的容器
Bytes BuildResponse(std::uint32_t value);
```

一个实用的分层方式是：

```text
Bytes
  负责拥有数据

std::span<const std::byte>
  负责只读查看数据

std::span<std::byte>
  负责写入调用方提供的缓冲区
```

`span` 让函数明确表达了所有权关系：函数只是借用数据，调用者仍然负责保证数据有效。

## 11. 需要记住的要点

1. `std::span` 是 C++20 的非拥有型连续内存视图。
2. `std::span<const std::byte>` 适合 RPC 请求体的只读解析。
3. 按值传递 `span` 不会复制底层消息体，只会复制一个小视图描述符。
4. `first()`、`last()`、`subspan()` 创建的是视图，不是新的字节数组。
5. `span` 不能延长底层数据的生命周期，也不能返回指向局部容器的视图。
6. 使用切片前先检查长度；`operator[]`、`first()` 和 `subspan()` 不会替你验证协议格式。
7. `span` 适合表达“借用一段连续内存”，`vector` 适合表达“我拥有这段数据”。
