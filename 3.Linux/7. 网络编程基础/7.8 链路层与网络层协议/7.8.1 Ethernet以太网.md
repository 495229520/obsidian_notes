# Ethernet 以太网

## 以太网负责的那一小段路

[[7.1 基础知识|分层模型]]把「数据送到地球另一端」拆成了几个小问题，Ethernet 只负责最底下那个：**一条链路的两头，怎么把一串字节完整地递过去**。

它管的范围只有一跳。物理层管的是「怎么把 1 和 0 变成电平或光信号」，而 Ethernet 在这之上补了三件事：

1. **划边界**：物理层交上来的是不断流的比特，Ethernet 规定从哪到哪算一帧。
2. **定收件人**：一条链路上可能挂着几十台机器，得说清这一帧是发给谁的。
3. **查错**：线上会出错，帧尾带一个校验和，错了直接丢掉。

第三条只查错、不重传。以太网从设计上就是**不可靠**的：坏帧默默丢弃，谁也不通知。要不丢不重不乱序，得靠上面的 [[7.5 TCP协议基础|TCP]]。

> [!note] 「以太网」这个词今天指两件事
> 一是 IEEE 802.3 那一整套物理层规范（双绞线、光纤、速率、编码）；二是链路层的帧格式。网络编程只关心后者。不管底下跑的是 100BASE-TX 还是 10GBASE-SR，交给协议栈的帧长得完全一样。

## 帧格式：哪些字节算帧长

![[图片/SVG/3_7_7_8_1_1.svg|900]]

日常见到的几乎都是 **Ethernet II** 格式（也叫 DIX 格式），头部固定 14 字节，结构简单到可以背下来：

| 字段 | 长度 | 说明 |
|:---|:---:|:---|
| 目的 MAC | 6 字节 | 这一帧交给谁 |
| 源 MAC | 6 字节 | 谁发的 |
| EtherType | 2 字节 | payload 是什么协议 |
| Payload | 46 ～ 1500 字节 | 上层数据 |
| FCS | 4 字节 | CRC-32 校验和 |

### 前导码不算帧长

帧真正上线之前，网卡还要在前面加 8 个字节：7 字节的前导码（`10101010` 重复）让接收端的时钟锁上发送端的节奏，1 字节的 SFD（`10101011`，末位从 0 变 1）标记「正文从下一位开始」。

这 8 字节由网卡硬件生成和剥离，**抓包工具看不到，也不计入帧长**。所以「以太网帧最大 1518 字节」这句话说的是从目的 MAC 到 FCS，线上实际传的是 1526 字节。

### FCS 通常也看不到

FCS 是覆盖整个帧的 CRC-32。接收网卡算一遍，对不上就直接丢，不往上送，也不告诉对端。驱动交给协议栈的一般是**已经剥掉 FCS 的帧**，所以 `tcpdump` 打印的 `length 74` 是 74 而不是 78。

> [!warning] 帧长口径有三种，别混着用
> - 线上字节数 = 前导码 8 + 帧 64～1518
> - 标准说的帧长 = 64 ～ 1518（含 FCS，不含前导码）
> - 抓包工具显示的长度 = 60 ～ 1514（连 FCS 也没了）
>
> 排障时对不上数，八成是三个口径串了。

### 插了 VLAN 标签之后

802.1Q 的 4 字节标签插在**源 MAC 之后、EtherType 之前**：前 2 字节固定 `0x8100`，后 2 字节装 3 位优先级（PCP）+ 1 位 DEI + 12 位 VLAN ID。

上限因此从 1518 涨到 1522，交换机必须能收这种略微超长的帧（业内叫 baby giant）。最小帧长仍然是 64：标签占了 4 字节，填充的下限就从 46 降到 42。

主机上通常看不到标签：交换机在 access 口进来时打上、出去时剥掉，只有 trunk 口和配了 VLAN 子接口的主机才见得着。

## MAC 地址的 48 位怎么读

一个 MAC 写成 `52:54:00:8f:1c:2a`，6 字节 48 位。前 3 字节是 **OUI**，IEEE 分配给厂商；后 3 字节厂商自己排。

真正有用的是**第一个字节的最低两位**：

| 位 | 名字 | 取值 | 含义 |
|:---:|:---:|:---:|:---|
| bit 0 | I/G | 0 | 单播，只发给一个接口 |
| | | 1 | 组播，一组接口都收 |
| bit 1 | U/L | 0 | 全球唯一，来自 IEEE 分配的 OUI |
| | | 1 | 本地管理，虚拟网卡或随机化出来的地址 |

对着这两位读几个常见地址：

- `ff:ff:ff:ff:ff:ff`：全 1，I/G 自然是 1。**广播**，本链路所有接口都必须收。
- `01:00:5e:xx:xx:xx`：IPv4 组播。MAC 的低 23 位直接抄 IPv4 组播地址的低 23 位。但 IPv4 组播地址有 28 位可变，**32 个组会映射到同一个 MAC**，网卡多收的那部分要靠 IP 层再滤一次。
- `33:33:xx:xx:xx:xx`：IPv6 组播，低 32 位抄 IPv6 组播地址的低 32 位。[[7.8.3 IPv6|IPv6]] 用它取代了广播。
- `52:54:00:...`：`0x52` = `0101 0010`，bit 1 是 1，本地管理地址。QEMU/KVM 虚拟网卡的典型前缀，Docker 容器则常见 `02:42:...`。

> [!tip] 网卡默认只收三类帧
> 目的 MAC 是自己的、是广播的、是自己订阅的组播。其余的在硬件层就丢了，不消耗 CPU。抓包能看到别人的帧，是因为 `tcpdump` 把网卡切成了**混杂模式**（promiscuous），关掉了这层过滤。

## EtherType：一个字段完成分用

接收方拿到一帧，得知道后面那坨数据该交给 IP、ARP 还是别的模块。EtherType 就干这件事，取值和动作是一一对应的：

| 值 | 交给谁 |
|:---|:---|
| `0x0800` | [[7.8.2 IPv4\|IPv4]] |
| `0x0806` | [[7.8.4 ARP\|ARP]] |
| `0x86DD` | [[7.8.3 IPv6\|IPv6]] |
| `0x8100` | 802.1Q，剥掉标签再读下一个 EtherType |
| `0x8863` / `0x8864` | PPPoE 发现阶段 / 会话阶段 |

这就是[[7.4 协议|协议]]那篇里说的「含义是什么」在链路层的答案：一个 2 字节的类型标签，把 payload 派发给正确的解析器。

历史上 802.3 把这两个字节当**长度**用，于是留下一条分界规则：

- 值 ≤ `0x05DC`（1500）→ 这是长度，老 802.3 格式
- 值 ≥ `0x0600`（1536）→ 这是 EtherType

1500 正好是 payload 上限，两种用法才能靠数值区分开。中间那段是保留的。今天除了 STP 这类协议还在用 802.3 + LLC 封装，基本都是 Ethernet II。

## 一帧在网络里怎么走

![[图片/SVG/3_7_7_8_1_2.svg|900]]

### MAC 只在一条链路内有效

这是链路层最容易搞错的一点：**MAC 地址不是端到端的**。

主机 A 要访问公网的服务器 B，它填目的 MAC 时填的是**默认网关**的 MAC，不是 B 的。原因很直白：A 根本没办法知道 B 的 MAC，因为 [[7.8.4 ARP|ARP]] 请求靠二层广播扩散，而广播出不了本地链路。

所以一次跨网段访问，帧头被重写了很多次：

| 层 | 跨路由器时 |
|:---|:---|
| IP 源/目的地址 | 不变（NAT 是唯一常见例外） |
| MAC 源/目的地址 | 每一跳整个换掉 |
| TTL | 每跳减一 |

路由器每收到一帧要做四件事：校验 FCS 后丢掉整个旧帧头，TTL 减一，重算 IP 首部校验和，再按新的下一跳封一个全新的 Ethernet 帧。「IP 端到端，MAC 逐跳」这句话，就是这个流程的压缩版。

### 交换机怎么学会转发

交换机开机时 MAC 表是空的，靠转发过程本身把表填起来：

1. 收到一帧，把**源 MAC** 和**入端口**记进 MAC 表，意思是这台机器挂在这个口后面。
2. 拿**目的 MAC** 查表。命中就只往那个口发；没命中就往除入端口外的所有口发一遍（泛洪）。
3. 对端一回包，交换机顺手学到它的位置，之后就不用再泛洪了。

学习用源 MAC，转发用目的 MAC，这两个动作看的不是同一个字段。表项会老化，Linux 网桥默认 300 秒，为的是机器换了端口之后表能自己纠正。

由此可以定出两个范围：

- **广播域**：一个广播帧能到达的范围。默认整台交换机（或整个 VLAN）是一个广播域，路由器切断它。
- **冲突域**：会互相争抢介质的范围。集线器时代整段线是一个冲突域，交换机的全双工端口下每个端口自成一个，CSMA/CD 实际上已经退休了。

> [!danger] 二层没有 TTL
> IP 有 TTL，转多了会被丢弃；Ethernet 帧头里**没有任何跳数字段**。所以二层一旦成环，一个广播帧会被无限泛洪复制下去，几秒内就能把整个广播域的带宽和 CPU 打满，这就是广播风暴。防它只能靠 STP/RSTP 这类协议主动阻塞掉冗余链路，把拓扑剪成一棵树。

## MTU、最小帧长与填充

**MTU 指 payload 的上限，不含 14 字节帧头。** Ethernet 的 1500 是这么来的，`ip link` 里看到的 `mtu 1500` 也是这个意思。

一个 1500 字节的 IP 数据报，在线上占 1500 + 14 + 4 = 1518 字节。IP 层要发更大的数据报，只有两条路：[[7.8.2 IPv4|IPv4]] 在路由器上分片，或者 [[7.8.3 IPv6|IPv6]] 靠路径 MTU 发现让源端提前把包做小。

另一头的 46 字节下限是历史包袱。10 Mbit/s 共享介质时代要靠 CSMA/CD 检测冲突，发送方必须在**帧发完之前**察觉到碰撞，这就要求帧的传输时间不短于信号跑一个来回的时间，算下来是 512 个比特位，即 64 字节。payload 不够就补 0 凑数。

> [!warning] 填充的字节不带长度信息
> Ethernet 头里没有长度字段，所以接收方无法从帧本身判断哪些是数据、哪些是填充。这活儿只能上层干：IP 首部里的总长度字段说了数据报有多长，多出来的直接忽略。
>
> 副作用是曾经的 **etherleak** 类漏洞：某些驱动用未清零的内存做填充，把内核栈上的残留数据泄露到了线上。

Jumbo Frame 是把 MTU 抬到 9000 的惯例做法（不在 IEEE 802.3 标准里）。存储网络和集群内网常用，能把每字节摊到的头部开销和中断次数都压下来。代价是**路径上每一台设备都得支持**，中间有一台没配，大包会被丢掉或触发分片，症状往往是「小包通、大包不通」这种最难查的问题。

## 在 Linux 上看链路层

### 看接口

```bash
# MAC、MTU、链路状态一次看全
ip link show eth0
#   2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP
#       link/ether 52:54:00:8f:1c:2a brd ff:ff:ff:ff:ff:ff

ip -s link show eth0        # 加 -s 看收发包数、错误数、丢弃数
ethtool eth0                # 协商速率与双工，网卡真实链路状态

cat /sys/class/net/eth0/address   # 脚本里读 sysfs 比解析 ip 输出稳
cat /sys/class/net/eth0/mtu

sudo ip link set eth0 mtu 9000    # 改大要求网卡和沿途交换机都支持
```

`ip link` 那行里 `state UP` 和 `LOWER_UP` 是两回事：前者是管理状态（你有没有启用它），后者是物理链路状态（网线插没插）。网线拔了会掉 `LOWER_UP`，但 `state` 仍是 `UP`。

### 抓帧

`-e` 是看链路层的关键开关，它让 `tcpdump` 把帧头也打出来：

```bash
sudo tcpdump -i eth0 -e -n -c 5
# 14:22:31.100211 52:54:00:8f:1c:2a > 52:54:00:12:34:56, ethertype IPv4 (0x0800), length 74: ...
```

把同网段目标和公网目标对比着抓，能直接看出上面说的「MAC 只在本地有效」：

```bash
sudo tcpdump -i eth0 -e -n 'host 192.168.1.20'   # 目的 MAC = 对方主机
sudo tcpdump -i eth0 -e -n 'host 1.1.1.1'        # 目的 MAC = 默认网关
```

Linux 网桥本身就是一台软件交换机，它的 MAC 表可以直接看：

```bash
bridge fdb show br br0
cat /sys/class/net/br0/bridge/ageing_time   # 单位 1/100 秒，30000 即默认 300 秒
```

### 自己解析一个帧

`AF_PACKET` 套接字拿到的是**完整的链路层帧**，缓冲区第 0 字节就是目的 MAC：

```cpp
#include <linux/if_ether.h>   // struct ethhdr、ETH_P_ALL、ETH_P_IP
#include <sys/socket.h>
#include <arpa/inet.h>        // htons / ntohs
#include <array>
#include <cstddef>            // std::byte
#include <cstdint>
#include <cstdio>
#include <cstring>

int main() {
    // 第三个参数要过 htons：内核按网络字节序比对 EtherType。
    // ETH_P_ALL 表示不过滤，什么帧都收上来。
    const int fd = ::socket(AF_PACKET, SOCK_RAW, htons(ETH_P_ALL));
    if (fd < 0) {
        std::perror("socket");        // 失败多半是缺 CAP_NET_RAW
        return 1;
    }

    std::array<std::byte, 2048> buf{};   // 1518 就够，留点余量给 VLAN 和 jumbo
    while (true) {
        const ssize_t n = ::recv(fd, buf.data(), buf.size(), 0);
        if (n < static_cast<ssize_t>(sizeof(ethhdr))) continue;

        ethhdr eh{};
        std::memcpy(&eh, buf.data(), sizeof(eh));      // 见下方说明，别用 reinterpret_cast

        const std::uint16_t type = ntohs(eh.h_proto);  // 线上是大端，比较前转回主机序
        const char* upper = "其他";
        switch (type) {
            case ETH_P_IP:   upper = "IPv4"; break;
            case ETH_P_ARP:  upper = "ARP";  break;
            case ETH_P_IPV6: upper = "IPv6"; break;
            default: if (type <= 1500) upper = "802.3 长度字段";
        }

        std::printf("dst=%02x:%02x:%02x:%02x:%02x:%02x  src=%02x:%02x:%02x:%02x:%02x:%02x  "
                    "type=0x%04x(%s)  len=%zd\n",
                    eh.h_dest[0], eh.h_dest[1], eh.h_dest[2],
                    eh.h_dest[3], eh.h_dest[4], eh.h_dest[5],
                    eh.h_source[0], eh.h_source[1], eh.h_source[2],
                    eh.h_source[3], eh.h_source[4], eh.h_source[5],
                    type, upper, n);
    }
}
```

有四个点值得说清楚：

- **为什么用 `memcpy` 而不是 `reinterpret_cast<ethhdr*>(buf.data())`。** 内核不保证缓冲区首地址满足 `ethhdr` 的对齐要求，而且把一块 `std::byte` 直接当成另一个类型来读属于类型双关，是未定义行为。`memcpy` 两个问题一起解决，编译器优化后通常也不产生额外拷贝。这一条和[[7.4 协议|自定义协议]]那篇里「结构体不能直接 send」是同一个道理的两面。
- **`ethhdr` 恰好 14 字节。** 它在内核头文件里带 `__attribute__((packed))`，而且 6 + 6 + 2 全是 1 字节或 2 字节对齐的成员，本来也不会有填充。换成自己写的结构体就未必了。
- **`h_proto` 必须过 `ntohs`。** 线上是大端，x86 是小端，不转换的话 `0x0800` 会读成 `0x0008`，一个 case 都命中不了。
- **收到的帧没有 FCS。** 网卡校验完就剥掉了，所以 `n` 最大是 1514 而不是 1518。

例子为了聚焦解析，省掉了 `fd` 的 RAII 包装和 `close`。真实代码里应该把它交给一个持有 fd 的小类管理，别让错误分支漏掉释放。

## 常见误区

| 说法 | 实际 |
|:---|:---|
| MAC 地址端到端保持不变 | 每过一个路由器整个重写；端到端不变的是 IP |
| 帧长等于 IP 数据报长度 | 差 14 字节帧头，算上 FCS 差 18 |
| 交换机也要读 IP 才知道往哪转 | 二层交换机只看目的 MAC；读 IP 的是路由器和三层交换机 |
| 抓包能看到 FCS | 一般看不到，网卡校验后就剥了 |
| MTU 1500 包含帧头 | 只指 payload，帧头另算 |
| 抓到的帧都 ≥ 64 字节 | 发送方向可能抓到不足 64 的帧，填充由更靠近硬件的一层补，具体看驱动 |
| MAC 全球唯一所以能当机器指纹 | U/L 位为 1 的本地管理地址随便设，虚拟网卡和手机的 MAC 随机化都在用 |

## 自测问题

1. 访问公网地址时，Ethernet 帧的目的 MAC 为什么通常是默认网关？
2. 交换机收到一个目的 MAC 不在表里的单播帧，会怎么处理？
3. 一个 EtherType 字段读出来是 `0x0300`，这一帧该怎么解释？
4. 二层成环为什么比三层成环危险得多？

> [!question]- 参考答案
> 1. 目的 MAC 必须是**本链路上**某个接口的地址。ARP 靠二层广播工作，广播出不了本地链路，主机没有办法解析到公网服务器的 MAC。IP 层判断目标不在本网段后选默认网关做下一跳，链路层就去解析网关的 MAC。
> 2. 从除入端口外的所有端口泛洪一遍。对端回包时交换机学到它的位置，之后的帧就只走那一个端口。
> 3. `0x0300` = 768，落在 1500 和 1536 之间的保留区，既不是合法长度也不是合法 EtherType，正常协议栈会丢弃。
> 4. IP 头有 TTL，绕圈的包最多转几十次就被丢掉；Ethernet 头里没有任何跳数字段，环路上的广播帧会被无限复制，几秒内打满整个广播域，只能靠 STP 事先把冗余链路阻塞掉。

## 关键要点

1. **Ethernet 只负责一跳**，划边界、定收件人、查错三件事，其中查错只丢不重传，可靠性归 TCP。
2. **帧头固定 14 字节**（6 + 6 + 2），帧长 64 ～ 1518，前导码 8 字节在这之外，FCS 通常抓不到。
3. **MTU 1500 说的是 payload 上限**，不含帧头；插 VLAN 标签后帧长上限变 1522，最小仍是 64。
4. **首字节最低两位定性质**：bit 0 分单播/组播，bit 1 分全球唯一/本地管理。
5. **EtherType 完成分用**，`0x0800`/`0x0806`/`0x86DD` 分别对应 IPv4/ARP/IPv6；≤ 1500 的值是老 802.3 的长度字段。
6. **IP 端到端不变，MAC 逐跳重写**，因此发往公网的帧目的 MAC 是网关。
7. **交换机学源 MAC、转目的 MAC**，未命中就泛洪；二层没有 TTL，成环必须靠 STP 兜底。
8. **看链路层的三条命令**：`ip -s link` 看接口和统计，`tcpdump -e` 看帧头，`bridge fdb show` 看软件交换机的 MAC 表。
