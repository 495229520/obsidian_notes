# ICMP 与 ICMPv6

## IP 不管的事，得有人说一声

[[7.8.2 IPv4|IP]] 提供的是尽力而为的服务：包丢了就丢了，没人通知源端。这在中途出错时很尴尬：发送方一直在等，却不知道对方压根不存在、路由绕成了环、还是包太大过不去。

ICMP 补的就是这个反馈通道。要点是**它只报告，不修复**：收到「目的不可达」之后怎么办，是发送方自己的事。

它的报告分成两类，性质完全不同：

| | 差错报文 | 查询报文 |
|:---|:---|:---|
| 谁发的 | 路径上的路由器，或目标主机的协议栈 | 主动发起的诊断工具 |
| 触发条件 | 处理某个数据报时出了问题 | 人为发起 |
| 例子 | 目的不可达、TTL 耗尽、需要分片 | Echo Request / Reply（`ping`） |
| 携带什么 | 出错那个报文的一部分 | 自定义的数据 |

> [!note] ICMP 不是传输层协议
> 它封在 IP 数据报里（IPv4 的 `Protocol = 1`），但没有端口号，也不为应用传数据。它属于 IP 层自己的控制平面，IP 用它来给 IP 报告状况。
>
> ICMPv6 更极端：它已经不只是诊断工具，[[7.8.4 ARP|邻居发现]]、路由器发现、地址自动配置全建在它上面。没有 ICMPv6，IPv6 根本跑不起来。

## 差错报文里回带了什么

![[图片/SVG/3_7_7_8_5_1.svg|900]]

ICMP 的通用头只有 4 字节：`Type`（大类）、`Code`（细分）、`Checksum`。后面还有 4 字节，含义随类型而定。比如「需要分片」这个差错，就把下一跳的 MTU 放在这里。

差错报文之后跟着**出错那个数据报的 IP 首部，加上它的前 8 字节数据**。

### 为什么偏偏是 8 字节

这是整个 ICMP 里最值得记的设计。

传输层的前 8 字节里，头 4 个字节一定是**源端口 + 目的端口**（[[7.5 TCP协议基础|TCP]] 和 UDP 都一样）。加上原始 IP 首部里的源 IP 和目的 IP，四元组就凑齐了。

于是发送方内核收到这个差错时，能精确定位到是**哪一条连接、哪一个 socket** 出的问题，把错误交给正在那儿等的 `send()` 或 `connect()`，而不是笼统地报个「网络有问题」。

对 UDP 来说 8 字节正好是整个 UDP 首部；对 TCP 是两个端口加上序号，序号还能进一步定位是哪个报文段。

> [!tip] 应用怎么拿到这些差错
> 默认情况下 UDP socket 收不到 ICMP 差错，因为内核不知道该给谁。**只有 `connect()` 过的 UDP socket** 才有确定的对端，`recvfrom` 才会返回 `ECONNREFUSED` 这类错误。
>
> 要拿到更详细的信息（比如是哪一跳回的、报文里带的 MTU 是多少），打开 `IP_RECVERR` 选项，然后用 `recvmsg(..., MSG_ERRQUEUE)` 从错误队列里读。

RFC 1812 后来建议尽量多回带一些原始数据，只要整个 ICMP 报文不超过 576 字节。但 8 字节是底线，也是所有实现都保证的部分。

## `ping`：Echo Request 和 Echo Reply

`ping` 用的是查询报文：发 Type 8，等 Type 0。那 4 个「随类型而定」的字节，在这里被拆成两个 16 位字段：

- **Identifier**：区分是哪个进程发的。
- **Sequence Number**：区分是第几个包，丢包率和乱序都靠它统计。

Identifier 不是多余的。raw socket 收不到「只属于我」的报文：内核会把本机所有 ICMP 回复都投给每一个打开的 raw ICMP socket。同时跑两个 `ping`，两边都会收到对方的回复，只能靠 Identifier 自己筛。

> [!tip] RTT 是怎么算出来的
> iputils 的 `ping` 把**发送时刻的时间戳直接写进 ICMP 的数据部分**。Echo Reply 要求原样返回收到的数据，所以时间戳会跟着回来，减一下就是 RTT。
>
> 这个技巧让 `ping` 不需要维护任何「序号 → 发送时间」的表。把状态寄存在对端必然会回显的字段里，是协议设计里很常见的一招，[[7.5 TCP协议基础|TCP]] 的时间戳选项走的是同一条路。

### `ping` 不通说明不了什么

只能说明：没收到 Echo Reply。可能的原因有一长串：

- 目标或路径上的防火墙把 ICMP 丢了（公有云默认安全组常常就是这样）；
- 目标主机开了 `icmp_echo_ignore_all`，故意不回；
- 回程路径不通，请求其实到了；
- 触发了速率限制，恰好这几个被丢了。

反过来，`ping` 通也不说明服务可用：协议栈回 Echo Reply 不需要应用进程参与，业务进程早挂了照样通。真要判断服务，得连端口。

排查时把 `ping` 和 [[7.8.4 ARP#命令|`arping`]] 配着用：`arping` 走二层不经过 IP，它通而 `ping` 不通，说明机器活着、链路正常，问题在 IP 层或防火墙。

## `traceroute` 与路径 MTU 发现

![[图片/SVG/3_7_7_8_5_2.svg|900]]

### TTL 阶梯

`traceroute` 的原理是「故意让包死在半路」：TTL 设成 1，第一跳路由器减到 0 就丢弃并回一个 Time Exceeded，源 IP 暴露了第一跳是谁；TTL 设成 2 逼出第二跳，如此递增。

终点的信号取决于用哪种探测包：

| 方式 | 探测包 | 终点回什么 |
|:---|:---|:---|
| UDP（Linux 默认） | 发往 33434 起的高端口 | 端口不可达，Type 3 Code 3 |
| ICMP（`-I`） | Echo Request | Echo Reply |
| TCP（`-T`） | SYN，通常打 80 或 443 | SYN-ACK 或 RST |

选 UDP 高端口是因为那个端口几乎肯定没人监听，能稳定拿到「端口不可达」。但现在很多防火墙丢 UDP，所以打不通时改用 `-T -p 443`，伪装成正常 HTTPS 流量，穿透率高得多。

### 读 `traceroute` 输出的三个坑

- **星号不代表不通。** 只说明这一跳没回 ICMP：可能配置了不回，可能被中间防火墙拦了，也可能撞上速率限制。后面几跳照常有回应就说明路是通的。
- **它只测正向路径。** 每一跳的回包各走各的路回来，回程可能完全是另一条链路。所以正反两个方向都跑一次 `traceroute`，看到的路径经常对不上，这是正常的。
- **同一跳出现多个不同 IP，多半是 ECMP。** 骨干网上常有多条等价路径，每个探测包被哈希到不同链路。想看到稳定路径可以用 `paris-traceroute`，它固定住参与哈希的那些字段。

### 路径 MTU 发现全靠 ICMP

一条路径上各段链路的 MTU 未必相同。发送方想避开分片，就得知道整条路上最小的那个值。

IPv4 的做法：所有包都置上 DF 位。某一跳发现包太大又不许分片，就丢掉并回一个 **Type 3 Code 4**，把自己出口的 MTU 写在报文里（RFC 1191 用的正是那 4 个「随类型而定」的字节）。发送方收到后按新值缩小，重发。

IPv6 更彻底：**路由器根本不做分片**，只能回 **Type 2（Packet Too Big）**。所以 PMTUD 在 IPv6 里不是优化，是必需品。

这里只讲 ICMP 这一侧承担了什么，源主机拿到 MTU 之后怎么记进路由缓存、分片本身怎么运作，见 [[7.8.2 IPv4#5. 路径 MTU 发现与黑洞|IPv4 的分片与 PMTU]]。

> [!danger] PMTU 黑洞
> 中间某台设备把 ICMP 一律丢弃，上面那个反馈就回不来了。发送方收不到任何提示，只会一遍遍按原大小重传，直到超时。
>
> 典型症状是：TCP 握手成功，`ping` 也通（都是小包），一开始传大数据就卡死。这是最难查的一类网络故障，因为所有「连通性检查」都显示正常。

Linux 有两条绕开的路子：

- **`tcp_mtu_probing`**：设成 1 或 2 后，内核不等 ICMP，直接靠二分探测收敛出可用大小（RFC 4821 的 PLPMTUD）。
- **MSS clamping**：在网关上把 TCP 握手时协商的 MSS 直接改小，`iptables ... TCPMSS --clamp-mss-to-pmtu`。PPPoE 拨号场景几乎是标配。

看一条路径当前缓存的 MTU：

```bash
ip route get 1.1.1.1
# 1.1.1.1 via 10.0.0.1 dev eth0 src 10.0.0.10 uid 1000
#     cache expires 596sec mtu 1400        ← 这里就是 PMTUD 学到的值
```

## ICMPv6 不是可选项

ICMPv6 把类型空间劈成两半，看最高位就知道性质：

- **1 ～ 127：差错报文**
- **128 ～ 255：信息报文**

| Type | 名字 | 干什么 |
|:---:|:---|:---|
| 1 | Destination Unreachable | 目的不可达 |
| 2 | **Packet Too Big** | PMTUD 唯一的信息来源，路由器不分片 |
| 3 | Time Exceeded | Hop Limit 耗尽，`traceroute` 靠它 |
| 4 | Parameter Problem | 首部字段有问题 |
| 128 / 129 | Echo Request / Reply | `ping6` |
| 133 / 134 | Router Solicitation / Advertisement | 路由器发现、地址自动配置（SLAAC） |
| 135 / 136 | Neighbor Solicitation / Advertisement | 取代 [[7.8.4 ARP|ARP]]，还负责重复地址检测 |
| 137 | Redirect | 告知更优的下一跳 |
| 130 ～ 132 | MLD | 组播成员管理 |

133 ～ 137 这几个类型的具体流程（NS 的组播目的地址怎么算、DAD 怎么做、RA 里带了什么）在 [[7.8.3 IPv6#6. NDP：ARP 的活它全包了|IPv6 的 NDP]] 那节，这里只关心它们为什么必须走 ICMPv6。

对比 ICMPv4，有三处实现上必须注意的差别：

1. **校验和覆盖伪首部。** ICMPv4 的校验和只算 ICMP 报文本身，ICMPv6 要把 IPv6 的源地址、目的地址、长度、下一个首部拼成伪首部一起算。自己构造 ICMPv6 报文时忘了这一步，对端会静默丢弃。
2. **报文长度不能超过 IPv6 最小 MTU 1280。** 差错报文回带原始数据时要按这个上限截断。
3. **NDP 报文的 Hop Limit 必须是 255。** 接收方检查这个值，不是 255 就丢。跳数一减就不可能还是 255，所以这条规则等于保证了报文来自本地链路，没被路由器转发过。这是个花钱很少的防护设计。

> [!danger] 屏蔽 ICMPv6 等于关掉 IPv6
> IPv4 时代「防火墙一刀切丢 ICMP」还能凑合运行，IPv6 下直接崩：
>
> - 丢 135/136 → 邻居解析失败，同网段都不通；
> - 丢 133/134 → 主机拿不到地址，SLAAC 挂掉；
> - 丢 Type 2 → PMTU 黑洞，大包全卡；
> - 丢 Type 1/3/4 → 所有差错反馈消失，故障全变成超时。
>
> RFC 4890 专门给了该放行哪些类型的建议，配 IPv6 防火墙前值得对着过一遍。

## 什么时候不该生成 ICMP 差错

如果每个出错的包都触发一个差错报文，网络很容易被自己压垮，也容易被人当放大器用。所以 RFC 1122 明确规定了几种「不许回」的情况：

| 不生成差错的情形 | 原因 |
|:---|:---|
| 触发它的本身就是 ICMP 差错报文 | 否则两台机器能互相回到天荒地老 |
| 目的地址是广播或组播 | 一个包会引来成百上千个回复 |
| 链路层就是广播 / 组播帧收到的 | 同上 |
| 分片报文中非第一片 | 只有首片带传输层头，其余片回了也没用 |
| 源地址不是单个主机（0.0.0.0、回环、广播、组播） | 回复无处可送，或会被放大 |

Smurf 攻击就是踩着第二条：伪造源地址后往广播地址发 Echo Request，整个网段一起回复给受害者。现在 Linux 默认 `icmp_echo_ignore_broadcasts = 1`，这条路封死了。

除了规则限制，还有速率限制：`net.ipv4.icmp_ratelimit` 控制差错报文的发送频率。这也是 `traceroute` 星号的来源之一：路由器不是不回，是被限流了。

## 在 Linux 上观察

```bash
ping -c 4 -n 1.1.1.1
ping6 -c 4 -n 2606:4700:4700::1111

# 探 MTU：-M do 强制置 DF，-s 是 ICMP 数据部分的字节数
# 1472 + 8（ICMP 头）+ 20（IP 头）= 1500，正好卡在标准 MTU 上
ping -M do -s 1472 -c 1 1.1.1.1
ping -M do -s 1473 -c 1 1.1.1.1     # 这个应该报 "message too long"

traceroute -n 1.1.1.1               # UDP 探测，默认
traceroute -I -n 1.1.1.1            # 改用 ICMP Echo
traceroute -T -p 443 -n example.com # 改用 TCP SYN，穿透防火墙最好使
tracepath 1.1.1.1                   # 自带 PMTU 探测，而且不需要 root
mtr -n 1.1.1.1                      # 持续采样，看丢包发生在哪一跳

sudo tcpdump -i eth0 -n icmp
sudo tcpdump -i eth0 -n icmp6

# 构造一个端口不可达，观察 Type 3 Code 3
nc -u 127.0.0.1 9999
```

`tracepath` 比 `traceroute` 更适合排 PMTU 问题：它一边测路径一边报告每一跳的 MTU 变化，最后直接给出 `pmtu` 值，而且不需要特权。

### 自己发一个 Echo Request

先写校验和。ICMP 用的是 RFC 1071 的反码求和，和 IP、TCP、UDP 是同一套算法：

```cpp
#include <netinet/ip.h>       // struct iphdr
#include <netinet/ip_icmp.h>  // struct icmphdr、ICMP_ECHO、ICMP_ECHOREPLY
#include <sys/socket.h>
#include <arpa/inet.h>
#include <array>
#include <cstddef>
#include <cstdint>
#include <cstdio>
#include <cstring>

// 按 16 位相加，进位绕回低位，最后取反
std::uint16_t checksum(const std::uint8_t* p, std::size_t len) {
    std::uint32_t sum = 0;
    for (std::size_t i = 0; i + 1 < len; i += 2)
        sum += static_cast<std::uint32_t>(p[i]) << 8 | p[i + 1];
    if (len & 1) sum += static_cast<std::uint32_t>(p[len - 1]) << 8;   // 奇数长度补一个 0 字节
    while (sum >> 16) sum = (sum & 0xFFFF) + (sum >> 16);              // 折叠进位
    return htons(static_cast<std::uint16_t>(~sum));
}
```

「进位绕回」是这套校验和的特点：16 位加法溢出的部分不丢弃，而是加回低位。这样算出来的结果与字节序无关，也让路由器可以增量更新校验和而不必整段重算。

然后构造并发送：

```cpp
const int fd = ::socket(AF_INET, SOCK_RAW, IPPROTO_ICMP);   // 需要 CAP_NET_RAW

icmphdr req{};
req.type = ICMP_ECHO;                 // Type 8
req.code = 0;
req.un.echo.id       = htons(1234);   // 标识本进程，收包时靠它过滤
req.un.echo.sequence = htons(1);
req.checksum = 0;                     // 必须先清零
req.checksum = checksum(reinterpret_cast<const std::uint8_t*>(&req), sizeof(req));

sockaddr_in dst{};
dst.sin_family = AF_INET;
::inet_pton(AF_INET, "1.1.1.1", &dst.sin_addr);
::sendto(fd, &req, sizeof(req), 0,
         reinterpret_cast<sockaddr*>(&dst), sizeof(dst));
```

`checksum` 字段本身也参与计算，所以**必须先清零再算**，顺序反了对端会认为报文损坏并静默丢弃。这类 bug 没有任何报错，只能靠抓包发现。

收包这一步有个容易踩的坑：

```cpp
std::array<std::uint8_t, 1500> buf{};
const ssize_t n = ::recv(fd, buf.data(), buf.size(), 0);

// raw IPv4 套接字收到的一定带 IP 首部，长度是 ihl × 4，不是固定的 20
iphdr ip{};
std::memcpy(&ip, buf.data(), sizeof(ip));
const std::size_t ip_len = static_cast<std::size_t>(ip.ihl) * 4;
if (n < 0 || static_cast<std::size_t>(n) < ip_len + sizeof(icmphdr)) return 1;

icmphdr rep{};
std::memcpy(&rep, buf.data() + ip_len, sizeof(rep));
if (rep.type == ICMP_ECHOREPLY && ntohs(rep.un.echo.id) == 1234)
    std::printf("seq=%u 回来了\n", ntohs(rep.un.echo.sequence));
```

三点说明：

- **IP 首部长度必须从 `ihl` 算。** 带选项时它超过 20 字节，写死 20 会把 ICMP 头解错位。这和 [[7.8.1 Ethernet以太网|Ethernet]] 那篇里「别用 `reinterpret_cast` 直接套结构体」是同一类问题：线上的长度是变的，代码不能假设。
- **必须按 `id` 过滤。** raw ICMP socket 会收到本机全部 ICMP 报文，包括别的进程 `ping` 的回复。这就是 Identifier 字段存在的理由。
- **不用 root 还有一条路。** Linux 提供 ping socket：`socket(AF_INET, SOCK_DGRAM, IPPROTO_ICMP)`，不需要 `CAP_NET_RAW`，内核会自己改写 Identifier 和校验和。能不能用取决于 `/proc/sys/net/ipv4/ping_group_range` 是否覆盖当前 gid，现在多数发行版已经放开，所以 `ping` 命令不再需要 setuid。

## 常见误区

| 说法 | 实际 |
|:---|:---|
| ICMP 是传输层协议 | 它封在 IP 里但没有端口，属于 IP 层自己的控制平面 |
| ICMP 能让 IP 变可靠 | 它只报告，不重传也不修复，怎么处理是发送方的事 |
| `ping` 不通说明主机离线 | 也可能是防火墙丢包、故意不回、回程不通或触发限速 |
| `ping` 通说明服务正常 | 协议栈回 Echo Reply 不需要应用参与，进程挂了照样通 |
| `traceroute` 的星号表示断了 | 只表示这一跳不回 ICMP，后面有回应就是通的 |
| `traceroute` 看到的是往返路径 | 只测正向，回程可能完全是另一条路 |
| 差错报文会带回整个原始数据报 | 只保证 IP 首部 + 前 8 字节，够凑出四元组就行 |
| UDP socket 一定能收到端口不可达 | 只有 `connect()` 过的才有确定对端，才收得到 |
| 屏蔽 ICMP 更安全 | IPv4 下会打断 PMTUD，IPv6 下直接让协议不可用 |
| ICMPv6 只是 ICMP 换了个版本号 | 邻居发现、地址自动配置都建在它上面，是必需组件 |

## 自测问题

1. `ping` 不通，为什么不能直接断言对方主机离线？
2. `traceroute` 靠什么让路径上的每一跳主动暴露自己？
3. ICMP 差错报文为什么必须回带原始数据报的前 8 字节，而不是 4 字节或 2 字节？
4. 为什么 ICMPv6 不能像 ICMPv4 那样被防火墙一刀切丢掉？

> [!question]- 参考答案
> 1. 收不到 Echo Reply 有很多种解释：路径或目标的防火墙丢了 ICMP、目标配置了不回 Echo、请求到了但回程路径不通、触发了速率限制。要判断主机是否活着，同网段可以用 `arping` 走二层，跨网段就连一个确定开放的 TCP 端口。
> 2. 把 TTL 从 1 开始逐次递增。TTL 归零的那一跳必须丢弃报文并回一个 Time Exceeded，回包的源 IP 就暴露了这一跳的身份。递增到目标主机时，改由目标回端口不可达或 Echo Reply，探测结束。
> 3. 因为传输层首部的前 4 字节一定是源端口和目的端口，再加上回带的原始 IP 首部里的两个 IP 地址，四元组就齐了。内核据此定位到具体的 socket，把错误交给正在等的那次调用。8 字节还能多带上 TCP 的序号，进一步定位是哪个报文段。
> 4. 因为 IPv6 把核心机制建在 ICMPv6 上：邻居发现（135/136）相当于 IPv4 的 ARP，路由器通告（133/134）负责地址自动配置，Packet Too Big（Type 2）是 PMTUD 的唯一信息来源，而 IPv6 路由器不做分片，没有它大包必然黑洞。全丢等于关掉 IPv6。

## 关键要点

1. **ICMP 只报告不修复**，分差错报文和查询报文两类，前者由路由器或目标协议栈被动产生。
2. **差错报文回带原 IP 首部 + 前 8 字节**，那 8 字节里有源端口和目的端口，内核靠它把错误投递到具体的 socket。
3. **`ping` 用 Type 8 / 0**；Identifier 区分进程、Sequence 区分包，发送时刻直接写在数据部分里，回来一减就是 RTT。
4. **`ping` 不通和服务不可用是两件事**，两个方向都不能互推。
5. **`traceroute` 靠递增 TTL 逼出每一跳**；星号只说明这一跳不回 ICMP，而且它测的只是正向路径。
6. **PMTUD 完全依赖 ICMP**：IPv4 是 Type 3 Code 4，IPv6 是 Type 2；ICMP 被丢就形成黑洞，症状是握手通、大包卡死。
7. **ICMPv6 是 IPv6 的必需组件**，1～127 是差错、128～255 是信息；NDP 报文的 Hop Limit 必须为 255，以此保证来自本地链路。
8. **差错报文有生成规则和速率限制**：不为 ICMP 差错、广播组播、非首片再生成差错，避免风暴和放大攻击。
