# 8.8 流控制

## 1. 简介

流控制（Flow Control）要解决的是一件很具体的事：**发送方发得比接收方处理得快，多出来的数据没地方放，只能丢掉**。

打个比方，两个人互相扔球，接球的那个手慢。扔球的人要是不管不顾地一直扔，球就会掉一地。流控制就是让扔球的人盯着对方的手速来。

TCP 内置了这套机制，UDP 没有。

## 2. TCP 流控制

TCP 的流控制是通过**滑动窗口协议（Sliding Window Protocol）**实现的。

### 2.1 工作原理

接收方在每个 ACK 里带一个**窗口大小（Window Size）**字段，也就是常说的 `rwnd`，告诉发送方它此刻还剩多少 [[8.7 IO缓冲#2.2 接收缓冲区（Receive Buffer）|接收缓冲区]]空间。发送方拿到这个数，就知道自己最多还能往外扔多少字节。

“滑动窗口”里的窗口，是发送方在自己的发送队列上划出来的一段：

![[图片/SVG/3_8_8_8_1.svg|900]]

窗口把发送队列切成四段，其中只有 ②③ 在窗口里：

| 区 | 含义 | 什么让它移动 |
|:---|:---|:---|
| ① 已发送、已确认 | 数据安全落地，发送缓冲区可以回收 | ACK 到达，左边界右移 |
| ② 已发送、未确认 | 还在网络里飞，随时可能要重传 | 每发一段就往右扩一点 |
| ③ 可以立即发送 | 窗口剩下的额度，写了就能发 | ② 增长时被挤小 |
| ④ 还不能发 | 应用层已经写进来，但没拿到许可 | 等右边界右移 |

窗口“滑动”就是这两条边界各自往右走：**左边界被 ACK 推动，右边界 = 左边界 + 接收方通告的窗口**。ACK 推着左边界前进 2、通告窗口没变，整个窗口就整体右滑 2；要是通告窗口同时从 5 缩到 3，右边界原地不动，窗口就被压窄——这就是接收方踩刹车的方式。

> [!warning] 接收方不能把右边界往回撤
> 收窄窗口只能靠“右边界少往前推”。把已经通告出去的右边界往回收（RFC 1122 称为 shrinking the window）是明确不推荐的：对端可能已经合法地把那段数据发出去了，回撤会让这些数据凭空变成越界数据。

### 2.2 一次完整的窗口变化

把接收缓冲区设成 9000 字节，跟着一次收发看 `rwnd` 怎么一路降到 0，又怎么恢复：

![[图片/SVG/3_8_8_8_2.svg|900]]

三个容易记错的点：

- **`rwnd` 报的是剩余空间，不是缓冲区大小。** 它随接收方读取的快慢上下浮动，读得快就回升，读得慢就往下掉
- **`rwnd = 0` 不代表连接出问题**，只是“暂时别发”。发送方停下来，连接本身完全正常
- **让 `rwnd` 回升的是应用层的 `read()`，不是内核。** 数据到了接收缓冲区只是换了个地方待着，没人取走窗口就一直是 0——所以业务线程一卡住，压力会直接反压到对端的发送速度上

### 2.3 零窗口探测

`rwnd = 0` 之后，发送方要等接收方发来“窗口更新”才能继续。麻烦在于这个窗口更新是一个**纯 ACK**：不带数据、不占序号，因此不在 TCP 的重传范围内。它在路上丢了就是丢了，没有任何机制会补发。

于是可能出现这样的死锁：接收方以为“我已经通知过了”，发送方还在等通知，两边一起挂住——连接看着好好的，但一个字节也不动。

TCP 把打破死锁的责任放在**发送方**身上：收到零窗口后，发送方启动一个**持续计时器（persist timer）**，到期就发一个 1 字节的**零窗口探测报文**，逼接收方回一个 ACK，顺带把当前窗口带回来。如果对方还是 0，探测间隔按指数退避逐步拉长到分钟级，一直探到窗口打开为止。

要注意这不是应用层的循环，整个过程都在内核里，应用层只会看到 `send()` 阻塞或者返回 `EAGAIN`。对端要是一直不读，这个探测能持续非常久——想给它设上限，用 `TCP_USER_TIMEOUT`。

### 2.4 窗口字段只有 16 位：窗口缩放选项

TCP 首部里的窗口字段是 16 位，最大只能表示 **65535 字节**。这个数字在 1981 年够用，今天远远不够。

一条 1 Gbps、RTT 50 ms 的链路，要跑满带宽，在途数据量得有：

```text
带宽时延积 = 1 Gbps × 50 ms ÷ 8 = 6.25 MB
```

而 64 KiB 的窗口上限只允许 64 KiB 在途，算下来吞吐最多 `65535 ÷ 0.05 ≈ 1.3 MB/s`，也就是 10 Mbps 出头。带宽再大也没用，卡在窗口上了。

RFC 7323 的**窗口缩放选项（Window Scale）**解决这个问题：握手时双方各自通告一个移位因子 `wscale`，之后所有窗口值都按 `实际窗口 = 通告值 << wscale` 来解释，最大能到 1 GiB。

三个要点：

- `wscale` **只能在 SYN 和 SYN-ACK 里协商**。握手时没谈成，整条连接就再也用不上了
- 两个方向各有独立的 `wscale`，取值可以不同
- Linux 默认开启（`net.ipv4.tcp_window_scaling = 1`）。但中间的老防火墙或 NAT 设备要是把这个选项抹掉，就会表现成“链路带宽明明很大，速度死活上不去”，是跨机房传输的经典疑难杂症

### 2.5 糊涂窗口综合症

接收方每腾出几十字节就急着通告一次“我有空位了”，发送方就会规规矩矩地发一个几十字节的小报文——40 字节的 TCP/IP 头驮着 20 字节数据，链路利用率惨不忍睹。这个现象叫**糊涂窗口综合症（Silly Window Syndrome）**。

收发两端各出一半力气来避免它：

| 谁 | 做法 |
|:---|:---|
| 接收方 | 空出来的空间不到一个 MSS、也不到缓冲区一半时，继续通告 0，攒够了再一次性通告（Clark 方案） |
| 发送方 | 手上数据不足一个 MSS、且还有数据没被确认时，先攒着不发——这就是 [[10.3 Nagle算法\|Nagle 算法]] |

所以 Nagle 算法和流控制是同一个问题的两个方向：流控制管“能不能发”，Nagle 管“值不值得现在发”。

## 3. UDP 流控制

**UDP 本身不实现流控制。**

UDP 的设计哲学是牺牲可靠性换速度。它只管把数据报发出去，不关心接收方处理不处理得过来。数据报到达目的地时，完全可能因为接收缓冲区溢出而被直接丢弃。

### 3.1 应用层实现流控制

UDP 上确实需要流控制的话，只能自己在应用层重造一遍：

1. 发送的数据包里加序列号
2. 接收方收到后回一个应用层的确认包
3. 发送方在超时时间内没等到确认，就认为丢了，重传
4. 确认包里顺带带上“我还能处理多少”，这就是应用层版本的窗口通告

这套逻辑要一行行自己写，UDP 协议本身一点忙都帮不上。

### 3.2 常见的应用层协议

一些基于 UDP 的应用层协议实现了自己的流控制和可靠性机制：

| 协议 | 说明 |
|:---|:---|
| **QUIC** | Google 开发，HTTP/3 的底层协议，实现了可靠传输和流控制 |
| **RTP/RTCP** | 用于实时音视频传输，RTCP 提供反馈机制 |
| **TFTP** | 简单文件传输协议，使用停等协议实现可靠传输 |

## 4. TCP 与 UDP 流控制对比

| 特性 | TCP | UDP |
|:---|:---|:---|
| **流控制** | 内置（滑动窗口） | 无 |
| **实现层** | 传输层 | 需应用层自行实现 |
| **窗口通告** | 通过 ACK 报文中的 Window 字段 | 不适用 |
| **零窗口处理** | 自动探测 | 不适用 |
| **适用场景** | 需要可靠传输的场景 | 实时性要求高的场景 |

## 5. 拥塞控制 vs 流控制

流控制容易与**拥塞控制（Congestion Control）**混淆，但它们解决的是不同的问题：

| 机制 | 目的 | 关注点 |
|:---|:---|:---|
| **流控制** | 防止发送方淹没接收方 | 端到端（接收方的处理能力） |
| **拥塞控制** | 防止发送方淹没网络 | 网络路径（路由器、交换机的处理能力） |

TCP 同时实现了这两种机制：

- **流控制**：通过滑动窗口（接收方通告的窗口大小）
- **拥塞控制**：通过拥塞窗口（`cwnd`）和算法（慢启动、拥塞避免、快重传、快恢复），详见 [[8.10 拥塞控制]]

实际发送窗口 = `min(rwnd, cwnd)`。

## 6. 在线上怎么看 rwnd

`ss -ti` 能直接看到一条连接当前的窗口状态：

```bash
$ ss -ti state established '( dport = :8080 )'
     cubic wscale:7,7 rto:204 rtt:3.5/1.75 mss:1448 rcv_space:14480 ...
```

- `wscale:7,7` — 两个方向各自协商到的窗口缩放因子。看到 `wscale:0,0` 说明没协商上，高带宽链路要重点怀疑中间设备
- `rcv_space` — 内核给接收窗口自动调优用的估计值，长期贴着很小的数，说明本端应用层读得太慢
- 反过来，对端窗口一直是 0 时，本端 `send()` 会长时间阻塞，`ss -t` 里能看到 `Send-Q` 持续不降

更多排障手法见 [[8.14 高性能发送与线上排障]]，缓冲区大小怎么调见 [[8.13 TCP内核队列与参数调优]]。

## 7. 关键要点

1. **流控制的目的**：防止发送方发得太快，接收方来不及处理
2. **靠滑动窗口实现**：左边界被 ACK 推动，右边界 = 左边界 + 接收方通告的 `rwnd`
3. **收窄窗口只能靠少往前推右边界**，不能把已经通告的右边界往回撤
4. **`rwnd = 0` 是暂停不是断开**，让它回升的是接收方应用层的 `read()`
5. **零窗口探测**：窗口更新是纯 ACK，丢了没人重传，所以由发送方定时探测来打破死锁
6. **窗口字段只有 16 位**，高带宽时延积链路必须靠握手时协商的窗口缩放选项
7. **糊涂窗口综合症**：收发两端各有一套攒数据的策略，发送端那套就是 Nagle
8. **UDP 无流控制**：需要就自己在应用层做
9. **流控制 ≠ 拥塞控制**：一个盯接收方，一个盯网络路径
