## 1. 简介

网络编程八股不只问协议，也会追问“怎么把数据高效发出去”和“线上连接异常怎么查”。这篇笔记补充零拷贝、批量 IO、MTU/MSS，以及常见排障命令。

---

## 2. 零拷贝解决什么

把一个文件发到 socket，能走的路不止一条，区别在于数据被 CPU 搬了几次、进出内核几次：

![[图片/SVG/3_8_8_14_1.svg|900]]

有个容易被口号带偏的地方：**“零拷贝”省的是 CPU 拷贝，不是全部拷贝**。磁盘到页缓存、页缓存到网卡这两次 DMA 谁也省不掉——数据总得从盘上出来、总得进网卡。真正被消掉的是中间那些 `memcpy`，以及来回进出内核态的上下文切换。

---

## 3. sendfile

`sendfile()` 适合把文件内容直接发到 socket，典型场景是静态文件服务器。

```cpp
#include <sys/sendfile.h>

off_t offset = 0;
ssize_t n = sendfile(sockfd, filefd, &offset, file_size);
```

它的关键特性是**数据全程不进用户态**，所以一次调用就够，上下文切换从 4 次降到 2 次。

但“sendfile 就是零拷贝”这句话得加个前提。看上图的 ③ 和 ④：

- 网卡**不支持** scatter-gather DMA 时，页缓存里的数据还得被 CPU 拷进 socket 缓冲区一次，只是拷贝次数从 2 降到 1
- 网卡**支持** SG-DMA 时，socket 缓冲区里只放描述符（内存地址 + 长度），网卡按描述符直接从页缓存取数据。这时候 CPU 拷贝才真的是 0 次

两种情况是同一个系统调用，差别只在硬件。现代服务器网卡基本都支持，但写文档或答题时最好把这个前提说出来。

几个使用限制：

- `in_fd` 必须是支持 `mmap` 的文件（普通文件可以，socket 和管道不行）
- Linux 2.6.33 之前，`out_fd` 必须是 socket；之后放宽了
- 一次调用未必发完，返回值要检查，剩下的要接着发

## 4. mmap

`mmap()` 把文件映射到进程地址空间，应用像访问内存一样访问文件。

```cpp
void* p = mmap(nullptr, len, PROT_READ, MAP_PRIVATE, filefd, 0);
```

它省掉了 `read()` 把文件复制到用户缓冲区那一次。但随后的 `send()` 仍然要把数据从映射区拷进 socket 缓冲区，所以只省了一次，不是零。

> [!warning] mmap 的几个坑
> - **文件被截断会 `SIGBUS`。** 映射建立之后别的进程 `truncate` 了这个文件，访问越界那部分会直接收到 `SIGBUS` 而不是普通的读错误
> - **缺页中断不是免费的。** 首次访问每一页都要触发一次缺页，小文件下这个开销可能超过省下的那次 `memcpy`
> - **只适合“要在用户态看数据”的场景。** 纯粹的转发不看内容，直接上 `sendfile` 更划算

## 5. splice

`splice()` 在两个内核对象之间移动数据，靠传递页引用而不是拷贝内容。

```cpp
splice(filefd, nullptr, pipefd[1], nullptr, len, SPLICE_F_MOVE);
splice(pipefd[0], nullptr, sockfd, nullptr, len, SPLICE_F_MOVE);
```

注意这里为什么凭空冒出来一个 pipe：**`splice()` 要求两个 fd 里至少有一个是管道**。管道在这里当的是内核缓冲区的角色，数据并不真的流经它，走的只是页引用。所以要搬两次，上下文切换回到 4 次。

它是 Linux 专有的，适合代理、转发这类“数据完全不用看”的场景。socket 到 socket 的转发用它最合适——`sendfile` 的 `in_fd` 不能是 socket，这种场景只能靠 `splice`。

## 6. writev 和 readv

`writev()` / `readv()` 是分散/聚集 IO，可以把多个不连续的缓冲区一次写出，或者一次读入多个缓冲区。

```cpp
#include <sys/uio.h>

iovec iov[2];
iov[0].iov_base = header;
iov[0].iov_len = header_len;
iov[1].iov_base = body;
iov[1].iov_len = body_len;

writev(fd, iov, 2);
```

典型用途：

- 协议头和 body 分开存放，但希望一次发出去
- 减少系统调用次数
- 省掉“为了拼一个完整包而先 `memcpy` 到一块新内存”的开销

两个实际用起来必须知道的点：

- **`writev` 一样会部分写。** 返回值可能小于总长度，剩下的要自己算清楚从哪个 `iovec` 的哪个偏移接着发，这比单缓冲区的短写处理麻烦得多
- **`iovcnt` 有上限。** `IOV_MAX` 在 Linux 上通常是 1024，超了直接返回 `EINVAL`。攒批发送时要记得分批

`readv` 更常见的用法是配合栈上的临时缓冲区一次读空内核，这个技巧见 [[8.15 输入输出缓冲区与协议解析器]]。

## 7. TCP_CORK 与 TCP_NODELAY

| 选项 | 作用 | 典型场景 |
|:---|:---|:---|
| `TCP_NODELAY` | 禁用 [[10.3 Nagle算法\|Nagle]]，小包尽快发送 | 低延迟交互 |
| `TCP_CORK` | 先攒住小片数据，凑够一个 MSS 再发 | 发送 header + body |

`TCP_CORK` 是“我还没攒完，先别发”，`TCP_NODELAY` 是“别等，马上发”。目标相反，用之前得非常清楚自己的发送模式。

两点补充：

- **`TCP_CORK` 有 200 ms 的上限。** 内核不会无限期攒下去，到点没凑够也会发出去。所以它不会把数据永远扣住，但也意味着最坏情况会引入 200 ms 延迟
- **典型用法是包住一段发送再放开**：`setsockopt(CORK, 1)` → 写 header → `sendfile` 写 body → `setsockopt(CORK, 0)`。这样 header 和 body 会被合成尽量少的报文

## 8. MTU、MSS、PMTU

| 概念 | 含义 |
|:---|:---|
| MTU | 链路层一次能承载的最大 IP 包大小，以太网常见 1500 |
| MSS | TCP 单段最大数据量，通常约等于 MTU 减去 IP/TCP 头 |
| PMTU | 路径上的最小 MTU |

面试重点：

- TCP 是字节流，应用层不应该依赖一次 `send()` 对应一个包
- MSS 影响 TCP 分段大小
- UDP 大包更容易遇到 IP 分片风险，见 [[9.1 UDP原理#11.2 MTU、分片与 PMTU]]

## 9. 排障的三层

工具很多，但用的顺序比用哪个更重要。按代价从低到高排，一共三层：

![[图片/SVG/3_8_8_14_2.svg|900]]

顺序不能倒过来。先抓包再看状态，往往是抓了一堆包，回头发现 `ss` 第一行就能看出问题。

---

## 10. 第一层：ss 看状态

```bash
ss -s                          # 各状态的总览，最快的一眼
ss -tanp                       # 带进程名，定位是哪个服务
ss -tan state time-wait | wc -l
ss -tan state close-wait
```

常用观察点：

- `TIME_WAIT` 暴涨 → 本机在大量主动关闭，见 [[10.2 TIME_WAIT状态]]
- `CLOSE_WAIT` 堆积 → 本机应用收到 FIN 后没 `close()`，见 [[8.11 TCP连接关闭与异常状态]]
- `SYN_RECV` 异常多 → 握手完不成，或者被 SYN flood，见 [[8.13 TCP内核队列与参数调优]]

同一层还有 `lsof`，用来把连接落到具体的进程和 fd 上：

```bash
lsof -p <pid>            # 这个进程开了哪些 fd
lsof -i :8080            # 这个端口被谁占着
ls /proc/<pid>/fd | wc -l   # 只想数个数的话这个更快
```

`ss` 回答“有多少连接、都是什么状态”，`lsof` 回答“是哪个进程、哪个 fd”。排查 fd 泄漏时两个配合用。

---

## 11. 第二层：ss -ti 看队列和窗口

这一层是最容易被跳过、但性价比最高的一层。`ss -ti` 把内核里那些平时看不见的变量都打出来了：

```bash
$ ss -ti state established '( dport = :8080 )'
ESTAB 0  4096  10.0.0.5:52314  10.0.0.9:8080
     cubic wscale:7,7 rto:204 rtt:35.2/8.1 mss:1448 cwnd:10 ssthresh:7
     bytes_sent:120480 bytes_retrans:2896 retrans:0/12 ...
```

| 字段 | 怎么读 |
|:---|:---|
| `Send-Q`（第二列） | 本端已写入内核、但还没被对端确认的字节数。持续不降说明对端收不动或网络堵 |
| `Recv-Q`（第一列） | 已到达内核、但应用还没读走的字节数。持续不降说明本端应用读得太慢 |
| `wscale:7,7` | 两个方向的窗口缩放因子，`0,0` 要怀疑中间设备，见 [[8.8 流控制]] |
| `rtt:35.2/8.1` | 平滑 RTT / 抖动，单位毫秒 |
| `cwnd` / `ssthresh` | 拥塞窗口和门限。两个都是个位数说明一直在丢包，见 [[8.10 拥塞控制]] |
| `retrans:0/12` | 当前未确认的重传段数 / 累计重传段数 |

监听套接字要单独看，两个 Q 的含义完全不同：

```bash
$ ss -lnt
State   Recv-Q  Send-Q  Local Address:Port
LISTEN  0       4096    0.0.0.0:8080
```

这里 `Send-Q` 是全连接队列的**容量**，`Recv-Q` 是**当前积压**。`Recv-Q` 不为零就说明 `accept()` 跟不上了。

全局的累计计数用 `nstat`，它比 `netstat -s` 好在能显示增量：

```bash
nstat -az TcpExtListenOverflows TcpExtListenDrops   # 全连接队列溢出
nstat -az TcpRetransSegs TcpOutSegs                 # 重传率 = 前者 / 后者
```

重传率是判断“到底是不是网络问题”最直接的一个数。它在涨，就别再花时间查应用代码了。

## 12. 第三层：tcpdump 抓包定论

前两层只能给方向，抓包才是定论性的证据——包到底出没出去。

```bash
tcpdump -i eth0 tcp port 8080 -nn -c 200          # 限量 200 个包就停
tcpdump -i eth0 host 10.0.0.1 and port 8080 -w out.pcap
tcpdump -i eth0 'tcp[tcpflags] & (tcp-rst) != 0' -nn   # 只抓 RST
```

常见观察点：

- 三次握手到底完成了没有
- 谁先发的 FIN——这直接决定 `TIME_WAIT` 该记在哪一端
- RST 是从哪一端来的
- 有没有重传，重传的是不是同一个序号
- 有没有出现 `win 0` 的零窗口通告

> [!warning] 线上抓包要限量
> 不加 `-c` 也不加过滤条件，在一台高流量机器上抓包，很容易把磁盘写满或者把 CPU 吃掉一大块。习惯是：先用 `-c` 限个数，用尽量精确的过滤表达式，写文件而不是打屏幕，抓完立刻停。

Wireshark 更适合把 `.pcap` 拉回本地做协议字段分析，它的 “Expert Information” 会自动标出重传、乱序、零窗口这些异常。

## 13. /proc/net/tcp

`/proc/net/tcp` 能看到内核记录的 TCP 连接，但状态是十六进制编码。

| 编码 | 状态 |
|:---|:---|
| `01` | ESTABLISHED |
| `02` | SYN_SENT |
| `03` | SYN_RECV |
| `06` | TIME_WAIT |
| `08` | CLOSE_WAIT |
| `0A` | LISTEN |

通常优先用 `ss`，需要脚本化或深入排查时再看 `/proc/net/tcp`。

## 14. errno 排障

| errno | 常见含义 | 排查方向 |
|:---|:---|:---|
| `ECONNREFUSED` | 对端端口没人监听或拒绝 | 服务是否启动、防火墙 |
| `ETIMEDOUT` | 连接超时 | 网络路径、防火墙、SYN 丢失 |
| `ECONNRESET` | 对端 RST | 对端异常关闭、协议错误 |
| `EPIPE` | 对端关闭后继续写 | 关闭逻辑、SIGPIPE |
| `EMFILE` | 进程 fd 用尽 | `ulimit -n`、fd 泄漏 |
| `ENFILE` | 系统 fd 用尽 | 系统级 fd 上限 |
| `EADDRINUSE` | 地址已被占用 | TIME_WAIT、已有监听进程 |

## 15. 面试问法

| 问题 | 回答要点 |
|:---|:---|
| sendfile 为什么快 | 减少用户态和内核态之间的数据拷贝 |
| writev 解决什么 | 多缓冲区一次 IO，减少拼接和系统调用 |
| TCP_CORK 和 TCP_NODELAY 区别 | 一个攒包，一个尽快发 |
| CLOSE_WAIT 多怎么查 | `ss -tanp state close-wait` + 检查应用 close |
| 怎么判断谁先关闭连接 | 抓包看 FIN 方向 |
| Send-Q 一直增长说明什么 | 对端接收慢或网络慢，本端输出积压 |
| sendfile 一定是零拷贝吗 | 不一定，网卡不支持 SG-DMA 时仍有 1 次 CPU 拷贝 |
| splice 为什么要一个 pipe | 它要求两端至少有一个是管道，管道充当内核缓冲 |
| 怎么快速判断是不是网络丢包 | 看 `nstat` 的重传率，别一上来就查代码 |

---

## 16. 关键要点

1. **零拷贝省的是 CPU 拷贝，不是全部拷贝**。两次 DMA 谁也省不掉
2. **`sendfile` 的“零”有前提**：网卡支持 SG-DMA 才是 0 次 CPU 拷贝，否则还剩 1 次
3. **数据要在用户态改（加密、压缩、改协议头），零拷贝就无从谈起**
4. **`splice` 需要一端是 pipe**，socket 到 socket 的转发只能靠它，`sendfile` 干不了
5. **`writev` 一样会部分写**，而且 `IOV_MAX` 通常只有 1024
6. **`TCP_CORK` 偏吞吐但有 200 ms 上限，`TCP_NODELAY` 偏低延迟**
7. **排障按代价从低到高**：`ss` 看状态 → `ss -ti` / `nstat` 看队列窗口 → 最后才抓包
8. **重传率是区分“网络问题”和“应用问题”最快的一个数**
