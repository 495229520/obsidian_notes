# TCP 内核队列与参数调优

## 简介

`listen(fd, backlog)` 背后不是一个简单队列。Linux TCP 服务端至少要理解两类队列：

- 半连接队列：收到 SYN，回复 SYN+ACK，等待最后 ACK
- 全连接队列：三次握手完成，等待应用 `accept()`

这篇笔记补充 [[7.7 listen和accept函数#backlog 参数详解|backlog 参数详解]] 的内核和排障视角。

---

## 两个连接队列

```text
客户端 SYN
   |
半连接队列 SYN queue
   |
收到最后 ACK，三次握手完成
   |
全连接队列 accept queue
   |
应用调用 accept()
```

| 队列 | 状态 | 受什么影响 |
|:---|:---|:---|
| 半连接队列 | `SYN_RECV` | `tcp_max_syn_backlog`、SYN flood、syncookies |
| 全连接队列 | `ESTABLISHED` 但未 accept | `listen(backlog)`、`somaxconn`、应用 accept 速度 |

如果应用层 `accept()` 太慢，全连接队列会堆积；如果 SYN 太多或被攻击，半连接队列会吃紧。

---

## backlog 的真实含义

在现代 Linux 中，`listen(fd, backlog)` 主要影响全连接队列长度，但最终还会被系统参数限制：

```bash
cat /proc/sys/net/core/somaxconn
```

实际队列上限可理解为：

```text
accept 队列上限 = min(backlog, net.core.somaxconn)
```

所以只在代码里写 `listen(fd, 65535)` 不够，系统参数太小也会限制效果。

---

## 常见内核参数

| 参数 | 作用 |
|:---|:---|
| `net.core.somaxconn` | 全连接队列上限 |
| `net.ipv4.tcp_max_syn_backlog` | 半连接队列上限 |
| `net.ipv4.tcp_syncookies` | SYN 队列压力大时启用 syncookies |
| `net.ipv4.ip_local_port_range` | 本机临时端口范围 |
| `net.ipv4.tcp_tw_reuse` | TIME_WAIT 端口复用相关策略 |
| `fs.file-max` | 系统级文件描述符上限 |

查看示例：

```bash
sysctl net.core.somaxconn
sysctl net.ipv4.tcp_max_syn_backlog
sysctl net.ipv4.tcp_syncookies
ulimit -n
```

## SYN flood

SYN flood 是攻击者大量发送 SYN，但不完成三次握手，导致服务端半连接队列被占满。

现象：

- 大量 `SYN_RECV`
- 正常客户端连接超时
- CPU 不一定很高，但新连接失败明显增多

排查：

```bash
ss -ant state syn-recv
ss -s
```

缓解：

- 增大 `tcp_max_syn_backlog`
- 启用 `tcp_syncookies`
- 前置负载均衡或防火墙限速
- 应用层不要把所有保护寄托在 backlog 上

---

## accept 太慢

如果三次握手已经完成，但应用迟迟不 `accept()`，全连接队列会满。

常见原因：

- 单线程 accept 后直接处理耗时业务
- accept 线程被日志、锁、磁盘 IO 阻塞
- 新连接速率超过应用处理能力
- fd 达到进程上限，accept 失败

改进方向：

- accept 后尽快把连接交给 [[13.4 epoll模型|epoll]] 或 worker
- 使用专门的 Acceptor
- 提高进程 `ulimit -n`
- 检查 `EMFILE` / `ENFILE`
- 必要时使用 `SO_REUSEPORT` 多进程监听

---

## 文件描述符上限

每个 TCP 连接至少占用一个 fd。高并发服务常见第一个瓶颈就是 fd 数量。

```bash
ulimit -n
lsof -p <pid> | wc -l
```

常见错误：

| errno | 含义 |
|:---|:---|
| `EMFILE` | 当前进程 fd 达到上限 |
| `ENFILE` | 系统 fd 达到上限 |

工程上要有 fd 耗尽保护：当 `accept()` 返回 `EMFILE` 时，服务不能陷入忙等。

---

## 端口耗尽

客户端主动发起大量短连接时，可能遇到临时端口耗尽。

四元组决定一条 TCP 连接：

```text
源 IP + 源端口 + 目的 IP + 目的端口
```

如果同一台机器短时间对同一个服务发起大量连接，源端口会成为限制；再叠加 [[10.2 TIME_WAIT状态|TIME_WAIT]]，问题会更明显。

排查：

```bash
sysctl net.ipv4.ip_local_port_range
ss -tan state time-wait | wc -l
```

改进：

- 使用长连接或连接池
- 减少主动关闭的一方
- 扩大临时端口范围
- 合理设置内核复用策略

---

## SO_REUSEPORT

`SO_REUSEADDR` 常用于解决重启时端口被 TIME_WAIT 占用；`SO_REUSEPORT` 允许多个 socket 绑定同一个 IP:port，常用于多进程或多线程服务负载分摊。

```cpp
int on = 1;
setsockopt(fd, SOL_SOCKET, SO_REUSEPORT, &on, sizeof(on));
```

区别：

| 选项 | 主要用途 |
|:---|:---|
| `SO_REUSEADDR` | 地址复用，解决重启绑定问题 |
| `SO_REUSEPORT` | 多个监听 socket 共享同一端口，内核分发连接 |

## 面试问法

| 问题 | 回答要点 |
|:---|:---|
| backlog 控制哪个队列 | 现代 Linux 主要控制全连接队列，并受 `somaxconn` 限制 |
| 半连接队列满会怎样 | 新 SYN 可能被丢弃或触发 syncookies |
| 全连接队列满说明什么 | 应用 accept 太慢或队列太小 |
| SYN flood 怎么防 | syncookies、增大队列、限速、防火墙、负载均衡 |
| fd 上限不够表现是什么 | `accept` 返回 `EMFILE/ENFILE` |
| 端口耗尽常见在哪 | 客户端大量短连接或 TIME_WAIT 堆积 |

---

## 关键要点

1. **半连接队列服务于握手过程，全连接队列服务于 `accept()`**。
2. **`listen(backlog)` 不是越大越好，还受 `somaxconn` 限制**。
3. **SYN flood 主要打半连接队列，accept 慢主要压全连接队列**。
4. **高并发服务必须关注 fd 上限和临时端口范围**。
5. **`SO_REUSEPORT` 是多监听 socket 负载分摊，不等同于 `SO_REUSEADDR`**。
