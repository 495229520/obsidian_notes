# 输入输出缓冲区与协议解析器

## 简介

前面几篇留下了两个“假设它存在”的东西：[[8.9 TCP的粘包和拆包]] 里那台解析状态机，需要一块能跨事件保存半条消息的地方；[[8.12 非阻塞connect与健壮收发]] 里的短写处理，需要一块能保存没发完数据的地方。

这两块地方就是**应用层的输入输出缓冲区**。这篇讲它到底该怎么实现，以及为什么每个非阻塞网络库都会自己写一个。

---

## 内核已经有缓冲区了，为什么还要一个

[[8.7 IO缓冲|内核的收发缓冲区]]解决的是“数据先放哪”，但它解决不了非阻塞编程的两个核心问题：

| | 内核缓冲区 | 应用层缓冲区 |
|:---|:---|:---|
| 归谁管 | 内核，`SO_RCVBUF` / `SO_SNDBUF` 调大小 | 应用自己，每条连接一份 |
| 能不能“看一眼不取走” | 不能，`recv` 一读就没了 | 能，`peek()` 随便看 |
| 能不能存半条消息 | 存得下，但没法只取一部分 | 这正是它的用途 |
| 关键作用 | 削峰、流控 | 让非阻塞 IO 和消息边界解耦 |

具体到两个方向：

- **输入侧**：非阻塞 `recv()` 拿回来的字节数完全随机，可能是半条消息，也可能是三条半。解析器需要一块地方把不完整的那部分攒着，等下一次事件再接上
- **输出侧**：`send()` 只写进去一半是常态。剩下的必须自己存着，等 `EPOLLOUT` 再续，总不能原地死等

**说到底，应用层缓冲区就是那个把“内核什么时候给我数据”和“我什么时候能凑出一条完整消息”解耦开的东西。**

---

## Buffer 的内部结构

结构本身非常简单：一块连续内存，加两个下标。

![[图片/SVG/3_8_8_15_1.svg|900]]

两个游标把内存切成三段，三个查询函数直接从游标算出来：

```cpp
size_t readableBytes()    const { return writerIndex_ - readerIndex_; }
size_t writableBytes()    const { return buf_.size()  - writerIndex_; }
size_t prependableBytes() const { return readerIndex_; }
```

四步操作里游标的移动规则也只有两条：

- `append()` 往里写数据，**只动 `writerIndex_`**
- `retrieve()` 取走数据，**只动 `readerIndex_`**；取空了就两个一起复位

图里第 ③ 步有个细节值得留意：解析走 5 字节之后，`prependable` 从 8 涨到了 13。多出来的这 5 字节谁也用不上，是纯浪费。所以 `retrieveAll()` 必须把两个游标一起复位，而不是任由 `readerIndex_` 一路往右爬。

---

## 前面那 8 个字节留着干什么

`kCheapPrepend` 这块预留空间是为**长度前缀回填**准备的。

序列化的时候，body 有多长常常要写完才知道。如果 buffer 前面没有富余空间，就得先把 body 序列化到临时地方、算出长度、再申请一块新内存把“长度 + body”拼起来——白白多一次拷贝。

留着这 8 个字节，就可以直接往前面塞：

```cpp
// 把 4 字节长度回填到 readable 区前面，不产生额外拷贝
void prependInt32(uint32_t x) {
    uint32_t be = htonl(x);
    readerIndex_ -= sizeof(be);
    std::memcpy(buf_.data() + readerIndex_, &be, sizeof(be));
}
```

`readerIndex_` 往左退 4，长度写进去，完事。这也解释了为什么复位时退回的是 `kCheapPrepend`（8）而不是 0——留 0 的话这个技巧就用不了了。

---

## 空间不够时：先腾挪，再扩容

写不下的时候有两条路，而且顺序不能反：

![[图片/SVG/3_8_8_15_2.svg|900]]

判断条件就一行：把 `prependable` 那块白占的空间算上，够不够放下要写的数据。

```cpp
void Buffer::makeSpace(size_t len) {
    if (writableBytes() + prependableBytes() < len + kCheapPrepend) {
        // 腾不出来，只能扩容。这一步会拷贝已有数据
        buf_.resize(writerIndex_ + len);
    } else {
        // 够用：把 readable 整体搬到最前面，顺手回收白占的 prependable
        size_t readable = readableBytes();
        std::memmove(buf_.data() + kCheapPrepend,
                     buf_.data() + readerIndex_, readable);
        readerIndex_ = kCheapPrepend;
        writerIndex_ = readerIndex_ + readable;
    }
}
```

为什么要先试腾挪：长连接跑久了，`readerIndex_` 会被一次次 `retrieve` 推到很靠后的位置，前面积攒一大块谁也用不上的空间。一次 `memmove` 就能把它全部收回来，不用申请新内存，缓冲区总长度也不变。而 `resize` 既要重新分配、又要拷贝已有数据，能省则省。

> [!warning] 扩容会让之前拿到的指针失效
> `peek()` 返回的是 `buf_.data() + readerIndex_`，扩容之后底层 `vector` 可能整块搬家。所以**绝对不要把 `peek()` 的返回值存下来跨调用使用**，解析器每次都要重新取。这是 Buffer 使用上最容易踩的一个坑，而且它通常不会立刻崩，要等到某次恰好触发扩容才出问题。

---

## 一次 readv 就把内核读空

读取这一步有个两难：Buffer 开小了，一次事件要 `recv` 好几轮；开大了，几万条连接每条都常驻一大块内存。

muduo 的解法是拿栈上的临时数组当第二块缓冲区，配合 `readv` 一次读走：

```cpp
ssize_t Buffer::readFd(int fd, int* savedErrno) {
    char extrabuf[65536];              // 栈上的，调用结束就没了，不占常驻内存
    iovec vec[2];
    const size_t writable = writableBytes();

    vec[0].iov_base = buf_.data() + writerIndex_;
    vec[0].iov_len  = writable;
    vec[1].iov_base = extrabuf;
    vec[1].iov_len  = sizeof(extrabuf);

    // Buffer 本身已经够大时就不劳烦 extrabuf 了
    const int iovcnt = (writable < sizeof(extrabuf)) ? 2 : 1;
    const ssize_t n = ::readv(fd, vec, iovcnt);

    if (n < 0) {
        *savedErrno = errno;
    } else if (static_cast<size_t>(n) <= writable) {
        writerIndex_ += n;                  // 全落进 Buffer，extrabuf 没被碰
    } else {
        writerIndex_ = buf_.size();         // Buffer 被填满
        append(extrabuf, n - writable);     // 溢出那段搬进来，这时候才触发扩容
    }
    return n;
}
```

这段代码值得逐块看：

- **`extrabuf` 在栈上**，64 KB。它只在这次调用期间存在，所以不管有几万条连接，都不会有几万个 64 KB 常驻
- **`iovcnt` 是算出来的**。Buffer 的 `writable` 本来就比 64 KB 大时，第二块纯属多余，少填一个 `iovec` 少一点开销
- **`n <= writable` 是常规路径**，一次系统调用搞定，`extrabuf` 一个字节没用上，也没付出任何代价
- **`n > writable` 才走第二条路**：多出来的那段 `append` 进 Buffer，代价是一次 `memcpy` 加可能的一次扩容，但省下了一次 `read` 系统调用

结果是两头的好处都占到了：初始 Buffer 可以开得很小（比如 1 KB），常规流量下一次 `readv` 就把内核缓冲区读空，突发大包也不会漏读。

## 输出缓冲区：结构一样，用法不一样

输出缓冲区的数据结构和输入的完全同构，但调用顺序有讲究——**不能一上来就往 Buffer 里塞**：

```cpp
void send(Connection* c, const char* data, size_t len) {
    size_t remaining = len;

    // 缓冲区是空的，说明没有积压，可以直接试着发
    if (c->output_buffer.readableBytes() == 0) {
        ssize_t n = ::send(c->fd, data, len, MSG_NOSIGNAL);
        if (n >= 0) {
            remaining -= n;
        } else if (errno != EAGAIN && errno != EWOULDBLOCK) {
            close_connection(c);
            return;
        }
    }

    // 没发完的（或者本来就有积压的）才进缓冲区
    if (remaining > 0) {
        c->output_buffer.append(data + (len - remaining), remaining);
        enable_writing(c);            // 这时才注册 EPOLLOUT
    }
}
```

两个顺序上的讲究：

- **先直接发，发不完才进缓冲区。** 绝大多数请求在正常负载下一次就发完了，这条路径上完全不碰 Buffer，也不会去动 epoll 注册。要是无脑先 `append` 再统一发，每个请求都白白多一次拷贝加一次 `epoll_ctl`
- **缓冲区非空时必须直接 `append`，不能插队直接发。** 否则新数据会跑到旧数据前面，把消息顺序搞乱

`EPOLLOUT` 的注册和摘除、高低水位反压见 [[8.12 非阻塞connect与健壮收发#EPOLLOUT 必须用完就摘|8.12]]，这里不重复。

## 线性缓冲区 vs 环形缓冲区

两种都常见，选哪个取决于消息是不是定长：

| | 线性（vector + 双游标） | 环形（ring buffer） |
|:---|:---|:---|
| 实现复杂度 | 低 | 中，回绕逻辑容易写错 |
| 数据是否连续 | **是**，可以直接把一段内存交给解析器 | 否，可能跨越回绕点，要按两段处理 |
| 容量 | 可以动态扩，代价是搬数据 | 通常定长，满了要么阻塞要么丢 |
| 支持 prepend | 天然支持 | 麻烦 |
| 空间回收 | 靠 `memmove` 腾挪 | 天然回收，不用搬 |
| 适合 | 变长消息、通用服务 | 定长消息、固定容量、单读单写无锁场景 |

“数据是否连续”这一条是关键。变长协议的解析器几乎都需要“给我一段连续内存，我从头扫”，环形缓冲区在回绕点上就得特殊处理，要么额外拷贝一次拼成连续的，要么解析器写成能处理两段的样子——两条路都不舒服。所以通用网络库基本都选线性方案。

## 分层：Buffer / Codec / 业务

写到这里，三层职责应该分得很清楚了：

| 层 | 只关心 | 完全不知道 |
|:---|:---|:---|
| Buffer | 字节的进出、空间的伸缩 | 消息边界在哪，协议长什么样 |
| Codec（解析器） | 边界怎么划、字段怎么编解码 | 数据从哪个 fd 来、什么时候来 |
| 业务 | 一条完整的消息该怎么处理 | 上面这些统统不知道 |

分开的最大好处不是好看，而是**Codec 可以脱离网络做单元测试**：

```cpp
// 不需要真的建立连接，直接喂字节
// 长度字段和 body 分开写成两个字面量，避免十六进制转义把后面的字符吃进去
Buffer buf;
buf.append("\x00\x00\x00\x05" "HELLO", 9);
buf.append("\x00\x00\x00\x03" "WOR",   7);     // 故意只给半条

std::vector<std::string> msgs = codec.parse(&buf);
assert(msgs.size() == 1);                       // 只该吐出一条
assert(buf.readableBytes() == 7);               // 半条原样留在缓冲区
```

粘包、半包这些最难在真实网络里稳定复现的路径，就这样变成了几行普通的单元测试——想造什么切法就造什么切法。这是分层带来的最实在的收益。

## 常见错误

| 错误 | 后果 |
|:---|:---|
| 把 `peek()` 的返回值存下来跨调用用 | 一次扩容之后变野指针，而且不会立刻崩 |
| 一次事件只解析一条消息 | 剩下的躺在缓冲区里等下次事件，消息慢一拍，见 [[8.9 TCP的粘包和拆包]] |
| 输出缓冲区不设上限 | 对端收不动时无限膨胀，最后 OOM，要靠高低水位反压 |
| 多个线程共用一条连接的 Buffer | 数据错乱。Buffer 不加锁，一条连接只归一个事件循环管 |
| `retrieve` 之后不复位游标 | `prependable` 越攒越大，白占内存还频繁触发腾挪 |

---

## 关键要点

1. **应用层缓冲区的作用是把“内核什么时候给数据”和“什么时候凑出一条完整消息”解耦**，内核缓冲区替代不了它
2. **结构就是一块连续内存加两个下标**，三段空间和三个查询函数全从游标算出来
3. **`append` 只动 `writerIndex_`，`retrieve` 只动 `readerIndex_`**，取空了两个一起复位
4. **前面预留 8 字节是为了长度前缀回填**，省掉一次拼包拷贝
5. **空间不够先 `memmove` 腾挪，腾不出来才 `resize`**；扩容会让之前拿到的指针失效
6. **`readv` + 栈上 64 KB 临时数组**，让小 Buffer 也能一次读空内核
7. **发送要先直接 `send`，发不完才进缓冲区**；缓冲区非空时必须排队，不能插队
8. **变长协议用线性缓冲区**，环形缓冲区的回绕点会让解析器变难写
9. **Buffer / Codec / 业务分三层**，最大收益是 Codec 能脱离网络做单元测试
