## 1. 问题引入

TCP [[7.6 套接字|套接字]] 的数据收发是**无边界**的。服务器端即使调用 1 次 `write()` 函数传输 40 字节的数据，客户端也可能通过 4 次 `read()` 函数调用每次读取 10 字节。但这也带来一些疑问：服务器端一次性传输了 40 字节，而客户端逐步分批接收。客户端接收 10 字节后，剩下的 30 字节在何处等待呢？是不是像飞机等待着陆而在空中盘旋一样，剩下 30 字节也在网络中徘徊并等待接收呢？

不是。数据不在网络里飘着，它躺在**接收端主机的内核内存**里。

**`write()` 调用后并非立即传输数据，`read()` 调用后也并非马上接收数据**。`write()` 那一瞬间数据被移到**输出缓冲**，`read()` 那一瞬间从**输入缓冲**里取。剩下的 30 字节从头到尾都在接收方内核的输入缓冲里，等着应用来读。

## 2. TCP 套接字 IO 缓冲

IO 缓冲是操作系统内核里的一块临时存储区，紧挨着每个 TCP [[7.6 套接字|套接字]]。TCP 是 [[7.5 TCP协议基础#2. 核心特性|全双工]] 的，所以每条连接有**两个**这样的缓冲区，两个方向各走各的。

![[图片/SVG/3_8_8_7_1.svg|1000]]

### 2.1 发送缓冲区（Send Buffer）

调用 [[8.3 TCP客户端#6.1 send 函数|send()]] 或 `write()` 时，数据**不是立即通过网络发送出去的**，而是先被复制到发送缓冲区，函数随即返回。真正什么时候上网，由内核根据 MSS 和拥塞窗口决定。

### 2.2 接收缓冲区（Receive Buffer）

网络上到达的数据先落进接收缓冲区，乱序的段在这里排好序，然后等应用程序用 [[8.3 TCP客户端#6.2 recv 函数|recv()]] 或 `read()` 取走。

两个缓冲区互不相干。对端读得慢只会堵住一个方向，反方向照常收发——这正是「全双工」在实现层面的样子。

## 3. IO 缓冲的特点

| 特点 | 说明 |
|:---|:---|
| **独立存在** | 缓冲区属于连接，不属于进程；每个 TCP 套接字单独一对 |
| **自动创建** | 随套接字创建、随套接字销毁，不用手工分配和释放 |
| **输出缓冲继续发送** | 关闭套接字后，输出缓冲里遗留的数据内核会继续发完 |
| **输入缓冲数据丢失** | 关闭套接字时，输入缓冲里还没读走的数据被直接丢弃 |

最后两条的不对称经常被忽略，但它有实际后果：**输入缓冲里还有未读数据时调用 `close()`，内核会给对端回一个 RST**，而不是走正常的四次挥手。对端此时如果还在 `recv()`，拿到的是 `ECONNRESET` 而不是有序关闭的 0。

想只关一个方向（比如「我发完了，但还要继续收」），用 `shutdown(fd, SHUT_WR)` 而不是 `close()`。详见 [[8.11 TCP连接关闭与异常状态]]。

## 4. 缓冲的作用

缓冲区把应用程序的读写速度和网络传输速度解耦开。具体是三件事：

![[图片/SVG/3_8_8_7_2.svg|1000]]

### 4.1 攒包提高有效载荷比

一个 TCP 段至少要驮 40 字节的头（IP 20 + TCP 20），这是固定成本。没有缓冲的话，应用每 `send()` 一个字节，网络上就跑一个 41 字节的包——有效载荷 2.4%，剩下的全是头。

有了缓冲区，内核可以把多次 `send()` 的数据攒起来，凑够一个 **MSS**（Maximum Segment Size，以太网上通常是 1460 字节）再打包发出去，有效载荷升到 97%。

> [!note] 攒包不总是好事
> 交互式应用（SSH、游戏、实时控制）宁可要低延迟也不要高带宽利用率。控制攒包行为的是 **Nagle 算法**，关掉它用 `setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, ...)`。
> Nagle 和延迟确认（Delayed ACK）撞在一起会产生 40ms 级的延迟毛刺，是网络排障里的经典现象，见 [[8.14 高性能发送与线上排障]]。

### 4.2 流量控制（Flow Control）

接收缓冲区的**空余量**会写进 TCP 报文头的窗口大小（Window Size）字段，通告给发送方。空余量减小，发送方就减速；降到 0（零窗口），发送方停止发送数据。

应用程序 `read()` 走一批数据后空余量回升，内核补发一个窗口更新报文，发送方恢复。

这条链路的意义在于：**接收方读得慢，压力会一路传导回发送方，而不是让数据在网络上丢掉。** 完整机制见 [[8.8 流控制]]。

### 4.3 留底供重传

数据被 `send()` 进发送缓冲区、由内核发到网络上之后，**不会立刻从缓冲区里删掉**。它要一直留到收到对端的 ACK 才释放。

超时没等到 ACK，TCP 就从发送缓冲区里把原始数据取出来重发。应用程序对这个过程一无所知。

反过来说：如果 `send()` 返回后就把数据丢掉，TCP 手里没有副本，重传就无从谈起。这是发送缓冲区省不掉的根本原因，也是 `send()` 返回成功**不等于对方收到**的原因——那时数据才刚进本机内核。

## 5. 缓冲区大小

### 5.1 查看默认值

```bash
# 默认的发送 / 接收缓冲区大小（字节）
cat /proc/sys/net/core/wmem_default
cat /proc/sys/net/core/rmem_default

# 允许设置的上限
cat /proc/sys/net/core/wmem_max
cat /proc/sys/net/core/rmem_max

# TCP 专用的三元组：最小值 默认值 最大值，内核会在这个区间内自动调整
cat /proc/sys/net/ipv4/tcp_wmem
cat /proc/sys/net/ipv4/tcp_rmem
```

`net.core.*` 是所有协议的通用默认值，`net.ipv4.tcp_*` 是 TCP 专用的。**只要不手工调用 `setsockopt`，TCP 就会在 `tcp_wmem` / `tcp_rmem` 给出的区间内自动伸缩缓冲区**，这通常比写死一个值更合适。

### 5.2 用代码设置

用 [[10.1 套接字选项#5. setsockopt 函数|setsockopt()]]：

```c
int sockfd = socket(AF_INET, SOCK_STREAM, 0);

int buf_size = 65536;   // 64KB
setsockopt(sockfd, SOL_SOCKET, SO_SNDBUF, &buf_size, sizeof(buf_size));
setsockopt(sockfd, SOL_SOCKET, SO_RCVBUF, &buf_size, sizeof(buf_size));

// 读回来看看内核实际给了多少
int actual = 0;
socklen_t len = sizeof(actual);
getsockopt(sockfd, SOL_SOCKET, SO_SNDBUF, &actual, &len);
printf("实际发送缓冲区大小: %d\n", actual);   // 通常是 131072，被翻倍了
```

> [!warning] 三个反直觉的地方
> - **Linux 会把你设的值翻倍。** 多出来的那份给内核自己的数据结构（`sk_buff` 等）用，所以 `getsockopt` 读回来的数是设置值的两倍，这不是 bug。
> - **手工设了 `SO_RCVBUF` 就关掉了自动调整。** 内核不再帮你伸缩，从此这个值写死。除非确实知道自己在干什么，否则让内核自己调更好。
> - **`SO_RCVBUF` 必须在 `connect()` / `listen()` 之前设。** 接收窗口缩放选项在三次握手时协商，握手完了再改，缩放因子已经定死了。

缓冲区大小的经验值是**带宽时延积**（BDP = 带宽 × RTT）。1Gbps 链路、RTT 50ms，BDP ≈ 6MB——缓冲区小于这个数，链路就跑不满，因为发送方会一直在等 ACK。

## 6. 关键要点

1. **缓冲区在内核里，每个 TCP 套接字独立一对**，随套接字自动创建和销毁。
2. **`write`/`send` 不等于发送**：数据先进输出缓冲，上网时机由内核定。
3. **`read`/`recv` 不等于接收**：数据早就到了输入缓冲，`read` 只是把它拷到用户空间。
4. **关闭时两个方向不对称**：输出缓冲的数据内核继续发完，输入缓冲里没读的直接丢弃——还会触发给对端的 RST。
5. **三个作用**：攒包提高有效载荷比、用空余量做流量控制、留底供超时重传。
6. **缓冲区大小优先交给内核自动调整**；真要手工设，参照带宽时延积，并且注意 Linux 会翻倍、以及必须在握手前设置。
