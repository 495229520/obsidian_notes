01 · Learning map

Day01 真正形成的是一条能力链。

命令只是入口，基础函数保证输入可靠；两套 I/O 接口解释数据如何流动；重定向、同步和锁则决定多进程环境下是否正确。

01
定位与操作
用命令找到文件、进程与磁盘问题，并在修改前确认目标。
grep -rn 找内容；find -name 找文件；先 kill，最后才 kill -9。
02
环境与权限
理解 PATH、父子进程环境继承，以及 rwx / UID / GID / umask。
export 只影响当前会话与后代；创建权限 = 请求权限被 umask 屏蔽后的结果。
03
安全输入与转换
格式化 I/O 先看返回值；不可信数字用 strtol 系列，不用 atoi 猜错误。
end == str：没读到数字；errno == ERANGE：越界；snprintf：检测截断。
04
两套文件接口
系统调用用 fd；标准 I/O 用 FILE* 和用户态缓冲。最终都进入内核文件对象链。
fileno 向下取 fd；fdopen 向上包装成流。
05
共享、落盘与互斥
dup/fork 共享打开实例；fflush 不等于落盘；锁行为取决于锁挂在哪个对象上。
dup2 改 fdtable；fsync 管持久化；F_OFD_SETLK 管区间互斥。

02 · Two interface routes

fd 与 FILE*：两条入口，一条内核主线。

点击切换关注路线。最关键的分界不是“哪个函数更高级”，而是用户态缓冲是否存在、资源由谁关闭、数据此刻停在哪一层。

fd 是 fdtable 的索引，没有 stdio 用户态缓冲；read/write 的返回值必须处理短读、短写、EOF 与错误。

03 · Buffer & durability

“刷新”有两层，不能混成一个动作。

stdio 缓冲属于进程；page cache 属于内核。fflush 只完成第一段交接，fsync 才在持久化语义上继续向下推进。

FILE* · user buffer

printf / fwrite 可能先把小写入聚合在用户空间。

fflush(fp)：把这些字节交给内核。

fflush
→

inode · page cache

write 成功通常只说明数据已进入内核管理的缓存页。

fsync(fd)：请求数据与必要元数据持久化。

fflush()用户缓冲 → 内核；不保证掉电后还在。
fsync()内核缓存 → 稳定存储；用于持久化边界。
fclose()会刷新 stdio 并关闭 fd；仍应检查返回值。

04 · Redirection lab

重定向不是搬数据，而是改指针。

dup2(3, 1) 的本质：关闭 fd 1 的旧引用，再让 fd 1 指向 fd 3 对应的同一个打开文件描述。

观察 fdtable，而不是 stdout 这个名字。

调用之后，fd 1 与 fd 3 可以互换使用，并共享文件偏移与文件状态标志。stdio 仍有独立用户缓冲，因此重定向前后要明确 fflush 边界。

07 · Three failure modes

今日三个卡点，都是“层级混淆”。

一旦先问“状态位于用户缓冲、打开实例还是 inode”，三个看似诡异的问题都会变成可推导的结果。

01

fork 后重复输出

printf 数据还在 FILE* 用户缓冲时 fork，父子会各自复制一份，退出刷新时可能各写一次。边界：fflush(stdout) 后再 fork。

02

任意 close 导致 POSIX 锁全丢

记录锁挂在 PID + inode，而不是某个 fd。当前进程关闭指向该 inode 的任意 fd，都可能释放本进程在该文件上的所有 POSIX 记录锁。

03

printf 与 write 顺序颠倒

write 直接进入内核，printf 可能仍滞留在用户缓冲。两套接口混用时必须显式建立 fflush 同步边界。
