## 1. 为什么连接对象生命周期复杂

在教学版 `epoll` 服务器里，常常只看到一个 `int fd`：

```text
epoll_wait() 返回 fd
    |
    |-- listen_fd -> accept
    |-- conn_fd   -> read / write / close
```

但在真实 C++ 网络库中，一个连接通常不只是一个 fd，而是一组对象共同维护的状态：

| 对象 | 典型职责 |
|:---|:---|
| `Socket` / `unique_fd` | 拥有 fd，在析构时 `close()` |
| `Channel` | 保存 fd 关注事件和回调，通常不拥有 fd |
| `TcpConnection` | 拥有连接状态、输入输出缓冲区、`Socket`、`Channel` |
| `EventLoop` | 在所属线程内分发事件、执行 pending functors |
| `TcpServer` / 连接表 | 保存活跃连接，决定连接对象何时可以释放 |

连接生命周期复杂，核心原因有三个：

1. `epoll_event.data.ptr` 或 `Channel` 回调里可能保存对象指针。
2. 关闭连接不是单个 `close(fd)`，还要从 `epoll` 和连接表中移除。
3. 多线程 Reactor 中，连接状态必须回到所属 EventLoop 线程修改。

> [!note] 核心问题
> 连接对象生命周期管理解决的是：**fd 关闭、事件注销、对象析构、回调执行这几件事必须按安全顺序发生**。
>
> 顺序错了，就可能出现 fd 泄漏、重复关闭、回调访问已析构对象、`epoll` 返回悬空指针等问题。

## 2. 对象边界：谁拥有 fd，谁只是观察 fd

理解生命周期，首先要分清所有权。

| 对象 | 是否拥有 fd | 说明 |
|:---|:---:|:---|
| `Socket` / `unique_fd` | 是 | RAII 封装 fd，析构时关闭 |
| `Channel` | 否 | 只保存 fd 和事件回调，不负责关闭 fd |
| `TcpConnection` | 间接拥有 | 通过 `Socket` 拥有连接 fd，并组合 `Channel`、buffer、状态 |
| `EventLoop` / `Poller` | 否 | 只负责监听和分发 fd 事件 |
| 连接表 | 拥有连接对象 | 常用 `std::shared_ptr<TcpConnection>` 保存活跃连接 |

这和 [[13.6 Reactor模式与EventLoop|Reactor]] 的角色划分一致：`Channel` 是事件处理入口，`TcpConnection` 才是连接状态和资源的聚合点。

![[图片/3.Linux/13. IO复用/13_8_2.svg|760]]

> [!warning] Channel 不要拥有 fd
> 如果 `Channel` 和 `Socket` 都认为自己负责关闭 fd，就容易重复 `close()`。
>
> 更清晰的设计是：`Socket` / `unique_fd` 负责资源释放，`Channel` 只负责把 fd 事件分发到回调。

## 3. 用 RAII 管理 fd

RAII 的核心是：资源在对象构造时取得，在对象析构时释放。对 socket fd 来说，就是把 `close(fd)` 放进析构函数，而不是散落在各个异常路径和 return 分支里。

```cpp
class UniqueFd {
public:
    explicit UniqueFd(int fd = -1) : fd_(fd) {}

    ~UniqueFd() {
        if (fd_ >= 0) {
            ::close(fd_);
        }
    }

    UniqueFd(const UniqueFd&) = delete;
    UniqueFd& operator=(const UniqueFd&) = delete;

    UniqueFd(UniqueFd&& other) noexcept : fd_(other.fd_) {
        other.fd_ = -1;
    }

    UniqueFd& operator=(UniqueFd&& other) noexcept {
        if (this != &other) {
            reset();
            fd_ = other.fd_;
            other.fd_ = -1;
        }
        return *this;
    }

    int get() const { return fd_; }

    int release() {
        int old = fd_;
        fd_ = -1;
        return old;
    }

    void reset(int newFd = -1) {
        if (fd_ >= 0) {
            ::close(fd_);
        }
        fd_ = newFd;
    }

private:
    int fd_;
};
```

这类封装体现了《Effective C++》Item 13 的原则：用对象管理资源，让析构函数负责释放资源。它也对应 [[独享智能指针|unique_ptr]] 的独占所有权思想，只是这里管理的是 fd，而不是 `new` 出来的对象。

> [!tip] fd RAII 的关键规则
> fd 拥有者应该不可复制，只能移动。
>
> 否则两个对象持有同一个 fd，析构时就可能重复关闭；而重复关闭 fd 在高并发服务器中尤其危险，因为相同的整数 fd 可能已经被内核复用给了另一条连接。

## 4. TcpConnection 的典型生命周期

一个连接从建立到释放，通常经历这些阶段：

| 阶段 | 触发条件 | 主要动作 |
|:---|:---|:---|
| 创建 | `accept4()` 返回 `conn_fd` | 设置非阻塞，创建 `TcpConnection` / `Channel` |
| 建立 | 注册到 sub loop | 加入连接表，注册读事件，触发 connection callback |
| 活跃 | `EPOLLIN` / `EPOLLOUT` | 读入 input buffer，发送 output buffer |
| 关闭中 | 对端关闭、本端主动关闭或错误事件 | 禁用事件，处理剩余输出，触发 close callback |
| 销毁 | 从连接表移除且无回调持有 | `Channel` 从 `epoll` 删除，`Socket` 析构关闭 fd |

可以把关闭流程记成：

```text
检测到关闭 / 错误
    |
    |-- 在所属 EventLoop 线程内处理 close
    |-- disableAll()，不再关注读写事件
    |-- 从 epoll 中 remove Channel
    |-- 从连接表 erase shared_ptr
    |-- 最后一个 shared_ptr 释放后析构 TcpConnection
    |-- Socket / unique_fd 析构 close(fd)
```

这比简单 `close(fd)` 多了几步，但每一步都有意义：

- 先禁用和移除事件，避免 `epoll` 后续再返回这个 fd 对应的旧对象。
- 再从连接表删除，允许连接对象在没有回调持有时析构。
- 最后由 RAII 对象关闭 fd，保证所有路径都能释放资源。

相关的 TCP 关闭状态可以回顾 [[8.11 TCP连接关闭与异常状态]]，`epoll` 关闭顺序可以对照 [[13.4 epoll模型#14. 关闭连接的顺序|epoll 的关闭连接顺序]]。

## 5. shared_ptr / weak_ptr 与回调安全

连接对象经常被多个地方临时引用：连接表、正在执行的回调、业务层异步任务、定时器回调等。因此网络库中常用 [[共享智能指针|shared_ptr]] 管理 `TcpConnection` 对象。

但回调里直接捕获裸指针或强引用都可能有问题：

| 捕获方式 | 风险 |
|:---|:---|
| 捕获裸指针 `this` | 回调执行时对象可能已经析构，产生悬空指针 |
| 长期捕获 `shared_ptr` | 可能延长连接生命周期，甚至形成循环引用 |
| 捕获 `weak_ptr` | 回调执行前先 `lock()`，对象存在才执行 |

典型思路是让 `Channel` 持有一个 `weak_ptr`，事件处理前尝试提升为 `shared_ptr`：

```cpp
void Channel::handleEvent() {
    if (auto guard = tie_.lock()) {
        handleEventWithGuard();
    }
}
```

这样做的目的不是让 `Channel` 拥有连接，而是在回调执行期间临时延长连接对象寿命，避免回调执行到一半对象被释放。

> [!warning] 避免 shared_ptr 环
> `TcpConnection` 拥有 `Channel`，如果 `Channel` 又强拥有 `TcpConnection`，就会形成引用环。
>
> 这类“观察但不拥有”的关系应该使用 `weak_ptr`。

## 6. 多线程下的释放顺序

在 one loop per thread 模型中，连接属于某个固定的 EventLoop。即使关闭请求来自 worker 线程，也应该投递回连接所属 loop。

```text
worker 线程想关闭连接
    |
    |-- queueInLoop(closeInLoop)
    |-- eventfd 唤醒所属 EventLoop
    |
所属 EventLoop 线程
    |-- 执行 closeInLoop()
    |-- 从 epoll 删除 Channel
    |-- 从连接表移除连接
```

这和 [[13.7 eventfd、timerfd与跨线程唤醒|跨线程唤醒]] 是同一套模型：其他线程只投递任务，不直接修改连接状态。

> [!note] 所属线程原则
> `TcpConnection` 的读写缓冲区、Channel 事件、连接状态最好都在所属 EventLoop 线程内修改。
>
> 这样可以减少锁，也能让生命周期顺序更容易推理。

## 7. 常见工程陷阱

| 问题 | 后果 | 正确做法 |
|:---|:---|:---|
| 直接 `close(fd)`，不从 `epoll` 删除 | 后续事件可能命中旧 fd 或旧指针 | 先禁用/删除 Channel，再释放 fd |
| `Channel` 和 `Socket` 都关闭 fd | 重复关闭，可能误关被复用的新 fd | 明确 fd 只有一个 RAII 拥有者 |
| 回调捕获裸指针 | 对象析构后回调访问悬空对象 | 用 `weak_ptr` 检查对象是否仍存在 |
| 回调长期捕获 `shared_ptr` | 连接对象迟迟不释放或形成引用环 | 观察关系使用 `weak_ptr` |
| 跨线程释放连接对象 | 和 EventLoop 正在分发事件发生竞态 | 投递回所属 EventLoop 线程释放 |
| 析构函数里做复杂业务回调 | 析构路径难以控制，可能重入 | 析构只释放资源，业务通知在关闭流程中完成 |

## 8. 面试问法

| 问题 | 回答要点 |
|:---|:---|
| 为什么连接对象生命周期比 fd 复杂？ | fd 只是内核资源，连接对象还包含 Channel、buffer、状态、回调和连接表引用。 |
| Channel 是否应该拥有 fd？ | 通常不应该。Channel 负责事件分发，fd 应由 Socket / unique_fd 这类 RAII 对象拥有。 |
| 为什么关闭连接前要从 epoll 删除？ | 避免后续 `epoll_wait()` 返回已经失效的 fd 或悬空对象指针。 |
| RAII 在网络连接里解决什么问题？ | 保证 fd 在所有路径上都能释放，避免泄漏和重复释放。 |
| 为什么 fd RAII 对象要禁止复制？ | 复制会产生多个拥有者，析构时可能重复关闭同一个 fd。 |
| shared_ptr 在连接管理中有什么作用？ | 让连接表和正在执行的回调可以安全共享连接对象生命周期。 |
| weak_ptr 解决什么问题？ | 表示观察关系，避免悬空回调和 `shared_ptr` 引用环。 |
| 多线程中谁负责释放连接？ | 连接所属 EventLoop 线程负责修改状态、移除 Channel 和触发释放流程。 |

---

## 9. 关键要点

1. `fd` 是内核资源，`TcpConnection` 是包含 fd、buffer、状态和回调的 C++ 对象。
2. `Channel` 通常不拥有 fd，只负责事件关注和回调分发。
3. fd 应该由 `Socket` / `unique_fd` 这类 RAII 对象唯一拥有。
4. 关闭连接要先禁用并移除事件，再从连接表删除，最后由 RAII 关闭 fd。
5. `shared_ptr` 适合表达连接对象的共享生命周期，`weak_ptr` 适合表达回调中的观察关系。
6. 避免 `TcpConnection -> Channel -> shared_ptr<TcpConnection>` 这类引用环。
7. 多线程 Reactor 中，连接状态和释放流程应回到所属 EventLoop 线程执行。
8. 析构函数负责释放资源，不应该承担复杂业务流程。
