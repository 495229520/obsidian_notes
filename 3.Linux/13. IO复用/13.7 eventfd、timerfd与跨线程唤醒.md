# eventfd、timerfd与跨线程唤醒

## 1. 为什么需要 eventfd / timerfd

在 [[13.6 Reactor模式与EventLoop|Reactor 与 EventLoop]] 中，`EventLoop` 的主循环通常长这样：

```text
while (!quit) {
    activeChannels = poller.poll(timeout);

    for channel in activeChannels:
        channel.handleEvent();

    doPendingFunctors();
}
```

这里有一个关键问题：如果某个 worker 线程已经处理完业务，想把“发送响应”“关闭连接”“更新连接状态”这类任务投递回连接所属的 EventLoop，而这个 EventLoop 正阻塞在 `epoll_wait()` 里，任务什么时候才能被执行？

答案是：需要一个能被 `epoll` 监听的唤醒事件。

`eventfd` 和 `timerfd` 都是 Linux 把“非 socket 事件”变成文件描述符的机制：

| 机制 | 解决的问题 | 在 EventLoop 中的角色 |
|:---|:---|:---|
| `eventfd` | 线程之间发送轻量级通知 | 唤醒阻塞在 `epoll_wait()` 的 EventLoop |
| `timerfd` | 定时器到期通知 | 把定时任务纳入 `epoll` 事件循环 |

> [!note] 核心定位
> `eventfd` 让“跨线程通知”变成 fd 可读事件，`timerfd` 让“时间到期”变成 fd 可读事件。
>
> 它们和 socket 一样都可以注册进 `epoll`，从而被同一个 EventLoop 统一调度。

## 2. eventfd：跨线程唤醒 EventLoop

`eventfd` 创建一个带 64 位无符号计数器的文件描述符，常用于线程间事件通知。

```c
#include <sys/eventfd.h>

int eventfd(unsigned int initval, int flags);
```

### 2.1 常用 flags

| flag | 说明 |
|:---|:---|
| `EFD_NONBLOCK` | 设置为非阻塞，避免读写卡住 EventLoop |
| `EFD_CLOEXEC` | 设置 close-on-exec，避免 fd 泄漏到子进程 |
| `EFD_SEMAPHORE` | 每次 read 只减 1，较少用于 EventLoop 唤醒 |

在网络库中常见写法是：

```cpp
int wakeupFd = eventfd(0, EFD_NONBLOCK | EFD_CLOEXEC);
```

> [!tip]
> 新代码优先使用 `EFD_NONBLOCK | EFD_CLOEXEC`。这和 `epoll_create1(EPOLL_CLOEXEC)`、`accept4(SOCK_NONBLOCK | SOCK_CLOEXEC)` 的工程思路一致：创建 fd 时就设置好关键属性。

### 2.2 读写语义

`eventfd` 内部可以理解成一个计数器：

| 操作 | 行为 |
|:---|:---|
| `write(eventfd, &value, 8)` | 把 `value` 加到内核计数器上 |
| `read(eventfd, &value, 8)` | 读出当前计数器，并把计数器清零 |
| 非阻塞读空 | 返回 `-1`，`errno` 为 `EAGAIN` |

普通模式下，如果计数器当前是 5，一次 `read()` 会读出 5，并把计数器清零。EventLoop 唤醒通常不关心“被唤醒了几次”，只关心“现在应该去处理 pending functors 了”，所以这种读清空语义正好合适。

```cpp
uint64_t one = 1;
write(wakeupFd, &one, sizeof(one));

uint64_t value = 0;
read(wakeupFd, &value, sizeof(value));
```

> [!warning] 必须读 eventfd
> `eventfd` 被 `epoll` 通知可读后，EventLoop 要调用 `read()` 消费这个事件。
>
> 如果只处理 pending functors 而不读 `eventfd`，fd 会一直保持可读，后续 `epoll_wait()` 会反复返回，造成无意义唤醒。

## 3. queueInLoop 的唤醒流程

在 one loop per thread 模型中，一个连接的状态应该由它所属的 EventLoop 线程修改。其他线程想操作连接时，不应该直接改连接对象，而应该把任务投递给对应 EventLoop。

典型流程可以抽象成：

```text
worker 线程
    生成一个任务 functor
    加锁放入 loop.pendingFunctors
    write(eventfd) 唤醒 loop

EventLoop 线程
    epoll_wait() 因 eventfd 可读返回
    read(eventfd) 消费唤醒事件
    doPendingFunctors()
    在 loop 线程内修改连接状态
```

这就是 `queueInLoop()` 需要唤醒机制的原因：它不仅要把任务放进队列，还要保证正在睡眠的 EventLoop 尽快醒来处理队列。

### 3.1 runInLoop 和 queueInLoop 的区别

| 接口 | 常见语义 | 是否一定唤醒 |
|:---|:---|:---|
| `runInLoop(cb)` | 如果当前就在 loop 线程，直接执行；否则投递 | 跨线程投递时需要唤醒 |
| `queueInLoop(cb)` | 总是放入 pending functors 队列 | 跨线程或正在执行 functor 时通常需要唤醒 |

简化伪代码：

```cpp
void EventLoop::queueInLoop(Functor cb) {
    {
        std::lock_guard<std::mutex> lock(mutex_);
        pendingFunctors_.push_back(std::move(cb));
    }

    if (!isInLoopThread() || callingPendingFunctors_) {
        wakeup();
    }
}

void EventLoop::wakeup() {
    uint64_t one = 1;
    write(wakeupFd_, &one, sizeof(one));
}

void EventLoop::handleRead() {
    uint64_t value = 0;
    read(wakeupFd_, &value, sizeof(value));
}
```

> [!warning] 不要跨线程直接操作连接
> worker 线程处理完业务后，应该把“写响应”“关闭连接”等操作投递回连接所属 EventLoop。
>
> 直接跨线程修改连接对象，容易引入竞态、悬空指针和状态错乱。

## 4. timerfd：把时间事件变成 fd

`timerfd` 可以创建一个定时器文件描述符。定时器到期后，这个 fd 会变成可读，因此可以直接加入 `epoll`。

```c
#include <sys/timerfd.h>

int timerfd_create(int clockid, int flags);

int timerfd_settime(int fd,
                    int flags,
                    const struct itimerspec *new_value,
                    struct itimerspec *old_value);
```

### 4.1 创建 timerfd

常见写法：

```cpp
int timerFd = timerfd_create(CLOCK_MONOTONIC,
                             TFD_NONBLOCK | TFD_CLOEXEC);
```

| 参数 | 常见选择 | 说明 |
|:---|:---|:---|
| `clockid` | `CLOCK_MONOTONIC` | 单调时间，不受系统时间被手动修改影响 |
| `flags` | `TFD_NONBLOCK` | 非阻塞，避免 EventLoop 卡住 |
| `flags` | `TFD_CLOEXEC` | 避免 fd 泄漏到子进程 |

### 4.2 设置一次性和周期定时

`timerfd_settime()` 使用 `itimerspec` 描述定时器：

```c
struct itimerspec {
    struct timespec it_interval;  // 周期；为 0 表示一次性
    struct timespec it_value;     // 第一次到期时间；为 0 表示停止
};
```

| 字段 | 含义 |
|:---|:---|
| `it_value` | 第一次什么时候到期 |
| `it_interval` | 到期后是否按周期重复触发 |

一次性定时器可以把 `it_interval` 设为 0；周期定时器则把 `it_interval` 设为固定间隔。

### 4.3 到期后的 read 语义

定时器到期后，`timerfd` 会变成可读。应用需要读取一个 `uint64_t`：

```cpp
uint64_t expirations = 0;
read(timerFd, &expirations, sizeof(expirations));
```

`expirations` 表示自上次 read 之后累计到期了多少次。如果 EventLoop 忙了一段时间，周期定时器可能已经到期多次，这个值就可能大于 1。

![[图片/3.Linux/13. IO复用/13_7_2.svg|760]]

> [!tip] timerfd 只是触发器
> `timerfd` 负责把“最近一次到期时间”变成 fd 事件。
>
> 多个业务定时任务如何排序、取消、重复调度，通常还需要最小堆、时间轮或 timer queue。连接心跳和超时管理会在 [[13.9 定时器、心跳与连接超时]] 继续展开。

## 5. eventfd / timerfd 与 epoll 集成

从 `epoll` 的视角看，`eventfd`、`timerfd` 和 socket fd 没有本质区别：它们都是可以等待的文件描述符。

典型注册方式：

```cpp
struct epoll_event ev;
ev.events = EPOLLIN;
ev.data.fd = wakeupFd;
epoll_ctl(epfd, EPOLL_CTL_ADD, wakeupFd, &ev);

ev.events = EPOLLIN;
ev.data.fd = timerFd;
epoll_ctl(epfd, EPOLL_CTL_ADD, timerFd, &ev);
```

事件分发时按 fd 或 Channel 找到对应 handler：

```text
epoll_wait() 返回
    |
    |-- listen_fd 可读  -> accept 新连接
    |-- conn_fd 可读    -> recv 数据
    |-- conn_fd 可写    -> flush output buffer
    |-- eventfd 可读    -> 读取 eventfd，执行 pending functors
    |-- timerfd 可读    -> 读取 timerfd，执行 timer callback
```

> [!note] 与 epoll 的关系
> `epoll` 仍然只是通知“这个 fd 可读了”。
>
> 对 `eventfd` 来说，可读表示有人写入了唤醒计数；对 `timerfd` 来说，可读表示定时器到期了。真正的任务执行仍在 EventLoop 回调里完成。

这和 [[13.4 epoll模型|epoll 模型]] 的核心定位一致：`epoll_wait()` 负责发现就绪事件，Reactor / EventLoop 负责把事件分发到正确的处理逻辑。

## 6. 常见工程陷阱

| 问题 | 后果 | 正确做法 |
|:---|:---|:---|
| `eventfd` 可读后不 read | fd 持续可读，EventLoop 反复被唤醒 | 在 wakeup channel 的 read handler 中消费计数 |
| `timerfd` 到期后不 read | 定时事件持续触发，可能造成空转 | read 出 `expirations` 后再执行回调 |
| 使用阻塞 fd | 读写空计数或异常路径可能卡住 EventLoop | 创建时使用 `EFD_NONBLOCK` / `TFD_NONBLOCK` |
| 跨线程直接修改连接 | 竞态、状态错乱、对象生命周期问题 | 通过 `runInLoop()` / `queueInLoop()` 投递回所属 loop |
| 把 `timerfd` 当成完整定时器系统 | 无法管理大量业务定时任务的排序、取消、重复调度 | `timerfd` 配合 timer queue、最小堆或时间轮 |
| 忘记 close fd | fd 泄漏 | 用 RAII 封装 fd 生命周期 |

## 7. 面试问法

| 问题 | 回答要点 |
|:---|:---|
| `eventfd` 解决什么问题？ | 把线程间通知变成 fd 可读事件，用于唤醒阻塞在 `epoll_wait()` 的 EventLoop。 |
| 为什么不用条件变量唤醒 EventLoop？ | EventLoop 正在 `epoll_wait()` 等 fd 事件；`eventfd` 可以加入同一个 epoll 集合，统一事件来源。 |
| `eventfd` 内部是什么模型？ | 内核维护一个 64 位计数器，write 累加，普通 read 读出并清零。 |
| `timerfd` 解决什么问题？ | 把定时器到期变成 fd 可读事件，让定时任务可以纳入 epoll/Reactor。 |
| `timerfd` read 出来的值是什么？ | 自上次 read 后累计到期次数，周期定时器中可能大于 1。 |
| 为什么 `timerfd` 常用 `CLOCK_MONOTONIC`？ | 单调时间不受系统墙上时间调整影响，更适合超时和间隔计时。 |
| `eventfd` / `timerfd` 是异步 I/O 吗？ | 不是。它们只是产生可读事件，具体处理仍由 EventLoop 回调完成。 |
| worker 线程处理完业务如何回写？ | 把写任务投递回连接所属 EventLoop，并通过 `eventfd` 唤醒它。 |

---

## 8. 关键要点

1. `eventfd` 把跨线程通知变成 fd 可读事件，常用于唤醒 EventLoop。
2. `timerfd` 把定时器到期变成 fd 可读事件，常用于把时间事件纳入 `epoll`。
3. `eventfd` 和 `timerfd` 都应该使用非阻塞和 close-on-exec 标志。
4. `eventfd` 普通模式下 read 会读出当前计数并清零。
5. `timerfd` read 出来的 `uint64_t` 表示累计到期次数。
6. `eventfd` / `timerfd` 可读后都必须 read 消费事件，否则可能导致 EventLoop 反复唤醒。
7. 跨线程操作连接时，应通过 `runInLoop()` / `queueInLoop()` 投递回所属 EventLoop。
8. `timerfd` 只是定时触发器，复杂心跳、超时和定时器容器需要额外的数据结构。
