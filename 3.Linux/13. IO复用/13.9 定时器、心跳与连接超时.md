## 1. 为什么 EventLoop 需要定时器

[[13.4 epoll模型|epoll]] 只负责等待 fd 的就绪事件，它不会主动告诉应用：

- 某个连接已经空闲太久
- 某个请求已经处理超时
- 某个客户端心跳已经丢失
- 某批半关闭连接应该被清理
- 某个定时任务应该执行

真实服务器除了 I/O 事件，还需要时间事件。成熟的 [[13.6 Reactor模式与EventLoop|EventLoop]] 通常会同时管理 socket fd、`eventfd`、`timerfd` 和 timer queue。

> [!note] 核心定位
> `timerfd` 负责把“最近一次到期时间”变成 fd 可读事件；timer queue 负责管理大量业务定时任务。
>
> 也就是说，`timerfd` 是唤醒源，timer queue 才是定时器系统的主体。

## 2. timerfd 与 timer queue 的分工

在 [[13.7 eventfd、timerfd与跨线程唤醒|timerfd]] 一节中已经知道，`timerfd` 可以加入 `epoll`，到期后产生可读事件。但一个服务器通常不是只有一个定时任务，而是有成千上万个连接和请求。

常见做法是：

1. timer queue 保存所有业务定时任务。
2. 找出最近一个到期任务的时间。
3. 用 `timerfd_settime()` 把 `timerfd` 设置到最近到期时间。
4. `timerfd` 到期后，EventLoop 读取 `timerfd`，再从 timer queue 中取出所有已到期任务执行。
5. 重新计算下一次最近到期时间，再次设置 `timerfd`。

```text
timer queue 中有很多任务
    |
    |-- 找最近到期时间
    |-- arm timerfd
    |
epoll_wait() 返回 timerfd 可读
    |
    |-- read(timerfd)
    |-- 执行所有已到期任务
    |-- 重新 arm timerfd
```

### 2.1 为什么不为每个连接创建一个 timerfd

每个连接一个 `timerfd` 看起来直观，但通常不是好设计：

| 做法 | 问题 |
|:---|:---|
| 每个连接一个 `timerfd` | fd 数量膨胀，`epoll_ctl()` 成本增加，资源管理复杂 |
| 一个 loop 一个 `timerfd` + timer queue | fd 少，统一排序，便于批量处理到期任务 |

所以 `timerfd` 更适合作为 EventLoop 的“闹钟”，而不是每个业务定时任务各自拥有一个 fd。

## 3. timer queue 的常见数据结构

timer queue 的核心操作通常有三类：

| 操作 | 含义 |
|:---|:---|
| add timer | 添加一个未来到期的任务 |
| cancel / refresh timer | 取消或刷新某个任务的到期时间 |
| get expired timers | 取出当前已经到期的任务 |

常见实现有两类：

| 数据结构 | 适合场景 | 特点 |
|:---|:---|:---|
| 最小堆 | 定时任务数量中等、到期时间分散 | 堆顶就是最近到期任务，插入/删除通常是 `O(log n)` |
| 时间轮 | 海量连接、超时精度不需要特别高 | 插入和推进近似 `O(1)`，实现更复杂，精度受槽位影响 |

### 3.1 最小堆模型

最小堆按到期时间排序：

```text
heap.top() = 最近到期任务
    |
    |-- 用 top.expireTime 设置 timerfd
    |-- timerfd 到期后弹出所有 expireTime <= now 的任务
    |-- 重新用新的 heap.top() 设置 timerfd
```

如果任务被取消，可以使用 lazy cancel：先把 timer 标记为 canceled，等它到堆顶时再丢弃，避免在堆中间删除的复杂度。

### 3.2 时间轮模型

时间轮把未来时间切成固定槽位，例如每 1 秒一个槽。连接有活动时，把它移动到未来的某个槽；指针每秒向前推进，当前槽里的连接如果没有被刷新，就认为超时。

```text
slot 0 -> 当前秒要检查的连接
slot 1 -> 1 秒后检查
slot 2 -> 2 秒后检查
...
```

时间轮适合大量空闲连接超时检查，因为它不要求每个连接都精确到纳秒级。网络服务器里的空闲超时通常只需要秒级或几十秒级精度。

## 4. 连接空闲超时

连接空闲超时解决的是：连接还没关闭，但长时间没有任何有效读写，继续保留会浪费 fd、内存和连接表空间。

常见策略：

```text
连接建立
    |
    |-- 记录 lastActiveTime
每次收到有效数据
    |
    |-- 更新 lastActiveTime
周期性扫描
    |
    |-- now - lastActiveTime > idleTimeout
    |-- 关闭连接
```

可以根据业务区分几种超时：

| 类型 | 触发条件 | 处理方式 |
|:---|:---|:---|
| 空闲连接超时 | 长时间没有读写活动 | 关闭连接，释放 fd |
| 请求超时 | 请求开始后迟迟没有完整响应 | 返回错误或关闭连接 |
| 写超时 | output buffer 长期发不出去 | 关闭慢连接或触发反压 |
| 半关闭清理 | 对端半关闭后长期不完成协议流程 | 定时关闭 |

> [!warning] 不要只依赖 TCP keepalive
> TCP keepalive 是内核级探活，默认周期通常很长，更适合发现底层连接是否还活着。
>
> 应用层空闲超时和请求超时是业务语义，不能完全交给 TCP keepalive。

## 5. 心跳机制

心跳用于在应用层判断对端是否仍然按协议工作。它和 TCP keepalive 不同：

| 机制 | 层次 | 典型目的 | 时间尺度 |
|:---|:---|:---|:---|
| TCP keepalive | 内核 TCP 层 | 判断 TCP 连接是否还可达 | 通常较长 |
| 应用心跳 | 应用协议层 | 判断业务对端是否活跃、是否卡死 | 由业务决定 |

应用心跳常见有两种模型：

| 模型 | 流程 | 适合场景 |
|:---|:---|:---|
| ping / pong | 一端定时发送 ping，对端回复 pong | 长连接网关、RPC、WebSocket |
| 被动刷新 | 只要收到任何有效业务包，就刷新活跃时间 | 业务消息频繁的连接 |

![[图片/3.Linux/13. IO复用/13_9_2.svg|760]]

心跳检测通常不是“丢一次就断开”，而是允许一定容忍度：

```text
每 heartbeatInterval 发送一次 ping
如果连续 missedLimit 次没有收到 pong
    认为连接失活
    投递 closeInLoop()
```

> [!tip] 心跳包也要走协议层
> 心跳不应该只是随便写几个字节。它应该是应用协议里明确的一类消息，否则接收端无法和普通业务数据可靠区分。

## 6. 超时关闭与连接生命周期

一旦定时器判断连接超时，关闭动作仍然要遵守 [[13.8 连接对象生命周期与RAII|连接对象生命周期]] 的规则：

```text
timer callback 判断连接超时
    |
    |-- weak_ptr.lock() 检查连接是否仍存在
    |-- queueInLoop(closeInLoop)
    |-- 在所属 EventLoop 中 disableAll / remove Channel
    |-- 从连接表移除 shared_ptr
    |-- RAII 析构关闭 fd
```

这里有两个重点：

1. 定时器回调不要长期强持有连接对象，否则可能让已关闭连接迟迟不释放。
2. 关闭连接仍应回到所属 EventLoop 线程，避免和 I/O 回调并发修改连接状态。

这也是为什么 timer callback 中经常使用 `weak_ptr`：对象存在就处理，已经释放就忽略。

## 7. 常见工程陷阱

| 问题 | 后果 | 正确做法 |
|:---|:---|:---|
| 为每个连接创建 `timerfd` | fd 数量膨胀，管理复杂 | 一个 EventLoop 一个 `timerfd`，配合 timer queue |
| `timerfd` 到期后只执行一个任务 | 同一时间到期的任务积压 | 取出并执行所有 `expireTime <= now` 的任务 |
| 执行到期任务后不重新 arm `timerfd` | 后续定时任务不再触发 | 根据新的最近到期时间重新设置 `timerfd` |
| 定时器回调强持有连接 | 连接无法及时释放，甚至引用环 | 使用 `weak_ptr` 观察连接对象 |
| 心跳丢一次就断开 | 网络抖动导致误杀连接 | 设置容忍次数或超时时间窗口 |
| 只依赖 TCP keepalive | 业务卡死或协议层失活不能及时发现 | 应用层心跳和业务超时单独设计 |
| 在 EventLoop 中执行大量重任务 | 定时器和 I/O 事件都被拖延 | 到期回调保持短小，重任务交给线程池 |

## 8. 面试问法

| 问题 | 回答要点 |
|:---|:---|
| `timerfd` 和 timer queue 是什么关系？ | `timerfd` 是 epoll 的唤醒源，timer queue 管理大量业务定时任务。 |
| 为什么不每个连接一个 `timerfd`？ | fd 数量和 epoll 管理成本会膨胀，一个 loop 一个 `timerfd` 更清晰。 |
| 最小堆如何管理定时器？ | 堆顶是最近到期任务，用堆顶时间设置 `timerfd`，到期后弹出所有过期任务。 |
| 时间轮适合什么场景？ | 海量连接的空闲超时检查，精度要求不高但需要低成本刷新。 |
| 心跳和 TCP keepalive 有什么区别？ | keepalive 是内核 TCP 探活，应用心跳是业务协议层活性检测。 |
| 连接超时后能直接 `close(fd)` 吗？ | 不建议。应投递回所属 EventLoop，按连接生命周期流程移除 Channel 和连接表。 |
| timer callback 为什么常用 `weak_ptr`？ | 避免回调访问已释放对象，也避免定时器强持有连接导致无法释放。 |
| 定时器回调为什么不能太重？ | EventLoop 线程会被拖住，影响 I/O 事件和后续定时任务。 |

---

## 9. 关键要点

1. `epoll` 不负责业务超时，真实服务器需要 timer queue 管理时间事件。
2. `timerfd` 是一个可被 `epoll` 监听的唤醒源，不适合为每个连接单独创建。
3. 一个 EventLoop 通常维护一个 `timerfd` 和一个 timer queue。
4. 最小堆适合按到期时间排序，时间轮适合海量连接的粗粒度空闲超时。
5. 连接空闲超时通常通过 `lastActiveTime` 或刷新定时器实现。
6. 应用心跳是协议层机制，TCP keepalive 是内核层机制，两者不是一回事。
7. 超时关闭连接仍然要回到所属 EventLoop，并遵守 Channel 移除和 RAII 释放顺序。
8. timer callback 应保持短小，重任务不要阻塞 EventLoop。
