# 13.6.1 回调函数与 Reactor 事件分发

上一篇 [[13.6 Reactor模式与EventLoop]] 已经说明了 Reactor 如何把 [[13.4 epoll模型|epoll]] 的就绪事件分发给 `Channel`。这一节专门补上一个关键问题：`Channel::handleEvent()` 最后为什么能调用到 `TcpConnection::handleRead()`、`Acceptor::handleRead()` 这些对象方法？

答案就是回调。

> [!note] 核心定义
> 在 Reactor 中，回调就是把“某个 I/O 事件发生时应该执行的处理函数”提前注册到 `Channel` 里。等 `epoll_wait()` 返回就绪事件后，`EventLoop` 调用 `Channel::handleEvent()`，再由 `Channel` 触发对应的回调函数。

更通用的回调概念见 [[15.12 回调函数]]。这一节只讨论它在 Linux Reactor 网络库中的具体落地。

---

## 1. 为什么 Reactor 离不开回调

`epoll_wait()` 只回答一个底层问题：

> 哪些 fd 当前就绪？

例如它可能返回：

```text
conn_fd = 8 发生 EPOLLIN
listen_fd = 3 发生 EPOLLIN
conn_fd = 9 发生 EPOLLOUT
```

但它不会回答：

- `fd = 3` 是监听 socket，还是普通连接 socket？
- `EPOLLIN` 到来后应该执行 `accept()`，还是执行 `recv()`？
- 读到的数据应该放进哪个连接对象的 input buffer？
- 连接关闭时应该如何清理 `Channel`、socket 和连接对象？

这些都不是 `epoll` 的职责，而是 Reactor 的职责。

可以这样分层理解：

```text
epoll
    只负责发现 fd 就绪

EventLoop
    负责等待事件、取出活跃 Channel、逐个分发

Channel
    负责保存 fd、关心的事件、实际发生的事件、对应回调

TcpConnection / Acceptor
    负责真正的 accept / read / write / close 逻辑
```

所以 Reactor 需要回调，是因为它要把“底层 fd 就绪”转换成“上层对象方法被调用”。

> [!tip] 一句话记忆
> `epoll` 看到的是 fd，Reactor 需要找到的是对象和行为；回调就是把行为提前保存起来。

---

## 2. 回调在 Reactor 中到底保存了什么

在 [[15.12 回调函数]] 中，回调的核心思想是：

> 调用方提供行为，框架或库决定调用时机。

放到 Reactor 中，对应关系就是：

| 通用回调概念 | Reactor 中的对应物 |
|:---|:---|
| 调用方提供行为 | `Acceptor` / `TcpConnection` 提供处理函数 |
| 框架保存回调 | `Channel` 保存 `readCallback_` 等成员 |
| 框架决定时机 | `EventLoop` 在 fd 就绪后触发 |
| 回调真正执行 | 进入 `handleRead()` / `handleWrite()` / `handleClose()` |

例如连接对象可能会把自己的读事件处理函数注册给 `Channel`：

```cpp
channel_->setReadCallback([this] {
    handleRead();
});
```

这段代码的含义不是“现在立刻读取数据”，而是：

```text
以后这个 Channel 发生可读事件时，调用当前 TcpConnection 对象的 handleRead()
```

所以回调在 Reactor 中保存的不是“事件结果”，而是“事件发生后要执行的动作”。

## 3. Channel：fd 与回调的绑定点

`Channel` 可以理解成 Reactor 里非常关键的一层绑定关系：

```text
一个 fd
    + 这个 fd 关心哪些事件
    + 这个 fd 本轮实际发生了哪些事件
    + 每种事件对应的处理函数
```

教学版结构可以写成：

```cpp
#include <cstdint>
#include <functional>
#include <utility>
#include <sys/epoll.h>

class Channel {
public:
    using EventCallback = std::function<void()>;

    explicit Channel(int fd)
        : fd_(fd) {}

    void setReadCallback(EventCallback cb) {
        readCallback_ = std::move(cb);
    }

    void setWriteCallback(EventCallback cb) {
        writeCallback_ = std::move(cb);
    }

    void setCloseCallback(EventCallback cb) {
        closeCallback_ = std::move(cb);
    }

    void setErrorCallback(EventCallback cb) {
        errorCallback_ = std::move(cb);
    }

    void setRevents(uint32_t revents) {
        revents_ = revents;
    }

    void handleEvent() {
        if ((revents_ & EPOLLHUP) && !(revents_ & EPOLLIN)) {
            if (closeCallback_) closeCallback_();
        }

        if (revents_ & EPOLLERR) {
            if (errorCallback_) errorCallback_();
        }

        if (revents_ & (EPOLLIN | EPOLLPRI | EPOLLRDHUP)) {
            if (readCallback_) readCallback_();
        }

        if (revents_ & EPOLLOUT) {
            if (writeCallback_) writeCallback_();
        }
    }

private:
    int fd_ = -1;
    uint32_t events_ = 0;
    uint32_t revents_ = 0;

    EventCallback readCallback_;
    EventCallback writeCallback_;
    EventCallback closeCallback_;
    EventCallback errorCallback_;
};
```

这里最关键的类型是：

```cpp
using EventCallback = std::function<void()>;
```

`std::function<void()>` 可以保存普通函数、lambda、仿函数、绑定后的成员函数等可调用对象。它比传统函数指针更适合现代 C++ 网络库，因为事件处理函数通常需要绑定对象状态。

更基础的函数指针回调可以回看 [[9.1.5 函数指针]]；lambda 写法可以回看 [[15.4 lambda]]。

### 3.1 handleEvent() 的四个分支为什么是这个顺序

上面那段 `handleEvent()` 有三处容易被写错。都不是语法问题，编译器一个字都不会说，但在生产环境里会表现成偶发丢数据。

**第一处：`EPOLLHUP` 必须配合 `!(revents_ & EPOLLIN)`。**

`EPOLLHUP` 表示连接两端都挂断了，但内核上报 `EPOLLHUP` 时，接收缓冲区里可能还留着对端关闭前发来的数据。如果只看 `EPOLLHUP` 就走 `closeCallback_()`，这批数据会连同连接一起被丢掉——表现出来就是“客户端明明发了最后一个请求，服务端偶尔收不到”。

加上 `!(revents_ & EPOLLIN)` 之后，只要还有数据可读，本轮就先走读路径，等下一轮读到 `read()` 返回 0 再关。

**第二处：`EPOLLRDHUP` 要和 `EPOLLIN` 走同一个分支。**

`EPOLLRDHUP` 表示对端关闭了写端（`shutdown(SHUT_WR)` 或进程退出）。它需要在 `events_` 里主动注册才收得到；不注册的话，半关闭只能靠 `read()` 返回 0 发现。把它归到读分支，是因为收到它之后要做的事和普通可读一样：继续 `read()`，直到返回 0 再判定对端关闭。

**第三处：分支之间不能写 `else`。**

`revents_` 是 bit mask 不是枚举。一个 fd 在同一轮里既可读又可写完全正常（对端发来请求的同时，本端 output buffer 刚好腾出空间）。写成 `else if` 会漏掉后面那个事件，而漏掉的 `EPOLLOUT` 意味着积压的响应再也发不出去。

## 4. EventLoop 如何触发回调

`EventLoop` 本身通常不直接知道 `TcpConnection` 的内部细节。它只拿到一批活跃 `Channel`，然后逐个调用：

```cpp
void EventLoop::loop() {
    while (!quit_) {
        activeChannels_ = poller_->poll(timeoutMs);

        for (Channel* channel : activeChannels_) {
            channel->handleEvent();
        }

        doPendingFunctors();
    }
}
```

底层 `EpollPoller` 大致做的是：

```cpp
int n = epoll_wait(epollfd_, events_.data(), events_.size(), timeoutMs);

for (int i = 0; i < n; ++i) {
    auto* channel = static_cast<Channel*>(events_[i].data.ptr);
    channel->setRevents(events_[i].events);
    activeChannels.push_back(channel);
}
```

注册与触发发生在完全不同的时刻，这一点从代码上看不出来——注册那行 lambda 和触发它的 `handleEvent()` 隔着一整个事件循环。把两段时间画在一起：

```mermaid
sequenceDiagram
    participant App as TcpConnection
    participant Ch as Channel
    participant Loop as EventLoop 线程
    participant K as 内核 epoll

    Note over App,K: 注册期：连接建立时走一遍
    App->>Ch: setReadCallback([this]{ handleRead() })
    Ch->>Ch: readCallback_ = 这个闭包
    Ch->>K: epoll_ctl(ADD, fd, data.ptr = this)

    Note over App,K: 运行期：此后每一轮
    Loop->>K: epoll_wait(timeout)
    activate Loop
    Note over Loop: 阻塞，让出 CPU
    K-->>Loop: 返回 n 个就绪 event
    deactivate Loop
    Loop->>Ch: setRevents(ev.events)
    Loop->>Ch: handleEvent()
    Ch->>App: readCallback_()
    App->>App: recv() 到 input buffer
    App-->>Ch: 返回
    Ch-->>Loop: 返回，处理下一个 Channel
```

这张图要点出的是代码里看不见的两件事：一是 lambda 写下的位置和它被调用的位置隔了一整轮 `epoll_wait()`，中间线程一直在睡；二是 `readCallback_()` 是同步调用的，`recv()` 没跑完，`handleEvent()` 就不会返回，`EventLoop` 也轮不到下一个 `Channel`。**一个慢回调会拖住整条 loop 上的所有连接**，这也是 one loop per thread 里“回调里不能做阻塞操作”的由来。

> [!warning] epoll 不是异步 I/O 完成通知
> `epoll_wait()` 返回 `EPOLLIN` 只表示“现在读大概率不会阻塞”，不是说数据已经自动读进用户缓冲区。真正的 `read()` / `recv()` 仍然发生在 `readCallback_` 触发后的处理函数里。

## 5. 为什么不用 map 统一保存所有事件回调

初学回调时，可以把它理解成：

```text
事件类型 -> 处理函数
```

用代码表达就是：

```cpp
#include <functional>
#include <iostream>
#include <map>
#include <string>

using Callback = std::function<void()>;

int main() {
    std::map<std::string, Callback> callbacks;

    callbacks["read"] = [] {
        std::cout << "处理读事件\n";
    };

    callbacks["write"] = [] {
        std::cout << "处理写事件\n";
    };

    std::string event = "read";

    if (callbacks.contains(event)) {
        callbacks[event]();
    }
}
```

这个模型适合帮助理解回调：

```text
注册阶段：保存事件和函数的对应关系
触发阶段：根据事件找到函数并调用
```

但 Reactor 的 `Channel` 通常不需要真的用 `map` 保存这些固定回调，原因有两个。

第一，事件种类固定且数量很少：

```text
readCallback_
writeCallback_
closeCallback_
errorCallback_
```

直接用成员变量更清晰。

第二，`EPOLLIN`、`EPOLLOUT`、`EPOLLERR` 这类事件不是互斥枚举，而是 bit mask。一个 fd 一轮可能同时发生多个事件：

```cpp
revents_ = EPOLLIN | EPOLLOUT;
```

这时不是“从 map 里选一个 key”，而是分别判断多个 bit：

```cpp
if (revents_ & EPOLLIN) {
    readCallback_();
}

if (revents_ & EPOLLOUT) {
    writeCallback_();
}
```

所以更准确的说法是：

> [!note]
> `map<事件类型, 回调>` 是理解回调注册的好模型；但在 Reactor 的 `Channel` 中，更常见的是“固定回调成员变量 + bit mask 判断”。

## 6. lambda 如何绑定成员函数

普通成员函数不能直接当作普通函数指针，因为它隐含一个 `this` 参数。成员函数回调必须同时绑定：

```text
哪个对象
哪个成员函数
```

现代 C++ 中最直观的写法是 lambda。

例如监听 socket 对应的 `Channel` 可以绑定到 `Acceptor`：

```cpp
class Acceptor {
public:
    Acceptor(EventLoop* loop, int listenFd)
        : loop_(loop), acceptChannel_(listenFd) {
        acceptChannel_.setReadCallback([this] {
            handleRead();
        });
    }

private:
    void handleRead() {
        // accept4() 新连接，并分发给某个 EventLoop
    }

    EventLoop* loop_ = nullptr;
    Channel acceptChannel_;
};
```

普通连接 socket 对应的 `Channel` 可以绑定到 `TcpConnection`：

```cpp
class TcpConnection {
public:
    TcpConnection(EventLoop* loop, int connFd)
        : loop_(loop), channel_(connFd) {
        channel_.setReadCallback([this] {
            handleRead();
        });

        channel_.setWriteCallback([this] {
            handleWrite();
        });

        channel_.setCloseCallback([this] {
            handleClose();
        });
    }

private:
    void handleRead() {
        // recv() 到 input buffer，再交给协议解析层
    }

    void handleWrite() {
        // 继续发送 output buffer 中未发送完的数据
    }

    void handleClose() {
        // 从 epoll 删除 Channel，并按顺序释放连接资源
    }

    EventLoop* loop_ = nullptr;
    Channel channel_;
};
```

也可以用 `std::bind`：

```cpp
using namespace std::placeholders;

channel_.setReadCallback(std::bind(&TcpConnection::handleRead, this));
```

不过在现代 C++ 中，lambda 通常更直观，也更容易看出捕获了哪些对象。

## 7. listen_fd 与 conn_fd 的回调差异

Reactor 中不同 fd 的“可读事件”含义不同。

| fd 类型 | 可读事件含义 | 常见回调 |
|:---|:---|:---|
| `listen_fd` | 有新连接可以 `accept()` | `Acceptor::handleRead()` |
| `conn_fd` | 对端发来数据，或连接关闭 | `TcpConnection::handleRead()` |

监听 socket 的读回调通常负责接收新连接：

```text
listen_fd 发生 EPOLLIN
    ↓
acceptChannel_.handleEvent()
    ↓
readCallback_()
    ↓
Acceptor::handleRead()
    ↓
accept4() 得到 conn_fd
    ↓
创建 TcpConnection / Channel
```

普通连接 socket 的读回调通常负责读取数据：

```text
conn_fd 发生 EPOLLIN
    ↓
connectionChannel.handleEvent()
    ↓
readCallback_()
    ↓
TcpConnection::handleRead()
    ↓
recv() 到 input buffer
    ↓
协议解析与业务处理
```

写事件也类似，但要特别注意：`EPOLLOUT` 通常不是长期监听，而是在 output buffer 有剩余数据时才打开。这个点在 [[13.6 Reactor模式与EventLoop#5.3 write 路径]] 中已经展开过。

## 8. 生命周期陷阱：this 捕获与 data.ptr

回调让代码变得灵活，但也引入了对象生命周期问题。

最典型的风险是 lambda 捕获 `this`：

```cpp
channel_.setReadCallback([this] {
    handleRead();
});
```

这段代码要求：

```text
只要 readCallback_ 还可能被调用，this 指向的对象就必须仍然存活
```

如果 `TcpConnection` 已经析构，但 `Channel` 仍然留在 `epoll` 中，后面 `epoll_wait()` 又返回该 fd 的事件，就可能出现：

```text
epoll_event.data.ptr 指向已释放对象
    ↓
EventLoop 找回悬空 Channel 指针
    ↓
Channel::handleEvent()
    ↓
readCallback_ 捕获的 this 已经失效
    ↓
未定义行为
```

因此连接关闭路径必须明确：

1. 先从 `epoll` 中删除或禁用对应 `Channel`。
2. 防止后续事件再次触发已关闭 fd。
3. 再按顺序释放 `TcpConnection`、socket RAII 对象和 `Channel`。
4. 如果涉及跨线程销毁，要投递回连接所属的 `EventLoop` 处理。

> [!warning] 生命周期比语法更重要
> `std::function` 和 lambda 解决的是“如何保存可调用对象”的问题，不自动解决“被捕获对象是否还活着”的问题。

### 8.1 更隐蔽的一种：回调在自己的栈帧里把自己拆了

上面说的是“对象先死、事件后到”，靠关闭顺序能解决。还有一种更难查的：**对象是在 `handleEvent()` 执行到一半时死的**。

`closeCallback_` 一路调到 `TcpServer::removeConnection()`，那里会执行 `connections_.erase(name)`。如果这个 map 持有的就是最后一个 `shared_ptr<TcpConnection>`，引用计数当场归零，`~TcpConnection()` 连带 `~Channel()` 一起跑完——**而此时调用栈还停在 `Channel::handleEvent()` 里面**。回到 `handleEvent()` 后面几个分支时，`revents_`、`readCallback_` 读的都已经是被释放的内存。

![[图片/3.Linux/13. IO复用/13_6_1_2.svg|900]]

muduo 的解法是给 `Channel` 加一个 `weak_ptr` 成员 `tie_`，在分派之前先把它提升成 `shared_ptr`：

```cpp
class Channel {
public:
    void tie(const std::shared_ptr<void>& obj) {
        tie_ = obj;
        tied_ = true;
    }

    void handleEvent() {
        if (tied_) {
            std::shared_ptr<void> guard = tie_.lock();
            if (!guard) {
                return;             // 对象已经没了，本轮什么都不做
            }
            handleEventWithGuard(); // guard 在整个分派期间都活着
        } else {
            handleEventWithGuard();
        }
    }

private:
    void handleEventWithGuard();    // 真正按 revents_ 分派的那段

    std::weak_ptr<void> tie_;
    bool tied_ = false;
};
```

这段代码有三个点容易看漏：

**为什么用 `weak_ptr` 而不是 `shared_ptr` 成员。** 如果 `Channel` 直接存一个 `shared_ptr<TcpConnection>`，而 `TcpConnection` 又持有 `Channel`，两者互相引用，计数永远降不到 0，连接对象会一直泄漏。`weak_ptr` 不增加计数，只保留“去看看它还在不在”的能力，这正是 [[weak_ptr]] 里打破循环引用的标准用法（《Effective Modern C++》Item 20：对可能悬垂的 `shared_ptr` 使用 `std::weak_ptr`）。

**`guard` 起的是延寿作用，不是保护作用。** `lock()` 成功后引用计数从 1 变成 2，之后 `connections_.erase()` 只是把计数打回 1，析构不会发生。真正的析构点被推迟到 `guard` 离开作用域——那时 `handleEventWithGuard()` 已经返回，`handleEvent()` 也不再碰任何成员。

**`guard` 的作用域必须包住整个分派过程。** 只把 `guard` 套在 `closeCallback_()` 那一句上是没用的，因为后面的 `readCallback_()` 分支同样会读 `revents_`。这也是 muduo 把分派逻辑单独拆成 `handleEventWithGuard()` 的原因：让作用域边界和函数边界对齐，不容易写漏。

`tie()` 需要在连接真正建立、`shared_ptr` 已经存在之后调用：

```cpp
void TcpConnection::connectEstablished() {
    channel_->tie(shared_from_this());   // 此时 this 已被 shared_ptr 管理
    channel_->enableReading();
    connectionCallback_(shared_from_this());
}
```

`shared_from_this()` 要求 `TcpConnection` 继承 `std::enable_shared_from_this<TcpConnection>`，并且对象确实是通过 `shared_ptr` 创建的。在构造函数里调用 `shared_from_this()` 会抛 `std::bad_weak_ptr`——那时控制块还没建立。

### 8.2 另一个相关陷阱：在 handleEvent 期间删别的 Channel

`EventLoop` 是先把活跃 `Channel*` 收进 `activeChannels_`，再遍历这个容器逐个 `handleEvent()`。如果某个回调里顺手关掉了另一条连接，被删的那个 `Channel*` 还留在 `activeChannels_` 里，轮到它时就是悬空指针。

muduo 用一个 `eventHandling_` 标志把这段区间标出来，`removeChannel()` 发现自己处在遍历期间时，会断言只允许删当前正在处理的那个 `Channel`。工程上更通用的做法是：**关闭动作一律 `queueInLoop()` 延后到 `doPendingFunctors()` 阶段执行**，那时遍历已经结束。这条路径和 [[13.7 eventfd、timerfd与跨线程唤醒]] 里的任务投递是同一套机制。

这部分可以继续和 [[13.8 连接对象生命周期与RAII]] 一起理解。

## 9. 和 C 回调接口的关系

C 风格回调通常长这样：

```cpp
using CCallback = void (*)(int fd, void* userData);

void registerCallback(CCallback cb, void* userData);
```

这种接口只能保存普通函数指针，所以需要通过 `void* userData` 额外传递对象地址。回调触发后，再把 `void*` 转回 C++ 对象指针：

```cpp
void onReadable(int fd, void* userData) {
    auto* conn = static_cast<TcpConnection*>(userData);
    conn->handleRead();
}
```

Modern C++ Reactor 更常见的是：

```cpp
using EventCallback = std::function<void()>;

channel.setReadCallback([this] {
    handleRead();
});
```

两者表面写法不同，本质一样：

```text
提前注册处理逻辑
    ↓
事件源在合适时机触发
    ↓
框架反过来调用用户逻辑
```

区别在于：

| 方式 | 保存什么 | 适合场景 |
|:---|:---|:---|
| 函数指针 + `void*` | 函数地址 + 用户上下文 | C API、系统接口、跨语言接口 |
| `std::function` + lambda | 任意可调用对象 | Modern C++ 网络库、业务回调 |

如果底层接口只接受 C 函数指针和 `void*`，可以参考 [[3.1 C回调接口与C++对象]] 中的 static 桥接模式。

## 10. std::function 的代价，以及虚函数这条路

`std::function` 用起来舒服，但它不是零成本抽象。做网络库时至少要知道它贵在哪，以及为什么老一辈的 Reactor 框架不用它。

### 10.1 三项开销

**堆分配。** `std::function` 内部有一块小对象缓冲（small object optimization），捕获的东西够小就存在栈上。标准没有规定这块缓冲多大，libstdc++ 是 16 字节。只捕获一个 `this` 指针（8 字节）通常能放下；捕获 `shared_ptr` 加几个参数就会溢出到堆。**回调注册在连接建立时只做一次，这点分配可以接受；但如果在每次读事件里临时构造 `std::function`，那就是每个请求一次 malloc。**

**间接调用。** 类型擦除意味着调用要经过一层虚函数式的跳转，编译器几乎不可能内联。相比之下，模板参数形式的回调（`template <class F> void setReadCallback(F&& f)`）能内联，但代价是 `Channel` 得跟着变成模板，整个类型体系会被污染。

**拷贝成本。** `std::function` 是值语义，拷贝时会连同捕获的东西一起拷。所以 setter 应该写成 `void setReadCallback(EventCallback cb) { readCallback_ = std::move(cb); }`——按值收再 `std::move` 进成员，调用方传右值时就只有一次移动。这也是《Effective Modern C++》Item 41 讲的“可拷贝形参用按值传递 + move”。

### 10.2 为什么不用虚函数

ACE 那一代的 Reactor 是靠继承做的：定义一个 `Event_Handler` 抽象基类，用户继承它并重写 `handle_input()` / `handle_output()`：

```cpp
class EventHandler {
public:
    virtual ~EventHandler() = default;
    virtual void handleInput(int fd)  {}
    virtual void handleOutput(int fd) {}
    virtual void handleClose(int fd)  {}
};
```

这条路的性能更好（一次虚调用，无堆分配），但有两个结构性问题：

**一是强制继承。** 想让某个已有的类接收 I/O 事件，就得改它的继承关系。业务类被迫和框架基类耦合，一个类还只能有一个 `handle_input()`——如果它同时管着两个 fd，就没法给两个 fd 写不同的处理逻辑。

**二是四个虚函数绑成一组。** 只关心读事件时，写、关闭、错误三个也得跟着继承下来。而 `std::function` 是四个独立成员，谁不设置就不触发。

《Effective C++》Item 35（考虑 virtual 函数以外的其他选择）讲的正是这个取舍：用 `std::function` 实现“策略模式”，把行为从类型体系里解耦出来。muduo 选 `std::function` 是因为在网络库这个场景下，**一次间接调用的开销远小于一次 `recv()` 系统调用**，而灵活性带来的收益是实打实的。

| | 虚函数 Handler | `std::function` 成员 |
|:---|:---|:---|
| 调用开销 | 一次虚调用 | 类型擦除跳转，可能有堆分配 |
| 耦合 | 业务类必须继承框架基类 | 无继承要求，lambda 即可 |
| 粒度 | 四个虚函数绑成一组 | 每种事件独立设置 |
| 同一对象管多个 fd | 做不到（只有一份虚表） | 可以，每个 Channel 一组回调 |
| 代表框架 | ACE | muduo、libevent 的 C++ 封装 |

## 11. 面试问法

| 问题 | 回答要点 |
|:---|:---|
| Reactor 为什么需要回调？ | `epoll` 只发现 fd 就绪，Reactor 需要把事件分发给对应对象和处理函数。 |
| `Channel` 通常保存什么？ | fd、关注事件 `events_`、实际事件 `revents_`、读写关闭错误回调。 |
| `EventLoop` 如何触发回调？ | `epoll_wait()` 返回后得到 active `Channel`，遍历调用 `Channel::handleEvent()`。 |
| `epoll_event.data.ptr` 常放什么？ | 常放 `Channel*` 或连接相关对象指针，用于从就绪事件找回上层对象。 |
| 为什么成员函数不能直接当普通函数指针？ | 非静态成员函数隐含 `this`，必须绑定具体对象。 |
| lambda 捕获 `this` 有什么风险？ | 回调执行时对象可能已析构，导致悬空指针和未定义行为。 |
| 为什么不用 `map` 保存所有回调？ | `EPOLLIN` 等事件是 bit mask，多个事件可同时发生；固定成员变量更直接。 |
| `std::function` 的优缺点是什么？ | 优点是统一保存各种可调用对象；缺点是类型擦除有一定开销，且不管理被捕获对象生命周期。 |
| `handleEvent()` 里 `EPOLLHUP` 为什么要判 `!EPOLLIN`？ | 上报 HUP 时接收缓冲区可能还有数据，直接走关闭会丢掉对端最后发的那批。 |
| `EPOLLRDHUP` 和 `EPOLLHUP` 差在哪？ | RDHUP 是对端关了写端（半关闭），要主动注册；HUP 是两端都断，内核总会报。 |
| 回调里销毁了自己会怎样？ | `handleEvent()` 的栈帧还在，后续分支读 `revents_` 就是 use-after-free。 |
| muduo 的 `tie_` 解决什么问题？ | 分派前把 `weak_ptr` 提升成 `shared_ptr`，把本轮的析构推迟到栈帧退出之后。 |
| `tie_` 为什么是 `weak_ptr` 不是 `shared_ptr`？ | `Channel` 和 `TcpConnection` 互相持有会形成循环引用，计数永远降不到 0。 |
| 为什么不用虚函数基类做 Handler？ | 强制业务类继承框架基类，四个虚函数绑成一组，且一个对象管不了多个 fd。 |
| 回调里能不能做阻塞操作？ | 不能。`handleEvent()` 是同步调用，一个慢回调会拖住同一条 loop 上所有连接。 |

## 12. 关键要点

1. 回调的核心是：把可调用对象提前交给框架，由框架决定调用时机。
2. `epoll` 负责发现 fd 就绪，不负责理解业务对象和处理逻辑。
3. `EventLoop` 负责等待事件并遍历活跃 `Channel`。
4. `Channel` 是 fd、事件 bit 和回调函数的绑定点。
5. `std::function<void()>` 常用于统一保存读、写、关闭、错误回调。
6. Reactor 中的 `EPOLLIN`、`EPOLLOUT`、`EPOLLERR` 是 bit mask，一轮可能触发多个回调；分支之间不能写 `else`。
7. `EPOLLHUP` 分支必须配合 `!(revents_ & EPOLLIN)`，否则会丢掉对端关闭前的最后一批数据。
8. 回调是同步调用的，`handleEvent()` 没返回，`EventLoop` 就轮不到下一个 `Channel`。
9. lambda 绑定成员函数时要特别注意 `this` 和被捕获对象的生命周期。
10. 对象可能在 `handleEvent()` 执行到一半时被自己的回调销毁，靠 `weak_ptr` 守卫（muduo 的 `tie_`）把析构推迟到栈帧退出之后。
11. `std::function` 不是零成本：类型擦除阻止内联，捕获超过小对象缓冲会触发堆分配；注册期分配一次可接受，每请求分配一次不行。
12. C 风格回调和 Modern C++ 回调写法不同，但本质都是“注册处理逻辑，等待框架反向调用”。
