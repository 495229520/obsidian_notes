# epoll 模型详解

## 简介

[[13.4 epoll模型]] 已经覆盖了 epoll 的基本 API、LT/ET 和示例代码。这篇笔记专门补面试和工程追问：错误事件怎么处理、ET 为什么必须非阻塞、`EPOLLONESHOT` 怎么配合线程池、惊群是什么、`accept4()` 有什么用。

---

## epoll 的三个核心对象

从工程视角看，epoll 服务器里通常有三类对象：

| 对象 | 作用 |
|:---|:---|
| `epoll_fd` | 内核中的事件表 |
| `listen_fd` | 监听新连接 |
| `conn_fd` | 已建立连接的数据收发 |

核心流程：

```text
socket/bind/listen
   |
listen_fd 加入 epoll
   |
epoll_wait()
   |
listen_fd 可读 -> accept 新连接
conn_fd 可读   -> read/recv
conn_fd 可写   -> send 未发送完的数据
异常事件       -> 清理连接
```

---

## LT 和 ET 的本质区别

| 模式 | 触发条件 | 编程要求 |
|:---|:---|:---|
| LT 水平触发 | 只要 fd 仍然可读/可写，就会反复通知 | 可以一次只处理一部分 |
| ET 边缘触发 | fd 状态发生变化时通知一次 | 必须非阻塞并循环处理到 `EAGAIN` |

ET 模式常见模板：

```cpp
while (true) {
    ssize_t n = recv(fd, buf, sizeof(buf), 0);
    if (n > 0) {
        // 处理数据
    } else if (n == 0) {
        close(fd);
        break;
    } else if (errno == EAGAIN || errno == EWOULDBLOCK) {
        break;  // 已经读空
    } else if (errno == EINTR) {
        continue;
    } else {
        close(fd);
        break;
    }
}
```

如果 ET 模式只读一次，缓冲区里剩下的数据可能不会再触发事件，这是高频面试点。

## 错误事件处理

epoll 返回事件时，不应该只判断 `EPOLLIN` 和 `EPOLLOUT`。真实服务至少要处理：

| 事件 | 含义 | 建议处理 |
|:---|:---|:---|
| `EPOLLERR` | fd 发生错误 | 用 `getsockopt(SO_ERROR)` 取错误，关闭连接 |
| `EPOLLHUP` | 对端挂断 | 关闭连接 |
| `EPOLLRDHUP` | 对端关闭写方向 | 读完剩余数据后关闭或进入半关闭逻辑 |

示例：

```cpp
if (ev.events & (EPOLLERR | EPOLLHUP | EPOLLRDHUP)) {
    int err = 0;
    socklen_t len = sizeof(err);
    getsockopt(fd, SOL_SOCKET, SO_ERROR, &err, &len);
    epoll_ctl(epfd, EPOLL_CTL_DEL, fd, nullptr);
    close(fd);
    continue;
}
```

## EPOLLONESHOT

多线程 epoll 服务器中，如果多个线程都可能处理同一个 fd，可能出现同一连接被并发处理的问题。

`EPOLLONESHOT` 的语义是：事件触发一次后，这个 fd 会从活跃通知中临时失效，必须重新 `epoll_ctl(..., EPOLL_CTL_MOD, ...)` 才会继续触发。

典型流程：

```text
fd 触发 EPOLLIN
   |
事件线程把任务交给 worker
   |
worker 读写并更新连接状态
   |
worker 重新 MOD 注册 EPOLLONESHOT
```

核心代码形态：

```cpp
event.events = EPOLLIN | EPOLLET | EPOLLONESHOT | EPOLLRDHUP;
epoll_ctl(epfd, EPOLL_CTL_MOD, fd, &event);
```

它适合和 [[12.7 条件变量与线程池|线程池]] 配合，但会增加状态管理复杂度。

## 惊群问题

惊群指多个进程或线程同时等待同一个事件，但最终只有一个能处理，其他都被无意义唤醒。

常见场景：

- 多进程都阻塞在同一个监听 socket 的 `accept()`
- 多个 epoll 实例同时监听同一个 `listen_fd`
- 高并发下大量线程被唤醒争抢同一资源

缓解方式：

- 使用单独 Acceptor 线程负责 `accept()`
- 使用 `SO_REUSEPORT` 让多个监听 socket 分摊连接
- 新内核中使用 `EPOLLEXCLUSIVE` 降低监听 socket 的惊群
- 不让多个 worker 同时处理同一个连接，必要时使用 `EPOLLONESHOT`

---

## accept4

`accept4()` 可以在接受连接时直接设置 `SOCK_NONBLOCK` 和 `SOCK_CLOEXEC`，避免先 `accept()` 再 `fcntl()` 的竞态和额外系统调用。

```cpp
int connfd = accept4(listenfd, nullptr, nullptr,
                     SOCK_NONBLOCK | SOCK_CLOEXEC);
```

优势：

- 新连接一创建就是非阻塞
- 避免多线程程序中 fd 被子进程继承
- 少一次或多次 `fcntl()` 调用

---

## EPOLLOUT 不要常驻

大多数 TCP socket 在正常情况下都是可写的。如果一直监听 `EPOLLOUT`，事件循环会频繁被唤醒。

常见策略：

1. 默认只关注 `EPOLLIN`
2. 发送缓冲区有剩余数据没发完时，临时关注 `EPOLLOUT`
3. 输出缓冲区清空后，取消 `EPOLLOUT`

这和 [[8.12 非阻塞connect与健壮收发#健壮发送：处理短写|非阻塞短写处理]] 是同一套工程模型。

---

## 关闭连接的顺序

epoll 服务器里关闭 fd 时，建议顺序是：

```text
从连接表删除
   |
epoll_ctl(DEL)
   |
close(fd)
   |
释放连接对象
```

如果先释放连接对象，而 epoll 事件里还保存着指针，就可能出现悬空指针。很多 C++ 网络库会在 `epoll_event.data.ptr` 中保存连接对象地址，因此生命周期要格外清楚。

## 服务端架构模型

### Reactor

Reactor 的思想是：事件循环等待 IO 就绪，然后分发给对应 handler。

```text
EventLoop
   |
epoll_wait
   |
Channel / Handler
   |
read / write / accept
```

Nginx、Redis、muduo 都可以用 Reactor 思想理解。

### Proactor

Proactor 的思想是：异步操作完成后通知应用。Linux 传统 epoll 更接近 Reactor；真正的 Proactor 更接近 IOCP 或 io_uring 的完成事件模型。

面试里可以这样回答：epoll 通知“可以读写”，应用自己读写；Proactor 通知“读写已经完成”。

### one loop per thread

高性能 C++ 网络库常见结构：

```text
main loop
   |
Acceptor 接受新连接
   |
按轮询分发给 sub loop
   |
每个 sub loop 在线程内管理一批连接
   |
耗时任务交给 worker pool
```

它避免多个线程同时操作同一个连接，降低锁复杂度。

## 定时器与心跳

epoll 本身只负责 fd 事件，不负责业务超时。真实服务通常还需要：

- 连接空闲超时
- 请求超时
- 心跳超时
- 定时清理半关闭连接

常见实现：

- `timerfd` 加入 epoll
- 最小堆管理定时器
- 时间轮管理大量连接超时

TCP keepalive 是内核级探活，默认周期通常很长；应用心跳是业务级保活，能更快发现逻辑层断连。两者不是一回事。

---

## 面试问法

| 问题 | 回答要点 |
|:---|:---|
| ET 为什么必须非阻塞 | 阻塞读写可能卡死事件循环，且必须读到 `EAGAIN` |
| `EPOLLERR` 怎么处理 | 查 `SO_ERROR`，清理连接 |
| `EPOLLONESHOT` 解决什么 | 防止同一 fd 被多个线程同时处理 |
| 惊群是什么 | 多个等待者被唤醒争抢同一事件 |
| 为什么不要常驻 `EPOLLOUT` | 大多数时间 fd 可写，会导致忙通知 |
| epoll 是 Reactor 还是 Proactor | 更接近 Reactor，通知就绪而非完成 |

---

## 关键要点

1. **ET 模式必须使用非阻塞 fd，并循环读写到 `EAGAIN`**。
2. **错误事件要统一处理，不能只看 `EPOLLIN`**。
3. **`EPOLLONESHOT` 常用于多线程防止同一连接并发处理**。
4. **`EPOLLOUT` 应该按需注册，输出缓冲区清空后取消**。
5. **epoll 服务器还需要定时器、心跳、连接生命周期管理**。
