# 从 fork 到 epoll：用一个聊天室服务器串起进程、线程与 IO 复用

> 这三章不要分开背。  
> 它们其实都在回答一个问题：  
> **当一个客户端因为 I/O 阻塞时，服务器还能不能继续服务其他客户端？**

我们用一个生产案例串起来：

> 你要写一个在线聊天室 / IM 长连接网关。  
> 用户 A、B、C 都连上服务器。服务器要接收消息、广播消息、维护在线用户列表、写日志。  
> 现在问题来了：如果 A 连上后一直不发消息，B 和 C 还能不能被服务？

这就是 [11. 进程](app://localhost/epitaxy/3.Linux/11.%20%E8%BF%9B%E7%A8%8B)、[12. 线程](app://localhost/epitaxy/3.Linux/12.%20%E7%BA%BF%E7%A8%8B)、[13. IO复用](app://localhost/epitaxy/3.Linux/13.%20IO%E5%A4%8D%E7%94%A8) 要解决的主线。

---

## 0. 总主线：三章知识在工程里的位置

|知识|解决什么问题|生产类比|
|---|---|---|
|进程|隔离、独立执行|一个客户一个分公司，安全但贵|
|IPC|进程之间协作|分公司之间用电话、文件、共享仓库沟通|
|线程|更轻量的并发|一个办公室多个员工，共享资源但容易抢|
|锁/同步|保护共享资源|多个员工改同一张在线用户表，需要排队|
|IO 复用|一个线程等待多个 fd|前台同时盯很多电话，谁响接谁|
|epoll|高效等待大量连接|电话响了自动通知前台，不用挨个问|

一句话：

> **多进程解决“一个连接卡住全局”；多线程降低并发成本；IO 复用解决“大量连接都在等”的问题。**

# 1. 第一版：单进程阻塞服务器

对应笔记：[13.1 IO复用简介](app://localhost/epitaxy/3.Linux/13.%20IO%E5%A4%8D%E7%94%A8/13.1%20IO%E5%A4%8D%E7%94%A8%E7%AE%80%E4%BB%8B.md)

最朴素的聊天室服务器大概是：

```text
accept()
read(client_fd)
write(client_fd)
```

看起来没问题，但生产里马上出事。

假设：

```text
client1 连接成功，但一直不发消息
server 阻塞在 read(client1)
client2 也想连接
```

这时服务器主执行流卡在：

```c
read(client1_fd, buf, sizeof(buf));
```

如果 `client1` 不发数据，`read()` 就阻塞。  
于是服务器无法继续处理 `client2`。

注意一个细节：

> `client2` 的 TCP 三次握手可能已经完成，连接可能已经进入 accept 队列。  
> 但你的应用程序没有机会继续 `accept()`，因为它卡在 `read(client1)`。

所以阻塞 IO 的问题不是“慢”，而是：

> **一个 fd 没准备好，整个执行流陪它等。**

### 面试官场景题

**Q：你写了一个单线程 TCP echo server。第一个客户端连上后一直不发数据，第二个客户端还能被处理吗？**

答题要点：

```text
不能及时被应用层处理。

原因是主线程已经阻塞在第一个连接的 read() 上。
第二个客户端的 TCP 连接可能已经进入内核 accept 队列，
但应用层没有机会继续调用 accept()。

解决方向包括：
1. 多进程
2. 多线程
3. 非阻塞 IO
4. IO 复用
```

# 2. 第二版：多进程服务器

对应笔记：[11.1 进程简介](app://localhost/epitaxy/3.Linux/11.%20%E8%BF%9B%E7%A8%8B/11.1%20%E8%BF%9B%E7%A8%8B%E7%AE%80%E4%BB%8B.md)、[11.8 基于多任务的多进程并发服务器](app://localhost/epitaxy/3.Linux/11.%20%E8%BF%9B%E7%A8%8B/11.8%20%E5%9F%BA%E4%BA%8E%E5%A4%9A%E4%BB%BB%E5%8A%A1%E7%9A%84%E5%A4%9A%E8%BF%9B%E7%A8%8B%E5%B9%B6%E5%8F%91%E6%9C%8D%E5%8A%A1%E5%99%A8.md)

既然一个执行流会被卡住，那最自然的想法是：

> 每来一个客户端，我 fork 一个子进程去处理它。  
> 父进程继续 accept 新连接。

模型变成：

```text
父进程：
  accept()
  fork()
  继续 accept()

子进程：
  read/write 当前客户端
  处理完退出
```

这样 `client1` 卡住，只会卡住它对应的子进程。  
父进程还可以继续服务 `client2`、`client3`。

这就是多进程并发服务器的直觉。

---

## 2.1 fork 后最容易考的点：父子进程关闭不同 fd

`fork()` 后，父子进程都会继承文件描述符。

假设服务器有：

```text
listen_fd：监听 socket
conn_fd：刚 accept 出来的已连接 socket
```

fork 后：

|进程|应该保留|应该关闭|原因|
|---|---|---|---|
|父进程|`listen_fd`|`conn_fd`|父进程只负责继续接新客户|
|子进程|`conn_fd`|`listen_fd`|子进程只负责当前客户|

为什么？

因为文件描述符背后有内核对象和引用计数。  
如果父进程不关闭 `conn_fd`，即使子进程退出，连接资源也可能不能及时释放。  
如果子进程不关闭 `listen_fd`，职责混乱，也会造成资源泄漏。

### 面试官场景题

**Q：多进程 TCP 服务器里，accept 后 fork，为什么父进程要 close(conn_fd)，子进程要 close(listen_fd)？**

答：

```text
fork 后父子进程都继承文件描述符。
父进程只负责监听和 accept 新连接，所以应该保留 listen_fd，关闭 conn_fd。
子进程只负责当前客户端，所以应该保留 conn_fd，关闭 listen_fd。

如果不关闭不需要的 fd，会造成资源泄漏，也可能导致连接引用计数不降，
连接关闭行为变得不符合预期。
```

---

## 2.2 多进程的第二个高频考点：僵尸进程

子进程退出后，父进程如果不回收它的退出状态，就会产生僵尸进程。

所以多进程服务器通常要处理 `SIGCHLD`：

```text
子进程退出
    ↓
内核给父进程发送 SIGCHLD
    ↓
父进程 waitpid 回收子进程
```

面试重点：

```c
while (waitpid(-1, &status, WNOHANG) > 0) {
    // 回收所有已退出子进程
}
```

为什么要 `while`？

因为多个子进程可能几乎同时退出，一个 `SIGCHLD` 可能对应多个子进程。

### 面试官场景题

**Q：多进程服务器如何避免僵尸进程？**

答：

```text
父进程需要回收子进程退出状态。
常见做法是注册 SIGCHLD 信号处理函数，
在处理函数中循环调用 waitpid(-1, &status, WNOHANG)。

使用 WNOHANG 是为了避免父进程阻塞；
使用循环是因为一次 SIGCHLD 可能对应多个子进程退出。
```

# 3. IPC：多进程隔离带来的协作成本

对应笔记：[11.2 进程间通信IPC](app://localhost/epitaxy/3.Linux/11.%20%E8%BF%9B%E7%A8%8B/11.2%20%E8%BF%9B%E7%A8%8B%E9%97%B4%E9%80%9A%E4%BF%A1IPC.md)

多进程解决了隔离和并发，但马上引出新问题：

> 每个客户端在不同子进程里。  
> 现在我要维护一个全局在线用户表，还要把 A 的消息广播给 B、C、D。  
> 可是进程之间地址空间隔离，它们看不到彼此的内存。

这时就需要 IPC。

不要死背“管道、消息队列、共享内存、信号量”，你按生产需求记。

|需求|适合方案|原因|
|---|---|---|
|父子进程传简单字节流|管道|简单，天然适合亲缘进程|
|传控制消息、任务|消息队列|消息有边界，可以异步|
|多进程共享大块数据|共享内存|拷贝少，速度快|
|控制谁先读谁先写|信号量|负责同步，不负责传数据|
|跨主机通信|socket|网络通信本身就是 socket|

---

## 3.1 生产案例：日志进程

聊天室里每个 worker 子进程都要写日志。

错误做法：

```text
每个子进程都直接写同一个日志文件
```

问题：

- 日志内容可能交错
- 磁盘 IO 可能拖慢业务进程
- 多进程写同一文件需要额外同步

更工程化的做法：

```text
worker 子进程
    ↓ 管道 / 消息队列
logger 进程
    ↓
统一写日志文件
```

这样：

- worker 只负责处理客户端
- logger 统一处理磁盘写入
- 职责更清晰

### 面试官场景题

**Q：共享内存是最快的 IPC，为什么还需要信号量？**

答：

```text
共享内存只解决“多个进程能看到同一块内存”的问题，
不解决“谁先写、谁后读、同时写怎么办”的问题。

如果多个进程同时修改共享内存里的在线用户表，
会产生竞态条件。

所以共享内存通常要配合同步机制，比如信号量、互斥锁等。
```

### 面试官场景题

**Q：管道、消息队列、共享内存、信号量怎么选？**

答题口诀：

```text
小数据、父子关系、顺序传输，用管道；
控制消息、异步任务，用消息队列；
大块数据、高吞吐，用共享内存，但必须加同步；
只做并发控制，不传数据，用信号量；
跨主机通信，用 socket。
```

# 4. 第三版：多线程服务器

对应笔记：[12.1 线程简介](app://localhost/epitaxy/3.Linux/12.%20%E7%BA%BF%E7%A8%8B/12.1%20%E7%BA%BF%E7%A8%8B%E7%AE%80%E4%BB%8B.md)、[12.6 多线程并发服务器案例](app://localhost/epitaxy/3.Linux/12.%20%E7%BA%BF%E7%A8%8B/12.6%20%E5%A4%9A%E7%BA%BF%E7%A8%8B%E5%B9%B6%E5%8F%91%E6%9C%8D%E5%8A%A1%E5%99%A8%E6%A1%88%E4%BE%8B.md)

多进程很好，但有两个问题：

```text
1. 创建和切换进程成本高
2. 进程之间共享数据麻烦，需要 IPC
```

所以我们升级成多线程。

模型变成：

```text
主线程：
  accept()
  pthread_create()

工作线程：
  read/write 当前客户端
  广播消息
  写日志
  更新在线用户表
```

线程比进程轻，因为同一进程内的线程共享很多资源。

---

## 4.1 线程共享什么，独有什么？

|内容|是否共享|
|---|---|
|进程地址空间|共享|
|堆|共享|
|全局变量|共享|
|文件描述符|共享|
|代码段|共享|
|栈|每个线程独有|
|寄存器|每个线程独有|
|程序计数器|每个线程独有|

这解释了为什么：

```c
int local_var;
```

通常每个线程各有一份，因为它在各自线程栈上。

但：

```c
std::set<int> online_users;
```

如果是全局在线用户表，所有线程都能访问，必须加锁。

---

## 4.2 多线程聊天室最容易出问题的地方

假设你有：

```text
online_users：在线用户集合
log_file：日志文件
connection_table：连接状态表
message_queue：消息队列
```

这些都属于共享资源。

如果两个线程同时执行：

```text
线程 A：用户 1001 上线，insert online_users
线程 B：用户 1002 上线，insert online_users
```

没有锁就可能数据竞争。

如果两个线程同时写日志：

```text
[用户A上线
[用户B发送消息]
]
```

日志可能交错。

所以多线程模型的核心不是“会创建线程”就完事，而是：

> **共享资源不是不能用，是要排队用。**

### 面试官场景题

**Q：多线程比多进程轻在哪里？**

答：

```text
线程共享同一进程的地址空间和大部分资源，
创建线程不需要复制完整进程资源，
线程切换通常也比进程切换轻。

但代价是共享资源更容易出现数据竞争，
一个线程崩溃也可能影响整个进程。
```

### 面试官场景题

**Q：多线程聊天室里哪些地方必须加锁？**

答：

```text
在线用户表、连接状态表、日志文件、共享消息队列、统计计数器等共享资源都需要同步保护。

只要多个线程可能同时读写，并且至少一个是写操作，就要考虑同步。
```

### 面试官追问

**Q：broadcast 的时候能不能一直持有大锁？**

可以，但不推荐。

原因：

```text
如果 broadcast 持有在线用户表的锁，
然后在锁内对每个 socket write，
某个 socket 写阻塞或发送缓慢，就会导致其他线程无法更新在线用户表。

工程上更好的做法通常是：
1. 加锁复制一份 fd 列表
2. 释放锁
3. 再逐个发送

或者每个连接维护输出缓冲区，由 IO 线程统一发送。
```

# 5. 为什么“一个连接一个线程”不是最终答案？

对应笔记：[12.6 多线程并发服务器案例](app://localhost/epitaxy/3.Linux/12.%20%E7%BA%BF%E7%A8%8B/12.6%20%E5%A4%9A%E7%BA%BF%E7%A8%8B%E5%B9%B6%E5%8F%91%E6%9C%8D%E5%8A%A1%E5%99%A8%E6%A1%88%E4%BE%8B.md)、[13.1 IO复用简介](app://localhost/epitaxy/3.Linux/13.%20IO%E5%A4%8D%E7%94%A8/13.1%20IO%E5%A4%8D%E7%94%A8%E7%AE%80%E4%BB%8B.md)

现在聊天室升级成 IM 长连接网关。

假设：

```text
10 万用户在线
每个用户 30 秒发一次心跳
真正发送消息的人很少
```

如果一个连接一个线程：

```text
10 万连接 = 10 万线程
```

问题很大：

1. 每个线程都有栈空间，内存开销大
2. 线程调度成本高
3. 上下文切换成本高
4. 大多数线程什么也不做，只是在阻塞等待 `read()`

这个时候问题的本质变了：

> 我们不缺处理消息的 CPU，  
> 我们缺的是一种低成本等待大量连接的方式。

所以引出 IO 复用。

记忆句：

> **多线程是多找几个员工等电话；IO 复用是装一个总机，哪部电话响了通知前台。**

### 面试官场景题

**Q：10 万长连接能不能一个连接一个线程？**

答：

```text
不适合。

一个连接一个线程会导致线程数量爆炸，
每个线程有栈内存开销，大量线程调度和上下文切换成本高。
更关键的是，长连接大多数时间处于空闲状态，
线程阻塞等待会造成资源浪费。

更常见的方案是：
非阻塞 socket + epoll + 线程池 / Reactor。
```

# 6. IO 复用登场

对应笔记：[13.1 IO复用简介](app://localhost/epitaxy/3.Linux/13.%20IO%E5%A4%8D%E7%94%A8/13.1%20IO%E5%A4%8D%E7%94%A8%E7%AE%80%E4%BB%8B.md)

IO 复用的核心是：

> 一个线程同时监听多个 fd，哪个 fd 就绪就处理哪个。

对比一下：

|模型|等待方式|问题|
|---|---|---|
|阻塞 IO|一个 fd 没好就卡住|不能同时处理多个连接|
|非阻塞 IO|不停轮询所有 fd|CPU 忙等|
|IO 复用|阻塞在 select/poll/epoll|由内核告诉你哪些 fd 就绪|

注意一个非常重要的误区：

> **IO 复用不是异步 IO。**

`select/poll/epoll` 通知你的是：

```text
这个 fd 现在可以读 / 可以写
```

但真正的读写仍然要你自己调用：

```c
read(fd, buf, size);
write(fd, buf, size);
```

所以它是 **就绪通知**，不是 **完成通知**。

### 面试官场景题

**Q：IO 复用是不是异步 IO？**

答：

```text
不是严格意义上的异步 IO。

IO 复用通知的是 fd 已经就绪，比如可以读或可以写。
应用程序仍然需要自己调用 read/write 完成数据拷贝。

真正异步 IO 是应用提交操作后，内核完成等待和数据拷贝，
最后通知应用“操作已经完成”。
```

# 7. select：最早的 IO 复用方案

对应笔记：[13.2 select模型](app://localhost/epitaxy/3.Linux/13.%20IO%E5%A4%8D%E7%94%A8/13.2%20select%E6%A8%A1%E5%9E%8B.md)

select 的思路：

```text
我把要监听的 fd 集合交给内核，
内核帮我看哪些 fd 就绪。
```

模型：

```text
FD_ZERO
FD_SET(listen_fd)
FD_SET(client1_fd)
FD_SET(client2_fd)

select(max_fd + 1, &readfds, ...)

遍历所有 fd：
  if FD_ISSET(fd):
      处理 fd
```

select 的关键点：

|点|说明|
|---|---|
|fd 集合|`fd_set` 位图|
|数量限制|通常 `FD_SETSIZE = 1024`|
|`nfds`|最大 fd + 1|
|返回后|`fd_set` 被内核修改，只保留就绪 fd|
|下次调用前|必须重新设置 `fd_set`|
|查找就绪 fd|用户态还要遍历所有 fd|
|复杂度|O(n)|

select 的痛点：

```text
1. 每次调用都要把 fd_set 从用户态拷贝到内核态
2. 内核要线性扫描 fd_set
3. 返回后用户态还要线性扫描找出就绪 fd
4. fd_set 返回后被修改，下次要重新构造
5. 默认 fd 数量限制通常是 1024
```

记忆句：

> **select 是每次把名单交给内核，回来还要自己挨个查。**

### 面试官场景题

**Q：select 为什么有 1024 限制？**

答：

```text
select 使用 fd_set 位图表示 fd 集合。
fd_set 的大小由 FD_SETSIZE 决定，通常默认是 1024。
fd 值必须小于 FD_SETSIZE。

虽然理论上可以调整宏或重新编译，
但工程上高并发场景通常不会这么做，而是选择 poll 或 epoll。
```

### 面试官场景题

**Q：为什么 select 每次调用前都要重新设置 fd_set？**

答：

```text
因为 fd_set 是输入输出参数。

调用前，它表示“我要监听哪些 fd”；
返回后，它被内核修改成“哪些 fd 就绪”。

所以 select 返回后原始监听集合被破坏，
下一轮必须重新 FD_ZERO / FD_SET。
```

---

# 8. poll：修补 select，但没有根治问题

对应笔记：[13.3 poll模型](app://localhost/epitaxy/3.Linux/13.%20IO%E5%A4%8D%E7%94%A8/13.3%20poll%E6%A8%A1%E5%9E%8B.md)

poll 的思路：

> 既然 `fd_set` 位图有 1024 限制，那我换成数组。

核心结构：

```c
struct pollfd {
    int   fd;
    short events;
    short revents;
};
```

其中：

```text
events：我要监听什么事件
revents：实际发生了什么事件
```

相比 select：

|对比项|select|poll|
|---|---|---|
|fd 表示|`fd_set` 位图|`pollfd` 数组|
|fd 数量限制|固定 1024 左右|无固定限制|
|输入输出|同一个 fd_set 被修改|events/revents 分离|
|查找就绪|遍历|仍然遍历|
|复杂度|O(n)|O(n)|

poll 解决了 select 的一些明显缺陷：

```text
1. 没有固定 1024 限制
2. events 和 revents 分离
3. 事件类型更清晰
```

但核心问题还在：

```text
1. 每次仍然要把 pollfd 数组传给内核
2. 内核仍然要遍历所有 fd
3. 用户态返回后仍然要遍历数组找 revents
```

记忆句：

> **poll 是名单变成数组，但还是要挨个查。**

### 面试官场景题

**Q：poll 相比 select 改进了什么？还剩什么问题？**

答：

```text
poll 使用 pollfd 数组，不再受 FD_SETSIZE 的固定限制；
events 和 revents 分离，调用后不破坏原始监听事件；
支持的事件类型也更丰富。

但它仍然需要每次把 fd 数组传给内核，
内核仍要线性扫描，
应用返回后仍要遍历数组找就绪 fd，
所以大量连接时仍然是 O(n) 模型。
```

---

# 9. epoll：Linux 高并发服务端核心

对应笔记：[13.4 epoll模型](app://localhost/epitaxy/3.Linux/13.%20IO%E5%A4%8D%E7%94%A8/13.4%20epoll%E6%A8%A1%E5%9E%8B.md)

epoll 的关键变化是：

> 不再每次把完整 fd 名单交给内核。  
> 而是先把要监听的 fd 注册到内核，之后 `epoll_wait()` 只返回就绪事件。

三个核心函数：

```c
epoll_create1();  // 创建 epoll 实例
epoll_ctl();      // 增删改 fd
epoll_wait();     // 等待就绪事件
```

可以这样理解：

```text
select/poll：
  每次开会都把完整名单交给内核：
  “帮我看看这些人谁有事。”

epoll：
  先把名单长期登记到内核：
  “以后谁有事，你直接通知我。”
```

对比：

|问题|select/poll|epoll|
|---|---|---|
|fd 集合|每次调用传入|内核长期维护|
|就绪检查|遍历所有 fd|返回就绪事件列表|
|大量空闲连接|成本高|更适合|
|fd 数量|select 有限制，poll 无固定限制|无固定 1024 限制|
|平台|select/poll 较通用|Linux 专有|

注意表达要严谨：

> 不要简单说 “epoll 永远 O(1)”。  
> 更准确说：**epoll 避免了 select/poll 每次按总连接数线性扫描的主要成本，`epoll_wait` 返回的是就绪事件列表。**

记忆句：

> **epoll 是名单留在内核，只告诉你谁真的响了。**

### 面试官场景题

**Q：epoll 为什么比 select/poll 更适合高并发？**

答：

```text
select/poll 每次调用都要传入完整 fd 集合，
内核要遍历所有 fd，
返回后用户态还要遍历找就绪项。

epoll 通过 epoll_ctl 把 fd 注册到内核维护的事件表中，
之后 epoll_wait 直接返回就绪事件数组。
对于大量空闲长连接，epoll 不需要每次按总连接数扫描，
所以更适合高并发网络服务。
```

# 10. LT 和 ET：epoll 高频考点

对应笔记：[13.4 epoll模型](app://localhost/epitaxy/3.Linux/13.%20IO%E5%A4%8D%E7%94%A8/13.4%20epoll%E6%A8%A1%E5%9E%8B.md)

## 10.1 LT：水平触发

LT 是默认模式。

规则：

```text
只要缓冲区里还有数据没读完，
epoll_wait 下次还会继续通知。
```

像这样：

```text
缓冲区有 100 字节
你只读了 20 字节
还剩 80 字节
下一次 epoll_wait 还会通知你
```

所以 LT 简单，不容易漏事件。

记忆句：

> **LT 是“只要还有数据，就一直提醒你”。**

---

## 10.2 ET：边缘触发

ET 只在状态变化时通知一次。

比如：

```text
无数据 -> 有数据
```

通知一次。

如果你没读完，后面可能不再通知，除非又有新数据到来。

所以 ET 必须配合：

```text
1. 非阻塞 fd
2. 循环 read
3. 一直读到 EAGAIN / EWOULDBLOCK
```

典型逻辑：

```c
while (true) {
    ssize_t n = read(fd, buf, sizeof(buf));

    if (n > 0) {
        // 处理数据
    } else if (n == 0) {
        // 对端关闭
        close(fd);
        break;
    } else {
        if (errno == EAGAIN || errno == EWOULDBLOCK) {
            break;  // 当前已经读空
        }

        close(fd);
        break;
    }
}
```

为什么必须非阻塞？

因为如果 fd 是阻塞的，你循环读到没数据时，`read()` 会卡住整个 event loop。  
这就违背了 epoll 的初衷。

记忆句：

> **ET 是“只提醒一次，你必须一次处理到没数据”。**

### 面试官场景题

**Q：ET 模式为什么必须使用非阻塞 IO，并且读到 EAGAIN？**

答：

```text
ET 只在状态变化时通知一次。
如果只读一部分数据，缓冲区里剩余的数据可能不会再次触发事件。

所以必须循环读，把当前缓冲区读空。
读到 EAGAIN 或 EWOULDBLOCK，说明当前已经没有数据可读。

如果 fd 是阻塞的，循环读到没数据时会阻塞整个事件循环，
所以 ET 必须配合非阻塞 IO。
```

# 11. epoll 工程追问：面试加分区

对应笔记：[13.4 epoll模型](app://localhost/epitaxy/3.Linux/13.%20IO%E5%A4%8D%E7%94%A8/13.4%20epoll%E6%A8%A1%E5%9E%8B.md)

## 11.1 为什么 EPOLLOUT 不应该常驻？

很多人会写：

```c
EPOLLIN | EPOLLOUT
```

这在生产里很危险。

原因：

> 大多数 TCP socket 大多数时间都是可写的。  
> 如果一直监听 `EPOLLOUT`，事件循环会频繁被唤醒，造成空转。

正确做法：

```text
默认只监听 EPOLLIN
    ↓
有数据要发，并且一次没写完
    ↓
临时注册 EPOLLOUT
    ↓
发送缓冲区清空
    ↓
取消 EPOLLOUT
```

### 面试官场景题

**Q：为什么 EPOLLOUT 不应该一直注册？**

答：

```text
因为大多数 socket 通常都是可写的。
如果常驻 EPOLLOUT，epoll_wait 会频繁返回可写事件，
导致 event loop 空转，浪费 CPU。

正确做法是：
只有输出缓冲区有待发送数据，并且一次没有写完时才注册 EPOLLOUT；
发送完成后取消 EPOLLOUT。
```

---

## 11.2 EPOLLONESHOT 解决什么问题？

在 epoll + 线程池模型中，可能出现：

```text
同一个 fd 的事件被多个线程同时处理
```

这会造成：

- 同一个连接被并发读
- 协议状态被多个线程同时修改
- 输出缓冲区竞争

`EPOLLONESHOT` 的作用是：

```text
这个 fd 的事件触发一次后，自动失效。
worker 处理完以后，需要 epoll_ctl MOD 重新激活。
```

### 面试官场景题

**Q：EPOLLONESHOT 解决什么问题？**

答：

```text
它用于避免同一个 fd 被多个线程同时处理。

在 epoll + 线程池模型中，一个连接事件触发后交给 worker 处理。
如果处理期间该 fd 又产生事件，可能被其他线程同时处理。

EPOLLONESHOT 让事件触发一次后临时失效，
worker 处理完后再通过 epoll_ctl MOD 重新激活。
```

---

## 11.3 epoll 是 Reactor 还是 Proactor？

传统 epoll 更接近 Reactor。

因为 epoll 通知的是：

```text
fd 可以读
fd 可以写
```

然后应用自己调用：

```c
read();
write();
```

所以它是就绪通知。

Proactor 是完成通知：

```text
读操作已经完成
写操作已经完成
这是结果
```

比如 IOCP、某些 `io_uring` 用法更接近完成事件模型。

### 面试官场景题

**Q：epoll 是 Reactor 还是 Proactor？**

答：

```text
传统 epoll 更接近 Reactor。

因为 epoll_wait 通知的是 fd 已经可读或可写，
真正的 read/write 仍然由应用程序自己执行。

Proactor 模型中，应用提交异步操作，
内核完成操作后通知应用结果。
```

# 12. 最终生产模型：epoll + 线程池 / Reactor

现在我们把前面全部收束成一个生产级 IM 网关。

架构：

```text
I/O 线程 / EventLoop
  |
  | epoll_wait()
  |
  |-- listen_fd 可读
  |     accept4 新连接
  |     设置非阻塞
  |     加入 epoll
  |
  |-- conn_fd 可读
  |     循环 read 到 EAGAIN
  |     解析协议
  |
  |-- 轻任务
  |     EventLoop 直接处理
  |
  |-- 重任务
        投递线程池

Worker 线程池
  |
  | 处理业务逻辑
  | 把响应写回连接的输出缓冲区

EventLoop
  |
  | 有待发送数据时监听 EPOLLOUT
  | 发送完成后取消 EPOLLOUT
```

这里每个部分都对应前面的知识：

|模块|对应知识|
|---|---|
|非阻塞 socket|避免 event loop 被单个 fd 卡死|
|epoll|等待大量连接|
|线程池|处理耗时业务|
|锁/队列|保护任务队列、连接表|
|输入缓冲区|处理半包、粘包|
|输出缓冲区|处理一次写不完|
|EPOLLOUT 动态注册|避免空转|
|EPOLLONESHOT|避免同一 fd 多线程并发处理|

# 13. 综合面试题：设计 10 万长连接聊天服务器

**Q：让你设计一个支持 10 万长连接的聊天服务器，你怎么做？**

可以这样答：

```text
我会使用非阻塞 socket + epoll + 线程池的 Reactor 模型。

1. 主线程或 I/O 线程创建 listen_fd，并设置非阻塞。
2. 使用 epoll_create1 创建 epoll 实例。
3. 把 listen_fd 加入 epoll，监听 EPOLLIN。
4. listen_fd 可读时，用 accept4 接收新连接，并设置 SOCK_NONBLOCK 和 SOCK_CLOEXEC。
5. 每个 conn_fd 加入 epoll，默认监听 EPOLLIN 和 EPOLLRDHUP。
6. conn_fd 可读时，循环 recv，直到 EAGAIN，避免 ET 模式下漏读。
7. 对于心跳、简单协议解析等轻任务，可以在 I/O 线程完成。
8. 对于数据库访问、复杂计算、推理调度等重任务，投递到线程池。
9. 每个连接维护输入缓冲区和输出缓冲区。
10. 有数据没发完时才注册 EPOLLOUT。
11. 输出缓冲区清空后取消 EPOLLOUT，避免事件循环空转。
12. 处理 EPOLLERR、EPOLLHUP、EPOLLRDHUP 等异常事件。
13. 关闭连接时，从连接表删除，epoll_ctl DEL，然后 close fd，释放连接对象。
```

最后总结一句：

> **多进程解决隔离，多线程解决轻量并发，epoll 解决大量连接等待，线程池解决耗时任务调度。**

# 14. 最后一张总表：你复习时就背这张

|模型|核心思想|优点|缺点|适合场景|
|---|---|---|---|---|
|单进程阻塞|一个执行流处理所有连接|简单|一个连接阻塞全局|教学、小工具|
|多进程|一个连接一个子进程|隔离好|资源开销大，IPC 麻烦|小规模并发、稳定性优先|
|多线程|一个连接一个线程|比进程轻，共享方便|锁、死锁、线程爆炸|中小规模并发|
|select|单线程等待多个 fd|跨平台，简单|1024 限制、重复拷贝、遍历|小规模、多平台|
|poll|用数组管理 fd|无固定 1024 限制|仍然 O(n) 遍历|中等规模|
|epoll|内核维护事件表，返回就绪列表|适合大量连接|Linux 专有，细节复杂|高并发服务端|
|epoll + 线程池|I/O 与业务解耦|工程主流|状态管理复杂|高并发生产服务|

## 最终记忆钩子

你可以这样背：

```text
单进程阻塞：
  一个 fd 不说话，整个程序陪它等。

多进程：
  一个客户一个分公司，安全但贵。

IPC：
  分公司之间不能直接看对方内存，只能通信。

多线程：
  一个办公室多个员工，沟通快但容易抢资源。

IO 复用：
  不给每个电话配员工，而是装一个总机。

select：
  每次把名单交给内核，回来还要自己挨个查。

poll：
  名单变成数组，但还是要挨个查。

epoll：
  名单留在内核，只告诉你谁真的响了。

ET：
  只提醒一次，你必须一次处理到没数据。

Reactor：
  事件来了，我分发给 handler。

Proactor：
  操作完成了，系统通知我结果。
```

这三章的主线就是：

> **从“增加执行流”到“改变等待方式”。**  
> 多进程、多线程都是增加执行流；  
> IO 复用是让少量执行流高效等待大量连接。
