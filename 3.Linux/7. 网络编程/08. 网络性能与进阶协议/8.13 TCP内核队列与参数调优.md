# 8.13 TCP 内核队列与参数调优

## 1. 简介

“连不上”是个很含糊的现象。它可能卡在客户端拿不到源端口，可能卡在服务端两个队列里的任何一个，也可能卡在 `accept()` 拿不到文件描述符——**每一道闸口的表现都不一样，能调的参数也完全不同**。

两个连接队列本身的机制（谁装什么、`backlog` 和 `somaxconn` 怎么取小、队列满了内核怎么处理）在 [[7.8 listen和accept函数#2. 两个队列|7.7]] 里讲过了，这篇不重复。这里换个视角：把一条连接建立路上的所有上限串起来，讲清楚**怎么定位是哪一道卡住了，以及各自能怎么改**。

---

## 2. 四道闸口

![[图片/SVG/3_8_8_13_1.svg|900]]

排障的顺序基本就是从左往右排除。有个规律值得记住：

- **①②④ 卡住时，客户端会明确失败**——`connect()` 返回错误或超时，日志里看得见
- **③ 卡住时，客户端会“以为成功”**——三次握手是内核完成的，客户端那边已经是 ESTABLISHED，服务端却当这条连接不存在。表现是“连上了但一直没响应”，最难查

所以看到“连接超时”先怀疑 ①②，看到“连上了没反应”直奔 ③，看到服务端日志里 `accept` 报错就是 ④。

---

## 3. 常见内核参数

| 参数 | 作用 | 归谁管 |
|:---|:---|:---|
| `net.core.somaxconn` | 全连接队列上限 | 闸口 ③ |
| `net.ipv4.tcp_max_syn_backlog` | 半连接队列上限 | 闸口 ② |
| `net.ipv4.tcp_syncookies` | 半连接队列压力大时启用 syncookies | 闸口 ② |
| `net.ipv4.tcp_syn_retries` | 客户端 SYN 重传次数，决定 connect 超时多久 | 闸口 ② |
| `net.ipv4.ip_local_port_range` | 本机临时端口范围 | 闸口 ① |
| `net.ipv4.tcp_tw_reuse` | 允许复用 TIME_WAIT 端口发起新连接 | 闸口 ① |
| `fs.file-max` | 系统级打开文件总数上限 | 闸口 ④ |
| `fs.nr_open` | 单进程 fd 号的硬上限，`ulimit -n` 不能超过它 | 闸口 ④ |

查看：

```bash
sysctl net.core.somaxconn net.ipv4.tcp_max_syn_backlog net.ipv4.tcp_syncookies
sysctl fs.file-max fs.nr_open
ulimit -n
```

> [!warning] 改了要能活过重启，也要能活过容器
> `sysctl -w` 只对当前运行的内核生效，重启就没了。要持久化得写进 `/etc/sysctl.d/*.conf`。
>
> 容器里更容易踩坑：`net.*` 里只有一部分是 **network namespace 隔离**的（`somaxconn`、`ip_local_port_range` 这些属于此列，容器内可以单独设），而 `fs.file-max` 是全局的，在容器里改不动，得去调宿主机或者容器运行时的 `--ulimit`。在容器里 `sysctl -w` 报 read-only 通常就是这个原因。

## 4. SYN flood

SYN flood 是攻击者大量发送 SYN，但不完成三次握手，导致服务端半连接队列被占满。

现象：

- 大量 `SYN_RECV`
- 正常客户端连接超时
- CPU 不一定很高，但新连接失败明显增多

排查：

```bash
ss -ant state syn-recv
ss -s
```

缓解：

- 增大 `tcp_max_syn_backlog`
- 启用 `tcp_syncookies`
- 前置负载均衡或防火墙限速
- 应用层不要把所有保护寄托在 backlog 上

---

## 5. accept 太慢

如果三次握手已经完成，但应用迟迟不 `accept()`，全连接队列会满。

常见原因：

- 单线程 accept 后直接处理耗时业务
- accept 线程被日志、锁、磁盘 IO 阻塞
- 新连接速率超过应用处理能力
- fd 达到进程上限，accept 失败

改进方向：

- accept 后尽快把连接交给 [[13.4 epoll模型|epoll]] 或 worker
- 使用专门的 Acceptor
- 提高进程 `ulimit -n`
- 检查 `EMFILE` / `ENFILE`
- 必要时使用 `SO_REUSEPORT` 多进程监听

---

## 6. 文件描述符上限

每个 TCP 连接至少占用一个 fd。高并发服务撞上的第一个瓶颈通常就是这里。

fd 上限其实是三层，从紧到松：

| 层级 | 参数 | 说明 |
|:---|:---|:---|
| 进程软限制 | `ulimit -n` | 进程实际能开的数量，可以在硬限制内自己调高 |
| 进程硬上限 | `fs.nr_open` | `ulimit -n` 的天花板，默认 1048576 |
| 系统总量 | `fs.file-max` | 全机所有进程打开文件数之和 |

```bash
ulimit -n                       # 当前进程软限制
cat /proc/sys/fs/nr_open        # 单进程硬上限
cat /proc/sys/fs/file-nr        # 已分配 / 空闲 / 上限
ls /proc/<pid>/fd | wc -l       # 某进程实际用了多少
```

常见错误：

| errno | 含义 | 撞的是哪一层 |
|:---|:---|:---|
| `EMFILE` | 当前进程 fd 用完 | `ulimit -n` |
| `ENFILE` | 系统 fd 用完 | `fs.file-max` |

### 6.1 EMFILE 会变成死循环

`EMFILE` 最麻烦的地方不是 `accept()` 失败，而是**失败之后那条连接还挂在全连接队列里**。LT 模式下监听 fd 因此一直处于可读状态，事件循环每一轮都来 `accept` 一次、每一次都返回 `EMFILE`，CPU 直接打满，而且一个请求也处理不了。

常用解法是预留一个“备用 fd”：

```cpp
// 启动时先占一个名额
int idle_fd = open("/dev/null", O_RDONLY | O_CLOEXEC);

// accept 循环里
int conn = accept4(listen_fd, nullptr, nullptr, SOCK_NONBLOCK | SOCK_CLOEXEC);
if (conn < 0 && errno == EMFILE) {
    close(idle_fd);                              // 腾出一个名额
    conn = accept(listen_fd, nullptr, nullptr);  // 用它把连接从队列里摘出来
    close(conn);                                 // 立刻关掉，给客户端一个明确的结束
    idle_fd = open("/dev/null", O_RDONLY | O_CLOEXEC);  // 重新占回来
}
```

这么做救不了容量，但至少把连接从队列里摘掉了，事件循环不再空转，客户端也能立刻失败而不是干等。muduo 里就是这个做法。

## 7. 端口耗尽

客户端主动发起大量短连接时，可能遇到临时端口耗尽。一条 TCP 连接由四元组唯一确定：

```text
源 IP + 源端口 + 目的 IP + 目的端口
```

这里有个常见的误解要澄清：**源端口不是全局唯一，只需要在同一个“目的 IP + 目的端口”下唯一**。所以一台机器对 `10.0.0.1:80` 用满 6 万个端口之后，对 `10.0.0.2:80` 照样能再开 6 万个。

由此得到三个方向的解法：

| 做法 | 原理 |
|:---|:---|
| 扩大 `ip_local_port_range` | 直接放大分子，最容易但空间有限 |
| 后端多准备几个 IP 或端口 | 换目的地址，每个目的地址各有一套端口空间 |
| 改用长连接 / 连接池 | 从根上不再频繁建连，效果最好 |

叠加 [[10.2 TIME_WAIT状态|TIME_WAIT]] 之后问题会更明显——主动关闭的一方要占着那个四元组 60 秒。相关的两个参数容易记混：

- `net.ipv4.tcp_tw_reuse`：允许把处于 `TIME_WAIT` 的端口**用于发起新的出方向连接**，需要开启 TCP 时间戳。它只帮客户端，对服务端的入方向连接没有任何作用
- `net.ipv4.tcp_tw_recycle`：在 NAT 环境下会误丢正常连接，**已在 Linux 4.12 中移除**。网上很多老调优文章还在推荐它，看到就跳过

排查：

```bash
sysctl net.ipv4.ip_local_port_range
ss -tan state time-wait | wc -l
```

## 8. SO_REUSEPORT

`SO_REUSEADDR` 解决的是重启时端口被 `TIME_WAIT` 占住导致 `bind` 失败；`SO_REUSEPORT` 是另一回事——它允许多个 socket 绑定同一个 `IP:port`，由内核按四元组哈希把新连接分发给其中之一。

```cpp
int on = 1;
setsockopt(fd, SOL_SOCKET, SO_REUSEPORT, &on, sizeof(on));
```

| 选项 | 主要用途 |
|:---|:---|
| `SO_REUSEADDR` | 地址复用，解决重启绑定失败 |
| `SO_REUSEPORT` | 多个监听 socket 共享同一端口，内核分发连接 |

它把 accept 从单点变成多点，也顺带避免了惊群。但有两个坑：

- **分发是按连接哈希，不是按负载。** 长连接场景下，某个进程可能恰好握着一堆重活，而别的进程闲着，内核不会帮你再均衡
- **滚动重启期间会丢连接。** 一个进程还在监听组里但已经开始退出时，内核照样往它那儿分发新连接。正确顺序是先 `close` 掉监听 fd 把自己从组里摘掉，处理完存量连接再退出

## 9. 从现象定位闸口

| 现象 | 大概率是哪一道 | 先看什么 |
|:---|:---|:---|
| `connect()` 返回 `EADDRNOTAVAIL` | ① 源端口 | `ip_local_port_range`、`TIME_WAIT` 数量 |
| `connect()` 超时，服务端没有任何记录 | ② 半连接队列 | `ss -ant state syn-recv`、是否被 SYN flood |
| 客户端说连上了，请求却没响应 | ③ 全连接队列 | `ss -lnt` 的 `Recv-Q`、`TcpExtListenOverflows` |
| 服务端日志里 `accept` 报错 | ④ fd | `ulimit -n`、`/proc/<pid>/fd` 数量 |
| CPU 打满但吞吐为零 | ④ fd（EMFILE 空转） | 同上，顺便查有没有备用 fd 保护 |

## 10. 面试问法

| 问题 | 回答要点 |
|:---|:---|
| backlog 控制哪个队列 | 现代 Linux 主要控制全连接队列，并受 `somaxconn` 限制 |
| 半连接队列满会怎样 | 新 SYN 可能被丢弃或触发 syncookies |
| 全连接队列满说明什么 | 应用 accept 太慢或队列太小 |
| SYN flood 怎么防 | syncookies、增大队列、限速、防火墙、负载均衡 |
| fd 上限不够表现是什么 | `accept` 返回 `EMFILE/ENFILE`，而且会空转烧 CPU |
| 为什么 EMFILE 会把 CPU 打满 | 连接还在队列里，LT 下监听 fd 一直可读 |
| 源端口是全局唯一的吗 | 不是，只在同一个“目的 IP + 目的端口”下唯一 |
| `tcp_tw_reuse` 能救服务端吗 | 不能，它只作用于出方向的新连接 |
| 端口耗尽常见在哪 | 客户端大量短连接或 TIME_WAIT 堆积 |

---

## 11. 关键要点

1. **一条连接要过四道闸口**：源端口 → 半连接队列 → 全连接队列 → `accept` 拿 fd。定位是哪一道，比背参数表有用
2. **①②④ 卡住客户端会明确失败，③ 卡住客户端会“以为成功”**，第三种最难查
3. **队列本身的机制在 [[7.8 listen和accept函数]]**，这里只管上限、观测和调优
4. **fd 上限是三层**：`ulimit -n` ≤ `fs.nr_open`，全机再受 `fs.file-max` 约束
5. **`EMFILE` 会让事件循环空转**，要用预留的备用 fd 把连接从队列里摘掉
6. **源端口只在同一目的地址下唯一**，所以后端多几个 IP 或端口就能成倍放大连接数
7. **`tcp_tw_reuse` 只帮客户端**；`tcp_tw_recycle` 已在 Linux 4.12 移除，别再照抄老文章
8. **`SO_REUSEPORT` 按四元组哈希分发，不按负载**，滚动重启时要先摘掉监听 fd 再退出
