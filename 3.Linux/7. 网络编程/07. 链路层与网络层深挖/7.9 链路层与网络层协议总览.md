# 7.9 链路层与网络层协议总览

> [!abstract] 本组笔记的定位
> 本组笔记沿着「一个 IP 数据报如何离开本机、跨越网络并反馈差错」的主线，补充链路层和网络层协议。分层模型的整体介绍见 [[7.1 网络分层模型]]，地址、子网与 CIDR 的计算见 [[7.2 IP地址与CIDR]]。这一篇是总览：先把四个协议串成一条完整链路，字段级的细节留给 7.9 到 7.13。

## 1. 为什么这四个协议要放在一起讲

[[7.1 网络分层模型|分层模型]]说清了每层负责什么，[[7.2 IP地址与CIDR|IP 地址]]说清了地址怎么算，但两者都没回答一个具体问题：程序里 `write()` 出去的一段数据，怎么变成网线上的信号，又怎么找到地球另一端那台机器。

回答这个问题需要四个协议合起来：

- **Ethernet** 管一条链路上相邻两个节点之间怎么传一帧；
- **IP** 管数据报跨越多条链路、经过多台路由器到达目标；
- **ARP** 管把 IP 层算出的「下一跳 IP」翻译成链路层能用的 MAC 地址；
- **ICMP** 管上面任何一步出错时，把消息送回源主机。

前三个是数据平面，最后一个是控制平面。少了 ARP，IP 数据报封不成帧，包发不出去；少了 ICMP，包丢在哪一跳你永远查不出来。

## 2. 一次跨网段通信：包在路上被改了什么

假设主机 A（`192.168.1.10`）要访问 `203.0.113.20`，中间隔着一台交换机和两台路由器。

![[图片/SVG/3_7_7_9_1.svg|1231]]

按发送顺序拆开，内核做的事是这样的：

```
主机 A (本地内核)
  │ 1. 目标 IP 203.0.113.20 非本网段
  │ 2. 查本地路由表: 下一跳 = 网关 192.168.1.1
  │ 3. 查本地 ARP 表: 得到网关 MAC (若无则发 ARP 广播)
  │ 4. 封装以太网帧:
  │    [源MAC: A | 目的MAC: R1] [源IP: A | 目的IP: B | TTL: 64] [数据]
  ▼
交换机 SW1 (纯二层转发)
  │ 只读帧头 [目的MAC: R1]，从连接 R1 的物理端口转发出去
  │ 帧内容一个字节不改，TTL 不变！
  ▼
路由器 R1 (三层路由节点)
  │ 1. 网卡收到帧，目的 MAC 是自己，剥掉以太网帧头
  │ 2. 检查 IP 头: 目的 IP 203.0.113.20 不是自己，需要路由
  │ 3. TTL 减 1 (64 -> 63)，重算 IP 校验和
  │ 4. 查 R1 路由表: 下一跳是 R2 的互联接口 IP
  │ 5. 查 R1 本地 ARP 表: 得到 R2 的 MAC
  │ 6. 重新封装全新以太网帧:
  │    [源MAC: R1出接口 | 目的MAC: R2入接口] [源IP: A | 目的IP: B | TTL: 63] [数据]
  ▼
路由器 R2 (终点路由节点)
  │ 1. 剥掉帧头，发现目的 IP 203.0.113.20 正好直连在自己的子网上！
  │ 2. TTL 减 1 (63 -> 62)，重算 IP 校验和
  │ 3. 查 R2 本地 ARP 表: 得到目标主机 B 的 MAC
  │ 4. 重新封装全新以太网帧:
  │    [源MAC: R2出接口 | 目的MAC: B] [源IP: A | 目的IP: B | TTL: 62] [数据]
  ▼
目标主机 B
     目的 MAC 是自己，目的 IP 是自己，逐层解包交付上层 socket！
```

图 A 的表格是这一路的结果：**MAC 每跳重写，IP 端到端不变，TTL 每跳减 1**。这条规则是后面所有抓包分析的基准线。本机抓包看到目的 MAC 是网关、目的 IP 是某个公网地址，这是正常现象，说明包要出本网段。

> [!note] 同网段的情况少两步
> 如果目标就在本网段，第 2 步选出的下一跳就是目标自己，ARP 直接问目标要 MAC，整条路上没有路由器，TTL 也不减。区别只在下一跳选谁，ARP 那一步的机制完全一样。

## 3. 四个协议的分工

| 协议 | 所在位置 | 回答的问题 | 主要标识 | 作用范围 |
|---|---|---|---|---|
| Ethernet | 数据链路层 | 相邻两个节点之间怎样传一帧 | MAC 地址、EtherType | 单条链路 |
| IPv4 / IPv6 | 网络层 | 数据报怎样跨网段到达目标 | IP 地址、路由前缀 | 端到端 |
| ARP | 夹在 IPv4 和链路层之间 | 下一跳 IPv4 对应哪个 MAC | IP 与 MAC 的映射 | 单个广播域 |
| ICMP / ICMPv6 | 网络层的控制协议 | 怎样报告差错、怎样诊断 | Type、Code | 从出错点回到源主机 |

三个协议的封装关系值得单独记一下，它决定了抓包时该按什么条件过滤：

| 谁装在谁里面 | 标识字段 | 抓包过滤 |
|---|---|---|
| IPv4 装在 Ethernet 帧里 | EtherType `0x0800` | `tcpdump ip` |
| IPv6 装在 Ethernet 帧里 | EtherType `0x86DD` | `tcpdump ip6` |
| ARP 装在 Ethernet 帧里 | EtherType `0x0806` | `tcpdump arp` |
| ICMP 装在 IPv4 数据报里 | IP 首部协议号 `1` | `tcpdump icmp` |
| ICMPv6 装在 IPv6 数据报里 | 下一个首部 `58` | `tcpdump icmp6` |

> [!warning] ARP 不在 IP 之上
> 很多图把 ARP 画在网络层，容易让人以为 ARP 报文外面套着 IP 头。实际上 ARP 报文直接装在 Ethernet 帧里，走的是自己的 EtherType `0x0806`，整个过程不经过 IP 层。ARP 里出现的 IP 地址只是被查询的数据，不是路由用的地址。

## 4. IPv4 走 ARP，IPv6 走 NDP

ARP 只服务于 IPv4。IPv6 把邻居解析、路由器发现与地址自动配置全部收进了 ICMPv6，称为 **NDP**（Neighbor Discovery Protocol，邻居发现协议，RFC 4861）。

| 维度 | IPv4 (ARP) | IPv6 (NDP) |
|---|---|---|
| **协议位置** | 独立的 EtherType `0x0806`，直接封装在以太网帧中 | 基于 ICMPv6，封装在 IPv6 报文中（Next Header `58`） |
| **寻址范围** | 广播到 `ff:ff:ff:ff:ff:ff`（打扰全网所有主机 CPU） | 组播到**被请求节点组播地址**（网卡硬件过滤，非目标零打扰） |
| **邻居解析报文** | ARP Request（广播） / ARP Reply（单播） | NS（Neighbor Solicitation 135）/ NA（Neighbor Advertisement 136） |
| **地址冲突检测** | 免费 ARP（Gratuitous ARP），无统一规范，全凭客户端自觉 | DAD（Duplicate Address Detection），未通过前地址处于 `tentative` 状态禁止通信 |
| **默认网关发现** | 依赖 DHCPv4 分配或人工静态指定 | RS（Router Solicitation 133）/ RA（Router Advertisement 134），网络层原生自带 |
| **自动地址配置** | 依赖有状态的 DHCPv4 服务器 | 支持 SLAAC（无状态自动配置）：结合 RA 前缀与接口 ID 自动生成全局单播地址 |
| **内核缓存位置** | `ip neigh` | 同样是 `ip neigh`，内核统一状态机驱动 |

### 4.1 为什么组播不打扰非目标主机？

IPv4 的 ARP 请求采用以太网广播（目的 MAC 为 `ff:ff:ff:ff:ff:ff`）。广播域内的所有网卡接收到该帧后，都会向操作系统 CPU 触发硬件中断（Hard IRQ）。操作系统内核从网卡环形缓冲区（Ring Buffer）读取数据帧，解析出 ARP 报文后判断目标 IP 是否属于本机。当确认不是本机 IP 时，内核将其丢弃。如果局域网内存在高频广播，所有主机的 CPU 都会反复处理无意义的中断与协议栈解析。

IPv6 废除了全网广播机制，改用**被请求节点组播地址**（Solicited-Node Multicast Address），将过滤操作直接下沉到网卡硬件层面。

#### 1. 组播 IP 与组播 MAC 的映射推导

发送端不需要向网络查询，可以直接根据目标主机的 IPv6 地址推导出对应的三层组播 IP 与二层组播 MAC。

假设目标主机的单播 IPv6 为 `2001:db8::8a2e:a1:b2c3`：

* **三层组播 IP（被请求节点组播地址，RFC 4291）**  
  固定前缀为 `ff02:0:0:0:0:1:ff00:0/104`（简写为 `ff02::1:ff`），占用 104 位。将目标单播 IPv6 的最低 24 位（即末尾 6 个十六进制字符 `a1:b2c3`）拼接至前缀末尾，补足 128 位：
  ```text
  固定前缀 (104 位):  ff02 : 0000 : 0000 : 0000 : 0001 : ff
  目标低 24 位:                                                    a1 : b2c3
  ────────────────────────────────────────────────────────────────────────────
  被请求节点组播 IP:  ff02 : 0000 : 0000 : 0000 : 0001 : ffa1 : b2c3
  (标准压缩格式):     ff02::1:ffa1:b2c3
  ```

* **二层组播 MAC（RFC 2464）**  
  以太网规范规定：IPv6 组播帧的以太网 MAC 前 16 位固定为 `33:33`。剩余 32 位直接复制该组播 IP 的最低 32 位（4 字节）：
  ```text
  固定 MAC 前缀 (16 位):  33 : 33
  组播 IP 低 32 位:               ff : a1 : b2 : c3
  ──────────────────────────────────────────────
  以太网组播 MAC:         33 : 33 : ff : a1 : b2 : c3
  ```

#### 2. 网卡硬件过滤与处理流程

这套映射机制在网络节点中的实际运行逻辑如下：

1. **接收端初始化**：主机配置单播 IPv6 地址时，内核协议栈会自动计算其对应的组播 MAC `33:33:ff:a1:b2:c3`，并通知网卡驱动将该 MAC 注册进网卡芯片内部的硬件过滤表（Multicast Filter Table）。
2. **发送端发起解析**：发送端需要解析目标 IP 的 MAC 地址时，在本地计算出上述组播 IP 与组播 MAC，封装 ICMPv6 NS（Type 135）报文发出。
3. **非目标主机的硬件过滤**：局域网内其他主机的网卡接收到电信号后，在 MAC 控制器芯片层面对比目的 MAC 与自身的硬件过滤表。由于未注册该组播 MAC，网卡硬件直接丢弃该数据帧，不向操作系统 CPU 触发硬件中断，不占用系统资源。
4. **目标主机的响应**：目标主机网卡的硬件过滤表匹配成功，触发硬件中断将数据帧提交内核协议栈，内核解析 NS 报文后向发送端单播回复包含自身真实 MAC 的 NA（Type 136）报文。

由于低 24 位拥有 $2^{24} \approx 1677$ 万个空间，同子网内两台设备后 24 位发生哈希碰撞的概率极低。即使出现极个别碰撞，也仅有对应节点产生中断并在协议栈内丢弃，不会像 IPv4 ARP 那样波及全网所有节点。

> [!warning] IPv6 网络不能全量阻断 ICMPv6
> IPv4 的地址解析依赖独立的 ARP 协议（EtherType `0x0806`），防火墙过滤 ICMP 仅影响 `ping` 探测，不影响链路层地址解析。
> IPv6 彻底移除了 ARP，将邻居地址解析（NS/NA，Type 135/136）与路由器发现（RS/RA，Type 133/134）直接集成在 ICMPv6 内部。如果防火墙全量丢弃 ICMPv6 报文，节点将无法解析下一跳链路层 MAC，也无法获取网络前缀与默认路由，导致整个 IPv6 网络通信中断。

### 4.2 Linux 内核的邻居状态机（NUD）

无论是 IPv4 ARP 还是 IPv6 NDP，Linux 内核的邻居子系统（Neighboring Subsystem）都由同一个邻居不可达检测（NUD）状态机驱动：

![[图片/SVG/3_7_7_9_2.svg|1240]]

- **`STALE` 状态的精妙设计**：当条目超时变成 `STALE` 时，内核并不会立刻把包卡住去发 ARP/NS，而是**允许直接复用旧 MAC 发出数据**，同时进入 `DELAY` 等待上层（如 TCP 的接收确认）。如果上层确认对端活着，条目自动恢复 `REACHABLE`；只有无确认时才进入 `PROBE` 单播探测。这最大程度避免了数据面的额外发包延迟。

#### 4.2.1. 冷启动：INCOMPLETE

你的程序要给局域网里的 `192.168.1.5` 发数据，内核查 **邻居表** 发现从来没见过这个 IP。 这时候没办法，以太网帧头封不出来，只能把业务包先扣在队列里，对外发 ARP 广播（IPv6 则是发 NS 组播）。这就是 **INCOMPLETE**。

- 对方回了应答：拿到 MAC，状态变成 **REACHABLE**，把刚才扣留的数据包推出去。
- 连发 3 次广播没人理：说明机器大概率不存在，状态切到 **FAILED**，内核直接给上层抛 `EHOSTUNREACH`。

#### 4.2.2. 蜜月期：REACHABLE

拿到 MAC 后的二三十秒内，状态都是 **REACHABLE**。这段时间内核完全信任这个 MAC，上层发什么包就直接往网卡丢，零阻碍。但这时间不能太长，万一对方换了机器或改了 IP 呢？所以大约 30 秒一过（内核会在这数值上下随机浮动，防止整网设备同时过期），条目就会面临老化。

#### 4.2.3. 最容易让人困惑的地方：STALE

按常规直觉，缓存一过期，是不是该立刻卡住发包、去网络里重新问一遍？ 内核偏不这么干。它把状态改成 **STALE**（陈旧），但**继续允许你拿旧 MAC 正常发包**。 因为在局域网里，机器绝大部分时候好几天都不会换网卡。如果一过期就发广播，网络里全是大喇叭，业务包还会凭空多出几十毫秒的排队延迟。 STALE 可以一直趴在表里不动。直到你的程序又要往这个目标发新包，状态才会切到 **DELAY**。

> [!question] 如果持续高频发包超过 30 秒，会变成 STALE 吗？
> **取决于发的是 TCP 还是 UDP。**
> 
> 内核判断可达性依赖邻居条目里的两个核心时间戳：
> - `used`：最后一次发包的时间（我方单向使用）。
> - `confirmed`：最后一次收到对端存活证据的时间（对端有明确回音）。
> 
> **只有 `confirmed` 才能重置 30 秒倒计时。** 单方面发包只能证明我方在发，无法证明对端活着。
> 
> - **TCP（双向有回应）—— 保持 REACHABLE，不会跌入 STALE**  
>   数据发出后，对端会回传 TCP ACK。内核 TCP 协议栈收到推进序号的合法 ACK 时，会调用 `dst_confirm_neigh()` 顺手更新 `confirmed = jiffies`。只要数据来回流动，倒计时每隔几十毫秒就被重置，条目可以一直续命在 `REACHABLE`。
> 
> - **UDP（单向发）—— 满 30 秒必然跌入 STALE**  
>   UDP 只管发不管收，调用 `sendto()` 只能刷新 `used`，不能证明对端没拔网线。30 秒一到，内核认定缺乏存活证据，强制切到 **STALE**。但因为发包仍在继续，紧接着会触发如下连锁反应：
>   1. 下一个 UDP 数据包发出，立刻将状态推进至 **DELAY**；
>   2. DELAY 的 5 秒宽限期内无上层协议确认，转入 **PROBE**；
>   3. 内核在底层单播发送 ARP 请求。对端应答后，`confirmed` 瞬间被刷新，状态重新拉回 **REACHABLE**；
>   4. 整个探测与切换期间，业务 UDP 数据包照常发出，没有任何阻塞。


#### 4.2.4. 蹭顺风车：DELAY

进入 **DELAY** 状态后，内核给你 5 秒宽限期。在这 5 秒内，业务包照常发，依然不发 ARP 探测。 内核在这里动了个心思：既然刚刚发出去了业务数据（比如一段 TCP 报文），如果对方真的活着，等会儿肯定会回一个 TCP ACK。 TCP 协议栈一旦收到这个 ACK，就会通过 `dst_confirm()` 顺手告诉邻居子系统：“对方活着呢，我刚收到回信了。” 邻居表收到这个顺风车信号，立刻把条目重置回 **REACHABLE**。 **从头到尾，内核没往局域网里多发一个探测包，应用层也没产生任何发包停顿**。

> “我不去多管闲事发 ARP 了。既然这是个 TCP 业务包，只要对面机器还在，对面的操作系统的 TCP 栈收到数据后，几毫秒内必然会回一个 TCP ACK。我只要在旁边瞅着，看能不能收到这个 ACK 就行。”
#### 4.2.5. 实在等不到了才查：PROBE

要是 5 秒宽限期过去了，上层协议没有任何动静（比如发的是纯 UDP，没有握手和确认机制；或者对方真掉线了），内核才确认自己必须亲自出手。 状态转为 **PROBE**。 这时候内核开始发探测。注意这里发的是**单播**，直接拿旧 MAC 单独问它“你还在不在”，依然不发广播，不惊动网络里的其他人。

- 对方应答了：重回 **REACHABLE**。
- 连续问了 3 次（每次间隔 1 秒）都没反应：彻底死心，切到 **FAILED**。

## 5. ICMP：网络层唯一会回话的协议

IP 本身是尽力而为（Best-Effort）的无连接协议：包送不到就静默丢弃，不解释也不重试。ICMP（RFC 792 / RFC 4443）补上的正是“为什么丢弃”的诊断回执。

### 5.1 差错报文的内核反查机制

所有的 ICMP 差错报文（Error Message）都有一个核心特征：**由中途丢弃数据报的设备（路由器或防火墙）生成，源 IP 是那台设备的接口地址，报文数据区必须附上“原始 IP 数据报的首部 + 传输层前 8 字节”**。

```text
┌─────────────────────────────────────────────────────────────┐
│ 外部 IP 首部: 源 IP = 中途路由器, 目的 IP = 源主机 A             │
├─────────────────────────────────────────────────────────────┤
│ ICMP 首部: Type (类型), Code (代码), Checksum (校验和)         │
├─────────────────────────────────────────────────────────────┤
│ 原始载荷镜像 (引用的原数据报):                                  │
│   ├── 原 IPv4 首部（包含源 IP、目的 IP、协议号）                 │
│   └── 原传输层前 8 字节:                                      │
│         • TCP: 源端口(2B) + 目的端口(2B) + 序列号 Seq(4B)      │
│         • UDP: 源端口(2B) + 目的端口(2B) + 长度(2B) + 校验和    │
└─────────────────────────────────────────────────────────────┘
```

**为什么必须附带这 8 字节？**  
因为中间设备发回 ICMP 时，目的端口是发送端主机的 IP，但**ICMP 首部本身没有传输层端口号**。源主机的内核协议栈收到 ICMP 报文后，正是拆开其载荷镜像、读取那 8 字节提取出原始的 `源端口:目的端口`，才能在内核的 Socket 哈希表中反查出具体是哪一个进程、哪个套接字（fd）触发了差错，进而将网络层差错转化为应用层感知的 `errno`：
- 收到 `Host/Port Unreachable` $\to$ `send()` 抛出 `ECONNREFUSED` 或 `EHOSTUNREACH`；
- 收到 `Frag Needed and DF set` $\to$ 触发内核更新该路由条目的 PMTU 缓存。

### 5.2 高频 ICMP 差错类型速查

| Type | Code | 英文名称 | 典型触发场景 | 操作系统对应 errno / 行为 |
|:---:|:---:|:---|:---|:---|
| **3** | **0** | Network Unreachable | 路由器无匹配路由条目，且无默认路由 | `ENETUNREACH` |
| **3** | **1** | Host Unreachable | 最后一跳路由器发送 ARP 广播超时无应答 | `EHOSTUNREACH` |
| **3** | **3** | Port Unreachable | UDP 报文到达目标主机，但目标端口无进程监听 | `ECONNREFUSED`（UDP 连接模式下） |
| **3** | **4** | Fragmentation Needed (DF set) | 数据报尺寸大于出接口 MTU，且 IP 头置了 DF 位 | 触发内核 PMTU 发现；若被防火墙屏蔽则引发 PMTU 黑洞 |
| **11** | **0** | TTL Expired in Transit | 路由环路或正常跳数耗尽，路由器将 TTL 减为 0 | `traceroute` 的核心探针原理 |
| **8 / 0** | **0** | Echo Request / Reply | ping 连通性探测（请求与应答） | 计算双向 RTT 延迟与丢包率 |

### 5.3 PMTU 黑洞问题

**为什么会出现 PMTU 黑洞？**

两台主机通信时，整条链路上最小的 MTU 称为路径 MTU（Path MTU）。TCP 默认在 IP 头部打上 `DF`（Don't Fragment，禁止分片）标志，用来避免 IP 分片带来的性能损耗。

正常情况下，如果中间某台路由器的出接口 MTU 只有 1420（比如走了 VPN 隧道或 PPPoE 链路），遇到 1500 字节的大包无法转发：
1. 路由器把这个大包丢弃；
2. 路由器发回一个 ICMP 差错报文（Type 3 Code 4：`Fragmentation Needed`），并在报文里标明自己这跳的最大 MTU（1420）；
3. 发送端收到通知后，把到该目标的路由 MTU 缓存调小，以后改发 1420 字节以内的小包，连接恢复通畅。

但在现实中，很多防火墙直接配置了“阻断所有 ICMP”。中间路由器发出的 Type 3 Code 4 报文在半路被防火墙直接扔掉，导致发送端永远收不到“需要调小包体”的通知。发送端只知道丢包了，于是反复按 1500 字节的原尺寸超时重传，每次都在中途同一处被扔。这种收不到 ICMP 报错、大包持续无声丢弃的死锁状态，就被称为 **PMTU 黑洞**。

**典型表现：小包通，大包卡死**

- `ping`、SSH 交互、HTTP 简单请求都正常，因为这些包尺寸通常只有几十到几百字节，远低于限制；
- 传输大文件、加载大图，或者进行 HTTPS/TLS 握手（服务端发出的证书链通常超过 1500 字节）时，TCP 会把数据塞满 1500 字节发出去，导致大包直接卡死在路上，由于收不到任何明确拒绝的信号，程序只能干等超时。

**排查与解决办法**

1. **终端探测**：用指定尺寸且禁止分片的大包测试临界值：
   ```bash
   ping -M do -s 1472 -c 1 203.0.113.20  # 1472 数据 + 8 ICMP头 + 20 IP头 = 1500
   tracepath 203.0.113.20               # 自动探测沿途整条路径的 PMTU
   ```
2. **主机端开启自适应探测（RFC 4821）**：
   开启内核的 TCP MTU 探测。当协议栈检测到大包持续超时且怀疑遇到黑洞时，会主动调小 MSS 进行二分探测，不再依赖 ICMP 回包：
   ```bash
   sudo sysctl -w net.ipv4.tcp_mtu_probing=1
   ```
3. **网关/路由器开启 MSS 钳制（MSS Clamping）**：
   在网络边界设备上拦截 TCP 握手帧，把 SYN 报文里的 MSS 宣告值直接改小（比如强行钳制到 1400 以下），从源头规避大包出动：
   ```bash
   iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu
   ```

### 5.4 ICMP 的防雪崩铁律（RFC 1122 规范保证）

为了防止网络中形成无法平息的差错报文风暴，标准严厉规定在以下 4 种情况下**绝对禁止回复任何 ICMP 差错报文**：
1. **对 ICMP 差错报文本生，绝不生成差错报文**（防止两端路由器互相“报错”形成死循环乒乓球）；
2. **对目的地址为广播或多播的数据报，绝不回复差错**；
3. **作为链路层广播帧收到的数据报，绝不回复差错**；
4. **对非首片 IP 分片（Fragment Offset > 0），绝不回复差错**（只针对包含传输层首部字节的首片报错）。

## 6. 常见误区

- **误区 1：源主机把包丢给网关，是因为“只有路由器才能查路由表”？**  
  **错误。** 发送端主机内核自身就运行着完整的路由引擎（`ip route`）。跨网段通信时，是**主机自己在本地查表**算出下一跳应当交给默认网关 `192.168.1.1`，而不是把寻址逻辑盲目推给路由器。
- **误区 2：ARP 广播是去“向其他路由器打听”下一跳的 MAC？**  
  **错误。** ARP 广播（`ff:ff:ff:ff:ff:ff`）是在当前广播域内直接向**拥有该 IP 的对端设备本人**索要 MAC。无关机器看一眼目的 IP 不是自己就静默丢弃，只有当事人本人会单播应答。同时，**路由器物理隔离广播域**，ARP 广播绝不可能跨越路由器到达别的网段。
- **误区 3：交换机内部维护着 ARP 缓存表？**  
  **错误。** 普通二层交换机只有 **MAC 地址表（FDB，端口映射）**，它对 IP 头、ARP 映射一无所知。ARP 表（`ip neigh`）只存在于拥有 IP 地址的三层端点（主机与路由器）内核中。此外，**交换机转发以太网帧时，TTL 绝对不会减 1**。
- **误区 4：MAC 地址跨网段会端到端保留？**  
  **错误。** 数据报每经过一台路由器，以太网帧头就会被彻底剥掉并以新的下一跳 MAC 重写；只有 IP 首部中的源 IP 和目的 IP（在无 NAT 情况下）端到端保持不变。
- **误区 5：免费 ARP（Gratuitous ARP）只是为了宣告开机？**  
  **错误。** 免费 ARP 在工业界有两大命脉作用：① **地址冲突检测（ACD）**：网卡启用前先向自己的 IP 发 ARP，若有人应答说明 IP 冲突；② **高可用 VIP 漂移**：Keepalived / VRRP 主备切换时，新节点立即全网广播免费 ARP，强制刷新全网交换机的 MAC 学习表以及所有主机的 ARP 缓存。
- **误区 6：ping 测出的 RTT 对称，说明去程和回程走相同的物理路径？**  
  **错误。** 互联网中**不对称路由（Asymmetric Routing）**极其普遍。去程可能走骨干网经上海节点，回程走 BGP 经广州节点。两端操作系统初始 TTL（Linux 默认 64，Windows 默认 128）也不同，单向抓包看到的 TTL 只能反映该单向经过的跳数。

## 7. 动手验证

先看内核的决策结果，再看链路上的实际字节，两边能对上就说明整条流水线理解透了。

### 7.1 内核决策与全状态邻居表

```bash
ip -br addr                    # 网卡、IP 与状态，一行一个接口
ip link show eth0              # MAC 地址和 MTU
ip route get 203.0.113.20      # 内核对目标 IP 的完整决策路径（via 下一跳、dev 出接口、src 源 IP）
ip neigh show nud all          # 显示所有状态的邻居条目（REACHABLE / STALE / DELAY / FAILED）
```

### 7.2 观察 ARP 首包排队现象

在清空 ARP 缓存后发包，能直观观测到“没有 MAC 就封不出以太网帧，首个 IP 报文必须等 ARP 完成”的现象：

```bash
# 1. 强制清空 ARP 缓存
sudo ip neigh flush all

# 2. 抓取链路层 ARP 与 ICMP 报文时序
sudo tcpdump -i eth0 -n 'arp or icmp' -c 4 &
ping -c 1 192.168.1.1
```

输出严格呈现四步：`ARP Request（广播）` $\to$ `ARP Reply（单播）` $\to$ `ICMP Echo Request` $\to$ `ICMP Echo Reply`。

### 7.3 抓取 ICMP 差错报文的 8 字节截断

在终端中制造一个端口不可达，亲眼观察路由器/目标主机返回的 ICMP 报文如何嵌套原始载荷：

```bash
# 终端 1：详细捕获 ICMP 差错报文与引用的原始载荷
sudo tcpdump -i any -nnvvv 'icmp and (icmp[icmptype] = 3 or icmp[icmptype] = 11)'

# 终端 2：向目标主机未开启的 UDP 随机高端口发包
nc -u -z -v 192.168.1.1 54321
```

*抓包结果分析*：在 Wireshark 或 tcpdump 展开字段中，可以清晰看到 ICMP 报文内部完整的原包 IP 头及前 8 字节（包含刚才发送的 UDP 源端口与目标端口 `54321`），印证内核根据这 8 字节反查定位套接字并抛出 `ECONNREFUSED`。

### 7.4 探测路径 MTU 与探测黑洞

探测路径 MTU 可用置 DF 位的大包逐步二分测试：

```bash
# Linux 下用 -M do 锁定 DF 位，禁止分片
ping -M do -s 1472 -c 1 203.0.113.20     # 1472 (ICMP数据) + 8 (ICMP头) + 20 (IP头) = 1500 字节

# 或者直接使用原生无需 root 的 tracepath 工具自动化逐跳发现 PMTU
tracepath 203.0.113.20
```

当数据包超出中间链路 MTU 时，会收到 `Frag needed and DF set`（ICMP Type 3 Code 4），报文中还会直接回传那一跳链路的下一跳 MTU 上限值。

> [!note] `-M do` 是 Linux 的写法
> macOS 的 `ping` 用 `-D` 置 DF 位，参数含义不通用。本组笔记的命令都以 Linux 为准。

## 10. 关键要点

1. **四个协议是一条流水线**：IP 定目标和下一跳，ARP/NDP 把下一跳换成 MAC，Ethernet 把帧送到对面，ICMP 在出错时把消息带回来。
2. **MAC 逐跳重写，IP 端到端不变，TTL 每跳减 1**。抓包时先核对这三条，不符合就说明拓扑理解错了。
3. **下一跳 IP 只用来查 MAC**，从不写进 IP 头。区分不开这两个地址，跨网段的包为什么发得出去就想不通。
4. **ARP 直接装在 Ethernet 帧里**，EtherType `0x0806`，不经过 IP 层；ICMP 装在 IP 里，协议号 `1`，但没有端口。
5. **IPv6 把邻居解析并进了 ICMPv6**。IPv4 里封 ICMP 只是 ping 不通，IPv6 里封 ICMPv6 会让网络直接不可用。
