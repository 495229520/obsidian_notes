# 13.7 eventfd、timerfd与跨线程唤醒

## 1. 为什么需要 eventfd / timerfd

在 [[13.6 Reactor模式与EventLoop|Reactor 与 EventLoop]] 中，`EventLoop` 的主循环通常长这样：

```text
while (!quit) {
    activeChannels = poller.poll(timeout);

    for channel in activeChannels:
        channel.handleEvent();

    doPendingFunctors();
}
```

这里有一个关键问题：如果某个 worker 线程已经处理完业务，想把“发送响应”“关闭连接”“更新连接状态”这类任务投递回连接所属的 EventLoop，而这个 EventLoop 正阻塞在 `epoll_wait()` 里，任务什么时候才能被执行？

答案是：需要一个能被 `epoll` 监听的唤醒事件。

`eventfd` 和 `timerfd` 都是 Linux 把“非 socket 事件”变成文件描述符的机制：

| 机制 | 解决的问题 | 在 EventLoop 中的角色 |
|:---|:---|:---|
| `eventfd` | 线程之间发送轻量级通知 | 唤醒阻塞在 `epoll_wait()` 的 EventLoop |
| `timerfd` | 定时器到期通知 | 把定时任务纳入 `epoll` 事件循环 |

> [!note] 核心定位
> `eventfd` 让“跨线程通知”变成 fd 可读事件，`timerfd` 让“时间到期”变成 fd 可读事件。
>
> 它们和 socket 一样都可以注册进 `epoll`，从而被同一个 EventLoop 统一调度。

Linux 里这样的机制不止这两个，`signalfd`、`inotify` 走的也是同一条路，见下文 5.2。

## 2. eventfd：跨线程唤醒 EventLoop

`eventfd` 创建一个带 64 位无符号计数器的文件描述符，常用于线程间事件通知。

```c
#include <sys/eventfd.h>

int eventfd(unsigned int initval, int flags);
```

### 2.1 常用 flags

| flag | 说明 |
|:---|:---|
| `EFD_NONBLOCK` | 设置为非阻塞，避免读写卡住 EventLoop |
| `EFD_CLOEXEC` | 设置 close-on-exec，避免 fd 泄漏到子进程 |
| `EFD_SEMAPHORE` | 每次 read 只减 1，较少用于 EventLoop 唤醒 |

在网络库中常见写法是：

```cpp
int wakeupFd = eventfd(0, EFD_NONBLOCK | EFD_CLOEXEC);
```

> [!tip]
> 新代码优先使用 `EFD_NONBLOCK | EFD_CLOEXEC`。这和 `epoll_create1(EPOLL_CLOEXEC)`、`accept4(SOCK_NONBLOCK | SOCK_CLOEXEC)` 的工程思路一致：创建 fd 时就设置好关键属性。

### 2.2 读写语义

`eventfd` 内部可以理解成一个计数器：

| 操作 | 行为 |
|:---|:---|
| `write(eventfd, &value, 8)` | 把 `value` 加到内核计数器上 |
| `read(eventfd, &value, 8)` | 读出当前计数器，并把计数器清零 |
| 非阻塞读空 | 返回 `-1`，`errno` 为 `EAGAIN` |

普通模式下，如果计数器当前是 5，一次 `read()` 会读出 5，并把计数器清零。EventLoop 唤醒通常不关心“被唤醒了几次”，只关心“现在应该去处理 pending functors 了”，所以这种读清空语义正好合适。

```cpp
uint64_t one = 1;
write(wakeupFd, &one, sizeof(one));

uint64_t value = 0;
read(wakeupFd, &value, sizeof(value));
```

> [!warning] 必须读 eventfd
> `eventfd` 被 `epoll` 通知可读后，EventLoop 要调用 `read()` 消费这个事件。
>
> 如果只处理 pending functors 而不读 `eventfd`，fd 会一直保持可读，后续 `epoll_wait()` 会反复返回，造成无意义唤醒。

### 2.3 三条容易踩的硬性约束

**读写长度必须正好是 8 字节。** `eventfd` 的 `read()` / `write()` 不接受任意长度，缓冲区小于 8 字节直接返回 `-1`，`errno` 为 `EINVAL`。所以下面这种写法是错的：

```cpp
uint32_t one = 1;                       // 只有 4 字节
write(wakeupFd, &one, sizeof(one));     // EINVAL，唤醒没发出去
```

必须用 `uint64_t`。这个错误的隐蔽之处在于：没检查 `write()` 返回值的话，程序不会崩，只会表现成“任务投递了但 EventLoop 一直不醒”。muduo 里这行的写法是判断返回值不等于 8 就打日志。

**计数器上限不是 `UINT64_MAX`。** 内核允许的最大值是 `0xfffffffffffffffe`，留了一个值给“溢出”状态。写入会导致超过上限时，阻塞 fd 会阻塞在 `write()`，非阻塞 fd 返回 `EAGAIN`。用作 EventLoop 唤醒时每次只加 1，正常来说撞不到这个上限；但如果 `read()` 那一侧漏了，累积久了就会——这也是“必须读”的另一个理由。

**`EFD_SEMAPHORE` 改的是读语义，不是写语义。**

| 模式 | `read()` 读出什么 | 读完计数器变成 |
|:---|:---|:---|
| 默认 | 当前计数（比如 5） | 0 |
| `EFD_SEMAPHORE` | 恒为 1 | 当前值 - 1 |

信号量模式下，计数没减到 0 之前 fd 一直保持可读。EventLoop 唤醒要的是“醒来一次，把队列扫干净”，不需要知道被投递了几次，所以用默认的读清空语义正好；用 `EFD_SEMAPHORE` 反而会让 `epoll_wait()` 为同一批任务反复返回。

## 3. queueInLoop 的唤醒流程

在 one loop per thread 模型中，一个连接的状态应该由它所属的 EventLoop 线程修改。其他线程想操作连接时，不应该直接改连接对象，而应该把任务投递给对应 EventLoop。

典型流程可以抽象成：

```text
worker 线程
    生成一个任务 functor
    加锁放入 loop.pendingFunctors
    write(eventfd) 唤醒 loop

EventLoop 线程
    epoll_wait() 因 eventfd 可读返回
    read(eventfd) 消费唤醒事件
    doPendingFunctors()
    在 loop 线程内修改连接状态
```

这就是 `queueInLoop()` 需要唤醒机制的原因：它不仅要把任务放进队列，还要保证正在睡眠的 EventLoop 尽快醒来处理队列。

### 3.1 runInLoop 和 queueInLoop 的区别

| 接口 | 常见语义 | 是否一定唤醒 |
|:---|:---|:---|
| `runInLoop(cb)` | 如果当前就在 loop 线程，直接执行；否则投递 | 跨线程投递时需要唤醒 |
| `queueInLoop(cb)` | 总是放入 pending functors 队列 | 跨线程或正在执行 functor 时通常需要唤醒 |

简化伪代码：

```cpp
void EventLoop::queueInLoop(Functor cb) {
    {
        std::lock_guard<std::mutex> lock(mutex_);
        pendingFunctors_.push_back(std::move(cb));
    }

    if (!isInLoopThread() || callingPendingFunctors_) {
        wakeup();
    }
}

void EventLoop::wakeup() {
    uint64_t one = 1;
    write(wakeupFd_, &one, sizeof(one));
}

void EventLoop::handleRead() {
    uint64_t value = 0;
    read(wakeupFd_, &value, sizeof(value));
}
```

### 3.2 唤醒条件里的 callingPendingFunctors_ 是干什么的

`queueInLoop()` 里的判断条件有两半，第二半特别容易被当成多余的：

```cpp
if (!isInLoopThread() || callingPendingFunctors_) {
    wakeup();
}
```

第一半好理解：不在 loop 线程，说明它可能正睡着，得叫醒。

第二半是说：**即使就在 loop 线程里，只要现在正在跑 `doPendingFunctors()`，也得写一次 `eventfd`**。原因在于 `doPendingFunctors()` 的实现方式：

```cpp
void EventLoop::doPendingFunctors() {
    std::vector<Functor> functors;
    callingPendingFunctors_ = true;

    {
        std::lock_guard<std::mutex> lock(mutex_);
        functors.swap(pendingFunctors_);   // 整个队列一次性搬走
    }

    for (const Functor& functor : functors) {
        functor();                          // 无锁执行
    }

    callingPendingFunctors_ = false;
}
```

`swap` 之后 `pendingFunctors_` 已经空了，本轮要跑的任务都在局部的 `functors` 里。如果某个 functor 执行过程中又调了 `queueInLoop()`，新任务只会进到已经被清空的 `pendingFunctors_`——**本轮的 `for` 循环扫不到它**。不写 `eventfd` 的话，这个任务就得一直等到下次真的有 I/O 事件才被执行，在一个空闲的服务器上可能是几十秒。

### 3.3 为什么要先 swap 再执行

`swap` 同时解决两个问题：

**缩短临界区。** 锁只按住一次 `vector::swap`（交换三个指针），functor 本身的执行完全在锁外。如果直接持锁遍历执行，一个耗时 10ms 的 functor 就会把其他线程的 `queueInLoop()` 阻塞 10ms。

**避免死锁。** functor 里再调 `queueInLoop()` 是完全合法的用法（比如“发完响应后关连接”）。持锁执行的话，`queueInLoop()` 会尝试第二次加同一把非递归的 `std::mutex`，直接死锁。

**锁只用来保护队列这个数据结构，不用来保护队列里内容的执行。**

> [!warning] 不要跨线程直接操作连接
> worker 线程处理完业务后，应该把“写响应”“关闭连接”等操作投递回连接所属 EventLoop。
>
> 直接跨线程修改连接对象，容易引入竞态、悬空指针和状态错乱。

### 3.4 投递的是任务，不是指针

跨线程投递还有一个容易忽略的地方：functor 捕获的往往是 `TcpConnection*`，而任务真正执行时，这条连接可能已经关掉了。

```cpp
// 危险：conn 是裸指针，执行时可能已经析构
loop->queueInLoop([conn, msg] { conn->send(msg); });
```

安全的写法是捕获 `shared_ptr`，或者捕获 `weak_ptr` 再在 functor 里 `lock()`：

```cpp
// 捕获 shared_ptr：任务在队列里排队时也把连接续着命
loop->queueInLoop([connPtr, msg] { connPtr->send(msg); });

// 捕获 weak_ptr：不续命，执行时连接没了就什么都不做
loop->queueInLoop([weakConn, msg] {
    if (auto conn = weakConn.lock()) {
        conn->send(msg);
    }
});
```

选哪个取决于语义：**“这条响应必须发出去”用 `shared_ptr`，“连接还在就发，没了就算”用 `weak_ptr`。** 两种写法的区别和 [[13.6.1 回调函数与Reactor事件分发]] 里 `Channel::tie_` 的取舍是同一件事——详细的所有权划分见 [[13.8 连接对象生命周期与RAII]]。

## 4. timerfd：把时间事件变成 fd

`timerfd` 可以创建一个定时器文件描述符。定时器到期后，这个 fd 会变成可读，因此可以直接加入 `epoll`。

```c
#include <sys/timerfd.h>

int timerfd_create(int clockid, int flags);

int timerfd_settime(int fd,
                    int flags,
                    const struct itimerspec *new_value,
                    struct itimerspec *old_value);
```

### 4.1 创建 timerfd

常见写法：

```cpp
int timerFd = timerfd_create(CLOCK_MONOTONIC,
                             TFD_NONBLOCK | TFD_CLOEXEC);
```

| 参数 | 常见选择 | 说明 |
|:---|:---|:---|
| `clockid` | `CLOCK_MONOTONIC` | 单调时间，不受系统时间被手动修改影响 |
| `flags` | `TFD_NONBLOCK` | 非阻塞，避免 EventLoop 卡住 |
| `flags` | `TFD_CLOEXEC` | 避免 fd 泄漏到子进程 |

### 4.2 设置一次性和周期定时

`timerfd_settime()` 使用 `itimerspec` 描述定时器：

```c
struct itimerspec {
    struct timespec it_interval;  // 周期；为 0 表示一次性
    struct timespec it_value;     // 第一次到期时间；为 0 表示停止
};
```

| 字段 | 含义 |
|:---|:---|
| `it_value` | 第一次什么时候到期 |
| `it_interval` | 到期后是否按周期重复触发 |

一次性定时器可以把 `it_interval` 设为 0；周期定时器则把 `it_interval` 设为固定间隔。

`it_value` 有一个容易被忽略的特殊值：**把 `it_value` 整个置 0 就是停表**，无论 `it_interval` 设成什么。这是取消一个已经 arm 的 timerfd 的唯一方式，不需要 close 再重建：

```cpp
struct itimerspec stop = {};      // 两个字段全 0
timerfd_settime(timerFd, 0, &stop, nullptr);
```

`timerfd_settime()` 的第二个参数 `flags` 决定 `it_value` 怎么解读：

| flags | `it_value` 的含义 | 什么时候用 |
|:---|:---|:---|
| `0` | 相对当前时刻的偏移（“3 秒后”） | 周期任务、心跳间隔 |
| `TFD_TIMER_ABSTIME` | 绝对时刻（“到 12:00:00 时”） | timer queue 直接填最近到期时间戳 |

muduo 的 `TimerQueue` 用的是相对时间：算出“最近的定时器还有多久到期”，再 arm 一次 timerfd。用 `TFD_TIMER_ABSTIME` 可以省掉这次相减，代价是要和 `clock_gettime()` 取的时钟保持同一个 `clockid`。

### 4.3 clockid 选 MONOTONIC 还是 REALTIME

| clockid | 特点 | 场景 |
|:---|:---|:---|
| `CLOCK_MONOTONIC` | 从开机起单调递增，不受 `date -s` 或 NTP 跳变影响 | 超时、心跳、间隔计时，网络库的默认选择 |
| `CLOCK_REALTIME` | 跟随系统墙上时间，会被手动改时间或 NTP 拉动 | 必须对齐日历时刻的任务（“每天零点结算”） |

选错的后果很具体：用 `CLOCK_REALTIME` 做 60 秒心跳超时，运维把系统时间往前调了一小时，所有连接会在同一瞬间被判定超时并集体断开。

如果确实需要 `CLOCK_REALTIME`，`timerfd_settime()` 可以加 `TFD_TIMER_CANCEL_ON_SET`（要配合 `TFD_TIMER_ABSTIME`）：系统时间被不连续地修改时，这个 timerfd 的 `read()` 会返回 `ECANCELED`，应用据此知道“刚才那次计时作废了，需要重算”，而不是默默地早到或晚到。

### 4.4 到期后的 read 语义

定时器到期后，`timerfd` 会变成可读。应用需要读取一个 `uint64_t`：

```cpp
uint64_t expirations = 0;
read(timerFd, &expirations, sizeof(expirations));
```

`expirations` 表示自上次 read 之后累计到期了多少次。如果 EventLoop 忙了一段时间，周期定时器可能已经到期多次，这个值就可能大于 1。

![[图片/3.Linux/13. IO复用/13_7_2.svg|1390]]

**这个数是“欠账”，不是“通知”。**图上那个例子里，100ms 周期的定时器碰上一次 320ms 的慢回调，内核已经数到 3，EventLoop 才回到 `epoll_wait()`。这时该跑几次回调，标准不管，得自己定：

- **心跳、超时检查**：跑一次就够，然后重排下一次。检查连接是否超时这类操作是幂等的，补跑三遍没有意义，反而放大了慢回调的影响。
- **计费、采样、限流令牌桶**：需要按 `expirations` 补齐，否则统计口径会随负载漂移。
- **绝对不能做的**：不 read。LT 模式下 fd 会一直保持可读，`epoll_wait()` 立刻返回，整条 loop 空转跑满一个核。

> [!tip] timerfd 只是触发器
> `timerfd` 负责把“最近一次到期时间”变成 fd 事件。
>
> 多个业务定时任务如何排序、取消、重复调度，通常还需要最小堆、时间轮或 timer queue。连接心跳和超时管理会在 [[13.9 定时器、心跳与连接超时]] 继续展开。

## 5. eventfd / timerfd 与 epoll 集成

从 `epoll` 的视角看，`eventfd`、`timerfd` 和 socket fd 没有本质区别：它们都是可以等待的文件描述符。

典型注册方式：

```cpp
struct epoll_event ev;
ev.events = EPOLLIN;
ev.data.fd = wakeupFd;
epoll_ctl(epfd, EPOLL_CTL_ADD, wakeupFd, &ev);

ev.events = EPOLLIN;
ev.data.fd = timerFd;
epoll_ctl(epfd, EPOLL_CTL_ADD, timerFd, &ev);
```

事件分发时按 fd 或 Channel 找到对应 handler：

```text
epoll_wait() 返回
    |
    |-- listen_fd 可读  -> accept 新连接
    |-- conn_fd 可读    -> recv 数据
    |-- conn_fd 可写    -> flush output buffer
    |-- eventfd 可读    -> 读取 eventfd，执行 pending functors
    |-- timerfd 可读    -> 读取 timerfd，执行 timer callback
```

> [!note] 与 epoll 的关系
> `epoll` 仍然只是通知“这个 fd 可读了”。
>
> 对 `eventfd` 来说，可读表示有人写入了唤醒计数；对 `timerfd` 来说，可读表示定时器到期了。真正的任务执行仍在 EventLoop 回调里完成。

这和 [[13.4 epoll模型|epoll 模型]] 的核心定位一致：`epoll_wait()` 负责发现就绪事件，Reactor / EventLoop 负责把事件分发到正确的处理逻辑。

### 5.1 ET 模式下这两个 fd 更要读干净

如果 wakeup fd 或 timerfd 用 `EPOLLET` 注册，“必须 read”就从“避免空转”升级成“避免丢事件”。ET 只在状态**变化**时通知一次：计数器从 0 变成非 0 时报一次，之后哪怕又被 `write()` 加了几次，也不会再报。没读干净的话，剩下的计数会静静躺在那里，直到下一次从 0 跳变——而如果一直没人写，就再也不会有通知了。

网络库里 wakeup channel 通常用 LT（默认），因为每次都读干净是本来就要做的事，LT 少一层“是否读干净”的心智负担。真要用 ET，`read()` 必须循环到返回 `EAGAIN`。ET 和 LT 的完整语义差别见 [[13.4 epoll模型]]。

### 5.2 「把 X 变成 fd」是 Linux 的一贯套路

`eventfd` 和 `timerfd` 不是两个孤立的 API，它们属于同一个设计思路：**Reactor 只会等 fd，那就把所有需要等的东西都做成 fd。**

| 机制 | 把什么变成了 fd | 传统替代方案的问题 |
|:---|:---|:---|
| `eventfd` | 线程间通知 | 条件变量不能进 epoll |
| `timerfd` | 定时器到期 | `SIGALRM` / `setitimer` 走信号，异步且难和 epoll 配合 |
| `signalfd` | 信号（`SIGINT`、`SIGCHLD` 等） | 信号处理函数只能调异步信号安全的函数，能做的事极少 |
| `inotify` | 文件系统变化 | 只能轮询 `stat()` |
| `epoll` 自身 | 一组 fd 的就绪状态 | 使得 epoll 可以嵌套 |

这个套路的价值在于**事件源的统一**。一旦所有等待点都变成 fd，主循环就只需要一个 `epoll_wait()`——不需要既等条件变量又等 socket，也不需要在信号处理函数里设标志位再回主循环轮询。`signalfd` 是其中最能说明问题的一个：优雅退出如果靠 `SIGTERM` 的信号处理函数，函数里几乎什么都不能做（不能加锁、不能 `printf`），只能设一个 `volatile sig_atomic_t` 标志；换成 `signalfd` 之后，收信号就变成了一次普通的 `handleRead()`，里面想干什么干什么。

## 6. 常见工程陷阱

| 问题 | 后果 | 正确做法 |
|:---|:---|:---|
| `eventfd` 可读后不 read | fd 持续可读，EventLoop 反复被唤醒 | 在 wakeup channel 的 read handler 中消费计数 |
| `timerfd` 到期后不 read | 定时事件持续触发，可能造成空转 | read 出 `expirations` 后再执行回调 |
| 使用阻塞 fd | 读写空计数或异常路径可能卡住 EventLoop | 创建时使用 `EFD_NONBLOCK` / `TFD_NONBLOCK` |
| 跨线程直接修改连接 | 竞态、状态错乱、对象生命周期问题 | 通过 `runInLoop()` / `queueInLoop()` 投递回所属 loop |
| 把 `timerfd` 当成完整定时器系统 | 无法管理大量业务定时任务的排序、取消、重复调度 | `timerfd` 配合 timer queue、最小堆或时间轮 |
| 忘记 close fd | fd 泄漏 | 用 RAII 封装 fd 生命周期 |
| `write(eventfd)` 传 4 字节 | 返回 `EINVAL`，唤醒根本没发出去，任务卡在队列里 | 必须用 `uint64_t`，并检查返回值是否等于 8 |
| 漏掉 `callingPendingFunctors_` 条件 | functor 里投递的新任务要等到下次有 I/O 才跑 | 唤醒条件写全：不在本线程 **或** 正在跑 functor |
| 持锁执行 pending functors | 临界区变长；functor 里再投递会死锁 | 先 `swap` 到局部 vector，出锁后再无锁执行 |
| functor 捕获裸 `TcpConnection*` | 任务排队期间连接可能已关闭，执行时是悬空指针 | 捕获 `shared_ptr`（续命）或 `weak_ptr`（执行前探活） |
| `timerfd` 用 `CLOCK_REALTIME` 做超时 | 系统时间被调整时，所有连接同时误判超时 | 用 `CLOCK_MONOTONIC`；必须用日历时间时加 `TFD_TIMER_CANCEL_ON_SET` |
| ET 模式下没把 fd 读干净 | 剩余计数不会再触发通知，事件彻底丢失 | wakeup channel 用 LT；用 ET 就循环读到 `EAGAIN` |

## 7. 面试问法

| 问题 | 回答要点 |
|:---|:---|
| `eventfd` 解决什么问题？ | 把线程间通知变成 fd 可读事件，用于唤醒阻塞在 `epoll_wait()` 的 EventLoop。 |
| 为什么不用条件变量唤醒 EventLoop？ | EventLoop 正在 `epoll_wait()` 等 fd 事件；`eventfd` 可以加入同一个 epoll 集合，统一事件来源。 |
| `eventfd` 内部是什么模型？ | 内核维护一个 64 位计数器，write 累加，普通 read 读出并清零。 |
| `timerfd` 解决什么问题？ | 把定时器到期变成 fd 可读事件，让定时任务可以纳入 epoll/Reactor。 |
| `timerfd` read 出来的值是什么？ | 自上次 read 后累计到期次数，周期定时器中可能大于 1。 |
| 为什么 `timerfd` 常用 `CLOCK_MONOTONIC`？ | 单调时间不受系统墙上时间调整影响，更适合超时和间隔计时。 |
| `eventfd` / `timerfd` 是异步 I/O 吗？ | 不是。它们只是产生可读事件，具体处理仍由 EventLoop 回调完成。 |
| worker 线程处理完业务如何回写？ | 把写任务投递回连接所属 EventLoop，并通过 `eventfd` 唤醒它。 |
| 为什么用 `eventfd` 而不是 `pipe`？ | `pipe` 占两个 fd 且有真实缓冲区可能写满；`eventfd` 只占一个，内部是计数器累加。 |
| `eventfd` 读写为什么必须是 8 字节？ | 内核实现固定按 `uint64_t` 收发，长度不足直接返回 `EINVAL`。 |
| `EFD_SEMAPHORE` 和默认模式差在哪？ | 默认 read 读出全部计数并清零；信号量模式每次只读出 1 并减 1，fd 会保持可读。 |
| `doPendingFunctors()` 为什么先 swap？ | 缩短临界区到一次指针交换，并让 functor 里再调 `queueInLoop()` 不会死锁。 |
| `callingPendingFunctors_` 那个条件是干什么的？ | 队列已被 swap 清空，此时新投递的任务本轮扫不到，必须写 eventfd 保证下一轮及时跑。 |
| `TFD_TIMER_ABSTIME` 什么时候用？ | `it_value` 要按绝对时刻解读时；timer queue 直接填最近到期时间戳可省一次相减。 |
| 怎么取消一个已经 arm 的 timerfd？ | `it_value` 整个置 0 再调 `timerfd_settime()`，不需要 close 重建。 |
| `signalfd` 和这两个是什么关系？ | 同一套设计思路：把非 fd 的事件源变成 fd，让主循环只用一个 `epoll_wait()` 等所有东西。 |

## 8. 关键要点

1. `eventfd` 把跨线程通知变成 fd 可读事件，常用于唤醒 EventLoop。
2. `timerfd` 把定时器到期变成 fd 可读事件，常用于把时间事件纳入 `epoll`。
3. 选 `eventfd` 而非 `pipe`，是因为它只占一个 fd、内部只有一个计数器、不会被写满。
4. `eventfd` 和 `timerfd` 都应该使用非阻塞和 close-on-exec 标志。
5. `eventfd` 的 `read()` / `write()` 长度必须正好 8 字节，否则返回 `EINVAL`。
6. `eventfd` 普通模式下 read 会读出当前计数并清零；`EFD_SEMAPHORE` 改的是读语义，不适合唤醒场景。
7. `timerfd` read 出来的 `uint64_t` 是累计到期次数，是“欠了几次”而不是“现在到期了”。
8. `eventfd` / `timerfd` 可读后都必须 read 消费事件：LT 下不读会空转，ET 下不读干净会丢事件。
9. 跨线程操作连接时，应通过 `runInLoop()` / `queueInLoop()` 投递回所属 EventLoop，且 functor 不要捕获裸指针。
10. `doPendingFunctors()` 先 `swap` 再无锁执行：既缩短临界区，也避免 functor 里再投递时死锁。
11. 唤醒条件是“不在本线程 **或** 正在跑 functor”，后半个条件漏了会让新任务卡到下次有 I/O 事件。
12. 超时和心跳一律用 `CLOCK_MONOTONIC`，避免系统时间调整导致连接集体误判超时。
13. `timerfd` 只是定时触发器，复杂心跳、超时和定时器容器需要额外的数据结构。
