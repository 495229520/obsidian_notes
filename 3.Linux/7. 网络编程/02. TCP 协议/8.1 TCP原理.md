# 8.1 TCP 原理

## 1. 概述

TCP（Transmission Control Protocol，传输控制协议）是面向连接的、可靠的、基于字节流的传输层通信协议，广泛应用于 HTTP、SMTP、FTP 等上层协议。

## 2. TCP/IP 网络模型

TCP/IP 协议栈采用分层设计，每一层负责不同的通信抽象：

| 层次 | 协议示例 | 主要功能 |
|:---|:---|:---|
| 应用层 | HTTP、SMTP、FTP、DNS | 为用户提供网络服务接口 |
| 传输层 | TCP、UDP | 提供端到端的数据传输服务 |
| 网络层 | IP | 负责数据包的路由和转发 |
| 链路层 | 以太网、WiFi | 在相邻节点间传输数据帧 |
| 物理层 | 双绞线、光纤 | 传输原始比特流 |

## 3. TCP 与 UDP 对比

TCP 和 UDP 是传输层的两种主要协议，设计权衡截然不同：

| 特性 | TCP | UDP |
|:---|:---|:---|
| **连接性** | 面向连接（需三次握手） | 无连接 |
| **可靠性** | 可靠传输（确认、重传、序号校验） | 不可靠（尽最大努力交付） |
| **传输方式** | 字节流（无消息边界） | 数据报（保留消息边界） |
| **拥塞控制** | 有（根据网络状态动态控速） | 无 |
| **传输效率** | 开销较大（头部至少 20 字节、维持连接状态） | 开销较小（头部仅 8 字节） |
| **适用场景** | 文件传输、网页浏览、远程终端 | 实时音视频、DNS 查询、低延迟游戏 |

### 3.1 TCP 的核心特性

- **面向连接**：通信前必须通过三次握手建立连接，通信结束时通过四次挥手断开连接。
- **可靠传输**：通过序列号、确认应答、超时重传、校验和与数据去重保证不丢、不乱、不重。
- **全双工通信**：连接双方各自拥有独立的发送缓冲区与接收缓冲区，可同时收发。
- **流量控制**：通过滑动窗口机制限制在途数据量，防止对端接收缓冲区溢出。
- **拥塞控制**：根据网络拥塞程度动态调整发送窗口，避免网络崩溃。

## 4. TCP 报文段结构

代码中操作的是 `read()`、`write()`、`connect()`、`accept()` 等系统调用，而网络中实际传输的是 TCP 报文段。

理解 TCP 报文段，核心在于确立一个原则：**TCP 维护的是连续字节流，而不是离散的数据包。** 序号和确认号均以字节为单位递增。

### 4.1 序列号 Seq：标记首字节编号

`Seq`（Sequence Number）记录当前报文段所携带数据的**第一个字节在整个发送字节流中的位置**。

假设客户端发送字符串 `Hello`（5 字节），起始字节编号为 `1000`：

| 字节内容 | `H` | `e` | `l` | `l` | `o` |
|:---|:---:|:---:|:---:|:---:|:---:|
| 字节编号 | 1000 | 1001 | 1002 | 1003 | 1004 |

该报文段的 `Seq = 1000`，数据载荷长度为 5 字节。区间表示为 `[1000, 1005)`。即使应用数据被拆分为多个 TCP 报文段发送，每个报文段依然按其所含首字节标记 `Seq`。

![[图片/3.Linux/8. TCP 编程/3_8_1_4.svg|900]]

### 4.2 确认号 Ack：累计确认机制

`Ack`（Acknowledgment Number）表示接收方**期望收到的下一个字节编号**。它同时代表该编号之前的所有连续字节均已完整接收。

接上例，接收方顺利收到 `1000 ~ 1004` 字节后，回传的 `Ack` 为 `1005`。

- 若字节连续到达，`Ack` 随接收进度向右推进：`Ack = Seq + Len`。
- 若中间出现丢包缺口（如收到了 1000~1004，随后收到了 1010~1015，但缺失了 1005~1009），接收方的 `Ack` 会停在 `1005`，不会越过缺口。

![[图片/3.Linux/8. TCP 编程/3_8_1_5.svg|900]]

### 4.3 为什么按字节编号而不是按包编号？

TCP 面向的是无边界的字节流。应用层单次 `write()` 的数据可能被网络栈拆分为多个 TCP 报文，多次小数据 `write()` 也可能被合并为单个报文。

若按“包”编号，拆包、粘包和乱序重传时无法精确定位哪些字节已达、哪些字节丢失。按字节编号，接收方只需依据 `Seq` 在接收缓冲区中拼装字节，就能自然完成去重与乱序重组。

### 4.4 控制标志位 Flags

TCP 首部包含 6 个核心标志位，用于控制连接状态与报文类型：

| 标志位 | 全称 | 说明 |
|:---|:---|:---|
| `SYN` | Synchronize | 发起连接，用于同步初始序号（ISN） |
| `ACK` | Acknowledgment | 确认号有效，除首个 SYN 包外几乎所有 TCP 报文均置 1 |
| `FIN` | Finish | 发送方数据已发送完毕，请求关闭该方向的连接 |
| `RST` | Reset | 复位连接，用于异常终止或拒绝连接 |
| `PSH` | Push | 提示接收方应尽快将缓冲区数据提交给应用层，减少排队延迟 |
| `URG` | Urgent | 紧急指针字段有效（现代编程中较少使用） |

### 4.5 为什么 SYN 和 FIN 消耗一个序号？

`SYN` 和 `FIN` 虽然不携带应用载荷数据，但它们是需要对端可靠确认的控制状态变更。为了将它们纳入 ACK 确认重传机制，TCP 规定它们各自占用一个逻辑序号：

- 发送 `SYN(seq=x)`，对端确认时的 `ack = x + 1`
- 发送 `FIN(seq=y)`，对端确认时的 `ack = y + 1`

普通 ACK 报文本质上是对序号的确认，如果不携带数据，则不消耗序号（下一个报文的 `Seq` 不会因纯 ACK 递增）。

### 4.6 报文首部结构与读包口诀

TCP 报文由固定首部（20 字节）、可选字段以及数据载荷组成：

![[图片/SVG/3_7_7_5_1.svg|1390]]

抓包排查时的读包思路：
- **Seq**：看本段数据从哪个字节开始。
- **Ack**：看对方下次该从哪个字节发。
- **Flags**：看当前报文处于建连、确认还是断连阶段。
- **Window**：看接收方当前还能容纳多少字节（限制发送额度）。

## 5. TCP 通信流程与生命周期

### 5.1 三次握手：双向可达性确认

TCP 是全双工协议，建立连接时必须确认双向均具备正常收发能力，并同步双方各自的初始序列号（ISN）。

![[图片/3.Linux/8. TCP 编程/3_8_1_3.svg|900]]

**握手过程与状态变迁：**

1. **第一次握手（SYN）**：
   客户端调用 `connect()`，向服务器发送 `SYN=1, seq=x`，进入 `SYN_SENT` 状态。
   *证明：客户端有发送能力。*
2. **第二次握手（SYN + ACK）**：
   服务器收到 SYN，回复 `SYN=1, ACK=1, seq=y, ack=x+1`，进入 `SYN_RCVD` 状态。
   *证明：服务器能正常接收客户端数据，且服务器具备发送能力。*
3. **第三次握手（ACK）**：
   客户端收到响应，向服务器发送 `ACK=1, seq=x+1, ack=y+1`，双方均进入 `ESTABLISHED` 状态。
   *证明：客户端能正常接收服务器数据，双向闭环完成。*

**为什么两次握手不够？**
若仅有两次握手，客户端若发送过一个滞留在网络中的旧 SYN 包，在旧连接结束后该包若终于到达服务器，服务器会误以为是新连接并立即建立（分配资源）。而客户端此时并未发起请求，不会理睬服务器响应，导致服务器端出现悬挂的单向无效连接。三次握手要求客户端完成最终确认，确保双方都确认这次建连是当前有效的。

### 5.2 数据传输：重传与流量控制

连接进入 `ESTABLISHED` 后，双方即可通过 `write()` / `read()` 传输数据。

#### 超时重传（丢包恢复）

当发送方发出一批报文后，会启动重传定时器（RTO，Retransmission TimeOut）。若在定时器到期前未收到对应的累计 ACK，发送方即判定数据丢失，自动以相同的原 `Seq` 重新发送该区间数据。

![[图片/3.Linux/8. TCP 编程/3_8_1_6.svg|900]]

#### 滑动窗口（流量控制）

接收方的应用层读取速度若低于网络到达速度，接收缓冲区会被填满。TCP 通过首部中的 `Window` 字段通告接收窗口大小（`rwnd`），告知发送方当前缓冲区尚能容纳多少字节。

![[图片/3.Linux/8. TCP 编程/3_8_1_7.svg|900]]

发送缓冲区被滑动窗口划分为四个逻辑区域：
1. **已发送并已确认**：处于窗口左侧，可从发送队列释放。
2. **已发送未确认**：处于窗口内，正在网络中传输，等待 ACK。
3. **允许发送但尚未发送**：处于窗口内，属于接收方允许发送的剩余额度。
4. **暂不可发送**：超过窗口右边界，必须等待对端确认推进窗口后方可发送。

收到新的 ACK 时，窗口左边界向右滑动，允许更多新数据进入可发送区间。

### 5.3 四次挥手：全双工安全断开

全双工通信意味着通信双方各有一条单向的数据通道，两个方向必须分别独立关闭。

![[图片/3.Linux/8. TCP 编程/3_8_1_8.svg|900]]

**挥手过程与状态变迁：**

1. **第一次挥手（FIN）**：
   主动关闭方（以客户端为例）调用 `close()`，发送 `FIN=1, seq=u`，进入 `FIN_WAIT_1` 状态，表明客户端数据已全部发出。
2. **第二次挥手（ACK）**：
   被动方收到 FIN，回复 `ACK=1, ack=u+1`，进入 `CLOSE_WAIT` 状态。客户端收到 ACK 后进入 `FIN_WAIT_2`。
   此时连接处于**半关闭（Half-Close）**状态：客户端不再发送数据，但仍可接收服务器发来的数据。
3. **第三次挥手（FIN）**：
   被动方处理完残留数据后调用 `close()`，发送 `FIN=1, seq=w`，进入 `LAST_ACK` 状态，通知客户端己方数据也已发完。
4. **第四次挥手（ACK）**：
   主动方收到 FIN，回复 `ACK=1, ack=w+1`，随后进入 `TIME_WAIT` 状态。被动方收到该 ACK 后立即进入 `CLOSED`。

**为什么需要 TIME_WAIT（持续 2MSL）？**
- **确保最终 ACK 送达**：若第四次挥手的 ACK 在网络中丢失，被动方会重传 FIN。主动方处在 `TIME_WAIT` 状态方可重新发送 ACK；若主动方已过早关闭，被动方重传的 FIN 将触发 RST 异常。
- **让残留报文在网络中自然消亡**：防止上一个连接的延迟报文在新连接中重现并造成数据污染。经过 2 个最大报文段寿命（2MSL）后，网络中残存的旧报文均已失效。

### 5.4 TCP 连接全生命周期总览

![[图片/3.Linux/8. TCP 编程/3_8_1_14.svg|1062]]

整个生命周期由三次握手启动，在 `ESTABLISHED` 状态下通过 Seq/Ack 机制维持可靠字节流传输，最后由四次挥手优雅断开连接。

### 5.5 Socket API 与底层交互映射

应用层通过 Socket API 与内核 TCP 协议栈进行交互：

#### 服务器端调用时序

| 步骤 | 系统调用 | 对应的 TCP 行为 |
|:---:|:---|:---|
| 1 | [[7.7 套接字#2. socket 函数\|socket()]] | 创建套接字结构体及默认缓冲区 |
| 2 | [[7.7 套接字#4. bind 函数\|bind()]] | 绑定本机 [[7.2 IP地址与CIDR\|IP地址]] 与 [[7.3 端口与五元组\|端口号]] |
| 3 | [[7.8 listen和accept函数#3. listen 函数\|listen()]] | 套接字进入被动监听状态（LISTEN），初始化半连接队列与全连接队列 |
| 4 | [[7.8 listen和accept函数#4. accept 函数\|accept()]] | 从已完成三次握手的全连接队列中取出一个已就绪的连接，返回新套接字 |
| 5 | `read()` / `write()` | 从接收缓冲区读取数据 / 将数据写入发送缓冲区 |
| 6 | `close()` | 发送 FIN，触发挥手流程 |

#### 客户端调用时序

| 步骤 | 系统调用 | 对应的 TCP 行为 |
|:---:|:---|:---|
| 1 | [[7.7 套接字#2. socket 函数\|socket()]] | 创建套接字结构体 |
| 2 | `connect()` | 触发 TCP 三次握手，阻塞等待服务器 ACK 直至连接建立（ESTABLISHED） |
| 3 | `write()` / `read()` | 将数据写入发送缓冲区 / 从接收缓冲区读取数据 |
| 4 | `close()` | 发送 FIN，触发连接断开 |

## 6. TCP 服务器编程要点

### 6.1 端口选择

- **知名端口（0 – 1023）**：由 IANA 分配，绑定需要 root 权限，参见 [[7.3 端口与五元组#2.1 知名端口（0 – 1023）|知名端口]]。
- **注册端口（1024 – 49151）**：供用户进程与常用服务使用。
- **动态端口（49152 – 65535）**：客户端临时端口范围，服务器应避免固定绑定该范围。

### 6.2 地址复用 SO_REUSEADDR

服务器主动关闭连接或异常崩溃重启时，原监听端口可能处于 `TIME_WAIT` 状态（默认持续数十秒至数分钟），导致立即重启时绑定报 `Address already in use` 错误。

```c
int opt = 1;
setsockopt(sockfd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));
```

在 `bind()` 之前设置 `SO_REUSEADDR` 选项，允许套接字重新绑定处于 `TIME_WAIT` 状态的本地地址与端口。

### 6.3 监听队列 backlog

`listen(sockfd, backlog)` 中的 `backlog` 参数决定了内核全连接队列的大小（Linux 2.2 之后）。在高并发突发建连场景下，若队列设置过小，超出队列上限的新连接请求可能被丢弃或回复 RST。

## 7. TCP 可靠性关键机制总结

| 机制 | 解决的问题 | 实现方式 |
|:---|:---|:---|
| **序列号（Seq）** | 字节乱序、重复包 | 每个数据字节按序标号，接收端据此按序拼装并去重 |
| **确认号（Ack）** | 丢包感知、状态同步 | 累计确认机制，通告下一个期待接收的字节编号 |
| **超时重传（RTO）** | 报文丢失无法到达 | 发送端启动定时器，超时未收确认则重发对应区间 |
| **流量控制（Flow Control）** | 接收端处理不过来溢出 | 接收端通过 `rwnd` 通告剩余接收能力，发送端按窗口限速 |
| **拥塞控制（Congestion Control）** | 中间路由器网络拥堵丢包 | 动态维护拥塞窗口 `cwnd`，通过慢启动、拥塞避免、快重传快恢复调节 |

---

## 8. 核心要点

- **面向字节流**：TCP 没有应用层的消息边界，Seq 和 Ack 跟踪的是字节偏移量，而非数据包个数。
- **建连三次，断连四次**：建连需确保双向收发能力并防范历史旧 SYN；断连因全双工特性需要两侧分别关闭。
- **TIME_WAIT 是主动关闭方的职责**：等待 2MSL 以确保最后 ACK 到达且旧报文消亡。
- **端到端控流**：实际发送量由接收方窗口与网络拥塞窗口的最小值共同决定：`min(rwnd, cwnd)`。
