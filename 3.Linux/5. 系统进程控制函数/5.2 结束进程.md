## 简介

进程自己走的终止出口有四个：从 `main` 返回、`exit()`、`_exit()`、`abort()`。它们的区别不在「进程死没死」，而在**死之前 libc 替你做了多少收尾**。

---

## 1. exit() 和 _exit() - 终止进程

### 函数原型

```c
#include <stdlib.h>
void exit(int status);

#include <unistd.h>
void _exit(int status);
```

### 功能对比

| 函数 | 头文件 | 清理操作 | 特点 |
|------|--------|----------|------|
| `exit()` | `<stdlib.h>` | 执行 | 标准 C 库函数，会执行清理操作 |
| `_exit()` | `<unistd.h>` | **不执行** | 系统调用，立即终止进程 |

![[图片/SVG/3_5_5_2_1.svg|1387]]

图 A 把整条路摊平了：`exit()` 从最左边进，依次走完 atexit、刷流、删临时文件三段，最后落到 `_exit(2)`；`_exit()` 从下面直接绕过去。两者的差别都发生在用户态。进了内核以后，收尾动作相同，父进程 `wait` 到的状态也看不出区别。

`return 0;` 和 `exit(0)` 走同一条路，从 `main` 返回等价于把返回值交给 `exit()`。差别只有一个：`return` 会先销毁 `main` 里的局部变量，`exit()` 不会。写 C 时基本无所谓，写 C++ 时就是析构函数跑不跑的问题。

### exit() 的清理操作

`exit()` 在真正终止进程前依次做这些事：

1. **调用 `atexit()` / `on_exit()` 注册的函数**：按注册的**逆序**执行
2. **刷新所有打开的输出流**：缓冲区里的数据这时才写出去
3. **关闭所有打开的流**
4. **删除 `tmpfile()` 创建的临时文件**
5. **调用 `_exit()`**：交给内核收尾

### 内核那一半

无论从哪个出口进来，落到 `_exit(2)` 后，内核做的事都一样：

1. **关闭所有文件描述符**
2. **释放进程占用的内存**
3. **向父进程发送 `SIGCHLD` 信号**
4. **把退出状态留在 `task_struct` 里**，等父进程来取（见 [[5.5 等待函数]]）

### 代码示例

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

void cleanup(void) {
    printf("Cleanup function called.\n");
}

int main() {
    atexit(cleanup);  // 注册清理函数

    printf("This message is in buffer");  // 注意：没有换行符，数据在缓冲区

    // 使用 exit() - 会刷新缓冲区并调用 cleanup
    exit(0);

    // 如果使用 _exit(0)，则：
    // 1. 不会打印 "This message is in buffer"
    // 2. 不会调用 cleanup()

    return 0;  // 不会执行到这里
}
```

### 何时使用 _exit()

在常见的 `fork() + exec()` 模式里，子进程只要没有进入 `exec` 的新程序就要退出，使用 `_exit()`。最典型的情况是 `exec` 失败后。

原因就是图 B 那三帧。`printf` 的数据先落在用户态缓冲区里，`fork()` 复制内存时也复制了这块缓冲区。子进程再调 `exit()`，第 ② 格会刷出它那份副本；父进程稍后又刷自己的，同一段文字就出现两遍：

```c
printf("hi\n");        // 终端上这行就刷出去了；重定向到文件则留在缓冲区
if (fork() == 0)
    exit(0);           // 换成 _exit(0) 就不会多刷一份
wait(NULL);
exit(0);
```

```
$ ./a.out           →  hi          （stdout 是行缓冲，fork 时缓冲区已经空了）
$ ./a.out > f.txt   →  f.txt 里是两行 hi
```

同一个程序接终端时正常，一重定向就出 bug。原因是 stdout 从行缓冲变成了全缓冲，`fork()` 时缓冲区不再是空的。

`_exit()` 跳过第 ② 格，子进程那份副本随地址空间一起丢掉，输出只出现一次。

还有一件事：`fork()` 也会复制 `atexit()` 注册的信息。子进程走 `exit()` 时会再跑一遍父进程的清理逻辑。释放连接、写日志、删文件这类操作跑两次，后果比多打一行字严重得多。

```c
pid_t pid = fork();
if (pid == 0) {
    // 子进程
    execlp("nonexistent", "nonexistent", NULL);
    // exec 失败
    perror("exec failed");
    _exit(1);  // 使用 _exit() 而非 exit()
}
```

`exec` 成功后，整个地址空间会被新程序替换，旧的缓冲区和 `atexit()` 注册信息也随之消失。只有 `exec` 失败、子进程继续执行旧程序时，才需要走 `_exit()` 这条退出路径。

## 2. atexit() - 注册退出处理函数

### 函数原型

```c
#include <stdlib.h>

int atexit(void (*function)(void));
```

### 功能

`atexit()` 只负责注册。程序正常终止时，运行库再调用已注册的函数，也就是走 `exit()` 或从 `main()` 返回这两条路。`_exit()`、`abort()` 和被信号终止都不会触发它。
`atexit()` 需要自己调用来注册退出处理函数：

```
atexit(cleanup1);
atexit(cleanup2);
atexit(cleanup3);
```

注册完成后，程序调用 `exit()`，或者从 `main()` 返回时，libc 会按注册顺序的逆序执行：

```
注册：cleanup1 → cleanup2 → cleanup3
执行：cleanup3 → cleanup2 → cleanup1
```

也就是 LIFO，后注册的先执行。

如果从未调用过 `atexit()`，`exit()` 就没有这一步可执行，直接继续刷新 stdio、删除 `tmpfile()` 文件，然后进入 `_exit()`。
### 特点

- **逆序执行**：后注册的先跑（LIFO）
- **同一个函数注册几次就跑几次**
- **不接参数、没有返回值**：想带上下文只能用全局变量，或者改用 `on_exit()`
- **数量上限**：POSIX 只要求实现至少支持 32 个（`ATEXIT_MAX`），glibc 是动态分配的，实际不设上限。别在代码里依赖某个具体数字

处理函数里再次调用 `exit()` 是未定义行为。确实需要立刻结束进程时，用 `_exit()`。

### 返回值

| 返回值 | 含义 |
|--------|------|
| `0` | 成功 |
| 非零 | 失败 |

### 代码示例

```c
#include <stdio.h>
#include <stdlib.h>

void cleanup1(void) {
    printf("Cleanup 1: Releasing resources...\n");
}

void cleanup2(void) {
    printf("Cleanup 2: Closing connections...\n");
}

void cleanup3(void) {
    printf("Cleanup 3: Saving state...\n");
}

int main() {
    // 注册顺序：1, 2, 3
    atexit(cleanup1);
    atexit(cleanup2);
    atexit(cleanup3);

    printf("Main function executing...\n");
    printf("Exiting normally.\n");

    return 0;  // 或 exit(0)
}
```

### 运行结果

```
Main function executing...
Exiting normally.
Cleanup 3: Saving state...
Cleanup 2: Closing connections...
Cleanup 1: Releasing resources...
```

逆序不是随便定的：后注册的清理函数往往依赖先注册的那些还没被拆掉。3 → 2 → 1 的顺序保证释放的方向和获取的方向相反。

## 3. on_exit() - 扩展的退出处理函数（非标准）

### 函数原型

```c
#include <stdlib.h>

int on_exit(void (*function)(int, void *), void *arg);
```

### 功能

`on_exit()` 也注册退出处理函数，只是处理函数能多收两个参数：

- **status**：传给 `exit()` 的状态码
- **arg**：注册时给的自定义指针

它和 `atexit()` 共用同一张注册表。两者混着注册时，仍按整体注册顺序倒着跑。

### 代码示例

```c
#include <stdio.h>
#include <stdlib.h>

void my_exit_handler(int status, void *arg) {
    printf("Exit status: %d, Message: %s\n", status, (char *)arg);
}

int main() {
    on_exit(my_exit_handler, "Goodbye!");

    printf("Program running...\n");

    exit(42);  // 退出状态码为 42
}
```

### 运行结果

```
Program running...
Exit status: 42, Message: Goodbye!
```

### 注意事项

> **警告**：`on_exit()` 是 GNU 扩展，不在 C 标准和 POSIX 里，macOS 和 BSD 上没有。要跨平台就用 `atexit()`，上下文靠全局变量传。

## 4. abort() - 异常终止进程

### 函数原型

```c
#include <stdlib.h>

void abort(void);
```

### 功能

给自身发送 `SIGABRT`，沿信号这条路终止，对应图 A 最下面那根线。

### 特点

- **拦不住**：`abort()` 先把 `SIGABRT` 从阻塞信号集里放出来再 `raise`。就算装了处理函数并从里面正常返回，它也会把信号处置恢复成默认再发一次，进程照样死
- **不调用 `atexit()` 注册的函数**
- **不刷新 stdio 缓冲区**：C 标准把这条留给实现，glibc 从 2.27 起明确不刷。所以 `abort()` 前面那句 `printf` 很可能根本没落盘，排查时改用 `fprintf(stderr, ...)`，stderr 是无缓冲的
- **留下 core dump**：前提是 `ulimit -c` 不为 0
- 父进程 `wait` 到的是 `WIFSIGNALED` 为真、`WTERMSIG` 返回 6

### 使用场景

- 检测到不可恢复的错误
- 断言失败（`assert()` 内部就是调它）
- 程序走到了本不该到达的分支

### 代码示例

```c
#include <stdio.h>
#include <stdlib.h>

void check_critical_condition(int value) {
    if (value < 0) {
        fprintf(stderr, "Critical error: negative value!\n");
        abort();  // 异常终止
    }
}

int main() {
    check_critical_condition(-1);
    printf("This won't be printed.\n");
    return 0;
}
```

例子里用 `fprintf(stderr, ...)` 而不是 `printf` 有原因：`abort()` 不刷 stdout 缓冲区，错误信息走 stdout 就可能丢失。

## 5. 进程退出状态

### 退出状态码约定

| 状态码 | 含义 | 谁定的 |
|--------|------|--------|
| `0` | 成功 | C 标准（`EXIT_SUCCESS`） |
| `1` | 一般错误 | 惯例 |
| `2` | 命令行用法错误 | 惯例 |
| `126` | 文件找到了但不能执行 | shell |
| `127` | 命令没找到 | shell |
| `128+N` | 被信号 N 终止 | shell |

后三行由 shell 换算，不是内核直接给出的结果。`128+N` 只存在于 `echo $?`；父进程用 `waitpid` 拿到的 `status` 中，信号编号单独放在低 7 位。两套编码别混。

### 获取退出状态

父进程用 [[5.5 等待函数|wait() 或 waitpid()]] 来取。拿到的 `status` 不是退出码本身，`exit(42)` 之后它等于 10752，必须过一遍宏：

| 宏 | 功能 |
|----|------|
| `WIFEXITED(status)` | 是不是正常退出 |
| `WEXITSTATUS(status)` | 取退出码，范围 0 到 255 |
| `WIFSIGNALED(status)` | 是不是被信号终止 |
| `WTERMSIG(status)` | 取终止信号的编号 |

退出码只有 8 位，`exit(-1)` 父进程读回来是 255。位布局的细节见 [[5.5 等待函数#5. status：先问死法，再取值|5.5 的第 5 节]]。

## 6. 总结对比

| 出口 | atexit 函数 | 刷 stdio 缓冲区 | 删 tmpfile | 使用场景 |
|------|-------------|------------------|------------|----------|
| `return`（从 main） | 调用 | 刷 | 删 | main 里正常返回 |
| `exit()` | 调用 | 刷 | 删 | 任意位置正常退出 |
| `_exit()` / `_Exit()` | 不调 | 不刷 | 不删 | fork 后子进程的失败路径 |
| `abort()` | 不调 | 不刷 | 不删 | 不可恢复的错误，留 core |

`_Exit()` 是 C99 标准里和 `_exit()` 等价的那个名字，不需要 `<unistd.h>`，跨平台时用它。

---

## 关键要点

- 四个出口的区别**全在用户态**：内核那半段（关 fd、还内存、发 SIGCHLD、留退出状态）谁走都一样
- **`exit()` 做三件事**：逆序跑 atexit 函数、刷新并关闭 stdio 流、删 `tmpfile()` 的临时文件，然后才调 `_exit()`
- **`fork()` 会连 stdio 缓冲区一起复制**，子进程走 `exit()` 会把副本再刷一遍，同一段输出打两次。接终端时是行缓冲看不出来，一重定向到文件就暴露
- 所以，在 `fork() + exec()` 模式中，子进程的 `exec` 失败路径用 `_exit()`；这样也能避开父进程的 atexit 函数被跑第二遍
- **`atexit()` 逆序执行**，只在 `exit()` 和 `main` 返回时触发；数量上限 POSIX 只保证 32 个，glibc 不设限
- **`abort()` 拦不住**：处理函数返回后它会恢复默认处置再发一次。glibc 2.27 起不刷缓冲区，排错信息走 stderr
- `echo $?` 里的 `128+N` 是 shell 的换算，和 `waitpid` 拿到的 `status` 不是一套编码
- 退出状态码 0 表示成功，非零表示失败，且只有 8 位
