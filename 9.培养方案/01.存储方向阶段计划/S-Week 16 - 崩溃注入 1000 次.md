# S-Week 16 - 崩溃注入 1000 次

> [!goal] 本周目标
> 回答"你怎么知道你的恢复代码是对的"：搭一个自动化崩溃注入框架，随机时刻 kill -9 正在写入的引擎，重启恢复，校验"已应答的必须都在、未应答的可丢不可坏"，循环 1000 次零丢失——总纲 S2 验收的硬性指标。这周大概率会挖出真 bug，修 bug 的过程本身就是面试故事。

## 学习目标

1. **不变量怎么定义？** committed（已应答）⊆ recovered（恢复后可见）⊆ attempted（已发起）；外加完整性约束：恢复后每条记录 CRC 合法、无半条记录存活。
2. **oracle 怎么建？** 父进程 fork 出引擎子进程；子进程每次收到 put 应答后把 (key, seq) 写进应答管道，父进程收到才记为 committed——oracle 活在父进程内存里，不受子进程崩溃影响。
3. **kill -9 测的是什么、不测什么？** 测进程崩溃一致性（fsync 时机、应答顺序、恢复逻辑）；不测断电——已 write 进 page cache 的数据内核仍会落盘。断电语义需要 dm-flakey / dm-log-writes 或虚拟机断电，本周做边界声明，可选加分实测。
4. **随机注入怎么可复现？** 固定并记录随机种子；失败样本自动归档（log 文件 + 种子 + 注入时刻），否则修 bug 无从下手。
5. **危险窗口在哪？** append 完成但 fsync 未完成、fsync 完成但应答未发出、everysec 的后台刷间隙、compaction rename 中间态。注入时刻要覆盖它们：按操作计数随机 + 按时间随机两种模式都要有。

## 1. 注入框架（Day 1-2）

- `crash_test` driver：fork 引擎子进程跑随机 workload（put / delete / overwrite 混合、随机 value 大小），父进程随机延迟后发 SIGKILL。
- 重启引擎 → 全库扫描 → 校验三条不变量。
- 单轮流程脚本化：一条命令跑完"起进程 → 杀 → 恢复 → 校验 → 出结果"。

## 2. 1000 次循环与修 bug（Day 3-4）

- `scripts/crash_loop.sh`：循环 + 进度输出 + 失败自动归档。
- 典型 bug 候选（自查清单）：应答早于 fsync、恢复时 tombstone 处理错、批内部分持久化后 offset 错位、everysec 线程与 writer 的竞争。
- 每个 bug 记进 `docs/crash_bugs.md`：现象 → 根因 → 修法 → 回归测试。格式沿用 [[S-Week 9 - eBPF 观测]] 的事故记录风格。

## 3. 语义边界与报告（Day 5）

- fsync=always：1000 次注入必须零"已应答丢失"。
- everysec / os 档：跑出"允许丢但不允许坏"的统计——丢的条数是否落在契约承诺的窗口内（对照 S-Week 14 的契约矩阵）。
- `docs/crash_injection.md`：框架图 + 不变量定义 + 结果表 + kill -9 vs 断电的边界声明。

## 4. 推理保温（约 25%）

- 维护态：复习 [[Week 8 - Prefill Decode + Open Source Repro]] 的 PD 分离与 KV transfer 要点——S-Week 20 学 RDMA 时会接上这条线。

## 面试问题

- 崩溃发生在 log 写完但 index 没更新时怎么办？你的引擎和 RocksDB 各怎么处理？
- kill -9 和拔电源，对你的测试意味着什么差别？
- 你的 oracle 为什么可信？它自己崩了怎么办？
- 1000 次都过了，能说恢复代码没 bug 吗？还缺什么？
- 讲一个你注入出来的真实 bug。
