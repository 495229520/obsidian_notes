# S-Week 25 - KV offload 三档对照与收支对账

> [!goal] 本周目标
> S4 的核心实验周：纯显存 / +CPU 内存 / +本地 NVMe 三档对照跑完，TTFT 与命中率两条主曲线出图，并与 [[KV cache offload 专题 - 收支公式与临界点]] 的收支公式逐项对账——实测节省 vs 公式预测，偏差归因到命中率、重叠度、带宽争抢、调度开销四关。本周的产出直接回答总纲报告的第 4/8 题："KV cache 什么时候值得 offload 到 SSD"。

## 学习目标

1. **对账的分子分母是什么？** 公式预测的每次命中节省 = 命中 token 数 × 每 token 重算时间 − 读回时间；实测节省 = 三档 TTFT 差值。两者对不上时，差额去了哪就是本周的分析工作。
2. **四关偏差各长什么样？** 命中率不足（复用没发生）、读回未与计算重叠（串行等待放大读回成本）、并发争抢（多请求同时读回挤 PCIe/盘）、调度与索引开销（查找、分块、反序列化）。
3. **TPOT 为什么是干扰探测器？** 设计上 offload 不该碰解码；TPOT 变差 = 读回流量抢了资源——用 iostat 时间线对齐 TPOT 时间线归因，方法就是 S-Week 9 的"后台流量伤前台"。
4. **NVMe 档和 CPU 档的差距该是什么形态？** 读回带宽差一个量级（PCIe DRAM ~30 GB/s vs 单盘 ~5-7 GB/s），但只要都跨过临界带宽，TTFT 收益都该显著——差距主要在高并发争抢下拉开。
5. **结论怎么写才诚实？** 按负载分开给（多轮对话收益大 / 控制组零收益且开销可测）、按档位给临界条件，不给单一"快 X%"。

## 1. 三档对照（Day 1-3）

- 矩阵：三档后端 × 四类负载（S-Week 24 的负载集）× 显存压力两档（装得下 / 装不下），每组 3 次。
- 记录：逐请求 TTFT、TPOT、吞吐、LMCache 命中率、`iostat`（NVMe 档）、`nvidia-smi` 显存与利用率采样。
- 中间检查（Day 2 晚）：多轮对话组的 NVMe 档 TTFT 相对纯显存驱逐场景应有肉眼可见改善——没有就停下来查（命中没发生 / 配置没生效 / 显存压力不足），别把三天租期烧在坏实验上。

## 2. 收支对账（Day 4）

- 公式侧：用本机型实测的 prefill 每 token 耗时（harness 有）与 KV 每 token 字节数，算出预测节省与临界带宽。
- 实测侧：三档 TTFT 差值按命中 token 数归一化。
- 对账表：每类负载一行——预测节省 / 实测节省 / 偏差 / 归因（四关里的哪一关，附证据：命中率数字、iostat 峰值、时间线对齐图）。
- 干扰专项：挑一个 TPOT 变差的时段，用 iostat 时间线对齐归因——S1 的观测能力在 GPU 场景变现的现场。

## 3. 主图与章节落稿（Day 5）

- 主图两张：TTFT（分档分负载的箱线/分位）与命中率-收益散点（命中率横轴、TTFT 节省纵轴——收益随命中率的走势一图胜千言）。
- `ai_data_path_report.md` 核心章节落稿："KV cache 什么时候值得 offload 到 SSD"——答案结构：临界带宽口算 + 实测对账 + 负载形态前提 + 边界（单卡、7-8B 模型、租用机型）。
- 与 [[Week 8 - Prefill Decode + Open Source Repro]] 连线一段：本实验是单机分层版，Mooncake 的跨节点 KV 流转是它的集群版——RDMA 单边写（S-Week 20）就是那条路的数据面。
