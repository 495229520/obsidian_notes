# S-Week 24 - KV offload 环境与负载构造

> [!goal] 本周目标
> 搭起 S4 核心实验的舞台：vLLM + LMCache 环境就绪，[[Week 5 - Serving Benchmark Harness]] 对接完成，设计出能区分"命中收益"与"offload 成本"的负载集，并跑出纯显存基线。本周不出结论，只保证下周的三档对照踩在干净的地基上——对照组设计错了，S4 整个实验就废了。

## 学习目标

1. **vLLM 自带的前缀缓存和 LMCache 差在哪？** vLLM 的 automatic prefix caching 命中发生在**显存内**；LMCache 把命中范围扩展到显存外（CPU 内存/磁盘/远端）。对照组必须把这两层分开，否则收益归因全错。
2. **负载要构造出什么形态？** 高复用组（多轮对话、共享系统提示）让命中有的放矢；控制组（相互独立的一次性请求）证明"没有复用时 offload 不帮忙也不添乱"。
3. **怎么让 offload 有意义？** KV 必须先溢出显存——限制 `gpu_memory_utilization` 或拉高并发与上下文长度，制造真实的驱逐压力；显存装得下时测出来的都是空话。
4. **TTFT 和 TPOT 各测什么？** TTFT 吃 prefill（命中直接省它）；TPOT 吃解码（设计上不该被 offload 影响，变差就是干扰信号）。
5. **命中率从哪来？** LMCache 的统计接口/日志 + harness 侧按请求记录——两边对得上才可信。

## 1. 环境搭建（Day 1-2）

- vLLM 起服务（模型选 7-8B 量级，单卡够用且口算基数熟悉）；LMCache 按当期文档接入 vLLM（connector 配置以当期版本为准，版本号进 `env.md`）。
- 三档存储后端逐档冒烟：纯显存（LMCache 关闭）/ +CPU 内存 / +本地 NVMe——每档发一条长 prompt 确认功能路径，NVMe 档用 `iostat` 确认真有盘流量（防"配置了但没生效"的假实验）。
- harness 对接：Week 5 的发压与指标管线接上 vLLM endpoint，TTFT/TPOT/吞吐三指标出数。

## 2. 负载集设计（Day 3）

| 负载 | 构造 | 用途 |
|---|---|---|
| 多轮对话 | 同前缀累积追问 8-16 轮 × N 个会话 | 命中收益的主战场 |
| 共享系统提示 | 长 system prompt（数 K token）× 多用户不同问题 | 前缀部分命中 |
| 控制组 | 相互独立的随机 prompt | 零复用下的 offload 开销底噪 |
| 长上下文 | 8K-32K 单轮 | 显存压力与驱逐行为 |

- 每类负载参数化进 harness 配置（轮数、会话数、上下文长度、并发），发压可复现。
- 显存压力档位：调 `gpu_memory_utilization` 或并发数，构造"KV 装得下 / 装不下"两种状态——下周对照的关键变量。

## 3. 纯显存基线（Day 4-5）

- 两组基线都要：vLLM 前缀缓存关 / 开（都不带 LMCache）——先量出"显存内命中"本身值多少，下周 LMCache 的增量才有分母。
- 每类负载 × 两组基线 × 3 次，记录 TTFT 分布（逐请求进 CSV）、TPOT、吞吐、显存占用（`nvidia-smi` 采样）、驱逐/命中计数。
- 交叉验证：多轮对话组开启前缀缓存后 TTFT 应显著下降——不降说明负载构造没造出复用，回去修负载而不是继续跑。
