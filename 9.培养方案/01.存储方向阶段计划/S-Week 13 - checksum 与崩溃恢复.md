# S-Week 13 - checksum 与崩溃恢复

> [!goal] 本周目标
> 给每条 record 加 CRC 校验，把"重启重放"升级成"面对损坏文件也能恢复到一致状态"：尾部半条记录截断、中间位翻转拒读。再手工制造 5 类损坏样本做恢复测试矩阵——这是 mini-kv-engine "crash consistency" 故事的第一章。

## 学习目标

1. **checksum 防什么？** 介质位翻转、torn write（一条记录只写了一半）、错位读——凡是"读出来的字节和写进去的不一样"的故障。
2. **checksum 防不了什么？** 写之前内存里就已损坏的数据（garbage in）、逻辑 bug（把值写给了错的 key）、整条记录干净地消失。
3. **torn write 怎么发生？** 一条 record 跨多个扇区/页，崩溃时只有一部分持久化；单个扇区（512B/4K）的写通常是原子的，跨扇区不保证。
4. **恢复策略为什么是"截断尾部"而不是"跳过坏块继续"？** append-only log 里一条坏记录之后再没有可信的对齐锚点；截断到最后一条完整记录，保证前缀一致性。
5. **CRC 怎么选、盖住哪些字节？** 用 crc32c（有 SSE4.2 硬件加速，RocksDB 同款）；覆盖 header + payload，crc 字段本身除外。

## 1. CRC 集成（Day 1-2）

- 写路径：序列化时计算 crc32c 填入头部。
- 读路径：`get` 与恢复扫描都做校验，失败返回明确的错误类型（区分"没找到"和"数据损坏"）。
- 单测：好记录读回、坏记录拒读。
- `docs/record_format.md` 更新 CRC 覆盖范围与字节序。

## 2. 恢复逻辑升级（Day 2-3）

启动扫描逐条校验，遇到以下任一情况停止并截断到最后一条完整记录：

- 长度字段越界（超出文件剩余长度或超过上限）。
- CRC 校验失败。
- 尾部不足一个完整 header。

截断动作打日志：从哪个 offset 截、丢弃了多少字节。之后引擎正常提供服务。

## 3. 损坏注入矩阵（Day 4-5）

用 `dd` / `truncate` 制造 5 类样本，每类跑一次恢复并核对预期：

| 损坏类型 | 制造方式 | 预期恢复行为 |
|---|---|---|
| 尾部截一半 | truncate 到记录中间 | 截断该记录，前缀完整 |
| payload 翻 1 bit | dd 定点改写 | 该记录拒读；若在尾部则截断 |
| header 翻 1 bit | dd 定点改写 | 同上，长度解析失败也能兜住 |
| 长度字段改超大 | dd 定点改写 | 越界检测触发，不越界读 |
| 文件清空 | truncate 0 | 空库启动，不崩溃 |

产出 `docs/recovery_notes.md`：故障模型表（防什么 / 防不了什么 / 防不了的靠谁）+ 5 类样本的实测结果。

可选加分：简版 compaction——离线合并出新 log 后用原子 rename 切换（rename 后要 fsync 目录，为什么留到 S-Week 14 讲）。
