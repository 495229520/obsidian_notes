# S-Week 15 - group commit 与多线程写入

> [!goal] 本周目标
> 打破"每条 put 一次 fsync"的吞吐天花板：多线程并发提交汇聚到单 writer，攒批一次 fsync、集体应答（group commit）。这是 v1 的核心并发设计，也是 RocksDB write group 的等价物。产出一条延迟-吞吐权衡曲线，TSAN 全绿。

## 学习目标

1. **group commit 为什么能提吞吐？** 小 IO 场景下 fsync 按次收费不按字节收费；N 条请求共享一次 fsync，吞吐近似乘 N。代价是每条请求的应答延迟里多了攒批等待。
2. **为什么单 writer 而不是多 writer 抢锁？** append-only log 的 offset 分配必须串行；单 writer + 队列把竞争点从文件挪到内存队列，而且请求在队列里天然聚成批。
3. **攒批参数怎么定？** max_batch_size 和 max_wait_us 双条件先到先触发；等待窗口太大 p50 变差，太小批攒不满、吞吐上不去。
4. **等待应答的线程怎么被唤醒？** 条件变量 + 批次序号（世代号）；要处理虚假唤醒（谓词循环）和一次唤醒一批的惊群成本。
5. **TSAN 能抓什么、抓不了什么？** 抓数据竞争（happens-before 违反）；抓不了 fsync 时机错误这类持久化语义 bug——所以 S-Week 16 还要崩溃注入。

## 1. 并发写路径设计（Day 1-2）

- 结构：提交线程把请求放入**有界** MPSC 队列，writer 线程取一批 → 序列化 → 一次 append → 按策略 fsync → 按世代号集体唤醒。
- 队列直接复用 [[17.6 并发队列：有界队列与无锁队列]] 的有界阻塞队列即可，无锁不是必需——先正确后快。
- `design_note.md` 记录备选方案与否决理由：每线程独立 log？多 writer + 分段锁？为什么都不如单 writer。

## 2. 实现与正确性（Day 3-4）

- 实现攒批与集体应答；`sync_policy` 三档与攒批正交（always 档收益最大）。
- 单测：并发 put 后全量 get 一致、批边界正确（攒批不改变单条语义）、delete 与 put 交错。
- 工具 gate：TSAN 与 ASAN 全绿；压测下无丢应答、无重复应答。

## 3. 权衡实测（Day 5）

- 负载：fsync=always，4K value，提交线程数 1 / 4 / 16，攒批开 / 关，每组 3 次。
- 记录吞吐 + p50 / p99 应答延迟，画曲线。
- 攒批吞吐的粗略模型（B 为每批平均聚合条数，正文用数据验证）：

$$
T_{group} \approx \frac{B}{t_{fsync}}
$$

- 预期形态：开 group commit 后吞吐随并发上涨，直到盘的 fsync 能力饱和；p99 随等待窗口抬升。不符合就解释。

## 4. 推理保温（约 25%）

- 维护态：KV cache 三道口算保手感（每 token KV 字节数、prefix cache 命中收益、offload 读回临界点）。
