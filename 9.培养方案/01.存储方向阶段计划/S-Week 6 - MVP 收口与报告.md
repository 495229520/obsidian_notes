# S-Week 6 - MVP 收口与报告

> [!goal] 本周目标
> 不学新东西。把前五周的实验在同一环境下统一重跑、写成一份可复现的 `benchmark_report.md`、配好 `reproduce.sh`，让 `linux-io-lab` 从"一堆实验"变成"一个能放上简历的项目"。收口质量直接决定下周投递的成色。

## 学习目标

1. **什么叫可复现？** 新机器上按 README 跑 `reproduce.sh` 能得到同量级结果。
2. **什么叫可信？** 每个结论都能点回原始 CSV/JSON；波动大的数据有解释而不是被删掉。
3. **什么叫诚实？** 报告写清限制（单机、单文件系统、云环境邻居噪声），Agent 生成与人工验证的部分分开声明。

## 1. 统一重跑（Day 1-3）

同一台机器、同一内核、同一文件系统，一次性重跑五组核心实验，每组 3 次：

| 实验 | 来源 |
|---|---|
| 冷/热 page cache 读（顺序/随机） | [[S-Week 1 - 环境搭建 + Page Cache 基线]] |
| buffered vs O_DIRECT | [[S-Week 2 - O_DIRECT + 持久化语义]] |
| write / fsync / fdatasync / 批量 fsync | [[S-Week 2 - O_DIRECT + 持久化语义]] |
| read vs mmap vs io_uring（QD 1/8/32） | [[S-Week 4 - mmap 与读路径对比]]、[[S-Week 5 - io_uring 异步 IO]] |
| fio 对照矩阵（精选 12 组） | [[S-Week 3 - fio 对照与 Benchmark Matrix]] |

规则（与推理版 benchmark 可信度标准一致）：

- 3 次重复间波动 > 10% 的组必须解释（邻居噪声？温度？cache 状态没清干净？），解释不了就标注为不确定，不得只留最好看的一次。
- `env.md` 更新为收口环境的最终版本。
- 原始数据全部保留在 `results/final/`，图表脚本从原始数据生成，禁止手改。

## 2. 报告与工程化（Day 4-6）

### 2.1 `benchmark_report.md` 结构

```text
1. 环境（机器/内核/盘/文件系统/工具版本）
2. 方法（负载定义、重复次数、warmup、计时口径）
3. 结果
   3.1 page cache：冷/热差 N 倍（图）
   3.2 三条读路径对比：read / mmap / io_uring 选型矩阵（图）
   3.3 持久化代价：fsync 策略吞吐差 N 倍（图）
   3.4 QD 扫描：吞吐饱和点与 p99 起飞点（图）
4. 结论（每条一句话 + 指向数据）
5. 限制与不确定性（云环境、单盘、单文件系统、非稳态 SSD）
6. Agent 使用声明（哪些是生成的、哪些是人工验证的）
```

### 2.2 `reproduce.sh`

从裸 Ubuntu 到全部结果的一键脚本：装依赖 → 编译 → 生成测试文件 → 跑五组实验 → 输出汇总表。破坏性步骤（drop_caches）前打印提示。用一台新租的机器实际验证一遍——这半小时的租金是这个项目可信度的价格。

### 2.3 README 定稿

- 一段话讲清项目回答了什么问题（不是"我学了什么"）。
- 关键图表直接嵌入。
- 明确写出 Agent 生成部分（CMake、脚本、图表）与人工部分（核心代码、结论判断）。

## 5. 本周产出文件

| 文件 | 内容 | 验收方式 |
|---|---|---|
| `results/final/` | 统一重跑的全部原始数据 | 不手动修改 |
| `docs/benchmark_report.md` | 六段式总报告 | 新读者 15 分钟能看懂结论 |

## 6. 验收标准

- [ ] 五组实验统一重跑完成，波动异常均有解释或标注。
- [ ] `reproduce.sh` 在一台新机器上验证通过。
- [ ] 报告六段齐全，限制与 Agent 声明诚实。
- [ ] 所有图表可从原始数据重新生成。
- [ ] 仓库对外可读：陌生人 clone 后知道从哪看起。
- [ ] 推理保温和面试保底完成本周额度。

## 面试问题

- 你怎么保证这个 benchmark 可复现？
- 某组数据波动 30%，你是怎么处理的？
- 这个项目最大的测量局限是什么？
- 哪些部分是 AI 生成的？你怎么验证它们？
- 如果换一个文件系统（ext4 → XFS），你预期哪些结论会变？
