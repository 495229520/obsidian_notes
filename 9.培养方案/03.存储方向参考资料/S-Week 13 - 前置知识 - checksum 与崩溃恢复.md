## 0. 先建立直觉：读出来的字节凭什么可信

做一次最朴素的破坏实验：

```bash
# 往你的 v0 数据文件里随手翻一个 bit
printf '\x01' | dd of=database.log bs=1 seek=100 count=1 conv=notrunc
# 重启引擎——v0 会发生什么？
```

v0 的行为是未定义的：可能解析出一条长度错乱的记录、可能 get 返回一个悄悄坏掉的 value、可能直接崩。**最危险的不是崩溃，是静默返回错误数据**（silent corruption）——用户拿到坏值却毫无察觉。checksum 的全部意义就是把"静默错误"转化为"显式错误"。

> [!important] 第一性原理
> 引擎对每条记录只能有三种反应：**正确返回、明确报错、明确丢弃**。绝不允许第四种——"不知道自己错了"。CRC 负责把第四种消灭掉，恢复策略负责在报错之后把引擎带回一致状态。

## 1. 故障模型：三类坏法，各自谁来防

| 故障 | 成因 | 谁来防 |
|---|---|---|
| torn write（半条记录） | 崩溃时跨扇区的写只完成一部分 | CRC 识别 + 尾部截断 |
| 介质位翻转 / 错位读 | 介质老化、固件 bug、传输错误 | CRC 识别 + 读路径报错 |
| 逻辑 bug（写错内容） | 程序自己写了合法但错误的数据 | 测试 + 崩溃注入（CRC 无能为力） |

CRC **防不了**的还有两类，面试必须能主动说：写入前内存里就坏了的数据（garbage in, garbage out——那是 ECC 内存的领域）；整条记录干净地消失（log 被外力截断到记录边界——CRC 全对但数据少了，要靠序号链或上层对账发现）。

## 2. CRC32C：怎么算、盖住哪些字节

- **选 crc32c 而不是普通 crc32**：Castagnoli 多项式有 SSE4.2 硬件指令（`_mm_crc32_u64`），单核每秒几 GB，在写路径上近似免费；RocksDB、ext4 都用它。
- **覆盖范围**：tstamp 起到 value 末尾——即除 crc 字段自身外的整条记录。写路径最后算、读路径最先验（"先校验后使用"）。
- **实现**：不要手写查表法——用现成实现（几十行的 SSE4.2 wrapper，或直接引入 crc32c 库）。手写多项式除法是本周最不值得花时间的事。
- 一个容易忽略的位置：**恢复扫描和 get 路径都要校验**。恢复时验一遍不代表之后盘不会再坏；get 每次读回都验，成本是内存级的。

## 3. 磁盘写的原子性与 torn write

能安全假设的只有一条：**单个逻辑扇区（512 B 或 4 KiB）的写是原子的**。你的 record 是变长的、可以横跨多个扇区，于是：

- 崩溃发生在 `write` 进行中 → 页缓存里只有部分页标脏 → 落盘后文件尾部是**半条记录**。
- 更隐蔽的：多个扇区落盘顺序不保证——记录中段先落、头部没落的"空洞"也可能出现（虽然 append 场景主要表现为尾部截断）。

数据库的三种应对：CRC + 截断（本周做的，日志型引擎的标准做法）、doublewrite buffer（InnoDB，页级先写副本）、full page write（PostgreSQL，checkpoint 后首次改页把整页塞进 WAL）。能对比这三种，面试里就是加分项。

## 4. 恢复策略：为什么是前缀截断

恢复扫描遇到以下任一情况，停止并截断到**最后一条完整记录的末尾**：

1. 剩余字节不足一个定长头；
2. 长度字段非法（超上限、越过文件尾）；
3. CRC 校验失败。

**为什么不跳过坏记录继续**：append log 里记录变长、无对齐锚点——坏记录的"下一条从哪开始"本身就是从坏数据里读出来的，不可信；就算能重新同步，跳过中间一条意味着后续重放建立在缺页历史上，KeyDir 可能指向被跳过 key 的过期版本。**前缀一致**（prefix consistency）是日志恢复唯一站得住的语义：保留一个"到某时刻为止完全正确"的历史。

截断用 `ftruncate` 到最后一条完整记录的末尾，然后**继续正常服务**（append 从新尾部开始）。截断动作必须打日志（见 6 节）。

尾部之外的损坏（中间某条老记录翻位）：恢复扫描会在它那里停下、把后面的好数据全截掉——这是两难权衡。工程折中：恢复扫描只对**尾部**做截断（最后 N 字节窗口内），中间损坏则标记该记录不可读、依赖 get 路径的 CRC 兜底并报警。把这个权衡写进 `recovery_notes.md`，比无脑选边更显功力。

## 5. 损坏注入：dd 与 truncate 的手术刀用法

五类样本的制造方法（全部脚本化进 `corrupt_inject.sh`，参数化 offset）：

```bash
# 1. 尾部截一半：truncate 到最后一条记录中间
truncate -s <mid_of_last_record> database.log

# 2. payload 翻 1 bit：先读原字节，异或 0x01 写回
orig=$(dd if=database.log bs=1 skip=$OFF count=1 2>/dev/null | xxd -p)
printf "$(printf '\\x%02x' $(( 0x$orig ^ 0x01 )))" | \
  dd of=database.log bs=1 seek=$OFF count=1 conv=notrunc

# 3. header 翻 1 bit：同上，offset 落在某条记录的头 20 B 内
# 4. 长度字段改超大：往 value_size 的位置写 0xFFFFFFFF
printf '\xff\xff\xff\xff' | dd of=database.log bs=1 seek=$LEN_OFF count=1 conv=notrunc
# 5. 文件清空
truncate -s 0 database.log
```

关键开关：`conv=notrunc`（不截断文件，原地覆写）、`bs=1 seek=N`（字节级定位）。每类样本跑恢复后核对三件事：恢复是否成功、丢了哪些 key、行为是否与 `recovery_notes.md` 的预期一致。offset 的计算写进脚本注释——半年后你还能看懂它坏在哪。

## 6. 恢复的可观测性

恢复不能是黑盒。每次启动至少输出：

- 扫描的总记录数、总字节数、耗时（S-Week 17 的恢复时间 benchmark 直接用它）；
- 是否发生截断：截断 offset、丢弃字节数、触发原因（哪一类非法）；
- 重建后的 KeyDir 条目数。

这几行日志在崩溃注入周（S-Week 16）是排查违例的第一现场——现在把它做好，那周会感谢自己。

## 7. 可选加分：简版 merge 与原子 rename

时间富余才做：离线 merge——遍历 KeyDir 把每个 key 的最新记录抄进新文件 → `fsync` 新文件 → `rename` 原子切换 → `fsync` 目录。两个语义点：`rename` 在同一文件系统内原子（要么旧要么新，不会半个）；rename 后不 fsync 目录，崩溃后可能看到旧目录项——这是 S-Week 14 目录 fsync 的预演。做不完就砍，边界声明。

## 8. 常见错误

- **CRC 盖住了 crc 字段自身**：算的时候把 crc 位置填零参与计算或干脆跳过，读写两侧必须同一约定——不一致的话所有校验都失败。
- **只在恢复时校验、get 不校验**：恢复后盘继续坏，静默错误从 get 路径漏回来。
- **长度检查在 CRC 之后**：先拿不可信的长度去读体再校验，越界读在校验前就发生了。顺序必须是"长度合法性 → 读体 → CRC"。
- **dd 忘了 conv=notrunc**：文件被截断到 seek 位置，制造出的是另一种损坏，实验白做。
- **截断后不打日志**：数据被静默丢弃，用户和测试都无法察觉——静默丢弃和静默错误一样危险。
- **对"中间损坏"也做截断**：把尾部策略无脑推广到全文件，一个老记录翻位就丢掉后面全部数据。
- **手写 CRC 查表实现**：耗时且容易错，用硬件指令或成熟库。

## 10. 关键要点总结

- checksum 的使命：把"静默错误"变成"显式错误"；引擎只允许正确、报错、丢弃三种反应。
- 只能假设单扇区写原子；变长记录必然面对 torn write。
- 前缀截断是日志恢复唯一可靠的语义：坏点之后没有可信锚点。
- 长度合法性检查先于一切——坏长度字段比坏数据更危险。
- 损坏注入要覆盖五类样本、全部脚本化、行为与文档逐条对照。
