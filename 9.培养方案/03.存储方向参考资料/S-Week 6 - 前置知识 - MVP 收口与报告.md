## 0. 先建立直觉：收口周产出的是可信度

一个 benchmark 项目的价值公式：结论的含金量 × 别人相信它的程度。前五周攒的是第一项，本周攒第二项。三层标准（详见 [[benchmark 报告与可复现工程专题]]）：

```text
可复现：新机器按 README 跑 reproduce.sh，得到同量级结果
可信：  每个结论能点回原始 CSV/JSON，波动有解释而不是被删掉
诚实：  限制写清楚，Agent 生成与人工验证分开声明
```

本周每个任务都能归到这三层里：统一重跑 → 可复现；波动解释 → 可信；限制与 Agent 声明 → 诚实。

## 1. 为什么必须统一重跑

前五周的数据不能直接拼成报告，因为它们**不同源**：

- 环境漂移：五周里内核可能升过级、文件系统碎片在累积、租的云主机根本不是同一台。
- 程序演进：`read_latency.cpp` 在 Week 2 加了 --direct，Week 1 的数据是旧版程序跑的。
- 口径不齐：早期实验的重复次数、warmup 处理可能不统一。

所以收口的第一动作是**同一台机器、同一内核、同一文件系统、当前版本的程序，一次性重跑五组核心实验**（清单见周计划第 1 节）。旧数据留档不删，但报告只引用 `results/final/` 里的重跑数据。统一重跑还有个副产品：它就是 reproduce.sh 的第一次全流程演练。

## 2. 波动怎么排查、怎么呈现

3 次重复波动 > 10% 的组，先排查后呈现。云主机上的排查清单（按命中率排序）：

| 嫌疑 | 检查方式 |
|---|---|
| cache 状态没清干净 | 实验脚本里 sync + drop_caches 是否每组都执行；Dirty 是否归零 |
| 邻居噪声（共享宿主机） | `top` 看 %st（steal time）；换时段复测是否消失 |
| 后台 writeback / cron | 重跑窗口内 iostat 是否有不属于实验的流量 |
| SSD 内部状态（GC/温度） | 波动集中在写实验；空闲几分钟后复测 |
| 参数没复原 | read_ahead_kb、调度器等是否还是 env.md 记录的值 |

呈现纪律只有一条硬规则：**三次结果全部保留全部展示**，波动大的组加一句解释或"不确定"标注。删数据挑好看的一次，等于把整个项目的可信度押在没人发现上——面试官最爱追问的恰恰是"这组怎么这么整齐"。

## 3. 六段式报告逐段要点

骨架在周计划 2.1 节，逐段的"合格线"：

1. **环境**：照着 [[benchmark 报告与可复现工程专题]] 第 5 节的清单逐项填，缺一项都算不完整——这段是别人复现的起点。
2. **方法**：负载定义（rw/bs/QD/direct）、重复次数、warmup 策略、计时口径（哪个时钟、掐头去尾没有）。合格线：别人不看代码能照着复刻实验。
3. **结果**：每小节一图一表，图表由脚本从 `results/final/` 生成；四个小节对应四条故事线（冷热差距、三路径选型、持久化代价、QD 扫描）。
4. **结论**：每条一句话 + 数据指针。写"冷热差 40 倍（3.1 节）"，不写"page cache 影响很大"。
5. **限制**：三段式（事实 + 影响范围 + 补救路径）。本项目至少三条：云环境邻居噪声、单盘单文件系统、SSD 非稳态。
6. **Agent 声明**：见第 6 节。

自测标准（周计划验收项）：找一个没看过项目的人（或让 Agent 扮演），15 分钟内能否说出"这个项目回答了什么问题、最重要的三个数字是什么"。

## 4. reproduce.sh 的设计

```text
./reproduce.sh
  1. 检查/安装依赖（gcc、cmake、liburing-dev、fio、sysstat）
  2. 编译全部程序
  3. 生成 8 GiB 测试文件（幂等：已存在且大小对就跳过）
  4. 依次跑五组实验（每组前 sync + drop_caches，执行前打印提示）
  5. 从原始数据重新生成汇总表与图，打印结果路径
```

工程要点：

- **破坏性/全局性操作前停下来问**：drop_caches 影响全机——打印说明并要求确认（或提供 --yes 给 CI 场景）。
- **trap 复原**：脚本改过的任何系统参数（如做过 readahead 实验的 setra），异常退出也要还原。
- **幂等**：中断重跑不留半成品；结果目录按时间戳分目录，绝不覆盖旧原始数据。
- **新机器实测是硬验收**：租一台干净机器从 git clone 跑到出结果——所有"我以为装了"的隐式依赖都会在这一步现形。

## 5. README：从"学习记录"到"项目门面"

最常见的失败模式是把 README 写成周记（"Week 1 我学了 page cache……"）。合格结构：

```text
一句话定位：这个仓库量化了 Linux 五条 I/O 路径的延迟构成与持久化代价
结论速览：3-5 条最有价值的数字（每条带图或表的链接）
实验索引：问题 → 方法 → 结论文档，一行一个实验
复现：环境要求 + reproduce.sh 用法 + 预计耗时
限制声明 + Agent 使用声明
```

区别就一条：**按问题组织，不按时间组织**。读者关心"你发现了什么"，不关心你的学习顺序。

## 6. Agent 使用声明怎么写

边界沿用总纲执行原则：Agent 可以生成脚手架、fio job、解析脚本、README 初稿；不可以决定结论、改 benchmark 数据、绕过 correctness gate。声明落到 README 的写法：

```text
## AI 协作声明
Agent 生成：CMake 脚手架、fio job file 模板、CSV 解析与画图脚本、README 初稿
人工完成：核心测量程序（pread/写策略/mmap/io_uring 主循环）、全部实验执行、
          数据解读与结论
验证方式：解析脚本输出与手算样本比对（3 组）；图表可由 reproduce.sh 重新生成
```

这段不是免责声明，是加分项：2026 年的面试官默认你用 AI，他要分辨的是"你在驾驭工具"还是"工具在驾驭你"——清晰的边界 + 可验证的机制，就是前者的证据。

## 7. 常见错误

- **报告引用了五周里不同环境的数据**：统一重跑的意义被架空，对比全部失效。
- **只重跑波动大的组**：其他组还是旧环境数据，同源性照样破——要跑就全跑。
- **挑三次里最好的一次**：可信度归零的最快方式。
- **图表手工修饰**（挪点、改坐标）：等同改数据；要改就改生成脚本并重跑。
- **reproduce.sh 只在开发机上验证**：新机器上第一步 apt 就挂——隐式依赖没暴露。
- **限制段写成客套话**（"时间有限，测得不全"）：要写具体边界和影响范围。
- **README 按周组织**：门面写成流水账。
- **收口周还在加新实验**：范围失控，收口拖成第八周——新想法记进阶段 1 的 backlog。

## 9. 关键要点总结

- 收口周产出可信度：可复现（重跑 + 脚本）、可信（数据溯源 + 波动解释）、诚实（限制 + Agent 声明）。
- 报告只引用统一重跑的同源数据；旧数据留档不引用。
- 波动是数据不是污点：全量保留 + 解释，比整齐的数字更有说服力。
- reproduce.sh 的硬验收是新机器实测——租金是可信度的价格。
- README 按问题组织；Agent 声明是工程素养的证据，不是道歉。
