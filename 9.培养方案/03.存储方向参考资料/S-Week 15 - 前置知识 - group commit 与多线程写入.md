> S-Week 14 结束时你有一个诚实但慢的引擎：always 档每条 put 一次 fsync，吞吐被设备 flush 时间死死封顶。本周不降低任何持久化承诺，把吞吐提一个数量级——手段只有一个：**让 N 条请求分摊同一次 fsync**。这是 RocksDB write group、MySQL 组提交、PostgreSQL commit_delay 共用的招式，你要亲手实现一遍并量化它的代价。

## 0. 先建立直觉：fsync 按次收费

小 I/O 场景下，一次 fsync 的成本近似固定（设备 flush 时间主导），跟这次刷了 1 条还是 100 条记录关系不大。于是：

$$
IOPS_{single} \approx \frac{1}{t_{fsync}}
$$

$$
T_{group} \approx \frac{B}{t_{fsync}}
$$

B 是每批攒到的条数。fsync 是"按次收费的过路费"——拼车就是全部秘密。代价也立刻可见：先到的请求要等车坐满（或等发车计时器到点），**每条延迟 += 攒批等待**。本周的全部工程都在这两个公式之间做交换。

## 1. 架构总览：MPSC 队列 + 单 writer

![[图片/9.培养方案/03.存储方向参考资料/9_3_15_1.svg|880]]

数据流四步：

1. N 个提交线程把请求（序列化前的 key/value + 一个 promise 槽位）放入 **MPSC 有界队列**，然后在自己的槽位上等。
2. **writer 单线程**取一批：队列非空时一次性排干（自然攒批），或按参数触发。
3. 批内请求序列化成一段连续 buffer → **一次 append + 一次 fdatasync**。
4. 按**批次序号（世代号）**集体唤醒，每个提交线程确认自己的批已提交后返回。

关键设计：offset 分配、fsync、KeyDir 更新全部收敛在 writer 一根线程里——**共享可变状态最小化**，绝大多数数据竞争在架构层面直接消失（[[17.1 并发同步概述：多执行流与共享可变状态]] 的原则落地）。

## 2. 为什么单 writer：三个备选方案的否决理由

design_note 并发章的素材，每条都要能脱稿：

| 备选 | 否决理由 |
|---|---|
| 多 writer 抢一把文件锁 | offset 分配必须串行，锁竞争点在最慢的资源（磁盘 fsync）上，锁持有时间毫秒级，并发度反而崩 |
| 每线程独立 log 文件 | 恢复要归并多个 log 的全序（需要全局序号），fsync 次数没省（每文件各刷各的），复杂度翻倍收益为负 |
| 无锁队列 + busy-poll writer | 延迟略降但烧一个核空转；我的瓶颈在 fsync 不在入队——先正确后快，有界阻塞队列足够 |

单 writer 的本质：把竞争点从"文件"挪到"内存队列"——内存的锁开销纳秒级，磁盘的串行化毫秒级，竞争应该发生在便宜的资源上。

## 3. 有界队列与背压

队列必须**有界**（复用 [[17.6 并发队列：有界队列与无锁队列]] 的有界阻塞队列）：

- 无界队列在 writer 跟不上时无限堆积——内存涨、延迟涨，最后 OOM；表面上"永不阻塞"，实际把故障推迟到最坏的时刻。
- 有界队列满时提交线程阻塞在入队上——**背压**天然形成：上游感知到下游饱和，压力止步于源头。
- 容量选型：够 writer 一批的量再留余量（如 4 × max_batch）；太小频繁触发背压，太大失去背压意义。

## 4. 条件变量的正确用法：谓词、世代号、虚假唤醒

提交线程等应答是本周最容易写错的代码，三条铁律：

1. **等待必须带谓词循环**：

```cpp
std::unique_lock lk(mu);
cv.wait(lk, [&]{ return committed_seq >= my_seq; });
```

不带谓词的裸 `wait` 面对**虚假唤醒**（POSIX 允许无理由返回）和**错批唤醒**（notify_all 叫醒所有人但只有一批该走）直接错。

2. **世代号（批次序号）做谓词**：writer 每提交一批递增 `committed_seq`；请求入队时领取自己的 `my_seq`。谓词 `committed_seq >= my_seq` 同时解决"我这批到底提交没有"和"通知在我 wait 之前就发了怎么办"（丢通知问题——状态在，通知丢了也无所谓）。
3. **改状态在锁内、notify 可在锁外**：`committed_seq` 的更新必须持锁（保证 wait 的检查-睡眠原子性）；`notify_all` 放锁外减少惊群后的锁排队。

为什么 `notify_all` 而不是 `notify_one`：一批完成时该走的是**整批**线程，one 只放走一个。惊群成本真实存在（整批线程醒来抢锁），实验里可以观测——这就是攒批参数影响 p99 的微观机制之一。

## 5. 攒批参数：双条件触发

```text
发车条件（先到先触发）：
  批大小达到 max_batch        —— 吞吐优先的闸门
  等待时间达到 max_wait_us    —— 延迟保底的闸门
```

- max_wait 太小：低负载下每批只有 1-2 条，退化回单条 fsync。
- max_wait 太大：p50 被攒批等待推高，低负载时延迟惨不忍睹。
- 一个工程细节：负载高时其实**不需要等**——writer 刚刷完上一批回来，队列里已经攒好下一批了（fsync 期间到达的请求自然堆积）。这叫"自然攒批"，RocksDB 的 write group 就是这个形态：**fsync 本身就是攒批计时器**。实现时优先依赖自然攒批，max_wait 只做低负载兜底。

## 6. 正确性工具：TSAN/ASAN 能抓什么、抓不了什么

```bash
cmake -B build-tsan -DCMAKE_CXX_FLAGS="-fsanitize=thread -g -O1"
cmake -B build-asan -DCMAKE_CXX_FLAGS="-fsanitize=address -g -O1"
```

- **TSAN 抓**：数据竞争（无同步的并发读写）、部分锁误用。基于 happens-before 分析，**竞争没被测试路径触发也可能报**——覆盖并发路径的压测单测跑在 TSAN 下价值最大。
- **TSAN 抓不了**：fsync 时机错误（应答早于落盘——语义对内存模型完全合法）、死锁之外的逻辑错序、性能问题。**这就是 S-Week 16 崩溃注入必须存在的原因**——TSAN 证并发安全，注入证持久化语义，两者不可互替。
- 纪律：TSAN 和 ASAN 分开构建（不兼容同时开）；CI 习惯上每次提交都跑并发单测的 TSAN 版。

## 7. 实验设计：延迟-吞吐曲线

- 负载：fsync=always、4 KiB value；变量：提交线程数 1 / 4 / 16 × 攒批开 / 关；每组 3 次。
- 指标：吞吐（条/秒）、p50 / p99 应答延迟——**逐条延迟进 CSV**，分位数事后算（S-Week 1 以来的纪律）。
- 预期形态（拿数据验证，不符合就解释）：
  - 攒批关：吞吐钉死在单条 fsync 上限附近，加线程只加排队延迟。
  - 攒批开：吞吐随线程数近线性上升，直到逼近设备顺序写/flush 能力；B（每批条数）随并发自然增大——记录每批实际大小的分布，它是解释曲线的钥匙。
  - p99 攒批开比关略差（等待 + 惊群），这是用延迟买吞吐的直接证据——两个数字并排放进报告。

## 8. 常见错误

- **裸 wait 不带谓词**：虚假唤醒/错批唤醒/丢通知三连坑，条件变量的第一铁律。
- **应答早于 fsync**：攒批重构时最容易引入——唤醒必须发生在 fdatasync 返回之后。
- **批内请求的 KeyDir 更新时机错**：索引更新也收敛到 writer 在 fsync 后统一做；提前更新会让并发 get 读到"未提交"数据（读到的值崩溃后可能消失——违反自己的契约）。
- **无界队列**：OOM 定时炸弹 + 失去背压。
- **notify 时机在改状态之前**：等待方醒来谓词还是假，又睡回去，实际白唤醒；先改状态（锁内）再 notify。
- **用 sleep 轮询代替条件变量**：延迟粒度和 CPU 双输——这周的主题就是学会正确的等待。
- **只在无 sanitizer 构建下跑压测**：竞争藏到 S-Week 16 才爆，代价翻倍。

## 10. 关键要点总结

- group commit = 拼车分摊 fsync：吞吐乘 B，每条延迟加等待——两个数字永远一起报。
- 单 writer 把串行化放在内存队列上，竞争发生在便宜的资源里；共享可变状态最小化是并发正确性的第一道防线。
- 条件变量三铁律：谓词循环、世代号状态、先改状态再通知。
- 高负载下 fsync 本身就是攒批计时器（自然攒批），参数只做低负载兜底。
- TSAN 证并发、崩溃注入证语义——两张证书缺一不可。
