## 0. 先建立直觉：测试的目标是杀死自己的引擎

普通单测回答"正常路径对不对"；崩溃注入回答一个更狠的问题：**在任意时刻拔掉进程，引擎醒来后还认不认账**。先想清楚"账"是什么——引擎对外的承诺只有一条：

> 我应答过"成功"的数据，重启后必须都在；我没应答的，可以在、可以不在，但不能把库搞坏。

测试框架的全部工作就是把这句话变成机器可校验的谓词，然后用随机性反复轰炸它。

> [!important] 第一性原理
> 崩溃注入的价值密度取决于**注入时刻的分布是否覆盖危险窗口**。均匀随机会把绝大多数注入浪费在"安全区"（两次写之间的空闲）；工程上要主动把注入压到 append 后 fsync 前、fsync 后应答前这些毫秒级窗口里——找 bug 不是撞大运，是打靶。

## 1. 不变量：什么叫"恢复是对的"

三个集合（父进程视角）：

- **attempted**：发起过的操作全集。
- **committed**：收到"成功"应答的子集。
- **recovered**：重启恢复后引擎里实际可见的数据。

校验谓词：

$$
committed \subseteq recovered \subseteq attempted
$$

- 左包含被破坏 = **丢数据**（应答过的没了）——fsync=always 下任何一次都是 P0 bug。
- 右包含被破坏 = **凭空多数据**（没发起过的出现了）——通常意味着恢复解析错位或内存越界。
- 附加完整性约束：恢复后全库每条记录 CRC 合法、无半条记录；get 任意 key 不崩溃。
- 注意 overwrite/delete 的语义细节：committed 集合要记**每个 key 最后一次已应答操作的值**（或墓碑）——校验的是"最终值一致"，不只是"key 存在"。

## 2. 框架：fork、SIGKILL 与应答管道

![[图片/9.培养方案/03.存储方向参考资料/9_3_16_1.svg|820]]

单轮流程：

1. 父进程建好管道，`fork`；子进程 `exec`（或直接函数调用）启动引擎，跑随机 workload（put/del/overwrite 混合、随机 value 大小），**每收到一次引擎应答**就向管道写一条 `(op, key, value_hash, seq)`。
2. 父进程持续读管道入 committed 集合；同时按注入策略睡一段随机时间，向子进程发 `SIGKILL`。
3. 父进程 `waitpid` 收尸，重启引擎（新进程）走 crash recovery。
4. 全库扫描出 recovered，跑三条谓词 + 完整性检查；结果与本轮参数一起落盘。

为什么 SIGKILL 而不是 SIGTERM：SIGKILL 不可捕获、不给任何清理机会——这才是"崩溃"；SIGTERM 会走析构和缓冲区 flush，测的是优雅退出，完全是另一件事。

## 3. oracle 的可信性论证

面试必问"你的 oracle 为什么可信"，三层答案：

1. **存活性**：committed 集合在父进程内存里，子进程怎么死都影响不到它。
2. **顺序性**：子进程必须在**引擎应答之后**才写管道——管道消息是"已应答"的忠实记录。写反了（先报管道再应答）会制造假阳性：管道说 committed、引擎其实还没 fsync。
3. **原子性**：单条管道消息 ≤ `PIPE_BUF`（Linux 4096 B）时 write 原子，不会两个消息交织；定长消息 + 一次 write 一条即可。

还有一个微妙点：SIGKILL 到达时，子进程可能有**已应答但还没写进管道**的操作——它们会被父进程当成"未提交"。这只会让校验**偏松**（左包含更容易成立），不会假阳性；把这个偏差写进 `crash_injection.md` 的方法论一节，体现你想过。反过来（写了管道但引擎还没应答）才是必须杜绝的方向。

## 4. kill -9 测什么、不测什么

本周最重要的语义边界，必须先想透再动手：

- **kill -9 后，page cache 不丢**——脏页属于内核，进程死了内核照常回写。所以：已 `write` 未 `fsync` 的数据，在 kill -9 场景下**大概率还在**。
- 由此推论：kill -9 **测不出**"该 fsync 没 fsync"这类 bug 的丢数据后果（要断电才暴露）；它测的是**崩溃一致性逻辑**——应答顺序、恢复解析、torn record 处理、并发窗口下的状态机正确性。
- 那 torn write 从哪来？kill 到达时 `write` 可能只执行了一半（系统调用被打断在用户态拷贝阶段之前/中间），或一批里只 append 了前几条——尾部半条记录依然会出现，恢复的截断逻辑依然被考验。
- **断电语义**的正规测法（边界声明 + 可选加分）：`dm-flakey`（设备映射层随机丢写）、`dm-log-writes`（记录写序列，离线重放到任意前缀再跑恢复——最接近"任意断电点"的工具）、虚拟机硬关机。写清楚"我用 kill -9 验证了进程崩溃一致性，断电一致性以 dm-log-writes 为 TODO"，比含糊地宣称"崩溃安全"专业得多。

## 5. 注入时刻设计：覆盖危险窗口

两种模式都要有：

- **按时间随机**：睡 `uniform(0, T)` 毫秒后 kill。简单，但大部分落在安全区。
- **按操作计数触发**：子进程每完成 N 次操作通过管道汇报，父进程在"第 K 次操作附近"kill——K 随机、附近加抖动。能把注入压进高频写入的密集区。

要覆盖的危险窗口清单（每个至少中弹过一次才算覆盖）：

| 窗口 | 暴露的 bug 类型 |
|---|---|
| append 后、fsync 前 | 恢复截断逻辑、torn record |
| fsync 后、应答前 | "多但不坏"语义、oracle 顺序 |
| everysec 后台刷间隙 | 丢失窗口是否 ≤ 承诺值 |
| group commit 批中途 | 批内前缀持久化、世代号应答 |
| merge/rename 中间态（若实现了） | 目录 fsync、双文件一致性 |

提高命中率的脏招（有效且正当）：把 value 调大、fsync 调成 always——单次操作的"危险窗口占空比"变大，同样的随机注入命中率翻倍。

## 6. 可复现性：种子与失败归档

- workload 生成器和注入时刻都从**同一个显式种子**派生；种子每轮递增并记录。复现一次失败 = 用同一种子重跑一轮。
- 注意：kill 时刻受调度噪声影响，同种子不保证字节级同现场——所以失败时还要**归档现场**：数据文件副本、恢复日志、committed 集合快照、种子与轮次号，打包进 `results/crash/failures/round_N/`。
- 循环脚本输出进度（每 100 轮一行：通过数/违例数/截断发生率），1000 轮跑完产出汇总表。截断发生率本身是个有意思的观测值——它告诉你注入命中危险窗口的比例。

## 7. 修 bug 的记录格式

这周的真正产出是 `crash_bugs.md`——每个 bug 一节，沿用 [[S-Week 9 - eBPF 观测]] 的事故记录风格：

```text
现象：第 217 轮，key=k042 已应答但恢复后缺失（左包含违例）
定位：恢复日志显示尾部截断 96 B；比对写路径，发现批内应答在
      fdatasync 返回前发出（唤醒代码在 fsync 调用之前）
根因：S-Week 15 重构时 notify 移到了错误位置
修复：唤醒移到 fdatasync 之后；加断言 committed_seq 只在刷盘后推进
回归：同种子重跑通过；新增单测锁死应答顺序；1000 轮重跑零违例
```

一个 bug 都没挖到不是好消息——先怀疑注入覆盖（对照 5 节清单），再怀疑校验谓词太松（比如只查 key 存在不查值），最后才允许相信代码真的对了。

## 8. 常见错误

- **oracle 顺序写反**：管道上报先于引擎应答——假阳性制造机，整周实验作废。
- **用 SIGTERM 或 SIGINT**：测的是优雅退出不是崩溃。
- **校验只查 key 存在、不查最终值**：overwrite 场景下旧值也算"在"，语义 bug 全漏。
- **注入只有时间均匀随机**：99% 打在安全区，1000 轮≈无效覆盖。
- **失败不归档现场**：知道挂了但永远复现不出来。
- **拿 everysec 档的丢失当 bug**：先对照契约矩阵——允许丢 ≤1 秒是承诺的一部分；该档校验的是"丢失量在窗口内 + 无损坏"。
- **测试和引擎共用一个进程**：引擎必须是独立子进程，否则 SIGKILL 连 oracle 一起带走。
- **循环里复用同一数据目录不清理**：上一轮的截断残骸污染下一轮，违例无法归因。

## 10. 关键要点总结

- 崩溃注入校验的是引擎唯一的对外承诺：committed ⊆ recovered ⊆ attempted，外加完整性。
- oracle 三要素：活在父进程、严格后于应答、单条消息原子。
- kill -9 测崩溃一致性逻辑，测不了断电丢页——边界声明是专业性的标志。
- 注入要打靶不要撒网：按操作计数触发 + 危险窗口清单对账。
- 可复现性 = 种子 + 现场归档；产出的灵魂是 crash_bugs.md 里的修 bug 故事。
