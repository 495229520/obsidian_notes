## 阅读说明

这篇是 [[S-Week 28 - 开源贡献冲刺]] 的总前置知识：选题前读 1-2 节，动手前过 3-4 节，发 report 前看 5 节。目标是总纲三选一（1 个 merged PR / 3 个 issue reproduction / 2 篇被认可的 benchmark report），优先级 LMCache > JuiceFS/fio > RocksDB/SPDK。

---

> 开源贡献最大的误区是把它当"新项目"来做——从零找 issue、啃陌生代码、憋大功能。正确姿势相反：**你过去一年攒下的实验记录里已经埋着贡献**——安装时文档对不上的那处、复现过的怪现象、和官方数据不一致的那组 benchmark。本周的工作是把它们捡起来、按项目规范包装、投递出去。挖矿在存量里，不在增量里。

---

## 0. 先建立直觉：贡献是实验的副产品，不是新任务

维护者视角决定一切：他们缺的不是代码，是**高质量的信息**——"哪个文档把新人带沟里了""哪个配置组合下行为异常且能稳定复现""社区外的机器上 benchmark 长什么样"。这三样恰好是你做 S1-S4 时天然产出的东西。所以本周的第一动作不是打开 LMCache 的代码，而是打开自己的 `env.md`、各周实验笔记和 gap-analysis——**素材已经在那了**。

> [!important] 第一性原理
> 贡献的价值 = 对维护者的信息增量 ÷ 维护者的处理成本。所有技巧（最小复现、遵循模板、提前沟通）都在做两件事：提高分子、降低分母。merged 与否有运气成分，但这个比值是你完全可控的。

## 1. 三种贡献物的性价比与选择

| 贡献物 | 门槛 | 周期 | 面试价值 | 适合谁 |
|---|---|---|---|---|
| 文档/小修复 PR | 低 | review 数天到数周 | merged 后是硬记录 | LMCache 这类新项目边角多，首选 |
| issue reproduction | 低-中 | 即时生效（提交即产出） | 展示定位与表达能力 | 你已练过（S-Week 17），量产可行 |
| benchmark report | 中 | 看社区互动 | 最贴你的报告纪律，差异化最高 | S4 的三档对照数据现成 |

组合建议：**1 个文档 PR（快、确定性高）+ 1-2 个 issue repro（存量兑现）**为主攻；benchmark report 作为加分项（S4 数据往 LMCache 的 discussion 发一篇）。三线并进但时间盒各自独立——任何一线卡住不拖累其他。

## 2. 选题：从自己的记录里挖，按两轴打分

素材普查（半天）：

- LMCache：S-Week 24/25 的安装记录——文档与实际不符处、配置项含义踩坑处、统计口径疑惑处；实验中复现过的异常行为（含版本与配置）。
- fio / JuiceFS：S1-S3 各周笔记里标过 TODO 或"怪现象"的条目；gap-analysis 里的存货。
- 打分两轴：**工作量**（小时级/天级）×**命中率**（是否有明确的 issue 模板可套、维护者近期是否活跃、类似 PR 的合并历史）。取"小时级 × 高命中"的前 2-3 个进时间盒。

命中率的快速侦察：看项目最近 30 天的 PR 列表——文档类 PR 的平均合并周期、维护者是谁、review 风格如何。这半小时的侦察比任何技巧都提升存活率。

## 3. 四步法的操作化

- **Reproduce**：干净环境（新虚拟机/容器）、固定版本与 commit hash、逐条命令记录——"在我机器上"不算复现，"在任何机器上按这几行命令"才算。
- **Minimize**：砍配置砍到再砍一项就不复现为止；最小化的过程本身常常就把根因逼出来了。
- **Analyze**：能定位到代码行最好；不能就给"行为对照 + 怀疑点"——诚实的半成品分析好过错误的完整结论。
- **Contribute**：严格套项目的 issue/PR 模板；PR 先在 issue 里留言意向（"我遇到 X，打算改 Y，方向对吗"）——被指错方向的成本远低于白写代码。

全程记录进 `docs/oss_contrib.md`：动机（哪次实验来的）→ 过程 → 提交链接 → 状态。这份文档是面试素材，价值不低于 merged 本身。

## 4. PR 的存活率工程

- 选题守恒律：改动越小、越客观（文档笔误 < 文档补全 < 复现脚本 < 行为修复 < 功能），合并概率越高——第一个 PR 从最左端起步。
- commit 与 PR 描述按项目惯例（看最近 merged 的 PR 学格式）；一个 PR 只做一件事。
- review 意见 48 小时内响应；被要求改就改，别辩护文风——**第一个 PR 的目标是建立信任，不是证明品味**。
- 石沉大海的处理：两周无响应可礼貌 ping 一次；再无响应就记录状态转投下一个——存活率是统计问题，不是单点执念。

## 5. benchmark report 怎么发才被认可

把你的报告纪律搬到别人的项目上，四要素：

1. 环境三元组 + 版本 + 配置全文（你的 env.md 直接复用）；
2. 方法透明：负载构造、重复次数、指标口径——照 S4 报告的写法；
3. **与官方/已知数据对照**：一致处确认、不一致处提问——"我的 NVMe 档命中收益比 README 示例低 X%，怀疑与 Y 有关，求证"是最好的互动钩子；
4. 提出一个可讨论的问题收尾（不是"求解释"，是"我猜测 A 或 B，倾向 A 因为……"）。

发布渠道按项目习惯：GitHub Discussions > issue（性能类标签）> 社区 Slack/论坛。被回复、被引用、被标 label 都算"社区认可"——截图归档。

## 6. 跟进与叙事沉淀

- 每个贡献物设每周跟进节奏（看通知、回 review）；状态机：提交 → 响应中 → merged / 收录 / 无响应归档。
- 面试叙事模板（一分钟版）："做 S4 时我发现 X（动机）→ 最小复现并定位到 Y（能力）→ 按社区流程提交，过程中学到 Z（协作）→ 现状 W（诚实）"——四拍缺一不可，"现状"如实说 review 中也完全成立。
- 简历表述纪律：merged 写 merged，在途写"提交并跟进中"——夸大在 reference check 面前是负资产。

## 7. 常见错误

- **从零找 issue 硬啃**：绕开自己的存量素材，命中率和效率双低。
- **第一个 PR 就动核心逻辑**：review 周期长、被拒概率高——从文档和脚本起步。
- **不看项目模板直接提交**：维护者第一眼就降权处理。
- **复现不固定版本**：主分支天天动，两周后自己都复现不了自己的 issue。
- **把 report 写成炫技**：没有对照与提问的 report 是广播，不是对话——没人回。
- **在一个 PR 上执念死磕**：两周规则 + 状态归档，存活率靠数量与质量，不靠等待。
- **简历夸大状态**："participated in" 写成 "contributed to core"——一查便知。

## 8. 学习检查清单

- [ ] 素材普查完成：候选清单 ≥5 条，两轴打分选出 Top 2-3。
- [ ] 目标项目的贡献规范与近期 merged PR 风格侦察完毕。
- [ ] 四步法每步的合格标准能复述（复现=任何机器、最小化=再砍就消失）。
- [ ] PR 存活率四招（选题守恒、模板、先沟通、快响应）就位。
- [ ] report 四要素与发布渠道明确。
- [ ] oss_contrib.md 骨架与面试叙事四拍模板就绪。

## 9. 关键要点总结

- 贡献从存量实验记录里挖，不从零开始——素材普查是第一动作。
- 价值公式：信息增量 ÷ 维护者处理成本；一切技巧服务这个比值。
- 组合拳：文档 PR（确定性）+ issue repro（存量兑现）+ benchmark report（差异化）。
- 第一个 PR 建立信任而非证明品味；两周规则防止单点执念。
- 状态如实沉淀：过程记录的面试价值不低于 merged 本身。
