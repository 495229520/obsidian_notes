## 0. 先建立直觉：实验的敌人是归因混乱

你想回答的问题是"KV offload 值不值"，但系统里同时存在四个变量：vLLM 自带的前缀复用、LMCache 的分层存取、显存驱逐压力、负载本身的复用度。不拆开它们，测出的 TTFT 差异是四者的混合物。实验设计的全部工作 = **让每次对照只动一个变量**——S-Week 2 的单变量原则，在一个复杂系统里的升级版。

> [!important] 第一性原理
> offload 的收益只在一个交集里存在：**有复用（不然没得命中）∧ 显存装不下（不然 vLLM 自己就缓存了）∧ 读回够快（不然不如重算）**。负载构造就是把实验精确送进这个交集，以及故意送到交集外（控制组）证明你知道边界在哪。

## 1. 两层前缀缓存：vLLM APC 与 LMCache 的分工

| 层 | 谁 | 命中发生在哪 | 容量边界 |
|---|---|---|---|
| 第一层 | vLLM automatic prefix caching（APC） | **显存内**：paged KV 的 block 按前缀哈希复用 | 显存里 KV 区域的大小 |
| 第二层 | LMCache | **显存外**：驱逐/未命中的 KV 从 CPU 内存、磁盘、远端读回 | 后端容量 |

关键推论：显存装得下的时候，第一层就把复用吃完了，第二层无事可做——**LMCache 的增量价值 = 显存外的那部分命中**。所以对照必须是"APC 开（基线）vs APC 开 + LMCache 开（实验组）"，而不是"全关 vs 全开"——后者测出的是两层之和，归因全错。

## 2. 环境栈：vLLM + LMCache 三档后端

- 模型选 7-8B（单卡够跑、每 token 128 KiB 的口算基数熟悉、prefill 速度适中便于观测 TTFT 差异）。
- LMCache 按当期文档接入 vLLM（connector/配置项随版本变化快——**以当期文档为准，版本号与配置全文进 env.md**，这是新项目的现实）。
- 三档后端逐档冒烟的验证点：
  - CPU 内存档：LMCache 统计里出现 store/retrieve 计数；
  - NVMe 档：`iostat` 看到目标盘真实流量——**配置生效的物理证据**，防"改了配置走的还是内存"；
  - 每档发同一条长 prompt 两次，第二次 TTFT 应明显更低（命中冒烟）。
- harness 对接：Week 5 的发压器指向 vLLM endpoint；确认逐请求的首 token 时间戳能拿到（TTFT 的原材料）。

## 3. 负载形态学：四类负载各证明什么

| 负载 | 构造要点 | 证明什么 |
|---|---|---|
| 多轮对话 | N 个会话并行，每会话同前缀累积追问 8-16 轮；轮与轮之间隔开（给驱逐留时间窗） | 命中收益主战场：前缀随轮次线性增长，复用率最高 |
| 共享系统提示 | 一个数 K token 的 system prompt × 大量不同用户问题 | 部分命中：只有公共前缀段复用 |
| 控制组 | 相互独立的随机 prompt，长度分布与实验组一致 | 零复用时 offload 的开销底噪（查找、元数据、误存） |
| 长上下文 | 8K-32K 单轮 | 显存压力与驱逐行为的放大器 |

构造纪律：

- 轮次间隔是多轮对话组的隐藏参数——请求背靠背时 KV 还热在显存里（第一层就命中了），隔开才能制造"被驱逐后从第二层读回"的目标场景。
- 控制组的 prompt 长度分布必须和实验组一致——否则 TTFT 差异里混进了"prompt 长短"这个无关变量。
- 所有负载参数化（会话数、轮数、间隔、长度、并发）进 harness 配置文件，git 管理——负载即代码。

## 4. 显存压力：没有驱逐就没有 offload

两个可调旋钮，任选或组合：

- `gpu_memory_utilization` 调低：直接压缩 KV 可用显存——最可控，推荐主用；
- 拉高并发会话数 × 上下文长度：真实但难精确控制。

校准方法：跑多轮对话负载，观察 vLLM 的 KV 使用率与驱逐计数（日志/metrics）——**目标是"装得下"与"装不下"两个清晰档位**，下周矩阵的关键维度。装不下档要真的看到驱逐发生（有计数为证），装得下档要确认零驱逐——两档之间界限模糊的配置弃用。

## 5. 指标语义：TTFT、TPOT、命中率的测量口径

- **TTFT**（time to first token）：请求发出到首 token 返回——prefill 时间 + 排队 + 调度。命中省的是 prefill 段，所以它是 offload 的主指标。**逐请求记录进 CSV**，报告用分布（p50/p99）不用均值——排队会造出长尾，均值骗人（S-Week 1 以来的老纪律）。
- **TPOT**（time per output token）：首 token 之后的平均每 token 间隔——解码速度。设计上 offload 不该碰它；它变差 = 读回流量在抢资源，是干扰探测器（下周的专项）。
- **命中率**：LMCache 统计（store/hit 计数）为主，harness 侧按请求推算为辅——两边对得上才可信；对不上先查统计口径（按 block 还是按请求）。
- 辅助指标：吞吐（requests/s）、显存占用与驱逐计数（`nvidia-smi` + vLLM metrics）、盘带宽（`iostat`，NVMe 档）。

## 6. 基线设计：两组纯显存基线为什么都要

- 基线 1：APC 关、LMCache 关——"什么都不缓存"的地板，量出负载的裸 prefill 成本。
- 基线 2：APC 开、LMCache 关——"显存内命中"的天花板，第一层的价值单独成账。
- 下周的三档（+CPU / +NVMe）都相对基线 2 比——增量才是 LMCache 的净贡献。
- 基线自检：多轮对话组从基线 1 到基线 2，TTFT 应显著下降——不降说明负载没造出复用，**回去修负载，不要带病进入下周**。

## 7. 常见错误

- **"全关 vs 全开"的对照**：两层缓存的收益混在一起，LMCache 的净贡献无法归因——本周第一大坑。
- **显存没打满就开测**：第二层无事可做，测出"offload 没用"的假结论。
- **请求背靠背发**：KV 热在显存，第一层全接了——轮次间隔是必要参数。
- **控制组长度分布与实验组不一致**：TTFT 差异混入长度变量。
- **NVMe 档不看 iostat**：配置没生效走了内存，数据白采。
- **TTFT 报均值**：排队长尾被抹平，分布才是真相。
- **版本不记录**：LMCache 迭代快，三个月后无法复现自己的实验。

## 9. 关键要点总结

- offload 收益只存在于"有复用 ∧ 装不下 ∧ 读回够快"的交集——负载构造就是把实验送进交集、控制组送出交集。
- LMCache 的净贡献 = 相对"APC 开"基线的增量；对照组切错，全盘归因错。
- 驱逐必须真实发生且有计数为证；配置生效要有物理证据（iostat）。
- TTFT 是主指标（逐请求、报分布），TPOT 是干扰探测器，命中率两边对账。
- 本周不出结论，出的是"下周可以放心跑"的地基。
