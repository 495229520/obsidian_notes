# 3.8 CUDA Week 4 前置知识 - MatMul + Tiling + Roofline

> 这篇笔记的目标不是提前写工业级 GEMM，而是把 [[3.7 CUDA Week 3 前置知识 - Transpose + Memory Coalescing|Week 3 的二维坐标、coalescing、shared memory tile]] 迁移到 [[Week 4 - MatMul v0]]：这一次核心问题不再只是“线程访问内存的形状”，而是“同一批 A/B 数据如何在 K 维上被重复利用，并转化成更多 FLOPs”。

Week 4 的关键词可以先记成一句话：

```text
transpose 训练你看懂访存形状；matmul 训练你看懂数据复用、计算密度和库 baseline 的差距。
```

## 0. 你现在已经掌握了什么

如果 Week 1 到 Week 3 已经走完，你至少应该能讲清楚这些基础：

- CUDA kernel 通过 `blockIdx`、`threadIdx`、`blockDim` 把线程映射到数据下标。
- 二维矩阵虽然看起来是二维，device memory 里通常仍然是一段连续的一维数组。
- row-major 下，`matrix[row][col]` 的线性下标是 `row * width + col`。
- 同一个 warp 内相邻线程访问连续 global memory 地址，通常更容易 coalescing。
- 一个 block 内线程可以用 shared memory 协作，`__syncthreads()` 只同步同一个 block。
- tiled transpose 的核心不是“shared memory 一定更快”，而是它改变了 global memory 的读写形状。
- correctness 必须先于 benchmark，非方阵和非 tile 对齐尺寸能暴露很多边界 bug。

Week 4 会继续使用这些基础，但观察重点升级了：

| Week | 主题 | 核心问题 |
|---|---|---|
| Week 1 | vector add | 每个线程如何处理一个独立元素？ |
| Week 2 | reduction | 多个线程如何协作得到一个值？ |
| Week 3 | transpose | 线程访问内存的形状为什么影响性能？ |
| Week 4 | matmul | 数据如何在 K 维被复用，并提高 FLOPs / byte？ |

> [!important] 第一层直觉
> MatMul 不只是“二维矩阵上开很多线程”。它真正重要的地方在于：一个 A 元素会被多个输出列复用，一个 B 元素会被多个输出行复用。shared memory tiling 的价值，就是把这种复用从慢速 global memory 拉到 block 内。

## 1. MatMul 到底在算什么

Week 4 先从最普通的 FP32 GEMM 形式开始：

$$
C[M,N] = A[M,K] \times B[K,N]
$$

也就是说：

- `A` 有 `M` 行、`K` 列。
- `B` 有 `K` 行、`N` 列。
- `C` 有 `M` 行、`N` 列。
- `C` 的每个元素，来自 `A` 的一行和 `B` 的一列做内积。

第 `row` 行、第 `col` 列的输出是：

$$
C_{row,col}=\sum_{k=0}^{K-1} A_{row,k}\cdot B_{k,col}
$$

![[图片/SVG/9_3_8_2.svg|955]]

### 1.1 row-major 下标

如果三个矩阵都用 row-major 存储：

```cpp
A[row, k]   -> A[row * K + k]
B[k, col]   -> B[k * N + col]
C[row, col] -> C[row * N + col]
```

这里最容易混的是每个矩阵自己的“每行长度”：

| 矩阵 | shape | 每行长度 | 访问公式 |
|---|---|---:|---|
| `A` | `M x K` | `K` | `A[row * K + k]` |
| `B` | `K x N` | `N` | `B[k * N + col]` |
| `C` | `M x N` | `N` | `C[row * N + col]` |

> [!warning] 常见错误
> 不要把 transpose 里的 `height / width` 机械搬到 matmul。MatMul 有三个维度：`M` 控制 C 的行，`N` 控制 C 的列，`K` 控制每个输出元素的内积长度。

### 1.2 一个线程计算一个 C 元素

naive CUDA matmul 最适合当第一版，因为它直接对应数学公式：

```cpp
__global__ void matmul_naive(
    const float* A,
    const float* B,
    float* C,
    int M,
    int N,
    int K) {
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    int row = blockIdx.y * blockDim.y + threadIdx.y;

    if (row < M && col < N) {
        float acc = 0.0f;
        for (int k = 0; k < K; ++k) {
            acc += A[row * K + k] * B[k * N + col];
        }
        C[row * N + col] = acc;
    }
}
```

可以先把它记成：

```text
thread(row, col) 负责一个 C[row, col]
它沿着 K 维循环，把 A 的一行和 B 的一列相乘累加
```

### 1.3 CPU reference 负责证明答案对

CPU reference 不追求快，只追求清楚：

```cpp
void matmul_cpu_ref(
    const std::vector<float>& A,
    const std::vector<float>& B,
    std::vector<float>& C,
    int M,
    int N,
    int K) {
    for (int row = 0; row < M; ++row) {
        for (int col = 0; col < N; ++col) {
            float acc = 0.0f;
            for (int k = 0; k < K; ++k) {
                acc += A[row * K + k] * B[k * N + col];
            }
            C[row * N + col] = acc;
        }
    }
}
```

> [!tip] 测试数据建议
> 不要只用全 1。可以用 `A[i] = sin(i) * 0.01f`、`B[i] = cos(i) * 0.01f`，或者用固定随机种子生成数据。全 1 容易掩盖下标错误。

## 2. naive matmul 为什么慢

naive matmul 的计算量其实很大：

```text
每个 C 元素需要 K 次乘法 + K 次加法
C 一共有 M * N 个元素
FLOPs 约等于 2 * M * N * K
```

所以 Week 4 的 benchmark 记录 TFLOPS：

```text
TFLOPS = 2 * M * N * K / time_seconds / 1e12
```

但 naive 版本的问题是：它虽然做了很多计算，却没有认真复用数据。

### 2.1 A 和 B 被重复读取

假设一个 block 计算 `16 x 16` 个 C 元素。对于这些输出：

- 同一行的多个 C 元素会反复读取同一段 A。
- 同一列的多个 C 元素会反复读取同一段 B。
- naive 版本每个线程都自己从 global memory 读，不和邻居共享。

例如：

```text
C[row, 0] 需要 A[row, 0..K-1]
C[row, 1] 也需要 A[row, 0..K-1]
C[row, 2] 仍然需要 A[row, 0..K-1]
```

这意味着 `A[row, k]` 会被同一行的很多输出列重复使用。如果每次都从 global memory 重新读，就浪费了复用机会。

> [!important] 第二层直觉
> naive matmul 慢，不是因为它数学公式错，而是因为它把“本来可以共享的数据”留在 global memory 里重复读取。

### 2.2 naive 的访存模式

对一个横向排列的 warp 来说，`col` 连续、`row` 相同：

```cpp
A[row * K + k]
B[k * N + col]
```

读 B 时，`col` 连续，地址通常连续：

```text
thread 0 -> B[k * N + col + 0]
thread 1 -> B[k * N + col + 1]
thread 2 -> B[k * N + col + 2]
...
```

读 A 时，同一行、同一个 `k` 下，多个线程可能都读同一个 `A[row * K + k]`。这不是 transpose 那种跨步写的问题，而是“同一个值被很多线程反复需要”的问题。

### 2.3 和 transpose 的区别

Week 3 transpose 的主要矛盾是：

```text
读连续时，写可能跨步
写连续时，读可能跨步
```

Week 4 matmul 的主要矛盾是：

```text
同一批 A/B 数据会服务很多 C 元素
如果不做 tiling，就会从 global memory 反复拿
```

所以 matmul 的优化重点不只是 coalescing，而是：

```text
coalescing + shared memory reuse + register reuse + 更高 arithmetic intensity
```

## 3. shared memory tiled matmul

shared memory tiled matmul 的核心想法是：

```text
一个 block 负责一个 C tile
每一轮从 K 维取一块 A tile 和一块 B tile
把 A/B tile 放入 shared memory
block 内线程同步
每个线程用 shared memory 中的数据累加自己的 C 元素
沿 K 维 tile 循环，直到累加完整个 K
```

![[图片/SVG/9_3_8_3.svg|955]]

### 3.1 一个 block 计算一个 C tile

假设 `TILE = 16`，一个 block 可以计算 `16 x 16` 个输出：

```text
C tile shape = 16 x 16
blockDim     = dim3(16, 16)
每个 thread 负责一个 C[row, col]
```

每一轮 K tile 中：

- `As[ty][tx]` 存 A 的一个 tile。
- `Bs[ty][tx]` 存 B 的一个 tile。
- 每个线程把一部分 A/B 从 global memory 搬到 shared memory。
- 同步后，每个线程在 shared memory 上做 `TILE` 次乘加。

### 3.2 教学版 tiled kernel 骨架

下面是概念骨架，不是最终优化版：

```cpp
template <int TILE>
__global__ void matmul_tiled(
    const float* A,
    const float* B,
    float* C,
    int M,
    int N,
    int K) {
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];

    int tx = threadIdx.x;
    int ty = threadIdx.y;
    int col = blockIdx.x * TILE + tx;
    int row = blockIdx.y * TILE + ty;

    float acc = 0.0f;

    for (int k0 = 0; k0 < K; k0 += TILE) {
        int a_col = k0 + tx;
        int b_row = k0 + ty;

        As[ty][tx] = (row < M && a_col < K)
            ? A[row * K + a_col]
            : 0.0f;

        Bs[ty][tx] = (b_row < K && col < N)
            ? B[b_row * N + col]
            : 0.0f;

        __syncthreads();

        for (int kk = 0; kk < TILE; ++kk) {
            acc += As[ty][kk] * Bs[kk][tx];
        }

        __syncthreads();
    }

    if (row < M && col < N) {
        C[row * N + col] = acc;
    }
}
```

这里的关键不是背代码，而是看懂四件事：

1. `row / col` 定位当前线程负责的 C 元素。
2. `k0` 表示当前正在处理 K 维的哪一段 tile。
3. A tile 的 shape 是 `C tile 的行 x K tile`。
4. B tile 的 shape 是 `K tile x C tile 的列`。

### 3.3 为什么需要两次 `__syncthreads()`

第一处同步：

```cpp
__syncthreads();
for (int kk = 0; kk < TILE; ++kk) {
    acc += As[ty][kk] * Bs[kk][tx];
}
```

它保证 block 内所有线程都已经把本轮 A/B tile 搬进 shared memory。

第二处同步：

```cpp
__syncthreads();
// 进入下一轮 k0，覆盖 As/Bs
```

它保证所有线程都已经用完当前 shared memory tile，避免某些线程提前进入下一轮，把 `As/Bs` 覆盖掉。

> [!warning] 不要只保留第一处同步
> 如果下一轮会复用同一块 `As/Bs` shared memory，那么覆盖前也要保证上一轮计算已经结束。

### 3.4 边界 tile 为什么补 0

当 `M/N/K` 不能被 `TILE` 整除时，边缘 tile 会有线程落在矩阵外。对 matmul 来说，越界位置应该补乘法的中性贡献：

```text
A 越界 -> 0
B 越界 -> 0
```

这样不会改变内积结果：

```text
acc += 0 * x
acc += x * 0
```

这和 Week 2 reduction 的非整除长度类似：sum 的越界元素补 `0.0f`，max 的越界元素要补负无穷或足够小的值。中性元必须跟算子语义一致。

## 4. register blocking toy

shared memory tiling 解决的是 block 内多个线程共享 A/B tile。register blocking 继续往前走一步：让一个线程负责多个 C 输出，从而在寄存器里复用读到的数据。

入门阶段可以只做 toy 版本：

```text
一个线程计算 2 个 C 元素，或者 4 个 C 元素
例如 C[row, col] 和 C[row, col + 1]
```

### 4.1 直觉例子

如果一个线程同时算同一行的两个输出：

```text
C[row, col]
C[row, col + 1]
```

这两个输出在同一个 `k` 下会用到同一个 A：

```text
C[row, col]     += A[row, k] * B[k, col]
C[row, col + 1] += A[row, k] * B[k, col + 1]
```

所以 `A[row, k]` 可以读一次，放在寄存器里，用两次。

### 4.2 toy 伪代码

```cpp
float acc0 = 0.0f;
float acc1 = 0.0f;

for (int k = 0; k < K; ++k) {
    float a = A[row * K + k];
    float b0 = B[k * N + col];
    float b1 = B[k * N + col + 1];

    acc0 += a * b0;
    acc1 += a * b1;
}

C[row * N + col] = acc0;
if (col + 1 < N) {
    C[row * N + col + 1] = acc1;
}
```

这只是直觉版本。真正高性能 GEMM 会有更复杂的 thread tile、warp tile、指令调度和 Tensor Core 路径。Week 4 先不要急着跳过去。

### 4.3 register pressure 的代价

register blocking 不是免费午餐：

- 一个线程算更多输出，需要更多 accumulator。
- 更多寄存器可能降低 occupancy。
- occupancy 下降后，GPU 可能更难隐藏 memory latency。
- 寄存器太多甚至可能 spill 到 local memory，性能反而下降。

> [!important] 第三层直觉
> register blocking 的收益来自寄存器复用；代价来自 register pressure。Week 4 不要求你写出最优 blocking，只要求你能用 Nsight 的 register count、occupancy、stall reason 解释收益和代价。

## 5. 数值分析与线性代数辅助

MatMul 的数学核心是大量内积。每个 `C[row, col]` 都是：

$$
\sum_{k=0}^{K-1} A_{row,k}B_{k,col}
$$

这意味着它天然包含 reduction：沿 K 维把很多乘积加起来。

### 5.1 内积就是局部 reduction

从 [[数值分析与 GPU Kernel 正确性]] 的角度看，matmul 不是纯粹的“二维索引题”，它还包含误差累积：

```text
K 越大，累加项越多
累加顺序不同，浮点结果可能略有差异
低精度输入如果低精度累加，误差会更明显
```

所以 correctness 不能用 `==`：

```cpp
float max_abs_error(
    const std::vector<float>& actual,
    const std::vector<float>& expected) {
    float max_err = 0.0f;
    for (size_t i = 0; i < actual.size(); ++i) {
        max_err = std::max(max_err, std::abs(actual[i] - expected[i]));
    }
    return max_err;
}
```

对于 FP32 naive / tiled 入门版，可以先用比较严格但仍允许浮点微差的阈值，例如：

```text
rtol = 1e-4
atol = 1e-4
```

实际阈值要根据 shape、输入范围、CPU reference 路径调整，不能永久照抄。

### 5.2 error report 比一句 pass 更有用

可以把 [[3.7 距离空间到 GPU Kernel 正确性 - 数学与代码桥接]] 的距离意识写进测试报告：

```python
import torch


def matmul_error_report(actual: torch.Tensor, expected: torch.Tensor):
    actual = actual.float()
    expected = expected.float()
    err = actual - expected

    max_abs = torch.max(torch.abs(err))
    mean_abs = torch.mean(torch.abs(err))
    rms = torch.sqrt(torch.mean(err * err))
    rel = torch.abs(err) / torch.clamp(torch.abs(expected), min=1e-6)
    max_rel = torch.max(rel)

    return {
        "max_abs": max_abs.item(),
        "mean_abs": mean_abs.item(),
        "rms": rms.item(),
        "max_rel": max_rel.item(),
    }
```

这里的数学含义是：

| 指标 | 对应直觉 |
|---|---|
| `max_abs` | 最坏一个元素错了多少 |
| `mean_abs` | 平均偏差 |
| `rms` | 整体能量误差，和 L2 思想接近 |
| `max_rel` | 相对量级下最坏偏差 |

> [!tip] 和线性代数的连接
> MatMul 输出是一个矩阵。你可以把误差矩阵 `E = C_cuda - C_ref` 看作另一个矩阵，再用 max abs、RMS、Frobenius norm 等方式判断它是否足够小。测试不是“肉眼看差不多”，而是明确选择距离和阈值。

### 5.3 FP32 accumulation 是入门阶段的安全默认

Week 4 先用 FP32 输入和 FP32 累加：

```cpp
float acc = 0.0f;
acc += A[row * K + k] * B[k * N + col];
```

后面进入 FP16/BF16/Tensor Core 时，常见工程问题会变成：

```text
输入是什么 dtype？
乘法是什么 dtype？
累加是什么 dtype？
输出是什么 dtype？
reference 用什么路径？
tolerance 为什么合理？
```

但 Week 4 v0 不需要提前实现这些复杂路径。先把 FP32 的正确性、tiling、benchmark、profiling 讲清楚。

## 6. benchmark / roofline / Nsight

MatMul 常用 TFLOPS 作为性能结果：

```text
FLOPs = 2 * M * N * K
TFLOPS = FLOPs / time_seconds / 1e12
```

但是 TFLOPS 只是结果。解释性能时，还要看数据搬运量和算术强度。

### 6.1 arithmetic intensity

算术强度可以先粗略理解成：

```text
arithmetic intensity = FLOPs / bytes moved
```

它回答的是：

```text
每搬 1 byte 数据，做了多少计算？
```

对于 matmul，tiling 的目标之一就是让同一批 A/B 数据被更多乘加复用，从而提高 FLOPs / byte。

![[图片/SVG/9_3_8_4.svg|955]]

### 6.2 compute-bound / memory-bound 怎么判断

可以先用 roofline thinking 粗略判断：

| 状态 | 直觉 | Week 4 观察 |
|---|---|---|
| memory-bound | 搬数据限制性能 | naive 可能因为复用差，实际 FLOPs 上不去 |
| compute-bound | 算力限制性能 | 优化后的 matmul 更可能接近计算上限 |
| 中间状态 | 访存和计算都还没喂满 | 入门 tiled 版本常见，需要结合 Nsight 指标解释 |

Week 4 不要求画出严格 roofline 模型，但 README / `profiling.md` 里要有这种判断意识：

```text
我这个版本慢，是因为 global memory 重复读取？
还是因为 shared memory / register 使用导致 occupancy 降低？
还是因为指令调度、tile size、register blocking 太弱？
```

### 6.3 Nsight Compute 关注什么

建议至少看这些指标：

| 指标 | 看什么 | 和 MatMul 的关系 |
|---|---|---|
| achieved occupancy | 实际驻留情况 | register / shared memory 使用过多可能降低 occupancy |
| SM utilization | SM 是否忙 | 算力有没有被喂起来 |
| memory throughput | global memory 压力 | naive 的重复读取会影响解释 |
| shared memory usage | shared tile 成本 | tile size 影响 shared memory 占用 |
| register count | 单线程寄存器压力 | register blocking toy 必看 |
| warp stall reason | warp 在等什么 | memory dependency、barrier、not selected 等要结合代码解释 |

### 6.4 cuBLAS baseline 怎么看

cuBLAS 是 baseline，不是 Week 4 v0 必须打败的对手。

自己写的 FP32 naive / tiled / register blocking toy 和 cuBLAS 的差距，可能来自：

- Tensor Core 或更高效的指令路径。
- 多级 tiling：thread tile、warp tile、block tile。
- 更成熟的 shared memory layout 和 bank conflict 处理。
- register blocking 与指令调度。
- 针对不同 shape 的 kernel selection。
- 多年工程优化，不是一个教学 kernel 一周内能追平的。

> [!note] 面试表达
> 我用 cuBLAS 作为工业库 baseline，不把打不过 cuBLAS 解释成失败。我的目标是能通过 benchmark 和 Nsight 说明 naive、tiled、register blocking toy 的性能变化，以及它们和 cuBLAS 差距大致来自哪里。

## 8. 关键要点总结

1. MatMul 的每个输出元素是一个 K 维内积，本质上包含 reduction。
2. naive 版本最重要的缺点是 A/B 数据复用差，global memory 重复读取多。
3. shared memory tiled matmul 让一个 block 复用 A/B tile，提升 FLOPs / byte。
4. register blocking 继续在单线程寄存器里复用数据，但会带来 register pressure。
5. correctness 要用 reference、误差阈值和非整除 shape 验证，不能只看 TFLOPS。
6. cuBLAS 是工业 baseline，差距需要解释，不需要在 Week 4 v0 打赢。
7. roofline thinking 的价值是把“快/慢”变成“受访存限制还是受计算限制”的判断。
