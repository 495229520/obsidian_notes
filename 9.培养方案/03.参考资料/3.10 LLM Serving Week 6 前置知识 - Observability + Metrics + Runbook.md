## 0. 你已经掌握了什么

如果已经完成 [[Week 5 - Serving Benchmark Harness]]，你应该已经能产出这样的结果表：

| Scenario | Req/s | Max Conc | Prompt | Output | TTFT p95 | TPOT p95 | TPS | Failed |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| low latency | 1 | 4 | 128 | 64 | low | low | modest | 0 |
| high throughput | 16 | 64 | 512 | 128 | higher | higher | high | maybe |
| long context | 2 | 16 | 4096 | 128 | high | medium | medium | maybe |
| backlog | overload | high | mixed | mixed | very high | unstable | plateau | rising |

这些表能告诉你：

- 哪个 workload 的 TTFT / TPOT / E2E latency 变差。
- TPS / RPS 是否已经到达平台瓶颈。
- failed requests 是否开始出现。
- request rate 和 max concurrency 调整后，延迟和吞吐如何交换。

但 Week 5 还不能完整回答：

```text
为什么 TTFT 变高？
为什么 TPS 不再上涨？
为什么 waiting requests 堆起来？
为什么 KV cache 接近满之后开始失败？
下一步应该调 request rate、max concurrency、max model len、prefix cache，还是换模型 / 增卡？
```

Week 6 要补的就是这条证据链：

```text
benchmark result
-> live metrics
-> dashboard panels
-> diagnosis
-> next experiment
-> mitigation / fix
```

> [!important] 第一层直觉
> Benchmark 是离线体检报告，observability 是在线监护仪，runbook 是医生看到指标后的处置路径。三者连起来，才像工程排障，而不是只会贴一张延迟表。

## 1. 为什么 Week06 要补 Observability

[[3.9 LLM Serving Week 5 前置知识 - Benchmark Harness + Metrics]] 解决的是“实验是否公平、可复现、可解释”。[[Week 6 - Observability + Metrics]] 继续往前走，解决的是“服务运行时如何定位瓶颈”。

LLM serving 的问题通常不是单指标问题：

| 看到的现象 | 单看 benchmark 的局限 | Week 6 要补的观测 |
|---|---|---|
| TTFT p95 变高 | 只知道首 token 慢 | queue time、waiting requests、prefill time、KV cache usage |
| TPOT / ITL 变高 | 只知道输出不顺滑 | decode time、running requests、generation tokens/s、KV cache pressure |
| TPS 不涨 | 只知道吞吐到顶 | running / waiting、GPU cache usage、failed requests、request_success |
| failed requests 增多 | 只知道失败率变高 | finish reason、HTTP errors、server log、OOM / timeout / length limit |
| GPU utilization 高 | 只知道 GPU 忙 | 是否真的带来 tokens/s，还是 batch / KV cache / queue 在恶化 |

> [!warning] 不要把 Grafana 当截图工具
> Dashboard 的价值不是“看起来专业”，而是让每个 benchmark 结论都有运行时证据。看板上每个 panel 都应该能回答一个诊断问题。

## 2. server-level metrics vs request-level metrics

vLLM 官方 metrics 设计里有一个很适合 Week 6 的心智模型：

```text
server-level metrics 用来解释 request-level metrics。
```

换成工程语言：

| 类型 | 关注对象 | Prometheus 类型 | 回答的问题 | 例子 |
|---|---|---|---|---|
| Server-level | 引擎当前状态 | Gauge / Counter | 服务现在忙不忙、堵不堵、资源满不满 | `vllm:num_requests_running`、`vllm:num_requests_waiting`、`vllm:kv_cache_usage_perc` |
| Request-level | 单个请求经历 | Histogram | 用户请求慢在哪里、SLO 是否被打穿 | `vllm:time_to_first_token_seconds`、`vllm:inter_token_latency_seconds`、`vllm:request_queue_time_seconds` |
| Throughput | token / request 产出 | Counter + rate | 单位时间处理多少输入和输出 | `vllm:prompt_tokens`、`vllm:generation_tokens`、`vllm:request_success` |

### 2.1 request-level 指标负责描述用户体验

| 指标 | 直觉 | 主要阶段 |
|---|---|---|
| TTFT | 用户多久看到第一个 token | queue + input processing + prefill + first decode |
| TPOT / ITL | 开始输出后是否顺滑 | decode |
| E2E latency | 一个请求完整花多久 | queue + prefill + decode + response |
| queue time | 请求在 WAITING 阶段等多久 | scheduler / admission |

### 2.2 server-level 指标负责解释为什么

| 指标 | 直觉 | 常见解释 |
|---|---|---|
| running requests | 正在执行的请求数 | batch 是否吃满、decode 是否拥挤 |
| waiting requests | 等待调度的请求数 | 是否 backlog、是否超出服务能力 |
| KV cache usage | KV cache 块使用比例 | 长上下文 / 高并发是否挤爆 cache |
| prompt tokens/s | prefill 输入 token 处理速率 | 长 prompt 压力、prefix cache 效果 |
| generation tokens/s | decode 输出 token 处理速率 | decode 吞吐、batch tradeoff |

> [!tip] 读图顺序
> 先看 request-level 指标确认用户体验是否变差，再看 server-level 指标解释原因。不要反过来只盯 GPU / cache，然后猜用户是否受影响。

## 3. vLLM metrics 暴露链路：/metrics -> Prometheus -> Grafana

vLLM OpenAI-compatible server 会通过 Prometheus 格式的 `/metrics` 暴露指标。Week 6 的最小链路是：

![[图片/SVG/9_3_10_2.svg|955]]

```text
benchmark client
-> vLLM OpenAI-compatible server
-> /metrics
-> Prometheus scrape
-> Grafana dashboard
-> runbook / report
```

### 3.1 先确认 `/metrics`，再做 dashboard

第一天不要急着美化 Grafana，先确认实际服务暴露了什么：

```bash
curl http://127.0.0.1:8000/metrics | rg "vllm:(num_requests|time_to_first|inter_token|queue|kv_cache|prompt_tokens|generation_tokens|request_success)"
```

需要记录：

```text
vLLM version:
server command:
model:
dtype:
max model len:
gpu_memory_utilization:
prefix caching:
CUDA / driver:
GPU:
metrics endpoint:
scrape interval:
```

> [!warning] 指标名要以当前 `/metrics` 为准
> vLLM 版本之间存在指标命名变化。官方 latest 文档里有 `vllm:prompt_tokens` / `vllm:generation_tokens` / `vllm:request_success`，部分设计文档或旧 dashboard 可能出现带 `_total` 的名字。实际项目中先 `curl /metrics`，再写 PromQL。

### 3.2 Week 6 必看的 vLLM 指标

| 类别 | 指标 | 用途 |
|---|---|---|
| Request state | `vllm:num_requests_running` | 当前进入执行 batch 的请求数 |
| Request state | `vllm:num_requests_waiting` | 当前等待处理的请求数 |
| Queue | `vllm:request_queue_time_seconds` | 请求在 WAITING 阶段等待多久 |
| Latency | `vllm:time_to_first_token_seconds` | TTFT |
| Latency | `vllm:inter_token_latency_seconds` | token 间隔，接近 TPOT / ITL |
| Latency | `vllm:request_time_per_output_token_seconds` | 按请求统计的 TPOT |
| Phase | `vllm:request_prefill_time_seconds` | prefill 阶段耗时 |
| Phase | `vllm:request_decode_time_seconds` | decode 阶段耗时 |
| Cache | `vllm:kv_cache_usage_perc` | KV cache 使用比例，1 表示 100% |
| Tokens | `vllm:prompt_tokens` | prefill token 计数，用 `rate()` 看 tokens/s |
| Tokens | `vllm:generation_tokens` | generation token 计数，用 `rate()` 看 tokens/s |
| Reliability | `vllm:request_success` | 成功请求数，通常带 finish reason 标签 |

### 3.3 PromQL 只服务诊断

入门阶段的 PromQL 不需要花哨，能回答问题就够：

```promql
rate(vllm:prompt_tokens[1m])
rate(vllm:generation_tokens[1m])
vllm:num_requests_running
vllm:num_requests_waiting
histogram_quantile(0.95, rate(vllm:time_to_first_token_seconds_bucket[5m]))
histogram_quantile(0.95, rate(vllm:request_queue_time_seconds_bucket[5m]))
histogram_quantile(0.95, rate(vllm:inter_token_latency_seconds_bucket[5m]))
vllm:kv_cache_usage_perc
rate(vllm:request_success[5m])
```

如果本机 `/metrics` 暴露的是 `_total` 命名，就把 counter 名按实际输出替换。

## 4. TTFT 变高如何排查

TTFT 是 Week 6 最值得练的 runbook 症状，因为它横跨 queue、prefill、网络和 cache。

![[图片/SVG/9_3_10_3.svg|955]]

### 4.1 TTFT 的组成

可以先粗略理解成：

```text
TTFT ~= client/network + server input processing + queue time + prefill time + first token generation
```

vLLM 设计文档里会把请求进入、排队、调度、prefill、new tokens 等事件拆开计算。对 Week 6 来说，关键不是背实现细节，而是知道 TTFT 不是单纯的 GPU kernel 时间。

### 4.2 排查表

| 先看指标 | 判断方向 | 下一步实验 | 临时缓解 | 长期修复 |
|---|---|---|---|---|
| `vllm:num_requests_waiting` 持续上升，`request_queue_time_seconds` p95 上升 | queueing / backlog | 降低 request rate，对比同一 prompt/output 下的 TTFT | 限流、降低 max concurrency、加 replica | 容量规划、autoscaling、按 workload 拆服务 |
| `request_prefill_time_seconds` 上升，prompt tokens/s 压力大 | prefill-heavy | 固定输出长度，扫 prompt length | 限制 max input length、启用 prefix cache | prefix cache、chunked prefill、长上下文优化 |
| queue 不高，prefill 不高，但 client 侧 TTFT 高 | network / gateway | 同机 curl 或内网压测，对比客户端耗时 | 旁路代理、降低跨区访问 | 网络链路、网关超时和 streaming 配置优化 |
| `kv_cache_usage_perc` 接近 1，waiting 上升或 preemption 增多 | KV cache pressure | 降 max model len / concurrency 做 A/B | 降低并发、缩短上下文、换小模型 | 多卡、paged KV 策略、cache / scheduler 调参 |

> [!important] 判断 queueing 的最短路径
> TTFT p95 上升时，如果 waiting requests 和 queue time 同时上升，优先按 backlog 处理；如果 waiting 不高，再继续看 prefill、network 和 KV cache。

## 5. TPOT / ITL 变高如何排查

TPOT / ITL 更接近 decode 阶段的体感：首 token 已经出来了，但后续 token 流得慢。

### 5.1 常见现象

```text
TTFT 还可以
streaming 已经开始
但每个 token 间隔越来越长
用户感觉模型说话卡顿
```

### 5.2 排查表

| 先看指标 | 判断方向 | 下一步实验 | 临时缓解 | 长期修复 |
|---|---|---|---|---|
| `inter_token_latency_seconds` p95 上升，`request_decode_time_seconds` 上升 | decode 慢 | 固定 prompt，扫 output length 和 max concurrency | 降低 max concurrency、限制 max_tokens | decode kernel / attention / KV cache 读优化 |
| running requests 很高，generation tokens/s 上升但 TPOT 变差 | batch 太大，吞吐换延迟 | 扫 max concurrency，画 TPS vs TPOT 曲线 | 按低延迟业务降低 batch 压力 | 分层服务：低延迟池和高吞吐池 |
| `kv_cache_usage_perc` 高，长上下文请求多 | KV cache 读带宽或 cache pressure | 分短上下文 / 长上下文 workload 对比 | 限制 long context 比例 | KV cache 优化、分页策略、多实例隔离 |
| generation tokens/s 不涨，running 也不高 | 可能是模型 / GPU / 配置瓶颈 | 对比更小模型、dtype、tensor parallel | 换小模型或降低输出长度 | 模型选择、并行配置、kernel 优化 |

> [!tip] TPOT 和 TPS 的关系
> 高 TPS 可能来自更大的 batch，但更大的 batch 也可能让单请求 TPOT 变差。报告里要同时写吞吐和单请求体验。

## 6. running requests / waiting requests / queue time 怎么看

这三个指标是 Week 6 的核心三件套：

| 指标 | 意义 | 变高时代表 |
|---|---|---|
| running requests | 正在模型执行 batch 中的请求 | 服务正在忙，batch 可能更满 |
| waiting requests | 等待被调度的请求 | backlog、capacity 不足、admission 受限 |
| queue time | 单个请求在 WAITING 阶段花的时间 | 用户 TTFT 里有多少来自排队 |

### 6.1 四种典型形态

| running | waiting | queue time | 解释 |
|---:|---:|---:|---|
| 低 | 低 | 低 | 负载低，baseline |
| 高 | 低 | 低 | 服务吃满但没有明显排队，可能是理想吞吐区 |
| 高 | 高 | 高 | 到达率超过处理能力，backlog |
| 低 | 高 | 高 | 调度 / admission / cache / 外部依赖可能卡住 |

### 6.2 和 Week 5 参数连起来

Week 5 调的 `request rate` 和 `max concurrency`，在 Week 6 看板上应该能看到对应变化：

| Week 5 操作 | Week 6 预期观测 | 解释 |
|---|---|---|
| 提高 request rate | waiting 和 queue time 可能上升 | 外部流量来得更快 |
| 提高 max concurrency | running 可能上升，TPOT 可能变差 | batch 更满，但单请求 decode 压力更大 |
| 增加 prompt length | prefill time、TTFT、KV cache usage 可能上升 | prefill-heavy |
| 增加 output length | decode time、TPOT、KV cache lifetime 可能上升 | decode-heavy |

## 7. KV cache / GPU cache usage 接近满时怎么判断

vLLM latest 文档中 `vllm:kv_cache_usage_perc` 表示 KV cache 使用比例，接近 1 就是接近满。

KV cache pressure 通常来自：

- prompt 太长。
- output 太长。
- 并发太高。
- `max_model_len` 配太大，预留空间压力高。
- 长上下文请求和短请求混在一起。
- prefix cache / KV cache 行为没有按预期复用。

### 7.1 不要只看 cache usage

| 组合现象 | 更可能的解释 | 动作 |
|---|---|---|
| cache usage 高，但 waiting 低、TTFT 稳 | 资源接近满但还没影响 SLO | 观察趋势，保留 headroom |
| cache usage 高，waiting 和 queue time 上升 | cache 限制 admission 或调度 | 降并发、降 max model len，分离长上下文 |
| cache usage 高，failed requests 增多 | OOM、长度限制、timeout 或调度失败 | 查 server log、benchmark raw errors、HTTP status |
| cache usage 高，TPOT 变差 | decode 读 KV 压力变大 | 降 batch、隔离 long output、优化 KV 访问 |

### 7.2 处理手段排序

| 手段 | 适合情况 | 代价 |
|---|---|---|
| 降低 max concurrency | backlog / cache pressure 突然出现 | TPS 可能下降 |
| 限制 max input / output tokens | 长上下文拖垮服务 | 产品能力受限 |
| 降低 `max_model_len` | 实际业务不需要极长上下文 | 无法服务超长请求 |
| 启用 / 验证 prefix cache | shared prefix 比例高 | 对随机 prompt 帮助有限 |
| 分离 workload | 长上下文和短请求互相影响 | 运维复杂度上升 |
| 增加 GPU / replica | 服务能力不足 | 成本上升 |

> [!warning] cache 接近满不是唯一原因
> KV cache usage 高只能说明压力存在，不自动等于根因。只有当它和 queue time、waiting requests、TTFT / TPOT 或 failed requests 同时变化时，才更像排障证据。

## 8. dashboard 应该服务谁：开发调试 / SRE 监控 / benchmark 报告

同一批 metrics 可以做三种 dashboard，但目标不同。

| 视角 | 关心什么 | Panel 应该怎么组织 |
|---|---|---|
| 开发调试 | 为什么这个场景慢 | 按阶段：queue、prefill、decode、KV cache、tokens/s |
| SRE 监控 | 线上是否接近 SLO 风险 | 按告警：TTFT p95、TPOT p95、waiting、error / failed、cache headroom |
| benchmark 报告 | 负载变化如何影响指标 | 按实验：低延迟、高吞吐、长上下文、shared prefix、backlog |

### 8.1 最小 dashboard 面板

| Panel | 指标 | 解释 |
|---|---|---|
| Request states | running / waiting | 服务是否排队 |
| Queue latency | queue time p50 / p95 | TTFT 中排队占比 |
| TTFT | TTFT p50 / p95 / p99 | 首 token 体验 |
| TPOT / ITL | ITL / TPOT p50 / p95 | streaming 是否顺滑 |
| Tokens/s | prompt tokens/s、generation tokens/s | prefill / decode 吞吐 |
| KV cache | KV cache usage | cache headroom |
| Request result | request_success / HTTP status / raw failed | 请求是否失败 |

> [!tip] 面试表达
> 我不是只搭了 Grafana，而是把 Week 5 的 benchmark 场景复跑到 dashboard 上，观察 queue、prefill、decode、KV cache 和 failed requests 的拐点，再把判断过程沉淀成 runbook。

## 9. runbook 写法：症状 -> 指标 -> 原因 -> 实验 -> 缓解 -> 长期修复

Runbook 不是“可能原因大全”，而是看到症状后的下一步动作。

![[图片/SVG/9_3_10_4.svg|955]]

### 9.1 模板

```markdown
## Symptom: TTFT p95 suddenly increases

### First metrics to check
- TTFT p95 / p99
- request_queue_time_seconds p95
- num_requests_waiting
- request_prefill_time_seconds p95
- kv_cache_usage_perc
- prompt_tokens/s

### Likely causes
- request backlog
- long prompt / prefill-heavy workload
- KV cache pressure
- network / gateway latency

### Next experiment
- replay the same workload with lower request rate
- fix prompt/output length and sweep max concurrency
- compare short prompt vs long prompt
- run local client near the server

### Immediate mitigation
- rate limit
- lower max concurrency
- shorten max input length
- route long-context traffic separately

### Long-term fix
- capacity planning / autoscaling
- prefix cache validation
- chunked prefill or scheduler tuning
- dashboard alert based on TTFT + queue time
```

### 9.2 五个必写症状

| 症状 | 先看指标 | 最重要判断 |
|---|---|---|
| TTFT 变高 | queue time、waiting、prefill、KV cache | 首 token 慢来自排队还是 prefill |
| TPOT / ITL 变高 | inter-token latency、decode time、running、generation tokens/s | decode 是否被 batch / KV cache 拖慢 |
| GPU utilization 高但 TPS 不涨 | tokens/s、running、waiting、failed | GPU 忙是否转化成有效吞吐 |
| KV cache usage 接近满 | cache usage、waiting、failed、TTFT / TPOT | cache 压力是否影响 SLO |
| failed requests 增多 | request_success finish reason、HTTP errors、server log、raw benchmark errors | 是 OOM、timeout、abort、length 还是网关错误 |

### 9.3 failed requests 的证据链

不要为 failed requests 虚构一个固定指标。更稳的证据链是：

```text
benchmark raw JSON / CSV failed count
-> HTTP status / client exception
-> vLLM request_success finish reason
-> server log
-> resource metrics and KV cache usage
```

报告里要把失败请求单独列出来，因为 failed requests 也消耗资源，不能从 TPS / cost 分析里消失。

## 关键要点总结

1. Week 5 benchmark 告诉你指标变了，Week 6 observability 解释为什么变。
2. server-level metrics 解释 request-level metrics：running / waiting / KV cache / tokens/s 用来解释 TTFT / TPOT / E2E。
3. TTFT 变高优先看 queue time 和 waiting requests，再看 prefill、network 和 KV cache pressure。
4. TPOT / ITL 变高优先看 decode time、running requests、generation tokens/s 和 KV cache usage。
5. KV cache usage 接近满要和 queue、latency、failed requests 联合判断。
6. Failed requests 不能只看一个指标，要结合 benchmark raw result、HTTP status、vLLM request result 和 server log。
7. Dashboard 不是截图材料，而是 runbook 的证据入口。
