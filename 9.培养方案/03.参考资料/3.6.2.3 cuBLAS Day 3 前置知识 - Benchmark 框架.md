## 1. Day 3 要解决什么

目标可以压成一句话：

```text
用统一 benchmark 框架公平比较 custom kernel 和 cuBLAS。
```

Day 3 不要求你优化 kernel，但要求你能回答：

- 测的是 GPU GEMM 本体，还是混入了 H2D / D2H？
- warmup 多少次？
- repeat 多少次？
- 取 median、min 还是平均值？
- TFLOPS 怎么算？
- `ratio vs cuBLAS` 的基准是哪一行？

> [!important] 第一层直觉
> benchmark 不是“跑一下看看”。它是一份实验协议：只要协议稳定，后续 naive、tiled、register blocking、cuBLAS 才能放到同一张表里比较。

---

## 2. 计时范围

建议计时范围：

```text
included: kernel / cublasSgemm 本身
excluded: cudaMalloc, H2D, D2H, CPU reference, CSV 写文件
```

典型流程是：

```text
1. host 初始化 A/B
2. cudaMalloc
3. H2D 拷贝 A/B
4. warmup 多次 GEMM
5. CUDA event start
6. repeat 多次 GEMM
7. CUDA event stop
8. D2H 拷贝 C
9. correctness 对拍
10. 写 benchmark.csv
```

其中只有第 5 到第 7 步属于 GEMM 计时窗口。

### 2.1 benchmark 一次完整迭代流程

建议把 benchmark 拆成两条路径：correctness run 和 timing run。

correctness run：

```text
初始化输入
运行一次 custom kernel 或 cuBLAS
D2H 拷回输出
和 reference 对拍
记录 correct / max error
```

timing run：

```text
初始化输入
H2D 拷贝
warmup 多次
CUDA event 计时 repeat 多次
记录平均、median 或 min
```

这两条路径可以复用同一个 kernel 调用函数，但目的不同：

- correctness run 证明结果可信。
- timing run 证明性能数字有稳定协议。

> [!warning] 不要为了省事跳过 correctness run
> 一个错误 kernel 也可能跑得很快。Day 3 的 benchmark 表里必须保留 `correct` 字段，否则 TFLOPS 没有工程意义。

## 3. CUDA event timing

CUDA event 可以记录 GPU 时间线上的事件。最小形状：

```cpp
cudaEvent_t start;
cudaEvent_t stop;
cudaEventCreate(&start);
cudaEventCreate(&stop);

cudaEventRecord(start);
for (int i = 0; i < repeat; ++i) {
    sgemm_row_major(handle, M, N, K, A, B, C);
}
cudaEventRecord(stop);
cudaEventSynchronize(stop);

float elapsed_ms = 0.0f;
cudaEventElapsedTime(&elapsed_ms, start, stop);
float avg_ms = elapsed_ms / repeat;

cudaEventDestroy(start);
cudaEventDestroy(stop);
```

建议默认：

```text
warmup = 10
repeat = 100
time = median 或 min
```

如果暂时只做最小版，可以先记录平均值，但 README 里要写清楚取值方式。

### 3.1 同步点和误差来源

`cudaEventRecord(stop)` 之后要调用：

```cpp
cudaEventSynchronize(stop);
```

它保证 stop event 已经在 GPU 时间线上完成，然后再读 elapsed time。否则 CPU 可能在 GPU 工作尚未完成时就继续往下走，计时结果不可靠。

warmup 的作用：

```text
避开首次运行的额外开销，让后续 repeat 更接近稳定状态。
```

repeat 的作用：

```text
降低单次波动，让一次偶然抖动不决定最终结果。
```

`median` 和 `min` 的取舍可以先这样理解：

| 取值 | 适合表达 |
|---|---|
| `median` | 更接近日常稳定表现 |
| `min` | 更接近最好情况下的 kernel 能力 |
| `mean` | 容易被偶发抖动拉偏，但最小实现简单 |

Day 3 可以先记录平均值，但 README 或表格里必须写清楚。后续要做作品集版本时，再升级到 median 或 min。

## 4. CSV 字段

`benchmark.csv` 至少记录这些列：

```text
M,N,K,dtype,layout,implementation,ms,TFLOPS,ratio_vs_cublas,correct
```

表格示例：

| M | N | K | dtype | layout | implementation | ms | TFLOPS | ratio_vs_cublas | correct |
|---:|---:|---:|---|---|---|---:|---:|---:|---|
| 512 | 512 | 512 | FP32 | row-major wrapper | tiled CUDA |  |  |  | pass |
| 512 | 512 | 512 | FP32 | row-major wrapper | cuBLAS SGEMM |  |  | 1.00 | pass |

`implementation` 不要写得太含糊。建议固定成：

```text
naive CUDA
tiled CUDA
reg-block toy
cuBLAS SGEMM
```

### 4.1 同 shape 成对记录规则

同一个 shape 下，custom kernel 和 cuBLAS baseline 最好相邻记录：

```text
512,512,512,FP32,row-major wrapper,tiled CUDA,...
512,512,512,FP32,row-major wrapper,cuBLAS SGEMM,...
```

这样做有两个好处：

- `ratio_vs_cublas` 的基准行一眼能找到。
- 后续写 README 表格时，不容易把不同 shape 的时间拿来相除。

建议排序规则：

```text
按 shape 分组
每组先放 custom kernel
每组最后放 cuBLAS SGEMM
```

如果同一个 shape 有多个 custom 版本，可以这样排：

```text
naive CUDA
tiled CUDA
reg-block toy
cuBLAS SGEMM
```

## 5. TFLOPS 和 ratio

GEMM 的 FLOPs 先按入门公式计算：

```text
FLOPs = 2 * M * N * K
TFLOPS = FLOPs / time_seconds / 1e12
```

如果 `ms` 是毫秒：

```text
time_seconds = ms / 1000
```

`ratio_vs_cublas` 建议定义成：

```text
ratio_vs_cublas = implementation_ms / cublas_ms
```

含义：

| ratio | 解释 |
|---:|---|
| `1.00` | 和 cuBLAS 一样快 |
| `2.00` | 耗时是 cuBLAS 的 2 倍 |
| `10.00` | 耗时是 cuBLAS 的 10 倍 |

> [!tip] 报告表达
> 对学习型 kernel 来说，ratio 大不是失败。真正重要的是能解释差距来自访存复用、tile 设计、register pressure、Tensor Core 路径还是库级调度。

## 6. 常见坑

- 把 `cudaMemcpy` 时间混进 GEMM 时间，导致比较不公平。
- 没有 warmup，第一次运行包含额外初始化开销。
- 只 repeat 一次，结果被系统噪声影响。
- cuBLAS 和 custom kernel 用了不同 shape 或不同 dtype。
- 只记录 ms，不记录 correctness。
- 只测试方阵，不覆盖非方阵和非 tile 对齐尺寸。
- CSV 没有记录 layout，后面无法确认是否经过 row-major wrapper。

## 7. 当天验收标准

Day 3 结束时，至少要做到：

- [ ] benchmark 框架能跑同一个 shape 下的 custom kernel 和 cuBLAS。
- [ ] 使用 CUDA event 计时。
- [ ] 明确排除 H2D / D2H 时间。
- [ ] 有 warmup 和 repeat。
- [ ] CSV 记录 `M/N/K/dtype/layout/implementation/ms/TFLOPS/ratio_vs_cublas/correct`。
- [ ] 同 shape 下 custom kernel 和 cuBLAS 成对相邻记录。
- [ ] README 能解释 `ratio_vs_cublas` 的含义。

最低 shape 建议：

```text
512 x 512 x 512
1024 x 1024 x 1024
257 x 509 x 1024
```

验收输出可以写成：

```text
benchmark.csv generated
timing scope = GEMM only
warmup = 10
repeat = 100
cuBLAS baseline recorded for each shape
```
