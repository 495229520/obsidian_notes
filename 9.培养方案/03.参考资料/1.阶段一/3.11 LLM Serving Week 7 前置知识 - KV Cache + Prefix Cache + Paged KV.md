## 0. 你已经掌握了什么

从 [[3.9 LLM Serving Week 5 前置知识 - Benchmark Harness + Metrics]] 开始，你已经知道 serving benchmark 不能只看平均 TPS：

- 长 prompt 会推高 TTFT。
- 长 output 会影响 TPOT / ITL 和 E2E latency。
- request rate 和 max concurrency 会影响 queueing。
- failed requests 不能从原始数据里删掉。
- random prompt、shared prefix、long context 是不同 workload。

从 [[3.10 LLM Serving Week 6 前置知识 - Observability + Metrics + Runbook]] 开始，你已经能把现象接到指标：

| Week 6 指标 | 说明 | Week 7 继续追问 |

| `vllm:time_to_first_token_seconds` | TTFT | 是 queue，还是 prefill / cache miss？ |
| `vllm:inter_token_latency_seconds` | TPOT / ITL | decode 是否持续读 KV cache 变慢？ |
| `vllm:kv_cache_usage_perc` | KV cache 使用比例 | cache 为什么这么快接近满？ |
| `vllm:num_requests_waiting` | 排队请求数 | 是容量不足，还是 cache 管理限制 admission？ |
| failed requests / logs | 失败请求 | 是 OOM、timeout、长度限制，还是 cache pressure？ |

```text

paged KV 为什么要多一层 block table？
这些结构如何影响 benchmark 和 observability？
```

> [!important] 第一层直觉
> KV cache 是 serving 系统把“已经算过的上下文”保存下来的方式。长上下文、共享 prefix、variable-length batch 的成本，最后都会落到 KV cache 的大小、复用和管理方式上。

## 1. 为什么 Week07 学 KV / Prefix / Paged KV / Radix

[[Week 7 - KV Cache + Prefix Cache + Paged KV]] 的阶段计划已经把问题说得很直接：

```text
长 prompt -> prefill 贵 -> TTFT 变高
长 context -> KV cache 大 -> 显存压力变高
variable-length requests -> cache 管理复杂
共享 system prompt / tools schema -> prefix cache 有收益
共享 prefix tree -> RadixAttention 组织可复用路径
decode attention -> 反复读 KV cache -> memory bandwidth 关键
```

所以 Week 7 关心的是 serving 系统里的三层问题：

| 层次 | 机制 | 回答的问题 |
|---|---|---|
| KV cache | 保存每层 attention 的 K / V | 长上下文为什么贵？decode 为什么读显存？ |
| Prefix cache | 复用相同 prefix 的 KV blocks | shared system prompt / tools schema 为什么能省 prefill？ |
| Paged KV | 用 block table 管理非连续 KV pages | variable-length requests 为什么需要更灵活的显存管理？ |

这三层会直接影响：

- TTFT：长 prompt、prefix cache miss、排队和 prefill 成本。
- TPOT / ITL：decode 阶段读取历史 KV 的节奏。
- GPU memory：KV cache footprint。
- KV cache usage：服务是否接近 cache headroom。
- failed requests：OOM、上下文过长、timeout、调度失败。
- cost：相同 GPU 小时内能服务多少有效 tokens。

## 2. KV cache 到底缓存什么

Transformer 每一层 attention 会把当前 token 的 hidden state 投影成 Q、K、V：

```text
Q: 当前 token 用来查询历史上下文
K: 历史 token 的 key
V: 历史 token 的 value
```

在自回归生成中，历史 token 的 K / V 一旦算出来，后续 decode step 会继续用它们。如果每生成一个新 token 都重新计算全部历史 token 的 K / V，成本会不可接受。所以 serving engine 会把每层的 K / V 保存下来。

![[图片/SVG/9_3_11_2.svg|955]]

### 2.1 prefill 阶段

prefill 处理完整输入 prompt：

```text
prompt tokens -> layer 0 K/V -> layer 1 K/V -> ... -> layer N K/V
```

这一阶段会：

- 计算 prompt 内所有 token 的 attention。
- 为 prompt token 写入 KV cache。
- 决定首 token 之前要等待多久。

所以长 prompt 主要推高 prefill 和 TTFT。

### 2.2 decode 阶段

decode 每次生成一个或一小批新 token：

```text
new token Q -> read old K/V cache -> compute attention -> write new K/V -> next token
```

这一阶段会：

- 持续读取历史 K / V。
- 每个新 token 追加自己的 K / V。
- 让长 output 和高并发持续占用 KV cache。

所以长 output / decode 阶段主要持续读 KV cache，影响 TPOT / ITL。

> [!warning] 不要把 KV cache 理解成“缓存模型输出”
> KV cache 缓存的是每层 attention 用到的 K / V tensor，不是最终文本，也不是 logits。它减少重复计算，但不会跳过模型本身的 decode。

## 3. KV cache memory 估算公式

入门估算可以先记这个公式：

```text
KV cache bytes
~= num_layers * batch * seq_len * num_kv_heads * head_dim * dtype_size * 2
```

最后的 `* 2` 是因为要同时存 K 和 V。

| 变量 | 含义 | 变大后影响 |
|---|---|---|
| `num_layers` | Transformer 层数 | 每层都要存 K/V，线性增长 |
| `batch` | 同时服务的请求数 | 高并发直接扩大 cache footprint |
| `seq_len` | 每个请求上下文长度 | 长 prompt + 长 output 都会增长 |
| `num_kv_heads` | KV heads 数 | MHA / GQA / MQA 会不同 |
| `head_dim` | 每个 head 的维度 | 模型越宽，单 token K/V 越大 |
| `dtype_size` | FP16/BF16/FP8 等字节数 | 低精度 KV cache 可以省显存 |

### 3.1 为什么长上下文贵

长上下文贵，不只是 prefill 计算多，还因为它会留下更大的 KV cache：

```text
4096 tokens 的请求
和 1024 tokens 的请求相比
KV cache footprint 约 4 倍
```

如果同时还有高 concurrency：

```text
seq_len 变长 * batch 变大
-> KV cache usage 接近满
-> waiting requests / queue time 上升
-> failed requests 风险上升
```

### 3.2 成本口径

Week 5 的 cost / 1M tokens 到 Week 7 要补充 cache 视角：

| 配置 | 可能收益 | 可能代价 |
|---|---|---|
| 限制 max model len | 降低 cache headroom 压力 | 不能服务超长上下文 |
| 降低 max concurrency | 降低同时占用的 KV cache | TPS / RPS 可能下降 |
| prefix cache | 减少重复 prefill | 对 random prompt 收益小 |
| paged KV | 减少碎片，提高调度灵活性 | 引入 block table / indirection |
| KV cache quantization | 降低显存占用 | 可能带来精度和 kernel 适配成本 |

## 4. prefill / decode 与 TTFT / TPOT 的关系

Week 5 已经把 prompt 和 output 分开测，Week 7 要解释为什么必须分开。

| 请求形态 | 主要压力 | 主要指标 | cache 解释 |
|---|---|---|---|
| short prompt + short output | baseline | TTFT / TPOT 都低 | KV footprint 小 |
| long prompt + short output | prefill-heavy | TTFT 高 | 一次性写大量 prompt K/V |
| short prompt + long output | decode-heavy | TPOT / E2E 高 | 持续读取和追加 K/V |
| long prompt + long output | prefill + decode | TTFT、TPOT、memory 都高 | cache 大且生命周期长 |
| high concurrency + long context | capacity pressure | waiting、failed、cost | KV cache usage 接近满 |

### 4.1 长 prompt 为什么推高 TTFT

长 prompt 在首 token 之前必须完成：

- tokenization / input processing。
- prompt attention / prefill。
- 每层 K/V 写入 cache。
- scheduler 等待和 admission。

如果 prefix cache 命中 shared prefix，重复 prefix 的 prefill 可以减少；如果 cache miss，长 prompt 的 TTFT 仍会高。

### 4.2 长 output 为什么影响 TPOT / ITL

长 output 的主要问题不是首 token，而是后续每个 token：

- 每步 decode 都要读取历史 KV。
- 历史越长，读取范围越大。
- batch 越大，同时读取的 request 越多。
- KV cache layout 越复杂，kernel 访存越依赖 block table 和 page locality。

所以 TPOT / ITL 变高时，要看 `request_decode_time_seconds`、`inter_token_latency_seconds`、generation tokens/s、KV cache usage 和 running requests。

## 5. prefix cache 为什么能降低重复 prefill 成本

vLLM 的 automatic prefix caching 会缓存已经处理过请求的 KV cache blocks。当新请求和旧请求有相同 prefix 时，新请求可以复用这些 blocks，跳过共享部分的重复 prefill。

![[图片/SVG/9_3_11_3.svg|955]]

### 5.1 它复用什么

prefix cache 复用的是：

```text
相同 prefix tokens -> 已经计算好的 KV cache blocks
```

不是复用最终回答，也不是改模型输出。

> [!important] 关键判断
> Prefix cache 不改变模型输出。它只是复用相同 prefix 的 prefill 结果，减少重复计算。

### 5.2 vLLM 的实现直觉

vLLM prefix caching 的核心做法是按 KV block 做缓存。一个 block 可以由 block 内 tokens 和它之前的 prefix 共同识别；vLLM 文档描述了 hash-based 的 approach，并在 KV cache manager 中维护 block pool、free queue、引用计数和 eviction。

对学习来说，先抓住三点：

| 机制 | 直觉 |
|---|---|
| fixed-size KV block | prefix 被切成可管理的 cache block |
| block hash | 用 token 内容和之前 prefix 判断是否能复用 |
| ref count / free queue | 多个请求可以共享 cached block，结束后再释放或保留 |

### 5.3 哪些 workload 收益最大

| Workload | 是否适合 prefix cache | 原因 |
|---|---|---|
| random prompt | 不适合 | 几乎没有相同 prefix |
| shared system prompt | 适合 | 多个请求共享系统指令 |
| shared tools schema | 很适合 | Agent 工具 schema 常重复且较长 |
| shared long document | 很适合 | RAG / 文档问答重复读取同一文档 |
| multi-turn context | 适合 | 多轮历史上下文可复用 |
| long output | 收益有限 | prefix cache 主要减少 prefill，不减少 decode 生成时间 |

### 5.4 RadixAttention / radix tree prefix matching

RadixAttention 可以先理解成 prefix cache 的组织方式升级：它用 radix tree 表示多个请求之间共享的 prefix 路径，让不同长度的 system prompt、tools schema、长文档 prefix 更容易复用已经算好的 KV blocks。

最小 mental model：

```text
request tokens
-> longest shared prefix
-> radix tree node
-> reusable KV blocks
-> unique suffix 继续 prefill
```

它解决的问题不是“让 attention 数学复杂度消失”，而是：

- 快速找到多个请求之间可复用的最长 prefix。
- 避免只按完整 prompt 粗暴判断命中。
- 让 Agent / RAG / coding assistant 的 shared prefix workload 更接近真实收益。

报告里应该把 RadixAttention 和普通 prefix cache 区分清楚：prefix cache 是“复用相同 prefix 的 KV blocks”这个能力；RadixAttention 更强调用 radix tree 管理和匹配这些 prefix。

## 6. random prompt benchmark 为什么不代表 Agent / RAG workload

random prompt 可以测基础容量，但它会掩盖 shared prefix 的收益。

真实 Agent / RAG / coding assistant 请求经常长这样：

```text
shared system prompt
+ shared tools schema
+ shared repo/document prefix
+ user-specific question
```

如果 benchmark 只用 random prompt，会得到一个错误倾向：

```text
prefix cache 看起来没用
```

但在真实业务里，相同 system prompt、tools schema、长文档 prefix 可能占输入的大头。此时 prefix cache 的收益会集中体现为：

- TTFT 降低。
- prompt tokens/s 压力下降。
- prefill time 下降。
- 同等 GPU 小时内完成更多有效请求。
- long document workload 的 cost / 1M effective tokens 下降。

### 6.1 Week 7 必测 workload

| 场景 | 目的 | 主要观察 |
|---|---|---|
| random prompt | prefix cache baseline | 命中率低时的 TTFT / tokens/s |
| shared system prompt | 模拟 chat / coding assistant | TTFT 是否下降 |
| shared tools schema | 模拟 Agent tool calling | 长 schema 下的 prefill 节省 |
| shared long document | 模拟 RAG / document QA | long prefix 的 cache 收益 |
| radix prefix | 多请求共享不同长度 prefix | radix tree node 与 KV block reuse |
| long context | 制造 KV cache pressure | cache usage、failed、queue |
| variable-length batch | 模拟真实混合请求 | fragmentation、调度、TPOT |

## 7. paged KV cache / PagedAttention 解决什么问题

如果每个请求都拿一段连续 KV cache，variable-length requests 会很麻烦：

- 有的请求很短，有的请求很长。
- 有的请求很快结束，有的请求持续 decode。
- 连续内存分配容易产生碎片。
- 调度器需要在有限 GPU memory 中塞下不同长度请求。

paged KV 的基本思路是：把每个请求的 KV cache 切成固定大小的 pages / blocks，逻辑上连续，物理上可以不连续。

```text
request logical tokens
-> block table
-> physical KV pages
```

![[图片/SVG/9_3_11_4.svg|955]]

### 7.1 它解决的是什么

| 问题 | paged KV 的作用 |
|---|---|
| 显存碎片 | 请求不需要一整段连续大内存 |
| variable-length request | 每个请求按需分配不同数量的 pages |
| 调度灵活性 | 新 token 追加时可以分配新 page |
| prefix / block 复用 | block 可以被缓存、共享、引用计数管理 |
| batch decode | kernel 通过 block table 找到每个请求的 KV pages |

### 7.2 它不解决什么

> [!warning] PagedAttention 不直接降低 attention 数学复杂度
> decode attention 仍然要看历史上下文。PagedAttention / paged KV 主要改善 KV block management、fragmentation、variable-length batch 和 attention 访存组织，不是把 attention 从数学上变成常数复杂度。

## 8. page table / block table 如何影响 kernel 访存

Paged KV 引入了一层间接寻址：

```text
logical block id -> physical page id -> K/V memory address
```

这层 indirection 带来灵活性，也带来 kernel 访存成本。

### 8.1 page size 的权衡

| Page size | 好处 | 风险 |
|---|---|---|
| 太大 | block table 更短，metadata 少 | 最后一页浪费多，短请求显存浪费 |
| 太小 | 分配粒度细，碎片少 | page table 更长，indirection / metadata 开销更多 |
| 合适 | 碎片和访问开销折中 | 需要结合 workload benchmark |

### 8.2 和 CUDA / MatMul 直觉的连接

[[3.8 CUDA Week 4 前置知识 - MatMul + Tiling + Roofline]] 里强调过数据复用和访存形状。Paged KV 不是 matmul tile，但思考方式相似：

| Week 4 MatMul | Week 7 Paged KV |
|---|---|
| A/B tile 如何复用 | K/V page 如何被 decode 读取 |
| global memory 访问是否规整 | physical pages 是否容易高效访问 |
| shared memory / register reuse | kernel 如何批量处理 KV blocks |
| roofline 看 compute / memory | decode attention 常受 KV cache 读带宽影响 |

FlashInfer / vLLM 的价值在这里：它们已经处理了大量工业 kernel layout 和调度细节，Week 7 的 toy 实验只需要帮助你理解 block table 和 memory read pressure，不需要从零复刻工业 attention。

## 9. toy contiguous KV vs toy paged KV

toy 实验的目标是理解 layout，不是追求工业性能。

![[图片/SVG/9_3_11_5.svg|955]]

### 9.1 contiguous KV baseline

连续 KV 可以先这样理解：

```text
request 0: [token 0 ... max_len]
request 1: [token 0 ... max_len]
request 2: [token 0 ... max_len]
```

优点：

- 地址计算直观。
- toy kernel 容易写。
- 固定长度 batch 下适合当 baseline。

缺点：

- variable-length requests 容易浪费预留空间。
- 请求结束后留下空洞。
- 长短请求混排时显存利用率差。

### 9.2 paged KV toy

paged KV toy 可以只做四件事：

```text
request_id
-> logical token positions
-> block table
-> physical KV pages
-> batch decode attention reads pages
```

最小数据结构：

```cpp
struct RequestKV {
    int request_id;
    int seq_len;
    std::vector<int> block_table; // logical block -> physical page
};
```

对比实验：

| 对比 | 观察 |
|---|---|
| fixed length vs variable length | contiguous 是否浪费显存 |
| page size 8 / 16 / 32 | 内部碎片和 table 长度 |
| short context vs long context | KV footprint 增长 |
| small batch vs large batch decode | TPOT / memory read pressure |
| prefix cache off / on | TTFT 和 prefill tokens/s |

## 10. FlashInfer / vLLM 作为 baseline，而不是从零硬写工业 attention

Week 7 应该读 vLLM 和 FlashInfer，但不要把目标变成“手写完整 serving engine”。

### 10.1 vLLM baseline

vLLM 提供两类关键参考：

- Automatic Prefix Caching：KV cache blocks、hash、free queue、ref count、eviction。
- Paged Attention：paged KV cache block 和 attention kernel 如何配合。

你要从 vLLM 学的是：

```text
serving engine 如何组织 KV blocks
prefix cache 如何和 KV manager 合作
block table 如何服务 batch decode
```

### 10.2 FlashInfer baseline

FlashInfer 提供 paged KV cache layout、batch decode / prefill wrapper、shared-prefix paged KV wrapper、cascade attention wrapper 等参考。

学习时重点看：

| API / 概念 | 学什么 |
|---|---|
| paged KV layout | page table / indptr / indices 如何表达 ragged requests |
| batch decode wrapper | decode attention 如何读取 paged KV |
| shared-prefix wrapper | shared prefix 和 unique suffix 如何分开处理 |
| cascade wrapper | 多级共享 prefix / KV segments 如何组合 |

> [!warning] 不要只说“调库就行”
> 面试或报告里要能说清楚库解决了什么问题、baseline 怎么设计、自己的 toy 版本验证了什么，以及为什么工业版本需要复杂的 layout / kernel / scheduler。

## 关键要点总结

1. KV cache 缓存每层 attention 的 K / V，不是缓存文本输出。
2. KV cache memory 随 `num_layers * batch * seq_len * num_kv_heads * head_dim * dtype_size * 2` 增长。
3. 长 prompt 主要推高 prefill 和 TTFT。
4. 长 output / decode 阶段主要持续读取 KV cache，影响 TPOT / ITL。
5. Prefix cache 复用相同 prefix 的 prefill KV blocks，不改变模型输出。
6. Random prompt benchmark 不能代表 shared system prompt、tools schema、long document prefix 等 Agent / RAG workload。
7. RadixAttention 用 radix tree 组织共享 prefix，让不同长度 prefix 也能找到可复用 KV blocks。
8. PagedAttention / paged KV 主要解决显存碎片、variable-length request 管理、调度灵活性和 attention 访存组织，不直接降低 attention 数学复杂度。
9. Page size 是折中：太大浪费显存，太小增加 block table / indirection 开销。
10. FlashInfer / vLLM 是 baseline 和参考，不是“跳过理解”的理由。
