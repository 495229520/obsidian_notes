## 1. Week 12 要解决什么

Week 9 到 Week 11 的主线基本是 FP32 GEMM：

```text
CUDA kernels
Triton matmul
CUTLASS example / profiler
cuBLAS SGEMM
统一 benchmark + profiling + report
```

Week 12 开始面对真实 LLM inference 更常见的问题：

```text
FP16 / BF16 input
FP16 / FP32 output
FP32 accumulation
Tensor Core path
cuBLAS HGEMM / GemmEx
Triton autotune
不同 tolerance
```

### 1.1 从 FP32 GEMM 到 mixed precision GEMM

FP32 表里通常写：

```text
dtype = FP32
```

但 mixed precision 不能这么粗糙。至少要拆成：

```text
input_dtype
output_dtype
compute_type
accumulate_type
reference_dtype
tolerance
```

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_16_2.svg|955]]

例如：

| 场景 | input | output | compute / accumulate | 说明 |
|---|---|---|---|---|
| SGEMM | FP32 | FP32 | FP32 | Week 9-11 主线 |
| HGEMM | FP16 | FP16 | 库默认 / 隐式 | 要查文档和实际设置 |
| GemmEx | FP16/BF16 | FP16/FP32 | 显式 compute type | 更适合报告写清口径 |
| Triton FP16 | FP16 | FP16/FP32 | 通常用 FP32 acc | 需要代码和结果确认 |

### 1.2 本周不手写 Tensor Core MMA kernel

Week 12 的目标不是：

```text
从 WMMA / mma.sync 手写一个高性能 Tensor Core GEMM
```

更合理的目标是：

```text
用 cuBLAS / Triton / CUTLASS 跑 mixed precision GEMM
记录 dtype / compute / tolerance
解释 Tensor Core 可能路径和证据边界
```

手写 Tensor Core MMA 可以作为后续深入专题。当前更重要的是建立实验纪律。

## 2. mixed precision 的实验口径

### 2.1 input / output / compute / accumulate

混合精度 GEMM 最容易犯的错误是只写：

```text
FP16 GEMM
```

这句话不够。你需要写成：

```text
A/B input dtype = FP16
C/D output dtype = FP16
compute type = FP32 or FP16
accumulate type = FP32 or FP16
reference = torch.matmul FP32 / cuBLAS / custom reference
tolerance = ...
```

可以把它理解成两条线：

```text
存储精度：A/B/C 在 memory 里是什么 dtype
计算精度：乘法、累加、中间结果用什么精度
```

> [!important] 第一层直觉
> mixed precision 的核心不是“更小的 dtype 更快”，而是“用更低精度存储/乘法换吞吐，同时用合适的 accumulation 和 tolerance 控制误差”。

### 2.2 SGEMM / HGEMM / GemmEx

三个名字先分清：

| 名称 | 常见含义 | 报告重点 |
|---|---|---|
| SGEMM | FP32 GEMM | FP32 baseline |
| HGEMM | half precision GEMM | 需要查清输出和计算口径 |
| GemmEx | 扩展 GEMM API | 可以显式记录 A/B/C type 和 compute type |

cuBLAS 文档里，`cublasGemmEx` 和 `cublasLtMatmul` 会使用 `cublasComputeType_t` 来选择 compute precision。不同 compute type 可能允许 Tensor Core、TF32、BF16 等快速路径，也可能使用更严格但更慢的 pedantic 模式。

### 2.3 reference 和 tolerance

FP16 / BF16 结果不能照搬 FP32 阈值。

建议记录：

```text
reference_dtype = FP32
max_abs_error
max_rel_error
rms_error
atol
rtol
pass / fail
```

对比时要说明：

- 输入分布是什么。
- K 有多大。
- 累加精度是什么。
- 输出 dtype 是什么。
- reference 是 FP32 还是同 dtype library baseline。

K 越大，累加项越多；低精度输入和输出越容易出现舍入误差。这个误差不是 bug，但必须被记录。

## 3. Tensor Core 的直觉和证据边界

### 3.1 Tensor Core 在做什么

Tensor Core 可以先理解成 NVIDIA GPU 上专门加速矩阵乘加的硬件单元。以经典 WMMA 直觉看，warp 级接口会把多个小矩阵片段组织成矩阵乘加：

```text
D = A * B + C
```

NVIDIA 的 Tensor Core 介绍里，早期 Volta 例子强调 FP16 input 和 FP32 accumulation；后续架构又扩展了 TF32、BF16 等路径。对 Week 12 来说，最重要的是：

```text
Tensor Core 路径和 dtype / compute type / shape / alignment / GPU architecture / library algorithm 都有关。
```

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_16_3.svg|955]]

### 3.2 dtype、shape、alignment、architecture

Tensor Core 不是你写了 FP16 就一定使用。

影响因素包括：

- GPU compute capability。
- CUDA / cuBLAS / Triton / CUTLASS 版本。
- input dtype，例如 FP16、BF16、TF32。
- compute type，例如 `CUBLAS_COMPUTE_32F`、`CUBLAS_COMPUTE_16F`、fast compute modes。
- shape 和 alignment。
- algorithm / kernel selection。
- profiler 里实际执行的 kernel 或指令。

所以报告里不要写：

```text
dtype 是 FP16，所以一定用了 Tensor Core。
```

更稳的写法：

```text
该配置满足常见 Tensor Core 路径的 dtype 前提；是否实际使用，需要结合 cuBLAS / CUTLASS / Triton kernel 名称或 profiler 指标确认。
```

### 3.3 什么时候能说“用了 Tensor Core”

可以分三档：

| 表述 | 什么时候使用 |
|---|---|
| 可能使用 Tensor Core | dtype / compute type / shape 满足条件，但没有 profiler 证据 |
| 很可能使用 Tensor Core | library 文档、kernel 名称、配置都指向 Tensor Core 路径 |
| 已确认使用 Tensor Core | profiler / SASS / 指令指标能支持 |

没有证据时，写“可能使用”是专业，不是保守过头。

## 4. cuBLAS HGEMM / GemmEx baseline

### 4.1 HGEMM 的口径

HGEMM 通常让你跑 half precision GEMM，但报告里不能只写：

```text
cuBLAS HGEMM: time = ...
```

应该写：

```text
implementation = cuBLAS HGEMM
input_dtype = FP16
output_dtype = FP16
compute_type = implicit / library default
reference_dtype = FP32
tolerance = ...
```

如果 API 没有显式暴露 compute type，就在表格里写清楚：

```text
compute_type = implicit
note = cublasHgemm API, details depend on library behavior and math mode
```

### 4.2 GemmEx 为什么更适合报告

`GemmEx` 的价值是显式：

```text
A type
B type
C type
compute type
algorithm
```

这对 mixed precision report 特别重要。你可以把同一个 shape 跑成几条不同口径：

```text
GemmEx FP16 input + FP32 compute
GemmEx BF16 input + FP32 compute
GemmEx FP32 input + TF32 fast mode
```

每一条都必须单独记录字段，不要混在一行里。

### 4.3 不要跨 dtype 算 ratio

ratio vs cuBLAS 只能在同一口径里算：

```text
same M/N/K
same input dtype
same output dtype
same compute type or explicitly comparable baseline
same timing scope
same correctness rule
```

不要写：

```text
FP32 CUDA tiled / FP16 cuBLAS HGEMM = ratio
```

这不是公平比较。

## 5. Triton FP16 / BF16 与 autotune 初版

### 5.1 Triton mixed precision 需要记录什么

Triton FP16 / BF16 matmul 接入 Week 10 代码时，至少记录：

```text
input_dtype
output_dtype
accumulator dtype
BLOCK_M / BLOCK_N / BLOCK_K
num_warps
num_stages
autotune key
reference dtype
tolerance
```

如果代码里 accumulator 是：

```python
acc = tl.zeros((BLOCK_M, BLOCK_N), dtype=tl.float32)
```

那报告就应该写：

```text
accumulate_type = FP32
```

不要只写 `Triton FP16`。

### 5.2 autotune 记录不是只保存最佳值

Triton `@triton.autotune` 会对一组 `triton.Config` 进行评估，key 变化时会重新评估对应配置。Week 12 的 autotune 初版至少要保留：

- configs 列表。
- autotune key，例如 `M/N/K` 或 shape bucket。
- 每个候选配置结果。
- 最佳配置。
- autotune warmup / repeat。
- 是否使用 cache。

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_16_4.svg|955]]

不要只写：

```text
autotune found best config
```

要写：

```text
在这 3 到 5 个候选配置中，这个 shape 下 best config 是 ...
```

### 5.3 FP32 表和 FP16/BF16 表分开

建议至少分两张表：

```text
Table A: FP32 GEMM comparison
Table B: mixed precision GEMM comparison
```

mixed precision 表里必须多出：

```text
input_dtype
output_dtype
compute_type
accumulate_type
tolerance
reference_dtype
```

## 6. CUTLASS mixed precision 和 report limitations

### 6.1 CUTLASS 行要补哪些字段

CUTLASS mixed precision 行建议记录：

```text
operation / kernel name
input dtype
output dtype
accumulator type
operator class
math instruction if visible
layout
tile shape if visible
verification result
profiler command
```

如果 CUTLASS profiler 输出里能看到 TensorOp、SIMT、kernel 名称、instruction shape 等信息，就放进 `config` 或 `note` 字段。

### 6.2 Tensor Core 结论怎么写才稳

稳妥模板：

```text
This run is a mixed precision GEMM with FP16 input and FP32 accumulation.
The configuration is compatible with Tensor Core execution on supported NVIDIA GPUs.
However, this report only claims Tensor Core usage when profiler/kernel evidence is available.
```

中文可以写：

```text
该配置具备 Tensor Core 路径的 dtype 前提，但是否实际走 Tensor Core，以 profiler / kernel 名称 / 指令证据为准。
```

### 6.3 给 Week 13/14 留接口

Week 13 会继续深入 CUDA GEMM warp tiling / pipeline，Week 14 会进入 cuBLASLt / advanced baseline。Week 12 的表格最好预留：

```text
math_mode
algo_id
operator_class
tile_shape
alignment
workspace
epilogue
```

这样后面接 cuBLASLt 或更细 CUTLASS profiler 时，不需要重做 schema。

## 7. Week12 实验检查表

### 7.1 必测 shape

| M | N | K | 用途 |
|---:|---:|---:|---|
| 512 | 512 | 512 | mixed precision sanity |
| 1024 | 1024 | 1024 | 常规 HGEMM |
| 1024 | 4096 | 4096 | LLM-like projection |
| 4096 | 4096 | 4096 | 大规模吞吐 |
| 128 | 256 | 768 | 小型非方阵 |

### 7.2 correctness 最低要求

- [ ] FP16 / BF16 reference 口径明确。
- [ ] 记录 max abs error / max rel error / RMS error。
- [ ] 记录 `atol` / `rtol`。
- [ ] tolerance 不照搬 FP32。
- [ ] 表格记录 `reference_dtype`。
- [ ] 对每个 dtype 组合单独判断 pass / fail。

### 7.3 benchmark 最低要求

- [ ] 至少跑通 cuBLAS HGEMM 或 GemmEx。
- [ ] 至少 3 个 shape 有 mixed precision benchmark。
- [ ] Triton FP16 / BF16 matmul 接入统一 benchmark。
- [ ] Triton autotune 至少有 3 组候选配置记录。
- [ ] 表格包含 input dtype、output dtype、compute type、accumulate type。
- [ ] ratio vs cuBLAS 不跨 dtype 乱算。
- [ ] Tensor Core 结论有证据边界。

### 7.4 report 必须回答

- SGEMM、HGEMM、GemmEx 的实验口径有什么不同？
- FP16 input + FP32 accumulation 和 FP16 accumulate 有什么区别？
- FP16 / BF16 correctness tolerance 怎么设？
- Tensor Core 为什么和 dtype、shape、alignment、architecture 有关？
- 这次运行是“可能使用 Tensor Core”还是“已确认使用 Tensor Core”？
- Triton autotune 调了哪些参数？
- FP32 表和 FP16/BF16 表是否分开？
- limitations 明确写了哪些不能证明的内容？

## 关键要点总结

- Week 12 的重点是 mixed precision 实验纪律，不是手写 Tensor Core MMA kernel。
- `dtype = FP16` 不够，必须拆成 input、output、compute、accumulate、reference、tolerance。
- FP16 / BF16 correctness 阈值不能照搬 FP32，要记录误差统计和输入分布。
- cuBLAS HGEMM 可以作为 half baseline，但 GemmEx 更适合报告显式记录类型口径。
- Tensor Core 是否实际使用，不能只靠 dtype 断言；要看 compute type、shape、alignment、architecture、kernel / profiler 证据。
- Triton autotune 初版要保留候选配置和结果，不只保存最佳值。
- FP32 comparison 和 mixed precision comparison 要分表，ratio vs cuBLAS 不能跨 dtype 乱算。
