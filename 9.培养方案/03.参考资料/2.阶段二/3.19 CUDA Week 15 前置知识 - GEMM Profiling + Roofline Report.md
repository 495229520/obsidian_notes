## 1. Week 15 要解决什么

前几周的问题是：

```text
能不能写出来？
能不能跑通？
能不能接入 benchmark？
能不能和 baseline 比？
```

Week 15 的问题变成：

```text
这些结果说明了什么？
为什么某个实现快？
为什么某个实现慢？
这个解释有没有 profiler 指标支撑？
哪些结论不能从当前实验推出？
```

![[图片/SVG/9_3_19_2.svg|955]]

### 1.1 从 benchmark 数字到工程结论

一个弱报告会这样写：

```text
CUDA v2 比 CUDA v1 快，cuBLAS 最快。
```

一个更稳的报告会这样写：

```text
在 1024x1024x1024 FP32 上，CUDA v2 相比 CUDA v1 提升了 X%，同时 register count 从 A 增加到 B，achieved occupancy 从 C 变为 D；Nsight 显示 global load efficiency / stall reason 有对应变化。cuBLAS 仍显著领先，因为它使用更成熟的调度、kernel selection 和架构特化路径。
```

这不是文字变长，而是证据变完整。

### 1.2 本周不做什么

Week 15 很容易滑成“再多跑几个 shape”。不要这样。

本周不要求：

- 不要求无限扩充 benchmark matrix。
- 不要求覆盖所有 GPU / CUDA 版本。
- 不要求做严格论文级 roofline model。
- 不要求每个实现都 Nsight 全量 profile。
- 不要求把 FP32、FP16、BF16 混在同一张 ratio 表里。

本周真正要拿到的是：

```text
一份能解释、能复现、能写进作品集的 GEMM profiling report。
```

## 2. 三条证据链：correctness / benchmark / profiling

GEMM report 最重要的不是图多，而是证据链不断。

```text
correctness -> benchmark -> profiling -> finding -> limitation
```

### 2.1 correctness 是入口

任何性能结论之前，先问：

| 问题 | 为什么 |
|---|---|
| reference 是谁？ | CPU reference、cuBLAS、double precision reference 口径不同 |
| tolerance 是多少？ | FP32、FP16、BF16 不能共用同一 tolerance |
| max abs / RMS 是否记录？ | 只有 pass/fail 不够排查 |
| 非整除 shape 是否测过？ | fast path 容易隐藏边界 bug |
| epilogue 是否包含在 reference 中？ | bias / activation 不能漏算 |

### 2.2 benchmark 说明发生了什么

benchmark 至少说明：

```text
same shape
same dtype
same timing scope
same warmup/repeat
same baseline
```

建议保留字段：

```csv
impl,shape,dtype,layout,time_ms,tflops,ratio_vs_cublas,ratio_vs_cublaslt,correctness,max_abs_error,rms_error,notes
```

benchmark 的作用是回答：

```text
谁更快？快多少？在哪个 shape / dtype 下？
```

### 2.3 profiling 解释为什么可能发生

profiling 的作用不是替代 benchmark，而是解释 benchmark。

| profiler 指标 | 回答什么 |
|---|---|
| achieved occupancy | 并发 warp 是否足够？是否被 register/shared memory 限制？ |
| register count | thread tile / unroll 是否带来 register pressure？ |
| shared memory usage | 每个 SM 可驻留 block 是否受限？ |
| memory throughput | 是否接近 memory bandwidth ceiling？ |
| global load efficiency | 访存是否规整、coalesced？ |
| shared bank conflict | shared layout / padding 是否有效？ |
| SM utilization / throughput | compute pipe 是否忙？ |
| stall reason | warp 为什么没有发射指令？ |

> [!warning] profiler 只能支持解释，不能自动给结论
> Nsight Compute 给的是指标。报告里要写出“这个指标回答什么问题”和“它不能证明什么”。

## 3. GEMM FLOPs、数据量和 arithmetic intensity

### 3.1 TFLOPS 怎么算

GEMM 的主要计算量通常估算为：

```text
FLOPs = 2 * M * N * K
```

因为每个 C 元素是 K 次乘加，乘法和加法各算一次浮点操作。

TFLOPS：

```text
TFLOPS = (2 * M * N * K) / time_seconds / 1e12
```

例如：

```cpp
double flops = 2.0 * M * N * K;
double tflops = flops / (time_ms / 1000.0) / 1e12;
```

> [!note] epilogue 是否计入 FLOPs 要写清
> 普通 GEMM report 通常先用 `2*M*N*K`。如果 bias / activation epilogue 也纳入分析，要单独说明，不要悄悄改变口径。

### 3.2 arithmetic intensity 怎么估

arithmetic intensity 简单说是：

```text
arithmetic intensity = FLOPs / bytes moved
```

对于理想 GEMM，粗略数据量可以估：

```text
bytes ~= sizeof(dtype) * (M*K + K*N + M*N)
```

对应：

```text
AI ~= (2*M*N*K) / bytes
```

但这只是理想下界。真实 kernel 会有：

- global memory 重复读取。
- shared memory 读写。
- cache hit / miss。
- epilogue 读写。
- padding 和边界处理。
- workspace 或中间结果。

所以报告里可以写：

```text
We use arithmetic intensity as roofline thinking, not as an exact traffic proof. Actual memory traffic is checked with profiler metrics when available.
```

### 3.3 roofline thinking 的边界

roofline 的直觉是：

```text
performance <= min(peak_compute, arithmetic_intensity * peak_memory_bandwidth)
```

![[图片/SVG/9_3_19_3.svg|955]]

它帮助你判断：

| 位置 | 可能解释 |
|---|---|
| 靠近 memory roof | 更像 memory-bound |
| 靠近 compute roof | 更像 compute-bound |
| 离两条 roof 都很远 | 可能是调度、occupancy、指令、bank conflict、实现开销 |
| 不同 dtype roof 不同 | FP32、TF32、FP16/BF16 不能混画不解释 |

Week 15 不要求画严格 roofline 模型，但必须有 roofline thinking：

```text
这个 shape 的 GEMM 理论 AI 很高，但手写 CUDA v1 仍慢，说明瓶颈不只是 DRAM bytes，而可能是数据复用层级、指令调度、occupancy 或 shared/register 资源管理。
```

## 4. Nsight Compute 指标怎么读

Nsight Compute 的报告很容易让人陷入截图和指标名。Week 15 建议按三层读：

```text
Speed of Light / high-level throughput
  -> Occupancy / resource
  -> Memory / warp stall / source correlation
```

### 4.1 先看 high-level，再看细节

最小 Nsight 命令可以记录成：

```bash
ncu --set full \
    --kernel-name regex:gemm \
    --launch-skip 5 \
    --launch-count 1 \
    --force-overwrite \
    --export results/cuda_v2_1024_fp32 \
    ./gemm_bench --impl cuda_v2 --m 1024 --n 1024 --k 1024 --dtype fp32
```

如果只想先采关键指标，可以用 metrics 白名单：

```bash
ncu --metrics \
sm__throughput.avg.pct_of_peak_sustained_elapsed,\
dram__throughput.avg.pct_of_peak_sustained_elapsed,\
sm__warps_active.avg.pct_of_peak_sustained_active,\
smsp__warp_issue_stalled_long_scoreboard_per_warp_active.pct \
./gemm_bench --impl cuda_v2 --m 1024 --n 1024 --k 1024
```

命令本身要进 `profiling.md`，否则 report 不可复现。

### 4.2 occupancy 高不等于快

occupancy 只是“有多少 warp 活跃”的一部分视角。高 occupancy 可能帮助隐藏 latency，但不等于 compute pipe 被充分利用。

典型误区：

```text
achieved occupancy = 90%，所以 kernel 很好。
```

更稳的判断：

```text
achieved occupancy 较高，但 SM throughput 仍低，同时 stall reason 显示 long scoreboard 占比高，说明活跃 warp 多不代表访存依赖被完全隐藏。
```

### 4.3 throughput 高也不等于实现好

memory throughput 高可能表示充分利用带宽，也可能表示重复读写太多。

| 现象 | 可能解释 |
|---|---|
| DRAM throughput 高，TFLOPS 低 | 可能重复 global load，算术复用不足 |
| SM throughput 高，TFLOPS 高 | 更接近 compute-bound，但还要看 dtype roof |
| shared bank conflict 高 | shared memory layout 可能拖慢 |
| register count 高，occupancy 低 | thread tile 可能过大 |
| tensor core 指标高 | mixed precision 可能走了 TC path，但仍要写证据边界 |

## 5. 横向对比：CUDA / Triton / CUTLASS / cuBLAS / cuBLASLt

横向对比不是把所有数字丢进一张大表，而是分维度看。

### 5.1 实现维度

| 实现 | 报告里应该说明 |
|---|---|
| CUDA v1 | 教学 baseline，说明 naive/tiled 的瓶颈 |
| CUDA v2 | 说明 warp/thread tile、register pressure、pipeline 是否有效 |
| Triton | 说明 DSL/autotune 配置和 kernel 表现 |
| CUTLASS | 工业 template baseline，说明 config / profiler 口径 |
| cuBLAS | simple vendor baseline |
| cuBLASLt | advanced vendor baseline，记录 heuristic/workspace/epilogue |

### 5.2 dtype 维度

FP32、FP16、BF16 需要分开解释：

```text
FP32 table:
  CUDA v1/v2, Triton FP32, CUTLASS FP32, cuBLAS SGEMM, cuBLASLt FP32

FP16/BF16 table:
  Triton mixed precision, CUTLASS TC path, cuBLAS HGEMM/GemmEx, cuBLASLt mixed precision
```

不要写：

```text
FP16 比 FP32 快，所以实现优化成功。
```

应该写：

```text
FP16/BF16 使用了不同 dtype 和可能不同硬件路径，必须在 mixed precision 小节单独解释。
```

### 5.3 shape 维度

核心 shape 建议冻结：

| Shape | 用途 | 报告角度 |
|---|---|---|
| `512x512x512` | 小规模 sanity | launch overhead / 小问题规模 |
| `1024x1024x1024` | 常规对比 | 主线性能比较 |
| `1024x4096x4096` | LLM-like projection | 非方阵、大 K/N |
| `4096x4096x4096` | 大 GEMM | 吞吐和库优化优势 |
| `127x129x131` | correctness / boundary | fast path 边界可靠性 |

## 6. report 结构和写法

建议 `gemm_profiling_report.md` 结构：

```text
Experiment setup
Benchmark matrix
Correctness method
Raw data links
Profiler commands
Summary tables
Roofline thinking
Findings
Limitations
Next steps
```

![[图片/SVG/9_3_19_5.svg|955]]

### 6.1 finding 必须能回到证据

每个 finding 最好按这个模板写：

```text
Finding:
  CUDA v2 improves over CUDA v1 on shape X.

Evidence:
  benchmark_results.csv row A/B shows TFLOPS X -> Y.
  ncu report path shows register count A -> B and achieved occupancy C -> D.

Interpretation:
  The improvement is consistent with better data reuse, but still below cuBLAS because ...

Limitation:
  Only verified on shapes X/Y/Z and FP32. Mixed precision is discussed separately.
```

### 6.2 limitations 是报告可信度的一部分

好的 limitations 不是自我否定，而是告诉读者你知道边界。

应该写：

- 没有覆盖所有 GPU 架构。
- 没有证明 heuristic 是全局最优。
- 没有对所有 Triton autotune config 做 exhaustive search。
- roofline 使用估算 traffic，不等于严格 memory trace。
- FP16/BF16 和 FP32 不直接比较 ratio。
- Nsight profile 只采样代表 shape，不能外推所有 shape。

不要写：

```text
本项目完全证明了 cuBLAS 为什么最快。
```

更稳：

```text
The report explains observed gaps under the tested shapes and environment. It does not prove global optimality across GPUs, CUDA versions, layouts, or all GEMM shapes.
```

## 7. Week15 实验检查表

### 7.1 冻结 benchmark matrix

`benchmark_matrix.md` 至少包含：

| 字段 | 示例 |
|---|---|
| shape | `1024x1024x1024` |
| impl | `cuda_v1`, `cuda_v2`, `triton`, `cutlass`, `cublas`, `cublaslt` |
| dtype | `fp32`, `fp16`, `bf16` |
| layout | `row-major` / descriptor |
| correctness | `pass/fail`, tolerance |
| benchmark source | CSV / JSON path |
| profiling source | Nsight report path |

### 7.2 Nsight profiling 最低要求

最低要求：

- CUDA tiled v1 有 Nsight 记录。
- CUDA v2 有 Nsight 记录。
- 代表 Triton kernel 可选采样。
- CUTLASS 可选使用 profiler 输出或 Nsight 采样。
- 记录 GPU、driver、CUDA、cuBLAS/cuBLASLt、Triton、CUTLASS 版本。

`profiling.md` 里每条命令都要带：

```text
impl
shape
dtype
command
output path
date
tool version
notes
```

### 7.3 summary table 字段

建议 summary table 分三类。

correctness：

```csv
impl,shape,dtype,max_abs_error,rms_error,tolerance,status,reference
```

performance：

```csv
impl,shape,dtype,time_ms,tflops,ratio_vs_cublas,ratio_vs_cublaslt,source_csv
```

profiling：

```csv
impl,shape,dtype,registers,shared_mem_bytes,achieved_occupancy,sm_throughput,dram_throughput,global_load_efficiency,shared_bank_conflict,top_stall,source_ncu
```

### 7.4 gemm_profiling_report.md 必须回答

最终 report 至少回答：

- 最终 benchmark matrix 是什么？
- correctness 怎么做，tolerance 怎么定？
- FP32 和 mixed precision 是否分开解释？
- TFLOPS 怎么算？
- arithmetic intensity 怎么估？
- Nsight 采了哪些实现、哪些 shape？
- 至少三个 finding 是什么？
- 每个 finding 的证据在哪里？
- 哪些结论不能从当前实验推出？
- 第三个人如何复跑核心实验？

## 关键要点总结

- Week 15 的核心不是继续加 kernel，而是把 Week 9-14 的结果整理成可解释、可复现的工程报告。
- correctness、benchmark、profiling 是三条证据链；任何 finding 都要能回到原始数据。
- TFLOPS 用 `2*M*N*K/time`，arithmetic intensity 用 `FLOPs/bytes` 做 roofline thinking，但要说明估算边界。
- occupancy、throughput、stall reason 都只是解释工具；不能把 profiler 截图直接当结论。
- FP32、FP16、BF16 必须分组解释，不跨 dtype 乱算 ratio。
- limitations 写得清楚，报告反而更可信。
