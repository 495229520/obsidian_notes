## 1. Serving benchmark 在测什么

LLM serving 的一次请求大致经历：

```text
client send request
-> server queue / scheduler
-> prefill prompt
-> decode output tokens
-> stream or return final response
```

单个 CUDA kernel benchmark 主要关心一个算子执行时间；serving benchmark 关心的是请求在整个系统里的生命周期。

![[图片/SVG/9_3_9_2.svg|955]]

### 1.1 TTFT：Time To First Token

TTFT 是用户提交请求后，等到第一个输出 token 的时间。

它通常包含：

- 请求进入服务端。
- 排队等待调度。
- prompt tokenization / prefill。
- 生成第一个 token。
- 返回第一个可见 token。

长 prompt、排队、prefix cache miss、GPU 忙、调度策略都会推高 TTFT。

> [!tip] 可以这样记
> TTFT 更接近“用户什么时候看到模型开始说话”。对聊天、Agent、coding assistant 来说，它直接影响体感响应速度。

### 1.2 TPOT / ITL：连续 token 的节奏

ITL 是 Inter-token Latency，也常被叫作 TPOT，也就是连续输出 token 之间的平均间隔。

对 streaming 响应来说，它影响的是：

```text
模型开始输出之后，后续文字流出来是否顺滑
```

NVIDIA NIM benchmarking 文档把 ITL 定义为 decode 阶段的指标，典型形式是：

```text
ITL = (E2E latency - TTFT) / (Total output tokens - 1)
```

这里不把首 token 放进 ITL，是为了让 ITL 更专注于 decode 阶段。

### 1.3 E2E latency：完整请求时间

E2E latency 是从请求发出到最后一个 token 返回的总时间：

```text
E2E latency = TTFT + generation_time
```

如果输出很短，TTFT 在 E2E 里占比很大；如果输出很长，decode 阶段会主导总时间。

### 1.4 TPS / RPS：吞吐不是一个数

Serving benchmark 里常见两类吞吐：

| 指标 | 含义 | 适合回答 |
|---|---|---|
| TPS | tokens per second，通常看 output token throughput | 系统整体生成 token 的能力 |
| RPS | requests per second | 系统每秒完成或接收多少请求 |

TPS 高不代表用户体验一定好。高并发下，系统可能通过 batching 提升总 TPS，但单个请求的 TTFT、TPOT、p95 latency 同时变差。

> [!warning] 不要只报告平均 TPS
> 只写平均 TPS，会掩盖 tail latency、failed requests、请求排队和单请求体验恶化。Week 5 报告至少要同时写 TTFT / TPOT 的 p50 / p95 / p99，以及 failed requests。

## 2. request rate 和 max concurrency

Week 5 特别容易混淆两个参数：

```text
request rate: 请求到达系统的速度
max concurrency: 同时允许执行的请求数量上限
```

vLLM `bench serve` 文档里也强调：`--request-rate` 控制请求发起速率，`--max-concurrency` 控制实际允许并发执行的请求数；两者同时使用时，如果服务端处理不过来，实际 request rate 可能低于指定值。

![[图片/SVG/9_3_9_3.svg|955]]

### 2.1 request rate：到达率

`request_rate = 4` 可以理解成：

```text
客户端平均每秒向服务端发起 4 个请求
```

它模拟的是外部流量压力。真实线上流量通常不是均匀的，所以 benchmark 还会有 burstiness 或到达分布。

### 2.2 max concurrency：并发上限

`max_concurrency = 32` 可以理解成：

```text
客户端最多允许 32 个请求同时处于执行或等待响应状态
```

它模拟的是客户端、网关或上层系统对并发的限制。并发上限太低，系统可能吃不满；并发上限太高，排队和 tail latency 可能恶化。

### 2.3 三种典型现象

| 现象 | 可能解释 |
|---|---|
| request rate 增大，TPS 上升，p95 也上升 | batching 更充分，但请求排队变长 |
| max concurrency 增大，TPS 上升，TPOT 变差 | 同时 decode 的请求更多，单请求节奏变慢 |
| failed requests 增加 | 队列爆掉、超时、OOM、上下文过长或服务端错误 |

> [!important] 第二层直觉
> request rate 是“外面来得有多快”，max concurrency 是“里面最多同时扛多少”。Serving benchmark 的很多拐点，都来自这两个量和服务端调度能力之间的矛盾。

## 3. prefill / decode：为什么 prompt 和 output 要分开测

LLM 推理可以粗略分成两个阶段：

```text
prefill: 处理输入 prompt，建立 KV cache
decode: 逐 token 生成输出，持续读取和更新 KV cache
```

这两个阶段对指标的影响不同。

### 3.1 长 prompt：主要影响 TTFT

长 prompt 进入服务端后，需要先做 prefill。prompt 越长：

- tokenization 和输入处理更多。
- attention prefill 计算更多。
- KV cache 初始化更多。
- 第一个 token 之前要等更久。

所以长 prompt + 短 output 的场景，常见现象是：

```text
TTFT 高
输出很快结束
E2E latency 主要由 prefill 决定
```

### 3.2 长 output：主要影响 TPOT / E2E

长 output 需要更多 decode step。每生成一个 token，都要基于已有上下文继续推理，并更新 KV cache。

所以短 prompt + 长 output 的场景，常见现象是：

```text
TTFT 可能不高
TPOT / ITL 和 decode 稳定性更重要
E2E latency 随输出长度增长
```

### 3.3 四类 shape 必测

| 场景 | prompt | output | 主要观察 |
|---|---:|---:|---|
| 短问短答 | short | short | 低延迟 baseline |
| 长上下文问答 | long | short | TTFT、KV cache、GPU memory |
| 内容生成 | short | long | TPOT / ITL、decode 稳定性 |
| 长文生成 | long | long | TTFT、TPOT、E2E、失败率 |

## 4. 为什么真实 workload 不是固定 prompt

固定 prompt / fixed output 很适合做 sanity check，但它不能代表真实 Agent / RAG / coding assistant 负载。

真实请求至少有这些变化：

- prompt length distribution：有短问题，也有长上下文。
- output length distribution：有一句话回答，也有长代码 / 长总结。
- shared prefix ratio：多个请求可能共享 system prompt、tools schema、RAG 文档前缀。
- long context ratio：一部分请求会带很长上下文。
- burstiness：流量可能突然爆发。

![[图片/SVG/9_3_9_4.svg|955]]

### 4.1 shared prefix 为什么重要

Agent / RAG / coding assistant 常常有这样的输入结构：

```text
shared system prompt
+ shared tools schema
+ shared repo / document prefix
+ user-specific question
```

如果 serving engine 支持 prefix caching，相同前缀可以减少重复 prefill。这个优化主要影响：

- TTFT。
- prefill 计算量。
- GPU memory / KV cache 使用方式。
- 成本，尤其是多轮或多请求复用同一上下文时。

### 4.2 random prompt benchmark 的局限

随机 prompt 可以测基础吞吐，但它可能低估或高估真实场景：

| workload | 优点 | 局限 |
|---|---|---|
| fixed prompt | 可控、容易复现 | 太不像真实请求 |
| random prompt | 能扫长度和吞吐 | 很难模拟 shared prefix |
| shared prefix | 接近 Agent / RAG | 需要认真构造数据，避免自欺欺人 |
| long context mix | 暴露 KV cache 压力 | 成本更高，失败率更值得记录 |

## 5. benchmark_config.yaml 应该锁住什么

可信 benchmark 的第一步不是跑命令，而是写配置。

```yaml
model:
  name: Qwen2.5-1.5B-Instruct
  dtype: bfloat16
  max_model_len: 4096

engine:
  name: vllm
  version: TBD
  gpu_memory_utilization: 0.90
  prefix_caching: false
  chunked_prefill: TBD

environment:
  gpu: TBD
  gpu_count: 1
  cuda: TBD
  driver: TBD
  pytorch: TBD
  triton: TBD

workload:
  total_requests: 512
  request_rate: 4
  max_concurrency: 32
  burstiness: 1.0
  prompt_length_distribution: fixed_512
  output_length_distribution: fixed_128
  shared_prefix_ratio: 0.0
  streaming: false

measurement:
  warmup_runs: 1
  repeats: 3
  raw_result: benchmark_results.csv
```

### 5.1 不能只保存聚合表格

最低要保留：

- 原始 CSV / JSON。
- benchmark 命令。
- server 启动命令。
- 模型、engine 版本和 commit。
- GPU、CUDA、driver。
- workload 配置。
- 异常请求和错误信息。

> [!warning] Agent 不能改 benchmark 数据
> Agent 可以生成脚本、表格、图和报告初稿，但不能替你修改原始 benchmark 结果。原始 CSV / JSON 应该作为证据保存，结论只能从它们派生。

### 5.2 结果表格模板

| Scenario | Req/s | Max Conc | Prompt | Output | TTFT p95 | TPOT p95 | TPS | RPS | Failed | Note |
|---|---:|---:|---|---|---:|---:|---:|---:|---:|---|
| low latency | 1 | 4 | 128 | 64 | TBD | TBD | TBD | TBD | 0 | baseline |
| high throughput | 16 | 64 | 512 | 128 | TBD | TBD | TBD | TBD | TBD | latency tradeoff |
| long context | 2 | 16 | 4096 | 128 | TBD | TBD | TBD | TBD | TBD | prefill-heavy |
| shared prefix | 4 | 32 | shared_2k | 128 | TBD | TBD | TBD | TBD | TBD | prefix cache |

## 6. 成本：cost / 1M tokens 怎么看

性能最终要和成本连起来。一个简单的入门口径：

```text
cost_per_hour = GPU hourly price
output_tokens_per_hour = output_TPS * 3600
cost_per_1M_output_tokens = cost_per_hour / output_tokens_per_hour * 1e6
```

如果要看 total tokens：

```text
total_TPS = input_TPS + output_TPS
cost_per_1M_total_tokens = cost_per_hour / (total_TPS * 3600) * 1e6
```

注意：

- output token 通常更接近 decode 吞吐。
- input token 多时，prefill 成本不能忽略。
- prefix cache 可能让“输入 token 账面很多，但实际重复 prefill 较少”。
- failed requests 不能从成本里消失，它们同样消耗了资源。

> [!important] 第三层直觉
> 低延迟、高吞吐、低成本通常不能同时无限优化。Week 5 的目标不是找到一个“永远最好”的配置，而是说清楚在当前 workload 下，你选择了哪种 tradeoff。

## 7. Week 5 实验检查表

### 7.1 必测 workload

- [ ] 低延迟：低 request rate、低 max concurrency、短 prompt、短 output。
- [ ] 高吞吐：高 request rate、高 max concurrency、中等 prompt / output。
- [ ] 长上下文：长 prompt、短 output 或长 prompt、长 output。
- [ ] 共享 prefix：system prompt / tools schema / 文档 prefix 复用。

### 7.2 必记录指标

- [ ] TTFT p50 / p95 / p99。
- [ ] TPOT / ITL p50 / p95 / p99。
- [ ] E2E latency p50 / p95 / p99。
- [ ] output TPS、RPS、goodput。
- [ ] total requests、failed requests、error message。
- [ ] GPU memory、KV cache usage、GPU utilization。
- [ ] cost / 1M output tokens、cost / 1M total tokens。

### 7.3 报告必须回答

- TTFT 和 TPOT / ITL 分别代表什么？
- request rate 和 max concurrency 为什么不是一回事？
- 为什么不能只看平均 TPS？
- 长 prompt 为什么推高 TTFT？
- 长 output 为什么更关注 decode / TPOT？
- shared prefix 为什么接近 Agent / RAG / coding assistant？
- TPS 上升但 p95 latency 变差时，你怎么解释？
- failed requests 来自超时、OOM、上下文长度还是服务端错误？
- 这个 benchmark 是否公平、可复现、可解释？

## 8. 最小复现链路

Week 5 的产物应该能串成一条证据链：

```text
benchmark_config.yaml
-> reproduce.sh
-> raw JSON / CSV
-> analysis notebook or script
-> benchmark_report.md
```

这条链路要保证：

- 新环境可以知道你怎么启动 server。
- 新环境可以知道你怎么发请求。
- 每个聚合指标都能回到原始数据。
- 每个结论都能回到某个场景和某组参数。
- 异常值和失败请求没有被静默删除。

### 8.1 reproduce.sh 骨架

```bash
#!/usr/bin/env bash
set -euo pipefail

MODEL="Qwen2.5-1.5B-Instruct"
PORT=8000

python -m vllm.entrypoints.openai.api_server \
  --model "${MODEL}" \
  --dtype bfloat16 \
  --max-model-len 4096 \
  --port "${PORT}" \
  > server.log 2>&1 &

SERVER_PID=$!

echo "Waiting for server..."
sleep 30

vllm bench serve \
  --backend openai-chat \
  --base-url "http://127.0.0.1:${PORT}" \
  --model "${MODEL}" \
  --num-prompts 512 \
  --request-rate 4 \
  --max-concurrency 32 \
  --save-result \
  --result-filename benchmark_results.json

kill "${SERVER_PID}"
```

这只是骨架。实际项目里要加 health check、日志目录、错误清理和多场景循环。

## 9. 关键要点总结

1. Serving benchmark 测的是端到端系统，不是单个 kernel。
2. TTFT 看首 token 等待，TPOT / ITL 看连续 token 节奏，E2E latency 看完整请求。
3. TPS / RPS 是系统吞吐，但不能替代 p95 / p99 latency。
4. request rate 是请求到达率，max concurrency 是并发上限，两者会共同影响排队和 tail latency。
5. 长 prompt 偏 prefill-heavy，长 output 偏 decode-heavy。
6. shared prefix 是 Agent / RAG / coding assistant 的关键 workload，不应该只测 random prompt。
7. 可信 benchmark 必须保留配置、命令、环境、原始结果和失败请求。
8. Agent 可以帮你生成脚本和报告，但不能替你改数据或下未经证据支持的结论。
