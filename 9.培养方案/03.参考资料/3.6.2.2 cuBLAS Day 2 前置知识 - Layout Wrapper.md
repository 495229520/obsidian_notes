## 1. Day 2 要解决什么

目标可以压成一句话：

```text
项目里继续按 row-major 写 A/B/C，但调用 cuBLAS 时得到同一个 C = A @ B。
```

你希望项目语义保持：

```text
C[M, N] = A[M, K] @ B[K, N]
```

但 cuBLAS 默认按 column-major 解释矩阵。Day 2 的重点，就是把这个差异写成一个清楚的 wrapper，而不是每次调用 `cublasSgemm` 都重新猜参数。

---

## 2. row-major 和 column-major

C/C++ row-major 下标：

```cpp
A[row, col] -> A[row * width + col]
```

cuBLAS column-major 下标：

```cpp
A[row, col] -> A[col * leading_dim + row]
```

对 row-major 的 `A[M,K]` 来说，内存中连续的是同一行的 K 个元素：

```cpp
A[row * K + k]
```

对 row-major 的 `B[K,N]` 来说，内存中连续的是同一行的 N 个元素：

```cpp
B[k * N + col]
```

> [!important] 第一层直觉
> cuBLAS 没有改变你的内存，只是用 column-major 眼光解释同一段内存。wrapper 的核心就是利用转置等价关系，让解释方式和数学语义重新对齐。

### 2.1 内存视角 sanity check

先看一个 row-major 小矩阵：

```text
A =
[ 1  2  3
  4  5  6 ]
```

C/C++ row-major 的一维内存是：

```cpp
std::vector<float> A = {
    1, 2, 3,
    4, 5, 6
};
```

如果 cuBLAS 把同一段内存当成 column-major，并且你告诉它这是 `3 x 2` 矩阵，它看到的是：

```text
cuBLAS view =
[ 1  4
  2  5
  3  6 ]
```

这正好是原始 row-major `A[2,3]` 的转置。这个 sanity check 用来建立一个关键直觉：

```text
row-major A[M,K] 的同一段内存，在 cuBLAS column-major 视角下像 A^T[K,M]。
```

> [!tip] Day 2 的检查方式
> 先用小矩阵手算“同一段内存被看成转置”，再看 wrapper 里的 A/B 交换。这样比直接背 `N, M, K` 更稳。

## 3. wrapper 的转置等价

项目想算：

```text
C = A @ B
```

如果 A、B、C 都按 row-major 存储，cuBLAS 从 column-major 视角看到的是它们的转置。因此可以利用：

```text
C^T = B^T @ A^T
```

所以调用 cuBLAS 时交换 A 和 B，并把维度从 `M, N, K` 调整成 `N, M, K`：

```cpp
// row-major A[M,K], B[K,N], C[M,N]
// cuBLAS column-major view:
// C^T[N,M] = B^T[N,K] @ A^T[K,M]

cublasSgemm(
    handle,
    CUBLAS_OP_N, CUBLAS_OP_N,
    N, M, K,
    &alpha,
    B, N,
    A, K,
    &beta,
    C, N
);
```

这里最关键的是三件事：

- cuBLAS 的第一个矩阵参数传 `B`。
- cuBLAS 的第二个矩阵参数传 `A`。
- `m / n / k` 传 `N / M / K`。

---

## 4. 参数模板

建议把 row-major SGEMM 包成一个函数，不要在 benchmark 里散落裸调用：

```cpp
void sgemm_row_major(
    cublasHandle_t handle,
    int M,
    int N,
    int K,
    const float* A,
    const float* B,
    float* C) {
    const float alpha = 1.0f;
    const float beta = 0.0f;

    cublasSgemm(
        handle,
        CUBLAS_OP_N, CUBLAS_OP_N,
        N, M, K,
        &alpha,
        B, N,
        A, K,
        &beta,
        C, N
    );
}
```

这个 wrapper 的命名要直接表达语义：

```text
sgemm_row_major(A[M,K], B[K,N]) -> C[M,N]
```

这样 README 里解释参数时，就可以说：

```text
cuBLAS assumes column-major matrices.
Our project stores matrices in row-major layout, so the wrapper calls cuBLAS with swapped A/B.
```

### 4.1 wrapper 调用数据流

row-major wrapper 不要求你改变 host 侧数据准备方式。项目里仍然按 C/C++ 语义准备：

```text
A[row * K + k]
B[k * N + col]
C[row * N + col]
```

调用 cuBLAS 时只在 wrapper 内部处理差异：

```text
host 按 row-major 初始化 A/B/C
cudaMemcpy 原样拷到 device
wrapper 接收 M/N/K 和 d_A/d_B/d_C
wrapper 调用 cublasSgemm 时交换 A/B
wrapper 把 m/n/k 传成 N/M/K
D2H 后仍按 row-major C[M,N] 对拍
```

也就是说，wrapper 的对外语义应该始终保持：

```text
sgemm_row_major(A[M,K], B[K,N]) -> C[M,N]
```

不要让调用方也跟着记 cuBLAS 的 column-major 参数。调用方只负责 row-major 语义，cuBLAS 细节封装在 wrapper 里。

## 5. 常见坑

- 只用 `1024 x 1024 x 1024` 方阵测试，参数写反也可能暂时看不出来。
- 忘记交换 A/B，导致结果实际对应另一种矩阵乘法。
- `lda / ldb / ldc` 仍按 `M / K / N` 随手填，没有跟随 cuBLAS 视角调整。
- 在 README 里只说“为了 cuBLAS 交换参数”，但没有解释 `C^T = B^T @ A^T`。
- wrapper 名字没有写明 row-major，后面加入 column-major 或 transpose 路径时容易混乱。

> [!warning] 方阵会骗你
> `M=N=K` 时，很多 shape 错误不会立刻暴露。Day 2 必须用非方阵验收。

---

## 6. 当天验收标准

推荐验收 shape：

```text
M = 257
N = 509
K = 1024
```

建议做两类检查：

| 检查 | shape | 目的 |
|---|---|---|
| 小尺寸手算 | `M=2, N=2, K=3` | 快速确认 A/B 交换和输出语义 |
| 非方阵压力 | `M=257, N=509, K=1024` | 暴露 `M/N/K`、`lda/ldb/ldc` 写反 |

小尺寸 case 可以用很简单的数据，让 CPU reference 和 cuBLAS 输出都容易打印检查。非方阵 case 则不要手算，只看 reference 误差和 wrapper 参数是否稳定。

Day 2 结束时，至少要做到：

- [ ] 写出 `sgemm_row_major` wrapper。
- [ ] 非方阵 shape 下和 CPU、PyTorch 或 NumPy 对拍正确。
- [ ] 小尺寸手算 case 能解释 `C = A @ B` 的 row-major 语义。
- [ ] README 能解释为什么传给 cuBLAS 的是 `N, M, K`。
- [ ] 能说明 `lda = N`、`ldb = K`、`ldc = N` 在 wrapper 里的来源。
- [ ] benchmark 记录里标明 layout 是 `row-major wrapper`。

验收输出可以写成：

```text
row-major SGEMM wrapper correct
shape = 257 x 509 x 1024
max_abs_error = xxx
cuBLAS args = N, M, K
```
