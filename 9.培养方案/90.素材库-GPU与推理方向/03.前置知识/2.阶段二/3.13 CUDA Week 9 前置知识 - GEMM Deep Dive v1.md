## 1. Week 9 和 Week 4 的区别

Week 4 的 matmul 是学习型的：

```text
先看懂 C[row, col] = dot(A row, B col)
再看懂 shared memory tiling 为什么减少 global memory 重复读取
最后用 roofline 建立 compute / memory 判断
```

Week 9 的 GEMM deep dive 是工程型的：

```text
同一组 shape
同一组输入
同一套 reference
同一套 timing
同一套 CSV
同一套 profiling 记录
```

也就是说，Week 9 不只是“再写一个 matmul kernel”。它要让每个版本都能放进同一张表里比较。

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_13_2.svg|955]]

### 1.1 从 kernel toy 到 GEMM lab

Week 4 的输出可以是一个教学 kernel。只要你能解释 A/B tile 和 `__syncthreads()`，它就达到了学习目标。

Week 9 的输出要更像一个小型实验项目：

```text
reference
-> custom CUDA kernels
-> cuBLAS SGEMM baseline
-> benchmark runner
-> Nsight profiling
-> README comparison report
```

这意味着每个实现都必须回答同一组问题：

- 输入 shape 是什么？
- 数据布局是什么？
- 结果和 reference 的误差是多少？
- 计时是否只包含 GEMM 本体？
- TFLOPS 怎么算？
- 和 cuBLAS 的差距是多少？
- profiling 指标能解释这个差距吗？

### 1.2 阶段二先统一协议，再谈优化

阶段二最容易犯的错是先追性能：

```text
先把某个 kernel 调快
-> 后面再补 correctness
-> 再后面发现 shape / layout / timing 都不统一
```

正确顺序应该反过来：

1. 先统一 correctness 协议。
2. 再统一 benchmark 协议。
3. 再接入 naive / tiled / register blocking / cuBLAS。
4. 最后用 profiling 解释差距。

> [!important] 第一层直觉
> Week 9 的“深挖”不是把一个 kernel 写复杂，而是让每一次性能比较都有证据链。没有 correctness 和 benchmark 协议，TFLOPS 只是一个看起来很漂亮的数字。

## 2. GEMM 三条证据链

GEMM lab 至少要有三条证据链：

```text
correctness -> benchmark -> profiling
```

它们分别回答不同问题：

| 证据链 | 回答的问题 | 典型产物 |
|---|---|---|
| correctness | 算得对吗？ | max abs error、RMS error、pass/fail |
| benchmark | 快多少？比较公平吗？ | `benchmark_results.csv` |
| profiling | 为什么快/慢？ | `profiling.md`、Nsight 指标 |

### 2.1 correctness 证据链

correctness 的目标不是一句 `pass`，而是能让你定位错误。

建议最少记录：

```text
implementation
M, N, K
dtype
layout
max_abs_error
max_rel_error
rms_error
correct
```

对 FP32 入门版本，可以先用固定随机种子生成输入，再和 CPU / PyTorch reference 对拍。

```cpp
struct ErrorStats {
    float max_abs_error;
    float max_rel_error;
    float rms_error;
    bool pass;
};
```

> [!warning] 不要只测全 1
> 全 1 输入容易把下标错误、layout 错误、边界错误藏起来。固定随机种子更适合做默认测试。

### 2.2 benchmark 证据链

benchmark 的目标是公平比较。

最小协议：

```text
warmup = 10
repeat = 100
timing = CUDA event
scope = kernel / cublasSgemm only
excluded = cudaMalloc, H2D, D2H, CPU reference, CSV write
```

TFLOPS 计算仍然是：

```text
FLOPs = 2 * M * N * K
TFLOPS = FLOPs / time_seconds / 1e12
```

如果后续要升级，可以从平均值改成 median 或 min，但 CSV 和 README 必须写清楚取值方式。

### 2.3 profiling 证据链

profiling 不要求每个 shape 都跑完整 Nsight。Week 9 最少选 1 到 2 个代表 shape：

- 一个常规方阵，例如 `1024 x 1024 x 1024`。
- 一个 LLM-like projection，例如 `1024 x 4096 x 4096`。

记录时不要只截一张图，要把结论写成判断链：

```text
现象：tiled CUDA 比 naive 快
证据：global memory throughput / SM utilization / achieved occupancy 变化
解释：A/B tile 复用减少了重复 global memory load
限制：register blocking v1 仍然远低于 cuBLAS，因为 tile 层级和指令调度很粗
```

## 3. row-major、M/N/K 与 cuBLAS wrapper

Week 9 必须把 layout 说清楚。因为 GEMM 最常见的错误，不是数学公式看不懂，而是 `M/N/K`、stride、layout、cuBLAS 参数被写反。

### 3.1 三个 stride 不能混

在 row-major 语义下：

```cpp
A[row, k]   -> A[row * K + k]
B[k, col]   -> B[k * N + col]
C[row, col] -> C[row * N + col]
```

三个矩阵的每行长度不同：

| 矩阵 | shape | row-major stride | 访问公式 |
|---|---|---:|---|
| `A` | `M x K` | `K` | `A[row * K + k]` |
| `B` | `K x N` | `N` | `B[k * N + col]` |
| `C` | `M x N` | `N` | `C[row * N + col]` |

不要把所有 stride 都写成 `N`，也不要把 Week 3 transpose 里的 `width / height` 机械搬过来。

### 3.2 非方阵和非整除 shape 为什么必须测

只测 `1024 x 1024 x 1024` 会掩盖很多错误：

- `M` 和 `N` 写反，方阵可能仍然能过。
- `lda / ldb / ldc` 写错，方阵可能不暴露。
- tile 边界没处理，整除 shape 可能不暴露。
- register blocking 写越界，规整 shape 可能不暴露。

所以 Week 9 至少要包含：

```text
16 x 16 x 16       debug
127 x 129 x 131    非整除边界
512 x 512 x 512    小 benchmark
1024 x 1024 x 1024 常规 GEMM
1024 x 4096 x 4096 LLM-like projection
4096 x 4096 x 4096 大规模压力测试
```

> [!important] 第二层直觉
> 方阵负责给你信心，非方阵和非整除 shape 负责抓 bug。GEMM lab 不能只靠方阵证明正确。

### 3.3 cuBLAS row-major wrapper 的判断方式

cuBLAS 默认按 column-major 解释矩阵。为了在 C/C++ row-major 语义下计算：

```text
C[M, N] = A[M, K] @ B[K, N]
```

常见 wrapper 会利用转置等价：

```cpp
// row-major A[M,K], B[K,N], C[M,N]
// cuBLAS column-major view:
// C^T[N,M] = B^T[N,K] @ A^T[K,M]
cublasSgemm(
    handle,
    CUBLAS_OP_N, CUBLAS_OP_N,
    N, M, K,
    &alpha,
    B, N,
    A, K,
    &beta,
    C, N
);
```

判断 wrapper 是否正确，不靠背参数，而靠对拍：

```text
同一组 A/B
custom CUDA row-major C
cuBLAS wrapper row-major C
CPU / PyTorch reference C
三者都对齐，才说明 wrapper 语义正确
```

## 4. naive CUDA matmul

naive 版本是所有优化的起点。它不是为了快，而是为了给后续 tiled / register blocking 提供一个最清楚的 baseline。

### 4.1 一个线程计算一个 C 元素

最小骨架：

```cpp
__global__ void matmul_naive(
    const float* A,
    const float* B,
    float* C,
    int M,
    int N,
    int K) {
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    int row = blockIdx.y * blockDim.y + threadIdx.y;

    if (row >= M || col >= N) {
        return;
    }

    float acc = 0.0f;
    for (int k = 0; k < K; ++k) {
        acc += A[row * K + k] * B[k * N + col];
    }

    C[row * N + col] = acc;
}
```

这个版本的优点是：

- 下标和数学公式一一对应。
- 容易 debug。
- 容易做非整除边界检查。

缺点也很明显：

- 每个线程独立从 global memory 读 A/B。
- block 内线程没有共享 A/B 数据。
- 数据复用没有被显式利用。

### 4.2 naive 的重复读取

对同一行的多个输出：

```text
C[row, col + 0] 需要 A[row, 0..K-1]
C[row, col + 1] 也需要 A[row, 0..K-1]
C[row, col + 2] 仍然需要 A[row, 0..K-1]
```

对同一列的多个输出：

```text
C[row + 0, col] 需要 B[0..K-1, col]
C[row + 1, col] 也需要 B[0..K-1, col]
C[row + 2, col] 仍然需要 B[0..K-1, col]
```

naive 的核心浪费是：

```text
明明 A/B 元素会服务很多 C 元素，却每次都让线程自己去 global memory 拿。
```

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_13_3.svg|955]]

### 4.3 naive 版本的验收

naive CUDA 最小验收：

- debug shape 能打印局部结果。
- 非方阵 shape correctness pass。
- 非整除 shape correctness pass。
- CSV 里记录 time、TFLOPS、correct。
- README 能解释为什么它慢。

不要急着优化 naive。naive 的价值是让后面每一个优化都有对照。

## 5. shared memory tiled v1

shared memory tiled 版本解决的是 block 内数据复用：

```text
把一小块 A 和一小块 B 从 global memory 搬进 shared memory
让 block 内多个线程反复使用这两块数据
沿 K 维一段一段累加
```

### 5.1 A tile、B tile、C tile 分别是什么

假设 `TILE = 16`：

| 对象 | shape | 含义 |
|---|---|---|
| C tile | `16 x 16` | 一个 block 负责的一块输出 |
| A tile | `16 x 16` | C tile 对应的 16 行 A，在当前 K tile 上的数据 |
| B tile | `16 x 16` | C tile 对应的 16 列 B，在当前 K tile 上的数据 |

每一轮 K tile：

```text
load A tile
load B tile
sync
accumulate TILE 次
sync
进入下一轮 K tile
```

### 5.2 教学版 tiled kernel 关键片段

核心结构：

```cpp
template <int TILE>
__global__ void matmul_tiled(
    const float* A,
    const float* B,
    float* C,
    int M,
    int N,
    int K) {
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];

    int tx = threadIdx.x;
    int ty = threadIdx.y;
    int row = blockIdx.y * TILE + ty;
    int col = blockIdx.x * TILE + tx;

    float acc = 0.0f;

    for (int k0 = 0; k0 < K; k0 += TILE) {
        int a_col = k0 + tx;
        int b_row = k0 + ty;

        As[ty][tx] = (row < M && a_col < K)
            ? A[row * K + a_col]
            : 0.0f;

        Bs[ty][tx] = (b_row < K && col < N)
            ? B[b_row * N + col]
            : 0.0f;

        __syncthreads();

        for (int kk = 0; kk < TILE; ++kk) {
            acc += As[ty][kk] * Bs[kk][tx];
        }

        __syncthreads();
    }

    if (row < M && col < N) {
        C[row * N + col] = acc;
    }
}
```

这段代码重点看四件事：

1. `row / col` 决定当前线程负责哪个 C 元素。
2. `k0` 决定当前处理 K 维的哪一段。
3. A tile 的列沿 K 维移动。
4. B tile 的行沿 K 维移动。

### 5.3 `__syncthreads()` 和边界补 0

第一处 `__syncthreads()`：

```text
保证所有线程都已经把 A/B tile 放进 shared memory。
```

第二处 `__syncthreads()`：

```text
保证所有线程都用完当前 A/B tile，再允许下一轮覆盖 shared memory。
```

边界补 0 的原因：

```text
M/N/K 不能被 TILE 整除时，边缘 tile 会访问矩阵外。
对乘加来说，越界位置应该贡献 0。
```

> [!warning] 不要只测整除 shape
> 如果只测 `512 x 512 x 512`，边界补 0 的 bug 可能完全不会暴露。`127 x 129 x 131` 这种 shape 才是 tiled kernel 的基本体检。

## 6. register blocking v1

shared memory tiling 让 block 内线程共享 A/B。register blocking 再往前走一步：让一个线程计算多个 C 元素，在寄存器里复用 A 或 B。

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_13_4.svg|955]]

### 6.1 1x2 / 2x1 / 2x2 thread tile

入门阶段不要一上来写复杂 thread tile。可以从三种小版本里选一种：

| thread tile | 一个线程计算 | 复用倾向 |
|---|---|---|
| `1x2` | 同一行两个输出 | 复用同一个 A 值 |
| `2x1` | 同一列两个输出 | 复用同一个 B 值 |
| `2x2` | 四个输出 | 同时复用 A/B，accumulator 更多 |

`1x2` 的直觉最简单：

```cpp
float acc0 = 0.0f;
float acc1 = 0.0f;

for (int k = 0; k < K; ++k) {
    float a = A[row * K + k];
    float b0 = B[k * N + col];
    float b1 = B[k * N + col + 1];

    acc0 += a * b0;
    acc1 += a * b1;
}

C[row * N + col] = acc0;
if (col + 1 < N) {
    C[row * N + col + 1] = acc1;
}
```

### 6.2 register reuse 的收益

register blocking 的收益来自：

- 一个线程持有多个 accumulator。
- 同一个 A 或 B 值可以服务多个输出。
- 一些中间值留在寄存器里，不必反复访问 shared/global memory。

它让你开始接触真正 GEMM 的核心思想：

```text
不是每个线程只算一个点，而是让线程 / warp / block 形成多层 tile。
```

### 6.3 register pressure 的代价

register blocking 不是免费午餐：

- accumulator 更多，寄存器占用更多。
- 寄存器多可能降低 occupancy。
- occupancy 降低后，GPU 隐藏 latency 的能力可能变弱。
- 如果寄存器不够，可能 spill 到 local memory，性能反而下降。

Week 9 先不要追最优 blocking。最重要的是在 `profiling.md` 里记录：

```text
registers per thread
achieved occupancy
local memory spill 是否出现
性能变化是否和 register pressure 对得上
```

## 7. benchmark runner 和 Nsight 指标

Week 9 的 benchmark runner 是阶段二后续 Week 10 Triton、Week 11 CUTLASS、Week 12 Tensor Core 的公共底座。这里协议越稳，后面越省力。

### 7.1 timing scope

建议一次 benchmark 分成两条路径：

correctness run：

```text
初始化输入
运行一次 implementation
D2H 拷回输出
和 reference 对拍
记录误差
```

timing run：

```text
H2D 准备好输入
warmup 多次
CUDA event start
repeat 多次 implementation
CUDA event stop
记录平均 / median / min
```

计时窗口只包含：

```text
custom kernel launch and execution
或
cublasSgemm execution
```

不包含：

```text
cudaMalloc
host input generation
H2D
D2H
CPU reference
CSV write
```

### 7.2 CSV 字段和 ratio vs cuBLAS

最小 CSV 字段：

```text
implementation,M,N,K,dtype,layout,warmup,repeat,time_ms,tflops,ratio_vs_cublas,correct,max_abs_error,rms_error
```

同一个 shape 下，custom kernel 和 cuBLAS 最好相邻：

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_13_5.svg|955]]

示例：

| implementation | M | N | K | dtype | layout | time_ms | TFLOPS | ratio_vs_cublas | correct |
|---|---:|---:|---:|---|---|---:|---:|---:|---|
| naive CUDA | 1024 | 1024 | 1024 | FP32 | row-major | TBD | TBD | TBD | pass |
| tiled CUDA | 1024 | 1024 | 1024 | FP32 | row-major | TBD | TBD | TBD | pass |
| register blocking v1 | 1024 | 1024 | 1024 | FP32 | row-major | TBD | TBD | TBD | pass |
| cuBLAS SGEMM | 1024 | 1024 | 1024 | FP32 | row-major wrapper | TBD | TBD | 1.00 | pass |

`ratio_vs_cublas` 要明确含义。建议使用：

```text
ratio_vs_cublas = custom_time_ms / cublas_time_ms
```

这样：

- `1.00` 表示和 cuBLAS 一样快。
- `2.00` 表示比 cuBLAS 慢 2 倍。
- `0.50` 表示比 cuBLAS 快，但学习版 FP32 kernel 通常不该轻易出现这个结果，出现就要先怀疑 benchmark 协议。

### 7.3 Nsight 最少看什么

Week 9 的 Nsight Compute 不必一次看完所有指标。最少关注：

| 指标 | 用来判断什么 |
|---|---|
| achieved occupancy | 线程块、寄存器、shared memory 是否限制并发 |
| SM utilization | 计算资源是否忙起来 |
| memory throughput | global memory 压力是否明显 |
| stall reason | warp 为什么等 |
| registers per thread | register blocking 的压力 |
| shared memory usage | tiled kernel 的资源占用 |

`profiling.md` 不要写成指标堆砌。每个结论尽量写成：

```text
现象 -> 指标 -> 解释 -> 限制
```

## 关键要点总结

- Week 9 的核心不是“再写一个 matmul”，而是建立可复现 GEMM lab。
- correctness、benchmark、profiling 是三条证据链，缺一条都不该下性能结论。
- row-major、M/N/K、stride、cuBLAS wrapper 必须用非方阵对拍验证。
- naive CUDA 是清晰 baseline，shared memory tiled v1 是第一层数据复用。
- register blocking v1 的收益来自寄存器复用，代价来自 register pressure。
- cuBLAS SGEMM 是工业 baseline，打不过不是失败；解释差距才是 Week 9 的学习目标。
- 这周打稳协议，是为了 Week 10 的 [[Week 10 - GEMM Triton + Benchmark Protocol]] 可以直接接入同一套比较框架。
