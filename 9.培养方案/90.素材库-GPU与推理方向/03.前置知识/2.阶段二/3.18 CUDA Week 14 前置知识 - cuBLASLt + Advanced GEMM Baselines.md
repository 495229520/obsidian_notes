## 1. Week 14 要解决什么

前几周已经有：

```text
CUDA v1/v2
Triton matmul
CUTLASS example / profiler
cuBLAS SGEMM / HGEMM / GemmEx
```

这些已经能支撑普通 GEMM comparison。但真实工程里，GEMM 往往不只是：

```text
D = alpha * A @ B + beta * C
```

还会牵涉：

```text
不同 layout
不同 dtype / compute type
algorithm selection
workspace budget
bias / activation / scale epilogue
heuristic cache
```

cuBLASLt 的价值就在这里：它把 GEMM 从“一个函数调用”扩展成“一个可描述、可选择、可复用的 matmul operation”。

### 1.1 cuBLASLt 不是 cuBLAS 的改名

普通 cuBLAS 的入门体验像这样：

```cpp
cublasSgemm(handle, opA, opB, m, n, k,
            &alpha, A, lda, B, ldb,
            &beta, C, ldc);
```

cuBLASLt 的体验更像这样：

```text
create handle
create operation descriptor
create A/B/C/D layout descriptors
create preference
query heuristic algorithm candidates
allocate workspace if needed
call cublasLtMatmul
destroy descriptors
```

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_18_2.svg|955]]

这看起来更麻烦，但它换来的是更强的表达能力。

### 1.2 advanced baseline 的价值

advanced baseline 对项目报告有三个价值：

| 价值 | 解释 |
|---|---|
| 可信度 | 报告不只拿手写 CUDA 和入门 `sgemm` 比，还知道 vendor library 的高级接口 |
| 可解释性 | layout、workspace、algorithm、epilogue 都可记录，避免“库函数黑盒” |
| 面试表达 | 能解释工业 GEMM baseline 怎么设，而不是只说“我调了 cuBLAS” |

但要注意：cuBLASLt 的结果不是你的手写 kernel 贡献。它是用来定标、解释差距和建立工程口径的。

## 2. cuBLAS vs cuBLASLt

### 2.1 普通 cuBLAS 的定位

普通 cuBLAS 适合：

- 快速接入 BLAS API。
- 做简单、稳定、可信的 baseline。
- 用 `cublasSgemm` / `cublasGemmEx` 覆盖常见 GEMM。
- 在学习早期避免被 descriptor 和 heuristic 分散注意力。

普通 cuBLAS 的好处是简单，坏处是它把很多选择隐藏在库内部。对于 Week 4 / Week 9，这是优点；对于 Week 14，它开始不够解释 advanced GEMM 场景。

### 2.2 cuBLASLt 的定位

cuBLASLt 更适合：

| 场景 | 为什么 |
|---|---|
| advanced GEMM baseline | 能显式记录 layout、compute type、workspace、algorithm |
| mixed precision | 与 compute type / scale / epilogue 配合更自然 |
| epilogue fusion | bias、ReLU、GELU 等后处理可以作为 matmul epilogue 配置 |
| heuristic reuse | 可查询 heuristic 并复用 algorithm result |
| 工程报告 | 能解释“baseline 是怎么来的”，不是只写一个库名 |

一句话区分：

```text
cuBLAS 是简单可靠的 BLAS baseline；
cuBLASLt 是更灵活、更可配置的 GEMM baseline 工具箱。
```

## 3. cuBLASLt 最小调用链

cuBLASLt 最小 GEMM 的核心对象可以先记成五类：

| 对象 | 作用 |
|---|---|
| `cublasLtHandle_t` | cuBLASLt 上下文 |
| `cublasLtMatmulDesc_t` | 描述 matmul operation：compute type、scale type、transpose、epilogue |
| `cublasLtMatrixLayout_t` | 描述 A/B/C/D：dtype、rows、cols、leading dimension、order |
| `cublasLtMatmulPreference_t` | 描述偏好：最大 workspace 等 |
| `cublasLtMatmulHeuristicResult_t` | heuristic 返回的 algorithm candidate 和 runtime properties |

### 3.1 descriptor / layout / preference / heuristic

建议把调用链写成这张图，而不是直接贴一大段代码：

```text
problem shape + dtype + layout
  -> operation descriptor
  -> matrix layout descriptors
  -> preference / workspace budget
  -> cublasLtMatmulAlgoGetHeuristic
  -> cublasLtMatmul
```

每一步都对应 report 字段：

| 调用链阶段 | report 字段 |
|---|---|
| problem shape | `M,N,K,batch` |
| operation descriptor | `opA,opB,compute_type,scale_type,epilogue` |
| matrix layout | `A_layout,B_layout,C_layout,D_layout,lda,ldb,ldc,ldd` |
| preference | `max_workspace_bytes` |
| heuristic | `algo_id,returned_results,heuristic_state` |
| matmul | `time_ms,tflops,correctness` |

### 3.2 教育型代码骨架

下面只保留最小骨架，不当完整项目实现教程：

```cpp
cublasLtHandle_t lt;
cublasLtCreate(&lt);

cublasLtMatmulDesc_t op_desc;
cublasLtMatmulDescCreate(&op_desc, CUBLAS_COMPUTE_32F, CUDA_R_32F);

cublasOperation_t transa = CUBLAS_OP_N;
cublasOperation_t transb = CUBLAS_OP_N;
cublasLtMatmulDescSetAttribute(
    op_desc, CUBLASLT_MATMUL_DESC_TRANSA, &transa, sizeof(transa));
cublasLtMatmulDescSetAttribute(
    op_desc, CUBLASLT_MATMUL_DESC_TRANSB, &transb, sizeof(transb));

cublasLtMatrixLayout_t A_desc, B_desc, C_desc, D_desc;
cublasLtMatrixLayoutCreate(&A_desc, CUDA_R_32F, rowsA, colsA, lda);
cublasLtMatrixLayoutCreate(&B_desc, CUDA_R_32F, rowsB, colsB, ldb);
cublasLtMatrixLayoutCreate(&C_desc, CUDA_R_32F, rowsC, colsC, ldc);
cublasLtMatrixLayoutCreate(&D_desc, CUDA_R_32F, rowsD, colsD, ldd);

cublasLtMatmulPreference_t pref;
cublasLtMatmulPreferenceCreate(&pref);
cublasLtMatmulPreferenceSetAttribute(
    pref, CUBLASLT_MATMUL_PREF_MAX_WORKSPACE_BYTES,
    &workspace_size, sizeof(workspace_size));

cublasLtMatmulHeuristicResult_t result{};
int returned = 0;
cublasLtMatmulAlgoGetHeuristic(
    lt, op_desc, A_desc, B_desc, C_desc, D_desc,
    pref, 1, &result, &returned);

if (returned > 0) {
    cublasLtMatmul(
        lt, op_desc,
        &alpha, A, A_desc, B, B_desc,
        &beta, C, C_desc, D, D_desc,
        &result.algo, workspace, workspace_size, stream);
}
```

> [!warning] 代码骨架不能替代官方文档
> 不同 CUDA 版本、dtype、layout、epilogue 对参数和限制的要求可能不同。实验实现时必须以当前环境的 CUDA/cuBLASLt 头文件和 NVIDIA 文档为准。

## 4. layout、op、leading dimension

cuBLAS 系列最容易踩坑的地方之一是 layout。很多学习项目的矩阵按 row-major 存，但 cuBLAS 传统接口常以 column-major BLAS 语义组织参数。cuBLASLt 虽然更灵活，但也要求你把 layout descriptor 写清楚。

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_18_3.svg|955]]

### 4.1 row-major 项目为什么更容易踩坑

假设项目里按 row-major 存：

```text
A[row, col] -> A[row * K + col]
B[row, col] -> B[row * N + col]
C[row, col] -> C[row * N + col]
```

你需要明确：

| 字段 | 必须回答 |
|---|---|
| `opA/opB` | 是否转置？是否为了适配 row-major 做了等价变换？ |
| `lda/ldb/ldc/ldd` | leading dimension 到底是 row stride 还是 column stride？ |
| matrix order | descriptor 是否显式设置 row-major / column-major？ |
| output D | D 和 C 是否同布局？是否原地？ |
| correctness | reference 是否用同一布局解释结果？ |

如果不写清 layout，benchmark 数字就很难被第三个人复现。

### 4.2 layout 字段必须进 report

建议每一行 cuBLASLt benchmark 都记录：

```text
A_order
B_order
C_order
D_order
opA
opB
lda
ldb
ldc
ldd
```

这看起来啰嗦，但它可以避免最常见的报告漏洞：

```text
性能数字看起来有了，但没人知道到底算的是 A @ B 还是 B^T @ A^T 的等价形式。
```

## 5. heuristic、algorithm、workspace

cuBLASLt 的 algorithm selection 可以先理解为：

```text
在给定 shape、dtype、layout、compute type、epilogue、workspace budget 的情况下，
库返回一组可能合适的 matmul algorithm candidate。
```

### 5.1 heuristic 不是全局最优证明

`cublasLtMatmulAlgoGetHeuristic()` 返回的 candidate 很有价值，但它不是数学意义上的全局最优证明。

你在报告里可以写：

```text
cuBLASLt heuristic selected algorithm X under workspace budget Y.
```

不要写：

```text
cuBLASLt 找到了全局最优算法。
```

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_18_4.svg|955]]

建议日志记录：

| 字段 | 说明 |
|---|---|
| `requested_algo_count` | 请求多少个候选 |
| `returned_algo_count` | 实际返回多少个候选 |
| `algo_id` | 使用的 algorithm 标识 |
| `workspace_size` | 该候选需要的 workspace |
| `state/status` | heuristic 是否成功 |
| `waves_count` | 如果 API 返回该字段，可作为运行特征记录 |

### 5.2 workspace 是算法搜索空间的一部分

workspace 不是“临时内存而已”。它可能影响可选 algorithm：

| workspace budget | 可能影响 |
|---:|---|
| 0 bytes | 只能选择无需额外 workspace 的算法 |
| 4 MB / 16 MB | 可能打开更多候选 |
| 64 MB / 128 MB | 可能获得更快算法，但占用更多显存 |

所以 benchmark 表要写：

```text
workspace_bytes = 0 / 4MB / 16MB / ...
```

否则 cuBLASLt 结果无法公平复现。

## 6. epilogue fusion

GEMM 的数学主体是：

```text
D = alpha * op(A) * op(B) + beta * C
```

epilogue 是 GEMM 主计算后的后处理。例如：

```text
D = bias + alpha * A @ B
D = relu(alpha * A @ B + bias)
D = gelu(alpha * A @ B + bias)
```

### 6.1 epilogue 在 GEMM 的哪里

如果不融合 epilogue，流程可能是：

```text
GEMM kernel writes D
separate bias kernel reads D and writes D
separate activation kernel reads D and writes D
```

如果融合进 epilogue，流程可能变成：

```text
GEMM kernel computes accumulator
apply bias / activation while writing D
```

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_18_5.svg|955]]

潜在收益：

- 减少一次或多次 global memory read/write。
- 减少 kernel launch overhead。
- 更贴近 LLM inference 中 linear + bias / activation 的真实模式。

潜在代价：

- descriptor 配置更复杂。
- correctness 对拍要包含 bias / activation。
- layout、dtype、epilogue 支持矩阵可能有限制。
- 不同 CUDA 版本支持范围可能变化。

### 6.2 本周只做最小调研

Week 14 的主线仍然是 advanced baseline。epilogue 不要抢主线。

本周可以选择两种口径之一：

| 口径 | 交付 |
|---|---|
| 最小实验 | 跑一个 bias epilogue case，并和 reference 对拍 |
| 只调研 | 写清 cuBLASLt 支持哪些 epilogue、为什么本周不展开 |

无论哪种，都不要把 epilogue fusion 的结果和普通 GEMM 直接混成同一行比较。它们解决的问题不同。

## 7. 如何接入 GEMM comparison report

cuBLASLt 应该作为 advanced vendor baseline 进入 report，而不是替换掉原来的 cuBLAS 行。

### 7.1 cuBLASLt 行应该记录什么

最小表格：

| Impl | Shape | Input | Compute | Layout | Algo | Workspace | Epilogue | Time(ms) | TFLOPS | Note |
|---|---|---|---|---|---|---:|---|---:|---:|---|
| cuBLAS SGEMM | 1024x1024x1024 | FP32 | FP32 | wrapper | n/a | 0 | none | TBD | TBD | simple baseline |
| cuBLASLt | 1024x1024x1024 | FP32 | FP32 | row/col desc | TBD | TBD | none | TBD | TBD | heuristic baseline |
| CUTLASS | 1024x1024x1024 | FP32 | FP32 | profiler config | kernel | n/a | none | TBD | TBD | industrial template |
| CUDA v2 | 1024x1024x1024 | FP32 | FP32 | row-major | manual | 0 | none | TBD | TBD | handwritten |

如果要算 ratio，必须写清 baseline：

```text
ratio_vs_cublas
ratio_vs_cublaslt
```

不要把两者混成一个 `ratio_vs_vendor`，因为 baseline 对象变了。

### 7.2 不要把 vendor baseline 当成手写贡献

报告里可以这样写：

```text
cuBLASLt was added as an advanced vendor baseline to understand algorithm selection, workspace, and epilogue configuration. It is used to calibrate the comparison, not claimed as a custom kernel optimization.
```

这句话很重要。它能把你的工程判断和“调库冒充优化”区分开。

## 8. Week14 实验检查表

### 8.1 必测 shape

先用少量 shape，把调用链和日志打稳：

| M | N | K | 用途 |
|---:|---:|---:|---|
| 1024 | 1024 | 1024 | sanity |
| 1024 | 4096 | 4096 | LLM-like projection |
| 4096 | 4096 | 4096 | large GEMM |

如果时间允许，再加：

| M | N | K | 用途 |
|---:|---:|---:|---|
| 127 | 129 | 131 | layout / boundary correctness |

### 8.2 correctness 最低要求

- cuBLASLt 最小 GEMM 和 CPU/reference 或 cuBLAS baseline 对拍。
- FP32 使用 FP32 tolerance。
- FP16/BF16 必须记录 input/output/compute/accumulate 口径和 tolerance。
- epilogue case 如果启用，reference 必须包含同样的 bias / activation。
- benchmark timing 不混入 H2D / D2H。

### 8.3 benchmark CSV 字段

建议新增这些字段：

```csv
impl,shape,input_dtype,output_dtype,compute_type,scale_type,A_order,B_order,C_order,D_order,opA,opB,lda,ldb,ldc,ldd,algo_id,workspace_bytes,epilogue,time_ms,tflops,ratio_vs_cublas,ratio_vs_cublaslt,correctness,notes
cublas_sgemm,1024x1024x1024,fp32,fp32,fp32,fp32,column-major,column-major,column-major,column-major,N,N,TBD,TBD,TBD,TBD,n/a,0,none,TBD,TBD,1.00,TBD,pass,simple-baseline
cublaslt,1024x1024x1024,fp32,fp32,fp32,fp32,row-major,row-major,row-major,row-major,N,N,TBD,TBD,TBD,TBD,TBD,TBD,none,TBD,TBD,TBD,1.00,pass,heuristic-baseline
```

### 8.4 cublaslt_notes.md 必须回答

`cublaslt_notes.md` 至少回答：

- cuBLASLt 和 `cublasSgemm` 的调用链差异是什么？
- operation descriptor 里设置了哪些属性？
- A/B/C/D layout descriptor 如何定义？
- workspace budget 是多少？
- heuristic 请求了几个候选，返回了几个？
- 最终使用哪个 algorithm？
- epilogue 是否启用？如果没有，为什么？
- cuBLASLt 结果如何进入 comparison report？
- 哪些结论不能从本周实验推出？

## 关键要点总结

- cuBLASLt 是 advanced GEMM baseline，不是普通 cuBLAS 的简单改名。
- cuBLASLt 的核心是 descriptor、layout、preference、heuristic、workspace 和 epilogue。
- heuristic 返回的是候选算法，不是全局最优证明；workspace 会影响候选空间。
- layout、op、leading dimension 必须写进 report，否则结果难以复现。
- epilogue fusion 可能减少 memory traffic 和 launch overhead，但本周只做最小调研。
- cuBLASLt 的结果用于校准和解释差距，不能写成手写 CUDA kernel 的优化成果。
