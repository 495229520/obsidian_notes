## 1. Week 16 要解决什么

前面七周已经有很多材料：

```text
CUDA kernels
Triton kernels
CUTLASS / cuBLAS / cuBLASLt baselines
FP32 / mixed precision results
benchmark CSV
Nsight reports
roofline thinking
profiling findings
```

如果不收束，它们只是散落实验。Week 16 要把它们变成作品集项目：

```text
repo structure
-> reproducible commands
-> correctness tests
-> benchmark tables
-> profiler evidence
-> comparison report
-> interview story
-> next steps
```

### 1.1 从实验堆到作品集

实验堆的特点：

- 文件很多，但入口不清楚。
- 表格很多，但不知道哪个是最终结果。
- 图很多，但找不到原始数据。
- kernel 很多，但分不清哪些是手写，哪些是库 baseline。
- 结论很多，但 limitations 不清楚。

作品集的特点：

- README 能解释项目目标和复现方式。
- report 能解释结果和证据。
- artifact index 能索引原始数据。
- limitations 能保护可信度。
- 面试表达能讲清能力边界。

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_20_2.svg|955]]

### 1.2 本周不做什么

Week 16 不要再把主线拉回“再优化一个 kernel”。

本周不要求：

- 不继续无限调 tile size。
- 不新增一堆未验证 shape。
- 不为了好看删掉失败实验。
- 不把项目包装成打败 cuBLAS。
- 不把 CUTLASS / cuBLAS / cuBLASLt 写成自己的手写 kernel。

本周真正要拿到的是：

```text
一个第三个人能看、能跑、能信的 GEMM lab 项目。
```

## 2. repo structure 和 artifact index

一个可展示项目需要稳定目录。可以按这个思路组织：

```text
matmul-lab-cuda-triton-cutlass/
  README.md
  src/
    cuda/
    triton/
    cutlass/
    cublas/
  benchmarks/
    raw/
    summary/
  profiling/
    ncu/
    profiling.md
  reports/
    gemm_comparison_report.md
    gemm_profiling_report.md
    artifacts_index.md
    gemm_stage2_retro.md
  scripts/
  docs/
```

这不是强制目录，而是提醒你：代码、原始数据、派生 summary、报告要分开。

### 2.1 raw data、summary、report 分开

| 类型 | 应放哪里 | 原则 |
|---|---|---|
| raw CSV / JSON | `benchmarks/raw/` | 不手工改 |
| summary table | `benchmarks/summary/` 或 report | 可由 raw 派生 |
| Nsight 输出 | `profiling/ncu/` | 保留命令和版本 |
| report | `reports/` | 写解释、结论、限制 |
| README | repo root | 做项目入口 |

### 2.2 失败实验也要有位置

失败实验不要直接删。可以在 artifact index 里标注：

| Artifact | Status | Why keep it |
|---|---|---|
| `cuda_v2_tile_128x128_failed.csv` | failed | correctness failed on boundary shape |
| `triton_config_sweep_raw.csv` | partial | autotune candidates used for final config |
| `ncu_cuda_v2_1024.ncu-rep` | valid | supports profiling finding #2 |

> [!note] 失败实验是工程判断的一部分
> 作品集不是只展示“成功截图”。能说明哪些优化没保留、为什么没保留，反而更像真实工程。

## 3. README 应该讲什么

README 是入口，不是完整论文。它要让新读者快速知道：

```text
这个项目是什么
实现了哪些 kernel
用了哪些 baseline
怎么验证 correctness
怎么跑 benchmark
核心结果是什么
怎么复现
有哪些限制
下一步是什么
```

### 3.1 README 是入口，不是论文

建议 README 结构：

```text
# matmul-lab-cuda-triton-cutlass

## Project Goal
## What is Implemented
## Baselines
## Correctness
## Benchmark Protocol
## Results Summary
## Profiling Findings
## How to Reproduce
## Limitations
## Next Steps
```

### 3.2 复现命令必须可复制

README 里的命令要尽量具体：

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j

./build/gemm_bench \
  --impl cuda_v2 \
  --m 1024 --n 1024 --k 1024 \
  --dtype fp32 \
  --warmup 20 --repeat 100 \
  --output benchmarks/raw/cuda_v2_1024_fp32.csv
```

Nsight 命令也要有：

```bash
ncu --set full \
  --kernel-name regex:gemm \
  --launch-skip 5 \
  --launch-count 1 \
  --force-overwrite \
  --export profiling/ncu/cuda_v2_1024_fp32 \
  ./build/gemm_bench --impl cuda_v2 --m 1024 --n 1024 --k 1024 --dtype fp32
```

如果命令依赖特定 GPU / CUDA 版本，要写清：

```text
Tested on: GPU X, CUDA Y, driver Z.
```

## 4. gemm_comparison_report.md 定稿

最终 report 应该比 README 更详细。README 负责“入口”，report 负责“论证”。

### 4.1 report 的主线

建议 `gemm_comparison_report.md` 结构：

```text
1. Experiment Setup
2. Implementations
3. Correctness Method
4. Benchmark Protocol
5. FP32 Results
6. Mixed Precision Results
7. Profiling Findings
8. Roofline Thinking
9. Engineering Tradeoffs
10. Limitations
11. Next Steps
```

实现列表要分组：

| 分组 | 实现 | 表述 |
|---|---|---|
| Hand-written | CUDA naive / tiled / v2 | 自己实现，用来理解优化链路 |
| DSL | Triton matmul / autotune | 自己写 kernel，但由 Triton 编译和优化 |
| Template baseline | CUTLASS | 工业模板库 baseline |
| Vendor baseline | cuBLAS / cuBLASLt | NVIDIA vendor baseline |

### 4.2 findings 必须可追溯

每个 finding 都按这条链写：

```text
Finding
-> Evidence
-> Interpretation
-> Limitation
```

例如：

```text
Finding:
CUDA v2 improves over CUDA tiled v1 on 1024x1024x1024 FP32.

Evidence:
benchmark summary row X shows TFLOPS A -> B.
ncu report Y shows register count and achieved occupancy changes.

Interpretation:
The improvement is consistent with better data reuse and larger thread tile.

Limitation:
This does not imply v2 is competitive with cuBLAS, and it was not verified across all shapes/GPU architectures.
```

## 5. correctness / benchmark / profiling 复查

Week 16 的 polish 不是调格式，而是复查可信度。

### 5.1 correctness 不给性能优化让路

至少写清：

| 项 | 要写什么 |
|---|---|
| reference | CPU reference / cuBLAS / high precision reference |
| tolerance | FP32、FP16、BF16 各自阈值 |
| errors | max abs error、RMS error |
| shape | 方阵、LLM-like、边界 shape |
| epilogue | bias / activation 是否包含在 reference |

如果某个优化只支持整齐 shape，也要写：

```text
vectorized fast path currently supports aligned shapes; non-divisible shapes use scalar fallback / are marked unsupported.
```

### 5.2 benchmark 协议固定

benchmark 协议要固定：

| 项 | 要写什么 |
|---|---|
| warmup | warmup 次数 |
| repeat | repeat 次数 |
| timing scope | 是否只计 kernel time |
| synchronization | timing 前后是否 sync |
| H2D/D2H | 是否排除 host-device copy |
| baseline | ratio 使用 cuBLAS 还是 cuBLASLt |
| dtype | FP32 和 mixed precision 是否分开 |

一句话原则：

```text
benchmark 公平性来自固定协议，不来自“看起来差不多”。
```

## 6. 面试表达：3 分钟和 10 分钟

作品集项目最终要能讲出来。Week 16 建议准备两版。

### 6.1 3 分钟版本

结构：

```text
1. 项目目标
2. 我实现了什么
3. 我如何验证 correctness 和 benchmark
4. 最重要的性能/工程结论
5. limitations 和下一步
```

示例骨架：

```text
我做了一个 matmul-lab-cuda-triton-cutlass 项目，用同一套 correctness 和 benchmark 协议比较手写 CUDA、Triton、CUTLASS、cuBLAS 和 cuBLASLt。手写部分包括 naive、shared memory tiled 和 CUDA GEMM v2；baseline 部分包括 CUTLASS profiler、cuBLAS/GemmEx 和 cuBLASLt heuristic。项目重点不是宣称超过 cuBLAS，而是用 benchmark、Nsight Compute 和 roofline thinking 解释不同实现的性能差距，并把 limitations 写清楚。下一步会把这套 benchmark/profiling 方法迁移到 LLM kernels，比如 attention、RMSNorm 和 serving path。
```

### 6.2 10 分钟版本

结构：

```text
1. 背景：为什么 GEMM 是 GPU infra 基础
2. correctness：reference / tolerance / edge shape
3. hand-written CUDA：v1 -> v2 的优化链路
4. Triton：DSL 和 autotune
5. CUTLASS / cuBLAS / cuBLASLt：baseline 定位
6. profiling：Nsight 指标和 roofline thinking
7. tradeoff：性能、可维护性、debug cost
8. limitations：没有证明什么
9. next：LLM kernels / attention / serving / multi-GPU inference
```

> [!tip] 面试里要主动区分“我写的”和“我复现/调用的”
> 这能避免被追问时显得含糊，也能体现工程诚信。CUDA/Triton 是你的实现线；CUTLASS/cuBLAS/cuBLASLt 是 baseline 和学习参照。

## 7. 阶段复盘和下一主线

### 7.1 GEMM 项目证明了什么

这个项目能证明的能力：

| 能力 | 证据 |
|---|---|
| CUDA kernel 基础 | naive、tiled、register blocking、v2 |
| benchmark 纪律 | warmup/repeat、统一 CSV、same shape/same dtype |
| baseline 意识 | cuBLAS、cuBLASLt、CUTLASS 定位清楚 |
| profiling 能力 | Nsight 指标、roofline thinking、stall reason |
| 工程表达 | README、report、limitations、artifact index |
| LLM infra 迁移 | 从 GEMM 协议迁移到 attention / serving |

这个项目不能证明：

- 全面打败 cuBLAS。
- 覆盖所有 GPU 架构。
- 找到全局最优 tile config。
- 完整实现工业 Tensor Core GEMM。
- 对所有 LLM shape 都最优。

### 7.2 如何衔接 LLM kernels / attention / serving

GEMM 项目收束后，不要无限留在 matmul。下一阶段可以自然转向：

| 下一主线 | 从 GEMM 继承什么 |
|---|---|
| RMSNorm / LayerNorm | correctness、benchmark、profiling 协议 |
| RoPE | dtype、layout、kernel fusion 意识 |
| Attention | tiling、shared memory、memory traffic、roofline thinking |
| FlashAttention | block-level streaming、online softmax、memory-bound 分析 |
| LLM serving | prefill/decode、KV cache、batching、end-to-end metrics |
| Serving engine | PagedAttention、RadixAttention、continuous batching、chunked prefill、PD disaggregation |
| Multi-GPU inference | TP / DP / PP / EP、NCCL collectives、RDMA、MoE EP / All-to-All |

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_20_5.svg|955]]

阶段二前八周的意义是：

```text
先用 GEMM 把性能工程方法练扎实，再迁移到更 LLM-specific 的 kernel 和 serving path。
```

### 7.3 multi-GPU inference 后续路线边界

Week 16 只做后续路线索引，不包装成已经实现 multi-GPU runtime。最低要把这些概念写进 `gemm_stage2_retro.md` 或 `multi_gpu_inference_next_steps.md`：

| 概念 | 先掌握什么 | 面试边界 |
|---|---|---|
| TP | tensor / hidden 维度切分 | 常见通信是 AllReduce、AllGather、ReduceScatter |
| DP | 多副本分摊请求 | 重点是 router、负载均衡和 cost tradeoff |
| PP | 按层切分 pipeline | 关注 bubble、micro-batch 和跨 stage latency |
| EP | MoE expert parallel | 关注 expert dispatch、load balance 和 All-to-All |
| NCCL | GPU collective 通信 | 能解释 AllReduce / AllGather / ReduceScatter / All-to-All 的用途 |
| RDMA | 跨机低延迟传输 | 能解释它为什么影响 KV transfer、expert dispatch 和 tail latency |

面试表达要克制：

```text
我还没有实现完整 multi-GPU runtime，但我已经把 GEMM profiling / benchmark 方法收束成作品集，并规划下一步用同样的方法分析 TP/DP/PP/EP、NCCL collective、RDMA 和 MoE EP 的通信瓶颈。
```

## 8. Week16 实验检查表

### 8.1 最终交付物

| 交付物 | 内容 | 验收 |
|---|---|---|
| `README.md` | 项目目标、运行、结果、限制 | 可作为作品集入口 |

| interview story | 3 分钟 / 10 分钟版本 | 能讲清项目 |

### 8.2 README 最低要求

- 项目目标清楚。
- 实现列表分组：hand-written、DSL、template baseline、vendor baseline。
- correctness 方法清楚。
- benchmark protocol 清楚。
- 至少一张结果 summary table。
- 有复现命令。
- limitations 不缺席。
- next steps 指向 LLM kernels / attention / serving。
- next steps 明确 serving engine 与 multi-GPU inference 的后续路线，但不冒充已实现。

### 8.3 report 最低要求

- FP32 和 mixed precision 分开。
- CUDA / Triton / CUTLASS / cuBLAS / cuBLASLt 角色分清。
- 每个主结论都能追溯到 CSV / profiler / environment。
- profiler 结论不只贴截图。
- roofline thinking 有估算和边界。
- 不跨 dtype 乱算 ratio。
- 不宣称打败工业库。

### 8.4 polish 前最后自检

发布前问自己：

- 新读者能在 README 里 3 分钟看懂项目吗？
- 命令能复制运行吗？
- 哪些文件是 raw data，哪些是 summary？
- 有没有把失败实验删到无法解释？
- 有没有混淆“手写实现”和“vendor baseline”？
- limitations 是否具体？
- 下一阶段是否明确？
- multi-GPU inference 是否只作为后续路线表达，没有包装成 Week 16 已实现 runtime？

## 关键要点总结

- Week 16 的核心是收束阶段二 GEMM 项目，而不是继续追加优化。
- README 是入口，comparison report 是论证，artifact index 是证据地图，retro 是阶段闭环。
- 作品集可信度来自可复现命令、correctness、benchmark 协议、profiler 证据和 limitations。
- 必须主动区分手写 CUDA/Triton 与 CUTLASS/cuBLAS/cuBLASLt baseline。
- 不要包装成“打败 cuBLAS”，要包装成“我理解 GEMM 优化链路和工程评估方法”。
- GEMM 收束后，下一主线应该转向 LLM kernels、attention 或 serving，而不是无限优化 matmul。
- multi-GPU inference 是后续路线：先理解 TP / DP / PP / EP、NCCL、RDMA、MoE EP / All-to-All，再考虑实验实现。
