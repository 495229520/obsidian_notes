## 1. Week 11 要解决什么

Week 9 和 Week 10 已经建立了：

```text
CUDA naive / tiled / register blocking
Triton matmul v1
cuBLAS SGEMM baseline
统一 correctness + benchmark + profiling 协议
```

Week 11 要做的是：

```text
CUTLASS example / profiler
-> CUTLASS benchmark row
-> CUTLASS hierarchy notes
-> comparison report CUTLASS section
```

### 1.1 CUTLASS 的定位

CUTLASS 可以先理解成：

```text
NVIDIA 开源的 CUDA C++ 模板库，用来表达和生成高性能 GEMM / convolution 等线性代数 kernel。
```

在这个学习阶段，它有三个价值：

- 作为工业 GEMM hierarchy 的学习对象。
- 作为比手写 CUDA / Triton v1 更接近工业实现的参考 baseline。
- 作为理解 Tensor Core、mainloop、epilogue、tile 层级的入口。

> [!important] 第一层直觉
> cuBLAS 更像“直接调用的 vendor library baseline”；CUTLASS 更像“能看到结构、能配置、能学习 hierarchy 的工业模板库”。

### 1.2 本周不做什么

本周不建议把目标定成：

```text
修改 CUTLASS 核心模板
读懂所有 CuTe / Collective / Kernel 源码
宣称自己写出了 CUTLASS 级别 GEMM
用一个 CUTLASS 数字证明自己手写 kernel 达到工业水平
```

更合理的 Week 11 目标是：

1. 能构建或运行 CUTLASS example / profiler。
2. 能把 CUTLASS 输出放进统一 comparison table。
3. 能解释 CUTLASS GEMM hierarchy 的基本层次。
4. 能清楚写出限制：哪些是复现，哪些是自己实现，哪些只是推测。

## 2. CUTLASS 和 CUDA / Triton / cuBLAS 的关系

Week 11 最重要的一件事，是把四类实现的定位分清楚。

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_15_2.svg|955]]

### 2.1 四类实现的定位

| 实现 | 定位 | 你在报告里应该怎么写 |
|---|---|---|
| 手写 CUDA | 学习型 kernel | 我实现了 naive / tiled / reg-block，用来理解优化路径 |
| Triton v1 | DSL 快速实现 | 我用 Triton 表达 block matmul，并接入同一协议 |
| CUTLASS | 工业模板库参考 | 我复现 CUTLASS example / profiler，并分析 hierarchy |
| cuBLAS | vendor library baseline | 我调用 cuBLAS 作为同 shape 性能基准 |

CUTLASS 不等于 cuBLAS。cuBLAS 是更封装的库调用；CUTLASS 暴露更多模板层级和 kernel 结构，适合学习和定制。

CUTLASS 也不等于手写 CUDA。你可以配置、复现、分析 CUTLASS，但不能把 CUTLASS example 的性能写成“我手写 kernel 的性能”。

### 2.2 为什么 CUTLASS 不是“自己的手写 kernel”

报告里应该明确区分：

```text
My CUDA kernels:
  naive CUDA
  shared memory tiled
  register blocking v1

My Triton kernels:
  Triton matmul v1

Reproduced / analyzed library baselines:
  CUTLASS GEMM example / profiler
  cuBLAS SGEMM
```

这样写更诚实，也更像工程报告。面试时反而加分：说明你知道不同层次的贡献边界。

## 3. CUTLASS GEMM hierarchy

NVIDIA CUTLASS 文档把 GEMM 映射成分层 tile：threadblock、warp、instruction / MMA 等层次分别对应 CUDA 执行模型和 GPU memory hierarchy。

可以先用这张图建立直觉：

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_15_3.svg|955]]

### 3.1 threadblock tile

threadblock tile 是一个 CUDA block 负责的一块 C 输出。

它负责：

- 从 global memory 读取 A/B 的大块 tile。
- 在 block 内通过 shared memory 组织数据复用。
- 沿 K 维做 mainloop。
- 把工作分给多个 warp。

在 CUTLASS 里，threadblock tile 的形状可以理解成类似：

```text
ThreadblockShape::{kM, kN, kK}
```

它对应：

```text
C tile: kM x kN
每轮 K tile: kK
```

大的 threadblock tile 能提高数据复用，但也会带来资源压力、边界浪费和 occupancy 变化。

### 3.2 warp tile

warp tile 是 threadblock tile 内部再分给 warp 的子块。

它负责：

- 从 shared memory 取当前 warp 需要的 A/B fragment。
- 在寄存器里组织局部 accumulator。
- 发出 SIMT 或 Tensor Core 相关的矩阵乘加指令。

可以先把它和 Week 10 的 Triton BLOCK 区分开：

```text
Triton BLOCK_M/N/K: 一个 program 的 tile 形状
CUTLASS warp tile: threadblock 内部某个 warp 负责的子 tile
```

### 3.3 instruction tile / MMA

instruction tile 是更底层的矩阵乘加单位。

在 Tensor Core 路径中，它会和 MMA 指令相关；在 SIMT 路径中，也可能对应 thread-level matrix multiply。

谨慎表达方式：

```text
CUTLASS hierarchy 中 instruction / MMA tile 是连接 warp-level GEMM 和硬件矩阵乘加指令的层次。
具体是否走 Tensor Core，要看 dtype、operator class、architecture、kernel 名称和 profiler 证据。
```

不要写：

```text
CUTLASS 一定用了 Tensor Core。
```

除非你有 profiler、kernel 名称或配置证据。

### 3.4 mainloop 和 epilogue

GEMM mainloop 负责：

```text
沿 K 维循环
读取 A/B tile
执行 MMA / multiply-accumulate
累积到 registers
```

epilogue 负责：

```text
把 accumulator 中的 C tile 写回 global memory
做 alpha / beta 线性组合
可能做 clamp、activation 或其他 elementwise 操作
组织 coalesced store
```

这解释了为什么工业 GEMM 不只是“一个 for 循环算完 C”。真正的实现还要处理加载、pipeline、寄存器布局、shared memory、写回和融合操作。

## 4. CUTLASS example / profiler 怎么接入

Week 11 不要求你一开始写 CUTLASS 模板。更实际的顺序是：

```text
确认版本
-> 跑 example / profiler
-> 保存命令和日志
-> 转成统一 benchmark 字段
-> 写 hierarchy notes
```

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_15_5.svg|955]]

### 4.1 先记录环境和版本

`cutlass_notes.md` 或 report 里至少记录：

```text
CUTLASS repo / release / commit
CUDA version
driver version
GPU model
compiler
build type
command
```

不要只贴一张运行截图。第三个人要能知道你到底跑的是哪个 CUTLASS。

### 4.2 example reproduction

最小复现记录应该包含：

```text
command:
  ./tools/profiler/cutlass_profiler ...

problem:
  M, N, K
  dtype A/B/C
  accumulator type
  layout A/B/C

result:
  runtime / time_ms
  GFLOPS / TFLOPS
  verification result
  kernel / operation name
```

如果使用 example 而不是 profiler，也同样记录：

- example 名称。
- build 命令。
- 运行命令。
- 输出日志。
- shape / dtype / layout。

### 4.3 profiler 行如何转换成统一字段

CUTLASS profiler 的字段不一定和你的 `benchmark_results.csv` 完全一致，所以需要做一层转换：

| CUTLASS 输出 | 统一字段 |
|---|---|
| operation / kernel name | `implementation` 或 `note` |
| problem size | `M,N,K` |
| data type / layout | `dtype,layout` |
| runtime | `time_ms` |
| GFLOPS | `TFLOPS` 或换算 |
| verification | `correct` |
| command / provider | `config` / `note` |

转换时保留原始输出，不要只保留改写后的 CSV。

## 5. CUTLASS benchmark 行怎么写

Week 11 的表格应该从 Week 10 扩展，而不是新建孤立的 CUTLASS 表。

### 5.1 同 shape 进入同一张表

同一个 shape 下建议相邻记录：

```text
CUDA tiled
Triton v1
CUTLASS profiler
cuBLAS SGEMM
```

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_15_4.svg|955]]

统一字段：

```text
implementation,M,N,K,dtype,layout,time_ms,tflops,ratio_vs_cublas,correct,config,note
```

其中 CUTLASS 行可以写：

```text
implementation = CUTLASS profiler
config = operation/kernel name + tile info if available
note = reproduced library baseline, not hand-written kernel
```

### 5.2 ratio vs cuBLAS 的解释

继续沿用 Week 9 / Week 10 的定义：

```text
ratio_vs_cublas = implementation_time_ms / cublas_time_ms
```

解释时注意：

- CUTLASS 接近 cuBLAS：说明该 CUTLASS 配置在这个 shape 上很强，但仍要看 dtype、layout、kernel、环境。
- CUTLASS 慢于 cuBLAS：不代表 CUTLASS 不行，可能是配置、kernel selection、problem shape、build flag 或 profiler 设置不同。
- CUTLASS 快于 cuBLAS：先检查是否同 dtype、同 shape、同 layout、同 timing scope、同 verification。

### 5.3 Tensor Core 路径要谨慎表述

Tensor Core 相关描述建议分三层：

```text
确定：CUTLASS hierarchy 支持 CUDA/Tensor Core 层次的 GEMM 映射。
可能：某个低精度配置可能走 Tensor Core。
证据：只有当 kernel 名称、operator class、dtype、profiler 指标能支持时，才写“本次运行使用了 Tensor Core 路径”。
```

尤其 Week 11 如果主要跑 FP32 SGEMM，不要强行把结论写成 Tensor Core 性能分析。Week 12 会专门进入 mixed precision / Tensor Core。

## 6. CUTLASS notes 和 report 章节

### 6.1 `cutlass_notes.md` 应该写什么

建议结构：

```text
1. CUTLASS 是什么
2. 本次使用版本和环境
3. example / profiler 命令
4. GEMM hierarchy
   - threadblock tile
   - warp tile
   - instruction / MMA tile
   - mainloop
   - epilogue
5. benchmark 转换规则
6. 和 CUDA / Triton / cuBLAS 的区别
7. 限制和下一步
```

`cutlass_notes.md` 不是 CUTLASS 源码阅读大全。它的价值是帮你把工业库结果放进自己的 GEMM comparison report。

### 6.2 comparison report 的 CUTLASS 段落

GEMM report 里的 CUTLASS 章节至少包含：

- setup：版本、环境、构建命令。
- command：example / profiler 运行命令。
- result：同 shape 表格。
- hierarchy：用自己的话解释层级。
- comparison：和 CUDA / Triton / cuBLAS 的定位差异。
- limitation：不是手写 kernel、不是完整模板改造、Tensor Core 路径需证据。

可以写成下面这种语气：

```text
CUTLASS is used here as an industrial template-library baseline and a hierarchy study target.
The reported result comes from CUTLASS profiler reproduction, not from my handwritten kernel.
```

这比含糊地写“我实现了 CUTLASS GEMM”要稳得多。

### 6.3 给 Week 12 留接口

Week 12 会进入 Tensor Core + mixed precision。Week 11 要提前保留字段：

```text
dtype_a
dtype_b
dtype_c
accumulator_type
operator_class
math_instruction
kernel_name
```

Week 11 可以先不填全，但表格结构要能容纳这些信息。

## 关键要点总结

- Week 11 的主线是引入 CUTLASS 作为工业模板库 baseline 和 GEMM hierarchy 学习对象。
- CUTLASS 不是 cuBLAS：它暴露更多结构和可配置层级；cuBLAS 更像直接调用的 vendor library baseline。
- CUTLASS 也不是你的手写 CUDA kernel：报告里必须区分复现 / 分析 / 自己实现。
- threadblock tile、warp tile、instruction tile 对应从粗到细的 GEMM 分层。
- mainloop 负责沿 K 维读取和累积；epilogue 负责把 accumulator 写回并做线性组合或 elementwise。
- CUTLASS benchmark 行必须接入 Week 9 / Week 10 的同 shape comparison table。
- Tensor Core 结论要有 dtype、kernel、operator class 或 profiler 证据；没有证据就写限制。
