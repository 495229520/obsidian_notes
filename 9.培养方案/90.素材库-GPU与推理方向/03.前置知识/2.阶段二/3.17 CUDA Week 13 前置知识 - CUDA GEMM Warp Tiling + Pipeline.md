## 1. Week 13 要解决什么

Week 9 的 CUDA v1 通常长这样：

```text
naive:
  one thread -> one C element

tiled v1:
  one block -> one C tile
  shared memory cache A/B tile
  one thread -> one C element

register blocking v1:
  one thread -> 1x2 / 2x1 / 2x2 C elements
```

这已经能说明 shared memory 复用，但还不够接近工业 GEMM。工业 GEMM 的核心不是只有“把 A/B 搬进 shared memory”，而是多层次地分配工作：

```text
threadblock tile: 一个 CTA 算 C 的大 tile
warp tile:       一个 warp 算 C 大 tile 里的一个子 tile
thread tile:     一个 thread 算多个 C 元素
register:        每个 thread 把自己的 accumulator 常驻寄存器
```

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_17_2.svg|955]]

### 1.1 从 v1 到 v2：不是换一个 tile size

如果只是把 `BLOCK_SIZE = 16` 改成 `32`，这不是 Week 13 的重点。Week 13 要把设计写清楚：

| 设计层级 | v1 常见写法 | v2 要补上的东西 |
|---|---|---|
| threadblock | 一个 block 负责一个 C tile | 明确 `BLOCK_M/BLOCK_N/BLOCK_K` |
| warp | 通常没有显式设计 | 明确每个 warp 负责哪个 C subtile |
| thread | 常是一个 C 元素或很小 thread tile | 明确 `THREAD_M/THREAD_N` 和 accumulator 数量 |
| global load | scalar load 为主 | 尝试向量化读取，并写清 alignment/fallback |
| shared memory | 简单二维数组 | 观察 layout、padding、bank conflict |
| K loop | load -> sync -> compute -> sync | 尝试 simple pipeline / double buffering |

### 1.2 本周不做什么

Week 13 容易被误解成“我要手写一个 CUTLASS”。这不现实，也不是当前训练目标。

本周不要求：

- 不要求手写完整 Tensor Core MMA kernel。
- 不要求实现 CUTLASS 级别的 template policy。
- 不要求追平 cuBLAS。
- 不要求所有 shape 都收益一致。
- 不要求把 simple pipeline 说成工业级 async pipeline。

本周真正要拿到的是：

```text
一个能跑、能测、能解释的 CUDA GEMM v2。
```

## 2. threadblock tile / warp tile / thread tile

GEMM 的 C 矩阵可以看成很多输出元素：

```text
C[M, N] = A[M, K] x B[K, N]
```

tile hierarchy 的意思是：不要让“线程”直接面对整个矩阵，而是分层切分。

### 2.1 三层 tile 分别解决什么

| 层级 | 负责什么 | 典型问题 |
|---|---|---|
| threadblock tile | 一个 CTA 负责 C 的一块，例如 `128x128` | shared memory 需要多少？一个 SM 能放几个 block？ |
| warp tile | 一个 warp 负责 block tile 的一部分，例如 `64x32` | warp 内线程如何映射到 C subtile？ |
| thread tile | 一个 thread 负责多个 C 元素，例如 `4x4` | accumulator 要多少寄存器？是否降低 occupancy？ |

一个简化设计可以先写成：

```cpp
constexpr int BLOCK_M = 128;
constexpr int BLOCK_N = 128;
constexpr int BLOCK_K = 8;

constexpr int WARPS_PER_BLOCK = 8;
constexpr int THREADS_PER_BLOCK = WARPS_PER_BLOCK * 32;

constexpr int THREAD_M = 4;
constexpr int THREAD_N = 4;
```

这段不是推荐唯一答案，而是提醒你：v2 设计必须把这些参数显式写出来。没有这些参数，后面的 register count、occupancy、shared memory size 都无法解释。

### 2.2 一个可落地的 v2 设计口径

在 `cuda_gemm_v2_design.md` 里，建议至少写清这张表：

| 参数 | 示例 | 解释 |
|---|---:|---|
| `BLOCK_M` | 128 | 一个 block 覆盖多少 C rows |
| `BLOCK_N` | 128 | 一个 block 覆盖多少 C cols |
| `BLOCK_K` | 8 / 16 | 每次 K loop 搬多少 A/B |
| `WARPS_PER_BLOCK` | 4 / 8 | 一个 block 中有几个 warp |
| `THREAD_M` | 2 / 4 | 一个 thread 负责多少 C rows |
| `THREAD_N` | 2 / 4 | 一个 thread 负责多少 C cols |
| accumulator | `THREAD_M * THREAD_N` | 每个 thread 的寄存器累加器个数 |
| shared memory | `A tile + B tile` | 是否双缓冲要乘以 stage 数 |

如果你还不能确定参数，先写候选：

```text
candidate A: BLOCK_M=64,  BLOCK_N=64,  BLOCK_K=8,  THREAD_M=2, THREAD_N=2
candidate B: BLOCK_M=128, BLOCK_N=64,  BLOCK_K=8,  THREAD_M=4, THREAD_N=2
candidate C: BLOCK_M=128, BLOCK_N=128, BLOCK_K=8,  THREAD_M=4, THREAD_N=4
```

然后用 correctness + benchmark + Nsight 筛，而不是凭感觉宣布最优。

## 3. register accumulator 与 register pressure

thread tile 的核心是：一个 thread 不再只算一个 C 元素，而是算一个小矩形。

例如 `THREAD_M = 2, THREAD_N = 2`：

```text
一个 thread 维护 4 个 accumulator:

acc[0][0] acc[0][1]
acc[1][0] acc[1][1]
```

这样做的收益是：同一个 A 值可以乘多个 B 值，同一个 B 值也可以服务多个 A row。数据从 shared memory 读到 register 后，能在 thread 内多用几次。

### 3.1 为什么一个 thread 要算多个 C 元素

一个教育型骨架如下：

```cpp
float acc[THREAD_M][THREAD_N] = {};

for (int kk = 0; kk < BLOCK_K; ++kk) {
    float a_frag[THREAD_M];
    float b_frag[THREAD_N];

    #pragma unroll
    for (int i = 0; i < THREAD_M; ++i) {
        a_frag[i] = As[thread_m_base + i][kk];
    }

    #pragma unroll
    for (int j = 0; j < THREAD_N; ++j) {
        b_frag[j] = Bs[kk][thread_n_base + j];
    }

    #pragma unroll
    for (int i = 0; i < THREAD_M; ++i) {
        #pragma unroll
        for (int j = 0; j < THREAD_N; ++j) {
            acc[i][j] += a_frag[i] * b_frag[j];
        }
    }
}
```

这里的关键不是语法，而是数据复用路径：

```text
shared memory -> register fragment -> multiple FMA -> register accumulator
```

### 3.2 register blocking 不是越大越好

`THREAD_M * THREAD_N` 越大，单线程复用越强，但寄存器也越多：

| thread tile | accumulator 个数 | 可能收益 | 可能代价 |
|---|---:|---|---|
| `1x1` | 1 | register 少，occupancy 高 | 数据复用弱 |
| `1x2` / `2x1` | 2 | 轻量复用 | 收益有限 |
| `2x2` | 4 | v1/v2 入门常用 | 仍较容易控 |
| `4x4` | 16 | 复用更强 | register pressure 明显上升 |
| `8x8` | 64 | 理论复用强 | 很可能 occupancy 和 spill 出问题 |

> [!warning] register pressure 是 Week 13 的核心风险
> 如果 v2 比 v1 慢，不一定是 tile hierarchy 错了，也可能是 accumulator、临时 fragment、索引变量和 unroll 共同把 register count 推高，导致 occupancy 下降或出现 spill。报告里要把 register count 和 achieved occupancy 放在一起看。

## 4. vectorized load 与 alignment

vectorized load 的直觉是：让每个线程一次搬更多连续数据，例如用 `float4` 一次搬 4 个 `float`。它主要服务 global memory 到 shared memory 的搬运阶段。

### 4.1 float4 解决的是什么

标量读取可能长这样：

```cpp
float x0 = A[offset + 0];
float x1 = A[offset + 1];
float x2 = A[offset + 2];
float x3 = A[offset + 3];
```

向量化读取可能长这样：

```cpp
const float4* A4 = reinterpret_cast<const float4*>(A + offset);
float4 v = A4[0];
```

它试图减少指令数量，并帮助形成更规整的连续访问。但这不是免费午餐。

### 4.2 alignment 和边界 fallback

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_17_3.svg|955]]

`float4` 的安全前提至少包括：

| 条件 | 为什么重要 |
|---|---|
| 地址满足对齐 | 不满足对齐会导致低效访问，严重时会造成错误假设 |
| 连续 4 个元素都在合法范围内 | 非整除 shape 不能越界读 |
| row stride 支持连续读取 | row-major 下跨行读取要特别小心 |
| fallback 存在 | `127x129x131` 这类 shape 不能被优化路径静默破坏 |

一个更稳的写法是把 vectorized load 当成 guarded fast path：

```cpp
bool aligned = (reinterpret_cast<uintptr_t>(ptr) % alignof(float4)) == 0;
bool in_bounds4 = col + 3 < limit;

if (aligned && in_bounds4) {
    float4 v = *reinterpret_cast<const float4*>(ptr);
    // store v.x/v.y/v.z/v.w to shared memory
} else {
    // scalar fallback with boundary checks
}
```

> [!note] 不要只在方阵上验证 vectorized load
> `1024x1024x1024` 很容易掩盖边界问题。Week 13 至少要保留 `127x129x131`，证明 vectorized path 不会破坏 correctness。

## 5. shared memory layout / padding / bank conflict

shared memory 的目标是把 global memory 的重复读取变成片上复用。但 shared memory 本身也有访问模式问题：多个线程如果在同一轮访问中落到冲突的 bank，会被拆成多次访问，吞吐下降。

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_17_4.svg|955]]

### 5.1 shared memory tile 的布局问题

一个常见写法：

```cpp
__shared__ float As[BLOCK_M][BLOCK_K];
__shared__ float Bs[BLOCK_K][BLOCK_N];
```

这很直观，但不一定总是最优。你要观察：

| 访问 | 可能问题 |
|---|---|
| threads load A row-contiguous | global coalescing 是否好？shared store 是否冲突？ |
| threads load B row-contiguous | B tile 后续被按列/行读时是否冲突？ |
| compute 读取 As/Bs | warp 内线程读 shared 的模式是否导致 bank conflict？ |
| padding 后 | bank conflict 是否下降？shared memory 用量是否增加？ |

### 5.2 padding 的直觉

padding 的目的不是“让数组变大”，而是错开地址到 bank 的映射。例如：

```cpp
__shared__ float Bs[BLOCK_K][BLOCK_N + 1];
```

多出来的 `+1` 可能改变下一行的起始 bank，从而减少某些列式访问下的冲突。

但 padding 也有代价：

```text
shared memory usage 上升
可能降低每个 SM 可驻留 block 数
可能让某些访问变复杂
收益依赖具体 layout 和 architecture
```

所以报告里不要写：

```text
padding 一定更快
```

更稳的写法是：

```text
在 shape X、tile config Y 上，padding 后 shared memory bank conflict 指标下降 / 未明显下降；TFLOPS 对应提升 / 无明显变化。该优化是否保留取决于更多 shape 的结果。
```

## 6. simple pipeline / double buffering

没有 pipeline 的 K loop 通常是：

```text
load A/B tile from global to shared
__syncthreads()
compute this K tile
__syncthreads()
next K tile
```

这会让 load 和 compute 更像串行阶段。pipeline / double buffering 的直觉是：准备两份 shared memory buffer，一份用于当前 compute，一份提前装下一段 K tile。

![[图片/9.培养方案/03.参考资料/2.阶段二/9_3_17_5.svg|955]]

### 6.1 pipeline 想隐藏什么

simple double buffering 的概念骨架：

```cpp
int stage = 0;

load_global_to_shared(stage, k0);
__syncthreads();

for (int k0 = BLOCK_K; k0 < K; k0 += BLOCK_K) {
    int next_stage = stage ^ 1;

    load_global_to_shared(next_stage, k0);

    // simplified teaching version:
    // real overlap depends on instruction scheduling and async copy support.
    compute_from_shared(stage);

    __syncthreads();
    stage = next_stage;
}

compute_from_shared(stage);
```

它想隐藏的是：

```text
global memory load latency
shared memory load latency 的一部分
同步前后的等待
```

### 6.2 Week 13 的简化实现边界

Week 13 可以先做“概念可解释”的 simple pipeline，不要把它包装成完整工业实现。

| 版本 | 允许写法 | 报告表述 |
|---|---|---|
| no pipeline | load -> sync -> compute -> sync | baseline |
| simple double buffer | 两份 shared buffer，尝试交错 load/compute | introductory pipeline |
| async copy pipeline | `cp.async` / barrier / stage 管理 | 本周可选，不作为必做 |
| CUTLASS pipeline | threadblock/warp/register 多层 double buffering | 工业 baseline，不手写复刻 |

如果 simple pipeline 没有提升，也不是失败。你需要解释：

- 是否 load 和 compute 没有真正 overlap？
- 是否 register/shared memory 用量上升抵消收益？
- 是否该 shape 已经不是 memory latency 主导？
- 是否同步位置让 pipeline 退化？

## 7. Nsight 和 report 怎么解释

Week 13 的报告不能只写“v2 更快/更慢”。要把优化和证据对应起来。

### 7.1 指标不是装饰

| 指标 | 对应问题 | 可能结论 |
|---|---|---|
| TFLOPS | v2 最终是否更快 | 只说明结果，不说明原因 |
| register count | thread tile 是否过大 | register pressure 可能限制 occupancy |
| achieved occupancy | 并发度是否下降 | occupancy 下降不一定坏，但要解释 |
| shared memory bank conflict | layout/padding 是否有效 | padding 是否值得保留 |
| global load efficiency | vectorized/coalesced load 是否有效 | scalar vs vectorized 是否有证据 |
| stall reason | 仍卡在哪里 | memory / dependency / instruction issue |
| ratio vs cuBLAS | 与 vendor baseline 差距 | 必须 same shape / same dtype |

最小分析模板：

```text
For shape 1024x1024x1024 FP32:
- CUDA v2 improves TFLOPS from X to Y vs CUDA v1.
- Register count increases from A to B, achieved occupancy changes from C to D.
- Global load efficiency improves / does not improve after vectorized load.
- Shared bank conflict metric decreases / remains similar after padding.
- CUDA v2 is still below cuBLAS because it lacks Tensor Core path, mature scheduling, epilogue optimization, and architecture-specific tuning.
```

### 7.2 为什么手写 CUDA GEMM 仍然很难追上 CUTLASS / cuBLAS

这部分要写得克制。CUDA v2 的价值是学习和解释，不是宣称工业替代。

| 差距来源 | 解释 |
|---|---|
| tile policy | 工业库有大量 architecture-specific tile config |
| pipeline | CUTLASS/cuBLAS 有更成熟的多 stage pipeline |
| Tensor Core | FP16/BF16/TF32 场景通常走专门 MMA path |
| epilogue | bias、activation、scale 等融合会影响真实业务性能 |
| swizzle / scheduling | block 排布会影响 L2 reuse 和 SM 利用 |
| edge handling | 非整除 shape 的高性能边界处理很复杂 |
| autotuning | 工业库覆盖更多 shape/dtype/layout |

可以写：

```text
CUDA v2 helped us see which layer matters, but it is still an educational kernel. It provides a readable bridge from Week 9 tiled GEMM to CUTLASS/cuBLAS, not a replacement for them.
```

## 8. Week13 实验检查表

### 8.1 必测 shape

沿用前几周的 shape，保证 report 可以横向比较：

| M | N | K | 用途 |
|---:|---:|---:|---|
| 512 | 512 | 512 | 快速迭代 |
| 1024 | 1024 | 1024 | 主对比 |
| 1024 | 4096 | 4096 | LLM-like projection |
| 4096 | 4096 | 4096 | 大规模吞吐 |
| 127 | 129 | 131 | 边界正确性 |

### 8.2 correctness 最低要求

- CUDA v2 和 reference 比较通过。
- CUDA v2 和 cuBLAS SGEMM 在同 shape / FP32 下误差可解释。
- vectorized load 打开和关闭都要跑 correctness。
- padding 打开和关闭都要跑 correctness。
- 非整除 shape 不允许因为 fast path 越界而跳过。

## 关键要点总结

- Week 13 的核心是把 CUDA GEMM 从 v1 的 block-level tiling 推到 threadblock / warp / thread 三层设计。
- register accumulator 提高 thread 内复用，但会带来 register pressure 和 occupancy 变化。
- vectorized load 必须写清 alignment、边界和 fallback，不能只在整齐方阵上跑通。
- shared memory padding 是为了解决特定访问模式下的 bank conflict，不是必然加速开关。
- simple double buffering 的价值是理解 pipeline，但不能夸大成 CUTLASS/cuBLAS 的工业级实现。
- v2 report 的重点不是“我追上了 cuBLAS”，而是“我知道差距在哪，并且能用指标证明每一步优化是否有效”。
