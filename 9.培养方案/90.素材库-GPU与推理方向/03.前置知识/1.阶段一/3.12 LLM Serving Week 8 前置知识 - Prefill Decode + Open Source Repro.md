## 1. 为什么 Week08 要把 prefill / decode 单独拉出来

Serving benchmark 里常见的误区是把所有 latency 混在一起看：

```text
E2E latency 变高 -> 模型慢
```

这个判断太粗。对 LLM serving 来说，至少要拆成：

```text
client / network
-> queue
-> prefill prompt
-> first token
-> decode output tokens
-> final response
```

Week 8 单独分析 prefill / decode，是因为这两段的资源画像不同：

| 阶段 | 主要输入 | 常见瓶颈 | 更敏感的指标 |
|---|---|---|---|
| prefill | prompt tokens | 长 prompt、batch prefill、prefix cache miss | TTFT、prefill time、GPU memory |
| decode | output tokens | 每步读 KV cache、batch decode、持续占用 cache | TPOT / ITL、output TPS、p95 latency |
| queue | request arrivals | request rate 超出服务能力、调度限制 | queue time、waiting requests、TTFT p95 |

> [!warning] 不要跳过 queue
> TTFT 变高不一定是 prefill kernel 慢，也可能是请求排队太久。Week 8 需要把 queue time 单独记录，否则很容易把调度压力误判成模型计算瓶颈。

## 2. prefill / decode 的时间线

一次 streaming 请求可以画成下面这条时间线：

![[图片/9.培养方案/03.参考资料/1.阶段一/9_3_12_2.svg|955]]

### 2.1 TTFT 更靠近 prefill

TTFT 是从请求发出到第一个 token 返回的时间。它通常包含：

- client 到 server 的通信。
- server 排队等待调度。
- prompt tokenization 或输入准备。
- prefill 处理 prompt tokens。
- 生成并返回第一个 token。

所以长 prompt、prefix cache miss、queue backlog 都会推高 TTFT。

可以先用这条判断：

```text
长 prompt + 短 output 下 TTFT 明显升高
-> 优先怀疑 prefill / queue / prefix cache miss
```

### 2.2 TPOT / ITL 更靠近 decode

TPOT / ITL 描述的是开始输出之后，连续 token 之间的节奏。

decode 阶段每生成一个新 token，都要：

- 读取历史 KV cache。
- 计算当前 token 的 attention。
- 写入新 token 的 K / V。
- 等下一步继续生成。

所以长 output 更容易暴露 decode 阶段的持续压力。

```text
短 prompt + 长 output 下 TPOT / ITL 变高
-> 优先看 decode throughput、KV cache read、running requests
```

### 2.3 queue 会污染两类判断

在高 request rate 或高 concurrency 下，queue 会让 TTFT 变差。这个时候不能只看 prompt length。

判断顺序建议是：

1. 先看 failed requests 是否出现。
2. 再看 waiting requests / queue time 是否上升。
3. 然后再判断 prefill / decode 本身。

如果 queue time 已经明显增加，说明系统可能先遇到了 admission / scheduling 压力，单独优化 prefill kernel 未必是第一优先级。

## 3. workload 设计

Week 8 至少要设计三类 workload：prefill-heavy、decode-heavy、mixed。最好再加 shared prefix、KV pressure、chunked prefill on/off 和 PD disaggregation，用来连接 Week 7 的 cache 机制。

![[图片/9.培养方案/03.参考资料/1.阶段一/9_3_12_3.svg|955]]

### 3.1 prefill-heavy

典型配置：

```yaml
name: prefill_heavy
prompt_tokens: 4096
output_tokens: 64
request_rate: [1, 2, 4]
max_concurrency: [4, 8, 16]
```

重点观察：

- TTFT p50 / p95 / p99。
- prefill time。
- queue time。
- GPU memory 和 KV cache usage。
- prefix cache hit / miss，如果框架能暴露。

报告里要能回答：

```text
长 prompt 推高 TTFT，是因为 prefill 本身变长，还是因为高并发下 queue 堆起来？
```

### 3.2 decode-heavy

典型配置：

```yaml
name: decode_heavy
prompt_tokens: 128
output_tokens: 1024
request_rate: [1, 2, 4]
max_concurrency: [4, 8, 16]
```

重点观察：

- TPOT / ITL p50 / p95。
- output TPS。
- running requests。
- KV cache usage。
- p95 E2E latency。

报告里要能回答：

```text
长 output 的主要问题是总时间变长，还是连续 token 间隔也变差？
```

### 3.3 mixed workload

真实 serving 很少只有一种请求。Agent / RAG / coding assistant 往往同时出现：

- 短问题短回答。
- 长文档短回答。
- 短 prompt 长输出。
- 共享 system prompt + tools schema。
- 长上下文 + 多轮对话。

mixed workload 要看：

- tail latency。
- failed requests。
- 不同请求类型之间是否互相拖慢。
- high request rate 下是否出现 backlog。

> [!tip] mixed 比固定 shape 更接近真实系统
> 固定 prompt / output shape 很适合做 baseline，但真实系统的调度问题经常出现在混合长度和突发请求里。

### 3.4 shared prefix 和 KV pressure

shared prefix workload 用来回答：

```text
相同 system prompt / tools schema / 文档前缀，是否真的降低了重复 prefill 成本？
```

KV pressure workload 用来回答：

```text
长 context + 高并发下，KV cache usage 是否接近上限？failed requests 是否增加？
```

这两类 workload 是 Week 7 的自然延伸：不是为了炫技，而是为了让 prefill / decode 的判断有 cache 证据。

### 3.5 chunked prefill on/off

chunked prefill 的直觉是：长 prompt 不一次性吃掉太长时间片，而是拆成多个 prefill chunk，让 decode 阶段有机会穿插执行。

实验配置至少记录：

```yaml
chunked_prefill: on_or_off
max_num_batched_tokens: TBD
prompt_tokens: [2048, 4096, 8192]
output_tokens: [64, 256]
```

观察重点：

- TTFT 是否下降，还是因为更多调度切换而变差。
- TPOT / ITL 是否改善，因为 decode 不再长期饥饿。
- prompt tokens/s 和 generation tokens/s 是否出现跷跷板。
- tail latency 是否比平均值更敏感。

不要把 chunked prefill 写成纯收益。它是在长 prompt、decode SLO 和 scheduler overhead 之间做 tradeoff。

## 4. prefill / decode disaggregation 的直觉

prefill / decode disaggregation 的基本想法是：

```text
prefill worker 专门处理长 prompt
decode worker 专门负责持续生成 token
中间传递 KV cache
```

![[图片/9.培养方案/03.参考资料/1.阶段一/9_3_12_4.svg|955]]

### 4.1 什么时候值得拆

可以考虑拆分的场景：

| 场景 | 原因 |
|---|---|
| 长 prompt 很多 | prefill 会占用大量计算，拖慢首 token |
| decode SLO 更重要 | 希望输出节奏稳定，不被长 prompt 干扰 |
| workload 分布稳定 | prefill / decode worker 比例可以估算 |
| 有高速互联 | KV transfer 成本可控 |
| 有清楚的观测指标 | 能证明拆分前后 TTFT / TPOT 的变化 |

这里的关键不是“拆分一定更高级”，而是要证明：

```text
隔离 prefill 压力带来的收益 > KV transfer 和系统复杂度
```

### 4.2 什么时候不值得拆

不适合硬上的场景：

- 单机小模型，通信和调度开销比收益大。
- workload 很轻，queue 没有明显压力。
- prompt / output 分布变化很大，worker 比例难估。
- 网络或 NVLink 传输成为新瓶颈。
- 团队还没有基础 benchmark 和 observability。

Week 8 的最低目标不要求真正部署 disaggregated serving。能用轻量 workload 分析写清楚适用边界，就已经有工程价值。

### 4.3 KV transfer 成本在哪里

KV transfer 不是一句“传过去”就结束。它至少包含：

- 每层 K / V tensor 的数据量。
- batch 和 seq length 对 KV bytes 的放大。
- prefill worker 到 decode worker 的网络 / NVLink / IPC 成本。
- block table / metadata 的一致性。
- 传输期间的调度等待。
- 失败恢复和重试复杂度。
- 跨机时 network / RDMA 传输延迟和带宽。

所以报告里不要只写：

```text
disaggregation lowers TTFT
```

更可信的写法是：

```text
在长 prompt、短 output、request rate = X 的场景下，拆分后 TTFT p95 下降，但 KV transfer 增加了 Y，decode TPOT 未明显恶化。该结论只适用于当前模型、GPU、网络和 workload。
```

### 4.4 router / worker / network boundary

PD disaggregation 的系统图至少要有五个节点：

```text
client
-> request router
-> prefill worker
-> KV transfer
-> decode worker
-> streaming response
```

如果是单机多卡，重点看 GPU 间传输、NVLink / PCIe 和 NCCL 相关开销；如果是跨机，必须把 network / RDMA boundary 画出来。

判断是否值得拆时，用这一句作为底线：

```text
prefill 隔离带来的 TTFT / decode SLO 收益，必须大于 KV transfer、network overhead 和系统复杂度。
```

## 5. benchmark 证据链

Week 8 的报告不只是写结论，而是留下证据链：

```text
workload_config.yaml
-> reproduce.sh
-> benchmark_results.csv / json
-> metrics snapshot
-> analysis table
-> prefill_decode_report.md
-> issue_reproduction.md / benchmark_report.md
```

### 5.1 配置必须能复跑

`workload_config.yaml` 至少要锁住：

```yaml
model: meta-llama/Llama-3.1-8B-Instruct
engine: vllm
engine_version: ...
gpu: ...
dtype: ...
max_model_len: ...
request_rate: ...
max_concurrency: ...
prompt_tokens: ...
output_tokens: ...
chunked_prefill: on_or_off
pd_disaggregation: off_or_on
seed: ...
raw_result: benchmark_results.json
```

如果涉及 prefix cache，要明确：

```yaml
prefix_cache: on
shared_prefix_tokens: 2048
random_suffix_tokens: 256
```

### 5.2 原始数据不能被改写

原始 CSV / JSON 是证据，不是排版素材。

> [!warning] 不要改 raw benchmark 结果
> 可以从原始结果派生表格、图和统计值，但不能手动改 raw CSV / JSON。异常点也应该保留，并在报告里解释原因。

推荐文件关系：

```text
benchmark_results.json
-> parse_results.py
-> summary_table.csv
-> prefill_decode_report.md
```

如果第三个人只能看到漂亮表格，看不到原始数据、命令和版本，这份报告就不够可信。

### 5.3 结论要带限制

好结论通常包含四部分：

```text
场景 + 观察到的指标 + 可能解释 + 限制
```

示例：

```text
在 prompt=4096、output=64、request_rate=4 的 prefill-heavy 场景中，
TTFT p95 明显高于短 prompt baseline；同时 queue time 只小幅增加，
KV cache usage 未接近上限，因此当前瓶颈更像是 prefill 计算本身。
该结论只覆盖当前模型、batching 策略和 GPU。
```

## 6. open-source reproduction 四步法

Week 8 的外部产出可以是 issue reproduction、benchmark report、docs PR 或小修复 PR。最稳的路线是：

```text
Reproduce -> Minimize -> Analyze -> Contribute
```

![[图片/9.培养方案/03.参考资料/1.阶段一/9_3_12_5.svg|955]]

### 6.1 Reproduce

先证明现象存在：

- issue / discussion / docs gap 链接。
- 框架版本、CUDA、driver、GPU、模型。
- server 启动命令。
- benchmark 命令。
- 原始日志和 raw result。
- 预期现象和实际现象。

如果复现不稳定，要直接写出来，不要假装稳定。

### 6.2 Minimize

最小化不是为了省字，而是为了降低 maintainer 判断成本。

优先缩小：

- 模型规模。
- prompt / output 长度。
- request rate / concurrency。
- 配置项数量。
- 环境变量。
- 无关脚本。

最低产出是一个别人能运行的 `reproduce.sh`。

### 6.3 Analyze

分析要和问题类型匹配：

| 问题类型 | 证据 |
|---|---|
| 性能问题 | benchmark 表、p50 / p95 / p99、raw result |
| serving 问题 | TTFT、TPOT / ITL、queue、KV cache usage、failed requests |
| kernel 问题 | Nsight Compute / Systems、shape、dtype、版本 |
| 文档问题 | 正确命令、实际报错、版本差异 |

如果证据只能说明“我这里变慢了”，就不要写成“框架有 bug”。更稳的表达是“在这个环境和配置下观察到以下现象，请帮忙确认是否预期”。

### 6.4 Contribute

贡献材料要让 maintainer 快速抓住重点：

```markdown
## Environment
## Command
## Expected
## Actual
## Raw results
## Minimal reproduction
## Notes / limitations
```

语气要克制。开源贡献不是证明自己对，而是帮助项目缩小问题空间。

## 7. Agent 边界

Agent 在 Week 8 很有用，但边界要写清楚。

Agent 可以做：

- 生成 benchmark 脚本草稿。
- 生成 `workload_config.yaml` 模板。
- 从 raw result 派生表格。
- 整理 issue reproduction 文案。
- 检查报告是否缺环境、命令、版本和限制。

Agent 不能做：

- 修改 raw benchmark 数据。
- 删除失败请求。
- 替你判断 issue 一定成立。
- 把单次实验夸大成通用结论。
- 伪造 maintainer 需要的日志或版本信息。

> [!important] 最终判断要人工负责
> Agent 可以帮你把证据摆整齐，但“这个现象是否真实、是否可复现、是否应该发 issue”必须由你基于原始数据判断。

## 关键要点总结

1. Week 8 的核心是综合：workload、metrics、KV cache 和开源复现要连成一条证据链。
2. TTFT 更靠近 queue + prefill + first token，TPOT / ITL 更靠近 decode 阶段。
3. 长 prompt 不等于一定 prefill-bound，必须排除 queue backlog。
4. 长 output 更容易暴露 decode rhythm 和 KV cache read pressure。
5. mixed workload 比固定 shape 更接近真实 serving，也更容易暴露 tail latency。
6. chunked prefill 可能缓解长 prompt 阻塞 decode，但要同时观察 TTFT、TPOT 和 scheduler overhead。
7. prefill / decode disaggregation 的价值来自资源隔离，但代价是 KV transfer、network overhead 和系统复杂度。
8. PD disaggregation 不一定更好；当 KV transfer / network cost 大于隔离收益时，应该明确写“不划算”。
9. 开源 reproduction 的最低标准是可复跑、可审查、结论克制。
10. Agent 可以整理证据，但不能修改原始数据，也不能替你做最终工程判断。
