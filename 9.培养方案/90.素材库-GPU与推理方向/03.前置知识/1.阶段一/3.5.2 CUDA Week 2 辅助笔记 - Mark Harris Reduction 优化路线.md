## 1. PDF 的核心问题

Reduction 要把很多输入合成一个输出，例如：

```cpp
sum = a[0] + a[1] + ... + a[n - 1];
```

这和 `vector add` 最大的差别是：很多线程要合作产生同一个结果。

PDF 先指出一个关键限制：普通 CUDA kernel 里没有跨 block 的全局同步。因为不是所有 block 都会同时驻留在 GPU 上，如果已经运行的 block 停在一个全局同步点等待尚未运行的 block，就可能占住 SM 资源，导致后面的 block 无法启动。

所以 reduction 的通用做法是：

```text
每个 block 先算自己的 partial sum
-> 写到 global memory
-> kernel 结束天然形成全局完成点
-> 再启动下一轮 kernel 继续 reduce partial sums
```

> [!important] 直觉
> kernel 边界就是最朴素、最可靠的全局同步点。Week 2 不需要先追求单 kernel 完成所有 reduction，先把多阶段 partial sum 路线写对。

## 2. 优化目标：看 bandwidth，不是只看 GFLOP/s

Reduction 的算术强度很低。对求和来说，基本是每读一个元素只做一次加法，所以瓶颈通常不是浮点计算能力，而是内存带宽、访存模式、同步开销和指令开销。

因此 benchmark 里更适合看：

```text
effective bandwidth = processed_bytes / kernel_time
```

这也是主笔记里 `GB/s` 列的来源。具体 benchmark 写法见 [[3.5.1 CUDA Week 2 辅助笔记 - Benchmark + Profiling]]。

---

## 3. 七个版本的优化路线

PDF 用 7 个 kernel 版本展示 reduction 如何从“能跑”变成“接近带宽上限”。下面的性能数字来自 PDF 中 G80 上 4M int reduction 的示例，主要用来看趋势，不要当成现代 GPU 的固定结论。

| 版本 | 主要写法 | 解决的问题 | 新的问题或代价 | PDF 示例带宽 |
|---|---|---|---|---:|
| 1 | interleaved addressing + `tid % (2*s)` | 最直接的树形规约 | warp 分支高度发散，`%` 很慢 | 2.083 GB/s |
| 2 | 用 `index = 2 * s * tid` 替代取模判断 | 减少分支发散和取模 | shared memory bank conflict | 4.854 GB/s |
| 3 | sequential addressing，步长从 `blockDim/2` 递减 | 消除主要 bank conflict | 第一轮一半线程空闲 | 9.741 GB/s |
| 4 | load 时每个线程先读两个元素并相加 | 减少 block 数和第一轮空闲 | 仍有循环与同步开销 | 17.377 GB/s |
| 5 | 展开最后一个 warp | 少做无用同步和循环判断 | 依赖旧式 warp-synchronous 写法 | 31.289 GB/s |
| 6 | 模板参数固定 block size，完全展开 | 编译期消除循环开销 | 需要按 block size 分发模板实例 | 43.996 GB/s |
| 7 | 每个线程处理多个元素，grid-stride 累加 | 用更多串行工作换更少 block 和 launch 层级 | 边界处理更容易写错 | 62.671 GB/s |

结论很清楚：前半段主要是算法和访存模式优化，后半段主要是减少指令、循环、同步和 kernel 层级开销。

## 4. Version 1：最直接的 interleaved addressing

第一版的核心形状是：

```cpp
for (unsigned int s = 1; s < blockDim.x; s *= 2) {
    if (tid % (2 * s) == 0) {
        sdata[tid] += sdata[tid + s];
    }
    __syncthreads();
}
```

它的优点是非常直观：每轮把相邻的两段合并，最后 `sdata[0]` 变成 block 内结果。

问题也很明显：

- `tid % (2 * s)` 会让同一个 warp 内有的线程执行加法、有的线程不执行，分支发散严重。
- `%` 在这个内层循环里很贵。
- 每一轮都要 `__syncthreads()`，同步次数随 `log2(blockDim)` 增加。

这一版适合当 correctness baseline，不适合作为最终性能版本。

---

## 5. Version 2：去掉慢取模，但引入 bank conflict

第二版把“线程是不是干活”的判断改成 index 计算：

```cpp
int index = 2 * s * tid;

if (index < blockDim.x) {
    sdata[index] += sdata[index + s];
}
```

这样可以让 warp 内分支形态更规整，也去掉 `%`。但它让线程访问 shared memory 的地址呈现跨步模式，容易打到同一个 bank，形成 bank conflict。

> [!note]
> shared memory 很快，但不是“只要用了就快”。如果一个 warp 内多个线程访问同一个 bank 的不同地址，就会被拆成多次访问。

---

## 6. Version 3：sequential addressing

第三版把循环方向反过来：

```cpp
for (unsigned int s = blockDim.x / 2; s > 0; s >>= 1) {
    if (tid < s) {
        sdata[tid] += sdata[tid + s];
    }
    __syncthreads();
}
```

这就是 Week 2 最应该先掌握的 shared memory reduction 形状。

它的好处：

- 活跃线程总是 `tid < s` 的连续前半段。
- shared memory 访问更连续，减少 bank conflict。
- 代码逻辑比 interleaved indexing 更容易检查。

它的问题：

- 第一轮只有一半线程在做加法。
- 仍然每一轮都同步。
- block 内 reduce 完以后，跨 block 的 partial sum 还要下一阶段处理。

---

## 7. Version 4：first add during global load

第三版第一轮一半线程空闲。第四版直接让每个线程从 global memory 读两个元素，并在写入 shared memory 前先加一次：

```cpp
unsigned int i = blockIdx.x * (blockDim.x * 2) + threadIdx.x;
sdata[tid] = g_idata[i] + g_idata[i + blockDim.x];
```

这样一个 block 实际处理 `2 * blockDim.x` 个输入元素，减少了 block 数，也把第一轮 reduction 融进 global load。

Week 2 写这一版时最容易错在边界：

```cpp
float x = (i < n) ? input[i] : 0.0f;
float y = (i + blockDim.x < n) ? input[i + blockDim.x] : 0.0f;
sdata[tid] = x + y;
```

> [!warning]
> PDF 示例为了讲优化主线，常默认输入规模和 block size 配得很整齐。自己的 Week 2 作业要处理 `n` 不能整除的情况，否则 benchmark 可能又快又错。

---

## 8. Version 5：展开最后一个 warp

当 reduction 进行到 `s <= 32` 时，活跃线程只剩一个 warp。旧式写法会利用 warp 内线程同步执行的性质，省掉最后几轮的 `__syncthreads()` 和循环判断，把最后几步手动写开。

这一步的动机是：最后一个 warp 里继续跑完整循环，会让很多 warp 也跟着执行循环判断和同步指令，做大量无用工作。

PDF 中给出的历史写法依赖 `volatile` shared memory 指针，防止编译器把 shared memory 读写重排或缓存到寄存器里。

> [!warning] 现代 CUDA 语境
> 这份 PDF 是经典资料，但它的最后 warp 展开写法属于较早的 shared-memory warp-synchronous 风格。现代 CUDA 更推荐用 `__shfl_down_sync` 做 warp reduction，或者在需要 shared memory 交换时显式使用 `__syncwarp()`。学习时要理解它“减少同步和循环开销”的意图，不要机械照搬旧代码。

---

## 9. Version 6：模板 + 完全展开

如果 block size 在编译期已知，编译器就可以把很多判断和循环展开成固定代码。PDF 用模板参数表达 block size：

```cpp
template <unsigned int blockSize>
__global__ void reduce_kernel(...);
```

然后在 host 端按运行时选择的 block size 分发：

```cpp
switch (threads) {
case 256:
    reduce_kernel<256><<<grid, block, shared_bytes>>>(...);
    break;
case 128:
    reduce_kernel<128><<<grid, block, shared_bytes>>>(...);
    break;
}
```

这样 kernel 内就可以写：

```cpp
if (blockSize >= 256) {
    if (tid < 128) {
        sdata[tid] += sdata[tid + 128];
    }
    __syncthreads();
}
```

`blockSize >= 256` 这类判断会在编译期确定，生成更少的运行时指令。

Week 2 可以先不追求模板完全展开。更合理的路线是：

```text
先写对 sequential addressing
-> 再写 first add during load
-> 再尝试 warp shuffle
-> 最后再考虑模板展开
```

## 10. Version 7：multiple adds per thread

第七版的思想来自 Brent's theorem：不要让每个线程只干极少的工作。可以让每个线程先串行累加多个元素，再把每个线程的局部结果放进 shared memory 做 block 内树形 reduction。

典型形状是 grid-stride loop：

```cpp
unsigned int i = blockIdx.x * (blockSize * 2) + threadIdx.x;
unsigned int gridSize = blockSize * 2 * gridDim.x;

float local = 0.0f;

while (i < n) {
    local += input[i];
    if (i + blockSize < n) {
        local += input[i + blockSize];
    }
    i += gridSize;
}

sdata[tid] = local;
```

这一步的意义：

- 每个线程做更多连续工作，减少 kernel 层级和中间 partial 数量。
- 用 grid-stride 保持不同线程的访问仍然尽量 coalesced。
- 对大输入更容易接近内存带宽上限。

代价是边界检查更复杂，也更需要 correctness check。

---

## 11. 算法复杂度：work-efficient 和 cost-efficient

树形 reduction 在数学上很漂亮：

```text
并行步数：O(log N)
总加法数：N - 1
```

所以它是 work-efficient：总工作量没有超过串行算法。

但如果给每个元素都分配一个线程，就会出现 cost 不划算的问题：

```text
线程数 O(N) * 时间 O(log N) = cost O(N log N)
```

Brent's theorem 给出的直觉是：少用一些线程，让每个线程先做一段串行工作，再做并行合并。这样总 cost 可以回到 O(N)，实际性能也常常更好。

这就是 Version 7 的理论背景。

## 12. 映射到 Week 2 作业

建议 Week 2 的实现顺序：

| 顺序 | 版本 | 验证重点 |
|---:|---|---|
| 1 | CPU reference | 后续所有 GPU 结果都和它比 |
| 2 | naive partial reduce | 理解 partial sum 和多 kernel 汇总 |
| 3 | shared memory sequential reduce | 掌握 `sdata` + `__syncthreads()` |
| 4 | first add during load | 处理 `2 * blockDim` 和非整除长度 |
| 5 | warp shuffle reduce | 用现代 warp 原语替代旧式最后 warp 展开 |
| 6 | multiple adds per thread | 用 grid-stride loop 提高大输入吞吐 |

每增加一个版本，都要保留同一套验证：

- `N = 1`、`N < blockDim`、`N = blockDim`、`N = blockDim + 1`。
- 非 2 的幂长度。
- 大数组，例如 `1M`、`64M`。
- `Check = PASS` 后再记录性能。

---

## 13. 常见坑

- 只做了 block 内 reduction，忘了继续 reduce 所有 `partial[blockIdx.x]`。
- `i + blockDim.x` 越界。
- 默认输入长度一定是 2 的幂。
- `__syncthreads()` 放在条件分支里，导致同一个 block 内不是所有线程都到达同步点。
- benchmark 只打印时间，不打印 `Check`。
- 把旧 PDF 里的 `volatile` 最后 warp 写法直接照搬到现代 CUDA 作业里。
- bandwidth 口径前后不一致，导致不同版本的 `GB/s` 不可比。

---

## 14. 一句话总纲

Mark Harris 这份 PDF 的主线不是“把代码越写越花”，而是：

```text
先用 kernel decomposition 解决跨 block 同步
-> 再用 shared memory 做 block 内协作
-> 再修正分支发散和 bank conflict
-> 再减少空闲线程、循环、同步和指令开销
-> 最后让每个线程承担更多串行工作来提高整体吞吐
```

Week 2 真正要带走的能力是：每看到一个 reduction 版本，都能说清楚它解决了哪个瓶颈，又引入了什么新的边界条件。
