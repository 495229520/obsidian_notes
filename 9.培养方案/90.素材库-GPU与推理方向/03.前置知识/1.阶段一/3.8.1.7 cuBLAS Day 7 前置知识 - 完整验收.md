## 1. Day 7 要解决什么

目标可以压成一句话：

```text
确认 cuBLAS baseline 能跑、能测、能对拍、能解释。
```

完整验收要同时看四件事：

- 代码结构是否清楚。
- correctness 是否可信。
- benchmark 是否公平。
- README 是否能解释结果。

> [!important] 第一层直觉
> Day 7 的产出不是“又跑了一次”。它是把 baseline 变成作品集证据：别人能复现你的命令，能理解你的表格，也能看懂你对性能差距的判断。

---

## 2. 最终项目结构

建议最终结构保持简单：

```text
/cublas
  bench_sgemm.cu
  bench_hgemm.cu
  cublas_wrapper.h
  benchmark.csv
README.md
```

每个文件的角色：

| 文件 | 角色 |
|---|---|
| `bench_sgemm.cu` | FP32 cuBLAS baseline 和 custom kernel 对比 |
| `bench_hgemm.cu` | FP16 / GemmEx baseline |
| `cublas_wrapper.h` | row-major wrapper 和通用检查逻辑 |
| `benchmark.csv` | 结构化记录性能结果 |
| `README.md` | 解释 API、layout、timing、结果和差距 |

不要为了显得完整而过早拆太多目录。这个阶段最重要的是路径清楚、结果可信。

### 2.1 文件到验收项映射

每个文件都应该能回答一个验收问题：

| 文件 | 证明什么 |
|---|---|
| `bench_sgemm.cu` | FP32 SGEMM baseline 能跑、能对拍、能计时 |
| `bench_hgemm.cu` | FP16 / GemmEx baseline 能跑，并记录类型信息 |
| `cublas_wrapper.h` | row-major wrapper 被集中封装，不散落在 benchmark 里 |
| `benchmark.csv` | 每个 shape 的 correctness、ms、TFLOPS 和 ratio 可追踪 |
| `README.md` | 实验协议、layout、baseline 边界和差距解释可读 |

如果某个文件不能对应一个验收问题，先不要急着加。Day 7 的目标是闭环，不是堆结构。

---

## 3. 最终 checklist

完整验收至少包括：

- [ ] 能跑 `cublasSgemm`。
- [ ] 能跑 `cublasHgemm` 或 `cublasGemmEx`。
- [ ] 同 shape 记录 cuBLAS 时间。
- [ ] 使用 CUDA event 计时。
- [ ] 明确排除 H2D / D2H 时间。
- [ ] 理解并实现 row-major wrapper。
- [ ] benchmark 覆盖方阵、非方阵和常规大尺寸。
- [ ] correctness 对拍通过。
- [ ] README 解释 Tensor Core 可能被 cuBLAS 使用。
- [ ] README 解释“打不过 cuBLAS 不是失败”。

其中前三项证明 baseline 能跑；中间几项证明实验可信；最后两项证明你能解释结果。

### 3.1 验收顺序

建议按这个顺序验收：

```text
1. correctness
2. timing
3. benchmark.csv
4. README
5. 复盘差距来源
```

不要先写 README 再回头补 correctness。更稳的顺序是：

- 先确认结果对。
- 再确认计时范围公平。
- 再把结果写入 CSV。
- 再把实验协议写进 README。
- 最后解释和 cuBLAS 的差距。

> [!tip] 验收不是一次跑完
> Day 7 可以分多轮修正。只要每轮都沿着 correctness -> timing -> CSV -> README 的方向收敛，就不会把错结果包装成漂亮报告。

## 4. 最低 benchmark 组合

最低 benchmark 组合建议：

| dtype | shape | implementation |
|---|---|---|
| FP32 | 512x512x512 | custom CUDA + cuBLAS SGEMM |
| FP32 | 1024x1024x1024 | custom CUDA + cuBLAS SGEMM |
| FP32 | 257x509x1024 | custom CUDA + cuBLAS SGEMM |
| FP16 | 1024x1024x1024 | cuBLAS HGEMM or GemmEx |

为什么保留 `257x509x1024`：

```text
非方阵更容易暴露 M/N/K、lda/ldb/ldc、row-major wrapper 是否写反。
```

为什么保留 FP16：

```text
它让你能进入 HGEMM / GemmEx 和 Tensor Core 解释，不只停留在 FP32 baseline。
```

---

## 5. README 最终检查

README 最后要能回答这些问题：

- 你用 cuBLAS 做什么 baseline？
- SGEMM 和 HGEMM 分别是什么 dtype？
- row-major wrapper 为什么交换 A/B？
- benchmark 是否排除了数据拷贝？
- TFLOPS 怎么算？
- ratio vs cuBLAS 怎么定义？
- FP16 cuBLAS 为什么可能非常快？
- 为什么打不过 cuBLAS 不是失败？

如果 README 能让陌生读者快速理解这些问题，Day 7 就不是形式验收，而是完成了项目叙事。

---

## 6. 常见坑

- benchmark.csv 有数据，但 README 没解释实验协议。
- README 写了实验协议，但 CSV 缺少 dtype、layout 或 correct 字段。
- 只跑方阵，layout bug 没暴露。
- FP16 结果没有说明 compute type。
- 只说 cuBLAS 快，没有解释 Tensor Core、库级 tiling 和调度差距。
- 过早展开 cuBLASLt、batched GEMM 或复杂 autotune，反而让普通 cuBLAS baseline 不稳定。

---

## 7. 完整验收输出

最终可以用这段话作为验收总结：

```text
This project uses cuBLAS as the vendor-optimized GEMM baseline.
It supports SGEMM and HGEMM/GemmEx benchmarks, uses CUDA events for GEMM-only timing,
records correctness and TFLOPS for each shape, and explains the performance gap
with layout, tiling, memory reuse, and possible Tensor Core paths.
```

中文版本：

```text
本项目用 cuBLAS 作为工业级 GEMM baseline。
实验覆盖 SGEMM 和 HGEMM/GemmEx，使用 CUDA event 只测 GEMM 本体，
按 shape 记录 correctness、耗时、TFLOPS 和 ratio，并在 README 中解释
row-major wrapper、Tensor Core 可能路径以及手写 kernel 与 cuBLAS 的性能差距。
```

### 7.1 最终交付包检查

最终交付前，建议确认：

- [ ] 代码能从干净构建目录编译。
- [ ] `benchmark.csv` 包含 SGEMM 和 HGEMM / GemmEx 的关键结果。
- [ ] 每条 benchmark 都有 `correct` 或误差记录。
- [ ] README 说明 GPU、CUDA/cuBLAS 版本和关键 shape。
- [ ] README 说明 row-major wrapper。
- [ ] README 说明 timing 排除 H2D / D2H。
- [ ] README 说明 cuBLAS 是 baseline，不是必须战胜的目标。
- [ ] README 有一段明确的性能差距复盘。

这份检查不是为了增加形式，而是让项目可以被别人复现、阅读和追问。
