## 1. Day 5 要解决什么

目标可以压成一句话：

```text
能解释 cuBLAS HGEMM baseline 可能使用 Tensor Core，因此它不是普通 CUDA core baseline。
```

Day 5 的任务不是背硬件细节，而是把比较边界讲清楚：

- FP32 naive CUDA vs cuBLAS SGEMM 可以作为粗 baseline。
- FP32 tiled CUDA vs cuBLAS SGEMM 更有参考价值。
- 手写 FP32 kernel vs cuBLAS HGEMM 不是同 dtype、同路径对比。

> [!important] 第一层直觉
> cuBLAS 是工业库 baseline。它可能根据 dtype、shape、硬件和版本自动选择高性能 kernel。你要解释差距，而不是把差距简单写成“我的 kernel 太慢”。

---

## 2. Tensor Core 的最小直觉

Tensor Core 是 NVIDIA GPU 上专门加速矩阵乘法的一类硬件单元。入门阶段可以先记成：

```text
Tensor Core 更擅长低精度矩阵乘法和混合精度累加。
```

常见相关 dtype：

- FP16
- BF16
- TF32

Tensor Core 从 Volta，也就是 compute capability 7.0 及以上 GPU 开始引入。不同架构、不同 CUDA / cuBLAS 版本支持和选择的路径会有差异。

### 2.1 能说与不能说

Day 5 的表达要稳。没有 profiler 或 kernel 名称证据时，可以说：

```text
cuBLAS may use Tensor Core kernels for eligible HGEMM cases.
```

不要直接说：

```text
This HGEMM run used Tensor Core.
```

更安全的判断边界是：

| 证据 | 可以怎么说 |
|---|---|
| 只知道用了 `cublasHgemm` | cuBLAS 可能选择 Tensor Core 路径 |
| 记录了 dtype / shape / GPU 架构 | 这个 case 具备 Tensor Core 相关条件 |
| profiler 显示 Tensor Core 指令或 kernel | 这次运行可以更明确地说明使用了 Tensor Core 路径 |

> [!warning] 不要把“可能”写成“必然”
> Day 5 的目标是解释 baseline 边界，不是证明每一次 HGEMM 都一定走 Tensor Core。

---

## 3. cuBLAS 为什么可能走 Tensor Core

cuBLAS 不只是一个简单函数包装。调用 `cublasHgemm` 或某些 `cublasGemmEx` 配置时，cuBLAS 可能在内部选择 Tensor Core kernel。

这意味着：

```text
cuBLAS HGEMM 可能同时享受：
低精度输入
高吞吐矩阵乘法硬件
成熟的 tile / warp / instruction 调度
多年库级优化
```

所以报告里不能把它写成：

```text
我的 naive CUDA kernel 只比 cuBLAS 慢很多。
```

更好的写法是：

```text
cuBLAS may use Tensor Core kernels for eligible HGEMM cases.
Therefore, cuBLAS HGEMM is a vendor-optimized mixed-precision baseline,
not a plain CUDA-core implementation.
```

## 4. 哪些因素影响路径

cuBLAS 是否选择 Tensor Core、以及路径是否高效，常受这些因素影响：

| 因素 | 影响 |
|---|---|
| GPU 架构 | Volta 及以上才有 Tensor Core 路径基础 |
| dtype | FP16 / BF16 / TF32 更可能走 Tensor Core |
| compute type | 是否允许混合精度累加 |
| shape | 某些尺寸更适合高效 tile |
| alignment | 数据对齐会影响高性能路径 |
| CUDA / cuBLAS 版本 | kernel selection 可能变化 |

这里的重点不是立刻掌握全部规则，而是知道 benchmark 结果不是只由你传了哪个 API 决定。

### 4.1 最小环境记录表

为了让 Tensor Core 解释有上下文，建议 benchmark 或 README 至少记录：

| 字段 | 示例 | 用途 |
|---|---|---|
| GPU | RTX 4090 / A100 / T4 | 判断硬件架构背景 |
| compute capability | 8.9 / 8.0 / 7.5 | 判断 Tensor Core 能力代际 |
| CUDA version | 12.x | 解释 runtime 和工具链背景 |
| cuBLAS version | 12.x | 解释库级 kernel selection 可能变化 |
| API | `cublasHgemm` / `cublasGemmEx` | 说明调用入口 |
| dtype | FP16 / BF16 / TF32 / FP32 | 说明是否是 Tensor Core 相关 dtype |
| compute type | FP16 / FP32 accumulate | 说明混合精度路径 |
| shape | M/N/K | 说明 tile 和 alignment 背景 |

不需要 Day 5 就做复杂 profiling，但这些字段能让你的解释从“听说 cuBLAS 很快”变成“这个实验环境下 cuBLAS baseline 为什么可能强”。

## 5. 报告里怎么解释

可以把对比拆成三类：

| 对比 | 是否公平 | 应该怎么解释 |
|---|---|---|
| naive CUDA vs cuBLAS FP32 | 可作为粗 baseline | 解释访存和 tiling 差距 |
| tiled CUDA FP32 vs cuBLAS SGEMM | 更有参考价值 | 解释库级优化和调度差距 |
| hand-written FP32 vs cuBLAS HGEMM | 不同 dtype / 路径 | 必须说明 Tensor Core 可能参与 |

README 可以放一段固定说明：

```text
cuBLAS may use Tensor Core kernels for eligible GEMM cases.
For FP16 / HGEMM, cuBLAS can use highly optimized Tensor Core paths.
Matching or beating cuBLAS is not expected for a learning kernel.
The goal is to measure the gap and explain where it comes from.
```

### 5.1 对比话术模板

FP32 SGEMM 对比可以写：

```text
For FP32 GEMM, cuBLAS SGEMM is used as the vendor-optimized baseline.
The gap mainly reflects library-level tiling, scheduling, memory reuse,
and other mature optimizations beyond the learning kernel.
```

FP16 HGEMM 对比可以写：

```text
For FP16 GEMM, cuBLAS HGEMM may use Tensor Core kernels when the case is eligible.
Therefore, this result should be interpreted as a mixed-precision vendor baseline,
not as a plain CUDA-core implementation.
```

GemmEx / mixed precision 对比可以写：

```text
For GemmEx, input dtype, output dtype, and compute type are recorded explicitly.
This avoids mixing FP16 input, FP32 accumulation, and FP16 output cases under one vague label.
```

中文报告可以写：

```text
本实验把 cuBLAS 作为工业级 baseline，而不是必须战胜的目标。
FP16 / HGEMM 场景下，cuBLAS 在符合条件时可能选择 Tensor Core 路径。
因此性能差距应结合 dtype、compute type、shape、GPU 架构和库级优化解释。
```

## 6. 常见坑

- 把 FP32 custom kernel 和 FP16 cuBLAS HGEMM 直接放在一起说“同类比较”。
- benchmark 表里没有写 dtype、compute type 和 API。
- 只说 Tensor Core 很快，但没有说明它是否只是“可能使用”。
- 不记录 GPU 架构和 CUDA / cuBLAS 版本。
- 把“打不过 cuBLAS”写成失败，而不是写成 baseline 差距分析。

> [!warning] 说法要稳
> 如果没有用 profiler 或日志确认具体 kernel，不要断言“这次一定用了 Tensor Core”。更稳的表达是：cuBLAS 在符合条件时可能选择 Tensor Core 路径。

## 7. 当天验收标准

Day 5 结束时，至少要做到：

- [ ] 能说明 Tensor Core 从 Volta 及以上 GPU 开始引入。
- [ ] 能说明 FP16 / BF16 / TF32 更可能相关。
- [ ] 能说明 shape、alignment、compute type 和版本会影响路径。
- [ ] README 或实验记录包含 GPU、CUDA/cuBLAS 版本、dtype、compute type 和 shape。
- [ ] README 解释 cuBLAS HGEMM 可能使用 Tensor Core。
- [ ] 报告里不把 FP32 custom kernel 和 HGEMM 当成同类实现直接比较。

验收输出可以写成：

```text
cuBLAS HGEMM may use Tensor Core kernels.
This baseline is vendor-optimized and may differ from a plain CUDA-core path.
The performance gap is expected and should be explained.
```
