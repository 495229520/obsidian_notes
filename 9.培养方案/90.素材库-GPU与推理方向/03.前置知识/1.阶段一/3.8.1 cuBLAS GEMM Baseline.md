## 阅读说明

这篇笔记的目标不是“完整掌握 cuBLAS 全家桶”，而是让你能把 cuBLAS 作为 GEMM baseline 放进 [[Week 4 - MatMul v0]] 和 `matmul-lab-cuda-triton-cutlass`。如果时间紧，先完成 Day 1 到 Day 3；如果要写进作品集，再补 Day 4 到 Day 7。

---

> [!important] 第一层直觉
> cuBLAS 是 NVIDIA 的 BLAS GPU 实现。你在这里要学会的是：用 `cublasSgemm` / `cublasHgemm` / `cublasGemmEx` 给自己的 GEMM 实现建立可信 baseline，并能解释性能差距来自哪里。

---

## 1. 学习目标和边界

本阶段 cuBLAS 的学习目标应该定成：

```text
会把 cuBLAS 作为 GEMM baseline。
```

而不是：

```text
完整掌握 cuBLAS 全家桶。
```

你需要会的内容很集中：

- `cublasCreate / cublasDestroy`：创建和销毁 cuBLAS handle。
- `cublasSgemm`：跑 FP32 GEMM baseline。
- `cublasHgemm`：跑 FP16 GEMM baseline。
- `cublasGemmEx`：显式控制输入类型、输出类型、compute type 和算法。
- CUDA event timing：只测 GEMM 本身，不把 H2D / D2H 混进去。
- row-major wrapper：处理 C/C++ row-major 和 cuBLAS column-major 的差异。
- Tensor Core 解释：知道 cuBLAS 可能走 Tensor Core 路径。
- README baseline 表达：说明“打不过 cuBLAS 不是失败”。

cuBLAS 的 GEMM 形式可以先记成：

```text
C = alpha * op(A) * op(B) + beta * C
```

这里 `op(A)` 和 `op(B)` 可以是不转置、转置或共轭转置。入门阶段先把 `CUBLAS_OP_N` 和 row-major wrapper 搞清楚，再考虑更复杂的转置组合。

---

## 2. 总学习时间

如果你已经会 CUDA kernel、`cudaMalloc`、`cudaMemcpy` 和 CUDA event 计时：

```text
5 到 7 天，约 15 到 25 小时。
```

如果 CUDA 还不熟：

```text
2 到 3 周。
```

如果目标只是“项目里能跑 cuBLAS baseline”：

```text
3 到 4 天可以完成最小可用版。
```

时间分配建议：

| 目标 | 时间 | 做到什么程度 |
|---|---:|---|
| 最小可用 baseline | 3-4 天 | SGEMM、row-major wrapper、CUDA event timing、benchmark.csv |
| 作品集可解释版本 | 5-7 天 | 加 HGEMM / GemmEx、Tensor Core 解释、README baseline 说明 |
| CUDA 同步补课版 | 2-3 周 | 同时补 CUDA memory、event、stream、correctness test |

## 3. Day 1：cuBLAS 基础和 SGEMM 跑通

目标：先让 `cublasSgemm` 正确跑起来。

最小 API 形状：

```cpp
cublasHandle_t handle;
cublasCreate(&handle);

cublasSgemm(
    handle,
    CUBLAS_OP_N, CUBLAS_OP_N,
    m, n, k,
    &alpha,
    A, lda,
    B, ldb,
    &beta,
    C, ldc
);

cublasDestroy(handle);
```

当天要学会：

- cuBLAS 程序需要链接 cuBLAS 库。
- `cublasHandle_t` 表示 cuBLAS 上下文。
- `cublasSgemm` 是 FP32 GEMM。
- `m / n / k` 描述 cuBLAS 视角下的矩阵维度。
- `lda / ldb / ldc` 是 leading dimension，不是随便填的 stride。

当天产出：

- 能编译链接 cuBLAS。
- 能跑一个 `float32` GEMM。
- 能用 CPU、PyTorch 或 NumPy 对拍结果。
- 能记录 `M / N / K / dtype / time / TFLOPS`。

验收标准：

```text
SGEMM result correct
shape = M x N x K
cuBLAS time = xxx ms
TFLOPS = xxx
```

> [!tip] Day 1 不追求快
> 第一天的重点是“跑通并对拍正确”。只要结果正确、参数解释得清楚，性能慢一点也没关系。

## 4. Day 2：column-major 和 row-major

这是 cuBLAS 最容易踩坑的地方。

cuBLAS 默认按 **column-major** 解释矩阵；C / C++ 里你通常按 **row-major** 写矩阵。官方文档也说明，cuBLAS 为了兼容 Fortran 环境使用 column-major，C/C++ 用户需要自己处理二维数组语义差异。

C/C++ row-major 常见下标：

```cpp
A[row, col] -> A[row * width + col]
```

cuBLAS column-major 常见下标：

```cpp
A[row, col] -> A[col * leading_dim + row]
```

如果你想在 row-major 语义下计算：

```text
C[M, N] = A[M, K] @ B[K, N]
```

一种常见做法是利用转置等价关系，在 cuBLAS 中交换 A / B：

```cpp
// row-major A[M,K], B[K,N], C[M,N]
// viewed by cuBLAS as column-major:
// C^T[N,M] = B^T[N,K] @ A^T[K,M]

cublasSgemm(
    handle,
    CUBLAS_OP_N, CUBLAS_OP_N,
    N, M, K,
    &alpha,
    B, N,
    A, K,
    &beta,
    C, N
);
```

当天产出：

- 写清楚 row-major wrapper。
- 同一个 shape 下验证 row-major wrapper 结果正确。
- README 解释为什么 cuBLAS 参数里是 `N, M, K`，而不是 `M, N, K`。

验收 shape 不要只用方阵：

```text
M = 257
N = 509
K = 1024
```

> [!warning] 方阵会骗你
> 只测 `1024 x 1024 x 1024` 很容易掩盖 layout 错误。非方阵更容易暴露 `M / N / K`、`lda / ldb / ldc` 是否写反。

## 5. Day 3：benchmark 框架

目标：同 shape 下公平比较你的 kernel 和 cuBLAS。

CUDA event 可以记录 GPU 时间线上的事件，`cudaEventElapsedTime` 计算两个 event 之间的 elapsed time，返回毫秒。这里用它测 GEMM 本身的 GPU 时间。

建议计时方式：

```text
warmup: 10 次
repeat: 100 次
time: 取 median 或 min
scope: 只测 kernel / GEMM 本身，不测 H2D / D2H
record: 每个 shape 单独记录 cuBLAS 时间
```

你要记录：

```text
M, N, K
dtype
layout
your_kernel_ms
cublas_ms
your_TFLOPS
cublas_TFLOPS
ratio = your_time / cublas_time
```

TFLOPS 计算：

```text
FLOPs = 2 * M * N * K
TFLOPS = FLOPs / time_seconds / 1e12
```

当天产出：

```text
bench_sgemm.cu
benchmark.csv
README 里有性能表格
```

表格模板：

| M | N | K | dtype | layout | implementation | ms | TFLOPS | ratio vs cuBLAS |
|---:|---:|---:|---|---|---|---:|---:|---:|
| 512 | 512 | 512 | FP32 | row-major wrapper | tiled CUDA |  |  |  |
| 512 | 512 | 512 | FP32 | row-major wrapper | cuBLAS SGEMM |  |  | 1.00 |

## 6. Day 4：HGEMM / GemmEx

目标：学会 half precision GEMM，并知道什么时候该用 `cublasGemmEx`。

### 方式 A：`cublasHgemm`

`cublasHgemm` 适合直接跑 FP16 输入、FP16 输出。它仍然是 GEMM 形式：

```text
C = alpha * op(A) * op(B) + beta * C
```

你可以先把它当作 HGEMM 最小入口：

```cpp
cublasHgemm(...);
```

### 方式 B：`cublasGemmEx`

后续更推荐逐步过渡到 `cublasGemmEx`，因为它可以显式指定：

- A / B 的数据类型。
- C 的数据类型。
- compute type。
- GEMM algorithm。

你应该至少跑这两类实验：

```text
FP16 input, FP16 output
FP16 input, FP32 accumulate, FP16 or FP32 output
```

当天产出：

- `bench_hgemm.cu`
- 至少 3 个 shape 的 HGEMM benchmark。
- README 写清楚：SGEMM 是 FP32，HGEMM 是 FP16。
- 如果使用 `GemmEx`，明确记录 input dtype、output dtype 和 compute type。

## 7. Day 5：Tensor Core 解释

你不需要在这个阶段手写 Tensor Core，但必须能解释：

```text
为什么 cuBLAS 的 HGEMM 可能非常快？
```

Tensor Core 从 Volta，也就是 compute capability 7.0 及以上 GPU 开始引入，用于加速矩阵乘法。cuBLAS 在合适条件下可能自动选择 Tensor Core 实现；是否使用会受到 dtype、compute type、shape、alignment、GPU 架构和 cuBLAS 版本影响。

README 可以这样写：

```text
cuBLAS may use Tensor Core kernels for eligible GEMM cases.
Therefore, cuBLAS is not just a simple CUDA-core baseline.
For FP16 / HGEMM, cuBLAS can use highly optimized Tensor Core paths,
so matching or beating cuBLAS is not expected for a learning kernel.
```

还要知道：

- FP16 / BF16 / TF32 更可能走 Tensor Core。
- shape 和 alignment 会影响 Tensor Core 路径是否高效。
- 不同 CUDA / cuBLAS 版本可能选择不同实现。
- 不要直接把 naive CUDA kernel 和 Tensor Core cuBLAS 当成“同等实现”比较。

报告里建议拆成两层：

| 对比 | 是否公平 | 应该怎么解释 |
|---|---|---|
| naive CUDA vs cuBLAS FP32 | 可作为粗 baseline | 解释访存和 tiling 差距 |
| tiled CUDA FP32 vs cuBLAS SGEMM | 更有参考价值 | 解释库级优化和调度差距 |
| hand-written FP32 vs cuBLAS HGEMM | 不同 dtype / 路径 | 必须说明 Tensor Core 可能参与 |

## 8. Day 6：README 和实验规范

README 至少写这些块：

```markdown
## cuBLAS Baseline

We use cuBLAS as the vendor-optimized GEMM baseline.

### APIs

- SGEMM: cublasSgemm
- HGEMM: cublasHgemm or cublasGemmEx

### Layout

cuBLAS assumes column-major matrices.
Our project stores matrices in row-major layout, so we call cuBLAS with swapped A/B.

### Timing

- warmup: 10 iterations
- repeat: 100 iterations
- timing: CUDA events
- data transfer excluded

### Why not beating cuBLAS is OK

cuBLAS is heavily optimized by NVIDIA and may use Tensor Cores.
The goal is to measure the gap and learn optimization techniques,
not necessarily to outperform cuBLAS.
```

中文报告可以写：

```text
cuBLAS 是工业级 GEMM baseline，不是必须战胜的目标。
本项目用 cuBLAS 校准同一 GPU、同一 dtype、同一 shape 下的参考性能。
手写 CUDA / Triton / CUTLASS 版本的价值在于解释性能差距来自哪里：
数据复用、访存合并、Tensor Core 路径、寄存器压力、occupancy 和边界处理。
```

这段非常重要。别人看到你的 README 时，要能立刻明白：

```text
你不是跑不过 cuBLAS。
你知道 cuBLAS 是工业级 baseline，并且知道自己在学习什么。
```

## 10. 推荐学习顺序

最合理顺序是：

```text
1. cublasCreate / cublasDestroy
2. cublasSgemm
3. CUDA event timing
4. row-major wrapper
5. cublasHgemm
6. cublasGemmEx
7. Tensor Core 解释
8. README baseline 说明
```

一周安排可以压缩成：

```text
第 1-2 天：SGEMM + row-major / column-major
第 3 天：benchmark 框架
第 4 天：HGEMM / GemmEx
第 5 天：Tensor Core 解释
第 6 天：README + 表格
第 7 天：清理代码、补充实验
```

学到这个程度就够了：

```text
你能把 cuBLAS 作为可信 baseline，并且能解释性能差距来自哪里。
```

## 11. 暂时不要展开的内容

暂时不要一上来学：

```text
cuBLASLt
batched GEMM
strided batched GEMM
FP8 / INT8 GEMM
复杂 autotune
```

cuBLASLt 很有用，尤其适合更灵活的数据布局、输入类型、计算类型、算法选择和 heuristics。但它应该放在普通 cuBLAS baseline 稳定之后再学。

这篇笔记的边界是：

```text
普通 cuBLAS GEMM baseline 先稳定。
再考虑 cuBLASLt 和更复杂 GEMM 路线。
```
