## 1. 先分清三件事

做 CUDA reduction 性能分析时，最容易把下面三件事混在一起：

| 名称 | 回答的问题 | 典型工具 |
|---|---|---|
| correctness check | 算得对不对？ | CPU reference、误差检查 |
| benchmark | 跑得多快？ | CUDA event |
| profiling | 为什么快或慢？ | Nsight Compute |

判断顺序必须是：

```text
correctness check 通过
-> CUDA event benchmark 得到可信时间
-> Nsight Compute 解释瓶颈
-> 写 profiling.md
```

如果 `Check = FAIL`，后面的耗时再快也不能用。因为错误的 kernel 可能少算了一部分数据，当然会显得更快。

---

## 2. benchmark 为什么必须带 Check

错误的 reduction 很可能有这些问题：

- 最后一个 block 的越界数据没有处理好。
- block 内少了一次 `__syncthreads()`。
- 只算了每个 block 的 partial sum，没有做第二阶段汇总。
- warp shuffle 的 mask 或活跃线程范围写错。
- 浮点误差检查用 `==`，导致正确结果被误判。

如果 benchmark 只打印：

```text
Version    N    Kernel(ms)
shared     1M   0.031
```

这个数字看起来很好，但无法判断它到底是“优化成功”，还是“少算了数据”。所以输出至少要包含：

```text
Version    N    Kernel(ms)    GB/s    Check
shared     1M   0.031         270.6   PASS
```

> [!important] 规则
> `Check = FAIL` 的性能数据不能进入最终结论，只能作为 debug 线索。

## 3. 一个完整 benchmark 应该怎么做

Week 2 的 benchmark 可以按这个流程写：

```text
1. 准备输入数据 input
2. CPU 上算 reference
3. GPU 上运行某个 reduction kernel
4. 把 GPU 结果拷回 host
5. 用 tolerance 检查 GPU result 和 CPU reference
6. warm-up 几次
7. 用 CUDA event 计时 repeat 多次
8. 打印平均耗时、最小耗时、有效带宽、Check
```

其中 warm-up 的作用是让第一次运行的额外开销不污染结果。第一次 kernel launch 可能包含上下文初始化、缓存状态变化等，不适合作为稳定性能数字。

### 3.1 CUDA event 计时骨架

CUDA event 适合测 GPU kernel 在 device 上的执行时间。典型代码形状如下：

```cpp
cudaEvent_t start, stop;
cudaEventCreate(&start);
cudaEventCreate(&stop);

for (int i = 0; i < warmup; ++i) {
    reduce_kernel<<<grid, block, shared_bytes>>>(d_input, d_partial, n);
}
cudaDeviceSynchronize();

float total_ms = 0.0f;
float min_ms = 1e30f;

for (int i = 0; i < repeat; ++i) {
    cudaEventRecord(start);
    reduce_kernel<<<grid, block, shared_bytes>>>(d_input, d_partial, n);
    cudaEventRecord(stop);

    cudaEventSynchronize(stop);

    float ms = 0.0f;
    cudaEventElapsedTime(&ms, start, stop);
    total_ms += ms;
    min_ms = std::min(min_ms, ms);
}

float avg_ms = total_ms / repeat;
```

这里的重点不是背 API，而是理解边界：

- `cudaEventRecord(start)` 放在 kernel 前。
- `cudaEventRecord(stop)` 放在 kernel 后。
- `cudaEventSynchronize(stop)` 保证 stop event 已经完成。
- `cudaEventElapsedTime` 得到的是两个 event 之间的 GPU 时间。

### 3.2 为什么不要把 cudaMemcpy 混进 kernel 时间

如果目标是比较 `naive reduce`、`shared memory reduce`、`warp shuffle reduce` 的 kernel 性能，计时范围最好只包 kernel。

否则你测到的是：

```text
host/device copy + kernel + result copy
```

这会让 kernel 之间的差异被拷贝时间淹没。拷贝时间当然也重要，但那是另一个问题，应该单独测。

### 3.3 effective bandwidth 怎么算

reduction 常常是 memory-bound，所以 benchmark 里通常会打印有效带宽：

```text
GB/s = bytes_read_or_written / kernel_time
```

对最简单的 sum reduction，可以先粗略按读输入计算：

```cpp
double bytes = static_cast<double>(n) * sizeof(float);
double gb_per_s = bytes / (avg_ms / 1000.0) / 1e9;
```

如果某个版本还会写大量中间结果，就应该把主要写入流量也算进去。这里先保持一个简单口径，关键是不同版本必须用同一个口径比较。

## 4. 最小 benchmark matrix 怎么设计

主笔记里的最小矩阵是：

| Version | N | Kernel(ms) | GB/s | Check |
|---|---:|---:|---:|---|
| naive partial reduce | 1K |  |  |  |
| naive partial reduce | 1M |  |  |  |
| naive partial reduce | 64M |  |  |  |
| shared memory reduce | 1K |  |  |  |
| shared memory reduce | 1M |  |  |  |
| shared memory reduce | 64M |  |  |  |
| warp shuffle reduce | 1K |  |  |  |
| warp shuffle reduce | 1M |  |  |  |
| warp shuffle reduce | 64M |  |  |  |

这张表的目的不是把数字填满，而是强迫自己做到公平比较：

- 同一组输入规模。
- 同一个 CPU reference。
- 同一个 tolerance。
- 同一个 warm-up 次数。
- 同一个 repeat 次数。
- 同一个 GB/s 计算口径。

`1K` 可以暴露 launch overhead 和小规模不稳定性；`1M` 适合观察常规规模；`64M` 更容易把 memory bandwidth 和同步开销拉开。

## 5. benchmark 输出应该长什么样

建议输出格式固定，后面写 `profiling.md` 会轻松很多：

```text
Version               N          Avg(ms)    Min(ms)    GB/s     Check
naive partial reduce  1024       0.012      0.011      0.34     PASS
naive partial reduce  1048576    0.210      0.205      19.97    PASS
shared memory reduce  1048576    0.058      0.056      72.34    PASS
warp shuffle reduce   1048576    0.045      0.044      93.21    PASS
```

这里 `Avg(ms)` 代表稳定平均水平，`Min(ms)` 代表最理想的一次。写报告时通常优先用 avg，但如果 avg 和 min 差距很大，要回头检查 repeat、系统负载、输入规模是否合理。

## 6. 什么时候开始 profiling

不要一上来就打开 Nsight Compute。更好的顺序是：

```text
先跑 correctness
-> 再跑 benchmark matrix
-> 找出差异明显的版本和 N
-> 只挑代表性 case 跑 Nsight Compute
```

例如 benchmark 显示：

```text
shared memory reduce 比 naive 快很多
warp shuffle reduce 比 shared memory 又快一点
```

这时可以挑 `N = 64M` 的三个版本跑 Nsight Compute，看看差异来自哪里：

- global memory 访问是否减少。
- achieved occupancy 是否变化。
- warp stall reason 是否从 memory dependency 变成 barrier 或 instruction dependency。
- shared memory 和 register 使用是否限制了并发 block 数。

---

## 7. Nsight Compute 应该看什么

Week 2 不需要一开始就读懂所有 Nsight 指标。先盯住这几类就够：

| 指标类型 | 你要问的问题 | 常见解释 |
|---|---|---|
| memory throughput | global memory 有没有接近带宽上限？ | 高吞吐可能说明 memory-bound |
| achieved occupancy | SM 上是否有足够多 warp 可运行？ | 太低可能被寄存器、shared memory、block size 限制 |
| warp stall reason | warp 主要在等什么？ | 可能在等内存、同步、指令依赖 |
| shared memory usage | 每个 block 用了多少 shared memory？ | 用太多会降低并发 block 数 |
| register count | 每个线程用了多少寄存器？ | 寄存器太多会压低 occupancy |

要注意：指标本身不是结论。指标只是证据。结论要写成：

```text
shared memory 版本比 naive 快，因为它减少了 global memory 中间访问；
benchmark 中耗时下降，Nsight 中 memory 相关 stall 降低，支持这个判断。
```

## 8. profiling.md 证据模板

`profiling.md` 不应该只是截图集合。建议每个 kernel 版本都用固定结构记录：

```text
Kernel:
Shape:
GPU:
CUDA:
Command:

Benchmark:
- Avg time:
- Min time:
- Effective bandwidth:
- Check:

Nsight key metrics:
- Memory throughput:
- Achieved occupancy:
- Top warp stall reason:
- Shared memory per block:
- Register count per thread:

Conclusion:

Next optimization:
```

### 8.1 示例

```text
Kernel:
shared memory reduce

Shape:
N = 67108864, blockDim = 256

Benchmark:
- Avg time: 0.62 ms
- Min time: 0.60 ms
- Effective bandwidth: 432 GB/s
- Check: PASS

Nsight key metrics:
- Memory throughput: high, close to expected device bandwidth range
- Achieved occupancy: acceptable
- Top warp stall reason: memory dependency
- Shared memory per block: moderate
- Register count per thread: not the main limiter

Conclusion:
shared memory reduce is faster than naive partial reduce on this shape.
The benchmark shows lower kernel time, and Nsight suggests the main pressure
is still global memory movement rather than synchronization.

Next optimization:
Try warp shuffle inside each warp to reduce shared memory traffic and
block-level synchronization.
```

这里的数字只是示例。真正写 Week 2 报告时，要用自己机器上跑出来的数据。

## 9. 常见坑

| 坑 | 后果 | 修正 |
|---|---|---|
| 不保留 Check | 错误 kernel 看起来更快 | 每行 benchmark 都打印 PASS / FAIL |
| 没有 warm-up | 第一次运行污染平均时间 | 正式计时前先跑几次 |
| repeat 太少 | 数据波动大 | 至少重复多次并打印 avg / min |
| 把 memcpy 混进 kernel 时间 | kernel 差异被拷贝时间掩盖 | kernel-only 和 end-to-end 分开测 |
| 不固定输入规模 | 不同版本不可比 | 使用同一组 N |
| profiler 代替 benchmark | 只有解释，没有事实 | 先用 CUDA event 建立时间事实 |
| Check 失败还写性能结论 | 结论无效 | 先修 correctness |

---

## 10. 一句话总纲

CUDA reduction 的性能分析顺序是：

```text
算对
-> 用 CUDA event 稳定测快慢
-> 用 Nsight Compute 解释为什么
-> 在 profiling.md 中把结论、证据、下一步写清楚
```

其中 `Check` 是门票，benchmark 是事实，profiler 是解释。
