## 取舍

### 主线，面试前必须形成证据

- Linux I/O、Page Cache、Direct I/O、持久化语义、io_uring 和性能观测。
- 存储引擎中的 WAL、恢复、校验、group commit、读写放大和压测方法。
- NVMe 的队列模型、SSD 的 FTL/GC、NUMA 和 PCIe 数据路径。
- 高性能网络的 RDMA 基础、RoCE 约束、NVMe-oF 的 TCP 与 RDMA 取舍。
- AI 存储场景中的训练数据加载、checkpoint 和 KV cache offload。重点是数据路径与成本，不是手写 CUDA kernel。

### 只保温，不另开项目

- vLLM/serving 的吞吐、TTFT、TPOT、KV cache 生命周期。
- CUDA Stream、Pinned Memory、GDS 的前提与回退路径。
- Agent 工具用于写测试、复现实验和审查结果。它不是当前的 Agent Infra 学习线。

### 面试前冻结

- GEMM、CUTLASS、FlashAttention、编译器和完整 GPU kernel 路线。
- Ceph/3FS 源码深读、多 Raft 分布式存储实现、Kubernetes Operator 和控制面项目。
- 需要真实 RDMA/GPU/GDS 环境才能证明的性能项目。没有硬件就记录语义、搭建 TCP 基线，不把软件模拟结果写成硬件性能结论。

## 项目上限

2027 暑期实习面试前，不承诺超过两个完整项目和一个交叉实验报告。

| 类型 | 交付 | 验收重点 |
| --- | --- | --- |
| 必做项目 1 | `linux-io-lab` 完整版 | buffered I/O、O_DIRECT、mmap、io_uring 的可复现实验；`fio`、`iostat`、`blktrace` 或 eBPF 证据；延迟分位数和故障定位 runbook。 |
| 必做项目 2 | `mini-kv-engine v1` | append log/WAL、校验、重放恢复、单 writer 或 group commit、崩溃注入、基准和设计说明。 |
| 交叉实验，不单独扩成大项目 | `nvme-of-lab` + AI 数据路径报告 | NVMe-oF/TCP 的可测基线；RDMA 对象模型和边界；把一个 checkpoint 或 KV cache offload 场景画成端到端数据路径。 |

GDS、LMCache、Mooncake、MLPerf Storage、Operator 和控制面属于后续解锁项。它们可以成为实习后的延伸，但不应抢走前两个项目的收口时间。

## 学习顺序

知识顺序与项目顺序不同。先掌握 Linux I/O 才能解释所有上层方案；`mini-kv-engine` 可以在深入 RDMA 前启动，以便在投递节点前拿到完整作品。

```text
性能与硬件基础
  -> Linux I/O 路径 + 观测
  -> io_uring
  -> 存储引擎与可靠性
  -> NVMe/SSD
  -> RDMA/RoCE
  -> NVMe-oF/SPDK
  -> AI GPU 数据路径

分布式存储架构阅读、控制面
  -> 面试后或明确匹配岗位时再进入
```

在 `8.高性能存储` 中，性能观测第 9 章从第一周就配合使用。第 7 章只做 JuiceFS、3FS 或 Ceph 的架构阅读；第 10 章默认不排期。

## 面试前的完成定义

- 两个项目都能在干净环境按文档复现，图表能追溯到原始数据和命令。
- 能从 `read()`、WAL 写入、NVMe 队列、RDMA 注册内存、NVMe-oF 到 GPU 数据搬运分别画出数据路径。
- 能明确说出哪些结论来自实测，哪些只是协议语义或硬件量级。
- 能解释一个 AI 场景的取舍：数据加载、checkpoint 或 KV cache offload 为什么会卡住 GPU，以及应该测什么。
