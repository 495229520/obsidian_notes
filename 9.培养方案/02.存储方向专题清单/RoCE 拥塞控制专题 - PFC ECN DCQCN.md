# RoCE 拥塞控制专题 - PFC ECN DCQCN

## 1. 第一环：RoCE 为什么怕丢包

RoCEv2 = IB 传输层封进 UDP 跑普通以太网。它的重传是网卡硬件实现的简化 **go-back-N**：丢一个包，从那个序号起的整个在途窗口全部重发——对比 TCP 的 SACK 精准补洞。高带宽下千分之一的丢包率就能把有效吞吐击穿。结论：RoCE 的性能前提是**网络基本不丢包**——"无损以太网"由此成为部署前提。

## 2. 第二环：PFC——不丢包的硬保证

PFC（Priority Flow Control，IEEE 802.1Qbb）：交换机某个优先级的入口缓冲逼近水线时，向**上游端口**发该优先级的 pause 帧，上游暂停发送直到解除。逐跳背压、缓冲不溢出、包不丢——机制本体就这一句。RDMA 流量被划进专门的优先级队列，PFC 只对它生效。

## 3. 第三环：PFC 的三个副作用（面试的分水岭）

1. **队头阻塞 / 受害者流**：pause 以优先级为粒度，同优先级里发往不拥塞方向的无辜流量陪着一起停。
2. **pause 风暴**：背压逐跳向上游传播——一个拥塞点可以让暂停帧波及一大片网络，拥塞被"扩散"而不是"解决"。
3. **PFC 死锁**：多台交换机的缓冲互相依赖成环（cyclic buffer dependency），谁都在等对方放行——极端但真实发生过的生产事故（微软的论文里有一手案例）。

一句话总结副作用：**PFC 把"丢包"换成了"停等的传染"**——救急可以，常态依赖它就是灾难。

## 4. 第四环：ECN + DCQCN——让 PFC 尽量不触发

思路：与其等缓冲满了硬刹车，不如提前轻点刹车。三个角色：

| 角色 | 谁 | 做什么 |
|---|---|---|
| CP（拥塞点） | 交换机 | 队列超阈值时给包打 ECN 标记（CE 位） |
| NP（通知点） | 接收端网卡 | 看到标记，向发送端回 CNP（拥塞通知包） |
| RP（反应点） | 发送端网卡 | 收到 CNP 按算法降速；之后快恢复 → 加性增 → 超增三阶段爬回 |

与 TCP 拥塞控制的三点不同（必考）：跑在**网卡硬件/固件**里不在内核；信号是显式的 **CNP** 不是丢包/RTT；调节的是**发送速率**不是窗口。

代价：**参数敏感**——ECN 水线、CNP 频率、速率恢复时间常数要按网络规模和流量形态调，调错要么欠吞吐要么压不住队列。这也是"RDMA 网络运维贵"的核心原因。

## 5. 第五环：分工总结

**DCQCN 做常态调速，把队列压在 PFC 水线之下；PFC 做最后防线，万一到线保证不丢。** 两者是纵深防御不是二选一——只有 PFC 会传染停等，只有 DCQCN 挡不住突发。现代 AI 集群的另一条路线是从根上减少拥塞（多路径/包喷洒、更激进的端侧调度），面试提一句表示视野即可。

## 6. 三分钟口述稿

```text
RoCEv2 的重传是硬件 go-back-N，丢一个包重发整个窗口，所以它的性能
前提是网络不丢包。第一道保证是 PFC：交换机缓冲到水线就向上游发
pause，逐跳背压保不丢。但 PFC 有三个著名副作用：按优先级粒度暂停
造成队头阻塞、背压逐跳传播形成 pause 风暴、极端情况下缓冲依赖成环
死锁——它把丢包换成了停等的传染。所以要 ECN 加 DCQCN 做常态调速：
交换机超阈值打 ECN 标记，接收端网卡回 CNP，发送端网卡降速再按快恢复、
加性增、超增爬回来——注意这套跑在网卡里、信号是显式 CNP、调的是
速率，三点都和 TCP 不同。分工是 DCQCN 把队列压在 PFC 水线之下，PFC
只当最后防线。它的代价是参数敏感、运维贵——这也是 NVMe-oF 选 TCP
还是 RDMA 的一部分账。边界我声明：概念和取舍我能推，真实交换机
没调过。
```

追问预案：

- "为什么不直接给 RoCE 做个 SACK？" → 精准重传需要网卡维护复杂的乱序缓冲与选择性确认状态，硬件成本高；新一代方案（如某些智能网卡/新传输协议）确实在往这个方向走——承认演进即可。
- "PFC 死锁的成环条件？" → 多交换机间该优先级的缓冲依赖构成环路（常由路由环路或故障重路由诱发），pause 相互等待——运维上靠拓扑设计与死锁检测规避。
- "ECN 水线怎么定？" → 太低误伤吞吐、太高来不及刹车，按 BDP 和流量突发度调——口述级答"存在这个权衡、参数要按规模标定"即可，不编数字。
- "你调过吗？" → 没有，我的 RDMA 实验在 soft-RoCE 上（没有真实交换机参与），这部分是概念级认知——主动声明边界。
