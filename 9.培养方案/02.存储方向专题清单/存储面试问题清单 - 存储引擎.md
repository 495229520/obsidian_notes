## Q1 介绍一下你的 KV 引擎的整体设计？为什么选 bitcask 模型？

**答案要点**：bitcask = 磁盘 append-only log + 内存 hash 索引：写永远顺序 append，读查索引后一次 pread——写吃满顺序带宽、读只有一跳。选它因为我的场景点查为主、key 集合装得进内存，而且 log 天然就是 WAL，crash consistency 从第一天就是对的。三个代价我都有对策：key 驻留内存（口算过上界）、启动重放（hint file 缓解）、空间放大（merge 回收）。

**证据**：[[S-Week 12 - mini-kv-engine v0 与 bitcask 模型]]；模型底稿 [[存储引擎专题 - bitcask 与哈希索引]]。

**追问预案**：
- "key 装不下内存怎么办？" → 换 LSM，索引分层下盘，代价是读放大。
- "为什么读只要一次 I/O？" → 索引存精确 (offset, size)，pread 直达，无树下探。

## Q2 你的 checksum 防的是哪类故障？防不了哪类？

**答案要点**：防"读出来 ≠ 写进去"：介质位翻转、torn write、错位读——每条记录 crc32c 覆盖除自身外全部字节，先校验后使用。防不了写之前就坏的数据（内存损坏、逻辑 bug）和整条记录干净消失。我用 5 类人工损坏样本（尾部截断、翻位、坏头、超长长度、清空）验证过恢复行为全部符合预期。

**证据**：[[S-Week 13 - checksum 与崩溃恢复]] 损坏注入矩阵；机制 [[存储引擎专题 - WAL 与 crash consistency]]。

**追问预案**：
- "为什么选 crc32c？" → SSE4.2 硬件加速、RocksDB 同款；对随机翻位检出率足够，不是密码学摘要也不需要是。
- "坏的是中间老记录怎么办？" → 读到它时报错返回；恢复扫描若截断中间会丢后面的好数据，所以只对尾部截断——中间损坏靠读路径校验兜底。

## Q3 崩溃发生在 log 写完但 index 没更新时怎么办？

**答案要点**：在我的引擎里这个窗口不存在危害——index 是内存结构，崩溃后本来就要靠重放 log 重建，log 里有这条就会被重建出来。真正要小心的窗口是"应答早于 fsync"：我的写路径固定为 append → fsync → 应答，顺序由单 writer 串行保证。RocksDB 的对应问题是"WAL 写完 memtable 没插入"，同样靠 WAL 重放解决——这正是 WAL 的定义性收益。

**证据**：[[S-Week 16 - 崩溃注入 1000 次]] 的不变量校验覆盖了该窗口。

**追问预案**：
- "怎么证明顺序没被编译器/CPU 重排？" → fsync 是系统调用，天然是顺序点；应答在 fsync 返回之后的程序顺序里，无需额外屏障。

## Q4 put 返回后掉电，数据还在吗？

**答案要点**：按持久化契约分三档答：always 档在——应答前已 fdatasync；everysec 档最多丢约 1 秒；os 档丢 writeback 窗口内全部。关键区分进程崩溃和断电：kill -9 三档都不丢（page cache 由内核善后），断电才按档位丢。我的契约矩阵把"策略 × 崩溃类型 → 丢多少"全部写死并用崩溃注入验证过。

**证据**：[[S-Week 14 - WAL 与 fsync 策略]] 契约矩阵；[[S-Week 2 - O_DIRECT + 持久化语义]] 的 fsync 家族数据。

**追问预案**：
- "fdatasync 和 fsync 差在哪？append 场景呢？" → 差非关键元数据；append 每笔改 size，两者几乎一样贵，预分配覆盖写才省。
- "rename 之后为什么还要 fsync 目录？" → 目录项的修改在目录文件里，不刷可能崩溃后看到旧目录内容。

## Q5 group commit 提升吞吐的代价是什么？为什么用单 writer？

**答案要点**：代价是每条请求的应答延迟里多了攒批等待——批越大吞吐越高、p50 越差，我有线程数 × 攒批开关的延迟-吞吐曲线。单 writer 是因为 append log 的 offset 分配必须串行：多 writer 抢锁把竞争放在文件上，单 writer + MPSC 队列把竞争移到内存，还让请求天然聚批。fsync=always 时吞吐从 1/t_fsync 变成 B/t_fsync，B 是每批条数。

**证据**：[[S-Week 15 - group commit 与多线程写入]] 消融曲线；对照 RocksDB write group。

**追问预案**：
- "攒批窗口怎么定？" → max_batch / max_wait 双条件先到先触发，扫过参数有数据。
- "等待线程怎么唤醒？" → 条件变量 + 批次世代号谓词，防虚假唤醒和错批唤醒。

## Q6 你怎么证明恢复代码是对的？

**答案要点**：自动化崩溃注入：父进程 fork 引擎子进程跑随机负载，随机时刻 kill -9，重启恢复后按 committed ⊆ recovered ⊆ attempted 三条不变量校验，fsync=always 下 1000 次零丢失。oracle 是父进程内存里的 committed 集合，经应答管道维护，不随子进程死。注入时刻覆盖四个危险窗口，失败样本连种子归档可复现。还挖出并修了真 bug，有完整记录。

**证据**：[[S-Week 16 - 崩溃注入 1000 次]]；`crash_bugs.md`。

**追问预案**：
- "1000 次都过 = 没 bug 吗？" → 不是，只是该注入分布下没观察到违例；补强方向是断电注入（dm-log-writes）和形式化。
- "kill -9 和断电差别？" → kill -9 后 page cache 数据内核仍会落盘，测不到"未 fsync 即丢"；断电语义我做了边界声明。

## Q7 LSM 为什么写快读慢？bloom filter 补救了什么？

**答案要点**：写快：关键路径只有 append WAL + 插 memtable，磁盘只做顺序写，随机更新被 memtable 合并。读慢：key 可能在 memtable 或任何一层 SSTable，逐层查即读放大。bloom filter 每 key 约 10 bit，把"肯定不在本文件"的判断留在内存，挡掉无效盘访问；有约 1% 误报（白读一次，不伤正确性），且救不了范围查询。

**证据**：[[LSM-tree 与 B+ tree 专题]]；DDIA 第 3 章。

**追问预案**：
- "leveled 和 tiered 怎么选？" → leveled 空间/读放大小写放大大，tiered 反之——按写读比例选。
- "写放大 10-30 倍怎么算的？" → 层容量 10 倍递增，每条数据平均逐层重写一次。

## Q8 你的引擎和 RocksDB 最大的差距是什么？

**答案要点**：按六维度对照：索引（我全内存 hash vs 分层 SSTable + block index）、WAL（合一 vs 独立可回收）、提交（单 writer vs write group）、恢复（全量扫描 vs WAL 重放 + MANIFEST）、空间回收（离线 merge vs 后台 compaction）、读优化（无需 vs bloom + block cache）。本质是我用"key 全驻内存"这一个假设换掉了 RocksDB 的大部分复杂度；假设不成立时，这六行就是要补的工程量。

**证据**：[[S-Week 17 - benchmark 与 design_note 收口]] 的差异表；`design_note.md`。

**追问预案**：
- "让你加范围查询怎么办？" → hash 索引换有序结构（内存 skiplist + 磁盘按 key 排序的 SSTable）——就是往 LSM 演化，v2 的规划。

## Q9 恢复时间被什么主导？怎么优化？

**答案要点**：全量扫描 log = 顺序读吞吐 × log 大小 + 逐条 CRC 开销，我实测过恢复时间随 log 大小的曲线，基本线性。优化三板斧：hint file（merge 时写紧凑索引，恢复只读它）、定期 checkpoint 索引快照、控制 log 大小（更积极的 merge）。RocksDB 的对应机制是 MANIFEST + 只重放尾部 WAL。

**证据**：[[S-Week 17 - benchmark 与 design_note 收口]] 恢复时间 benchmark。

## Q10 磁盘写是原子的吗？torn write 怎么发生？

**答案要点**：只能假设单个扇区（512B/4K）写原子，跨扇区的记录在崩溃时可能只持久化一部分——这就是 torn write。我的记录允许任意长度，所以恢复必须处理半条记录：CRC 识别 + 前缀截断。数据库的其他对策：MySQL 的 doublewrite buffer（页级）、PostgreSQL 的 full page write（WAL 里存整页）。

**证据**：[[S-Week 13 - checksum 与崩溃恢复]] 尾部截断样本；机制 [[存储引擎专题 - WAL 与 crash consistency]]。

**追问预案**：
- "为什么不把记录填充到扇区边界回避 torn write？" → 空间放大换鲁棒性，小 value 场景浪费严重；CRC + 截断更便宜——这是 design_note 里的显式取舍。
