# 副本与 EC 取舍专题

> [!goal] 目标

## 1. 两大流派一句话

- **多副本（replication）**：同一份数据完整存 N 份（典型 3 副本）。简单、读写路径短、修复直接，代价是 3 倍空间。
- **纠删码（EC, erasure coding）**：数据切成 k 个分片，用 Reed-Solomon 一类编码算出 m 个校验分片，k+m 个分片分布到不同节点——任意丢 m 个都能恢复。典型 4+2：空间开销 1.5 倍，容忍度与 3 副本相当（丢 2 个）。

$$
overhead_{EC} = \frac{k+m}{k}
$$

## 2. 三角取舍表

| 维度 | 3 副本 | EC 4+2 |
|---|---|---|
| 空间开销 | 3.0 倍 | 1.5 倍 |
| 写路径 | 写 3 份完整数据（可并行） | 编码计算 + 写 6 个分片 |
| 读路径（正常） | 就近读任意一份 | 读 k 个分片重组（或定位到数据分片直读） |
| 读路径（降级，节点故障时） | 读别的副本，无额外代价 | 读 k 个存活分片**解码重建**，延迟陡增 |
| 修复一个坏节点 | 从任一副本整份拷贝 | 读 k 个分片才能重建 1 个分片——**修复放大** |
| CPU | 近零 | 编解码消耗（现代 CPU 有加速，仍非零） |

两个必须会讲的机制：

- **修复放大与修复风暴**：EC 重建 1 个分片要读 k 份数据——大节点故障时全集群掀起 k 倍读流量的重建风暴，挤占前台带宽；副本修复只要 1 倍拷贝。这是 EC 在修复维度的隐藏账单。
- **小写问题（partial write）**：改一个条带里的一小段 → 校验分片必须同步更新 → 读旧数据 + 旧校验、算新校验、写回（read-modify-write），一次小写放大成多次 IO。所以 EC 天然适合**一次写入、整对象不可变**的数据（对象存储、备份、大文件），惧怕原地随机改。

## 3. 工业分层惯例：谁在用什么

- **热数据 / 小对象 / 低延迟**：副本——HDFS 默认 3 副本、Ceph 块存储池常用 3 副本、3FS 的 CRAQ 也是副本流（链式复制变体）。
- **冷数据 / 大对象 / 成本敏感**：EC——对象存储的主流（MinIO 默认 EC、各云对象存储内部）、HDFS 3.x 对冷数据支持 EC、Ceph 对象池用 EC。
- 常见架构是**分层混用**：写入先落副本层（吸收小写与低延迟需求），沉冷后转 EC 层——把两个流派各自放在自己擅长的负载上，和"append 换顺序写"一样是负载分层的思路。

## 4. Ceph 泛读附录：两个概念即止

总纲红线：Ceph 只读架构文档、能画写路径即可，不碰源码。

- **RADOS 写路径**（一张草图）：client 按对象名经 CRUSH 算出 PG 和主 OSD → 写主 OSD → 主 OSD 并行分发副本（或 EC 分片）→ 全部确认后应答 client。要点：**强一致（应答即全副本落定）**、主 OSD 是每个 PG 的协调者。
- **CRUSH**：用集群拓扑图 + 哈希**计算**出数据位置，而不是查中心化的位置表——去掉了元数据服务器这个瓶颈和单点，代价是拓扑变更（加减盘）会触发数据再平衡。与 JuiceFS/3FS 的"元数据引擎记位置"是两种路线：**算位置 vs 记位置**——这个对照放进对比笔记正合适。

## 5. 面试口述模板

```text
副本和 EC 是空间、修复、延迟的三角对换：3 副本三倍空间，但读写路径
短、降级读无代价、修复只要整份拷贝；EC 比如 4+2 只要 1.5 倍空间、
容忍度相当，但降级读要解码、修复一个分片要读 k 份数据——大故障时
是 k 倍读流量的修复风暴。EC 还有小写问题：改条带一小段就要读改写
校验分片，一次小写放大成多次 IO，所以它适合一次写入不可变的大对象。
工业惯例是分层：热数据小对象走副本，沉冷后转 EC——MinIO、各家对象
存储都是 EC 主力，HDFS 和 Ceph 块池默认副本。Ceph 我泛读过架构：
RADOS 写路径是 client 经 CRUSH 算出 PG 和主 OSD、主 OSD 分发副本、
全落定才应答；CRUSH 的特别之处是用拓扑加哈希算位置而不是查表，
去掉元数据单点，代价是拓扑变更触发再平衡——和 JuiceFS 用元数据
引擎记位置是两条路线。
```

追问预案：

- "4+2 和 3 副本容忍度一样，为什么不全用 EC？" → 三角的另外两边：降级读延迟、修复放大、小写放大——空间省下的钱在这三处付回去，负载决定划不划算。
- "EC 的读放大发生在什么时候？" → 正常读可以直读数据分片（系统化编码），放大主要在降级读和修复时。
- "副本就没有写放大吗？" → 有，3 副本写放大就是 3（网络与盘都是）；EC 的写放大是 (k+m)/k 加上小写场景的 read-modify-write——比较要按负载算，不是背结论。
- "CRUSH 的再平衡为什么是代价？" → 位置由拓扑计算而来，拓扑一变一批对象的"正确位置"就变了，触发迁移流量——运维上要控制变更节奏。
