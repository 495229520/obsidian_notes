# 训练数据集格式专题 - 小文件问题与打包格式

> [!info] 所属路线
> - 位置：AI / GPU 数据路径主线，排在 [[checkpoint I O 专题 - burst write 隔离]] 之后——checkpoint 讲"写侧"，本篇讲"读侧"的数据长什么样。
> - 用途：回答 AI 存储面试的高频起手题"训练数据到底怎么存、怎么读"。[[8.7 DataLoader 与 GPU 空闲归因]] 讲的是"读得慢 GPU 会空转"，本篇补上游一层：**数据的物理组织方式决定了读路径能不能快**。
> - 认知级专题，不排实验；S4 报告里画数据加载路径时直接引用。

> [!goal] 目标
> 讲清四件事：小文件为什么是 AI 存储的头号敌人；打包格式（WebDataset / TFRecord）如何把随机小读变成顺序大读；列存（Parquet / Arrow）和权重格式（safetensors）分别解决什么；shuffle 与顺序读的天然冲突怎么调和。

## 1. 小文件为什么是头号敌人

一个典型图像训练集是"百万到十亿个几十 KB 到几百 KB 的样本"；文本 token 化后单条样本更小。按总纲的分析框架数一遍固定成本：

1. **数切换**：每个文件一次 open + 若干次 read + 一次 close，系统调用和元数据查找（dentry/inode）都是与文件大小无关的固定开销——文件越小，固定成本占比越高。这正是 [[1.1 VFS 与系统调用路径]] 里"小 IO 时固定成本占比最高"的极端案例。
2. **元数据压力**：十亿级文件意味着十亿级 inode 和目录项，list/stat 风暴能先于数据读把元数据服务打垮（[[7.2 元数据路径瓶颈]]，这也是 [[7.6 AI 存储 vs 传统 NAS]] 的核心分歧点）。
3. **对象存储的请求语义**：S3/OSS 每个对象一次 GET，是一次完整的 HTTP 往返。【量级】数据中心内一次请求往返几百 μs 到几 ms，读一个 100 KB 对象，时间大头是往返而不是传输（[[7.7 对象存储路径]]）。
4. **打不满带宽**：介质和网络的吞吐都靠顺序大块喂饱（[[0.7 性能指标 IOPS 带宽 延迟 P99]]）；随机小读把吞吐问题退化成 IOPS 和延迟问题。

【事实】所以 AI 数据集的存储设计从一开始就绕着一个目标转：**把"百万次随机小读"变成"千次顺序大读"**。所有主流格式都是这句话的不同实现。

## 2. 打包格式：WebDataset / TFRecord

思路完全一致：把样本顺序拼进大文件（shard），读时整段顺序扫。

| 格式 | 容器 | 一条记录 | 生态 |
| --- | --- | --- | --- |
| WebDataset | 标准 tar，若干百 MB 到 GB 级一个 shard | tar 内相邻的同名不同后缀文件（`0001.jpg` + `0001.json`） | PyTorch 社区，对象存储友好（可流式读 tar） |
| TFRecord | 自定义记录流文件 | 长度前缀 + protobuf 序列化的 Example | TensorFlow 系 |

共同收益：

- 读路径变成顺序扫 shard，readahead 和对象存储的大块 Range GET（[[7.8 Multipart 与 Range GET]]）都能生效；
- 元数据从"十亿文件"缩成"千级 shard"，list/stat 压力消失；
- shard 是自包含的，天然适合分布式训练按 worker 切分。

【取舍】代价是失去"按文件名随机取任意样本"的能力——这引出第 4 节的 shuffle 问题。

## 3. 列存与权重格式

### Parquet / Arrow：按列裁剪

文本/表格数据常用 Parquet（磁盘列存）+ Arrow（内存列存）。对存储路径的意义有两点：

- **按列裁剪**：训练只读 `text` 列时不碰其他列，读放大显著低于行存整行扫描；
- **mmap 零反序列化**：HF datasets 把数据集物化为 Arrow 文件后用 mmap 加载，读路径就是 [[1.5 mmap 读路径]]——首次访问缺页读盘，之后命中 Page Cache，多个 DataLoader worker 进程共享同一份物理页（[[1.2 Page Cache 命中与未命中]]）。"上百 GB 数据集为什么能'秒加载'"的答案就是 mmap 惰性加载，不是真读完了。

### safetensors：checkpoint 与权重

torch.save 的默认格式本质是 pickle。【事实】pickle 反序列化可以执行任意代码，公开分发模型权重时这是真实的安全问题；而且 pickle 是流式格式，不知道张量在文件中的偏移，无法选择性读取。

safetensors 的布局是"JSON 头（每个张量的 dtype/shape/偏移）+ 紧凑的张量字节区"：

- 纯数据无代码，加载安全；
- 已知偏移，可以 mmap 后零拷贝按需取张量——推理框架加载大模型权重、[[8.6 Checkpoint 同步异步分片]] 里按 rank 分片读 checkpoint，依赖的都是这个性质；
- 顺序紧凑布局对 [[8.2 GDS 与 cuFile]] 这类直读路径也友好。

## 4. 核心矛盾：shuffle 与顺序读

SGD 要求样本近似随机；存储要求顺序读。全局精确随机 = 每个样本一次随机小读，回到第 1 节的灾难。工程解法是**两级伪随机**：

```text
epoch 开始
  → shard 列表整体洗牌（千级元素，代价为零）
  → 每个 worker 顺序读自己的 shard（存储看到的是顺序大读）
  → 读出的样本进内存 shuffle buffer（如数千条），从 buffer 随机弹出
```

【取舍】随机性上界受 buffer 大小限制（同一 shard 内相邻样本仍有相关性），换来的是存储路径完全顺序化。实践中配合"写 shard 时就预洗一次数据"，训练精度与全局随机没有可测差异——这是"用语义上稍弱的保证换数量级性能"的又一例，与 fsync 三档（[[S-Week 14 - WAL 与 fsync 策略]]）是同一类思维。

## 5. 端到端路径串联

把本篇接到已有笔记，就是一条完整的训练数据路径：

```text
对象存储上的 shard（7.7/7.8）
  → 可选缓存层：JuiceFS / Alluxio 类（7.3，把远端对象变成本地缓存命中）
  → DataLoader worker 顺序读 + prefetch（8.7）
  → 解码/增广（CPU 瓶颈时 GPU 依然空转，见 8.7 的归因方法）
  → pinned memory + H2D 拷贝（8.10 / 8.11）
```

面试画图时按这条线画，每层标出"固定成本在哪、顺序性靠什么保住"。

## 6. 面试问法与答法骨架

| 问题 | 答法骨架 |
| --- | --- |
| 训练数据为什么不直接存百万张小图？ | 固定成本（系统调用/元数据/请求往返）占比随文件变小而暴涨；元数据服务先崩；打包成 shard 顺序读是通解。 |
| WebDataset 解决了什么？ | 把随机小读变顺序大读 + 元数据缩千倍；代价是失去随机访问，用两级 shuffle 补。 |
| shuffle 不就破坏顺序读了吗？ | shard 级洗牌 + 内存 buffer 二级随机，存储层看到的仍是顺序读；随机性受 buffer 限制，是有意的取舍。 |
| safetensors 比 torch.save 好在哪？ | 无 pickle 代码执行风险；头部记录偏移，支持 mmap 零拷贝和按张量选择性读取，分片加载 checkpoint 靠它。 |
| HF datasets 为什么加载大数据集很快？ | Arrow + mmap 惰性加载，只建映射不读数据，实际 IO 推迟到访问时并被 Page Cache 摊平。 |
