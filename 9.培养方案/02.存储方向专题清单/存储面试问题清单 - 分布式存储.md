## Q1 介绍一下 JuiceFS 的架构？一次写入的路径？

**答案要点**：元数据/数据分离：元数据放可插拔的事务引擎（Redis/TiKV/MySQL），数据切块放对象存储——file → 64 MiB chunk → slice（一次连续写一个 slice）→ 默认 4 MiB block 上传。写路径：客户端切块上传对象存储 + 元数据引擎记映射事务；读路径查元数据后按 block 拉取，靠本地缓存缓解对象存储的毫秒级延迟。定位是用便宜弹性的对象存储换成本，适合云原生通用负载。

**证据**：[[分布式存储阅读专题 - JuiceFS 与 3FS]]；JuiceFS 官方架构文档（阅读笔记）。

**追问预案**：
- "为什么对象存储上不能直接跑文件系统语义？" → 无目录树、无原子 rename、按请求计费高延迟——所以元数据必须外置事务引擎。
- "元数据引擎挂了怎么办？" → 它就是可用性瓶颈点，选型（Redis vs TiKV）决定上限——这是该架构的显式代价。

## Q2 3FS 为什么用 RDMA + NVMe？和 JuiceFS 差在哪？

**答案要点**：目标负载不同：3FS 为 AI 训练的大规模随机读定制——数据面 RDMA + 全闪 NVMe 微秒级直达，副本用 CRAQ 让读打到链上任意干净节点摊开压力，还提供绕过 FUSE 的原生客户端；官方基准 180 节点 6.6 TiB/s 聚合读。JuiceFS 数据面是对象存储 HTTP（毫秒级），优化的是成本与弹性。一句话：JuiceFS 押通用+成本，3FS 押单一负载的极限吞吐——架构由目标负载决定。

**证据**：[[分布式存储阅读专题 - JuiceFS 与 3FS]] 对比笔记；3FS 设计笔记（阅读标注）。

**追问预案**：
- "3FS 为什么不做读缓存？" → 训练读是一次性扫描/随机读，命中率低——负载假设决定放弃；推理 KV cache 场景缓存故事就相反。
- "CRAQ 和链式复制的差别？" → 普通链式复制只能读尾节点，CRAQ 允许读任意干净节点，读吞吐随链长摊开。

## Q3 元数据为什么普遍要和数据路径分离？

**答案要点**：两种负载的诉求相反：数据面要吞吐（大块、顺序、可并行），元数据要低延迟事务（小、随机、强一致，rename/mkdir 是事务）——放一起互相拖累。所以 JuiceFS 外置事务引擎、3FS 用 FoundationDB、Ceph 的 MDS 独立于 OSD。分离的代价是多一次元数据往返和一个独立的可用性瓶颈——工程上用缓存 + 租约缓解。

**证据**：[[分布式存储阅读专题 - JuiceFS 与 3FS]]（两系统 + Ceph 三方印证）。

## Q4 副本和 EC 怎么选？

**答案要点**：空间/修复/延迟三角：3 副本 3 倍空间但路径短、降级读无代价、修复整份拷贝；EC 4+2 只要 1.5 倍空间、容忍度相当，但降级读要解码、修复一个分片读 k 份数据（修复风暴）、小写要读改写校验（read-modify-write 放大）。所以惯例分层：热数据小对象走副本，一次写入的冷大对象走 EC——MinIO 和对象存储 EC 主力，HDFS/Ceph 块池默认副本。

**证据**：[[副本与 EC 取舍专题]]。

**追问预案**：
- "EC 的写放大是多少？" → 正常整条带写是 (k+m)/k；小写场景加上 read-modify-write 另算——按负载算不背结论。

## Q5 CRUSH 解决什么问题？代价是什么？

**答案要点**：数据定位的去中心化：用集群拓扑 + 哈希**计算**出对象位置，而不是查中心位置表——去掉元数据服务器的容量瓶颈和单点。代价：拓扑一变（加减盘）一批对象的"正确位置"改变，触发再平衡迁移流量，运维要控节奏。与 JuiceFS/3FS"记位置"路线相对：算位置省元数据、变更贵；记位置变更灵活、元数据引擎是瓶颈。

**证据**：Ceph 架构文档泛读 + RADOS 写路径草图（client → CRUSH 定位 → 主 OSD → 副本分发 → 全落定应答）。

**追问预案**：
- "Ceph 写路径的一致性？" → 强一致：应答即全副本落定，主 OSD 是 PG 协调者——读到架构层，源码级留待深入。

## Q6 AI 存储和传统 NAS 的本质区别？

**答案要点**：三条：扩展模型（元数据/数据分离后各自横向扩 vs 单头纵向）；数据面技术栈（RDMA + 全闪 / 对象存储 vs 自管盘阵 + NFS 协议）；负载假设（为训练吞吐或云弹性定制、敢于放弃通用特性——如 3FS 放弃读缓存——vs 通用文件共享求全）。归根到底：这一代系统按目标负载做减法，传统 NAS 按协议兼容做加法。

**证据**：[[分布式存储阅读专题 - JuiceFS 与 3FS]] 第 5 节对照表。

## Q7 如果给你的 mini-kv-engine 加分布式，第一步做什么？

**答案要点**：先定冗余与一致性，不是先拆分片：单机引擎已有 WAL 和确定性重放，最自然的第一步是**主从复制**——log 天然是复制流（把 append 的记录流发给 follower 重放），提交点语义扩展成"多数派落盘再应答"。然后才是按 key 分片与元数据服务。这个演化路径正好复用我 S2 的全部语义资产：契约矩阵变成复制一致性级别，崩溃注入框架扩展成分区注入。

**证据**：[[存储引擎专题 - WAL 与 crash consistency]]（log 即复制流的地基）；阅读线的架构参照。

**追问预案**：
- "为什么不直接上 Raft？" → 最终要共识协议管成员与选主；但先手写主从能把复制流、幂等重放、一致性级别想透——学习路径和工程路径的区别，我说得清。
