## 1. 两个系统各一句话

- **JuiceFS**：把 POSIX 文件系统架在"独立元数据引擎 + 对象存储"上——用便宜无限的对象存储放数据，用事务型存储放元数据，换来云原生的弹性与成本。
- **3FS**（DeepSeek Fire-Flyer File System）：为 AI 训练负载定制的并行文件系统——RDMA + NVMe SSD 全闪架构，押注"大规模随机读"这一种负载形态，官方基准给到 180 节点 6.6 TiB/s 聚合读吞吐。

一开始就记住分野：**JuiceFS 优化的是"通用 + 成本 + 弹性"，3FS 优化的是"单一负载的极限吞吐"**——后面每条架构差异都能回溯到这句。

## 2. 元数据路径对比

| | JuiceFS | 3FS |
|---|---|---|
| 元数据放哪 | 独立元数据引擎（Redis / TiKV / MySQL 可插拔） | 无状态元数据服务，落 FoundationDB（事务型 KV） |
| 为什么分离 | 对象存储没有目录树/rename 语义，元数据操作要低延迟事务 | 同理，且无状态服务好横向扩 |
| 代价 | 元数据引擎成为独立的可用性/性能瓶颈点，选型决定上限 | 依赖 FoundationDB 的事务吞吐 |

共同结论（面试可直接说）：**现代分布式文件系统几乎都把元数据从数据路径里拆出来**——数据要吞吐、元数据要事务，两种负载放一起谁都做不好；差异只在拆出来之后放进什么引擎。

## 3. 数据路径对比：一次写入的旅程

- **JuiceFS**：file → 64 MiB chunk → slice（一次连续写产生一个 slice）→ 默认 4 MiB block 上传对象存储；元数据引擎记录 chunk/slice/block 的映射事务。读路径反过来：查元数据 → 按 block 从对象存储拉取（配本地缓存缓解对象存储延迟）。
- **3FS**：客户端经 RDMA 直达存储节点的 NVMe SSD；副本一致性用 **CRAQ**（链式复制的变体，读可以打到链上任意节点，摊开读压力）；提供 FUSE 之外的原生客户端接口（绕开 FUSE 的拷贝与上下文切换开销，贴近其"吞吐至上"的目标）。
- 对照点：JuiceFS 的"数据面"是对象存储的 HTTP（毫秒级、按请求计费）；3FS 的数据面是 RDMA + 本地 NVMe（微秒级）——**S3 学的两层技术栈正好是这两个系统的数据面**，把这句写进对比笔记，阅读线和实验线就缝合了。

## 4. AI 负载适配：3FS 押的三个注

1. **随机读为主**：训练数据加载是海量小随机读，3FS 干脆放弃常规读缓存设计（缓存对一次性扫描的训练读几乎无命中收益），把复杂度让位给裸吞吐。
2. **RDMA + 全闪**：数据面微秒级，配合 GPU 节点的数据饥渴——对标 [[NVMe-oF 专题 - TCP 与 RDMA transport 取舍]] 里"机柜内 AI 存储上 RDMA"的判断。
3. **KVCache 场景**：3FS 的设计笔记明确把 KV cache 存取列为目标场景之一——与阶段 3 的 KV offload 直接相关，读到这段时做好标记。

## 5. 与传统 NAS 的本质区别

| 维度 | 传统 NAS（NFS 一类） | JuiceFS / 3FS 这代系统 |
|---|---|---|
| 扩展模型 | 纵向为主，单头瓶颈 | 元数据/数据分离后各自横向扩 |
| 数据后端 | 自管盘阵 | 对象存储（JuiceFS）/ 分布式全闪（3FS） |
| 一致性协议 | 协议层（NFS 语义）承担 | 元数据事务 + 数据面复制协议（如 CRAQ）分层承担 |
| 目标负载 | 通用文件共享 | 云原生通用（JuiceFS）/ AI 训练吞吐（3FS） |

## 7. 面试口述模板

```text
我按同一组问题读了 JuiceFS 和 3FS：元数据在哪、一次写怎么走、为谁
设计。共同点是元数据都从数据路径拆出来放进事务型引擎——JuiceFS 可
插拔 Redis/TiKV，3FS 用 FoundationDB——因为数据要吞吐、元数据要事
务。数据面正好是两代技术栈：JuiceFS 把文件切成 chunk/slice/block
放对象存储，用便宜换弹性；3FS 用 RDMA 加 NVMe 全闪、CRAQ 链式复制
摊开读压力，还提供绕过 FUSE 的原生客户端，押注 AI 训练的大规模随机
读，官方给到 180 节点 6.6 TiB/s。所以结论是架构由目标负载决定：
JuiceFS 优化通用加成本，3FS 优化单一负载的极限吞吐——它俩的数据面
恰好就是我 S3 实验的两条 transport 路线。
```

追问预案：

- "为什么 3FS 不做读缓存？" → 训练读是一次性海量扫描/随机读，缓存命中率低还占内存——负载假设决定放弃；换成推理 KV cache 复用场景，缓存故事就完全不同。
- "JuiceFS 的对象存储延迟怎么办？" → 本地缓存层 + 大块预取；本质是承认毫秒级数据面，用缓存把热路径拉回本地——适合吞吐型不适合超低延迟型负载。
- "CRAQ 和普通链式复制差在哪？" → 链式复制读只能读尾节点；CRAQ 允许读链上任意"干净"节点，读吞吐随节点数摊开——写路径仍走全链。
- "你会怎么选型？" → 先问负载：通用共享 + 成本敏感选 JuiceFS 一类；AI 训练吞吐敏感、有 RDMA 网络选 3FS 一类；再问团队运维能力——这是架构题不是信仰题。
