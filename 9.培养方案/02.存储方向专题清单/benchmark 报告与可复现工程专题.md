# benchmark 报告与可复现工程专题

> [!info] 所属路线
> - 培养方案阶段：S-Week 6 首次完整执行；S-Week 11 README 定稿、mini-kv-engine / nvme-of-lab / gds-kv-offload-lab 的每份报告都沿用
> - 排序：05.20
> - 与 [[存储性能分析专题 - fio 与 benchmark matrix]] 的分工：05.00 管**测量设计**（负载、参数、口径），本专题管**报告与工程化**（怎么写出来、怎么让人复现、怎么诚实声明）。

> [!goal] 目标
> 把"一堆实验数据"变成"一个能放上简历的项目"的全套标准：三层可信度、六段式报告、波动处理决策、reproduce.sh 工程规范、Agent 使用声明。这套标准是两条线（存储 + 推理）共用的项目门面工艺。

---

## 1. 三层可信度标准

| 层 | 定义 | 检验方式 |
|---|---|---|
| **可复现** | 新机器按 README 跑 `reproduce.sh` 得到同量级结果 | 真的租一台新机器跑一遍 |
| **可信** | 每个结论能点回原始 CSV/JSON；波动有解释而不是被删掉 | 随机抽一条结论向上溯源 |
| **诚实** | 限制写清楚（云环境、单盘、单文件系统）；Agent 生成与人工验证分开声明 | 面试官问"局限是什么"时你答的和报告一致 |

三层是递进的：不可复现的数据谈不上可信，不诚实的报告可信也白搭——面试官只要抓到一处夸大，整个项目折价。

## 2. 六段式报告骨架

```text
1. 环境    机器/内核/盘/文件系统/工具版本——别人复现的起点
2. 方法    负载定义、重复次数、warmup、计时口径——数字的合法性来源
3. 结果    每小节一张图 + 一个对比表，图表从原始数据脚本生成
4. 结论    每条一句话 + 指向数据（"冷热差 40 倍，见 3.1"）
5. 限制    云环境邻居噪声、单盘、单文件系统、非稳态 SSD
6. Agent   哪些是生成的（脚手架/脚本/图表）、哪些是人工的（核心代码/结论）
```

两条写作纪律：

- **结论段只写"数据支撑得起"的话**：写"O_DIRECT 随机读比 buffered 冷读慢 8%"，不写"O_DIRECT 更慢"——量化、限定条件、可溯源。
- **限制段的三段式**（事实 + 影响范围 + 补救路径）：见 [[S-Week 11 - 前置知识 - 完整版收口]] 第 5 节，S-Week 6 首次执行时就按这个格式写。

## 3. 波动处理决策树

统一重跑中 3 次重复波动超过 10% 的组，按此决策，**禁止只留最好看的一次**：

```text
波动 > 10%
 ├─ 能定位原因？
 │   ├─ cache 状态没清干净 / 参数没复原 → 修掉，重跑该组
 │   ├─ 云邻居噪声（top 看 %steal、不同时段复现）→ 换时段重跑；
 │   │    仍波动则保留全部三次并在报告标注
 │   └─ SSD 内部状态（GC/温度）→ 保留数据，结论限定"非稳态"
 └─ 定位不了 → 数据保留、结论标注"不确定"，写进限制段
```

波动本身就是数据：报告里"这组波动 30%，原因是 X"比一排整齐的数字更能证明你测过真机器。

## 4. reproduce.sh 工程规范

从裸 Ubuntu 到全部结果的一键脚本，检查单：

- **依赖自装**：apt 安装、编译、生成测试文件全在脚本内，不假设环境。
- **破坏性步骤有确认**：drop_caches、改 `read_ahead_kb` 前打印提示等待确认；退出路径用 trap 复原一切系统参数。
- **幂等**：中断后重跑不产生半成品污染（临时文件清理、结果目录带时间戳或先清空）。
- **输出汇总**：跑完打印结果表与原始数据路径，而不是让人自己去翻。
- **新机器实测**：租一台干净机器全流程验证——"这半小时的租金是项目可信度的价格"。

## 5. 环境记录清单（总纲第十一节的硬性要求）

每份 benchmark 必须记录，缺一项数据就不完整：

```text
机器型号与云厂商实例类型        内核版本（uname -r）
文件系统与挂载参数              盘型号（nvme id-ctrl）
本地盘还是云盘（云盘数据不进报告）  fio / liburing 等工具版本
job file / 命令行原样            drop_caches 与否
重复次数（≥3，含 warmup，不只报最好）
```

## 6. Agent 使用声明规范

边界（总纲执行原则，两条线一致）：

- **Agent 可以做**：脚手架、CMake、fio job file、解析与画图脚本、README 初稿。
- **Agent 不可以做**：决定结论、修改 benchmark 数据、绕过 correctness gate / 崩溃注入测试。

声明写法：README 单列一节，两栏列清"生成部分"与"人工验证部分"，并写明验证方式（如"解析脚本的输出与手算 3 组样本比对"）。这不是自我贬值——**在 AI 工具普及的招聘环境里，清晰的边界声明本身就是工程素养的证据**，也是面试问"哪些是 AI 写的"时唯一站得住的答案。

## 7. 面试口述模板

```text
我的 benchmark 项目按三层标准收口：可复现——reproduce.sh 在新租的
机器上从裸系统跑通过；可信——报告里每条结论都指向原始数据文件，三
次重复波动超过 10% 的组保留全部数据并解释原因，比如有一组随机写波
动 30%，我用不同时段复测排除了邻居噪声，标注为 SSD 非稳态；诚实——
限制段写明云环境、单盘、单文件系统的边界，AI 生成的脚手架和人工验
证的核心逻辑分开声明。报告是六段式：环境、方法、结果、结论、限制、
Agent 声明，结论每条一句话带数据出处。
```

追问预案：

- "数据波动你怎么处理？" → 决策树：先定位（cache/邻居/SSD 状态），能修则重跑，不能修则全量保留 + 标注，绝不挑好看的。
- "怎么证明不是 AI 编的数据？" → 原始数据不可改的纪律 + 图表脚本从原始数据生成 + 新机器可复现——链条上任何一环都能当场验证。
- "换个文件系统结论会变吗？" → 预期变化最大的是 fsync 家族（journal 策略不同），这正是限制段写单文件系统的原因——把限制答成理解深度。
