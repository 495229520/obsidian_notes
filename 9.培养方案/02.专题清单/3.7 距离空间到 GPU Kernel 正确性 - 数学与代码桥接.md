# 3.7 距离空间到 GPU Kernel 正确性 - 数学与代码桥接

这篇笔记把 [[第02次课-距离空间笔记]] 和 [[数值分析与 GPU Kernel 正确性]]、[[Week 2 - Reduction + Profiling]]、[[LLM Kernel 专题清单]] 串起来。

核心问题是：

> 数学课里说“距离决定收敛和误差含义”；写 GPU / LLM kernel 时，这句话落到代码里就是：**你用什么距离判断 CUDA 输出和 reference 是否足够接近？**

## 1. 距离空间在代码里的翻译

数学中的距离空间写作：

$$
(X,d)
$$

其中：

- $X$ 是对象集合，可以是向量、函数、矩阵、张量、序列。
- $d(x,y)$ 是距离，用来回答两个对象有多接近。

在 GPU kernel correctness test 里，可以对应成：

| 数学语言 | 代码语言 |
|---|---|
| $X$ | 所有可能输入 / 输出张量的集合 |
| $x$ | CUDA kernel 输出 |
| $y$ | CPU / PyTorch reference 输出 |
| $d(x,y)$ | 误差度量，例如 max abs error、L2 error、relative error |
| $d(x,y) < \varepsilon$ | correctness test 通过 |

所以 correctness test 本质上是在问：

```text
CUDA 输出和 reference 输出，在我选定的距离下，是否足够接近？
```

这比一句“结果差不多”更严格，因为它要求你明确说清楚：

- 哪个空间里的对象在比较？
- 选了什么距离？
- 阈值 $\varepsilon$ 是多少？
- 为什么这个阈值对当前 dtype / shape / 算子合理？

---

## 2. 同一个输出，选不同距离就是选不同工程目标

[[第02次课-距离空间笔记]] 里强调：同一个集合上可以定义不同距离，从而得到不同的几何结构。

对应到 kernel 测试：同一组输出张量，也可以用不同误差度量来看。

设 CUDA 输出为 `actual`，PyTorch reference 为 `expected`，误差为：

```text
err = actual - expected
```

常见距离可以这样理解：

| 距离 / 误差 | 代码形式 | 它关心什么 |
|---|---|---|
| $L_\infty$ / max abs error | `torch.max(torch.abs(err))` | 最坏的一个元素错了多少 |
| $L_1$ / mean abs error | `torch.mean(torch.abs(err))` | 平均绝对偏差 |
| $L_2$ / RMS error | `torch.sqrt(torch.mean(err * err))` | 整体能量误差 |
| relative error | `abs(err) / abs(expected)` | 相对真实量级错了多少 |
| `allclose` | `atol + rtol * abs(expected)` | 绝对误差和相对误差混合判断 |

这些不是“哪个更高级”的区别，而是工程目标不同：

- 如果你怕任何一个 logits 位置爆掉，要看 `max abs error`。
- 如果你关心整体输出质量，要看 `L2 / RMS error`。
- 如果输出量级跨度很大，要看 relative error。
- 如果输出接近 0，要特别依赖 `atol`，不能只看 relative error。

## 3. PyTorch correctness test：把距离写成代码

下面这个函数不是为了替代 `torch.testing.assert_close`，而是把“距离空间”的思路显式写出来：

```python
import torch


def error_report(actual: torch.Tensor, expected: torch.Tensor):
    actual = actual.float()
    expected = expected.float()
    err = actual - expected

    max_abs = torch.max(torch.abs(err))
    mean_abs = torch.mean(torch.abs(err))
    rms = torch.sqrt(torch.mean(err * err))
    rel = torch.abs(err) / torch.clamp(torch.abs(expected), min=1e-6)
    max_rel = torch.max(rel)

    return {
        "max_abs": max_abs.item(),
        "mean_abs": mean_abs.item(),
        "rms": rms.item(),
        "max_rel": max_rel.item(),
    }
```

然后再用 `assert_close` 做正式门槛：

```python
def check_kernel(actual: torch.Tensor, expected: torch.Tensor, dtype: torch.dtype):
    report = error_report(actual, expected)
    print(report)

    if dtype == torch.float32:
        rtol, atol = 1e-5, 1e-6
    elif dtype in (torch.float16, torch.bfloat16):
        rtol, atol = 1e-2, 1e-2
    else:
        raise ValueError(f"unsupported dtype: {dtype}")

    torch.testing.assert_close(actual, expected, rtol=rtol, atol=atol)
```

这里的数学含义是：

```text
先用多个距离观察误差形状
再用一个明确阈值决定 PASS / FAIL
```

## 4. 为什么 `allclose` 同时需要 `atol` 和 `rtol`

PyTorch 的 close 判断本质是：

$$
|actual-expected|\leq atol+rtol\cdot |expected|
$$

这可以理解成混合距离：

- `atol` 控制绝对误差。
- `rtol` 控制相对误差。

为什么不能只用相对误差？

如果 `expected` 接近 0：

```text
expected = 0.000001
actual   = 0.000002
```

绝对误差很小：

```text
|actual - expected| = 0.000001
```

但相对误差可能很大：

```text
0.000001 / 0.000001 = 1
```

这不一定代表 kernel 真的坏了，可能只是接近 0 的位置对 relative error 特别敏感。

为什么不能只用绝对误差？

如果 `expected` 很大：

```text
expected = 1000000
actual   = 1000001
```

绝对误差是 1，看起来不小；但相对误差是：

```text
1 / 1000000 = 1e-6
```

对某些 FP32 计算来说，这可能完全可以接受。

所以 `atol + rtol * |expected|` 本质是在说：

```text
小数值区域用绝对误差兜底
大数值区域用相对误差判断
```

## 5. 距离选择如何影响 LLM kernel

### 5.1 Reduction：sum / max 的 correctness

Week 2 的 reduction 是最直接的例子。

sum reduction 输出是一个数或一组 partial sum。测试时可以用：

```python
expected = x.float().sum()
actual = cuda_reduce_sum(x)
torch.testing.assert_close(actual, expected, rtol=1e-4, atol=1e-4)
```

这里要注意：GPU 并行归约和 CPU 串行求和的加法顺序不同，FP32 加法不满足严格结合律，所以不能用 `==`。

max reduction 则更适合看 `max abs error`，因为最大值是一个选择问题：

```python
expected = x.float().max()
actual = cuda_reduce_max(x)
torch.testing.assert_close(actual, expected, rtol=0.0, atol=0.0)
```

如果输入是普通 FP32 且没有 NaN，max 的结果通常应该精确一致；但如果涉及 FP16、NaN、mask、非整除长度，就要单独说明测试规则。

### 5.2 RMSNorm：更像 $L^2$ / 能量误差

RMSNorm 的核心是：

$$
\sqrt{\frac{1}{d}\sum_i x_i^2}
$$

这和 $L^2$ 距离、均方误差有明显亲缘关系：都在关心平方和，也就是整体能量。

所以 RMSNorm kernel 的 correctness 不应该只看一个元素是否偶然接近，还要看整体误差：

```python
y_ref = rmsnorm_ref(x, weight)
y_cuda = rmsnorm_cuda(x, weight)

report = error_report(y_cuda, y_ref)
print("RMS error:", report["rms"])

torch.testing.assert_close(y_cuda, y_ref, rtol=1e-2, atol=1e-2)
```

工程含义：

- 输入可以是 FP16 / BF16。
- 中间平方和最好用 FP32 accumulation。
- `eps` 是数值稳定项，不是随手可删的常数。
- hidden size 越大，reduction 误差越需要认真看。

### 5.3 Softmax：距离背后还有概率分布

Softmax 输出可以看作一行概率分布：

$$
p_i=\frac{e^{x_i-\max(x)}}{\sum_j e^{x_j-\max(x)}}
$$

correctness 里至少要看：

- `max abs error`：最坏位置偏了多少。
- `sum error`：每行概率和是否接近 1。
- 极端输入：大正数、大负数、mask 后的无效位置。

代码模板：

```python
y_ref = torch.softmax(x.float(), dim=-1).to(x.dtype)
y_cuda = softmax_cuda(x)

torch.testing.assert_close(y_cuda, y_ref, rtol=1e-2, atol=1e-2)

row_sum = y_cuda.float().sum(dim=-1)
torch.testing.assert_close(
    row_sum,
    torch.ones_like(row_sum),
    rtol=1e-3,
    atol=1e-3,
)
```

这里的数学意识是：你不只是在比较两个张量，还在比较两个概率分布是否足够接近。

### 5.4 Quantization：近似空间里的距离

INT8 / FP8 量化可以理解成把原始连续值投影到低精度集合里：

$$
x \approx scale \cdot q
$$

这时“距离”就是衡量量化损失的工具：

```python
q, scale = quantize_int8(x)
x_hat = dequantize_int8(q, scale)

report = error_report(x_hat, x)
print(report)
```

但 LLM 推理里不能只看 `x_hat` 和 `x` 的距离，还要看下游影响：

- dequant 后 matmul 输出误差。
- logits 误差。
- top-k / sampling 结果是否变化。
- 吞吐提升是否足以抵消质量损失。

这就是距离空间思想进入系统工程后的样子：**先定义误差，再讨论速度是否值得。**

## 6. CUDA 代码里的距离意识

在 CUDA kernel 本体中，我们通常不直接计算完整距离；距离更多出现在 host 侧测试和 benchmark 报告里。

但是 kernel 写法会决定误差大小。例如 reduction：

```cpp
__global__ void reduce_sum_kernel(const half* input, float* partial, int n) {
    extern __shared__ float sdata[];

    int tid = threadIdx.x;
    int idx = blockIdx.x * blockDim.x + threadIdx.x;

    float x = 0.0f;
    if (idx < n) {
        x = __half2float(input[idx]);
    }

    sdata[tid] = x;
    __syncthreads();

    for (int stride = blockDim.x / 2; stride > 0; stride /= 2) {
        if (tid < stride) {
            sdata[tid] += sdata[tid + stride];
        }
        __syncthreads();
    }

    if (tid == 0) {
        partial[blockIdx.x] = sdata[0];
    }
}
```

这段代码里有几个数学到工程的对应关系：

| 代码选择 | 数学 / 误差含义 |
|---|---|
| `half` 输入转 `float` 累加 | 控制舍入误差传播 |
| 越界补 `0.0f` | sum 的中性元，不改变结果 |
| 分层 reduction | 改变加法顺序，可能引入微小 FP32 差异 |
| host 侧用 tolerance 检查 | 用距离判断是否足够接近 |

如果把 `float x` 改成 `half x`，kernel 可能更省资源，但误差也可能变大。此时不是凭感觉判断，而是回到距离：

```text
FP16 accumulation 的 d(actual, expected) 是否仍小于阈值？
速度提升是否被 benchmark / profiler 支撑？
```

## 7. benchmark 和 profiling 不能替代距离

[[3.5.1 CUDA Week 2 辅助笔记 - Benchmark + Profiling]] 里已经强调：

```text
correctness 是门票
benchmark 是事实
profiler 是解释
```

从距离空间角度看，correctness 的门票就是：

$$
d(y_{cuda},y_{ref})<\varepsilon
$$

benchmark 只能回答：

```text
这个 kernel 跑了多少 ms？
```

profiler 只能回答：

```text
它为什么这么快或这么慢？
```

它们都不能回答：

```text
这个结果在数学上是否足够接近 reference？
```

所以每个 LLM kernel 的实验记录至少应该包含：

```text
Kernel:
Shape:
Dtype:
Reference:
Distance / metric:
Tolerance:
Correctness:
Benchmark:
Profiler evidence:
Conclusion:
```

## 8. 一个可复用的实验报告模板

以后做 RMSNorm、Softmax、dequant、MatMul toy kernel 时，可以直接按这个模板写：

```text
Kernel:
RMSNorm

Object space:
FP16 input tensors with shape [batch, hidden]

Reference:
PyTorch FP32 accumulation implementation

Distance / metric:
max_abs, rms, torch.assert_close with rtol / atol

Tolerance:
rtol = 1e-2, atol = 1e-2

Reason:
Input / output dtype is FP16, but reduction uses FP32 accumulation.
The threshold is chosen to tolerate FP16 rounding while catching obvious mistakes.

Correctness:
PASS on random, zeros, large values, non-power-of-two hidden size.

Benchmark:
CUDA event, warmup = 10, repeat = 100.

Profiler evidence:
Nsight Compute shows memory throughput is the main bottleneck.

Conclusion:
Kernel is numerically acceptable under the chosen metric and faster than the PyTorch baseline on the tested shape.
```

## 9. 学习闭环

可以把这条线记成：

```text
距离空间：选 d(x,y)，定义什么叫接近
数值分析：研究误差如何产生、传播、放大
CUDA kernel：把公式写成并行代码
correctness test：用距离判断结果是否足够接近
benchmark / profiling：在正确的前提下解释性能
```

所以数学和代码不是两条线。

在 GPU Performance / LLM Kernel 方向里，数学负责提出“什么叫正确、什么叫接近、什么叫稳定”；代码负责在硬件约束下实现它；benchmark 和 profiler 负责证明这个实现是否值得。
