## 一、选择题（概念基础）

**1.** 关于 `char` 类型的符号性，正确的是：
- A. `char` 一定是有符号的（-128~127）　　B. `char` 一定是无符号的（0~255）
- C. `char` 是否有符号由编译器/平台决定　　D. `char` 占 2 字节

**2.** 不带后缀的浮点字面量 `3.14` 的类型是：
- A. `float`　　B. `double`　　C. `long double`　　D. 由上下文推导

**3.** `auto b{ 100LL };` 中 `b` 的类型是：
- A. `int`　　B. `long`　　C. `long long`　　D. `unsigned long long`

**4.** 对 `enum class Day { Mon, Tue };`，正确的是：
- A. `Day` 可隐式转换为 `int`　　B. 可写 `int x = Day::Mon;`
- C. 必须用 `Day::Mon` 访问，且转 `int` 需 `static_cast`　　D. 枚举器 `Mon` 会污染外层作用域

**5.** 下列哪种类型别名定义方式是 C++11 推荐的：
- A. `#define INT64 long long`　　B. `typedef long long INT64;`
- C. `using INT64 = long long;`　　D. `auto INT64 = long long;`

**6.** 表达式 `int a{500}; unsigned b{1000}; a - b;` 的运算结果类型是：
- A. `int`　　B. `unsigned int`　　C. `long`　　D. 编译错误

**7.** C++ 中把 `double` 转成 `int` 最推荐的写法是：
- A. `(int)d`　　B. `int(d)`　　C. `static_cast<int>(d)`　　D. `reinterpret_cast<int>(d)`

**8.** 关于 `static_cast` 与 `reinterpret_cast`，正确的是：
- A. 二者都做编译期类型检查，等价　　B. `static_cast` 拒绝 `int*`→`double*`，`reinterpret_cast` 允许
- C. `reinterpret_cast` 会产生实际数值转换代码　　D. `static_cast` 可转换任意不相关指针

**9.** 单精度浮点字面量正确的写法是：
- A. `200f`　　B. `200.0f`　　C. `200F`　　D. `200.0d`

**10.** 十六进制 `0x3D7` 等于十进制：
- A. 983　　B. 985　　C. 1727　　D. 879

> [!success]- 参考答案（第一节）
> 1. **C**。`char` 的符号性是**实现定义**的：x86 上多为有符号（-128~127），有些平台（如部分 ARM）默认无符号（0~255）。需要确定符号性时应显式写 `signed char` / `unsigned char`，存字节数据用 `unsigned char` 更稳妥。
> 2. **B**。不带后缀的浮点字面量一律是 `double`。`float` 需后缀 `f`/`F`，`long double` 需 `l`/`L`。这也是 `float x = 3.14;` 会有"`double`→`float` 收窄"警告的原因。
> 3. **C**。后缀 `LL`/`ll` 是 `long long`；`L` 是 `long`，`U` 是 `unsigned`，可组合（`ULL`）。`auto` 按字面量后缀推导，故 `b` 是 `long long`。
> 4. **C**。`enum class` 是强类型限定作用域枚举：枚举器不泄漏到外层作用域，必须 `Day::Mon` 访问；**不能隐式转 `int`**，转换要 `static_cast<int>(c)`。A/B/D 都是普通 `enum` 的特性。
> 5. **C**。`using` 是 C++11 推荐方式，语法直观且支持模板别名；`typedef` 仍可用但写法别扭；`#define` 是文本替换、无类型无作用域、不推荐；D 不是合法语法。
> 6. **B**。两个不同类型运算时低优先级类型转向高优先级，`int` 与 `unsigned int` 同级但**有符号让位于无符号**，`a` 被转成 `unsigned int`，结果类型是 `unsigned int`（这正是负值回绕 bug 的根源，见第 20 题）。
> 7. **C**。数值类型间转换用 `static_cast`：编译期检查、意图清晰、可搜索。A/B 是 C 风格转换（弱检查、不推荐）；`reinterpret_cast` 用于位模式重解释，对数值转换是错误工具。
> 8. **B**。`static_cast` 只允许"相关类型"转换，`int*`→`double*` 不相关会**编译报错**；`reinterpret_cast` 几乎不检查、仅重解释位模式、不产生数值转换。这正是 `static_cast` 更安全的体现。
> 9. **B**。`float` 字面量必须**带小数点 + 后缀 `f`/`F`**。`200f` 缺小数点不合法，`200F` 同样缺小数点，`200.0d` 无 `d` 后缀。
> 10. **A**。`0x3D7 = 3×16² + 13×16¹ + 7×16⁰ = 768 + 208 + 7 = 983`。注意 1727 是它的八进制写法（`01727`）。

## 二、概念辨析（判断对错并说明理由）

**11.** `float` 能表示约 ±3.4E38 的范围，所以 `float a{65923600.f}; a += 0.000001f;` 之后 `a` 会精确地增加 0.000001。

**12.** `const int hp{900};` 和 `int const hp{900};` 含义完全相同。

**13.** `#define hp 100` 定义出来的 `hp` 是一个常量变量，会在内存中分配空间并接受类型检查。

**14.** 普通 `enum Color { Red, Green };` 的枚举器会隐式转换为 `int`，且名字会暴露在外层作用域。

**15.** 枚举的底层类型可以是浮点数，例如 `enum class E : double { ... };`。

**16.** 单独写一条语句 `a++;` 比 `++a;` 慢，所以对内置类型也应优先用 `++a`。

**17.** `wchar_t wc{ L'我' };` 用 `std::cout << wc;` 能正常显示"我"这个字。

**18.** `using namespace std;` 和 `using std::cout;` 在效果和安全性上完全一样。

> [!success]- 参考答案（第二节）
> 11. **错**。`float` 范围大但**有效精度只有约 7 位**。`65923600` 已占约 8 位有效数字，`0.000001` 远低于该量级下的最小可分辨增量（ULP），被直接"吃掉"，`a` 不变。范围由指数决定、精度由尾数决定，两者是独立的。
> 12. **对**。修饰基础类型时 `const` 写在类型左右等价，都表示 `hp` 不可修改。仓库推荐 `const int hp{900};` 或 `int const hp{900};` 这类带花括号初始化的写法。（涉及指针时 `const` 位置才会改变语义。）
> 13. **错**。`#define` 是**预处理器文本替换**：编译前把 `hp` 原样换成 `100`，没有类型、不占内存、无作用域、不受类型检查、调试器也看不到。要常量请用 `const`/`constexpr`（《Effective C++》Item 2：宁可以编译器替换预处理器）。
> 14. **对**。这正是传统 `enum` 的两个"坑"：枚举器隐式转 `int`、名字泄漏到外层作用域易冲突。`enum class` 同时修复了这两点。
> 15. **错**。枚举的底层类型必须是**整数类型**（`int`/`short`/`long` 等），不能是浮点类型。
> 16. **错**。对内置类型，单独使用时 `a++` 与 `++a` 生成的汇编**完全相同**，无性能差异。性能差异只出现在**自定义类型**（如迭代器）：后缀版要保存并返回旧值副本。详见第 56 题。
> 17. **错**。`std::cout << wchar_t` 输出的是**对应的数字编码**而非字符。要显示宽字符需用 `std::wcout`。
> 18. **错**。`using namespace std;` 引入整个命名空间，易造成名称冲突（尤其放在头文件里会"传染"）；`using std::cout;` 只引入单个标识符，更安全可控，工程中应优先后者。

> [!success]- 参考答案（第三节）
> 19. 输出 `B 66`。`'A'` 的 ASCII 是 65，`c++` 后变 66（字符 `'B'`）。以 `char` 输出显示字符 `B`，`static_cast<int>` 显示数值 66。
> 20. 输出 `4294966796`。`int - unsigned` 时 `a` 被转成 `unsigned`，按模 2³² 运算：`500 - 1000 = -500 ≡ 2³² - 500 = 4294966796`。这是有符号/无符号混用的经典陷阱。
> 21. 输出 `1`（即 `true`）。`a` 约 6.6×10⁷ 已用满 `float` 的 ~7 位精度，`0.000001` 低于该量级 ULP 被丢弃，`c == a` 成立。
> 22. 依次输出 `100`、`A`、`350`。
>     - 第 1 行 `::a` 用 `::` 强制访问**全局** `a` = `100`；
>     - 第 2 行 `a` 按就近原则取最内层的 `char a{'A'}`，以 `char` 输出显示 `A`；
>     - 第 3 行在中间块内，最近的 `a` 是 `350`。
>     （注：笔记原文把 `::a` 注释成"打印 A"是注释错位，`::a` 实际是全局的 `100`，以此为准。）
> 23. 依次输出 `0xff`、`0377`、`255`。流的进制/`showbase` 是**粘性的**：`hex`+`showbase` 后输出 `0xff`；切到 `oct`（`showbase` 仍生效）输出 `0377`；切回 `dec` 输出 `255`（十进制无前缀）。
> 24. 输出 `3.14`。`std::fixed` 固定小数模式 + `setprecision(2)` 保留 2 位小数。注意 `setprecision`/`setw`/`setfill` 需要包含 `<iomanip>`。
> 25. 输出 `11 15`。词法分析采用"最长匹配（max munch）"，`b+++a` 解析为 `(b++) + a`：先用 `b` 的旧值 10 算 `10 + 5 = 15` 赋给 `c`，再令 `b` 自增为 11。

```cpp
unsigned int a = 3;
int b = -1;
if (b < a) std::cout << "b < a";
else       std::cout << "b >= a";
```

**29.**
```cpp
double x = 0.1 + 0.2;
if (x == 0.3) std::cout << "equal";
else          std::cout << "not equal";
```

**30.**
```cpp
enum class Color { Red, Green, Blue };
Color c = Color::Green;
int x = c + 1;              // 想得到 2
std::cout << c;             // 想打印 1
```

**31.** 用 Modern C++ 重写下面这段代码：
```cpp
#define SIZE 5
#define PI 3.14
int arr[SIZE];
double d = PI;
int n = (int)d;
```

> [!success]- 参考答案（第四节）
> 26. **bug 类型**：违反**严格别名规则（strict aliasing）**——通过 `int*` 访问实际是 `float` 的对象是未定义行为，优化器可能据此产生错误代码。修复（查看位表示用安全方式）：
>     ```cpp
>     // C++20：
>     int i = std::bit_cast<int>(f);
>     // 或通用做法：
>     int i;
>     std::memcpy(&i, &f, sizeof(f));
>     ```
> 27. **bug 类型**：C 风格转换隐藏了危险的不相关指针转换，`*pd` 按 8 字节读取只有 4 字节的 `int`，**越界读 + 严格别名 UB**。修复：本意若是数值转换应写 `double d = static_cast<double>(a);`——而且若误写成 `static_cast<double*>(&a)` 会直接**编译报错**，从而当场暴露错误意图。
> 28. **bug 类型**：有符号/无符号混合比较。`b` 被转成 `unsigned`（→ 4294967295），于是 `b < a` 为假，反直觉地输出 `b >= a`。修复：避免混用，或显式同类型比较：
>     ```cpp
>     if (b < static_cast<int>(a)) ...   // 在确认 a 不超过 int 范围时
>     ```
> 29. **bug 类型**：浮点相等比较。`0.1 + 0.2` 在二进制浮点下不精确等于 `0.3`，输出 `not equal`。修复：用容差比较：
>     ```cpp
>     if (std::fabs(x - 0.3) < 1e-9) ...
>     ```
> 30. **bug 类型**：`enum class` 不能隐式转 `int`，`c + 1` 和 `std::cout << c` 都**编译报错**。修复：显式转换：
>     ```cpp
>     int x = static_cast<int>(c) + 1;     // 2
>     std::cout << static_cast<int>(c);    // 1
>     ```
> 31. Modern C++ 重写（`constexpr` 替 `#define`、`std::array` 替 C 数组、`static_cast` 替 C 转换）：
>     ```cpp
>     constexpr int size{ 5 };
>     constexpr double pi{ 3.14 };
>     std::array<int, size> arr{};        // 值初始化为 0
>     int n = static_cast<int>(pi);
>     ```

## 五、简答题

**32.** `const`、`#define`、`constexpr` 三种定义常量的方式有什么区别？现代 C++ 该优先用哪个？

**33.** 简述 `static_cast` 和 `reinterpret_cast` 的本质区别及各自适用场景。

**34.** 什么是隐式类型转换？为什么 `int - unsigned` 这类表达式容易出 bug？如何避免？

**35.** `typedef` 和 `using` 定义类型别名有什么区别？为什么推荐 `using`？

**36.** 普通 `enum` 和 `enum class` 有哪些区别？为什么推荐 `enum class`？

**37.** `using namespace std;` 有什么风险？工程中应如何使用命名空间？

> [!success]- 参考答案（第五节）
> 32. **`#define`**：预处理器文本替换，无类型、无作用域、不入符号表、不可调试。**`const`**：有类型的只读变量，受作用域和类型检查约束，值不一定在编译期可知。**`constexpr`**：要求值在**编译期**确定，可用于数组维度、模板参数、`case` 标签等常量表达式上下文。优先级：**`constexpr` > `const` > `#define`**（《Effective C++》Item 2）。
> 33. **`static_cast`**：编译期检查的"相关类型"转换（数值互转、继承层次指针、`void*` 还原、`enum`↔`int`），可能生成实际数值转换代码，相对安全。**`reinterpret_cast`**：仅**重新解释位模式**、不做数值转换、几乎不检查，用于指针↔整数、底层内存/硬件操作，极易触发 UB。口诀：能用 `static_cast` 就别用 `reinterpret_cast`。
> 34. 隐式转换是编译器在混合类型运算/赋值时**自动**把"低优先级"类型转成"高优先级"类型。`int - unsigned` 时 `int` 被转成 `unsigned`，负结果会回绕成巨大正数（见第 20 题）。避免：统一类型、对会做减法/比较的量谨慎选无符号、需要时用 `static_cast` 显式对齐类型、打开 `-Wsign-conversion`/`-Wsign-compare` 警告。
> 35. 二者都创建类型别名、语义等价。区别：`using` 语法是 `using 别名 = 原类型;`，**可读性更好**（别名在左、像赋值），尤其**支持模板别名**（`template<class T> using Vec = std::vector<T>;`，`typedef` 做不到）。故 C++11 起推荐 `using`。
> 36. 区别：①**作用域**——`enum class` 枚举器限定在枚举名作用域内（`Color::Red`），不泄漏；普通 `enum` 泄漏到外层。②**隐式转换**——`enum class` 不能隐式转 `int`，普通 `enum` 会。③**前向声明/底层类型**——`enum class` 默认底层 `int`、可指定。推荐 `enum class` 因为**类型更安全、不污染命名空间**。
> 37. 风险：把整个 `std` 拉进当前作用域，易与自定义名冲突，并可能因 ADL 导致**意外的重载决议**；放在**头文件**里会传染给所有包含者，是工程大忌。做法：头文件永不写 `using namespace`；`.cpp` 里需要时优先用 `using std::cout;` 这类**精确 using 声明**，或直接写 `std::` 前缀。

## 七、简答深化题

**42.** `float` 为什么能表示约 ±3.4E38 这么大的范围，却只有约 7 位有效精度？范围和精度分别由什么决定？

**43.** 什么是严格别名规则（strict aliasing）？为什么 `reinterpret_cast` 做类型双关会让优化器产生错误代码？标准可移植的替代方案是什么？

**44.** **跨章综合题**：结合内存对齐（见 [[1.2 函数栈帧建立与销毁原理]]），解释 `struct S { char c; int i; };` 的 `sizeof(S)` 为什么常见是 8 而不是 5？这和基本数据类型的对齐要求有什么关系？

**45.** `auto` 类型推导、`typeid(x).name()`、`sizeof(x)` 分别是在**编译期**还是**运行期**完成的？

**46.** 全局变量、局部变量、命名空间成员，三者的**可见性**和**生命周期**各有什么不同？`::` 限定符在其中起什么作用？

> [!success]- 参考答案（第七节）
> 42. IEEE 754 单精度把 32 位分成：1 位符号 + 8 位**指数** + 23 位**尾数**。**范围由指数决定**（8 位指数能表示 ~10±38 的量级），**精度由尾数决定**（23 位尾数 ≈ log₁₀(2²⁴) ≈ 7.2 位十进制有效数字）。所以可以"很大"和"很精确"不可兼得：表示大数时最低有效位代表的实际数值很大，小增量会被丢弃（第 11、21 题）。
> 43. 严格别名规则：标准规定不允许通过"不兼容类型"的指针/引用访问同一对象（`char*` 等少数例外）。优化器**假设不同类型的指针不会指向同一块内存**，据此重排/缓存读写；若你用 `reinterpret_cast` 跨类型访问，编译器的假设被打破，生成的代码可能读到旧值或被优化掉。可移植替代：`std::memcpy` 复制位模式，或 C++20 `std::bit_cast`（要求同大小、trivially-copyable）。
> 44. `int` 要求 **4 字节对齐**（地址必须是 4 的倍数）。`struct S` 里 `char c` 占偏移 0，若 `int i` 紧跟在偏移 1 就违反对齐，编译器在 `c` 后插入 **3 字节 padding**，使 `i` 落在偏移 4；总大小 `1 + 3 + 4 = 8`，且按最严格成员（`int`，4）补齐到 4 的倍数。这与基本类型的 `alignof` 直接相关：结构体整体对齐 = 成员中最大的对齐要求。（详细布局机制见结构体章节与 [[1.2 函数栈帧建立与销毁原理]]。）
> 45. **`auto` 推导**：纯**编译期**，编译器根据初始化表达式确定类型，运行期无开销。**`sizeof`**：**编译期**常量表达式（对变长以外的类型）。**`typeid(x).name()`**：类型信息本身编译期就定了，但拿到 `name()` 字符串是**运行期**调用（对多态类型 `typeid` 还会运行期查 vtable）。一句话：前两者编译期，`typeid().name()` 取值在运行期。
> 46. **全局变量**：文件/程序级可见（配合 `extern` 跨文件），生命周期贯穿整个程序（静态存储期）。**局部变量**：从声明处到所在 `{}` 块结束可见，生命周期随块进入/退出创建销毁（自动存储期）。**命名空间成员**：在命名空间作用域内可见，需 `ns::name` 或 `using` 引入；生命周期同其存储类别（命名空间里的变量通常是静态存储期）。`::` 用于显式指定作用域：`::name` 访问全局/最外层，`ns::name` 访问指定命名空间——解决就近原则下被遮蔽（shadow）的名字访问问题。

## 八、概念辨析进阶

**47.** 辨析 `const` / `constexpr` / `#define` 三种"常量"。

**48.** 辨析 隐式转换 / 显式转换`(T)x` / `static_cast` / `reinterpret_cast` 四种类型转换。

**49.** 辨析 `char` / `wchar_t` / `char16_t` / `char32_t` 四种字符类型。

**50.** 辨析 `typedef` / `using` / `#define` 三种"别名"手段。

> [!success]- 参考答案（第八节）
> 47. `#define` 是**预处理替换**（无类型/无作用域/不调试）；`const` 是**有类型的只读变量**（值不必编译期可知）；`constexpr` 要求**编译期可求值**，能用于常量表达式上下文。口诀：**能 `constexpr` 就 `constexpr`，要变量语义用 `const`，永远别用 `#define` 定常量**。
> 48. 隐式转换：编译器**自动**做（可能悄悄丢精度）；显式 `(T)x`：C 风格、**弱检查**、可读性差、不可搜索；`static_cast`：C++ 风格、**编译期检查相关类型**、意图清晰；`reinterpret_cast`：**只重解释位模式**、几乎不检查、最危险。口诀：日常数值/继承转换用 `static_cast`，底层位操作万不得已才 `reinterpret_cast`，C 风格转换一律避免。
> 49. `char`：1 字节，存 ASCII/字节，符号性实现定义；`wchar_t`：宽字符，Windows 上 2 字节、Linux 上 4 字节（不可移植）；`char16_t`：固定 2 字节，UTF-16 编码单元；`char32_t`：固定 4 字节，UTF-32 一个码点。口诀：要确定宽度做 Unicode 就用 `char16_t`/`char32_t`，别依赖 `wchar_t` 的大小。
> 50. `#define`：预处理文本替换，**不推荐**做类型别名（无作用域、易出错）；`typedef`：C 风格别名，能用但写法别扭、不支持模板别名；`using`：C++11 推荐，**可读性好 + 支持模板别名**。口诀：类型别名一律用 `using`。

## 九、大厂面试场景题 / 八股常考

> 偏真实工程与系统岗会问的"为什么""怎么排查""怎么优化"。

**51.** 一个记账程序用 `float` 存金额，跑久了发现总额对不上、小额加不进去。为什么？怎么修？

**52.** 服务端把一个 C++ 结构体直接 `memcpy` 进缓冲区，通过 socket 发给另一台不同架构的机器，对端解析出来字段全乱。请系统列出可能原因和正确做法。

**53.** Code review 时看到大量 C 风格转换 `(T)x`，你建议改成 `static_cast`。除了"风格更现代"，还有哪些实际工程收益？

**54.** 同事写的 `for (unsigned i = n; i >= 0; --i) { ... }` 永远跑不完。为什么？这类有符号/无符号 bug 怎么系统排查？

**55.** 团队规范"头文件里禁止 `using namespace std;`"。请解释这条规则背后的具体危害。

> [!success]- 参考答案（第九节）
> 51. **现象**：金额累加误差越来越大，远小于当前总额的零头加不进去。**原因**：`float` 只有 ~7 位有效精度，金额（尤其大额 + 小数）会精度损失；且很多十进制小数（如 0.1）二进制无法精确表示。**解决**：用**整数存最小货币单位**（如"分"）做精确运算；或用定点/十进制库（如 `decimal`）。**延伸**：金融、计费场景一律避免用浮点直接表示钱。
> 52. **现象**：对端字段错位/数值错乱。**原因**：① 结构体含 **padding**（且可能是未初始化垃圾）；② **字节序**不同（大端/小端），多字节整数被反转；③ **类型宽度**不固定（`int`/`long` 在不同 ABI 大小不同）；④ **对齐/ABI** 差异导致成员偏移不同；⑤ 含指针/`std::string` 时传的是本机地址，无意义。**解决**：用**定长类型**（`uint8_t`/`uint16_t`/`uint32_t`）逐字段**手动序列化**、统一**网络字节序**（`htonl`/`htons`）、不传指针/复杂对象，或用 Protobuf/FlatBuffers。**延伸**：见 [[1.2 函数栈帧建立与销毁原理]] 的对齐部分与结构体章节。
> 53. **现象/动机**：C 风格转换隐患多。**原因/收益**：① `static_cast` 做**编译期类型检查**，把"不相关类型转换"变成编译错误（`(T)x` 会默默放行）；② 它会在需要时退化成更危险的 `const_cast`/`reinterpret_cast`，而 C 风格转换把这些**混为一谈**、看不出意图；③ `static_cast<...>` 关键字**易于全局搜索/审计**；④ 可读性强、意图明确。**延伸**：《Effective C++》Item 27——尽量少转型、要转就用 C++ 风格。
> 54. **现象**：死循环。**原因**：`i` 是 `unsigned`，**永远 `>= 0`**；当 `i` 从 0 再 `--` 会回绕成 `UINT_MAX`，条件恒真。**解决**：循环计数用 `int`，或改写终止条件（如 `for (unsigned i = n; i-- > 0; )`）。**排查**：打开 `-Wsign-compare`/`-Wsign-conversion`，对所有"会做减法/递减到 0/与负数比较"的量审查其有/无符号性。**延伸**：容器 `size()` 返回无符号，倒序遍历尤其要小心。
> 55. **现象**：头文件污染。**原因**：头文件被大量 `#include`，`using namespace std;` 会把整个 `std` 注入**每个**包含者的全局作用域，导致：① 与用户自定义名（如自写的 `count`、`distance`、`array`）**冲突**；② 因 ADL 改变重载决议、引入**难以察觉的歧义**；③ 一处污染、处处中招，难以定位。**解决**：头文件只写全限定名 `std::`；`.cpp` 内确需简写时用精确 `using std::xxx;`。**延伸**：这属于"接口卫生"，和"头文件最小依赖"是同一类工程准则。

## 十、补充加分题

**56.** 对内置类型 `a++` 和 `++a` 无差异，但对自定义类型（如迭代器）为什么常说"优先用 `++a`"？从拷贝开销角度分析。

**57.** 浮点数 `1E2` 既能表示整数 100 也能表示小数。IEEE 754 是怎么用同一套格式统一表示整数和小数的？为什么用 `float` 存大整数也会丢精度？

**58.** `typeid(a).name()` 为什么在不同编译器输出不一样（MSVC 显示 `int`，GCC 显示 `i`）？

**59.** **性能/缓存题**：要存储上亿个数值，选 `int8_t` / `int` / `int64_t` 该怎么权衡？从内存占用与缓存局部性角度分析。

> [!success]- 参考答案（第十节）
> 56. 后缀 `a++` 的语义要求**返回自增前的旧值**，所以自定义类型的后缀 `operator++` 内部要先**拷贝一份旧对象**、自增后返回该副本——多一次构造/析构。前缀 `++a` 直接自增并返回 `*this` 的引用，**无拷贝**。对迭代器等"重对象"，这个拷贝是 O(对象大小) 的实打实开销；对内置 `int` 编译器优化到完全相同，所以差异只在自定义类型。结论：默认写 `++a` 是更安全的习惯。
> 57. IEEE 754 用 `值 = ±尾数 × 2^指数` 的**科学计数法**统一表示：指数为正即可表示整数部分。整数能被精确表示的前提是它能落在尾数位宽内——`float` 尾数 24 位（含隐含位），能精确表示的整数上限约 2²⁴ = 16,777,216；超过后相邻可表示整数间隔 >1，于是大整数被"四舍五入"，出现丢精度（如 `float(16777217)` 可能等于 16777216）。
> 58. `name()` 返回的是**实现定义**的字符串，标准不要求人类可读。MSVC 直接返回 `"int"`；GCC/Clang 返回的是 **name mangling（名称改编）** 后的编码（`int`→`"i"`），需要 `c++filt` 或 `abi::__cxa_demangle` 才能还原。所以 `typeid().name()` 只适合调试参考、**不可跨编译器依赖其具体文本**。
> 59. **权衡维度**：① 内存占用——`int8_t` 是 `int64_t` 的 1/8，上亿元素差出数百 MB~GB；② **缓存局部性**——元素越小，一条 cache line（通常 64 字节）装得越多，顺序遍历命中率越高、带宽利用越好；③ 取值范围/溢出——`int8_t` 只够 -128~127，越界就错；④ 运算开销——小类型运算时可能先整型提升到 `int`。**结论**：在**值域够用**的前提下选最小类型（省内存、对缓存/SIMD 友好）；值可能很大就用 `int`/`int64_t`。这正是 AI Infra/高性能场景常用量化（`int8`）压缩数据的动机之一。

## 十一、进制转换专项

> 本章 [[2.1 C++基本数据类型]] 用大量篇幅讲了进制转换，这里集中手算练习。要求能在纸上写出过程。

**60.** 把十进制 `983` 分别转成二进制、八进制、十六进制。

**61.** 把二进制 `0b1111010111` 转成十进制和十六进制。

**62.** 把 `0x3D7` 直接转成二进制和八进制（用分组法，**不经过十进制**）。

**63.** 写出下列数的所有合法进制前缀/后缀写法：二进制 `1010`、八进制 `75`、十六进制 `1A3F`。

> [!success]- 参考答案（第十一节）
> 60. **除基取余，逆序读余数**：
>     - 二进制：983÷2 反复取余 → `1111010111`（验算 512+256+128+64+16+4+2+1 = 983）。
>     - 八进制：983÷8=122…7，122÷8=15…2，15÷8=1…7，1 → `1727`。
>     - 十六进制：983÷16=61…7，61÷16=3…13(D)，3 → `3D7`。
> 61. **按位权展开求和**：`1×2⁹ + 1×2⁸ + 1×2⁷ + 1×2⁶ + 0 + 1×2⁴ + 0 + 1×2² + 1×2¹ + 1×2⁰ = 512+256+128+64+16+4+2+1 = 983`，十进制 `983`。再每 4 位一组转十六进制：`0011 1101 0111` → `3 D 7` → `0x3D7`。
> 62. **十六进制每位拆 4 位二进制**：`3→0011`、`D→1101`、`7→0111` → `0b001111010111`。**二进制每 3 位一组（从右）转八进制**：`001 111 010 111` → `1 7 2 7` → `01727`。（4 位/3 位分组法比经过十进制更快，因为 16=2⁴、8=2³。）
> 63. 依笔记的前后缀表：
>     - 二进制 1010：前缀 `0b1010` / `0B1010`，后缀 `1010b` / `1010B`。
>     - 八进制 75：前缀 `0o75` / `0O75` / `075`，后缀 `75o` / `75O`。
>     - 十六进制 1A3F：前缀 `0x1A3F` / `0X1A3F`，后缀 `1A3Fh` / `1A3FH`。
>     （注：C++ 标准实际只支持 `0b`/`0`/`0x` 前缀字面量；表中的字母**后缀**形式是进制记法约定，并非所有都被编译器直接接受。）
