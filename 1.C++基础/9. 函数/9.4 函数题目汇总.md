## 一、选择题（概念基础）

**1.** 关于函数名，下列说法**正确**的是：
- A. 函数名是一个关键字　　B. 函数名在大多数场景会隐式转换为指向该函数的指针
- C. 函数名存储在栈区　　D. 直接输出函数名会调用该函数

**2.** 仅有下列哪一项不同时，**不能**构成函数重载？
- A. 参数个数　　B. 参数类型　　C. 参数顺序　　D. 返回值类型

**3.** 数组作为函数参数 `void f(int arr[])`，在函数内 `sizeof(arr)`（64 位）得到：
- A. 数组总字节数　　B. 8　　C. 元素个数　　D. 4

**4.** 关于默认参数，下列说法**错误**的是：
- A. 默认值从右向左给　　B. 声明和定义处只能有一处给默认值
- C. `int f(int a = 1, int b)` 合法　　D. 默认值调用效率可能更高（直接压入立即数）

**5.** 下列哪个返回是**安全**的？
- A. 返回函数内局部 `int` 的引用　　B. 返回函数内局部数组首地址
- C. 返回函数内 `static int` 的引用　　D. 返回函数内局部 `int` 的地址

**6.** 关于顶层 const 与底层 const 对重载的影响，正确的是：
- A. 顶层 const 构成重载，底层不构成　　B. 底层 const 构成重载，顶层不构成
- C. 两者都构成重载　　D. 两者都不构成重载

**7.** 后缀递增运算符的成员函数原型是：
- A. `T operator++()`　　B. `T& operator++()`　　C. `T operator++(int)`　　D. `T& operator++(int)`

**8.** 下列运算符中**不能**被重载的是：
- A. `[]`　　B. `()`　　C. `::`　　D. `<<`

**9.** 流运算符 `operator<<` 通常必须实现为友元函数，根本原因是：
- A. 性能更高　　B. 左操作数是 `std::ostream` 而非自定义类，且无法修改标准库
- C. 友元能内联　　D. 成员函数不能返回引用

**10.** 关于函数模板 `template <typename T> T f(T a, T b);`，调用 `f(1, 3.14)` 的结果是：
- A. T 推导为 double　　B. T 推导为 int　　C. 编译错误（T 无法同时是 int 和 double）　　D. 运行期决定

**11.** 当同时存在「精确匹配的普通函数」「函数模板特化」「通用模板」时，重载决议的优先级从高到低是：
- A. 通用模板 > 特化 > 普通函数　　B. 普通函数 > 特化 > 通用模板
- C. 特化 > 普通函数 > 通用模板　　D. 三者等价，报二义性

**12.** `__cdecl` 与 `__stdcall` 的核心区别是：
- A. 参数压栈顺序不同　　B. 谁清理栈不同（cdecl 调用者、stdcall 被调用者）
- C. 返回值寄存器不同　　D. 没有区别

> [!success]- 参考答案（第一节）
> 1. **B**。函数名在多数场景隐式转换为函数指针，输出它得到的是函数代码段的起始地址，不是调用它。函数代码在 `.text` 代码区，不在栈。
> 2. **D**。仅返回值不同不构成重载——编译器匹配时只看函数名和参数列表。A/B/C 都能构成重载。
> 3. **B**。数组退化为指针，`sizeof` 得到指针大小 8（64 位），丢失长度信息。这正是要额外传 size 或用数组引用模板的原因。
> 4. **C**。默认值必须从右向左连续给：`int f(int a = 1, int b)` 中左边有默认值右边没有，非法。
> 5. **C**。`static` 变量生命周期贯穿程序，返回其引用安全。A/B/D 都返回了离开函数即销毁的栈对象（悬空引用/指针）。
> 6. **B**。底层 const（`const int*`、`const int&`）改变了参数语义，构成重载；顶层 const（`const int`、`int* const`）按值传递时被忽略，不构成重载。
> 7. **C**。后缀 `operator++(int)` 用 `int` 哑参与前缀区分，返回**值**（修改前的副本）；前缀 `operator++()` 返回引用 `T&`。
> 8. **C**。`::`（作用域）、`.`、`.*`、`?:`、`sizeof`、`typeid` 不能重载。`[]`、`()`、`<<` 都可以。
> 9. **B**。`cout << obj` 的左操作数是 `ostream`，若写成成员函数就成了 `obj.operator<<(cout)`（写法颠倒），且我们无法给标准库 `ostream` 加成员，所以用友元（两个操作数都作参数）。
> 10. **C**。两个参数都用同一个 `T`，`int` 和 `double` 无法同时推导，编译错误。解决：显式 `f<double>(1, 3.14)` 或用两个类型参数。
> 11. **B**。普通函数（精确匹配）> 函数模板特化 > 通用模板（可推导）> 需类型转换的普通函数。
> 12. **B**。两者参数都从右向左压栈；区别在栈清理责任：`__cdecl` 调用者清理（故支持可变参数如 printf），`__stdcall` 被调用者清理（`ret 8`），Win32 API 用它。

## 二、概念辨析（判断对错并说明理由）

**13.** 函数模板本身就是一个函数，编译后会生成一份通用代码处理所有类型。

**14.** `extern "C"` 修饰的函数可以重载。

**15.** 派生类定义了一个同名函数后，基类所有同名重载版本依然可以通过派生类对象直接调用。

**16.** 赋值运算符 `operator=` 中不需要自赋值检查，因为 `a = a` 不会发生。

**17.** `const` 引用既能绑定左值也能绑定右值，而非 `const` 左值引用只能绑定左值。

**18.** 函数内的 `static` 局部变量每次进入函数都会重新初始化。

**19.** `operator[]` 提供 const 与非 const 两个版本，纯粹是为了写法好看，没有实质区别。

**20.** `auto a = rx;`（`rx` 是 `int&`）后，`a` 的类型是 `int&`。

**21.** 非类型模板参数可以是 `double` 类型（C++20 之前）。

**22.** 同一个函数模板，传入不同类型会生成不同的函数实例；传入相同类型但数值不同则复用同一份实例。

> [!success]- 参考答案（第二节）
> 13. **错**。模板**不是函数**，是生成函数的"蓝图"。每种类型参数会实例化出一份**独立**的函数代码（见 [[9.2.7 函数模版本质（汇编）]] 的不同 `call` 地址），可能造成代码膨胀。
> 14. **错**。`extern "C"` 禁用名称修饰（name mangling），函数名就是唯一符号，无法区分同名函数，因此不能重载。它用于 C/C++ 互操作。
> 15. **错**。派生类同名函数会**隐藏**基类所有同名重载（名字隐藏），`d.func(double)` 会去匹配派生类的 `func(int)` 并隐式转换。需 `using Base::func;` 把基类重载引入。
> 16. **错**。`a = a` 真实存在（尤其引用/指针别名）。若不检查，先 `delete[]` 旧资源再 `memcpy`，会读已释放内存。必须 `if (this == &other) return *this;`。
> 17. **对**。`const T&` 可绑定临时量（右值），这也是 `operator<<` 第二参用 `const&` 才能输出临时对象的原因；非 const 左值引用不能绑右值。
> 18. **错**。`static` 局部变量只在**首次**执行到声明处初始化一次，之后保持上次的值，存于 `.data`/`.bss` 而非栈，不随调用创建销毁。
> 19. **错**。有实质区别：非 const 版本返回 `T&` 支持写（`arr[i]=x`）；const 版本返回 `const T&`，使 `const` 对象/`const` 引用也能只读访问。没有 const 版本，`void f(const MyArray&){ ...a[0]... }` 无法编译。
> 20. **错**。`auto` 会忽略引用和顶层 const，`a` 是 `int`（拷贝）。要保留引用须写 `auto& a = rx;`，或用 `decltype(rx)` / `decltype(auto)`。
> 21. **错**。C++20 之前非类型模板参数只允许整型、枚举、指针、引用、`nullptr_t`，**不允许** `float`/`double` 和类类型。
> 22. **对**。类型决定实例：`ave<int>` 与 `ave<short>` 是两份不同代码、不同地址；`ave(short(100),short(200))` 与 `ave(short(300),short(400))` 复用同一份 `ave<short>`。

> [!success]- 参考答案（第四节）
> 31. **悬空引用**：`result` 是栈上局部变量，函数返回即销毁，返回的引用指向无效内存（UB）。修复：直接返回值 `int getValue(){ return 42; }`；若确需引用语义，返回 `static`/全局/传入参数的引用。
> 32. **缺自赋值检查**：`a = a` 时先 `delete[] cstr`，再 `memcpy(cstr, o.cstr,...)` 读的是已释放内存。修复：函数开头 `if (this == &o) return *this;`。（Modern C++ 更推荐 copy-and-swap 或直接用 `std::string` 免去手写。）
> 33. **缓冲区溢出**：`strcpy` 无边界检查，`src` 超过 64 字节就溢出 `buffer`，可覆盖返回地址（栈溢出攻击面）。修复（Modern C++）：用 `std::string dst = src;` 彻底避免裸缓冲区；若必须用 C 数组，`strncpy(buffer, src, sizeof(buffer)-1); buffer[63]='\0';`。
> 34. **缺 const 版本**：`const MyArray&` 只能调 const 成员，而 `operator[]` 只有非 const 版本 → 编译错误。修复：补 `const int& operator[](size_t i) const { return data[i]; }`。
> 35. **特化必须在首次使用前可见**：通用模板已在 `process(10)` 处实例化出 `process<int>`，之后才出现的特化会导致"特化在实例化后"的错误/未定义行为。修复：把 `template<> void process<int>(int)` 的声明放在任何使用之前。
> 36. **new[]/delete 不匹配**：`new Particle[5]` 必须配 `delete[]`，写成 `delete` 是未定义行为（且不会调用重载的 `operator delete[]`）。修复：`delete[] arr;`，并补充重载 `operator new[]`/`operator delete[]`。
> 37. **违反 ODR**：非 inline 函数定义放头文件，被多个 `.cpp` 包含会重复定义，链接报 `multiple definition`。修复：头文件只放**声明** `int add(int,int);`，定义放某个 `.cpp`；或加 `inline`（`inline int add(...){...}`）允许多 TU 定义。

## 五、简答题

**38.** 用一句话分别说明值传递、指针传递、引用传递的差异与各自适用场景。

**39.** 为什么"数组作为函数参数"无法在函数内用 `sizeof` 得到长度？有哪两种保留长度的办法？

**40.** 函数声明与定义有什么区别？什么是 ODR？内联函数是怎样的例外？

**41.** 前缀 `++` 和后缀 `++` 在重载实现上有何区别？为什么说前缀通常更高效？

**42.** 运算符重载用成员函数和友元函数各适合什么场景？为什么 `2.0 * v`（标量在左）通常要用友元？

**43.** `#pragma once` 和 `#ifndef` 包含保护各自的优缺点是什么？

**44.** `static` 全局变量和普通全局变量在链接属性上有什么区别？这有什么用？

**45.** 函数模板的「特化」和「重载」有什么区别？当两者同时存在且都能匹配时谁优先？

> [!success]- 参考答案（第五节）
> 38. **值传递**：拷贝实参，函数内改副本不影响外部，适合小对象/需要独立副本；**指针传递**：传地址，可改外部变量、可为 `nullptr`、可传大对象避免拷贝，适合可选参数/C 接口；**引用传递**：实参的别名，语法简洁不可为空，`T&` 改外部、`const T&` 零拷贝只读（大对象首选）。
> 39. 数组作参数会**退化**为指向首元素的指针，丢失长度，`sizeof` 只得指针大小。办法：① 额外传一个 `size` 参数；② 用**数组引用模板** `template<typename T, size_t N> f(T(&arr)[N])`，编译期捕获 N（也可用非类型参数推导）。
> 40. 声明给出接口（返回类型+函数名+参数类型），可多次，不分配代码；定义给出函数体，是生成机器码的依据。**ODR（一次定义规则）**：一个函数在整个程序只能定义一次，否则链接报重复定义。**内联例外**：`inline` 函数可在多个翻译单元各有一份定义，但必须完全相同。
> 41. 前缀 `T& operator++()`：直接自增并返回 `*this` 引用，无拷贝；后缀 `T operator++(int)`：要先保存旧值副本 `T t=*this`，自增后返回旧副本，多一次对象拷贝。前缀无副本、返回引用，所以更高效，循环里优先 `++it`。
> 42. 成员函数：左操作数必须是本类对象（`*this`），适合 `=`、`[]`、`()`、`->`、`++`、类型转换、复合赋值；友元函数：两个操作数都作参数、地位对称，适合 `+ - * /`、`<<`、`>>`。`2.0 * v` 左操作数是 `double` 不是类对象，无法写成成员函数，必须用友元 `operator*(double, const Vector&)`。
> 43. `#pragma once`：简洁、通常更快（编译器按文件去重），但非标准（个别老编译器/奇怪文件系统可能失效）；`#ifndef/#define/#endif`：标准、完全可移植，但需三行且依赖宏名唯一（撞名会漏包含）。现代项目两者常并用或优先 `#pragma once`。
> 44. 普通全局变量是**外部链接**，可被其他文件 `extern` 引用；`static` 全局变量是**内部链接**，仅本翻译单元可见。用处：隐藏实现细节、避免跨文件符号冲突（类似匿名命名空间）。
> 45. 特化是**模板的特殊版本**（`template<>`），是同一模板族的定制实现；重载是**独立的函数**（普通函数或不同签名的模板）。优先级：精确匹配的**普通函数 > 模板特化 > 通用模板**——所以普通函数重载会"盖过"特化。

## 七、简答深化题

**51.** 函数调用时栈帧是怎样建立和销毁的？请结合 `push ebp / mov ebp, esp / ... / pop ebp / ret` 说明 EBP、ESP、返回地址的角色。

**52.** 为什么"返回局部变量的引用/指针"是悬空？这和[[6.6 堆与栈的区别|栈帧的生命周期]]有什么关系？哪些返回是安全的？

**53.**【跨章综合】函数参数中 `T&`、`const T&`、`T&&` 三种引用分别对应什么值类别/语义？结合[[13.2 右值引用|右值引用]]说明 `void f(int&)` 与 `void f(int&&)` 重载时 `f(10)` 走哪个、为什么。

**54.** 函数模板为什么通常要把定义写在头文件里，而普通函数定义放头文件却会违反 ODR？

**55.** 名称修饰（name mangling）是什么？它如何让 C++ 支持重载而 C 不支持？`extern "C"` 在这里起什么作用？

**56.** `auto`、`decltype`、`decltype(auto)` 在类型推导上各有什么规则差异？后置返回类型 `-> decltype(a+b)` 解决了什么问题？

**57.** placement new 是什么？为什么用了 placement new 之后必须手动调用析构函数，且不能用普通 `delete` 释放？

> [!success]- 参考答案（第七节）
> 51. 进入函数：`push ebp` 保存调用者栈底，`mov ebp, esp` 把当前栈顶设为新栈帧基址，之后 `sub esp, N` 为局部变量开空间；参数通过 `[ebp+8]`、`[ebp+0Ch]` 访问，局部变量通过 `[ebp-x]` 访问，返回值常放 EAX。退出：`mov esp, ebp` / `pop ebp` 恢复调用者栈底，`ret` 弹出返回地址跳回调用点。EBP=栈帧基准、ESP=实时栈顶、返回地址=call 自动压入的下一条指令地址。
> 52. 局部自动变量分配在**当前函数的栈帧**里，函数返回时栈帧被回收（ESP/EBP 恢复），那块内存随时可能被下一个调用覆盖。返回它的地址/引用，调用者拿到的是指向已失效栈帧的悬空引用，解引用是 UB。安全返回：`static`/全局变量引用、传入参数的引用、堆上 `new`（或智能指针管理）的对象。
> 53. `T&` 绑左值、可改实参；`const T&` 绑左值或右值、只读（大对象传参首选）；`T&&` 绑右值、用于移动语义/转移资源。`f(10)`：`10` 是右值，`f(int&&)` 精确匹配右值引用版本优先；`f(int&)` 不能绑右值。这正是按值类别重载、实现移动 vs 拷贝分流的基础。
> 54. 模板在编译期按使用类型实例化，编译器必须在每个使用它的翻译单元**看到完整定义**才能生成实例化代码，所以定义放头文件；而模板实例化的符号是 COMDAT/weak 的，链接器会折叠去重，不算违反 ODR。普通（非 inline）函数的符号是强符号，多个 TU 各定义一份就重复定义、违反 ODR。
> 55. 名称修饰是编译器把函数名连同参数类型编码成唯一符号名（如 `_Z4funci` vs `_Z4funcd`）。因为重载函数签名不同→修饰后符号不同，链接器能区分，故 C++ 支持重载；C 不修饰、函数名即符号，同名即冲突。`extern "C"` 关闭修饰，让符号是纯函数名，用于和 C 互操作，但代价是该函数不能重载。
> 56. `auto` 按初始值推导、**丢弃引用和顶层 const**（`auto a = rx` 得 `int`）；`decltype(expr)` 按表达式精确推导、**保留引用和 const**；`decltype(auto)` 像 auto 一样从初始化器推导但保留引用/const。后置返回类型让返回类型能引用形参名（普通前置写法里 `a`、`b` 还未声明），从而 `decltype(a+b)` 取得正确的提升后类型，避免大类型截断成小类型。
> 57. placement new `new (buf) T(args)` 在**已分配好的内存**上仅调用构造函数、不分配新内存。因此释放时不能 `delete`（它会调用 `operator delete` 去释放那块你并非用普通 new 得到的内存），必须**手动 `obj->~T()`** 调析构，再按 buf 实际的分配方式释放（如 `delete[] buf` 或释放内存池）。常用于内存池、容器预留空间后逐个构造。

## 八、概念辨析进阶

**58.** 辨析「函数重载」「函数模板」「模板特化」三者，各用一句口诀概括。

**59.** 辨析「拷贝构造函数」与「赋值运算符」：调用时机、是否需要释放旧资源、是否需要自赋值检查。

**60.** 辨析 `typedef`、`using`、`auto`、`decltype` 四者在"获取/命名类型"上的角色。

**61.** 辨析「函数指针」「函数对象（仿函数）」「`std::function`」「lambda」四种可调用体的差异与取舍。

**62.** 辨析顶层 const 与底层 const，并说明它们对「重载」「`auto` 推导」「能否绑定右值"分别有何影响。

**63.** 辨析 `__cdecl` / `__stdcall` / `__fastcall` / `__thiscall` 四种调用约定的关键差异。

> [!success]- 参考答案（第八节）
> 58. **重载**=同名不同参的多个独立函数（编译期按参数选）；**模板**=一份蓝图按类型生成多份函数（用时实例化）；**特化**=给模板的某个具体类型开小灶。口诀：重载靠"参数列表"，模板靠"类型推导"，特化靠"指定类型定制"。
> 59. 拷贝构造在**创建新对象**时调用（`T b = a;`），新对象无旧资源、不需释放、不需自赋值检查；赋值运算符在**对象已存在**时调用（`c = a;`），必须先释放自身旧资源、且要自赋值检查。口诀：有 `=` 且左边是"新生"就是拷贝构造，左边是"老对象"就是赋值。
> 60. `typedef`/`using` 给已知类型**起别名**（`using` 还支持模板别名，更直观）；`auto` 让编译器从**初始值**推导变量类型；`decltype` 从**表达式**推导类型且保留引用/const。前两者是"命名类型"，后两者是"推导类型"。
> 61. **函数指针**：最轻量、无状态、类型即签名，可指向自由函数；**仿函数**：重载 `operator()` 的类对象，可携带状态、易内联、类型安全；**lambda**：编译器自动生成的匿名仿函数，捕获即状态，写法最简；**`std::function`**：类型擦除的统一包装器，能装下以上任意可调用体，但有一点运行时开销（可能堆分配+间接调用）。口诀：要状态用仿函数/lambda，要统一存储/回调表用 `std::function`，要极致性能且无状态用函数指针或直接传 lambda（模板参数）。
> 62. 顶层 const 修饰对象本身（`const int`、`int* const`），底层 const 修饰所指内容（`const int*`、`const int&`）。对**重载**：底层构成、顶层不构成；对 **`auto` 推导**：顶层被丢弃（`auto` 从 `const int` 得 `int`），底层保留（从 `const int*` 得 `const int*`）；对**绑右值**：`const T&`（底层 const 引用）能绑右值，非 const 引用不能。
> 63. 都从右向左压栈；关键差异在**栈清理**和**寄存器传参**：`__cdecl` 调用者清栈、支持可变参数（printf）；`__stdcall` 被调用者清栈、不支持可变参数（Win32 API）；`__fastcall` 前两个参数走 ECX/EDX 寄存器、被调用者清栈；`__thiscall` 是成员函数专用、`this` 走 ECX。口诀：谁清栈 + 几个参数进寄存器。

## 九、大厂面试场景题

> 偏真实工程与系统/安全/高性能方向，会问"为什么""怎么排查""怎么优化""怎么设计"。

**64.** 一个线上服务接收外部输入，用 `char buf[256]; strcpy(buf, userInput);` 处理，安全团队报了高危漏洞。请说明漏洞原理、可能的危害，以及从代码到系统的多层防护手段。

**65.** 某函数返回了 `std::string&`，指向函数内的局部 `std::string`，本地测试正常、上线偶发乱码甚至崩溃。请解释为什么"偶发"，以及你如何快速定位这类悬空引用问题。

**66.** 团队代码里一个模板工具函数被大量类型实例化，编译产物体积暴涨、编译变慢。这是什么现象？从代码组织和编译/链接层面有哪些缓解手段？

**67.** 有人把热点路径上的小对象比较器写成了 `std::function<bool(const T&, const T&)>` 传给 `std::sort`，profiling 发现比传 lambda 慢很多。原因是什么？怎么改？

**68.** 排查一个"链接错误 `undefined reference to foo(int)`"和另一个"`multiple definition of bar`"。这两类错误分别通常由什么引起？各自怎么修？

**69.** 设计一个对象频繁创建销毁的粒子系统，`new/delete` 成了瓶颈。你会怎样用重载 `operator new/delete` 或内存池优化？需要注意什么？

**70.** 后缀 `operator++` 在循环 `for (auto it = c.begin(); it != c.end(); it++)` 里相比前缀有什么隐性开销？对自定义迭代器为什么强调写 `++it`？

> [!success]- 参考答案（第九节）
> 64. **现象**：`strcpy` 无边界检查，`userInput` 超过 256 字节就溢出 `buf`。**原因/危害**：溢出数据可覆盖栈上保存的 EBP 和**返回地址**，攻击者可劫持控制流跳到 shellcode（栈溢出攻击）。**解决（分层）**：代码层——改用 `std::string`/`std::vector` 或带长度的 `strncpy`/`snprintf`，永不信任输入长度；编译层——开启 Stack Canary（`-fstack-protector`）；系统层——ASLR 随机化地址、DEP/NX 让栈不可执行。**延伸**：根因是裸缓冲区+无界拷贝，Modern C++ 用 RAII 容器从源头消除。
> 65. **现象**：返回局部 `std::string` 的引用，函数返回后栈帧回收，引用悬空。**为什么偶发**：栈内存被回收但不会立即清零，下一次函数调用才覆盖它——在被覆盖前读到的可能仍是"看似正确"的旧值，所以本地轻负载测试常常蒙混过关，高并发下栈复用频繁才暴露乱码/崩溃。**定位**：用 AddressSanitizer（`-fsanitize=address`）能直接报 stack-use-after-return；编译器 `-Wreturn-local-addr`/`-Wdangling` 静态告警；code review 时盯函数返回的 `&`/引用是否指向局部。修复：返回值（靠移动/RVO）或返回 static/成员/堆对象。
> 66. **现象**：模板**代码膨胀（code bloat）**——每种类型实例化一份独立代码。**缓解**：① 把与类型无关的逻辑抽到非模板基函数，模板只做薄包装（thin template idiom）；② 对确定会用的类型用**显式实例化**集中到一个 TU，别处 `extern template` 声明，避免重复实例化；③ 依赖链接器 COMDAT 折叠去重相同实例；④ 控制模板参数维度（如非类型参数组合爆炸）。延伸：见 [[9.2.7 函数模版本质（汇编）]]。
> 67. **现象**：`std::function` 比直接传 lambda 慢。**原因**：`std::function` 是**类型擦除**包装，每次调用经过一次间接（虚）调用，且可能堆分配存储被包装对象，编译器难以内联比较器；而把 lambda 作为模板参数传给 `std::sort`，比较器类型在编译期已知，可被**完全内联**。**解决**：让 `sort` 的比较器走模板形参（直接传 lambda/仿函数），把 `std::function` 留给确实需要"统一类型容器/延迟绑定"的场景。
> 68. `undefined reference`：声明了但**链接期找不到定义**——常因只 `#include` 了声明却没编译/链接对应 `.cpp`、库未链接、`extern "C"` 与 C++ 修饰不一致、模板定义没在头文件。修：补上定义所在的目标文件/库、确保模板定义可见。`multiple definition`：同一强符号被**定义多次**——常因非 inline 函数/全局变量定义写在了头文件并被多个 TU 包含。修：头文件只放声明、定义放单个 `.cpp`，或加 `inline`/`static`（内部链接）。
> 69. 用**类特定的 `operator new/delete`** 接管该类内存：维护一个空闲块链表/内存池，`operator new` 从池里取（池空才向系统申请），`operator delete` 把块归还池而非真正释放，省去频繁 malloc/free 与系统调用。注意：① `operator new/delete` 是隐式静态成员；② `new[]`/`delete[]` 要配套重载并匹配使用；③ 分配失败抛 `std::bad_alloc`、`delete` 应 `noexcept` 且容忍 `nullptr`；④ 多线程要加锁或用每线程池；⑤ 对齐要满足。也可直接用 `std::pmr` 内存资源。
> 70. 后缀 `it++` 要先**拷贝一份旧迭代器**作为返回值，再自增原对象——多一次拷贝构造和析构。内置指针类型编译器能优化掉，但**自定义迭代器**（可能持有多个成员、甚至堆资源）的拷贝并不廉价，循环里这次拷贝的返回值通常被丢弃，纯属浪费。所以惯例写 `++it`：前缀直接自增返回引用、零拷贝。

## 十、补充加分题

**71.**【复杂度/性能分析】对比"普通递归求阶乘 `factorial(n)`"与"尾递归 `factorial_tail(n, acc)`"在时间复杂度、空间复杂度、栈帧使用上的差异。为什么尾递归在支持 TCO 的编译器上能做到 O(1) 栈空间？没有 TCO 时呢？

**72.**【汇编】下面是 `__cdecl` 调用 `add(3, 5)` 的汇编，请解释每条指令，并指出"谁清理栈"。
```asm
push 5
push 3
call add
add esp, 8
```

**73.**【模板汇编本质】解释为什么 `ave(short(100), short(200))` 和 `ave(short(300), short(400))` 调用同一个函数地址，而 `ave(100, 200)`（int）调用另一个地址。这对二进制体积意味着什么？

**74.**【源码设计】`std::vector::operator[]` 不做边界检查而 `at()` 做，这是有意的设计权衡。请分别说明两者的取舍，以及你在自定义容器里会怎么设计。

> [!success]- 参考答案（第十节）
> 71. 两者时间都是 **O(n)**（n 次乘法/调用）。普通递归：每层 `return n * factorial(n-1)`，递归调用后还有乘法待做，必须保留本层栈帧等子调用返回，栈深 **O(n)**，n 大时栈溢出。尾递归：递归调用是函数**最后一个操作**，本层无后续计算，编译器可把它优化成跳转、复用同一栈帧（TCO），空间降到 **O(1)**。但 TCO 不是标准强制（MSVC Debug、未开优化时常不做），**没有 TCO 时尾递归仍是 O(n) 栈**，深递归该改成显式迭代。
> 72. `push 5`/`push 3`：参数从右向左压栈（先 b=5 后 a=3）；`call add`：把返回地址压栈并跳转到 add；`add esp, 8`：调用返回后**调用者**把 ESP 上移 8 字节（2 个 int），清理掉刚才压入的参数。"谁清栈"——`__cdecl` 由**调用者**清，这也是它能支持可变参数的原因（调用者知道压了几个）。
> 73. 函数模板按**类型**实例化：`short` 版本 `ave<short>` 是一份独立代码、固定地址，两次 short 调用只是数值不同、复用同一实例；`int` 调用需要 `ave<int>`，是另一份代码、另一个地址。意味着模板的二进制体积随**用到的不同类型种数**增长（code bloat），而非随调用次数增长；相同类型的大量调用不增加代码量。
> 74. `operator[]`：不检查边界，换取**零开销**的高频随机访问（热点路径、已知索引安全时），代价是越界即 UB；`at()`：每次检查并在越界时抛 `std::out_of_range`，**安全但有分支开销**，适合索引来自外部/不可信输入。自定义容器设计：提供两者——`operator[]` 走快路径（可在 Debug 下加 `assert` 兜底），`at()` 走安全路径；让调用方按场景选择"性能"还是"安全"。

## 十一、模板与重载决议专项

> 本章模板/重载内容密集，单列一节强化"编译期到底选了谁"的推理能力。

**75.** 给定下列重载，逐一判断每个调用选中哪个版本并说明理由。
```cpp
void f(int);          // (1)
void f(double);       // (2)
void f(const int*);   // (3)
template <typename T> void f(T);   // (4)

f('a');               // a
f(3.14f);             // b
int x = 0; f(&x);     // c
f("hi");              // d
```

**76.** 下面代码能编译吗？如果报二义性，给出修复方案。
```cpp
void g(int a, double b);
void g(double a, int b);
int main() { g(1, 1); }
```

**77.** 解释非类型模板参数为何会"成倍"增加实例数量。下面会生成几个不同的函数实例？
```cpp
template <typename T, int Max>
T clamp(T v) { return v > Max ? Max : v; }
int main() {
    clamp<int, 100>(50);
    clamp<int, 100>(80);
    clamp<int, 200>(150);
    clamp<double, 100>(3.0);
}
```

**78.** `template <typename T> T bigger(T a, T b)` 对 `int*` 直接用会比较指针地址而非指向值。请用「全特化」和「普通函数重载」两种方式各修复一次，并说明若两者同时存在，`bigger(px, py)` 会调用哪个。

> [!success]- 参考答案（第十一节）
> 75.
> - **a** `f('a')`：`char` 经整型提升到 `int`，精确匹配的非模板 (1) 优先于模板 (4) → **选 (1)**。
> - **b** `f(3.14f)`：`float` 提升到 `double`，匹配 (2)；非模板优先于模板 → **选 (2)**。
> - **c** `f(&x)`：实参 `int*`，(3) 需 `int*`→`const int*` 的 const 转换可匹配；模板 (4) 可推 `T=int*` 精确匹配。模板这里是更好的匹配（无需 const 转换），但通用规则是"非模板同样好时优先非模板"——此处模板严格更优（精确）→ **选 (4) `f<int*>`**。（若把 (3) 改成 `int*` 精确，则非模板优先选 (3)。）
> - **d** `f("hi")`：字面量类型 `const char[3]`，(1)/(2)/(3) 都不精确匹配（(3) 需数组→`const int*`？类型不符），模板 (4) 推导 `T=const char*` → **选 (4)**。
>   （要点：精确匹配的非模板 > 精确匹配的模板 > 需转换的非模板。）
> 76. **不能编译，二义性**。`g(1,1)` 对 (1) 需第二参 `int→double`，对 (2) 需第一参 `int→double`，两者各需一次同级标准转换、无人更优 → ambiguous。修复：显式转换消歧，`g(1, static_cast<double>(1));`（选第一个）或 `g(static_cast<double>(1), 1);`（选第二个）。
> 77. 非类型参数的**每个不同取值**都参与实例化键，等价于又多了一维类型。本例生成 **3 个**实例：`clamp<int,100>`（前两次调用复用）、`clamp<int,200>`、`clamp<double,100>`。即 `(T, Max)` 组合各异就各生成一份——这是非类型参数容易引发 code bloat 的原因。
> 78.
> ```cpp
> // 通用模板
> template <typename T> T bigger(T a, T b) { return a > b ? a : b; }
> // 方式一：全特化
> template <> int* bigger<int*>(int* a, int* b) { return *a > *b ? a : b; }
> // 方式二：普通函数重载
> int* bigger(int* a, int* b) { return *a > *b ? a : b; }
> ```
> 若特化与普通函数同时存在，`bigger(px, py)` 调用**普通函数重载**——优先级"普通函数 > 模板特化 > 通用模板"。

## 十二、栈帧与底层专项（含画图）

> 系统编程视角：把抽象的"函数调用"落到内存布局上。

**79.**【画图题】用 ASCII 画出一次函数调用时栈帧从高地址到低地址的布局，标出「参数」「返回地址」「保存的 EBP」「局部变量/缓冲区」分别在 `[ebp±x]` 的哪一侧，并指出栈溢出攻击通常覆盖哪一项。

**80.**【画图/分析】画出 `factorial(3)` 递归调用时栈的增长方向与各栈帧的入栈/出栈顺序，并说明为什么递归过深会栈溢出。

**81.** 结合静态变量的存储位置画出/列出一个程序的主要内存区段（代码区、`.data`、`.bss`、堆、栈），并把下列对象各归到对应段：函数代码、`static int x=10`、`static int y`（未初始化）、函数内局部 `int`、`new int` 的对象、字符串字面量 `"abc"`。

> [!success]- 参考答案（第十二节）
> 79.
> ```
> 高地址
> ├─────────────────────────┤
> │ 参数 arg2 / arg1         │  [ebp+0Ch], [ebp+8]   ← 调用者压入
> ├─────────────────────────┤
> │ 返回地址 (Return Addr)   │  [ebp+4]              ← call 自动压入
> ├─────────────────────────┤
> │ 保存的 EBP (Saved EBP)   │  [ebp]                ← push ebp
> ├─────────────────────────┤
> │ 局部变量 / buffer[]      │  [ebp-4], [ebp-8]...  ← sub esp 开辟
> ├─────────────────────────┤
> 低地址 (ESP 栈顶)
> ```
> 局部缓冲区在低地址、返回地址在高地址；`strcpy` 等向 buffer 写入超长数据时，数据从低地址往高地址覆盖，依次盖掉 Saved EBP 和**返回地址**（`[ebp+4]`）——这正是栈溢出攻击劫持控制流的目标。Stack Canary 就插在局部变量与返回地址之间放哨。
> 80.
> ```
> 栈向低地址增长 ↓（先调用先入栈，后调用先返回 —— LIFO）
> ┌────────────────┐ 高地址
> │ main() 栈帧     │
> ├────────────────┤
> │ factorial(3)    │ ← 最先入栈
> ├────────────────┤
> │ factorial(2)    │
> ├────────────────┤
> │ factorial(1)    │
> ├────────────────┤
> │ factorial(0)    │ ← 最后入栈，命中 base case 最先返回（return 1）
> └────────────────┘ 低地址（ESP）
> ```
> 每层递归都新建一个栈帧（参数+返回地址+局部），直到 base case 才逐层返回、出栈。递归过深时栈帧累积超过线程栈大小（通常几 MB），就栈溢出崩溃——所以无 base case 的无限递归必崩，深递归应改迭代。
> 81.
> ```
> ┌───────────────┐ 低地址
> │ 代码区 .text   │  函数代码、成员函数代码、字符串字面量"abc"(常在.rodata)
> ├───────────────┤
> │ .data         │  static int x = 10（已初始化非零）
> ├───────────────┤
> │ .bss          │  static int y（未初始化/零，加载时清零）
> ├───────────────┤
> │ 堆 (heap)     │  new int 分配的对象（手动/智能指针管理）
> │      ↓        │
> │      ↑        │
> │ 栈 (stack)    │  函数内局部 int、函数参数（随调用创建销毁）
> └───────────────┘ 高地址
> ```
> 归段：函数代码→代码区；`"abc"`→只读常量区(.rodata)；`static int x=10`→`.data`；`static int y`→`.bss`；局部 `int`→栈；`new int`→堆。要点：static 不在栈上，故跨调用保值。
