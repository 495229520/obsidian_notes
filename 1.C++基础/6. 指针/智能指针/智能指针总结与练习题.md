# 智能指针总结与练习题

> 基于 [[独享智能指针]]、[[共享智能指针]]、[[weak_ptr]] 三篇笔记的提炼总结。

---

## 一、知识体系总览

三种智能指针的分工：

| 类型 | 所有权 | 拷贝 | 典型场景 |
|------|--------|------|----------|
| `unique_ptr` | 独占 | 不可拷贝，只能 move | 工厂函数、局部资源管理、容器元素 |
| `shared_ptr` | 共享（引用计数） | 可拷贝 | 多个持有者、异步任务共享资源 |
| `weak_ptr` | 不拥有（弱引用） | 可拷贝 | 打破循环引用、缓存、观察者 |

---

## 二、unique_ptr 核心要点

### 1. 零开销抽象
- 默认删除器下 `sizeof(unique_ptr<T>) == sizeof(T*)`（通常 8 字节）
- 有状态删除器会增加大小（函数指针 → 16 字节，有状态 lambda → 更大）

### 2. 关键接口
| 操作 | 效果 |
|------|------|
| `make_unique<T>(args)` | 推荐创建方式（C++14），异常安全 |
| `get()` | 获取原始指针，**不释放所有权** |
| `release()` | 释放所有权，返回原始指针，**调用者负责 delete** |
| `reset(p)` | 释放旧对象，接管新对象 |
| `reset()` | 释放对象，变为空指针 |
| `std::move(p1)` | 转移所有权，p1 变为 nullptr |

### 3. 关键设计点
- 不可拷贝（拷贝构造和拷贝赋值被 `= delete`）
- 支持移动语义（移动构造 + 移动赋值）
- 可以隐式 `std::move` 转换为 `shared_ptr`
- 支持自定义删除器（模板第二个参数）

---

## 三、shared_ptr 核心要点

### 1. 控制块与内存布局
```
shared_ptr 实例               控制块
┌──────────────┐     ┌──────────────────────┐
│ 对象指针      │────→│ shared_count (atomic) │
│ 控制块指针    │──┐  │ weak_count  (atomic) │
└──────────────┘  │  │ 删除器 / 分配器       │
                  └─→└──────────────────────┘
```

- `sizeof(shared_ptr<T>)` = 2 个指针（16 字节）
- `make_shared` 一次分配对象+控制块，`new + shared_ptr` 两次分配

### 2. 线程安全边界
- ✅ 引用计数增减：线程安全（`std::atomic`）
- ❌ 所管理对象的访问：不是线程安全的
- ❌ 同一个 `shared_ptr` 实例的并发写入：不是线程安全的

### 3. enable_shared_from_this
- 解决"在成员函数中获取自身的 `shared_ptr`"问题
- 原理：内部存储一个 `weak_ptr`，`shared_from_this()` 通过它构造 `shared_ptr`
- 前提：对象必须已被某个 `shared_ptr` 管理，否则抛出 `std::bad_weak_ptr`
- 典型错误：`std::shared_ptr<T>(this)` — 创建独立的控制块，导致双重删除

### 4. make_shared 的局限
- 不支持自定义删除器
- 当 `weak_ptr` 存在时，即使对象已销毁，控制块+对象的内存块也不会释放

---

## 四、weak_ptr 核心要点

### 1. 定位
- 一种**弱引用**，指向 `shared_ptr` 管理的对象，但**不增加 shared_count**
- 不能直接解引用，必须通过 `lock()` 获取 `shared_ptr`

### 2. 关键接口
| 方法 | 说明 |
|------|------|
| `lock()` | 对象存在 → 返回有效的 `shared_ptr`；已销毁 → 返回空 |
| `expired()` | 对象是否已销毁（等价于 `use_count() == 0`） |
| `use_count()` | 返回 shared_count（调试用） |
| `reset()` | 释放弱引用 |

### 3. 循环引用解决模式
```
Parent ──shared_ptr──→ Child
Child  ──weak_ptr────→ Parent    ← 这里用 weak_ptr 是關鍵
```
- 规则：**拥有者用 shared_ptr，被拥有者用 weak_ptr**
- 常见模式：树结构中父→子用 shared_ptr，子→父用 weak_ptr；observer 模式

---

## 五、三种指针选择决策树

```
需要动态分配对象？
  ├─ 只有一个拥有者？
  │   └─ 是 → unique_ptr（首选，可随时转为 shared_ptr）
  │
  ├─ 多个拥有者？
  │   └─ 是 → shared_ptr
  │       └─ 是否存在循环引用风险？
  │           └─ 是 → 用 weak_ptr 打破循环
  │
  └─ 只是观察，不拥有？
      └─ 是 → weak_ptr
```

---

## 六、常见陷阱速查

| 陷阱 | 说明 |
|------|------|
| 用 `get()` 返回的指针 delete | 导致双重释放 |
| `release()` 后忘记 delete | 内存泄漏 |
| `shared_ptr<T>(this)` | 多个控制块 → 双重删除 |
| 两个 shared_ptr 互相引用 | 循环引用 → 内存泄漏 |
| 用同一个裸指针构造两个 shared_ptr | 两个独立控制块 → 双重删除 |
| unique_ptr 误用拷贝 | 编译错误，应用 std::move |

## 参考答案

### Q1
**问题**：用同一个裸指针构造两个 `unique_ptr`，两者都认为自己独占所有权，作用域结束时都会 delete，导致**双重释放（double free）**。
**修复**：
```cpp
auto p1 = std::make_unique<int>(42);  // 直接用 make_unique
// 或者
auto p2 = std::move(p1);  // 转移所有权，p1 变为 nullptr
```

### Q2
```
1      // expired() → true（sp 已 reset）
0      // use_count() → 0（没有 shared_ptr 指向对象）
```

### Q3
unique_ptr 作为函数参数有三种方式：
- **按值传递** `f(unique_ptr<T> p)`：转移所有权，调用方必须 `std::move` 或传临时对象。调用后原指针失效。
- **按引用传递** `f(unique_ptr<T>& p)`：不转移所有权，函数可以修改指针内容。调用后原指针仍有效。
- **按 const 引用传递** `f(const unique_ptr<T>& p)`：不转移所有权，函数只能读取。一般不推荐（如果只是读取指向的对象，直接传 `const T*` 或 `const T&` 更好）。

### Q4
不能编译。`unique_ptr` 不可拷贝，`f(p1)` 试图拷贝 `p1`。需要改为：
```cpp
f(std::move(p1));  // p1 的所有权转移到函数参数，调用后 p1 == nullptr
```
如果不想转移所有权，应该将 `f` 的签名改为 `f(const std::unique_ptr<int>& p)` 或直接传 `int*` / `int&`。

### Q5
- `sp1 = shared_ptr<Widget>(new Widget)`：2 次分配（Widget 对象 + 控制块）
- `sp2 = sp1`：0 次分配（引用计数从 1 → 2）
- `sp3 = make_shared<Widget>()`：1 次分配（对象+控制块合并）
- `sp2 = sp3`：sp1/sp2 指向的旧 Widget 引用计数从 2 → 1（sp1 还持有），sp3 指向的新 Widget 从 1 → 2

### Q6
**写法 B 更好**。原因：
- 异常安全：如果 `process` 的另一个参数在求值时抛出异常，写法 A 中 `new Widget` 可能泄漏
- 内存分配效率：`make_shared` 一次分配 vs `new + shared_ptr` 两次分配
- 代码简洁

### Q7
`shared_from_this()` 依赖对象内嵌的 `weak_ptr`（从 `enable_shared_from_this` 继承），这个 `weak_ptr` 只有在对象首次被 `shared_ptr` 接管时才被初始化。构造函数执行时，对象还没有被任何 `shared_ptr` 接管，`weak_ptr` 未初始化，调用 `shared_from_this()` 会导致未定义行为或抛出 `std::bad_weak_ptr`。

### Q8
LRU Cache 使用 `weak_ptr` 的原因：
- Cache 不应该阻止对象被释放（不拥有所有权）
- 当外部没有 `shared_ptr` 持有对象时，对象应能正常释放，cache 条目自动失效
- 每次访问 cache 时 `lock()` 检查是否仍然有效

```cpp
template<typename K, typename V>
class LRUCache {
    std::unordered_map<K, std::weak_ptr<V>> cache;
public:
    std::shared_ptr<V> get(const K& key) {
        auto it = cache.find(key);
        if (it != cache.end()) {
            if (auto sp = it->second.lock()) {
                return sp;  // 对象仍存在
            }
            cache.erase(it);  // 对象已销毁，清理 cache
        }
        return nullptr;
    }
};
```

### Q9
**不合理**。`parent` 使用 `shared_ptr` 会导致循环引用：
- 父节点通过 `children` 持有子节点的 `shared_ptr`
- 子节点通过 `parent` 持有父节点的 `shared_ptr`
- 两者互相持有，引用计数永远不会归零 → 内存泄漏

**修正**：
```cpp
struct TreeNode {
    int value;
    std::weak_ptr<TreeNode> parent;  // 子→父用 weak_ptr
    std::vector<std::shared_ptr<TreeNode>> children;
};
```

### Q10
```cpp
class WidgetFactory {
public:
    // 返回 unique_ptr：调用方获得独占所有权
    // 调用方可根据需要转换为 shared_ptr
    std::unique_ptr<Widget> createWidget(int id) {
        return std::make_unique<Widget>(id);
    }
};
```

设计理由：
- 返回 `unique_ptr` 给调用方最大的灵活性——可以独占使用，也可以 `std::move` 转为 `shared_ptr`
- 如果返回 `shared_ptr`，调用方无法转为 `unique_ptr`（不可逆）
- 工厂不持有 Widget，用 `unique_ptr` 返回表达所有权转移语义最自然
- 异常安全：构造过程中抛异常，`unique_ptr` 自动释放

### Q11
"C 语言的 `malloc/free` 需要手动管理，容易忘记释放或重复释放。C++ 的三类智能指针用 RAII 自动管理内存：`unique_ptr` 独占资源，不能拷贝只能转移，相当于'这东西是我的，别人别碰'；`shared_ptr` 共享资源，通过引用计数在所有持有者都放弃后自动释放，相当于'大家一起用，最后一个走的关灯'；`weak_ptr` 不参与所有权，只是偶尔观察一下资源还在不在，专门解决 `shared_ptr` 互相引用导致无法释放的问题。"

### Q12
- **(1) 安全**：`local = g_data` 拷贝 `shared_ptr`，引用计数原子增加，多线程安全
- **(2) 安全**：读取操作，如果有其他线程同时写 `local->set_value()`，则不安全；但仅从 `shared_ptr` 管理的对象访问而言，这是普通的数据竞争问题
- **(3) 不安全**：多个 reader 线程同时读/写 `Data` 的同一个字段，不是线程安全的。需要互斥锁保护 `Data` 内部状态
- **(4) 安全**：对 `g_data` 的赋值是原子的（`shared_ptr` 的赋值和析构操作线程安全）

**核心要点**：`shared_ptr` 本身的引用计数操作是线程安全的，但这只保证对象不会被提前释放。对象内部数据的并发读写仍然需要额外的同步机制。
