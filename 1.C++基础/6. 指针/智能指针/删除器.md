# 删除器（deleter）

删除器是智能指针持有的可调用对象，负责在需要清理资源时执行释放动作。`unique_ptr`、`shared_ptr` 决定何时结束资源的所有权，删除器决定届时调用 `delete`、`fclose`、`free`，还是资源库提供的销毁函数。

## 1. 删除器、析构函数与 RAII

`std::unique_ptr<T>` 的完整类型是 `std::unique_ptr<T, std::default_delete<T>>`。第二个模板参数指定删除器类型；默认删除器对单个对象执行 `delete`，数组版本 `std::default_delete<T[]>` 执行 `delete[]`。

删除器和 [[12.1.7 析构函数|析构函数]] 的职责不同。对于普通类对象，`delete p` 会调用对象的析构函数，再释放它占用的存储；只调用析构函数不会自动归还这块内存。自定义删除器则按资源的约定执行清理，例如 `fclose` 关闭文件流，归还对象池的操作甚至可以保留对象，留给下一次复用。

| 资源如何获得 | 对应的清理动作 |
|---|---|
| `new T` / `new T[]` | `delete` / `delete[]` |
| `malloc`、`calloc` | `free` |
| `fopen` | `fclose` |
| POSIX `open`、`socket` | `close` |
| 对象池 `acquire` | 该对象池的 `release` |
| `ibv_reg_mr` | `ibv_dereg_mr` |
| `cudaMalloc` | `cudaFree` |

获取和释放方式必须匹配，`malloc` 得到的内存不能交给默认执行 `delete` 的智能指针。普通 C++ 对象仍优先用 `std::make_unique` 或 `std::make_shared` 创建；对接 C API 时，再把返回的资源句柄立即交给带自定义删除器的所有者。

RAII 把清理动作绑定到所有者的析构上。局部所有者在正常离开作用域、提前 `return`，或异常栈展开经过该作用域时，都会执行析构。这个保证依赖析构确实发生；`std::abort`、强制结束进程等情况不能靠 RAII 收尾。

## 2. 用 unique_ptr 包装文件资源

[[独享智能指针|unique_ptr]] 的类型形式是 `std::unique_ptr<T, D>`。`T` 表示被管理的对象类型，`D` 表示删除器类型。普通情况下可以把它理解为“资源指针 + 删除器对象”；严格说，`D::pointer` 还可以指定满足要求的自定义指针类型。

下面是一个完整的 C++17 示例。`FileCloser` 定义 `operator()`，因此 `closer(fp)` 就等价于调用 `closer.operator()(fp)`。文件指针在创建后立即交给 `FilePtr`，后续分支不必重复写关闭操作。

```cpp
#include <cstdio>
#include <memory>

struct FileCloser {
    void operator()(std::FILE* fp) const noexcept {
        if (fp != nullptr) {
            (void)std::fclose(fp);
        }
    }
};

using FilePtr = std::unique_ptr<std::FILE, FileCloser>;

int main() {
    FilePtr file(std::tmpfile());
    if (!file) {
        return 1;
    }
    std::puts("file acquired");
    file.reset();
    std::puts("owner cleared");
}
```

创建成功时输出两行：`file acquired`、`owner cleared`。`reset()` 调用删除器关闭旧文件，再让所有者保持为空；末尾析构不会再关一次。换成 `std::fopen("test.txt", "r")` 也使用相同的删除器，但要处理文件不存在的情况。这里忽略关闭返回值只用于演示生命周期；如果写入结果依赖关闭时的刷新，应显式检查 `fclose` 的结果。

函数指针和 lambda 也能作删除器。以下是两种替代声明，使用时选一种即可；头文件同上。

```cpp
auto close_file = [](std::FILE* fp) noexcept {
    if (fp != nullptr) {
        (void)std::fclose(fp);
    }
};
std::unique_ptr<std::FILE, decltype(close_file)> file1(
    std::tmpfile(), close_file);

std::unique_ptr<std::FILE, decltype(&std::fclose)> file2(
    std::tmpfile(), &std::fclose);
```

`decltype(close_file)` 取得该 lambda 的闭包类型；在 C++17 中，即使无捕获，也需要把这个 lambda 对象传给构造函数。函数指针版本则显式传入 `&std::fclose`，不能让它成为空函数指针。`fclose` 返回 `int` 没有关系，智能指针不会使用这个返回值。

函数指针版本能够直接使用 `fclose`，是因为空的 `unique_ptr` 不调用删除器。若把这个删除器用于带空指针的 `shared_ptr`，就需要额外判空。

| 操作 | 对当前资源的影响 |
|---|---|
| 非空 `unique_ptr` 析构 | 调用它持有的删除器 |
| `reset()` | 清理旧资源，变为空 |
| `get()` | 借出指针，所有权保留 |
| `release()` | 返回指针并放弃所有权，**不调用删除器** |
| 移动构造另一个 `unique_ptr` | 转移资源和删除器，原所有者变为空 |

`release()` 后必须有明确的接管者，否则资源会泄漏。不要为了观察地址就调用它，也不要对 `get()` 返回的指针手动释放。具体行为可查 [标准草案中的 release 与 reset](https://eel.is/c++draft/unique.ptr.single.modifiers)。

## 3. 删除器怎样影响类型和内存布局

`std::unique_ptr<T, D1>` 和 `std::unique_ptr<T, D2>` 是不同类型，即使两个删除器执行完全相同的动作。编译器知道具体的 `D`，通常可以内联调用；删除器仍然是对象的一部分，并非“只存在于类型里”。空删除器的存储常被空基类优化或 `[[no_unique_address]]` 消除，后者是 C++20 的语言特性。

下面的大小只是常见 64 位实现中的观察值，不能当作标准保证。实际结果还受指针表示、对齐、库实现和删除器类型影响。

| 删除器形式 | 通常需要保存什么 | 常见的 `unique_ptr` 大小 |
|---|---|---|
| 默认删除器、空函数对象、无捕获 lambda | 资源指针；删除器存储可被压缩 | 8 字节 |
| 函数指针 | 资源指针 + 函数地址 | 16 字节 |
| 带一个指针的函数对象或 lambda | 资源指针 + 状态指针 | 16 字节 |

有状态删除器适合记录“资源应该归还给谁”。下面是接口片段，假设项目已经定义 `Buffer`、`BufferPool`，且池提供不抛异常的 `release(Buffer*)`：

```cpp
struct PoolDeleter {
    BufferPool* pool;  // 借用池，不拥有池

    void operator()(Buffer* buffer) const noexcept {
        pool->release(buffer);
    }
};

using BufferPtr = std::unique_ptr<Buffer, PoolDeleter>;

BufferPtr acquire_buffer(BufferPool& pool) {
    return BufferPtr(pool.acquire(), PoolDeleter{&pool});
}
```

`BufferPtr` 销毁时将缓冲区交还给原来的池。`pool` 必须比所有借出的 `BufferPtr` 活得更久；保存一个裸指针并不会延长池的生命周期。这里的裸指针表达借用，缓冲区的归还责任由 `BufferPtr` 承担。

[[共享智能指针|shared_ptr]] 则把删除器的具体类型隐藏在共享管理机制中。常见实现将删除器、强弱引用计数和资源管理信息放进控制块；`shared_ptr<T>` 本身通常保存对象指针和控制块指针。因此，不同删除器可以对应同一个 `std::shared_ptr<T>` 类型。

![[图片/SVG/删除器-所有权与释放路径.svg|900]]

图中画的是自定义删除器的常见实现模型，不是标准规定的成员布局。`shared_ptr` 的别名构造还允许 `get()` 指向子对象，而控制块仍管理原资源；不能据此把删除器理解成总是接收当前的 `get()`。

沿用前面的 `FileCloser`，共享文件所有权可以这样写：

```cpp
std::shared_ptr<std::FILE> first(std::tmpfile(), FileCloser{});
if (!first) {
    return 1;
}
auto second = first;
first.reset();   // second 仍持有所有权，文件保持打开
second.reset();  // 最后一个强所有者退出，调用 FileCloser
```

这段代码可替换完整示例中 `main` 的函数体。即使删除器换成判空后调用 `fclose` 的 lambda，指针类型仍然是 `std::shared_ptr<std::FILE>`。若存在 [[弱引用智能指针|weak_ptr]]，资源释放后控制块可能继续存活，但不会因此再次执行资源清理。可对照 [shared_ptr 的析构规则](https://eel.is/c++draft/util.smartptr.shared.dest)。

`std::make_shared` 和 `std::make_unique` 都没有接收自定义删除器的重载；传入的普通参数用于构造被管理对象。需要自定义清理时，使用对应的智能指针构造函数。

## 4. RDMA 资源的 RAII 包装

在 [[4.4 内存注册与零拷贝|内存注册]] 中，`ibv_reg_mr` 创建 MR，`ibv_dereg_mr` 注销 MR。MR 的所有者负责撤销注册，底层缓冲区仍由另一位所有者管理。

下面是 Linux/libibverbs 的接口片段。删除器检查注销结果；这里选择在清理失败时终止进程，避免继续释放可能仍被注册的缓冲区。这是一种明确的失败策略，项目也可以设计可报告、可恢复的显式关闭接口。

```cpp
#include <infiniband/verbs.h>
#include <cstddef>
#include <exception>
#include <memory>
#include <stdexcept>

struct MRDeleter {
    void operator()(ibv_mr* mr) const noexcept {
        if (mr != nullptr && ibv_dereg_mr(mr) != 0) {
            std::terminate();
        }
    }
};

using MRPtr = std::unique_ptr<ibv_mr, MRDeleter>;
```

工厂函数只接管返回的 MR，不接管传入的 PD 和缓冲区。注册失败时还没有 MR 需要清理，可以正常抛出异常通知调用者。

```cpp
MRPtr register_memory(ibv_pd* pd, void* buffer, std::size_t size) {
    MRPtr mr(ibv_reg_mr(pd, buffer, size,
        IBV_ACCESS_LOCAL_WRITE | IBV_ACCESS_REMOTE_WRITE));
    if (!mr) {
        throw std::runtime_error("ibv_reg_mr failed");
    }
    return mr;
}
```

返回的 `MRPtr` 独占注册资源，调用者必须保证 PD 和缓冲区一直有效，直到 MR 成功注销。远程写权限需要同时启用本地写权限；`ibv_dereg_mr` 成功返回 0，失败返回错误码，仍有 Memory Window 绑定时可能失败。这些约定来自 [libibverbs 的 MR 手册](https://github.com/linux-rdma/rdma-core/blob/master/libibverbs/man/ibv_reg_mr.3)。

多个资源组成连接对象时，可以利用成员按声明逆序析构的规则，但要先理清依赖：QP 依赖 PD 和关联的 CQ，MR 依赖 PD 以及注册的缓冲区。一个简化组合可以按 `context → PD → CQ → buffer → MR → QP` 的顺序声明，使销毁按反方向进行。QP 的关联关系见 [libibverbs 的 QP 手册](https://github.com/linux-rdma/rdma-core/blob/master/libibverbs/man/ibv_create_qp.3)。

这个顺序仅处理对象间的生命周期关系。关闭前仍要停止提交新请求，并按协议和 verbs 约定结束相关本地、远程访问；成员逆序析构不会自动等待所有异步操作完成。

## 5. 使用时守住的边界

删除器必须不抛异常，通常把 `operator()` 声明成 `noexcept`。这不是只在异常栈展开时才成立：标准对 `unique_ptr` 析构调用删除器时抛出的异常明确规定为未定义行为；异常若试图离开 `noexcept` 函数，则会调用 `std::terminate`。`noexcept` 不会把可能失败的清理动作变成成功。规则见 [unique_ptr 析构约定](https://eel.is/c++draft/unique.ptr.single.dtor)。

`unique_ptr` 在空指针时跳过删除器，`shared_ptr(nullptr, deleter)` 则建立了带删除器的所有权组，最后一个强所有者退出时仍会调用 `deleter(nullptr)`。这也是前面 `FileCloser` 保留判空的原因。默认构造的空 `shared_ptr` 没有这种清理动作，参见 [shared_ptr 自定义删除器构造规则](https://eel.is/c++draft/util.smartptr.shared.const)。

一个资源只能被接管一次。不要从同一个 `get()` 分别构造两个独立所有者，否则可能重复关闭或重复释放。需要共享就复制已有的 `shared_ptr`，需要转交独占所有权就移动 `unique_ptr`；删除器不会替程序识别所有权冲突。

整数句柄需要单独设计。POSIX 文件描述符的无效值是 `-1`，而 `0` 也是合法描述符，不能直接当普通指针塞进 `unique_ptr`。专用的 `unique_fd` 包装通常更清楚；为保存一个 fd 额外分配一个 `int`，还会增加一次堆分配和一份内存清理责任。

清理函数可能失败时，应区分“已经调用清理”与“清理成功”。文件关闭、MR 注销的返回值不会由智能指针传给调用者。如果业务必须知道结果，就在正常流程中提供可检查的关闭操作，并让析构承担不抛异常的兜底清理。
