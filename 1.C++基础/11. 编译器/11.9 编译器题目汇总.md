## 一、选择题（概念基础）

**1.** C++ 程序从源码到可执行文件的标准阶段顺序是：
- A. 编译 → 预处理 → 汇编 → 链接
- B. 预处理 → 编译 → 汇编 → 链接
- C. 预处理 → 汇编 → 编译 → 链接
- D. 编译 → 汇编 → 链接 → 预处理

**2.** 关于「翻译单元 (Translation Unit)」，正确的是：
- A. 一个 `.cpp` 文件本身就是翻译单元，与头文件无关
- B. 翻译单元 = 源文件 + 所有 `#include` 头文件（递归预处理展开后）
- C. 整个工程的所有源文件合起来是一个翻译单元
- D. 翻译单元是链接阶段才形成的单位

**3.** 对于**非 inline、外部链接**的普通函数，ODR 规定在整个程序中可以有几个定义？
- A. 每个翻译单元一个　　B. 任意多个，只要相同
- C. 整个程序恰好一个　　D. 不限

**4.** 关于 `inline` 关键字，正确的是：
- A. 保证函数一定被内联展开
- B. 只是对编译器的建议，编译器可忽略，但允许多翻译单元重复定义
- C. 会强制关闭所有优化
- D. 只能用于成员函数

**5.** 在命名空间作用域定义 `const int N = 10;`（无 `extern`），它的默认链接性是：
- A. 外部链接　　B. 内部链接　　C. 无链接　　D. 未定义

**6.** C++ 编译器进行「名称修饰 (Name Mangling)」的根本原因是：
- A. 加密代码　　B. 压缩符号表
- C. 支持函数重载，为同名不同参的函数生成唯一符号
- D. 兼容 C 语言

**7.** `extern "C"` 的作用是：
- A. 让函数变成内联　　B. 禁用名称修饰，按 C 的方式生成符号
- C. 把函数导出为动态库　　D. 强制外部链接

**8.** `#define`、`#include`、`#ifdef` 这些指令在哪个阶段处理？
- A. 编译　　B. 汇编　　C. 链接　　D. 预处理

**9.** `assert` 宏的行为受哪个宏控制？定义它会发生什么？
- A. `DEBUG`，定义后启用 assert
- B. `NDEBUG`，定义后 assert 展开为空操作被完全移除
- C. `_DEBUG`，定义后终止程序
- D. `__cplusplus`，定义后禁用 assert

**10.** 关于 `static_assert` 的检查时机，正确的是：
- A. 运行时，受 NDEBUG 控制
- B. 编译时，不受 NDEBUG 影响
- C. 链接时
- D. 预处理时

**11.** 匿名命名空间中的成员，其链接性是：
- A. 外部链接　　B. 内部链接（只在当前翻译单元可见）
- C. 无链接　　D. 取决于成员类型

**12.** 当代码以 C++17 编译时，`__cplusplus` 的值是：
- A. `199711L`　　B. `201103L`　　C. `201703L`　　D. `202002L`

> [!success]- 参考答案（第一节）
> 1. **B**。预处理（文本展开）→ 编译（生成 `.s` 汇编）→ 汇编（生成 `.o` 目标文件）→ 链接（合并成可执行文件）。
> 2. **B**。翻译单元是编译的基本单位 = 源文件 + 递归展开的所有头文件，每个翻译单元**独立编译**。
> 3. **C**。非 inline、外部链接实体属于「整个程序范围」的 ODR：全程序恰好一个定义，多一个就 `multiple definition`。
> 4. **B**。`inline` 是建议而非命令；它真正的硬约束作用是 **ODR 豁免**——允许多个翻译单元各有一份相同定义，链接器合并为一个。
> 5. **B**。命名空间作用域的 `const` 对象默认**内部链接**，所以放进头文件被多个 `.cpp` 包含也不冲突（各有一份副本）。需要跨文件共享要加 `extern`。
> 6. **C**。重载允许同名不同参共存，编译器必须给每个重载生成唯一符号名（如 `_Z5printi` / `_Z5printd`），否则链接器无法区分。
> 7. **B**。`extern "C"` 关闭名称修饰，符号名保持原样，用于和 C 代码 / C 库联调（见 [[10.1 C和C++联调]]）。
> 8. **D**。所有 `#` 开头的指令在**预处理**阶段完成，编译器看到的已是展开后的代码。
> 9. **B**。`NDEBUG` 未定义时 assert 生效；定义后（Release 默认）assert 展开为 `((void)0)`，检查代码在编译期被完全移除，零运行时开销。
> 10. **B**。`static_assert` 是**编译期**断言，永远不受 `NDEBUG` 影响，常用于类型 / 常量检查。
> 11. **B**。匿名命名空间等价于（且优于）`static`，成员是内部链接，只在本翻译单元可见。
> 12. **C**。`201703L` 对应 C++17；`199711L`=C++98/03，`201103L`=C++11，`202002L`=C++20。

## 二、概念辨析（判断对错并说明理由）

**13.** 只要写了 `inline`，函数就一定会被编译器内联展开。

**14.** 在头文件里定义一个**普通（非 inline）** 函数并被两个 `.cpp` 包含，链接时会报 `multiple definition`。

**15.** `#pragma once` 是 C++ 标准规定的头文件保护方式。

**16.** 命名空间作用域的 `const` 全局变量默认是外部链接。

**17.** 匿名命名空间和 `static` 完全等价，可以无脑互换。

**18.** 只要给函数宏 `#define SQUARE(x) ((x)*(x))` 的参数和整体都加了括号，它就和 `inline` 函数一样安全了。

**19.** 可以在 `assert` 的表达式里放有副作用的代码（如 `assert(++i < n)`），因为发布版也会执行它。

**20.** C++17 起，`constexpr` 函数才隐式成为 `inline`。

**21.** 在头文件里写 `using namespace std;` 是推荐做法，能少敲字。

**22.** 定义了 `NDEBUG` 后，`assert` 和 `static_assert` 都会被禁用。

> [!success]- 参考答案（第二节）
> 13. **错**。`inline` 只是建议。函数体过大、递归、通过函数指针 / 虚函数调用等情况编译器都可能拒绝内联。它的可靠语义是 ODR 豁免，不是"保证展开"。
> 14. **对**。非 inline 函数是程序级 ODR 实体，两份定义 = 重复定义。修复：加 `inline`、改放 `.cpp`、或用 `static` / 匿名命名空间。
> 15. **错**。`#pragma once` 是被**绝大多数编译器支持的扩展**，但不是标准。可移植性最强的仍是 `#ifndef/#define/#endif` 宏保护。
> 16. **错**。默认是**内部链接**。需要外部链接必须显式 `extern const int N = ...;`（定义处也要带 extern）。
> 17. **错**。匿名命名空间能容纳**类型、模板**（`static` 不能修饰类），且是 C++ 推荐写法；二者只在「变量/函数内部链接」这一点上重叠。
> 18. **错**。括号只解决**运算符优先级**问题，解决不了**参数多次求值**：`SQUARE(a++)` 展开成 `((a++)*(a++))`，`a` 被自增两次。这正是 `inline` 函数优于宏之处（参数只求值一次、有类型检查、可调试）。
> 19. **错**。`NDEBUG` 定义后整个 assert 表达式被移除，副作用随之消失，导致 Debug / Release 行为不一致。应"先执行副作用，再断言结果"。
> 20. **错**。是 **C++11** 起 `constexpr` 函数隐式 inline；C++17 新增的是 `constexpr` **静态数据成员**隐式 inline。
> 21. **错**。头文件里的 `using namespace` 会污染所有包含它的翻译单元，引发难查的名字冲突 / 二义性。应在 `.cpp` 的局部作用域用，或只用 `using std::xxx;` 声明。
> 22. **错**。只有 `assert`（运行期）受 `NDEBUG` 控制；`static_assert`（编译期）永远生效。

## 三、代码输出预测

> 除特别说明，均假设 64 位、C++17、MSVC 或 GCC 标准行为。

**23.**
```cpp
#define SQUARE(x) x * x
std::cout << SQUARE(1 + 2);
```

**24.**
```cpp
#define STR(x) #x
std::cout << STR(a + b);
```

**25.**
```cpp
#define CONCAT(a, b) a##b
int xy = 42;
std::cout << CONCAT(x, y);
```

**26.**
```cpp
void tick() { static int c = 0; std::cout << ++c << ' '; }
int main() { tick(); tick(); tick(); }
```

**27.** 假设下面两个宏调用所在行的行号是 8：
```cpp
#define STR(x)  #x
#define XSTR(x) STR(x)
std::cout << STR(__LINE__) << ' ' << XSTR(__LINE__);
```

**28.**
```cpp
#define MAX(a, b) ((a) > (b) ? (a) : (b))
int x = 5;
int r = MAX(x++, 3);
std::cout << r << ' ' << x;
```

**29.**
```cpp
namespace Lib {
    inline namespace v2 { int f() { return 2; } }
    namespace v1        { int f() { return 1; } }
}
int main() { std::cout << Lib::f() << Lib::v1::f() << Lib::v2::f(); }
```

> [!success]- 参考答案（第三节）
> 23. 输出 **5**。宏只做文本替换：`SQUARE(1 + 2)` → `1 + 2 * 1 + 2`，按优先级先算 `2*1=2`，得 `1+2+2=5`。这就是"参数和整体都要加括号"的反例。
> 24. 输出 **`a + b`**。`#` 字符串化把参数原样转成字符串字面量 `"a + b"`，再被 `cout` 打印。
> 25. 输出 **42**。`##` 把标记 `x` 和 `y` 拼成 `xy`，于是打印变量 `xy` 的值 42。
> 26. 输出 **`1 2 3 `**。`static` 局部变量只初始化一次、跨调用保持，`++c` 依次得 1、2、3。
> 27. 输出 **`__LINE__ 8`**。关键在「带 `#` 的宏不会先展开参数」：`STR(__LINE__)` 直接字符串化成 `"__LINE__"`；多包一层 `XSTR` 会先把 `__LINE__` 展开成 `8` 再字符串化 → `"8"`。这是 stringify 必须套两层的经典原因。
> 28. 输出 **`6 7`**。展开为 `((x++) > (3) ? (x++) : (3))`：条件里 `x++` 取 5、`x`→6，`5>3` 真；分支里 `x++` 取 6、`x`→7。故 `r=6`、`x=7`（`?:` 有序列点，行为有定义，但 `x` 被自增两次正是宏多次求值的坑）。
> 29. 输出 **`221`**。`Lib::f()` 因 `v2` 是 inline namespace 直接解析到 v2 → 2；`Lib::v1::f()` → 1；`Lib::v2::f()` → 2。拼起来 `221`。

## 四、找错与修复（指出 bug 并改正）

**30.**
```cpp
// counter.h
#ifndef COUNTER_H
#define COUNTER_H
int g_count = 0;          // 被 a.cpp 和 b.cpp 都 #include

```

**31.**（要求用 Modern C++ 重写）
```cpp
#define SQUARE(x) x * x
#define MAXV(a, b) a > b ? a : b
// 调用：
int s = SQUARE(3 + 1);     // 期望 16
int m = MAXV(2, 3) * 10;   // 期望 30
```

**32.**
```cpp
int remaining = 3;
assert(--remaining >= 0);  // 想确认递减后非负
// ... 后续依赖 remaining 已被递减
```

**33.**
```cpp
// utils.h —— 没有任何保护
struct Point { int x, y; };
inline int area(Point p) { return p.x * p.y; }
// 某 .cpp 直接或间接两次 #include "utils.h"
```

**34.**
```cpp
int age;
std::cin >> age;
assert(age >= 0);          // 校验用户输入
process(age);
```

**35.**
```cpp
#define LOG(msg) std::cout << msg << '\n';
if (ok)
    LOG("ok");
else
    LOG("fail");
```

> [!success]- 参考答案（第四节）
> 30. **bug 类型**：ODR 违规 / 链接期 `multiple definition`。头文件里**定义**了非 inline 全局变量，每个包含它的翻译单元各生成一份定义。
> **修复（Modern，C++17）**：`inline int g_count = 0;`（inline 变量，链接器合并为一份）；或头文件 `extern int g_count;` 声明 + 唯一一个 `.cpp` 里 `int g_count = 0;` 定义。
> 31. **bug 类型**：宏优先级 + 多次求值。`SQUARE(3+1)` → `3+1*3+1=7`（非 16）；`MAXV(2,3)*10` → `2>3?2:3*10` → 因 `?:` 优先级最低，实际是 `2>3 ? 2 : 30` = 30 看似对，但 `MAXV(a,b)` 一旦传入带副作用实参会重复求值，且无类型检查。
> **修复（Modern C++）**：
> ```cpp
> template <typename T>
> constexpr T square(T x) { return x * x; }   // 类型安全、参数求值一次
> // 直接用标准库的 std::max，别自造 MAXV：
> int s = square(3 + 1);          // 16
> int m = std::max(2, 3) * 10;    // 30
> ```
> 32. **bug 类型**：assert 副作用。Release（`NDEBUG`）下整句被删，`--remaining` 不执行，`remaining` 仍是 3，后续逻辑错乱且 Debug/Release 不一致。
> **修复**：把副作用挪出去——`--remaining; assert(remaining >= 0);`
> 33. **bug 类型**：缺少头文件保护，同一翻译单元内重复展开 → `Point` 重复定义（同一 TU 内类型不可重复定义）。
> **修复**：加 `#pragma once`，或经典 `#ifndef UTILS_H / #define UTILS_H / ... / #endif`。
> 34. **bug 类型**：用 assert 做运行时 / 用户输入校验。Release 下断言被移除，非法输入直通 `process`。assert 只该用于"程序内部逻辑上不可能发生"的情况。
> **修复**：用正常错误处理：
> ```cpp
> if (age < 0) { std::cerr << "invalid age\n"; return; }  // 或抛异常
> process(age);
> ```
> 35. **bug 类型**：宏以 `;` 结尾导致悬空 else——`if(ok) LOG("ok");` 展开成 `if(ok) std::cout<<...<<'\n';;`，多出的空语句让 `else` 失去配对，编译报 `else without a previous if`。
> **修复**：用 `do { } while(0)` 包裹，调用处再加分号：
> ```cpp
> #define LOG(msg) do { std::cout << (msg) << '\n'; } while (0)
> ```

## 五、简答题

**36.** 什么是翻译单元？它和"源文件"是同一个东西吗？

**37.** 用一句话分别说明 ODR 对（a）非 inline 函数 /（b）inline 函数、模板、类 这两类实体的约束。

**38.** 什么是名称修饰？为什么 C++ 需要它而 C 不需要？

**39.** `inline` 除了"建议内联"，对 ODR 的真正作用是什么？为什么 header-only 库要用它？

**40.** `#include <header>` 和 `#include "header"` 在搜索路径上有什么区别？

**41.** 匿名命名空间和 `static`（文件作用域）相比，多了哪些能力？为什么 C++ 推荐前者？

**42.** `assert` 和 `static_assert` 的核心区别是什么？各举一个典型使用场景。

> [!success]- 参考答案（第五节）
> 36. 翻译单元 = 一个源文件经预处理、递归展开所有 `#include` 后形成的完整代码，是编译器**独立编译**的基本单位。它不等于源文件——源文件只是入口，头文件内容也并进来了。
> 37. （a）非 inline 函数 / 非 inline 全局变量：**整个程序恰好一个定义**。（b）inline 函数 / 变量、模板、类：**每个翻译单元至多一个定义，且所有翻译单元里的定义必须逐字节相同**（否则是 UB）。
> 38. 名称修饰是编译器把函数名连同其参数类型、所在类 / 命名空间编码进符号名的机制。C++ 有重载、命名空间、成员函数，同名实体必须靠修饰区分出唯一符号；C 无重载，函数名直接当符号，所以不需要。
> 39. `inline` 给实体 **ODR 豁免**：允许它在多个翻译单元各有一份相同定义，链接器去重合并为一个。header-only 库的函数 / 变量定义在头文件、被多处包含，必须 inline 才不触发 `multiple definition`。
> 40. `<>` 只在系统 / 编译器指定的包含路径里找（标准库）；`""` 先在当前文件所在目录找，找不到再退回到 `<>` 的路径。项目自己的头用 `""`，标准库 / 第三方用 `<>`。
> 41. 匿名命名空间能给**类型和模板**赋予内部链接（`static` 只能修饰变量 / 函数，不能修饰 class）；且写法统一、更符合现代风格。所以 C++ 推荐用匿名命名空间替代文件作用域 `static`。
> 42. `assert` 是**运行期**断言，受 `NDEBUG` 控制可被关闭，用于查"运行到这里某条件应当为真"的内部逻辑假设（如指针非空）；`static_assert` 是**编译期**断言，永不被关闭，用于"编译期可判定"的检查（如 `static_assert(sizeof(void*)==8)`、模板里 `static_assert(std::is_integral_v<T>)`）。

## 六、综合设计与手写代码

**43.** 写一个可以放进头文件、被多个 `.cpp` 安全包含的工具函数 `clamp(v, lo, hi)`（把 v 夹到 `[lo, hi]`）。说明为什么不会触发 ODR 问题。

**44.** 写一个 `platform_name()`，根据预处理平台宏返回 `"Windows" / "Linux" / "macOS" / "Unknown"`。

**45.**（Modern C++ 重构）把下面这组宏改写成类型安全、无多次求值、可调试的现代写法：
```cpp
#define PI 3.14159
#define CIRCLE_AREA(r) PI * r * r
#define IS_EVEN(n) (n % 2 == 0)
```

**46.** 实现一个自定义断言宏 `MY_ASSERT(cond, msg)`：在 `NDEBUG` 下为空操作；否则失败时打印条件文本、自定义消息、`__FILE__`、`__LINE__`、`__func__` 并 `abort()`。

> [!success]- 参考答案（第六节）
> **43.**
> ```cpp
> // clamp_util.h
> #pragma once
> inline int clamp(int v, int lo, int hi) {
>     return v < lo ? lo : (v > hi ? hi : v);
> }
> ```
> 要点：`inline` 给 ODR 豁免，多个翻译单元各有一份相同定义、链接器合并；`#pragma once` 防同一 TU 内重复展开。（若要泛型可写成模板，模板本身也享 ODR 豁免。）
>
> **44.**
> ```cpp
> constexpr const char* platform_name() {
> #if defined(_WIN32)
>     return "Windows";
> #elif defined(__linux__)
>     return "Linux";
> #elif defined(__APPLE__)
>     return "macOS";
> #else
>     return "Unknown";
> #endif
> }
> ```
> 要点：平台宏由编译器预定义，条件编译在预处理期就裁剪掉其它分支；`_WIN32` 在 32/64 位 Windows 都定义。
>
> **45.**
> ```cpp
> constexpr double pi = 3.14159;                 // 替代 #define PI
>
> template <typename T>
> constexpr T circle_area(T r) { return pi * r * r; }   // 类型安全、r 只求值一次
>
> constexpr bool is_even(int n) { return n % 2 == 0; }  // 真正的函数，有类型检查
> ```
> 要点：`constexpr` 既能编译期求值又是真正的具名实体，遵守作用域、可调试、参数求值一次；彻底规避宏的优先级与多次求值坑。
>
> **46.**
> ```cpp
> #ifdef NDEBUG
>     #define MY_ASSERT(cond, msg) ((void)0)
> #else
>     #define MY_ASSERT(cond, msg)                                  \
>         do {                                                      \
>             if (!(cond)) {                                        \
>                 std::cerr << "Assertion failed: " #cond           \
>                           << "\n  msg : " << (msg)                 \
>                           << "\n  at  : " << __FILE__ << ':' << __LINE__ \
>                           << "\n  func: " << __func__ << '\n';     \
>                 std::abort();                                     \
>             }                                                     \
>         } while (0)
> #endif
> ```
> 要点：`#cond` 字符串化条件文本；`__FILE__/__LINE__/__func__` 定位；`do{}while(0)` 保证语句安全；`NDEBUG` 分支保证发布版零开销。

## 七、简答深化题

**47.** 为什么命名空间作用域的 `const` 变量默认是内部链接？这一设计如何让 `const int N = 100;` 放进头文件被多处包含仍然安全？

**48.** C++17 的 `inline 变量`解决了什么历史痛点？链接器面对多个翻译单元里同名的 inline 变量定义是怎么处理的？

**49.**（跨章）结合 [[10.1 C和C++联调]]：C++ 调用一个 C 写的库函数，若忘了 `extern "C"` 会出现什么链接错误？从名称修饰角度解释根因。

**50.** "隐蔽的 ODR 违规"——同一个类在不同翻译单元因条件编译而成员不同。为什么它**不报链接错误**却是未定义行为？后果可能是什么？

**51.**（跨章）ADL（参数依赖查找）是什么？为什么泛型代码里交换两个对象要写 `using std::swap; swap(a, b);` 而不是直接 `std::swap(a, b)`？

**52.** 为什么 `constexpr` 函数隐式 `inline`？请从"它常定义在头文件、可能在编译期也可能在运行期被调用"两个角度解释。

> [!success]- 参考答案（第七节）
> 47. C++ 沿袭"const 常量多用于头文件里的编译期常量"的惯例，给它内部链接，意味着**每个翻译单元各持一份独立副本**，彼此不是同一个外部符号，自然不冲突——这正是 `const int N = 100;` 能安全进头文件的原因。代价：它不是跨 TU 共享的同一对象，取地址在不同 TU 得到不同地址。要共享必须 `extern const`。
> 48. 痛点：C++17 前，想在头文件提供一个**全局可共享变量**（如库的全局配置），要么 `extern` 声明 + 某个 `.cpp` 定义（样板繁琐），要么用函数包静态局部变量。`inline 变量`让定义直接写在头里、被多处包含也只代表**同一个**对象。链接器对 inline 变量按"弱符号 / COMDAT 折叠"处理：多份相同定义合并保留一份、地址唯一。
> 49. 现象：编译过、链接报 `undefined reference to "foo"`（或 MSVC `unresolved external symbol`）。根因：C 库里 `foo` 的符号名就是 `foo`（C 无修饰），但 C++ 端把它当 C++ 函数，按修饰规则去找 `_Z3foo...` 之类的符号，名字对不上。加 `extern "C"` 让 C++ 端按 C 方式生成 / 查找符号即可。
> 50. 链接器只按符号名匹配，类定义不产生需要去重的外部符号（类是"每 TU 一份、须完全相同"的实体），所以两份**不同**的类定义骗过了链接器，没有报错。但程序此后对该类的大小、成员偏移在不同 TU 各按各的理解访问，造成内存布局错位——可能读到垃圾值、踩内存、崩溃，且极难复现定位。根治：不要用条件编译改变会跨 TU 共享的类型布局。
> 51. ADL：调用未限定的函数时，编译器还会到**实参类型所在的命名空间**里找候选。`using std::swap; swap(a, b);` 先把 `std::swap` 引入为兜底候选，再靠 ADL 找到该类型自定义的、可能更高效的 `swap`；若直接写 `std::swap(a,b)` 就**屏蔽了用户自定义版本**，只能用泛型（可能多一次拷贝 / 构造）。
> 52. `constexpr` 函数通常写在头文件、被多个 TU 包含，隐式 inline 给它 ODR 豁免避免重复定义错误。同时 constexpr 函数有"双重身份"：实参是常量表达式时在**编译期**求值（如初始化 `constexpr`/数组大小），否则退化为普通函数在**运行期**调用——inline 让这份定义在所有 TU 一致可用。

## 八、概念辨析进阶

**53.** 辨析「声明 (declaration)」与「定义 (definition)」。

**54.** 辨析三种链接性：外部链接 / 内部链接 / 无链接。

**55.** 辨析四种存储期：自动 / 静态 / 动态 / 线程。

**56.** 辨析常量/小函数的三种实现：`#define` 宏 / `inline` 函数 / `constexpr`。

**57.** 辨析三种"检查 / 报错"手段：`assert` / `static_assert` / `#error`。

> [!success]- 参考答案（第八节）
> 53. 声明只是"告诉编译器某名字存在及其类型"（`extern int x; void f(); class C;`），可重复多次；定义则"真正创建实体并分配 / 给出实现"（`int x; void f(){} class C{};`），受 ODR 约束。口诀：**声明可多次，定义看 ODR**。
> 54. 外部链接——名字可被其他 TU 引用（普通全局变量 / 函数）；内部链接——只在本 TU 可见（`static` 全局、`const` 全局、匿名命名空间成员）；无链接——只在本作用域可见（局部变量）。口诀：**跨文件 / 跨不出文件 / 跨不出作用域**。
> 55. 自动——进作用域生、出作用域死（局部变量）；静态——整个程序生命期存在、只初始化一次（全局、`static` 局部）；动态——`new`/`malloc` 手动分配释放（Modern C++ 用智能指针管）；线程——每个线程一份副本（`thread_local`）。口诀：**栈 / 全程序 / 堆 / 每线程**。
> 56. 宏：纯文本替换，无类型检查、无作用域、参数可能多次求值，最不安全；`inline` 函数：真函数，有类型检查、可调试、参数求值一次；`constexpr`：在 inline 函数基础上还能**编译期求值**。口诀：**能用 constexpr 就别用宏**。
> 57. `assert`：运行期、可被 `NDEBUG` 关、查运行时内部假设；`static_assert`：编译期、不可关、查类型 / 常量；`#error`：预处理期、用于"配置不满足就拒绝编译"（如 `#if __cplusplus < 201703L` → `#error "needs C++17"`）。口诀：**运行期 / 编译期 / 预处理期** 三级防线。

## 九、大厂面试场景题 / 八股常考

**58.** 链接时报 `multiple definition of 'xxx'`，你会从哪几个方向排查和修复？

**59.** 链接时报 `undefined reference to 'xxx'`（MSVC：`unresolved external symbol`），常见原因有哪些？怎么定位？

**60.** 一段代码 Debug 跑得好好的，切到 Release 就行为异常 / 崩溃。和本章哪个知识点高度相关？怎么查？

**61.** 改了一个被几百个文件包含的头文件里的一行，整个工程全量重编译。从编译依赖角度，有哪些手段能显著降低这种重编译？

**62.** 为什么模板的定义通常必须放在头文件里？这和普通函数"声明放头、定义放 cpp"的惯例为什么不一样？

**63.** 项目编译越来越慢，作为负责人你会从哪些方向做编译加速？

> [!success]- 参考答案（第九节）
> 58. **现象**：链接期重复定义。**原因**：① 头文件里定义了非 inline 函数 / 全局变量且被多个 TU 包含；② 同名函数在多个 `.cpp` 各写了一份。**解决**：头文件里的定义改 `inline`（C++17 变量也可 inline）；或函数定义移到唯一 `.cpp`、头里只留声明；仅本文件用的加 `static` / 匿名命名空间。**延伸**：用 `nm`/`dumpbin` 看是哪个符号、出现在哪些 `.o` 里。
> 59. **现象**：找不到符号定义。**原因**：① 只声明没定义；② 定义所在的 `.cpp`/`.o`/库没参与链接（漏链 `-l` 或源文件）；③ C/C++ 混用漏了 `extern "C"` 导致修饰名对不上；④ 签名不一致（参数 / const 不同 → 修饰名不同）。**解决**：补定义、补链接、加 `extern "C"`、核对签名。**延伸**：`c++filt` 把报错里的修饰名反解成人类可读签名，最快定位是哪个重载没实现。
> 60. **现象**：Debug 正常、Release 异常。**原因**：极可能是 `assert` 里写了副作用代码（如 `assert(p = init())`、`assert(--n>=0)`），Release 定义 `NDEBUG` 后整句被删，副作用丢失。也可能是依赖了 UB 被优化暴露。**解决**：审查所有 assert 是否含赋值 / 自增 / 函数调用副作用，把副作用挪出断言；开 `-Wall` 并用 sanitizer 复查。**延伸**：assert 只放"只读判断"。
> 61. **现象**：头文件改一行触发雪崩式重编译。**原因**：大量 TU 物理依赖该头。**解决**：① **前向声明**代替 `#include`（只用到指针 / 引用时）；② **PIMPL** 把实现细节藏进 `.cpp`，头里只剩不变的接口；③ 拆分大头文件、按需包含；④ 预编译头（PCH）放稳定的第三方头。**延伸**：减少头里的 `inline` 大函数 / 模板实例，能进一步降耦合。
> 62. **现象**：模板定义放 `.cpp` 会 `undefined reference`。**原因**：模板要在**实例化点**才生成具体代码，编译某个 TU 时若只看到声明、看不到定义，就无法实例化；普通函数则在自己的 `.cpp` 编译出唯一符号、链接期解析即可。**解决**：模板定义放头文件（随包含进入每个用到它的 TU，靠 ODR 豁免去重）；或显式实例化。**延伸**：这也是模板"代码膨胀"和编译变慢的来源之一。
> 63. **现象**：构建耗时增长。**原因**：头依赖重、模板 / inline 多、重复包含。**解决**：前向声明 + PIMPL 砍依赖、预编译头、Unity/Jumbo build 合并 TU、`ccache` 缓存、并行编译 `-j`、把重模板下沉到少数 TU 显式实例化。**延伸**：用 `-ftime-trace`（Clang）/ build profiler 找出最耗时的头与实例化点，定向优化。

## 十、补充加分题

**64.**（性能分析）`inline` 既然消除调用开销，是不是越多越好？请从代码膨胀、指令缓存（i-cache）、编译期角度分析它的代价；它会改变算法的 Big-O 吗？

**65.** `__COUNTER__` 和 `__LINE__` 都能用来生成"唯一名字"，二者有什么区别？各自适合什么场景？（注意 `__COUNTER__` 的可移植性）

**66.** 怎样用 `inline namespace` 做库的 ABI / 版本控制？给出最小示例并说明老用户代码为何无需改动就能默认用上新版本。

**67.**（跨章）结合结构体对齐：`#pragma pack(1)` 把结构体压紧后，用它直接 `memcpy` 收发网络数据有什么风险？为什么说"按字段逐个序列化"比直接发结构体更稳？

> [!success]- 参考答案（第十节）
> 64. 不是越多越好。**代价**：① 代码膨胀——函数体在每个调用点复制，可执行文件变大；② i-cache：热点小函数内联能提升局部性，但盲目内联大函数会撑爆指令缓存、增加 miss，反而变慢；③ 编译期：头里的 inline 多，改一处触发大量重编译。**Big-O**：内联只改变**常数因子**（省掉调用 / 压栈开销），不改变算法复杂度。结论：内联适合短小高频函数，交给编译器在 `-O2` 自行决策通常最好。
> 65. `__LINE__` 同一行多次展开值相同，跨行才不同——适合"每个使用点位于不同源码行"的场景；`__COUNTER__` 每次取值自增、保证同一行内多次使用也唯一——适合一行里要生成多个唯一名（或宏被多次展开）。注意 `__COUNTER__` 是编译器扩展（MSVC/GCC/Clang 支持）、非标准，跨平台要小心。
> 66. ```cpp
> namespace mylib {
>     inline namespace v2 {           // 默认版本
>         int api() { return 2; }
>     }
>     namespace v1 { int api() { return 1; } }
> }
> // 老代码：mylib::api()  → 自动解析到 v2（因 v2 是 inline）
> // 需要旧行为：mylib::v1::api()
> ```
> `inline namespace` 让内层成员"透明"地出现在外层，`mylib::api()` 默认绑定到被标 inline 的版本。发布新版只需把 inline 标到 v2，旧调用代码一字不改即升级；同时符号里仍含版本信息，便于 ABI 隔离。
> 67. 风险：`#pragma pack(1)` 取消填充后，**不同编译器 / 平台**对成员的字节序（endianness）、整型宽度、有无尾部对齐的处理仍可能不同，直接 `memcpy` 收发会在异构端解析错位；且未对齐访问在某些架构上更慢甚至出错。更稳的做法是**逐字段序列化**：对每个整型显式 `htonl/htons` 转网络字节序、定长写入，接收端逐字段读回，彻底摆脱对内存布局的隐式依赖（见 [[7.3 结构体与联合体题目汇总]] 的字节序题）。

## 十一、编译/链接专项（符号 / 段布局 / ODR 链接错误）

> 本章为系统/后端岗高频，重点考"会读符号、懂链接、能定位 ODR 类错误"。

**68.**（符号反解）链接器报错里出现符号 `_Z5printi` 和 `_Z5printPKc`。它们分别对应什么 C++ 函数？你会用什么命令把修饰名还原成可读签名？

**69.**（ODR 链接错误）`a.cpp` 和 `b.cpp` 各自定义了 `void log() { ... }`（非 inline、外部链接）。链接会发生什么？给出**三种**互不相同的修复思路。

**70.**（undefined reference）头文件声明了 `int sum(int, int);` 并被使用，但忘了提供定义。编译期会报错吗？链接期呢？错误信息长什么样？

**71.**（隐蔽 ODR）`config.h` 用 `#ifdef DEBUG_MODE` 给 `struct Config` 加 / 减一个成员，`a.cpp` 定义了 `DEBUG_MODE` 再包含、`b.cpp` 没定义就包含。会报错吗？运行时会怎样？怎么根治？

**72.**（链接性 vs 存储期 + 段布局）说明下列四者各自的链接性与存储期，并指出它们大致落在可执行文件的哪个段：① 全局 `int g;` ② 函数内 `static int s = 1;` ③ 函数内 `int local;` ④ 字符串字面量 `"hi"`。

> [!success]- 参考答案（第十一节）
> 68. `_Z5printi` → `print(int)`；`_Z5printPKc` → `print(char const*)`（Itanium ABI：`_Z` 前缀、`5print` 是长度+名、后面是参数类型编码，`i`=int、`PKc`=pointer to const char）。还原命令：Linux/GCC 用 `c++filt _Z5printi`；查目标文件符号用 `nm a.o`；MSVC 用 `undname` / `dumpbin /symbols`。
> 69. 链接报 `multiple definition of 'log()'`——两个 TU 各有一份外部链接定义，违反程序级 ODR。三种修复：① 改成 `inline void log(){...}`（ODR 豁免，多份相同定义合并）；② 只在一个 `.cpp` 定义、头文件里只放声明 `void log();`；③ 若两处本就是各自私有，用 `static` 或匿名命名空间给它内部链接，使两个符号互不可见。
> 70. 编译期**不报错**——`sum` 已声明，调用处类型匹配，每个 TU 独立编译时不关心定义在哪。链接期报错：`undefined reference to 'sum(int, int)'`（GCC）/ `unresolved external symbol "int __cdecl sum(int,int)"`（MSVC）。修复：提供 `sum` 的定义并确保其 `.o` 参与链接。
> 71. **不报链接错误**（类定义不产生需要去重的外部符号，骗过链接器），但构成隐蔽 ODR 违规 → **未定义行为**。两个 TU 对 `Config` 的大小 / 成员偏移理解不一致，跨 TU 传递 / 访问该对象时内存错位，可能读到垃圾、踩坏栈堆、偶发崩溃且极难复现。根治：不要用条件编译改变跨 TU 共享类型的布局；要可配置就把差异藏到不影响布局的实现里，或全工程统一宏定义。
> 72. ① 全局 `int g;`：外部链接、静态存储期 → 若零初始化在 `.bss`，非零初始化在 `.data`。② `static int s=1;`：无链接（局部作用域名字）但静态存储期 → `.data`（值为 0 则 `.bss`）。③ `int local;`：无链接、自动存储期 → **栈**（不在静态段）。④ `"hi"`：静态存储期、只读 → `.rodata`（常量区）。口诀：**初始化非零→.data，零→.bss，只读常量→.rodata，代码→.text，自动变量→栈**。（段名属实现细节，标准只规定链接性 / 存储期；此处段归属为常见平台行为，作了解。）
