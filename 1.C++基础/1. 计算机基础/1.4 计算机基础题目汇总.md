## 一、选择题（概念基础）

**2.** 宏展开、头文件包含、删除注释、条件编译发生在哪个阶段？
- A. 预处理　　B. 编译　　C. 汇编　　D. 链接

**3.** 把汇编代码（`.s`）翻译成机器指令、生成可重定位目标文件（`.o`）的阶段是：
- A. 预处理　　B. 编译　　C. 汇编　　D. 链接

**4.** "漏写分号"这类错误最可能在编译的哪一步被报出？
- A. 词法分析　　B. 语法分析　　C. 语义分析　　D. 链接

**5.** ELF 文件开头的魔数 `7F 45 4C 46` 对应的 ASCII 是：
- A. `.ELF`　　B. `ELF.`　　C. `0ELF`　　D. `ELF0`

**6.** ELF 的"链接视图"和"执行视图"分别以什么为单位？
- A. 都以段(Segment)　　B. 链接视图以节(Section)，执行视图以段(Segment)　　C. 链接视图以段，执行视图以节　　D. 都以节(Section)

**7.** 已初始化且非零的全局变量 `int g = 10;` 存放在：
- A. `.text`　　B. `.data`　　C. `.bss`　　D. `.rodata`

**8.** 未初始化的全局变量 `int g;` 存放在哪个段，该段有何特点？
- A. `.data`，占磁盘　　B. `.bss`，不占磁盘只在运行时占内存　　C. `.rodata`，只读　　D. 栈

**9.** `nm` 输出中，符号 `U printf` 的含义是：
- A. printf 是全局函数　　B. printf 是局部函数　　C. printf 是未定义符号（本文件引用但未定义）　　D. printf 是弱符号

**10.** cdecl 调用约定中，函数参数的压栈顺序是：
- A. 从左向右　　B. 从右向左　　C. 随机　　D. 按类型大小

**11.** `call` 指令除了跳转，还会自动完成什么？
- A. 保存 ebp　　B. 把返回地址压栈　　C. 清理参数　　D. 分配局部变量空间

**12.** 进程虚拟地址空间中，堆和栈的生长方向是：
- A. 都向上　　B. 都向下　　C. 堆向上（低→高），栈向下（高→低），相向生长　　D. 堆向下，栈向上

> [!success]- 参考答案（第一节）
> 1. **B**。预处理（`.i`）→ 编译（`.s`）→ 汇编（`.o`）→ 链接（可执行）。
> 2. **A**。所有以 `#` 开头的指令都在预处理阶段处理，产物仍是纯文本。
> 3. **C**。汇编器把 `.s` 翻成机器码，生成可重定位目标文件 `.o`，但外部地址未定。
> 4. **B**。语法分析按语法规则组织 Token 成 AST，括号不匹配/缺分号在此报"语法错误"。
> 5. **A**。`7F`是标志字节，`45 4C 46`即 `E L F`，整体读作 `.ELF`，标识 ELF 文件。
> 6. **B**。链接视图以 Section（`.text`/`.data`…，给链接器）；执行视图以 Segment（`LOAD`…，给加载器，决定加载权限）。
> 7. **B**。已初始化非零的全局/静态变量在 `.data`。
> 8. **B**。未初始化或零初始化的全局/静态变量在 `.bss`，不占磁盘空间，运行时才占内存。
> 9. **C**。`U` = Undefined，本文件引用但未定义（如 printf 定义在 libc），等链接解析。
> 10. **B**。cdecl 参数从右向左压栈。
> 11. **B**。`call` = `push eip(返回地址)` + `jmp 目标`，所以 `ret` 才能跳回。
> 12. **C**。堆从低地址向高地址、栈从高地址向低地址，相向生长以最大化可用空间。

## 二、概念辨析（判断对错并说明理由）

**13.** 预处理后的文件体积通常比源文件小。

**14.** `.bss` 段在可执行文件里要占用和变量总大小一样多的磁盘空间。

**15.** 局部静态变量虽然作用域在函数内，但它存放在 `.data`/`.bss`，生命周期是整个程序。

**16.** 普通局部变量会在符号表中产生一个符号。

**17.** 静态链接生成的可执行文件比动态链接的小。

**18.** 函数返回时，返回值通常通过 `eax` 寄存器带回调用者。

**19.** 在 cdecl 约定中，是被调用者（Callee）负责清理参数占用的栈空间。

**20.** 字符串字面量 `"hello"` 可以通过 `char* p = "hello"; *p='a';` 修改。

> [!success]- 参考答案（第二节）
> 13. **错**。预处理会展开宏、插入头文件内容，文件通常变**大**很多（仍是纯文本）。
> 14. **错**。`.bss` 只记录大小，不占磁盘空间，运行时才分配并清零，这正是它与 `.data` 的区别。
> 15. **对**。静态局部变量存储期是整个程序，放在 `.data`/`.bss`，只是可见性限制在函数内。
> 16. **错**。普通（非静态）局部变量**不产生符号**，编译器直接生成操作栈空间的汇编指令。
> 17. **错**。静态链接把用到的库代码拷进可执行文件，体积**更大**；动态链接只存引用，体积更小。
> 18. **对**。整型返回值约定放在 `eax`（x86）由被调函数写入、调用者读取。
> 19. **错**。cdecl 由**调用者(Caller)** 清理参数栈（如 `add esp, 8`），这也是 cdecl 支持可变参数的原因。
> 20. **错**。字符串字面量在 `.rodata`（只读），写入触发段错误；且 `char* p = "..."` 在现代 C++ 已不合法（应 `const char*`）。

## 三、段归属与符号类型预测

**21.** 判断下列各变量/对象通常存储在哪个段或区域（`.text`/`.rodata`/`.data`/`.bss`/栈/堆）：
```cpp
int g1 = 10;                 // (a)
int g2 = 0;                  // (b)
static int s1 = 5;           // (c)
const char* msg = "hello";   // (d) 指针 msg 本身？ "hello" 字符串？
void func() {
    int local = 1;           // (e)
    static int sl;           // (f)
    int* p = new int(7);     // (g) 指针 p 本身？ new 出来的 int？
}
```

**22.** 给定代码，预测 `nm` 输出中每个符号的标识字母（T/t/D/d/B/b/R/U）：
```cpp
int global_initialized = 42;        // (a)
int global_uninitialized;           // (b)
static int static_initialized = 100;// (c)
static void helper() {}             // (d)
void public_function() {}           // (e)
int main() { printf("hi"); }        // (f) main? printf?
```

**23.** `int sum(int a, int b)` 内 `int temp = 0;`，汇编用 `mov dword ptr[ebp-4], 0`；而取参数 `a` 用 `mov eax, dword ptr[ebp+8]`。问：为什么局部变量用 `ebp-`，参数用 `ebp+`？`ebp+8` 中间"跳过"了什么？

> [!success]- 参考答案（第三节）
> 21. (a) `.data`（已初始化非零全局）；(b) `.bss`（零初始化全局）；(c) `.data`（已初始化静态）；(d) 指针 `msg` 本身在 `.data`（全局指针），`"hello"` 在 `.rodata`；(e) 栈（普通局部）；(f) `.bss`（零初始化局部静态）；(g) 指针 `p` 本身在栈，`new int(7)` 出来的对象在堆。
> 22. (a) `D`（全局已初始化）；(b) `B`（全局未初始化）；(c) `d`（静态已初始化，局部可见）；(d) `t`（static 函数）；(e) `T`（全局函数）；(f) `main` 是 `T`，`printf` 是 `U`（未定义，定义在 libc）。
> 23. 因为 `ebp` 是当前帧的固定基准：序言时 `push ebp`（保存旧 ebp）+ `mov ebp, esp`，随后 `sub esp` 为局部变量在**更低地址**开辟空间，故局部变量在 `ebp-偏移`；而参数是调用者在 `call` **之前**压栈的，位于**更高地址**，故用 `ebp+偏移`。`ebp+8` 跳过了两个 4 字节：`ebp+0` 处的"保存的旧 ebp" 和 `ebp+4` 处的"返回地址"，所以第一个参数在 `ebp+8`。

## 四、找错与修复（指出 bug 并改正）

**24.**
```cpp
int* func() {
    int data = 10;
    return &data;        // 返回局部变量地址
}
```

**25.**
```cpp
void copy(const char* src) {
    char buf[8];
    strcpy(buf, src);    // src 可能远超 8 字节
}
```

**26.**
```cpp
char* p = "hello world";
p[0] = 'H';              // 想把首字母改大写
```

**27.**
```cpp
// 头文件 util.h（被多个 .cpp 包含）
int counter = 0;         // 想做一个全局计数器
```

**28.**
```cpp
// a.cpp
int gdata = 999;
// b.cpp
int gdata;               // 想引用 a.cpp 里的 gdata
int x = gdata + 1;
```

**29.**
```cpp
// C 风格：手动管理一段堆内存并返回
int* makeBuf(int n) {
    int* p = (int*)malloc(sizeof(int) * n);
    for (int i = 0; i < n; ++i) p[i] = i;
    return p;            // 调用方记得 free
}
// 要求：用 Modern C++ 重写，杜绝泄漏
```

> [!success]- 参考答案（第四节）
> 24. **悬垂指针**：`data` 在栈上，函数返回执行 `mov esp,ebp`/`pop ebp` 后其内存被回收，下次调用即被覆盖。修复：按值返回 `int`，或返回堆对象（`std::unique_ptr<int>` / `std::vector`），或由调用者传入缓冲区。
> 25. **缓冲区溢出**：`buf[8]` 装不下长 `src`，溢出会覆盖 saved ebp 和返回地址，可被劫持控制流。修复：用 `std::string`，或 `snprintf`/有界拷贝并检查长度，避免 `strcpy`。
> 26. **写只读段**：`"hello world"` 在 `.rodata`，写入触发段错误；且 `char* p = "..."` 现代 C++ 不合法。修复：`char buf[] = "hello world"; buf[0]='H';`（数组是可写副本），或用 `std::string s = "hello world"; s[0]='H';`。
> 27. **重复定义（ODR 违反）**：头文件里定义全局变量，多个 `.cpp` 包含会产生多份定义，链接报"multiple definition"。修复：头文件用 `extern int counter;`（声明），在某一个 `.cpp` 里定义 `int counter = 0;`；或 C++17 用 `inline int counter = 0;`。
> 28. **概念澄清/潜在重复定义**：`b.cpp` 里 `int gdata;` 是又一个**定义**（暂定定义），与 `a.cpp` 的 `gdata` 在链接时可能冲突或意外合并。要"引用外部"应写 `extern int gdata;`（声明，对应 `nm` 的 `U`），链接器再到 `a.o` 的 `D gdata` 完成符号解析。
> 29. **C 风格手动内存**。Modern 重写：
> ```cpp
> #include <vector>
> #include <numeric>
> std::vector<int> makeBuf(int n) {
>     std::vector<int> v(n);
>     std::iota(v.begin(), v.end(), 0);   // 填 0,1,2,...
>     return v;                            // 移动/RVO 返回，自动释放
> }
> ```
> 要点：`std::vector` 取代 `malloc`，离开作用域自动释放，调用方无需 `free`，无泄漏风险。

## 五、简答题

**30.** 简述编译四个阶段各自的输入、输出和核心任务。

**31.** 词法分析、语法分析、语义分析分别做什么？各能发现哪类错误？

**32.** `.data` 和 `.bss` 有什么区别？为什么要分成两个段？

**33.** 符号表的三大作用是什么？

**34.** 静态链接和动态链接的核心区别、各自优缺点是什么？

**35.** 为什么 `ebp` 在函数运行中比 `esp` 更适合做访问局部变量和参数的基准？

> [!success]- 参考答案（第五节）
> 30. **预处理**：输入 `.c/.cpp`，输出 `.i`，处理 `#` 指令（宏展开/头文件包含/去注释/条件编译）。**编译**：输入 `.i`，输出 `.s`，做词法/语法/语义分析并优化，翻成汇编。**汇编**：输入 `.s`，输出 `.o`，翻成机器码（可重定位目标文件）。**链接**：输入多个 `.o`，输出可执行文件，合并段 + 符号解析 + 重定位。
> 31. **词法分析**：字符流→Token 流，识别关键字/标识符/字面量/操作符；发现非法字符等。**语法分析**：Token→AST，按文法检查结构；发现"语法错误"（缺分号、括号不匹配）。**语义分析**：检查 AST 意义并做类型检查/作用域检查/参数匹配；发现类型不兼容、未声明变量等。
> 32. `.data` 存已初始化且非零的全局/静态变量，需在文件中保存初值，**占磁盘**；`.bss` 存未初始化或零初始化的全局/静态变量，只记录大小**不占磁盘**，运行时分配并清零。分开是为了节省可执行文件体积（大量零数据无需存盘）。
> 33. ① **符号解析**：链接器据符号表把跨模块的引用与定义对应起来；② **重定位**：把符号的临时地址修正为最终内存地址；③ **调试**：调试器用符号表显示函数名/变量名/行号。
> 34. 核心区别在"库代码何时、以何种方式并入程序"。静态链接在链接期把用到的库代码拷进可执行文件：独立性好、不依赖外部库，但体积大、库更新需重新编译，多个程序不能共享。动态链接运行时由 OS 加载 `.so`/`.dll`：体积小、多程序共享、库可单独升级，但运行时依赖环境，缺库无法启动。
> 35. 因为 `esp` 在函数体内会随 `push`/`pop`/子调用频繁变动，偏移不稳定；而 `ebp` 在序言 `mov ebp,esp` 后被固定为本帧基准，整个函数期间不变，于是局部变量（`ebp-`）和参数（`ebp+`）都能用稳定偏移寻址。

## 六、综合分析与设计

**36.** 用文字/ASCII 画出 `int sum(int a, int b)` 被 `main` 调用、刚执行完序言（`push ebp; mov ebp,esp; sub esp,4Ch`）后的栈帧，自上（低地址）而下（高地址）标出：局部变量区、saved ebp、返回地址、参数 a/b，并标注 `esp` 和 `ebp` 位置。

**37.** 解释 `call sum` 与 `ret` 是如何配对工作的（用伪代码描述两条指令对 `esp`/`eip` 的影响），并说明这对"返回地址"为什么是缓冲区溢出攻击的目标。

**38.** （Modern C++ 重构题）下面是一段"C with Classes"风格、依赖全局可变状态与裸内存的计数器模块，请用 Modern C++ 重写（消除头文件全局定义、裸 `new`、悬垂风险）：
```cpp
// counter.h
int* g_counts = nullptr;        // 头文件里定义全局指针（坏味道）
void initCounts(int n) { g_counts = new int[n]; for (int i=0;i<n;++i) g_counts[i]=0; }
void inc(int i) { g_counts[i]++; }
// 没有任何 delete
```

> [!success]- 参考答案（第六节）
> 36.
> ```text
> 低地址（esp 一侧，栈顶）
> ┌─────────────────────────────┐  <- esp（sub esp,4Ch 后的新栈顶）
> │ 局部变量区(temp 等, ebp-4..) │
> ├─────────────────────────────┤  <- ebp（mov ebp,esp 后固定基准）
> │ saved ebp（main 的旧 ebp）   │  ebp+0
> ├─────────────────────────────┤
> │ 返回地址（call 压入）        │  ebp+4
> ├─────────────────────────────┤
> │ 参数 a (10)                  │  ebp+8
> ├─────────────────────────────┤
> │ 参数 b (20)                  │  ebp+12
> └─────────────────────────────┘
> 高地址（main 的栈帧方向）
> ```
> 要点：局部变量在 `ebp-`，saved ebp 在 `ebp+0`，返回地址 `ebp+4`，第一个参数 `ebp+8`；参数由调用者在 call 前从右向左压栈。
> 37.
> ```text
> call ADDR:  push eip(下一条指令地址) ; eip = ADDR     // esp-4，返回地址入栈
> ret:        pop eip                                   // esp+4，弹出返回地址给 eip
> ```
> 二者配对：`call` 压入返回地址使被调函数能跳回，`ret` 弹出它恢复执行流。由于返回地址就在局部变量（如数组）上方的高地址处，向高地址溢出的缓冲区写入会覆盖它；当 `ret` 执行时就跳到被篡改的地址，攻击者借此把控制流导向恶意代码——这正是栈溢出攻击的核心。
> 38.
> ```cpp
> // counter.hpp
> #include <vector>
> class Counter {
> public:
>     explicit Counter(int n) : counts_(n, 0) {}   // RAII：构造即分配
>     void inc(int i) { ++counts_.at(i); }         // at 越界抛异常
>     int get(int i) const { return counts_.at(i); }
> private:
>     std::vector<int> counts_;                    // 自动释放，无裸 new/delete
> };
> ```
> 要点：用类 + `std::vector` 封装状态，RAII 自动管理生命周期；消除头文件全局变量（避免 ODR/多重定义）、裸 `new[]`（无泄漏）、悬垂指针；`at()` 提供边界安全。

## 七、简答深化题

**39.** 从 Section（文件层面）到运行时内存区域（进程层面）是怎样映射的？为什么说"堆和栈不是 `.o` 文件里预先存在的 Section"？

**40.** `const char* msg = "hello";` 中，`msg` 和 `"hello"` 分别存在哪里？为什么很多人会混淆？请把"指针变量本身"和"指针指向的对象"分开讲清。

**41.** 类的非静态成员变量和静态成员变量在存储上有何根本区别？举例说明 `A* p = new A;` 时 `p->x`（非静态）和 `A::count`（静态）各在哪里。

**42.** （跨章综合）结合[[1.2 函数栈帧建立与销毁原理]]与[[1.3 进程的虚拟地址空间]]，说明"为什么不能返回局部变量地址""为什么大数组放栈上易崩溃"本质上是同一类问题的两个表现。

**43.** 弱符号（W）和强符号、未定义符号（U）在链接时如何参与符号解析？弱符号有什么实际用途？

> [!success]- 参考答案（第七节）
> 39. 可执行文件里的 Section（`.text`/`.data`/`.bss`/`.rodata`）在加载时由 OS 映射到进程虚拟地址空间的对应区域：`.text`→代码区、`.rodata`→只读数据区、`.data`→已初始化数据区、`.bss`→未初始化数据区（运行时清零）。但**堆和栈是运行时**由 OS 和运行时环境动态维护的内存区域，文件里只描述了它们的起始/布局约定，并没有现成的 Section 存放堆栈内容——它们随程序执行才产生、增长。
> 40. `msg` 是一个全局指针变量，通常在 `.data`（已初始化非零）；`"hello"` 是字符串字面量，通常在 `.rodata`（只读）。混淆源于把"指针"和"它指向的内容"当成一回事。要点：指针变量本身有自己的存储位置（取决于它是局部/全局/成员），而它指向的对象另有存储位置（可能在堆/栈/`.rodata`/`.data`）。改 `msg` 是改 `.data` 里的指针值，改 `*msg` 才是去写 `.rodata`（非法）。
> 41. 非静态成员变量**跟随对象本体**：对象在堆则成员在堆、在栈则在栈，每个对象各有一份；静态成员变量不属于任何具体对象，类似全局变量存于 `.data`/`.bss`，全类共享一份。例：`A* p = new A;` 时对象在堆，故 `p->x` 在堆；而 `A::count` 在 `.data`/`.bss`，与对象数量无关。
> 42. 两者都源于"**栈内存的生命周期只在函数调用期间**"。返回局部变量地址：函数 `ret` 后该栈帧被回收（`mov esp,ebp`/`pop ebp`），指针指向已失效内存→悬垂。大数组放栈：栈空间有限（线程栈通常 1~8MB），且栈从高地址向低地址生长，过大局部数组会越过栈边界→栈溢出崩溃。本质同为"栈区容量有限且随帧释放"，所以大对象/需跨函数存活的对象应放堆（或 `.data`/`static`）。
> 43. 强符号（已初始化的函数/全局变量定义）在多文件中只能有一个，重复即链接错误；弱符号可有多个，链接器优先选强符号，无强符号时选任一弱符号。未定义符号（U）必须在链接时由某个目标文件/库的定义来解析，否则报"undefined reference"。弱符号用途：提供可被用户覆盖的默认实现（如库默认函数）、避免多处提供同名定义时冲突等。

## 八、概念辨析进阶

**44.** 辨析 `.text` / `.data` / `.bss` / `.rodata`（内容 + 权限 + 是否占磁盘）。

**45.** 辨析 Section / Segment（链接视图 vs 执行视图）。

**46.** 辨析"声明 (declaration)" / "定义 (definition)" / `extern` 关键字（结合符号 U 与 D）。

**47.** 辨析 `esp` / `ebp` / `eip`（在函数调用中的角色）。

> [!success]- 参考答案（第八节）
> 44. `.text`：机器指令，只读+可执行，占磁盘；`.data`：已初始化非零全局/静态变量，可读写，占磁盘；`.bss`：未初始化/零初始化全局/静态变量，可读写，**不占磁盘**（只记大小）；`.rodata`：字符串字面量和只读常量，只读，占磁盘。口诀：text 代码、rodata 只读、data 有初值、bss 零初值不占盘。
> 45. Section 是链接视图的单位（`.text`/`.data`…），供编译器/链接器做静态分析与重定位；Segment 是执行视图的单位（`LOAD` 等），供 OS 加载器决定加载到内存的权限。一个 Segment 可包含多个 Section。口诀：链接看节、运行看段。
> 46. 声明只引入名字与类型、不分配存储（可多次），如 `extern int g;`，对应符号 `U`；定义分配存储/给出实体（全程序唯一），如 `int g=10;`，对应符号 `D`/`B`。`extern` 用于"声明一个在别处定义的符号"，让编译期通过、留待链接解析。口诀：声明是"承诺有"，定义是"真的有"。
> 47. `esp` 栈指针，始终指栈顶（低地址），随 push/pop 变动；`ebp` 帧基指针，序言后固定为当前帧基准，用于稳定寻址局部变量(`ebp-`)与参数(`ebp+`)；`eip` 指令指针，指向下一条要执行的指令，`call` 压入其旧值作返回地址、`ret` 弹回它实现跳转。

## 九、大厂面试场景题 / 八股常考

**48.** 面试官问："`int g;` 写在全局和写在函数里（不加 static），存储位置和生命周期一样吗？为什么？"

**49.** 程序链接时报 `undefined reference to 'foo'`，请说出常见的几种原因和排查思路。

**50.** 程序链接时报 `multiple definition of 'bar'`，最常见的根因是什么？怎么修复？

**51.** "为什么修改一个 `.cpp` 文件后只需重新编译它再链接，而不用全量重编？"请从"编译以文件为单位、链接以工程为单位"解释。

**52.** 线上程序偶发 Segmentation Fault，结合本章知识列出至少 4 类可能原因并说明各自机理。

> [!success]- 参考答案（第九节）
> 48. **不一样**。全局 `int g;` 是静态存储期，放 `.bss`（零初始化），生命周期是整个程序，且产生符号、链接可见；函数内 `int g;`（非 static）是普通局部变量，放**栈**，生命周期仅本次函数调用，**不产生符号**，且未初始化时是垃圾值（不保证为 0）。机理在于存储期与创建方式不同，而非"叫什么名字"。
> 49. **现象**：符号 U 未被解析。**常见原因**：① 只声明没定义（漏实现）；② 定义所在的 `.o`/库没参与链接（漏 `-l`/链接顺序错）；③ C/C++ 混链 name mangling 不一致（缺 `extern "C"`）；④ 函数签名不匹配导致符号名不同。**排查**：`nm`/`objdump -t` 看符号是 U 还是缺失、确认定义文件是否链接、检查链接顺序与 `extern "C"`。
> 50. **根因**：违反 ODR——通常是在**头文件里定义了**全局变量/非 inline 函数，被多个 `.cpp` 包含产生多份强符号定义。**修复**：头文件只放声明（`extern`/函数原型），定义放唯一 `.cpp`；或对变量/函数用 `inline`（C++17 `inline` 变量），或匿名命名空间/`static` 限定为内部链接。
> 51. 编译阶段以**文件**为单位：每个 `.cpp` 独立编译成 `.o`，未改的文件的 `.o` 可复用；链接阶段以**工程**为单位：把所有 `.o` 合并、解析符号、重定位成可执行文件。所以改一个文件只需重编它、再整体链接，大幅节省时间——这正是"分而治之"的编译模型与 Makefile 增量编译的基础。
> 52. ① **空指针解引用**：访问 `0x0` 附近的 OS 保留陷阱区；② **悬垂指针**：用已释放的栈/堆内存（返回局部地址、use-after-free）；③ **缓冲区溢出/越界**：写越界破坏栈帧或堆元数据；④ **写只读段**：改 `.rodata` 字符串字面量；⑤ **栈溢出**：过大局部数组或无限递归越过栈边界。机理都归结为"访问了无权限或已失效的虚拟地址"，触发 MMU 异常被 OS 终止。

## 十、补充加分题

**53.** 32 位系统为何每个进程是 4GB 虚拟地址空间？"用户空间私有、内核空间公有"对进程间通信(IPC)有什么影响？

**54.** 64 位（x86-64）系统的地址空间与 32 位相比有哪些关键变化？为什么实际只用 48 位？

**55.** 虚拟地址是如何变成物理地址的？MMU 在其中起什么作用？虚拟地址空间"它不存在你却看得见"如何理解？

**56.** （性能/机理分析题）`.bss` 不占磁盘但运行时占内存并被清零——这对一个声明了 `int huge[1000000];` 全局数组的程序，磁盘体积和启动行为分别有什么影响？

> [!success]- 参考答案（第十节）
> 53. 32 位地址总线/指针能表示 `2³² = 4GB` 的地址，故每进程虚拟空间 4GB。每个进程的**用户空间私有**（各自独立映射，互不可见），**内核空间公有**（所有进程共享同一份内核映射）。因此进程间通信不能直接读写对方用户空间，需借助内核空间提供的机制（如管道、共享内存、消息队列等）在内核中转或建立共享映射。
> 54. 变化：虚拟空间理论上达 `2⁶⁴`（16 EB），用户/内核各占一半且中间有巨大"空洞"；起始地址不再是 `0x08048000`，而更高（如 `0x400000`）。实际只用 **48 位**（256 TB）是因为当前 CPU 的页表/硬件只实现 48 位有效地址（高位需符号扩展），64 位全用既无必要也增加页表开销。
> 55. CPU 发出虚拟地址，**MMU**（内存管理单元）通过页表把虚拟页号翻译成物理页框号，拼上页内偏移得到物理地址（配合 TLB 缓存加速）。"看得见"是因为进程视角下地址连续可用、可寻址；"不存在"是因为它并非物理内存的真实位置，只有被访问且建立映射时才对应到物理内存（甚至可能在磁盘交换区），未映射部分只是地址编号而无实体。
> 56. **磁盘体积**：`huge` 在 `.bss`，不占磁盘，可执行文件不会因这 4MB 数组而变大（只记录大小）。**启动/运行**：程序加载时 OS 为 `.bss` 分配内存并清零（常用按需分页 + 零页映射，首次访问才真正分配物理页），所以运行时占约 4MB 内存。对比若放 `.data` 并显式初始化非零值，则要把 4MB 数据存进磁盘，文件显著变大。

## 十一、编译链接 · 符号专项

**57.** 写出查看以下信息分别用什么命令（GCC/binutils）：(a) 只做预处理；(b) 只编译到汇编；(c) 编译到目标文件；(d) 查看 ELF 文件头；(e) 查看符号表；(f) 反修饰 C++ 符号名。

**58.** 给定两个文件，描述符号解析与重定位的完整过程：
```c
// file1.c
int gdata = 999;          // 定义
// file2.c
extern int gdata;         // 声明
int a = gdata;
```

**59.** 为什么 C++ 的符号在 `nm` 里看起来是一堆乱码（如 `_Z3sumii`）？这叫什么？它解决了什么 C 语言没有的问题？

**60.** `static` 用在三种位置（全局变量/局部变量/函数）时，分别对"符号可见性/存储期/作用域"产生什么影响？

> [!success]- 参考答案（第十一节）
> 57. (a) `gcc -E main.c -o main.i`；(b) `gcc -S main.i -o main.s`；(c) `gcc -c main.s -o main.o`；(d) `readelf -h main.o`；(e) `nm main.o`（或 `objdump -t` / `readelf -s`）；(f) `nm -C main.o`（demangle）。
> 58. 编译 `file2.c` 时 `gdata` 是外部声明，地址未知，`file2.o` 符号表里标为 `U gdata`；`file1.c` 定义 `gdata`，`file1.o` 里是 `D gdata`（已初始化非零，在 `.data`）。链接时：**符号解析**——链接器在 `file1.o` 找到 `D gdata` 与 `file2.o` 的 `U gdata` 配对；**重定位**——把 `file2.o` 中所有引用 `gdata` 的占位地址修正为 `gdata` 在最终镜像中的实际地址。
> 59. 这叫 **name mangling（名字修饰）**。C++ 支持函数重载、命名空间、类成员，同名函数可有不同参数，编译器把参数类型/作用域等编码进符号名（如 `_Z3sumii` 表示 `sum(int,int)`）以保证符号唯一。C 没有重载，符号名就是函数名。`nm -C` 可反修饰还原可读名；与 C 互操作要用 `extern "C"` 关闭 mangling。
> 60. **全局变量加 static**：把外部链接变为**内部链接**（符号仅本文件可见，`nm` 小写 `d/b`），存储期/作用域不变（仍是文件级）。**局部变量加 static**：作用域仍限函数内，但**存储期变为整个程序**，存放在 `.data`/`.bss`（只初始化一次）。**函数加 static**：函数变内部链接，仅本文件可见（`nm` 小写 `t`），避免与其他文件同名函数冲突。

## 十二、栈帧与内存布局画图专项

**61.** 用 ASCII 画出 32 位进程虚拟地址空间从低地址到高地址的整体布局（至少含：保留区、`.text`、`.rodata`、`.data`、`.bss`、堆、共享库、栈、内核空间），并标出堆和栈各自的生长方向。

**62.** 结合栈帧结构解释一次完整的 `sum(a,b)` 调用中 `esp`/`ebp` 的变化轨迹：从"准备参数"到"`ret` 返回"，列出每一步对栈的影响（序言 push ebp / mov ebp,esp / sub esp，尾声 mov esp,ebp / pop ebp / ret），并说明这套机制如何保证返回后 `main` 的栈帧被正确恢复。

> [!success]- 参考答案（第十二节）
> 61.
> ```text
> 高地址 0xFFFFFFFF
> ┌─────────────────────────┐
> │ 内核空间 (0xC0000000~)   │  所有进程共享，用户态不可访问
> ├─────────────────────────┤
> │ 栈 .stack                │  ↓ 向下生长（高→低），每线程独有
> │      ...                 │
> │ （中间空洞）             │
> │ 共享库映射 (.so/.dll)    │
> │      ...                 │
> │ 堆 .heap                 │  ↑ 向上生长（低→高），malloc/new
> ├─────────────────────────┤
> │ .bss   未初始化/零全局   │
> │ .data  已初始化非零全局  │
> │ .rodata 只读常量/字符串  │
> │ .text  代码 (0x08048000) │  只读可执行
> ├─────────────────────────┤
> │ 保留区 (0x00000000~)     │  空指针陷阱区，访问即段错误
> └─────────────────────────┘
> 低地址 0x00000000
> ```
> 要点：堆向上、栈向下，相向生长以共享中间空间；`.text` 从 `0x08048000` 起，内核空间 `0xC0000000` 以上共享。
> 62. 轨迹：①**准备参数**：`push b`、`push a`（从右向左），`esp` 下移 8。②**call sum**：压返回地址，`esp` 再 -4，`eip` 跳入 sum。③**序言**：`push ebp`（保存 main 的 ebp，`esp`-4）→ `mov ebp,esp`（ebp 固定为当前帧基准）→ `sub esp,4Ch`（为局部变量下移栈顶）。④**函数体**：用 `ebp-` 访问局部变量、`ebp+8/+0Ch` 访问参数，结果入 `eax`。⑤**尾声**：`mov esp,ebp`（栈顶回到 saved ebp 处，瞬间释放局部变量）→ `pop ebp`（恢复 main 的 ebp，`esp`+4，栈顶指向返回地址）→ `ret`（弹出返回地址给 eip，跳回 main）。⑥回到 main 后由调用者 `add esp,8` 清理参数（cdecl）。正因为序言保存了旧 ebp、尾声逐步对称地还原 esp 与 ebp，main 的栈帧基准和栈顶都被精确恢复，调用链得以维持。
