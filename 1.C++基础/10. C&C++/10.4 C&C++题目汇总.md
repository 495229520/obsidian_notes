## 一、选择题（概念基础）

**1.** `extern "C"` 的作用是：
- A. 让 C 代码能调用 C++ 函数　　B. 告诉 C++ 编译器对该函数使用 C 链接规范（不做名称修饰）
- C. 把 C++ 代码编译成 C 代码　　D. 启用 C 语言的标准库

**2.** C++ 调用 C 函数若忘记 `extern "C"`，最典型的后果是：
- A. 运行时崩溃　　B. 编译报错　　C. 链接报 `undefined reference`　　D. 没有任何问题

**3.** 用于判断"当前是否为 C++ 编译环境"的预定义宏是：
- A. `__STDC__`　　B. `__cplusplus`　　C. `__cpp__`　　D. `_CPP_`

**4.** 关于 C 和 C++ 的 `const`，正确的是：
- A. 两者都必须初始化　　B. C 的 const 必须初始化，C++ 可不初始化
- C. C++ 的 const 必须初始化，C 的可不初始化　　D. 两者都可不初始化

**5.** C++ 中 `const int a = 20;` 后 `printf("%d", a)` 通常被编译器优化成 `printf("%d", 20)`，这种优化叫：
- A. 内联展开　　B. 常量折叠　　C. 死代码消除　　D. 循环展开

**6.** 在 C 中可以省略 `struct` 关键字直接写 `Point p;` 吗？
- A. C 和 C++ 都可以　　B. C 可以，C++ 不可以
- C. C 不可以（必须 `struct Point p;`），C++ 可以　　D. 两者都不可以

**7.** C 调用 C++ 类对象时，最常用的跨语言封装手法是：
- A. 把类定义直接放进 C 头文件　　B. 用 `void*` 不透明指针 + `extern "C"` 包装函数
- C. 用模板包装　　D. 用 C++ 引用作参数

**8.** 下列哪种内存释放是**未定义行为**？
- A. `malloc` 配 `free`　　B. `new` 配 `delete`
- C. `new[]` 配 `delete[]`　　D. `malloc` 配 `delete[]`

**9.** GCC/Clang 的 C++ 修饰符号通常以什么前缀开头？
- A. `?`　　B. `_Z`　　C. `@`　　D. `__imp_`

**10.** C++ 中通过 `int* p = (int*)&a; *p = 30;` 修改一个 `const int a` 的值，标准上的定性是：
- A. 合法且可移植　　B. 未定义行为　　C. 编译错误　　D. 一定能成功改值

> [!success]- 参考答案（第一节）
> 1. **B**。`extern "C"` 让 C++ 编译器对被修饰函数按 C 链接规范处理——**不做名称修饰**，符号名保持原样，从而能与 C 目标文件链接。它不改变语言、不"翻译代码"。
> 2. **C**。C++ 会把 `print(int)` 修饰成 `_Z5printi` 之类，而 C 目标文件里是 `print`，链接器找不到匹配符号 → `undefined reference`（MSVC 是 LNK2001/LNK2019）。
> 3. **B**。`__cplusplus` 由 C++ 编译器预定义、C 编译器不定义，配合 `#ifdef __cplusplus` 写出 C/C++ 通用头文件。
> 4. **C**。C++ 的 `const` 必须初始化（`const int b;` 报错）；C 的 const 可以不初始化（本质是"常变量"，编译器至多警告）。
> 5. **B**。常量折叠（Constant Folding）：编译期已知的 `const` 值在使用处被直接替换为字面量，类似宏替换但类型安全。
> 6. **C**。C 中使用结构体类型要带 `struct` 关键字（或先 typedef），C++ 可省略直接 `Point p;`。
> 7. **B**。用 `void*` 不透明指针隐藏 C++ 类型，配 `extern "C"` 导出 `create/destroy/do_something` 等 C 可链接的包装函数。直接把类放进 C 头文件，C 编译器不认识 `class`。
> 8. **D**。三组分配/释放必须配对：`malloc`↔`free`、`new`↔`delete`、`new[]`↔`delete[]`。`malloc` 配 `delete[]` 是 UB。
> 9. **B**。`_Z` 是 GCC/Clang（Itanium ABI）C++ 符号前缀；`?` 是 MSVC C++ 符号；`_` 是某些平台的 C 符号。
> 10. **B**。在 C++ 中 `const` 对象可能被常量折叠、放只读区，强转去 const 后写入是**未定义行为**（典型表现是 `a` 仍读出旧值 20、`*p` 读出 30）。

## 二、概念辨析（判断对错并说明理由）

**11.** `extern "C"` 修饰的函数也可以重载，只要参数列表不同。

**12.** 把 `extern "C" { ... }` 直接写进 C 编译的 `.c` 文件里也能编译通过。

**13.** C++ 异常可以安全地穿过 `extern "C"` 边界传播给调用它的 C 代码。

**14.** 在 C 中 `const int a = 20;` 后通过指针把它改成 30，`a`、`*p`、`*(&a)` 都会读出 30。

**15.** 在 C++ 中对 `const int a = 20;` 同样操作后，`printf("%d %d %d", a, *p, *(&a))` 也会输出 `30 30 30`。

**16.** 头文件里写 `int global_var = 10;` 被多个源文件包含会导致 `multiple definition`。

**17.** C++ 全局对象在不同翻译单元之间的初始化顺序是有保证的、确定的。

**18.** `const int a = getValue();`（`getValue()` 运行时才返回）在 C++ 中仍会被常量折叠。

> [!success]- 参考答案（第二节）
> 11. **错**。`extern "C"` 关闭名称修饰，符号名就是函数名，无法区分同名函数，因此**不能重载**。
> 12. **错**。`extern "C"` 是 C++ 的语法，C 编译器不认识，放进 `.c` 会编译错误。所以惯例用 `#ifdef __cplusplus` 包住它，让 C 编译时跳过。
> 13. **错**。C 不支持 C++ 异常机制，异常穿过 C 帧是未定义行为。必须在 `extern "C"` 边界 `try/catch(...)` 兜住，转成错误码返回。
> 14. **对**。C 把 const 当普通变量存内存，`a`、`*p`、`*(&a)` 都从同一内存读，改后全是 30。
> 15. **错**。C++ 常量折叠：`a` 和 `*(&a)` 被替换成字面量 20，只有 `*p` 从内存读到 30，故输出 `20 30 20`（且改 const 本身是 UB）。
> 16. **对**。头文件里的是**定义**（带初始化/分配存储），多个 TU 包含即重复定义。应改成 `extern int global_var;`（声明），在某个 `.cpp` 里定义一次。
> 17. **错**。跨翻译单元的全局/静态对象初始化顺序**未定义**（static initialization order fiasco）。解决用"首次使用时构造"——函数内静态局部变量。
> 18. **错**。值要到运行时才确定，编译期未知，**不会折叠**，此时 `a` 的行为更接近 C 的 const（真实占内存）。

> [!success]- 参考答案（第三节）
> 19. 输出 `20 30 20`。C++ 常量折叠：`a`→字面量 20，`*p`→内存读 30，`*(&a)`→优化为 20。（注意：写 const 本身是 UB，这是常见编译器的观察结果。）
> 20. 输出 `30 30 30`。C 把 const 当变量存内存，三处都读同一内存，改后全为 30。这正是 C 与 C++ const 的本质差异。
> 21. **链接错误**。C++ 把 `square` 修饰成 `_Z6squarei`，C 目标文件里是 `square`，符号不匹配 → undefined reference / LNK2019。修复：`extern "C" int square(int x);`。
> 22. 输出 `30 30`。`getValue()` 运行时返回，`a` 不被折叠、真实占内存，`a` 和 `*p` 读同一内存都是 30——行为退回到类似 C 的 const。
> 23. 两种情况都是 `c_add`（未修饰）。`.cpp` 包含时 `__cplusplus` 有定义，`extern "C"` 生效，按 C 链接；`.c` 包含时跳过 `extern "C"`，本就不修饰。这保证了同一头文件 C/C++ 都能正确链接。
> 24. C：(1) `const int a;` 合法（可不初始化）；(2) 合法。C++：(1) **报错**（const 必须初始化）；(2) 合法。

// C++ 调用 C 库 mylib.c 中的 void log_msg(const char*);
void log_msg(const char* s);   // 直接声明

```cpp
extern "C" int risky_div(int a, int b) {
    if (b == 0) throw std::runtime_error("div0");  // 提供给 C 调用
    return a / b;
}
```

**27.**
```cpp
char* buf = (char*)malloc(100);
// ... 使用 ...
delete[] buf;
```

**28.**
```cpp
// global.h
int counter = 0;     // 被 a.cpp 和 b.cpp 都 #include
```

**29.**
```cpp
// file1.cpp
std::string config = "default";
// file2.cpp
extern std::string config;
static int n = config.length();  // 读取另一个 TU 的全局对象
```

**30.**
```cpp
const int SIZE = 10;
int* p = (int*)&SIZE;
*p = 20;
int arr_use = SIZE;     // 期望此后 SIZE 是 20
```

> [!success]- 参考答案（第四节）
> 25. **缺 extern "C" 导致名称修饰不匹配**：C++ 修饰 `log_msg`，链接器在 C 目标文件找不到。修复：`extern "C" void log_msg(const char* s);`（或把声明放进带 `#ifdef __cplusplus` 包裹的头文件）。
> 26. **异常穿越 C 边界**：`extern "C"` 函数会被 C 代码调用，C 无法处理 C++ 异常，传播过去是 UB。修复：`try { ... } catch(...) { return -1; }`，用错误码代替异常。
> 27. **malloc/delete[] 混用**：`malloc` 的内存必须 `free`。修复（C 风格）`free(buf);`；Modern C++ 应根本避免裸分配，用 `std::string`/`std::vector<char>`。
> 28. **头文件中定义变量 → multiple definition**：`int counter = 0;` 是定义。修复：头文件改 `extern int counter;`，在某个 `.cpp` 里 `int counter = 0;` 定义一次。（或 C++17 用 `inline int counter = 0;`。）
> 29. **静态初始化顺序未定义**：`file2.cpp` 的 `n` 初始化时，`file1.cpp` 的 `config` 可能尚未构造 → 读到空/崩溃。修复：用"首次使用时构造"——`std::string& config(){ static std::string c = "default"; return c; }`。
> 30. **强转去 const 改 const 是 UB**：C++ 中 `SIZE` 多半被常量折叠，`arr_use` 仍是 10，`*p` 改的内存无意义。修复：本就不该这么干；要可变用普通变量，要编译期常量用 `constexpr int SIZE = 10;`。

## 五、简答题

**31.** 为什么 C++ 需要名称修饰而 C 不需要？这与函数重载有什么关系？

**32.** 写出一个 C/C++ 通用头文件的标准骨架，并解释 `#ifdef __cplusplus` + `extern "C"` 的作用。

**33.** C 调用 C++ 的类时，为什么常用 `void*` 不透明指针？给出包装接口的基本思路。

**34.** C 的 const 和 C++ 的 const 在"内存本质"上最大的区别是什么？什么是常量折叠？

**35.** 混合编译时为什么推荐用 `g++`（而不是 `gcc`）来做最后的链接？

**36.** `undefined reference` 和 `multiple definition` 这两类链接错误分别通常由什么引起？

> [!success]- 参考答案（第五节）
> 31. C++ 支持函数重载，同名函数靠参数列表区分，编译器把参数类型编码进符号名（名称修饰），使每个重载有唯一符号；C 不支持重载，函数名即唯一符号，无需修饰。正因如此，C++ 调 C（或反之）时符号名对不上，要用 `extern "C"` 关闭修饰。
> 32. 骨架：
> ```cpp
> #ifndef LIB_H
> #define LIB_H
> #ifdef __cplusplus
> extern "C" {
> #endif
>     void c_func(int);
> #ifdef __cplusplus
> }
> #endif
> #endif
> ```
> `__cplusplus` 仅在 C++ 编译时有定义：C++ 包含时启用 `extern "C"` 按 C 链接；C 包含时跳过（C 不认识 `extern "C"`）。一份头文件 C/C++ 通用。
> 33. C 不认识 `class`，无法直接持有 C++ 对象类型。用 `void*` 把对象指针"擦除类型"传给 C，再用 `extern "C"` 导出一组操作函数：`void* create()`（内部 `new MyClass` 返回指针）、`void destroy(void*)`（`delete static_cast<MyClass*>(p)`）、`void op(void*, ...)`（转回类型再调方法）。C 侧只拿着不透明句柄。
> 34. C 的 const 是"常变量"：一定占内存、所有访问都从内存读，可被指针改且改了就生效。C++ 的 const 是"常量"：编译期已知值时做**常量折叠**——把使用处直接替换成字面量，可能根本不占可寻址内存。常量折叠就是编译期把已知 const 的值内联到使用点（类似宏但类型安全）。
> 35. `g++` 链接会自动带上 C++ 标准库和运行时（异常、RTTI、全局对象构造等支持）；`gcc` 默认不链接 libstdc++，混合程序里 C++ 部分会缺符号。编译各自的 `.c`/`.cpp` 可分别用 gcc/g++，但**最终链接用 g++**。
> 36. `undefined reference`：声明了却找不到定义——常因缺 `extern "C"` 致符号名不匹配、没链接对应目标文件/库、模板定义没放头文件。`multiple definition`：同一强符号定义多次——常因头文件里写了变量/非 inline 函数定义并被多个 TU 包含。前者"补定义/对符号"，后者"头文件只放声明"。

> extern "C" {

> **38.**
> ```cpp
> // logger_c.h —— C 可见
> #ifdef __cplusplus
> extern "C" {
> #endif
>     void* logger_create();
>     void  logger_write(void* h, const char* msg);
>     void  logger_destroy(void* h);
> #ifdef __cplusplus
> }
> #endif
> // logger_c.cpp
> extern "C" void* logger_create() { return new Logger(); }
> extern "C" void  logger_write(void* h, const char* m) {
>     static_cast<Logger*>(h)->write(m);
> }
> extern "C" void  logger_destroy(void* h) { delete static_cast<Logger*>(h); }
> ```
> 要点：`void*` 不透明句柄擦除 C++ 类型；create/destroy 配对管理生命周期；每个入口 `static_cast` 回真实类型。
>
> **39.**
> ```cpp
> extern "C" int safe_div(int a, int b, int* out) {
>     try {
>         if (b == 0) return -1;          // 失败码
>         *out = a / b;
>         return 0;                        // 成功
>     } catch (...) {
>         return -1;                       // 绝不让异常逃逸到 C
>     }
> }
> ```
> 要点：错误用返回码表达；`catch(...)` 在边界兜住一切异常；结果通过出参 `out` 返回。
>
> **40.**
> ```cpp
> #include <string>
> #include <iostream>
> std::string build(const std::string& name) {
>     return "user:" + name;        // RAII 管理内存，无泄漏/溢出
> }
> int main() {
>     std::string s = build("alice");
>     const std::size_t len = s.size();   // 需要可变就别用 const
>     std::cout << s << " len=" << len << '\n';
> }
> ```
> 要点：`std::string` 消灭 `malloc`/`strcpy`/`strcat`/裸缓冲区与 `malloc`+`delete` 混用；长度若需修改就用非 const 变量，杜绝强转去 const 的 UB。

## 七、简答深化题

**41.** 详细说明从"C++ 源码"到"可执行文件"的过程中，名称修饰发生在哪个阶段、链接器如何用符号名解析调用，从而解释为什么 `extern "C"` 能修好链接错误。

**42.** 静态初始化顺序问题（static init order fiasco）的根因是什么？"首次使用时构造（Construct On First Use）"为什么能解决它？有什么残留代价？

**43.**【跨章综合】结合 [[9.1.10 函数约定调用|调用约定]]，说明为什么"名称修饰对了但仍可能调用出错"——即调用约定不一致会带来什么问题，`__cdecl` 与 `__stdcall` 在这里的差异。

**44.** `const`、`#define` 宏、`constexpr` 三者都能定义"常量"，从类型安全、作用域、是否占内存、是否保证编译期求值角度比较，并说明 C++ 中应优先用谁。

**45.** 为什么 `nullptr` 比 C 的 `NULL`（`(void*)0` 或 `0`）更安全？结合重载决议说明 `f(NULL)` 可能调错重载的场景。

**46.** 解释 `nm -C`、`c++filt`、`undname` 这些工具在排查混合编译链接错误时的作用，以及 `_Z` / `?` 前缀如何帮助你判断符号来源。

> [!success]- 参考答案（第七节）
> 41. 编译阶段，编译器把每个函数按其签名生成符号名——C++ 做名称修饰（编码参数类型），C 不做。链接阶段，链接器靠符号名把"调用处的未定义符号"与"定义处的符号"配对解析。若 C++ 调用方把 `print(int)` 修饰成 `_Z5printi`，而 C 定义方导出 `print`，符号名不匹配就 undefined reference。`extern "C"` 让 C++ 调用方也按 C 规则生成 `print`，两边符号一致即可解析。
> 42. 根因：不同翻译单元的非局部静态对象，其构造顺序由链接/加载顺序决定，标准**不保证**跨 TU 顺序。若 A 的初始化依赖 B，而 B 还没构造，就读到未初始化对象。Construct On First Use 把对象藏进函数内的 `static` 局部变量，C++ 保证它在**首次调用该函数时**才构造，从而强制"用之前必已初始化"。残留代价：首次访问有一次初始化判断（线程安全的局部静态在 C++11 起由编译器加同步）、对象通常不再析构（或析构顺序仍需小心）。
> 43. 名称修饰解决的是"找不找得到符号"，调用约定解决的是"怎么传参/谁清栈"。即使符号匹配，若调用方与被调方对参数压栈顺序、栈清理责任理解不一致（如一方以为 `__cdecl` 调用者清栈、另一方按 `__stdcall` 被调用者清栈），运行时会栈不平衡、崩溃或数据错乱。Windows 下跨语言/跨 DLL 要显式统一约定（如都 `__stdcall`），`__cdecl` 调用者清栈支持可变参数，`__stdcall` 被调用者清栈是 Win32 API 惯例。
> 44. `#define`：纯文本替换，无类型、无作用域（全局污染）、不占内存、编译期、但不类型安全易出错；`const`：有类型、有作用域、C++ 中可能被折叠不占内存、但不保证编译期求值（运行时初值就退化为普通常变量）；`constexpr`：有类型、有作用域、**保证编译期可求值**、可用于数组维度/模板实参。优先级：能 `constexpr` 就 `constexpr`，否则 `const`，尽量不用宏定义常量。
> 45. `NULL` 常被定义为整数 `0`，参与重载决议时会被当 `int`，导致 `f(int)` 与 `f(char*)` 同时存在时 `f(NULL)` 误选 `f(int)`。`nullptr` 类型是 `std::nullptr_t`，只能隐式转成指针、不能转成整数，故 `f(nullptr)` 稳定选指针重载，类型安全。
> 46. `nm -C program.o` 列出目标文件符号并解码（demangle）修饰名，便于看清缺哪个符号；`c++filt _Z5printi` 把单个修饰符号还原成 `print(int)`；`undname`（MSVC）解码 `?` 开头的 MSVC 符号。前缀帮助判断来源：`_Z` 是 GCC/Clang C++ 符号（说明被修饰了，可能缺 `extern "C"`），`?` 是 MSVC C++ 符号，纯函数名（无前缀修饰）通常是 C 符号——对比调用方/定义方前缀即可定位是不是修饰不一致。

## 八、概念辨析进阶

**47.** 辨析「名称修饰」「调用约定」「链接规范（`extern "C"`）」三者，各自解决什么层面的问题。

**48.** 辨析 C 的 const（常变量）、C++ 的 const（常量）、`constexpr` 三者在"是否占内存、是否编译期、能否被指针改后生效"上的差异。

**49.** 辨析 `undefined reference`、`multiple definition`、`LNK4042` 三类链接器诊断的成因。

**50.** 辨析 `malloc/free`、`new/delete`、`new[]/delete[]`，并说明为什么三者绝不能交叉混用。

> [!success]- 参考答案（第八节）
> 47. 名称修饰：编译期把函数签名编码进符号名（解决"重载如何唯一标识、链接如何配对"）；调用约定：参数传递顺序与栈清理责任（解决"运行时怎么调用、栈平不平衡"）；链接规范 `extern "C"`：选择按 C 还是 C++ 规则生成符号（解决"跨语言链接符号名对齐"）。口诀：修饰管"名字"，约定管"调用方式"，`extern "C"` 管"用哪套命名规则"。
> 48. C 的 const：一定占内存、运行期变量、指针改后生效（真改）。C++ 的 const：编译期已知值时折叠、可能不占可寻址内存、强转去 const 改它是 UB（常读出旧值）。`constexpr`：保证编译期求值、可用作编译期常量（数组维度/模板参数），更明确。口诀：C 的 const 是"变量"，C++ 的 const 是"可能被内联的常量"，`constexpr` 是"铁定编译期"。
> 49. `undefined reference`：符号有引用无定义（缺 `extern "C"`/缺目标文件/缺库）。`multiple definition`：同一强符号定义多次（头文件里放了定义）。`LNK4042`：链接器发现同名符号来自不同编译单元/设置，常因同名源文件（`x.c` 与 `x.cpp` 生成同名 `x.obj`）或缺 `extern "C"`。口诀：找不到 vs 太多份 vs 重名冲突。
> 50. `malloc/free` 是 C 库函数、只管原始内存不调构造析构；`new/delete` 是运算符、分配并构造/析构单个对象；`new[]/delete[]` 处理数组并对每个元素构造/析构。交叉混用（如 `malloc` 后 `delete`、`new[]` 后 `delete`）会导致析构不调用、堆元信息不匹配、堆破坏——UB。口诀：哪套分配就用哪套释放，单个对单个、数组对数组。

## 九、大厂面试场景题

> 偏真实工程：跨语言集成、构建链接、库设计。

**51.** 你要把一个成熟的 C++ 算法库提供给一个纯 C 的老项目调用。请描述你的接口设计方案（头文件、对象生命周期、异常、内存所有权）和需要规避的坑。

**52.** 编译一个 C++ 调 C 的项目时报 `undefined reference to 'foo'`，但 `foo` 明明在 C 文件里定义了。你会怎么一步步排查并定位根因？

**53.** 某 C/C++ 混合工程在 Windows 上偶发崩溃，调试发现是一个跨 DLL 的回调函数栈不平衡。最可能是什么问题？怎么修？

**54.** 团队有人用 `const int` 定义了一组"配置常量"放在头文件里，另一处用 `(int*)&CONF` 强转后修改来做"热更新"，线上行为时灵时不灵。请解释为什么时灵时不灵，正确做法是什么。

**55.** 一个 C++ 库的全局 `Logger` 单例在程序退出时偶发崩溃，怀疑和另一个全局对象的析构顺序有关。请解释成因并给出工程上稳妥的设计。

> [!success]- 参考答案（第九节）
> 51. **方案**：① 头文件用 `#ifdef __cplusplus` + `extern "C"` 暴露纯 C 接口；② 用 `void*` 不透明句柄封装 C++ 对象，提供 `create/destroy` 配对管理生命周期；③ 每个入口 `try/catch(...)` 把异常转成错误码，绝不让异常逃逸；④ 明确内存所有权——谁分配谁释放，跨边界内存提供配套 `lib_alloc/lib_free`，不让 C 侧 `free` 掉 C++ `new` 的内存。**坑**：异常逃逸、`new/free` 混用、把 C++ 类型/模板/`bool` 直接塞进 C 头文件、调用约定不一致、最终链接忘了用 g++。
> 52. **现象**：链接缺符号。**排查**：① `nm -C foo.o | grep foo` 看 C 目标文件里符号是不是裸 `foo`；② `nm -C main.o | grep foo` 看 C++ 调用方引用的是不是 `_Z3fooi`（被修饰）；③ 若一边修饰一边没修饰 → 根因是 C++ 声明缺 `extern "C"`；④ 顺带确认 `foo.o` 真的参与了链接、用的是 g++ 链接。**解决**：给声明加 `extern "C"`（或放进带 `__cplusplus` 守卫的头文件）。**延伸**：模板/inline 缺定义、库顺序也会报同样错。
> 53. **现象**：跨 DLL 回调栈不平衡崩溃。**原因**：调用方与被调方**调用约定不一致**（一方 `__cdecl` 调用者清栈，另一方按 `__stdcall` 被调用者清栈），每次调用栈指针偏移积累导致崩溃。**解决**：在函数指针 typedef、声明、定义三处显式统一调用约定（Windows 回调常用 `__stdcall`/`CALLBACK`），并确保头文件被双方共享。**延伸**：名称修饰对了不代表调用方式对了（见第 43 题）。
> 54. **现象**：强改 const 配置时灵时不灵。**原因**：C++ 对编译期已知的 `const` 做常量折叠，使用处被替换成字面量，强转改内存对"已折叠的读取点"无效（读旧值）；只有未折叠（如运行时初始化）的读取点才读到新值——是否折叠取决于编译器/优化，故时灵时不灵，且本质是 UB。**解决**：配置要可变就用普通变量/原子变量+正规热更新机制；要编译期常量用 `constexpr`；绝不强转去 const。
> 55. **现象**：退出时全局单例析构崩溃。**原因**：跨 TU 全局对象析构顺序是构造逆序但跨 TU 仍不确定，`Logger` 可能先于仍在使用它的对象析构，后者析构里再用 `Logger` → 访问已销毁对象。**解决**：用 Construct/Use On First Use——`Logger& logger(){ static Logger inst; return inst; }`；或用带生命周期管理的单例（引用计数/显式 shutdown 顺序）。**延伸**：这是 static init/destroy order fiasco 的析构侧表现。

## 十、补充加分题

**56.**【编译期 vs 运行期】请判断下列各项发生在编译期还是运行期，并简述依据：① C++ 对 `const int n=5` 的常量折叠；② 名称修饰；③ `extern "C"` 的链接规则选择；④ `const int n=getValue()` 的取值；⑤ 全局对象构造。

**57.**【符号/底层】给定 GCC 修饰符号 `_Z5printi` 与 `_Z5printPKc`，分别还原成 C++ 函数签名，并说明 `i`、`PKc` 的含义；再说明为什么 `extern "C"` 后符号会变成 `print`。

**58.**【性能/设计】跨 C 边界用 `void*` 不透明指针封装 C++ 对象，相比"直接内联 C++ 代码"，在调用开销、可内联性、ABI 稳定性上各有什么取舍？为什么库的稳定 ABI 边界常故意用这种"句柄 + C 接口"风格？

> [!success]- 参考答案（第十节）
> 56. ① 编译期（值编译期已知，折叠成字面量）；② 编译期（编译器按签名生成符号名）；③ 编译期（`extern "C"`/`__cplusplus` 决定生成何种符号，是编译期决策）；④ 运行期（`getValue()` 运行时才返回，故 `n` 不折叠）；⑤ 运行期（全局对象在 `main` 前的运行时初始化阶段构造，跨 TU 顺序未定义）。
> 57. `_Z5printi` → `print(int)`（`i`=int）；`_Z5printPKc` → `print(const char*)`（`PKc`：P=pointer、K=const、c=char，即"指向 const char 的指针"）。`_Z` 是 Itanium ABI 前缀、`5print` 是长度+名字。加 `extern "C"` 后按 C 链接、不修饰，符号回到纯 `print`——也因此这俩重载就无法共存。
> 58. **取舍**：`void*` 句柄 + C 接口每次调用要过一层函数边界、`static_cast` 还原类型，**不能跨边界内联**，有轻微调用开销；但换来**ABI 稳定**——调用方只依赖固定的 C 函数签名和不透明指针，C++ 类的内存布局/成员/模板改了都不影响二进制接口。直接内联 C++ 代码可内联、零开销，但把类布局暴露成 ABI，库一改头文件下游就得重编。**结论**：动态库/插件/跨语言边界追求 ABI 稳定与解耦，故意用"句柄+C 接口"（如很多 C 库、Windows COM 风格）；追求极致性能且同源编译时才内联 C++。

## 十一、编译与链接专项

> 本章本质是"编译/链接"主题，单列一节强化符号、目标文件与构建链路的推理。

**59.** 解释从多个 `.c`/`.cpp` 到可执行文件的完整链路：预处理 → 编译 → 汇编 → 链接，各阶段产物是什么，名称修饰和符号解析分别发生在哪一步。

**60.** 给定构建：`a.cpp` 定义 `int g=1;`，`b.cpp` 也定义 `int g=1;`，`c.h` 里写 `int g;` 被两者包含。会出现什么链接结果？分别如何修复"头文件定义"和"多 TU 定义同名全局"？

**61.** 同一工程里有 `parser.c` 和 `parser.cpp`，构建后报 `LNK4042`。请说明触发原因，并给出至少两种解决办法。

**62.** 一个头文件里的函数 `inline int sq(int x){return x*x;}` 被 10 个 `.cpp` 包含却不报 multiple definition，但去掉 `inline` 就报错。请从 ODR 角度解释。

> [!success]- 参考答案（第十一节）
> 59. 预处理：展开 `#include`/宏，产出翻译单元（纯文本）；编译：语法分析+生成目标代码，C++ 在此做**名称修饰**生成带修饰符号的汇编；汇编：汇编代码→机器码目标文件 `.o`/`.obj`（含符号表、未解析符号）；链接：把各目标文件/库的符号配对解析（**符号解析**在这一步），重定位地址，产出可执行文件。修饰发生在编译、解析发生在链接——所以修饰不一致到链接才暴露。
> 60. `c.h` 的 `int g;` 是**暂定定义**，被多个 TU 包含+`a.cpp`/`b.cpp` 各自又定义，链接器看到多个强符号 `g` → `multiple definition`。修复"头文件定义"：头文件改 `extern int g;`，仅一个 `.cpp` 里 `int g=1;`。修复"多 TU 同名全局"：只保留一处定义，其余用 `extern` 声明引用；若确需每个 TU 私有，用 `static`（内部链接）或匿名命名空间。C++17 也可 `inline int g=1;` 放头文件。
> 61. **原因**：同名源文件 `parser.c` 与 `parser.cpp` 编译出同名目标 `parser.obj`，相互覆盖/冲突，链接器报 LNK4042（同名符号来自不同编译单元/设置）；也可能叠加"C++ 调 C 缺 `extern "C"`"。**解决**：① 重命名源文件避免同名（`parser_c.c`/`parser_cpp.cpp`）；② 配置构建把 C/C++ 目标输出到不同目录；③ 正确加 `extern "C"` 让跨语言符号一致。
> 62. ODR 规定非 inline 函数全程序只能有一个定义，头文件里的普通函数定义被 N 个 TU 包含即 N 份定义 → 违反 ODR、链接报重复定义。`inline` 是 ODR 的法定例外：允许同一函数在多个 TU 各有一份**完全相同**的定义，链接器把它们折叠成一个（符号是 weak/COMDAT）。所以 `inline int sq` 可安全放头文件，去掉 `inline` 就回到"一处定义"约束而报错。
