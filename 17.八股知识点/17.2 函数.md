# 17.2 函数

按 C++17 整理，重点讨论普通函数。每题附原笔记引用，代码片段彼此独立。

## 一、声明、定义与顺序

### 1. 声明和定义有什么区别？必须写在调用前吗？

声明告诉编译器函数名、返回类型和参数类型；定义提供函数体。定义同时也是声明，因此可以直接把完整定义放在调用前。

普通函数调用处需要先看见声明，定义可以放在调用后或其他源文件。参数名可以省略，也不必与定义中的名字相同；接口类型必须一致。

```cpp
int add(int, int);                 // 先声明

int main() {
    return add(1, 2) == 3 ? 0 : 1; // 此处知道接口即可
}

int add(int a, int b) {            // 后定义
    return a + b;
}
```

只有声明、实际调用却找不到定义，通常会出现链接错误。函数之间相互调用时，先声明再分别定义；自己直接递归不需要额外声明。类内定义的成员函数可以调用同一个类里稍后声明的成员函数，不必机械地按调用顺序排列。

引用：[[1.C++基础/9. 函数/9.1 基础函数/9.1.8 函数声明与定义|函数声明与定义]]。

### 2. 声明和定义通常放在哪里？

- 对外接口声明放 `.h/.hpp`，普通函数定义放一个 `.cpp`；调用方和实现方都包含这个头文件。
- 仅当前 `.cpp` 使用的辅助函数，可以放匿名命名空间中，避免暴露给其他源文件。
- 模板定义、需要在头文件提供实现的 `inline` 函数，通常放头文件。
- 普通函数定义不能直接嵌套在另一个函数体中；需要局部可调用对象时可以用 lambda。

同一个函数可以有多次一致声明。普通具有外部链接的非 `inline` 函数，在程序中需要定义时只能有一个定义。

头文件保护只防止同一翻译单元重复包含，不能解决多个 `.cpp` 包含头文件后产生的普通函数重复定义。

引用：[[1.C++基础/9. 函数/9.1 基础函数/9.1.9 头文件#4. 源文件与头文件的分工|头文件与源文件]]、[[1.C++基础/11. 编译器/11.1 ODR唯一定义规则|ODR]]。

## 二、默认参数

### 3. 默认参数只能写在声明中，不能写在定义中吗？

不对。定义也是声明，所以两处都可以提供默认值；同一作用域中，已经可见的默认值不能重复指定，即使两次相同也不行。

```cpp
int sum(int a, int b = 10);        // 默认值放接口声明中

int sum(int a, int b) {            // 定义处不再重复 = 10
    return a + b;
}

int square(int x = 2) {           // 定义同时作为首次声明，可以给默认值
    return x * x;
}
```

调用处必须已经看见相应默认值，才能省略实参。`sum(1)` 等价于 `sum(1, 10)`，`square()` 等价于 `square(2)`。工程中通常把默认值放在头文件声明里，让各调用方看到同一套接口；只写在另一个 `.cpp` 的定义中，对调用方没有帮助。

引用：[[1.C++基础/9. 函数/9.1 基础函数/9.1.2 函数参数#默认参数|默认参数]]；[标准草案：默认参数规则](https://eel.is/c++draft/dcl.fct.default)。

### 4. 默认值为什么不能隔开？调用时能跳过中间参数吗？

对普通、非参数包的形参，一旦某个参数有默认值，它右侧的参数也必须有默认值，可以来自当前声明或同一作用域先前的声明。

- `void f(int a, int b = 2, int c = 3);` 合法。
- 单独写 `void f(int a = 1, int b, int c = 3);` 不合法，`b` 缺默认值。
- `f(1)` 使用后两个默认值；`f(1, 8)` 只使用最后一个默认值。
- 不能写 `f(1, , 9)` 跳过中间参数；必须写 `f(1, 2, 9)`。

默认参数不属于函数类型，也不会生成多个重载。默认表达式在每次需要它的调用时求值，可能包含函数调用，并不保证“使用默认参数更快”。

引用：[[1.C++基础/9. 函数/9.1 基础函数/9.1.2 函数参数#默认参数|默认参数]]；[标准草案：位置、求值与函数类型](https://eel.is/c++draft/dcl.fct.default)。

## 三、函数重载

### 5. 重载根据什么区分？返回类型可以吗？

普通函数在同一作用域中同名，参数类型列表不同，可以构成重载。

| 差异 | 能否构成重载 | 示例 |
|---|---|---|
| 参数个数 | 能 | `f(int)` 与 `f(int, int)` |
| 参数类型 | 能 | `f(int)` 与 `f(double)` |
| 参数类型的排列顺序 | 能 | `f(int, double)` 与 `f(double, int)` |
| 只有参数名不同 | 不能 | `f(int a)` 与 `f(int b)` |
| 只有返回类型不同 | 不能 | `int f(int)` 与 `double f(int)` |
| 只有默认值不同 | 不能 | `f(int = 1)` 与 `f(int = 2)` |

所以“根据参数列表、返回类型区分重载”不准确。普通函数调用不会根据接收结果的变量类型来挑选重载；仅返回类型不同的两个声明本身就不合法。

引用：[[1.C++基础/9. 函数/9.2 函数重载/9.2.1 函数重载#2. 函数重载的条件|重载条件]]；[C++17 标准草案：不能构成重载的声明](https://timsong-cpp.github.io/cppwp/n4659/over.load)。

### 6. const、引用、数组参数怎样影响重载？

- `f(int)` 与 `f(const int)` 是同一函数：按值参数的顶层 `const` 不参与区分。`f(int*)` 与 `f(int* const)` 也是如此。
- `f(int*)` 与 `f(const int*)` 可以重载；`f(int&)` 与 `f(const int&)` 也可以，所指或所引用对象的类型不同。
- `f(int&)` 与 `f(int&&)` 可以区分左值、右值。
- `f(int a[5])`、`f(int a[10])`、`f(int* a)` 都调整为同一种参数类型，不能靠数组长度重载；数组引用 `int (&a)[5]` 则保留长度。
- 非静态成员函数的 `void f();` 与 `void f() const;` 可以重载，区别在于是否允许修改当前对象。

引用：[[1.C++基础/9. 函数/9.2 函数重载/9.2.1 函数重载#3. const 修饰符与函数重载|const 重载]]、[[1.C++基础/9. 函数/9.1 基础函数/9.1.2 函数参数#使用模板和数组引用|数组参数]]。

### 7. 前面的参数相同，后面多一个默认参数，会怎样？

两个重载可以合法共存，但省略最后一个实参时可能二义。区别在于“能声明两个函数”和“某次调用能否唯一匹配”。

```cpp
void log(int level);
void log(int level, int code = 0);

void test() {
    // log(1);                    // 错误：两个版本都能匹配，二义性
    log(1, 2);                    // 正确：只有第二个版本能匹配
}
```

编译器不会因为第一个函数“参数更少”或“不需要默认值”就优先选它。若同样的实参对两个重载有不同的类型匹配优劣，则还要按重载决议判断，不能仅看有没有默认参数。

设计接口时，避免这类调用范围重叠；可删除多余重载、去掉默认值，或使用不同函数名。

引用：[[1.C++基础/9. 函数/9.2 函数重载/9.2.1 函数重载#6. 默认参数与函数重载|默认参数与重载冲突]]。

### 8. 有隐式类型转换时，怎样选择重载？

先找出实参数量和类型都能匹配的候选，再比较转换优劣。常见顺序是：精确匹配优于类型提升，类型提升优于其他标准转换，标准转换优于用户定义转换。

例如 `f(int)` 与 `f(double)`：`f(1)` 选前者，`f(1.0)` 选后者；传入 `short` 时，提升为 `int` 优于转换为 `double`。

多参数时不能只看第一个参数，也不是“转换次数相加，谁少选谁”；需要有唯一最佳候选。若 `f(int, double)` 与 `f(double, int)` 都可见，调用 `f(1, 1)` 就会二义。

引用：[[1.C++基础/9. 函数/9.2 函数重载/9.2.1 函数重载#5. 重载决议 (Overload Resolution)|重载决议]]；[C++17 标准草案：最佳候选](https://timsong-cpp.github.io/cppwp/n4659/over.match.best)、[转换优先级](https://timsong-cpp.github.io/cppwp/n4659/over.ics.rank)。

## 四、inline 与内联展开

### 9. inline 只是建议，已经没有实际作用了吗？

`inline` 对“把函数体展开到调用点”的作用是建议，编译器可以忽略；没写 `inline` 的函数也可能被展开。展开可能减少调用开销、便于进一步优化，也可能增大代码体积，并不保证更快。

但不能说 `inline` 已经“名存实亡”。它还有明确的语言作用：允许同一个具有外部链接的函数，在满足 ODR 条件时定义于多个翻译单元。因此，**写在头文件中的函数定义**是它的一项实际用途。

“内联展开”是编译器优化，“声明为 inline”是语言属性，两者不能等同。

引用：[[1.C++基础/11. 编译器/11.3 inline|inline]]、[[2.C++高级/2. inline 内联/2. inline内联#1. 简介与现代认知|inline 的两种作用]]；[标准草案：inline 语义](https://eel.is/c++draft/dcl.inline)。

### 10. inline 函数如何放进头文件？有哪些限制？

```cpp
// utils.h
#pragma once

inline int twice(int x) {
    return x * 2;
}
```

多个 `.cpp` 可以包含这个头文件。各翻译单元中的定义需要满足 ODR：定义的 token 序列相同，名称查找结果等也符合一致性要求；不能只是“函数名相同”。同一翻译单元内仍不能重复定义。

通常把完整定义放头文件，让使用它的翻译单元可见。只在头文件声明 `inline`，却把定义藏在一个 `.cpp` 中，不是正确的通用组织方式。

在 C++17 中，类内定义的成员函数、`constexpr` 函数隐式为 `inline`。同一个外部链接 `inline` 函数在全程序中是同一实体，地址相同，函数内的静态局部变量也共享。

引用：[[1.C++基础/11. 编译器/11.3 inline#4. inline 与 ODR|inline 与 ODR]]、[[1.C++基础/11. 编译器/11.1 ODR唯一定义规则#4. 多翻译单元中的定义|跨文件定义规则]]；[C++17 标准草案：ODR](https://timsong-cpp.github.io/cppwp/n4659/basic.def.odr)。

## 五、递归与优化

### 11. 递归要满足什么条件？深度增加会发生什么？

递归需要明确的终止条件，并保证每一步都朝终止条件推进。只有出口代码、实际却永远到不了，仍然会无限递归；图遍历还要防止沿环反复访问。

通常每一层未返回的调用都占用栈帧。若每层额外空间为常数，最大深度为 D，递归栈空间就是 `O(D)`；深度过大可能栈溢出，不能指望用普通 C++ 异常稳定捕获。

时间复杂度看总调用量，栈空间看同时存活的最深调用链：线性递归不一定慢，存在大量重复分支的递归才可能出现指数级计算。

尾递归可能被编译器优化成循环，但 C++ 不保证尾调用优化。需要控制深度时，可改循环或显式栈；显式栈通常仍需保存相应状态，只是避免依赖深层函数调用栈。

引用：[[1.C++基础/9. 函数/9.1 基础函数/9.1.11 递归函数|递归函数]]、[[1.C++基础/1. 计算机基础/1.2 函数栈帧建立与销毁原理|函数栈帧]]。

### 12. 记忆化和动态规划分别优化什么？

记忆化在递归中缓存已经求出的状态，下次直接复用，减少重复计算。它本身就是自顶向下的动态规划；通常不会减少第一次计算时的最大递归深度，还需要缓存空间。

自底向上的动态规划按依赖顺序用循环求解状态，可以去掉递归栈；如果只依赖少量旧状态，还能使用滚动数组或几个变量压缩空间。

以斐波那契为例，按单次整数运算为常数时间计算：

| 方法 | 时间 | 额外空间 |
|---|---|---|
| 朴素递归 | 指数级 | `O(n)` 递归栈 |
| 记忆化递归 | `O(n)` | `O(n)` 缓存 + `O(n)` 递归栈 |
| 自底向上，用两个变量递推 | `O(n)` | `O(1)` |

不是所有递归都值得加缓存：需要存在可复用的重复子问题，缓存键还要完整表达状态。若瓶颈只是调用链太深，单纯记忆化通常解决不了。

引用：[[5.算法/5.2 算法/5.2.19 动态规划#两种实现方式|记忆化与递推]]、[[5.算法/5.2 算法/5.2.19 动态规划#变量代替数组|空间优化]]。

## 六、函数模板

### 13. 模板参数怎样推导？类型不同会自动找共同类型吗？

编译器比较函数形参模式和实参类型，在编译期推导模板参数。同一个 `T` 从不同实参推导出的结果必须一致，不会为了凑成一致类型而自动进行 `int → double` 转换。

```cpp
template<class T>
T combine(T a, T b) {
    return a + b;
}

// combine(1, 2);              // T = int，结果为 3
// combine(1, 2.5);            // 错误：T 分别推导为 int 和 double
// combine<double>(1, 2.5);    // 显式指定 T = double，结果为 3.5
```

需要接受不同类型时，可以改用两个模板参数，如 `template<class T, class U> auto combine(T a, U b)`，在函数体中 `return a + b;`，由返回表达式推导结果类型；不必为每种类型组合写特化。

“函数模板不允许隐式转换”也不准确：推导阶段有自己的匹配规则；类型确定后，不参与推导或已显式指定类型的形参可以进行正常的隐式转换。

引用：[[1.C++基础/9. 函数/9.2 函数重载/9.2.2 函数模版#5. 类型推导规则|模板参数推导]]、[[1.C++基础/9. 函数/9.2 函数重载/9.2.5 auto类型推导#3.3 C++14 简化写法|不同参数类型与返回类型]]；[C++17 标准草案：调用中的推导](https://timsong-cpp.github.io/cppwp/n4659/temp.deduct.call)。

### 14. 按值、引用、const 和数组分别怎么推导？

假设 `const int ci = 1;`、`int a[3]{};`：

| 形参模式 | 实参 | 推导结果 |
|---|---|---|
| `T value` | `ci` | `T = int`，忽略顶层 const |
| `T& value` | `ci` | `T = const int`，形参为 const int& |
| `const T& value` | `ci` | `T = int`，const 已由形参模式提供 |
| `T value` | `a` | `T = int*`，数组退化 |
| `T& value` | `a` | `T = int[3]`，保留数组类型和长度 |

按值推导忽略顶层 `const`，但保留所指对象的 `const`：传入 `const int*` 时，`T` 仍是 `const int*`。不能笼统地说“模板推导会去掉 const”。

对于由当前函数模板推导的 `T&&`，它是转发引用：传入 `int` 左值时 `T = int&`，引用折叠后形参为 `int&`；传入 `int` 右值时 `T = int`，形参为 `int&&`。`const T&&` 不属于这种情况。

引用：[[1.C++基础/9. 函数/9.2 函数重载/9.2.2 函数模版#5.2 引用和 const 的处理|引用与 const 推导]]；[C++17 标准草案：推导调整与转发引用](https://timsong-cpp.github.io/cppwp/n4659/temp.deduct.call)。

### 15. 什么时候显式指定类型？能只指定一部分吗？

当推导冲突、模板参数没有出现在可推导位置，或者想主动指定计算类型时，可以写 `函数名<类型...>(实参...)`。从左往右指定，后面的参数可以继续推导或使用默认模板参数。

```cpp
template<class R, class A>
R convert_to(A value) {
    return static_cast<R>(value);
}

// convert_to<int>(3.8);       // R 显式指定为 int，A 推导为 double，结果为 3
// int x = convert_to(3.8);    // 错误：普通调用不会根据左侧的 int 反推 R
```

函数默认实参不能用来推导模板类型：`template<class T> void f(T x = 0);` 的 `f()` 无法推导 `T`；可以调用 `f<int>()`，或另给默认模板参数 `template<class T = int>`。

模板参数数量多于函数实参数量，并不代表一定要显式指定。例如 `template<class T, std::size_t N> void inspect(T (&a)[N]);`，从一个数组实参就能同时推导元素类型 `T` 和长度 `N`。

引用：[[1.C++基础/9. 函数/9.2 函数重载/9.2.6 函数模版参数|模板参数与非类型参数]]、[[1.C++基础/9. 函数/9.2 函数重载/9.2.5 auto类型推导#3.1 显示指定返回类型|显式指定返回类型]]；[C++17 标准草案：显式模板实参](https://timsong-cpp.github.io/cppwp/n4659/temp.arg.explicit)。

### 16. 函数模板特化是什么？支持偏特化吗？

全特化用 `template<>` 为某组确定的模板实参提供专门实现。例如普通相等比较对指针比较地址，而 C 字符串需要比较内容：

```cpp
#include <cstring>

template<class T>
bool same(T a, T b) {
    return a == b;
}

template<>
bool same<const char*>(const char* a, const char* b) {
    return std::strcmp(a, b) == 0; // 前提：a、b 均指向有效的零结尾字符串
}
```

`same(1, 1)` 使用主模板；两个 `const char*` 实参使用这个全特化。`char*` 和 `const char*` 是不同类型，不会自动共用同一个特化。

函数模板支持全特化，**不支持偏特化**。`template<class T> void f(T*);` 是另一个函数模板重载，不是对 `f(T)` 的偏特化。

特化声明应在主模板声明之后，并在每个相关翻译单元中先于会触发该版本隐式实例化的使用。若把函数模板全特化的定义放进公共头文件，通常要单独加 `inline`；它不会自动继承主模板的 `inline` 属性。

### 17. 普通函数和函数模板同时匹配，谁优先？

先比较实参到形参的匹配优劣；在其他条件相同、匹配同样好的情况下，普通函数优先。模板匹配更好时，模板可以胜出。

```cpp
int pick(int) {
    return 1;
}

template<class T>
int pick(T) {
    return 2;
}

// pick(1);                   // 1：同样精确匹配，普通函数优先
// pick(1.5);                 // 2：模板直接匹配 double，普通函数需要转换
// pick<>(1);                 // 2：显式使用模板语法，排除普通函数
```

`pick<>(1)` 的空尖括号表示使用函数模板，模板参数仍可自动推导；它不保证选中某一个主模板，也不意味着跳过该模板对应的全特化。

### 18. 多个模板怎样选择？全特化会独立参与竞争吗？

匹配同样好时，通过模板偏序选择更特定的模板。例如对指针实参，`f(T*)` 通常比 `f(T)` 更特定；这里的“偏序”是比较重载，不是偏特化。无法选出唯一最佳候选时仍会二义。

全特化不作为独立的重载候选竞争。先通过重载决议选中函数模板，再使用它对应的全特化（如果有）；不能背成固定的“普通函数 > 全特化 > 主模板”。

```cpp
template<class T>
int route(T) { return 1; }             // 主模板 A

template<>
int route<int*>(int*) { return 2; }   // A 的全特化，此时还没有 B

template<class T>
int route(T*) { return 3; }           // 另一个主模板 B
```

若 `int x = 0;`，则 `route(&x)` 返回 3：B 更特定，A 的特化不会抢先胜出。`route<int*>(&x)` 返回 2：显式令 `T = int*` 后，B 的形参会是 `int**`，不匹配；选中 A 后使用它的特化。

### 19. 显式指定、显式实例化、显式特化有什么区别？

| 写法 | 含义 |
|---|---|
| `combine<double>(1, 2)` | 调用时显式指定模板实参；仍使用相应模板实现 |
| `template int combine<int>(int, int);` | 显式实例化定义，要求从主模板实例化这个版本，不另写函数体 |
| `template<> int combine<int>(int, int) { /* 专门实现 */ }` | 显式全特化，为这个版本另外提供实现 |

函数模板的定义通常放头文件，让需要隐式实例化它的翻译单元能看到。也可以将定义放在 `.cpp` 中，为确定的类型提供显式实例化；调用方不能因此任意使用没有提供实现的其他类型。

模板不是运行时才按类型选择函数，也不是“完全不能编译”：编译器会先检查模板本身，依赖模板参数的部分再随实例化检查。
