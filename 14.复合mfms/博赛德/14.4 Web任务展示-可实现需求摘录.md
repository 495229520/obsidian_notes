# Web任务展示需求：当前可实现范围

日期：2026-09-19。场景：博赛德 feature_vis。根据用户最新确认，应用端分为任务系统与Web；Web只展示，不创建任务、不控制调度或设备。本文从《接口需求-任务调度》v1.0中筛选，保留原需求编号供核对。原需求已按用户要求修订为v2.0，v1.0备份保存在工程Trellis任务research目录。

“可实现”表示现有已约定数据足以支持开发，并非Web API已经上线。当前桥接app.py仅提供/handle_job接单；列表、详情、统计与Web推送接口均需新增。未验证现场部署。

## 0. 补充核对：设备ROS数据也可用于Web

用户补充下位机com_interfaces与ROS为可用数据来源后，本次扩大核对范围。任务清单/执行阶段来自Record和调度Stream；设备树、机械臂与底盘遥测来自现有C++中台和ROS。此前仅因任务Stream不含设备字段而排除全部设备展示的结论已修正。Web仍只读，设备展示接口尚待开发。

| 可增加的展示 | 字段／来源 | 当前链路与边界 |
|---|---|---|
| 设备树与机械臂/底盘分组 | CommunicationInterface.deviceTree()；DeviceTreeRobot.groupId及各设备id/name/type | 已有C++快照与信号；同group_id分组，不等于调度robotCode或mapObjectCode，需要明确外部身份映射；多臂不默认选第一台 |
| 设备通信状态与最后收件时间 | deviceStatuses()/deviceStatusUpdated；hasHeartbeat、online、lastSeenMs、dbState | 已有全量摘要；支持Fr/Aubo/Seer状态话题。区分从未收到、过期和DB生命周期，不能把心跳在线当作设备可执行 |

| 仙工位置与定位可信度 | pose_x/y、angle、confidence、current_station、last_station | 已有数据；原消息位置/朝向经转换为mm/度再转回。current_station表示最近站点，不证明停靠。数值可展示，叠加地图还缺frame/map版本关联 |

| 当前设备错误提示 | Fr.robot_err_code；Seer.err_code/err_msg；Aubo安全模式 | 可展示已提供的当前异常；Aubo无通用错误码字段，摘要errCode=0不能证明无故障。仍不等于完整告警生命周期/历史平台 |

### 不能直接承诺的细节

- 现有全量deviceStatuses主要是心跳/错误摘要；完整机械臂状态沿当前设备订阅链传递，Worker对AGV还有已连接设备组过滤。多设备Web完整快照/并发订阅需专门聚合，不能将当前Qt单设备选择逻辑直接当车队10Hz服务。
- 状态话题按完整deviceId命名：`/<deviceId>_state`；命令service用六位prefix。Web身份应来自订阅设备，不凭robot_index或robot_name猜测对应任务。
- 本地FrAdapterPublisher把robot_index、curtask_index、curstep_index分别写为0、0、1，软件版本也写固定字符串。不能用这些字段证明真实调度任务、执行步骤或实际固件版本；最终SDK发布节点的行为需另核对。
- Fr.robot_err_code为uint8，适配器从main_code赋值；不能声称保留所有完整厂商错误码。main_code/sub_code在msg标为弃用，不能把它们作为新的稳定Web契约。
- AgvOrderState.msg定义了单号、步骤、loaded/unloaded等，但本次核对的SeerCtrlState不包含该消息；定义存在不足以证明已接入中台，暂不据此恢复子运单或取放料台账承诺。
- ROS状态消息没有统一源时间戳；lastSeenMs和转换时间为中台收件时间，不是机器人实际采样时间。机械臂/底盘/任务状态来自不同源，不承诺同一帧同步；应分别标来源和更新时间。
- 有srv控制接口不意味着Web要开放控制。点动、急停指令、IO写入、导航等仍不纳入只读界面。

## 1. 数据边界

任务清单来自 `logisticsTaskRecord`：原六字段保存在context，当前有效状态为task_status。调度Stream按taskCode关联任务，eventId负责消息身份、sequence负责顺序、taskStatus负责执行状态。taskStatus是状态码，不是任务ID或机器人ID。

中台先持久保存、去重并校验事件，再按顺序更新Record；Web读取中台整理后的任务视图，不直接把Redis最后一条消息当成任务真相。乱序、冲突、拒绝和仅收件确认的事件不能覆盖有效状态。门完成5/8来自中台核验OPENED。

原文列出的t_robotitem、t_windtaskrecord、t_windwaybillrecord、t_map*等表，仅是该需求文档提出的来源。本次已约定的Record与任务状态Stream不保证可读取这些表，也不包含它们的完整字段。后续如扩展数据源应单独核对，本文不声称这些能力在整个系统中永久不可实现。

## 3. 字段摘录与对接建议

以下是Web任务视图建议，不是已发布API。主身份保留taskCode，避免把物流任务编号伪装成调度内部taskId。

| Web建议字段 | 当前来源 | 展示规则 |
|---|---|---|
| taskCode | Record.task_code | 原字符串任务编号，关联主键 |
| containerCode | context.containerCode | 气罐编号，不作为件数 |
| startStorageCode/endStorageCode | context同名字段 | 业务编码；无坐标、中文名、占用信息 |
| startStorageOpenDoor/endStorageOpenDoor | context同名字段 | 是否需要开门，不是门实时状态 |
| taskStatus | Record.task_status | 当前已应用状态，保留原整数及统一展示名称 |
| arrivedStorageCode | Record.arrived_storage_code | 当前阶段到点关联，可空；进入6/10/201/601会清空，不是实时位置 |
| createdAt/updatedAt | Record.created_at/updated_at | 中台落库/更新时间，不冒充现场事件发生时间 |
| startedAt/endedAt | Record.started_at/ended_at | 可空；不能用createdAt或updatedAt补成执行时间 |
| endedReason/errorCode | Record.ended_reason/error_code | 有值才展示，错误码保留原类型；中台不编造码义 |

起终点编码可以作列表筛选项，但不能据此生成完整站点库。门请求ID可作为排查信息按需提供，不是任务主键。数据库BIGINT如需暴露，应序列化为字符串，避免浏览器数字精度丢失。

### 当前阶段名称

| taskStatus | Web展示 | 依据 |
|---|---|---|
| 1 | 已生成 | 中台受理落库 |
| 2 | 已下发 | 调度已入队并建进度；不能据此推导startedAt |
| 3 | 已分配 | 已报告分配阶段；消息没有机器人编号，不能展示分配给哪台车 |
| 4 | 已到起点 | 调度到点；需门时结合门动作显示等待，不能一律当等待 |
| 5 | 起点门已打开 | 中台核验本次OPENED；不代表门现在仍开着 |
| 6 | 运送中（气罐已上车） | 取货上车事实；任务系统收到反馈6后自动关门 |
| 7 | 到终点，准备放下 | 调度到点；需门时结合门动作判断等待 |
| 8 | 终点门已打开 | 中台核验本次OPENED |
| 9 | 已放下 | 调度事实，不等于整单完成 |
| 10 | 车离开 | 调度事实，不等于整单完成 |
| 201 | 正常结束 | 整单完成 |
| 301 | 超时结束 | 现有实现限连续三次开门超时，不泛化成所有设备故障 |
| 601 | 手动取消 | 调度报告结果；不因此给Web增加取消按钮 |

已定义名称的100/202/501/502/503/504尚未接入当前Record合法转换；例如504收件SUCCESSED仅表示消息已保存。不能把诊断中的504直接当作已应用任务状态。若需要在Web展示这类原始上报，应独立标明“上报未应用”，另行设计。

原文t_windtaskrecord.status的0–6、运单status和物流taskDetailStatus是不同枚举。不得套用原文“6=TIMEOUT”。Web展示阶段多于任务系统反馈的6/201/601，两者是不同接口。

## 5. 统计与刷新必须保留的限制

- 状态统计以Record当前有效状态为准，每个taskCode计一单；不按Stream消息、通知或重投次数累计。
- “今日接单数”按createdAt分日；“今日完成数”必须有真实endedAt且状态为201。缺失结束时间的完成任务只能纳入当前状态分布，不能假装发生在今天。
- 301单列超时，不能把所有未知/未完成任务计为失败。当前异常任务数最多明确标注为“301任务数”，不能命名为设备活动告警数。
- 执行耗时仅在开始、结束时间齐全且含义已核实时计算。阶段已等待时长、11态导航阶段和0–100%进度没有可靠来源；不以状态编号/总状态数计算百分比。
- Stream可能长时间没有新任务事件；这不证明机器人离线。Web可以显示查询失败、最后更新时间或“暂无新状态”，不套用原文1秒在线/8秒stale的心跳规则。
- 不用状态6当实时载荷传感器；它只证明该任务曾完成取货上车。5/8同理不能用于实时门开闭指示灯。
- 分页、筛选、统计须采用相同过滤条件和明确时区/asOf。原文P95小于800ms及10Hz均无本次实测依据，不能列为已达成。

## 6. 本期接口与验收建议

优先开发任务列表、任务详情、任务数量统计和刷新；可沿用原T1/T3的GET路径，但必须改为上述物流任务视图，明确URL参数是taskCode。统计路径及推送形式另行冻结，不把本文建议视为现成接口。

验收应检查：六字段与任务系统原单一致；任务去重与分页；Stream乱序/重投不导致状态倒退；5/8只来自匹配OPENED；无需门显示跳过；601/301不伪装完成；缺少可选字段显示未提供；所有数量按任务计而非件数；页面刷新后仍显示Record事实；Web没有写操作入口。

正常：任务到起点4、真实OPENED后5、气罐上车6，Web按有效状态更新。
基础：刚接单的任务显示1，startedAt/endedAt为空，不显示机器人名称或已运行时长。
错误：收到504的SUCCESSED就把Record状态改成504；未收到新事件8秒即标离线；将6显示超时；把一条201记录当一件上料产量。

本次仅文档核对，未新增API、修改业务代码或运行现场联调。历史133项验证不代表Web接口通过验收。
