# 博赛德数据中台：应用层与调度最新对接摘要

核对日期：2026-09-19。适用场景：博赛德 feature_vis。依据9月18日v2协议、9月19日调度模块快照和当前本地代码整理。前次整理未读取《接口需求-任务调度.md》；本轮用户明确授权后已读取并单独形成Web可实现需求摘录，原文后续已按用户要求修订为v2.0，v1.0已备份。本文汇总已有约定，并纳入本轮用户对应用层划分和接口表的更正；Web清单明确标为待确认范围。

## 1. 应用层当前要完成的业务

应用层分为任务系统与Web显示界面，两者分别对接中台。以下搬运、门控、状态回传属于任务／物流系统。任务系统下发“把指定气罐从起点搬到终点”的任务，中台负责接收、保存、转交调度和反馈；需要开门时，由中台联系物流系统，物流系统对接工厂门控。调度负责执行安排、路径规划和下位机交互。

### 接收搬运任务

HTTP/2接单路径为 `/handle_job`，任务固定六字段：

| 字段 | 业务含义 |
|---|---|
| taskCode | 应用层生成的唯一任务编号，字符串，整条链路保持原值 |
| startStorageCode | 气罐起始业务点位 |
| endStorageCode | 气罐目标业务点位，不能与起点相同 |
| containerCode | 气罐编号 |
| startStorageOpenDoor | 到起点抓取前是否需要开门，JSON布尔值 |
| endStorageOpenDoor | 到终点放下前是否需要开门，JSON布尔值 |

开门布尔值表示动作需求，不表示门当前状态。正常业务每个任务下发一次、内容固定；异常超时补发须沿用原编号和原内容。同编号同内容幂等，同编号不同内容拒绝，不提供任务参数更新接口。

中台在同一事务写入Record和OutBox后才返回 `{"code":200,"message":"接收成功"}`；这表示已受理落库，运输仍由调度执行。编号业务长度由应用层约束，中台校验结构和类型，数据库不得静默截断。现场方法与鉴权需按实际配置核验。

### 反馈运输进度

通过HTTP/2向应用层 `/api/ocean-base/openApiSeer/compositeRobotTaskStatusFeedBack` 发送 `taskCode` 和 `taskDetailStatus`，首期仅反馈：

| taskDetailStatus | 业务时点 | 应用层处理 |
|---|---|---|
| 6 | 已确认气罐取到小车上 | 更新运送中，并按原任务起点及开门需求处理起点关门 |
| 201 | 整单正常结束 | 更新完成 |
| 601 | 手动取消 | 更新取消 |

不能用“首张运单下发”代替取货上车事实。应用层可靠接收后返回HTTP 2xx及JSON整数code=200；失败说明原因。中台保留待反馈并重试，同任务按事件顺序发送；任务系统按 `taskCode + taskDetailStatus` 幂等。用户最新澄清：发送6表示气罐已在小车上，任务系统收到后自动关门；不据此推断同一任务在终点放货后还要第二次发送6。网络重试保持原任务编号和状态，不能重复触发同一关门动作。

调度上报6后立即继续，不等待中台返回、应用层HTTP确认或门关闭。迟到6应关联原任务起点，不能根据车辆当前点位决定关哪扇门；现场规则仍需联调确认。

### 开门协作

当调度上报到起点4或到终点7，且对应开门需求为true，中台向物流系统发送：

```json
{"requestOpenDoorId":"door-T001-0001","taskCode":"T001","storageCode":"START-001","doorStatus":"OPEN"}
```

物流系统实际完成开门后，回调同四字段，`doorStatus` 改为 `OPENED`。同动作重试复用请求ID；新动作使用新ID。中台核对任务、请求ID、点位和当前阶段，通过后才让调度继续取放。无需开门时跳过门等待。

门请求响应code=200只表示接收；明确其他业务code及message可形成门失败。网络超时、HTTP错误、无效响应只重试，不能推断门已经打开或明确失败。当前代码只发OPEN。接口表列出doorStatus=OPEN/CLOSE；当前已确认的自动关门链路是气罐取到小车上后，中台反馈6，任务系统自动关门。无需为这次关门另发CLOSE，不自行新增终点放货后第二次6或CLOSE动作。

### 已明确与尚待落实的任务系统接口

本轮接口表已明确四字段OPENED回调，响应为 `{"code":200,"message":"门已打开"}`；不能再把完成通知方式或响应格式列为未定义。门请求地址仍标为待物流系统提供，回调URL未填写，方法和鉴权仍需配置落实，不能直接复用六字段接单地址。反馈6的时点已明确为取货上车，任务系统收到后自动关门；撤回此前关于两阶段各发送一次6的推断。此说明不单独定义终点放货后的另一项关门动作，不擅自扩展流程。取消/异常门处理及301后的恢复仍需明确。日志上传接口和错误数据上报字段未提供；不自动增加501/503/504等HTTP反馈。

### Web显示界面的对接范围（用户已明确只读）

Web只展示。中台根据任务需求表中的原始任务清单，以及调度Stream的taskCode/sequence/taskStatus整理当前执行情况后供Web查询。取消、暂停、恢复、手动门控和导航控制均不属于本期范围。

本轮用户已明确授权读取《接口需求-任务调度》，完成逐项筛选；任务列表、详情、有效阶段与任务数量统计具备数据基础，Web接口待开发。补充核对ROS后，机械臂状态、Seer底盘遥测、设备树与心跳也具备部分数据来源，可纳入只读展示开发；地图关联、子运单和生产件数仍缺完整依据。详细摘录见同目录 `bosaide-web-display-scope.md`，不能把任务Stream误认为设备心跳。

## 2. 与调度的最新对接

中台同事务创建 `logisticsTaskRecord` 和 `logisticsTaskOutBox`，两个独立雪花主键，OutBox.logistics_task_id关联Record.id，无触发器。Record只由中台写；调度领取OutBox并维护0待处理、1数据库处理完成待Redis投递、2投递成功、3失败。OutBox状态不代表车辆进度。

调度通过 `bosaide:scheduler:events` 上报，消费组middleware；中台通过 `bosaide:middleware:results` 返回，调度消费组scheduler。每条消息只用一个data字段保存JSON字符串。任务系统无需接入这两个Stream；Web取数接口另行定义。

上报身份字段为eventId、taskCode、sequence、taskStatus；4/7还必须带对应实际storageCode。sequence按任务从1递增，重试和重启不重置；中台生成的1/5/8不占调度序号。

最新v2返回固定八字段：`messageId/sourceEventId/taskCode/taskStatus/status/requestOpenDoorId/storageCode/reason`，无type，不适用填null。成功拼写严格为 `SUCCESSED`，门失败为 `FAILED`。

| 场景 | 返回调度 | Record及业务含义 |
|---|---|---|
| 普通状态可靠保存 | 原taskStatus + SUCCESSED | 只确认收件，不保证业务状态已应用 |
| 4/7且无需开门，任务与点位核对通过 | 原4/7 + SUCCESSED | 无需门等待；缺号时仍可收件确认 |
| 4/7且需要开门 | 不提前成功；真实OPENED后返回原4/7 + SUCCESSED | Record分别写5/8 |
| 4/7对应门动作明确失败 | 原4/7 + FAILED及原因 | 不写5/8、不放行取放 |

无法核对的4/7只持久诊断，不能伪造成功或失败。调度通过返回Stream等门，不再轮询Record。消息持久提交后才Redis XACK；返回重发保持messageId与内容不变，调度须持久去重和恢复pending。

301名称为超时结束，当前实现覆盖调度判定的连续三次开门超时；不回传应用层，也不自动派生4/7的FAILED。504为分配失败，普通收件仍回504/SUCCESSED，但业务转换尚未定义。完整状态枚举不等于每种业务流转均已实现。

## 3. 验证与错误处理

| 条件 | 当前契约 |
|---|---|
| 接单任一表写入失败 | 同事务回滚，不返回接收成功 |
| 重复同编号、内容不同 | 拒绝冲突，不产生第二次运输 |
| 事件提交失败 | 不XACK、不发布虚假成功 |
| 应用层反馈失败 | 持久重试，不阻塞后续执行事实落库 |
| 需要门但只有请求接收200 | 继续等待OPENED，不返回门成功 |
| 失败动作或终态之后迟到OPENED | 不恢复旧动作，不重复放行 |

正常用例：需门4→OPEN请求接收→真实OPENED→Record5、调度收到4/SUCCESSED→取货→6→中台异步反馈6。
基础用例：无需门4核验后确认收件，跳过门等待。
错误用例：将OPEN接收200当门已开、将504的收件成功当分配成功、将旧execution_state=6超时当新状态6上车。

后续联合验收应覆盖四种开门布尔组合、重复接单、门回调重复/错点/过时、反馈失败与顺序、消息重投和pending恢复，以及真实HTTP/2、现场门路由和调度消费。
