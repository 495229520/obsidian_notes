# MFMS 数据中台与应用层 · 需求对齐

> 本文用于当前应用层与 MFMS 数据中台的联合评审。架构边界以 `.trellis/ARCHMAP.md`、`.trellis/spec/constraints.md` 和 Vault 中的 v0.4 架构文档为准；未决事项不得由应用层或中台自行补齐。

## 1. 对齐结论

| 主题        | 数据中台                                                | 应用层（MES / Qt / Web / SCADA / 开发者工作台） | 当前结论                    |
| --------- | --------------------------------------------------- | ------------------------------------ | ----------------------- |
| 原始需求      | 接收、校验、生成 ID、持久化 `Requirement`                       | 创建、编辑、提交、查看需求及受理结果                   | **中台单写**                |
| 订单        | 读取调度系统产生的订单并组装视图                                    | 展示订单、进度和异常                           | **调度单写，中台/应用只读**        |
| 运单        | 读取运单及实时执行事实，保留来源和质量                                 | 展示车辆、路线、执行状态和风险                      | **调度单写，Adapter 发布实时事实** |
| 设备实时状态    | 消费 Redis Stream，解码、按来源更新快照、计算质量                     | 查询/订阅状态和新鲜度                          | **中台是状态视图提供者**          |
| 控制权       | 调用下位机 Query / Acquire / ForceAcquire / Release，记录审计 | 发起操作、二次确认、展示结果                       | **下位机唯一裁决**             |
| 设备命令      | 仅在下位机确认持权后透传                                        | 开发者调试入口，按权限开放                        | **中台不实现锁**              |
| 权限与审计     | 鉴权、角色、请求 ID、原因、结果和审计留存                              | 登录态、按钮可见性、风险提示                       | **强制操作 fail-closed**    |
| 现场网络/设备发现 | 使用经评审的设备注册和端点信息                                     | 展示连接/可达性                             | **IP 不是稳定身份或控制权证明**     |
|           |                                                     |                                      |                         |


任务系统有一个日志接口，上传日志，下发的需求是JSON，存储到mysql，供调度系统查看，调度系统也在mysql中存储执行的时间和完成的时间和完成的结果，上传回给任务系统

跟任务系统走的是HTTP2.0，自己走的是ARM
## 2. 分层职责与接口

### 2.1 应用层需要中台提供

1. **需求接口**：新建、校验、提交、查询、按 `requirement_uid` 查看版本与受理状态；重复提交必须可通过幂等键识别。
2. **统一视图接口**：返回 Requirement、只读 Order/Waybill、设备快照和执行事实，并标记来源、`observed_at`、`received_at`、`sequence`、`schema_version`、`quality`。
3. **实时订阅接口**：提供全量快照、增量更新、断流后的重建提示；未知 schema、乱序、重复、缺口和多源冲突必须可解释。
4. **控制访问接口**：Query、Acquire、ForceAcquire、Release，以及持权后的调试命令薄包装；每个请求透传 `request_id` 和完整 `device_id`。
5. **结果和错误接口**：区分成功、明确拒绝、设备异常、不可用和“结果未知”；超时后必须支持显式查询或明确提示无法确认。
6. **审计查询接口**：供有权限角色查询控制申请、强制申请和调试命令的请求上下文、原因、页面展示快照、下位机结果和时间。

### 2.2 中台需要应用层遵守

- 应用层不直连 SDK、下位机总线、Redis Stream 或 MySQL；统一通过中台稳定 DTO/API。
- 应用层不根据订单/运单状态推断控制权，不把 `ControlSnapshot` 当授权证明。
- 强制申请必须展示风险提示、要求原因并执行二次确认；审计不可用时禁止继续。
- `UNKNOWN` / `STALE` 状态只用于禁用或提示，不能被前端改写为成功、失败或持权。
- 收到超时不得自动重发强制申请；先执行权威查询。
- 应用层只能操作当前用户有权限且已注册的设备，不能仅凭 IP 选择目标。

## 3. 业务对象对齐

### 3.1 Requirement（中台写）

**已确认最小语义**：业务来源、工作站点/别名、上下料意图、业务对象集合、业务时间、数量、优先级、创建/修改信息和幂等信息。

**待联合冻结**：物理表名与 DDL、字段类型和可空性、`ids[]` 元素/顺序/存储、时间戳含义、数量校验、优先级范围、revision/change/cancel 规则和保留策略（Q-32、Q-47、Q-48）。

### 3.2 Order（调度写）

订单由调度系统从需求拆分生成，至少表达工作站点名称/别名、`type`（LOAD/UNLOAD）、`ids[]`、时间戳、数量和优先级。中台只读，不提供创建、修改、取消、修复或推进订单的 API。

### 3.3 Waybill（调度写）

运单由调度系统继续拆分或编排，Adapter 负责执行并发布实时事实。设备分配、路线、生命周期、终态、重试/替换、交接和关联 ID 由调度与 Adapter 联合冻结（Q-54）；中台只读并组装展示视图。

推荐血缘：`requirement_uid → order_uid → waybill_uid`。任何实时消息都不能直接改写三类持久化事实。

## 4. 应用页面/能力映射

| 应用能力 | 中台后端能力 | 读写性质 | 关键验收 |
|---|---|---|---|
| 需求录入 | `RequirementIntakeService` + Requirement Repository | 写需求 | 校验失败可解释；重复请求幂等；有受理结果 |
| 需求追踪 | `RequirementQueryService` + 只读派生查询 | 读 | 可追溯到订单/运单；缺口和延迟可见 |
| 订单/运单看板 | `RequirementView`、Order/Waybill read model | 读 | 不出现中台写接口；状态来源可见 |
| AGV/机器人状态 | `StateManager` + Stream decoder | 读/订阅 | 质量为 UNKNOWN/FRESH/STALE/UNSUPPORTED；不跨来源静默覆盖 |
| 生产/调试控制 | `ControlAccessService` + 下位机 client | 调用 | 下位机响应为最终结果；无权命令明确拒绝 |
| 强制夺权 | 权限、原因、二次确认、审计 + `ForceAcquire` | 高风险调用 | 审计不可用即禁止；超时显示结果未知 |
| 开发者调试 | `DebugCommandService` | 调用 | 仅开发者/管理员；设备目标有完整身份；不绕过下位机 |
| 运维与恢复 | 健康、缓存质量、断流/重启状态 | 读 | 重启后实时状态从 UNKNOWN 重建 |

## 5. 状态和错误展示约定

| 中台状态 | 应用层表现 | 禁止解释 |
|---|---|---|
| `FRESH` | 正常显示，可显示更新时间 | 不能解释为控制权持有 |
| `STALE` | 显示过期并提示刷新/断流 | 不能直接当设备故障或任务失败 |
| `UNKNOWN` | 显示未知，控制按钮默认关闭 | 不能当作空闲、成功或无任务 |
| `UNSUPPORTED` | 显示协议/版本不支持，保留原始证据 | 不能按旧 schema 猜测 |
| 下位机明确拒绝 | 展示标准拒绝原因 | 不能由前端重试覆盖 |
| 调用超时 | 展示“结果未知”，引导 Query | 不能展示为失败或自动 Force 重试 |

| P0-B Redis Stream 契约 | Payload、单位、时间、序列、来源实例、运单关联、新鲜度 | 下位机 + Adapter + MFMS | 规划中，Q-31/Q-45 |
| P0-C 数据契约 | DDL、单写权限、拆分、幂等、claim/failover、变更、运单生命周期 | 业务 + Scheduler + DBA + Adapter + MFMS | 规划中，Q-32/Q-46～Q-48/Q-54 |
| 网络契约 | 多机器人端点、路由/NAT、A03-T2 网段冲突、ROS 广播边界 | 网络/现场 + MFMS | 待现场确认 |

**进入代码实现的前置条件**：P0 契约完成人工评审并记录姓名、版本、日期和结论；候选 DDL、字段、函数名和错误码在签字前只能标记为 candidate/unknown。

## 7. 需要应用层代表确认的问题

- 应用层的正式角色和权限是否采用 `viewer / operator / developer / admin`，各角色可见页面与可执行动作是什么？
- 需求创建后的用户可见状态是“已接收、校验失败、待调度、已拆分、已取消”中的哪些集合？谁负责最终业务解释？
- 应用层需要全量查询还是 WebSocket 增量推送；可接受的实时延迟和过期阈值是多少？
- Order/Waybill 看板需要哪些筛选、聚合和历史追踪字段；哪些字段必须显示来源和质量？
- ForceAcquire 和 DebugCommand 的审批、原因、审计保留期与查询权限如何定义？
- 多机器人选择是否基于稳定 `robot_id/device_id` 注册表；禁止把 IP 直接作为 UI 目标选择键。

## 8. 本轮行动清单

1. 应用层提供页面/角色/字段清单，标出必填、只读、可编辑和展示优先级。
2. 业务、Scheduler、DBA、Adapter、MFMS 五方完成 P0-C 数据契约评审。
3. 下位机与 Adapter 提供 P0-A/P0-B 的真实接口、消息样例和结果码证据。
4. MFMS 根据签字结果冻结稳定 DTO、Repository 权限和错误映射；未签字段保持 unknown。
5. 用正常、拒绝、超时未知、断流、重启、重复提交和多源冲突场景做应用联调验收。
