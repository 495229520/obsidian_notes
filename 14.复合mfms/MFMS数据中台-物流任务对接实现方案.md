# MFMS 数据中台物流任务对接实现方案

> [!info] 文档用途
> 本文用于数据中台、调度系统及应用层任务系统的接口评审。版本 V0.1，日期 2026-09-14，状态：讨论稿，待与调度系统开发人员评审。
> 数据库字段、状态约束、技术选型及运行参数均为建议设计，不代表三方已签署接口契约。本文未实施代码变更、数据库迁移或现场部署。

本文完整保留本次讨论形成的首版方案，并将已确认需求、建议设计和待协商接口分开。现有 [[MFMS数据中台与应用层-需求对齐]] 涉及更广泛的中台架构；本文聚焦本次物流任务对接，不自动替代既有架构文档。后续评审需核对两者的任务模型及实现基线。

## 一、已确认需求与方案结论

数据中台负责建立以下闭环：

**接收应用层 JSON → 写入 MySQL → 调度系统读取并执行 → 调度系统写入进度、时间、结果和错误码 → 中台通过 HTTP 回传应用层。**

### 1. 已确认需求

| 项目 | 本次确认内容 |
|---|---|
| ARM 含义 | 指数据中台、调度系统和下位机组成的整体系统，不是处理器架构或另一个通信协议 |
| 中台职责 | 将应用层 JSON 需求落库，读取调度系统写回的数据，并向应用层转发 |
| 调度职责 | 读取任务、拆分需求、规划路径、与下位机通信及执行；这些逻辑不归中台负责 |
| 内部交接 | 中台与调度系统通过 MySQL 交换任务和执行信息 |
| 执行信息 | 调度系统写入执行开始时间、完成时间、完成结果及失败错误码 |
| 结果值 | `1` 表示完成，`0` 表示失败 |
| 错误码 | 调度系统定义，应用层任务系统维护映射；中台只保存和转发 |
| 外部通信 | 常规 HTTP/JSON，不要求 HTTP/2；最初的“HTTP2.0”表述已在本次讨论中澄清 |
| 物流平台地址 | `10.10.10.9` |
| 复合机器人侧接收地址 | `192.168.83.74:18888` |
| 首期状态 | 已提供接口说明指出当前主要使用 `4`、`201`、`601` |
| 日志接口 | 应用层存在日志上传接口，但本次尚未提供其 URL 和请求字段 |

### 2. 建议设计的范围

建议新增任务主表、执行事件表、待上报消息表、上报尝试记录表，共四张表。任务执行事实与网络上报状态分别保存，避免应用层暂时不可达时丢失结果。

四张表的名称、字段类型、状态约束、事务模板、轮询参数、HTTP 错误码及后台进程组织均需在评审后定稿。已有的两个外部 JSON 样例按原接口说明保留。

## 三、职责与整体结构

```mermaid
flowchart LR
    A["应用层任务系统<br/>10.10.10.9"] -->|"HTTP 下发 JSON"| B["数据中台<br/>192.168.83.74:18888"]
    B -->|"任务持久化"| D[("MySQL")]
    D -->|"查询、领取任务"| S["小车调度系统"]
    S -->|"执行进度、时间、结果、错误码"| D
    D -->|"读取执行事件"| B
    B -->|"HTTP 状态反馈、日志上传"| A
    S <-->|"调度系统自行实现"| L["下位机"]
```

| 参与方 | 职责 |
|---|---|
| 应用层任务系统 | 生成任务、接收反馈、解释调度错误码 |
| 数据中台 | 校验和保存任务、读取执行事件、可靠回传、记录接口调用结果 |
| 小车调度系统 | 领取任务、拆分步骤、规划路径、控制下位机、写入执行信息 |
| 下位机 | 执行设备动作，向调度系统返回设备结果 |

中台不维护错误码含义，不推断设备动作结果，不负责路径规划、任务拆分或下位机通信。

`ifOpenDoor` 作为任务属性保存并提供给调度器。附件中的开关门、设备空位和工艺路线流程属于整体业务背景，不因此自动纳入中台实现范围。若后续需要中台转发开门申请或门状态，应另行补充接口及事件契约。

业务参考为《【博赛德】物流自动化项目解决方案_V1.1.pdf》第 6—9 页及用户提供的流程截图。附件仅作为需求参考；文件名标注 V1.1，但 PDF 封面和修订表写的是 V1.0，后续评审应确认正式版本。

## 四、外部接口设计

### 1. 接收任务

方向：应用层 → 中台。

建议使用 `POST`，地址按用户提供的信息保留：

[任务接收接口](http://192.168.83.74:18888/handle_job)

```json
{
  "taskCode": "20260731001",
  "startStorageCode": "RAfCK01-1-1-1",
  "endStorageCode": "AGV01-1-1",
  "containerCode": "LH001",
  "ifOpenDoor": true
}
```

建议处理规则：

- 四个编码字段必须为非空字符串，保留大小写和前导零。
- `ifOpenDoor` 必须为布尔值。
- 保存结构化字段和完整原始 JSON。
- 数据库事务提交成功后，才能返回“接收成功”。
- 相同 `taskCode`、相同任务内容重复下发，返回成功，不重复创建任务。
- 相同 `taskCode`、不同任务内容，返回冲突，不覆盖已接收任务。
- 接收成功表示任务已持久化，不表示已经执行。

成功响应沿用已有接口说明：

```json
{
  "code": 200,
  "message": "接收成功"
}
```

已知规则是 `code=200` 为正常，其他为报错；报错时 `message` 必须说明原因。

建议中台接收接口采用下列错误码。HTTP 状态与响应体 `code` 是否一致，须由应用层确认，不能据现有样例认定对方已支持此规则。

| 建议 code | 含义 |
|---|---|
| `400` | 参数错误 |
| `409` | 同一任务编号对应不同任务内容 |
| `503` | 数据库暂不可用 |
| `500` | 其他内部错误 |

上述接入错误与调度系统产生的业务错误码分别管理。

### 2. 状态回传

方向：中台 → 应用层。

建议使用 `POST`，目标地址：

[复合机器人任务状态反馈接口](http://10.10.10.9/api/ocean-base/openApiSeer/compositeRobotTaskStatusFeedBack)

```json
{
  "taskCode": "20260731001",
  "taskDetailStatus": 201
}
```

首期已明确的状态：

| 状态 | 含义 | 建议数据来源 |
|---|---|---|
| `4` | 已拿起 | 调度系统写入明确事件 |
| `201` | 正常结束 | 调度系统写入明确事件 |
| `601` | 手动取消 | 调度系统确认取消后写入事件 |

接口说明提供的完整枚举如下，首期尚不意味着全部启用：

| 状态 | 含义 | 状态 | 含义 |
|---|---|---|---|
| `1` | 已生成 | `2` | 已下发 |
| `3` | 已分配 | `4` | 已拿起 |
| `5` | 已出库位 | `6` | 运送中 |
| `7` | 准备放下 | `8` | 已放下 |
| `9` | 车离开 | `10` | 等待确认 |
| `100` | 挂起 | `201` | 正常结束 |
| `202` | 手动正常结束 | `501` | 异常结束 |
| `502` | 手动异常结束 | `503` | 下发失败 |
| `601` | 手动取消 | — | — |

**数据库中的执行结果 `1/0` 与接口状态码不是同一套字段。** 中台不能将“执行中”推断为“已拿起”，也不能将失败自动转换为取消。状态枚举中的 `503` 与上一节建议的 HTTP 接入错误 `503` 也不是同一语义。

建议调度系统同时提供执行结果和需要回传的 `taskDetailStatus`。失败状态如何使用 `501/503` 等枚举，须与任务系统确认；首版不自行建立映射。

上层成功响应按现有接口说明为：

```json
{
  "code": 200,
  "message": "接收成功"
}
```

### 3. 错误码与日志上传

错误码由调度系统定义，任务系统解释。中台保存原始值及 JSON 类型，不翻译、不重新编号，不丢弃字符串中的前导零。

目前提供的状态接口只有两个字段，尚不能证明该接口支持附加错误码。建议处理如下：

- 数据库先完整保存错误及日志原始数据。
- 日志接口地址、字段和成功响应补齐后，由独立适配器上传。
- 接口契约未补齐的消息标记为“等待接口配置”，持续保留。
- 不擅自向现有状态接口添加 `errorCode` 等未约定字段。
- 首期没有新增“接收取消任务”接口；状态 `601` 仅表示取消结果反馈。

## 五、MySQL 表设计（建议）

建议新增四张表。任务和执行事件是双方共享契约；上报队列和尝试记录由中台维护。

建议使用 MySQL 8.0、InnoDB、`utf8mb4`。内部主键使用 `BIGINT`，业务编码使用区分大小写的字符串，时间使用 UTC `DATETIME(3)`。具体字符串长度、字段精度、权限和保留期限由评审确定。下列名称属于建议数据库字段，不代表已确认的外部 JSON 字段。

### 1. `logistics_task`：任务主表

保存任务内容、领取信息和最新执行结果。

| 字段组 | 主要字段 | 建议写入方 |
|---|---|---|
| 标识 | `id`、`task_code` | 中台 |
| 任务内容 | `start_storage_code`、`end_storage_code`、`container_code`、`if_open_door` | 中台 |
| 原始请求 | `raw_request` JSON、`request_hash` | 中台 |
| 执行状态 | `execution_state`、`task_detail_status` | 中台初始化待执行状态，调度系统后续更新 |
| 执行归属 | `scheduler_id`、`claimed_at` | 调度系统 |
| 时间 | `received_at`、`started_at`、`finished_at`、`updated_at` | 按职责分别写入 |
| 结果 | `result`、`error_payload` JSON | 调度系统 |
| 并发控制 | `version` | 领取或状态更新事务 |

建议约束：

- `task_code` 唯一，作为重复下发的判定依据。
- `execution_state` 使用 `PENDING / CLAIMED / RUNNING / SUCCEEDED / FAILED / CANCELED`。
- `result` 初始为 `NULL`，成功为 `1`，失败为 `0`。
- 取消单独记为 `CANCELED`，`result` 为 `NULL`；这项取消存储约定待调度方确认。
- 失败必须保留调度系统提供的错误数据。
- 索引覆盖 `(execution_state, received_at, id)`，支持调度器查找待领取任务。

不能将 `result` 默认设为 `0`，否则尚未执行的任务会被误认为失败。

`request_hash` 用于任务内容比较。实现时应按确定的 JSON 规范化规则比较，不能仅因键顺序或空白不同就判为不同任务；参与比较的字段范围需在契约定稿时锁定。

### 2. `logistics_task_event`：执行事件表

追加保存执行进度、结果和日志事件，避免中台轮询漏掉短暂出现的状态。

| 字段 | 说明 |
|---|---|
| `id`、`task_id` | 事件及所属任务 |
| `event_seq` | 同一任务内递增的事件序号 |
| `event_type` | 开始、状态变化、完成、失败、取消、日志 |
| `task_detail_status` | 调度系统提供的反馈状态，可空 |
| `result` | 本次事件的结果，可空 |
| `error_payload`、`log_payload` | 原始错误与日志 JSON |
| `occurred_at`、`created_at` | 事件发生时间和入库时间 |
| `bridged_at` | 中台完成生成上报记录的时间 |

建议约束：

- `(task_id, event_seq)` 唯一，用于事件去重。
- 调度系统在同一事务中更新任务主表并追加事件。
- 已产生的业务事件不覆盖；`bridged_at` 是中台维护的处理标记。
- 中台按未处理记录查询，不只依赖“最大自增 ID”，避免并发事务提交顺序导致漏读。

例如同一次轮询间隔内，调度器先写入 `4`，随后写入 `201`，主表只保留最新状态，事件表则保留两次变化，供中台顺序反馈。

### 3. `logistics_callback_outbox`：待上报消息表

将执行完成与网络发送分开，使断网、超时或重启后仍能继续回传。

| 字段组 | 主要字段 |
|---|---|
| 关联 | `id`、`event_id`、`task_id`、`message_kind` |
| 消息 | `payload` JSON、`contract_version` |
| 发送状态 | `delivery_state`、`attempt_count`、`next_attempt_at` |
| 发送占用 | `lease_until`、`worker_id` |
| 结果 | `last_error`、`delivered_at`、`created_at` |

建议约束：

- `message_kind` 区分状态反馈与日志上传。
- `(event_id, message_kind)` 唯一，防止重复生成上报消息。
- 状态包括待发送、发送中、等待重试、已成功、等待接口配置、需要人工处理。
- 缺少契约时保存事件关联，`payload` 可空，不构造猜测性报文。
- 状态与日志分别维护发送进度，日志接口缺失不阻塞已确定的状态反馈。
- 同一任务的状态反馈保持事件顺序。

### 4. `logistics_callback_attempt`：上报尝试记录表

每次调用追加一条记录，用于追查上报问题。

主要字段：

`id`、`outbox_id`、`attempt_no`、`requested_at`、`responded_at`、`http_status`、`business_code`、`response_body`、`transport_error`、`duration_ms`。

它记录接口调用情况；需要上传的业务日志保存在事件表。两者用途不同。

## 六、运行流程与项目落地（建议）

### 1. 调度系统领取与写回

调度器通过短事务锁定并领取待执行任务，写入归属后提交，再进行实际执行。多调度实例使用行锁及 `SKIP LOCKED` 避免重复领取；这是 MySQL 官方说明的队列表适用场景。参见 [MySQL 锁定读取文档](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)。

双方交付统一的领取和写回事务模板，并确认以下规则：

- 只有领取者能更新任务执行状态。
- 时间、结果和事件必须一起提交。
- 重复事件不重复落库，终态不能被旧进度覆盖。
- 调度器失联后，中台不自动重新派发任务；由调度系统确认实际执行情况。

### 2. 中台生成并发送反馈

1. 查询未处理事件。
2. 在同一事务中生成上报记录并标记事件已处理。
3. 提交事务后，再发送 HTTP 请求，不在数据库事务中等待网络。
4. HTTP 成功且响应 JSON 的 `code=200`，才标记上报成功。
5. 网络异常、超时、HTTP `429/5xx` 进入重试；确定的参数或业务拒绝进入人工处理状态。
6. 记录每次调用，重启后恢复待发送消息及过期发送占用。

数据库原始结果不会因上报成功而删除。

首版建议参数如下，全部可配置，尚非已约定的性能指标：

| 参数 | 建议初值 |
|---|---|
| 事件轮询间隔 | `500 ms` |
| 每批读取上限 | `100` 条 |
| HTTP 请求超时 | `10 s` |
| 重试间隔 | 从 `1 s` 指数增加，上限 `60 s`，加入抖动 |
| 持续未成功告警 | `24 h`；消息继续保留 |

HTTP 响应丢失时可能出现重复回传，因此建议交付语义为“至少一次送达”。任务系统需要确认重复状态和重复日志的处理规则，不能承诺跨系统绝对只发送一次。

### 3. 软件结构

建议在 `mfms_server` 内新增任务对接模块，并提供独立后台进程 `mfms_task_bridge`，使任务接收和回传不依赖桌面界面是否打开。

| 模块 | 职责 |
|---|---|
| HTTP 接收器 | 接收、解析、校验任务 |
| 任务数据库服务 | 幂等写入、事件读取、上报事务 |
| 状态反馈客户端 | 调用已知状态接口 |
| 日志适配器 | 按后续确认的契约上传原始日志和错误 |
| 上报工作器 | 重试、恢复、发送记录及积压告警 |

技术选择建议沿用 C++17、Qt5、QMYSQL：HTTP 服务使用 `cpp-httplib`，回传使用 Qt Network。前者支持本次确认的 HTTP/1.1 接入方向，后者提供 Qt 异步网络接口。参见 [cpp-httplib 官方说明](https://github.com/yhirose/cpp-httplib) 和 [Qt Network 文档](https://doc.qt.io/archives/qt-5.15/qnetworkaccessmanager.html)。

数据库对象由专用线程创建和使用，HTTP 线程只传递请求数据。复用项目数据库配置规范，新增独立连接，不跨线程共享现有连接。读取 JSON 时遵守项目 prepared SELECT 的 `CAST` 要求，并测试长度上限。

原有 Qt、Gateway、ROS 和设备命令链保持现状。本次不新增设备运动接口，不引入路径调度逻辑。

### 4. 迁移与部署

建议采用独立增量 SQL 创建四张表及索引，不重新导入整份 `MFMS_BASE.sql`。

中台和调度系统分别配置数据库账户，按表和字段职责授权。服务地址、数据库连接、轮询和重试参数通过配置提供。

建议实施顺序：

1. 保护并整合代码基线。
2. 定稿数据库及双方事务契约。
3. 实现接收接口。
4. 实现事件读取和可靠回传。
5. 补齐日志契约并实现适配。
6. 完成测试环境联调。
7. 部署到经确认的现场环境。

回滚时停止新增服务并切回旧版本，保留任务、事件及发送记录，不直接删表。

## 七、验收标准与联调前置条件

### 1. 建议验收场景

| 场景 | 预期结果 |
|---|---|
| 正常下发 | 一条任务持久化后返回成功 |
| 同一任务并发重复下发 | 仅生成一条任务 |
| 同编号、不同内容 | 明确报错，不覆盖原任务 |
| 数据库写入失败 | 不返回接收成功 |
| 两个调度器同时领取 | 同一任务仅一个领取成功 |
| 状态 `4` 后立即出现 `201` | 两个事件均保留并按序反馈 |
| 执行失败 | 保存 `result=0` 和原始错误，不擅自解释或映射 |
| 取消 | 明确记录取消，与成功、失败区分 |
| 上层断网或返回业务错误 | 记录尝试，按规则重试或转人工处理 |
| 中台在事务或回传过程中重启 | 已接收任务不丢失，未完成上报可恢复 |
| 日志接口尚未配置 | 数据保留并可查询，不冒充上传成功 |
| 编码含前导零、错误码为字符串 | 保存和转发后含义及类型不变 |

建议先使用隔离 MySQL 和模拟 HTTP 端完成行为测试，再做双方系统联调。本次方案核查未执行构建、数据库集成测试或现场接口调用。

### 2. 尚需补齐的外部契约

| 缺项 | 首版建议处理 |
|---|---|
| 日志上传 URL、字段、成功响应 | 日志持久化，上报记录等待接口配置 |
| 失败状态及错误数据上传格式 | 保存调度器原始数据，不自行选择 `501/503` 或扩展现有接口 |
| 调度器写回样例和错误数据类型 | 提供上述数据库契约，由调度方对接确认 |
| 鉴权、重复回调处理规则 | 作为真实接口联调的启动条件 |
| 时间是否需要回传、采用何种字段 | 先完整入库，不加入未约定的外部报文 |

首版可以完成任务接收、数据库交接和已知状态回传；失败详情及日志的完整外部闭环，在对应接口契约补齐后启用。
