# 故障模型扩展：Crash Fault、Omission、Corruption、Byzantine 与 Silent Data Corruption

> **“没有回答”和“回答了错误内容”不是同一个问题。** 节点宕机时，系统主要需要决定谁接班、从哪里继续；节点仍在线却返回坏数据时，系统还必须判断哪些证据可信、哪个版本正确，以及修复会不会把最后一份好数据覆盖掉。副本数、Raft 多数派和重试次数，不能替代这三个判断。

先把 [[7.23 Raft 算法与安全性：选举、日志复制与提交规则]] 的“选举—复制—提交”与 [[7.24 Raft 持久化、崩溃恢复与 Snapshot]] 的“稳定存储—恢复入口—快照边界”连起来，再阅读本篇。这里不重讲 Raft 状态机，而是审计它依赖的假设。[[7.17 Recovery 与 Rebuild]] 解决怎样补回冗余，本篇先追问：**拿什么作为正确的修复源？**

> [!info] 范围与资料口径
> 稳定原理以 Martin Kleppmann《Designing Data-Intensive Applications》第 1 版第 8 章为底座，并对照 Raft、PBFT、Protocol-Aware Recovery 原论文。etcd 只引用 **v3.6** 文档中的完整性检测机制，不把版本相关开关当成普遍协议规则。本文的校验契约、隔离状态机与故障注入矩阵属于**基于这些原理构造的工程设计**，不是声称某个开源系统已有相同接口。官方资料查阅于 2026-09-16。[^ddia][^raft][^par][^etcd]

## 1. 先把“故障”拆成四个维度

单说“系统能容忍两个故障”几乎没有信息。必须同时回答：什么部件出错、允许怎样出错、观察者看见什么、哪些东西仍被认为可信。

| 维度 | 要写清的问题 | 存储场景中的例子 |
| --- | --- | --- |
| 故障对象 | 进程、网络、内存、介质、元数据，还是完整节点？ | 数据页坏了，但进程与心跳正常 |
| 行为约束 | 只能停止？会丢消息？会返回错误字节？会任意偏离协议？ | `read()` 成功，但读出的是另一对象的页 |
| 时间与检测 | 是否会重启？是否有已知延迟上界？能否可靠识别故障？ | 暂停、拥塞与断电都可能表现为超时 |
| 可信基础 | 哪些状态和代码必须正确？ | 摘要所在 manifest、校验器、任期记录、密钥 |

DDIA 将**时间假设**与**节点故障假设**分别讨论：crash-recovery 不等于网络同步，也不表示磁盘可以随意遗忘已经承诺保存的数据。[^ddia] 因此，一份有用的设计声明应类似：

> 本系统允许进程崩溃与恢复，允许网络丢失、重复、乱序与长时间延迟；协议安全性依赖持久化承诺不被遗忘。另有独立完整性机制检测指定粒度的存储损坏；不保证在校验器、权威摘要与多数投票节点同时失信时仍正确。

这比“我们使用 Raft，所以数据安全”更接近可验证的契约。

![[图片/SVG/8_7_7_34_1.svg|900]]

**读图要点：**上半比较节点或链路的外部行为；下半说明“有没有被发现”是另一个轴。SDC 不是必须排在 Byzantine 后面的“更严重一级”。

## 2. 六组术语：不能只靠中文直译理解

### 2.1 Crash-stop：停下以后不再执行

Crash-stop 模型允许节点在任意位置停止执行，之后不再恢复。停止前，它仍按算法行动；已经发出的消息可能继续在网络中传递。这里的“永久停止”是模型约束，不是说现实中绝对不能重新启动机器。一个允许节点重新加入的实现，可以将其视为新身份，也可以改用 crash-recovery 模型。[^ddia][^cambridge]

### 2.2 Fail-stop：先问作者有没有额外假设故障可检测

不同资料的命名并不统一。例如 Kleppmann 的课程讲义把 crash-stop 与 fail-stop 并列写作同义术语；Rutgers CS 417 讲义则用更强的 fail-stop 语义，把故障最终能够被其他节点检测出来也纳入模型假设。[^cambridge][^failstop]

本篇采用以下阅读约定：**“停止后不再恢复”称 crash-stop；需要更强检测能力时，显式写“fail-stop + 可靠故障检测”。** 不从 `fail-stop` 一个单词偷偷推出完美故障检测器。

在工程中，`SIGKILL` 可以制造进程停止，却不能让远端瞬间知道它已停止。对远端而言，崩溃、链路中断和极慢响应可能具有相同观察结果。超时提供的是怀疑与行动时机，不是“机器已死”的数学证明。这个区别与 [[7.15 Membership 与故障检测]] 的 suspect、超时和成员变更直接相关。

### 2.3 Crash-recovery：会回来，但不能忘记承诺

节点可以重启，易失内存可以丢失；算法另外规定必须保留下来的稳定状态。对 Raft 而言，至少要正确维护任期、投票和日志的持久化依赖。[^ddia][^raft]

**掉电后恢复**与**任意改写已持久化内容后恢复**不是同一模型。前者可以由日志与快照协议处理；后者需要先识别损坏，再重新建立可信状态。把坏的 `votedFor` 清空再启动，可能使同一身份在一个任期投出第二张票；“数据库可以从别处拷回来”不代表投票历史可以随意重置。

### 2.4 Omission：本来应发生的动作没有发生

Omission 可以是发送遗漏、接收遗漏、链路丢包，或某次请求没有得到应有响应。描述时应写清边界：网卡没有发出、网络丢掉，还是服务端处理后响应丢失。

【构造例】客户端发送 `Put(req_id=42)`，服务端已提交，响应却丢失。客户端看见的是 omission，不知道操作是否完成。它需要的是 [[7.13 幂等 重试 与请求去重]] 中的请求身份与重试语义，而不是直接执行一次新的非幂等写入。

从“之后再没有新响应”的外部行为看，crash-stop 可以表现为持续的 omission；但**不能据此反推一次 omission 就是 crash**。持续分区与无限延迟还会破坏可用性条件；重试不是对永不恢复的链路给出成功保证。[^cambridge]

### 2.5 Corruption：内容或状态不再符合原契约

Corruption 不只包含单个 bit flip。它可以是错误地址写入、陈旧块重现、长度字段被改、快照页丢失、内存计算错误，或缓冲区被复用后发送了另一条请求的内容。PAR 论文明确把用户数据与文件系统元数据故障一起纳入存储故障模型。[^par]

“Arbitrary corruption”应说明任意性的范围：是任意磁盘字节、任意一条报文，还是整个节点的代码与密钥都可受影响？**局部存储损坏模型不自动等于完整节点的 Byzantine 模型。** 例如数据页可以任意坏，但独立校验器与可信摘要仍正确，这比“节点可伪造一切回复”弱得多。

### 2.6 Byzantine：节点可以任意偏离协议，不要求有恶意

Byzantine 允许故障节点发送相互矛盾的消息、谎报持久化、伪造自身状态，或者选择性沉默。恶意攻击是成因之一，程序缺陷和硬件错误也可能产生这种外部行为。不是只有“向两个人说不同的话”才算 Byzantine；那只是一个重要特例，称为 equivocation。[^ddia][^pbft-model]

分类关键是**协议允许的行为集合**，而不是运维是否相信同事、节点是否在内网，或这次故障是否出于主观恶意。

## 3. Silent Data Corruption：坏数据越过了哪一道检查？

本篇把 SDC 定义为：**在所讨论的观察边界上，错误数据没有伴随可识别的错误信号，而被当成成功结果交付或使用。** “Silent”必须带观察者和时间点；它不是“永远无法发现”。

| 观察结果 | 当前边界上的分类 | 下一步 |
| --- | --- | --- |
| 读失败并返回 `EIO` | 已报告的读取故障 | 切换来源或尝试恢复 |
| 返回字节后被页校验拒绝 | 下层成功，但本层已检测损坏 | 隔离该页，不交给上层 |
| 页校验通过，但对象身份不匹配 | 内容自洽，身份契约失败 | 拒绝错址或旧版本数据 |
| 返回成功，应用随后发现 checkpoint 不一致 | 在应用检查前是静默损坏 | 明确发现层级并定位传播路径 |
| 所有层都接受，训练结果悄悄改变 | SDC 进入业务结果 | 已有检测体系存在覆盖缺口 |

“介质 latent corruption”强调坏数据潜伏在未被读取的位置；“SDC”强调它未被当前边界发现。冷数据可能已经潜伏损坏，但尚未被任何业务读取；一旦 scrub 检出，就不应继续把它当作“健康，只是有点可疑”。

【推导】同一个物理 bit flip 可以依次变成三种不同结果：设备 ECC 纠正后，对应用无影响；被文件校验发现后，对应用是显式错误；漏过所有检查后，才可能成为应用侧 SDC。因此，不能只数 CRC 层数，必须画出生成、存储、验证与消费的真实边界。端到端论证的关键正是：局部传输保护不能替代最终功能所需的完整性检查。[^endtoend]

## 4. Raft 的保证很强，但保证的是假设成立时的协议性质

Raft 原文的基础范围是非拜占庭条件下的复制状态机：可以处理消息丢失、重复、乱序、网络分区与节点停止；恢复节点从稳定存储继续。**“Raft 只处理 crash”不应误读为“Raft 连丢包都不处理”。**[^raft]

### 4.1 三种经常被混为一谈的正确性

| 正确性 | 问题 | 主要机制 |
| --- | --- | --- |
| 历史一致 | 哪条命令被提交，顺序是什么？ | Raft 日志、任期、提交规则 |
| 表示完整 | 记录、快照、页面字节是否仍是承诺的版本？ | 校验、身份绑定、恢复协议 |
| 业务语义正确 | 提交的操作与计算结果是否符合业务要求？ | 验证规则、状态机实现、业务不变量 |

Raft 可以让健康副本忠实复制同一个错误输入。若应用本来就生成了一份错误但格式合法的 checkpoint，复制它既不能发现模型参数的语义错误，也不能还原原本“应该生成”的参数。PBFT 同样不会凭空知道一份获授权写入的文件内容在业务上是否合理。[^pbft-properties]

### 4.2 三节点、两张 ACK，并不等于两次独立内容认证

【构造反例 A：承诺遗忘】A 为 Leader，B/C 为 Follower。A 已持久化日志 L，B 错误地回复成功却没有保存；C 尚未收到。A 按 A+B 返回提交成功后宕机。若 B 的错误行为还影响它对日志新旧的陈述，或者其后因丢失历史而参与不安全选举，基础 Raft 的前提已经被破坏。不能继续引用“任意一个节点故障都安全”来覆盖这种执行；**一个存储承诺失信加一个 crash，不是原模型中的一个 crash。**

【构造反例 B：稳定记录后来损坏】B 的已保存命令 payload 改变，但记录表面的 index/term 仍相同。如果实现没有足够校验而直接应用，本地状态机会与其他副本分叉。Raft 的日志匹配性质不是一个每次读取都逐字节比较多数副本的机制；它依赖协议规则与可信状态成立。

【构造反例 C：复制前已经错】A 在日志入口之前把请求值 10 错写成 90，再对 90 生成校验并复制。三份副本、三份校验都一致；系统只是更可靠地保存了错误输入。需要在更早、仍可信的生产者边界保护原始意图。

![[图片/SVG/8_7_7_34_2.svg|900]]

**读图要点：**“返回成功”的证据被标红时，问题不是少等了一张票，而是成功回复不再代表协议原来要求的承诺。

### 4.3 尾部截断不是通用的数据损坏修复方法

崩溃留下的未完成尾记录，在存储协议能够确认它尚未对外承诺时，通常可以丢弃；**已经稳定保存、后来才损坏的记录，不能仅因校验失败就当作未提交尾巴删除。** 特别是中间记录、快照替代的历史、任期/投票元数据，其处理规则不相同。

PAR 的重要启示是把本地检测与分布式恢复结合起来，并让恢复理解协议历史；不是让校验器“从第一个坏字节截断到文件尾”。[^par] 具体日志与快照顺序仍回到 [[7.24 Raft 持久化、崩溃恢复与 Snapshot]]，本篇只增加“稳定数据可能后来变坏”的审计维度。

## 5. 从局部校验到端到端完整性：先画覆盖区间

### 5.1 每道校验都只能保护自己包住的区间

【工程设计】对一个不可变 checkpoint chunk，先在可信生产者冻结内容，再生成摘要；摘要连同对象身份、版本、范围进入受保护的 manifest。数据进入存储后允许经过拷贝、网络、持久化和重建，消费者最终按这份期望值验证。

这里有两个容易漏掉的窗口：

**生成摘要以前。** 错误值已经进入缓冲区，再用 SHA-256 计算它，只能证明以后读到的仍是这个错误值。

**校验通过以后。** 已验证缓冲区又被共享写者或异步复用覆盖，后续消费仍可能出错。需要明确缓冲区的不可变性、所有权和生命周期；“上一层已经校验”不等于当前字节仍未变化。

![[图片/SVG/8_7_7_34_3.svg|900]]

**读图要点：**上方长线是应用级摘要的覆盖区间，下面短线是各局部机制的区间。局部检查降低错误到达终点的机会，但不会自动填满前后两个盲区。[^endtoend]

### 5.2 Checksum、Hash、MAC：区别首先在信任关系

| 机制 | 可以支撑的判断 | 不能单独证明什么 |
| --- | --- | --- |
| CRC / 非密码校验 | 指定错误模型下，内容发生变化的检测 | 对主动篡改的抗伪造、版本新鲜性 |
| 密码 Hash + 可信期望摘要 | 读到的字节匹配预期内容身份 | 摘要来源真实、该版本最新、业务语义正确 |
| MAC / 签名 | 具有对应密钥权限的一方认证了消息 | 签发方本身正确、消息一定新鲜、数据一定可取回 |
| 版本、任期、提交证据 | 当前协议允许采用哪一份状态 | 该状态实际字节未损坏 |

PBFT 使用身份认证与摘要等机制来约束伪造；这些机制仍有密钥和计算安全假设。[^pbft-model] 在本篇的工程设计中，**不要求所有存储系统都给每个块加 MAC**：仅防随机介质错误时，可靠校验和受控元数据可能已符合威胁模型；若存储节点会主动返回任意内容，则期望摘要或认证密钥不能完全受同一故障节点控制。

【反例】让节点同时返回 `payload` 与 `SHA256(payload)`，客户端只检查两者一致，没有建立可信期望值。一个任意作恶的节点可以换掉 payload 后重算 hash。这不是 SHA-256 被破解，而是验证问题被定义错了。

### 5.3 不能只绑定 payload

【设计契约】验证键至少考虑：`object_id`、不可变 `generation`、`chunk/stripe_id`、`shard_id`、`offset`、`length`、格式/编码版本，以及对应内容摘要。哪些字段进入摘要、哪些通过可信 manifest 绑定，可按格式选择，但必须有**无歧义的规范化编码**。

这能把四类不同错误分开：内容被改、读错对象、旧版本重放、范围或分片顺序错配。单纯 payload 校验通过，不排除后三类。Hash 相等是内容判断；[[7.9 一致性模型]] 中的“当前读应返回哪个版本”是另一份契约。

## 6. “检测后退出”能收缩故障影响，但不会自动变成 fail-stop

在受限损坏模型中，校验失败后停止交付相关数据，可以把“错误结果”转成“该片不可用”。这是将检测与冗余恢复连接起来的关键，但有四个前提。

第一，检测必须发生在错误数据被应用、ACK 或用作修复源**之前**；已经扩散的错误不能靠后来退出追溯撤销。

第二，检测器、拒绝路径和身份/版本依据仍可信；若故障节点能跳过检查并谎报通过，这条转换就不成立。

第三，拒绝范围要覆盖损坏涉及的全部职责。单个对象块坏了，可以隔离块；Raft 任期、投票、成员身份或关键映射坏了，不能让节点一边“禁读”一边继续按未知状态投票。

第四，重新加入有受控协议。清空坏节点再以原身份直接启动，可能遗忘此前对外承诺。需要按实现的成员替换、追赶、快照安装或恢复流程重建可信状态。

![[图片/SVG/8_7_7_34_4.svg|900]]

**读图要点：**“检测 → 隔离”只关闭危险输出；“重新健康”必须经过身份/历史、内容与发布三个关卡，不能由进程重启成功直接触发。

### 6.1 一个可审计的处置顺序

【工程设计】检测异常后，先冻结该故障范围的危险输出并保留原始数据、校验期望值和日志证据；再解析其对象身份与协议位置。能够独立验证的健康副本或正确 EC 分片才可以进入恢复输入集合。恢复写入临时位置，完成校验和持久化，再按版本/任期检查发布。无法找到可信源时，维持显式不可用并告警，不拼凑“看起来差不多”的内容。

这里的“保留证据”尤其重要：第一轮自动修复若覆盖了所有冲突副本，第二轮可能只看到一个一致但错误的结果。完整性事件不能只以“报警消失”验收。

### 6.2 etcd 对照：检测、告警与恢复是额外机制

etcd v3.6 文档区分启动时检查、压缩 revision 的 hash 检查和最新 revision 的周期检查；启动检查不匹配时退出，运行中检查可触发 CORRUPT 告警，并提供成员恢复/替换等路径。[^etcd]

它说明了一个架构分工：**Raft 管协议历史，完整性检查继续检查状态表示是否分叉。** 比较状态摘要时还要确保比较的是同一逻辑 revision、相同快照/压缩边界与同一种摘要口径；正常落后的 Follower 不应仅因本地状态较旧就被判为介质损坏。

本文不提供“对生产数据目录直接删除再启动”的快捷命令。真实恢复应固定 etcd 版本，先确认多数派、备份与成员身份，再执行该版本官方流程。

## 7. 多数派怎样遇到信任边界：CFT 与 BFT 的差别

### 7.1 Crash-tolerant quorum 的交集不是坏字节投票器

三个节点中，两个大小为 2 的多数派至少相交 1 个节点。在 crash-fault 世界，交集节点按协议办事且记住承诺，所以可以把历史约束带到下一次决定中。

但若交集恰好是会撒谎或遗忘承诺的节点，**集合相交这个数学事实本身不再足够**。需要更强协议，确保交集里存在正确节点，并确保正确节点不能为冲突决定提供有效证据。

### 7.2 经典 PBFT 的 3f+1 与 2f+1：把条件一起记

在经典 PBFT 所讨论的认证模型与故障界限下，常用规模为 `N=3f+1`，关键证据集合大小为 `Q=2f+1`。协议还需要正常节点遵守阶段规则、身份认证不被突破，以及支持进展的时序条件。不能把这两个数当成所有 BFT 协议的无条件定律。[^pbft-model][^pbft-properties]

【交集推导】两个证据集合的交集下界为：

$$
|Q_1\cap Q_2|\ge 2Q-N
=2(2f+1)-(3f+1)=f+1.
$$

最多有 `f` 个故障节点，所以交集中至少有一个正确节点。对于 `f=1`，四个节点中的两个三节点集合至少交叠两个，其中至少一个正确。**正确节点的签名/认证、状态记录与阶段约束**才使这个交集有安全含义；只把普通 Raft 节点加到四个不会得到 PBFT。

### 7.3 BFT 也有其信任与故障数量上限

【推论】同一缺陷同时影响全部副本、所有节点共享被攻破的管理权限、权威输入本身错误，或恢复时把正确状态覆盖到不存在，都不能由“拜占庭”三个字兜底。DDIA 对共享软件缺陷与故障相关性的提醒，在这里与数据中心真实故障域直接相接。[^ddia]

本篇的目标不是把每个内部存储集群改造成 BFT 集群，而是清楚区分：当前在容忍 crash、在检测受限 corruption，还是确实需要面对任意不可信参与者。

## 8. 在线节点不是单个“健康位”：至少维护两类状态

【工程设计】节点视图与数据视图应分离：

| 节点/服务维度 | 数据/协议维度 |
| --- | --- |
| 可连通、拥塞、超时、进程退出 | 对象版本、已验证范围、检测到的坏片 |
| CPU、磁盘、网络资源可用 | 校验期望值来源、最近 scrub 覆盖时间 |
| 是否能参与当前成员配置 | 是否有可信日志、任期与快照基础 |

节点可以在线但某些对象损坏；节点离线但盘上数据仍完好；集群存在足够的字节却暂时拿不到可信 manifest；所有校验都通过却读到了过期对象。上述状态不应压缩成同一个 `healthy=true`。

对 `node_down` 告警做得很好，不代表能发现 `checksum_mismatch`。对 `checksum_mismatch` 做得很好，也不代表能发现“数据与摘要一起被错误版本替换”。这直接影响 [[7.16 数据放置与 Rebalance]] 的迁移验收：新节点接收完字节，不等于这些字节已被可信地接管。

## 9. 常见处置：逐个说明它解决不了什么

| 做法 | 有效之处 | 必须保留的边界 |
| --- | --- | --- |
| 增加副本 | 增加可恢复来源 | 不自动识别谁正确，也不防共同错误输入 |
| 延长超时 / 重试 | 应对延迟与暂时 omission | 不修复错误内容，可能反复命中坏缓存 |
| 所有字节加 checksum | 降低漏检指定损坏的机会 | 仍须保护身份、版本、期望值与检查后的缓冲区 |
| 节点校验失败就退出 | 收缩尚未传播的坏输出 | 需要可靠检测，不能遗忘承诺后随意重入 |
| 选择多数一致的副本 | 某些受限模型下帮助筛选 | 必须同版本、来源独立，不能覆盖最后一份可信旧证据 |
| 自动 repair | 补回已验证内容和冗余 | 来源未验证时会造成 repair poisoning |
| 定期备份 | 增加历史恢复点 | 备份可能已含损坏，必须验证且保持故障隔离 |

这些不是对某个产品的默认行为描述，而是用来审计具体实现的检查表。

## 10. 故障注入：不要只会 kill 一个进程

实验应在可丢弃数据与独立环境中进行。把原始输入及其摘要保存在**不参与被测故障注入的 oracle** 中。仅以被测集群自己重算的 hash 作为最终答案，会重复同一信任错误。

| 注入点与故障 | 应观察到的结果 | 必须失败的错误实现 |
| --- | --- | --- |
| 持久化前杀进程 | 未承诺尾部按协议处理，不返回虚假成功 | 先 ACK 后稳定 |
| 成功响应在网络丢失 | 同一请求重试不重复执行非幂等动作 | 把未知结果当作从未执行 |
| 只丢一个方向的消息 | 允许怀疑与切换，但无越权旧写 | 仅凭本地 lease 判断仍可写 |
| 已持久化日志中部翻转一位 | 检出、隔离、按历史恢复 | 盲截断后继续投票 |
| 快照某页被另一页替换 | 身份/范围或整体摘要检查拒绝 | 只接受该页自己携带的校验 |
| 数据与本地 hash 一起换成旧版本 | 可信版本依据拒绝回滚 | hash 通过就返回当前版本 |
| 故障节点声称“已经 fsync” | 明确暴露超出基础 CFT 的边界 | 把 ACK 数当作反欺骗认证 |
| 修复输入之一损坏 | 坏输入不得传播到健康目的地 | 先解码、覆盖后再检查 |
| 生成摘要前篡改生产者缓冲区 | 暴露覆盖盲区；由更早 oracle 检出 | 宣称端到端 hash 能修正错误原始值 |
| 修改校验后的共享缓冲区 | 所有权/冻结机制阻止或最终检查检出 | 复用已验证内存而不保护生命周期 |
| 所有来源都坏或权威依据丢失 | 显式不可用、保留证据、告警 | 返回拼接内容并宣告恢复成功 |

每次记录：故障范围、对象与 generation、协议 index/term、注入前后字节、首次检测时间、危险输出是否已发生、最终 oracle 结果、恢复及重新加入依据。

### 验收不要只看可用性

至少分别统计：错误成功返回数、已确认历史是否丢失、坏数据被当作修复源的次数、检测延迟、修复暴露窗口，以及前台超时/P99。**安全性目标中的“零错误交付”是实验通过条件，不是有限实验能够证明所有执行永远正确。** 测试未触发某个边界，只能说明该次测试未观察到违反。

## 11. 与 EC 的连接：把未知错误变成已知缺片

副本恢复要找到可信的完整拷贝；EC 恢复要找到足够多、同版本、独立有效的编码分片。二者共同依赖“这份输入可用于恢复”的证据。

在下一篇 [[7.35 Erasure Coding 完整性工程：Reed-Solomon、LRC、Checksum、Degraded Read 与 Rebuild]] 中，坏片一旦被可信校验定位，就可以从候选集合移除，作为 erasure 处理。但移除会消耗冗余预算；校验元数据不可用、好片数量不足，或 LRC 方程不满秩时，都不能继续宣称“还有很多服务器在线，所以能恢复”。

> [!important] 本篇的最终边界
> **Crash tolerance 保护的是守规矩的节点可能停止；完整性工程保护的是数据表示可能出错；Byzantine tolerance 则要处理节点任意偏离协议。** 检测与隔离可以在明确假设下连接这些世界，但不能删掉假设。

## 12. 自检与面试口述

**问题 1：三个 Raft 副本里有一个磁盘坏块，是否一定安全？** 不能只由副本数判断。先看坏的是业务页、日志还是任期/投票元数据；是否在使用前检出；是否存在可信正确来源；节点是否按受控协议停止和恢复。已知的局部坏页与任意持久化承诺失信不是一个模型。

**问题 2：SDC 是否等于 Byzantine？** 不等于。SDC 描述错误未在某观察边界被报告；Byzantine 描述节点允许任意偏离协议。一次 SDC 可能让节点产生越界行为，但受限介质损坏、检测漏失和完全不可信节点不能混为同一个威胁模型。

**问题 3：既然 checksum 不完美，为什么仍然值得做？** 因为系统可以明确其保护范围，把大量实际损坏变成可定位、可拒绝的错误，再依赖冗余恢复。工程目标是可靠组合，而不是用单项机制声称绝对正确。

**问题 4：检测到坏块以后直接重启，有什么问题？** 重启不提供正确版本，不修复坏介质，也不证明此前投票承诺仍在。错误状态可能被再次加载或在重入时覆盖健康副本。

**问题 5：为什么多数一致仍可能全错？** 因为这些副本可能共同复制了错误输入、同一个旧版本，或经过同一缺陷的编码路径；一致性与正确性是两个判断。
