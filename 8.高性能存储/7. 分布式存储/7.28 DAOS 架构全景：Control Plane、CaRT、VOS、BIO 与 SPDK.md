# DAOS 架构全景：Control Plane、CaRT、VOS、BIO 与 SPDK

> [!abstract] 先建立一个可以用来读源码的模型
> **DAOS 不是把 RDMA、Raft 和 SPDK 首尾相接，而是让它们分别承担通信、少量权威元数据的一致性，以及节点内存储访问。**
> 应用的数据先由对象层决定分布与保护方式，再由 CaRT 传递操作与数据，由 VOS 维护本地版本和索引，由 BIO/SPDK 驱动 NVMe；管理、故障处理和元数据服务从旁协调这条路径。[1][2]

> [!info] 阅读范围与版本
> 本系列以 **DAOS 2.8.0** 和上方固定源码提交为基线，面向 Linux 上的架构与源码阅读。教材只支撑复制、版本和性能分析等基础模型；DAOS 的组件职责以官方文档与源码为依据。
> 源码目录中的部分 README 保留了早期 PMem、epoch 管理和线程配置的设计描述，**文件存在于新版本中，不表示里面的所有旧设计都已成为该版本的实现承诺**。本系列不沿用旧的 `CONT_EPOCH_COMMIT` 编程模型。[3][4]

## 1. 从已有知识跨到 DAOS，需要补哪一层

读过 [[4.2 Verbs 编程模型]] 和 [[5.6 SPDK 用户态驱动]]，已经能理解“如何把字节搬到另一台机器”和“如何驱动本机 SSD”。但完整存储系统还要回答：这个字节属于哪个对象、应该放在哪些节点、哪个版本可以读、发生故障后谁有权改变布局。

这正是对象服务、元数据服务、VOS 和恢复机制的工作。不要让 RDMA 的低延迟掩盖了这些上层语义。

| 已有知识 | DAOS 中的对应位置 | 不能直接画的等号 |
|---|---|---|
| RPC、异步完成、批量传输 | CaRT、Mercury、客户端任务与事件机制 | CaRT 不是 gRPC 换一个网卡 |
| RDMA、内存注册、provider | Mercury 的 OFI/libfabric 或 UCX 路径 | OFI 不等于必定使用 RDMA |
| 本地索引、MVCC、空间管理 | VOS、版本索引、VEA | VOS 不是一个远程共享内存窗口 |
| 用户态 NVMe 驱动 | BIO → SPDK Blobstore/bdev/驱动 | DAOS 的网络协议不是 NVMe-oF |
| 复制状态机、主从与选主 | 管理服务数据库；Pool/Container 服务的 RDB | 每次对象写入不都经过一个全局 Raft |
| 控制面、资源编排 | `daos_server`、管理服务、`dmg` | 控制面不是用户数据的转发代理 |
| 故障域、数据放置、恢复 | Pool Map、placement、rebuild | 检测到异常不等于数据已经重建 |

这张表是**工程映射**，不是说这些组件实现相同的 API。复制与分区本来就是不同问题；教材中“少量协调节点维护元数据、更多节点承担实际工作”的区分，有助于理解 DAOS 的分工，但不能代替 DAOS 的实现证据。[1][5]

## 2. 一张总图：把管理、对象语义和字节路径分开

![[图片/SVG/8_7_7_26_1.svg|900]]

**图 1 的阅读方法：**上方是管理进程与管理通信，下方展开一个存储引擎。蓝色表示网络，绿色表示对象与本地存储逻辑，棕色表示持久介质。右上角的 RDB 是元数据服务所用的基础设施，不是从客户端到 NVMe 必经的一段串行代理。

在一条正常的数据访问路径上，应用链接 `libdaos`，直接与存储引擎通信。客户端的 `daos_agent` 提供认证和系统附着信息等支持，并不逐块转发应用 payload。服务端 `daos_server` 管理本机引擎，但大块对象数据也不需要先经过它的 Go/gRPC 层。[1]

### 2.1 三种通信，属于不同边界

| 通信机制 | 典型参与者 | 承担的工作 |
|---|---|---|
| gRPC | `dmg` / agent / control server | 管理接口、系统附着相关信息、控制面间协调 |
| dRPC，运行在 Unix Domain Socket 上 | 同机的 server ↔ engine；client library ↔ agent | 跨进程但不跨主机的控制与认证交互 |
| CaRT | `libdaos` ↔ engine；engine ↔ engine | 对象及元数据 RPC、bulk 数据传输、集体通信 |

**“数据面中的控制消息”不是“控制面的 gRPC”。** 例如 `update` 的对象 ID、key、extent、事务上下文和 bulk 描述信息，仍然是通过 CaRT 发往 engine 的对象请求，只是其中并不一定内联整个 payload。[1]

### 2.2 CaRT、Mercury、OFI 与 UCX

**CaRT（Collective and RPC Transport）**提供 DAOS 使用的通信组织能力；Mercury 位于其下，提供 RPC 与 bulk 传输等机制。OFI 是开放 fabric 接口体系，libfabric 是相应的通信库。2.8 的官方支持列表同时包含 OFI/libfabric 和 UCX 路径。[1][3]

正确理解是 **Mercury 下可以选择不同网络抽象**，而不是固定的 `Mercury → UCX → libfabric → RDMA` 串行栈。选择 `ofi+tcp` 与选择支持 RDMA 的 provider，在 CPU 开销、传输机制和观测方式上也不能混为一谈。

已有的 [[4.6 RoCE 与 InfiniBand]] 解释了网络与传输背景；到 DAOS 中，还必须记录实际 provider、设备、接口与版本，才能判断某次 I/O 是否真的走了所讨论的 RDMA 路径。

### 2.3 Native、DFS 与 dfuse：应用从哪一层进入

Native Object API 直接暴露 DAOS 的对象与 key/value 操作；**DFS（DAOS File System）**通过 `libdfs` 在对象之上组织文件和目录；**dfuse** 则提供基于 FUSE 的挂载入口，让普通文件接口应用访问相应容器。[1][12]

因此，同样写一个 checkpoint，应用直接调用对象 API、直接使用 DFS，或者经 dfuse 的 POSIX 路径进入，经过的软件层并不相同。不能看到底层有 SPDK，就宣布最上层应用的每条文件操作也全部绕过内核。后面的性能比较必须先标明这个入口。

## 3. 进程、rank、target、xstream：四个不同的坐标

源码里最容易混淆的不是某个算法，而是“这个标识究竟指一台机器、一个进程，还是一个逻辑执行单元”。

| 名称 | 本文采用的理解 | 不应推导出的结论 |
|---|---|---|
| Host / storage server node | 部署存储组件的主机 | 一台主机必定只有一个 engine |
| `daos_server` | Go 控制面进程，启动和监控本机 engine | 它就是处理所有 Object I/O 的进程 |
| `daos_engine` | C 数据面进程，运行存储服务 | 一个 engine 就对应一块 SSD |
| Rank | 系统内标识 engine 的逻辑编号 | Rank 等于 IP、PID，或应用的 MPI rank |
| Target | engine 暴露的可寻址存储目标，承载池的本地分片 | Target 是整个 pool，或者一块裸盘的同义词 |
| Xstream | Argobots 的执行流，承载调度与执行 | Xstream 数量可由这张概念图固定推算 |
| ULT | 在执行流上协作调度的用户级线程 | 使用 ULT 就没有共享状态竞争 |

引擎使用 Argobots 组织执行；BIO 把 SPDK 的 I/O 通道和完成轮询与执行流结合。具体核心绑定、target 数量、辅助执行流和设备映射属于配置及实现细节，不能把某个早期 README 的线程数量视为所有部署的定律。[1][2]

[[5.11 Reactor Thread 与 Poller]] 能帮助理解“主动推进完成事件”的模型；[[5.23 Target CPU NUMA NIC SSD 亲和性]] 则解释了为什么同样的接口调用，跨 NUMA 搬运后可能得到完全不同的性能。这里借用的是调度与局部性模型，不是宣称 DAOS 直接采用了某个通用 Reactor 模板。

> [!warning] 协作式调度仍然有等待成本
> 等待网络或 SSD 时，可以让出当前 ULT，或者由其他任务推进完成；但对一个绑定执行流执行长时间、不让出的计算或不受控阻塞操作，仍可能拖慢该执行流上的其他工作。分析时要区分“一个请求等待”“一个 ULT 让出”和“底层 OS 线程被阻塞”。

## 4. 数据模型：从 pool 一直定位到一段 value

下面的模型来自 DAOS Storage Model、Object 和 VOS 文档，而不是 S3 bucket/key 模型的照搬。[4][6][7]

| 层级 | 回答的问题 | 例子与边界 |
|---|---|---|
| Pool | 资源从哪些 targets 预留？布局和故障域是什么？ | 一个系统中的分布式资源池；不是每个用户一个本地目录 |
| Container | 哪个对象命名空间？事务、快照和数据管理归属哪里？ | `checkpoints` 数据集；不等于 Docker container |
| Object / OID | 哪个对象？采用什么类型、分片与保护布局？ | 容器内唯一的 128 位对象标识 |
| Dkey | 对象内部的数据如何获得分布与局部性？ | `tensor-part-42`，是应用选择的 distribution key |
| Akey | 该 dkey 下的哪个值或数组？ | `payload`、`shape`；这里的 attribute 不是容器属性表 |
| Single / Array value | 更新一个完整值，还是固定大小记录数组中的若干范围？ | shape 可用 single；payload 可用 array |
| Epoch | 本次操作及版本选择处于什么逻辑时间？ | 与事务/MVCC 相关，不是网络包序号 |

一次对象 I/O 可以先按概念记成：

**Container handle + OID/对象 handle + dkey + akey + value/extent + transaction context。**

### 4.1 用一个 checkpoint 例子穿起来

假设应用把一个 checkpoint 放入容器 `C`。对象 `O` 中，`dkey=tensor-part-42` 下有 `akey=shape` 和 `akey=payload`。前者存小的形状描述，后者存记录大小为 1 字节的数组。

写入 payload 的第 4096～8191 字节时，使用数组范围“起始记录 4096，记录数 4096”。应用并不是把 OID 当作远端虚拟地址，也不是把 dkey 当作硬盘 LBA。**客户端对象层完成分布映射，服务端 VOS 再完成本地索引和介质位置查找。**

如果对象采用 `OC_RP_2G1`，可以把它理解为“一个冗余组，两份副本”，不是“一个 target 内保存两份就等于跨节点容错”。同一个 dkey 提供逻辑局部性，但副本和 EC 会引入多个物理分片；不能把“同 dkey 共置”简化成“数据永远只存在一台机器上”。[6]

### 4.2 Single value 与 array value 不一样

Single value 的更新替换整个值；array value 则支持按固定记录大小描述的范围更新。高层 Array API 又可以把数组切成多个 chunk，并映射到不同 dkey，因此“原生 key-array 对象”和“高层 Array API”也不是相同层级。[4][6][7]

这种差别会影响小写放大、EC 条带、请求数量与索引数量。做实验时，仅写“4 KiB I/O”还不够，还要说明它是完整 single value，还是一个大数组中的 4 KiB extent。

## 5. 对象服务、VOS、BIO 和 SPDK 各负责什么

### 5.1 对象服务：把逻辑对象变成分布式操作

对象服务解释对象类型和 class，计算/使用 placement，组织到各 shard 的请求，并与数据保护、校验和及分布式事务机制（DTX，Distributed Transaction）协作。复制模式下的某次 I/O 可以由选定的 leader shard 协调其他分片，**这个 leader 不等于 Pool Service 的 Raft leader**。[6]

[[7.1 副本 vs EC]] 解释了两种保护方案的成本；DAOS object class 把这些选择落实到对象布局。不要把示例中的副本数当作系统默认值，也不要假定 `GX` 对象在扩容后自动增加原先编码在 OID 中的冗余组数；固定布局和新对象布局需要分别分析。[6]

### 5.2 VOS：单个 target 上的版本化对象存储

**VOS（Versioning Object Store）**维护本地 container、object、dkey、akey 及 value/extent 索引，结合版本与事务状态判断哪些数据可见。它还涉及对象或 key 的创建/删除历史、DTX 状态，以及 aggregation 对旧版本空间的回收。[7]

VOS 的核心问题是“指定逻辑对象的哪些版本、哪些范围可见”，不是“给我一个 LBA，我发 NVMe 命令”。它和普通文件系统一样需要索引与崩溃一致性，但暴露的数据模型并不是 POSIX inode 模型。

### 5.3 BIO：把逻辑存储需求接到本地介质

**BIO 是 Blob I/O，不是 Linux 内核的 `struct bio`。** 它管理 NVMe 相关 I/O、DMA 缓冲、设备状态及相关映射。SPDK Blobstore 提供较大粒度 blob，DAOS 的细粒度空间分配机制（VEA 等）进一步处理 extent 分配。[1][2]

BIO 的服务器侧 DMA-safe 缓冲区也是网络 bulk 与 NVMe DMA 的衔接点。这一事实决定了 DAOS 的“零拷贝”应按具体内存区间解释，详见 [[7.29 DAOS 数据路径：Object IO、RPC、RDMA、NVMe 与 Zero-Copy]]。

### 5.4 SPDK：执行节点内的设备访问，不决定分布式语义

SPDK 提供用户态 NVMe 访问及其上层存储组件；DAOS 使用它访问本机设备。SPDK 本身并不替 DAOS 决定 pool membership、对象分片或者事务提交。[2]

因此，[[5.1 NVMe-oF 架构]] 中“远端暴露 NVMe 控制器/namespace”的模型，与这里“远端执行 DAOS 对象操作，服务端用 SPDK 访问本地 NVMe”的模型，网络边界不同。**都使用 RDMA 和 NVMe，不意味着使用同一套存储协议。**

## 6. 持久介质：不要把 PMem 时代的图当成唯一部署

| 观察角度 | PMem 型路径 | Metadata-on-SSD 路径 |
|---|---|---|
| VOS 元数据工作位置 | 利用字节寻址持久内存模型 | 运行时元数据位于 DRAM，持久状态依赖 SSD 相关结构 |
| 本地崩溃恢复关注点 | 持久内存事务、索引一致性与持久化边界 | WAL、持久 metadata、checkpoint 与恢复顺序 |
| 大块用户数据 | 可由 BIO/SPDK 访问 NVMe | 仍可由 BIO/SPDK 访问 NVMe |
| 必须避免的误解 | 普通 DRAM 不是 PMem | 配一个 RAM 路径并不自动获得持久性 |

Metadata-on-SSD 中的 **WAL、META、DATA 是存储角色**，并不必然对应三块独立 SSD。WAL 与 metadata checkpoint 配合，使运行时元数据可以从持久状态恢复；这和跨节点 RDB 的 Raft 日志不是一个层面的日志。[8]

> [!warning] 2.8 的支持边界
> 官方 2.8 Release Notes 将新建 Metadata-on-SSD pool 使用的 allocator v2、**不启用 metadata eviction** 的路径列为生产支持；默认 memory-to-metadata ratio 为 100%。低于 100% 的比例涉及技术预览，不能直接作为成熟的超内存元数据方案。旧 Phase1 pool 不会仅因被新版本打开就自动转换。[3]

这里没有给出可直接用于生产的部署 YAML。主机的真实介质、持久控制元数据位置、设备绑定和故障域必须由部署清单确认，而不是从架构图反推。

## 7. 元数据支线与诊断工具：RDB、SMD、DDB 不要混

**RDB（Replicated Database）**为 Pool/Container 等服务提供基于 Raft 的复制元数据能力。除此之外，控制面管理服务还有独立的系统数据库实现；VOS 本地对象索引和 SMD 的设备/blob 映射也都是元数据，但不应统称为“RDB 里的数据”。[9][10]

**DDB 是 DAOS Debug Tool**。它导航和检查 VOS 格式内容，也提供显式写模式。它不是复制数据库，也不是每次请求必须经过的后台数据库服务。第一次看到 `src/utils/ddb/`，应联想到诊断工具，而不是给总架构再加一个常驻数据代理。[11]

各类权威信息的持有者、Raft 组与成员变化的边界，在 [[7.30 DAOS 元数据：RDB、Raft、Pool、Container 与 Membership]] 中展开。先掌握这一区分，再读 [[7.20 元数据服务高可用]]，才不会把“元数据服务还有 quorum”误当成“用户数据一定未丢”。

## 9. 读完后应该能回答

**为什么 agent 不应该画在 payload 的必经线上？** 因为它承担认证和附着支持，应用的 DAOS 数据通信由 libdaos 与 engine 直接进行。[1]

**为什么 VOS 和 SPDK 之间还需要 BIO 等层？** 因为对象版本和 extent 语义需要转换成可提交的介质 I/O，还要处理 DMA 缓冲、blob/设备映射及错误生命周期。[2][7]

**为什么一台主机坏了，不等于只少一个 target？** 一台主机可以有多个 engine，一个 engine 可以有多个 target，故障影响范围必须按真实拓扑展开。[1]

**为什么 `Object I/O → Raft → NVMe` 是不合适的总图？** 它把元数据复制和用户数据路径混在一起，遮蔽了对象保护、DTX 以及各 target 上的本地存储工作。[6][9][10]

**下一步应该追什么？** 不再背术语，沿 [[7.29 DAOS 数据路径：Object IO、RPC、RDMA、NVMe 与 Zero-Copy]] 追踪一次 update/fetch，再用 [[7.30 DAOS 元数据：RDB、Raft、Pool、Container 与 Membership]] 检查故障时谁改变布局和权威状态。
