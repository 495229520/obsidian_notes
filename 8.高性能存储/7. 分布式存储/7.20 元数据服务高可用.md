# 元数据服务高可用

> [[7.2 元数据路径瓶颈]] 讲清了一件事：每一次 IO 都要先向元数据服务（MDS）「问路」。这带来一个直接推论——**数据节点挂一台只影响一部分数据，MDS 挂了是全集群的 open/create/stat 一起停摆**，训练任务集体卡在打开文件的那一行。所以 MDS 是整个系统里最需要「不能倒」的组件。高可用（HA）不是玄学，就是四件工程事的组合：把状态复制出去（[[7.11 Primary-Backup 与 Multi-Raft]]）、及时发现主死了（[[7.15 Membership 与故障检测]]）、安全地换人（[[7.12 Lease 与 Fencing]]）、让客户端在切换期间体面地等待和重试（[[7.13 幂等 重试 与请求去重]]）。前面几篇把每个零件讲透了，本篇把它们装配成一台完整的机器：从主宕机那一刻起，逐段数清楚「多久能恢复、每段在等什么、谁来保证不出双主」。

前置：[[7.2 元数据路径瓶颈]]（MDS 是什么、为何在关键路径上）、[[7.11 Primary-Backup 与 Multi-Raft]]（复制与选主）、[[7.12 Lease 与 Fencing]]（租约与围栏）。

## 1. 名词与背景：先把「高可用」说成人话

三个术语先给直白定义【事实】：

- **高可用（HA, High Availability）**：单台机器故障时，服务在可接受的时间内自动恢复，不需要人半夜上线救火。度量是「几个 9」——99.9% 可用意味着一年最多停 8.8 小时，99.99% 是 53 分钟；
- **RTO（Recovery Time Objective）**：故障发生到恢复服务，**中断了多久**。本篇的主线就是拆解 MDS 的 RTO 由哪几段组成；
- **RPO（Recovery Point Objective）**：恢复之后，**丢了多少数据**。RPO 由复制方式决定——同步复制（写操作等备副本确认才返回）RPO = 0；异步复制可能丢掉尾部若干秒的更新【取舍】。

一个容易混的点：**RTO 和 RPO 是两笔独立的账**。切换再快（RTO 小），如果用的是异步复制，照样丢数据（RPO > 0）；反过来同步复制保证不丢，但切换慢照样停服很久。元数据是「关于数据的数据」——丢一条元数据（比如文件布局）可能让一个完好的文件变成不可读，所以生产的元数据复制几乎总是选同步路线，把代价付在平时每次写多一跳 RTT 上【实践】。

用多线程的直觉类比：MDS 好比进程里那把全局锁的持有者。持有者线程崩了，别的线程不能干等——得有机制检测「它死了」、安全地把锁的所有权转移给候补者，并且保证旧持有者「诈尸」后不能再改共享状态。本篇整篇都在讲这三件事的分布式版本。

## 2. 要恢复的状态是什么：持久与易失两本账

[[7.2 元数据路径瓶颈]] §1 的四张表，按「主挂了之后怎么找回来」分成两类【事实】：

| 状态 | 内容 | 恢复来源 |
| --- | --- | --- |
| **持久状态** | 命名空间（目录树）、文件布局、分片位置 | WAL/日志复制到备机或事务 KV（[[6.1 WAL 与 Crash Consistency]]）——切换时**回放**到最新 |
| **易失状态** | 客户端会话、租约、缓存授权、在途请求 | **不复制**——切换后由客户端**重建（reclaim）**，或干脆等旧租约超时作废 |

为什么易失状态不复制【取舍】：会话和租约变更的频率比目录树修改高一个量级以上，同步复制它们会把复制带宽花在最不值钱的数据上；而它们天然可以从客户端那一侧重建——客户端自己记得「我持有哪些租约、哪些请求还没收到回复」。代价是切换流程里多出一个**冻结窗口**：新主上任后不能立刻发新租约，要么等旧租约全部自然过期，要么开一个 reclaim 窗口让老客户端来重新登记——这段时间是 RTO 的固定组成部分，后面 §4 会数到它。

## 3. 三条高可用路线：HA 做在哪一层

工业系统的 MDS HA 有三条主流路线，区别在「复制和切换的机器装在哪一层」【事实】：

| 路线 | 代表 | 做法 | 切换时要做的事 |
| --- | --- | --- | --- |
| **主备 + 共享日志** | HDFS NameNode HA | 主把编辑日志写入 quorum 日志服务（JournalNode），热备持续 tail 回放；ZKFC 负责检测与切换 | 提升备机：补完日志尾部 + 围栏旧主 |
| **分片多活** | CephFS 多活 MDS | 按子树把命名空间切给多个 rank，每个 rank 配 standby（可选 standby-replay 热备）| 只切故障的那一个 rank，其他分片不受影响 |
| **无状态 MDS + 事务 KV** | [[7.3 JuiceFS 架构]]、[[7.4 3FS 架构]] | 元数据全部下沉到 Raft 复制的事务 KV，MDS 变成无状态翻译层 | MDS 层任意实例等价、随便挂；HA 难题整体转移给 KV 的 Multi-Raft（[[7.11 Primary-Backup 与 Multi-Raft]]）|

三点读表须知：

1. **「多活」不是同一份数据两个主**【事实】。CephFS 的多活是「多个分片各自有主，同时服务不同子树」；任何一条元数据记录，任一时刻仍然只有一个写入者。真正的「同份数据双主」是 [[7.14 Split Brain]] 里要不惜代价避免的事故；
2. **第三条路线没有消灭切换，只是把它搬进了 KV**。KV 的某个 Raft 组换主时，落在该组上的元数据操作照样停顿——只是停顿的粒度从「整个命名空间」缩小到「一个分片」，且 Raft 的秒级选主是现成的、被反复验证过的实现【取舍】；
3. **分片路线把故障域切小了，也把故障变频繁了**【取舍】：10 个分片各自独立切换，单次影响 1/10 的命名空间，但「有分片在切换」的概率是单点的 10 倍。可用性设计从「避免一次大停摆」变成「让每次小停摆便宜」。

对照 [[7.5 Ceph RADOS 与 CRUSH]] 的另一手：位置表用 CRUSH 算法现算，从元数据里整个删掉——最好的高可用是让那部分状态根本不存在。

## 4. 故障切换全流转：每一段在等什么

![[图片/SVG/8_7_20_1.svg|900]]

以「主备 + 同步复制日志」为例，从主宕机到完全恢复，六段依次发生【事实】：

| 段 | 发生什么 | 等待点 | 量级 |
| --- | --- | --- | --- |
| ① 检测 | 主停止心跳；Monitor 数静默次数（[[7.15 Membership 与故障检测]]） | **k × 心跳周期的超时窗**——收紧则误判率升，放宽则 RTO 长 | 秒级 |
| ② 判死 + 选主 | 多数派裁决、挑选备机、世代号（epoch）+1 | 一轮多数派共识的 RTT | 亚秒~秒 |
| ③ 围栏（fencing） | 新 epoch 公告给存储层/KV：旧 epoch 的写一律拒绝（[[7.12 Lease 与 Fencing]]） | 围栏生效的确认 | 亚秒 |
| ④ 日志回放 | 新主把未 apply 的复制日志回放到最新（[[6.1 WAL 与 Crash Consistency]]） | **回放时长 ∝ 未 checkpoint 的积压量** | 秒~分钟，**常见大头** |
| ⑤ 会话/租约重建 | 冻结窗口：等旧租约过期，或接受客户端 reclaim | **下限 = 租期**（§2 的账） | 秒~几十秒 |
| ⑥ 客户端恢复 | 客户端重连、验 epoch、带原 request id 重放在途请求（[[7.13 幂等 重试 与请求去重]]） | 重试退避的最后一跳 | 亚秒 |

**RTO ≈ ① + ② + ③ + ④ + ⑤**。三条必须刻进脑子的规则：

1. **顺序不可颠倒：先围栏，再回放，再上岗**【事实】。检测是允许误判的（旧主可能只是网络抖了并没死），正确性不靠「确认它真死了」，靠 epoch 让旧主复活后的写全部作废。如果先回放再围栏，回放的「终点」可能还在被旧主追着改写——新主基于一个仍在变动的状态上岗，就是脑裂；
2. **④ 是平时看不见的隐性债**【实践】。系统正常运行时 checkpoint 偷懒没人察觉，日志越积越长；一切换，全集群陪着新主回放十分钟。回放时长应该作为常态监控项，而不是事故后的惊喜；
3. **客户端的读与写命运不同**【事实】。租约有效期内，客户端缓存的路径/布局照常命中，读几乎无感——这正是 [[7.2 元数据路径瓶颈]] §4.3 客户端缓存的第二重价值：平时省 RTT，切换时当缓冲垫。写和缓存未命中则从 ① 卡到 ⑥，应用侧表现为 open/create 挂住几秒到几十秒。压缩「写不可用窗口」的三个抓手正好对应三段：调快检测（①）、勤做 checkpoint（④）、缩短租期（⑤）——每个都有反面代价，没有免费的旋钮【取舍】。

## 5. 切换做对之后：别让 HA 方案自己变成新问题

- **热备回放（standby-replay）**【取舍】：备机平时就持续 tail 日志回放，切换时 ④ 趋近于零，RTO 主要剩检测和租约两段。代价是备机内存/CPU 与主同规格常驻——**用 2 倍资源买 RTO**。元数据规模大、恢复慢的系统（CephFS 大目录树）值得买；
- **半死不活比死透更糟（灰色失败）**【实践】：主没崩，但磁盘变慢/GC 停顿/丢包 30%——心跳还在续，检测不触发，全集群跟着它慢。对策是把健康定义从「心跳活着」升级为「关键操作延迟达标」，必要时主动自杀让位（触发一次干净的切换，胜过无限期拖累）；
- **切换风暴**【实践】：切换瞬间，所有客户端的重试同时砸向新主——新主一上任就被打垮，再触发一次「切换」。客户端必须带指数退避 + 抖动（§6 的代码），服务端必须对恢复期限流（[[7.18 Backpressure 与过载保护]]同款思路）；
- **检测参数不是越灵敏越好**【取舍】：超时收得太紧，一次网络抖动就触发无谓切换，切换本身就是一次几十秒的停顿——误判率 × 切换成本才是真实代价，[[7.15 Membership 与故障检测]] 的误摘除雪崩在 MDS 上同样成立。

## 6. Modern C++：客户端切换壳——同一个 request id + 世代号验证

切换期间客户端的正确行为可以浓缩成一个重试壳。核心是两件事：**重试全程复用同一个 request id**（让服务端能去重，[[7.13 幂等 重试 与请求去重]]），以及**每次应答校验 epoch**（识别「我连的还是旧主」）。

```cpp
#include <chrono>
#include <cstdint>
#include <expected>
#include <random>
#include <thread>

enum class RpcError { kTimeout, kNotPrimary, kStaleEpoch };

struct MetaReply { /* inode、布局等 */ };

// 幂等键：同一 (client_id, seq) 无论重发多少次，服务端只执行一次
struct RequestId {
    std::uint64_t client_id;
    std::uint64_t seq;
};

class MetaClient {
public:
    std::expected<MetaReply, RpcError> Call(const auto& op) {
        const RequestId id{client_id_, next_seq_++};   // 整个重试过程复用这一个 id
        auto backoff = std::chrono::milliseconds{20};
        for (int attempt = 0; attempt < kMaxAttempts; ++attempt) {
            if (auto r = Send(primary_, epoch_, id, op); r.has_value())
                return r;                              // 正常返回或确定性业务错误
            else if (r.error() != RpcError::kTimeout)  // 对方明说：主换人了 / 我的视图旧了
                RefreshView();                         //   → 立刻拉新主地址与新 epoch
            else
                RefreshView();                         // 超时：主可能已死，同样先刷新视图
            std::this_thread::sleep_for(Jitter(backoff));
            backoff = std::min(backoff * 2, std::chrono::milliseconds{2'000});
        }
        return std::unexpected{RpcError::kTimeout};
    }

private:
    static constexpr int kMaxAttempts = 8;

    std::chrono::milliseconds Jitter(std::chrono::milliseconds base) {
        std::uniform_int_distribution<int> d(0, static_cast<int>(base.count()));
        return base + std::chrono::milliseconds{d(rng_)};   // 打散惊群
    }

    void RefreshView();   // 向 Monitor/KV 查询当前主与 epoch，更新 primary_ 与 epoch_
    std::expected<MetaReply, RpcError> Send(/* endpoint */ const auto& ep,
                                            std::uint64_t epoch, RequestId id,
                                            const auto& op);

    std::uint64_t client_id_;
    std::uint64_t next_seq_ = 0;
    std::uint64_t epoch_ = 0;
    /* endpoint */ struct {} primary_;
    std::mt19937 rng_{std::random_device{}()};
};
```

**关键点**：

- `RequestId` 在 `Call` 开头生成一次、循环内复用——如果每次重试换新 id，「超时后重发」就可能把一次 mkdir 变成两次，切换期间的在途请求正是重复执行的高发区；
- 收到 `kNotPrimary`/`kStaleEpoch` 不是错误，是**协议的一部分**：切换期间必然发生，处理方式是刷新视图后带同一 id 重发，对上层完全透明;
- 退避加随机抖动（`Jitter`）是防「切换风暴」的客户端半边：没有它，成千上万客户端的重试在同一毫秒对齐，新主上任即被击穿（§5）；
- 服务端的另半边（按 `(client_id, seq)` 去重、按 epoch 拒旧写）见 [[7.13 幂等 重试 与请求去重]] 与 [[7.12 Lease 与 Fencing]] 的验票代码。

## 7. 排障清单：症状 → 判定 → 处置

| 症状 | 先看什么 | 典型根因 | 处置方向 |
| --- | --- | --- | --- |
| 切换后集群卡住几分钟才恢复 | 新主日志回放进度 | checkpoint 太稀，回放积压大（§4④） | 加密 checkpoint 频率；上 standby-replay |
| 切换完成后 p99 出现秒级毛刺一波 | 毛刺时间 vs 租约到期时间 | 冻结窗口 + 租约批量到期重建（§4⑤） | 缩短租期或实现主动 reclaim；租约到期时间打散 |
| 出现两份互相矛盾的元数据 | 存储层是否校验 epoch | 围栏缺失或顺序错了：旧主复活继续写（§4 规则 1） | 补 fencing token 校验；事故数据按日志仲裁 |
| 无故频繁切换 | 检测超时参数、网络丢包率 | 超时过紧 + 网络抖动，误判触发（§5） | 放宽 k×心跳；升级健康判定维度 |
| 新主一上任就过载再挂 | 切换时刻的请求曲线 | 客户端重试无退避，惊群（§5） | 客户端指数退避+抖动；服务端恢复期限流 |
| MDS 没挂但全集群变慢 | MDS 关键操作延迟 vs 心跳状态 | 灰色失败：半死的主，HA 不触发（§5） | 健康检查纳入延迟指标；支持手动/自动让位 |

## 8. 陷阱与误区

> [!warning] 常见错误
> 1. **把「有备机」当作「高可用做完了」**：备机只解决 §4 的 ④ 有数据可回放；没有检测、围栏、租约重建和客户端重试的配合，备机只是一份温备份。
> 2. **切换流程先提升后围栏**：顺序反了就是给脑裂开门——正确性来自「旧 epoch 写被拒」，不是「确认旧主死透」。
> 3. **RTO 达标就宣布胜利，不看 RPO**：异步复制 + 快速切换 = 快速地丢数据。元数据丢一条，可能是一批文件永久变砖。
> 4. **租期只按平时性能调**：租期越长平时越省 RTT，但它同时是切换冻结窗口的下限——这是一个双向旋钮，要按「可接受的写不可用窗口」倒推。
> 5. **只测「杀掉主」的演练**：kill -9 是最善良的故障。慢盘、丢包、半连通这些灰色失败才是生产里 HA 掉链子的主场——故障注入要覆盖「慢而不死」。
> 6. **忽略切换期间的在途请求**：切换窗口里超时的 mkdir/create 如果用新 id 盲目重发，就是重复执行；幂等 id 不是优化，是切换正确性的一部分。

## 9. 关键结论

| 结论 | 性质 |
| --- | --- |
| MDS 故障是全集群停摆（每次 IO 都要问路），HA 优先级高于任何数据节点 | 事实 |
| RTO 与 RPO 独立：RTO = 检测+选主+围栏+回放+租约等待；RPO 只由复制方式决定，元数据几乎总选同步复制 | 事实/实践 |
| 状态分两本账：持久状态靠日志复制回放，会话/租约不复制、靠客户端重建——冻结窗口由此而来 | 事实 |
| 三条路线：主备+共享日志 / 分片多活 / 无状态 MDS+事务 KV——第三条没消灭切换，只是把它缩小到 KV 分片粒度 | 事实/取舍 |
| 先围栏再上岗的顺序不可颠倒；安全靠 epoch 作废旧主，而非「确认真死」 | 事实 |
| 日志回放常是 RTO 大头且平时不可见：checkpoint 频率与 standby-replay 是主要抓手 | 实践 |
| 客户端缓存+租约让读几乎无感、写卡满全程；压写窗口的三旋钮（检测/ckpt/租期）各有反面代价 | 事实/取舍 |
| 切换正确性延伸到客户端：同一 request id 重放 + epoch 验证 + 退避抖动，三者缺一不可 | 实践 |
