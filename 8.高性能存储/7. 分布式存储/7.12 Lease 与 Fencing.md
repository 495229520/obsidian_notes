# Lease 与 Fencing

> [[7.11 Primary-Backup 与 Multi-Raft]] 留下一个口子：主备骨架里，裁判怎么判定主已死、怎么安全地把主权交给下一任？难点在于分布式系统的基本事实——**"没收到回复"永远无法区分是死了、慢了还是网络断了**。**Lease（租约）**用"带过期时间的授权"回答这个问题：裁判不用联系失联的旧主，等租约过期即可放心换人。但 lease 的安全性建立在**时钟假设**上，而进程可能被 GC/调度/换页冻结几十秒且自己毫无察觉——所以旧主复活双写的窗口永远存在，必须由 **fencing token（栅栏令牌）**在最终写入点兜底：每任主拿一个单调递增的世代号，存储节点持久化见过的最大值、拒绝一切旧号。一句话：**lease 负责活性（尽快换主），fencing 负责安全性（旧主写不进）**——两者缺一不可。

前置：[[7.11 Primary-Backup 与 Multi-Raft]]（主的任命与判死问题从何而来）。

---

## 1. 名词与背景：判死难题与"带过期时间的授权"

**判死难题**【事实】：裁判（协调者）与主 A 之间靠心跳维持联系。心跳断了，可能是 A 宕机，也可能是 A 正忙、网络抖动、或裁判自己的网络出问题。若裁判贸然任命新主 B，而 A 其实活着且还在接客户端写——同一份数据两个定序者，各写各的，这就是 [[7.14 Split Brain]]，会造成**静默数据损坏**（两边都认为自己写成功了）。

**Lease（租约）的定义**【事实】：一个**带过期时间的授权**——裁判对 A 说："从现在起 T 秒内你是主"（T 称为 TTL）。A 在到期前不断**续约**；续约断掉后，裁判只需**等到租约过期**，就可以确信"A 已经不再行使主权"，从而安全任命 B——**全程不需要联系 A**。这是 lease 最关键的性质：收回权力不依赖与失联者通信。

类比【类比】：DHCP 分配 IP 就是租约——路由器不用问"你还在用吗"，到期没续就直接把 IP 分给别人。会议室预订同理：到点没续订，下一个人直接进。

为什么"到期自动收回"成立？因为 A 自己也在计时【事实】：A 每次续约成功后知道"我的主权到某时刻为止"，此后每次服务写请求前先自查租约是否仍有效，过期就主动停止服务。于是安全性化归为一个命题：**"A 认为自己还是主"的时间段，与"裁判认为 A 已不是主"的时间段，不能重叠**。这个命题成立与否，完全取决于双方的时钟——这就是下一节。

## 2. Lease 的时钟力学：谁计时、怎么计时

**用单调时钟，不用墙钟**【实现】：Linux 提供两类时钟——`CLOCK_REALTIME`（墙钟，NTP 可以调它，会跳变甚至回拨）和 `CLOCK_MONOTONIC`（单调钟，只会匀速前进，NTP 只能微调其速率）。租约算的是**时间段**（"从续约起 10 秒"），必须用单调钟：墙钟一次回拨就能让"已过期"的租约起死回生。C++ 里对应 `std::chrono::steady_clock`（单调）与 `system_clock`（墙钟）。

**两端计时不对称**【实现】：网络传输有延迟，双方对"租约从何时开始"的认知天然有偏差。安全的做法是让偏差朝保守方向叠加：

- **持有方 A**：从"发出续约请求"那一刻起算 TTL——实际生效时刻只会更晚，所以 A 会**提前**认为自己过期（宁可早退位）；
- **裁判**：从"收到续约请求"那一刻起算 TTL，并在到期后**再多等一个余量 ε**（覆盖两端时钟速率漂移的上界）才任命新主（宁可晚换人）。

这样只要"两端时钟速率漂移有上界"这一假设成立，"A 先认为自己过期，裁判后判定 A 过期"的顺序就有保证——主权期无重叠。**注意这是前提假设而非可证明的事实**【前提】：它假设不了真实世界的全部（比如时钟硬件故障），更挡不住下面这种情况——

**持有者可能整段时间被冻结，且毫无察觉**【事实】。操作系统层面有一整族机制能让一个进程"失去几秒到几十秒"：

- 运行时 STW（stop-the-world）暂停：GC、JIT 去优化（C++ 服务也有类似场景：长临界区、被 `SIGSTOP`、coredump dump 中）；
- 内核调度延迟：CPU 超卖、cgroup CPU 配额被打满（容器里极常见）、实时进程抢占；
- 内存：缺页涌入、swap 换入、`mlock` 缺失导致关键页被回收；
- 虚拟化：VM 热迁移、宿主机停顿；
- 同步 IO 卡住：写日志的 fsync 卡在故障盘上几十秒。

冻结期间 A 的"检查租约是否过期"这行代码根本没机会执行；醒来后它执行的第一条指令还是冻结前的下一条——**先检查租约、再执行写，检查通过和写到达存储之间同样可能被冻结**。所以"每次写前检查租约"只能缩小窗口，不能消灭窗口。

1. A 在 STW 停顿中续约中断；裁判等满 TTL + ε 后把租约授予 B（token 从 33 递增到 34）；
2. A 苏醒后**不知道时间已流逝**，仍按冻结前的认知行事——它的租约检查代码要么还没跑到，要么用的是停顿前缓存的判断；
3. A 迟到的写抵达存储节点。如果存储不设防，这次写会覆盖 B 的新数据——**双主已成事实，lease 没能挡住**。

结论【事实】：lease 提供的是**大概率**无双主（活性好、常态下正确），但它的安全论证依赖"漂移有上界 + 持有者能及时自查"两个前提，而后者会被 STW 类事件打破。要**无条件**的安全，就必须在数据路径的终点设闸——fencing。

## 4. Fencing token：最终写入点的单调世代号

**定义**【事实】：裁判每次授出主权（首次授予或换任），生成一个**单调递增**的整数——fencing token（也叫 epoch、世代号；ZooKeeper 用 zxid 充当，Chubby 叫 sequencer，Raft 里 term 就是它的协议内形态）。主的每个写请求都携带自己的 token；**存储节点持久化记录见过的最大 token，拒绝一切小于它的写**。

三条纪律决定 fencing 是否真的有效【实现】：

1. **校验必须在最终写入点**。在网关、代理层校验都可能被绕过或与写乱序；只有实际落数据的那个节点（或对象存储的条件写原语，如 If-Match/CAS）做校验，才封死一切路径。类比 [[4.12 rkey lkey 生命周期]]：授权的验证必须发生在硬件/存储的门口，而不是中间层的善意里；
2. **max_token 必须持久化**，且与数据写入原子（同一条 WAL 记录）。否则存储节点重启后失忆，旧 token 又能写进来；
3. **token 由裁判统一签发**，与租约一起交付。主自己不能编号。

一个必须说破的细节【事实】：fencing 保证的是"**一旦新主 B 的 34 落盘，旧主 A 的 33 永远写不进**"，而不是"A 复活后的一切写都被拒"。若 A 的迟到写抢在 B 的首写之前到达，存储时见 max=33，照常放行——这不破坏安全性（此刻 B 尚未写入任何依赖旧状态的数据），但意味着**B 上任后的第一件事应当是带着 34 写一条记录（哪怕 no-op）把门关上**——与 Raft 新 leader 先提交本任期 no-op 是同一个思想。

**与 Raft 的关系**【事实】：Raft 组内不需要额外 fencing——term 就是 token，AppendEntries 自带 term 校验，旧 leader 的复制请求会被多数派拒绝。需要显式 fencing 的是**协议之外的路径**：Primary-Backup 的数据面写入、拿着分布式锁去写共享存储的任何客户端、以及 lease read（见下节）之外的旁路读写。

## 5. 真实工作负载：checkpoint 场景里 lease 的两笔账

沿用 [[7.11 Primary-Backup 与 Multi-Raft]] 的场景：3000 GPU worker 每 30 分钟 checkpoint，数据面 Primary-Backup 写 chunk，元数据面 Multi-Raft。lease 在这两层各有一个用途，各算一笔性能账。

**用途一：数据面 chunk 主副本租约（GFS 式）**【实现】。协调者给每个 chunk 的主副本发租约（GFS 论文取 60 s，心跳捎带续约）。价值在**省网络与省协调者**：客户端可以缓存"谁是主"直接发写，协调者不在数据路径上；主挂了，最坏等一个 TTL 后协调者换主。因果账：

- TTL 大（如 60 s）→ 续约流量与协调者 CPU 可忽略；代价是主宕机后该 chunk 最长 60 s 不可写——**尾延迟里的秒级空洞**，靠客户端把写切到其他 chunk/文件规避；
- TTL 小 → 空洞短，但 3000 worker × 数万 chunk 的续约风暴会把协调者打成热点——续约必须按节点合并捎带（与 [[7.11 Primary-Backup 与 Multi-Raft]] 心跳合并同理），否则协调者网卡与 CPU 先炸。

**用途二：元数据面 leader lease read（省一次多数派往返）**【实现】。线性一致读的朴素做法：leader 收到读也要走一轮多数派确认自己还是 leader（ReadIndex：一次心跳往返），否则可能读到旧 leader 的陈旧状态。**lease read** 用租约替代这次往返：leader 在租约有效期内直接读本地状态机，零网络。因果账：

| 资源 | ReadIndex | Lease Read |
| --- | --- | --- |
| 网络 | 每读一次心跳往返（可攒批摊薄） | 读不出网，零消息 |
| 吞吐 | 读吞吐受心跳往返与攒批窗口限制 | 读吞吐 = 本地状态机上限，checkpoint 元数据风暴下差距成倍 |
| 尾延迟 | p99 含一次 RTT（跨机房时显著） | p99 ≈ 本地读；但**租约续期失败瞬间读全部降级/拒绝**，出现毛刺 |
| 安全前提 | 只依赖多数派通信 | 额外依赖时钟漂移上界假设——**用正确性换性能的显式取舍** |

【取舍】lease read 是"把时钟假设引入读路径"换吞吐：漂移假设被打破（VM 迁移、时钟故障）时可能读到旧值。TiKV/etcd 等都提供两种模式，metadata 服务这类读多写少、RTT 敏感的场景通常开 lease read，并把租约期钉在 election timeout 之内（保证旧 leader 租约过期前新 leader 选不出来，构成协议内自洽）。

**CPU 与内存**【实践】：lease 机制本身开销极小（一个定时器 + 心跳捎带续约字段）；真正的成本在**误判引发的切换**——TTL 设得太贴近 GC/盘抖的常见停顿时长，会把毛刺放大成主备切换（选举 + 缓存重建 + 客户端重路由），一次切换的代价远大于省下的心跳。经验方向：TTL 至少高于运行时常见停顿的 p99.9，再用 fencing 兜住剩余概率。

## 6. Modern C++：持有方自查 + 存储方验票

持有方：把"租约有效才允许写"做成 RAII 守卫。用 `steady_clock` 计时、留提前量，检查通过才拿到"许可"对象：

```cpp
#include <chrono>
#include <cstdint>
#include <mutex>
#include <optional>

using Clock = std::chrono::steady_clock;  // 单调钟：NTP 拨不动

class Lease {
public:
    Lease(std::chrono::milliseconds ttl, std::chrono::milliseconds margin)
        : ttl_{ttl}, margin_{margin} {}

    // 续约成功回调：t_sent 是"发出续约请求"的时刻（持有方保守计时）
    void on_renewed(Clock::time_point t_sent) {
        std::lock_guard lk{mu_};
        expiry_ = t_sent + ttl_;
    }

    // 写路径入口：拿不到票据就不许写。margin 提前退位，缩小复活窗口
    struct Permit { std::uint64_t token; };
    std::optional<Permit> check(std::uint64_t token) const {
        std::lock_guard lk{mu_};
        if (Clock::now() + margin_ >= expiry_) return std::nullopt;
        return Permit{token};
    }

private:
    mutable std::mutex mu_;
    Clock::time_point expiry_{};   // 默认过期：未续约前无主权
    std::chrono::milliseconds ttl_;
    std::chrono::milliseconds margin_;
};
```

存储方：token 校验与写入必须原子，且 max_token 随数据一起持久化——这才是**真正的安全边界**（持有方自查只是优化）：

```cpp
#include <cstdint>
#include <mutex>
#include <span>

class FencedStore {
public:
    enum class WriteResult { ok, stale_token };

    WriteResult write(std::uint64_t token, std::span<const std::byte> record) {
        std::lock_guard lk{mu_};
        if (token < max_token_) return WriteResult::stale_token;  // 旧主：拒绝
        max_token_ = token;
        // 同一条 WAL 记录写入 {max_token_, record} 并 fsync：
        // 重启后 max_token_ 从 WAL 恢复，失忆 = fencing 失效
        wal_append_and_fsync(max_token_, record);
        return WriteResult::ok;
    }

private:
    void wal_append_and_fsync(std::uint64_t, std::span<const std::byte>);
    std::mutex mu_;
    std::uint64_t max_token_{0};
};
```

要点【实践】：`check()` 通过与写到达 `FencedStore` 之间仍可能被冻结——这正是两段代码必须**同时存在**的原因：`Lease::check` 管活性与常态效率，`FencedStore` 管最终安全。

## 7. 故障案例与一场著名争论

**故障案例**【实践】：某集群主节点（带 JVM 的元数据服务）发生 12 s 的 full GC。租约 TTL 为 10 s，裁判判死、B 上任并开始写。A 苏醒后其写线程队列里还积着几百个已通过租约检查的写请求，全部涌向存储——存储侧没有 token 校验，B 刚写的元数据被 A 的旧状态覆盖，数天后才由巡检的校验和发现。根因链：停顿时长越过 TTL（活性机制按设计工作）→ 缺 fencing（安全机制缺位）→ 静默损坏。修复：存储写入接口加 epoch 条件写；同时把 TTL 提到停顿 p99.9 之上减少无谓切换。

**Redlock 之争**【事实与观点分开】：Redis 的 Redlock 算法主张用多个独立 Redis 节点上的带 TTL 锁实现分布式锁。Martin Kleppmann 的批评（"How to do distributed locking"）指出：凡是**依赖 TTL 而缺少 fencing token 落到存储侧校验**的锁，都挡不住 GC 停顿式的旧持有者复活；antirez 的回应则认为其时钟假设在实践中足够。这里的**事实**是：无 fencing 的 lease/锁在停顿场景存在双写窗口（本篇 §3 已构造出来）；**观点分歧**只在"该窗口的概率是否可接受"。存储系统的立场应当明确：数据正确性不赌概率——写路径终点必须验票。

## 8. 排障清单：症状 → 原因 → 检查

| 症状 | 常见原因 | 检查动作 |
| --- | --- | --- |
| 主备切换后出现两份冲突数据 | 旧主复活双写，存储侧无 token 校验 | 审计写路径终点是否验票；比对两份数据携带的 epoch |
| 切换频繁但节点其实健康 | TTL 贴着 GC/盘抖的停顿分布 | 拉停顿时长分布（GC 日志、调度延迟直方图）对比 TTL |
| 存储重启后旧主又能写入 | max_token 未持久化或未与数据原子写入 | 检查 WAL 记录格式与恢复路径是否回放 token |
| lease read 偶发读到旧值 | 时钟漂移假设被打破（VM 迁移、时钟故障）；或租约期 > election timeout | 核对两个时长的配置关系；查宿主机迁移事件 |
| 租约过期后仍有写成功 | 只在代理层校验 token，最终写入点未校验 | 逐层核对校验位置；旁路（运维工具、修复脚本）是否绕过 |
| 换主后新主首写前旧写混入 | 新主未先写 no-op 关门 | 上任流程加"先带新 token 写一条记录" |
| 容器内主节点频繁被判死 | cgroup CPU 配额打满导致心跳线程饿死 | 查 throttling 计数；心跳线程提优先级/独立配额 |

## 9. 陷阱与误区

> [!warning] 常见错误
> 1. **用墙钟算租约**：`CLOCK_REALTIME`/`system_clock` 会被 NTP 跳变回拨，"已过期"能起死回生。租约计时只用 `CLOCK_MONOTONIC`/`steady_clock`。
> 2. **两端从同一时刻起算**：忽略网络延迟与漂移，主权期可能重叠。持有方从发出请求起算并提前退位，授予方从收到起算并多等 ε。
> 3. **以为"写前检查租约"就安全**：检查与写达到存储之间可被 STW/调度冻结任意长。检查只缩小窗口，封死窗口靠存储侧 fencing。
> 4. **token 校验放在中间层**：网关校验挡不住绕行与乱序。校验必须在最终写入点，且 max_token 与数据原子持久化。
> 5. **把"连接还在"当"租约还在"**：TCP keepalive 与租约无关；租约是显式的时间契约，必须显式续约、显式自查。
> 6. **TTL 拍脑袋**：太小→毛刺变切换风暴；太大→故障空洞拉长尾延迟。以停顿分布 p99.9 为下界、以可容忍不可写窗口为上界去夹。
> 7. **忘了旁路**：修复脚本、数据搬迁工具直写存储不带 token——一次运维操作就能重演双写。所有写路径统一走验票入口。

## 10. 关键结论

| 结论 | 性质 |
| --- | --- |
| "没回复"无法区分死/慢/断——判死必须引入时间契约，这就是 lease | 事实 |
| Lease = 带 TTL 的授权：收回权力不需要联系失联者，只需等待过期 | 事实 |
| 租约计时用单调钟；持有方保守计时提前退位，授予方多等漂移余量 ε | 实现 |
| STW/调度/换页/虚拟化都能冻结进程且其毫无察觉——"写前检查"消灭不了复活窗口 | 事实 |
| Lease 保活性（大概率无双主），fencing 保安全（旧主必然写不进）：职责不同，缺一不可 | 事实 / 取舍 |
| Fencing token 三纪律：最终写入点校验、max_token 与数据原子持久化、裁判统一签发 | 实现 |
| Fencing 的精确语义：新主首写落盘后旧主永远写不进；新主上任先写 no-op 关门 | 事实 |
| Lease read 用时钟假设换掉每读一次多数派往返：读吞吐大增，正确性前提显式变弱 | 取舍 |
| TTL 选择被两头夹：> 停顿分布 p99.9（防误切换），< 可容忍不可写窗口（防空洞过长） | 实践结论 |
