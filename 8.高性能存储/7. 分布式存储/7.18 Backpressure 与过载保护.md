# Backpressure 与过载保护

> 过载不是"变慢"，而是一种**会自我放大的病**：请求排队 → 延迟超过客户端超时 → 客户端重试 → 到达的请求更多 → 队列更长。没有保护的系统在负载超过容量后，**有效产出反而随负载上升而下降**，最后所有资源都在做"注定超时的死工作"——这叫拥塞崩溃（congestion collapse）。Backpressure（背压）是解药的总名：让"下游忙"这个信号逐级传回上游，使上游主动慢下来或尽早失败，而不是把压力囤在中间的队列里。本篇先建立队列直觉，再讲信号从哪来、压回去的四层机制、客户端怎么配合，最后落到存储系统特有的背压链与 C++ 实现。

前置：[[7.17 Recovery 与 Rebuild]]（重建流量是最典型的"内部大客户"，必须可被背压）、[[6.14 Write Stall]]（存储引擎自带的单机背压）、[[1.8 一次 read write 全路径图]]（单机 write 路径的背压链，本篇是它的分布式延伸）。

## 1. 名词与背景：队列的非线性

先给定义【事实】：

- **容量（capacity）**：系统单位时间能完成的请求量上限，由最紧的资源决定（盘的 IOPS、网卡带宽、CPU、锁）；
- **到达负载（offered load）**：单位时间**到达**的请求量。注意它 ≠ 用户发起量——重试会让到达量成倍于发起量；
- **goodput vs throughput**：throughput 是处理掉的请求量，goodput 是其中**对用户有用**的部分（在超时前返回、结果被用上）。过载时两者分道扬镳：系统忙得冒烟（throughput 高），但处理的全是已被客户端放弃的请求（goodput ≈ 0）；
- **背压（backpressure）**：下游把"我处理不过来"的信息传给上游、迫使上游降速的机制。名字来自流体管道：末端阀门关小，压力会沿管道逆流而上。

队列的关键直觉【事实】：延迟对利用率是**非线性**的。排队论给的定性结论：利用率 50% 时排队延迟很小；80% 时开始明显；95% 以上排队延迟急剧拉升并对负载波动极度敏感。配合 Little 定律：

$$
L = \lambda \cdot W
$$

在途请求数 L = 到达率 λ × 平均逗留时间 W。它反过来同样有用：**固定在途上限 L，就等于强制 λ 与 W 的乘积有界**——这就是"并发度限制"这种背压手段的数学依据。

工程推论【实践】：不要把系统规划在 90% 利用率上运行——那不是"还有 10% 余量"，而是"任何一点抖动都会把延迟推上天"。余量买的是延迟的稳定性。

## 2. 雪崩的解剖：重试放大与死工作

无保护系统从"满载"到"崩溃"的完整链条【事实】：

1. 到达负载略超容量（比如 110%），队列开始线性增长；
2. 排队时间超过客户端超时（比如 1 s），客户端开始重试；
3. 重试叠加在原有负载上：设每个失败请求重试 2 次，到达负载变成原来的约 3 倍——**超载 10% 被放大成超载 200%**；
4. 服务端仍在诚实地处理队列头部的请求——但它们排队太久，客户端早已放弃。处理完、结果无人认领，这就是**死工作（wasted work）**：消耗了 100% 的资源，goodput 趋近 0；
5. 更阴险的是**亚稳态（metastable failure）**【事实】：触发过载的原因（流量尖峰、慢盘）消失后，系统**不会自己恢复**——重试流量本身就足以维持过载。必须人工干预（封流量、重启）才能回到好的稳态。

重试放大的乘法【事实】：调用链有 3 层、每层失败后重试 3 次，最底层故障时它收到的请求最多放大 **3 × 3 × 3 = 27 倍**。层数越深，放大越猛——这是微服务/分布式存储比单体更容易雪崩的结构性原因。

## 3. 信号：怎么知道自己过载了

背压的第一步是**测得准**。候选信号从差到好【实现】：

| 信号 | 问题 |
| --- | --- |
| CPU 利用率 | 与用户可感知的延迟关系松散；IO 密集服务 CPU 不高也能过载 |
| 队列**长度** | 阈值难定：同样 1000 个请求，处理快时无害、处理慢时致命 |
| 队列**等待时间** | 直接对应用户感受，天然自适应处理速度的变化——首选信号 |
| 在途请求数（inflight） | 配合 Little 定律可推延迟；适合做硬上限 |
| 下游显式反馈 | 最准：下游返回"过载"错误码或建议退避时间，上游不用猜 |

首选**排队时间**的原因【事实】：它就是"这个请求还有多少延迟预算可烧"的直接度量。一个已经排了 900 ms 的请求（客户端超时 1 s）几乎注定超时——继续处理它就是制造死工作。

## 4. 机制：从入口到客户端的四层防线

### 4.1 入口准入（admission control）：有界队列 + 快速拒绝

第一原则【事实】：**队列必须有界**。无界队列不是在"接纳"负载，而是把过载转化为延迟和内存增长，最后以 OOM 或全员超时的形式爆发——它只是把崩溃推迟并放大。

有界之后的行为选择【实现】：

- **满则快速拒绝（fail fast）**：立刻返回"过载"错误。被拒的客户端拿到明确信号，可以退避或去别的副本；比让它排队 2 秒后超时好得多——**快速失败是有礼貌的行为，缓慢成功才是灾难**；
- **按排队时间丢弃（load shedding）**：出队时检查已排队时长，超过延迟预算的直接丢弃不处理——这些是注定的死工作，丢掉它们把资源留给还来得及的请求；
- **过载时切 LIFO**：FIFO 在过载时处理的是"最老、最接近超时"的请求；LIFO 优先处理最新请求，保住它们的时效。Facebook 生产采用"自适应 LIFO + CoDel 式队列超时"的组合【实现】：正常时 FIFO，过载时切 LIFO 并收紧排队时限。

分级准入【实现】：拒绝也要看身份——前台读写 > 元数据操作 > 重建/rebalance（[[7.17 Recovery 与 Rebuild]]）> scrub。过载时先掐后台内部客户，这是"降级"最自然的形态。

### 4.2 限流与自适应并发

- **令牌桶（token bucket）**：控制**速率**，允许短突发。适合对外的配额、对内的后台任务限速（[[6.16 Rate Limiter 与后台任务隔离]]）；
- **并发度限制**：控制**在途数**，配合 Little 定律间接控制延迟。上限可以自适应：延迟恶化就乘性收缩、平稳就加性增长——把 TCP 拥塞控制的 **AIMD** 思想搬到应用层（Netflix 的 concurrency-limits 库是现成实现【实现】）。

### 4.3 降级：主动少做事

过载时按价值排序砍工作【实现】：暂停 deep scrub → 压缩重建配额到保底值 → 关闭非关键统计/审计 → 读路径返回略旧的缓存数据（若一致性模型允许，[[7.9 一致性模型]]）。降级的关键是**预先设计好开关**，而不是事故现场临时改代码。

### 4.4 客户端配合：退避、预算与熔断

背压是双人舞，服务端拒绝、客户端要会退【实现】：

- **指数退避 + 抖动（exponential backoff + jitter）**：重试间隔 1s、2s、4s……并加随机抖动。没有抖动，一批同时失败的客户端会同步重试，形成周期性冲击波（thundering herd）；
- **重试预算（retry budget）**：限制重试流量占比（如重试 ≤ 正常请求的 10%）。预算耗尽就直接向上层报错。这是防止 27 倍放大的关键闸门——**逐请求限重试次数挡不住集体行为，预算限的是总量**【事实】；
- **熔断（circuit breaker）**：对某下游的失败率超阈值后，一段时间内不再发请求、直接本地失败，给下游喘息窗口；
- **超时预算传递（deadline propagation）**：入口定总预算（如 500 ms），逐跳扣减传递；预算耗尽的请求在任何一层都立即放弃——保证没有人为已死的请求打工。

端到端原则【事实】：**背压必须一直传到最外层的负载来源**（用户、上层服务、内部后台任务）。任何一层"好心吸收"压力（无界缓冲、无限重试）都会把自己变成下一个爆点——中间层的美德是诚实转发压力，不是硬扛。

## 5. 这就是 TCP 流控的应用层重演

学过网络的读者会觉得眼熟——完全正确【类比】：

| TCP 机制 | 分布式服务对应物 |
| --- | --- |
| 滑动窗口（接收方通告 rwnd） | 在途请求数上限 / 有界队列 |
| 拥塞控制 AIMD | 自适应并发度限制 |
| ECN（显式拥塞通知） | 下游返回"过载"错误码 / 建议退避 |
| RED / CoDel 主动队列管理 | 按排队时间主动丢请求（load shedding） |
| 超时重传 + 指数退避 | 客户端重试 + backoff |

差别在于【事实】：TCP 的流控保护的是**一条连接**的接收方；RPC 层的过载保护面对的是**多对多**的全局问题——单连接都守规矩，加总仍可能压垮共享的盘和网。所以应用层必须有自己的全局机制（准入、预算），不能指望传输层代劳。存储场景还有一个 TCP 管不到的死角：**RDMA/内核旁路路径绕开了内核协议栈的排队反馈**（[[4.13 RDMA 操作顺序性]]），背压更要在应用层显式做。

## 6. 存储系统的背压链：从客户端到盘

分布式存储的写路径把多级队列串成一条链，任何一级堵住，压力都应当逐级向上传【实现】：

```
客户端 → 接入层队列 → 主副本复制窗口 → 备副本日志 fsync → 存储引擎 memtable/compaction → 盘
```

三个存储特有的背压源【事实】：

1. **引擎级 write stall**：LSM 引擎 compaction 追不上写入时主动减速/停写（[[6.14 Write Stall]]）——这是引擎内建的背压，它把"盘不够快"翻译成"写变慢"，应当继续向上翻译成"接入层限流"，而不是在副本层无限攒队列；
2. **复制在途窗口**：leader 对慢 follower 的未确认日志有内存上限（[[7.11 Primary-Backup 与 Multi-Raft]] 第 7 节的 `FollowerProgress`），窗口满即停止向它发送——防止一个慢副本吃爆 leader 内存；
3. **内部客户**：重建、rebalance、scrub 是不请自来的大流量（[[7.17 Recovery 与 Rebuild]]），必须挂在与前台同一套准入/配额体系下，而且优先级更低——过载时第一个被掐。

慢节点的传染路径【事实】：一块慢盘 → 该节点上的副本确认变慢 → `W=N` 的副本组整组变慢（[[7.11 Primary-Backup 与 Multi-Raft]]）→ 客户端对这批分片超时重试 → 重试流量摊到全集群。**局部劣化通过重试变成全局过载**——这就是为什么过载保护是"分布式存储稳定性工程"的核心科目，也解释了为什么慢节点要及时检测并摘除（[[7.15 Membership 与故障检测]]）。

## 7. Modern C++：按排队时间准入 + 重试预算

服务端：有界队列，入队记时间戳，出队时超预算直接丢（load shedding 的最小实现）：

```cpp
#include <chrono>
#include <deque>
#include <mutex>
#include <optional>

template <typename Request>
class AdmissionQueue {
    using Clock = std::chrono::steady_clock;
    struct Item { Request req; Clock::time_point enqueued_at; };

public:
    AdmissionQueue(std::size_t max_depth, std::chrono::milliseconds queue_budget)
        : max_depth_{max_depth}, queue_budget_{queue_budget} {}

    // 入口准入：队列满 → 快速拒绝（调用方向客户端返回"过载"，而非默默排队）
    bool try_enqueue(Request req) {
        std::lock_guard lk{mu_};
        if (queue_.size() >= max_depth_) return false;
        queue_.push_back({std::move(req), Clock::now()});
        return true;
    }

    // 出队即 shedding：排队超预算的请求已注定超时，处理它只是制造死工作
    std::optional<Request> dequeue() {
        std::lock_guard lk{mu_};
        const auto now = Clock::now();
        while (!queue_.empty()) {
            Item item = std::move(queue_.front());
            queue_.pop_front();
            if (now - item.enqueued_at <= queue_budget_)
                return std::move(item.req);
            ++shed_count_;  // 丢弃计数：必须暴露成指标，静默丢弃排障时是黑洞
        }
        return std::nullopt;
    }

private:
    std::mutex mu_;
    std::deque<Item> queue_;
    const std::size_t max_depth_;
    const std::chrono::milliseconds queue_budget_;
    std::uint64_t shed_count_{0};
};
```

客户端：重试预算——按成功流量的固定比例挣预算，重试花预算，预算耗尽直接失败：

```cpp
#include <mutex>

class RetryBudget {
public:
    // ratio: 重试流量占正常流量的上限，如 0.1（10%）
    RetryBudget(double ratio, double burst) : ratio_{ratio}, tokens_{burst}, burst_{burst} {}

    void on_success() {
        std::lock_guard lk{mu_};
        tokens_ = std::min(tokens_ + ratio_, burst_);  // 每次成功挣 ratio 个重试额度
    }

    bool try_spend_retry() {
        std::lock_guard lk{mu_};
        if (tokens_ < 1.0) return false;  // 预算耗尽：放弃重试，向上层报错
        tokens_ -= 1.0;
        return true;
    }

private:
    std::mutex mu_;
    const double ratio_;
    double tokens_;
    const double burst_;
};
```

要点【实践】：`shed_count_`、拒绝数、预算耗尽数都必须导出成监控指标——过载保护生效时系统"看起来在报错"，没有指标佐证，值班人员的第一反应会是把保护关掉。

## 8. 排障清单：症状 → 原因 → 检查

| 症状 | 常见原因 | 检查动作 |
| --- | --- | --- |
| 负载尖峰过后系统迟迟不恢复 | 亚稳态：重试流量自维持过载 | 对比"客户端发起量"与"服务端到达量"的比值；临时封重试/降流量打破循环 |
| 内存缓慢上涨后 OOM | 某层无界队列在吸收压力 | 逐层盘点队列上限；找出"从不拒绝请求"的那一层 |
| 服务端满载但业务成功率≈0 | 死工作：处理的全是已超时请求 | 对比 throughput 与 goodput；确认出队侧有排队时间检查 |
| 故障时底层服务请求量暴增数倍 | 多层重试叠乘放大 | 数调用链层数与各层重试次数；引入重试预算与 deadline 传递 |
| 周期性同步流量尖刺 | 退避无抖动，客户端同步重试 | 检查 backoff 实现是否加 jitter |
| 一块慢盘拖垮全集群 p99 | 慢副本 → 组变慢 → 超时重试全局扩散 | 定位慢盘（[[9.2 iostat 指标解读]]）；确认慢节点摘除与副本组切换生效 |
| 开了限流反而报错更多 | 限流阈值低于实际容量，或按请求数限流而大小请求成本悬殊 | 用压测标定真实容量；按字节/成本记账而非按请求数 |
| 重建期间前台被打死 | 内部客户未纳入准入体系 | 确认 recovery/scrub 走同一套配额且优先级更低（[[7.17 Recovery 与 Rebuild]]） |

## 9. 陷阱与误区

> [!warning] 常见错误
> 1. **用无界队列"扛住"流量**：队列不生产容量，只把过载转成延迟+内存。所有队列必须有界，满了要么拒绝要么丢。
> 2. **把拒绝当成事故**：拒绝是保护生效的样子。目标不是零拒绝，而是"被接纳的请求都在预算内完成"。缓慢的成功比快速的失败对全局伤害大得多。
> 3. **重试当可靠性银弹**：无预算的重试是雪崩的燃料。重试只该用于瞬时故障，且受预算与退避约束；对"过载"错误的正确反应是退避，不是立刻再试。
> 4. **超时后放任请求继续执行**：客户端已放弃，服务端还在为它读盘算校验——纯死工作。deadline 要随请求传递，每层检查后决定是否继续。
> 5. **只在一层做保护**：只有入口网关限流，内部重建流量照样打死盘；只有服务端拒绝，客户端不退避照样风暴。背压是一条链，断在哪层哪层爆。
> 6. **按请求数而非成本记账**：1 KB 读和 16 MB 写在配额里等价，会让大请求穿透限流。配额记字节或标准化成本单位。
> 7. **压测只测到 100% 负载**：过载保护的验收标准是**150%、200% 负载下 goodput 保持平稳**，而不是 100% 时性能多好。不做过载压测，第一次验证就在生产事故里。

## 10. 关键结论

| 结论 | 性质 |
| --- | --- |
| 排队延迟对利用率非线性：高利用率下微小波动即引发延迟爆炸；容量余量买的是延迟稳定性 | 事实 |
| 无保护系统过载时 goodput 崩塌：资源被"已被客户端放弃的请求"耗尽（死工作） | 事实 |
| 重试是放大器：多层 × 多次呈乘性放大；亚稳态下重试流量可在诱因消失后自维持过载 | 事实 |
| 最好的过载信号是排队时间与在途数（Little 定律），其次是下游显式反馈；CPU 与队列长度都不可靠 | 实现 |
| 四层防线：有界队列+快速拒绝 → 限流/自适应并发 → 降级 → 客户端退避+重试预算+deadline 传递 | 实现 |
| 背压必须端到端传导到负载来源；任何一层默默吸收压力都会成为爆点 | 事实 |
| 分布式过载保护是 TCP 流控思想在应用层的重演，但要解决多对多的全局问题，传输层代劳不了 | 类比 / 事实 |
| 存储特有：write stall、复制窗口、重建流量三大背压源；慢盘经重试放大可演变为全局过载 | 事实 / 实践 |
| 保护机制必须带指标（拒绝数、丢弃数、预算耗尽数）并做超载压测，否则事故现场会被误关 | 实践结论 |
