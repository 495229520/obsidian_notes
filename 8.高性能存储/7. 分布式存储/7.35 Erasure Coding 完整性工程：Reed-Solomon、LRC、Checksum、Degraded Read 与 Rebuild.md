# Erasure Coding 完整性工程：Reed-Solomon、LRC、Checksum、Degraded Read 与 Rebuild

> **EC 解码器解决“已知哪些位置缺失以后，怎样从剩余方程恢复字节”，不自动解决“谁在返回错误字节”。** 生产恢复链必须是：确定对象与版本 → 验证候选分片 → 排除坏片 → 判断可解码 → 重构 → 对照可信期望值复验 → 持久化 → 受控发布。少掉一个环节，都可能把冗余变成错误传播器。

[[7.1 副本 vs EC]] 已建立空间、读写和修复成本的总体模型。本篇沿 [[7.17 Recovery 与 Rebuild]] 进入实际恢复路径，并以前一篇 [[7.34 故障模型扩展：Crash Fault、Omission、Corruption、Byzantine 与 Silent Data Corruption]] 的“检测、隔离与可信来源”为前提。

> [!info] 范围与符号约定
> 本篇以**系统码形式的 Reed–Solomon（RS）擦除恢复**为基线，记 `RS(k,m)` 为 `k` 个数据分片加 `m` 个冗余分片，`n=k+m`；有的资料把 RS 写成 `(n,k)`，不要直接套数字。LRC 使用单独的 `LRC(k,ℓ,g)`，分别表示数据片、局部校验片、全局校验片。所有带宽数字都是明确假设下的算例，不是生产测量。标准原理依据 RFC 5510 与编码理论讲义；LRC 对照 Azure Storage 原论文；产品行为固定对照 **Ceph Squid** 文档。资料查阅于 2026-09-16。[^rs][^coding][^lrc][^ceph-ec]

## 1. 把总体模型的前提补齐

进入公式前，先限制四句经常被过度使用的话。

| 简写 | 本篇采用的精确定义 |
| --- | --- |
| “任意 k 片可恢复” | RS/MDS 编码中，同一编码实例、同一版本、不同位置且内容正确的任意 k 片；不适用于所有 LRC |
| “容忍 m 个故障域” | 要先由放置规则证明，这些故障域合计不会移除超过容错范围的片 |
| “还有 k 片，所以服务正常” | 数学上可恢复不等于元数据可访问、读策略允许、写入能确认或性能达标 |
| “恢复一片需要读 k 片” | 本篇基线是传统整分片 RS 解码，不是所有局部修复码、再生码或子分包优化的下界 |

这些限定不是削弱 EC，而是把选型公式变成可执行的恢复条件。

## 2. Stripe、Shard、Symbol：三个粒度不能混用

【本篇布局】一个逻辑对象被划分为多个 stripe。每个 stripe 含 `k` 个数据 shard，编码后生成 `m` 个 parity shard。每片有效编码长度为 `S` 字节；末条带需要 padding 时，真实逻辑长度另存于元数据。

$$
\text{逻辑容量}=kS,\qquad
\text{编码后容量}=(k+m)S,\qquad
A_{space}=\frac{k+m}{k}.
$$

对 `RS(8,3)`、`S=4 MiB`：一个 stripe 表示 `32 MiB` 逻辑数据，编码数据为 `44 MiB`，理论空间倍率为 `1.375×`。校验元数据、对象头、padding、对齐与分配开销不包含在这个数中。

**Symbol 是代数粒度。** 例如 GF(2⁸) 下可将每个字节看作一个域元素：在同一字节偏移处，把各数据片的元素组合成校验元素。整个 shard 是许多这样的编码位置的集合，不是“一个 4 MiB 的大整数”。RFC 5510 对 source symbol、repair symbol、systematic code 与生成矩阵有明确区分。[^rs]

**Checksum block 是验证粒度。** 它可以是 4 KiB、64 KiB 或其他大小，不必等于 shard。参数必须来自实际格式；不能把某产品一个例子的 block 大小说成 EC 的标准。

## 3. RS 为什么能恢复：从足够多的独立方程开始

### 3.1 系统码形式：数据片本身无需解码

以列向量为约定，设一个编码位置上的数据为 `d∈GF(q)^k`，完整编码向量为 `c∈GF(q)^n`：

$$
c=Gd,\qquad
G=\begin{bmatrix}I_k\\P\end{bmatrix}.
$$

前 `k` 行是单位矩阵，因此对应的 `k` 个编码元素就是原始数据。`P` 的行是校验方程。这里的列向量写法与 RFC 5510 的行向量写法互为转置，并不表示两种不同编码。[^rs]

对 RS/MDS 编码，选取任意 `k` 个不同且正确的位置形成集合 `A`，其生成子矩阵 `G_A` 可逆，于是：

$$
d=G_A^{-1}c_A.
$$

要重建一个数据片，只需求目标所需的行组合；要重建 parity，则从已恢复的数据或等价解码关系重新编码。输入集合不变时，可复用解码矩阵；但矩阵缓存键必须包含 codec 参数、分片身份与可用位置集合，而不是只记“缺了两片”。

### 3.2 一个可手算的有限域例子

【教学构造，不是生产 codec】采用素数域 GF(17)，两个数据元素为 `D0=5, D1=9`，定义：

$$
P0=D0+D1\pmod {17}=14,\qquad
P1=D0+2D1\pmod {17}=6.
$$

其生成矩阵四行为 `(1,0)`、`(0,1)`、`(1,1)`、`(1,2)`，任意两行在 GF(17) 下独立。如果两个数据位置都缺失，只剩 `P0=14, P1=6`：

$$
D1=P1-P0=6-14\equiv9\pmod {17},\qquad
D0=P0-D1=14-9=5.
$$

这个例子展示“冗余是额外方程”，不是“把数据复制成某种神秘形式”。实际字节级实现常使用 GF(2⁸) 等扩域，其加法是 XOR，乘法按选定域多项式进行；**不能把 `% 256` 当作 GF(2⁸) 乘法**。

### 3.3 独立方程还需要正确输入

仍用该算例：`D0` 缺失，错误的 `D1=10` 被当成正确值，`P0=14` 仍正确。解码会给出 `D0=4`。此时 `(4,10)` 恰好满足这条 parity 方程，**“方程解出来了”不能证明它是原来的 `(5,9)`**。

如果只拿这两个输入重新编码，再检查自己新生成的校验，得到的是一个自洽的新码字。需要额外的可信期望摘要或足够的独立编码约束，才能发现偏差；不要用“新算出来的 checksum 等于新算出来的 checksum”充当验收。

## 4. Erasure 与 Error：先定位坏片为什么如此重要

### 4.1 已知缺失：每个位置消耗一份擦除预算

对 `RS(k,m)`，最多 `m` 个已知位置不可用时仍可由剩余正确元素恢复。不存在的数据、读取明确失败的数据、身份不符的数据、被可信 checksum 检出的坏数据，都可以从本次候选集合排除。它们的物理成因不同，但对**这次擦除解码**都表现为不可用输入。

此处“坏片变缺片”有前提：校验器和期望值可信，拒绝发生在解码前，排除的位置正确，未排除的输入仍满足模型。若节点能同时篡改数据和期望值，转换没有完成。

### 4.2 未知错误：定位与恢复一起消耗距离预算

RS/MDS 的最小距离为 `d_min=n-k+1=m+1`。对于支持相应纠错能力的解码算法，要保证唯一恢复任意 `e` 个未知位置错误加 `s` 个已知擦除，经典条件为：

$$
2e+s<d_{min},\quad\text{即}\quad 2e+s\le m.
$$

【推导】删去 `s` 个已知擦除位置，最小距离至少剩 `d_min−s`；要让两个半径为 `e` 的错误球不相交，需要 `2e<d_min−s`。MDS 的距离关系由 Singleton 界取得等号得到。[^coding]

这不是说“校验失败一次等于损失两个 parity”。**已经定位的损坏算 erasure，一份预算；未定位的错误才进入 `e`。** 同时，常见存储擦除解码 API 只接收 missing-index 列表，并不自动实现未知错误的纠正。数学上允许纠错，不等于当前库能够发现或纠正它。

| RS(8,3) 情况 | 预算 | 结论 |
| --- | --- | --- |
| 3 个明确不可用位置，其余正确 | `s=3` | 可进行擦除恢复 |
| 1 个未知错误 + 1 个擦除 | `2×1+1=3` | 对具备相应能力的纠错解码器，处于唯一恢复界内 |
| 1 个未知错误 + 2 个擦除 | `2×1+2=4` | 超出保证边界 |
| 上一行的错误被可信校验定位 | `e=0,s=3` | 转为擦除恢复，仍在边界内 |
| 4 个明确不可用位置 | `s=4` | 普通 RS(8,3) 不保证从剩余 7 片恢复全部数据 |

这些数量严格对应**同一编码位置/恢复单元**。三个不同 shard 的不同偏移各坏一小块，不一定等于每个编码位置都有三处错误；把整个 shard 全部隔离是一种可能更保守的实现选择。

## 5. 完整性元数据：重构需要一份不可随意自报的“标准答案”

### 5.1 一条可审计的分片身份

【工程设计】逻辑上应能够恢复以下关系；它们不必全部塞进每个物理块头：

| 字段或映射 | 防止的错误 |
| --- | --- |
| object / tenant / namespace | 返回了别人的对象，或跨租户错配 |
| immutable generation / version | 旧片与新片混用，或旧对象重放 |
| stripe_id、shard_index、data/parity role | 块身份或编码行错位 |
| offset、encoded_length、logical_length | Range 错位、截短、padding 误解释 |
| codec_id、field/matrix/layout version、k/m | 用错误矩阵或错误布局解释数据 |
| per-range / per-shard digest | 验证实际参与计算的字节 |
| manifest commitment / root | 验证期望值的来源及归属 |

如果叶子摘要只覆盖 payload，身份必须由可信映射绑定；另一种做法是用有域分隔、长度编码与确定字节序的规范化格式一起覆盖头和 payload。不要直接 hash C++ 结构体内存，因为 padding、字节序和布局版本可能改变。

### 5.2 Data 与 parity 都要验证

数据片用于正常读；parity 片可能长期只在恢复时被读。正常读持续成功，不代表冷 parity 仍完好。恢复前必须验证每个实际使用的输入，包括 parity。

对重构输出，还应与该版本原本的目标摘要或可信整体承诺比较。**“写入时给重建片生成了一个新的 CRC”只保护从该时刻以后的变化，不能追认重建算法输入一定正确。** 可信 manifest 可以保存各 shard 的期望摘要，或保存支持目标范围验证的树形承诺；具体格式由系统设计决定。

### 5.3 期望值也必须可恢复、可认证、可判版本

若数据 shard 分散在十一个节点，但唯一 manifest 丢失，系统可能保有足够字节，却不知道哪种参数、顺序或版本有效。元数据副本、提交记录、备份以及可信根同样需要可靠性设计。这与 [[7.20 元数据服务高可用]] 的数据/控制路径分工相接。

面对主动不可信节点时，可将摘要承诺放在客户端、受保护控制面或有适当认证的元数据中；面对随机损坏时，也要避免数据及唯一摘要落入同一容易共同损坏的区域。信任依据不同，方案不同，不能用“都在一个 JSON 里”代替威胁模型。

## 6. LRC：减少常见修复的参与者，不是免费增加 MDS 容错

### 6.1 明确一个具体布局，而不是泛讲“LRC 更快”

以 Azure 论文的 `LRC(6,2,2)` 结构为例：数据分成 `D0,D1,D2` 与 `D3,D4,D5` 两组，各有一个 local parity `L0,L1`，另有覆盖六片数据的 global parity `G0,G1`。本文统一重新编号，避免不同资料的 x/y 下标混淆。[^lrc]

在这个局部 XOR 结构中：

$$
L0=D0\oplus D1\oplus D2,\qquad
L1=D3\oplus D4\oplus D5.
$$

若只有 `D0` 不可用，可以读取 `D1,D2,L0` 三个 helper 重建；传统整片 `RS(6,3)` 基线需要六个 helper。局部修复的是“一个故障位置”，却读取三个 helper，不是“只读一个校验块就恢复整组”。

![[图片/SVG/8_7_7_35_2.svg|900]]

**读图要点：**上半展示单数据片的局部恢复路径；下半在同一布局中移除整组数据及其 local parity，说明剩余片数足够也可能缺少独立信息。

### 6.2 一个四片丢失、却不能恢复的反例

【按上述布局推导】假设缺失 `D0,D1,D2,L0`。仍存在 `D3,D4,D5,L1,G0,G1`，数量正好为 6。但 `L1` 只约束已知的第二组数据；对第一组三个未知量，只有 `G0,G1` 两个全局方程。最多两个独立方程，不足以唯一确定三个未知数。

所以 **n−k=4 个冗余片，不代表任意 4 片丢失都可恢复**。论文给出的特定 LRC 构造能容忍任意 3 片故障，以及一部分 4 片故障；具体可恢复性取决于布局和系数。不要把这个结论扩展到所有冠名 LRC 的实现。[^lrc]

### 6.3 选型应比较三条轴

| 本篇指定编码 | 片总数 / 理论空间倍率 | 最坏模式下保证的擦除数 | 单个数据片传统整片恢复读量 |
| --- | --- | --- | --- |
| RS(6,3) | `9 / 1.5×` | 任意 3 | `6S` |
| RS(6,4) | `10 / 1.667×` | 任意 4 | `6S` |
| 指定 LRC(6,2,2) | `10 / 1.667×` | 任意 3；部分 4 | 局部条件满足时 `3S` |

表中的数值由指定布局计算；没有将不同故障模式或局部修复算法混为同一统计量。局部组同时缺多片、local parity 不可用、缺失的是 global parity 时，应调用该编码的可解码性判定与全局路径，而不是始终按 `3S` 预算。

### 6.4 Ceph 的 LRC 参数不能机械照搬论文

Ceph Squid 的 `lrc` 插件文档使用自己的 `k/m/l` 参数和分层编码描述；其中 `l` 表示 locality，不能直接当作本文 `ℓ` 的“局部校验片数量”。其文档还说明如何通过局部组减少读取其他 OSD 的数量。[^ceph-lrc]

放置策略进一步决定节省的是总 helper 读量、跨主机流量，还是跨机架流量。将局部组放近可能减少跨机架通信，但整机架失效会同时移除组内多片；要把机架故障映射成实际消失的编码行，再检查可解码性。[[7.16 数据放置与 Rebalance]] 中的故障域不能被“local”一词自动满足。

## 7. 正常读与 Degraded Read：先验证，后决定需要多少片

### 7.1 正常读的快速路径

对系统码 RS，若请求范围对应的数据 shard 可访问且验证通过，可以直接返回，不必每次读取全部 parity，也不必为一次小读重构整个对象。前提是映射、generation 与范围完整性可验证。

副本系统在节点失败时也会经历降级、负载转移与尾延迟变化；EC 的特征不是“唯有 EC 会降级”，而是某些数据片不可用时引入了**多 helper 读与解码计算**。

### 7.2 Degraded Read 的三个门

【工程设计】第一道是**身份与版本门**：固定本次读取允许的 manifest/generation，拒绝其他对象或其他编码位置。第二道是**输入完整性门**：读取的字节通过可信的范围校验才计入 usable 集合。第三道是**重构输出门**：解码结果匹配目标期望值，才返回客户端。

![[图片/SVG/8_7_7_35_3.svg|900]]

图中是一个读请求的逻辑时序，不表示每个方框必须是独立线程；实际 RPC 与多个 helper 可以并发。客户端等待的是**足够的合格输入与最终验证**，不是“最先返回的 k 个 TCP 响应”。

对于 RS，应选择 `k` 个不同且正确的编码位置；对于 LRC，应让恢复计划满足当前方程结构，不能只检查 `usable.size() >= k`。返回重复 shard ID 的两个节点不是两个独立方程。

### 7.3 超时、坏片与慢片不能混成一个永久状态

超时的 helper 对当前请求可以暂时不使用，但超时并不证明其磁盘数据损坏。校验失败才是该范围内容不可信的直接证据之一。调度器可给慢片发起替代读；迟到结果到达时仍需检查请求 generation 与生命周期，不能悄悄进入已经完成的解码任务。

【策略取舍】并行读取超过 `k` 个候选，选择最先满足条件的集合，可能减轻 straggler 对延迟的影响，但会增加读流量和在途内存。取消 RPC 也不保证远端已经停止磁盘 I/O。对冲次数和预算要与 [[7.18 Backpressure 与过载保护]] 联动，而不是每次超时都无限扩散。

## 8. 读放大还取决于校验粒度，不只取决于 k

假设某次请求需要不可用数据片里的 `R` 字节。在编码与校验都支持相同范围恢复时，传统 RS 至少可按该范围向 `k` 个 helper 请求对应字节，不必机械读取 `k` 个完整 shard。

如果校验 block 大小为 `B`，且每个 helper 需要读取覆盖该范围的完整校验块，对于分片内偏移 `o`，所需校验区间长度为：

$$
V=B\left\lceil\frac{(o\bmod B)+R}{B}\right\rceil.
$$

【算例前提】`R=4 KiB`，请求落在一个 `B=64 KiB` 校验块内，`k=8`；无缓存命中、无额外对齐与其他 I/O。helper 总读取为 `8×64 KiB=512 KiB`，对逻辑请求的读放大为 `128×`。不是常见的 `8×`，因为这里分母是 **4 KiB 的用户 Range**。

若请求跨两个校验块，`V` 变为 `128 KiB`；若有更细粒度可信摘要或树形证明，验证范围可以不同。仅说“EC 的读放大是 k”会掩盖小 Range 的真实代价。

同理，压缩与加密改变可独立解码/验证的粒度。对整块压缩帧或整块认证加密结果做一个 tiny Range，不保证能仅取同等大小的编码范围。必须明确 EC 编的是明文、压缩结果还是密文，以及对应的完整性边界；本篇不指定唯一流水线。

## 9. Reconstruction 与 Rebuild：算出字节，不等于恢复冗余

**Reconstruction** 是计算过程：从可用输入得到所需片或所需范围。它可以只服务这次降级读，结果暂存在内存。

**Rebuild / Repair** 是系统过程：选择目标、读取与重构、校验、持久化、更新映射，并让冗余度真正恢复。一次降级读成功，不代表后台已经补好缺片；如果没有写回，下一次读仍可能再次承担重构成本。

### 9.1 修复状态不是一个“完成百分比”

【工程设计】可使用以下状态区分不同保证：

| 状态 | 已经得到的证据 | 还不能宣称的事 |
| --- | --- | --- |
| Detected / Suspect | 存在不可用片或异常信号 | 尚未判定所有来源健康 |
| Planned | 固定 generation、输入位置与目标放置 | 还没有可用输出 |
| Reconstructed | 已计算候选字节 | 候选必然正确或已持久 |
| Verified | 与可信期望内容匹配 | 断电后仍在，或映射已接管 |
| Durable | 数据与必要元数据满足持久化契约 | 并发版本/拓扑仍允许发布 |
| Published | 条件发布成功，路由与冗余记录生效 | 永远不会再次损坏 |

### 9.2 一条保守但可审计的修复提交链

【设计流程】读取可信 manifest 并固定 `(object,generation,stripe,layout_epoch)`；收集合格 helper；解码到新的临时位置；将输出与该 generation 的期望摘要比较；写入目标且满足文件系统/对象存储所承诺的持久化屏障；必要时执行规定粒度的回读校验；最后以条件更新方式发布映射。

条件发布至少检查内容 generation 未变、当前放置/成员配置仍接受该目标，以及本次任务仍持有有效修复权限。若发布失败，候选数据保持未发布状态，按策略重试或回收，**不能把旧修复结果直接标成新版本的健康片**。这与 [[7.12 Lease 与 Fencing]] 中“旧执行者不能越权写入”的问题同源。

**内容 generation 与 placement epoch 不要混用。** 移动同一不可变内容通常不改变其内容身份；只改变放置位置或版本的元数据。覆盖式用户更新则产生新内容版本，旧条带的修复必须继续按旧版本隔离。

### 9.3 Crash、并发写与部分覆盖

在持久化之前崩溃，重启后不能仅看见文件名就标记完成；持久化之后、发布之前崩溃，应能识别未发布候选；发布之后崩溃，恢复入口必须能指向已经满足持久化契约的数据。旧位置的回收应晚于新映射的可靠接管与相关读者生命周期结束。

EC 不意味着只能永远整对象写。Ceph Squid 文档明确描述了基于 BlueStore 的 EC 部分写支持，并把校验与 deep scrub 联系起来。[^ceph-ec] 不可变对象/COW 是降低并发恢复复杂度的一条设计路线，不是所有 EC 系统的唯一实现。原地更新则需要额外解决数据与 parity 的版本一致性、写洞及恢复事务边界。

## 10. Repair Amplification：先选分母，再算流量

### 10.1 传统 RS 整片修复的基线账

令需要恢复的一个缺失 shard 大小为 `S`，从 `k` 个 helper 各读 `S`，生成一个输出写入目标；忽略校验元数据、重试、压缩和缓存：

$$
R_{src}=kS,\quad W_{dst}=S,\quad
A_{read}=\frac{R_{src}}{S}=k,\quad
A_{rw}=\frac{R_{src}+W_{dst}}{S}=k+1.
$$

“修复读放大 8×”与“修复读写总量 9×”可以同时正确，因为口径不同。

| 计量位置 | 传统单片修复基线 | 容易漏掉的条件 |
| --- | --- | --- |
| helper 逻辑读取总量 | `kS` | 是否整片、是否缓存命中 |
| 目标逻辑写入 | `S` | 是否额外回读、底层写放大 |
| 解码器设在目标节点时的应用传输 | 远端 helper → 目标，最多按本例 `kS` 计 | 本地 helper 不经过网络；目标写盘不是网络包 |
| 解码器另设且所有 helper/目标均远端 | `kS` 输入加 `S` 输出 | 拓扑或共置可改变网络账 |
| 网卡收发计数之和 | 可能把同一传输算两端 | 不要与单向应用传输字节混用 |
| 交换网络 link-bytes | 同一字节经过多跳会累计 | 跨机架瓶颈需按具体链路重算 |

![[图片/SVG/8_7_7_35_4.svg|900]]

**读图要点：**上半将源读量与目标写量分开；下半展示临时结果变为已发布冗余的顺序。图中的 `9×` 是读写总字节，不自动等于跨机架网络流量。

### 10.2 RS(8,3) 修复 8 TiB：用吞吐下界检查承诺

【算例】某个故障节点上需重建的编码分片合计 `D=8 TiB`；每条带只重建其中一片，仍有足够正确 helper，采用传统整片 RS，忽略额外开销：

- helper 总读取：`8D=64 TiB`。
- 目标总写入：`D=8 TiB`。
- 逻辑读写总量：`72 TiB`。

若分配给恢复的**目标有效写入/产出速率**为 `400 MiB/s`，仅目标这一约束就给出：

$$
T\ge\frac{8\times2^{20}\ MiB}{400\ MiB/s}
=20971.52\ s\approx5.83\ h.
$$

要兑现该产出，helper 聚合读取必须持续提供约 `3200 MiB/s`，解码路径也要支撑对应吞吐。假设 helper 聚合预算实际只有 `1 GiB/s`，则源读约束变为：

$$
T\ge\frac{64\ TiB}{1\ GiB/s}
=65536\ s\approx18.20\ h.
$$

因此不能只用“坏盘容量 ÷ 目标盘写速率”许诺恢复时间。排队、前台竞争、网络扇入、解码 CPU、校验、额外回读与发布都会进一步增加时间。

### 10.3 同一条带多片同时修复：不要重复读同一组 helper

【基线优化推导】同一条带缺 `q≤m` 片且剩余满足条件时，统一解码可读取一组 `k` 个 helper，生成 `q` 个输出：

$$
R=kS,\quad W=qS,\quad
A_{read,target}=\frac{k}{q},\quad
A_{rw,target}=\frac{k+q}{q}.
$$

逐片独立修复可能读到 `qkS`。统一修复省掉重复读，但要增加在途输出、调度协调与失败处理复杂度；不同条带无法因为恰好同机故障就凭空共享输入。这也不是再生码意义上的通用最优下界。

## 11. Scrubbing：把潜伏错误的发现时间纳入可靠性

前台只读热数据时，冷数据与 parity 的损坏可能长期不被触发。Scrubbing 的作用是主动读取并验证存量数据，而不是仅巡检进程心跳。验证应覆盖 data/parity、身份与版本映射，以及验证所依赖的元数据。

【工程设计】对每个对象或条带保留：最后成功覆盖的范围与时间、当前不可用位置、可信可恢复性、修复队列状态，以及已完成发布的冗余度。全量扫描、抽样校验与分层扫描可以组合，但“抽样这次没发现”不能替代“全体数据已通过验证”。

可以把风险暴露时间拆成：

$$
T_{exposure}=T_{detect}+T_{queue}+T_{read/decode/write}+T_{verify/publish}.
$$

这是阶段时间的记账式，不是数据丢失概率公式。对“立即被察觉的宕机”和“数周后 scrub 才发现的坏片”，`T_detect` 可能完全不同。只优化重建 CPU，可能对最长的潜伏窗口没有帮助。

### 11.1 修复源必须先过校验，不能用修复掩盖分歧

遇到两个自报校验都正确、但版本或摘要冲突的候选，先回到权威 manifest 与历史判断；不要随便挑一个同步到全体。否则 scrub 本来应该发现问题，却变成传播错误的后台任务。

即使只坏一小块，整片重写也会增加 I/O；如果格式支持按验证单元恢复，能否只修坏范围应由编码位置、持久化原子性与摘要结构共同决定，而不只是追求较小写量。

### 11.2 Scrub 速率与恢复产出速率要分开计量

【算例】`RS(8,3)` 的 `1 PiB` 逻辑数据，对应理想编码 payload 为 `1.375 PiB`。若要在 30 天内完整读取这些 payload 一遍，忽略元数据、重读与开销，平均总扫描读取至少约为：

$$
\frac{1.375\times2^{30}\ MiB}{30\times86400\ s}
\approx569.60\ MiB/s.
$$

这个聚合平均值不保证每块盘、每个机架都能完成周期，也不包含扫描发现错误后产生的 repair 流量。应同时记录周期覆盖率与最久未校验范围，而非只看全局平均带宽。

## 12. 调度、背压与故障域：生产恢复的三个预算

### 12.1 剩余容错预算

对本篇 RS 基线，若某条带已有 `s` 个明确不可用位置，且其余已验证正确，可暂记剩余擦除余量为 `m−s`。该指标不覆盖潜伏未检出的错误。LRC 则应使用具体失效模式与可解码性判定，不能只写 `冗余片总数−坏片数`。

对同样的等待时长，已经接近不可恢复边界的条带通常应得到更高修复优先级。但调度要同时限制热盘、慢盘、网络和目标节点压力，避免优先级机制导致所有高风险任务互相拖死。

### 12.2 修复队列稳定性预算

令 `λ` 为新出现的待修复目标字节速率，`μ` 为在同一口径下实际完成验证与发布的目标字节速率。长期平均 `μ≤λ` 意味着队列无法收敛；只增加“下载并解码出来”的字节计数，不能证明冗余恢复速度足够。

要限制每盘读取、每节点扇入、每机架跨域带宽、解码任务并发数、内存字节和未发布写入数。故障期对前台 P99 的影响需要与任务队列共同观察，不能把全部 I/O 交给 repair 后再依靠超时重试维持业务。

### 12.3 放置与相关故障预算

假设 `RS(8,3)` 的 11 片散在 11 台主机，但某机架恰好容纳其中 4 片。丢一台主机是丢 1 片；丢这个机架是丢 4 片，已经超出任意擦除保证。**“每片不同主机”不能推出“任意机架失效安全”。**

对 LRC，局部组有意共置时更要逐模式检查。还应考虑共享电源、控制器、固件批次与软件缺陷等相关性。AFR 的独立故障近似、修复速率和数据丢失概率不能被简单压成“冗余数乘修复速度”。可靠性模型需要明确假设，而可恢复性首先需要实际布局。

## 13. 写入确认条件：读得出来不代表可以安全承诺新写

【受限推导】对一个新的不可变 RS 条带，若系统宣称“写入确认后，即使再任意丢失 `f` 个已落盘 shard，仍可恢复”，那么在仅按独立 shard 计数、且所有已确认内容正确的前提下，确认时至少需要 `k+f` 个持久片。仅 `k` 个已确认片没有额外擦除余量。

这只是必要的数据片数量条件，不是完整写协议。还要保证 manifest 提交、对象可见性、放置故障域、并发更新与确认语义。对于 LRC，应检查允许发生的每种故障模式是否仍满秩，而不是套 `k+f` 就结束。

Ceph Squid 文档也把 EC 数学恢复与 `min_size` 等运行条件分开讨论。[^ceph-ec] 真实系统可能为安全而在“仍有 k 片”时停止某些 I/O；不要为追求表面可用性，直接把生产阈值调到最低。

## 14. 完整故障案例：两片掉线，一片损坏

【构造场景】不可变 checkpoint 的某条 `RS(8,3)` stripe，generation=42。`D1,D4` 所在节点不可达，`P1` 的某校验块已经损坏；其余 8 个位置对目标范围正确，manifest 与期望摘要可信。需要读取的范围位于 `D1`。

**错误路径：**把最先返回的八个响应直接作为输入，其中混入坏 `P1`。擦除解码器可能输出错误结果；随后给结果重算新 CRC、覆盖目标，再宣布修复完成，会把损坏扩散到新片。

**正确路径：**先以 manifest 固定 generation 与范围，排除两个暂不可达位置；验证候选后将 `P1` 的坏范围排除。此时该恢复单元的 `s=3=m`，剩下恰好八个合格位置，进行 RS 擦除恢复。输出通过目标期望摘要后可以完成本次 Range 读；后台任务继续按持久化与条件发布流程补回冗余。

**再坏一片时：**在修复尚未可靠发布的窗口内，若另一个必要位置永久丢失，全部数据恢复保证不再成立。停止返回未经验证的重构值，并区分临时不可达、可等待恢复的来源，以及确实永久丢失。不能仅凭一次读取超时就宣布对象永久丢失。

**manifest 不可信时：**即使八片字节都存在，也不能把本例继续当作有可信期望值的恢复；必须先恢复或重新建立元数据依据。这正是上一篇故障模型的边界。

## 15. 最小实验闭环：把“解码成功”升级为“恢复正确”

不需要一开始部署大集群。先用文件模拟 shard、独立文件保存可信 manifest 与原始输入，明确这只是逻辑恢复实验，不模拟真实持久化硬件。随后再把网络、落盘与故障域加入。

### 15.1 编码与解码测试

对指定 `RS(8,3)` 实现，在固定的一组测试数据上枚举 `0…3` 个擦除位置，共：

$$
\sum_{i=0}^{3}\binom{11}{i}=1+11+55+165=232
$$

种模式。每种恢复都与独立原始输入比较，而不是只检查库返回码。更换数据种子、大小、末条带长度、codec 参数和 SIMD/标量路径；232 个位置模式覆盖不代表已覆盖所有数据与实现行为。

对 LRC，验证指定布局下可恢复与不可恢复的模式，至少包含 `D0,D1,D2,L0` 的反例。若库返回成功却与 oracle 不同，实验失败；若模式本来不可恢复而被清楚拒绝，则是正确行为。

### 15.2 完整性与恢复发布测试

| 故障注入 | 必须验证的性质 |
| --- | --- |
| 一个 data 或 parity 的单 bit flip | 使用前检出，坏输入不进入 decode |
| 读取两个节点上相同 shard ID | 不能充当两个独立输入 |
| 将 generation=41 的完整合法片混入 42 | 即使本地 checksum 正确也必须拒绝 |
| 交换 stripe/shard header 或 Range offset | 身份与长度契约拒绝错配 |
| 数据与自带 hash 一起替换 | 独立可信 manifest 仍能拒绝 |
| 恢复结果输出缓冲区被修改 | 返回/持久化前的契约检查或不可变机制阻止 |
| 编码器/解码器同一错误实现 | 独立 oracle 检出，不能只做自我往返 |
| 重建完成但尚未持久化时崩溃 | 不能标健康，恢复后正确处理临时结果 |
| 已持久化但尚未发布时崩溃 | 候选可重用或回收，不成为无条件当前版本 |
| 修复中发生用户更新或 rebalance | 旧 generation / epoch 的任务不能越权发布 |
| 源片在第二次读取时改变 | 重新验证实际参与解码的字节，避免检查/使用竞争 |
| 少于所需独立有效输入 | 显式拒绝，不返回部分拼接对象 |

### 15.3 Benchmark 不只测 encode GB/s

【实验矩阵】变化维度至少包含 `k/m`、shard 大小、checksum block、请求 Range、失效位置/数量、cache 命中、helper 延迟分布、目标共置与否，以及 repair 与前台并发比例。

输出至少包含：正常读与降级读的 P50/P99；校验、解码与排队分别耗时；helper 逻辑读量；目标写入与验证回读量；应用传输字节及跨机架流量；最终发布的修复吞吐；峰值在途内存；最旧未 scrub 范围与修复窗口。

把测量值和理论 `kS` 基线放在同一份记录里。实际更大时，沿对齐、校验粒度、重复读、对冲、底层写放大、重试和拓扑逐项解释；实际更小时，确认是否有缓存、局部读取或其他编码优化，而不是先判定实现不正确。

## 16. 自检：五个必须能解释的边界

**“RS 能纠错，所以不需要 checksum？”** 不成立。未知错误与已知擦除的预算不同，存储库可能只做擦除解码；输出还必须绑定正确对象和版本。Parity 不是密码学认证。

**“有四个 parity 的 LRC，一定能坏四片？”** 不成立。要看局部/全局方程与系数；本篇明确给出了四片缺失却秩不足的结构反例。

**“修复 8 TiB，只需要写 8 TiB？”** 目标逻辑写入是这个数；传统 RS(8,3) 单片恢复还需要约 64 TiB helper 读取，另有实际校验、网络、读回和介质开销。分母与计量位置必须一起说。

**“Degraded Read 成功意味着对象已修好？”** 不成立。内存中的范围重构可能只服务本次请求；必须完成持久化与有效映射发布，冗余才真正补回。

**“最快的修复是不是占满所有带宽？”** 不一定。可能把前台、其他高风险条带和 helper 队列一起拖垮。要以最终安全发布的修复产出、剩余容错风险和前台 SLO 联合调度。

> [!important] 本篇的工程闭环
> **可信身份与版本 → 验证有效输入 → 检查可解码性 → 重构 → 对照期望值复验 → 持久化 → 条件发布 → 持续 scrub。** RS/LRC 决定方程结构，Checksum 决定输入能否信任，恢复协议决定何时可以宣告“已恢复”。

[^coding]: Venkatesan Guruswami. *Introduction to Coding Theory*, CMU Spring 2010, “Notes 4: Elementary bounds on codes”, §1 “Singleton bound”。用于 MDS 的 `d_min=n−k+1`；本文的 `2e+s<d_min` 由剩余距离与唯一解码条件推导。[作者讲义](https://www.cs.cmu.edu/~venkatg/teaching/codingtheory/notes/notes4.pdf)。
[^lrc]: Cheng Huang, Huseyin Simitci, Yikang Xu, Aaron Ogus, Brad Calder, Parikshit Gopalan, Jin Li, Sergey Yekhanin. *Erasure Coding in Windows Azure Storage*, USENIX ATC 2012, §2.1–2.2，Figures 1–2。本文只用其 `(6,2,2)` 结构及对应保证作为特定案例，并独立推导容量与秩不足反例；不是对所有 LRC 的统一定义。[原论文](https://www.usenix.org/system/files/conference/atc12/atc12-final181_0.pdf)。
[^ceph-ec]: Ceph Squid Documentation, *Erasure code*, “Erasure Coding with Overwrites” 与 “Erasure-coded pool recovery”。用于 BlueStore 部分写、完整性检查与恢复/运行阈值的实现对照；不是通用配置建议。[官方文档](https://docs.ceph.com/en/squid/rados/operations/erasure-code/)。
[^ceph-lrc]: Ceph Squid Documentation, *Locally repairable erasure code plugin*，参数、low-level mapping/layers 与恢复示例。用于说明产品的 `l` 和论文参数不同，以及局部恢复与放置的联系。[官方文档](https://docs.ceph.com/en/squid/rados/operations/erasure-code-lrc/)。
