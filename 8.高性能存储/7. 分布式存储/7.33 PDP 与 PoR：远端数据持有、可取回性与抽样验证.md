# PDP 与 PoR：远端数据持有、可取回性与抽样验证

一份 Checkpoint 大到 TB/PB 以后，定期把它全部下载回来计算 Hash，验证本身就会消耗大量网络和存储资源。**能否只交换一小段证明，就判断远端是不是还保有数据？可以，但必须说明预处理、随机抽样、密码学和恢复模型的前提。**

先把问题拆成两句：**不把全部数据传给验证者**，与**远端也不读取全部数据**，不是一回事。某些方案只减少网络；某些方案还能减少每轮服务端读取，但需要提前生成认证信息，并接受概率与编码模型限定的结论。PDP 和 PoR 的价值正在于明确这种成本与保证的交换关系。[^pdp][^jk][^sw]

> [!info] 本篇范围与证据
> 面向不可变的大型 Checkpoint、对象存储与远端备份审计。关注“能证明什么、处理多少字节、保留什么可信状态”，不从零实现可上线的密码协议。
>
> 原始依据包括 Ateniese 等人的 PDP、Juels–Kaliski 的 PoR，以及 Shacham–Waters 的 Compact PoR。资料核对日期：2026-09-16。对具有修订的论文采用所链接的完整版本，不把某个早期构造的特性套到全部 PDP / PoR。
>
> 容量、抽样表和示意流程是本篇推导；代码仅验证概率公式，不是已部署的 PDP / PoR 服务，也不构成正式安全证明。

## 1. “数据还在”到底指什么

### 1.1 六种不同的结论

| 希望验证的性质 | 一个可能的证据 | 不能顺带推出的结论 |
|---|---|---|
| 已读块的内容正确 | 与可信 Hash、MAC、AEAD tag 或 Merkle root 验证相符 | 没读取的块全部正确 |
| 远端能回答关于数据的挑战 | 对新鲜随机挑战返回有效响应 | 一次通过就逐字节检查了整个文件 |
| 远端状态足以恢复文件 | PoR 安全模型中的可提取性论证 | 当前这一条短证明包含完整文件 |
| 返回的是预期版本 | 可信 generation／提交记录与认证 manifest 一致 | 只凭一个合法旧 tag 就知道“最新” |
| 远端看不到明文 | 正确加密及密钥管理 | PoR 默认具有明文机密性 |
| 将来可在恢复窗口内下载 | 冗余、运维保障与恢复性能演练 | 今天的证明承诺明天一定在线 |

[[9.13 完整性、认证与机密性：Checksum、Hash、HMAC、AEAD 与 AES-GCM|完整性、认证与机密性]] 负责已读取内容的安全边界。本篇继续追问：**内容还没有全部取回时，有什么证据能约束不可信存储者的状态？**

### 1.2 缓存摘要，不等于保存了原文

设远端收到文件 $F$，先保存 $h=H(F)$，随后删掉 $F$。它仍然能回答“这个文件的 Hash 是多少”。如果你发送随机 nonce，要求它返回：

$$
H(\mathrm{nonce}\parallel h)
$$

它同样可以回答，因为该计算只需要摘要 $h$。**在旧摘要外面再包一层新鲜 Hash，不会把证明重新绑定到已经删除的 TB 数据。**

换成 $H(\mathrm{nonce}\parallel F)$ 呢？远端一般需要处理 $F$，但只保留 $H(F)$ 的客户端也不能直接据此算出预期结果。客户端可以预先存一批挑战对应的答案，但有限预计算只支持相应有限检查，且普通构造仍可能要求服务端每次全量扫描。这正是早期 PoR 论文分析的基线之一。[^jk]

### 1.3 先分四笔成本

![[图片/SVG/8_7_7_33_1.svg|900]]

图中没有把数据读取藏在“生成证明”这个方框里。计算成本必须至少拆成：

| 成本 | 主要发生在哪里 | 典型内容 |
|---|---|---|
| 初始预处理 | 写入端、编码端或受信生成端 | 全量读入、切块、纠删编码、生成认证信息、上传 |
| 每轮服务端成本 | 存储端 | 找到挑战块、读取块和辅助元数据、计算响应 |
| 每轮网络与验证成本 | 双方及验证者 | challenge、response、校验所需计算和可信元数据 |
| 真正恢复成本 | 存储端、网络、恢复端 | 下载足够的数据、解码、解密、业务装载 |

**短证明不是把所有成本都压缩成短证明的字节数。** 一轮 PoR 可以只传很少的信息，却仍然要在远端读取若干真实数据块。正常完整恢复原始明文时，也不可能只靠一个几十字节的历史证明凭空生成 PB 文件。

## 2. PDP 与 PoR：关注点不同，不能只看名字分类

### 2.1 PDP：Provable Data Possession

PDP 让验证者对远端数据发起挑战，并据响应获得远端持有数据的概率性证据。经典构造用每块认证信息与聚合结构，让验证者不必下载整份文件，甚至不必逐个接收被抽中的原始块。[^pdp]

这里的“持有”是协议安全模型中的性质，不必要求远端物理磁盘上存在与上传字节一一对应的原样文件。压缩、纠删编码、从其他副本取回等表示或访问方式，是否被排除，要看协议是否对此作了额外约束。

不能把一个固定 challenge 的正确答案当作普遍持有证明，也不能仅凭“PDP”三个字认定方案公开可验证、支持动态修改或具有某种严格可提取性。

### 2.2 PoR：Proof of Retrievability

PoR 的核心是 **extractor，可提取器**：在指定模型和安全假设下，如果一个存储者能够以足够高的概率正确回答随机审计挑战，那么存在一个与该存储者交互的算法，可以恢复目标文件。[^jk][^sw]

这句话里的限定都不能删：

**“足够高的概率”** 不是“某一次刚好通过”。

**“存在可提取器”** 是对协议的安全定义和证明要求，不是声称审计响应本身携带完整文件。

**“与存储者交互”** 意味着提取过程通常需要许多查询；模型可能允许对某个存储状态进行特定的 oracle 访问。不能把论文中的 extractor 当作一个能对已经永久关机的服务器继续下载数据的工具。

**“目标文件”** 是被协议保护和编码的那个字节对象。若该对象是密文，提取密文并不保证拥有解密 key，更不保证它能被当前框架当作有效 Checkpoint 加载。

### 2.3 两者的实用区分

| 比较维度 | PDP 中通常关心的事 | PoR 必须进一步说清的事 |
|---|---|---|
| 对手 | 不可信、可能丢弃数据的存储端 | 可能任意偏离协议的证明者 |
| 一轮操作 | 对挑战给出持有相关响应 | 对挑战给出可验证响应 |
| 恢复关联 | 看具体安全模型，不凭名称保证 | 高成功概率如何导出文件可提取性 |
| 编码 | 不由 PDP 名字统一规定 | 典型构造用冗余编码吸收残余丢失 |
| 证明大小 | 可以聚合，也可以较大 | 可以紧凑，但取决于具体方案与参数 |
| 审计者权限 | 有私有与公开等不同设计 | 同样有私有与公开验证设计 |

这不是“所有 PDP 永远不能证明恢复、所有 PoR 都能直接恢复”的二元分类。评估一个实现时，应要求它指出对应论文／定义、证明版本与参数，再判断所声称的性质是否成立。PDP 早期论文与后续完整版本存在安全修订，正说明仅凭标题或摘要不足以选型。[^pdp][^sw]

## 3. 一轮 challenge-response 应该长什么样

### 3.1 初始阶段：先建立不可伪造的绑定

以不可变文件为例，初始阶段需要确定文件身份和版本，切分或编码数据，生成方案所需的块认证信息，并保护验证元数据。验证者保留的通常是 key、公钥、文件标识、认证过的参数和必要的承诺；具体大小依方案而定。

初始阶段需要处理整个被保护对象，可以与原始写入流水线融合，但不是“从未读过数据，只保存一个名字，就开始证明 PB 文件存在”。

### 3.2 在线阶段：挑战必须真的影响验证关系

![[图片/SVG/8_7_7_33_2.svg|900]]

一次审计的教学结构可以写成：

```text
Challenge = scheme-defined sample indices + random coefficients / seed
Response  = data-dependent proof for this Challenge and committed file version
Verify    = check authenticated metadata, proof equation, context, deadline
```

索引决定访问哪些块；若方案使用聚合，随机系数决定如何组合块。短 seed 能否替代显式索引／系数列表，取决于具体方案的生成和安全假设。不是所有协议都把 nonce、seed、系数定义成同一种东西。[^pdp][^sw]

工程 envelope 还应绑定 `audit_id`、版本、发起者、时间窗口等上下文。但**只把旧证明放进一个新的带 nonce 的 JSON 包，并没有改变旧证明的数学验证关系**。新鲜性必须进入挑战与证明本身，并由验证端拒绝不匹配、重复或过期的响应。

### 3.3 防止“验证者自己替对方造答案”

验证者不应在挑战里暴露足以伪造块认证信息的秘密，也不能把预期响应直接发送给对方后只检查它是否原样返回。对公开验证方案，验证公钥应允许检查，但不允许生成任意块的合法认证值。

私有验证表示只有持有验证秘密的一方能检查证明；公开验证表示可向第三方开放验证。**公开验证不等于零知识，也不自动隐藏被挑战数据的线性关系。** 是否允许第三方接触明文、挑战记录和响应，必须另做隐私分析。[^sw]

## 4. 抽样公式：少读成立的条件是什么

### 4.1 建立一个能精确计算的模型

先讨论最简单的“抽块并检查内容”的审计，不把复杂协议的安全定理混进概率计算。

设总共有 $N$ 个审计块，其中 $d$ 个块在审计时无法正确提供；损坏集合在本次抽样前已固定。客户端从 $N$ 个块中**均匀、不放回**地选择 $s$ 个不同索引。假设抽到坏块就必然检出，且攻击者不能根据挑战在答复前补回数据。

则完全漏掉坏块的概率为：

$$
P_{\mathrm{miss}}=\frac{\binom{N-d}{s}}{\binom{N}{s}}
=\prod_{j=0}^{s-1}\frac{N-d-j}{N-j}
$$

其中 $s>N-d$ 时漏检概率为零；没有坏块时自然不发生“检出坏块”。检出概率为：

$$
P_{\mathrm{detect}}=1-P_{\mathrm{miss}}
$$

这些是有限总体抽样的组合计数结果：分母是所有样本集合的数量，分子是只从完好块中抽样的集合数量。

### 4.2 固定损坏比例：样本数可以不随文件容量增长

记 $f=d/N$。不放回抽样满足：

$$
P_{\mathrm{miss}}\le(1-f)^s
$$

若每次独立**有放回**抽取，则 $(1-f)^s$ 是精确值；对于不放回方案，它是方便使用的上界。要求漏检概率不超过 $\delta$，可选择：

$$
s\ge\left\lceil\frac{\ln\delta}{\ln(1-f)}\right\rceil
$$

下面的表按该上界计算，适用于“至少存在所列比例的坏块”、抽样数不超过总体且前述模型成立的场景。若计算结果超过 $N$，可改为全量不放回检查，而不是试图抽取超过总体的不同索引。

| 坏块比例至少为 | 检出概率至少 99% | 检出概率至少 99.9% |
|---|---:|---:|
| 10% | 44 块 | 66 块 |
| 1% | 459 块 | 688 块 |
| 0.1% | 4,603 块 | 6,905 块 |
| 0.01% | 46,050 块 | 69,075 块 |

比如坏块比例至少为 1%，抽 688 块，模型中的检出概率下界约为 **99.900685%**。这不是实测故障检出率，也不直接等于任一紧凑 PoR 的全部安全参数。

![[图片/SVG/8_7_7_33_3.svg|900]]

图把“固定坏块比例”与“只有一个坏块”摆在一起。前者解释抽样审计为什么可扩展，后者解释它为什么不能替代完整扫描。

### 4.3 只有一个坏块：保证少读就不成立了

当 $d=1$，不放回抽样的检出概率恰好是：

$$
P_{\mathrm{detect}}=\frac{s}{N}
$$

若要求以 99% 的概率发现唯一一个坏块，就要抽至少 99% 的块。**“PB 文件只抽几百块就能保证任何一个字节都没坏”是错误结论。**

一般地，少量读取不可能对未读任意位置的任意错误提供确定性逐字节保证。PoR 不是绕过这个事实，而是通过安全模型和编码冗余，把“足够可回答”与“文件仍可恢复”联系起来。

### 4.4 别把条件概率倒过来读

“若至少坏了 1%，本轮有 99.9% 概率检出”不等于“本轮通过后，文件有 99.9% 的概率完全无损”。后者需要额外的先验与统计模型，而且“完全无损”也比“坏块比例不到某阈值”更强。

重复审计的累计计算同样有条件。若坏块集合固定，每轮使用独立的新随机样本，且数据状态没有变化，可以讨论多轮漏检概率的乘积。若长期重复同一组索引、只抽活跃对象、损坏随时间迁移，或攻击者能预知样本，就不能直接套这个乘积。

这里的 $d$ 还不是“物理上被删掉的扇区数量”。如果远端仍能从编码冗余或其他副本生成正确块，逻辑数据可能仍然可取回；如果目标是证明某一块物理盘上保有独立副本，那需要额外协议，而不是更换 $d$ 的名字。

## 5. 一个 PiB Checkpoint 的成本账本

### 5.1 全量下载的下界

以下统一使用二进制容量：$1\,\mathrm{PiB}=2^{50}$ 字节，$1\,\mathrm{MiB}=2^{20}$ 字节。100 Gbit/s 是十进制链路速率。

假设审计对象的**实际存储表示**为 1 PiB；若原始数据经过纠删编码后变大，应按变大后的表示重新计算。仅按 100 Gbit/s 满速有效载荷传输的理想下界：

$$
T_{\mathrm{download}}\ge\frac{2^{50}}{100\times10^9/8}
\approx90{,}072\text{ s}\approx25.02\text{ h}
$$

这还没有计入协议、介质、并发竞争、解码和解密等开销，也不是某个系统的性能预测。它只说明：反复全量下载可以成为独立的大任务。

### 5.2 抽 688 个 4 MiB 块，要读的仍是 GiB

若审计块 $B=4\,\mathrm{MiB}$，则：

$$
N=\frac{2^{50}}{2^{22}}=2^{28}=268{,}435{,}456
$$

抽 688 个块需要处理的逻辑数据量为：

$$
sB=688\times4\,\mathrm{MiB}=2.6875\,\mathrm{GiB}
$$

“只有 688 个索引”不能被简写成“只读了 688 字节”。辅助认证信息、Merkle 路径和物理读放大还未计入。

这个样本数对“至少 1% 坏块”的模型能达到前述检出下界；但若整个 1 PiB 对象中仅有一个 4 MiB 块损坏，同样 688 个不同样本的检出概率只有约 **0.0002563%**。

### 5.3 网络成本取决于返回的究竟是什么

| 验证方法 | 服务端主要数据处理量 | 返回验证者的主要内容 | 需要的可信前提 |
|---|---|---|---|
| 下载全文件后校验 | $D$ | $D$ 字节 | 可信摘要／认证元数据 |
| 抽块 + 独立 MAC | 约 $sB$ | 约 $sB$ 加各块 tag | MAC key、认证过的块身份与总体范围 |
| 抽块 + Merkle proof | 约 $sB$，另读树路径 | $sB$ 加路径证明 | 可信 root、编码规则、文件身份与版本 |
| 同态聚合类 PDP / PoR | 通常仍约 $sB$，另有代数计算 | 聚合数据与聚合认证值 | 具体方案的设置、认证参数与安全假设 |
| 仅返回旧摘要 | 可以不读 $D$ | 很短 | **不构成文件持有证明** |

表中的 $sB$ 是常见按挑战块生成响应时的**逻辑读取量级**，不是对所有构造的统一精确公式，更不是存储设备实际读取的承诺。缓存、预处理、额外索引和专门编码可能改变实现成本，需要在协议分析里单独列账。

对于上面的 4 MiB 块，独立返回块的方案仍要传约 2.6875 GiB。若二叉 Merkle 树有 $2^{28}$ 个叶子、Hash 为 32 字节，独立路径未去重时每条路径为 28 个 Hash，688 条路径约 602 KiB；它们是**附加在真实块数据上的证明**。多重证明可以减少重复节点，但不能靠只返回树节点就证明数据本体仍在。

### 5.4 审计块变小，会把压力移到哪里

若改成 4 KiB 审计块，688 块的逻辑数据量降到 2.6875 MiB，但 1 PiB 对象有 $2^{38}$ 个审计块。

只为演示块数对元数据的影响，假设每块需要 32 字节辅助认证元数据：4 MiB 分块时总计 8 GiB，4 KiB 分块时总计 8 TiB。**32 字节不是所有 PoR 的统一 tag 长度，这里也没算纠删编码、树节点和索引。**

小块还可能造成大量随机读取。一个 4 KiB 逻辑范围读取是否真的只从介质取 4 KiB，取决于对象存储、文件系统、压缩、纠删编码布局与缓存。[[7.8 Multipart 与 Range GET]] 能解释如何请求一个范围，但 Range GET 接口本身并不保证底层零读放大。

## 6. 从“返回块”到“返回聚合证明”

### 6.1 第一条基线：真实块 + 认证信息

客户端要求远端返回被抽中的块 $m_i$，再验证：

$$
\operatorname{HMAC}_K(\operatorname{Encode}(\mathrm{fileID},\mathrm{version},i,m_i))
$$

认证基准必须由初始可信生成过程建立，key 不能给可能作恶的存储端。远端可以保存块与对应 tag，然后原样返回。该基线容易理解和测试，但每轮传输的是所抽块本身。是否能进一步作为一个形式化 PoR，需要编码方式、挑战过程和安全证明共同支持；并非随便加一个 HMAC 就完成了 PoR。[^sw]

Merkle 方案也有类似边界：真实块先 Hash，再沿认证路径验证到可信 root。若只返回早已保存的 leaf hash 与认证路径，服务器在删除原始块后仍可能回答，所以它没有证明对应块内容仍可提供。

### 6.2 HMAC 与 AES-GCM tag 不能直接拿来线性聚合

通常不存在这种可用关系：

$$
\operatorname{HMAC}_K(a\cdot x+b\cdot y)
\stackrel{?}{=}a\cdot\operatorname{HMAC}_K(x)+b\cdot\operatorname{HMAC}_K(y)
$$

任意拼接、异或或相加各块 MAC，不会自动得到对块线性组合的可验证认证值。GCM tag 也不是可以直接改造成 PDP authenticator 的接口。**存储审计的同态认证结构，是一种专门设计，而不是普通 MAC 的一个开关。**[^pdp][^sw]

### 6.3 用单文件代数模型理解“聚合”

下面沿用 Shacham–Waters 私有验证构造的教学轮廓。它只展示等式为什么成立，省略正式方案中的文件封装、编码细节与完整安全参数；**不能照着几行公式自制生产协议**。每个 $m_i$ 暂时只是有限域 $\mathbb F_p$ 中的一个元素，而不是任意长度的 4 MiB 字节串。[^sw]

可信生成端保留秘密 $\alpha$ 和伪随机函数 key $k$，为每个块生成：

$$
\sigma_i=f_k(i)+\alpha m_i\pmod p
$$

验证者选择挑战索引和随机系数 $a_i$。远端计算：

$$
\mu=\sum_{i\in I}a_i m_i\pmod p,\qquad
\sigma=\sum_{i\in I}a_i\sigma_i\pmod p
$$

验证者不需要取回所有 $m_i$，只检查：

$$
\sigma\overset{?}{=}\sum_{i\in I}a_i f_k(i)+\alpha\mu\pmod p
$$

这条等式成立是由线性展开得到的。认证值使伪造组合受到秘密的约束，随机挑战使旧的固定组合通常无法回答新的查询。**等式可验只是起点；从能答挑战到能提取文件，仍然需要论文中的安全证明。**

对多个文件、可更新版本或不同协议，不能不经分析就复用这个简化模型中的秘密与索引命名空间。正式设计需要保持文件身份和参数的认证绑定。

### 6.4 “证明与文件大小无关”也需要固定其他参数

真实块可以分为 $u$ 个有限域元素，即 sectors。聚合时通常得到 $u$ 个线性组合 $\mu_1,\ldots,\mu_u$ 加一个认证值。因此在这一类构造中，证明大小会随 sector 数增长：**不是把一个 4 MiB 块当作单个 32-byte 元素后丢掉剩余信息。**[^sw]

在固定 sector 编码的近似模型下，将 688 个块聚合成“一个块大小的组合 + 认证值”，可以把返回数据从约 2.6875 GiB 降到约一个 4 MiB 聚合块的量级；精确大小取决于有限域编码与方案参数。服务端仍需处理被选中的 688 块。

早期论文中很短的具体字节数依赖当时安全参数。不能把历史的 80-bit 安全级别示例直接当成今天新系统的配置建议，也不能把“固定安全参数下不随文件块数 $N$ 增长”误写成“永远固定 32 或 40 字节”。

## 7. PoR 为什么需要把认证与编码放在一起思考

### 7.1 抽样容易漏掉少量丢失，而编码可以吸收少量丢失

设文件被编码为 $n$ 个片段，达到某个解码条件即可恢复。若审计和安全证明能约束远端仍保有足够的可恢复信息，那么不需要证明每一份物理片段都原封不动，仍可能得到原文件可提取的结论。[^jk][^sw]

这不是“发现坏块以后 MAC 自动修复了它”。认证用于区分有效信息与不可接受的信息；冗余编码或副本提供恢复所需的信息。如何将不可接受的符号转成 erasure、如何处理错误与缺失，必须符合编码器和解码器的真实能力。

### 7.2 两条恢复路径，不要画成一条

![[图片/SVG/8_7_7_33_4.svg|900]]

上方是普通运维恢复：请求足够有效数据，按编码规则重建。下方是形式化可提取性：以满足条件的证明者为交互对象，收集足够信息并提取文件。安全定义中存在 extractor，并不意味着日常恢复应该用海量审计查询代替正常下载。

要证明“所有经常答对的对手都保有足够信息”，必须处理对手选择性回答、错误回答、查询相关性，以及信息是否足以独立恢复等问题。只算出一个抽样命中概率，或者写出一条聚合等式，还没有完成这项证明。

### 7.3 全局损坏比例小，不代表每个 EC stripe 都能恢复

一个教学例子：理想的 `4+2` MDS erasure code 每个 stripe 有 4 个数据片段与 2 个冗余片段，任意 4 个有效片段可以恢复该 stripe。这个结论的单位是 **stripe**。若某一个 stripe 丢了 3 片，即使整份巨大文件的总体丢失比例极低，这个 stripe 仍可能无法恢复。

因此不能从“全局只坏了 0.01%”推导“所有 4+2 stripe 都安全”。需要方案本身证明的编码布局与对抗模型，或者恰当的分层／按 stripe 审计、交织与冗余策略。审计粒度、故障域和恢复域必须对齐。基础概念见 [[7.1 副本 vs EC]]，恢复运维见 [[7.17 Recovery 与 Rebuild]]。

### 7.4 `PDP + 任意 EC` 不是一句正式的 PoR 定理

ECC／EC 不是一个给任何协议“升级成 PoR”的插件。需要明确编码的恢复阈值、对手可以破坏的模式、认证覆盖、挑战分布、可接受成功率以及 extractor 的前提。

Juels–Kaliski 的早期 sentinel 构造使用隐藏哨兵与编码，并有其审计次数等约束；Shacham–Waters 给出了不同的紧凑构造与提取论证。这些是具体方案的差异，不能概括为“所有 PoR 都必须加密哨兵”或“所有 PoR 都只能检查固定次数”。[^jk][^sw]

## 8. 应用到巨大 Checkpoint：保护哪个字节对象

### 8.1 一条可解释的组合路径

![[图片/SVG/8_7_7_33_5.svg|900]]

这是本篇的**分层架构示例**，不是宣称任意组件拼接后都自动满足某个 PoR 安全定义：

先得到一致的应用快照 $F$；按明确的分块 AEAD 格式形成序列化密文对象 $G$，其中包含恢复所需的 nonce、tag 和认证元数据；再选择一个已分析的 PoR 构造，按其编码和认证要求保护 **$G$**。可信控制面保留经过认证的文件身份、格式参数、manifest 与允许恢复的 generation。

日常审计针对 $G$ 的相应存储表示。完整恢复时先按 PoR／存储编码约定得到 $G$，再取得正确 key，验证／解密，最后完成框架层装载。AEAD nonce 的管理与本篇审计 challenge 的随机性是两个不同问题。

**PoR 对密文成立，不等于证明明文 key 还在。** 将 key 备份、KMS 可用性、旧 key 恢复与密文存储拆成独立故障域，并把它们纳入恢复演练。

### 8.2 不要混淆四种块

| 粒度 | 定义它的是谁 | 影响什么 |
|---|---|---|
| 应用 Checkpoint chunk | 写入／恢复应用 | 张量分片、流式装载、manifest |
| AEAD message / chunk | 加密格式 | nonce、tag、认证前不可见边界 |
| PDP / PoR audit block / sector | 审计构造 | 挑战、证明大小、认证元数据、读取量 |
| EC stripe／物理 I/O 单位 | 编码与存储实现 | 故障恢复域、随机读与读放大 |

这四个大小可以不同。把审计块从 4 MiB 调成 4 KiB，不意味着 AES-GCM 可以跳过认证规则对内部任意片段独立验 tag；也不意味着底层对象存储能免费读取 4 KiB。

### 8.3 版本、动态修改与垃圾回收

对 Checkpoint，更容易审查的是不可变版本：写入新版本，发布新 manifest，审计时固定版本，旧版本按保留策略回收。不要在审计中途原地覆盖同名块，同时还使用旧认证信息。

动态 PDP / PoR 有专门的更新与认证数据结构问题，不是给静态协议加一个 `PUT /block` 接口。审计与 GC 也要协调：如果审计合同要求保留版本 4，但 GC 已合法删除版本 4，本轮失败不能直接报告为恶意丢数据。身份与保留窗口应成为审计上下文。

### 8.4 远端持有不等于物理副本独立

两台服务端可能共同访问同一个后端；某台机器也可能在挑战后从其他节点拉取缺失数据。若它能在协议条件下正确作答，普通持有／可取回审计未必区分这些实现。

要证明独立副本数、指定地理位置、持续存储某段时间、某块介质确实经过扫描，需额外的协议与威胁模型。deadline 可以限制部分临时拉取行为，但**低延迟响应本身不是独立副本或地理位置的密码学证明**。

## 9. 审计怎样进入可靠性系统

### 9.1 三种工作各自负责什么

| 工作 | 主要目标 | 无法被另外两种直接取代的理由 |
|---|---|---|
| 持有／可取回性抽样审计 | 低通信成本地约束远端数据状态 | 可以面向不可信服务端，但结论受协议和抽样模型约束 |
| 后台全量／分批 scrubbing | 逐步覆盖实际数据与介质错误，触发修复 | 抽样可能长期漏过极稀疏错误；检查存储路径的范围需单独定义 |
| 完整恢复演练 | 验证 key、网络、格式、模型状态与恢复窗口 | 数据可提取不等于应用真的能在 SLO 内启动 |

如果服务端本身不可信，它声称“完成了一次 scrub”不是独立密码学证据；如果服务端处于自己的可信基础设施内，后台 scrub 则仍是发现并修复静默错误的实际机制。两种威胁模型不能混用。

### 9.2 一轮失败，至少区分三个原因类

**Proof invalid**：响应已收到，但认证关系、文件上下文或证明格式不成立。保留 challenge、版本、错误分类、实现版本与可安全记录的响应摘要。

**Timeout / unavailable**：截止时间内没有有效响应。它可以表示丢数据，也可以是网络、排队、资源限制或服务不可用；不能未经排查就等同于密码学伪造。

**Policy mismatch**：版本已过期、审计范围与保留策略冲突、验证 key／参数错误。需要首先核对控制面合同。

失败后可增加抽样、定向读取、切换可信恢复源、发起修复或暂停回收，但不能用“重试一次通过了”覆盖之前的失败证据。修复源也要验证，避免把未认证数据传播给其他副本。

### 9.3 审计预算要考虑整个对象集合

如果每个对象每轮都抽 $s$ 个块、块大小为 $B$，对 $M$ 个对象的服务端逻辑读取量约为 $MsB$，尚未计读放大和辅助元数据。单对象看起来很轻，并不意味着上百万对象每分钟都审计很轻。

应分别记录 challenge 数、逻辑读取字节、物理读取字节、证明字节、服务器 CPU、验证 CPU、排队延迟、超时、无效证明、版本不匹配及覆盖对象集合。按租户和恢复价值制定策略，同时保留不可预测的抽样，避免只检查容易命中的缓存热点。

将预算控制接到 [[7.18 Backpressure 与过载保护]]，将审计窗口与恢复窗口接到 [[9.7 SLO 与性能回归]]。最终监控面板不应只有一个绿色的“proof pass”。

## 10. 可运行实验：验证抽样数字，不冒充 PoR 实现

本节只用 Python 标准库。样本量函数采用前述有放回精确值／不放回上界，因此参数 `bad_fraction` 表示假设的最小坏块比例，不是从一次通过结果中估计出来的比例。

### 10.1 计算达到目标漏检概率所需的样本数

`log1p(-f)` 在 $f$ 很小时比先计算 `1-f` 再取对数更稳健。`f=1` 单独处理；没有坏块时无法通过抽样“检出坏块”，所以本函数拒绝 `f=0` 这一目标。

```python
import math

def min_samples(bad_fraction: float, miss_probability: float) -> int:
    if not 0.0 < bad_fraction <= 1.0:
        raise ValueError("bad_fraction 必须在 (0, 1] 内")
    if not 0.0 < miss_probability < 1.0:
        raise ValueError("miss_probability 必须在 (0, 1) 内")
    if bad_fraction == 1.0:
        return 1
    return math.ceil(math.log(miss_probability) /
                     math.log1p(-bad_fraction))
```

函数没有输入总体 $N$，因为它返回的是上界公式的结果。用于不放回策略时，调用者还需检查 $s\le N$；若超出，选择全量检查或者重新定义目标，而不是继续抽取不存在的不同块。

### 10.2 计算不放回抽样的精确检出概率

直接计算两个巨大的组合数容易引入不必要的大整数。这里在对数域累加乘积，最后用 `expm1` 减少概率接近零时的相减误差。函数时间复杂度为 $O(s)$，适合本节这类中小规模数值检查，不应对接近 PB 级总体块数的 $s$ 直接跑循环。

```python
def detection_without_replacement(n: int, bad: int, samples: int) -> float:
    if n <= 0 or not 0 <= bad <= n or not 0 <= samples <= n:
        raise ValueError("需要 n > 0，且 bad、samples 均在 [0, n] 内")
    if bad == 0 or samples == 0:
        return 0.0
    if samples > n - bad:
        return 1.0
    log_miss = math.fsum(math.log1p(-bad / (n - j))
                         for j in range(samples))
    return -math.expm1(log_miss)
```

当 $d=1$ 或全量检查时，应使用简单解析表达验证代码，而不是盲信复杂函数。这也是本节后面的测试所做的事。

### 10.3 复现样本表与 1 PiB 示例

以下测试的 `assert` 都应通过。`bad = ceil(0.01N)` 保证示例中的整数坏块数确实至少达到 1%，避免比例到块数转换时向下取整改变假设。

```python
expected = [(0.1, 44, 66), (0.01, 459, 688),
            (0.001, 4603, 6905), (0.0001, 46050, 69075)]
for fraction, at_99, at_999 in expected:
    assert min_samples(fraction, 0.01) == at_99
    assert min_samples(fraction, 0.001) == at_999
    print(fraction, at_99, at_999)

n, samples, block_bytes = 2**28, 688, 4 * 2**20
bad = math.ceil(0.01 * n)
p = detection_without_replacement(n, bad, samples)
assert p >= 0.999
assert math.isclose(detection_without_replacement(n, 1, samples),
                    samples / n, rel_tol=1e-12)
print("至少 1% 坏块的检出概率：", round(p, 9))
print("仅 1 块损坏的检出概率：", samples / n)
print("逻辑读取 GiB：", samples * block_bytes / 2**30)
# 约 0.999006862；约 2.563e-6；2.6875 GiB
```

最后一行注释是概率与容量计算，不是一个 PoR 系统的实测结果。真实挑战的随机索引必须按协议安全要求产生；为了可重复实验而固定 seed 的伪随机模拟，不能直接用作生产审计的可预测挑战源。

### 10.4 这个概率实验没有证明什么

它没有验证 HMAC／同态认证的不可伪造性，没有证明 extractor 存在，没有覆盖网络对手、缓存补回、编码恢复、动态修改或密钥管理。对于聚合协议，“抽中坏块必然失败”也不能直接套用：可能涉及线性组合碰撞、对手能从其他信息恢复回答，以及方案特有的 soundness error。

正确做法是将**统计抽样模型**、**密码学安全定理**与**系统故障实验**分别报告，而不是把三者合并成一个 `99.9% secure` 标签。

## 11. 系统实验合同：从概率计算走到可验证产物

| 实验 | 需要保存的输入 | 要验证的现象与边界 |
|---|---|---|
| 固定比例删块 | 总体、坏块集合、随机样本、次数 | 独立块校验的检出频率应与抽样模型一致 |
| 仅坏一个块 | 同上 | 少量样本可能长期漏检；不应宣传“全量无损” |
| 只保留 Hash／tag | 删除前后对象状态、challenge | 简单摘要回显仍能通过；真正数据依赖挑战不能靠回显通过 |
| 重放旧 proof | 旧 challenge、旧 proof、新 challenge | 应拒绝与本轮挑战不匹配的响应 |
| 合法旧版本 | 两份合法 manifest 与版本策略 | 由可信版本状态拒绝，不把拒绝归因于 Hash 错误 |
| 一个 stripe 集中丢失 | 编码参数、stripe 映射、丢失位置 | 观察恢复域与全局丢失比例的差别 |
| 服务端限速／断网 | 请求时间、队列、deadline | 区分 timeout 与 invalid proof |
| 审计正常但 key 丢失 | 密文证明、key 恢复日志 | 密文可取回，不等于明文可恢复 |
| 完整恢复演练 | 版本、key、全体文件、装载结果 | 检查模型与优化器状态，以及真实恢复时间 |

表中涉及删除、故障和密钥丢失的操作只能在隔离测试数据上实施。不要拿唯一一份真实 Checkpoint 验证恢复失败。

## 12. 自测：把“验证”说成精确的句子

**服务器发来正确 root hash，能证明它还保存了文件吗？** 不能。它可能只保留了 root 或整个 Hash 树。需要响应与新挑战及数据本体形成协议规定的关系。

**为什么固定坏块比例时几百个样本就有价值？** 在均匀独立等条件下，漏检概率随样本数指数下降，主要取决于比例而非总块数。但只有一个坏块时，比例会随总体变大而趋近零。

**紧凑证明到底省了什么？** 常见同态聚合方案主要减少传回验证者的块与认证信息；服务器仍需读取／处理挑战涉及的数据，且还支付代数计算成本。

**拿普通 HMAC 做个求和，能实现 Compact PoR 吗？** 不能。普通 HMAC 没有需要的同态验证结构，而且聚合等式本身也不等于可提取性证明。

**PoR 通过后可以删除其他备份吗？** 不能据此作出这个结论。审计不承诺未来在线、不证明副本物理独立，也不替代恢复窗口、密钥和故障域设计。

**PDP / PoR 能不能回答“巨大 Checkpoint 少读验证”？** 能在明确假设下做到每轮不下载全文、通常只处理部分远端数据，并获得概率性持有／可取回性保证；不能由此声称这次已经逐字节检查了所有数据，也不能省掉真正恢复时取得足够信息的成本。
