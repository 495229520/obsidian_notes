# 7.31 Content-Addressed Storage 与 Merkle Tree：Chunk、Manifest、Merkle DAG 与增量校验

> [!abstract] 内容身份与版本发布
> 业务名称指向版本，版本通过 Manifest 引用不可变数据块。内容哈希验证字节身份；Merkle 结构支持子结构共享、成员证明和差异定位。最新版本、持久性和应用恢复语义由相应协议保证。
>
> KV Prefix 还要区分计算输入的复用键与实际 KV 字节的摘要；缓存命中后仍需验证取回的数据。

## 1. 先把三个业务问题放进同一张图

考虑三个需求：存储服务希望只上传新增加的数据；训练任务希望保留多个 Checkpoint 而不无条件复制所有未变化内容；推理服务希望复用已经算过的前缀。它们都涉及“已有的东西能否复用”，但复用的判据并不完全一样。

下面是一种用于理解和设计系统的统一抽象，不是在声称三个产品采用了相同的内部实现。

![[图片/SVG/8_7_7_31_1.svg|900]]

从上往下读这张图：

名称层解决可变的业务指向，例如 `checkpoints/run-A/latest`。同一个名称今天可能指向版本 101，明天指向版本 102。名称自身通常不是内容哈希，也不应该靠扫描所有 Chunk 来发现它的新值。

描述层保存某个版本的 Manifest，包括有哪些分片、顺序、长度、格式以及恢复时需要的业务元数据。Manifest 自身也可以作为不可变对象，用内容 ID 标识。

内容层存放不可变 Chunk。相同的 Chunk ID 可以被多个版本引用，因而产生结构共享。IPFS 的 Merkle DAG 就把节点内容及其链接纳入内容寻址；同一个子节点可以拥有多个父节点。[^ipfs-dag]

放置层把内容 ID 翻译成实际位置，例如对象存储 Key、节点集合或本地 Pack 文件偏移。内容身份与位置分开之后，搬迁副本不必改变业务版本的内容身份。已有的 [[7.16 数据放置与 Rebalance]] 解决的是“放到哪里”，本篇解决的是“要找的究竟是哪份内容”。

这个模型有三条独立的检查路径：

| 路径 | 检查的问题 | 不能替代什么 |
| --- | --- | --- |
| 名称 → 版本 | 是否读到了有权限访问的、符合一致性要求的版本 | 不能替代数据块校验 |
| Root → Manifest → Chunk | 引用关系、长度与字节身份是否匹配 | 不能替代业务语义验证 |
| Chunk ID → 存储位置 → 实际读取 | 该副本此刻是否可读、字节是否正确 | 不能由旧的摘要缓存代替 |

因此，有 Root 不代表有可用副本；有可用副本不代表有最新版本；有最新版本也不代表模型状态在业务上正确。后两层长期是否仍然健康，由 [[8.高性能存储/7. 分布式存储/7.32 Data Scrubbing 与 Anti-Entropy：Bit Rot、Checksum Tree、Replica Repair 与后台校验|7.32 Data Scrubbing 与 Anti-Entropy：Bit Rot、Checksum Tree、Replica Repair 与后台校验]] 接着讨论。

对 [[8.6 Checkpoint 同步异步分片]]，描述层需要覆盖完整训练状态；对 [[8.14 分层缓存与 KV Cache 生命周期]]，语义复用与跨介质搬运的字节校验需要分开。

## 2. CAS 的身份、不可变性与信任边界

### 2.1 Content-Addressed Storage 不是 Compare-And-Swap

两者常缩写成 CAS，本篇默认指 Content-Addressed Storage，内容寻址存储。到第 8 节更新业务指针时，会用到另一种 CAS：Compare-And-Swap，比较并交换，届时写全称以避免混淆。

最小的内容寻址模型是：

$$
\operatorname{id}(x)=H(\operatorname{Encode}(\text{format},\text{type},x))
$$

查询者给出期望 ID，存储层返回候选字节，查询者按约定重新计算 ID 并比较。IPFS 的 CID 还包含内容解释、哈希等相关编码信息，不能把所有系统的内容 ID 都想象成不带类型的裸摘要字符串。[^ipfs-how]

“按哈希命名”与“按哈希验证”是两件事。 把一个文件命名为其旧摘要，并不能阻止底层介质把文件内容改坏；读取后不校验，内容寻址就只剩下一个命名习惯。

### 2.2 Immutable object 到底不允许改什么

不可变对象承诺：在同一个内容 ID 下，逻辑上可接受的内容不能改变。新内容产生新 ID，旧版本仍可引用旧 ID。

这不妨碍后台重新压缩、迁移副本、把多个 Chunk 打包，或修复一个损坏的物理副本。条件是系统明确区分“逻辑内容身份”和“物理表示身份”，并在表示转换后验证相应的不变量。restic 的设计区分 Blob、Pack 和索引，展示了数据复用单位与物理存放单位不必相同。[^restic-design]

也不要从不可变性推导持久性：一个对象可以永不被修改，却在写入后立即因掉电丢失；可以正确落盘，却被无引用回收删除。不可变、持久、可达、有足够冗余，是四种不同属性。

### 2.3 必须把“期望值”放在信任模型里

假设客户端既从不可信服务端获取数据，又从同一个响应里获取所谓的正确摘要。服务端只需一起替换二者，就能返回一对自洽的错误值。正确做法是让期望的 Root/内容 ID 来自已经认证的版本记录、可信发布流程或事先保存的可信引用。

哈希碰撞不可忽略，但也不能把所有失败都归因于碰撞。实际设计首先应防止的是：读取了错误版本、漏绑对象类型、序列化不确定、把一份旧摘要当成当前介质验证结果。加密哈希在这里提供内容承诺的基础，不自行提供发布者身份认证和防回滚。

### 2.4 六种标识各有作用

| 标识 | 含义 | 不能据此推出 |
| --- | --- | --- |
| Semantic key | 同一计算输入及必要上下文的身份 | 输出 Tensor 字节未损坏 |
| Chunk ID | 按约定编码计算的内容身份 | 对象仍有可用副本 |
| Root hash | 某个结构及其覆盖内容的承诺 | 这是最新、合法发布的 Root |
| Object key | 对象存储命名空间中的键 | 键就是内容摘要 |
| Version / generation | 版本选择及并发控制信息 | 当前副本的字节正确 |
| Physical locator | 节点、设备、Pack、Offset 等位置 | 内容身份必须随搬迁改变 |

受认证的版本记录应把 Root 与 Namespace、Generation、协议版本和必要的发布元数据绑定。签名证明发布者认可了某份承诺；客户端接受规则或一致性控制面负责防回滚。发布前的应用错误、所有副本被删除、密钥丢失，都不能靠内容哈希解决。

### 2.5 碰撞概率与编码错误分开分析

理想 $b$ 位摘要面对 $n$ 个独立不同对象，且 $n\ll 2^{b/2}$ 时，碰撞概率近似为：

$$
P_{\mathrm{collision}}\approx\frac{n(n-1)}{2^{b+1}}
$$

这是生日界的近似，不覆盖算法弱点、摘要截断和实现错误。排障时还应检查编码差异、缓冲区复用和摘要字段取错；输入编码已经有歧义时，换更强的哈希函数没有用。

## 3. Chunk：怎么切，决定什么能够复用

### 3.1 三类边界各自适合什么问题

| 切块方法 | 边界由什么决定 | 优点 | 代价与限制 |
| --- | --- | --- | --- |
| 固定长度 | 字节偏移与固定块长 | 简单、随机定位容易、元数据规则 | 前方插入字节可能使后续块全部错位 |
| 内容定义切块，CDC | 滚动指纹等边界判据，通常配合最小/最大块长 | 插入删除后，有机会重新找到相同边界 | 边界计算有成本；收益依赖数据分布与参数 |
| 应用对齐 | Tensor、参数分片、页、完整 Token Block 等 | 更容易对齐应用的读写和兼容边界 | 不同业务布局可能限制跨版本共享 |

这里的滚动指纹用于“在哪里切”，不必等同于最终用于安全内容身份的加密哈希。二者的角色应在代码与文件格式中分别命名。

【推导】原始字节被切成 `[ABCD][EFGH][IJKL]`。在最前面插入一个字节后，固定 4 字节边界变成 `[xABC][DEFG][HIJK][L]`。虽然只插入了 1 字节，所有块的内容身份都可能变了。这解释了为什么“修改量小”不必然意味着“传输量小”。

CDC 可以改善这类边界漂移，但并不承诺任意输入都能高比例去重。即使使用相同算法，切块参数不同，也可能生成不同的块集合。restic 对跨仓库去重的说明明确要求关注 Chunker 参数的一致性。[^restic-working]

### 3.2 块越小，并非越先进

设数据大小为 $S$，平均块长为 $C$，块数近似 $N=S/C$，每个 Manifest 条目占 $m$ 字节，则条目元数据约为 $Nm$。

减小 $C$ 有机会缩小局部更新、局部修复和 Range Read 的放大；同时却增加条目数、索引项、请求数量、哈希调用管理成本以及小对象处理成本。把许多小 Chunk 装入较大的 Pack 可以缓解物理小对象问题，但会新增索引、压缩边界与回收放大。

对 Checkpoint，应从 Tensor/Shard 的实际访问方式出发；对 KV Cache，应从模型执行所使用的 Token Block、数据布局和复用域出发。先选正确性边界，再测量粒度，而不是先宣布“统一采用 4 MiB”。 本文后面的 4 MiB 只是算账示例。

【算例】1 TiB 数据用 4 MiB 块时有 262,144 个条目；若每条 64 B，描述符约 16 MiB。改用 64 KiB 块后有 16,777,216 个条目，描述符约 1 GiB。两者都还没计入请求、索引和分配器开销，小块可能把瓶颈转移到 [[7.2 元数据路径瓶颈]]。

### 3.3 先压缩、先加密，都会改变“相同”的含义

对明文字节取哈希，可以在不同压缩表示间保留逻辑身份；对压缩后的字节取哈希，则压缩算法、版本和参数变化可能产生新身份。随机化加密通常使相同明文产生不同密文，所以密文哈希通常不能直接带来明文级去重。

可以设计“逻辑 Blob ID + 物理密文对象 ID”的双层索引，但需要清楚约定在哪一层校验、解密后验证什么。跨租户公开明文内容哈希还可能泄漏内容相等关系，使低熵内容被枚举猜测。不要为了去重自行引入确定性加密或所谓“用内容哈希当密钥”的方案；安全设计需要独立审查。

## 4. Manifest：内容正确之外，还要描述完整

### 4.1 Manifest 是一份可验证的重组契约

一个通用的文件 Manifest 可以包含：格式版本、哈希算法/编码、总字节数、切块策略，以及有序的 `(offset, length, chunk_id)` 条目。Checkpoint Manifest 还需要相应的训练和恢复信息。这是本文的设计示例，不是现有产品的通用线格式。

校验时不仅要逐块匹配摘要，还要检查偏移没有意外重叠或缺口、累计长度与总长度相符、引用数量和类型合法。否则，三个 Chunk 各自正确，却按错误顺序连接，仍然会得到错误对象。

为了让相同描述产生相同 Root，编码必须确定：字段顺序、整数宽度和字节序、字符串编码、空值、列表顺序、重复字段处理，都需要规范。JSON 文本多一个空格也会改变原始字节；`json.dumps(sort_keys=True)` 不能被直接宣称为完整实现 RFC 8785。需要 JCS 时，应按它规定的完整规范实现或使用受验证的库。[^jcs]

下面是 Checkpoint 字段草图，展示逻辑布局需要受到怎样的保护；它不对应任何产品的现行文件格式。

```yaml
format: checkpoint-manifest-v1
training_step: 42000
model_revision: weights-schema-7
objects:
  - name: layer.0.weight
    dtype: float32
    shape: [1024, 1024]
    byte_order: little
    chunks:
      - logical_offset: 0
        byte_length: 4194304
        id: sha256:<完整摘要>
```

下载 Manifest 时先限制对象大小、核对预期 ID，再按受限 Schema 解析，检查重复字段、未知字段策略、范围和资源上限。若 Shape、Dtype、字节序已由可信父 Manifest 保护，叶子无需重复承诺这些字段；但整个验证路径必须覆盖它们。结构验证通过以后，还要确认所有必需引用实际可读。

### 4.2 用类型标签和长度消除结构歧义

如果只是拼接可变长度字段，`("ab", "c")` 与 `("a", "bc")` 都能变成字节串 `abc`。这不是哈希函数发生碰撞，而是进入哈希之前，编码已经丢了字段边界。

本文实验使用如下自定义规则：

$$
D(t,p_1,\ldots,p_k)=\operatorname{SHA256}\bigl(t\parallel
\operatorname{u64}(|p_1|)\parallel p_1\parallel\cdots\parallel
\operatorname{u64}(|p_k|)\parallel p_k\bigr)
$$

$t$ 是一个单字节类型标签，`u64` 是大端无符号 64 位整数。这样，同一套编码中，数据块、叶子、内部节点和根封装不会被当作同一类输入解释。RFC 9162 也区分叶子与内部节点的哈希前缀，但它的实际树形与编码规则不同；本文实验不能和 Certificate Transparency 的证明直接互通。[^rfc9162]

### 4.3 平铺 Manifest 不等于高效的增量元数据结构

把全部 $N$ 个 Chunk ID 放进一个大列表，然后只对整个列表取一次哈希，可以得到内容寻址的 Manifest；但修改一个条目后，通常仍要序列化并写出整个列表。

要让元数据本身也增量更新，可以把条目分组，形成多层不可变节点。更新一个叶子，只创建它到根的路径上的新节点；其他子树继续共享。对于有界扇出、稳定布局的平衡树，单点更新涉及 $O(\log N)$ 个结构节点。

业务版本信息也应放在正确位置：若把 `training_step` 塞进每个 Chunk 的 ID，即使某个 Chunk 的字节没有变化，它也会因 Step 变化而失去跨版本共享。通常应让 Chunk ID 标识可复用的内容，Manifest 标识内容在版本中的角色。

## 5. Merkle Tree、Merkle DAG 与 Hash Chain

### 5.1 Merkle Tree：父摘要承诺子结构

二叉示意中，叶子摘要来自数据/条目，内部摘要来自有顺序的两个子摘要，层层计算得到 Root。树形、空树、奇数叶子和字段编码必须明确；“遇到奇数就随便复制最后一个”不是无条件正确的通用规则。RFC 9162 给出了一套具体定义，而不同系统可以选择不同定义。[^rfc9162]

Merkle Tree 不要求一定是二叉树。更大的扇出可以减少层数，却会改变节点大小、路径证明需要携带的兄弟信息以及缓存/网络开销。对比两棵树前，双方必须采用兼容的结构约定。

以下两套规则都能定义确定的树，但不能混用 Root 或 Proof：

| 项目 | RFC 9162 §2.1 | 本篇第 10 节教学格式 |
| --- | --- | --- |
| 叶子 | `H(0x00 ∥ payload)` | `D(L, index, length, chunk_id)` |
| 内部节点 | `H(0x01 ∥ left ∥ right)` | `D(N, left, right)` |
| 非 2 的幂 | 按小于叶数的最大 2 的幂递归切分 | 用专门的空位摘要补齐 |
| 空树 | `H(空字节串)` | 一个空位加 `count=0` 的 Root 封装 |
| 根 | 顶层树摘要；树大小另由协议承诺 | `D(R, count, top)` |

RFC 中 `0x00`、`0x01` 是单字节标记。第 10 节保留显式位置、长度与叶数绑定，并使用不可变节点实现路径复制；这两项选择与是否采用 RFC 树形是不同的设计维度。[^rfc9162]

### 5.2 Merkle DAG：允许共享子节点

普通树中，一个节点有一个父节点；在 DAG 中，同一个不可变子节点可以被多个父节点引用。两个版本只要共享相同子内容，就可以指向同一个节点 ID。节点内容包含对孩子的哈希引用，因而孩子改变会沿依赖方向传播到受影响的祖先。[^ipfs-dag]

这种共享不是“把两个可变对象锁到一起”，而是“两个不可变版本引用同一个不可变内容”。旧版本的 Root 不被修改，新版本得到新的 Root。

共享也会扩大单个坏块的影响范围：一个 Chunk 可能被数百个历史 Root 引用。应通过引用索引或可达性分析列出受影响版本，并按内容重要性与剩余健康冗余安排修复。去重字节数不能代替业务影响范围。

一般 DAG 不保证对数高度，可能是一条长链或包含大量祖先。$O(\log N)$ 的更新结论要求稳定的平衡结构；把全局可变字段复制进所有节点，也会让小变更扩散到整张图。

### 5.3 Hash Chain：也是依赖承诺，但不自动拥有二叉证明的效率

前缀哈希链可以写为 $K_i=H(K_{i-1},B_i,\text{context})$。后面的身份依赖整个前缀，因此修改前面的输入，会影响后续身份。

这种链特别适合表达“当前块依赖之前所有块”的计算语义，但它不是一棵平衡的二叉 Merkle Tree。不能直接把二叉树的 $O(\log N)$ 局部更新或成员证明结论套给整条前缀链。

## 6. Merkle Proof：用一条路径验证一个成员

![[图片/SVG/8_7_7_31_2.svg|900]]

图中要证明第 3 个索引位置的叶子 `L3` 属于某个 8 叶子的 Root。这里索引从 0 开始，所以它是第 4 个数据块。只需给出三个兄弟摘要：`L2`、`H01`、`H47`。验证者从目标数据计算 `L3`，依次重建 `H23`、`H03` 和顶部摘要，最后与可信 Root 比较。

左右顺序不能丢。 `H(left, right)` 一般不同于 `H(right, left)`。验证者需要索引与树大小，或一个同等严格的路径描述，才能知道每层如何拼接。若证明机制绑定了长度和位置，还能避免把一个合法块挪到不正确的位置而不被发现。

对 $N=2^h$ 个叶子的平衡二叉树，一条路径包含 $h=\log_2N$ 个兄弟摘要。叶子本身是数据还是一个条目，要由格式规定；不能拿“我证明了 Manifest 中有这个摘要”冒充“我已经读取并验证了那个摘要对应的实际数据”。

### 6.1 一个 1 TiB 的量级例子

【推导，非实测】设对象大小为 $1\ \text{TiB}=2^{40}$ 字节，固定 Chunk 大小为 $4\ \text{MiB}=2^{22}$ 字节，采用 32 字节摘要：

$$
N=2^{18}=262\,144,\qquad h=18
$$

一条证明的兄弟摘要共 $18\times32=576$ 字节，另加索引、格式、总叶数等元信息。若验证的是整个 4 MiB Chunk，仍需获得并哈希这 4 MiB 数据；576 字节不是整个验证过程的总流量。

仅叶子摘要约占 8 MiB；完整二叉树的 $2N-1$ 个摘要约占 16 MiB，尚未计入 Manifest 字段、节点对象头、索引、分配器和副本开销。量级相差很大，但不能因此把所有元数据开销都忽略。

### 6.2 一条成功证明不承诺什么

| 能证明的范围 | 还缺少的条件 |
| --- | --- |
| 数据/条目与给定 Root 的成员关系相符 | Root 本身的来源必须可信 |
| 被绑定的位置、长度等字段没有被替换 | 不代表其它未读取的数据也健康 |
| 某个既定版本的局部内容匹配 | 不代表它是最新版本，或没有被回滚 |
| 内容按约定结构被承诺 | 不代表 Checkpoint 来自同一个训练 Step |

普通 Inclusion Proof 也不是通用的“不存在证明”。后者需要有序结构、边界证明或专门的认证数据结构。RFC 9162 的 Consistency Proof 主要证明日志之间的追加关系，也不要与存储系统的强一致性混淆。[^rfc9162]

## 7. 增量 diff：省掉的是哪些工作

![[图片/SVG/8_7_7_31_3.svg|900]]

图中只有索引 3 对应的 Chunk 变化。新版本创建新的叶子和祖先节点，但继续引用其余未变化子树。比较两个 Root 后，算法只进入摘要不同的分支；相等的分支直接跳过。

### 7.1 把四类成本分开

| 工作 | 前提与成本 | 不能省略的事情 |
| --- | --- | --- |
| 首次构建 | 读取被覆盖的全部数据并计算叶子摘要，再建立树 | 第一次必须了解数据内容 |
| 已知位置的单点更新 | 稳定树形下重算该块及祖先路径 | 新块本身仍需读取/接收并校验 |
| 比较已建立的两棵树 | 相等子树剪枝，只遍历有差异的区域 | 摘要必须有效，比较的范围必须一致 |
| 传输差异 | 发送缺失/变化的 Chunk 及必要结构 | 接收方仍要验证实际接收的字节 |

在稳定、对齐的平衡树中，$k$ 个变化叶子的差异定位有一个常用上界 $O(k\log N)$；共享的祖先只需访问一次，因此这只是较宽松的上界，最坏不会优于遍历整体的 $O(N)$ 量级。完全相等的树比较 Root 即可结束。若树形不对齐、范围不一致或切块边界大幅漂移，这个简化模型就不适用。

### 7.2 最容易混淆的两个“增量”

增量生成版本：应用或写入路径知道哪些块变了，因此可以只重写这些块及对应元数据。这要求脏块跟踪、日志或其他可靠的变更来源。无法可靠判断哪些字节变化时，仅看到文件时间戳或旧索引不能直接断言“其它块都没变”。

增量发现两个副本的差异：双方已经维护好覆盖同一范围的摘要结构，交换少量摘要，定位应该同步的范围。Dynamo 的 Anti-Entropy 用 Merkle Tree 缩小副本比较和传输范围，但建立与维护摘要本身仍然有代价。[^dynamo]

> [!warning] 比较旧摘要，不是重新检查旧数据
> 如果磁盘数据静默损坏，却没有经过正常写路径更新摘要树，两个副本缓存的 Root 可能依然相同。树比较会跳过它，直到某个实际读取/校验过程发现问题。Merkle diff 优化差异定位，deep scrub 补上实际读取验证。

这也回答“巨大 Checkpoint 能否少读数据完成验证”：验证某一块相对可信 Root 的成员关系可以少读；同步两个已建立索引的版本可以少传；但要确定本地全部现存副本此刻都能被正确读出，不能仅靠旧 Root 免除相应数据读取。

### 7.3 逻辑范围与物理文件不能混比

双方要对齐哈希/编码版本、叶子定义、逻辑范围以及可比较的快照边界。分布式 KV 的两个副本可能保存相同逻辑记录，却因 Compaction 得到不同 SSTable 文件；按文件字节比较会产生与逻辑分歧无关的差异。

逻辑叶子应按系统规则规范化 Key、可见版本、Value 和删除信息。[[7.22 分布式存储系统中的事务与 MVCC（Percolator 模型）]] 的可见性边界决定了这次摘要究竟覆盖哪些记录。

## 8. 发布、读取与 GC：不可变数据仍有并发问题

### 8.1 数据先就绪，再发布可变指针

一种可落地的协议是：写入缺失的 Chunk，达到约定的持久化/冗余条件；写入并验证 Manifest；确认所有必需引用可达且满足发布策略；最后把业务名称从 `(generation=g, root=R0)` 条件更新为 `(g+1, R1)`。

![[图片/SVG/8_7_7_31_4.svg|900]]

图中的等待区间是发布者等待数据层达到约定的持久条件，不是只等内存拷贝或网络发送完成。元数据指针的 Compare-And-Swap 则是另一个原子性边界：它阻止两个发布者无条件覆盖对方，但不会自动把数据写入和元数据更新变成跨系统原子事务。

如果系统采用复制提交，需要明确何种确认允许发布；如果使用文件系统，要按实际持久化模型处理文件和目录更新；如果使用对象存储，要遵循其对象完成与条件更新语义。已有 [[7.9 一致性模型]] 与 [[7.20 元数据服务高可用]] 负责解释名称服务和版本记录的可见性，内容寻址不能替代它们。

可以将发布过程分成以下状态，便于定义恢复和清理动作：

| 状态 | 必须成立的条件 | 对读者是否可见 |
| --- | --- | --- |
| `PREPARING` | 在途对象受上传 Pin 保护 | 否 |
| `CONTENT_READY` | 必需 Chunk 达到配置的持久化/冗余条件 | 否 |
| `MANIFEST_READY` | Manifest 与所需引用全部就绪 | 否 |
| `COMMITTED` | 条件发布新的 Generation/Root | 是 |
| `ABORTED` | 放弃发布，按引用和保留规则清理 | 否 |

失败者只能清理自己不再需要、且没有被其他版本或读者保护的对象。副本确认条件可结合 [[7.10 Quorum 读写]] 分析。

### 8.2 两个崩溃位置，后果完全不同

在发布前崩溃：可能留下未被正式版本引用的 Chunk/Manifest。这是可回收的孤儿，通常优于公布一个不完整版本。

在指针先更新、数据尚未满足策略时崩溃：读者可能看到一个已经发布却无法完整读取的版本。这是悬空引用，不是“再算一次 Root”能修好的问题。

读取时应先固定一个 Root，再沿它读取整个对象；不要读取每个分片之前都重新查询 `latest`。否则前半读取旧版、后半读取新版，即使每个块都通过各自版本的校验，也没有组成一个单一版本。

### 8.3 GC 的根集合不能只有 latest

根集合至少应覆盖：保留的历史版本、正在读取的已固定版本、正在写入/准备发布的对象，以及备份和快照保留策略要求保留的引用。可以用引用追踪、租约、事务化引用记录或带宽限期的标记清扫实现，但需要与发布协议配合。

典型竞态是：写入者上传了一个 Chunk，GC 看到它尚未被正式 Manifest 引用，立即删除；随后发布者提交了引用它的 Manifest。要避免这种竞态，需要写入期间的保护机制，而不是仅把“GC 运行慢一点”当正确性保证。

副本搬迁则不应随意重写 Manifest 中的内容 ID。将位置从 A 迁移到 B 后验证内容不变，再更新放置索引；这正是内容身份与 [[7.16 数据放置与 Rebalance|放置策略]] 分层的价值。

### 8.4 条件写的范围与过期 Writer

两个 Writer 都从 Generation 41 出发时，发布必须校验预期版本或等效并发令牌；失败者重新读取状态，再决定重试、保留分支或放弃。还要结合 [[7.12 Lease 与 Fencing]] 拒绝已经失去发布资格的 Writer。

S3 的 `If-None-Match` 可用于限制不存在时创建，`If-Match` 可检查目标对象当前 ETag；条件只保护对应对象操作，不能把多个 Chunk、Manifest 和版本记录一起变成跨对象事务。应用应明确受保护的 Key、条件失败处理和重试后的孤儿清理。[^s3-conditional]

### 8.5 读取固定版本与 Pin 必须衔接

如果 Reader 先读到 Root，GC 随即删除其内容，再申请 Pin 就已经太晚。协议可以提供 `read_and_pin`，也可以采用有明确保证的保留窗口；不能把两个无保护操作当成原子过程。

Pin 还需要过期、续期与故障处理。崩溃 Reader 不应永久阻止回收；Reader 也必须处理 Pin 失效，而不是假定已见过的 Root 永久可读。

### 8.6 长期保留需要保护恢复依赖

保留密文与摘要但丢失密钥，或保留旧格式却失去可用解码器，都会使字节完整的对象无法恢复。密钥轮换、格式迁移和兼容恢复环境应纳入保留策略，并验证迁移后的应用对象。

删除一个业务版本只移除一组引用；被其他 Root 共享的 Chunk 可能仍需保留。业务要求删除某类内容时，还需要处理相关版本、备份、引用与密钥，不能只删一个名称就认为全部内容已经移除。

## 9. KV Prefix、Checkpoint 与对象存储的统一与区别

![[图片/SVG/8_7_7_31_5.svg|900]]

### 9.1 KV Prefix：相同输入上下文，不等于已校验输出字节

vLLM 的 Prefix Caching 设计将父块哈希、当前完整块的 Token 和额外区分信息用于缓存身份；额外信息包括 LoRA、多模态输入和缓存隔离相关信息。当前文档还强调仅缓存完整块。这里只引用这种输入依赖结构，不把活动文档中的默认算法当成所有部署版本的事实。[^vllm]

一个跨服务缓存设计可以显式写成：

$$
K_i=H(\operatorname{Encode}(\text{reuse-domain},K_{i-1},\text{tokens}_i,\text{extras}_i))
$$

这里的 `reuse-domain` 是本文建议明确建模的复用域：模型权重版本、必要的适配器与位置语义、租户隔离，以及影响缓存兼容性的表示约束等。某些信息在单模型服务内部可以是隐含常量，但跨模型、跨进程或跨版本共享时就必须重新审视。

这个 $K_i$ 是计算输入的语义身份，不是实际 KV Tensor 字节的内容哈希。 合理的持久化设计可以同时保存：

| 字段 | 作用 |
| --- | --- |
| `prefix_key` | 判断计算输入是否属于同一个合法复用域 |
| `kv_blob_id` / checksum | 对实际保存、传输或恢复的 KV 字节进行校验 |
| `layout / dtype / format` | 判断这些字节能否被当前运行时解释和使用 |

两个 Token Block 的文字相同，但之前的前缀不同，一般不能据此复用同一 KV；前面的输入发生变化，后续链上的 Key 也需要变化。另一方面，同一语义输入在不同实现与数值路径下不一定序列化成逐字节相同的结果。语义复用策略与位级校验策略应分别定义。

跨进程或持久化复用时，应重新核对模型权重 Revision、Tokenizer/预处理、Adapter、多模态输入、位置编码、Dtype、布局与并行分片约定。单个 Engine 中的隐含常量，跨服务后可能需要显式记录；这是一份设计检查项，不是 vLLM 内部字段清单。

仍在追加的 Block 应先留在私有缓冲区，封口后再发布不可变结果。封口还要等待 GPU 或异步 DMA 完成；[[8.11 cudaMemcpy 与 CUDA Stream]] 中的操作提交与数据就绪不是同一时刻。

Cache Salt 只能帮助限定复用键空间，读取仍需要租户授权。若可靠上游和模型仍可用，损坏 KV 可以隔离、取消命中并重算；这个恢复方式不适用于没有等价上游的唯一 Checkpoint。

### 9.2 Checkpoint：Merkle Root 承诺描述，不负责创造一致切面

对分布式训练，Manifest 至少要能定位所有必需 Shard，并关联恢复所需的模型/优化器状态、训练 Step、必要的随机数状态和数据进度。具体字段取决于框架与恢复契约；这是一份应用完整性需求，不是统一文件格式。

假设 Rank 0 写的是 Step 100，Rank 1 写的是 Step 101。两份 Shard 都可以拥有正确的哈希，并一起形成合法 Merkle Root；这个 Root 只承诺了一个混合内容集合，不能把它变成一致的 Step 100 Checkpoint。一致切面必须在捕获状态和提交 Manifest 的协议中保证。

增量收益也要实测。训练过程中很多权重与优化器字节都会变化，不能因为采用 CAS 就预设高去重率。可以共享的内容可能来自未变化的分片、稳定资源或结构元数据，而不是每次训练更新后的所有 Tensor。

异步保存还要固定源缓冲区的所有权：在训练同步点冻结或复制状态到 Staging 区，后台 Hash、压缩和上传结束前不能复用它。否则摘要与上传可能各自读到不同的训练状态。[[8.6 Checkpoint 同步异步分片]] 的完成协议应区分单个 Shard 上传完成、全部 Shard 校验完成和 Root 已发布。

恢复时 GPU 数量或并行配置可能变化。Manifest 应保存 Tensor 的逻辑名称与范围，让恢复器重新分片；旧字节校验与新布局映射都要验证。先压缩整个大文件再切块也可能扩大局部变更，分块压缩则需权衡压缩率和小块成本。

### 9.3 对象存储：把 Key、Version、内容 ID 分开

已有 [[7.7 对象存储路径]] 解释对象请求到存储后端的路径。本篇在它上面增加一个身份层：可以用内容 ID 作为 Key 的组成部分，但对象存储并不会仅因 Key 看起来像 SHA-256，就自动验证上传内容与 Key 相符。

Multipart 是传输组织方式，不自动等于应用 CAS Chunk 的组织方式。S3 的 ETag 也不能被泛化为整个对象的 MD5，特别是 Multipart 等情况；应按具体接口与 Checksum 类型解释完整对象校验和分段/组合校验。[^s3] 这与 [[7.8 Multipart 与 Range GET]] 的关系是：传输边界和验证边界要显式对齐，而非根据字段名字猜测。

应用可以使用 `chunks/<algo>/<digest>`、`manifests/<digest>` 与 `refs/<namespace>/<name>` 组织键空间。一次 `HEAD` 只能证明条目存在；系统仍需通过可信记录和相应校验确认已有内容满足 ID，不能永久复用一个已损坏对象。

将多个 Chunk 打包成 Pack 后，需要受保护的 `chunk_id → pack_id, offset, stored_length, encoding` 索引。Range GET 取回片段后仍应核对边界、解码结果和逻辑摘要。Object Versioning 可以保留同名 Key 的历史，但不替代应用内容身份、保留策略或删除权限。

## 10. 可运行实验：构树、证明与差异定位

使用 Python 3.10+ 标准库，把本节所有 `python` 代码块按顺序保存到同一个 `merkle_lab.py` 后运行。实验统一采用第 4.2 节的类型标签与长度编码、第 5.1 节的填充树规则，增加不可变节点的路径复制；它不采用 RFC 9162 的线格式。

实验只处理内存中的字节与摘要，不实现对象服务、磁盘持久化或网络解析。首次构树、已知位置更新和双树比较是三个独立操作，可以分别观察成本。

### 10.1 定义无歧义的哈希输入

Chunk ID 只绑定可复用字节；叶子再绑定索引与长度；Root 封装绑定实际叶数。每个字段有长度前缀，各类节点有不同标签。

```python
from __future__ import annotations
from dataclasses import dataclass
from hashlib import sha256
from hmac import compare_digest


def u64(value: int) -> bytes:
    if not 0 <= value < 264:
        raise ValueError("value is outside uint64")
    return value.to_bytes(8, "big")


def digest(tag: bytes, *parts: bytes) -> bytes:
    if len(tag) != 1:
        raise ValueError("tag must contain exactly one byte")
    encoded = tag + b"".join(u64(len(p)) + p for p in parts)
    return sha256(encoded).digest()


def chunk_id(data: bytes) -> bytes:
    if not isinstance(data, bytes):
        raise TypeError("payload must be immutable bytes")
    return digest(b"C", data)


def leaf(index: int, data: bytes) -> bytes:
    return digest(b"L", u64(index), u64(len(data)), chunk_id(data))
```

这种编码是本实验的格式。正式协议还要固定算法和格式版本，不能把它标成 CID、JCS 或 Certificate Transparency。

### 10.2 构造不可变节点与确定的树形

每个节点保存半开区间 `[lo, hi)`。实际叶数不足 2 的幂时，用专门的 `E` 摘要填充；空树也保留一个空位，Root 中的 `count` 将它与单个空字节块区分开。

```python
@dataclass(frozen=True)
class Node:
    lo: int
    hi: int
    value: bytes
    left: Node | None = None
    right: Node | None = None


@dataclass(frozen=True)
class Tree:
    count: int
    top: Node

    @property
    def root(self) -> bytes:
        return digest(b"R", u64(self.count), self.top.value)


def parent(left: Node, right: Node) -> Node:
    assert left.hi == right.lo
    return Node(left.lo, right.hi,
                digest(b"N", left.value, right.value), left, right)


def build(chunks: list[bytes]) -> Tree:
    n = len(chunks)
    u64(n)
    width = 1 << (max(1, n) - 1).bit_length()

    def walk(lo: int, hi: int) -> Node:
        if hi - lo == 1:
            value = leaf(lo, chunks[lo]) if lo < n else digest(b"E")
            return Node(lo, hi, value)
        mid = (lo + hi) // 2
        return parent(walk(lo, mid), walk(mid, hi))

    return Tree(n, walk(0, width))
```

首次构树仍读取全部输入，创建线性数量的节点。冻结 dataclass 和不可变 bytes 使旧结构不被原地修改；它们不提供分布式并发或存储持久性保证。

### 10.3 提取自底向上的证明

沿索引下降时记录兄弟摘要，返回时反转为叶子到根的顺序。证明无需重复传左右标记，验证器按索引推导方向。

```python
def make_proof(tree: Tree, index: int) -> list[bytes]:
    if not 0 <= index < tree.count:
        raise IndexError("leaf index out of range")
    path = []
    node = tree.top
    while node.hi - node.lo > 1:
        assert node.left is not None and node.right is not None
        if index < node.left.hi:
            path.append(node.right.value)
            node = node.left
        else:
            path.append(node.left.value)
            node = node.right
    return list(reversed(path))
```

路径提取依赖已保存的节点摘要；若服务端临时重建整棵树，生成证明之前仍会付出全量构建成本。

### 10.4 验证数据、位置、叶数与证明长度

验证器拒绝无效索引、多余或缺少的兄弟摘要，并将最终结果与可信 Root 比较。真实网络入口还需要类型、报文大小、资源上限和算法版本检查；本例假设输入已经正确解析为声明的 Python 类型。

```python
def verify(data: bytes, index: int, count: int,
           siblings: list[bytes], expected: bytes) -> bool:
    if not 0 < count < 264 or not 0 <= index < count:
        return False
    if len(siblings) != (count - 1).bit_length():
        return False
    if len(expected) != 32 or any(len(s) != 32 for s in siblings):
        return False
    node = leaf(index, data)
    pos = index
    for sibling in siblings:
        node = (digest(b"N", sibling, node) if pos & 1
                else digest(b"N", node, sibling))
        pos //= 2
    return compare_digest(digest(b"R", u64(count), node), expected)
```

### 10.5 已知单块变化，只复制受影响路径

`update` 不改旧树，也不复制整份节点数组。只为变化叶子及其祖先创建节点，未变化的兄弟直接复用；重复提交相同内容则返回原树。

```python
def update(tree: Tree, index: int, data: bytes) -> Tree:
    if not 0 <= index < tree.count:
        raise IndexError("leaf index out of range")
    value = leaf(index, data)

    def walk(node: Node) -> Node:
        if node.hi - node.lo == 1:
            return node if node.value == value else Node(node.lo, node.hi, value)
        assert node.left is not None and node.right is not None
        left, right = node.left, node.right
        if index < left.hi:
            left = walk(left)
        else:
            right = walk(right)
        if left is node.left and right is node.right:
            return node
        return parent(left, right)

    top = walk(tree.top)
    return tree if top is tree.top else Tree(tree.count, top)
```

稳定树形下新增节点数为 $O(\log N)$，新块本身仍要哈希。调用者必须已经知道修改位置；该函数不会主动发现磁盘 Bit Rot，也不处理插入、删除导致的树形变化。

### 10.6 对齐树上的 diff

只接受按本实验规则构建、实际叶数相同的两棵树。相等子树立即返回，避免重复遍历；不同的真实叶子才进入结果。

```python
def changed_indices(old: Tree, new: Tree) -> list[int]:
    if old.count != new.count:
        raise ValueError("diff requires aligned leaf counts")
    changed = []

    def walk(a: Node, b: Node) -> None:
        if a.value == b.value:
            return
        if a.hi - a.lo == 1:
            if a.lo < old.count:
                changed.append(a.lo)
            return
        assert a.left is not None and a.right is not None
        assert b.left is not None and b.right is not None
        walk(a.left, b.left)
        walk(a.right, b.right)

    walk(old.top, new.top)
    return changed
```

比较的是已经构建的逻辑承诺；结果不表示所有磁盘副本刚被读取过。CDC 重排、不同叶数与不同版本布局需要额外的对齐策略。

### 10.7 主场景：证明、路径更新与结构共享

只改 8 个块中的索引 3，检查更新结果与全量重建一致、旧 Root 不变、右半棵树和左侧未变子树仍是同一对象。

```python
original = [f"chunk-{i}".encode() for i in range(8)]
old_tree = build(original)
old_root = old_tree.root
updated = original.copy()
updated[3] = b"chunk-3-modified"
new_tree = update(old_tree, 3, updated[3])
path = make_proof(old_tree, 3)
assert verify(original[3], 3, 8, path, old_root)
assert not verify(b"tampered", 3, 8, path, old_root)
assert not verify(original[3], 2, 8, path, old_root)
assert not verify(original[3], 3, 8, path[:-1], old_root)
assert new_tree.root == build(updated).root
assert old_tree.root == old_root != new_tree.root
assert changed_indices(old_tree, new_tree) == [3]
assert old_tree.top.right is new_tree.top.right
assert old_tree.top.left is not None and new_tree.top.left is not None
assert old_tree.top.left.left is new_tree.top.left.left
assert update(old_tree, 3, original[3]) is old_tree
assert chunk_id(b"same") == chunk_id(b"same")
assert leaf(0, b"same") != leaf(1, b"same")
print("proof siblings:", len(path))
print("changed indices:", changed_indices(old_tree, new_tree))
print("path update: matches rebuild; unchanged subtrees shared")
```

### 10.8 空树、单叶、奇数叶与篡改边界

遍历 0～65 个叶子，对每个合法位置检查证明、篡改拒绝、单点更新和 diff。这里把新 Root 与独立的全量重建结果交叉核对。

```python
proof_cases = update_cases = 0
for n in range(66):
    blocks = [f"block-{i}".encode() for i in range(n)]
    tree = build(blocks)
    assert changed_indices(tree, tree) == []
    if n == 0:
        assert not verify(b"", 0, 0, [], tree.root)
    for i in range(n):
        proof = make_proof(tree, i)
        assert verify(blocks[i], i, n, proof, tree.root)
        assert not verify(blocks[i] + b"!", i, n, proof, tree.root)
        assert not verify(blocks[i], i, n + 1, proof, tree.root)
        assert not verify(blocks[i], i, n, proof, bytes(32))
        assert not verify(blocks[i], i, n, proof + [bytes(32)], tree.root)
        if proof:
            assert not verify(blocks[i], i, n, [b"short"] + proof[1:], tree.root)
        proof_cases += 1
        modified = blocks.copy()
        modified[i] += b"!"
        patched = update(tree, i, modified[i])
        assert patched.root == build(modified).root
        assert changed_indices(tree, patched) == [i]
        update_cases += 1
assert build([]).root != build([b""]).root
print("proof cases:", proof_cases, "update/diff cases:", update_cases)
```

预期输出：

```text
proof siblings: 3
changed indices: [3]
path update: matches rebuild; unchanged subtrees shared
proof cases: 2145 update/diff cases: 2145
```

这些断言验证算法在给定输入上的行为。它们不证明密码学安全、分布式发布原子性或存储持久性。

## 11. 从教学实验走向 C++ 存储服务

本篇与 C++/Linux 主线的结合点，不是自己实现 SHA-256 压缩函数，而是把边界落到接口与测试里。可以先定义三个互相独立的接口族：

| 接口族 | 需要保持的不变量 | 建议观察量 |
| --- | --- | --- |
| `put_chunk / get_verified_chunk` | 同一 ID 下接受的逻辑内容唯一；读后验证 | 哈希字节数、验证失败、重复上传比例 |
| `build_manifest / diff_roots` | 编码确定、范围一致、版本结构不可变 | 新增结构节点、访问摘要数、差异字节数 |
| `publish_version / pin_root / collect` | 不发布未就绪引用，不回收受保护引用 | 发布失败、孤儿量、读者租约、GC 延迟 |

实现上让哈希算法来自维护良好的库，以 RAII 管理缓冲区和句柄，明确字节序，给输入长度和递归深度设上限。不要把网络完成、`write()` 返回、持久化确认以及版本发布看成同一个完成事件。

基准测试至少分开记录：输入总字节、真正哈希的字节、读取的摘要节点数、新写的数据/元数据字节、网络传输量、端到端延迟及失败重试。只报告“diff 很快”而不说明树如何生成，会掩盖系统的大头成本。

进一步的工程实验可以在已有 [[7.13 幂等 重试 与请求去重]] 的基础上实现幂等 Chunk 写入，再通过故障注入测试“Chunk 就绪后、Manifest 发布前”中断是否只产生可清理孤儿。这里给的是待实现实验目标，不是本篇笔记已经完成的存储系统测试。

### 11.1 基准测试应覆盖不同变更与读取方式

流水线吞吐受各阶段可持续服务速率约束，重叠执行的耗时不能简单相加。分别测 Staging Copy、Hash、压缩、RPC、落盘与发布等待的处理和排队时间。

| 变量 | 至少覆盖 | 避免的误判 |
| --- | --- | --- |
| 变更模式 | 单点覆写、头部插入、全量更新 | 只测最利于去重的数据 |
| 分块 | 固定小块、固定大块、CDC | 隐藏请求和索引开销 |
| 表示 | 原始、分块压缩、整文件压缩 | 忽略边界扩散 |
| 数据路径 | 热缓存、冷读、远端 | 把内存 Hash 吞吐当存储吞吐 |
| 索引状态 | 已建树、首次构树、路径更新 | 混淆构建和比较成本 |
| 恢复 | 单对象、全版本、重新分片 | 只验证能写，没验证能恢复 |

第 6.1 节算例中，直接对 Payload 生成叶子的平衡树更新需要 1 次叶子 Hash 与 18 次内部 Hash。本篇实验额外计算 Chunk ID、带位置的叶子和 Root 封装，不能照搬 19 次作为代码的实际调用数。

### 11.2 故障注入与验收

在隔离测试对象上注入错误，除检测失败外，还要确认错误数据没有进入计算或再次发布。

| 注入 | 应有结果 |
| --- | --- |
| 改 Payload 一位，保留旧 ID | 拒绝不匹配字节 |
| 调换两块，或修改 Shape 而不更新 Manifest ID | 布局或结构校验失败 |
| 缺一个 Rank 分片 | 版本停留在未发布状态 |
| 两个 Writer 基于同一 Generation 发布 | 只有满足条件的一次提交成功 |
| 返回旧 Root 与合法 Proof | 按版本接受规则处理，不把 Proof 当最新性证明 |
| 已共享 Chunk 丢失 | 列出全部受影响的保留 Root |
| GC 与 Reader/上传并发 | Pin 或保留协议保护正在使用的引用 |
| 缓存 Root 未变，底层字节改变 | 实际重读校验发现损坏 |
| Hash/上传前缓冲区被训练线程复用 | 所有权与完成事件检查暴露问题 |

一个后续原型可以实现临时目录内的 Chunk Store、树形 Manifest 和版本目录，记录共享对象、发布可见点、孤儿清理与修复前后校验结果。本篇已经运行的是第 10 节算法实验；上述系统级实验需要另行实现。

## 12. 常见误区与面试自测

### 12.1 先纠正七个危险的等号

| 错误等号 | 正确边界 |
| --- | --- |
| CAS = 强一致存储 | 内容身份不决定可变名称的线性一致性 |
| Root 相同 = 磁盘此刻没坏 | 可能只是相同的旧摘要，需要实际读取校验 |
| Merkle Proof = 远端保存了全部数据 | 单个成员证明不等于全部数据可取回性 |
| KV Prefix Key = KV 字节哈希 | 前者可以是计算输入身份，后者才校验结果字节 |
| 改一块 = 一定只写 $O(\log N)$ 元数据 | 需要分层持久结构，平铺 Manifest 可能整体重写 |
| 不可变 = 不需要事务/租约 | 发布、GC、版本指针和读者生命周期仍然竞争 |
| Checkpoint 校验通过 = 一定能恢复 | 还要验证一致切面、完整状态与运行时兼容性 |

### 12.2 五个需要说出“为什么”的问题

问题一：1 TiB Checkpoint 验证一个 4 MiB Chunk，为什么不用下载另外近 1 TiB？

因为可信 Root 已经承诺全体条目的结构，目标数据加上路径上的兄弟摘要足以重建 Root。但如果任务是验证本地所有实际副本没有静默损坏，就必须另做数据读取校验，不能把这两个目标偷换。

问题二：为什么换一台存储节点，不应该自动改变数据的内容 ID？

迁移改变的是位置，而不是逻辑内容。把放置加入内容身份，会让一次 Rebalance 扩散成大量 Manifest/Root 变化。应该让放置索引承担位置更新，内容校验保护搬运结果。

问题三：明明只有一个文件条目变化，为什么 Manifest 上传仍然很大？

因为它可能是平铺列表。内容寻址不自动提供持久树形结构；只有把元数据也切成可共享节点，才能沿受影响路径做增量更新。

问题四：两个节点保存的相同 KV Prefix Key，为什么还需要 Blob Checksum？

Key 可能只承诺 Token 前缀和上下文，不承诺存储介质上的具体结果字节。网络传输、缓存、落盘或恢复过程仍可损坏实际 KV，需要独立校验以及格式兼容检查。

问题五：一个旧 Root 的所有 Proof 都能验证，为什么客户端仍然可能被回滚？

因为成员关系只针对那个 Root 成立。是否最新、是否授权发布、是否允许回滚，由受认证的版本记录、一致性协议和客户端接受策略保证。

问题六：为什么去重率高的共享对象需要关注影响范围？

因为一个物理损坏可能使多个保留版本无法恢复。调度要看引用范围、重要性和剩余合格冗余，不能只看坏对象的容量。
