# 3FS 架构

> [[7.3 JuiceFS 架构]] 用「现成组件 + FUSE 拼装」换开发效率，把延迟账单交给对象存储 RTT 与 FUSE 税。3FS（Fire-Flyer File System，DeepSeek 2025 年开源【事实】）走到光谱另一端：为 AI 训练/推理负载定制,**把本仓库前几章的每一件武器全部用上**——NVMe 直通（第 3 章）、RDMA 网络（第 4 章）、io_uring 式共享内存环（第 2 章）、事务 KV 元数据（[[7.2 元数据路径瓶颈]] 第三代）,再用 CRAQ 链式复制拿到「强一致 + 读扩展」。公开基准:180 个存储节点聚合读吞吐 6.6 TiB/s【公开基准】。本篇按由浅到深讲三层:它赌的负载画像、四组件架构与 CRAQ 的一致性机制、以及一次读请求穿过共享内存环与 RDMA 的全路径——等待点与拷贝逐步对账。读完你会发现:3FS 的每个设计都是前几章某条结论的「那就当真做到底」。

前置：[[7.2 元数据路径瓶颈]]（无状态元数据 + 事务 KV 路线）、[[2.1 SQ CQ 模型]]（USRBIO 的形状来源）、[[4.4 内存注册与零拷贝]] + [[4.5 Send Recv 与 RDMA Read Write]]（数据怎么直达用户缓冲）、[[7.1 副本 vs EC]]（链式复制是副本路线的变体）。

## 1. 负载画像：AI 存储赌的三件事

3FS 的所有激进选择都建立在对负载的三个判断上【前提】：

1. **读为主,且是「大文件内的随机大块读」**：训练数据集经打包（[[7.6 AI 存储 vs 传统 NAS]]）后是 TB 级大文件,每步随机抽样读几百 KiB~几 MiB——不是小 IO,但也不是纯顺序;
2. **缓存几乎无用**：数据集远大于内存,且随机抽样让局部性趋近于零——每个样本一个 epoch 只读一次。**page cache 命中率 ≈ 0 还白付一次内核拷贝**,所以 3FS 直接 O_DIRECT 绕开缓存（[[1.3 Buffered IO 与 O_DIRECT]] 「缓存无益则绕开」的教科书案例）【事实/取舍】;
3. **写是大块批量**：checkpoint（[[8.6 Checkpoint 同步异步分片]]）与 KVCache 落盘（[[8.4 KV Cache Offload]]）——吞吐敏感,延迟不敏感。

这三条把设计空间砍到只剩一条路:**不做缓存、不做小 IO 优化,把全部预算押给「聚合带宽」与「强一致」**。对照 [[7.3 JuiceFS 架构]] 的通用负载假设,可以看清「负载画像决定架构」这句话的分量。

## 2. 四组件与 CRAQ：强一致怎么不牺牲读扩展

![3FS 架构与 CRAQ 链式复制：上方为四组件——cluster manager 管成员与链表、无状态 metadata service 把文件语义翻译成 FoundationDB 事务、storage service 管 NVMe chunk、客户端分 FUSE 与 USRBIO 两条路；中部为 CRAQ 链式复制——写请求进 head 沿链传播到 tail 才提交，传播中各节点持 dirty 版本，提交后变 clean，读可打到链上任意节点，clean 直接返回、dirty 需向 tail 查询已提交版本号；下方标注写延迟为链长乘跳延迟、读吞吐为链长倍扩展、与 C++ 版本发布 acquire 检查的对应](../../图片/SVG/3fs-架构与CRAQ链复制.svg)

四个组件,职责刀切【事实】：

| 组件 | 职责 | 关键点 |
| --- | --- | --- |
| cluster manager | 成员管理、故障检测、分发链表（哪些节点组成哪条复制链） | 控制面,不在 IO 路径（[[10.1 数据面与控制面分工]]） |
| **metadata service** | 把 open/stat 等文件语义翻译成 **FoundationDB 事务** | **无状态**——挂了随便换一台,扩展加机器即可;[[7.2 元数据路径瓶颈]] §4.3 路线的纯粹形态 |
| **storage service** | 每节点管本机 NVMe 上的 chunk,执行链式复制 | 数据面主体 |
| client | FUSE 客户端（兼容路径）+ **USRBIO 原生接口**（性能路径,§3） | 文件切成 chunk 分布到多条链 |

**CRAQ（Chain Replication with Apportioned Queries）**是一致性核心【事实】。普通链式复制:写进 head → 逐跳传到 tail → tail 确认即提交;读只能找 tail（唯一确定「已提交到哪」的节点）——强一致,但读全压 tail,不扩展。CRAQ 的改进:

- 每个节点为 chunk 保留版本,写传播中标记 **dirty**,tail 提交后回传确认,各节点标记 **clean**;
- **读可以打到链上任意节点**:该节点若是 clean → 直接返回（最常见情形）;若是 dirty → 向 tail 查询已提交版本号,按版本号返回——多一次小消息往返,但数据不用从 tail 搬【事实】。

账目【事实/取舍】:写延迟 = 链长 × 单跳延迟（RDMA 下单跳 μs 级,3 节点链仍是 μs 级量级）,比主从并行复制的 max(两跳) 略差;换来的是**读吞吐随链长线性扩展**且始终强一致——对「读为主」的负载画像,这笔交换blatantly划算。这也解释了为什么选副本而非 EC:训练读要的就是「任何副本直接读」,EC 的降级读与修复账（[[7.1 副本 vs EC]]）与画像不符【取舍】。

C++ 对照【事实】:CRAQ 的 dirty/clean 就是「写已发生但未发布」与「已发布」——tail 的提交确认沿链回传 = release 发布逐级可见;读端遇 dirty 去问 tail 拿已提交版本 = 不确定时向发布点做一次 acquire 确认。单机内存模型里「写缓冲未刷出时别的核读到什么」的问题,在这里以「链上未提交版本能不能被读到」的形式重演,答案也同构:要么读已发布的,要么去权威处确认版本。

## 3. 数据路径:USRBIO 环与一次读的全流转

FUSE 路径的税在 [[7.3 JuiceFS 架构]] §1 算过:每请求两次切换 + 多跳拷贝。对 6.6 TiB/s 的目标这不可接受,3FS 于是提供 **USRBIO**（user-space ring based IO）原生接口【实现】:应用与 3FS 客户端进程之间建立**共享内存环**——应用把 IO 请求（Iov:目标缓冲、文件偏移、长度）写进提交环,客户端轮询取走执行,完成后填完成环。**形状与 io_uring 的 SQ/CQ 完全同构**（[[2.1 SQ CQ 模型]]）,只是两端从「进程-内核」换成「进程-进程」;应用的读缓冲预先注册给 RDMA 网卡（[[4.4 内存注册与零拷贝]]）,数据可以直达。

一次「读训练样本 512 KiB」的全路径对账（USRBIO + CRAQ clean 读的主路径）:

| 步骤 | 发生什么 | 层级 | 等待点 | 拷贝 |
| --- | --- | --- | --- | --- |
| ① 应用填 Iov 入提交环 | 用户态内存写 + 环发布（release 语义,[[5.6 SPDK 用户态驱动]] §4 同款） | 用户态 | 无（零 syscall） | 无 |
| ② client 轮询取到请求 | 查元数据缓存定位 chunk 所在链,挑一个副本节点 | client | **W1:轮询间隙 + 元数据未命中时一次 FoundationDB 事务往返** | 无 |
| ③ RDMA 发读请求 | 请求消息到 storage service | 网络 | **W2:去程 ~μs**（[[4.1 RDMA 为什么快]]） | 小消息 |
| ④ 存储节点读 NVMe | O_DIRECT 读 chunk:走第 3 章整套本地路径,数据 DMA 进注册缓冲 | 盘 | **W3:盘服务时间,几十 μs——最大头** | T1:盘 DMA → 节点内存 |
| ⑤ RDMA WRITE 回数据 | 节点把数据**直写应用注册好的缓冲**——两端 CPU 不碰数据（[[4.5 Send Recv 与 RDMA Read Write]]） | 网络 | **W4:512 KiB 串行化,~几十 μs @200 Gbps**【量级】 | T2:节点网卡 DMA 读出;H1:本端网卡 DMA 写入用户缓冲 |
| ⑥ 完成事件入完成环 | client 填完成,应用轮询/批量收割 | 用户态 | W5:收割间隙 | 无 |

对账结论【事实】:

1. **全程零 syscall、零内核拷贝、零 page cache**——数据从盘到用户缓冲只经 3 次 DMA（T1/T2/H1）,CPU 一个字节没搬:第 2 章（环）、第 3 章（O_DIRECT）、第 4 章（注册内存 + 单边写）三套机制的串联,「CPU 零拷贝」的口径与 [[5.1 NVMe-oF 架构]] §4 完全一致;
2. 等待点里**盘（W3）仍是大头**,网络两跳合计 ~一个 RTT + 串行化——与 NVMe-oF 的结论同形;元数据（W1）靠客户端缓存摊薄,只在冷启动/失效时付全价;
3. 聚合吞吐的来源不是单次快,而是**每条链、每块盘、每张网卡都可并行**:文件切 chunk 散在多条链上,client 对多个节点同时发起深队列读——[[2.3 iodepth 与提交完成路径]] 的恒满窗打法,打到整个集群规模【事实】。

写路径（checkpoint）差异只在:client 把数据 RDMA 给 head,链式传播 W_chain = 链长 × 单跳,tail 确认后元数据提交——大块顺序写,吞吐由链的聚合带宽决定,延迟被 [[8.6 Checkpoint 同步异步分片]] 的异步化掩盖【事实】。

## 5. 排障清单:症状 → 判定 → 处置

| 症状 | 先看什么 | 典型根因 | 处置方向 |
| --- | --- | --- | --- |
| 聚合读吞吐远低于硬件纸面值 | 单节点盘带宽 × 节点数 vs 实测;chunk 分布是否均匀 | 热点链/热点盘:文件 chunk 分布不均 | 检查文件切分与链表分配;打散热点数据集 |
| 训练读延迟毛刺 | 区分 W1(元数据)/W3(盘)/W4(网络):按段打点 | 元数据缓存失效风暴,或某链 dirty 读集中问 tail | 元数据预热;写读混布时检查 checkpoint 是否与读抢链 |
| 写(checkpoint)期间读性能下滑 | 链上节点的盘与网卡利用率 | 写传播占链带宽,与读争同一批节点 | checkpoint 错峰/限速;读写分池(不同链表)【实践】 |
| FUSE 路径性能远低于预期 | 是否误用 FUSE 而非 USRBIO | FUSE 税(切换+拷贝)在高吞吐下不可摊薄 | 性能路径改用原生接口;FUSE 只留给兼容性场景 |
| RDMA 侧偶发超时/重连 | 网络计数器:PFC 风暴、拥塞([[4.7 PFC ECN 与 DCQCN]]) | 大规模 incast(众节点向单 client 回数据) | 拥塞控制调优;client 侧限制并发扇入 |
| p99 随集群规模变差 | 尾延迟是否被最慢节点决定(fan-out 等齐) | 慢盘/慢节点拖累所有跨它的读 | 慢节点检测摘除([[10.6 健康检查与故障摘除]]);对冲读 |

## 6. 陷阱与误区

> [!warning] 常见错误
> 1. **把 3FS 当通用文件系统评估**:拿小文件/低并发/缓存友好负载测它,结论必然难看——它按 §1 的画像明确放弃了这些场景;架构评估先对负载画像。
> 2. **忽略「无缓存」的另一面**:所有读真打到盘,盘的稳态性能与队列深度直接暴露给应用——[[3.6 空盘与稳态性能]] 的账没有 page cache 兜底。
> 3. **以为强一致必然牺牲读性能**:CRAQ 证明「强一致 + 读扩展」可以同时要,代价转移到写延迟(链长跳数)与 dirty 读的版本查询——先看负载读写比再下结论。
> 4. **链式复制的链长当自由参数**:每加一跳,写延迟加一跳、每字节多占一份盘和一份网——链长 = 容错度 × 写延迟 × 成本的三方约束,同 [[7.1 副本 vs EC]] 的冗余账。
> 5. **USRBIO 环的轮询成本记不进预算**:与 SPDK 同款取舍——client 轮询烧核;部署时 client 的 CPU 配额要按 [[5.6 SPDK 用户态驱动]] §6 的账算。
> 6. **只看 6.6 TiB/s 不看条件**:该数字是 180 节点、特定硬件（多网卡 + 满配 NVMe）、读为主负载下的聚合值【公开基准】——迁移结论前先按自己的节点数与网卡带宽折算上限。

## 7. 关键结论

| 结论 | 性质 |
| --- | --- |
| 3FS 的一切激进选择源于负载画像:随机大块读为主、缓存无益、写是大块批量——画像决定架构 | 前提 |
| 四组件刀切:控制面(cluster manager)不进 IO 路径;元数据无状态化,事务全下沉 FoundationDB | 事实 |
| CRAQ:写沿链传播(dirty),tail 提交回传(clean);读打任意节点,dirty 时向 tail 确认版本——强一致 + 读吞吐随链长扩展 | 事实 |
| CRAQ 的 dirty/clean 就是发布语义的分布式版:release 逐级可见,不确定时 acquire 问权威 | 事实 |
| USRBIO = 进程间的 SQ/CQ 环:零 syscall 提交收割;配 RDMA 注册缓冲,盘到用户缓冲 3 次 DMA,CPU 零拷贝 | 事实 |
| 读路径等待点:盘仍是大头(几十 μs),网络一个 RTT + 串行化,元数据靠缓存摊薄——与 NVMe-oF 同形 | 事实/量级 |
| 聚合吞吐来自全集群并行(chunk 散链 + 深队列恒满窗),不是单次 IO 快 | 事实 |
| 3FS = 前六章结论的集成样本:每个模块对应一章;读源码按对位表走 | 实践结论 |
