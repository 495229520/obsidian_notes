# Split Brain

> [[7.12 Lease 与 Fencing]] 讲的是"一个旧主复活"的时间线，本篇把镜头拉远看空间全景：**网络分区（network partition）**——节点都活着、但互相不可达——会把集群切成几个互相看不见的岛，每个岛都可能保留或选出一个"自认合法"的主。两个主同时接受写，同一份数据长出两条互不知晓的历史，这就是 **split brain（脑裂）**。它比宕机可怕得多：宕机丢的是可用性（服务停了，人人知道），脑裂丢的是**正确性**（两边都返回"写成功"，损坏无声发生）。本篇的核心论点只有一句：**"出现两个自认的主"无法预防——因为"看不到对方"永远推不出"对方已死"；能做到的是让少数派的写必然失败**：多数派裁决在前（选主、提交都要过半），写入终点 fencing 兜底（旧世代号写不进）。理解了这两道防线各自挡什么、漏什么，就理解了几乎所有分布式存储在"节点故障后为何仍然正确"这道题上的答案。

前置：[[7.10 Quorum 读写]]（多数派的数学：W > N/2 保证任意两写交叠）、[[7.12 Lease 与 Fencing]]（判死难题与单调世代号）。

## 1. 名词与背景：分区不是宕机

**网络分区的定义**【事实】：集群中一部分节点与另一部分节点之间的网络通信中断，但**两侧节点自身都在正常运行**。这是它与宕机的本质区别——宕机的节点不再做任何事，分区里的节点还在满负荷服务它能看到的客户端。

类比【类比】：一栋办公楼两层之间的内线电话断了。两层的人都还在上班，各自都以为"对方今天没来"，于是各开各的会、各做各的决定——等电话修好，才发现两层对同一件事拍了板出两个相反的结论。

**为什么分区在真实网络里并不罕见**【事实】。分布式系统的教科书假设常被简化成"网络偶尔丢包"，但生产环境的分区来源要具体得多：

- **交换机/路由器故障**：核心交换机重启、机房间专线中断——最经典的"一刀两半"；
- **网卡半死（单向可达）**：硬件故障或驱动 bug 让 A→B 方向通、B→A 方向丢。此时 TCP 连接在两端都可能显示 `ESTABLISHED`（TCP 是在**收发数据时**才发现对端失联的，空闲连接可以"活"很久）【事实】；
- **防火墙/ACL 误下发**：一条规则把某个端口段掐断——控制面端口通、数据面端口断这类"部分协议分区"尤其迷惑；
- **拥塞**：网络没断，但心跳包排在打满的队列里超时——从检测器视角与断网不可区分（这正是 [[7.11 Primary-Backup 与 Multi-Raft]] 里"没收到回复无法区分死/慢/断"的网络层根源）。

**Split brain 的定义**【事实】：分区的两侧（或多侧）**各自存在一个认为自己有权定序写入的主**，且都在接受客户端写。后果是**数据分叉（divergence）**：同一个键在两侧演化出不同的值与历史，分区愈合后没有任何通用算法能自动判断"谁对"——要么按某种规则丢掉一侧的写（用户视角：静默丢数据），要么把冲突上抛给应用（用户视角：读出两个值）。

一个必须先立住的观念【事实】：**脑裂的根源不是代码 bug，而是信息论层面的不可区分性**——"我收不到 N3 的心跳"这条证据，与"N3 宕机""N3 与我之间断网""N3 只是慢"三种世界完全兼容。任何检测器都只能在超时后**猜**。所以正确的系统不追求"猜得准"，而是把安全性建立在**猜错也不出错**的机制上——这就是后面两道防线的设计哲学。

## 2. 分区的形态学：不只"一刀两半"

不同形态的分区骗过不同的检测器，排障时先判断形态【事实】：

| 形态 | 现象 | 骗过谁 | 常见诱因 |
| --- | --- | --- | --- |
| **对称分区** | 两侧互不可达，岛内正常 | 最"良性"：多数派裁决直接生效 | 核心交换机故障、机房间链路中断 |
| **单向可达（半开连接）** | A 发得出去，B 的回包丢；A 判 B 死，B 觉得一切正常 | 把"发出即算成功"的检测；TCP keepalive（连接看似活着） | 网卡半死、单向 ACL、NAT 表项超时 |
| **非传递分区** | A↔B 通、B↔C 通、A↔C 不通 | 一切假设"连通有传递性"的检测；也让"A 替 C 转达"式的 gossip 出现视图撕裂 | 跨机架局部链路故障、隧道 MTU 问题 |

两条工程推论【实践】：

1. 检测必须要求**双向应答**（我发 ping、收到对方针对这个 ping 的 pong 才算可达），不能用"TCP 连接还在"或"我发出去没报错"代替——应对半开连接；
2. 检测最好有**第三方视角**（让别的节点替你探测，SWIM 式间接 ping，详见 [[7.15 Membership 与故障检测]]）——应对非传递分区。

## 3. 双主如何产生：一条五节点时间线

![[图片/SVG/8_7_14_1.svg|900]]

按图走一遍完整因果链（5 节点，分区切成 2|3）【事实】：

1. **t0**：N1 是主（term=33），客户端甲、乙都写 N1，一切正常；
2. **t1**：分区发生。少数岛 {N1, N2}，多数岛 {N3, N4, N5}。注意客户端也会被分区分到某一侧——甲只能到达少数岛，乙只能到达多数岛；
3. **t2**：多数岛的节点收不到 N1 心跳，超时判 N1 死，发起选举。N4 拿到 3/5 票（多数）当选，term=34；
4. **t3**：**关键时刻**——N1 此刻仍认为自己是主（它看不到多数岛，也就收不到任何"你已被废黜"的通知；这条通知在物理上无法送达）。如果 N1 不做任何自查，它会继续接受甲的写；
5. **t4**：甲写 x=1 到 N1（N1 本地 ack，或 N1+N2 两份 ack）；乙写 x=2 到 N4（3 份 ack）。**同一个键，两条历史，双主既成事实**；
6. **t5**：分区愈合。两侧的日志无法合并——x=1 和 x=2 都自称"已提交"。

这条时间线上没有任何一步是 bug【事实】：每个节点、每个客户端都在按自己看到的世界正确行事。这就是为什么防脑裂不能靠"写更仔细的代码"，只能靠改变游戏规则——让 t4 那一步的"甲的写"**结构性地失败**。

## 4. 防线一：多数派裁决——两侧最多一侧能继续

规则只有两条【事实】：

1. **选主要过半**：候选人必须拿到 > N/2 票才能成为主；
2. **提交要过半**：主的每笔写必须收到 > N/2 个副本的 ack 才算提交（即 [[7.10 Quorum 读写]] 的 W > N/2——它保证任意两个"多数"必有交集，两个主不可能同时各凑一个互不相交的多数）。

推论【事实】：任何分区形态下，**至多一个岛握有多数**。少数岛既选不出新主（凑不齐票），已有的主也提交不了写（凑不齐 ack）——它在结构上被降级为只读或不可用。图中 5 节点 2|3 分区：少数岛最多凑 2 票/2 ack，全部小于 3，甲的写在"提交"这一步就会失败，返回超时或明确的不可用错误。

三个必须说破的细节：

**细节一：旧主要主动自查退位（step down）**【实现】。N1 提交不了写只是"写不成"，但如果它还在**服务读**，客户端会从它读到越来越旧的数据。所以协议要求：主发现自己连续若干周期凑不齐多数心跳应答，就主动放弃主身份、停止服务读写。Raft 的 leader 在无法联系多数派时会停掉 lease read，就是这个动作。**但 step down 依赖本地时钟与线程调度**——一次 STW 停顿就能让它迟到（[[7.12 Lease 与 Fencing]] §3 的完整时间线），所以它只是活性优化，不是安全保证。

**细节二：偶数节点与两副本没有"多数"可用**【事实】。2 节点集群任何分区两侧各 1 票，谁也不过半，全体停摆（这是保正确性的行为，但可用性归零）。解法是 **2+1 仲裁者（witness / tiebreaker）**：第三个节点只参与投票、不存数据，成本极低。双机房对称部署（各一半节点）是同一个问题的放大版——witness 必须放在**第三个故障域**（第三机房/云上），否则机房间断链时两边永远打平。

**细节三：多数派的分母是"成员名单"，名单本身要一致**【前提】。">N/2" 里的 N 是谁定义的？如果两侧对"集群有哪些成员"认知不一致（比如一侧刚加了两台机器而另一侧不知道），两个"多数"可以互不相交，防线一直接失效。所以成员变更必须走共识协议——这是 [[7.15 Membership 与故障检测]] 的主题。

## 5. 防线二：Fencing——少数派的写在终点被拒

防线一的漏洞在细节一里已经露头：**旧主的 step down 可能迟到**（STW、调度冻结），迟到期间它已 ack 过的读、以及仍在管道里的写都可能造成危害；更普遍地，凡是**绕过协议直写存储**的路径（Primary-Backup 的数据面、运维脚本）都不受"提交要过半"约束。

兜底机制在 [[7.12 Lease 与 Fencing]] 已完整展开，这里只放结论【事实】：

- 每任主持有裁判签发的**单调递增世代号**（term / epoch / fencing token）；
- **最终写入点**（真正落数据的存储节点）持久化见过的最大世代号，拒绝一切更小世代号的写；
- 新主上任先带新世代号写一条记录（哪怕 no-op）"关门"，此后旧主的一切写必然被拒——**这条保证不依赖任何时钟**。

对照一个更暴力的传统方案【事实】：HA 集群（Pacemaker 等）的 **STONITH**（Shoot The Other Node In The Head）——不确信对方死，就通过带外通道（IPMI/PDU）直接把对方断电，用物理手段制造"确定的死亡"。它的问题：带外通道自己也可能被分区（然后两边互相开枪，或都开不了枪）。STONITH 与 fencing token 的关系值得体会【设计】：前者试图**消灭对方**来保证唯一性，后者放弃消灭对方、只保证**对方的写无效**——后者不需要额外硬件通道，也没有"互相开枪"的对称死锁，这是现代存储系统普遍选 token 路线的原因。

## 6. 客户端视角：脑裂期间你读到什么

防线齐备的系统里，分区期间客户端的体验按所在岛分化【事实】：

- **多数岛客户端**：短暂抖动（选举期间不可写，通常亚秒到秒级），之后读写正常；
- **少数岛客户端**：写超时/被拒；读则取决于配置——旧主若未及时 step down，可能读到**陈旧但自洽**的数据（不脏、只是旧）。要求"读也必须新"的业务（例如读配置后做资金操作），读路径必须走线性一致读（ReadIndex / lease read，见 [[7.12 Lease 与 Fencing]] §5），此时少数岛的读也会失败——**用可用性换正确性是显式选择**（[[7.9 一致性模型]] 的语义坐标系）。

工程提醒【实践】：客户端 SDK 的**重试逻辑**在分区时是放大器——对"不可用"错误无脑重试会把少数岛的请求反复打向注定失败的节点。正确做法：区分"可重试（超时）"与"应换节点（明确的 not-leader 错误）"，配合退避；这与 [[7.13 幂等 重试 与请求去重]] 的超时语义直接衔接。

## 7. Modern C++：模拟多数派如何消灭双提交

模拟 5 节点集群被随机分区成两个岛，两侧各有一个候选主尝试提交写。对比两种策略：`local`（岛内有 ack 就算提交——无 quorum 系统的行为）与 `majority`（ack > N/2 才算提交）。统计一万次随机分区里"两侧都提交成功"（= 脑裂成立）的比例：

```cpp
#include <algorithm>
#include <cstdint>
#include <print>
#include <random>
#include <vector>

// 一次分区实验：nodes 个节点被随机切成两个岛（每个岛至少 1 台），
// 两侧各有一个自认的主，各自尝试提交一笔写
struct Trial { int island_a = 0, island_b = 0; };

int main() {
    constexpr int kNodes = 5, kTrials = 10'000;
    std::mt19937 rng{42};
    std::uniform_int_distribution<int> cut{1, kNodes - 1};  // 岛 A 的大小

    for (bool use_majority : {false, true}) {
        int split_brain = 0;
        for (int t = 0; t < kTrials; ++t) {
            const Trial p{cut(rng), 0};
            const int a = p.island_a, b = kNodes - a;
            // 各岛的主能收到的 ack 数 = 本岛节点数（对面物理上不可达）
            auto committed = [&](int acks) {
                return use_majority ? acks > kNodes / 2 : acks >= 1;
            };
            if (committed(a) && committed(b)) ++split_brain;  // 两侧都提交 = 分叉
        }
        std::println("{:>8} 策略：双提交比例 = {:5.1f}%",
                     use_majority ? "majority" : "local",
                     100.0 * split_brain / kTrials);
    }
}
```

```bash
g++ -std=c++23 -O2 -Wall -Wextra -o split_sim split_sim.cpp && ./split_sim
#    local 策略：双提交比例 = 100.0%
# majority 策略：双提交比例 =   0.0%
```

怎么读这个结果：`majority` 行的 0 是**结构性的零**——a + b = 5，不可能 a > 2 且 b > 2 同时成立，这就是"任意两个多数必相交"的具体形态；`local` 行的 100% 则说明**不设多数派约束时，脑裂不是小概率事故而是分区的必然结果**。留一个练习：把节点数改成 4（偶数），在切分里允许 2|2——你会看到 `majority` 策略下两侧**都提交不了**（双侧 2 ≤ N/2）：这就是 §4 细节二"偶数打平、全体停摆"的数值版，也是 witness 存在的理由。

## 8. 检测、自愈与演练

**如何在生产中发现脑裂（或它的前兆）**【实践】：

- **双主指标**：每个节点上报 `is_leader`（0/1）布尔指标，监控系统对同一集群求和——**和 > 1 持续超过一个选举周期就该拉警报**。注意瞬时 >1 可能只是选举交接的观测毛刺，要看持续时间；
- **世代号不连续**：客户端/存储侧观察到 term 回退（收到比已见更小的 term 的请求）——说明有旧主复活的写正在被 fencing 拒绝，防线在工作但值得追根因；
- **数据面信号**：副本间校验和对不上、同一键版本分叉——这是**事后**信号，出现即说明防线已被穿透，进入数据修复流程；
- **网络面信号**：节点间 ping 矩阵出现非对称（A→B 通、B→A 不通）或非传递空洞。

**故障演练（在测试集群主动制造分区）**【实践】：

```bash
# 对称分区：在 N1、N2 上执行，掐断与多数岛三台机器的双向通信
iptables -A INPUT  -s 10.0.0.3,10.0.0.4,10.0.0.5 -j DROP
iptables -A OUTPUT -d 10.0.0.3,10.0.0.4,10.0.0.5 -j DROP

# 单向分区（半开连接）：只丢 N1 的入方向——N1 发得出去、收不到回包
iptables -A INPUT -s 10.0.0.4 -j DROP

# 拥塞式"软分区"：不断网，给心跳路径加 2s 延迟 + 抖动
tc qdisc add dev eth0 root netem delay 2000ms 500ms

# 恢复
iptables -F && tc qdisc del dev eth0 root
```

演练要验证的清单（对应 [[9.6 故障注入矩阵]] 的行）：① 少数岛的写在多长时间内开始被拒；② 旧主多久 step down；③ 多数岛选主耗时与期间的 p99；④ 分区愈合后少数岛节点如何追赶日志（对接 [[7.19 副本落后与日志截断]]）；⑤ 全程 `is_leader` 之和的时间线。

**已发生脑裂后的自愈**【实践】：没有通用自动方案。常见流程：确认分叉范围（按世代号与时间窗筛选两侧的写）→ 选定权威侧（通常是多数侧/世代号大的一侧）→ 少数侧的冲突写导出为"待人工裁决"清单交业务方——**丢弃必须是显式决定，不能让系统默默做**。Galera/etcd 等对少数侧的标准处理是清空重同步（把该节点当新节点加入）。

## 9. 排障清单：症状 → 原因 → 检查

| 症状 | 常见原因 | 检查动作 |
| --- | --- | --- |
| 监控里同一集群 `is_leader` 之和 > 1 且持续 | 真脑裂：成员名单两侧不一致 / 选主未走多数派 | 核对两"主"各自的成员视图与 term；查最近的成员变更操作 |
| 分区愈合后用户报"写丢了" | 少数侧曾接受写，愈合时被覆盖/截断 | 按 term 与时间窗审计两侧日志；确认写路径是否有 fencing |
| 少数岛读到越来越旧的数据 | 旧主未 step down 且读走了本地路径 | 查 step down 逻辑的触发条件；读语义是否要求线性一致 |
| 一侧判对方全死、对方毫无感知 | 单向可达（半开连接） | 双向 ping 矩阵；网卡错误计数（`ethtool -S`）；单向 ACL |
| 选举风暴：主换来换去不收敛 | 拥塞式软分区（心跳排队超时）/ 非传递分区 | `tc -s qdisc` 看队列丢包；ping 矩阵找非传递空洞；心跳超时 vs RTT p99.9 |
| 2 节点/双机房集群分区后全体不可写 | 偶数打平，无多数——**这是设计行为** | 补 witness 到第三故障域，而不是调低选主门槛 |
| 加节点后原本正常的集群裂成两主 | 成员变更未走共识，两侧 N 不一致 | 审计成员变更流程；见 [[7.15 Membership 与故障检测]] §5 |
| 存储侧大量 stale-term 拒写日志 | 旧主复活写被 fencing 挡住（防线在工作） | 找旧主为何迟迟不退位（STW/调度冻结）；确认新主已写 no-op 关门 |

---

## 10. 陷阱与误区

> [!warning] 常见错误
> 1. **把"收不到心跳"当"对方死了"**：这是脑裂的第一因。证据在两侧完全对称——唯一可靠的判据是"我这侧是否握有多数"。
> 2. **调低选主门槛换可用性**：旧版 Elasticsearch 的 `minimum_master_nodes` 配小于多数，分区两侧各选 master、各自接受索引写，愈合后一侧被整体覆盖——所有"可调的 quorum"配置都要按多数派下限审查（ES 7.0 起已改为内置多数派，正因这个坑太多人踩）。
> 3. **双机房对称部署不放 witness**：机房断链必打平。witness 必须在第三故障域，且要审计它与两机房的连通独立性。
> 4. **以为多数派够了，不做 fencing**：step down 依赖时钟与调度，STW 冻结的旧主照样能把迟到的写送进无防护的存储——两道防线缺一不可（[[7.12 Lease 与 Fencing]] §3 的构造）。
> 5. **检测只看 TCP 连接状态**：半开连接下 `ESTABLISHED` 毫无意义；必须应用层双向应答。
> 6. **脑裂后让系统"自动合并"**：通用自动合并不存在（除非数据结构本身可交换，如 CRDT）。丢弃哪侧必须是带审计的显式决定。
> 7. **演练只测对称分区**：单向与非传递分区才是检测器的盲区，故障注入矩阵里三种形态都要有（[[9.6 故障注入矩阵]]）。

## 11. 关键结论

| 结论 | 性质 |
| --- | --- |
| 分区 ≠ 宕机：节点都活着但互相不可达；"看不到对方"推不出"对方已死"，且证据在两侧对称 | 事实 |
| 脑裂 = 分区多侧各有自认的主同时接受写 → 数据分叉；丢的是正确性而非可用性 | 事实 |
| 双主的出现无法预防，能保证的是"少数派的写必然失败" | 事实 / 设计 |
| 防线一（多数派）：选主与提交都要 > N/2；任意两个多数必相交 → 至多一侧能继续 | 事实 |
| 多数派的分母是成员名单——名单不一致则防线失效，成员变更必须走共识 | 前提 |
| 偶数节点/双机房会打平；witness（只投票不存数据）放第三故障域是标准解 | 实现 |
| 防线二（fencing）：单调世代号在最终写入点校验，正确性不依赖时钟；STONITH 是硬件版前身，有互相开枪问题 | 事实 / 取舍 |
| 旧主 step down 是活性优化不是安全保证：STW 可让它任意迟到 | 事实 |
| 分区三形态（对称/单向/非传递）骗过不同检测器：检测要双向应答 + 第三方视角 | 实践结论 |
| 脑裂后无通用自动合并；丢弃少数侧的写必须是显式、带审计的决定 | 实践结论 |
