# 9.12 Checksum 与 Hash 工程：CRC32C、xxHash、SHA-256、BLAKE3 与硬件加速

> [!abstract] 本篇的主线
> **先确定要防什么错误，再确定 Hash 哪些字节、输出多少位、如何保存和验证，最后才比较 GB/s。**
>
> CRC32C 适合具有明确错误模型的快速校验；xxHash 适合非对抗性快速索引/指纹；SHA-256 与 BLAKE3 提供密码学摘要能力，但裸 Hash 不提供来源认证。任何算法都无法自动修复错误的字段编码、错误版本选择或可变缓冲区竞态。

[[9.11 端到端数据完整性：ECC、CRC、FCS、RDMA ICRC、NVMe PI 与 Silent Data Corruption]] 解决“保护从哪里到哪里”。本篇解决保护范围内的算法与成本，为 [[8.15 Prefix 淘汰 一致性 与故障恢复]] 的缓存键和 [[8.17 万卡集群分布式 Checkpoint 极致加速实践（MegaScale & DeepSeek 方案）]] 的分片摘要分别建立地基。**这两类 Hash 的输入语义不同，不应只有一个模糊的 `hash()` 字段。**

## 1. Checksum、Hash、Cryptographic Hash：不是三种互斥标签

**Checksum** 常表示“为了检测意外改变而附加的校验值”；**Hash** 表示把输入映射为摘要/散列值的函数；**Cryptographic Hash** 进一步要求抵抗特定的计算攻击。工程讨论里，同一个密码学 Hash 也可以被当作文件 checksum 使用，因此不能按词语外观推导安全属性。

| 你真正需要的性质 | 核心问题 | 示例 | 不能顺带假设 |
|---|---|---|---|
| 错误检测 | 字节发生指定类型的变化，能否发现？ | CRC32C、文件摘要 | 能纠正原始内容 |
| 快速分布/索引 | 键能否均匀落入桶，计算是否便宜？ | xxHash | 同值一定是同一对象 |
| 抗碰撞 | 能否刻意找出任意两个不同输入却同摘要？ | SHA-256、BLAKE3 | 对象来自可信发送者 |
| 抗原像 | 给一个摘要，能否构造一个匹配输入？ | 密码学 Hash | 可以直接用作密码存储 KDF |
| 消息认证 | 不知道密钥的人能否伪造有效内容？ | HMAC-SHA-256、合适的 keyed mode | 旧的合法消息不能重放 |

NIST 对 Hash 安全性质的定义与 HMAC 的认证构造分别见参考资料。**“非密码学 Hash 的输出看上去随机”不是“它具有抗对抗性构造能力”。**[^nist][^hmac]

## 2. 五类算法放到同一张工程表里

| 算法/明确变体 | 常用输出 | 是否为密码学 Hash | 典型定位 | 并行/加速要点 |
|---|---:|---|---|---|
| CRC32C / Castagnoli | 32 bit | 否 | 协议、块或记录的意外错误检测 | 专用 CRC 指令、查表、carry-less multiply/folding |
| XXH64 | 64 bit | 否 | 快速非对抗性指纹、索引 | 面向吞吐的整数运算；不要和 XXH3 混为一种算法 |
| XXH3_64 / XXH3_128 | 64 / 128 bit | 否 | 小键与大缓冲区快速指纹 | 不同长度路径，可用 SIMD；seed/secret 不是 MAC |
| SHA-256 | 256 bit | 是 | 通用内容摘要、可信根的组成部分 | SHA 专用指令；单消息链与多消息并行要区分 |
| BLAKE3，默认 Hash 模式 | 默认 256 bit，可扩展输出 | 是 | 大对象摘要、可利用树结构的并行场景 | SIMD + 内部树；是否多线程取决于 API/实现 |

这里把 xxHash 的变体拆开，是因为文件格式写 `xxhash` 不够具体。`XXH64`、`XXH3_64bits` 和 `XXH3_128bits` 不是相互替换的不同“档位”；算法、seed/secret 参数、输出编码都需要固定。[^xxhash]

也不应写成“SHA-256 永远比 CRC 慢很多”或“BLAKE3 永远最快”：输入大小、实现、CPU 指令集、缓存状态、线程数和内存带宽都能改变结论。后文使用**明确的假设值推导预算**，不把未知目标机器的表现伪装成实测排行榜。

## 3. CRC32C 的数学直觉：对多项式做模运算

### 3.1 把比特串看成 GF(2) 多项式

在 GF(2) 中，系数只有 0/1，加减法都是 XOR。忽略初值、反射和最终异或这些表示约定，设消息为 $M(x)$，生成多项式为 $G(x)$、次数为 $r$，CRC 的核心是：

$$
R(x) = M(x)x^r \bmod G(x)
$$

把余数附加后，得到相应的合法码字。若错误模式为 $E(x)$，且它刚好能被 $G(x)$ 整除，就可能把一个合法码字变成另一个合法码字，从而漏检。

这解释了 CRC 的两个特点：**它针对某些错误模式有结构性的检测保证，而不是纯粹“随机压缩”；它也存在结构性的漏检模式，因此不是防篡改算法。** 对满足通常条件的 $r$ 次 CRC，多项式结构可以保证检测长度不超过 $r$ 的非零突发错误；更长消息和其他错误模式的能力必须结合具体多项式分析。[^crc-model]

这里突发错误的“长度”指首尾错误位之间的跨度，并不要求中间每一位都翻转。也不要把它误读成“任意分布的 32 个坏位都能由 CRC32C 检出”。

### 3.2 CRC-32 与 CRC32C：只差一个 C，结果完全不同

下表使用常见的 reflected 实现约定，省略多项式隐含的最高位 $x^{32}$。

| 名称 | 普通表示多项式 | 反射表示多项式 | ASCII `123456789` 的常见最终 CRC |
|---|---|---|---|
| IEEE CRC-32 | `0x04C11DB7` | `0xEDB88320` | `0xCBF43926` |
| CRC32C / Castagnoli | `0x1EDC6F41` | `0x82F63B78` | `0xE3069283` |

这两个测试向量采用初始状态全 1、输入/输出的相应反射约定、最终异或全 1。协议还可能对结果的字节顺序、覆盖字段和残数检查方式另作规定，**“多项式一样”仍不足以保证线上互通**。CRC32C 的协议说明及测试方法可对照 RFC 3720 附录 B 和 Google CRC32C 的测试。[^iscsi-crc][^google-tests]

容易踩坑的三处是：

- Python `zlib.crc32` 是常见 IEEE CRC-32，不是 CRC32C。
- x86 名叫 `CRC32` 的 SSE4.2 指令计算 Castagnoli CRC32C，不是 Ethernet 的 IEEE CRC-32。
- RoCE ICRC 不等于对 payload 调用一次 CRC32C；其算法与头部规范化边界见 9.11。

### 3.3 一个可编译的 C++20 参考实现

下面是**用来验证参数和流式状态的逐位参考实现，不是性能实现**。把两个 C++ 代码块依次合并为 `crc32c_reference.cpp`。`std::span<const std::byte>` 表达只读、非拥有的字节视图，函数不分配内存，也不接管调用者的所有权。

第一段显式区分“未最终异或的内部状态”和“对外发布的最终值”，避免多段更新时每段都错误地重置/取反。

```cpp
#include <cstddef>
#include <cstdint>
#include <iomanip>
#include <iostream>
#include <span>
#include <stdexcept>
#include <string_view>

std::uint32_t crc32c_update_raw(
    std::uint32_t state, std::span<const std::byte> bytes) {
    for (const auto value : bytes) {
        state ^= std::to_integer<std::uint8_t>(value);
        for (int bit = 0; bit < 8; ++bit) {
            const auto mask = 0u - (state & 1u);
            state = (state >> 1) ^ (0x82F63B78u & mask);
        }
    }
    return state;
}

std::uint32_t crc32c(std::span<const std::byte> bytes) {
    return crc32c_update_raw(0xFFFFFFFFu, bytes) ^ 0xFFFFFFFFu;
}
```

第二段不仅检查已知向量，还遍历所有切分点，证明“把同一输入分两次更新”和一次更新得到相同最终结果。这里的 `update_raw` 是我们定义的接口；生产库的 `Extend` 可能接收已最终化的 CRC，**不能按函数名猜测其状态约定**。

```cpp
int main() {
    try {
        constexpr std::string_view text = "123456789";
        const auto bytes = std::as_bytes(
            std::span<const char>(text.data(), text.size()));
        if (crc32c(bytes) != 0xE3069283u || crc32c({}) != 0u) {
            throw std::runtime_error("known-answer test failed");
        }
        for (std::size_t cut = 0; cut <= bytes.size(); ++cut) {
            auto state = crc32c_update_raw(0xFFFFFFFFu, bytes.first(cut));
            state = crc32c_update_raw(state, bytes.subspan(cut));
            if ((state ^ 0xFFFFFFFFu) != crc32c(bytes)) {
                throw std::runtime_error("streaming test failed");
            }
        }
        std::cout << std::hex << std::uppercase << crc32c(bytes)
                  << "\nPASS: empty, known vector, every split\n";
    } catch (const std::exception& error) {
        std::cerr << error.what() << '\n';
        return 1;
    }
}
```

编译命令如下。这里用优化选项只是正常编译，并不会把逐位算法自动变成具备完整平台分派能力的生产 CRC 库。

```bash
g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic crc32c_reference.cpp -o crc32c_reference
./crc32c_reference
```

预期首行是 `E3069283`，随后是测试通过信息。这是单个线程内的纯计算，不需要把函数调用画成虚假的异步时序。

## 4. 碰撞概率：先区分“找任意一对”与“验证一个既定对象”

![[图片/SVG/8_9_9_12_2.svg|900]]

以下计算假设摘要是**均匀、近似独立的 $b$ 位输出**，输入相互不同，且不是攻击者针对弱算法选择的输入。它用于容量预算和建立直觉，**不是对任意 CRC 错误模式或非密码学 Hash 的安全证明**。

### 4.1 场景 A：一份已知摘要，检查一个错误候选

固定正确对象的摘要后，一个独立错误候选恰好匹配的近似概率是：

$$
P_{one} \approx 2^{-b}
$$

若确实发生了 $K$ 次这样的错误候选比较，至少一次误接受近似为：

$$
P_{miss} \approx 1-(1-2^{-b})^K \approx \frac{K}{2^b}
\quad (K \ll 2^b)
$$

**这里的 $K$ 是错误候选比较次数，不是所有正常读请求数。** 把每天一万亿次正常 I/O 直接乘以 $2^{-32}$，算成每天必然损坏多少文件，是把条件概率和故障发生率混在一起了。

不过，遇到软件把“错误数据和正确配套的新摘要”一同送来的情况，这个模型完全不适用：那不是随机碰撞，而是依据已经被替换。9.11 的最小实验专门演示了这种结构性问题。

### 4.2 场景 B：一个内容寻址空间里，任意两对象是否撞键

如果有 $n$ 个不同对象，它们之间有：

$$
\binom{n}{2} = \frac{n(n-1)}{2}
$$

对可能的比较。令期望碰撞对数为：

$$
\lambda = \frac{n(n-1)}{2^{b+1}}
$$

在适用的生日近似下：

$$
P_{any} \approx 1-e^{-\lambda}
$$

只有 $\lambda\ll 1$ 时，才能继续近似 $P_{any}\approx\lambda$。概率不会超过 1；当 $\lambda$ 很大时，要说“接近必然至少一对碰撞”，而不是“碰撞概率超过 100%”。

| 不同对象数 $n$ | 摘要位数 $b$ | 期望碰撞对数 $\lambda$ | 至少一对碰撞的近似概率 |
|---:|---:|---:|---:|
| $10^6$ | 32 | 约 116.4 | 约 1 |
| $10^6$ | 64 | $2.71\times10^{-8}$ | $2.71\times10^{-8}$ |
| $10^9$ | 64 | 约 0.0271 | **约 2.67%** |
| $10^9$ | 128 | $1.47\times10^{-21}$ | $1.47\times10^{-21}$ |

这不是说十亿个 64 位键必定产生严重业务事故：哈希表可以用完整键比较化解桶碰撞，系统也可能分域、拒绝冲突或存储更长指纹。但它说明：**不能把 64 位指纹当成大规模永久对象身份的数学唯一凭证。**

分域计算时，要按真正独立的命名空间分别预算，再累计整体风险；加入一个公开 namespace 字段并不自动增加输出位数。对攻击者可控输入，不能把 xxHash 的随机输入统计当成抗攻击保证。

### 4.3 截断、重复校验、多重 CRC 的常见误算

把 SHA-256 截断到 64 位后，摘要命名空间就只有 64 位；一般生日攻击工作量的量级对应 $2^{32}$，不能仍宣称拥有完整 SHA-256 的抗碰撞强度。对一般长度的消息，完整 SHA-256 通常以约 128 位抗碰撞、256 位原像安全强度来理解；具体模型及限制以标准讨论为准。[^nist]

对同一字节用同一算法重算两遍，不会获得“双倍摘要位数”。它可能帮助发现部分瞬态计算错误，但若结果、输入和错误模式具有相关性，不能当成独立概率相乘。

两个 CRC 的生成多项式、输入覆盖和错误模式可能相关；如果错误发生在两个生成点之前，两者还会一致地保护错误数据。因此不能直接把“两层 CRC32”记作 $2^{-64}$ 的端到端漏检保证。[^crc-model]

## 5. xxHash：很好的快速指纹，不是密码学认证

xxHash 的目标是快速、良好的分布质量与可移植实现。XXH3 对不同输入长度采用不同路径，并利用适合目标架构的 SIMD 运算；XXH64 则是另一个固定算法。选择时同时看小键延迟和大缓冲区吞吐，而不是只看一张大块 GB/s 图。[^xxhash]

### 5.1 合适的使用模式

**哈希表分桶。** Hash 只负责选择桶，最终用完整键的相等比较确认对象。发生 hash collision 不等于查询结果错误。

**非对抗性快速筛选。** 先用短指纹跳过明显不同的对象，命中后再比较完整内容或更强的摘要。短指纹是加速器，不是唯一真值来源。

**允许明确剩余风险的缓存索引。** 根据容量、输入控制权和错误后果选择 64/128 位，并设计冲突/拒绝策略。不要因为对象“只是缓存”就忽略错误 KV 可能直接改变模型输出。

### 5.2 不合适的推论

xxHash 有 seed 和某些 secret 接口，但它仍被项目定位为非密码学 Hash。不能据此当作 MAC、租户隔离边界或抗恶意内容构造方案。公开 seed 可以划分版本/实例语义，但它不是密钥认证。[^xxhash]

实现还应固定摘要的**规范编码**：返回的整数如何按字节序保存；128 位结果的字段顺序如何约定；是否使用库提供的 canonical 表示。不要直接把包含 padding 的 C++ 对象内存当作跨进程格式。

## 6. SHA-256：顺序的消息压缩链，成熟的使用生态

SHA-256 把消息按规定填充后，以 64 字节块进入压缩链，后续块依赖前一块产生的状态。它支持流式增量更新，但不能把一个文件随便分成四段，分别算 SHA-256，再 XOR 四个结果，就声称得到了标准 `SHA256(file)`。[^sha-standard]

可以利用的并行性主要有三种，含义不同：

| 并行方式 | 是否仍得到标准单文件 SHA-256 | 条件 |
|---|---|---|
| 使用 SHA 专用指令/优化压缩实现 | 是 | 实现正确，CPU/OS 支持相应路径 |
| 多个不同文件/记录并行 Hash | 每个文件各自是标准结果 | 有足够独立消息，可批处理 |
| 自定义分块 Hash 后计算 Merkle root | 根不是标准 `SHA256(file)` | 必须定义新的树格式、顺序、域分离和版本 |

SHA-256 的优势不只在安全强度，也在跨语言、工具与格式兼容。需要某种合规属性时，应确认**具体模块、版本、运行模式和认证范围**；“用了 SHA-256”不自动意味着整套系统获得相应认证。

裸 `SHA256(message)` 能在有可信预期摘要的前提下验证内容，但不证明谁提供了 message。需要消息认证时使用 HMAC-SHA-256 等标准构造，避免自行使用 `SHA256(key || message)`。后者不能替代 HMAC 的安全设计。[^hmac]

## 7. BLAKE3：树结构能并行，但不要把算法和线程池混为一谈

### 7.1 内部 1 KiB chunk 不等于你的 4 MiB Checkpoint chunk

BLAKE3 的算法内部将输入按 **1024 字节 chunk** 组织，每个 chunk 内有 **64 字节 block**。它使用 chunk counter、模式/节点标志和树结构组合内部 chaining value。因而可以在一个大消息内部利用更丰富的并行性，同时保持确定的最终结果。[^blake3-spec]

应用的 Checkpoint 分片可能是几十 GiB，应用校验 chunk 可能是 1–16 MiB。这些都是**外层存储协议粒度**，不需要与 BLAKE3 的 1024 字节内部粒度相等。

![[图片/SVG/8_9_9_12_3.svg|900]]

图上半部的 SHA-256 压缩链与中部 BLAKE3 树，说明的是算法依赖；下半部的 Checkpoint chunk/Merkle root 是应用格式，不能和前两者混为一个结果。

### 7.2 不能自己拼接公开 chunk digest 来复刻标准结果

如下表达式一般**不是**标准 BLAKE3 对完整文件的输出：

$$
\operatorname{BLAKE3}(\operatorname{BLAKE3}(chunk_0)\Vert
\operatorname{BLAKE3}(chunk_1)\Vert\cdots)
$$

原因不只是“树形状可能不对”：独立 chunk 的公开 Hash 输出与算法内部 CV 的用途不同，chunk counter、PARENT/ROOT 等标志也参与定义。应使用官方实现的流式/并行 API；若要自定义对象树，就把它明确命名为另一种**外层 manifest/Merkle 格式**，并固定叶子和父节点编码。[^blake3-spec]

### 7.3 SIMD、不启线程、启线程，是三个不同层次

官方 C 实现的 `blake3_hasher_update()` 是**单线程**接口，但单线程内部仍可利用 SIMD。当前官方 C 文档另外提供可选的 `blake3_hasher_update_tbb()`，需要按对应构建条件使用 oneTBB；它不是普通 `update()` 自动产生的行为。[^blake3-c]

因此基准必须明确：测的是单线程库调用、显式多线程 API，还是 CLI 的默认线程策略。把多核 `b3sum` 与单核 SHA-256 直接比较而不说明核数，只证明了两套运行配置的速度不同。

### 7.4 默认 Hash、keyed mode、扩展输出也不能混用

默认推荐输出通常为 32 字节；BLAKE3 还提供 keyed mode、derive-key mode 和扩展输出。它们的模式语义必须写入协议。输出截短会降低可用强度，而把输出拉长到超过 256 位也不会让底层安全强度无限增长。BLAKE3 也不是为了抵抗离线猜测而设计的慢速、内存困难型密码存储函数。[^blake3-c][^blake3-main]

对 Checkpoint 而言，一个明确的 `BLAKE3-256 / unkeyed / format-v1`，比只写“使用 BLAKE3”更容易做跨实现验证和未来迁移。

## 8. 给 8.15 补地基：Prefix Key 与 KV Byte Digest 是两个对象

[[8.15 Prefix 淘汰 一致性 与故障恢复]] 中的教学性 `hash_combine` 便于讲清哈希链依赖，但它不是生产级抗碰撞身份协议。需要纠正两种过强的表述：

**“内容唯一决定 Hash”是确定性方向；“Hash 唯一决定内容”不成立。** 有限位宽函数必然允许多个输入映射到同一个值。工程方案依赖的是可接受的碰撞风险、适当的威胁模型以及必要的二次验证，不是数学单射。

**“同一前缀能复用”需要计算环境约束。** 键应编码那些会影响 KV 可复用性的状态，例如模型/权重版本、adapter、位置编码相关配置、token 序列和前缀依赖，以及在该系统中影响布局兼容性的 dtype/量化/并行布局。字段取舍应由真实缓存契约决定，不能机械地照抄一份固定清单。

| 字段/摘要 | 输入是什么 | 回答的问题 |
|---|---|---|
| Prefix lookup key | 规范化计算环境 + 前缀 token 链 | 这段语义上下文是否存在可复用条目？ |
| KV byte digest | 实际保存的 KV 字节及其记录描述 | 搬运/存储后是否还是那份字节？ |
| 租户/权限策略 | 身份、授权规则、共享域 | 这个请求是否有权读取该缓存？ |

**对 token 和环境做 Hash，不等于已经对 KV payload 做了完整性校验。** KV 在 DMA、缓存池或远端存储中被损坏，Prefix Key 可能完全不变。反过来，KV 字节自洽，也不能证明它对应了正确的 token 前缀。

### 8.1 一个安全得多的键格式思路

定义应用协议而非声称某框架现行实现：

$$
k_i = H(\text{domain}_{prefix,v1}\Vert
\operatorname{Encode}(\text{environment}, k_{i-1}, \text{token block}_i))
$$

`Encode` 明确 token 整数宽度、字节序、字段长度、父摘要长度以及环境标识。对外部可控内容、跨租户共享及错误命中后果严重的场景，优先审视密码学 Hash 与隔离策略，而不是只把 FNV 风格乘数换成另一个常数。

公开 salt/namespace 可以影响命名空间与缓存共享行为，但不能单独取代授权。某个系统要求每租户不共享缓存时，应由真正的权限和索引规则落实；不能假设“加了 salt，所以所有侧信道和误授权都自动解决”。

## 9. 编码不清晰，再强的 Hash 也会“合法撞上”

考虑两个不同字段元组：`("ab", "c")` 和 `("a", "bc")`。简单拼接后都得到 `abc`，它们 Hash 相同并不是密码学碰撞，**而是你给了 Hash 同一个输入**。

下面的纯 Python 示例使用“字段数量 + 每字段长度 + 字段内容”的固定大端编码；固定域用于把这种对象与其他用途分开。它演示编码约束，不是通用序列化格式或完整的安全协议。

```python
import hashlib
import struct

def framed(fields: tuple[bytes, ...]) -> bytes:
    if len(fields) >= 2**32:
        raise ValueError("too many fields")
    parts = [struct.pack(">I", len(fields))]
    for field in fields:
        if len(field) >= 2**64:
            raise ValueError("field too large")
        parts.extend((struct.pack(">Q", len(field)), field))
    return b"".join(parts)

def key(fields: tuple[bytes, ...]) -> bytes:
    return hashlib.sha256(b"prefix-example/v1\x00" + framed(fields)).digest()

assert b"ab" + b"c" == b"a" + b"bc"
assert framed((b"ab", b"c")) != framed((b"a", b"bc"))
assert key((b"ab", b"c")) != key((b"a", b"bc"))
print("PASS: field boundaries remain distinct")
```

在真实协议里还要规定 UTF-8/Unicode 规则、是否允许重复字段、整数的有符号性、空值和空字符串的区别、浮点表示、未知字段和版本迁移。JSON `sort_keys=True` 本身不是完整的跨语言规范化协议；确需规范化 JSON 时，可对照 RFC 8785 的约束，不把某个语言的默认序列化当作全球统一编码。[^jcs]

更不要 Hash C++ 结构体的原始内存：padding 可能未初始化，字段布局受 ABI 影响，整数与浮点表示也未必满足跨平台格式要求。**格式稳定性比在内存中少调用一次 encode 更值得优先保证。**

## 10. 给 8.17 补地基：Chunk Digest、Manifest Root 与可信提交

建议把 [[8.17 万卡集群分布式 Checkpoint 极致加速实践（MegaScale & DeepSeek 方案）]] 的校验设计拆为三件独立工作：

**Chunk digest。** 对稳定的存储表示生成精确摘要，方便并行验证、定位坏块和局部重传。摘要位数依据容量与威胁模型选定；32 字节的密码学摘要经常是值得评估的基线，而不是任意场景强制配置。

**Manifest root。** 绑定有序 chunk 描述符、各自摘要、完整对象范围、epoch 与格式版本。外层 Merkle root 可以采用 SHA-256 或 BLAKE3 构造，但它是自定义格式的根，不能谎称是标准整文件摘要。叶子和内部节点必须采用不同域或无歧义的类型编码，固定树形和最后一个不完整块的处理规则。

**受信提交记录。** 保存/认证根摘要及允许恢复的版本。裸根摘要不能自行建立信任；认证后的旧根也需要按恢复策略处理。验证顺序与生成边界延续 9.11，不在这里用“算法更强”掩盖协议空洞。

### 10.1 粒度的账：校验值本身通常不大，管理成本才容易被漏掉

设总数据量 $S$、应用 chunk 大小 $C$、每个摘要 $h$ 字节：

$$
N_{chunk}=\left\lceil\frac{S}{C}\right\rceil,\qquad
M_{digest}=N_{chunk}h
$$

**示例假设：** $S=1\ \mathrm{TiB}$，$C=4\ \mathrm{MiB}$，$h=32$ 字节。

计算得 $N_{chunk}=262{,}144$，纯摘要数组大小为 **8 MiB**；相对数据的比例约 **0.000763%**。这只是摘要字段，不包含描述符、索引、manifest 编码、树节点、认证信息、RPC 和分配器开销。

变小的 chunk 可以改善坏块定位、并行调度和失败重传粒度，但会增加条目数、每条固定开销及管理负担。变大的 chunk 减少元数据，却增加重读/重传放大和验证完成前的等待。不要因为“Hash 才 32 字节”就断言整个 chunking 方案几乎没有成本。

## 11. 硬件加速：专用指令、SIMD 与多线程分别优化什么

| 路径 | 加速方式 | 需要特别核对的条件 |
|---|---|---|
| x86 CRC32C | SSE4.2 的 CRC32 指令 | 算法是 Castagnoli；运行时是否可用 |
| CRC 多项式 folding | PCLMULQDQ/相应 carry-less multiply 路径 | 多项式、归约常数、分块长度与实现正确性 |
| ARM CRC | 架构 CRC 扩展的相应指令 | CRC32 与 CRC32C 指令/接口不同，不能选错 |
| SHA-256 | SHA 专用指令与优化汇编实现 | CPU 特性、库分派、目标构建和消息粒度 |
| XXH3 / BLAKE3 | SSE/AVX/NEON 等 SIMD 路径 | 支持的 ISA、OS 状态支持、数据长度、实际 dispatch |
| 多核 Hash | 多消息并行或算法支持的单消息并行 | 线程数、NUMA、调度成本与共享内存带宽 |

Google CRC32C 明确提供面向 x86/ARM 的硬件加速路径；BLAKE3 C 实现包含多种 SIMD 实现与分派逻辑。**编译时存在这些代码，不等于运行时一定使用了期望路径。**[^google-crc][^blake3-c]

还要避免一个名词陷阱：x86 CRC32 指令属于 SSE4.2 扩展，但其 CRC 状态操作不等同于“自动把一大段字节以 SIMD 并行扫完”。单一 CRC 状态存在依赖链；高吞吐实现可能利用独立流、合并或 folding 技术。是否使用向量寄存器、一次处理多少字节，要看真正的实现，不看宣传里的 ISA 名称。

正确的部署策略通常是运行时分派加可用的 portable fallback，并为不同路径运行相同向量和随机测试。开发机用 `-march=native` 编译的二进制，不应未经检查就部署到 ISA 较旧或能力不同的机器上。

## 12. GB/s 成本：先算吞吐预算，再讨论“能不能隐藏”

![[图片/SVG/8_9_9_12_4.svg|900]]

以下全是**标明假设的预算推导，不是本机或某款 CPU 的实测值**。统一使用：`GB/s = 10^9 byte/s`，`GiB = 2^30 byte`，避免把网络 Gb/s、十进制 GB/s 和二进制 GiB/s 混在一起。

### 12.1 单次完整 Hash 的计算时间

设输入 $S$ 字节，当前线程配置下有效 Hash 吞吐为 $B_h$：

$$
T_{hash}=\frac{S}{B_h}
$$

对 **64 GiB** 输入，只改假设吞吐：

| 假设有效吞吐 | 对 64 GiB 的纯 Hash 时间 | 含义 |
|---:|---:|---|
| 2 GB/s | 34.36 s | 必须评估多核、并行或更早的流水化 |
| 10 GB/s | 6.87 s | 不表示这 6.87 秒都能隐藏 |
| 25 GB/s | 2.75 s | 仍要检查内存/存储是否共享瓶颈 |

这里没有磁盘读取、网络等待、元数据处理和 Hash 验证重读。若生产写入端和恢复端都要扫一遍，同一份数据的生命周期至少还涉及两次相应的摘要计算工作；它们可能发生在不同时间、不同机器上，不能简单算作同一时刻的两倍核数。

### 12.2 持续流的核数预算

设要处理的有效载荷流量是 $R$ GB/s，单核可持续 Hash 吞吐为 $B_c$，使用 $C$ 个核，Hash 服务利用率近似为：

$$
\rho=\frac{R}{C B_c}
$$

若要求平均利用率不超过 $u$，理想核数下界为：

$$
C \ge \left\lceil\frac{R}{u B_c}\right\rceil
$$

**例：** 400 Gb/s 是原始位速率 **50 GB/s**；假设扣除各种影响后的目标 payload 为 **40 GB/s**，假设单核实测可持续 **8 GB/s**，那么算术容量至少 5 核。若为波动预留空间、目标 $u=0.5$，则需要约 **10 核**。

“5 核刚好够”只是一条平均容量等式。它没有为突发、调度、NUMA、慢 chunk 和尾延迟留空间；真实核数也不一定线性扩展，因为这些核共享缓存和内存控制器。

### 12.3 内存流量：Hash 不是零成本读取

考虑明确的简化场景：GPU D2H DMA 把 $S$ 字节写入 Host staging，CPU Hash 读一遍，RNIC 再读一遍发送。如果三段流量都经过我们计量的内存边界，而且没有缓存命中抵消，那么主机内存流量预算约为：

$$
S_{D2H\ write}+S_{hash\ read}+S_{NIC\ read}\approx 3S
$$

这是**边界定义下的流量模型**，不是所有平台的内存控制器计数都必然等于 $3S$。缓存命中、DMA 一致性、DDIO、写分配和额外拷贝可能改变实测结果。若又用另一个 CPU 遍历算 CRC，则可能再增加一次读；若把编码/拷贝/Hash 融合，可能减少额外遍历，但仍要付计算和至少一次数据访问成本。

因此整体可持续吞吐有一个类似 roofline 的上界：

$$
R_{pipeline}\le
\min\left(CB_c,\frac{B_{mem}}{a},B_{network},B_{storage},B_{other}\right)
$$

其中 $a$ 是相对于有效载荷的实际内存流量放大系数，必须在选定计量边界下解释；`B_other` 可包含压缩、编码等剩余阶段的吞吐上限。

### 12.4 串行时看求和，流水时看瓶颈，还要看排队

完全串行的处理时间近似：

$$
T_{serial}=T_{read}+T_{hash}+T_{write}
$$

充分重叠、缓冲有界且阶段资源不严重互相争用时，大量 chunk 的稳态时间受最慢阶段控制，可粗略写成：

$$
T_{pipeline}\gtrsim
\max(T_{read},T_{hash},T_{write})+T_{fill/drain}
$$

这并不意味着可以无上限并发。Hash 阶段追不上输入时，队列会积压；为了保护训练或在线推理的 P99，需要对 chunk 数、buffer 字节、队列等待时间和 CPU/NUMA 资源施加约束。相关方法接到 [[9.10 跨层性能归因：CPU、NUMA、PCIe、NIC、Switch、RDMA 与 NVMe 的 P99]]，而不是只展示一个单函数 GB/s。

### 12.5 在 GPU 上 Hash 是否更好？

数据已经在 GPU 上时，GPU 侧生成摘要可能把保护起点前移，且避免为了 Hash 再额外搬一份数据。但它也消耗 SM/HBM 带宽，并需要正确的 stream/event 依赖。数据原本不在 GPU 上时，搬到 GPU 再算可能得不偿失。

比较时应计入端到端路径及训练干扰，而不是只比较 GPU kernel 与 CPU loop 的内部吞吐。无论选择哪个位置，都必须明确它实际覆盖哪些字节变化；性能选择同时是在选择 9.11 中的保护边界。

## 13. Benchmark Matrix：测出“为什么快”，而不是贴一张排名

### 13.1 至少控制这些维度

| 维度 | 建议测试点 | 为什么影响结论 |
|---|---|---|
| 输入大小 | 16/64/256 B，4 KiB，1/4/16 MiB | 初始化、尾块处理和大块吞吐占比不同 |
| Working set | 固定小缓冲、适合 LLC、明显超过 LLC 的轮换缓冲 | 缓存带宽不等于 DRAM 带宽 |
| 并发 | 单线程，固定核数，目标业务并发 | 区分算法速度与多核扩展 |
| NUMA | 本地分配/本地执行，对照远端访问 | 远端访问和互连会改变上限 |
| 输入组织 | 连续缓冲，分散小片，真实序列化对象 | API 调用与拷贝可能主导 |
| 实现 | 版本/commit、编译器、优化参数、实际 ISA 路径 | 算法名相同不代表执行路径相同 |
| 路径 | 内存微基准、文件流、真实 Checkpoint/恢复 | 纯计算时间不等于服务完成时间 |

对同一输入先验证摘要正确，再计时。所有候选算法处理相同的输入规模和工作集；计时区外完成分配、数据准备和必要的预热，避免编译器删掉结果。不同算法的摘要值本来就不同，不能用“都返回同一个摘要”作为跨算法正确性测试。

### 13.2 如何读取官方性能数字

xxHash README 曾给出在 i7-9700K、Ubuntu 20.04、clang 10 `-O3` 等固定条件下的吞吐示例，其中 XXH3 的 SSE2 大块结果约为 **31.5 GB/s**。同页也提示缓存驻留数据可能出现超过主存带宽的结果。**它是特定实验的历史结果，不是目标服务器的性能承诺，也不是 31.5 GB/s 的网络/文件端到端吞吐。**[^xxhash]

阅读任何表格时先寻找 CPU、输入大小、工作集、线程数、是否含 I/O、单位和实现版本；缺其中几项，就把结果当作“值得测试的线索”，而不是容量规划依据。

### 13.3 一个没有额外依赖的 SHA-256 测量骨架

下面脚本使用 Python 标准库，实际 Hash 由运行环境中的实现承担。它只测**同一个 32 MiB 缓冲重复参与 one-shot SHA-256**，不能代表纯 DRAM 扫描，也不能作为 CRC32C/xxHash/BLAKE3 的对比结果。使用 Python 3.10+ 保存为 `sha256_bench.py` 后运行。

```python
import hashlib
import os
import ssl
import statistics
import time

size, repeats, rounds = 32 * 1024**2, 8, 7
data = os.urandom(size)  # 分配和随机数据准备不进入计时。
expected = hashlib.sha256(data).digest()
rates = []
for _ in range(rounds):
    cpu_start, wall_start = time.process_time(), time.perf_counter()
    result = None
    for _ in range(repeats):
        result = hashlib.sha256(data).digest()
    wall = time.perf_counter() - wall_start
    cpu = time.process_time() - cpu_start
    if result != expected or wall <= 0:
        raise RuntimeError("invalid benchmark result")
    rate = size * repeats / wall / 1e9
    rates.append(rate)
    print(f"{rate:.3f} GB/s; wall={wall:.4f}s; CPU={cpu:.4f}s")
print(ssl.OPENSSL_VERSION)
print(f"median={statistics.median(rates):.3f} GB/s; fixed-buffer test only")
```

这里输出 wall time 与 process CPU time，是为了不把“用了多少 CPU 时间”和“用户等了多久”混成一项。真实评估还应记录 CPU 型号、频率策略、线程/CPU affinity、NUMA、负载和实际实现路径。脚本打印 OpenSSL 版本用于环境记录，**并不证明所有 Hash 操作在任何 Python 构建中都由相同 OpenSSL 后端执行**。

扩展到其他算法时保留同样的输入和计时结构，换成相应库的生产 API，并记录参数。不要用本篇逐位 C++ 参考 CRC 对比某个优化汇编 SHA/BLAKE3，再得出“CRC 天生更慢”的结论。

### 13.4 真正应该交付的结果

除了 GB/s，至少给出 `cycles/byte、CPU time、线程/核数、chunk latency P50/P99、验证队列等待、额外内存流量、业务 P99/MFU 变化`。对于恢复路径，还要看坏块重读比例、失败对象定位时间以及完整恢复时间。

不要把七轮微基准的总耗时分位数标成生产请求 P99。微基准验证实现上限；真实负载与 [[9.7 SLO 与性能回归]] 的门禁验证这项优化是否值得上线。

## 14. 选型示例：把“快”和“可信”放在不同职责上

以下是工程起点，不是对所有系统的固定推荐。

| 场景 | 可评估的起点 | 必须同时设计的部分 |
|---|---|---|
| 固定协议规定 CRC32C | 正确实现 CRC32C，优先成熟分派库 | 精确覆盖字段、初值/最终值、字节序和错误处理 |
| 进程内哈希表 | xxHash 等快速 Hash + 完整键比较 | 哈希碰撞处理、输入控制权和 DoS 风险 |
| 非对抗性缓存指纹 | XXH3_128 等候选 + 明确碰撞预算 | 语义身份、冲突策略、实际数据校验 |
| 长期 Checkpoint/大对象 | SHA-256 或 BLAKE3-256 等候选 | 稳定表示、分块、受信 manifest、恢复验证 |
| 不可信来源/需要来源认证 | 合适的 MAC/签名协议 | 密钥、版本、防重放策略与可信根 |

一种常见的分工设计是：局部路径使用协议规定的快速 CRC，应用对象使用更长的摘要，manifest 再有明确的信任/认证机制。**这些机制解决不同问题，不能把它们的位数简单相加作为总安全强度。**

有时额外算第二种摘要值得，有时反而多扫一遍内存、增加队列和尾延迟。判断依据应是新增了什么保护、是否兼容现有格式，以及测得的资源成本，而不是“多一种总比少一种好”。

## 15. 自测：能答清这些问题，才算把 Hash 地基补齐

**问题一：为什么十亿个 64 位指纹要考虑约 2.67% 的任意碰撞概率，而校验一个错误文件不是这个概率？**

前者比较的是 $n(n-1)/2$ 对不同对象，属于生日问题；后者把一个错误候选与一个固定预期摘要比较，均匀模型下约为 $2^{-64}$。两者事件空间不同。真实错误率与攻击输入还需另建模型。

**问题二：把 CRC32C 换成 SHA-256，能修复“rank 7 文件和其摘要一起被当作 rank 8”吗？**

不能只靠更换算法修复。必须绑定对象描述符，并由独立的恢复请求/manifest 规定期望身份。否则只是给错误对象提供了更强的自洽检查。

**问题三：BLAKE3 能多核并行，为什么调用 `blake3_hasher_update()` 仍可能只占一个核？**

算法提供并行机会，不代表该 API 自动创建线程。官方 C 普通 update 是单线程，可利用 SIMD；显式多线程 API/CLI 的策略和构建条件需要另核对。

**问题四：为什么 Cache Key 没变，也不能证明 KV 数据没坏？**

Cache Key 通常 Hash token 前缀和环境；KV Byte Digest Hash 实际 KV payload。输入对象不同，一项不能替代另一项。

**问题五：40 GB/s 输入，单核 8 GB/s，分配 5 核是不是性能问题解决了？**

这只是理想平均容量相等，利用率已到 1。还必须给突发与尾延迟留余量，并确认多核扩展、NUMA、内存流量和其他流水阶段不是更低的上限。

> [!tip] 最后记住这条设计顺序
> **错误/威胁模型 → 保护起止点 → 输入编码和身份 → 算法/位数 → 可信依据 → 生命周期与验证门禁 → CPU/内存/队列成本 → 真实恢复测试。**
>
> 从“哪种 Hash 最快”开始，往往会跳过最容易造成错误恢复的前五项。
