# 完整性、认证与机密性：Checksum、Hash、HMAC、AEAD 与 AES-GCM

假设你向对象存储上传了一份 Checkpoint，恢复前要回答三个问题：**读回来的字节有没有变化，这些字节是不是被授权的一方写下的，存储服务商能不能看懂内容？** 这三个问题分别对应完整性、认证和机密性。一个算法不一定同时回答它们。

再加两个存储系统问题：这是不是应该恢复的最新版本，以及远端是否还保有足以恢复的数据。前者需要可信版本状态，后者进入 [[7.33 PDP 与 PoR：远端数据持有、可取回性与抽样验证|PDP、PoR 与抽样审计]]。**不要把一次 Hash 相等、一次 AEAD 解密成功、一次远端审计通过，写成同一种“验证成功”。**

> [!info] 本篇范围
> 面向存储、网络和 AI Infra 工程：学习选对原语、定义被保护的字节、管理 key/nonce，以及处理验证失败。不会从零实现 AES、GHASH 或密码协议。
>
> 资料核对日期：2026-09-16。GCM 的具体上限以 NIST SP 800-38D **2007 年正式版**为锚点；2026 年修订工作仍处于预草案征求意见阶段，不能把拟议变更当作已经发布的新标准。示例采用完整 128-bit tag，不依赖截短 tag。[^nist-gcm][^nist-revision]
>
> 文中的容量与概率均为注明假设的计算，代码为本地教学实验，不是云存储产品的安全认证或吞吐量实测。

## 1. 先定义安全目标，再讨论算法

### 1.1 三个主目标，两个容易漏掉的目标

**Integrity，完整性**：相对于某个可信基准，检测数据是否被不允许地改变。“完整”不只是每个块内部的字节没变，还可能要求块的顺序、数量、文件长度和元数据关系正确。

**Authenticity，真实性／消息认证**：确认数据能通过某种授权凭据的检验。MAC 验证成功说明消息与共享密钥下的认证关系成立；它不能区分共享同一把密钥的几个参与者，也不是“某个人签过字”的证据。

**Confidentiality，机密性**：未经授权的一方不应获得被保护的明文内容。加密通常仍会泄露长度、访问时序等信息，除非协议另外处理这些泄漏。

**Freshness，新鲜性／防重放与防回滚**：一个合法的旧 Checkpoint 仍然可能有正确的 Hash、MAC 和 AEAD tag。判断它是否过期，需要消息序号、generation、可信提交记录或其他防回滚状态。

**Availability / Retrievability，可用性／可取回性**：对方能不能提供数据，或者其状态中是否保有足以恢复文件的信息。MAC、AEAD 本身不能阻止删除，也不能保证未来恢复速度。[^aead][^hmac]

图中把“字节正确”“授权写入”“隐藏内容”与“版本最新”“能否恢复”分开。后两项并不是增加一个更长的 tag 就能得到的性质。

### 1.2 威胁模型要写到具体参与者

| 事件或攻击能力 | 单独对比本地可信 Hash | 共享密钥 MAC / 正确使用的 AEAD | 还需要什么 |
|---|---|---|---|
| 介质上的随机 bit flip | 通常能检出 | 验证通常失败，但不能据此判断根因 | 重读、隔离、定位、可信副本修复 |
| 攻击者同时改文件和同目录的 `.sha256` | 只有旧摘要仍可信时才有意义 | 不掌握 key 时，不能据此自由生成有效认证值 | 保护可信基准与密钥 |
| 攻击者返回一个合法旧版本 | 能通过旧版本对应的 Hash | 能通过旧版本对应的认证 | 可信“期望版本”与拒绝回滚策略 |
| 攻击者交换两个块的位置 | 只验证块内容可能仍通过 | 未绑定对象／位置时也可能通过 | 认证索引、长度、对象身份、manifest |
| 攻击者删掉整个尾部或某个文件 | 已读取块的验证可全部成功 | 已读取块的认证可全部成功 | 可信文件清单、总长度、块数、提交边界 |
| 拥有写入 key 的程序写错张量 | Hash 能忠实对应错误结果 | 错误结果也能获得合法认证 | 业务一致性检查和恢复演练 |
| 对方删除全部数据，只保留摘要 | 摘要仍能返回 | 旧 tag 仍能返回 | 读取真实数据、审计协议、冗余与备份 |
| 加密 key 丢失，密文仍完整 | 密文 Hash 完全正常 | 无法恢复明文 | 可恢复且受控的密钥备份 |

表中的“认证通常失败”是在 key 未泄漏、参数与实现正确的前提下说的。**安全结论必须带上前提，不能只有算法名字。**

## 2. Checksum、Hash、MAC 和签名：差异不在输出长得像不像

### 2.1 原语选择表

| 原语 | 是否用秘密 | 主要用途 | 单独不能提供什么 |
|---|---|---|---|
| CRC 等 checksum | 否 | 按其检测能力发现偶然传输／存储错误 | 面向主动攻击者的消息认证、保密 |
| xxHash 等非密码学 Hash | 否 | 快速散列、非对抗性指纹等 | 不能把它当密码学抗伪造承诺 |
| SHA-256 等密码学 Hash | 否 | 内容指纹、内容寻址、可信摘要比较、协议组件 | 没有可信基准时不自动认证来源；不加密 |
| HMAC-SHA-256 | 是，共享密钥 | 消息认证及对认证内容的完整性保护 | 不保密、不自动防重放、不区分同 key 持有者 |
| 数字签名 | 私钥签名，公钥验证 | 允许不持有签名私钥的一方检查签名 | 不自动保密；公钥与身份的关系仍须可信 |
| AEAD，如 AES-GCM | 是，共享密钥 | 同时加密明文、认证密文与关联数据 | 不自动防回滚、保可用、证明作者身份 |

这张表是**用途边界**，不是吞吐量排名。实际实现可能利用不同的硬件指令，不能仅按“CRC 比 Hash 短”推断整条 I/O 路径的性能。[^hmac][^aead][^nist-gcm]

### 2.2 Hash 为什么不等于认证

把 `data.bin` 和 `SHA256(data.bin)` 放在同一个不可信目录，攻击者完全可以把它们一起换成：

```text
modified.bin
SHA256(modified.bin)
```

攻击者不需要寻找 SHA-256 碰撞，只需要重新计算一次公开函数。问题出在**验证基准也被攻击者控制了**，不是 SHA-256 的碰撞安全性失效。

如果客户端事先安全地保留了旧摘要，或者摘要来自经过认证的 manifest，那么 Hash 比较就有了可信锚点。攻击者此时需要让不同内容匹配那个被固定的基准，不能再简单地改完文件后重算摘要。

![[图片/SVG/8_9_9_13_2.svg|900]]

图左表示“文件与摘要都来自同一个不可信地方”；图右表示认证 key 留在可信侧。可信 Hash、可信公钥和秘密 MAC key 的信任模型不同，不能统称为“服务端返回的校验码”。

### 2.3 不要混淆三种 Hash 安全目标

**原像抵抗**：给定摘要，难以找出一个输入。**第二原像抵抗**：给定一个具体输入，难以找出另一个具有相同摘要的输入。**碰撞抵抗**：难以找出任意两个不同而摘要相同的输入。

对理想的 256-bit Hash，通用碰撞搜索的生日界量级是 $2^{128}$，不是 $2^{256}$；这并不意味着匹配一个指定可信摘要也只需同样的工作量。工程上先分清攻击目标，不要把“256 位输出”机械换算成所有场景下的同一安全强度。

更不能把 Hash 当加密：低熵输入可以被字典枚举，摘要并不提供可逆的授权解密接口。

## 3. HMAC：公开 Hash 与秘密 key 的标准组合

### 3.1 HMAC 的结构

HMAC 定义为：

$$
\operatorname{HMAC}_K(m)=H\bigl((K_0\oplus opad)\parallel H((K_0\oplus ipad)\parallel m)\bigr)
$$

其中 $K_0$ 是按 Hash 的**分组长度**处理后的 key，过长时先 Hash，再补零；`ipad` 为重复的 `0x36`，`opad` 为重复的 `0x5c`。对于 SHA-256，分组长度是 64 字节，摘要输出是 32 字节，两者不能混淆。公式解释设计边界，实际代码调用经过维护的库。[^hmac][^sha]

不要自行替换为 `SHA256(key || message)`。对 SHA-256 这类结构，简单前缀拼接会暴露长度扩展问题；标准 HMAC 不是这种构造。也不要用 `SHA256(message || key)` 或“双 Hash 几次”临时设计自己的 MAC。

**HMAC 没有要求每条消息使用一个 nonce。** 相同 key 和相同消息得到相同 MAC 并不构成 HMAC 的误用。但同一消息被再次提交时依然能够通过认证，因此防重放必须在被认证消息中绑定序号、上下文，并由接收者维护接受规则。[^hmac]

### 3.2 一个能运行的替换实验

下面模拟攻击者能改数据与公开摘要，但不能读到客户端的 MAC key。先准备初始数据及可信认证值；随机 key 只存在于本次进程，不输出到日志。

```python
import hashlib
import hmac
import secrets

key = secrets.token_bytes(32)
original = b"checkpoint: step=100; tensor=correct"
changed = b"checkpoint: step=100; tensor=modified"
trusted_mac = hmac.digest(key, original, "sha256")
```

攻击者可以重新计算公开摘要，却不能在不知道 key 的条件下自由签发正确的 HMAC。比较认证值时使用常量时间比较接口，而不是手写“逐字符比到第一个不同就返回”的函数。

```python
attacker_digest = hashlib.sha256(changed).digest()
print("替换数据和摘要后：", hashlib.sha256(changed).digest() == attacker_digest)
print("仍匹配原始 MAC：", hmac.compare_digest(
    trusted_mac, hmac.digest(key, changed, "sha256")))
# 替换数据和摘要后： True
# 仍匹配原始 MAC： False
```

这个实验不是在破解 Hash，也没有证明 HMAC 的安全性。它只隔离一个工程事实：**谁有权决定验证基准**。它同样不能说明 `changed` 是否为最新模型、完整训练状态或可用的 Checkpoint。

### 3.3 key 与消息编码是协议的一部分

若认证对象是一个块，应定义类似下面的输入，而不是只认证裸字节：

```text
Encode(domain, tenant_id, checkpoint_id, generation,
       object_id, chunk_index, plaintext_length, chunk_bytes)
```

`Encode` 必须能唯一分辨各字段。例如直接拼接 `"ab" + "c"` 和 `"a" + "bc"` 会得到相同字节串；使用固定宽度、长度前缀或经过约定的规范序列化。这里的 `domain` 表示用途域，防止同一份认证字节被移作另一类协议消息。

key 还需要用途隔离。一个根秘密可以通过 HKDF 等标准机制派生不同用途的密钥，并把用途信息放入 `info`；不要把同一段字节随意同时用于数据加密、manifest MAC、远端审计。HKDF 不是把弱口令变成强密码的专用慢速口令派生器。[^hkdf]

## 4. AEAD：一次调用返回密文与认证标签

### 4.1 接口比“先 AES 再 Hash”更准确

AEAD 的抽象接口是：

$$
(C,T)=\operatorname{Seal}(K,N,P,A)
$$

$$
\operatorname{Open}(K,N,C,A,T)\rightarrow P\quad\text{或}\quad\mathrm{FAIL}
$$

$K$ 是 key，$N$ 是 nonce，$P$ 是明文，$C$ 是密文，$T$ 是 tag，$A$ 是 associated data，通常称 AAD。某些库把 `C || T` 合并为一个返回值，而不是两个独立缓冲区。[^aead][^py-aead]

| 字段 | 需要保密吗 | 能放在存储对象旁边吗 | 主要约束 |
|---|---|---|---|
| key | 是 | 不应与密文一起以明文形式存放 | 生成、访问控制、隔离、轮换、备份 |
| nonce | 否 | 可以 | GCM 在同一 key 下不能重复用于加密 |
| ciphertext | 内容已加密 | 可以 | 改变后应不能通过认证 |
| tag | 否 | 可以 | 不丢失、不随意截短、验证失败则拒绝 |
| AAD | 否 | 可以，或由上下文重新构造 | 不加密，但与密文一起认证；编码需确定 |

![[图片/SVG/8_9_9_13_3.svg|900]]

图中的认证闸门是 API 语义，不是可选的业务优化。AEAD 保护 AAD 的真实性，但不会隐藏 AAD，所以不要把需要保密的租户信息或敏感模型参数名直接放入 AAD 后声称“全部已加密”。

### 4.2 AAD 应绑定什么

对不可变的 Checkpoint chunk，本篇建议把以下上下文纳入认证设计：协议格式版本、tenant、checkpoint identity、generation、对象身份、chunk index、明文长度，以及必要的算法／key 标识。字段可放在 AAD，也可被可信 manifest 以等价方式绑定，核心是**解析和验证的语义不能留空**。

这里有两个不同的检查：

**密码学检查**：收到的密文是否与这份 AAD 匹配？

**业务上下文检查**：这份 AAD 是否就是当前请求应该接受的 tenant、对象和 generation？

把服务器发来的 `generation=4` 原样塞入解密函数，验证成功后就宣称“这是最新版本”，只完成了第一种检查。应该从可信提交状态得到预期 `generation=5`，然后验证或显式拒绝不匹配。AAD 认证一个声明，并不自动证明声明满足当前业务策略。[^aead]

### 4.3 解密过程中出现的字节，不一定已经认证

高层 AEAD 接口可以等验证成功后才返回明文。低层流式 API 可能在最终 tag 校验之前就输出临时明文字节：**不能提前交给模型反序列化器、业务消费者、外部网络或提交路径。**

使用 OpenSSL EVP 的 AEAD 接口时，最终解密认证必须成功；失败时，此前产生的输出不能使用。若为了流式处理写入临时文件，该文件必须保持隔离，不能被其他消费者观察为有效结果，认证成功后才能发布。[^openssl]

认证失败也不是“确定有人入侵”的同义词：key 选错、nonce 丢失、AAD 编码不一致、截断、介质损坏和主动篡改都可能导致失败。对外避免泄露不必要的失败差异，对内保留能够定位版本和对象的诊断信息，但不记录密钥或未认证明文。

## 5. AES-GCM：理解组合结构，不手写密码原语

### 5.1 AES 与 GCM 各负责什么

AES 是分组密码，其分组长度为 128 bit；AES-128 / AES-256 指 key 的位数，不是一次处理 128 / 256 字节，也不是 tag 的长度。GCM 把计数器模式的加密与 GHASH 认证结构组合起来。[^aes][^nist-gcm]

可以用下面的轮廓理解实现：计数器经过 AES 产生密钥流，与明文异或得到密文；AAD、密文及编码后的长度进入 GHASH；GHASH 的结果再结合由 nonce 和 AES 产生的掩码，形成 tag。

GHASH 中的 `H` 通常表示由 AES key 派生的内部值，例如 $H=E_K(0^{128})$。**它不是 SHA-256，也不是可以拿出来替代 HMAC 的公开 Hash。** GCM 的安全性依赖整个组合，包括长度编码、nonce 规则、tag 长度与每把 key 的使用限制。[^nist-gcm]

### 5.2 nonce 的底线：同一个 key 下的加密调用不能重复

对标准 AES-GCM，通常使用 **96-bit，也就是 12 字节 nonce**。nonce 不必保密，核心要求是同一把 key 的加密调用不能重复使用它。不同 key 的 nonce 可以相同；重复读取并解密同一条已经存在的密文，也不等于重新加密使用 nonce。[^aead][^nist-gcm]

若两条消息使用相同 key 与 nonce，计数器加密会重复使用密钥流，重叠长度范围内有：

$$
C_1\oplus C_2=P_1\oplus P_2
$$

这会暴露明文间的关系，认证安全性也会遭到严重破坏。**改用 AES-256、增加 AAD 中的对象名，或者“消息只差一点”，都不能修复同一 key/nonce 重用。**[^aead]

### 5.3 随机 nonce 并不等于永不碰撞

若在同一 key 下独立均匀生成 $q$ 个 96-bit nonce，在生日近似适用时：

$$
P_{\text{collision}}\approx\frac{q(q-1)}{2\cdot2^{96}}
$$

例如 $q=2^{32}$ 时，该近似约为 $2^{-33}$。这是**仅针对 nonce 随机碰撞的概率**，不是 AES-GCM 的完整安全界，也不是允许加密这么多次的配置建议。完整限制还与消息长度、总处理分组数、tag 长度、验证尝试和具体协议要求有关。[^nist-gcm]

还必须把多个 worker、机器、进程恢复、容器克隆、虚拟机快照恢复后的使用合并到**同一 key 的生命周期**里计数。单个进程里从零开始递增的变量，并不具备跨崩溃的唯一性。

### 5.4 一个可审查的 nonce 生命周期设计

一种工程设计是 `nonce = writer_prefix || counter`，例如 32-bit 前缀与 64-bit 计数器。这里的位宽只是示例；要成为可用设计，前缀必须在同一 key 下被可靠、唯一地分配，计数器不能回退，且还要遵守选定协议的使用上限。**随机选个 32-bit 前缀并不能宣称全局无碰撞。**

![[图片/SVG/8_9_9_13_4.svg|900]]

图中“先持久化预留区间，再使用区间”牺牲一部分未用编号，换取崩溃后不复用。任何可能已经用于加密、但结果是否成功尚不确定的编号，都视为已消耗，不回收。

| 场景 | 应有的行为 | 常见错误 |
|---|---|---|
| 多 writer 共享 key | 可靠分配不重叠的 namespace／区间 | 每台机器独立从 nonce=0 起步 |
| 进程崩溃 | 从已持久化的新区间继续，或切换全新 key | 只恢复计数器旧快照 |
| VM／容器状态克隆 | 重新取得唯一分配状态，必要时换 key | 同时复制 key 和 nonce 状态 |
| 网络超时重试 | 可重发已保存的同一份密文包；重新 Seal 时用新 nonce | 把 nonce 当幂等请求号反复用于不同加密调用 |
| key 轮换 | 对实际 key material、key_id 和已写对象保持明确映射 | 只修改 key_id，实际 key 不变，却重置 nonce |
| counter／使用预算到限 | 提前停止、换 key，禁止绕回 | 整数溢出后继续使用 |

[[7.13 幂等 重试 与请求去重]] 解决“同一个业务请求不要执行两次”，但不能代替 nonce 管理。业务请求标识和密码学 nonce 是两种不同的资源。

独立随机生成每个 Checkpoint 的数据 key，可以缩小每把 key 的使用范围；它仍需要可信 key 生成、包装保存、访问控制和恢复能力。**不要为减少 nonce 协调而制造不可恢复的密钥孤岛。**

### 5.5 单条 GCM 消息也有长度上限

NIST SP 800-38D 正式版对单次 GCM 明文长度给出的上限是：

$$
\operatorname{len}(P)\le 2^{39}-256\text{ bit}
=2^{36}-32\text{ byte}
$$

即 **64 GiB 减 32 字节**。实际库或上层协议可能限制得更低。不能把 TB/PB 级 Checkpoint 当成一条无限长 GCM 消息；把同一操作拆成许多次 `Update()`、最后只验一个 tag，也不会重置单条消息的密码学长度预算。[^nist-gcm]

对新工程设计，本篇采用每块完整 16-byte tag。不要从“库允许设置更短的 tag”推导出“任何长度都同样安全”。也不要把总伪造风险完全简化成“尝试次数除以 $2^{128}$”：那遗漏了 GCM 的其他使用量与结构性约束。

## 6. 把 AEAD 放进 Checkpoint：认证块，还要认证集合

### 6.1 不可变 chunk 与认证 manifest

下面是**本篇建议的应用层设计**，不是某个对象存储的默认承诺：

每个 chunk 独立 AEAD 加密；一个经过认证的 manifest 绑定 Checkpoint 身份、generation、文件清单、每个文件的长度、块序与块数、对象 locator、算法与 key 标识，以及选定的内容承诺。可信控制面决定哪个 manifest 是已提交且允许恢复的版本。

![[图片/SVG/8_9_9_13_5.svg|900]]

图里有两道不同的边界。**chunk tag** 验证一个块及其上下文；**manifest + 可信提交状态** 确定整个集合是否完整、是否为预期版本。仅验证已收到的块，不能发现“尾部还有一个块从未返回”。

manifest 可以用客户端保留的 key 计算 MAC，也可以由受信写入方签名，让不持有签名私钥的恢复方验证。签名公钥本身需要可靠分发。只在同一个不可信存储桶里放 `manifest.json` 和它的公开 Hash，不会凭空产生信任。

### 6.2 写入与恢复的状态边界

建议的写入次序是：冻结一致的应用快照，生成／选择 key，分配 nonce，写入加密块并完成存储侧所要求的持久化步骤，生成认证 manifest，最后原子地发布提交指针。具体持久化和原子性语义要看存储产品与控制面的实际保证。

恢复时先取得可信的期望 generation 和 manifest 身份，验证 manifest，再根据其中的文件集合取块。每块通过认证后才进入消费者；若需要整份 Checkpoint 原子可见，则所有必需块与结构检查都完成后才切换为可用版本。

若恢复程序先加载“目前拿到的所有块”，最后才发现 optimizer state 丢了一部分，密码学没有替它定义“完整训练快照”。模型参数、优化器状态、随机数状态、分片映射和框架格式，都属于应用恢复合同。

### 6.3 防回滚必须有独立可信状态

合法旧 manifest 和合法旧密文通常可以一起通过认证。因此防回滚依赖“期望的最新提交点”不能被攻击者同样回滚。可选择可信元数据服务、受保护的单调版本状态或其他符合威胁模型的机制；不是任意一个可改写的 `latest.txt` 都能承担这个角色。

[[7.12 Lease 与 Fencing]] 中的 epoch 可以阻止旧 writer 继续影响某些系统操作，但只有相关状态和校验被完整纳入协议，才可能支撑这里的版本决策。**出现一个名叫 epoch 的字段，不等于自动获得密码学防回滚。**

## 7. 最小 AES-GCM 实验：篡改会失败，重放却可能成功

这个实验使用 Python 的高层 `AESGCM` 接口，便于观察 API 语义。它不实现持久化 nonce 分配器，也不是可直接上线的 Checkpoint 格式。本包在 Python 3.13.5、`cryptography 46.0.4` 上运行了这些片段；该版本记录仅用于复现，不表示它是最新版本。

缺少依赖时在隔离环境中安装库，然后把本节的 Python 代码块按顺序放进同一个脚本运行。

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install cryptography
```

### 7.1 先把上下文序列化成 AAD

下面用固定顺序的 JSON 数组演示确定编码。真实跨语言协议仍需明确整数范围、字符编码、字段含义与规范编码规则，不能把“任意 JSON 看起来一样”当成字节完全相同。

```python
import json
import secrets
from cryptography.exceptions import InvalidTag
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

def make_aad(generation: int, index: int, size: int) -> bytes:
    if generation < 0 or index < 0 or size < 0:
        raise ValueError("generation、index、size 必须非负")
    fields = ["checkpoint/chunk/v1", "tenant-demo", "ckpt-demo",
              generation, index, size]
    return json.dumps(fields, separators=(",", ":"),
                      ensure_ascii=True).encode("utf-8")
```

这里故意保留 `generation`，后面用它展示“认证上下文”与“期望最新版本”的区别。`size` 指明文长度，不是密文加 tag 后的总长度。

### 7.2 一把全新 key，只执行一次加密

本实验每次运行都产生全新 key，并且只执行一次加密，因此不涉及跨进程 nonce 分配。不能把这个内存示例改成“保存同一个 key、各进程任意加密”后继续忽略生命周期约束。

```python
key = AESGCM.generate_key(bit_length=256)
aes = AESGCM(key)
nonce = secrets.token_bytes(12)
plain = b"checkpoint tensor chunk"
aad = make_aad(generation=4, index=0, size=len(plain))
sealed = aes.encrypt(nonce, plain, aad)  # 返回 ciphertext || 16-byte tag
assert len(sealed) == len(plain) + 16
assert aes.decrypt(nonce, sealed, aad) == plain
```

nonce 需要与密文一起被保存；如果它丢失，只有密文和 key 也不能按本格式完成正常恢复。API 把 tag 放在返回值尾部，写入长度、网络 framing 和存储 manifest 都必须按真实返回值处理。[^py-aead]

### 7.3 分别破坏密文、tag、nonce 和 AAD

`flip()` 只改一个字节，确保失败不是由于把参数改成完全不被接口接受的类型。测试函数只把 `InvalidTag` 认作本实验期待的认证失败，其他程序错误仍会显式暴露。

```python
def flip(data: bytes, offset: int) -> bytes:
    changed = bytearray(data)
    changed[offset] ^= 1
    return bytes(changed)

def rejected(engine: AESGCM, n: bytes, blob: bytes, ad: bytes) -> bool:
    try:
        engine.decrypt(n, blob, ad)
    except InvalidTag:
        return True
    return False
```

下面所有测试应输出 `True`。错误 key 与错误上下文不是同一种运维原因，但都会使这份密文无法通过对应认证。

```python
cases = [
    ("密文变化", aes, nonce, flip(sealed, 0), aad),
    ("tag 变化", aes, nonce, flip(sealed, -1), aad),
    ("nonce 变化", aes, flip(nonce, 0), sealed, aad),
    ("AAD 版本变化", aes, nonce, sealed,
     make_aad(5, 0, len(plain))),
    ("密文截断", aes, nonce, sealed[:-1], aad),
    ("key 错误", AESGCM(AESGCM.generate_key(bit_length=256)),
     nonce, sealed, aad),
]
for label, engine, n, blob, ad in cases:
    result = rejected(engine, n, blob, ad)
    assert result, label
    print(label, result)
```

### 7.4 原样重放：密码学验证仍然成功

这次不篡改任何内容，只再次提交同一份旧密文。重新解密是合法行为，所以高层 AEAD 接口会接受它；应用是否应该接受版本 4，是另一项策略。

```python
print("旧包原样再次解密：", aes.decrypt(nonce, sealed, aad) == plain)
trusted_latest_generation = 5
received_generation = 4
print("符合当前版本策略：", received_generation == trusted_latest_generation)
# 旧包原样再次解密： True
# 符合当前版本策略： False
```

本节最后一行是教学用的最小策略表达。生产系统中，“可信最新版本”本身必须被可靠保存与获取，否则比较动作再正确也只是拿两个不可信值互相确认。

## 8. 性能与空间：看覆盖的字节，不只看算法名字

### 8.1 完整处理仍然需要读到相应内容

对一段总长为 $D$ 的字节串，重新计算覆盖全体数据的 checksum、Hash、HMAC 或 AEAD 验证，都需要处理那些字节。流式 API 可以把峰值内存降到 chunk 级，但不能让全量验证神奇地变成只处理一个摘要。

实际写入时，可以在已有数据流中融合加密／认证，减少额外内存拷贝或重复 I/O。这个优化节省的是额外遍历，不是取消“被保护内容必须进入认证计算”的要求。需要低网络传输的远端持有审计时，应使用 7.33 中的抽样与专门证明结构，而不是让服务器只返回旧 tag。

### 8.2 每块认证的固定开销

若每块独立保存 12-byte nonce 与 16-byte tag，则不计 AAD、manifest、对齐和编码冗余时，固定附加开销为：

$$
\text{overhead ratio}=\frac{28}{B}
$$

取 $B=4\,\mathrm{MiB}$，约为 **0.000668%**。这个数只是空间比例计算，不能证明小块方案总成本可以忽略：块数增多会增加对象请求、元数据、密钥查找、调度与认证调用成本。若 nonce 可由已认证上下文可靠推导而不逐块存储，存储格式中的开销也会不同。

### 8.3 应记录哪些测量项

分别测已有缓冲区上的加密吞吐、真实读写路径吞吐、CPU 时间、内存带宽、对象请求数、P50/P99、认证失败处理路径，以及完整恢复耗时。指定 CPU 型号、库版本、硬件加速是否生效、线程数、块大小、NUMA 位置和持久化要求。

不要通过“开启了 AES 指令集”就认定系统不再受 CPU 影响。也不要把纯内存加密 GB/s 当成从远端恢复 Checkpoint 的吞吐量。跨层测量的口径可沿用 [[9.10 跨层性能归因：CPU、NUMA、PCIe、NIC、Switch、RDMA 与 NVMe 的 P99|跨层性能归因]]，把加密、网络、存储和恢复器的边界分开。

## 9. 故障实验与实现审查

把以下案例加入 [[9.6 故障注入矩阵]]。本表是待落地的系统测试合同；上节代码只覆盖其中的局部 API 行为。

| 注入方式 | 应检查的结果 | 不能接受的实现行为 |
|---|---|---|
| 改密文字节或 tag | 认证失败；数据不进入消费者 | 把临时明文先交给加载器再报错 |
| 改 chunk index／tenant／generation | 拒绝跨上下文替换 | 只信服务端提供的上下文 |
| 替换成合法旧版本 | 由可信版本策略拒绝 | 只检查 tag 就接受 |
| 删除尾块／漏一个文件 | manifest 集合检查失败 | 已收到的块都通过便宣布成功 |
| 重试、writer 重启、快照回滚 | 不发生 key/nonce 重复加密 | nonce 随本地计数器回退 |
| 篡改算法与 key_id | 认证／策略检查失败或安全拒绝 | 未认证字段任意切换旧算法或密钥 |
| key 服务不可用或旧 key 丢失 | 清晰报告密钥故障，按授权恢复流程处理 | 把密文认证正常误报为数据可恢复 |
| 一个副本认证失败 | 保留证据、选可信恢复源、修复后再验证 | 自动用未经验证的副本覆盖所有数据 |

**审查重点不是“库调用看起来对不对”，而是下面这些状态是否完整：**谁生成 key，谁有权认证，什么定义了对象身份，nonce 的唯一性跨哪些进程成立，哪些字节在认证成功前可见，以及谁决定最新提交版本。

## 10. 自测：能回答这些问题，就掌握了本篇边界

**为什么 SHA-256 没被破解，文件仍能被替换？** 因为攻击者可能同时替换文件与公开摘要。缺的是可信基准，不一定是更强的 Hash。

**HMAC 通过能证明是哪台机器写的吗？** 同一 key 的所有持有者都可以生成合法 MAC。认证关系不能自动细化为唯一作者身份。

**把 checkpoint ID 放在 AAD，是否允许同 key 的 nonce 重复？** 不允许。AAD 不会修复 GCM 的密钥流复用。

**AES-GCM tag 正确，能否断言没有发生磁盘 bit rot？** 只能说在相应假设下，这次读取和认证没有发现不一致。未读的数据、已被修复的错误、错误原因定位，都不是单次 tag 检查的结论。

**为什么分块都有合法 tag，完整 Checkpoint 仍然可能不可用？** 可能缺块、缺文件、被回滚、丢 key，或训练状态之间不一致。块认证不等于集合与业务恢复合同。

**AEAD 与 PDP / PoR 能否互相替代？** 不能。AEAD 处理读到的数据的保密与认证；PDP / PoR 在各自假设下审计远端持有／可取回性。它们可以组合，但组合边界需要明确定义。
