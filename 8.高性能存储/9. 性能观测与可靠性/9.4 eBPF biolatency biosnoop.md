# eBPF biolatency biosnoop

> `biolatency` 回答“块请求延迟分布是什么形状”，`biosnoop` 回答“哪一笔请求在什么时候、由谁、对哪块设备发出，并耗时多久”。两者通常复用块层 tracepoint 和 eBPF map，但输出粒度不同：前者在内核聚合直方图，后者把每笔完成事件送到用户态。

前置：[[1.7 块层与 blk-mq]]（request、tag 与完成）、[[9.2 iostat 指标解读]]（设备汇总指标）、[[9.3 blktrace 与块层生命周期]]（Q、D、C 事件与延迟边界）。

---

## 1. 这两个工具解决什么问题

一次存储排障通常从四种视角逐步下钻：

| 工具 | 数据粒度 | 适合回答 | 主要代价 |
| --- | --- | --- | --- |
| `iostat -x` | 每设备、每采样区间的平均值 | 哪块设备、读还是写、何时开始积压 | 平均值会抹平短毛刺 |
| `biolatency` | 内核内延迟直方图 | 延迟分布是否出现长尾、哪个设备或请求类型异常 | 桶宽限制分位数精度 |
| `biosnoop` | 每个块请求一行 | 哪些请求构成长尾、PID/进程/扇区/大小是什么 | 高 IOPS 下事件量大 |
| `blktrace` | 块层完整事件流 | 合并、拆分、requeue、Q→D 与 D→C 如何变化 | 采集量和分析成本最高 |

【实践】先用 `iostat` 找设备和时间窗，再用 `biolatency` 判断延迟分布，最后对异常窗口运行 `biosnoop`。只有需要完整状态转换时才进入 blktrace。这样可以把观测开销限制在问题附近。

## 2. eBPF 在内核里怎样运行

eBPF 程序是一段由内核验证后执行的字节码【事实】。它可以挂到 tracepoint、kprobe、网络 hook 等事件上；事件发生时，程序读取有限上下文，更新 BPF map，或把一条记录写入 ring buffer / perf buffer。用户态程序负责加载、附着、周期读取和展示。

对 C++ 并发工程师，可以先建立三个类比【类比，非等同】：

- **tracepoint** 类似只读回调点：内核执行到固定位置时调用已附着的 BPF 程序；
- **BPF map** 类似受内核管理的并发容器：哈希表保存请求起始时间，per-CPU array 保存分片计数；
- **ring buffer** 类似有界 MPSC 队列：多个 CPU 生产事件，用户态单独消费。

类比的边界很重要【事实】：eBPF 程序运行在内核事件路径上，不能像普通线程一样睡眠等待用户态。ring buffer 满时，程序应记录丢失或放弃本条事件，不能阻塞块设备完成路径。

### 2.1 verifier 保证什么

加载前，verifier 会检查控制流、指针来源、边界和 helper 调用是否满足内核规则【实现】。通过验证只说明程序不会以已知非法方式访问内核内存，不说明测量语义正确。tracepoint 选错、时间边界选错、请求关联键冲突，仍会得到“合法但错误”的数据。

### 2.2 BCC、bpftrace 与 libbpf

| 方式 | 特点 | 适用 |
| --- | --- | --- |
| BCC tools | 自带 `biolatency`、`biosnoop`，常在目标机即时编译 BPF C | 学习、临时排障 |
| bpftrace | 用脚本快速附着 tracepoint，表达聚合与打印 | 一次性验证假设 |
| libbpf CO-RE | 依赖 BTF，构建 BPF object 与 skeleton，随应用发布 | 生产采集器、版本化运维 |

【取舍】BCC 上手快，但目标机需要匹配的工具链、内核信息和 Python 运行环境。libbpf CO-RE 把加载和分发做成工程产物，部署更稳定，但需要维护 BPF object、BTF 兼容与采集协议。

## 3. 观测边界：它测到的不是应用总延迟

![[图片/SVG/8_9_9_4_1.svg|900]]

常见 `biolatency` 默认测量块请求从 **issue 到 complete** 的时间【实现，依工具版本而定】：

```text
block_rq_issue                                block_rq_complete
       │                                              │
       └──────── 驱动 / 传输 / 设备 / 完成回传 ────────┘
```

这与 [[9.3 blktrace 与块层生命周期]] 的 `D→C` 边界接近。它通常不包含：

- 应用线程池、协程队列和锁等待；
- 系统调用进入 VFS 后、块请求产生前的文件系统工作；
- Page Cache 命中的读，因为没有块请求；
- buffered write 返回后到后台回写开始前的驻留时间；
- `block_rq_complete` 之后，原应用线程被唤醒并获得 CPU 的时间。

部分 BCC 版本提供“包含 OS queue time”的选项，起点会前移到 request insert / queue 附近【实现】。运行前必须查看本机 `biolatency --help`，并把实际边界写进报告。不要只记录命令名。

> [!warning] 名字相同不代表语义完全相同
> 不同发行版可能打包不同年份的 BCC；同名工具也可能改用 tracepoint、raw tracepoint 或 kprobe 兼容不同内核。确认版本、attach 点和选项后，结果才可跨机器比较。

## 4. 一笔请求如何被关联

### 4.1 issue：写入起始状态

当 `block_rq_issue` 触发时，BPF 程序获取单调时钟时间，并以 request 身份作为 key 写入哈希 map【典型实现】：

```text
start[request_id] = {
    issue_ns,
    pid,
    comm,
    device,
    sector,
    bytes,
    op_flags
}
```

这里的 `request_id` 常来自内核 `struct request *` 指针或 tracepoint 提供的等价关联信息【实现】。指针只在该请求生命周期内有效，完成后会被内核复用，所以 complete 路径必须及时删除 map entry。

### 4.2 complete：计算 delta 并删除

```text
state = start.lookup(request_id)
if state exists:
    delta_ns = now_ns - state.issue_ns
    histogram[log2(delta)] += 1          # biolatency
    ringbuf.submit(state + delta_ns)     # biosnoop
    start.delete(request_id)
```

【事实】`bpf_ktime_get_ns()` 使用内核单调时钟，适合计算同一主机内的时间差，不受系统时间校准或 NTP 跳变影响。不同主机的单调时钟没有共同原点，客户端和服务端事件不能直接拿时间戳相减。

### 4.3 合并、拆分与 requeue

块层可以合并相邻请求、拆分大请求，也可以把 request requeue【实现】。这会影响“应用 IO 次数、块 request 次数、设备命令次数”的对应关系。成熟工具会针对其 attach 点维护关联；自己写采集器时，不能假设一次 `read()` 必然对应一组 issue/complete。

进程归因也有边界：

- direct IO 的提交上下文通常接近发起线程；
- buffered write 的落盘可能由 writeback 内核线程发起；
- 合并后的 request 可能包含多个上层 bio；
- 设备完成事件发生在中断或 softirq 上下文，complete 时的当前 PID 不是原始提交者。

因此 biosnoop 必须在请求早期保存 PID/comm，不能在 complete 时读取 `current` 后当作发起者【事实】。

## 5. biolatency：在内核聚合延迟分布

`biolatency` 的关键设计是：每笔完成只更新一个 histogram bucket，用户态按间隔读取聚合结果【实现】。它不会为每笔 IO 打印一行，所以在高 IOPS 环境下比 biosnoop 更适合作为第一层分布观测。

典型命令以本机 `--help` 为准：

```bash
sudo biolatency -m -D 1 10
```

常见语义：

- `-m`：用毫秒显示桶；对低延迟 NVMe，微秒桶更有分辨率；
- `-D`：按设备分别输出直方图；
- `1 10`：每 1 秒输出一次，共 10 次；
- 某些版本支持按请求 flags、磁盘或 JSON 输出。

发行版也可能把工具安装到固定目录：

```bash
sudo /usr/share/bcc/tools/biolatency 1 10
```

### 5.1 log2 histogram 怎么读

常见 BPF 直方图用 `log2(delta)` 选桶【实现】：

```text
0–1 μs
2–3 μs
4–7 μs
8–15 μs
16–31 μs
...
```

每个桶宽度按 2 倍增长。优点是固定 map 大小覆盖很宽的延迟范围；代价是越靠近尾部，桶越宽，无法知道桶内样本的精确位置【取舍】。

若要从直方图估算 p99：从低桶向高桶累加 count，第一次达到总样本数 99% 的桶就是 p99 所在范围。报告应写成“p99 落在 256–511 μs 桶”，不要伪造为某个精确微秒值。

### 5.2 per-CPU map 为什么常见

所有 CPU 若对同一个全局计数器做原子加，高 IOPS 下会让同一缓存行在核间弹跳【实现】。per-CPU histogram 为每个 CPU 保存一份桶，热路径只改本地副本，用户态读取时再求和。这与 C++ 中的 sharded counter 是同一类取舍：用更多内存和汇总工作换取提交路径少争用。

### 5.3 直方图能证明什么

直方图可以证明：

- 分布是单峰还是出现第二个慢峰；
- 长尾是否只发生在读、写或某块设备；
- 调整 fio QD 后，整个分布移动还是只有尾部变差；
- p99 异常是否与一秒平均 await 被稀释同时发生。

它不能单独证明慢在 NAND、网络、target 或中断处理，因为 issue→complete 把这些阶段合在一起【事实】。

## 6. biosnoop：输出单请求证据

`biosnoop` 在请求完成时向用户态发送一条记录。字段随 BCC 版本变化，常见内容包括：时间、进程名、PID、设备、读写方向、扇区、字节数、排队时间和总延迟。

```bash
sudo biosnoop -d nvme0n1
```

先运行 `biosnoop --help` 确认设备过滤、queue time 和时间戳选项。高 IOPS 机器不要直接无过滤长时间运行。

### 6.1 如何从事件流定位长尾

一次最小分析顺序：

1. 按 `LAT` 从大到小筛出异常请求；
2. 看异常是否集中在某个设备、读写方向或请求大小；
3. 检查相同时间窗内是否出现大量并发请求；
4. 对照 fio job、应用日志和 `iostat`；
5. 需要区分 Q→D 与 D→C 时，进入 [[9.3 blktrace 与块层生命周期]] 或增加 queue tracepoint。

> [!warning] PID 不是可靠的业务请求 ID
> writeback、异步 IO、合并和多层块设备会改变执行上下文。PID/comm 是归因线索，不是跨层唯一标识。要关联业务请求，需要应用显式 trace ID，并在用户态、文件系统、网络和服务端分别建立证据。

### 6.2 ring buffer 的背压

biosnoop 的数据路径是：

```text
BPF complete handler → ring/perf buffer → 用户态 poll → 格式化/写出
```

用户态打印终端通常比生成事件慢。缓冲区满时不能让 BPF 程序阻塞 IO 完成路径，因此会丢记录或增加 lost counter【事实/实现】。结论必须同时报告：采集窗口、过滤条件、事件数、丢失数和采集器 CPU。

【取舍】生产采集器应优先输出二进制结构到内存队列，再由独立线程批量编码和落盘。不要在事件回调里同步写日志或做 DNS、符号化等慢操作。

## 7. 从汇总异常到单请求的实验流程

以 [[9.1 fio Benchmark Matrix]] 的 4 KiB 随机读 QD 扫描为例：

### 7.1 建立基线

```bash
iostat -x -y 1
sudo biolatency -D 1 30
```

记录 fio 的 clat 分位数、`iostat` 的 `aqu-sz` / `r_await`，以及 biolatency 的设备直方图。三个观测点边界不同，但数量级应能解释彼此。

### 7.2 复现尾部变化

依次运行 QD 1、8、32、128【实验设计】。若 IOPS 已到平台，`aqu-sz` 与 fio p99 继续增长，同时 biolatency 整体右移，说明新增并发已进入块层或驱动以下排队。若 fio p99 上升而 biolatency 不变，时间更可能在块层之前或 complete 之后。

### 7.3 对异常窗口运行 biosnoop

使用设备和持续时间过滤，只抓复现窗口。若慢请求集中在固定设备，结合 SMART、温度和 [[3.5 GC 写放大与 Over-Provisioning]]；若多盘同步出现，检查 CPU、IRQ、PCIe、虚拟层或共享网络。

### 7.4 保存可审计结果

```text
主机 / 内核 / BCC 或 libbpf 版本：
attach 点与延迟起止事件：
设备 MAJ:MIN 与 lsblk 映射：
过滤条件、采集时长、样本数、lost 数：
fio 配置与同期 iostat：
直方图单位、桶范围与聚合维度：
网络协议、target 节点与跨机时钟方案：
```

## 8. 网络存储：同一个 D→C 跨过了哪些层

### 8.1 NVMe/TCP、iSCSI 与 NVMe/RDMA

这些协议在客户端呈现块设备，因此客户端的 block tracepoint 可见请求【事实】。但 issue→complete 可能同时包含：

```text
客户端块层 / 驱动
  → TCP 或 RDMA 传输
  → 交换网络
  → target 协议线程或 poller
  → target 块层与设备
  → 完成沿原路返回
```

客户端 biolatency 右移只证明端到端块完成变慢，不能把责任直接归给客户端磁盘【事实】。最小交叉观测：

- 客户端：block latency、TCP 重传或 RDMA 拥塞、NIC queue / drop；
- target：协议队列、CPU/poller、target 物理盘 biolatency；
- 网络：交换机丢包、PFC/ECN（RoCE）或 TCP retransmission；
- 跨机：统一 wall clock 用于事件对齐，单机 delta 仍用 monotonic clock。

传输层差异见 [[5.2 Transport TCP vs RDMA]]，跨端延迟账见 [[5.4 延迟分解方法论]]。

### 8.2 NFS 与 SMB

NFS/SMB 在客户端是文件协议，不一定生成客户端本地块 request【事实】。客户端运行 biolatency 可能看不到业务 IO；应观察 RPC、socket 与协议 tracepoint，并在服务端对实际块设备运行 biolatency/biosnoop。

### 8.3 Ceph RBD 与多副本

RBD 映射为块设备时，客户端可见 block latency，但 complete 可能等待网络与 OSD 确认【实现】。副本、EC、主 OSD 排队和慢 OSD 都会落入同一个客户端 delta。需要按 OSD 节点采集叶子设备分布，不能只看客户端一张直方图。

## 9. 环境、权限与兼容性

### 9.1 先检查 attach 点

```bash
sudo bpftrace -l 'tracepoint:block:*'
sudo bpftool feature probe
test -r /sys/kernel/btf/vmlinux && echo BTF-ready
```

运行条件【前提】：

- 内核启用 BPF、tracefs 和目标 block tracepoint；
- BCC 即时编译需要可用的内核类型信息或 headers；
- libbpf CO-RE 通常依赖 `/sys/kernel/btf/vmlinux`；
- 需要 root，或按内核版本授予 `CAP_BPF`、`CAP_PERFMON` 等能力；旧内核常退化为 `CAP_SYS_ADMIN`；
- kernel lockdown、容器 seccomp 和宿主机策略可能禁止加载或 attach。

### 9.2 容器里的设备名

容器看到的路径、PID namespace 和宿主机 `MAJ:MIN` 可能不同【实现】。eBPF 运行在宿主机内核，生产排障应记录宿主机设备映射与 cgroup/container ID。不要只按容器内 `/dev` 名字过滤。

### 9.3 tracepoint 与 kprobe 的取舍

tracepoint 是内核明确暴露的观测接口，通常比依赖函数名和参数布局的 kprobe 稳定【取舍】。但 tracepoint 字段仍会随内核演进；CO-RE 可以处理部分类型布局变化，不能修复语义变化。升级内核后要用回归负载验证采集器。

## 10. Modern C++：用 RAII 管理 libbpf skeleton

BPF 侧通常使用受限 C 生成字节码；用户态采集器可以使用 Modern C++ 管理 skeleton 和 ring buffer。下面假设 `bpftool gen skeleton` 已生成 `biotrace.skel.h`。

```cpp
#include <bpf/libbpf.h>

#include <cerrno>
#include <chrono>
#include <cstddef>
#include <memory>
#include <stdexcept>
#include <system_error>
#include <utility>

#include "biotrace.skel.h"

struct SkeletonDeleter {
    void operator()(biotrace_bpf* p) const noexcept {
        if (p != nullptr) {
            biotrace_bpf__destroy(p);  // 同时销毁 skeleton 持有的 bpf_link
        }
    }
};

struct RingBufferDeleter {
    void operator()(ring_buffer* p) const noexcept {
        if (p != nullptr) {
            ring_buffer__free(p);
        }
    }
};

using Skeleton = std::unique_ptr<biotrace_bpf, SkeletonDeleter>;
using RingBuffer = std::unique_ptr<ring_buffer, RingBufferDeleter>;

class BiotraceSession {
public:
    static BiotraceSession open() {
        Skeleton skeleton{biotrace_bpf__open_and_load()};
        if (!skeleton) {
            throw std::runtime_error{"cannot open and load biotrace BPF object"};
        }

        if (const int rc = biotrace_bpf__attach(skeleton.get()); rc < 0) {
            throw std::system_error{-rc, std::generic_category(),
                                    "cannot attach block tracepoints"};
        }

        const int map_fd = bpf_map__fd(skeleton->maps.events);
        if (map_fd < 0) {
            throw std::system_error{-map_fd, std::generic_category(),
                                    "cannot resolve events map fd"};
        }
        ring_buffer* raw_ring = ring_buffer__new(
            map_fd, &BiotraceSession::on_event, nullptr, nullptr);
        if (raw_ring == nullptr) {
            throw std::system_error{errno, std::generic_category(),
                                    "cannot create ring buffer"};
        }

        return BiotraceSession{std::move(skeleton), RingBuffer{raw_ring}};
    }

    BiotraceSession(const BiotraceSession&) = delete;
    BiotraceSession& operator=(const BiotraceSession&) = delete;
    BiotraceSession(BiotraceSession&&) noexcept = default;
    BiotraceSession& operator=(BiotraceSession&&) noexcept = default;

    void poll(std::chrono::milliseconds timeout) {
        const int rc = ring_buffer__poll(ring_.get(),
                                         static_cast<int>(timeout.count()));
        if (rc < 0 && rc != -EINTR) {
            throw std::system_error{-rc, std::generic_category(),
                                    "ring buffer poll failed"};
        }
    }

private:
    BiotraceSession(Skeleton skeleton, RingBuffer ring)
        : skeleton_{std::move(skeleton)}, ring_{std::move(ring)} {}

    static int on_event(void*, void* data, std::size_t size) noexcept {
        // 只做定长校验和入队；格式化、符号化、落盘交给其他线程。
        return (data != nullptr && size > 0) ? 0 : -1;
    }

    Skeleton skeleton_;  // 先声明
    RingBuffer ring_;    // 先析构 ring，再析构 skeleton 与 links
};
```

RAII 处理三条失败路径【实现】：加载失败时不留下 object；attach 后创建 ring buffer 失败时 skeleton 析构并解除链接；正常退出时 ring buffer 先释放，随后 skeleton 销毁 links 和 maps。`SIGKILL` 不执行析构，但进程退出后内核仍会按 fd 引用计数回收 BPF object 与 link【事实】。

生产采集器还要补：lost counter、事件 schema 版本、bounded queue、批量编码、退出信号和采集器自监控。ring callback 只入队，不在 IO 完成热路径的用户态后半段做慢操作【实践】。

## 11. 开销控制

事件成本取决于 attach 点数量、map 操作、输出频率和过滤范围【事实】。

| 设计 | 热路径动作 | 开销趋势 |
| --- | --- | --- |
| 全局 histogram | 一次时间读取 + map lookup/update | 低，但全局桶可能争用 |
| per-CPU histogram | 更新本 CPU 桶 | 较低，读取时需要合并 |
| 每请求 biosnoop | start map + ring/perf output + delete | 随 IOPS 线性增长 |
| 多维 key | device × op × cgroup × bucket | map 更大，用户态合并更重 |
| 无过滤全盘采集 | 所有块设备事件 | 容易淹没问题设备与消费者 |

控制顺序【实践】：先限制设备，再限制时间窗，再选择操作类型；确认问题后才增加 PID、cgroup、stack 等维度。每增加一维，都要记录 map 容量、lost 数和采集器 CPU。

## 12. 陷阱与误区

> [!warning] 常见错误
> 1. 把 biolatency 的 issue→complete 叫作“应用请求延迟”，遗漏 VFS、Page Cache、应用排队和唤醒调度。
> 2. 把 D→C 叫作“纯 NAND 延迟”，遗漏驱动、控制器、网络、target、DMA 和中断。
> 3. 在 NFS 客户端看不到 block 事件，就认定业务没有存储 IO。
> 4. 在 complete 回调读取当前 PID，把中断或 softirq 上下文当作原始提交者。
> 5. 忽略 merge、split、requeue，强行让一次系统调用对应一笔 request。
> 6. 从 log2 histogram 伪造精确 p99，而不是报告分位数所在桶。
> 7. 长时间无过滤运行 biosnoop，却不检查 lost events 和采集器 CPU。
> 8. 跨主机直接相减 monotonic timestamp，忽略每台主机的时钟原点不同。
> 9. 内核升级后继续使用旧 kprobe 字段偏移，不做回归验证。
> 10. 在 ring buffer callback 中同步格式化和写盘，让消费者主动制造丢事件。

## 13. 关键结论

| 结论 | 性质 |
| --- | --- |
| biolatency 在内核聚合块请求延迟直方图，适合先判断分布形状 | 事实 |
| biosnoop 输出单请求元数据与延迟，适合对长尾样本做归因 | 事实 |
| 常见默认边界是 block_rq_issue→block_rq_complete，不是应用端到端延迟 | 实现边界 |
| start map 以 request 身份关联起止事件，complete 后必须删除 | 典型实现 |
| per-CPU histogram 用空间和读取合并换取热路径少争用 | 取舍 |
| ring buffer 是有界通道，消费者跟不上时不能阻塞 IO 路径，只能丢事件 | 事实 / 取舍 |
| 网络块设备的 D→C 可能包含客户端、网络、target 与远端介质 | 事实 |
| NFS/SMB 客户端不一定有本地块事件，应转向 RPC 观测和服务端块层 | 事实 |
| 工具版本、attach 点、时间边界、过滤与 lost 数是结果可比较的前提 | 前提 |
| iostat → biolatency → biosnoop → blktrace 是由低开销到高细节的下钻顺序 | 实践结论 |
