# blktrace 与块层生命周期

> `iostat` 告诉你一个采样窗口内“平均发生了什么”，`blktrace` 则记录单个块请求在关键状态点发生了什么。它能把块层总等待拆成软件排队与下层执行两段，也能看到合并、拆分、重排和重试。它看不到请求进入块层之前的全部时间。

前置：[[1.7 块层与 blk-mq]]（bio、request、软件队列与硬件队列）、[[9.2 iostat 指标解读]]（先用汇总指标确认异常设备与时间窗）。

---

## 1. 从平均值下钻到事件

排障顺序通常是：

```text
fio / 业务 SLO 发现延迟变化
  → iostat 确认设备、读写方向与异常时间窗
  → blktrace 记录请求事件
  → blkparse 解码，btt 聚合 Q→D、D→C、Q→C
  → eBPF 或子系统追踪补齐块层之前/之后的时间
```

【取舍】`blktrace` 适合复现环境、短时间定点采样和内核 IO 路径学习。高 IOPS 设备会产生大量事件，持续全量追踪有 CPU、内存和磁盘写入成本；生产环境常先用 [[9.4 eBPF biolatency biosnoop]] 做过滤与直方图，再缩小到几十秒的 blktrace 窗口。

## 2. 请求经过哪些事件

![[图片/SVG/8_9_9_3_1.svg|900]]

一条理想化的请求时间线：

```text
Q（进入块层） → G/I（申请并插入 request） → D（下发驱动） → C（完成）
                 ↘ M/F（与相邻请求合并）
                 ↘ R（资源不足、路径故障等原因导致重入队）
```

事件代码的常见含义：

| 代码 | 名称 | 含义 |
| --- | --- | --- |
| `Q` | queue | IO 进入块层请求队列处理 |
| `G` | get request | 分配 request 结构或 tag 相关资源 |
| `I` | insert | request 插入调度或派发队列 |
| `M` / `F` | back/front merge | 与后方 / 前方相邻请求合并 |
| `X` | split | 一个请求因边界或大小限制被拆分 |
| `D` | issue | request 下发给驱动 |
| `C` | complete | request 完成并返回块层 |
| `R` | requeue | request 未完成，重新排队 |
| `P` / `U` | plug / unplug | 当前提交上下文攒批 / 刷出批次 |

> [!note] 事件序列不是固定协议
> 内核版本、blk-mq、IO 调度器、设备类型、trace action 过滤和 device-mapper 层级都会改变可见事件。现代 NVMe 的快速路径可能没有完整的 `G/I` 组合；合并、拆分和 requeue 会让“一条 Q 对一条 D 对一条 C”的简单配对失效【实现】。分析前先查看真实事件，不要硬套模板。

---

## 3. 三段时间各自代表什么

### 3.1 `Q → D`：块层软件等待

这一段常包含【实现】：

- plug 攒批等待；
- IO 调度器排序与公平控制；
- 合并、拆分和映射；
- blk-mq tag 或驱动队列资源等待；
- device-mapper、加密、RAID 或 multipath 上层处理。

`Q→D` 增长时，先检查 QD、调度器、tag、CPU 调度和多层映射。它不等于“CPU 算了这么久”，其中也可能有资源等待。

### 3.2 `D → C`：驱动以下的完成时间

对本地 NVMe，这一段通常覆盖驱动下发、PCIe/NVMe 队列、设备内部执行、DMA、完成中断或轮询以及完成回传【事实】。它仍不是纯 NAND 时间，因为控制器排队、FTL、GC、固件和中断处理都在其中。

对 NVMe/TCP、iSCSI 或其他网络块设备，`D→C` 还可能跨过客户端传输、网络、target 队列与 target 介质【实现】。客户端 blktrace 无法把这段自动拆成“网络”和“服务端磁盘”。需要同一时间基准下的网络与服务端观测。

### 3.3 `Q → C`：块层总驻留时间

这是请求在所追踪块设备层的总时间。它与 iostat 的 `await` 观测边界接近，但两者统计方法、事件过滤、合并与采样区间不同，只应做量级交叉验证【前提】。

### 3.4 不在图里的时间

块层 trace 通常不覆盖：

- 应用线程池或协程队列等待；
- `read()` 进入内核后，在 VFS、文件系统锁和 Page Cache 中花费的时间；
- Page Cache 命中，因为根本没有块请求；
- `C` 之后的 softirq 后续、唤醒、调度和用户线程恢复；
- NFS/SMB 客户端的 RPC 请求，因为它们不是客户端本地块 IO。

所以“fio clat 5 ms，Q→C 只有 200 μs”是有效线索：剩余时间在所追踪块层之外，或追踪了错误设备层级。

## 4. 采集前先确认设备层级

```bash
lsblk -o NAME,TYPE,MAJ:MIN,PKNAME,FSTYPE,MOUNTPOINTS
findmnt -T /mnt/bench/fio.test
```

`MAJ:MIN` 是内核设备身份【事实】。同一个文件路径可能依次经过：

```text
文件系统 → dm-crypt / LVM / multipath → md RAID → nvme0n1
```

追踪逻辑设备能看到上层端到端块等待；追踪物理设备能看到叶子盘。RAID 分条会让一笔上层请求变成多个叶子请求，dm-crypt 会在层间加入 CPU 工作【实现】。根因分析常需要同时采逻辑层与叶子层，但不能用扇区号直接跨层硬配对，映射、拆分与合并会改变地址和请求数量。

> [!warning] 不要追错 namespace 或分区
> fio 打到 `/dev/nvme1n1p1`，却只追 `/dev/nvme0n1`，结果可能安静得像“块层没有问题”。先用 `findmnt`、`lsblk` 和 `MAJ:MIN` 建立路径，再采集。

## 5. 一次 30 秒的最小采集

安装发行版的 `blktrace` 工具包后，以 root 采集专用测试设备：

```bash
sudo blktrace -d /dev/nvme0n1 -o trace -w 30
```

它会按 CPU 生成 `trace.blktrace.<cpu>` 二进制文件。随后解码文本并生成供 `btt` 使用的合并二进制流：

```bash
blkparse -i trace -o trace.txt -d trace.bin
btt -i trace.bin -o btt
```

边采边看适合教学和低负载复现：

```bash
sudo blktrace -d /dev/nvme0n1 -o - | blkparse -i -
```

【取舍】管道模式便于即时观察，但终端输出会反过来消耗 CPU，并可能跟不上高 IOPS 事件流。正式采样先写二进制，结束后离线解析。

只关心下发与完成时可以过滤 action，降低数据量：

```bash
sudo blktrace -d /dev/nvme0n1 -a issue -a complete -o trace -w 30
```

过滤会丢失合并、重排和 `Q→D` 证据【取舍】。第一次复现建议全事件短采样，确认问题形状后再收窄。

## 6. 读一行 blkparse 输出

典型行的形状如下，实际字段会随 action 改变：

```text
259,0    3       241     1.203456789   9182  D  R  2048 + 8 [fio]
│        │       │       │             │     │  │  │      └─ 进程名
│        │       │       │             │     │  │  └─ 起始扇区 + 扇区数
│        │       │       │             │     │  └─ RWBS：读/写/同步/屏障等标志
│        │       │       │             │     └─ action：这里是 issue
│        │       │       │             └─ PID
│        │       │       └─ 相对时间戳（秒）
│        │       └─ 每 CPU 序号
│        └─ CPU
└─ 设备 major,minor
```

`R` 表示 read；`W` 表示 write。`S`、`F` 等附加字母可表示同步或 flush 等语义，具体组合以本机 `blkparse` 手册和内核事件为准【前提】。

分析时先做三个筛选：

1. 同一 `MAJ:MIN`；
2. 同一读写方向和相近请求大小；
3. 同一异常时间窗。

再按扇区、序号和事件关联请求。遇到 merge、split、requeue 时，用 `btt` 的请求跟踪结果或专用脚本处理，不能只按扇区做一对一匹配。

## 7. 用 btt 聚合生命周期

`btt` 会把 blktrace 事件转换为阶段统计、活动深度和请求分布。重点问题：

| 观察 | 含义 | 候选根因 |
| --- | --- | --- |
| Q→D 整体升高，D→C 稳定 | 软件队列或资源等待增加 | QD 过深、tag、调度器、CPU、dm 层 |
| Q→D 稳定，D→C 整体升高 | 下层完成变慢 | 设备 GC/温控、链路、网络 target |
| D→C 只有少数长尾 | 设备或传输偶发抖动 | GC、错误恢复、重传、路径切换 |
| requeue 增多 | 请求无法按首次下发完成 | 资源不足、multipath、设备重置 |
| merge 增多且平均请求变大 | 顺序性或预读正在合并 | 可能提高带宽，不一定是异常 |
| split 增多 | 请求跨边界或超过限制 | 文件系统/映射边界、max sectors |

【前提】阶段名称和输出文件随 blktrace/btt 版本不同。先读工具帮助，再把统计定义写进实验记录。不要只保存截图；保留原始二进制 trace、命令、设备映射、内核版本和 fio job 文件。

## 8. 三个机制案例

### 8.1 QD 过深

```text
fio QD 8  → IOPS 继续增长，Q→D 低，D→C 稳定
fio QD 32 → IOPS 接近平台，Q→D 开始增长
fio QD 128→ IOPS 不再增长，Q→D 与 p99 大幅增长
```

结论【取舍】：设备已到服务上限，新增深度只把等待从应用窗口搬进块层。降低 QD 往往能用少量吞吐交换较大的 p99 改善。用 [[9.2 iostat 指标解读]] 的 `aqu-sz` 与 await 同步验证。

### 8.2 SSD GC 或温控

若 Q→D 稳定、D→C 周期性拉长，同时 SMART 温度贴近阈值或随机写已进入稳态 GC，延迟来源在驱动以下的概率较高【证据链】。但 blktrace 不能区分固件排队、FTL GC 和 NAND 重试；还需要 NVMe SMART、错误日志、设备遥测和对照负载。

### 8.3 NVMe/TCP 长尾

客户端 D→C 包含 TCP 往返、target 排队和 target 设备。若客户端 D→C 拉长，而服务端物理盘 D→C 稳定，同时 TCP 重传或 NIC 丢包增加，网络段是更强候选【证据链】。若服务端盘也同步拉长，则先查 target 设备和写放大。跨网络路径见 [[5.4 延迟分解方法论]]。

## 9. 采集开销与数据完整性

高 IOPS 环境里，每笔 IO 可产生多个事件。采集前估算：

```text
事件速率 ≈ IOPS × 每请求可见事件数 × 被追踪设备层数
```

控制方法【取舍】：

- 将窗口缩短到能覆盖复现的 10 至 30 秒；
- 只追目标设备，不追 `-d` 范围之外的无关盘；
- 确认问题形状后使用 `-a` 过滤 action；
- 原始 trace 写到另一块设备，避免写入流量污染被测盘；
- 检查采集结束信息中的丢事件或缓冲区不足提示；
- 同时记录 CPU 使用率，确认追踪本身没有改变问题。

【安全】trace 可能包含进程名、设备地址分布和工作负载模式。生产数据需要按日志策略保存与脱敏。

## 10. Modern C++：用 RAII 管理 tracefs 开关

自建小型采集器时，异常路径最怕忘记关闭 trace event。下面的守卫只演示资源生命周期；读取 ring buffer 和事件格式仍应使用 libtraceevent / libtracefs 等库。

```cpp
#include <filesystem>
#include <fstream>
#include <stdexcept>
#include <utility>

class TraceEventGuard {
public:
    explicit TraceEventGuard(std::filesystem::path enable_file)
        : enable_file_{std::move(enable_file)} {
        write("1");
    }

    TraceEventGuard(const TraceEventGuard&) = delete;
    TraceEventGuard& operator=(const TraceEventGuard&) = delete;

    ~TraceEventGuard() {
        try {
            write("0");
        } catch (...) {
            // 析构函数不抛异常；生产代码应写入独立错误通道。
        }
    }

private:
    void write(const char* value) const {
        std::ofstream out{enable_file_};  // RAII：每次写完自动关闭 fd
        if (!out || !(out << value)) {
            throw std::runtime_error{"cannot update trace event"};
        }
    }

    std::filesystem::path enable_file_;
};

// 需要 root，路径通常位于 /sys/kernel/tracing/events/block/
// TraceEventGuard issue{".../block_rq_issue/enable"};
// TraceEventGuard done{".../block_rq_complete/enable"};
```

RAII 保证正常返回和异常退出都会执行关闭动作【实现】。进程被 `SIGKILL` 或系统崩溃时析构函数不会运行，因此采集器启动时仍要先恢复已知状态【前提】。

## 11. 陷阱与误区

> [!warning] 常见错误
> 1. 把 D→C 叫作“SSD NAND 延迟”，忽略驱动、控制器、GC、中断和网络块传输。
> 2. 认为所有请求都严格经历 Q、G、I、D、C，忽略内核版本和 blk-mq 快速路径。
> 3. 用扇区号简单配对 merged、split、requeue 请求。
> 4. 追踪逻辑卷却把结果当作叶子盘，或只追一块叶子盘遗漏 RAID 分条。
> 5. 看到 fio clat 高、Q→C 低就认定工具错误；差值可能在块层之前或完成之后。
> 6. 在 NFS 客户端运行 blktrace，期待看到服务端磁盘生命周期。
> 7. 在被测盘上写巨量 trace 文件，让观测流量干扰实验。
> 8. 没检查丢事件，就对不完整序列做延迟分布。

## 12. 关键结论

| 结论 | 性质 |
| --- | --- |
| blktrace 记录块请求事件，适合从设备平均值下钻到单请求生命周期 | 事实 |
| Q→D 主要反映块层软件排队，D→C 反映驱动以下完成时间 | 实现边界 |
| D→C 不是纯介质时间；网络块设备还可能包含网络与 target | 事实 |
| Q→C 不含块层之前的 VFS/Page Cache/应用排队，也不含完整唤醒调度 | 事实 |
| merge、split、requeue 和多层设备会改变请求身份与数量 | 实现 |
| 事件集合随内核、调度器和设备而变，不能硬套固定状态机 | 前提 |
| 先用 iostat 缩小设备与时间窗，再做短时 blktrace，能降低观测开销 | 实践结论 |
| 原始 trace、设备映射、内核版本和负载配置必须一起保存 | 实践结论 |
