# 跨层性能归因：CPU、NUMA、PCIe、NIC、Switch、RDMA 与 NVMe 的 P99

[[9.5 p99 毛刺定位]] 给出了刻画、分层、验证的方法。本篇把范围收紧到 **NVMe/RDMA + SPDK Target + 本地 NVMe 后端**：同一条链同时受 CPU、内存位置、PCIe、网卡、交换机、RDMA 资源与 SSD 影响，怎样用可复查的证据确定慢在哪里？

先熟悉 [[5.24 NVMe-oF 端到端数据路径：Host、RDMA Fabric、Target Reactor、bdev 与 NVMe]] 的缓冲区和完成边界。本篇的交付目标不是“列出了很多命令”，而是：**一份固定负载合同，一组边界明确的观测，一条可证伪的假设，一次可逆干预，以及重复实验后的结论。**

> [!info] 适用范围与证据等级
> 命令与事件名核对日期：**2026-09-11**；SPDK RDMA 状态机以 **`v25.09`** 为固定源码锚点，不代表要求使用这一版本。计数器随 RNIC/ASIC/驱动变化，先查本机能力。
>
> 下文场景是**诊断练习**，不是已执行的故障实验。环境没有真实 RNIC、交换机和 SSD 的测量数据，不能把任何示意图、推导数值或预期现象写成实测结论。标明“支持某假设”“尚未排除”比给错误根因更有用。

## 1. 先定义 P99：它不是最慢值，也不是最慢 1% 的均值

一个延迟分布的第 99 百分位描述一个分位边界，不是最大延迟，不承诺所有请求都小于它，也不直接描述它以上请求到底慢多少。有限样本、插值方式和直方图分桶会影响估计；报告 P99 时同时交付样本量、P99.9、最大值与错误/超时数。

例如一个窗口只有 1,000 个成功请求，最慢 1% 只有约 10 个样本；再往上估计 P99.9 就更不稳定。只把成功请求放入延迟分布、却不报告超时，会把最差请求从分布里“删掉”。这是测量口径错误，不是优化。

### 1.1 负载合同应先写成一行

| 维度 | 必须记录的内容 |
|---|---|
| 软件与硬件 | Host/Target 栈、内核/SPDK/fio 版本、固件、NIC/SSD 型号、CPU/NUMA/PCIe 拓扑 |
| 请求形状 | 读/写分开，bs、对齐、随机范围、分布、是否缓存、是否要求持久化 |
| 并发与到达 | jobs、qpair 数、配置 QD、**实际在途量**、目标与实际 IOPS、突发/闭环/回放 |
| 时间与样本 | 预热、采样窗口、稳态判据、重复次数、请求数、错误、超时、重试 |
| 测量定义 | `lat` 还是 `clat`，起止事件、时钟域、桶边界、采样率、丢失事件 |
| 干扰条件 | 其他租户、CPU 频率/功耗策略、温度、后台任务、监控开销 |

对于 fio，`slat`、`clat`、`lat` 的起止定义随引擎有差别；`lat_percentiles=1` 请求总延迟分位数，不能把默认完成延迟分位数偷偷改名为应用总延迟。fio 外部业务排队也不会自动进入它的计时范围。窗口直方图 `write_hist_log + log_hist_msec` 记录的是 **completion latency**；它不因开启 `lat_percentiles` 就自动变成窗口总延迟直方图。[^fio]

**闭环负载的限制。** 固定 QD 测试在系统变慢后会减少新提交速率，适合研究在途约束下的服务能力，但不等价于固定到达率的线上业务。需要另外记录 offered load 和请求在负载发生器处的等待，或使用经验证的定速/回放方式。不要机械地给 `io_uring` 加上 `io_submit_mode=offload` 就声称解决 coordinated omission：fio 文档对 async 引擎的可靠适用性明确有保留。[^fio]

## 2. 分位数不可加减：用一个反例把规则钉住

[[5.4 延迟分解方法论]] 的“分段对账”需要进一步收紧：**P50 也不能加减。** 可加性属于同一批请求上可加的随机变量及其均值，不属于“看起来比较稳定”的某个分位数。

构造 100 个请求，每个请求经过 A、B 两段。第 1 个请求 A=101 μs，第 2 个请求 B=101 μs，其余对应段均为 1 μs。按 nearest-rank 定义：

- A 的 P99 = 1 μs，B 的 P99 = 1 μs；
- 总延迟中有 98 个 2 μs、2 个 102 μs，因此总 P99 = **102 μs**，而不是 2 μs。

下面是纯计算验证，不需要真实设备。它把“各层长尾出现在不同请求上”直接编码出来；分位算法明确使用 nearest-rank，避免库默认插值造成例子数值不同。

```python
from math import ceil

def percentile_nearest_rank(values: list[int], p: float) -> int:
    if not values or not 0 < p <= 1:
        raise ValueError("需要非空样本，且 0 < p <= 1")
    return sorted(values)[ceil(len(values) * p) - 1]

a = [101] + [1] * 99
b = [1, 101] + [1] * 98
total = [x + y for x, y in zip(a, b)]
print(*(percentile_nearest_rank(x, 0.99) for x in (a, b, total)))
# 输出：1 1 102
```

代码只有排序和计算，不涉及异步执行主体。它证明的是“把各段 P99 相加”可能严重低估；换一种样本相关结构，也可能高估。P50 的反例同样简单：A=`[1,1,11]`，B=`[11,1,1]`，各自中位数都为 1，总和中位数却为 12。

窗口聚合遵守同一原则：**先合并具有相同边界的直方图桶计数，再求分位数**；不能平均每分钟 P99，也不能按 IOPS 加权平均 P99。计数加权可以构成总体分布，分位数加权不能。读写和不同负载类应先分别报告，防止慢流量被大流量掩盖。

## 3. 双时钟域：能相减的是时长，不是两台机器的裸时间戳

![[图片/SVG/8_9_9_10_1.svg|900]]

图中 Host 与 Target 各有自己的计时器。箭头表达因果，不暗示两个本地时钟的刻度已经同步。P99 归因先要解决这个测量几何问题，再谈哪个指标升高。

### 3.1 先给一个请求定义边界

下列 `H_* / T_*` 是**本文建议的教学埋点名，不是 SPDK 自带 trace 名称**。

| 边界 | 定义 | 时钟域 |
|---|---|---|
| `H_BEGIN` | Host 本次被测 I/O 的提交计时开始 | Host |
| `H_DONE` | Host 在定义好的完成接口观察到该 I/O 完成 | Host |
| `T_RECV_OBS` | Target 软件观察到命令接收完成 | Target |
| `T_BDEV_SUBMIT` | Target 即将向 bdev 提交该请求 | Target |
| `T_BDEV_CB` | Target 执行该请求的 bdev 完成回调 | Target |
| `T_RESP_POST_BEGIN` | **实际发布 response 之前**的记录点 | Target |

先在本地求时长，再按各自计时器频率换算到统一单位：

\[
W_i = H_{DONE,i}-H_{BEGIN,i}
\]

\[
R_i = T_{RESP\_POST\_BEGIN,i}-T_{RECV\_OBS,i}
\]

如果 i 真的是同一条成功请求、区间被正确嵌套、时钟速率误差在预算内，那么 `W_i − R_i` 可以作为一个**混合余项**。它包含 Host 提交/完成、去程传输、Target 收包到软件观察、实际响应发布和回程等未覆盖开销，**不能命名为纯网络 RTT**。

**为什么用 POST_BEGIN，不用 Target 的 COMPLETED？** response 发布之后，Host 可能已经收到了完成，而 Target 尚未观察本地 SEND CQE 或完成请求对象回收。此时 Target 的 `RDMA_REQ_COMPLETED` 可能在 Host 完成之后。用它当“必然嵌套在 Host I/O 中”的端点，会破坏余项模型，甚至产生负值。也不要在 post 返回后才采一个时间戳，却默认它早于 Host 完成。[^rdma-src]

`T_BDEV_CB − T_BDEV_SUBMIT` 也不是纯介质时间：它包含 bdev、驱动/队列、设备执行和完成观察延迟。普通读路径的数据回传区间也会包含 WR 资源等待和 CPU 推进，不能全部记给交换机。

### 3.2 没有逐请求关联，平均值也不自动合法

对同一批、同一权重的可加请求时长，均值可以分段求和。来自两个独立测试、不同窗口或不同成功请求集合的均值之差，则只是一种对照差异，不是某一层的精确开销。

跨机相减本地时间戳需要有误差预算：时钟偏移、漂移、时间戳采集位置、软件观察延迟都算进去。仅写“已经开 NTP/PTP”不足以支持微秒级单程延迟结论。没有可靠同步时，优先保留同域时长和因果关系；只有单位相同还不够，计时器速率换算也必须正确。

### 3.3 请求 ID 必须跨过复用与重试

至少记录 `run_id + controller/connection_epoch + qid + cid + generation`，并保留 bdev 子请求与父请求关系。CID 和对象指针会复用，连接重建后旧 ID 也可能重现；只靠 LBA 或邻近时间戳无法可靠区分相同地址并发读、重试、拆分与合并。[^rdma-src]

原生工具未必直接给出整条链的统一 ID。可以使用已有的对象关联信息，再增加必要的关联埋点；不能凭空假定 fio、内核 trace 和 SPDK trace 的 ID 已经互通。报告必须说明采样率、环形缓冲覆盖、丢事件、缺失配对比例，以及排除请求的规则。

## 4. 在 SPDK 上把等待落实到真实状态

以下事件名在 SPDK **`v25.09/lib/nvmf/rdma.c`** 的 trace 注册中可核对。在线文档的示例日志可能来自更早版本，名字不完全相同；本机 trace 定义优先。[^rdma-src]

| 原生事件 / 事件对 | 可以追问的问题 | 不能直接下的结论 |
|---|---|---|
| `RDMA_REQ_NEW`、`RDMA_REQ_NEED_BUFFER` | 请求何时进入处理，是否等缓冲 | NEW 不是网线上物理到包的硬件时间戳 |
| `RDMA_REQ_TX_PENDING_H2C` → 后续推进 | 写数据拉取是否等 transport 资源 | pending 不等于交换机正在丢包 |
| `RDMA_REQ_TX_H2C` → `RDMA_REQ_RDY_TO_EXECUTE` | 写数据传输及软件观察是否拖延 | 整段不等于线路传输时延 |
| `RDMA_REQ_EXECUTING` → `RDMA_REQ_EXECUTED` | 后端执行跨度是否变大 | 不等于纯 NAND 或 SSD 内部固件时间 |
| `RDMA_REQ_TX_PENDING_C2H` | 读数据回传资源是否受限 | 不能单凭它证明 PCIe 饱和 |
| `RDMA_REQ_RDY2COMPL_PEND`、`RDMA_REQ_COMPLETING` | response 提交/完成阶段是否积压 | 不同方向、in-capsule 优化不一定经过相同事件序列 |
| `RDMA_REQ_COMPLETED` | Target 请求何时满足回收推进条件 | 不等于 Host 的应用完成时间 |

`TRACE_BDEV_IO_START / TRACE_BDEV_IO_DONE` 与 RDMA 请求对象的关系也在该源码中注册；是否采到了足够关联字段，要对本机 trace 文件验证。遇到区间增长，进一步区分**资源 pending、执行耗时、完成产生后未被软件收割**，不要只把事件之间的跨度贴上一个硬件名称。

trace 使用共享内存环形缓冲；快照可能已经丢掉较早的事件。官方 `spdk_trace_record` 能连续记录，但记录器本身的 CPU、存储和调度开销也需要测量。先开启必要的 `nvmf_rdma` 组，在短复现窗口采集，再考虑加 bdev/NVMe 组；不要默认 `-e all` 对性能完全无扰动。[^trace]

## 5. 七层证据表：工具看到哪里，就只能先证明到哪里

| 层 | 首轮证据 | 高价值对照 | 常见越界归因 |
|---|---|---|---|
| **CPU / Reactor** | 每核采样、线程/poller busy/idle 增量、调度延迟、热点栈、完成推进间隔 | 保持负载相同，调整热点 qpair 分布或隔离干扰线程 | CPU 100% 就是饱和；空轮询也可能满核 |
| **NUMA** | CPU 位置、实际内存/大页分配、NIC/SSD 节点、可用互联计数 | CPU 与 buffer 位置分开做 A/B，重建资源确认真正改变 | 绑核正确就等于 DMA 本地；`numa_node=-1` 等于本地 |
| **PCIe** | `LnkCap/LnkSta`、链路宽度/速率、上游拓扑、错误增量、可用带宽计数 | 确认链路恢复或更换隔离拓扑后，在同负载重复 | 设备标称 x16 就按 x16 算；AER 正常就排除带宽瓶颈 |
| **NIC** | 字节/包速率、丢弃/错误、按优先级 PFC 收发与时长、驱动统计 | 对齐窗口、方向和 priority，比较受影响连接 | 全端口均值低就没有瞬时拥塞；计数器名称各厂一致 |
| **Switch** | 实际路径、端口/队列 watermark、ECN、PFC、出口丢弃、共享缓冲 | 在隔离环境改变突发或竞争流，验证受影响队列 | 有 PFC 的端口就是拥塞起点；watermark 能替代完整队列时序 |
| **RDMA** | QP 状态、重试/RNR/访问错误、read 并发配置、pending、收发资源 | 在相同 payload/并发下检查资源窗口与完成推进 | 把 RNR、链路丢包、rkey 错误混成同一种重试 |
| **NVMe / bdev** | bdev 延迟/队列、驱动完成跨度、设备健康、温度、可用厂商日志 | 同一后端原位观测；本地/远端和 malloc 替换辅助缩小范围 | callback 跨度就是 NAND；SMART 没报警就没有尾延迟问题 |

这张表采用“利用率、饱和/排队、错误分别检查”的思路，但每项都要落到实际资源与单位上。USE 是组织调查的方法，不是一个指标就能定责的规则。[^use]

### 5.1 CPU、NUMA、PCIe：别把拓扑错位当作网络抖动

检查 `spdk_thread`、操作系统线程和逻辑核的对应关系，再看热点连接是否集中。扩大 Reactor core mask 并不自动改变全部 qpair 的归属；迁移后内存页也不保证跟着迁移。`numastat -p` 能帮助核对分配，但不是 DMA 或远程访存流量计。设备节点信息缺失时，`-1` 应保留为未知，而不是在报告中填“node 0”。[^concurrency]

PCIe 应沿 `NIC/SSD → 下游端口 → PCIe switch/Root Port → CPU/内存` 看共享链路。核对的是 **实际协商状态 LnkSta**，不是只读最大能力 LnkCap。AER 或链路错误增量可以提供线索，但纠错计数与慢请求同时出现不自动证明因果；没有错误也不能排除正常带宽竞争。恢复链路/驱动绑定属于维护变更，不是只读排障步骤。[^pci][^pciutils]

### 5.2 NIC、Switch、RDMA：区分反馈、症状和根因

以 mlx5 为例，ethtool 可暴露按优先级的 pause 计数、持续时间及其他物理端口计数，但字段、单位与支持范围必须对应驱动文档。读两个时刻的差值并处理重置、回绕；不同 counter 的“字节”“时间单位”不能自行猜成同一口径。[^mlx5]

PFC 的暂停可能是下游拥塞传播来的背压，受影响端口未必是源头。ECN/CNP 增长可以说明反馈机制在工作，不单独证明丢包，也不证明拥塞已被有效压住。要把受影响的流映射到实际 ECMP 路径、DSCP/PCP/priority 和交换机队列，再看时间与方向；全端口均值可能掩盖微突发。交换机 CLI 随厂商/ASIC 变化，本文不编造统一的“查询所有 RoCE 队列”命令。[^roce]

**RoCE 快路径不等于 Linux 普通 TCP/IP 数据路径。** `nstat TcpRetransSegs` 看不到 RDMA 传输级重试；普通 tcpdump 是否能看到对应流量、`tc netem` 是否影响 RNIC offload 路径，都需要验证。不能“netem 加了延迟但 P99 不变”就宣布 fabric 已排除。[^roce][^host-rdma]

### 5.3 SPDK 后端：内核块工具的盲区要写进报告

当本地 PCIe SSD 由 SPDK 用户态驱动接管，针对普通内核块层的 `iostat`、`blktrace`、`biolatency` 不会给出它的完整 I/O 路径。Host 若使用 Linux initiator，Host 块层仍可观测，但它看到的远端块请求跨度包含 transport、Target 和后端。[^nvme][^blk-mq]

SPDK 路径改用 bdev 统计/直方图、RDMA/bdev/NVMe trace 与设备管理接口。`bdev_get_iostat` 是聚合统计，不是逐请求 P99；直方图要确认启用状态、分桶和 tick 频率。健康信息可通过支持的 `bdev_nvme_get_controller_health_info` 获取；可选 CUSE 是另一套接口，不能默认存在标准 `/dev/nvme…` 节点。[^rpc][^nvme]

## 6. 一套低风险采集顺序

下面命令不自动切换驱动、不改 PFC/ECN 参数、不重置设备。它们仍会消耗资源，应在授权实验窗口使用。每段先设置环境变量，失败时停止，不猜测设备名。

### 6.1 留下拓扑与设备身份

先用 `IFACE` 标识实验 RNIC 的 netdev，`SSD_BDF` 标识 **Target 的本地 PCIe SSD**。BDF 应从现有配置核对，不是远端 Host namespace 的编号；输出可能包含序列号等信息，对外发布前脱敏。

```bash
: "${IFACE:?设置实验 RNIC 的 netdev 名称}"
: "${SSD_BDF:?设置已核对的 Target SSD PCIe BDF}"
lscpu -e=CPU,NODE,SOCKET,CORE
numactl --hardware
readlink -f "/sys/class/net/$IFACE/device"
cat "/sys/class/net/$IFACE/device/numa_node"
cat "/sys/bus/pci/devices/$SSD_BDF/numa_node"
lspci -t
lspci -vv -s "$SSD_BDF"
ethtool -i "$IFACE"
```

这些命令给出位置和协商状态，不直接测请求延迟。RNIC 的 PCIe 上行也要按查到的 BDF 检查；只看 SSD 的 LnkSta 不足以覆盖整条链。查看多个 HugePage 节点的资源分布时，还要核对进程的实际映射，而不是只记录节点预留总量。

### 6.2 保存低频计数快照，再围绕异常加密采样

以下以已经运行的实验 Target 为对象。确认返回的方法后，才调用该实例支持的统计接口；不支持的接口标为缺失证据，不伪造零值。[^rpc]

```bash
: "${RPC_SOCK:?设置实验 Target 的 RPC socket 路径}"
python3 scripts/rpc.py -s "$RPC_SOCK" rpc_get_methods
python3 scripts/rpc.py -s "$RPC_SOCK" thread_get_stats
python3 scripts/rpc.py -s "$RPC_SOCK" thread_get_pollers
python3 scripts/rpc.py -s "$RPC_SOCK" nvmf_get_stats
python3 scripts/rpc.py -s "$RPC_SOCK" bdev_get_iostat
ethtool -S "$IFACE"
rdma link show
rdma resource show qp
```

负载前后各保存一次带单调时间/墙钟时间标记的原始结果，算区间增量；不要把启动以来累计的 pause 次数拿去和一个 1 秒的 P99 窗口对应。汇总若只每秒采一次，只能发现秒级变化；微突发仍需要设备提供的峰值、事件或更细粒度遥测。

需要 bdev 直方图时，先运行 `bdev_enable_histogram --help`、`bdev_get_histogram --help`，按本机版本对目标 bdev 启用并记录配置。全局统计正常但某个 poller 异常时，进一步保存 Reactor/线程映射，再做 CPU profiling。持续高频 JSON-RPC 不应替代低开销 trace。

### 6.3 fio 输出：总延迟与窗口完成直方图分开命名

`DEV` 仍须是已核对的实验远端块设备，不能因为只读就对线上服务任意施压。基线使用一个 job，先减少变量；扩展到多 job 后保留每 job 结果。[^fio]

```bash
: "${DEV:?设置已核对的实验远端块设备}"
test -b "$DEV" || { echo "DEV 不是块设备" >&2; exit 1; }
RUN="p99-$(date -u +%Y%m%dT%H%M%SZ)"
mkdir -p "$RUN"
fio --name=e2e --filename="$DEV" --readonly --rw=randread \
    --ioengine=io_uring --direct=1 --bs=4k --iodepth=32 --numjobs=1 \
    --time_based=1 --ramp_time=15 --runtime=60 \
    --lat_percentiles=1 --percentile_list=50:95:99:99.9 \
    --write_hist_log="$RUN/clat" --log_hist_msec=1000 \
    --output-format=json+ --output="$RUN/fio.json"
```

这产生一份最终汇总，以及 1 秒窗口的 **clat** 直方图。不要把 `log_avg_msec` 的平均延迟日志排序后称作请求 P99。若需要每秒 **lat** 分布，应使用确实记录该口径的请求日志/埋点，并评估逐 I/O 记录带来的开销；不要擅自把 clat 当替代品。确认实际达到的 QD 后，再比较其他组。

### 6.4 trace 的取证边界

启动参数、trace 组列表和输出文件名应从当前实验实例的帮助与日志读取。需要重启启用时，先安排隔离窗口；不要对正在运行的生产 Target 照抄启动命令。

```bash
build/bin/nvmf_tgt --help
python3 scripts/rpc.py -s "$RPC_SOCK" trace_get_tpoint_group_mask
build/bin/spdk_trace --help
build/bin/spdk_trace_record --help
```

检查完帮助后，使用实例日志给出的 PID/共享内存名采集，而不是猜一个固定路径。结束时要记录事件是否完整、记录器是否掉队、采集前后性能有无变化。使用原生事件量段时，按源码确认事件发生位置；采用第 3 节的精确嵌套模型则需要相应自定义埋点，不能用“名字看起来类似”的事件硬替换。[^trace][^rdma-src]

## 7. 从相关性走到因果：一次只改变能解释的因素

![[图片/SVG/8_9_9_10_2.svg|900]]

先找到异常第一次出现的**观测区间**，再在该区间中提出机制假设。图中每层都是“证据 → 干预 → 复测”，不是“看见某个计数器 → 宣布根因”。

| 对照 | 能帮助缩小什么范围 | 需要防止的混杂 |
|---|---|---|
| 真实 NVMe bdev → malloc bdev | 异常是否依赖真实后端路径 | malloc 也用 CPU/内存，且吞吐上升会改变网络负载 |
| 远端路径 → 本地同类后端测试 | fabric/前端是否值得继续调查 | 工作线程、并发模型、负载到达分布已改变 |
| 固定内存位置，只调整处理 CPU | CPU 调度/局部性是否敏感 | 原有 I/O channel、qpair 归属是否随之变化 |
| 固定 CPU，重建并验证 buffer 位置 | DMA/内存局部性是否敏感 | 仅改 numactl 参数未必改变已经分配的大页 |
| 固定总请求率，调整 qpair 分布 | 单队列/单线程热点是否敏感 | 只增加 jobs 同时增加总负载，不能当作纯扩展性对照 |
| 固定数据量，改变突发形状 | 微突发与队列容量是否相关 | 平均 IOPS 相同不等于瞬时负载相同 |
| 更换受控 fabric 路径 | 某条实际链路/队列是否相关 | ECMP、MTU、优先级映射、竞争流需重新确认 |

比较尾延迟时，尽量同时给出**匹配负载点**和**容量曲线**。只在同 QD 比较两种更快/更慢的实现，会同时改变吞吐和排队状态；不能把全部 P99 差异归给被修改的那一个组件。A→B→A 的可逆重复能帮助发现温度、缓存与后台任务的趋势，但仍需足够的样本和重复窗口。

## 8. 四个诊断练习：每个都必须能被反证

### 8.1 CPU 满核，但究竟是忙轮询还是推进不足？

**观察目标：** 端到端尾延迟变大，某条连接的后端“提交到回调”跨度也变大。

先采热点栈、线程/poller busy 增量和完成观察间隔。若大量时间是空轮询，且资源不排队，满核不能解释慢；若某个 Reactor 长回调或调度延迟同时阻塞了 RDMA 与 NVMe 完成推进，才有 CPU 路径的机制证据。保持总 IOPS 不变，把热点 qpair 重新分配到实际可用的处理上下文，复测后再恢复。

**可反证条件：** 改善 CPU 推进后，该段分布不变；或完成推进正常而设备/链路区间持续变长。此时不能继续把“CPU 100%”当结论。后端 callback 延迟变长也不单独证明 SSD GC。[^concurrency][^nvme]

### 8.2 CPU 已绑对节点，数据仍跨 NUMA？

**观察目标：** 小块低负载尚可，大块或高吞吐时 P99 明显恶化，NIC 与 SSD 单独能力看起来充足。

检查实际大页/缓冲位置。如果 CPU、NIC、SSD 在 node 0，而 buffer 在 node 1，CPU 与两类设备都可能为访问 buffer 付出跨节点成本。若 CPU 也在 node 1，则不能再声称 CPU 对该 buffer 远程访存，应分别画每个参与者的路径。

**干预：** 在隔离实例中重建缓冲，固定其实际节点，其他条件不变；记录互联/内存计数与匹配吞吐点分布，再恢复原布局。只是重启并加一个 CPU mask，不构成“内存位置已改变”的证据。没有硬件互联计数时，应保留归因不确定性。[^concurrency]

### 8.3 ECN/PFC 与 P99 同时升高，就是交换机根因？

**观察目标：** 端到端尾部增长，Target 后端执行区间相对稳定，传输相关区间变长。

对齐受影响的 QP、实际路径和 priority，检查出口队列峰值、ECN、PFC 方向与持续时间，同时排除 Target 接收资源不足。ECN 是反馈证据；PFC 可能从更下游传播。先找拥塞与积压从哪里开始，而不是选择计数最大的一端。

**干预：** 在隔离网络降低竞争流突发性、保持平均测试负载，观察同一队列证据与同一批请求传输区间是否一起恢复。若只有应用 P99 变好、网络证据没变化，也可能是负载发生器变了；若后端也出现同步长尾，应继续检查共同负载因素。[^roce][^mlx5]

### 8.4 网络和 CPU 都没满，PCIe 仍会限速吗？

**观察目标：** 大块吞吐出现平台，某些拓扑组合比单设备基线差，延迟随队列增长。

核对实际协商宽度/速率和共享上行。两块设备各自标称带宽足够，不代表共享的上游端口能同时承载两者。健康的链路也可能正常地被容量打满，没有 AER 并不排除此情况。

**干预：** 维护窗口中恢复异常协商状态，或在可比硬件上调整受控拓扑；保持请求率和缓冲位置一致，复测吞吐拐点与时延分布。如果只更换了整台机器，则得到的是整体平台对照，不能声称单独证明 PCIe。[^pci][^pciutils]

## 9. 收口报告：把“知道很多组件”变成可审查的工程产物

| 报告字段 | 最低内容 |
|---|---|
| 问题与范围 | 哪个负载、哪个完成口径、何时、多少请求受到影响 |
| 拓扑与版本 | Host/Target、CPU/内存节点、PCIe、NIC/交换机、后端、软件配置 |
| 基线与异常 | 原始分布、样本量、实际吞吐/QD、错误/超时、分时间窗口结果 |
| 请求关联 | ID 组成、拆分/重试处理、丢事件、时钟域与误差预算 |
| 假设与反证 | 机制如何导致该区间变慢，什么结果会推翻它 |
| 干预与回滚 | 只改了什么、什么没变、如何验证改变生效、怎样恢复 |
| 重复与门禁 | A/B/A 或重复试验、噪声范围、匹配负载点、吞吐和错误没有恶化 |
| 未解决问题 | 哪些层仍缺观测，下一步需要哪一项证据，而不是罗列所有工具 |

样本存在时间相关性时，不能把百万个相关请求当成百万次独立重复。优先给出多轮窗口的波动，再选择符合数据结构的置信区间方法；分块重采样也要解释分块依据，不能用一个很窄的误差条掩盖实验设计的问题。

性能改进还必须经过正确性和恢复检查。读数据校验、写/Flush/FUA 语义、超时与重连、错误率和资源回收应按测试范围建立门禁。减小 timeout 让成功请求 P99 更好、或者丢掉慢请求，都不是服务质量改进。结果进入 [[9.7 SLO 与性能回归]] 的门禁，操作步骤进入 [[9.8 Runbook 与可运维产物]]；故障注入只在授权隔离环境按 [[9.6 故障注入矩阵]] 执行。

> [!question] 面试时用一条证据链回答
> “我先固定请求形状和完成口径，确认不是统计或负载发生器偏差。然后按 Host 与 Target 各自的时钟域量段，关联同一请求，找尾部增长的区间；再结合该区间的队列、计数器和执行上下文提出假设。最后在相同负载点只改变一个可验证的因素，做可逆重复，并检查吞吐、错误、数据正确性与恢复语义。缺失的证据会明确写出来，不会用 P99 相减或一个利用率指标代替根因。”
