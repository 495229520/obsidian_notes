# 跨层性能归因：CPU、NUMA、PCIe、NIC、Switch、RDMA 与 NVMe 的 P99

> [!abstract] 从“指标相关”走到“同一请求的证据链”
> **先确认慢的是同一请求的哪一道边界，再问哪种机制让这段变慢。** 请求 ID 连接业务层，传输批次连接运行时，队列埋点解释软件等待，NIC/交换机计数说明共享资源状态，GPU 时间线最后回答消费者是否真正被阻塞。没有这些连接，CPU、NIC、GPU 三张图同时变红，也可能只是同一负载变化的三个后果。

本篇保留原来的 **NVMe/RDMA + SPDK Target + 本地 NVMe 后端** 方法，并增加第 5—11 节的完整 KV 传输案例。它与 [[8.21 NCCL 异步执行与性能：CUDA Stream、Overlap、nccl-tests 与故障诊断]] 共用“提交、完成观察、可消费、业务结束”四层边界，但**不把 NIXL 传输当作 NCCL collective**。

> [!info] 证据等级、版本和可执行性
> 核对日期：**2026-09-19**。SPDK 状态名保留原笔记的 `v25.09` 源码锚点；KV 案例固定到 **vLLM `v0.10.2` 的 `NixlConnector`**，用于可复查地定位接口，不代表推荐部署旧版本，也不代表当前主分支结构未变。
>
> 本篇没有真实 GPU、RNIC、交换机的采样输入。**毫秒时间线、批次、请求 ID、计数器数值和 A/B 结果都是构造样本。** CPU 对账程序已执行，验证的是数据关联与算术，不是硬件性能。实际部署须填写原始 trace、日志、counter 与版本清单，才能形成实测结论。

## 1. 先固定被测工作，再讨论 P99

### 1.1 P99 不等于最慢值，也不能只统计“幸存请求”

P99 是指定样本分布的百分位边界，不是最大值，也不是最慢 1% 的平均值。报告时明确分位算法或直方图桶、样本量、预热与稳态窗口，并同时报告 P99.9、最大值、错误、重试和超时。删掉超时后成功请求 P99 下降，不是服务质量提高。

| 合同项 | NVMe/RDMA 实验 | KV 传输实验新增内容 |
|---|---|---|
| 请求形状 | 读写、块大小、QD、持久化语义 | prompt 长度、命中率、实际 KV 字节、层/块布局 |
| 到达模型 | 闭环、定速、回放、突发 | 请求到达、Prefill 完成节奏、Decode 批次 |
| 并发实体 | jobs、qpair、Reactor、buffer | request、worker、TP/PP rank、batch、rail |
| 完成口径 | Host 完成、Target 回调、持久化 | transport DONE、KV 可消费、首个 Decode token |
| 实际资源 | CPU、内存 NUMA、PCIe、NIC、SSD | GPU UUID、显存容量、CUDA stream、GDR/staging |
| 失败与观测 | 错误、重试、掉 trace | 取消、过期 attempt、未完成 batch、缺失 worker |

固定 QD 的闭环系统在变慢时会减少新提交，不能代表固定到达率的线上排队。对照除了“相同 QD”，还应给出匹配 offered load 的延迟与容量曲线。KV 场景中，修改缓存命中率、prompt 分布、TP 配置或传输字节，本身就改变了被测工作。

fio 的 `slat/clat/lat` 需要按引擎解释；`write_hist_log` 产生的窗口直方图是 completion latency，不会因开启 `lat_percentiles` 自动变成端到端业务延迟。也不能对异步引擎机械添加 `io_submit_mode=offload` 就声称解决了 coordinated omission；应遵守 fio 对适用范围的限制。[^fio]

### 1.2 分位数不相加，也不相减

构造 100 个请求：A 段只有第一个请求为 101 μs，其余为 1；B 段只有第二个请求为 101 μs，其余为 1。nearest-rank 定义下，A、B 的 P99 都是 1 μs，但总耗时的 P99 是 102 μs。

以下纯计算直接验证“长尾不发生在同一个请求上”的后果；它没有设备时序，不需要异步图。

```python
from math import ceil

def percentile(values: list[float], p: float) -> float:
    if not values or not 0 < p <= 1:
        raise ValueError('invalid percentile input')
    return sorted(values)[ceil(len(values) * p) - 1]

a = [101.0] + [1.0] * 99
b = [1.0, 101.0] + [1.0] * 98
total = [x + y for x, y in zip(a, b)]
assert [percentile(v, 0.99) for v in (a, b, total)] == [1.0, 1.0, 102.0]
```

即使 P50 也没有可加性：`[1,1,11]` 与 `[11,1,1]` 的中位数各为 1，相加后的中位数为 12。只有同一组请求、相同权重、正确可加的逐请求时长及其均值，才有相应可加关系。

聚合窗口要先合并同桶边界的计数，再求分位数，不能平均或按 IOPS 加权平均 P99。多 rank 也先按同一请求汇合，再形成请求分布，而不是拿各 worker 的 P99 拼接。基础方法衔接 [[9.5 p99 毛刺定位]]。

## 2. 时钟域与请求身份：看起来对齐，不等于可以相减

### 2.1 同域量段，跨域连因果

每个事件至少保存 `clock_domain、timestamp、unit、host、process/worker_epoch`。同一主机的进程间单调时钟也要确认容器 time namespace、采集接口及校准条件；GPU 时间来自 profiler 映射或有明确范围的 event 持续时间，不能直接当作 CPU 单调时钟。

跨 host 的裸 `perf_counter_ns()` 不能相减。PTP/NTP 已启用只是状态，不是精度证明；偏移、漂移、采集位置、时间戳开销及 GPU 映射误差都应进入预算。若两端映射误差分别为 $\epsilon_A,\epsilon_B$，跨域时间差至少要考虑合成误差边界，不能用不确定性大于观测差值的数据做微秒级因果判决。

无法可靠对齐时，保留各端本地时长，通过 request/attempt/message 关系连接因果箭头。宁可标出“去程与远端处理尚未分解”，也不把两个来源的时间戳减成一个看似精确的网络时延。

### 2.2 NVMe-oF 的嵌套区间仍有用，但余项不是纯网络

下面 `H_* / T_*` 是建议埋点，不是 SPDK 原生 trace 名称：

$$
W_i=H_{DONE,i}-H_{BEGIN,i}
$$
$$
R_i=T_{RESP\_POST\_BEGIN,i}-T_{RECV\_OBS,i}
$$

只有当 i 是同一条请求，区间嵌套成立，时间单位与速率换算正确时，$W_i-R_i$ 才是合法的混合余项。它还包含 Host 提交/完成、软件观察、往返传输和未覆盖的 Target 处理，**不能命名为纯网络 RTT**。

不要拿 Target 的最终 `RDMA_REQ_COMPLETED` 当作必然早于 Host 完成的端点：Host 可能已收到响应，而 Target 尚未观察本地 SEND 完成或回收对象。`RESP_POST_BEGIN` 也不能悄悄替换为 post 返回后的采样点。原笔记这一边界应继续保留。[^spdk-rdma]

### 2.3 ID 必须跨过复用、重试与合并

NVMe 链至少需要 `run_id + connection_epoch + qid + cid + generation`。CID、内存地址、对象指针和 LBA 都可能复用，不适合作为全局唯一键。

KV 传输更复杂：一个业务请求可以有多个 attempt；一个 attempt 跨多个 rank；一个 batch 可能包含多个请求；一个请求也可能拆成多个 batch。需要显式关系表，不能只凭“这个时刻附近有个 handle”做关联。下文给出具体模型。

## 3. 保留 NVMe/RDMA 方法：真实状态名与观测盲区

以下原生事件可在 SPDK `v25.09/lib/nvmf/rdma.c` 中复查。它们是软件状态边界，不是交换机线上的硬件到包时间。[^spdk-rdma]

| 原生状态/跨度 | 有助于调查 | 不能直接断言 |
|---|---|---|
| `RDMA_REQ_NEW` → `NEED_BUFFER` 等 | Target 入站与缓冲等待 | 从网线到程序的全部时延 |
| `RDMA_REQ_TX_PENDING_H2C` | 拉取写数据前的资源等待 | 交换机正在丢包 |
| `RDMA_REQ_TX_H2C` → `RDY_TO_EXECUTE` | H2C 数据传输及完成观察 | 纯线上传输时长 |
| `RDMA_REQ_EXECUTING` → `EXECUTED` | 后端执行跨度 | 纯 NAND/SSD 固件时间 |
| `RDMA_REQ_TX_PENDING_C2H` | 读数据回传等待 | PCIe 一定饱和 |
| `RDMA_REQ_RDY2COMPL_PEND` / `COMPLETING` | 响应发布路径 | Host 业务已经完成 |
| `RDMA_REQ_COMPLETED` | Target 回收推进边界 | 与 Host 的完成时间完全相同 |

四个盲区必须写进报告。第一，SPDK CPU 满核可能只是空轮询，需要 busy/idle、热点栈、队列和推进间隔区分。第二，SPDK 用户态 NVMe 驱动接管的设备路径不能靠内核 `iostat/blktrace/biolatency` 完整覆盖。第三，`bdev_get_iostat` 是聚合统计，不是逐请求 P99。第四，RoCE offload 不等同于 TCP 数据路径，`TcpRetransSegs` 或未经验证的 netem/tcpdump 结果不能替代 RDMA 证据。[^spdk-nvme][^spdk-concurrency][^spdk-rpc][^roce]

这些原则迁移到 KV 路径后，分别变成：progress 线程满核不证明推进充分；GPU 内存上的传输不经过普通块层；总 RDMA bytes 不等于每请求完成；GPU 上没有 NCCL kernel 不代表 NIXL 没有传输。

## 4. 各资源层的假设，要配上能推翻它的证据

| 资源 | 常见误判 | 更有区分力的证据 / 对照 |
|---|---|---|
| CPU | 100% 所以是 CPU 瓶颈 | 有效推进、空轮询比例、回调耗时、run queue、完成扫描间隔 |
| NUMA | 线程绑核正确，所以路径局部 | buffer 实际归属、GPU/NIC 根复合体、DMA 路径及内存重建对照 |
| PCIe | 没有 AER，所以不可能限速 | 协商宽度/速率、共享上行、同负载吞吐拐点与可比拓扑 |
| NIC | 平均带宽没满，所以无网络瓶颈 | 单方向/单 rail、实际突发、优先级队列、时间粒度、接收资源 |
| Switch | ECN/PFC 非零，所以根因在此 | 受影响端口/队列/方向、传播起点、竞争流与可逆控制 |
| NVMe | callback 变慢，所以 SSD GC | 后端与 poller 分解；固定到达负载下替换后端做二分 |
| GPU | utilization 高，所以不在等数据 | 消费 kernel 的依赖、SM/HBM 争用、通信驻留与有效工作 |

对照必须只改一项可确认的因素。只给新进程加 `numactl` 不证明既有 GPU/host buffer 位置改变；只把 QD 调大同时提升 offered load，也不能声称发现了单队列扩展性。A→B→A、匹配负载点和独立重复比某一轮漂亮的 P99 更有说服力。

## 5. KV 案例的固定边界：vLLM NixlConnector 的 READ 拉取

### 5.1 为什么选择这个实现？

案例固定到 **vLLM `v0.10.2`** 的 `vllm/distributed/kv_transfer/kv_connector/v1/nixl_connector.py`，文件 blob 为 `17f5be76ce400c611f14676edf55c0f25e8f414a`。这份实现中能直接追到请求元数据、READ transfer 创建、异步提交、后续状态查询和 worker 完成上报。[^vllm-nixl]

本例限定：Prefill/Decode 已有可兼容的模型和 KV 布局；两个必要 TP worker 位于同一 Decode host；每 worker 传输 32 MiB，整个请求本次需要的**逻辑唯一 payload 合计 64 MiB**；每 worker 一个本地教学 batch。这个字节量是案例输入，不是某个模型的默认 KV 大小公式。握手冷热、host staging、异构 TP 等分支须另列 cohort，不能混成一份分布。

这是 **Decode 发起 READ、从 Prefill 拉取数据** 的路径，不是 AllReduce。源端 TX 和目的端 RX 是同一份数据的两种观测；把它们相加会把一次有效搬运重复计费。注册、布局与块映射的前提衔接 [[8.16 PD 分离（Prefill-Decode Disaggregation）下的 KV Cache 网络传输架构]] 和 [[8.14 分层缓存与 KV Cache 生命周期]]。

### 5.2 真实源码锚点与建议埋点

| 固定版本中的位置 | 源码所做的事 | 建议增加的观测；非原生事件名 |
|---|---|---|
| `start_load_kv()` | 处理 `reqs_to_recv`，未握手则走后台握手，随后处理 ready requests | `LOAD_ENTER`、`HANDSHAKE_WAIT`、`READY_DEQUEUE` |
| `_read_blocks_for_req()` | 把 request 与源端 engine、本地/远端 block 列表传给读取流程 | request→worker→块映射摘要 |
| `_read_blocks()` | 选择 descriptor，`make_prepped_xfer("READ", ...)` 创建 handle | `BATCH_BUILD`、`HANDLE_BIND` |
| `nixl_wrapper.transfer(handle)` | 开始异步传输 | `SUBMIT_BEGIN` / `SUBMIT_RETURN`，分开计时 |
| `_recving_transfers[request_id]` | 保存请求对应的 handle 列表 | handle 生命周期与 request/attempt 关系 |
| `_pop_done_transfers()` | `check_xfer_state()`，`PROC` 继续，`DONE` 释放 handle，错误走失败分支 | `POLL_BEGIN/END`、返回状态，释放前记录 ID |
| `get_finished()` | 收集本 worker 完成；host-buffer 分支还调用 `sync_recved_kv_to_device()` | `WORKER_RECV_DONE` 与 staging 耗时 |
| worker 输出到 scheduler | 汇合必要 worker 的结果，再恢复请求处理 | `ALL_WORKERS_READY`、`KV_USABLE`、`DISPATCH` |

前六行可直接沿固定文件追踪；最后一行是跨进程/调度边界的**接入观测要求**，不能仅在 connector 文件里加一条日志就假装已经观测到调度器。该版本 `get_finished()` 的说明明确指出，scheduler 经执行器使用各 worker 输出跟踪完成。[^vllm-nixl]

一个重要细节：该版本把 `(handle, time.perf_counter())` 加入 `_recving_transfers` 的位置在 **`transfer(handle)` 返回之后**。仅拿这个现有时间戳计算“传输延迟”，会漏掉 descriptor 准备、提交调用和此前排队，且终点仍可能是后续轮询观察，不是 NIC 硬件完成。应自己在调用前后分别记录，不能把已有字段改名后当作完整时长。[^vllm-nixl]

## 6. 关联模型：请求 → 分片/批次 → handle → 设备窗口

![[图片/SVG/8_9_9_10_4.svg|900]]

### 6.1 用业务稳定键连接局部 ID

| 实体 | 建议键 / 属性 | 解决的歧义 |
|---|---|---|
| 业务请求 | `run_id + logical_request_id` | 网关、Prefill、Decode 的本地 request ID 可能不同 |
| 一次尝试 | `attempt_id + route_epoch` | 重试/重路由不能接上旧完成 |
| 执行 worker | `engine_id + worker_epoch + tp_rank + pp_rank` | 进程重启、TP rank 复用 |
| 传输批次 | `worker_key + batch_seq + connection_epoch` | 不是单独一个可能复用的 native handle |
| 内存与块 | `allocation_generation + block_generation + layout_id` | 原地址被新对象复用、旧 descriptor 失效 |
| 设备位置 | GPU UUID/BDF、HCA/port、NIC BDF、netdev/ifindex、PF/VF、rail | “mlx5_0” 等局部名字跨主机不唯一 |
| 时间域 | `host + clock_id + calibration_id` | 防止把相同单位当成同一时钟 |

在消息元数据中传递稳定关联键，显式维护 `logical_request_id ↔ prefill_request_id ↔ decode_request_id`。不能默认两个服务生成的 `request_id` 字符串天然相等，也不必把一个服务的内部 ID 强行改成全局 ID。

### 6.2 batch 不是一个新的万能 request ID

“Batch”在这里是**诊断模型中的一组提交单元**。固定版本原生接口暴露的是 transfer handle 与请求的映射，不保证存在同名的 `batch_id` 字段。若底层一次提交合并了多个请求，应增加关系表：

| 关系字段 | 作用 |
|---|---|
| `request_attempt_key → batch_key → fragment_id` | 支持一对多和多对一，不丢失拆分与合并 |
| `src/dst_block_range、layer/rank、offset、length` | 解释真实搬了哪段 KV |
| `planned_bytes、submitted_bytes、unique_completed_bytes、retry_bytes` | 区分计划、尝试流量与逻辑有效数据 |
| `handle_bind/unbind` | handle 生命周期，防止指针/整数复用误连 |

一个请求跨两条 rail 时，要保留每个 fragment 的所属 rail；连接重建之后改变 epoch。某个 transfer 完成不等于整个 request 完成，整个 request 完成也不意味着某个聚合 batch 中其他请求都完成。

### 6.3 Request 到 NIC 的连接有两种证据强度

强连接来自 backend/provider 的可关联记录：某 handle 如何映射到连接、QP、WR、CQ，再到实际 HCA/port。该连接**不由 NixlConnector 自动完整提供**；需要底层已有遥测或额外埋点。其次是较弱的“批次使用的 worker/设备与同一窗口的端口观测”。这种关系只能支持资源层假设，不能把端口字节精确分给一个请求。

若 backend 自动分流或多 rail，不得仅凭 GPU-NIC 邻近关系就宣称走了那张网卡。应保存实际 transport/rail 选择证据。无法进一步映射到 QP 时，报告明确写“端口级同期证据”。

请求 ID、handle、block ID 都属于高基数字段，保留在 trace/log 中。聚合 metrics 使用有界标签，如 engine、worker、状态、大小桶、rail；不要把每个 request ID 变成长期时序数据库的一组标签。

## 7. 一套埋点合同：每个边界对应一个明确动作

下面均为本笔记建议增加的语义事件，不是声称 vLLM/NIXL 已原生导出这些名字。

| 事件 | 精确定义 | 它之后还可能等什么 |
|---|---|---|
| `D_ADMIT` | Decode 端接受本次 handoff 尝试 | 容量与接收 block |
| `BLOCKS_RESERVED` | 本次需要的目标 block 已保留 | descriptor、握手、软件提交队列 |
| `XFER_QUEUED` / `DEQUEUED` | 同一批次实际入队/出队 | 不可以用函数调用间隔替代 |
| `SUBMIT_BEGIN/RETURN` | 调用 `transfer(handle)` 前后 | backend 推进、对端、网络、完成观察 |
| `POLL_BEGIN/END(status)` | 状态查询前后，保存返回码 | 其他 handle、其他 worker |
| `WORKER_RECV_DONE` | 本 worker 所需 handle 都完成 | host staging、可见性、跨 worker 汇合 |
| `KV_USABLE` | 此次尝试的全部必要分片满足 GPU 消费契约 | 调度/批次/其他计算依赖 |
| `DISPATCH` | 调度器实际将请求交给执行路径 | CPU launch 与 GPU 前置工作 |
| `GPU_DECODE_BEGIN` | 依赖这份 KV 的第一个 Decode kernel 真正开始 | 后续计算、采样和响应处理 |
| `SERVER_TOKEN_READY` | 服务端定义的本次 Decode token 可交付 | 发往客户端的排队和传输 |

事件记录建议包含：稳定键、原生对象 ID、时间域、单调时间戳、单位、线程、GPU/stream、字节、状态和必要的父子关系。日志应采用低开销缓冲写入；不在每个 poll 上同步刷磁盘，也不为了埋点在热路径里插 `cudaDeviceSynchronize()`。

针对 timeout/cancel，必须产生独立终态；没有 `KV_USABLE` 不是“耗时为零”，而是尚未完成、失败或证据缺失。遇到丢 trace，要报告覆盖率及排除规则，不能只保留看起来完整的快请求。

## 8. 16 ms 构造案例：钱究竟花在哪里？

![[图片/SVG/8_9_9_10_5.svg|900]]

### 8.1 先声明时钟与完成口径

业务键为 `demo-001 / R-017 / attempt=2`。两个 worker 都在 Decode host D0，CPU 事件使用已确认可比的单调时间，GPU activity 假设已由 profiler 映射到同一轴。源端 Prefill 的事件只作为因果前驱，不参与以下裸时间戳相减。

本节计算的是 **Decode 接受 handoff 到服务端本次 Decode token ready**，不是从用户发出请求开始的完整 TTFT。完整 TTFT 还可能包括入口排队、Prefill、路由和输出网络；某些 PD 架构由 Prefill 输出首 token，因此不能把这里的 first Decode token 直接改名为用户首 token。

### 8.2 请求主干：八段相加等于 16 ms

| 观察区间 | 时间轴 / ms | 时长 / ms | 合法解释 |
|---|---|---:|---|
| `D_ADMIT → BLOCKS_RESERVED` | 0.0—1.0 | 1.0 | 容量准入与 block 预留路径 |
| `XFER_QUEUED → DEQUEUED` | 1.0—4.0 | 3.0 | 已有独立入队/出队埋点的软件等待 |
| `SUBMIT_BEGIN → SUBMIT_RETURN` | 4.0—4.2 | 0.2 | 本例两个 worker 的提交包络；不是时长相加 |
| `SUBMIT_RETURN → 最后 worker DONE 观察` | 4.2—10.0 | 5.8 | backend/数据路径/进展/观察的混合跨度 |
| `最后 worker DONE → KV_USABLE` | 10.0—10.4 | 0.4 | 跨 worker 汇合及本例的可消费发布路径 |
| `KV_USABLE → DISPATCH` | 10.4—12.0 | 1.6 | 完成了传输，仍等待调度 |
| `DISPATCH → GPU_DECODE_BEGIN` | 12.0—12.3 | 0.3 | host launch、GPU 排队等尚未细分区间 |
| `GPU_DECODE_BEGIN → SERVER_TOKEN_READY` | 12.3—16.0 | 3.7 | Decode 计算及服务端可交付处理，不全是 GPU 时间 |

这里两 worker 的提交起止被构造为相同时间，以得到易于检查的主干。真实系统若提交错开，须保存每 batch 独立区间，再沿必要依赖求汇合；不能把并行 worker 的 0.2 ms 各加一次。

$$
1.0+3.0+0.2+5.8+0.4+1.6+0.3+3.7=16.0\text{ ms}
$$

这张表已经给出一个确定结论：**不能把 16 ms 全部归给网络，也不能把 5.8 ms 直接叫 wire time。** 至于网络、polling、host progress 在 5.8 ms 内各占多少，还需要更细证据。

### 8.3 两个 batch：只有最后一份必要数据就绪，request 才能继续

| Worker / batch | 唯一 payload | 提交返回 | 最后一次 `PROC` | 第一次 `DONE` |
|---|---:|---:|---:|---:|
| TP0 / B420 | 32 MiB | 4.2 | 6.5 | 7.4 |
| TP1 / B421 | 32 MiB | 4.2 | 7.0 | 10.0 |

在状态单调、查询反映该状态且采样可近似为点的前提下，**backend 进入被观测 DONE 状态**的时刻满足：

$$
C_{420}\in(6.5,7.4],\qquad C_{421}\in(7.0,10.0]
$$

因此 TP1 的完成观察滞后只能约束为 $[0,3.0)$ ms，**不能断言“轮询浪费了整整 3 ms”**。若查询存在缓存、查询调用有显著持续时间或状态发布还依赖 progress，需要按实际契约进一步扩大/修改区间。

这些边界约束的是软件/后端状态，不是线上的最后一个包、更不是任意 GPU 消费者的可见性时刻。要量实际 CQE 到软件观察的滞后，必须取得同域或经过校准的硬件/底层完成证据。即使 NIC bytes 在 7.2 ms 后趋于平坦，也只是一个资源层线索，不证明此请求所有 DMA、通知、可见性条件在 7.2 已完成。

TP0 在 7.4 完成，TP1 到 10.0 才被观察为完成。若误用 `min(worker_done)` 代替全部必要 worker 的汇合，就会发布不完整 KV。应根据请求的必要 worker/fragment 集合检查完整性，而不是固定假设“任何一个 rank 报完就行”。

### 8.4 扩到多 host 和多 rail 时，不把当前简化条件偷偷保留

多 Decode host 时，`max(worker_timestamp)` 需要时钟校准或由中心协调者记录完成观察，不能跨 host 直接取最大裸时刻。多 rail 时，一个 batch 的最终完成可能是所有分片中最晚的一个；底层分块流水允许部分层提前计算时，也应按真实消费 DAG 建模，而不是强制等整请求完成。

## 9. NIC counter：把“有流量”升级为有范围的证据

![[图片/SVG/8_9_9_10_7.svg|900]]

### 9.1 必须先确认这个 counter 是否包含 RDMA

以下名称来自 Linux mlx5 的官方定义；其他厂商/版本必须核对本机支持，缺失不能填零。[^mlx5]

| mlx5 示例 | 定义与单位要点 | 用于本案例的限制 |
|---|---|---|
| `rx_vport_unicast_bytes` / `tx_vport_unicast_bytes` | 普通 vport unicast 统计，**排除 RDMA** | 不能凭它判断 RoCE KV 是否传输 |
| `rx_vport_rdma_unicast_bytes` / `tx_vport_rdma_unicast_bytes` | RDMA unicast bytes | 仍是对应 vport 聚合，不含 request ID |
| `rx_bytes_phy` | 物理端口接收字节，包含 Ethernet header 和 FCS | 不等于唯一 KV payload，混入端口其他流量 |
| `rx_prio[p]_pause` | 接收 PFC pause 帧计数 | 非零不等于本请求被阻塞 |
| `rx_prio[p]_pause_duration` | μs；收到 pause 导致本端该优先级不能发送的时间 | **是 RX 收到暂停，但影响本端 TX** |
| `tx_prio[p]_pause_duration` | 发出的 pause 时长统计 | 不能按同一方向解释成本端发送停顿 |
| `rx_prio[p]_marked` | 设备针对 host congestion 标记的 ECN 包 | 不能当成“交换机出口标记数” |
| `outbound_pci_stalled_rd/wr` | 最近一秒的百分比类指标 | 是 gauge，不是累计 counter；不能做差分速率 |

这也是为什么“`ethtool -S` 有数字”不够：同一个输出中可能混有不同层级、方向、单位和统计类型。必须把定义随原始数据保存。监控含 PF/VF 或其他租户时，也要核对 vport 与物理端口范围。

### 9.2 一个可以手算的窗口，不是一份逐请求账单

构造一个已校准的 D0 端口采样窗口，长度为 4 ms。假设 `rx_vport_rdma_unicast_bytes` 增量是 70,000,000 B，则该窗口观测速率为：

$$
R=\frac{70{,}000{,}000}{0.004}=17.5\times10^9\text{ B/s}=140\text{ Gbit/s}
$$

这个数属于**该 vport、该方向、该 4 ms 窗口**。即使本例逻辑 payload 为 64 MiB，也不能未经流量隔离、counter 定义及请求映射，就把全部 70,000,000 B 记给 R-017。协议口径、其他 RDMA 操作、重试等差异需要独立解释，不能预设增量必定等于 payload。

若用本请求的逻辑唯一 payload 除以 `SUBMIT_BEGIN → 最后 DONE 观察` 的 6 ms：

$$
\frac{64\times2^{20}}{0.006}=11.18481\text{ GB/s}
$$

这是**包含提交与完成观察的逻辑有效吞吐**，不是 RNIC 线速。17.5 和 11.18481 两个值不同不构成矛盾，因为分子范围和时间窗口不同。

### 9.3 采样数据必须经过六项核对

先核对同一设备和方向，再核对累计 counter / gauge、单位、采样时间、计数重置/溢出和背景流量。连接重建、驱动重载、设备 reset 后出现负增量，应标记为不连续区间，不能简单 `max(delta,0)` 后继续当正常样本。

串行读取多个 sysfs/ethtool 字段并不产生真正原子快照。记录采集开始与结束，采集跨度就是误差的一部分。每秒一个样本不能解释 3 ms 的空窗，几毫秒的轮询也未必能抓到微突发；图中理想化的细时间轴不是保证 shell 采集具备相同分辨率。

PFC/ECN 还必须按实际流量的 priority、DSCP/PCP 映射、物理路径与方向解释。pause 可能从下游传播；收到 pause 的端口不必是拥塞源。平均不满、drop 为零都不排除更短时间尺度的竞争或有反馈控制的拥塞。[^mlx5][^roce]

## 10. 完成、可消费与取消：正确性也是性能归因的一部分

![[图片/SVG/8_9_9_10_6.svg|900]]

### 10.1 一条 transfer DONE，还要经过哪些门？

第一道是该 worker 的所有必要 handle；第二道是全部必要 worker/fragment；第三道是 GPU 消费契约；第四道是 scheduler 实际发车。固定版本在 host-buffer 分支中，会在 `get_finished()` 内对接收数据执行 `sync_recved_kv_to_device()`，因此 host staging 模式不能套用“RDMA DONE 即显存可读”的假设。[^vllm-nixl]

GPU-direct 模式也不是“随便在某条 CUDA stream 记个 event 就等到了外部 RNIC 写入”。外部 DMA、注册一致性、完成观察与 GPU 工作提交之间必须符合 backend 和 CUDA 的内存排序契约。一个与这些写入毫无依赖关系的 CUDA event，不能凭名字成为它们的 fence。[^gdr]

`KV_USABLE` 是应用在满足这些条件后给出的**语义承诺**，不是另一个硬件计数器。日志写到这里之前，要先验证此 attempt 尚有效、布局与 generation 匹配，并且所有必要范围完成。

### 10.2 取消与重试不能通过“删掉记录”解决

建议状态关系为：`RESERVED → QUEUED → IN_FLIGHT → WORKER_DONE → KV_USABLE → DISPATCHED`；失败/取消可以从中间状态进入 `CANCEL_PENDING/FAILED`，但不意味着 DMA 已经停止或内存可以立即回收。这是工程状态模型，不是 NIXL 原生 enum 的复制。

请求取消后，旧 attempt 的完成不能发布到新 attempt。buffer/descriptor/rkey 的回收要等 backend 规定的终止、drain 或最后使用者结束；generation 检查只解决身份匹配，不会神奇地停止已提交 DMA。重试既保留用户最终延迟，也保留每次尝试与重试流量，不能只报告最后一次较快尝试的延迟。

发现 checksum/内容验证失败，即使时延更好也不通过。测试还应覆盖“完成通知迟到”“worker 失联”“部分 batch 成功”“调度取消后仍收到 DONE”，并确认不会把一半 KV 当作完整输入。数据完整性的进一步设计见 [[9.11 端到端数据完整性：ECC、CRC、FCS、RDMA ICRC、NVMe PI 与 Silent Data Corruption]]。

## 11. 为什么这个案例里“网络更快了，用户仍然没快”？

### 11.1 两个同样合法的解释，需要不同实验证据

**解释 A：完成收割频率限制。** 假设 backend 更早到达完成，但 worker 仍到下一次扫描才观察到结果；`first DONE` 与 `KV_USABLE` 不变，用户窗口自然不变。需要底层完成时间和上层扫描时间联合证明，不能仅凭 `PROC → DONE` 的长间隔断言。

**解释 B：调度门槛限制。** 即使 `KV_USABLE` 从 10.4 提前到 8.0，scheduler 若仍到 12.0 才 dispatch，本例最终仍到 16.0 才产生本次服务端 Decode token。此时网络优化是真实的，上层调度却仍处在关键路径上。

核心关系与 8.21 一致：

$$
T_{decode\_start}=\max(T_{KV\_usable},T_{other\_deps},T_{scheduler\_gate})
$$

$T_{other\_deps}$ 包括必要计算和资源条件；实际多层流水应使用更细的 DAG。减少依赖的一个分支，不一定改变这个最大值。

### 11.2 三组构造对照：不是现场优化成绩

| 组别 | 最后 worker 的 DONE 观察 | KV 可消费 | Dispatch | GPU 开始 | 本次服务端 token ready |
|---|---:|---:|---:|---:|---:|
| A 基线 | 10.0 | 10.4 | 12.0 | 12.3 | 16.0 |
| B 传输能力提高，但上层门不变 | 10.0 | 10.4 | 12.0 | 12.3 | 16.0 |
| C 假设完成收割和调度都提前 | 7.6 | 8.0 | 8.2 | 8.5 | 12.2 |

B 中网络更快是额外的对照前提，必须由独立传输与底层证据确认；表本身无法证明它。C 同时改变了两个上层因素，**是解释关键路径的反事实，不是可以隔离归因的单变量实验**。实际应先只改完成收割，再只改调度，分别回滚，最后才评估组合。

不能凭空给 vLLM 写一个不存在的“poll_interval”配置。相关干预应在固定源码和线程所有权允许的开发实验中实现，遵守 backend progress/线程安全约束；增加查询频率还可能抢占 CPU、放大锁竞争和降低吞吐。

### 11.3 一个可证伪的实验矩阵

| 假设 | 支持它的联合证据 | 可逆干预 | 推翻或削弱它的结果 |
|---|---|---|---|
| 应用软件排队主导 | queue dwell 上升，提交后区间稳定 | 同负载下调整提交批次/所有权 | dwell 不变或整体仍由其他段主导 |
| 完成收割迟缓 | 底层完成早、上层观察晚，扫描间隔对应 | 合法地缩短收割间隔，其他条件不变 | DONE 观察提前但业务窗口不动 |
| GPU/调度门主导 | KV 已可用，dispatch/消费仍晚 | 固定负载下改变调度时机 | dispatch 提前而 GPU 仍被其他依赖堵塞 |
| 共享 fabric 拥塞 | 同路径队列/PFC/ECN与 batch 异常对应 | 隔离竞争流，保持测试到达分布 | 网络证据不变或后端/host 同时变化 |
| Host staging 限制 | H2D、buffer 复用等待在关键路径 | 同数据/正确性下比较支持的路径 | copy 变短却没有缩短消费者等待 |
| PCIe/NUMA 共享资源限制 | 相同位置组合可重复出现吞吐拐点 | 固定工作量与分配位置的受控拓扑对照 | 仅换整机，无法隔离单个因素 |

容量不够的负载下，加速一个组件会提高上游提交速率、改变下游排队。既要比较匹配负载点，也要扫描容量曲线，防止把这种二阶变化归成“优化失败”。

## 12. CPU 对账程序：先让 ID、区间和算术过检查

下面 A—C 三块按顺序保存成 `kv_reconcile.py`。它只使用标准库，**数据明确为构造**；实际采集器应导入同一 schema 的真实记录，而不是保留这些常量。程序拒绝重复 batch、缺失必要 worker、混入旧 attempt 和不一致的汇合时刻。

**A．用不可变记录表示 batch。** 每条记录属于指定请求、attempt 与 worker；时间是同一个 Decode 时钟域中的构造毫秒值，payload 是唯一有效字节，不把源 TX 和目的 RX 重复相加。

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Batch:
    request: str
    attempt: int
    worker: int
    batch: str
    submit_return: float
    last_proc: float
    first_done: float
    unique_bytes: int

# Synthetic data, all times are milliseconds in one Decode-host clock domain.
run, req, attempt, domain = 'demo-001', 'R-017', 2, 'decode-0/mono'
batches = [
    Batch(req, attempt, 0, 'B420', 4.2, 6.5, 7.4, 32 * 2**20),
    Batch(req, attempt, 1, 'B421', 4.2, 7.0, 10.0, 32 * 2**20),
]
events = [('admit', 0.0), ('blocks_reserved', 1.0), ('submit_begin', 4.0),
          ('submit_return', 4.2), ('last_worker_done', 10.0),
          ('kv_usable', 10.4), ('dispatch', 12.0),
          ('gpu_decode_begin', 12.3), ('server_token_ready', 16.0)]

```

**B．先校验关联再计算。** 重复 batch、错误 attempt、缺失 worker 或与最慢必要 worker 不符的完成点会停止程序。失败不能被默认值零掩盖。

```python
# Keys are explicit. Production input must additionally validate epochs and domains.
keys = [(run, b.request, b.attempt, b.worker, b.batch) for b in batches]
if len(set(keys)) != len(keys):
    raise ValueError('duplicate batch; do not count the bytes twice')
if any((b.request, b.attempt) != (req, attempt) for b in batches):
    raise ValueError('mixed request or retry attempt')
if {b.worker for b in batches} != {0, 1}:
    raise ValueError('missing required worker')
if any(not b.submit_return <= b.last_proc < b.first_done for b in batches):
    raise ValueError('invalid completion observation bounds')
times = dict(events)
if len(times) != len(events):
    raise ValueError('duplicate event')
if abs(max(b.first_done for b in batches) - times['last_worker_done']) > 1e-9:
    raise ValueError('request completion does not match the slowest worker')

stages = []
for (name_a, ta), (name_b, tb) in zip(events, events[1:]):
```

**C．逐段对账与不确定性。** 按明确边界相减并验证单调性，再输出状态完成区间；逻辑字节除以观察跨度只命名为观察口径 goodput。

```python
    if tb < ta:
        raise ValueError('non-monotonic sequence or unaligned clocks')
    stages.append(tb - ta)
    print(f'{name_a} -> {name_b}: {tb-ta:.2f} ms')
assert abs(sum(stages) - 16.0) < 1e-9
for b in batches:
    print(f'{b.batch}: completion in ({b.last_proc:.1f}, {b.first_done:.1f}] ms; '
          f'observation lag in [0, {b.first_done-b.last_proc:.1f}) ms')
logical_bytes = sum(b.unique_bytes for b in batches)
observed_seconds = (times['last_worker_done'] - times['submit_begin']) / 1000
print(f'logical goodput / observed span: {logical_bytes/observed_seconds/1e9:.5f} GB/s')
print(f'constructed end-to-end: {sum(stages):.2f} ms; domain={domain}')
```

代码是单进程纯数据校验，没有异步设备调用，因此无需把源码重复画成时序图；它校验的异步边界已经体现在第 8 节 SVG 中。生产输入还要验证 clock domain/epoch、必要分片列表、缺失率与错误状态，不能只校验程序中两个 worker 是否存在。

执行过的 CPU 校验结果为：分段总和 **16.00 ms**，两个完成状态区间分别为 **(6.5,7.4]** 和 **(7.0,10.0] ms**，观察跨度上的逻辑有效吞吐为 **11.18481 GB/s**。这些是构造数据的计算结果，不是网卡成绩。

## 13. 现场采集顺序：先低风险定位，再缩短窗口

### 13.1 保存身份与拓扑，不直接改生产配置

先根据部署配置确认 `IFACE` 和 GPU/RDMA 设备映射。以下都是只读命令；输出可能包含序列号和拓扑信息，对外共享前脱敏。

```bash
: "${IFACE:?设置已核对的实验 RNIC netdev}"
nvidia-smi
```

### 13.2 采 counter 时保留读数包络

`ethtool -S` 一次读取不是高分辨率请求追踪。下面是一次只读采样包装，保存读取前后单调时间；它不修改接口，也不假定各字段同时更新。程序失败时保留 stderr，不把缺失 counter 当零。运行前设置 `IFACE`。[^mlx5]

```python
import json
import os
import subprocess
import time

iface = os.environ['IFACE']
begin = time.monotonic_ns()
result = subprocess.run(['ethtool', '-S', iface], text=True,
                        capture_output=True, check=False)
end = time.monotonic_ns()
print(json.dumps({'clock': 'host-monotonic', 'begin_ns': begin, 'end_ns': end,
                  'iface': iface, 'rc': result.returncode,
                  'stdout': result.stdout, 'stderr': result.stderr}))
if result.returncode:
    raise SystemExit(result.returncode)
```

图底部是采样线程与 ethtool 子进程的调用顺序，琥珀色框标出阻塞。等待区间就是 `subprocess.run()` 的 begin—end，**不是 request 的传输区间**。先用低频窗口判断是否值得深入，再用设备支持的队列峰值、事件遥测或低开销 trace 缩小范围。不要用持续高速 fork `ethtool` 代替毫秒级遥测。

### 13.4 最小可交付证据目录

现场运行可建立 `manifest、request_events、batch_edges、worker_events、gpu_trace、nic_samples、switch_samples、errors、summary` 等文件集合。manifest 明确原始文件名、时钟域、版本、采样率、设备范围和实验变量。这里列的是**现场应产生的证据**，本下载包没有伪造这些硬件采集文件。

对齐顺序是：先请求/attempt，后必要 batch/worker，再本地时间段，最后端口/队列窗口与 GPU 依赖。时间邻近只能筛选候选，不能替代身份与因果匹配。

## 14. 最终报告：把结论写成可以被审查的句子

| 报告部分 | 合格写法 |
|---|---|
| 现象 | 指定 workload、到达率、请求数与完成口径的分布退化 |
| 定位 | 同一 cohort 中哪个可观测区间增长，哪些尚未分解 |
| 关联 | request→attempt→batch→worker→GPU，及端口证据的强弱 |
| 机制 | 为什么该资源/等待可能导致这个区间变长 |
| 验证 | 单变量、变更生效证明、回滚、重复窗口与噪声 |
| 质量门 | 吞吐、错误/超时、取消清理、KV 内容与布局正确性 |
| 不确定性 | 时钟误差、缺失事件、共享端口、未观测 backend 内部 |

例如：**“R-017 的 16 ms 构造窗口中，3 ms 明确属于软件队列，1.6 ms 属于 KV 可用后的调度等待；5.8 ms 仍混合传输与完成观察。现有数据不支持把全部 5.8 ms 归因于 fabric，也不支持声称轮询确定浪费了 3 ms。”** 这是一条有边界的结论。

现场则需要原始证据与重复实验，才能把“支持某假设”升级为“在指定条件下干预该因素使该段和整体窗口同步改善”。结果进入 [[9.7 SLO 与性能回归]]；可复查操作进入 [[9.8 Runbook 与可运维产物]]；取消、超时、断链等注入只在隔离环境按 [[9.6 故障注入矩阵]] 执行。

> [!question] 面试式自测
> **为什么 NIC bytes 不能分给一个 request？** 因为 counter 通常属于共享 vport/端口窗口，缺少请求归属，而且字节与时间口径未必等于逻辑 payload。
>
> **为什么第一个 worker DONE 不够？** 因为消费者需要的是所有必要分片的完整、当前 generation 的 KV，而不是任意一个局部完成。
>
> **为什么网络加速后总延迟可能不变？** 因为完成观察、跨 worker 汇合、可见性或调度门可能仍决定消费者开始时间。
>
> **为什么不能用两个 P99 相减估计网络？** 因为分位数不是同一请求可加区间；再加上时钟与完成边界不同，差值没有那个语义。
