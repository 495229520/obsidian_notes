# fio Benchmark Matrix

> `fio` 的价值不是跑出一个最大 IOPS 数字，而是用受控变量回答具体问题：请求经过哪条 IO 路径、并发窗口多大、设备在稳态下能提供什么吞吐和延迟。测试条件没有固定，结果就不能复现，也不能用于回归。

前置：[[1.3 Buffered IO 与 O_DIRECT]]（两条本地 IO 路径）、[[1.7 块层与 blk-mq]]（队列与背压）、[[2.3 iodepth 与提交完成路径]]（异步并发窗口）、[[3.6 空盘与稳态性能]]（SSD 预处理）。

---

## 1. 先定义测量对象

一份 fio 结果至少要同时回答四个问题【前提】：

1. **目标是谁**：普通文件、裸块设备、逻辑卷，还是挂载在客户端的网络文件系统；
2. **路径是什么**：buffered IO 还是 `O_DIRECT`，同步引擎还是异步引擎，是否经过文件系统；
3. **负载是什么**：读写比例、顺序或随机、块大小、工作集、线程数和队列深度；
4. **时间窗口是什么**：预热多久、测量多久、设备是否进入温度与 GC 稳态。

> [!warning] 写测试会改数据
> 对 `/dev/nvme0n1`、逻辑卷或分区运行 `write`、`randwrite`、`trim` 会覆盖数据。先用 `lsblk -f` 和 `findmnt` 确认目标未挂载且不承载系统数据。学习阶段优先对专用测试文件运行。

### 1.1 fio 在系统路径中的位置

![[图片/SVG/8_9_9_1_1.svg|900]]

图中有两个容易混淆的边界：

- `direct=0` 的读可能命中 Page Cache；此时 fio 测到的是内存与拷贝路径，不是设备【事实】；
- `direct=1` 只绕过 Page Cache，不绕过 VFS、文件系统映射、块层、驱动和设备【事实】。具体路径见 [[1.3 Buffered IO 与 O_DIRECT]]。

对网络存储还要再加一层【实现】：fio 进程在客户端执行时，文件 IO 会经过客户端文件系统、RPC 或 NVMe-oF 发起端、网卡、交换网络、服务端和服务端设备。fio 的 `--client/--server` 只是远程控制 fio worker；它不会自动把本地文件 IO 变成网络 IO。

## 2. 六个正交变量

基准矩阵要一次只改变一个变量。下面六项构成最小实验坐标系。

| 变量 | fio 参数 | 机制问题 | 常用取值 |
| --- | --- | --- | --- |
| 访问模式 | `rw` | 顺序性、读写混合、写后 GC | `read`、`write`、`randread`、`randwrite`、`randrw` |
| 请求大小 | `bs` | 单次固定成本与带宽摊销 | `4k`、`16k`、`128k`、`1m` |
| 单 worker 深度 | `iodepth` | 每个 job 最多保持多少请求在途 | `1`、`8`、`32`、`128` |
| 并行 worker | `numjobs` | CPU、队列、文件与锁的并发 | `1`、CPU/NUMA 受控的多 job |
| 缓存路径 | `direct` | Page Cache 是否参与 | `0` 或 `1` |
| 工作集与时间 | `size`、`runtime` | 是否越过缓存并进入稳态 | 大于内存缓存；持续到曲线稳定 |

### 2.1 `iodepth` 不等于设备队列深度

`iodepth` 是**每个 fio job 的目标在途上限**【事实】。近似总并发窗口：

$$
Q_{fio} \approx numjobs \times iodepth
$$

它不保证设备始终看到同样深度。请求可能在 io_uring、文件系统、blk-mq tag 池、驱动队列或网络传输层等待。同步引擎通常一次只能阻塞等待一笔 IO；把 `iodepth` 写成 32 也不会凭空得到 32 个在途请求【实现】。因此要同时查看 fio 输出中的 `iodepth_level`，再用 [[9.2 iostat 指标解读]] 的 `aqu-sz` 交叉验证块层实况。

利特尔法则给出结果自检：

$$
Q \approx IOPS \times latency_{seconds}
$$

例：300 kIOPS、平均完成延迟 100 μs，对应约 30 个在途请求。若 fio 声称 QD=1 却同时给出这组数字，先检查聚合方式、job 数和单位。

### 2.2 `numjobs` 与 CPU、NUMA

多个 job 不只是增加 IO 并发，还会增加以下资源竞争【实现】：

- 多个提交线程争用 CPU 时间；
- worker 可能跨 NUMA 节点访问 buffer 或 PCIe 设备；
- 同一文件上的元数据锁、extent 分配和日志事务可能串行；
- 多个网络连接会改变 TCP 拥塞窗口、RSS 队列与服务端分片方式。

所以多 job 结果必须记录 CPU 绑定和 NUMA 放置。NVMe 与网卡拓扑见 [[3.8 PCIe 拓扑与 NUMA]]。

## 3. 最小 Benchmark Matrix

下面的矩阵先测设备基本形状，再测业务近似。`QD` 指 `numjobs × iodepth` 的目标值；实际深度仍要看观测结果。

| 组 | 模式 | `bs` | QD | 回答的问题 | 主指标 |
| --- | --- | ---: | ---: | --- | --- |
| A1 | 顺序读 | 1 MiB | 1 | 单流延迟与单流带宽 | BW、clat p50/p99 |
| A2 | 顺序读 | 1 MiB | 32 | 设备与 PCIe 带宽上限 | BW、CPU、`%util` |
| A3 | 顺序写 | 1 MiB | 32 | 稳态写带宽与温控 | BW 时间序列、p99 |
| B1 | 随机读 | 4 KiB | 1 | 不排队时的路径底噪 | clat p50/p99 |
| B2 | 随机读 | 4 KiB | 32 | 常用并发点的 IOPS | IOPS、clat p99 |
| B3 | 随机读 | 4 KiB | 128 | 饱和后排队代价 | IOPS 增量、p99 增幅 |
| C1 | 随机写 | 4 KiB | 32 | FTL、GC 与写放大影响 | IOPS、p99、稳态曲线 |
| C2 | 70% 读 / 30% 写 | 4 KiB | 32 | 读写互相干扰 | 读 p99、写 p99 |
| D1 | 业务块大小分布 | 业务 QD | 业务值 | 容量规划与回归 | SLO 对应分位数 |

【取舍】矩阵不是越大越好。先固定 `direct=1`、引擎、文件系统、CPU 绑定和设备状态，只扫描 `rw × bs × QD`。定位到拐点后再展开 job 数、读写比例和网络参数。全排列会把根因淹没在组合数量里。

## 4. 一份可复现的 job 文件

先准备专用目录和测试文件。不要把命令中的路径替换成在线数据盘。

```ini
[global]
filename=/mnt/bench/fio.test
size=32G
ioengine=io_uring
direct=1
time_based=1
runtime=60
ramp_time=15
group_reporting=1
thread=1
randrepeat=1
allrandrepeat=1
invalidate=1

[randread-4k-qd1]
rw=randread
bs=4k
iodepth=1
numjobs=1

[randread-4k-qd32]
stonewall
rw=randread
bs=4k
iodepth=32
numjobs=1

[mixed-4k-qd32]
stonewall
rw=randrw
rwmixread=70
bs=4k
iodepth=32
numjobs=1
```

运行并保留机器可读结果：

```bash
fio fio-matrix.fio --output-format=json+ --output=fio-matrix.json
```

参数语义【事实/实现】：

- `ramp_time=15`：前 15 秒执行负载但不计入最终统计，用于填充队列和预热路径；
- `stonewall`：上一组完成后再启动下一组，避免三组互相干扰；
- `group_reporting=1`：聚合 job 输出。排查长尾时仍要保留每 job 数据，避免聚合掩盖单盘或单核异常；
- `invalidate=1`：尝试在开始前使文件缓存失效。它不能替代 `direct=1`，也不能清除设备内部 DRAM/SLC 缓存。

### 4.1 SSD 写测试的稳态前提

刚清空的 SSD 有大量空闲块和可用 SLC 缓存，写成绩高于长期运行状态【事实】。验收写性能时先按厂商或实验规范预处理，常见做法是对整个测试区域顺序写满，再用目标随机写负载运行到 IOPS 与 p99 不再持续漂移。完整机制见 [[3.6 空盘与稳态性能]]。

【取舍】预处理会消耗写入寿命，也会彻底覆盖测试区域。只对专用设备执行，并把预处理方法、写入量、盘温和 SMART 基线写进报告。

## 5. 读懂 fio 输出

### 5.1 三段延迟

fio 常见延迟字段：

| 字段 | 含义 | 可能包含的机制 |
| --- | --- | --- |
| `slat` | fio 开始提交到 IO 引擎接受请求 | 用户态准备、系统调用、队列满时的提交阻塞 |
| `clat` | IO 引擎接受请求到完成被 fio 收割 | 内核排队、驱动、设备或网络、完成通知 |
| `lat` | 从 fio 发起到 fio 观察到完成 | 近似 `slat + clat` |

`clat` 不是 NAND 介质延迟【事实】。对本地块设备，它包含块层排队、驱动与完成路径；对 NVMe/TCP、iSCSI 或网络文件系统，它还包含客户端协议栈、网络、服务端排队和服务端介质。要把其中一段拆出来，需要 [[9.3 blktrace 与块层生命周期]]、网络遥测或服务端追踪。

### 5.2 平均值不能代表尾部

至少报告：

- IOPS 或带宽，以及测量时长；
- `clat` 的 p50、p95、p99、p99.9；
- 最大值只作异常线索，不单独作为 SLO；
- fio 的 CPU 占用、上下文切换和实际 iodepth 分布；
- 同期 `iostat -x`、温度、频率、SMART 与网络丢包/重传。

> [!warning] 百分位聚合陷阱
> 多个 job 各自的 p99 不能通过算术平均得到全局 p99。需要合并直方图或原始样本。`group_reporting` 的聚合范围也要与业务请求范围一致。

### 5.3 带宽、IOPS 与请求大小

当请求都为固定大小且没有重试时：

$$
BW \approx IOPS \times block\ size
$$

4 KiB × 250 kIOPS 约等于 0.95 GiB/s。若换成 1 MiB 后 IOPS 降到 7k，带宽仍可接近 6.8 GiB/s。这不是退化，而是每个请求搬运的数据变多。

## 6. 本地盘与网络存储的分层差异

| 目标 | fio 进程位置 | `iostat` 能看到什么 | 还要观察什么 |
| --- | --- | --- | --- |
| 本地文件 / 块设备 | 本机 | 本机块层完成请求 | Page Cache、CPU、IRQ、SMART |
| NVMe/TCP、iSCSI 块设备 | 客户端 | 客户端虚拟块设备的端到端块层等待 | TCP 重传、NIC 队列、target 端块设备 |
| NVMe/RDMA | 客户端 | 发起端块设备等待 | RDMA CQ、拥塞信号、target 端队列 |
| NFS / SMB 文件 | 客户端 | 可能没有对应本地块设备统计 | RPC 延迟、重传、服务端 iostat |
| fio `--client` 控制远端 worker | 控制端与 worker 分离 | 取决于 worker 实际打开的目标 | 控制流量与数据流量要分开理解 |

网络路径还有一个并发下限【事实】：若单请求大小为 $S$、端到端延迟为 $W$，单个在途请求只能贡献约 $S/W$ 的吞吐。要填满带宽为 $B$ 的链路，需要的窗口近似：

$$
Q \ge \frac{B \times W}{S}
$$

这与 TCP 的 bandwidth-delay product 是同一类容量约束。加深队列可以填满链路，但超过最慢层的处理能力后，只会增加排队和 p99【取舍】。NVMe-oF 的传输差异见 [[5.2 Transport TCP vs RDMA]]。

## 7. Modern C++：用 RAII 保存一次实验上下文

下面的辅助类不负责发 IO，只负责保证结果文件完整关闭，并在异常路径上保留本次实验的参数。实际生产系统更适合直接解析 fio JSON，而不是从终端文本提取数字。

```cpp
#include <chrono>
#include <filesystem>
#include <fstream>
#include <stdexcept>
#include <string>
#include <string_view>

class RunManifest {
public:
    explicit RunManifest(const std::filesystem::path& path)
        : out_{path, std::ios::out | std::ios::trunc} {
        if (!out_) {
            throw std::runtime_error{"cannot create benchmark manifest"};
        }
        out_ << "status=running\n";
    }

    RunManifest(const RunManifest&) = delete;
    RunManifest& operator=(const RunManifest&) = delete;

    void add(std::string_view key, std::string_view value) {
        out_ << key << '=' << value << '\n';
        if (!out_) {
            throw std::runtime_error{"cannot write benchmark manifest"};
        }
    }

    void complete() {
        out_ << "status=complete\n";
        completed_ = true;
    }

    ~RunManifest() {
        if (!completed_) {
            out_ << "status=aborted\n";
        }
    }

private:
    std::ofstream out_;
    bool completed_{false};
};
```

RAII 在这里提供的不是性能，而是实验可审计性：异常、提前返回或后续命令失败时，析构函数仍会关闭文件并留下 `aborted` 状态【实现】。

## 9. 陷阱与误区

> [!warning] 常见错误
> 1. 用 1 GiB 文件做 buffered read，然后把内存带宽当成 SSD 带宽。
> 2. 只写 `iodepth=128`，不确认引擎是否异步，也不看实际深度分布。
> 3. 把 `numjobs × iodepth` 当成设备内部真实队列深度。
> 4. 拿空盘短测写成绩做容量规划，忽略 SLC 缓存、GC、温控和稳态。
> 5. 同时改变块大小、job 数、深度和读写比例，结果变化后无法归因。
> 6. 只报平均延迟，省略 p99、测量时长和样本数。
> 7. 在客户端测网络文件系统，却只看客户端本地盘的 iostat。
> 8. 用 fio `--client` 代替真实的网络存储数据路径测试。

## 10. 关键结论

| 结论 | 性质 |
| --- | --- |
| fio 结果只对确定的目标、路径、负载和时间窗口成立 | 前提 |
| `direct=1` 绕过 Page Cache，但仍经过文件系统映射、块层、驱动和设备 | 事实 |
| `iodepth` 是每 job 目标在途上限，不保证等于设备实际队列深度 | 事实 |
| `numjobs × iodepth` 增加并发，也增加 CPU、NUMA、锁和网络连接变量 | 实现 / 取舍 |
| QD、IOPS、延迟应满足利特尔法则的量级关系 | 事实 |
| SSD 写验收必须说明预处理、稳态、盘温和测试区域 | 前提 |
| 网络存储的 fio clat 包含客户端、网络、服务端与介质，需跨端观测拆解 | 事实 |
| 基准矩阵先单变量扫描，再围绕拐点展开，才能保留因果关系 | 实践结论 |
