# cgroup IO 隔离与多租户 QoS

> 限速解决"谁也别把设备打爆"，隔离解决"打爆的人别连累无辜的人"。cgroup v2 的 io 控制器是内核块层提供的第二道隔离，位置在应用层限速之下、设备之上。

---

## 1. 问题：吵闹邻居

同一块 NVMe 上跑两类负载是常态：延迟敏感的在线读（点查、KV cache 读回）和吞吐型后台写（checkpoint burst、compaction、数据摄取）。后台顺序写一旦放开，设备队列被大块写占满，在线读的 p99 立即恶化——这就是 [[9.5 p99 毛刺定位]] 里最常见的一类毛刺来源，checkpoint 场景的定量分析见 [[8.6 Checkpoint 同步异步分片]]。

隔离可以做在三个层次，作用点和适用范围不同：

| 层次 | 手段 | 边界 |
| --- | --- | --- |
| 应用内 | 自建 Rate Limiter、后台任务限速（[[6.16 Rate Limiter 与后台任务隔离]]） | 只管得住自己进程；跨进程/跨容器无效 |
| 内核块层 | cgroup v2 io 控制器（本篇） | 管同一内核下所有进程；作用于块设备粒度 |
| 设备端 | NVMe 规范中的 WRR 仲裁、部分企业盘的 namespace QoS | 【事实】规范存在但生态支持零散，生产少用 |

多租户（容器/云环境）下应用层限速指望不上，内核层是主要抓手。

## 2. cgroup v2 io 控制器三件套

对每个 cgroup、每个块设备，可配三类策略，思路从"硬"到"软"：

### io.max：绝对上限

`io.max: "253:0 rbps=... wbps=... riops=... wiops=..."`——按设备号硬限带宽/IOPS，超出的请求在块层排队等待。

【取舍】可预期性最好（租户买多少配多少），但**不做工作量守恒**：设备空闲时被限的组也用不满，带宽白白浪费。适合按 SKU 卖配额的公有云盘场景。

### io.weight（iocost）：按权重比例分

各 cgroup 按权重分享设备能力，空闲时任何组可以用满，繁忙时按比例收敛——工作量守恒。难点是"设备能力"没有单一单位（4K 随机和 1M 顺序消耗完全不同），所以 iocost 用一个**成本模型**把每个 IO 折算成统一开销，模型参数可以用 fio 测出的设备 QoS 特性校准。

【取舍】共享集群内部混部的默认选择；代价是成本模型偏差会导致分配不准，上线前要用 [[9.1 fio Benchmark Matrix]] 的对照方法验证。

### io.latency：延迟保护

给延迟敏感组设一个目标（如 p99 若干 ms）；内核监测该组的完成延迟，超标时对同设备上其他组节流。语义是"保一个，压其余"，天然匹配"在线读保延迟、后台写随便"的场景。

【事实】它是保护性机制而不是分配机制：只有受保护组受损时才介入，平时不干预。

## 3. buffered write 的记账难题

块层隔离面临一个经典问题：buffered write 的 write() 只是写进 Page Cache，真正下盘的是稍后的内核回写线程——**IO 到达块层时，发起者早已不是写入进程**。

- 【事实】cgroup v1 时代 writeback 无法归属到发起 cgroup，io 限速对 buffered write 基本失效，只有 O_DIRECT 可控——这是"v1 的 blkio 不管用"这句经验的真实来源。
- cgroup v2 打通了 memcg 与 blkcg：每个脏页记住所属 cgroup，回写 IO 按归属记账、按策略节流。这是 v2 相对 v1 在存储隔离上的本质改进。
- 推论：做隔离实验时，O_DIRECT 负载的行为最干净（[[1.3 Buffered IO 与 O_DIRECT]]）；buffered 负载则要意识到节流发生在回写路径上，观察到的是"脏页积压 → 写进程被 balance_dirty_pages 减速"的间接链条（[[1.4 fsync fdatasync 与持久化语义]] 里回写机制的延伸）。

## 4. 作用边界

- 作用点在块层（进调度器之前），对上层入口（read/write、io_uring、mmap 缺页）一视同仁；io_uring 不能绕过它。
- 管的是"本机内核看得见的块设备"：本地 NVMe、NVMe-oF initiator 挂出的 nvme-of 块设备都算；但对 target 端整机的公平性无能为力——跨机 QoS 要靠分布式层（[[7.18 Backpressure 与过载保护]]）。
- SPDK 用户态驱动完全绕过内核块层，cgroup io 对它无效（[[5.6 SPDK 用户态驱动]]）；SPDK 场景的隔离靠自身的 QoS 配置。

## 5. 最小验证实验

两个 cgroup 对照即可复现"吵闹邻居 → 隔离生效"的完整故事：

```text
组 A：fio 4K randread，iodepth 低，记录 p99（在线读画像）
组 B：fio 1M 顺序写，iodepth 高（checkpoint burst 画像）
对照 1：无隔离同时跑 → A 的 p99 相对独跑恶化（量化毛刺）
对照 2：给 A 配 io.latency 目标后重跑 → A 的 p99 恢复，B 吞吐下降（隔离的代价）
```

观测配 [[9.4 eBPF biolatency biosnoop]] 按 cgroup 分桶看延迟分布，设备侧配 [[9.2 iostat 指标解读]] 确认队列占用变化。这组实验可以直接作为 linux-io-lab 的延伸小节或面试口述素材。
