# 9.11 端到端数据完整性：ECC、CRC、FCS、RDMA ICRC、NVMe PI 与 Silent Data Corruption

> [!abstract] 先回答最重要的问题
> **每一层都有校验，不等于应用的原始状态被从头保护到了恢复时刻。** 校验只能约束“在某个生成点看到的字节”与“在某个验证点看到的字节”之间的关系。错误可能出现在生成点之前、验证点之后、两种保护机制交接的空隙，也可能根本不是位翻转，而是拿错分片、读到旧版本、漏掉对象、快照混入不同 step。
>
> Checkpoint 自己保存摘要，是为了让恢复端能对照**写出时留下的独立依据**验证内容；把 job、epoch、tensor、分片位置和长度纳入完整性协议，是为了验证“这是不是我要恢复的那份状态”。摘要本身仍然不能证明训练计算正确，也不能单独保证持久化、真实性或新鲜性。

[[8.17 万卡集群分布式 Checkpoint 极致加速实践（MegaScale & DeepSeek 方案）]] 已经建立“不可变快照 → 多级下刷 → manifest 提交”的流水线。本篇不重复加速方案，而是逐段审计：**谁生成校验、谁验证、校验保护什么、错误落在边界之外怎么办。** 算法、碰撞预算和 CPU 成本放在 [[9.12 Checksum 与 Hash 工程：CRC32C、xxHash、SHA-256、BLAKE3 与硬件加速]]。

## 1. 先区分四个问题：字节、身份、持久性、来源

下面是本篇使用的工程分类，而不是把四种不同语义统称为“可靠”。

| 问题 | 验证内容 | 典型机制 | 单独不能证明什么 |
|---|---|---|---|
| 字节完整性 | 读到的字节是否与保存依据一致 | CRC、Hash、ECC 检测路径 | 是否属于正确的 epoch |
| 对象身份与快照一致性 | job、版本、分片集合、位置、布局是否匹配 | manifest、版本绑定、完整集合检查、快照隔离 | 字节是否真的落到了持久介质 |
| 持久性与原子可见性 | 成功返回之后，指定故障下能否恢复完整状态 | 持久化屏障、后端提交、原子发布、恢复协议 | 内容在写入前是否已经错了 |
| 真实性与新鲜性 | 谁授权了内容，以及是不是允许恢复的版本 | 受信 manifest、MAC/签名、外部版本策略 | 计算结果是否符合数学语义 |

**一个非常重要的反例：** 昨天的完整 Checkpoint 及其 SHA-256 都正确，今天误把它标为最新。字节校验可以全部通过；失败的是版本选择。再强的 Hash 也不会自动知道今天应该恢复哪个 epoch。

《Linux 多线程服务端编程》附录 A.1.13 讨论过相似问题：TCP、IP、以太网已经有检查，为何应用消息仍需要校验。这里沿用其“保护边界”思路，但不把有限位宽的 CRC 写成绝对不出错的保证，也不把所有网络错误都简化成同一种概率。[^chen]

## 2. Bit Flip、ECC Error 与 Silent Data Corruption 不是同义词

**Bit Flip** 描述某个位发生了 `0 ↔ 1` 变化。原因可能是瞬态扰动，也可能是持续性硬件问题。**Silent Data Corruption，SDC** 描述的是结果：错误内容被当作正常内容交给了某个使用者，而该层没有把这次错误报告出来。

因此，位翻转不一定导致 SDC；SDC 也不一定源于位翻转。为排障建立如下分类：

| 事件 | 是否发生错误 | 使用者看到什么 | 应如何命名 |
|---|---:|---|---|
| ECC 纠正了能力范围内的错误 | 是 | 正确数据；可能有 corrected counter | 已纠正错误，不是这次读的 SDC |
| ECC 检测到但无法纠正，访问报错 | 是 | 错误状态、poison 或失败 | 已检测的不可纠正错误 |
| 内容改变，所有相关检查均未发现 | 是 | “成功”加错误数据 | SDC |
| 软件把 rank 7 的合法数据写入 rank 8 对象 | 是 | 合法编码、合法 CRC、错误身份 | 应用语义错误，可表现为 SDC |
| 存储返回 I/O error | 可能 | 显式失败 | 不能仅凭失败就称 SDC |

Linux RAS/EDAC 区分 corrected、uncorrected 等事件；事件能否记录、能否继续执行以及能否定位到 DIMM，取决于硬件和驱动暴露的能力。**“没有查到 ECC 报错”只能说没有这份证据，不能证明整个数据路径没有错误。**[^ras]

## 3. 把保护范围画出来：不是一层套一层的保险箱

![[图片/SVG/8_9_9_11_1.svg|900]]

图中横向表示数据所经历的阶段，条带表示校验的生成与验证区间，不表示各阶段真实耗时。一次 Checkpoint 的存留时间可能是几周，而一次 Ethernet 帧的保护区间只覆盖相应帧的传输。

审计任意一层时，只问下面五件事：

1. **生成点**：校验对应的是原始 GPU 状态、Host staging、RNIC 取出的数据，还是块层提交时的数据？
2. **验证点**：检查发生在接收端、块设备、对象服务，还是恢复端真正使用前？
3. **覆盖字段**：只有 payload，还是也含对象身份、长度、位置和版本？
4. **生命周期**：验证之后谁还能写这块内存？摘要是不是也会被一同覆盖？
5. **失败策略**：丢包、重试、返回错误、隔离对象，还是误把错误当作正常回执？

这些问题比“这层使用多少位 CRC”更早决定方案是否成立。Linux 的数据完整性文档明确指出，许多设备内部检查工作在各自的隔离域中；只有沿路径保留并验证保护信息，才能把保护范围连起来。[^linux-integrity]

### 3.1 校验是边界关系，不是“正确性标签”

设应用最初希望保存的字节为 $D_0$，校验生成时实际读到 $D_g$，恢复时读到 $D_r$。摘要比较检查的是：

$$
H(D_r) \stackrel{?}{=} H(D_g)
$$

它并没有直接检查 $D_g = D_0$。如果错误先把 $D_0$ 改成了 $D_1$，随后所有设备都忠实保护 $D_1$，那么所有局部校验都可能正常。

这不是 Hash 算法失效，而是**校验依据建立得太晚**。此外，即便 $H(D_r)=H(D_g)$，有限摘要也不能在数学上保证 $D_r=D_g$；碰撞问题另见 9.12。本篇首先解决“漏保护”，再考虑“保护范围内的漏检”。

## 4. ECC：纠正编码内的错误，不理解 Checkpoint 的语义

ECC 是 Error-Correcting Code，一类纠错码的统称，不是某个固定算法，也不是“另一个名字的 CRC”。以常用于教学的 **SECDED** 为例：在一个受保护码字内保证纠正单比特错误、检测双比特错误。这里的“单/双”指**一个码字内**，不是整条 DIMM、整个 GPU 或整个文件内。超过编码能力的错误可能被检测、可能不可纠正，也可能发生误判；不能把 SECDED 推广为任意多比特错误都能发现。[^ras]

理解 ECC 时需要同时看三个层次：

- **编码粒度**：保护哪一组数据位和冗余位；设备内部编码、内存控制器编码和跨芯片保护不是一个粒度。
- **覆盖部件**：DRAM/HBM、缓存、内部 SRAM、链路和计算单元的保护，必须分别查对应平台文档。
- **错误处理**：纠正后继续、上报不可纠正、poison、进程终止等，不是统一的“都能修复”。

一个软件线程把错误数值正常写入 ECC 内存，内存控制器可以为错误数值生成完全合法的码字。之后 ECC 读出“正确”，意思是读写编码自洽，不是那个数值符合训练算法。

同理，**设备内部/on-die ECC 的存在，不足以推出从应用寄存器到远端存储的整条路径都有相同保护**。讨论具体 CPU/GPU/DIMM 时，应画出厂商实际公布的覆盖边界，不用一个 `ECC enabled` 代替整张图。

对 GPU 路径，[[8.12 GPUDirect RDMA]] 中的“绕过 CPU staging”改变了搬运路径，但并没有让应用摘要和一致性检查失去意义：减少拷贝可能减少某些机会点，**零拷贝并不等于零损坏、零竞态或零验证成本**。

## 5. Ethernet FCS：保护帧，不保护整个存储生命周期

Ethernet 的 FCS 是帧尾的 32 位 CRC。它针对相应 Ethernet 帧的字段进行校验，所用多项式属于通常称作 IEEE CRC-32 的体系，**不是 CRC32C/Castagnoli**。多项式与错误模式、消息长度共同决定检测能力，不能把所有“32 位 CRC”视为同一个算法。[^crc]

这里最容易混淆的是三个范围：

| 范围 | FCS 能回答什么 | FCS 不能回答什么 |
|---|---|---|
| 某个接收 MAC 看到的帧 | 帧与其 FCS 是否一致 | 发送应用在更早时刻想发送什么 |
| 网络中的不同帧/链路段 | 各段按各自机制检测帧错误 | 把一次通过等同于整个网络及端系统绝对无错 |
| 数据已经进入主机或长期存储 | 本次帧接收时的检查结果 | 之后内存是否被覆盖、几周后文件是否仍完整 |

经路由重新封装后，新的 Ethernet 帧拥有其对应的 FCS。桥接、store-and-forward、cut-through 等设备如何转发、重新生成或处理坏 FCS，存在实现差异；**不要为了画简图，写成“每个交换机必定把所有包的 FCS 全部重算”**。本篇论点并不依赖这一假设：帧保护本来就不是 Checkpoint 对象的持续身份凭据。

坏 FCS 通常导致丢弃或错误计数；普通 Ethernet FCS 本身不是应用级重试和持久化协议。即使可靠传输随后重发成功，也只能说明相应传输完成，不能据此发布 Checkpoint manifest。

## 6. RoCE ICRC：跨越网络，但仍然有明确的端点

### 6.1 为什么还需要 Invariant CRC

RoCEv2 的 ICRC 不是简单对整个 Ethernet 帧再做一次 CRC。它保护规定的网络/传输头和 payload，计算时按协议对某些会变化的字段做规范化处理。这样，中间网络正常修改 TTL、Hop Limit 或拥塞相关字段时，不会让原本合法的包因为这些允许的变化而校验失败。

Linux v6.12 的 RXE 软件实现可以作为可核对的阅读入口：`rxe_icrc_hdr()` 处理头部，`rxe_icrc_generate()` 生成，`rxe_icrc_check()` 验证。实现会规范化 IPv4 的 TTL、ToS、头校验字段，IPv6 的相应字段以及 UDP checksum/BTH 保留位，再结合其他 RDMA 头、payload 和 padding 计算 CRC。**它使用的是 CRC-32 路径，不是 CRC32C。** 这份源码用来展示边界与算法路径，不代表所有硬件 RNIC 的内部实现。[^rxe]

无需背下全部掩码才能理解重点：

> ICRC 验证的是 RoCE 传输端点看到的规定内容，不是 CPU/GPU 在更早时刻计算出的模型状态，也不是远端进程随后持久化的对象。

### 6.2 三个不能从 ICRC 通过推导出的结论

第一，发送缓冲区在 RNIC 读取之前已经被错误写入，RNIC 仍可以为错误内容生成合法 ICRC。

第二，接收端完成检查以后，远端程序可能用错地址、发生缓冲区复用竞态、错误拼接 chunk，或把正确字节存到错误的对象路径。

第三，整个传输完全正确，但应用发送的本来就是旧 epoch 的分片。包头中的地址、QP 或其他传输字段，并不能替代完整的 Checkpoint 身份协议。

### 6.3 CQE 不是“远端已经恢复验证并落盘”的收据

`ibv_poll_cq()` 获取的是 Work Completion，且必须检查 `wc.status`；它不返回“这个 checkpoint 的全部分片已被远端应用校验并提交”这样的状态。普通 RDMA Write 也不能被假定为自动产生远端应用可消费的接收完成通知；是否使用 Write with Immediate、Send 或单独控制消息，需要协议明确设计。[^verbs]

因此应用至少需要区分：

```text
本地 WR 完成
≠ 远端应用收到并验证该对象
≠ 指定故障域内已持久化
≠ 整个 epoch 已提交
```

这正是 [[8.17 万卡集群分布式 Checkpoint 极致加速实践（MegaScale & DeepSeek 方案）]] 中不同完成状态不能压成一个布尔值的另一层原因。

## 7. PCIe：LCRC、ECRC 与 FLIT 模式不能混讲

在传统 **Non-FLIT** PCIe 路径中，可以用下面两个层次建立直觉：

| 机制 | 保护边界 | 工程含义 |
|---|---|---|
| LCRC | 相邻 PCIe 链路端之间的数据链路保护 | 发现链路错误，结合链路重放机制处理 |
| ECRC | 可选的 TLP 级端到端检查 | 比单链路覆盖更远，但仍是 PCIe 事务边界 |

ECRC 的“End-to-End”是该事务路径的端到端，不是应用状态到未来恢复进程的端到端。支持 ECRC、开启生成、开启检查、沿途按要求处理，是不同条件。**发现设备有 ECRC capability，不足以证明这次 I/O 的有效数据路径已经启用完整保护。**[^pcie-ecrc]

> [!important] 版本边界
> PCIe 6.0 引入的 FLIT 模式使用 FEC、CRC 与重放协作，不能直接把 Non-FLIT 的 LCRC 图当作所有代际和工作模式的实际报文格式。本篇保留“链路级 / 事务级 / 应用级”这组稳定的边界，不把旧格式泛化到所有 PCIe 模式。[^pcie6]

TLP 传输了正确字节，仍可能是软件准备的错误字节。设备正确执行了 DMA，也可能是驱动给了错误的地址。链路保护和地址映射/IOMMU 是不同机制；后者同样不能自动理解“这个地址里应该是 epoch 42 的 optimizer state”。

## 8. NVMe PI：除了内容，还尝试检查“是否放在正确位置”

### 8.1 SSD 介质 ECC、NVMe PI、应用摘要分别管什么

SSD 内部对闪存介质采用的纠错机制，与 Host/Controller 交换的 Protection Information，不是同一件事。**PI 将数据块与一份约定格式的保护信息关联，使支持它的 I/O 路径节点能够检查内容和部分位置语义；应用摘要则把对象语义与恢复流程接上。**[^linux-integrity][^nvme-pi]

![[图片/SVG/8_9_9_11_2.svg|900]]

传统 **8 字节、16-bit Guard PI** 可用下表理解。这里只描述这一传统格式，不能把它当成所有 NVMe PI 格式的字段布局。[^pi-vendor]

| 字段 | 传统宽度 | 作用 | 不要误解成 |
|---|---:|---|---|
| Guard Tag | 16 bit | 按规定范围计算的完整性检查，传统格式使用相应 CRC-16 | 任意 SHA 摘要或 CRC32C |
| Application Tag | 16 bit | 由上层赋予含义并按掩码等规则检查的标签 | 自动包含完整 job/epoch/tensor 身份 |
| Reference Tag | 32 bit | 在相应保护类型中参与块位置/顺序检查 | 能自动识别文件名、训练 step 和所有地址错误 |

在传统保护类型的抽象下，Type 1 的参考标签与逻辑块地址关联，Type 2 使用命令提供的起始参考信息，Type 3 不提供同样的参考标签位置检查。**具体比较条件、跳过规则及标签行为，要以选定 NVM Command Set 版本、PI 格式和命令字段为准。** 实现中存在“生成了标签但未启用相应检查”的配置，不能只看标签是否出现。[^spdk-dif]

### 8.2 为什么 Guard 之外还需要 Reference Tag

假设 A、B 两个 LBA 都保存合法数据和合法 Guard。系统把 A 的整个“数据 + Guard”错放到了 B。只检查 Guard，看到的仍是一组自洽数据。

在支持且启用位置检查的模式下，Reference Tag 提供另一项约束：**这块数据宣称的位置，是否等于本次 I/O 期望的位置？** 这能覆盖部分 misdirected I/O，而不是仅检查随机位变化。

仍然存在边界：软件若从一开始就准备了错误的 LBA，并与错误地址一致地生成标签，PI 不知道应用真正想写哪里。若数据和位置标签被一致地错误重映射，也不能简单承诺必然检出。因此它是更多证据，不是逻辑意图的万能证明。

### 8.3 新格式不能省略，但也不能想当然

NVM Express 2.0 引入的增强包括 **16 字节 PI**，可使用 **32 位或 64 位 Guard**，并增强 Storage/Reference Tag 的表达。这里“16 字节 PI”和“16-bit Guard”是两个完全不同的概念。也不能因为出现“32-bit CRC”，就直接替换成 CRC32C；必须匹配该格式定义的算法。[^nvme-pi]

落地时至少核对四项：

1. Namespace **支持**哪些 metadata/PI 格式；
2. Namespace **当前格式化选择**了哪种 LBA、metadata 和 PI 布局；
3. Host、传输、控制器和中间块设备是否**保留并传递**所需 metadata；
4. 命令中的 **PRACT/PRCHK 及相应标签字段**，究竟要求怎样生成、传递、剥离和检查。

PRACT 等字段的行为还与命令方向和 metadata 配置有关，不宜脱离格式给一个“设成 1 就更安全”的口诀。[^pi-vendor]尤其是由较晚一层重新生成 PI 的路径：**重新计算出的合法 PI 不能向前追溯证明它之前的字节没有出错。**

Linux 文档给出的普通文件系统路径就是一个有用例子：由块层生成保护信息时，起点在相应 I/O 提交处，而不是应用最初建立快照的时刻。文档包含历史接口说明，查阅当前内核代码时应另核对版本，不照抄旧 API 作为现行接口保证。[^linux-integrity]

## 9. “所有局部检查都成功”的三种失败

![[图片/SVG/8_9_9_11_3.svg|900]]

### 9.1 错误发生在局部校验生成之前

GPU 状态 $D_0$ 已经形成并留下可信摘要；Host staging 随后被错误写成 $D_1$。RNIC 对 $D_1$ 生成 ICRC，远端 SSD 路径对 $D_1$ 生成 PI，各段可以全部通过。恢复端用原始摘要比较 $D_1$，才有机会发现错误。

若第一份应用摘要也等到 Host 已经变成 $D_1$ 才生成，**这个错误就不在该应用摘要的覆盖范围内**。是否要在 GPU 上先计算摘要、在传输两端比较，取决于需要覆盖哪一段，以及计算和搬运成本是否可接受。这是一项明确的覆盖范围取舍，不是“Host Hash 天生等于从 GPU 开始的端到端保护”。

### 9.2 错误发生在验证之后

远端收到数据并验证通过，接着把 buffer 放回池中；另一个请求重用 buffer，而原来的异步写盘尚未真正取完数据。错误源自所有权/生命周期，ICRC 无法保护接收验证之后的覆盖。

设计时要保证从摘要读取到最后一个相关消费者完成之间的数据不变，或使用明确的版本化/COW/独立副本。**“Hash 已经算完，可以回收 buffer”通常是错误的释放条件；Hash 完成并不代表所有 I/O 消费者都已完成。**

### 9.3 内容完全合法，但身份不对

恢复 rank 8 时读到了 rank 7 的文件，并且连同 rank 7 的合法摘要一起读回。裸文件摘要通过，却没有证明这份对象是 rank 8 所需的那份。

解决办法是把内容与身份绑定，并从**独立的期望 manifest/恢复请求**取得身份。如果“期望的 rank、epoch、摘要”全部无条件来自被检查对象本身，校验只是自证一致，不是证明它满足这次恢复请求。

## 10. 应用端到端协议：摘要必须和身份、生命周期一起设计

以下是可实现的工程设计，不声称某个框架已经使用同样字段。

### 10.1 先规定到底 Hash 哪些字节

Checkpoint 可以同时存在多种表示：张量逻辑内容、序列化字节、压缩后对象、加密后的存储表示。至少明确两种摘要的区别：

| 摘要 | 生成位置 | 验证位置 | 主要作用 |
|---|---|---|---|
| `stored_digest` | 最终存储表示确定之后 | 读回后、解析/解压或解密流程的相应边界 | 验证存储对象精确字节 |
| `logical_digest`（可选） | 规范化的逻辑表示确定之后 | 解码/转换后、使用之前 | 验证跨表示转换后的预期内容 |

加密数据采用 AEAD 时还应按其规范验证认证标签；不要用裸 Hash 替代 AEAD 的认证。[^aead]字节摘要也不会自动消除浮点布局、字节序、NaN 编码或版本差异，逻辑摘要必须有明确规范化规则。

### 10.2 让一条记录同时回答“是什么”和“属于谁”

建议对每个 chunk 的描述包含 `format_version、hash_algorithm、job_id、checkpoint_epoch、tensor_id、shard_id、chunk_index、offset、length`，并按场景补充 dtype、shape、layout、压缩参数和加密相关标识。这里字段集合是协议设计，不是万能固定模板。

一种清晰的两层做法是：

$$
d_i = H(\text{stored bytes}_i)
$$

$$
\ell_i = H(\text{domain}_{leaf}\ \Vert\ \operatorname{Encode}(\text{descriptor}_i, d_i))
$$

前者便于对精确对象字节做流式校验；后者把对象摘要和语义身份绑定。`Encode` 必须无歧义：固定字段顺序、类型、字节序、长度前缀、未知字段规则，不能直接拼接字符串或 Hash C++ 结构体的内存。如何编码与选算法详见 [[9.12 Checksum 与 Hash 工程：CRC32C、xxHash、SHA-256、BLAKE3 与硬件加速]]。

manifest 再绑定**有序条目、总数、覆盖区间和同一个 epoch**。验证时不仅比较每个 $d_i$，还要拒绝缺片、重复编号、非法重叠、未覆盖区间、超长对象和未知算法。单纯“遍历收到的所有文件并校验”发现不了根本没收到的文件。

### 10.3 摘要放在哪里，不只是一个文件格式问题

数据和摘要放在一起并不自动错误：随机破坏通常不会刚好把它们变成另一组有效组合。但是，误操作、错误重写、重放或恶意修改可能同时改变两者。

对于随机故障，需要可靠保存原始 manifest，控制其修改权限，并保护自身完整性。对于不可信存储/跨信任域，应从可信通道获得 manifest 或其根摘要，或者验证 MAC/签名；**只给 manifest 再加一份同处可任意改写的裸 Hash，不会凭空产生信任根。** HMAC 是标准化的带密钥消息认证构造，不应自行用 `H(key || message)` 代替。[^hmac]

即便签名完全正确，旧的签名 manifest 仍然可以被重放。允许恢复哪个版本，还要由可信的提交记录、外部 generation/fencing 状态或操作者明确的恢复选择决定。这里“新鲜性”不是永远拒绝旧版本：故障恢复本来就可能刻意选择较旧的完整恢复点。

## 11. 把验证接入提交和恢复，而不是只在 save() 里调用一次 Hash

![[图片/SVG/8_9_9_11_4.svg|900]]

建议的协议顺序如下；每个步骤的完成条件都需要独立记录。

**建立快照。** 使用 [[8.6 Checkpoint 同步异步分片]] 中的一致性边界，冻结同一个 epoch 的对象集合。应用摘要应在声明的最早稳定表示上生成，不能一边读取可变状态一边假定读到了完整快照。

**传输和暂存。** 把摘要、身份及相应数据交给后续节点。接收端对照发送时保留的依据验证，而不是接收后重新生成摘要并把它直接当作原始依据。验证通过可以产生 `VERIFIED` 回执，但还不是最终的持久化回执。

**持久化与提交。** 完成目标故障域要求的持久化。对本地文件，`write()` 成功不是 `fsync()` 成功；文件数据同步也不自动同步目录项，基于 rename 发布的方案需要按文件系统语义处理目录同步。远端对象存储使用其明确的提交与一致性语义，不能照搬本地 `fsync`。[^fsync]

**发布 manifest。** 聚合所有预期分片的校验、身份和持久化证据，先保证 manifest 自身可恢复，再按协议发布“这个 epoch 可恢复”。原子发布路径、失败重试和 fencing 延续 8.17；本篇增加的是“发布前必须核对的证据”。

**恢复时再验证。** 固定此次恢复使用的 manifest 版本，先检查格式和完整集合，再逐 chunk 检查长度、身份、摘要。允许流式验证后使用已经验证的 chunk，但不能在全局恢复尚未成立时把半个 epoch 对外宣告为有效状态。否则虽然每块都正确，整体仍可能不一致。

> [!warning] 不要把几个完成状态混为一谈
> `HASHED` 证明已经为某份字节建立摘要；`VERIFIED` 证明某次比较通过；`DURABLE` 依赖具体后端和故障域；`COMMITTED` 依赖完整 epoch 的发布协议。没有任何一个状态可以自动推导其余三个。

## 12. 最小故障实验：不碰真实磁盘，也能复现边界漏洞

把下面三个 Python 代码块按顺序放入 `integrity_lab.py`，使用 Python 3.10+ 运行。它只操作进程内的不可变 `bytes`，不读写磁盘、不注入真实硬件故障。模型刻意很小：**只证明内容检查、身份检查和受信依据不是一件事**，不是一套可上线的 Checkpoint 实现。

第一段定义记录和无歧义的固定模式编码。`frozen=True` 加 `bytes` 避免实验本身引入可变缓冲区竞态；字段范围先检查，再按固定大端编码。教学中的 `JOB` 是固定域，不涉及字符串规范化。

```python
from dataclasses import dataclass, replace
import hashlib
import struct
import zlib

JOB = b"checkpoint-lab/v1/job-A"

@dataclass(frozen=True)
class Record:
    epoch: int
    shard: int
    payload: bytes
    digest: bytes

def digest_of(epoch: int, shard: int, payload: bytes) -> bytes:
    if not (0 <= epoch < 2**64 and 0 <= shard < 2**32):
        raise ValueError("identity out of range")
    frame = JOB + struct.pack(">QIQ", epoch, shard, len(payload)) + payload
    return hashlib.sha256(frame).digest()

def make_record(epoch: int, shard: int, payload: bytes) -> Record:
    data = bytes(payload)
    return Record(epoch, shard, data, digest_of(epoch, shard, data))
```

第二段把“对象内部自洽”与“满足恢复请求”分开。期望 epoch/shard 从调用者传入，而不是从对象照抄。生产协议还要验证预期长度、完整集合、受信 manifest 和认证信息；这个函数有意不实现这些部分。

```python
def self_consistent(record: Record) -> bool:
    return record.digest == digest_of(
        record.epoch, record.shard, record.payload)

def accepted(record: Record, expected_epoch: int, expected_shard: int) -> bool:
    identity_ok = (record.epoch, record.shard) == (
        expected_epoch, expected_shard)
    return identity_ok and self_consistent(record)

def flip_one_bit(data: bytes) -> bytes:
    if not data:
        raise ValueError("need at least one byte")
    return bytes([data[0] ^ 1]) + data[1:]
```

第三段保持原始摘要不变后损坏内容，再演示“晚生成的局部 CRC 可以通过”。这里 `zlib.crc32` 只是模拟局部检查的 **IEEE CRC-32**，不是 RoCE ICRC、不是 CRC32C，也不模拟真实报文的字段覆盖。

```python
good = make_record(42, 8, b"optimizer-state")
bad = replace(good, payload=flip_one_bit(good.payload))
late_crc = zlib.crc32(bad.payload)
old = make_record(41, 8, good.payload)
wrong_shard = make_record(42, 7, good.payload)
rewritten = make_record(42, 8, b"wrong-but-self-consistent")

assert accepted(good, 42, 8)
assert zlib.crc32(bad.payload) == late_crc
assert not accepted(bad, 42, 8)
assert self_consistent(old) and not accepted(old, 42, 8)
assert self_consistent(wrong_shard) and not accepted(wrong_shard, 42, 8)
assert accepted(rewritten, 42, 8)  # 裸摘要不能认证内容来源！
print("PASS: late CRC, corruption, stale epoch, wrong shard, untrusted rewrite")
```

这个实验的最后一个断言尤其重要：**能同时改写内容和摘要的人，仍可构造同一身份下的自洽错误记录。** `accepted()` 不是安全协议；缺少的正是可信原始摘要或经过认证的 manifest。加长 Hash 不会修复这个结构性缺陷。

这是单进程纯计算实验，没有线程等待或 I/O 完成时序，因此不人为附加“函数互相调用”的泳道图；真实异步所有权和提交顺序已经在上一节 SVG 中表达。

## 13. 故障注入矩阵：检查你究竟覆盖了什么

把以下矩阵接到 [[9.6 故障注入矩阵]]，分别记录“故障是否触发、哪一层发现、是否阻止错误恢复”。**检出率的分母是实际注入并确认生效的故障，不是所有正常 I/O 数。**

| 注入位置/方式 | 局部检查可能怎样表现 | 应用协议的预期结果 | 实验要证明的边界 |
|---|---|---|---|
| 原始摘要生成后翻转 payload 位 | 随后重算的链路检查仍可通过 | 与保留的摘要不匹配 | 内容保护从摘要生成时刻开始 |
| 第一份应用摘要生成前破坏源状态 | 后续所有检查可通过 | 裸摘要未必能发现 | 需要更早依据或计算语义检查 |
| 在链路上破坏受保护帧 | FCS/ICRC 等可能检出并丢弃 | 不允许错误对象被提交 | 重试完成与错误数据提交要区分 |
| 接收验证后、异步落盘前复用 buffer | 已完成的网络检查无能为力 | 下游/恢复检查应发现 | 验证后生命周期仍需保护 |
| 数据+Guard 成套错置到另一个 LBA | Guard 可通过；位置检查视 PI 模式而定 | 应用身份也应检查 | 内容自洽不等于位置正确 |
| 交换两个合法 shard 及其裸摘要 | 每个文件内部校验可通过 | 拒绝身份/映射不匹配 | 摘要须绑定描述符和预期对象 |
| 少写一个 chunk，却只遍历现存文件 | 存在的文件都能通过 | 拒绝不完整 manifest/覆盖集合 | “所有收到的都对”不等于“都收到了” |
| 返回旧 epoch 数据+合法 manifest | 字节与签名都可能合法 | 按独立恢复版本策略处理 | 内容真实性不等于新鲜性 |
| 同时替换内容与未认证摘要 | 可以自洽 | 与可信 manifest 不符或认证失败 | 裸 Hash 不提供来源认证 |
| `kill -9`/掉电发生在发布前后 | 不一定存在校验错误 | 只暴露可恢复的完整 epoch | 崩溃一致性是另一条验收轴 |

不要直接对生产块设备执行 `dd`、format、固件故障注入或破坏性写入来“测试 PI”。软件模拟放在隔离副本中；真实硬件注入先确认平台机制、回滚路径和测试权限。

## 14. 观测与定位：从“有没有 CRC error”升级到证据链

### 14.1 每一层都留证据，但不要把计数器当作充分证明

| 层 | 可采集证据 | 常见误判 |
|---|---|---|
| CPU/内存/GPU | RAS/EDAC、ECC corrected/uncorrected、GPU 错误日志 | counter 为零，所以整个计算和搬运都正确 |
| PCIe | AER、设备日志、重放/链路错误相关计数 | 只要有 AER 就断言是某个 Checkpoint 内容损坏 |
| Ethernet/RDMA | NIC/交换机 FCS、丢包、ICRC/重试等可用计数，CQ 错误 | 把 PFC/拥塞和数据损坏混为一个问题 |
| NVMe/后端 | PI 错误状态、控制器 error log、介质错误、对象校验记录 | SMART 没报错就认为所有对象都完整 |
| 应用 | expected/actual digest、对象身份、版本、长度、来源副本、验证阶段 | 只记录一个“checksum failed”，无法追溯起点 |

Linux AER 与 GPU ECC 工具提供的是相应平台暴露的错误证据，并不替代应用层的对象记录。[^aer][^nvidia-smi]

只读排查可以先查看本机工具帮助，确认支持的命令形态，再查询实际设备。下面演示命令不是跨版本保证，也不是完整自动诊断脚本：

```bash
nvme --version
nvme help
# 常见 2.x 命令形态；设备名须先确认，以下操作仅查询。
nvme id-ns /dev/nvme0n1
nvme smart-log /dev/nvme0
nvme error-log /dev/nvme0
nvidia-smi -q -d ECC
lspci -vv
```

当前 nvme-cli 上游文档已经出现 `nvme id ns` 的分层命令形态，同时保留旧 `id-ns` 别名；**以实际安装版本的帮助为准**，不要把命令语法变化误认为设备不支持 PI。Namespace Identify 的能力字段与当前格式字段也要分别解读。[^nvme-cli]

### 14.2 发生 mismatch 后，怎样缩小范围

先隔离受影响对象和原始 manifest，保留 expected/actual digest、完整身份、软件/固件版本、采集时间和源副本。不要立刻用当前错误对象重新生成摘要“修复报警”。

然后沿着**同一份对象、同一个版本**比较边界证据：源快照摘要、staging 摘要、接收端摘要、持久化读回摘要、恢复端摘要。最早出现不一致的两份证据之间，是优先调查区间。注意可变缓冲区重读和不可信摘要可能让证据失真；有条件时用独立副本、独立进程或不同实现交叉复核。

错误计数和时间关联只能辅助归因，不是充分因果证明。与 [[9.10 跨层性能归因：CPU、NUMA、PCIe、NIC、Switch、RDMA 与 NVMe 的 P99]] 一样，最好用受控对照缩小区间，而不是看到某层有异常就把全部责任归给它。

### 14.3 检出不等于修复

CRC/Hash 只提供检测信息，通常不能重建原始内容。修复需要可信副本、纠删码或回退到另一个完整恢复点。复制发生在错误之后时，多份副本可以一致地错误；多数票并非所有故障模型下的真值来源。

在线读校验之外，设计定期 scrub 和恢复演练：scrub 缩短损坏潜伏时间，恢复演练检查 manifest、分片、布局和重建路径能否真正协作。不要把“校验扫描成功率”替代“完整恢复成功率”。把隔离、重读、切换副本、回退 epoch 和保留证据的流程写入 [[9.8 Runbook 与可运维产物]]。

## 15. 能用于设计评审的五个结论

**一，End-to-End 必须带端点。** 说明是 MAC 到 MAC、RoCE 传输端点、PCIe 事务端点、Host 到存储，还是稳定快照到恢复使用。不同机制叫同一个名字，不等于覆盖范围相同。

**二，校验值不能从已经错误的数据中追溯出原始真值。** 摘要生成点决定最早覆盖边界；验证之后的数据生命周期决定最晚覆盖边界。

**三，合法内容也可能是错误对象。** 用无歧义描述符绑定内容、身份、位置和版本，再对照独立的完整 manifest。

**四，完整性、持久性、原子性、认证与新鲜性各自需要协议。** 一个 Hash、一次 CQE、一个 `fsync` 或一份签名，都不应被赋予它没有提供的语义。

**五，性能优化不能让验证成为旁路。** 要计入 Hash CPU、内存带宽、验证队列、恢复 P99 和最坏情况下的重读成本，但不能为了“快”而先把未验证状态标为成功。计算成本与算法选型继续阅读 [[9.12 Checksum 与 Hash 工程：CRC32C、xxHash、SHA-256、BLAKE3 与硬件加速]]。

> [!tip] 面试口述：为什么各层都有 CRC，Checkpoint 还要自己校验？
> 各层 CRC 只保护各自的生成和验证边界，无法覆盖生成前、验证后以及层间的软件错误。错误数据也能被正常编码、正常传输、正常落盘，所有局部检查都可能成功。Checkpoint 需要在稳定快照上保留摘要，恢复时对照原始依据验证，同时绑定 epoch、分片身份、长度和完整集合。这样既检测字节变化，也防止拿错对象。摘要仍不能替代一致性快照、持久化、受信 manifest 和恢复版本策略，更不能证明训练计算本身正确。

[^chen]: 陈硕，《Linux 多线程服务端编程：使用 muduo C++ 网络库》，附录 A.1.13“TCP 的可靠性有多高”，并参照 §7.5 的应用消息校验讨论。本次读取了用户 Library 中该书对应片段；用于保护边界问题，不将教材中的简化描述扩展为绝对可靠性保证。
[^ras]: Linux Kernel Documentation, [RAS subsystem](https://docs.kernel.org/admin-guide/RAS/main.html)；[EDAC documentation, v5.16](https://www.kernel.org/doc/html/v5.16/driver-api/edac.html)。错误类型与报告机制；具体 ECC 编码能力取决于平台。
[^linux-integrity]: Linux Kernel Documentation, [Data Integrity](https://www.kernel.org/doc/html/latest/block/data-integrity.html)，特别是 Introduction、Data Integrity Extensions 与 Normal Filesystem。文档包含历史背景与接口，本文使用其分层保护原则，不据此保证某个当前堆叠设备的支持状态。
[^crc]: RFC 3385, [iSCSI CRC/Checksum Considerations](https://www.rfc-editor.org/rfc/rfc3385.html)，§3–§4。讨论 CRC 多项式、错误模型及消息长度，不把其特定误码模型套成通用事故概率。
[^rxe]: Linux v6.12, [`drivers/infiniband/sw/rxe/rxe_icrc.c`](https://github.com/torvalds/linux/blob/v6.12/drivers/infiniband/sw/rxe/rxe_icrc.c)，`rxe_icrc_hdr`、`rxe_icrc_check`、`rxe_icrc_generate`。
[^verbs]: rdma-core, [`ibv_poll_cq(3)`](https://man7.org/linux/man-pages/man3/ibv_poll_cq.3.html) 与关联的 [`ibv_post_send(3)`](https://man7.org/linux/man-pages/man3/ibv_post_send.3.html)。Work Completion 描述与应用持久化协议属于不同层次。
[^pcie-ecrc]: Rambus, [End-to-End Cyclic Redundancy Check (ECRC)](https://www.rambus.com/chip-interface-ip-glossary/ecrc/)；Intel, [ECRC on the RX Path](https://www.intel.com/content/www/us/en/docs/programmable/683093/15-1/ecrc-on-the-rx-path.html)。用于区分链路/事务边界及可选检查，不作为所有产品的开启状态证明。
[^pcie6]: PCI-SIG, [PCIe 6.0 Specification Webinar Q&A: Deeper Dive into FLIT Mode, PAM4 and FEC](https://pcisig.com/blog/pcie%C2%AE-60-specification-webinar-qa-deeper-dive-flit-mode-pam4-and-forward-error-correction-fec)。
[^nvme-pi]: NVM Express, [Changes in NVM Express Revision 2.0](https://nvmexpress.org/changes-in-nvm-express-revision-2-0/) 与 [The NVM Command Set: New Specification Features and More](https://nvmexpress.org/the-nvm-command-set-new-specification-features-and-more/)。增强 PI 介绍；本文没有把概述代替逐条命令规范。
[^spdk-dif]: SPDK, [`spdk_dif_ctx` documentation](https://spdk.io/doc/structspdk__dif__ctx.html)。上下文包含保护类型、块布局、参考/应用标签及检查标志；真实部署须以匹配版本的 NVM Command Set 和驱动实现确认。
[^hmac]: RFC 2104, [HMAC: Keyed-Hashing for Message Authentication](https://www.rfc-editor.org/rfc/rfc2104.html)。
[^fsync]: Linux man-pages, [`fsync(2)`](https://man7.org/linux/man-pages/man2/fsync.2.html)，包括目录项同步与错误处理边界。
[^aer]: Linux Kernel Documentation, [PCI Express AER Driver HOWTO](https://docs.kernel.org/PCI/pcieaer-howto.html)。
[^nvidia-smi]: NVIDIA, [System Management Interface documentation](https://docs.nvidia.com/deploy/nvidia-smi/index.html)，ECC 查询与设备能力相关说明。
[^nvme-cli]: linux-nvme/nvme-cli, [`nvme-id-ns` documentation](https://github.com/linux-nvme/nvme-cli/blob/master/Documentation/nvme-id-ns.txt)。命令形态以安装版本为准。

[^pi-vendor]: KIOXIA, [What is T10 Protection Information?](https://blog-us.kioxia.com/post/2023/09/26/what-is-t10-protect-information)，传统 PI 字段与边界；Memblaze，[真正的端到端数据保护是什么样的？](https://www.memblaze.com/innovate/technical-articles/172.html)，PRACT/PRCHK 的产品工程解释。本文不把这些产品的能力或推荐设置泛化到全部 NVMe 设备。
[^aead]: RFC 5116, [An Interface and Algorithms for Authenticated Encryption](https://www.rfc-editor.org/rfc/rfc5116.html)。
