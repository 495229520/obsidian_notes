# AIDC 数据保护：TLS、mTLS、KMS、Envelope Encryption 与密钥轮换

> [!abstract] 本篇的学习预算
> AIDC 在本文指 AI Data Center（AI 数据中心）。目标是能看懂架构图、识别明文暴露点、解释 DEK/KEK 分工，并参与密钥轮换和恢复评审。**不实现 TLS、不自创加密协议、不展开密码学证明。**
>
> 学习顺序仍然是：端到端完整性 → Checksum / Hash → 认证与 AEAD → 本篇。加密不能替代正确的对象版本、持久化协议、Scrubbing、备份和恢复测试；这一篇不应抢占前面完整性主线的时间。

## 1. 先问“防谁、保护哪一段”，再问“用了什么算法”

假设训练作业把 Checkpoint 写进远端对象存储。至少有三种不同的风险：网线上被旁路读取；存储介质或备份副本被拿走；有权运行代码的主机进程直接读出模型和密钥。三者分别对应传输、静态存储和使用中的保护边界，不能靠一个“已开启加密”的开关统一回答。TLS 面向通道，信封加密面向数据对象；保护使用中的数据则需要另行评估可信执行环境及其信任根。[^tls][^envelope][^cc]

| 首先要回答的问题 | 常见机制 | 不能据此推出 |
|---|---|---|
| 传输中的载荷会不会被窃听或篡改？ | TLS；适配实际路径的 IPsec / MACsec | 接收进程、后续代理和落盘文件都看不到明文 |
| 对端是不是我期望的服务或工作负载？ | 证书校验、mTLS、工作负载身份 | 该身份可以读任意租户的 Checkpoint |
| 磁盘或对象副本泄漏后能否直接解读？ | 磁盘、服务端或客户端加密 | 运行时主机被攻陷后仍无法读取数据 |
| 数据是否属于正确租户、对象、代次和分片？ | 认证上下文、版本协议、可信 Manifest | 只要某一块的 AEAD tag 有效，它就是最新版 |
| 数据坏了还能不能恢复？ | 副本、EC、备份、修复与恢复演练 | 有 Hash 或有加密就必然可恢复 |

后两行是系统设计上的组合要求：密码学原语判断的是其输入所定义的语句，版本选择与可恢复性必须由系统另外建立。

图中的三条泳道是三条**分别需要检查**的路径。上面的控制 RPC 使用 mTLS，并不会让下面的 RDMA 数据载荷自动进入 TLS record。最重要的标注不是“哪里画了锁”，而是“加密在哪里开始、解密在哪里结束”。[^grpc][^rdma-ipsec]

### 1.1 静态加密也分层

磁盘加密通常将明文边界放在主机或存储控制层；对象存储的服务端加密将其放在存储服务中；客户端先加密、再上传，则可以把边界前移到客户端。第三种方式能减少对存储服务读取明文的信任，但客户端必须承担对象格式、密钥授权、恢复和应用兼容性。**“存储服务能解密”和“存储服务只能保存密文”是两种不同的架构。**[^envelope]

本文后面的方案采用**客户端信封加密**作为教学模型，并不是断言所有 AIDC 都应采用它。是否需要这一层，取决于数据分类、租户隔离要求与威胁模型。

## 2. TLS 与 mTLS：加密通道、身份认证、业务授权是三件事

### 2.1 TLS 不只是“把数据变成乱码”

在典型的证书认证 TLS 连接里，握手协商协议参数并完成认证和密钥建立，之后用对称 AEAD 保护 application data。证书中的长期私钥与连接使用的流量密钥不是同一把钥匙。这里以 TLS 1.3 的协议模型理解边界，不讨论完整握手细节。[^tls]

普通服务端认证 TLS 中，客户端验证服务端；客户端也可以通过 token 等应用层机制表明身份。mTLS 则让服务端也要求并验证客户端证书。对 gRPC 来说，通道凭证与逐调用凭证仍是不同的概念，不能把“TLS 已建立”理解为业务授权完成。[^grpc]

| 检查点 | 正确理解 | 常见误区 |
|---|---|---|
| 证书信任 | 验证受信任签发链、有效期和用途 | 只看“对方发来了一张证书” |
| 对端身份 | 核对预期 DNS 名称或工作负载身份绑定 | 受同一 CA 签发就一定是目标服务 |
| mTLS | 双方按配置证明其证书身份 | 有客户端证书就可以绕过租户 ACL |
| 应用授权 | 身份是否有权执行本次操作、访问该对象 | TLS 成功等于 `ReadCheckpoint` 获准 |
| 代理与网关 | 分别标明每一跳是否重新加密 | 入口 HTTPS 等于端到端加密 |

证书校验属于认证路径；身份到权限的映射是应用必须补齐的策略。不要通过关闭校验来“修复”连接问题；那会改变所依赖的安全前提。[^grpc]

### 2.2 TLS 在代理处终止，边界就到代理为止

假设客户端与网关间有 TLS，但网关到对象服务是明文，那么第二跳仍暴露载荷。即便第二跳也有 TLS，这也是两段独立的加密通道，网关仍能接触明文。需要让网关看不到载荷时，必须改变终止位置，或增加客户端对象加密，而不是把两把锁画成一把端到端锁。

TLS 1.3 的 0-RTT early data 还有额外的重放风险。Checkpoint 提交、删除、租户配置更新等有副作用操作，不应未经协议设计就放进 early data；普通连接的重试幂等性也仍需应用自己处理。[^tls]

## 3. DEK、KEK、KMS：大数据在本地加密，小密钥集中治理

### 3.1 三个名字各管一件事

**DEK（Data Encryption Key）**直接保护数据。**KEK（Key Encryption Key）**保护 DEK，即对 DEK 进行包装（wrap）。**KMS（Key Management Service）**是管理和使用密钥的服务，提供身份与策略检查、密钥版本和状态管理、审计及密码操作接口；它不等于某个固定算法，也不必然等于 HSM。[^envelope][^kms-deep]

用抽象符号表示一个对象：

$$
(C,T)=\operatorname{AEAD.Encrypt}_{DEK}(N,P,A)
$$

$$
W=\operatorname{Wrap}_{KEK}(DEK,\text{wrap context})
$$

其中 P 是明文，C 是密文，T 是认证标签，N 是 nonce，A 是附加认证数据，W 是包装后的 DEK。`Wrap` 是抽象接口：实际可能是专用 key-wrap，也可能是 KMS 提供的认证加密操作，不能默认所有厂商使用相同密文格式。[^envelope]

关键不是“多套一层密码更神秘”，而是**分离大数据吞吐与密钥治理**。对象载荷可以在工作进程附近批量处理，而 KEK 的使用受集中策略约束。以 AWS KMS 为例，`GenerateDataKey` 可以返回明文 DEK 和其加密副本；KEK 本身不交给业务进程。明文 DEK 仍会出现在被授权的调用方内存中。[^generate]

![[图片/SVG/8_9_9_14_2.svg|900]]

写入路径中，KMS 返回的只是小密钥及包装结果，TB 级载荷不需要经过 KMS。读取路径先取密文与包装记录，授权解包得到 DEK，再在客户端执行认证解密。图里的“等待”是 KMS 请求尚未完成的依赖，不暗示必须阻塞某个操作系统线程。

### 3.2 包装后的 DEK 可以跟密文存一起，明文 DEK 不行

W 不是明文密钥，可以作为对象元数据保存。恢复时还需要确定 KMS 服务、密钥标识和适用的上下文。**不能只保存密文、却把恢复所需的包装记录放在会丢失的临时目录里。**[^envelope]

业务端应限制明文 DEK 的存活时间和可见范围，避免进入日志、core dump、调试输出和持久化缓存。简单的变量离开作用域不等于密码学意义上的可靠清除；要依赖适当的密钥容器、库和进程隔离，不能把普通字符串处理当作完整的密钥保护方案。AWS 的数据密钥接口文档也要求使用后尽快清除明文副本。[^generate]

## 4. 为 Checkpoint 设计信封：标签通过不等于对象正确

### 4.1 教学元数据：稳定的载荷描述与可轮换的包装记录分开

以下仅是**字段设计示例，不是可直接部署的存储格式**。将 `payload` 与 `key_envelope` 分开，是为了避免“换一层 KEK 包装”被误实现成“修改所有数据块的认证输入”。

```yaml
payload:
  format_version: 1
  tenant_id: tenant-a
  checkpoint_id: checkpoint-demo
  generation: 42
  shard_id: rank-003
  total_plaintext_length: 1073741824
  chunk_count: 256
  content_key_id: opaque-dek-id
key_envelope:
  kms_key_ref: provider-specific-key-reference
  wrapping_version: provider-specific-version-or-ciphertext-metadata
  wrapped_dek: base64-encoded-wrapped-key
  wrap_context_schema: checkpoint-key-envelope-v1
```

这里的 1 GiB、256 块只是示例，不是性能建议；真正的格式还需规定算法套件、每块 nonce / tag 的位置、规范序列化、字段长度、结束标记以及 Manifest 的认证方式。`content_key_id` 是标识符，不是密钥。不要依赖可能被重新指向的可变 alias 来解释历史对象；有的 KMS 在包装密文内部编码实际版本，不能把示例字段当成各家通用 API。

### 4.2 AAD 绑定上下文，但上下文也要来自可信的预期

可以把租户、对象 ID、generation、shard、chunk index、明文长度、格式版本等稳定信息绑定进每块的认证上下文。这样将一块数据搬到另一个位置或代次时，正确的验证方会拒绝上下文不匹配的载荷。**验证方必须从本次请求和可信元数据得到预期值，不能盲信密文旁边攻击者一同提供的字段。**

AWS KMS 的 encryption context 是一种具体的 AAD 机制：解密必须使用匹配的上下文，而且该上下文不是秘密，可能出现在审计日志中。因此这里只放非敏感标识，不放用户提示词、私密路径或明文凭证。[^context]

应用层数据 AEAD 的 AAD 与 KMS 包装 DEK 的 context 是两层不同输入。若希望只做 rewrap，载荷 AAD 就不应直接绑定未来会变化的 `wrapping_version`；包装记录自身仍须使用适当认证和可信元数据协议保护。不能为了轮换方便而完全放弃元数据认证。

### 4.3 分块加密必须处理重排、截断和 nonce 复用

对于本文采用的 AES-GCM 等要求 nonce 唯一的 AEAD，同一 DEK 下不能重复使用 nonce；并行 rank、重试、断点续传和崩溃后计数器回退都需要纳入设计。不能简单地让所有 rank 都从 nonce=0 开始使用同一把 DEK。重传已经生成的同一份密文，不等于再次加密；重新计算或修改分块则必须遵守格式的 nonce 分配规则。更稳妥的工程路径是采用经过审查的分段加密格式，而不是现场拼一个“随机数加 AES-GCM”的协议。[^streaming]

每块认证通过，也不意味着整体对象没有被截短。读取方还必须检查预期块数、总长度、终止标记或已认证 Manifest，并拒绝缺失或重排的块。分段认证允许在相应块认证通过后消费该块，但**不能将尚未确认完整性的 Checkpoint 宣布为可恢复版本**。这就是载荷认证与对象提交协议的分工。

### 4.4 三个加密解决不了的反例

**源头已经错了。** 程序把错误的张量写进 P，再合法加密，tag 仍会通过。密码学没有理解张量语义。

**拿到的是旧版本。** 旧 Checkpoint 的 tag 也完全有效。防回滚需要可信的期望 generation、目录或提交记录；AEAD 不是“最新版本检测器”。

**密文损坏了但没有恢复源。** 认证失败能阻止错误数据被静默使用，却不能凭空恢复数据。副本、纠删码、Scrubbing 与备份仍有自己的位置。

这三个反例只依赖机制的输入输出定义，不需要额外的密码学知识：验证器没有检查的命题，不会因为“使用了加密”就自动成立。

## 5. 密钥轮换：先说清到底换了什么

![[图片/SVG/8_9_9_14_3.svg|900]]

图中把“新写入改用新 KEK”“历史 DEK 改包装”“载荷换 DEK 重加密”分成三行，因为它们的 I/O 成本、迁移状态与风险完全不同。

| 操作 | 实际变化 | 历史载荷是否必须重写 | 不能误解为 |
|---|---|---|---|
| KEK / KMS 版本轮换 | 新加密或新包装使用新版本 | 通常不自动重写 | 历史数据已全部改用新 DEK |
| DEK rewrap | 同一 DEK 改由另一 KEK / 版本包装 | 通常不必；更新包装元数据 | 旧 DEK 泄漏已经被修复 |
| DEK 替换与 re-encrypt | 用新 DEK 生成新载荷密文 | 通常要重新处理数据 | 只改 key ID 就完成 |
| 证书与信任根轮换 | 更换身份凭证或信任配置 | 与对象载荷不是同一操作 | KMS 的历史对象也随之迁移 |

Google Cloud KMS 明确说明 key rotation 不会自动重加密已加密数据。AWS KMS 也将 KMS key material rotation 与数据密钥轮换区分：保留旧材料用于解密历史密文，不代表替换应用层 DEK。具体存储服务是否另有后台迁移，要查该产品的语义。[^rotation][^aws-rotation]

### 5.1 一个可恢复的计划轮换流程

下面是本文建议的运维流程，不是某家云的固定命令序列。

首先建立引用清单：哪些在线对象、快照、备份和异地副本仍依赖旧版本。然后创建并验证新版本，让新写入切换到新版本，读取路径暂时兼容新旧包装。

确有历史迁移需求时，再执行限速 rewrap：先生成新的包装记录，校验可解包性，通过条件更新或事务切换元数据，避免迁移与并发写入互相覆盖。迁移任务记录对象 generation、源包装版本与结果，支持重复执行和断点恢复。

最后在**没有旧 DEK 缓存的进程**中恢复抽样的历史对象和备份，确认依赖消除后，按保留策略禁用或销毁旧版本。只测试刚写入的新对象，无法证明旧备份可恢复；只测试热缓存读取，也无法证明 KMS 解密链条仍可用。

### 5.2 “定期轮换”与“泄漏应急”不是一个剧本

若旧 KEK 的材料和旧包装记录都已被攻击者获得，仅将 W 改成新包装，并不能让攻击者忘掉旧 DEK。若 DEK 已泄漏，保留同一 DEK 的 rewrap 同样不能恢复其机密性。需要评估受影响载荷、新 DEK 重加密、权限撤销与副本暴露范围；已经被复制走的明文无法通过轮换追回。

同理，禁用 KMS key 主要阻止之后通过该服务执行相关操作，并不远程擦除客户端已经拿到的 DEK。恢复和撤销测试都必须考虑内存缓存及尚未结束的任务。

## 6. KMS 进入的是密钥路径，不应成为每个包的热路径

### 6.1 先算密钥粒度，而不是先问 KMS 能跑多少 QPS

设总数据量为 S，每个独立 DEK 保护的数据量为 G。如果每份 DEK 都单独调用一次 KMS，冷启动情况下，调用数的数量级是：

$$
N_{KMS}\approx \lceil S/G\rceil
$$

这是调用次数的教学估算，忽略了重试、缓存、复用和具体服务优化。以 1 TiB 为例：每 4 MiB 配一个 DEK 是 262,144 份密钥；每 1 GiB 对象配一个 DEK 是 1,024 份。**两种方案都可以使用 4 MiB 的数据块，DEK 粒度不必等于 I/O 分块粒度。**

较细 DEK 粒度可缩小暴露影响范围，却增加元数据与冷启动密钥操作；较粗粒度可以减少调用，但扩大共享密钥范围，并使 nonce 管理更重要。本文不指定统一最佳粒度，评审对象应是一个租户、对象或不可变 shard 的生命周期，而不是一个网络包。

### 6.2 缓存、可用性和撤销时效是一组取舍

短期缓存 DEK 可以减轻重复解密和 KMS 故障的影响，但也扩大明文密钥在内存中的存活窗口，使权限撤销不能立即影响已拿到密钥的任务。缓存键至少要包含正确的租户与对象上下文；不能让“相同 key ID”造成跨租户复用。

KMS 超时应当触发明确的失败、有限重试或预先设计好的受控缓存策略，**不能自动退回明文写入**。审计也要两层都有：KMS 记录密钥操作，应用记录对象访问；一次解包后被缓存使用的数千次读取，不会天然变成数千条 KMS 解包记录。这是缓存架构的直接结果，而不是 KMS 日志缺陷。

可观测项包括 KMS 操作 P99、冷/热缓存命中、限流与重试、活动 DEK 数、旧包装引用数、认证失败数、恢复耗时以及撤销生效时间。不要把密钥材料作为日志字段。

## 7. GPU / RDMA 数据面的加密边界

### 7.1 控制连接不是数据连接

不少系统用 TCP / gRPC 完成认证、元数据交换或 bootstrap，随后由 RNIC 直接搬运载荷。RoCE 流量可以位于普通内核网络栈之外，不能因为 TCP 控制连接加了 TLS，就推断 RNIC 发出的数据包也受到同样保护。NVIDIA 的 RDMA IPsec 文档专门描述了这条路径对 full hardware offload 的要求。[^rdma-ipsec]

**rkey 不是 AES key。** 它是远端访问已注册内存时使用的访问控制标识之一，不承担把线上的 payload 加密的功能。[^verbs]

GPUDirect RDMA 描述的是第三方设备直接访问 GPU 内存的数据路径，也不是机密性协议。[^gdr]

### 7.2 可以在哪一层保护？

| 保护位置 | 适用视角 | 必须核对的边界 |
|---|---|---|
| TCP 连接的 TLS / kTLS | 实际经过该 TLS 通道的数据 | 是否有旁路、代理终止或另开的数据连接 |
| 应用 / 对象层 AEAD | 发送前已经是密文的载荷 | 接收端何时认证解密、谁管理 DEK |
| RoCEv2 的 IPsec 硬件路径 | 支持相应功能的 RNIC / DPU | 型号、crypto SKU、驱动、固件、模式、VF 和策略 |
| MACsec | 选定的二层安全连接 | 实际终止设备与二层拓扑，而非凭名称假设端到端 |
| GPU 可信执行环境 | 使用中数据的硬件信任边界 | 支持的 GPU、CPU TEE、驱动、拓扑和 attestation 策略 |

IPsec 与 MACsec 是不同层次的保护。MACsec 不应被简单理解成“必定每跳解密”，也不能默认跨任意路由网络端到端成立；要画出实际的安全连接和终止位置。支持普通 IPsec 加速也不等于支持所需的 RoCE 数据路径；NVIDIA 的功能文档本身列有版本和模式限制。[^rdma-ipsec][^macsec]

### 7.3 加密可能改变原来的“零拷贝”设计

应用层先加密，可能需要独立密文缓冲区、额外内存遍历与认证完成栅栏；若硬件在数据路径中完成加解密，则成本与瓶颈又不同。正确的说法不是“加密必然破坏零拷贝”，而是：**重新画出每一块缓冲区、DMA 方向、密钥驻留点和明密文转换点，再验证实现。**[^gdr][^rdma-ipsec]

例如在接收后、认证之前让 GPU 消费数据，会把“尚未认证的字节”暴露给计算。分块流水线可以做，但消费边界必须是经过认证的块，并与对象级完整性检查配合。

### 7.4 不要把 GPU confidential computing 画成一把万能锁

使用中保护是另一条技术线：硬件隔离、可信度量、attestation，以及由策略决定是否释放密钥。其兼容性取决于实际产品、配置和拓扑。NVIDIA 的 attestation 文档明确列出 GPU、驱动和交换设备的前提；不能由“GPU 型号较新”推导出任意 RDMA / NVLink / 多机组合都已经被保护。[^attestation]

这一层在本篇只要求认识概念，不要求搭建平台。它也不证明应用逻辑正确、模型输出真实或服务永不宕机。

## 8. 一次设计评审，留下哪些可验证的东西？

下面是建议的验收矩阵，**不是本文已执行的线上或硬件实验**。测试用非敏感样本、隔离环境与可恢复的测试密钥，不对生产密钥执行销毁实验。

| 测试 | 应观察到什么 | 能排除的错误理解 |
|---|---|---|
| 错误服务端身份 / 缺失客户端凭证 | 在预期认证边界拒绝 | “建立了加密通道就算安全” |
| 合法身份访问别的租户 | 业务授权拒绝且审计可定位 | “mTLS 替代 ACL” |
| 更改载荷、块位置或可信预期 AAD | 拒绝认证或对象完整性检查 | “tag 与对象上下文无关” |
| 新版本轮换后冷恢复旧备份 | 通过正确历史包装恢复 | “新数据能读等于历史数据也能读” |
| KMS 断连、限流、缓存到期 | 有界失败 / 重试，不降级明文 | “KMS 故障自动关闭加密” |
| 对已配置加密的真实 RDMA 路径验收 | 策略、硬件计数器、对端解密证据一致 | “控制面 TLS 就是数据面证据” |

RDMA / NIC offload 可能让主机上的抓包点看到加密前或解密后的数据；某些旁路流量也不经过普通抓包路径。因此应先说明采集点，再组合端口镜像、设备能力与计数器、负向策略测试来论证。只凭“tcpdump 没看到明文”或“看到了明文”都不足以给整条数据路径定性。

性能评估分别记录不加密基线、数据面加密、加密加 KMS 冷启动、稳态缓存与轮换期间的数据；比较吞吐、CPU、内存带宽、GPU 空闲时间、失败与尾延迟。这里可以沿用 [[9.10 跨层性能归因：CPU、NUMA、PCIe、NIC、Switch、RDMA 与 NVMe 的 P99]] 的边界归因方法，因为新成本可能落在 CPU、内存、PCIe、RNIC 或密钥服务，而不一定是网络本身。

## 9. P2 学到这里就够了

能用一张图回答下面三组问题，就可以回到 Hash / Integrity 和高性能数据路径主线。

**第一组：边界。** 哪些位置有明文？TLS 在哪里终止？哪个进程持有 DEK？RNIC 发出的到底是明文载荷还是受独立机制保护的载荷？

**第二组：轮换。** 这次是改 KMS 新版本、rewrap，还是更换 DEK 重加密？旧备份依赖哪些密钥？客户端缓存会怎样影响撤销？

**第三组：正确性。** tag 通过能证明什么，不能证明什么？如何防错租户、错代次、截断与回滚？密钥服务不可用时会不会静默降级？

> [!summary] 一句话收口
> **TLS 保护通道，mTLS 补充双向身份认证；DEK 保护数据，KEK 保护 DEK，KMS 管理其使用。轮换必须讲清历史对象与恢复语义，GPU / RDMA 必须单独核对真实的数据面边界。**
