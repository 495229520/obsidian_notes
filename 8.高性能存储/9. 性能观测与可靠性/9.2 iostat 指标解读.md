# iostat 指标解读

> `iostat -x` 是块设备的周期体检表。它把内核累计计数器换算成速率、平均队列长度、平均等待时间和忙碌比例。它适合发现“哪块设备、哪类请求、从什么时候开始异常”，但不能单独证明异常发生在 NAND、驱动、文件系统还是应用。

前置：[[1.2 Page Cache 命中与未命中]]（哪些请求不会到块层）、[[1.7 块层与 blk-mq]]（队列、合并与 tag）、[[9.1 fio Benchmark Matrix]]（如何制造受控负载）。

---

## 1. iostat 读的是计数器差分

Linux 块层为每个设备维护累计统计，`iostat` 主要读取 `/proc/diskstats` 和 sysfs，再用相邻两次采样的差分除以时间间隔【实现】：

```text
内核累计计数器(t0) ─┐
                     ├─ 差分 / Δt ─> r/s、w/s、await、aqu-sz、%util
内核累计计数器(t1) ─┘
```

推荐从一秒采样开始：

```bash
iostat -x -y 1
```

- `-x`：输出扩展设备指标；
- `-y`：跳过“开机以来”的第一份报告，避免把长期累计平均值当成当前状态；
- `1`：每秒采样。毛刺比 1 秒短时，平均值仍会稀释，需要 [[9.4 eBPF biolatency biosnoop]] 或 [[9.3 blktrace 与块层生命周期]]。

【前提】字段名随 sysstat 版本和内核支持变化。旧版本可能显示 `avgqu-sz`，新版本常显示 `aqu-sz`；discard、flush 列也可能缺失。保存报告时同时记录 `iostat -V`。

## 2. 指标从哪一层产生

![[图片/SVG/8_9_9_2_1.svg|900]]

图中的核心关系是：**速率描述完成了多少，队列描述积压了多少，await 描述平均等了多久，%util 只描述采样期内是否一直有请求在途。** 四类指标必须组合解释。

`iostat` 的观测边界在块设备层【事实】：

- Page Cache 命中的读不会形成块请求，所以不计入 `r/s`；
- buffered write 通常先修改内存脏页，真正的 `w/s` 可能由后台 writeback 线程稍后产生；
- 文件系统锁、应用线程池排队、用户态拷贝时间不在 `await` 内；
- 对本地 NVMe，dispatch 到 completion 的时间在设备统计里；
- 对网络块设备，客户端看到的等待可能包含网络与服务端；对 NFS/SMB 文件 IO，客户端可能根本没有对应块设备。

## 3. 第一组：完成速率与请求大小

| 指标 | 含义 | 判读要点 |
| --- | --- | --- |
| `r/s`、`w/s` | 每秒完成的读、写请求数 | 接近 IOPS；是块层合并后的设备请求，不一定等于应用调用次数 |
| `rkB/s`、`wkB/s` | 每秒读取、写入的数据量 | 与 `r/s × rareq-sz`、`w/s × wareq-sz` 量级相符 |
| `rareq-sz`、`wareq-sz` | 平均读、写请求大小 | 大顺序 IO、预读和合并会抬高它 |
| `rrqm/s`、`wrqm/s` | 每秒被合并的读、写请求数 | 相邻请求在块层合并；NVMe + `none` 下可能很低 |
| `%rrqm`、`%wrqm` | 合并请求占比 | 只说明合并行为，不直接代表性能好坏 |
| `d/s`、`dkB/s` | discard 速率与数据量 | TRIM、文件删除或空间回收可能触发 |
| `f/s` | flush 请求速率 | 与 `fsync`、日志提交和设备写缓存语义相关 |

### 3.1 应用 IO 次数不等于设备 IO 次数

三种机制会改变计数【事实】：

1. **Page Cache 命中**：应用 `read()` 完成，但设备 `r/s` 不增加；
2. **合并**：多个相邻 bio 合成一个 request，设备 IOPS 小于上层请求数；
3. **拆分**：超过设备最大请求大小或跨越映射边界时，一个上层 IO 变成多个设备请求。

因此不能直接拿应用 QPS 除以 `r/s` 推导“每请求一次磁盘 IO”。先确认缓存命中、请求大小和文件布局。

## 4. 第二组：await 与排队

### 4.1 `r_await`、`w_await`

`r_await` / `w_await` 是读 / 写请求从进入被统计的块设备队列到完成的平均时间，单位毫秒【事实】。它通常包含：

```text
块层或调度器排队 + 驱动/传输等待 + 设备执行 + 完成回传
```

它不包含请求到达块层之前的文件系统锁、Page Cache 命中处理、应用队列，也不等于 SSD 内部 NAND 访问时间。

旧版 `await` 把读写合在一起。读写延迟差异大时，合并均值会隐藏问题，应优先看 `r_await` 和 `w_await`。

### 4.2 `aqu-sz`

`aqu-sz` 是采样区间内设备队列中请求数的时间平均【事实】。可把它理解成“队列长度曲线下面积 ÷ 采样时间”，其中通常包含正在服务的请求。

利特尔法则提供量级校验：

$$
aqu\mbox{-}sz \approx (r/s + w/s + d/s) \times await_{weighted} / 1000
$$

`await` 以毫秒计。flush、不同请求类型、采样边界和分层设备会带来偏差，所以这里只用于检查数量级【前提】。

### 4.3 为什么平均 await 会掩盖毛刺

一秒内若 999 个请求耗时 100 μs，另 1 个耗时 100 ms，平均值约 200 μs；那个 100 ms 请求对同步业务仍可能造成超时。`iostat` 只有汇总均值，没有延迟分布【事实】。尾延迟要看 fio 直方图、eBPF 直方图或单请求追踪。

## 5. 第三组：`%util` 不是通用饱和度

`%util` 近似表示采样区间内，设备至少有一个 IO 在途的时间占比【事实】：

$$
\%util \approx \frac{\Delta io\_ticks}{\Delta time} \times 100\%
$$

对同一时刻只能有效处理一个请求的设备，接近 100% 常与饱和相符。多队列 NVMe、RAID、device-mapper 和网络块设备可以并行处理多个请求；`%util=100%` 只说明队列一直非空，不能说明所有通道、队列或链路都已用满【前提】。

判断 NVMe 是否进入饱和区，应联合观察：

- 继续提高 fio QD 时，IOPS / 带宽是否停止增长；
- `aqu-sz` 是否继续增加；
- `r_await` / `w_await` 和 p99 是否随队列增长；
- CPU、PCIe、NUMA、IRQ 与设备温度是否先到上限；
- SMART 是否显示温控、介质错误或持续 GC。

> [!warning] 不要使用 `svctm` 做根因分析
> 旧版 iostat 的 `svctm` 是从聚合计数推导的平均服务时间，面对并行设备不成立，新版 sysstat 已移除。需要设备阶段时间时，用 blktrace 的 dispatch-to-complete、eBPF block tracepoint 或设备遥测。

## 6. 组合判读：从现象到下一步

单列没有结论。下面的组合只给出**候选机制**，不是自动诊断。

| 现象 | 可能机制 | 下一步验证 |
| --- | --- | --- |
| `r/s` 上升，`r_await` 稳定，`aqu-sz` 同比例上升 | 设备仍在有效扩展并行度 | 继续小步提高 QD，找吞吐拐点 |
| IOPS 不再增长，`aqu-sz` 和 await 持续上升 | 最慢层已到服务上限，新增请求只排队 | fio 降 QD；blktrace 拆 Q→D 与 D→C |
| `%util=100%`，await 仍低且 IOPS 随 QD 增长 | 多队列设备处于持续忙碌但未必饱和 | 看吞吐曲线、CPU、PCIe 与队列分布 |
| `w_await` 周期性尖峰，`wkB/s` 呈锯齿 | 脏页回写、日志提交、SSD GC 或节流 | 看 `/proc/vmstat`、SMART、blktrace |
| `rrqm/s` 高、`rareq-sz` 变大、`r/s` 下降但 BW 上升 | 预读或块层合并把小请求变成大请求 | 对照应用请求统计与 readahead 设置 |
| fio clat 高，但本地物理盘 await 低 | 延迟在块层之前、虚拟层、网络或远端 | 查文件系统、dm 设备、RPC、服务端 |
| 应用读吞吐高，设备 `r/s≈0` | Page Cache 命中 | 用 `mincore`、缓存冷启动或 `direct=1` 验证 |
| `d/s` 突增并伴随写延迟 | discard 与前台写争用 | 检查挂载 `discard`，对比定时 `fstrim` |

### 6.1 一次受控 QD 扫描

使用 [[9.1 fio Benchmark Matrix]] 的 4 KiB 随机读，依次扫描 QD 1、8、32、128，同时运行：

```bash
iostat -x -y 1
```

预期分成三段【实践】：

1. **浅队列**：QD 增加，IOPS 近似增加，await 变化小；
2. **平台区**：IOPS 增量变小，`aqu-sz` 和 p99 开始抬升；
3. **过载区**：IOPS 基本不变，新增 QD 主要变成排队时间。

这条曲线比单独的 `%util` 更接近“设备在什么并发下饱和”。

## 7. 多层设备与网络存储

### 7.1 先画设备栈

`lsblk` 可以显示块设备父子关系：

```bash
lsblk -o NAME,TYPE,MAJ:MIN,PKNAME,FSTYPE,MOUNTPOINTS
```

LVM、dm-crypt、multipath、md RAID、容器卷都会增加统计层【实现】。上层 `dm-0` 的 await 包含映射与下层等待；物理盘指标则只描述各自收到的请求。排查时同时采集逻辑设备和叶子设备，不能把两个层级的 IOPS 相加后当成业务量。

### 7.2 网络存储的观测边界

| 类型 | 客户端 iostat | 缺失的层级 |
| --- | --- | --- |
| NVMe/TCP、iSCSI | 可见客户端块设备端到端等待 | TCP 重传、target 排队、target 物理盘需另采 |
| NVMe/RDMA | 可见客户端块设备等待 | RDMA 拥塞、CQ 处理、target 端设备 |
| NFS、SMB | 通常无对应客户端块设备 | RPC、网络、服务端文件系统与块设备 |
| Ceph RBD | 可见 RBD 或映射后的块设备，取决于接入方式 | OSD 网络、复制/EC、各 OSD 盘 |

【事实】客户端 `await` 高、服务端物理盘 `await` 低并不矛盾。差值可能在客户端队列、TCP/RDMA 传输、服务端线程池、复制确认或元数据路径。需要把时间线对齐，再看 `nfsstat` / 协议指标、`ss -ti`、NIC 丢包与重传、服务端 iostat。延迟分解框架见 [[5.4 延迟分解方法论]]。

## 8. 进程、CPU 与内存的交叉观测

`iostat` 只能说明设备发生了什么，不能说明谁发起。最小联动组合：

```bash
iostat -x -y 1       # 设备：量、队列、平均等待、忙碌时间
pidstat -d 1         # 进程：谁在读写、谁被 IO 阻塞
vmstat 1             # 系统：run queue、blocked、swap、CPU iowait
```

三点边界【事实】：

- CPU `iowait` 是 CPU 空闲且系统有未完成块 IO 的时间，不是“设备利用率”，也不能归因到单个进程；
- 进程发出 buffered write 后可能很快返回，真正写盘的是内核 writeback 线程；
- 容器内看到的设备和宿主机叶子设备可能不是同一层，采集位置要记录。

## 9. Modern C++：从 `/proc/diskstats` 计算两个核心量

下面只读取稳定的基础字段，用 RAII 管理输入文件。它演示 `%util` 与 `aqu-sz` 的来源，不替代 sysstat 对设备名、热插拔、discard 和单位的完整处理。

```cpp
#include <fstream>
#include <sstream>
#include <stdexcept>
#include <string>

struct DiskCounters {
    std::string name;
    unsigned long long io_ms{};
    unsigned long long weighted_io_ms{};
};

DiskCounters read_diskstats(const std::string& wanted) {
    std::ifstream input{"/proc/diskstats"};  // RAII：离开作用域自动关闭
    if (!input) {
        throw std::runtime_error{"cannot open /proc/diskstats"};
    }

    for (std::string line; std::getline(input, line);) {
        std::istringstream row{line};
        unsigned major{}, minor{};
        DiskCounters out;
        unsigned long long reads{}, reads_merged{}, sectors_read{}, read_ms{};
        unsigned long long writes{}, writes_merged{}, sectors_written{}, write_ms{};
        unsigned long long in_flight{};

        if (row >> major >> minor >> out.name
                >> reads >> reads_merged >> sectors_read >> read_ms
                >> writes >> writes_merged >> sectors_written >> write_ms
                >> in_flight >> out.io_ms >> out.weighted_io_ms;
            row && out.name == wanted) {
            return out;
        }
    }
    throw std::runtime_error{"device not found: " + wanted};
}

struct Derived {
    double util_percent;
    double average_queue;
};

Derived derive(const DiskCounters& a, const DiskCounters& b,
               double elapsed_ms) {
    if (elapsed_ms <= 0 || b.io_ms < a.io_ms ||
        b.weighted_io_ms < a.weighted_io_ms) {
        throw std::runtime_error{"invalid sample interval or reset counters"};
    }
    return {
        100.0 * static_cast<double>(b.io_ms - a.io_ms) / elapsed_ms,
        static_cast<double>(b.weighted_io_ms - a.weighted_io_ms) / elapsed_ms
    };
}
```

`io_ms` 在设备至少有一个请求进行时累加；`weighted_io_ms` 按在途请求数加权累加【实现】。后者除以区间毫秒数，得到平均队列长度的形状。

## 10. 陷阱与误区

> [!warning] 常见错误
> 1. 把第一份“开机以来”的平均值当成当前一分钟状态。
> 2. 把 `await` 当成纯设备服务时间，忽略排队、驱动和网络块传输。
> 3. 把 NVMe 的 `%util=100%` 直接翻译成“没有剩余吞吐”。
> 4. 用一秒平均值判断毫秒级 p99 毛刺。
> 5. 只看逻辑卷，不看下层物理盘；或把多层计数重复相加。
> 6. 在 NFS 客户端找本地磁盘瓶颈，遗漏 RPC、网络和服务端。
> 7. 忽略 Page Cache，看到设备 `r/s=0` 就认定应用没有读数据。
> 8. 继续使用 `svctm` 估算现代并行设备的服务时间。

## 11. 关键结论

| 结论 | 性质 |
| --- | --- |
| iostat 用累计块设备计数器的区间差分生成速率和平均值 | 实现 |
| `r/s`、`w/s` 是设备层完成请求，不等于应用系统调用次数 | 事实 |
| await 包含块层排队到完成，不包含块层之前的应用与文件系统等待 | 事实 |
| `aqu-sz` 是平均在途请求数，可用利特尔法则做量级校验 | 事实 |
| `%util` 表示队列非空的忙碌时间，多队列设备上不等于饱和度 | 前提 |
| 吞吐封顶、队列增长、await 上升的组合比单列阈值更有诊断力 | 实践结论 |
| iostat 没有延迟分布，不能单独定位 p99 毛刺 | 事实 |
| 网络存储必须同时观察客户端、网络、服务端和服务端叶子设备 | 实践结论 |
