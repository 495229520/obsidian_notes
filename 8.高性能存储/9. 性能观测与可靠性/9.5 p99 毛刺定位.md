# p99 毛刺定位

> 前四篇给了工具：[[9.1 fio Benchmark Matrix]] 造负载、[[9.2 iostat 指标解读]] 看设备汇总、[[9.3 blktrace 与块层生命周期]] 拆块层事件、[[9.4 eBPF biolatency biosnoop]] 看分布与单请求。本篇把它们串成一套**方法**：怎么定位 p99 毛刺。核心是一句话——**均值告诉你系统是否健康，p99 告诉你最坏 1% 的请求经历了什么**。在 [[8.7 DataLoader 与 GPU 空闲归因]] 的训练场景里，这两个量不是抽象指标：p99 毛刺直接翻译成 GPU 利用率的周期性凹陷。定位毛刺的第一原理不是抓包，是**先刻画（周期、幅度、相关性），再分层二分**。
>
> 沿用全章那个负载：**8 卡小文件训练 + 每 30 分钟一次 checkpoint，数据在共享存储上**。它的 p99 毛刺来源丰富，正好当靶子。

前置：[[9.2 iostat 指标解读]]（为什么平均 await 掩盖毛刺）、[[9.3 blktrace 与块层生命周期]]（Q→D 与 D→C 分段）、[[9.4 eBPF biolatency biosnoop]]（延迟直方图与单请求证据）、[[8.7 DataLoader 与 GPU 空闲归因]]（毛刺如何变成空泡）。

## 1. 毛刺是什么，为什么均值看不见

p99 是一个**次序统计量**：把窗口内所有请求延迟排序，第 99 百分位的那个值——只有 1% 的请求比它更慢【事实】。毛刺（spike / tail latency）就是这个 p99（或 p999）远高于中位数的现象。

均值看不见毛刺，是算术决定的【事实】。一次 100 ms 的慢请求混进 999 次 1 ms 的快请求，平均只被抬高约 0.1 ms——[[9.2 iostat 指标解读]] §4.3 讲的「平均 await 掩盖毛刺」就是这个：`iostat` 报的是采样区间的平均值，一个短促的尖峰会被整段稀释掉。所以**用均值做 SLA、用均值调优，会系统性地漏掉最伤用户的那部分**。

毛刺在不同场景翻译成不同的痛【因果】：

- 在线服务：p99 是用户等待的上界，是 SLA 的落点；
- 训练：p99 是**取一个 batch 的最坏耗时**。只要它超过预取队列存货能撑的时间（[[8.7 DataLoader 与 GPU 空闲归因]] §3），就是一次 GPU 空泡。于是 p99 毛刺 = GPU 利用率凹陷——**尾延迟和 GPU 利用率是同一枚硬币**。

![p99 毛刺定位方法全景：① 对齐时间线——GPU 利用率的周期性凹陷与取数 p99 的尖峰在时间上对齐（标注周期 T），说明凹陷↔尖峰强相关，先量周期与幅度别急着抓包；② 周期指纹表——每 epoch 一次对应 shuffle 齐读的 incast、每 N 分钟规律对应 checkpoint 齐射、不规则成簇对应 SSD GC/温控、数据集大于内存后每步对应页缓存悬崖、与采样点对齐对应监控自身、随机无周期对应排队争用；③ 分层二分梯——端到端 p99 自上而下逐层拆：应用/预取队列（profiler data_time）、文件系统/元数据（nfsstat）、页缓存（命中率）、块层 Q→D 与 D→C（blktrace btt）、设备（biolatency，GC/温控）、网络（nstat 重传/PFC-ECN），口径不同不能直接相减；④ 尾延迟放大器——incast 多打一打爆缓冲、fan-out 一打多取 max（P(全≤t)=P(单≤t)的N次方，N=100 时仅约37%全在门内）、重试放大把一次慢变两次慢；底部为定位流程：刻画→对号→二分→验证](../../图片/SVG/p99毛刺-周期归因与分层二分.svg)

## 2. 第一步：刻画毛刺（周期、幅度、相关性）

新手看到毛刺的第一反应是「上 eBPF 抓包」。这往往过早——**没先刻画就抓包，等于在噪声里捞针**。刻画三件事，每一件都能砍掉大半嫌疑范围【实践】：

1. **周期**：毛刺是**周期性**还是**随机**？周期性的话周期 T 是多少？这是最有信息量的一维——一个规律出现的毛刺，其周期往往直接指向某个定时事件（下节的指纹表）。
2. **幅度**：p99 比基线高多少倍？p999、p9999 怎样？幅度决定它是否值得追（p99 高 2 倍 vs 高 100 倍是两回事），也决定它会不会击穿队列变成空泡。
3. **相关性**：毛刺和什么事件在时间上对齐？和 epoch 边界？和 checkpoint？和另一台机器的 GC？（上图①：GPU 利用率的凹陷与取数 p99 的尖峰对齐，就是一条强相关线索。）

刻画用的是**低开销的聚合观测**，不是逐请求抓取：`biolatency`（[[9.4 eBPF biolatency biosnoop]]）周期输出直方图看分布形状与周期，配合业务侧的 p99 时间序列。只有确定了周期和相关性、锁定复现窗口后，才对那个窗口上 `biosnoop` / `blktrace` 抓单请求证据——这是 9.4 §7 「从汇总异常到单请求」的下钻顺序在毛刺定位上的应用。

## 3. 周期对号：常见毛刺源的「指纹」

周期本身就是指纹。把观测到的周期特征对号入座（上图②），能在动工具之前先把嫌疑收敛到一两层【实践】：

| 周期特征 | 疑似源 | 机制 / 证据在哪层 |
| --- | --- | --- |
| 每个 epoch 一次 | shuffle 后齐读 | 多 worker 同时打存储 = incast，尖峰在网络 / 元数据层（[[7.2 元数据路径瓶颈]]、[[4.7 PFC ECN 与 DCQCN]]） |
| 每 N 分钟规律 | checkpoint（[[8.6 Checkpoint 同步异步分片]]） | N-rank 齐射写，抢带宽 + incast 突发；证据在网络与存储写路径 |
| 不规则、成簇 | SSD GC / 温控（[[3.5 GC 写放大与 Over-Provisioning]]） | 设备内部回收/降频，D→C 尖峰（[[9.3 blktrace 与块层生命周期]] §8.2） |
| 数据集 > 内存后每步都有 | 页缓存悬崖（[[1.2 Page Cache 命中与未命中]]） | 命中率塌，每 batch 从命中变冷读，块请求量陡增 |
| 与监控采样点对齐 | 监控 / 日志自身 | 观测器自己制造毛刺（[[9.4 eBPF biolatency biosnoop]] §6.2 的 ring buffer 消费、日志 fsync） |
| 随机、无明显周期 | 排队 / 争用 | QD 过深或抢 CPU / softirq，此时**均值往往也升**，不只是尾部（[[9.2 iostat 指标解读]] §8） |

最后一行的判据很有用【方法】：**如果均值和尾部一起升**，多半是排队/争用（负载压过了服务能力），要降 QD 或加服务能力；**如果均值不动、只有尾部尖**，多半是间歇性事件（GC、incast、监控），要去抓那个事件。这条「均值动没动」的岔路，在下一步分层之前就能定大方向。

## 4. 第二步：分层二分定位

刻画之后，把**端到端 p99 自上而下拆到层**，每层配一把尺，找**尖峰第一次出现的那一层**（上图③）。这是把 9.1–9.4 的工具按层排好：

| 层 | 尺（工具） | 这层的边界 / 关注 |
| --- | --- | --- |
| 应用 / 预取队列 | profiler `data_time`（[[8.7 DataLoader 与 GPU 空闲归因]] §5） | 是不是根本没到存储——空泡在队列这端就产生了 |
| 文件系统 / 元数据 | `nfsstat`、`stat` 计数（[[7.2 元数据路径瓶颈]]） | 小文件 `open`/`stat` 尖峰，海量元数据 RPC |
| 页缓存 | 命中率、第二 epoch 是否变快（[[1.2 Page Cache 命中与未命中]]） | 命中就不进块层，miss 才有块请求——毛刺可能只在冷读上 |
| 块层 Q→D \| D→C | `blktrace` + `btt`（[[9.3 blktrace 与块层生命周期]]） | Q→D 是软件排队，D→C 是驱动以下——分清毛刺在排队还是在设备 |
| 设备 | `biolatency`（[[9.4 eBPF biolatency biosnoop]]） | 介质本身：GC / 温控 / 掉速（[[3.5 GC 写放大与 Over-Provisioning]]） |
| 网络（网络存储） | `nstat` 重传、PFC/ECN 计数（[[5.2 Transport TCP vs RDMA]]、[[4.7 PFC ECN 与 DCQCN]]） | D→C 里可能整段跨了网络到 target 与远端介质 |

二分的纪律有两条【事实】：

- **口径不同不能直接相减**（[[9.4 eBPF biolatency biosnoop]] 全篇的主题）。`biolatency` 测的是 `block_rq_issue → complete`（≈ D→C），不含 VFS、页缓存、应用排队，也不含 complete 之后线程被唤醒拿到 CPU 的时间。业务侧 p99 减不去 biolatency 的 p99——它们的起止点不一样。分层是为了**定位尖峰第一次出现在哪层**，不是为了让各层数字相加等于总数。
- **网络存储的 D→C 是复合的**（[[9.3 blktrace 与块层生命周期]] §8.3、[[9.4 eBPF biolatency biosnoop]] §8）。客户端看到的一次「块请求慢」，可能是客户端块层、传输、交换网络、target 协议线程、target 物理盘任意一段慢。客户端 `biolatency` 右移只证明端到端变慢，要在 target 侧也采一份叶子设备的分布才能定责。

## 5. 尾延迟的放大器：为什么分布式让毛刺更毒

单机的毛刺已经够烦，分布式会把它**放大**——这是 AI 存储/训练场景 p99 特别难缠的根因（上图④）【事实】：

**① incast（多打一）**。epoch shuffle 后所有 worker 齐读、checkpoint 时所有 rank 齐写，都是「多个发送方同时打一个出口（交换机/机头）」。出口缓冲瞬间溢出 → 丢包 → 重传，或触发 PFC 反压（[[4.7 PFC ECN 与 DCQCN]]）——一次齐射就是一次尾延迟尖峰。这解释了 §3 指纹表里两个最常见的周期毛刺。

**② fan-out（一打多，取 max）**。一个上层请求要打 N 个后端（副本、EC 分片、多个元数据分片），必须**等最慢的那个返回**。于是整请求的延迟分布是各后端的**最大值**分布。记单后端延迟 CDF 为 F_one，N 个独立后端全部在 t 内返回的概率是：

$$
F_{all}(t) = \left[ F_{one}(t) \right]^{N}
$$

代入一组数字看它多毒：单后端 p99 = q（即 F_one(q) = 0.99），fan-out 到 N=100，则整请求在 q 内完成的概率只有 0.99 的 100 次方 ≈ 0.37——**约 63% 的请求会撞上至少一个后端的尾部**。也就是说，**单后端"1% 的慢"被 fan-out 放大成整请求"63% 的慢"**。这就是 Dean & Barroso "The Tail at Scale" 的核心：规模本身是尾延迟放大器。对策是对冲请求（hedged request，多发一份取先到）、或让后端的尾部足够短。

**③ 重试放大**。超时重发把「一次慢」变成「一次慢 + 一次重来」，尾部更长，还更难和真实的慢区分开。重试要有退避和上限，否则在拥塞时火上浇油（把 incast 变成 incast²）。

三个放大器叠加，就是为什么同一块盘单机测着 p99 挺好，一上分布式训练集群就毛刺不断——**毛刺不是被谁制造的，是被规模放大的**。

## 6. Modern C++：滑动窗口 p99 + 毛刺检测器

把 §2 的「刻画」自动化：一个 log2 桶直方图（复用 [[9.4 eBPF biolatency biosnoop]] §5.1 的思路，固定内存覆盖很宽范围）算窗口 p99，一个检测器把窗口 p99 和滚动基线比，超过 k 倍就标记并抓上下文——**window_id 序列就是周期，p99/baseline 就是幅度**，正好喂给 §2 的刻画。

```cpp
#include <array>
#include <bit>
#include <cstdint>
#include <optional>

// log2 桶延迟直方图:固定内存覆盖很宽范围(9.4 §5.1 的取舍)
class LatencyHistogram {
public:
    void record(std::uint64_t ns) {
        // 落到 [2^b, 2^{b+1});bit_width(4)=3 → b=2 → 桶 [4,8)
        const std::size_t b = ns < 2 ? 0 : static_cast<std::size_t>(std::bit_width(ns) - 1);
        ++bucket_[b < kBuckets ? b : kBuckets - 1];
        ++count_;
    }

    // 返回 p 分位所在桶的上界(ns);诚实起见只给范围,不伪造精确值(9.4 §5.1)
    std::uint64_t percentile_upper(double p) const {
        const std::uint64_t target = static_cast<std::uint64_t>(p * static_cast<double>(count_));
        std::uint64_t acc = 0;
        for (std::size_t b = 0; b < kBuckets; ++b) {
            acc += bucket_[b];
            if (acc >= target) return std::uint64_t{1} << (b + 1);
        }
        return std::uint64_t{1} << kBuckets;
    }

    std::uint64_t count() const { return count_; }
    void reset() { bucket_.fill(0); count_ = 0; }

private:
    static constexpr std::size_t kBuckets = 48;   // 覆盖到 ~2^48 ns ≈ 3 天,足够
    std::array<std::uint64_t, kBuckets> bucket_{};
    std::uint64_t count_ = 0;
};

// 毛刺检测:每窗口算一次 p99,与 EWMA 基线比;超 k 倍则标记并抓读数
class SpikeDetector {
public:
    struct SpikeEvent {
        std::uint64_t window_id;    // ★ 序列揭示周期(§2 刻画的第一维)
        std::uint64_t p99_ns;       // ★ 幅度
        double        baseline_ns;
    };

    explicit SpikeDetector(double k = 3.0, double alpha = 0.2)
        : k_{k}, alpha_{alpha} {}

    // 一个观测窗口结束时调用;返回本窗口是否为毛刺
    bool close_window(const LatencyHistogram& win, std::uint64_t window_id) {
        const auto p99 = static_cast<double>(win.percentile_upper(0.99));
        const bool spike = baseline_ > 0 && p99 > k_ * baseline_;
        if (spike) last_ = SpikeEvent{window_id, static_cast<std::uint64_t>(p99), baseline_};
        // ★ 基线只用「非毛刺」窗口更新,否则毛刺会把基线自己抬上去,越测越钝
        if (!spike)
            baseline_ = baseline_ == 0 ? p99 : alpha_ * p99 + (1 - alpha_) * baseline_;
        return spike;
    }

    std::optional<SpikeEvent> last_spike() const { return last_; }

private:
    double k_, alpha_;
    double baseline_ = 0;
    std::optional<SpikeEvent> last_;
};
```

**逐段讲解**【实现】：

- **log2 桶的诚实**：`percentile_upper` 只返回 p99 落在哪个桶的上界，不伪造一个精确微秒值——这是 [[9.4 eBPF biolatency biosnoop]] §5.1 「报告应写成 p99 落在 256–511 μs 桶」的代码版；固定 `kBuckets` 个桶用 O(1) 内存覆盖从纳秒到天的范围；
- **基线只用非毛刺窗口更新**：这是最容易写错的地方。如果毛刺窗口也参与 EWMA，几次大毛刺就会把基线抬高，检测器越测越钝、最后什么都报不出来——所以 `if (!spike)` 那行是关键的一票否决；
- **`SpikeEvent` 抓的正是刻画三要素**：`window_id` 的序列给出**周期**，`p99_ns / baseline_ns` 给出**幅度**，把它和业务事件时间轴对齐就得到**相关性**——§2 的三件事全在这里落地；
- **热路径纪律**：`record` 只做一次 `bit_width` 和一次自增，无锁无分配，可以直接放在请求完成回调里；真放进生产采集器时，按 [[9.4 eBPF biolatency biosnoop]] §5.2 的做法每 CPU 一份直方图，读取时再合并，避免缓存行争用。

## 7. 定位流程模板（可复现）

把方法固化成一张可照着走的表【方法】：

```text
① 刻画   biolatency 周期直方图 + 业务 p99 时间序列
         → 周期?幅度?和什么对齐?   均值也升还是只有尾部升?
② 对号   周期特征查指纹表(§3) → 收敛到一两层
③ 二分   端到端 p99 自上而下拆层(§4),每层配尺
         找尖峰"第一次出现"的层;网络存储要在 target 侧也采一份
④ 验证   动"一个"变量(关 checkpoint / 数据集扩到 > 内存 / 降 QD / 换本地盘)
         看毛刺是否消失 → 消失即根因;别一次动多个变量
```

第 ④ 步的「一次只动一个变量」是实验纪律【实践】：毛刺定位最容易犯的错是同时改三样，然后不知道是哪样起了作用。每次只动一个，对照毛刺时间序列，才能建立因果而非巧合。

保存可审计结果（沿用 [[9.4 eBPF biolatency biosnoop]] §7.4 的模板，补上毛刺专有字段）：

```text
主机 / 内核 / 工具版本与 attach 点：
毛刺周期 T、幅度(p99 / 基线倍数)、对齐的事件：
分层证据(每层 p99 所在桶、口径起止点)：
网络存储:client 与 target 两侧分布、重传/PFC 计数：
验证:改动的单一变量、改动前后毛刺时间序列：
```

## 8. 陷阱与误区

> [!warning] 常见错误
> 1. **用均值判断有没有毛刺**：均值天然稀释尖峰（§1、[[9.2 iostat 指标解读]] §4.3）——要看 p99/p999，不是 avg。
> 2. **没刻画就抓包**：先量周期和相关性能砍掉大半嫌疑（§2）；上来就 `biosnoop` 无过滤长跑，只会淹没自己还制造新毛刺。
> 3. **把分层 p99 直接相减**：各层口径起止点不同（§4、[[9.4 eBPF biolatency biosnoop]]）——分层是定位尖峰首现的层，不是做减法。
> 4. **网络存储只看客户端一张图**：客户端 D→C 是复合的（§4、§5），必须在 target 侧也采叶子设备分布才能定责。
> 5. **毛刺窗口污染基线**：EWMA 把毛刺也算进去 → 基线被抬高 → 检测器变钝（§6）；基线只用正常窗口更新。
> 6. **忽略 fan-out 的尾放大**：单后端 1% 的慢，fan-out 到 100 个后端能变成整请求 63% 的慢（§5）——规模本身是放大器。
> 7. **一次动多个变量做验证**：改完毛刺没了却不知道是哪一改起的作用（§7）——一次一个。
> 8. **忘了监控自己会制造毛刺**：与采样点对齐的毛刺，先怀疑观测器本身（§3、[[9.4 eBPF biolatency biosnoop]] §6.2）。

| 结论 | 性质 |
| --- | --- |
| 均值判健康、p99 判最坏 1%；均值天然稀释尖峰，做 SLA / 调优要用尾部 | 事实 |
| 训练场景 p99 毛刺 = GPU 利用率凹陷：尾延迟就是利用率（接 8.7） | 因果 |
| 方法第一步是刻画（周期 / 幅度 / 相关），不是抓包——周期本身是最强指纹 | 实践结论 |
| 均值也升 = 排队争用；均值不动只有尾升 = 间歇事件（GC/incast/监控） | 方法论 |
| 第二步分层二分：找尖峰"第一次出现"的层；口径不同不能相减 | 事实 |
| 网络存储的 D→C 是复合的，必须 client 与 target 两侧对采 | 事实 |
| 分布式三放大器：incast 打爆缓冲、fan-out 取 max、重试翻倍——规模放大尾部 | 事实 |
| fan-out 尾放大 F_all = F_one 的 N 次方：单后端 1% 慢 → N=100 时整请求 63% 慢 | 事实 |
| 检测器基线只用非毛刺窗口更新，否则越测越钝；验证一次只动一个变量 | 实现 / 实践 |
