# TRIM / Discard

> 块设备接口天生只有两个动词：读、写——没有"释放"。于是删除文件时，文件系统在自己的账本上把块标回空闲，而 SSD 的 FTL 对此一无所知，仍把那些旧数据当有效页搬来搬去。**TRIM/Discard 就是给块设备补上的第三个动词 `free()`**：主机告诉设备"这段 LBA 我不要了"，FTL 把对应映射标失效，GC 从此不再为死数据买单。它是把 [[3.6 空盘与稳态性能]] 里"稳态很慢"的盘往回拉的唯一常规手段。

前置：[[3.4 SSD FTL 与地址映射]]（L2P 映射、失效页从哪来）、[[3.5 GC 写放大与 Over-Provisioning]]（WAF = 1/(1−u)，本篇反复引用）。

---

## 1. 名词与背景：为什么"删了"设备不知道

先把三件事分开【事实】：

1. **`rm file` 删除的是目录项和 inode**，数据块只是在文件系统的空闲位图里标回可用——块里的字节原封不动；
2. **块设备接口（提交读/写请求的那层契约）没有"这块不用了"的语义**——HDD 时代不需要：覆盖写就地生效，无所谓块的生死；
3. **SSD 需要**：FTL 异地更新 + 整块擦除的模式下（[[3.4 SSD FTL 与地址映射]]），"哪些页是死的"直接决定 GC 要搬多少数据。没有失效信息，FTL 只能假设**所有写过的 LBA 都还有效**。

用内存分配器类比：文件系统像应用代码，FTL 像 `malloc` 的实现。TRIM 缺席时，等于应用从不调 `free()`——分配器眼里堆越"用"越满，压缩搬运（GC）越来越贵。TRIM 就是那句迟到的 `free()`。

一个具体后果：一块盘写满过一次再把文件全删掉，文件系统显示 99% 空闲，但**FTL 眼里它仍是一块 100% 满的盘**——随机写照样触发满盘级别的 GC，性能是 [[3.6 空盘与稳态性能]] 的稳态水平而不是空盘水平【事实】。

各协议的叫法（语义同类，Linux 内核统称 **discard**）【事实】：

| 层 | 名称 |
| --- | --- |
| ATA（SATA 盘） | TRIM（DATA SET MANAGEMENT 命令） |
| SCSI/SAS | UNMAP |
| NVMe | Dataset Management（DSM）命令的 **Deallocate** 属性 |
| Linux 块层 | `REQ_OP_DISCARD` 类型的 bio |

## 2. 端到端路径：一次删除怎么走到 FTL

![[图片/SVG/8_3_15_1.svg|900]]

对照上图，四层各干什么【事实】：

1. **用户态三个入口**：日常路径是 `rm`/`truncate`/`fallocate(FALLOC_FL_PUNCH_HOLE)`（释放文件中段空间）；`fstrim` 是"批量补发"工具；`blkdiscard` 绕过文件系统直接对整个块设备下发（逻辑清盘，[[3.6 空盘与稳态性能]] 预处理第一步）；
2. **文件系统**：把块标回空闲后，**发不发 discard 是个策略开关**——挂载了 `-o discard`（实时模式）就在释放时下发；默认不发，攒着等 `fstrim` 触发 `FITRIM` ioctl 时对"当前所有空闲段"整批下发；
3. **块层**：discard 作为 `REQ_OP_DISCARD` bio 走与读写同一条 blk-mq 管道，只带 LBA 范围不带数据；按设备上报的 `discard_granularity`（设备接受的最小对齐单位）拆分对齐。**中间每一层堆叠设备（LVM、dm-crypt、md RAID）都必须选择透传它**，任何一层不支持，discard 就静默消失（§7 排障要点）；
4. **设备**：NVMe 驱动把范围打包成 DSM Deallocate 命令（一条最多 256 个 LBA 范围【事实】）。控制器只做一件事：**把 L2P 表里这些 LBA 的表项标为无效**。不擦 NAND——擦除仍由 GC 在自己的节奏里做。收益是异步兑现的：下一轮 GC 挑牺牲块时，这些页不再算有效页，u 下降，按 WAF = 1/(1−u) 传导为写放大下降。

一个容易被忽略的副作用【实现】：**读一个已 deallocate 的 LBA 不再触碰 NAND**——控制器查表发现无映射，直接按预定值返回（通常全零）。这就是 [[3.6 空盘与稳态性能]] §1 说的"读零快路径"：对刚 TRIM 过的区域测读性能，测的是控制器查表速度，不是介质。

## 3. 实时 vs 批量：两种下发策略的取舍

| 维度 | 实时（`-o discard`） | 批量（`fstrim` / `fstrim.timer`） | 性质 |
| --- | --- | --- | --- |
| 触发时机 | 每次块释放（删文件、日志提交后） | 手动或定时器（发行版默认每周） | 事实 |
| 请求形态 | 碎：跟随删除粒度，量大且散 | 整：空闲段合并成大范围，一次发完 | 事实 |
| 对前台 IO 的干扰 | 持续小干扰，删除密集时可见延迟毛刺 | 集中在执行窗口内，可挑低峰期 | 实践 |
| 失效信息时效 | FTL 实时拿到，GC 收益最快 | 两次 fstrim 之间 FTL 账本滞后 | 事实 |
| 空间回收（thin 卷/云盘） | 实时 | 滞后至多一个周期 | 事实 |

【取舍】通用建议是**批量为主**：现代发行版默认启用 `fstrim.timer`，每周一次对绝大多数负载够用；`-o discard` 留给两类场景——删除量巨大且持续（如数据库频繁 drop 表）、或 thin provisioning 卷要求空间及时归还（[[3.10 Namespace]] 的 NUSE 同款逻辑）。历史上还有第三个理由站在批量这边：早年部分 SATA 盘的 queued TRIM 实现有缺陷，内核 libata 至今维护着黑名单强制降级为非队列 TRIM（清空队列才能执行，代价大）——实时模式在这类盘上格外伤【实践】。

```bash
systemctl status fstrim.timer          # 定时器是否启用（多数发行版默认每周）
sudo fstrim -av                        # 立即对所有支持的挂载点执行, -v 打印回收量
findmnt -o TARGET,OPTIONS / | grep discard   # 检查是否挂了实时 discard
```

`fstrim -v` 输出的字节数读法【前提】：那是**本次向设备下发的范围总量**，不是"这次真的新释放了这么多"——ext4 会记住已 trim 过的组避免重复下发，XFS 则每次全量重发，同一台机器连跑两次数字可能差很远，不能当"垃圾产生速率"用。

## 4. 语义细节：hint、读返回值与安全性

三条最容易误读的语义边界【事实】：

1. **TRIM 是提示（hint），不是指令**。规范允许设备延迟、合并、甚至忽略 Deallocate。因此它不提供任何"数据已消失"的承诺——不能当擦除用；
2. **读已 deallocate LBA 的返回值有三档**，由 Identify Namespace 的 **DLFEAT** 字段上报：未定义（旧数据、零、任意值都合法）/ 全零 / 全一。要"读回必为零"的确定性语义，用 Write Zeroes 命令或确认 DLFEAT=001b；
3. **TRIM ≠ 安全擦除**。映射标失效后，旧数据仍躺在 NAND 里直到 GC 擦除，实验室手段可恢复。合规销毁走 Format NVM（Secure Erase / Crypto Erase）。

```bash
sudo nvme id-ctrl /dev/nvme0 | grep oncs      # bit 2 = 支持 DSM（Deallocate）
sudo nvme id-ns /dev/nvme0n1 -H | grep -A3 dlfeat   # 读已 deallocate 块的返回值语义
lsblk --discard                                # DISC-GRAN/DISC-MAX 非零 = 整条路径支持 discard
```

`lsblk --discard` 是排查第一站：它逐层显示每个块设备（含 dm/md 中间层）的 discard 粒度与上限，**哪一层显示为 0，discard 就死在哪一层**【实践】。

## 5. 对照实验：TRIM 到底救回多少稳态性能

实验设计（变量：是否 TRIM；控制：同盘、同预处理、同负载）：

```bash
# ⚠️ 毁灭性写入, 仅在测试盘上执行；完整预处理逻辑见 3.6
DEV=/dev/nvme0n1

# 共同起点：清盘 + 顺序填 2 遍 + 随机写压到稳态（判据同 3.6 §3）
sudo blkdiscard $DEV
sudo fio --name=fill --filename=$DEV --direct=1 --rw=write --bs=1M --iodepth=32 --loops=2
sudo fio --name=age --filename=$DEV --direct=1 --rw=randwrite --bs=4k --iodepth=32 \
         --time_based --runtime=1800

# A 组（无 TRIM）：直接测稳态随机写
sudo fio --name=A --filename=$DEV --direct=1 --rw=randwrite --bs=4k --iodepth=32 \
         --time_based --runtime=300 --output=A.json --output-format=json

# B 组（TRIM 一半地址空间后测同样负载, 写入范围限制在未 TRIM 的一半）
HALF=$(( $(sudo blockdev --getsize64 $DEV) / 2 ))
sudo blkdiscard --offset $HALF --length $HALF $DEV        # 后一半整段 deallocate
sudo fio --name=B --filename=$DEV --direct=1 --rw=randwrite --bs=4k --iodepth=32 \
         --size=$HALF --time_based --runtime=300 --output=B.json --output-format=json
```

**预期与解读**【实践】：B 组 IOPS 高于 A 组、p99 更平——被 TRIM 的一半让 FTL 的有效数据占比骤降，等价于临时把 OP 拉高了 50 个百分点（[[3.5 GC 写放大与 Over-Provisioning]] §3 的容量余量逻辑）。两个口径提醒：

- B 组效果会随继续写入**衰减**——空闲页被新写填回，账本重新变满；TRIM 买到的是一次性余量，不是永久提速；
- 对比时确认 fio 的写入范围没落进已 TRIM 区再读回验证数据——那部分读是"查表回零"，会把读延迟拉出虚假的漂亮数字（§2 副作用）。

## 6. Modern C++：把 PUNCH_HOLE 变成一次可观察的 discard

文件层的"局部删除"接口是 `fallocate(FALLOC_FL_PUNCH_HOLE)`：把文件中段的数据块还给文件系统（读该区域返回零，文件大小不变）。若挂载了 `-o discard`，这次释放会实时转成 discard 下发——这是**不碰裸设备、无破坏性**的最小观察路径：

```cpp
// punch_hole.cpp —— 在文件中间打洞，观察文件系统释放块（可选转成 discard）
// 编译: g++ -std=c++23 -Wall -Wextra -o punch_hole punch_hole.cpp
#include <fcntl.h>
#include <sys/stat.h>
#include <unistd.h>

#include <cerrno>
#include <print>
#include <system_error>
#include <utility>

class UniqueFd {
public:
    explicit UniqueFd(int fd = -1) noexcept : fd_(fd) {}
    ~UniqueFd() { if (fd_ >= 0) ::close(fd_); }

    UniqueFd(const UniqueFd&) = delete;
    UniqueFd& operator=(const UniqueFd&) = delete;
    UniqueFd(UniqueFd&& o) noexcept : fd_(std::exchange(o.fd_, -1)) {}
    UniqueFd& operator=(UniqueFd&& o) noexcept {
        if (this != &o) { if (fd_ >= 0) ::close(fd_); fd_ = std::exchange(o.fd_, -1); }
        return *this;
    }
    [[nodiscard]] int get() const noexcept { return fd_; }

private:
    int fd_;
};

[[nodiscard]] long blocks_of(int fd) {
    struct stat st{};
    if (::fstat(fd, &st) != 0) {
        throw std::system_error{errno, std::generic_category(), "fstat"};
    }
    return st.st_blocks;    // 实际占用的 512B 块数——打洞前后对比它
}

int main() {
    constexpr off_t kMiB = 1 << 20;
    UniqueFd fd{::open("hole_demo.bin", O_RDWR | O_CREAT | O_TRUNC, 0644)};
    if (fd.get() < 0) {
        throw std::system_error{errno, std::generic_category(), "open"};
    }

    if (::fallocate(fd.get(), 0, 0, 8 * kMiB) != 0) {   // 预分配 8 MiB 真实块
        throw std::system_error{errno, std::generic_category(), "fallocate(alloc)"};
    }
    std::println("打洞前: st_blocks = {}", blocks_of(fd.get()));

    // 把 [2 MiB, 6 MiB) 还给文件系统；KEEP_SIZE: 文件长度不变, 中段变洞
    if (::fallocate(fd.get(), FALLOC_FL_PUNCH_HOLE | FALLOC_FL_KEEP_SIZE,
                    2 * kMiB, 4 * kMiB) != 0) {
        throw std::system_error{errno, std::generic_category(), "fallocate(punch)"};
    }
    std::println("打洞后: st_blocks = {}（少 4 MiB 对应的块数）", blocks_of(fd.get()));
    return 0;
}
```

**关键点**：`st_blocks` 打洞后立刻减少——这证明的是**文件系统层**的释放；释放是否继续变成设备层的 discard，取决于挂载选项（`-o discard` 实时发；否则等下次 `fstrim` 扫到这段空闲区）。想亲眼确认下发，可同时开 `sudo nvme smart-log /dev/nvme0` 前后对比，或在测试环境用 `bpftrace` 挂 `tracepoint:block:block_rq_issue` 过滤 discard 请求【实践】。裸设备版的对应物是对块设备 fd 做 `BLKDISCARD` ioctl（`uint64_t range[2] = {offset, len}`）——`blkdiscard` 工具的内核入口就是它，毁灭性，此处不做成可运行示例。

## 7. 云盘、虚拟化与故障定位

**云盘/虚拟盘上 discard 的含义变了**【实现】：物理 SSD 上它优化的是 GC；云盘（EBS、云硬盘）与 thin 卷上它的主要作用是**归还已分配空间**——后端是分布式存储或 thin pool，discard 让"你不再占这些字节"传达到计费与分配层。虚拟化链路上 virtio-blk 自内核 5.0 起支持 discard 透传，更早的环境只有 virtio-scsi（UNMAP）能传【事实】。同一条命令，本地盘上是性能手段，云上是容量手段——判断"要不要 TRIM"先想清楚在优化哪个。

**故障定位路线**（症状 → 检查）【实践】：

1. **稳态随机写越来越慢、删文件也不见好转** → `systemctl status fstrim.timer` 看定时器是否被禁用；`sudo fstrim -av` 手动执行看回收量是否巨大（巨大 = 长期没 trim 过）；
2. **fstrim 报 "the discard operation is not supported"** → `lsblk --discard` 逐层看 DISC-GRAN：全 0 出现在哪层，问题就在哪层——常见元凶是 dm-crypt（默认出于安全考虑不透传，需 `--allow-discards` 显式打开：discard 模式会暴露"哪些区域是空的"）、老 md RAID5/6、不支持的虚拟化后端；
3. **挂了 `-o discard` 后删除密集期延迟毛刺** → 大概率是实时模式的代价（或 SATA 盘落在 libata 黑名单里被强制非队列 TRIM）；换批量模式对照验证；
4. **TRIM 后空间没回来（thin 卷/云盘）** → 确认整条栈透传 + 后端确实支持回收；`nvme id-ns` 看 NUSE 是否下降（[[3.10 Namespace]] §5）。

## 8. 陷阱与误区

> [!warning] 常见错误
> 1. **"删了文件盘就快回来了"**：不下发 discard，FTL 账本不变，稳态性能一分不涨——文件系统的空闲 ≠ FTL 的空闲。
> 2. **把 TRIM 当安全擦除**：映射失效 ≠ 数据消失；销毁数据走 Format NVM / Crypto Erase。
> 3. **把 TRIM 当即时提速按钮**：收益经由"GC 少搬运"异步兑现，写放大与 p99 的改善出现在**后续**的写入里，不是命令返回那一刻。
> 4. **基准测试忘了 TRIM 状态是变量**：对刚 TRIM 的区域测读 = 测查表回零；两块盘对比必须从 `blkdiscard` 清盘这个共同起点出发（[[3.6 空盘与稳态性能]] §3）。
> 5. **默认 discard 一定能到设备**：dm-crypt/RAID/虚拟化任何一层都可能吞掉它，`lsblk --discard` 逐层核实。
> 6. **在盘快满时指望 fstrim 救急**：能 trim 的只有文件系统空闲块——盘真满了没得可 trim，答案在容量规划与 OP，不在 TRIM。

## 9. 关键结论

| 结论 | 性质 |
| --- | --- |
| 块接口原生无"释放"语义；TRIM/Discard 补上第三个动词，把文件系统与 FTL 的两本账重新对齐 | 事实 |
| Deallocate 只标 L2P 失效、不擦 NAND；收益走"GC 牺牲块 u 下降 → WAF 下降"异步兑现，效果等价于临时增加 OP | 事实 |
| 实时（-o discard）碎而及时，批量（fstrim.timer）整而滞后；通用负载批量为主 | 取舍 |
| TRIM 是 hint：读返回值由 DLFEAT 定档，无擦除承诺，非安全销毁 | 事实 |
| 堆叠层（dm-crypt/RAID/虚拟化）逐层透传才可达设备，lsblk --discard 是排障第一站 | 实践 |
| 本地盘上 TRIM 是性能手段，thin 卷与云盘上是空间回收手段 | 事实 |
