# NVMe Interrupt 与 MSI-X

> [[3.2 Queue Pair 与 Doorbell]] 讲完了完成侧的"零成本发现"：设备把 CQE DMA 进主机内存，相位位翻转，主机读自家 DRAM 就能看到。但它默认了一个前提——**有人在看**。如果提交线程早已睡眠、CPU 在跑别的任务，CQE 躺在内存里没人理，完成就等于没发生。本篇讲通知的最后一公里：设备如何用 MSI-X 把"有新回执"精确地告诉**正确的那个 CPU**。对多线程工程师来说这是熟悉的问题换了硬件外衣：生产者 push 完数据后，是 `notify_one` 叫醒消费者，还是让消费者自旋等待——中断就是硬件版的 `notify_one`。

前置：[[0.4 PCIe BAR MMIO 与 MSI-X]]（MSI-X 在 PCIe 层是什么）、[[3.2 Queue Pair 与 Doorbell]]（CQ 与相位位）、[[0.6 Interrupt Busy Polling 与 Context Switch]]（中断 vs 轮询总论）。

---

## 1. 问题：CQE 已经在内存里，谁去看？

先区分两件常被混为一谈的事：

- **完成的事实**：设备把 16 字节 CQE DMA 写进主机 DRAM——此刻工作已经做完；
- **完成被发现**：某个 CPU 上的代码真正读到这条 CQE，开始处理。

两者之间的空隙就是 [[0.6 Interrupt Busy Polling 与 Context Switch]] 定义的**完成发现延迟**。填补这段空隙只有三种策略：

| 策略 | 机制 | C++ 对应 |
| --- | --- | --- |
| 中断 | 设备发消息打断 CPU | `condition_variable::wait` + 生产者 `notify_one` |
| 忙轮询 | CPU 循环检查相位位 | 自旋读 `std::atomic` 标志 |
| 混合 | 先睡一小会再轮询 / 攒一批再通知 | 带超时的 wait、批量 notify |

**【类比，非等同】** 这组对应贯穿全篇：CQE 是共享数据，中断是通知信号。C++ 里 `notify_one` 不携带数据、只负责叫醒，被唤醒者仍要自己去队列里取——中断完全一样：**中断不搬数据，数据早已 DMA 到位，中断只是"叫醒服务"**。理解了这一点，本篇所有设计取舍都能推出来。

为什么这几微秒值得单独一篇【量级】：NVMe 设备单笔延迟几十 μs（好的盘 ~10 μs），中断路径上的 ISR 进出、线程唤醒、上下文切换、缓存变冷合计约 1–几 μs——设备越快，这段软件开销占比越大。SPDK 干脆全轮询把它归零（[[5.6 SPDK 用户态驱动]]），代价是烧掉整个核。

## 2. MSI-X：中断其实是一次内存写

### 2.1 从共享线到消息

名词先行。PCI 设备向 CPU 发中断的方式经历了三代【事实】：

| 机制 | 形态 | 向量数 | 问题 |
| --- | --- | --- | --- |
| INTx | 边带信号（模拟"拉一根线"） | 每设备 1 个，多设备共享 | 共享线需逐个驱动查询是谁；无法定向 |
| MSI | 内存写消息 | 最多 32 个，地址连续 | 向量少；所有向量指向同一地址、只能同一目标 |
| MSI-X | 内存写消息 | 最多 2048 个，**每向量独立地址/数据** | ——当代标准 |

**【事实】** MSI-X 的"中断"在 PCIe 线路上就是一次 **Memory Write TLP**：设备向平台约定的中断目标地址（x86 上是 LAPIC 的地址窗口）写入一个数据值，中断控制器把这次写翻译成"向某个 CPU 投递某个向量号"。每个向量的（Message Address, Message Data）存在设备 BAR 空间里的 **MSI-X 表**中，由内核在初始化时填写——**改这张表 = 改中断投递到哪个核**，这就是 IRQ 亲和性的硬件基础（[[0.4 PCIe BAR MMIO 与 MSI-X]] 有表结构细节）。

### 2.2 为什么 NVMe 非 MSI-X 不可

回看 [[3.1 NVMe 命令模型]] 那张 AHCI 对比表：AHCI 单中断，所有核共享一个通知入口；NVMe 每核一对 QP（[[3.3 Admin Queue 与 IO Queue]]），如果完成通知仍是单点，"每核独享队列"就白设计了——所有核的完成都挤到一个核上处理，再跨核转发。

**每条 CQ 绑一个独立 MSI-X 向量**，才让"哪条队列完成，就精确通知哪个核"成为可能。多队列 + 多向量是一套设计的两半：队列消灭提交侧的共享，向量消灭完成侧的共享。

## 3. 可见性：为什么"先 CQE 后中断"是可靠的

一个值得较真的并发问题：设备先 DMA 写 CQE（①），再发 MSI-X 消息（②）。CPU 收到中断进 ISR 去读 CQE 时，**凭什么保证 ① 的写已经可见**？如果 ② 超车 ①，ISR 会读到旧相位位、空手而归。

**【事实】** 保证来自 PCIe 事务排序规则：**同一设备发出的 posted Memory Write 不互相超车**。CQE 的 DMA 写和 MSI-X 消息都是 posted Memory Write TLP，同源同向，② 到达时 ① 必已到达并进入缓存一致域。

**【类比，非等同】** 这就是硬件版的 release/acquire 发布协议：

- 设备侧"先写数据（CQE），再写信号（中断消息）"≈ `store(memory_order_release)`；
- ISR 进来"看到信号，再读数据"≈ `load(memory_order_acquire)`；
- 与 [[3.2 Queue Pair 与 Doorbell]] 提交侧的"填 SQE → 屏障 → 敲门铃"互为镜像——**那边是主机向设备发布，这边是设备向主机发布**，两个方向各靠一套排序规则兜底。

但驱动仍然**以 CQ 内容为准，不以中断为准**【实现】：ISR 进来后按相位位扫描，扫到多少处理多少（可能一次中断收割多条 CQE），扫不到就空转返回。中断只是提示，状态在内存——所以杂散中断不致错，丢一次中断也只是晚发现（下次中断或轮询兜底），这正是"通知与数据分离"设计的健壮性红利。

## 4. 向量分配与 IRQ 亲和：完成回到提交核

### 4.1 内核怎么分向量

**【实现】** Linux nvme 驱动初始化时通过 `pci_alloc_irq_vectors()` 申请向量：Admin 队列占一个，每条 IO CQ 各一个；向量数不足时（设备上限、VM 限制）多条队列共享。分配时带 `PCI_IRQ_AFFINITY` 标志——内核把这些向量按 **managed IRQ affinity** 机制自动摊到各 CPU，与 blk-mq 的"队列 ↔ CPU"映射对齐（[[1.7 块层与 blk-mq]]）。

结果是 [[3.3 Admin Queue 与 IO Queue]] 已经预告过的闭环：**提交、执行返回、完成处理都在同一个核**。

### 4.2 为什么必须回提交核

这不是洁癖，每一条都对应真实成本【量级】：

- **缓存局部性**：请求上下文（bio、request 结构、应用的等待队列项）是提交核写的，还热在它的 L1/L2。完成处理落在别的核 = 这些缓存行先迁过去、处理完再迁回来；
- **唤醒成本**：睡眠的提交线程在提交核的调度队列上。异核唤醒需要一次处理器间中断（IPI）+ 目标核的调度延迟；同核唤醒省掉这一跳；
- **无共享**：同核处理意味着完成路径不需要任何跨核同步——与提交侧"每核独享 SQ 免锁"是同一原则的两端。

**C++ 对应**：sharded executor / thread-per-core（[[5.12 无锁 thread-per-core 模型]]）——任务在哪个线程提交，就在哪个线程收尾；消灭共享，而不是保护共享。muduo 的"one loop per thread"是同一张图纸的网络版。

**【实现】** managed IRQ 的亲和性由内核统一管理，`irqbalance` 和手工写 `/proc/irq/N/smp_affinity` 都改不动它——这是特性：防止好心的负载均衡工具把精心对齐的向量迁走。但在老内核、自定义驱动或某些 VM 配置下中断仍可能"漂移"，错配的代价见上图右半。

### 4.3 观测

```bash
grep nvme /proc/interrupts        # 每个向量的编号、类型（IRQ 域）、各 CPU 上的计数
cat /proc/irq/<N>/effective_affinity_list   # 该向量实际落在哪个 CPU
mpstat -P ALL 1                   # %irq / %soft：中断处理吃了多少 CPU
```

健康形态：每个 nvme 向量的计数只在**一个** CPU 上增长，且该 CPU 正是对应队列的提交核。若某向量的计数散布在多核、或集中到与队列映射无关的核上，就有错配。

## 5. 中断的成本账与合并

### 5.1 一次中断花掉什么

【量级】单次中断的固定成本：打断流水线进 ISR（~μs 级进出）、扫描 CQ、若需唤醒线程则再加调度与上下文切换（[[0.6 Interrupt Busy Polling 与 Context Switch]] 的成本表）。单看很小，乘上百万 IOPS 就是每秒百万次中断——CPU 大量时间花在"接电话"而不是干活上，这就是**中断风暴**。缓解思路和网络栈 NAPI 同源：一次中断里**批量收割**尽可能多的 CQE，摊薄固定成本【实现】。

### 5.2 中断合并：攒一批再叫

**【事实】** NVMe 原生支持中断合并（Interrupt Coalescing），`Set Features` FID 08h 配置两个参数，**任一满足即触发**：

- **Aggregation Threshold**：攒够 N 条 CQE 打一次中断；
- **Aggregation Time**：距首条未通知的 CQE 超过 T（100 μs 粒度）必须打——给延迟上界。

```bash
nvme get-feature /dev/nvme0 -f 8 -H    # 查看当前合并配置（默认通常为 0：不合并）
```

**【取舍】** 这是经典的吞吐-延迟交换，C++ 对应"生产者攒 N 个任务才 `notify_one` 一次"：

| 负载 | 效果 |
| --- | --- |
| 高 IOPS | 阈值先到：中断次数 ÷N，每条平均只多等几 μs——划算 |
| 低负载 / 孤立 IO | 凑不够阈值，干等时间窗到期——单笔延迟凭空 + 最多一个时间窗 |

所以延迟敏感的读路径通常**关掉**合并，吞吐型场景才开。更麻烦的是它对 p99 的影响不均匀：同样的配置下，孤立请求吃满时间窗、成批请求几乎无感——平均延迟没动，尾部却抬了。

### 5.3 中断 vs 轮询：完整的谱系

把第 2 章和第 5 章的选项排成一条谱线【取舍】：

| 模式 | 发现延迟 | CPU 占用 | 适用 |
| --- | --- | --- | --- |
| 中断（默认） | μs 级（ISR + 唤醒） | 空闲近零 | 通用、混部 |
| 中断 + 合并 | 加一个有界延迟 | 更低 | 高 IOPS 吞吐型 |
| 混合轮询（`io_poll`） | 亚 μs~μs | 睡一段 + 轮一段 | 快盘同步 IO |
| io_uring IOPOLL | 亚 μs | 烧核（系统调用内轮询） | 专用低延迟（[[2.7 SQPOLL 与 IOPOLL]]） |
| SPDK 全轮询 | 最低且稳定 | 整核 100% | 独占核的存储服务（[[5.6 SPDK 用户态驱动]]、[[5.11 Reactor Thread 与 Poller]]） |

判断准则沿用 [[0.6 Interrupt Busy Polling 与 Context Switch]]：**中断优先省 CPU，轮询优先降发现延迟**；设备越快、SLO 越严、核越能独占，越往轮询端走。IOPOLL 模式下队列干脆不注册中断向量——通知路径整条消失，本篇的所有成本一并归零，代价是那个核别想干别的。

## 6. 动手：把"唤醒成本"量出来

中断路径的软件成本里，最大的一块是"睡眠线程被唤醒"。这个成本不需要 NVMe 设备也能测——用两个线程复现通知的两种策略，量出的差值就是完成发现延迟的软件份额：

```cpp
#include <atomic>
#include <chrono>
#include <condition_variable>
#include <mutex>
#include <print>
#include <thread>

// 对照实验：通知者置位后，等待者多久能观察到。
// spin ≈ 轮询相位位；cv ≈ 中断唤醒睡眠线程。
namespace {

using Clock = std::chrono::steady_clock;
constexpr int kRounds = 10'000;

long long measure_spin() {
    std::atomic<Clock::time_point> stamp{};
    std::atomic<bool> flag{false};
    long long total_ns = 0;

    std::jthread waiter{[&] {
        for (int i = 0; i < kRounds; ++i) {
            while (!flag.load(std::memory_order_acquire)) { /* 自旋 */ }
            total_ns += std::chrono::duration_cast<std::chrono::nanoseconds>(
                            Clock::now() - stamp.load(std::memory_order_relaxed))
                            .count();
            flag.store(false, std::memory_order_release);
        }
    }};
    for (int i = 0; i < kRounds; ++i) {
        stamp.store(Clock::now(), std::memory_order_relaxed);
        flag.store(true, std::memory_order_release);          // "CQE 可见"
        while (flag.load(std::memory_order_acquire)) { }      // 等对方收走
    }
    return total_ns / kRounds;
}

long long measure_cv() {
    std::mutex mtx;
    std::condition_variable cv;
    Clock::time_point stamp;
    bool ready = false;
    bool consumed = true;
    long long total_ns = 0;

    std::jthread waiter{[&] {
        for (int i = 0; i < kRounds; ++i) {
            std::unique_lock lk{mtx};
            cv.wait(lk, [&] { return ready; });               // 睡眠，等"中断"
            total_ns += std::chrono::duration_cast<std::chrono::nanoseconds>(
                            Clock::now() - stamp).count();
            ready = false;
            consumed = true;
            cv.notify_one();
        }
    }};
    for (int i = 0; i < kRounds; ++i) {
        std::unique_lock lk{mtx};
        cv.wait(lk, [&] { return consumed; });
        consumed = false;
        stamp = Clock::now();
        ready = true;                                          // "CQE 可见"
        lk.unlock();
        cv.notify_one();                                       // "MSI-X 消息"
    }
    return total_ns / kRounds;
}

}  // namespace

int main() {
    std::println("spin (≈polling)  : {} ns/round", measure_spin());
    std::println("cv   (≈interrupt): {} ns/round", measure_cv());
    return 0;
}
```

```bash
g++ -std=c++23 -O2 -pthread -o notify_cost notify_cost.cpp && ./notify_cost
```

**读结果的方式**：典型机器上自旋在几十~几百 ns 量级，条件变量唤醒在 1–几十 μs 量级（含 futex 系统调用与调度），且后者抖动大得多。这个差值就是"轮询为什么值得烧一个核"的定量答案——对 10 ms 的 HDD 无所谓，对 10 μs 的 NVMe 是 10%+ 的开销，对 SPDK 要伺候的更快介质则不可接受。注意这是**软件同源类比**：真实中断路径还有 ISR 进出和硬件投递延迟，量级判断一致，数值不等【前提】。

## 7. 陷阱与误区

> [!warning] 常见错误
> 1. **把中断当数据通道**：数据与 CQE 早在中断之前就 DMA 完成了。中断只是提示，因此"中断丢了"不丢数据，只晚发现。
> 2. **手工调 `smp_affinity` 不生效就硬改**：nvme 的向量是 managed IRQ，内核托管亲和性——改不动是特性。真要自定义队列映射，走驱动参数或队列数配置，不要绕过托管机制。
> 3. **以为向量/队列越多越好**：数量是与设备协商的（[[3.3 Admin Queue 与 IO Queue]]）；VM 里 hypervisor 常只给少量向量，多核共享队列与中断，物理机上的调优经验直接失效。
> 4. **开了中断合并后奇怪的 p99**：孤立请求吃满聚合时间窗，成批请求无感——平均没变、尾部抬升。排查 p99 毛刺时记得查 FID 08h（[[9.5 p99 毛刺定位]]）。
> 5. **认为轮询永远更快**：轮询占死一个核。混部环境里被抢占的轮询线程比睡眠线程更惨——既没省延迟又烧了 CPU。轮询的前提是核可独占【前提】。
> 6. **在 ISR 语境里做重活**：中断上下文只做"确认 + 批量收割 + 触发后续"，重逻辑延后——和"硬中断要短"的通用纪律一致（[[0.6 Interrupt Busy Polling 与 Context Switch]]）。

## 8. 关键结论

| 结论 | 性质 |
| --- | --- |
| MSI-X 中断在 PCIe 上是一次 Memory Write TLP；每向量独立地址/数据，最多 2048 个 | 事实 |
| 每条 CQ 绑独立向量：多队列消灭提交侧共享，多向量消灭完成侧共享——一套设计的两半 | 事实 / 设计 |
| PCIe 同源 posted write 保序 ⇒ 中断可见时 CQE 必已可见：设备→主机方向的 release/acquire | 事实 / 类比 |
| 驱动以 CQ 内容为准、中断只是提示：一次中断批量收割，杂散/丢失中断均不致错 | 实现 |
| managed IRQ 把每个向量亲和到提交核：同核完成 = 缓存热 + 免 IPI + 无跨核同步 ≈ sharded executor | 实现 / 类比 |
| 中断固定成本 μs 级；设备越快占比越大——这是轮询路线（IOPOLL/SPDK）存在的理由 | 量级 |
| 中断合并 = 批量 notify：高负载摊薄中断，低负载给单笔加有界延迟，对 p99 影响不均匀 | 取舍 |
| 轮询的前提是核可独占；混部环境下中断反而是更稳的选择 | 取舍 / 前提 |
