# ZNS（选修）

> 常规 SSD 用 FTL 把"异地更新 + 整块擦除"的物理现实藏起来，替主机兜底随机写——代价是 GC、写放大、OP 与不可预测的 p99（[[3.4 SSD FTL 与地址映射]]、[[3.5 GC 写放大与 Over-Provisioning]] 两篇的全部内容）。**ZNS（Zoned Namespace）反其道而行：不藏了**。地址空间切成一个个只能顺序写的 zone，回收以整 zone 为单位由主机显式触发——约束上移给软件，换回设备侧 WAF ≈ 1 和可预测的延迟。选修定位：Storage Infra 面试与生产不必需，但它是理解"FTL 到底替你付了什么代价"的最好反面教材。

前置：[[3.4 SSD FTL 与地址映射]]（FTL 在隐藏什么，本篇讲不隐藏会怎样）。

---

## 1. 背景：FTL 的账单与"双重日志"

先复述问题（不熟请回 3.4/3.5）：NAND 只能整块擦除、页不能就地覆盖，FTL 用页级 L2P 映射 + GC 把这套物理现实翻译成"可随机覆盖写的块设备"。这层翻译的账单【事实】：

- **写放大**：GC 搬运让 NAND 承受的写 = 主机写 × WAF；
- **容量税**：OP 预留 7%~28% 不可寻址容量给 GC 腾挪；
- **DRAM 税**：页级映射表约为容量的千分之一（1 TB 盘 ≈ 1 GB DRAM）【量级】；
- **确定性税**：GC 何时发作、抢多少带宽，主机无法预测——稳态 p99 毛刺的主要来源。

更讽刺的是**双重日志（log-on-log）**问题【事实】：上层软件早就是追加写的——LSM-tree（RocksDB）顺序写 SSTable、WAL 顺序追加、对象存储整段写——这些负载在软件层已把随机写整理成了顺序写；落到常规 SSD 上，FTL **再做一遍**同样的日志化（异地更新本质上就是记日志），两层各自 GC、互相不知道对方的数据生死。[[3.15 TRIM Discard]] 是给这个裂缝打的补丁（事后同步失效信息）；ZNS 是把裂缝焊死：**既然上层本来就顺序写，那就把顺序写定成接口契约，设备侧的翻译层整个撤掉**。

ZNS 不是孤例，是"zoned 块设备"家族的 NVMe 成员【事实】：SMR 叠瓦磁盘（ZBC/ZAC 标准）因磁道重叠同样只能顺序写，Linux 内核用同一套 zoned block device 框架伺候两者——这也是为什么下文的内核工具不带 "nvme" 字样。

## 2. Zone 模型：地址空间长什么样

![[图片/SVG/8_3_16_1.svg|900]]

对照上图 A 区【事实】：

- **namespace = 一排定长 zone**。每个 zone 一段连续 LBA，起点叫 **ZSLBA**（Zone Start LBA）；
- **每个 zone 一支写指针（WP, Write Pointer）**：新数据只能精确写在 WP 位置，写完 WP 前移——zone 内部就是一条只追加的日志；
- **zone 内不可覆盖、不可跳写**：不落在 WP 上的写被设备拒绝（Zone Invalid Write 错误）。想"改"某笔数据？写到别的 zone，旧的等整 zone 回收；
- **回收 = Zone Reset**：WP 拉回 ZSLBA，整 zone 数据失效。它就是"整块擦除"的接口化——3.4 里 FTL 内部的 victim 擦除动作，现在成了主机显式调用的命令，扮演 [[3.15 TRIM Discard]] 里"整段 deallocate"的角色，但从可选优化变成了唯一的空间回收方式；
- **ZCAP ≤ ZSZE**：zone 的可写容量（ZCAP）可以小于它占的编址大小（ZSZE，常取 2 的幂便于寻址计算）——中间的洞不可读写。算可用空间用 ZCAP，算 LBA 偏移用 ZSZE，混用是新手第一坑。

两个资源上限约束并发结构（图 B 区右下）【事实】：同时处于 open 状态的 zone ≤ **MOR**（Max Open Resources），open + closed 合计（active）≤ **MAR**（Max Active Resources）。设备为每个活跃 zone 维护缓冲与元数据，这两个数常常只有十几到几百【量级】——**应用能同时写多少条"日志流"是硬件给定的**，软件的并发写设计必须围绕它。

### 状态机

图 B 区的迁移线用文字复述一遍（完整状态还有 READ ONLY / OFFLINE 两个介质异常态）【事实】：

- EMPTY --第一笔写（隐式）或 Zone Open 命令（显式）--> **OPEN**：接收写入，占 open + active 资源；
- OPEN --Zone Close--> **CLOSED**：暂停写、释放 open 名额、保留 active（WP 不动，随时可续写）——写流多于 MOR 时靠它轮转；
- OPEN --写满 ZCAP 或 Zone Finish--> **FULL**：只读，不占资源。Finish 用于"这条日志提前封卷"；
- FULL --Zone Reset--> EMPTY，循环闭合。

## 3. 顺序写约束下的并发问题与 Zone Append

约束"必须写在 WP 上"和高队列深度天然冲突【事实】：同一 zone 上并发提交两个写（QD > 1），到达设备的顺序不保证（[[3.2 Queue Pair 与 Doorbell]]——多队列、乱序完成是 NVMe 的设计前提），后到的那个 LBA 对不上 WP，直接报错。两条出路：

1. **串行化**：同一 zone 同时只挂一个在途写。Linux 对 zoned 设备默认用 `mq-deadline` 调度器做 per-zone 写锁【实现】——代价是单 zone 写吞吐被 QD=1 封顶，只能靠多 zone 并行找回带宽；
2. **Zone Append**：ZNS 新增的命令，语义反转——主机不指定 LBA，只说"追加到这个 zone"，**设备返回实际落点 LBA（ALBA）**。多个 append 可以并发在途，设备内部排队定序。这是把"分配地址"的权力又还给了设备一小块【取舍】：换来高 QD，代价是数据的最终地址要从完成项里读、上层索引必须接受"写完才知道地址"（RocksDB/ZenFS 类追加型结构无所谓，需要预知地址的结构不适）。

这个矛盾与解法值得记住——它是**接口约束如何反向塑造软件结构**的标准案例：ZNS 把 SSD 的并行度从"盲目多队列"改写成"多 zone × 每 zone 单流（或 append）"。

## 4. 责任重划：主机多干什么，设备少干什么

图 C 区展开成表【事实/取舍】：

| 维度 | 常规 SSD | ZNS |
| --- | --- | --- |
| 映射粒度 | 页级 L2P（DRAM ≈ 容量/1000） | zone 级（表小约三个量级） |
| 随机写 | FTL 吸收 | **接口层拒绝**——主机自己整理成顺序写 |
| GC | 设备后台，时机不可控 | 主机显式：挑 zone → 搬活数据 → Reset |
| OP | 7%~28% | ≈ 0（无设备侧 GC 腾挪需求） |
| 设备侧 WAF | 1/(1−u)，稳态常见 2~5 | ≈ 1（设备不搬数据） |
| 尾延迟 | GC 抢带宽，p99 靠猜 | 可预测——没有背后进程 |
| 主机软件 | 现成文件系统直接用 | 必须 zone 感知（改造成本全在这） |

三点澄清，防止把表读成"ZNS 全面胜利"：

- **写放大没有消失，是搬家了**【事实】：主机做 zone 回收时照样要搬活数据——只是搬运的决策者变成最懂数据生死的一方（比如 RocksDB 直接把整个 SSTable 的生命周期对齐到 zone，回收时几乎无活数据可搬，总 WAF 才真正逼近 1）。上层放置策略差，主机侧 WAF 一样难看；
- **确定性是主要卖点，吞吐不是**【取舍】：同代硬件裸带宽相近，ZNS 赢在稳态不塌、p99 平——对照 [[3.6 空盘与稳态性能]]，ZNS 盘没有"空盘 vs 稳态"两副面孔；
- **多租户噪声邻居问题依旧**【事实】：zone 只是地址切分，NAND 通道与总带宽仍共享（同 [[3.10 Namespace]] "无性能隔离"的结论）。

## 5. 动手：不用真盘，null_blk 五分钟建实验场

ZNS 真盘不好弄，但内核的 `null_blk` 能模拟 zoned 块设备，语义完整、无需硬件【实践】：

```bash
# 创建一个 4 GiB、zone 大小 64 MiB 的模拟 zoned 盘（内存后备, 重启即失）
sudo modprobe null_blk nr_devices=1 memory_backed=1 zoned=1 zone_size=64 gb=4

cat /sys/block/nullb0/queue/zoned            # host-managed：主机管理型 zoned 设备
cat /sys/block/nullb0/queue/scheduler        # 应为 [mq-deadline]（per-zone 写锁靠它）

sudo blkzone report /dev/nullb0 | head -4    # 每 zone 一行：start/len/wptr/状态
# start: 0x000000000, len 0x020000, wptr 0x000000 ... zcond: 1(em) [type: 2(SEQ_WRITE_REQUIRED)]

# 顺序写 zone 0 起点：成功, WP 前移
sudo dd if=/dev/zero of=/dev/nullb0 bs=4k count=256 oflag=direct
sudo blkzone report /dev/nullb0 | head -1    # wptr 变为 0x000800（256×4KiB=1MiB=0x800 扇区）

# 违反约束：跳过 WP 往 zone 中段写 → 立刻 I/O error（这就是 Zone Invalid Write）
sudo dd if=/dev/zero of=/dev/nullb0 bs=4k count=1 seek=4096 oflag=direct,seek_bytes

sudo blkzone reset /dev/nullb0               # 全盘 Reset：所有 WP 归位（可加 --offset/--count 只重置部分）
sudo modprobe -r null_blk                    # 收尾
```

一组对照实验的骨架【实践】：同一 `null_blk` 设备上，(A) `fio --rw=write --bs=1M`（zone 内顺序）跑通；(B) `fio --rw=randwrite` 直接大面积报错——**"随机写不可用"不是性能劣化而是硬错误**，这一刻能真切体会 ZNS 把什么责任推给了软件。真盘上想继续深入：`nvme zns id-ns /dev/nvme0n1` 看 ZCAP/MAR/MOR，`nvme zns report-zones` 对应 `blkzone report`。

## 6. Modern C++：枚举 zone 与写指针

内核给 zoned 设备的 ioctl 是 `BLKREPORTZONE`（头文件 `linux/blkzoned.h`），在上面的 `null_blk` 上即可运行——一次把"zone 数组 + 每支 WP"读出来，等于自己实现 `blkzone report` 的核心：

```cpp
// zone_report.cpp —— 枚举 zoned 块设备的前 N 个 zone, 打印状态与写指针
// 编译: g++ -std=c++23 -Wall -Wextra -o zone_report zone_report.cpp
// 运行: sudo ./zone_report /dev/nullb0
#include <fcntl.h>
#include <linux/blkzoned.h>
#include <sys/ioctl.h>
#include <unistd.h>

#include <cerrno>
#include <cstddef>
#include <memory>
#include <print>
#include <system_error>
#include <utility>

class UniqueFd {
public:
    explicit UniqueFd(int fd = -1) noexcept : fd_(fd) {}
    ~UniqueFd() { if (fd_ >= 0) ::close(fd_); }

    UniqueFd(const UniqueFd&) = delete;
    UniqueFd& operator=(const UniqueFd&) = delete;
    UniqueFd(UniqueFd&& o) noexcept : fd_(std::exchange(o.fd_, -1)) {}
    UniqueFd& operator=(UniqueFd&& o) noexcept {
        if (this != &o) { if (fd_ >= 0) ::close(fd_); fd_ = std::exchange(o.fd_, -1); }
        return *this;
    }
    [[nodiscard]] int get() const noexcept { return fd_; }

private:
    int fd_;
};

[[nodiscard]] constexpr const char* cond_name(std::uint8_t cond) {
    switch (cond) {
        case BLK_ZONE_COND_EMPTY:    return "EMPTY";
        case BLK_ZONE_COND_IMP_OPEN: return "IMP_OPEN";
        case BLK_ZONE_COND_EXP_OPEN: return "EXP_OPEN";
        case BLK_ZONE_COND_CLOSED:   return "CLOSED";
        case BLK_ZONE_COND_FULL:     return "FULL";
        case BLK_ZONE_COND_READONLY: return "READONLY";
        case BLK_ZONE_COND_OFFLINE:  return "OFFLINE";
        default:                     return "?";
    }
}

int main(int argc, char** argv) {
    const char* dev = argc > 1 ? argv[1] : "/dev/nullb0";
    constexpr std::uint32_t kZones = 8;             // 只看前 8 个

    UniqueFd fd{::open(dev, O_RDONLY)};
    if (fd.get() < 0) {
        throw std::system_error{errno, std::generic_category(), "open"};
    }

    // 变长结构: 报告头后紧跟 nr_zones 个 blk_zone——按字节配好再解释
    const std::size_t bytes = sizeof(blk_zone_report) + kZones * sizeof(blk_zone);
    auto buf = std::make_unique<std::byte[]>(bytes);
    auto* report = reinterpret_cast<blk_zone_report*>(buf.get());
    report->sector = 0;                             // 从设备起点开始报告
    report->nr_zones = kZones;

    if (::ioctl(fd.get(), BLKREPORTZONE, report) != 0) {
        throw std::system_error{errno, std::generic_category(),
                                "BLKREPORTZONE（不是 zoned 设备？）"};
    }

    std::println("{}: 报告 {} 个 zone（扇区 = 512B）", dev, report->nr_zones);
    for (std::uint32_t i = 0; i < report->nr_zones; ++i) {
        const blk_zone& z = report->zones[i];
        std::println("zone {:>2}  start={:>10}  cap={:>8}  wp=+{:<8}  {}",
                     i, z.start, z.capacity, z.wp - z.start, cond_name(z.cond));
    }
    return 0;
}
```

**读法**：`wp - start` 是该 zone 已写扇区数；对 EMPTY zone 它是 0，FULL zone 等于 `capacity`。用 `dd` 写 1 MiB 再跑一遍，能看到 WP 精确前移 2048 个扇区——**设备状态完全可枚举、可预测**，这正是 ZNS 卖的确定性在最小尺度上的样子。写路径想继续练：`zonefs`（每个 zone 挂成一个只能追加的文件）是比裸 ioctl 温和得多的台阶【实践】。

## 7. 生态现状与选型判断

软件栈从下到上【事实，截至 2025】：

- **内核**：zoned block device 框架（`CONFIG_BLK_DEV_ZONED`）统一伺候 ZNS 与 SMR；`mq-deadline` 保序；
- **文件系统**：f2fs、btrfs 支持 zoned 模式；`zonefs` 做最薄封装；传统 ext4/XFS **不能**直接放上去；
- **应用层**：RocksDB + **ZenFS** 插件是标杆案例（SSTable 生命周期对齐 zone）；Ceph SeaStore、各大云厂自研引擎有适配；
- **工具/库**：`libzbd`、`blkzone`（util-linux）、`nvme zns` 子命令、`null_blk`/QEMU 模拟。

【取舍】选型一句话：**workload 已是追加型、且掌控整条软件栈**（自研存储引擎、日志系统、对象存储）→ ZNS 的 WAF/OP/确定性收益真实可取；workload 含大量就地随机写、或依赖现成通用文件系统 → 不要碰，你会在主机侧重新发明一个不如厂商固件成熟的 FTL。这也是本篇标"选修"的原因：它是特定 workload 的利器，不是常规 SSD 的替代品。

## 8. 陷阱与误区

> [!warning] 常见错误
> 1. **把 ZCAP 当 ZSZE 用**：可用空间按 ZCAP 累加，LBA 定位按 ZSZE 对齐——用错一个，要么容量虚高，要么写进洞里报错。
> 2. **忽略 MAR/MOR**：并发写流数是硬件资源，不是软件想开多少开多少；超限 open 直接报 Too Many Active/Open Zones。
> 3. **以为 ZNS 消灭了写放大**：只是把 GC 决策权和搬运成本移交主机；放置策略差，主机侧 WAF 照样高。
> 4. **在同一 zone 上开高 QD 普通写**：乱序到达必报 Zone Invalid Write；要么串行（接受 QD=1），要么改用 Zone Append。
> 5. **把 ZNS 当"更快的盘"来评测**：它卖的是稳态确定性；拿空盘峰值对比常规 SSD 得不出有意义的结论（口径见 [[3.6 空盘与稳态性能]]）。
> 6. **忘了 Reset 是唯一回收手段**：没有按 LBA 的 deallocate；数据生命周期管理必须以 zone 为粒度设计，这个约束要在数据结构设计期就进场，事后补救等于重写。

## 9. 关键结论

| 结论 | 性质 |
| --- | --- |
| ZNS 把"异地更新 + 整块擦除"从 FTL 内部现实提升为接口契约：zone 顺序写、WP 单向前移、Reset 整段回收 | 事实 |
| 设备侧收益：WAF ≈ 1、OP ≈ 0、映射表缩小约三个量级、尾延迟可预测 | 事实 |
| 写放大与 GC 没有消失，是移交给了更懂数据生死的主机——收益大小取决于上层放置策略 | 事实 / 取舍 |
| 顺序写约束与高 QD 冲突：per-zone 串行（mq-deadline）或 Zone Append（设备返回落点）二选一 | 事实 / 取舍 |
| MAR/MOR 把"并发写流数"变成硬件资源，软件并发结构必须围绕它设计 | 事实 |
| 适用边界清晰：追加型 workload + 自控软件栈；随机写场景等于在主机重写 FTL | 取舍 |
| null_blk + blkzone + BLKREPORTZONE 构成零硬件实验场，约束与状态机全部可复现 | 实践 |
