# Bounce Buffer vs 直读

> [[8.2 GDS 与 cuFile]] 证明了盘可以 DMA 直写显存,似乎中转缓冲(bounce buffer:盘→主存缓冲→H2D 拷贝→显存)该被扫进历史。本篇用一个真实负载证明事情相反:**两条路径各有不可替代的主场,分界线不是「哪个快」,而是「谁第一个消费数据」**。贯穿负载:一台 8 卡训练节点跑多模态模型,每卡要吃两种数据——图像(JPEG,需要 CPU 解码增广)与 tokenized 文本(定长张量,GPU 直接消费)。同一台机器、同一批盘,图像必须走 bounce,文本适合走直读——把这两条路的吞吐、CPU、内存带宽因果链算清楚,「选哪条」就从玄学变成算术。

前置：[[8.1 GPU 内存层次与数据搬运]]（传统路径的 6 次总线账、pinned 的分水岭——本篇全程使用）、[[8.2 GDS 与 cuFile]]（直读路径的机制与验伪）、[[1.3 Buffered IO 与 O_DIRECT]]（缓存有益/无益的判据）。

---

## 1. 两条路径的本体

先把名字钉死【事实】：

- **bounce buffer 路径**：盘 --DMA--> 主存缓冲 --（可选 CPU 处理）--> pinned 缓冲 --DMA--> 显存。数据在主存「弹」一下再走,故名 bounce。做得好时(O_DIRECT + 直接读进 pinned 缓冲)是 2 次 DMA + 0 次 CPU 拷贝;做得差时(buffered 读 + pageable 内存)是 [[8.1 GPU 内存层次与数据搬运]] §3 那张 6 穿越 + 2 拷贝的账单;
- **直读路径（GDS）**：盘 --DMA--> 显存(BAR1),主存全程不参与,1 次 DMA。

单看总线账直读完胜。但账本上没写的一行才是决策关键【事实】:**bounce 路径中途经过主存——如果 CPU 本来就要碰这份数据,这次「弹跳」是免费的必经之路;直读把数据送进显存,CPU 再想碰就得再搬回来**。

---

## 2. 贯穿负载:同一台节点上的两种数据

8 卡节点,每卡供数需求(量级设定,方法可迁移)【量级】:图像流 2 GB/s/卡(解码前的 JPEG 字节),文本流 1 GB/s/卡(tokenized 定长张量)。合计:图像 16 GB/s、文本 8 GB/s,盘阵供给没问题([[3.7 nvme-cli 实操]]),问题全在「怎么进显存」。

### 2.1 图像流:CPU 必须先消费 → bounce 是必经之路

JPEG 不能直接喂给训练 kernel——要 CPU(或专用硬件)解码、resize、增广【事实】。数据的第一个消费者是 CPU,于是:

```text
盘 --DMA--> 主存(O_DIRECT 读进普通缓冲) --CPU 解码增广--> 写入 pinned 环形缓冲 --DMA--> 显存
```

这条链的因果账【事实/量级】:

| 环节 | 资源 | 需求(16 GB/s 压缩字节,解码后 ~3×膨胀) |
| --- | --- | --- |
| 盘读 | 盘带宽 | 16 GB/s——盘阵轻松 |
| 解码增广 | **CPU 核** | JPEG 解码单核百 MB/s 量级 → **几十个核全职解码**——最先撞墙的资源 |
| 解码输出写 + pinned 拷入 | **主存带宽** | 解码后 48 GB/s 的写 + 读,叠加盘 DMA 16 GB/s——主存总线上百 GB/s 级流量 |
| H2D | PCIe | 48 GB/s ÷ 8 卡 = 6 GB/s/卡——Gen4 x16 富余 |

**因果链读法**【实践】:GPU 空闲(利用率掉)← H2D 供不上 ← pinned 环空 ← 解码吞吐不足 ← CPU 核不够或主存带宽被抢。瓶颈几乎总在 CPU 解码,而不是任何一段搬运——这就是为什么图像训练节点堆 CPU 核数、为什么出现 nvJPEG/DALI(把解码也搬进 GPU,消灭 CPU 环节,代价是烧 GPU 算力)【实现/取舍】。此负载上 GDS 无从谈起:**直读送进显存的是 JPEG 字节,GPU kernel 不认**。

### 2.2 文本流:GPU 是第一消费者 → 直读的主场

tokenized 张量是定长二进制,GPU 直接消费,CPU 全程不需要看一眼【事实】。此时 bounce 的「弹跳」纯属浪费:主存带宽白付 2 次穿越、pinned 池白占、还多一段拷贝流水线要编排。直读一步到位:8 GB/s 全程只出现在「盘→显存」的 P2P 路径上,主存流量为 0,CPU 只发 cuFile 命令【事实】。

叠加效应容易被忽略【实践】:文本流走直读,**省下的主存带宽正好补贴给图像流的解码**——两条路径不是各自优化,是在同一根主存总线上互相让路。这就是「吞吐-CPU-内存带宽」三者在一台机器里的因果耦合:直读的收益要按「腾出来的主存带宽 × 图像流的受益」算总账,只盯文本流自己的延迟会低估它。

## 3. 决策表:五个判据

![Bounce Buffer 与直读的路径对比与决策图:上半部分左右两条路径——bounce 路径为盘 DMA 进主存缓冲、CPU 可选处理后写 pinned 环、再 DMA 过 PCIe 进显存,标注两次 DMA 与主存流量;直读路径为盘经 cuFile 一次 DMA 直写显存 BAR1,主存零流量;下半部分为五判据决策表——第一消费者是 CPU 还是 GPU、数据是否重复读(page cache 有益性)、IO 对齐与尺寸、拓扑是否 PIX、故障回退,以及贯穿负载中图像流走 bounce、文本流走直读的结论](../../图片/SVG/gpu-bounce与直读决策.svg)

| 判据 | 倾向 bounce | 倾向直读(GDS) |
| --- | --- | --- |
| **第一消费者**(决定性) | CPU 要解码/解压/增广/校验 | GPU 直接消费原始字节(张量、checkpoint、KV cache) |
| 重复读 | 热数据集反复读——page cache 命中免盘 IO([[1.2 Page Cache 命中与未命中]]);直读强制 O_DIRECT 放弃这层缓存 | 冷数据/读一次(epoch 遍历大数据集,命中率≈0) |
| IO 形状 | 小、不对齐、碎(FUSE/网络文件系统) | ≥百 KiB 大块、4 KiB 对齐([[8.2 GDS 与 cuFile]] 的硬要求) |
| 拓扑 | GPU 与盘 SYS 关系(跨 socket,P2P 打折) | PIX/PXB 同 Switch([[8.1 GPU 内存层次与数据搬运]] §4) |
| 工程性 | 路径通用,处处能跑,便于调试 | 依赖 nvidia-fs/文件系统适配,有静默回退风险([[8.2 GDS 与 cuFile]] §3) |

一句话版【实践】:**先问「谁先消费」,再问「缓存有没有益」,最后才比拼搬运次数**——搬运账是三个判据里权重最低的,这正是 8.2 结尾「GDS 收益一半在 CPU 退休」结论的另一面。

## 4. 把 bounce 做对:pinned 环 + 双缓冲流水线

图像流逃不开 bounce,那就把它做到理论上限——**用重叠隐藏搬运**:H2D 拷贝第 N 批时,CPU 在解码第 N+1 批,GPU 在算第 N-1 批。三级流水线,每级一份资源,谁最慢谁定吞吐【事实】。Modern C++ 骨架(RAII + 双缓冲,可直接扩成 N 缓冲环):

```cpp
#include <cuda_runtime.h>

#include <array>
#include <cstddef>
#include <span>
#include <stdexcept>

// 复用 8.1 的 PinnedBuffer(RAII 管理 cudaMallocHost)与 ck() 错误检查

class DoubleBufferedLoader {
public:
    DoubleBufferedLoader(std::size_t batch_bytes, void* dev_dst)
        : bufs_{PinnedBuffer{batch_bytes}, PinnedBuffer{batch_bytes}}, dev_{dev_dst} {
        ck(cudaStreamCreate(&stream_), "stream create");
    }
    ~DoubleBufferedLoader() { cudaStreamDestroy(stream_); }
    DoubleBufferedLoader(const DoubleBufferedLoader&) = delete;
    DoubleBufferedLoader& operator=(const DoubleBufferedLoader&) = delete;

    // 生产者(CPU 解码线程):拿到「空闲」缓冲填数据——上一轮 H2D 没完成时在此等待
    std::span<std::byte> acquire() {
        ck(cudaStreamSynchronize(stream_), "wait prev H2D");   // 背压点:PCIe 慢则 CPU 在此被卡
        return {static_cast<std::byte*>(bufs_[cur_].data()), bufs_[cur_].size()};
    }

    // 填完提交:异步 H2D(pinned 才真异步,8.1 §2),随即切换缓冲让 CPU 填下一批
    void submit(std::size_t filled) {
        ck(cudaMemcpyAsync(dev_, bufs_[cur_].data(), filled,
                           cudaMemcpyHostToDevice, stream_), "H2D async");
        cur_ ^= 1;                       // CPU 立即转去填另一块——解码与搬运重叠
    }

private:
    std::array<PinnedBuffer, 2> bufs_;
    void* dev_;
    cudaStream_t stream_{};
    unsigned cur_ = 0;
};
```

三个读码要点【事实】:

1. `acquire()` 里的同步就是**背压**:PCIe 或 GPU 消费慢于解码时,CPU 生产者被自然卡住——与 [[6.7 Compaction 策略]] §3 的有界流水线同构,缓冲数量(2→N)决定能吸收多大的速率抖动;
2. 稳态吞吐 = min(盘读, 解码, H2D, GPU 计算)——**流水线只隐藏延迟,不创造带宽**;加缓冲改善的是抖动容忍,不是均值【事实】;
3. pinned 环在构造时一次分配,数据路径零分配——[[8.1 GPU 内存层次与数据搬运]] 的池化军规。

## 5. 排障清单:症状 → 判定 → 处置

| 症状 | 先看什么 | 典型根因 | 处置方向 |
| --- | --- | --- | --- |
| GPU 利用率锯齿,数据等待时间高 | 流水线各级速率:盘读/解码/H2D 谁最慢 | 解码 CPU 不足(图像流最常见) | 加解码核/上 GPU 解码;确认主存带宽没被别的流抢 |
| H2D 带宽远低于 8.1 的健康值 | 缓冲是 pinned 还是 pageable;Async 是否真异步 | pageable 路径多一次驱动拷贝且不异步 | 换 pinned 池;复测 bandwidthTest 对照 |
| 上了 GDS 数字没变 | [[8.2 GDS 与 cuFile]] 的内核计数器 | 静默回退 compat,其实在跑 bounce | 按 8.2 §4 三步验伪再对比 |
| 直读上线后图像流反而变快/变慢 | 主存带宽占用前后对比 | 两条流共享主存总线的耦合(§2.2) | 按总账评估;NUMA 绑定把两条流分 socket【实践】 |
| 热数据集换直读后变慢 | 之前的 page cache 命中率 | 直读 O_DIRECT 放弃了缓存,冷读全打盘 | 热负载留 buffered bounce;直读只给冷大流 |
| 小文件/不对齐负载直读报错或退化 | IO 尺寸分布;对齐 | 4 KiB 对齐与大块是直读硬前提 | 打包对齐([[7.6 AI 存储 vs 传统 NAS]]);或改走 bounce |

## 6. 陷阱与误区

> [!warning] 常见错误
> 1. **把「直读比 bounce 少拷贝」当成普适结论**:第一消费者是 CPU 时,bounce 的主存中转是必经之路,直读反而要把数据从显存搬回来——方向性错误,不是性能差异。
> 2. **bounce 一定慢的刻板印象**:O_DIRECT 直读进 pinned + 双缓冲重叠后,bounce 稳态可以打满 PCIe——它输的是主存带宽与 CPU 占用,不一定输吞吐。
> 3. **忽略两条流的总线耦合**:直读的收益要算「腾出的主存带宽给了谁」;单流 A/B 测试测不出这部分。
> 4. **热数据上直读**:O_DIRECT 绕过 page cache,重复读负载把缓存红利全丢——[[1.3 Buffered IO 与 O_DIRECT]] 的判据先于一切 GPU 考量。
> 5. **加深缓冲池来「提吞吐」**:流水线吞吐 = 最慢一级,缓冲只平抖动;深池只是把 OOM 风险换个姿势。
> 6. **忘了验证 GDS 真伪就下结论**:compat 回退让「直读组」实际在跑 bounce——所有对比实验先过 8.2 的计数器关。

## 7. 关键结论

| 结论 | 性质 |
| --- | --- |
| 决策第一判据是「谁第一个消费数据」:CPU 要处理 → bounce 是必经之路;GPU 直接消费 → 直读主场 | 事实 |
| 判据优先级:第一消费者 > 缓存有益性 > 对齐/尺寸/拓扑 > 搬运次数——总线账权重最低 | 实践结论 |
| bounce 做对 = O_DIRECT 读 + pinned 环 + 异步 H2D 重叠:2 次 DMA、稳态可满 PCIe;做错 = 6 穿越 2 拷贝 | 事实 |
| 流水线吞吐 = min(盘, 解码, H2D, 计算);缓冲深度平抖动不提均值;acquire 的同步点即背压 | 事实 |
| 图像类负载瓶颈几乎总在 CPU 解码——堆核、GPU 解码(DALI/nvJPEG)是对症药;搬运优化是错靶 | 实践结论 |
| 同一主存总线耦合两条流:直读省下的主存带宽补贴 bounce 流——收益按机器总账算,不按单流算 | 事实 |
| 热数据的 page cache 红利与直读的 O_DIRECT 互斥——重复读负载慎上直读 | 事实/取舍 |
| 所有 bounce vs 直读对比,先验证直读组没有静默回退 | 实践结论 |
