# LMCache 与 Mooncake

> [[8.4 KV Cache Offload]] 结尾指出单机缓存的天花板:命中率被负载均衡打散、单机 DRAM/NVMe 容量有限。本篇继续那个贯穿负载——70B 级、32k 上下文的聊天服务——把它从一台机器放大到一个集群,看两个工业系统怎么接手:**LMCache** 把 8.4 的分层引擎产品化并做到跨实例共享;**Mooncake**(月之暗面 Kimi 的服务架构,FAST'25 论文公开【事实】)更激进——**整个推理集群围绕 KV Cache 重新组织**:prefill 与 decode 分成两个池、全集群的 DRAM/SSD 拼成一个 KV 池、请求调度以「缓存命中最大化」为第一目标。看懂这两个系统的方法不是记架构图,而是跟住一条因果链:**混布为什么伤尾延迟 → 分离为什么造出搬运需求 → 池化为什么值得为搬运付费**——吞吐、尾延迟、CPU、内存、网络五个变量在这条链上互为因果,这正是分布式系统设计的日常。

前置：[[8.4 KV Cache Offload]]（体积账、决策不等式、TTFT/TBT——本篇直接续用）、[[4.1 RDMA 为什么快]] + [[4.4 内存注册与零拷贝]]（KV 搬运的网络机制）、[[7.2 元数据路径瓶颈]]（池化后「块在哪」又是一张元数据表）。

---

## 1. 单机天花板:三个结构性矛盾

把贯穿负载摆上一个 16 节点集群,单机方案(每实例自己做 8.4 的分层缓存)暴露三个矛盾【事实】:

1. **命中率被路由打散**:同一用户的第二轮对话被负载均衡发到另一台机器——那里没有他的前缀 KV,白白重算。前缀亲和路由能缓解,但与负载均衡目标冲突:热用户扎堆的实例过载,冷实例空转【取舍】;
2. **prefill 与 decode 互相踩踏(混布干扰)**:两相的资源画像相反——prefill 是算力密集的大 kernel(秒级占住 SM),decode 是访存密集的小步快跑(毫秒级一步)。同卡混布时,一个 32k prefill 挤进来,正在 decode 的所有会话被卡住几百 ms——**TBT 的 p99 直接被别人的 prefill 决定**【事实】。这是经典的「长任务阻塞短任务」队列问题,与 [[6.7 Compaction 策略]] 里后台大 IO 顶前台读、[[9.5 p99 毛刺定位]] 里大请求排队同构;
3. **容量与算力绑死**:想加 KV 容量只能整机加卡——而 KV 想要的是便宜的 DRAM/SSD,不是昂贵的 HBM 和算力([[5.1 NVMe-oF 架构]] §1 存算分离三笔账的推理版)。

三个矛盾对应三味药:**共享缓存层(LMCache)、P/D 分离、KV 池化(Mooncake)**。

---

## 2. LMCache:把 8.4 的引擎做成可共享的缓存层

LMCache 是开源的 KV 缓存中间层(与 vLLM 等引擎经 connector 集成)【实现】,可以概括为「8.4 的工程完全体 + 两个越出单机的能力」:

- **分层完全体**:GPU HBM → CPU DRAM → 本地盘 → 远端后端,KV 按 **chunk(token 段)** 为单位存取与索引——粒度比 paged block 粗,专为跨层/跨机搬运摊薄固定开销【实现】(8.4 §4 的 `base_latency` 教训:段太小,固定开销吃掉收益);
- **跨实例共享**:实例 A 算过的前缀,实例 B 经 P2P/共享后端取用——命中率不再被路由打散,矛盾 1 的直接解药;
- **超越前缀的复用**:前缀复用要求 token 序列完全相同;LMCache 的 blending 类技术允许拼接复用非前缀的 KV 段(如 RAG 场景里同一批文档 chunk 出现在不同 prompt 的不同位置),代价是拼接处需少量重算修正【实现/取舍】——把「缓存键」从「整个前缀」细化到「内容段」,命中面大幅展宽。

对存储工程师,LMCache 的定位一句话【事实】:**它之于推理引擎,如同一个带多级后端与对等共享的分布式 buffer cache 之于文件系统**——vLLM 管「页表与计算」,LMCache 管「页在哪、怎么搬」。

## 3. Mooncake:围绕 KV Cache 重组整个集群

![Mooncake 式 KVCache 中心架构全景:上方 conductor 全局调度器按缓存命中最大化与 TTFT/TBT SLO 选择 prefill 与 decode 实例;左侧 prefill 池跑算力密集的长 prefill 并把产出的 KV 逐层写入池;中部为全集群 DRAM 与 SSD 拼成的分布式 KVCache 池,前缀命中的 KV 就近取用;右侧 decode 池从池中拉取 KV 后做访存密集的逐 token 生成,TBT 不再被别人的 prefill 阻塞;底部 Transfer Engine 以 RDMA 多网卡与拓扑感知路径执行所有 KV 搬运,标注 KV 在 prefill 到 decode 之间的流动与网络成为新的关键资源](../../图片/SVG/mooncake-PD分离与KV池.svg)

Mooncake 的四个组件,每个都是对 §1 某矛盾的回答【事实/实现】:

| 组件 | 做什么 | 回应的矛盾 |
| --- | --- | --- |
| **prefill 池 / decode 池** | 两相物理分开:prefill 节点只跑 prefill(长上下文用分块流水并行),decode 节点只跑 decode | 矛盾 2:TBT 不再被别人的 prefill 踩,两相各自按画像选硬件与并行度 |
| **分布式 KVCache 池**(Mooncake Store) | 全集群 CPU DRAM + SSD 拼成一个池,KV 按 chunk 存放、按前缀哈希索引 | 矛盾 1+3:命中全局可见;容量用便宜介质独立扩展 |
| **Transfer Engine** | 所有 KV 搬运的执行层:RDMA、多网卡聚合、拓扑感知选路(挑同 NUMA/同 Switch 的网卡,[[3.8 PCIe 拓扑与 NUMA]] 的账)、GPU 直达([[4.4 内存注册与零拷贝]]) | 分离制造的搬运需求由它买单 |
| **Conductor(调度器)** | 为每个请求选 prefill/decode 实例:第一目标是**前缀命中最大化**,并按预测负载对 TTFT/TBT SLO 做准入控制(过载时提前拒绝) | 把「缓存」从底层机制升格为**调度的第一公民** |

**必须算清的一笔账——P/D 分离不是免费的**【事实/取舍】:分离后,prefill 产出的 KV 必须搬到 decode 节点(贯穿负载:每条 32k 请求 ~10 GiB)。这笔搬运在混布架构里根本不存在。它成立的条件有二:

1. 网络足够快:10 GiB 走 RDMA 200 Gb/s ≈ 0.4 s,且**逐层流水**——prefill 算完第 L 层就发第 L 层的 KV,传输与计算重叠,大部分被掩盖(8.4 §3 同款重叠,搬到了网络上)【实现】;
2. 换来的东西更值钱:decode 池的 TBT 尾延迟干净了(没有 prefill 踩踏),prefill 池的算力利用率高了(长任务连续跑,不被打断)——**用网络带宽(可花钱买)换尾延迟质量与两相各自的利用率(买不到)**。

这正是 [[5.1 NVMe-oF 架构]] 存算分离逻辑的第三次出现:资源画像不同的两种活,分开各自扩展,中间用足够快的网络粘住;网络成为新的关键资源,也成为新的故障域。

## 4. 因果关系总表:五个变量怎么互相牵动

用贯穿负载把全链因果串起来(排障与容量规划都从这张表出发)【实践】:

| 动作 | 吞吐 | 尾延迟 | CPU | 内存 | 网络 |
| --- | --- | --- | --- | --- | --- |
| 池化命中率 ↑ | prefill 算力省下 → 集群吞吐 ↑ | TTFT p50 ↓(命中路径) | 索引/搬运 CPU 略增 | 池占用 DRAM/SSD ↑ | 取回流量 ↑ |
| P/D 分离 | 两池利用率各自 ↑ | **TBT p99 大幅 ↓**(踩踏消失) | — | — | **新增 KV 搬运流量**(每请求 GiB 级) |
| 网络拥塞/慢节点 | 传输掩盖失效 → prefill 等待 → 吞吐 ↓ | TTFT p99 ↑(取回慢尾) | — | — | 根因所在:incast、拓扑错配([[4.7 PFC ECN 与 DCQCN]]) |
| 池容量不足→逐出激进 | 命中率 ↓ → 吞吐 ↓ | TTFT p99 ↑(未命中变多) | 重算 CPU/GPU ↑ | 根因所在 | 流量结构变差(反复重取) |
| 准入控制(过载拒绝) | 有效吞吐 ↑(不做会超时作废的活) | SLO 内请求延迟稳 | — | — | — |

读表方法【实践】:每一行都是「一个旋钮,五个仪表」——**任何单指标优化必须同时报告另外四列的变化**,这是评审推理系统设计的最低标准;反过来排障时,五个仪表里先动的那个通常不是根因,沿本表逆向找「谁牵动了它」。

## 5. 排障清单:症状 → 判定 → 处置

| 症状 | 先看什么 | 典型根因 | 处置方向 |
| --- | --- | --- | --- |
| TBT p99 毛刺(混布架构) | 毛刺时刻是否有长 prefill 进入同卡 | 混布踩踏(§1 矛盾 2) | 短期:chunked prefill 限制单步占用;根治:P/D 分离 |
| 分离后 TTFT 反而变差 | KV 传输是否逐层流水;网络利用率 | 整段传完才开始 decode,掩盖失效 | 开启逐层流水;检查 Transfer Engine 选路(网卡拓扑) |
| 集群命中率远低于单机复现值 | 路由是否前缀亲和;池索引是否全局可见 | 请求打散且实例缓存孤岛 | 上共享池/亲和路由;确认 connector 正确接入 |
| 取回带宽上不去 | 单网卡还是多网卡聚合;chunk 大小 | 小 chunk 固定开销 + 单流瓶颈 | 加大 chunk;多网卡并发;核对 RDMA 注册复用([[4.4 内存注册与零拷贝]]) |
| 池节点 DRAM 吃满后整体变慢 | 逐出水位;SSD 层延迟分布 | 逐出不及时,或下沉层太慢拖住取回 | 调水位线;SSD 层只收长段(8.4 盈亏平衡);扩池 |
| 高峰期大量请求超时 | 是否有准入控制;超时请求占用的算力比例 | 过载时仍全收,做完即作废的活挤占 SLO 内请求 | 按预测负载提前拒绝/降级(Mooncake 的准入思路)【实现】 |

## 6. 陷阱与误区

> [!warning] 常见错误
> 1. **把 P/D 分离当纯收益**:每请求 GiB 级的 KV 搬运是分离凭空造出的成本——网络预算不足、不做逐层流水,分离比混布更糟。
> 2. **命中率当唯一 KPI**:强行提高命中(超长保留、无限扩池)会把 DRAM/网络拖进瓶颈——§4 的表,五个仪表一起看。
> 3. **忽略池的元数据路径**:「哪个 chunk 在哪个节点」是一张全局索引表——QPS 与一致性问题回到 [[7.2 元数据路径瓶颈]],池越大越要按那一篇的方法审视。
> 4. **拿单机基准推集群收益**:单机命中率不含路由打散效应;集群实验必须用真实 trace 的会话分布【实践】。
> 5. **忘了 KV 池也是故障域**:池节点挂掉,命中变未命中,prefill 池瞬间承压——容量规划要含「池降级时 prefill 池扛得住重算风暴」的余量,同 [[5.5 Multipath 与故障切换]] 的 N−1 逻辑。
> 6. **传输层不做拓扑感知**:网卡与 GPU 跨 NUMA/跨 Switch 时,RDMA 带宽打折([[3.8 PCIe 拓扑与 NUMA]])——集群版的「买对卡还要插对槽」。

## 7. 关键结论

| 结论 | 性质 |
| --- | --- |
| 单机 KV 缓存的三个天花板:命中率被路由打散、prefill/decode 混布踩踏 TBT、容量与算力绑死 | 事实 |
| LMCache = 分层引擎的工程完全体 + 跨实例共享 + 非前缀复用(blending)——推理界的分布式 buffer cache | 事实/实现 |
| Mooncake = 集群围绕 KV 重组:P/D 两池 + 全集群 DRAM/SSD 拼成 KV 池 + RDMA 传输引擎 + 命中优先的调度器 | 事实/实现 |
| P/D 分离的本质交易:凭空新增每请求 GiB 级搬运,换 TBT 尾延迟纯净 + 两相利用率——成立前提是快网络 + 逐层流水掩盖 | 事实/取舍 |
| 这是存算分离逻辑的第三次出现(NVMe-oF、3FS 之后):画像不同的活分开扩展,网络粘合并成为新瓶颈与新故障域 | 事实 |
| 缓存从机制升格为调度第一公民:请求放置按命中最大化,过载做准入控制——「有效吞吐」优先于「名义吞吐」 | 事实/实现 |
| 五变量因果表是评审与排障的主工具:任何单指标优化必须同时报告其余四列 | 实践结论 |
| 池是新的元数据问题(7.2)与新的故障域(5.5 N−1):老课题在新楼层原样收租 | 实践结论 |
