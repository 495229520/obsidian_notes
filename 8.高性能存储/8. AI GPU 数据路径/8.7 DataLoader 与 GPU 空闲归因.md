# DataLoader 与 GPU 空闲归因

> 一台 8×H100 训练节点是机房里最贵的东西，它每秒的折旧都在跑；DataLoader 唯一的职责就是**别让它等**。这条冷酷算术贯穿本章：GPU 每 `t_compute` 秒吃掉一个 batch，DataLoader 就必须在这段时间里把下一个 batch 准备好——准备慢了，差出来的就是**空泡**（GPU 停在那儿等数据的时间）。整篇围绕一个可量的量：
>
> $$
> t_{bubble} = \max(0,\ t_{data} - t_{compute})
> $$
>
> 以及它的归一化形式——**加速器利用率** AU（就是 [[8.6 Checkpoint 同步异步分片]] 的 goodput 换个场景）。本篇用一个具体负载把「吞吐、尾延迟、CPU、内存、网络」串成一条因果链：**8 卡训练一个 ResNet-50 类图像模型，数据是 ImageNet 量级的海量小 JPEG，放在共享存储上，同时每 30 分钟做一次 checkpoint**。这个负载会把数据路径的每一层都压出问题来。

前置：[[8.1 GPU 内存层次与数据搬运]]（H2D 路径、pinned 才真异步的分水岭）、[[1.2 Page Cache 命中与未命中]]（跨 epoch 重读命中）、[[7.2 元数据路径瓶颈]]（小文件为什么专杀元数据）、[[7.6 AI 存储 vs 传统 NAS]]（拆入口、从队列到 GPU 利用率的因果链）。

## 1. 空泡从哪来：先把流水线画清楚

一个训练 step 的数据要穿过四段，前三段是 DataLoader 的活，最后一段才是 GPU（对照下图顶部流水线）：

![DataLoader 流水线与空泡归因全景：顶部为四段流水线——存储读取（本地盘/NFS/对象存储）→ CPU 预处理 workers（解码/增广/collate，常吃满核）→ pinned + H2D（pinned 才真异步）→ GPU 计算，段间是预取队列；中部两条时间线对比健康态（数据段≤计算段，预取把数据完全藏进计算背后，GPU 无空泡）与饥饿态（数据段>计算段，队列很快抽干，每步都要等，标注队列吸收方差补不了均值）；下部为归因决策树三刀——profiler 看 step 分解定 data_time 占比、换合成数据看空泡是否消失、iostat/nfsstat 定层，以及按层对号的修复杠杆清单](../../图片/SVG/dataloader-流水线与空泡归因.svg)

```text
存储读取 ──▶ CPU 预处理 ──▶ pinned + H2D ──▶ GPU 计算
（IO/网络）  （解码/增广/collate） （PCIe 入口）    （前向/反向/通信）
└──────────── DataLoader 的三段 ────────────┘   └── GPU ──┘
```

理想情况下这是一条**流水线**：GPU 算 step N 的同时，DataLoader 后台已经在准备 batch N+1、N+2。只要「准备一个 batch」的时间藏得进「算一个 batch」的时间里，GPU 就一刻不停。**空泡出现在准备赶不上消费的那一刻**——而准备的快慢，由这三段里最慢的一段决定。

一个关键区分要立在最前面【事实】：GPU 空泡**不是**存储慢的同义词。存储、CPU、PCIe 任何一段成为瓶颈都会让 GPU 挨饿；归因的第一步永远是**先定位是哪一段**，而不是条件反射去换更快的盘。下面三节先把三段各自吃什么资源讲清楚，再讲它们如何互相拖累，最后给定位方法。

## 2. 三段流水线，各吃一种资源

| 段 | 主要瓶颈资源 | 在这个负载里的具体形态 | 参考 |
| --- | --- | --- | --- |
| 存储读取 | IOPS / 带宽 / **网络** / 元数据 QPS | 海量小 JPEG：每张一次 `open`+`stat`+`read`，元数据 RPC 比数据 RPC 还多 | [[7.2 元数据路径瓶颈]] |
| CPU 预处理 | **CPU 核** + 主存带宽 | JPEG 解码 + resize + 数据增广，是纯 CPU 密集活，常吃满所有 worker 核 | [[8.1 GPU 内存层次与数据搬运]] §3 |
| pinned + H2D | **PCIe 入口** + pinned 内存 | batch 拷进 pinned 缓冲、DMA 过 PCIe 进显存；pageable 会退化成假异步 | [[8.1 GPU 内存层次与数据搬运]] §2 |

三段各吃一种资源，这就是为什么「加更快的盘」经常无效：如果瓶颈在 CPU 解码，盘再快，batch 也卡在解码那一段出不来。

**存储段的小文件陷阱**【事实】：ResNet-50 负载的样本是 ~110 KB 级的小 JPEG。对存储系统，这意味着请求里**元数据操作压倒数据操作**——每读一张图要先解析路径、查 inode、再读那点数据（[[7.2 元数据路径瓶颈]] §2 的 open+read 流转）。在共享存储上，这些元数据操作是一次次网络 RPC；小文件负载把瓶颈从「带宽」搬到了「元数据 QPS 与网络往返」。这也是为什么同样的盘，跑大文件顺序读（3D 医学影像那种）和跑小文件随机读，喂 GPU 的能力可以差一个量级。

**CPU 段的隐形账**【量级】：JPEG 解码不便宜。一张图解码 + 增广动辄毫秒级，而 H100 算一个 batch 可能就几十毫秒——**几十张图的解码就能吃掉一个 step 的全部预算**。所以 DataLoader 要开多个 worker 进程/线程并行解码。但 worker 不是越多越好（§4 讲它怎么反噬）。

**H2D 段的分水岭**【前提】：batch 最终要过 PCIe 进显存。只有源缓冲是 **pinned（页锁定）内存**时，`cudaMemcpyAsync` 才真异步、才能和 GPU 计算重叠；pageable 内存会让拷贝退化为同步，H2D 与计算串行——这条分水岭在 [[8.1 GPU 内存层次与数据搬运]] §2 讲透了，这里只强调：**它直接决定第三段能不能藏进计算背后**。

## 3. 队列吸收方差，补不了均值

三段流水线之间靠**预取队列**（prefetch queue）解耦——workers 把准备好的 batch 塞进队列，训练循环从队列取。这个队列是理解「吞吐 vs 尾延迟」的关键，也是最容易被误用的杠杆。

先分清两种完全不同的病（对照上图中部两条时间线）【设计】：

- **饥饿（稳态问题）**：数据段的**平均**时间 > 计算段的平均时间。队列会被稳定抽干，之后**每一步**都要等。这是吞吐不足——DataLoader 的持续供给速率低于 GPU 的消费速率。
- **毛刺（方差问题）**：数据段平均够快，但**偶尔**有一个 batch 特别慢（一次元数据慢查询、一次 GC、一次网络重传）。如果队列里有存货，这次慢就被存货盖住了，GPU 感觉不到。

这就推出那条最重要、也最反直觉的结论【实践】：

> **队列深度吸收的是方差（尾延迟），补不了均值（吞吐不足）。**

用排队论说就是 Little's law——队列里的平均存货 = 消费速率 × 平均停留时间：

$$
L = \lambda W
$$

其中 λ 是消费速率、W 是一个 batch 在队列里的平均停留时间。想让队列常态有货以吸收毛刺，你需要生产速率**略高于**消费速率，让队列能在毛刺间隙回填。如果生产速率本来就低于消费速率（饥饿），队列只会一路排空到 0，加多深都一样——**加大 prefetch 深度治不了饥饿，只是把撞墙推迟几个 step**。

反过来，这也解释了尾延迟为什么在训练里格外毒【因果】：单次数据段的 p99 尾延迟，只要**大于队列存货能撑的时间**，就会直接变成一次 GPU 空泡。所以 [[9.5 p99 毛刺定位]] 里那些「周期性 p99 尖峰」，在训练场景的翻译就是「GPU 利用率周期性凹陷」——尾延迟和 GPU 利用率是同一枚硬币。

## 4. 因果链：CPU、内存、网络如何互相拖累

前三节把三段当成独立的看。真实负载里它们**共享同一台主机的 CPU、主存和网卡**，于是互相踩脚——这才是归因难的地方。

**① 跨 epoch 的页缓存：第二个 epoch 突然变快**【事实】。第一个 epoch 冷读，样本从存储真的读上来；读上来的数据会留在 [[1.2 Page Cache 命中与未命中]] 的页缓存里。如果**整个数据集小于主机内存**，第二个 epoch 就大面积命中页缓存，存储段几乎不干活，吞吐陡增。这是好事，但埋了两个坑：（a）你以为存储够快，其实是内存在替它扛——**数据集一旦大于内存，页缓存失效，每个 epoch 都冷读，真实瓶颈才暴露**；（b）跑 benchmark 时这就是作弊（[[8.8 MLPerf Storage]] 专门要求数据集 > 内存来堵这个洞）。

**② worker 数量：加到一定程度开始反噬**【取舍】。worker 太少 → CPU 解码跟不上，存储明明有货 GPU 却挨饿；worker 太多 → 进程/线程数超过物理核，上下文切换和调度开销上升，而且每个 worker 都要一份预取缓冲，**主存占用和主存带宽争用**跟着涨。存在一个甜点，且这个甜点会被同机的其他负载推着走（见下条）。

**③ 抢核、抢主存带宽、抢网卡**【因果】。这个负载不是只有 DataLoader 在跑：
- [[8.6 Checkpoint 同步异步分片]] 的**后台落盘线程**每 30 分钟醒一次，跟 decode workers 抢 CPU、抢主存带宽——checkpoint 期间训练吞吐抖一下，根因常在这里（8.6 §6 排障表已埋了指向本篇的线索）；
- 共享存储走网络时，收包的 **softirq / 网卡中断**也吃 CPU，和 decode workers 在同一批核上打架；
- decode 把数据从内核缓冲拷到用户缓冲、再拷进 pinned，每一次都吃**主存带宽**（[[8.1 GPU 内存层次与数据搬运]] §3 那笔「内存总线穿越几次」的账）。主存带宽是有限的，H2D 拷贝、decode 拷贝、checkpoint 落盘拷贝共用这一条总线。

**④ epoch 边界的网络 incast**【事实】。每个 epoch 开始要 shuffle，然后所有 worker 几乎同时向存储发起一批读——**多打一**的 incast 时刻（[[7.6 AI 存储 vs 传统 NAS]] §3、[[4.7 PFC ECN 与 DCQCN]]）。交换机缓冲被瞬间打满，触发丢包重传或 PFC 反压，这批读的尾延迟被拉高，队列还没预热就被抽干——于是 epoch 开头几个 step 特别容易空泡。这正是 [[9.5 p99 毛刺定位]] 里「每 epoch 一次的周期毛刺」的指纹。

把这四条连起来就是本章反复强调的那句话：**吞吐、尾延迟、CPU、内存、网络不是五个独立指标，是同一个数据路径在五个截面上的投影**。动其中一个，另外四个都会响应。

## 5. 归因：三刀切下去，层就定位了

面对「GPU 利用率只有 70%」，不要猜，按下图决策树切三刀【方法】：

1. **第一刀——profiler 看 step 分解**。用框架自带的 profiler（PyTorch Profiler、`nsys` 等）看每个 step 的 `data_time`（等数据）占 `step_time` 的比例。占比高 → 确实是数据供给问题，继续切；占比低 → 空泡在别处（通信、kernel launch、显存换页），不在 DataLoader，别在这儿浪费时间。
2. **第二刀——换合成数据**。把 DataLoader 换成「内存里直接吐随机张量」的合成数据源，绕开存储和解码。空泡消失 → 瓶颈在 DataLoader 这三段里（分岔点）；空泡还在 → 问题在 GPU 侧或 H2D，回第一刀重看。
3. **第三刀——存储/主机分层定位**。空泡因换合成数据而消失，说明是 DataLoader 的锅，再分「存储段」还是「主机段」：
   - 存储段：`iostat -x`（[[9.2 iostat 指标解读]]）看设备是否饱和、`nfsstat` 看 NFS 层重传与队列、对象存储看前缀热点。**第二个 epoch 明显变快 = 页缓存在帮忙**，数据集大于内存后会消失（§4①）。
   - 主机段：`mpstat`/`top` 看 decode workers 是否吃满核、pinned 是否用对（pageable 假异步会让 H2D 与计算不重叠）。

这三刀的价值在于**每一刀都排除掉半棵树**：先分清「是不是数据问题」，再分清「存储还是主机」，最后才动工具箱。顺序反了——一上来就换盘、加 worker——大概率是无效调参。

## 6. Modern C++：一个有界预取队列 + 空泡计数

把 §3 的队列和 §4 的背压写成代码。这对有 C++ 多线程基础的读者是熟悉的**生产者-消费者**：workers 生产（读+解码+pin），训练循环消费；队列满则背压、空则记一次空泡。关键是那个 `starvation_` 计数器——它就是 §5 第一刀之前你能自己埋的**空泡第一手证据**。

```cpp
#include <condition_variable>
#include <cstddef>
#include <cstdint>
#include <deque>
#include <mutex>
#include <optional>
#include <thread>
#include <vector>

// 一个已解码、已 pin、可直接 H2D 的 batch(pinned 才真异步,8.1 §2)
struct Batch {
    PinnedBuffer host;            // 复用 8.1 的 RAII pinned 缓冲
    std::uint64_t index = 0;
};

// 有界预取队列:满则阻塞生产者(背压),空则给消费者记一次空泡
class PrefetchQueue {
public:
    explicit PrefetchQueue(std::size_t capacity) : cap_{capacity} {}

    // 生产者(worker):队列满就等 —— 把「解码比消费快」的多余产能挡在门外,
    // 否则 workers 会无限吃主存去缓冲用不上的 batch(§4② 的内存账)
    void push(Batch b) {
        std::unique_lock lk{mu_};
        not_full_.wait(lk, [&] { return q_.size() < cap_ || closed_; });
        if (closed_) return;
        q_.push_back(std::move(b));
        not_empty_.notify_one();
    }

    // 消费者(训练循环):队列空 = GPU 要停等 = 一次空泡,先计数再阻塞
    std::optional<Batch> pop() {
        std::unique_lock lk{mu_};
        if (q_.empty() && !closed_) {
            ++starvation_;                    // ★ 空泡归因的第一手证据
            not_empty_.wait(lk, [&] { return !q_.empty() || closed_; });
        }
        if (q_.empty()) return std::nullopt;  // 已关闭且抽干
        Batch b = std::move(q_.front());
        q_.pop_front();
        not_full_.notify_one();
        return b;
    }

    void close() {
        { std::lock_guard lk{mu_}; closed_ = true; }
        not_empty_.notify_all();
        not_full_.notify_all();
    }

    std::uint64_t starvation() const {
        std::lock_guard lk{mu_};
        return starvation_;
    }

private:
    mutable std::mutex mu_;
    std::condition_variable not_full_, not_empty_;
    std::deque<Batch> q_;
    std::size_t cap_;
    std::uint64_t starvation_ = 0;
    bool closed_ = false;
};

// 拥有一组 worker 的 DataLoader;RAII 保证析构时干净收尾
class DataLoader {
public:
    DataLoader(std::size_t num_workers, std::size_t queue_depth, SampleSource& src)
        : queue_{queue_depth}, source_{src} {
        workers_.reserve(num_workers);
        for (std::size_t i = 0; i < num_workers; ++i)
            workers_.emplace_back([this](std::stop_token st) { run(st); });
    }

    std::optional<Batch> next() { return queue_.pop(); }  // 训练循环调用
    std::uint64_t bubbles() const { return queue_.starvation(); }

    ~DataLoader() { queue_.close(); }   // 先唤醒阻塞的 workers,再由 jthread 析构 join

private:
    void run(std::stop_token st) {
        while (!st.stop_requested()) {
            auto raw = source_.next();               // 存储读:IO/网络,可能阻塞、可能长尾
            if (!raw) break;
            queue_.push(decode_and_pin(std::move(*raw)));  // CPU 解码+增广+拷进 pinned
        }
    }

    PrefetchQueue queue_;               // 先声明 → 最后析构:workers join 后队列才销毁
    SampleSource& source_;
    std::vector<std::jthread> workers_; // 后声明 → 最先析构:stop + join
};
```

**逐段讲解**：

- **背压不是可选项**：`push` 在队列满时阻塞，把「decode 比 GPU 消费快」时多出来的产能挡住——否则 workers 会无限缓冲用不上的 batch，把主存吃穿（§4② 的内存账），这是生产者-消费者最经典的无界队列翻车；
- **`starvation_` 就是可观测性**：消费者发现队列空、不得不阻塞，正是一次 GPU 空泡。把它计数暴露出来，你在跑 profiler 之前就有了「空泡次数」的直接读数——这是 §5 三刀法的地基；
- **析构顺序是 RAII 的关键**：成员按声明逆序析构，`workers_` 声明在最后 → 最先析构。`~DataLoader` 体先调 `queue_.close()` 唤醒所有阻塞在 `push`/`pop` 的 worker，随后 `std::jthread` 逐个 `request_stop` + `join`，最后才轮到 `queue_` 销毁——**队列的生命周期严格长于使用它的线程**，不会出现「线程还在 push、队列已析构」的 use-after-free；
- **锁纪律**：锁只保护队列状态，`source_.next()`（可能阻塞在网络 IO）和 `decode_and_pin`（CPU 密集）全程**不持锁**——否则一个 worker 卡在慢 IO 上会连累所有 worker，这和 [[8.6 Checkpoint 同步异步分片]] §5「IO 期间不持锁」是同一条铁律；
- **扩展方向**：worker 用进程还是线程取决于是否受 Python GIL 之类的约束；`SampleSource` 背后可以是本地盘、NFS 或对象存储 SDK；`decode_and_pin` 可以进一步把解码 offload 到 GPU（NVJPEG 之类）——骨架不变，只是把 CPU 段的活挪走。

## 7. 修复杠杆按层对号

归因定层之后才谈修复。每个杠杆都有明确的**「不适用」清单**——先归因后动刀，顺序反了全是无效调参（对照上图底部）：

| 层 | 杠杆 | 机制 | 不适用于 |
| --- | --- | --- | --- |
| 存储 | 小文件打包成顺序大文件（tar / WebDataset 类） | 把「海量元数据 + 随机小读」变成「少量顺序大读」，绕开 [[7.2 元数据路径瓶颈]] | 已经是大文件顺序读的负载 |
| 存储 | 本地 NVMe 做二级缓存（[[7.3 JuiceFS 架构]] 式） | 热数据落到本地盘，跨 epoch 复用，省掉远端网络往返 | 数据集远大于本地盘、或每 epoch 全量唯一 |
| 存储 | 拆入口（多机头 / 分片） | N 个并发入口抬 N 倍聚合带宽（[[7.6 AI 存储 vs 传统 NAS]] §4） | 瓶颈根本不在存储（在 CPU/H2D） |
| 主机 | 增加 decode workers | 并行解码，抬高 CPU 段吞吐 | 已经吃满物理核——再加只增上下文切换（§4②） |
| 主机 | 换便宜解码 / 离线预处理 | 预解码成张量、或用更轻的编码，砍掉每 epoch 的 CPU 重复劳动 | 增广必须在线随机（预处理会固化增广） |
| 主机 | pinned 内存池化 | 让 H2D 真异步，藏进计算背后（[[8.1 GPU 内存层次与数据搬运]] §2） | 已经在用 pinned |
| 重叠 | 加大 prefetch 深度 | 吸收数据段的尾延迟毛刺 | **稳态饥饿**——队列吸收方差补不了均值（§3） |
| 重叠 | GDS 直读（[[8.2 GDS 与 cuFile]]） | 大块顺序读绕过页缓存与 CPU 拷贝，直进显存 | **小文件海**——GDS 救不了元数据瓶颈（8.2 §2） |

最后一行是最常见的误区：GDS/直读听起来是「更快的数据路径」，但它只在**大块顺序读**上有意义（3D 影像那种）；对 ResNet-50 的小文件海，瓶颈在元数据和 CPU 解码，GDS 一点忙帮不上。**杠杆要对着定位出来的那一层用。**

## 8. 排障清单

| 症状 | 先测什么 | 常见根因 → 处置 |
| --- | --- | --- |
| GPU 利用率低但稳定 | profiler 看 `data_time` 占比（§5 第一刀） | 占比高 = 数据供给不足，继续切；占比低 = 空泡在 GPU 侧/通信，不在本篇 |
| 换合成数据后利用率满 | 对比合成 vs 真实数据源 | 瓶颈确在 DataLoader 三段——进第三刀分存储/主机 |
| 第二个 epoch 明显变快 | 数据集大小 vs 主机内存 | 页缓存在替存储扛（§4①）；数据集 > 内存后会消失，别把它当存储快 |
| 加 prefetch 深度没用 | 数据段平均时间 vs 计算段 | 稳态饥饿而非毛刺（§3）——队列补不了均值，去抬存储/CPU 吞吐 |
| 加 worker 后反而更抖 | `mpstat` 看核数与上下文切换 | worker 超过物理核（§4②）——回退到甜点值 |
| 每个 epoch 开头几步卡顿 | epoch 边界的网络指标、`nfsstat` 重传 | shuffle 后 incast（§4④、[[4.7 PFC ECN 与 DCQCN]]）——错峰读、预热队列 |
| checkpoint 期间训练吞吐抖 | checkpoint 落盘线程的 CPU/主存占用 | 后台落盘抢核/带宽（[[8.6 Checkpoint 同步异步分片]] §6）——限速落盘或错峰 |
| 「异步」了但 H2D 没重叠 | 缓冲是 pinned 还是 pageable | pageable 假异步（[[8.1 GPU 内存层次与数据搬运]] §2）——换 pinned 池 |
| 存储侧看着不忙但 GPU 还是等 | `iostat` 的 `%util` vs 元数据 QPS | 小文件负载瓶颈在元数据不在带宽（[[7.2 元数据路径瓶颈]]）——打包成大文件 |

## 9. 陷阱与误区

> [!warning] 常见错误
> 1. **把「GPU 空泡」直接等同于「存储慢」**：CPU 解码、pageable H2D、通信都能让 GPU 挨饿——不先归因就换盘，大概率白花钱。
> 2. **用加大 prefetch 深度治稳态饥饿**：队列吸收方差、补不了均值（§3）；饥饿是生产速率 < 消费速率，加深度只是推迟撞墙。
> 3. **拿第二个 epoch 的高吞吐当存储性能**：那是页缓存在帮忙（§4①）；数据集大于内存后原形毕露，也是 benchmark 作弊的来源。
> 4. **worker 越多越好**：超过物理核后上下文切换和主存带宽争用反噬，还要跟 checkpoint 落盘、网络 softirq 抢资源（§4②③）。
> 5. **小文件海上用 GDS**：GDS 只救大块顺序读，救不了元数据瓶颈（§7、[[8.2 GDS 与 cuFile]]）。
> 6. **无界预取队列**：不背压的生产者会把主存吃穿——生产者-消费者的经典翻车（§6）。
> 7. **只看平均 `data_time`，忽略尾部**：单次数据段的 p99 只要超过队列存货能撑的时间，就是一次空泡（§3）——尾延迟就是 GPU 利用率（[[9.5 p99 毛刺定位]]）。
> 8. **忽略同机负载的相互踩脚**：DataLoader、checkpoint 落盘、网络收包共享 CPU/主存/网卡——调优要放在整机视角看，不是孤立调 DataLoader。

## 10. 关键结论

| 结论 | 性质 |
| --- | --- |
| 空泡 = max(0, 数据时间 − 计算时间)；AU（利用率）= 计算 ÷（计算 + 空泡），就是 goodput 换场景 | 事实 |
| 数据路径三段各吃一种资源：存储（IO/网络/元数据）、CPU（解码/主存带宽）、H2D（PCIe/pinned） | 事实 |
| 归因第一步永远是定层，不是换盘：三刀法（profiler → 合成数据 → iostat/nfsstat） | 方法论 |
| 队列深度吸收方差（尾延迟毛刺），补不了均值（稳态饥饿）——两种病要分开治 | 实践结论 |
| 单次数据段 p99 > 队列存货能撑的时间 = 一次 GPU 空泡：尾延迟就是 GPU 利用率 | 因果 |
| 小文件海的瓶颈在元数据 QPS 与网络往返，不在带宽——决定了存储选型与修复杠杆 | 事实 |
| 第二个 epoch 变快 = 页缓存在替存储扛；数据集 > 内存后消失 | 事实 |
| 吞吐/尾延迟/CPU/内存/网络是同一数据路径的五个投影：DataLoader、checkpoint、softirq 抢同一台主机 | 因果 |
| 修复杠杆按定位出的层对号用，每个杠杆都有明确的「不适用」清单 | 取舍 |
