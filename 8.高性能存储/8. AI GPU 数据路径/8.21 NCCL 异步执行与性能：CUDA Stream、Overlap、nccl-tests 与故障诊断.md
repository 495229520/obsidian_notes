# 8.21 NCCL 异步执行与性能：CUDA Stream、Overlap、nccl-tests 与故障诊断

> [!abstract] 本篇解决什么问题
> 把三个问题分开：**调用什么时候返回，结果什么时候能用，整个训练 step 有没有变短。** `ncclAllReduce()` 返回、CUDA stream 到达完成事件、所有 rank 都完成一个训练 step，并不是同一个观察点。只看到两个 stream 上都有活动，也不能认定通信已经被有效隐藏。

[[8.11 cudaMemcpy 与 CUDA Stream]] 给出了 stream/event 的入门模型，本篇把它扩展到多 GPU 的 collective。[[8.12 GPUDirect RDMA]] 解释了 GPU 显存如何进入网络数据路径；这里关心的是这些路径如何被提交、等待、测量和诊断。框架怎样决定何时提交梯度通信，接着看 [[8.22 PyTorch Distributed：ProcessGroupNCCL、DDP、FSDP 与通信计算重叠]]。

**阅读边界。** 本篇不重复展开 Ring/Tree、channel、protocol 和拓扑搜索的实现，只保留性能分析必要的机制。参考资料为核对日能访问到的 NVIDIA 官方文档，其中 NCCL 文档标识为 2.31.2；参数、默认值与特定硬件加速路径须以实际加载的 NCCL/CUDA 版本为准。本文的数字例题、时间线均为**教学构造，不是实测结果**；当前制作环境没有 CUDA GPU，代码未进行 GPU 编译或运行。

## 1. 先区分三种“异步”

### 1.1 CPU 返回，不等于 GPU 已经做完

常规、成功的 NCCL stream 调用负责把操作提交到指定 CUDA stream；数据搬运和规约在设备侧执行。CPU 可以继续向下运行，但不能因此在别的 stream 中无依赖地读写同一缓冲区。NCCL 文档明确把操作入队与设备完成分开，设备完成应使用 CUDA stream/event 等机制观察。[^nccl-stream]

| 层次 | 你实际观察到的事 | 不能直接推出什么 |
|---|---|---|
| Host API / 提交层 | 调用返回，或一组操作完成入队 | 输出显存已可任意读取 |
| CUDA / 设备层 | 某条 stream 到达事件；其此前工作已完成 | 别的 stream、别的 rank、整个训练 step 都已完成 |
| 多 rank / 任务层 | 各 rank 按协议完成本轮计算与通信 | 本轮参数已持久化，或任务可无损故障恢复 |

这里的分层不是额外的 NCCL 协议，而是观察口径。类似 RDMA 中“发了 WR”和“收到了符合语义的 CQE”不能混淆，CUDA/NCCL 也需要明确完成标记；但**CUDA event 不是 RNIC CQE，也不是训练 checkpoint**。

### 1.2 Nonblocking communicator 是另一个维度

CUDA 上的异步执行，不要求先把 communicator 配置为 nonblocking。`config.blocking = 0` 控制的是某些 NCCL 操作的 **host 侧进展与返回行为**；遇到 `ncclInProgress` 时，需要按相应 API 的约定查询 `ncclCommGetAsyncError()` 等待 NCCL 完成这阶段的进展。查询结果变成 `ncclSuccess`，不应被解释为所有关联 CUDA kernel 均已结束。[^nccl-comm]

因此要问完整的一句话：**是 host 线程不等待，还是 GPU 消费 stream 不等待，还是不同 rank 不需要对齐？** 最后一项通常不能随意省略：参与者必须提交匹配的 collective。

## 2. 一次通信的依赖图：生产 → 规约 → 消费

设 `grad` 在 compute stream 中生成，NCCL 在 comm stream 中原地规约，optimizer 又要在 compute stream 中读取 `grad`。正确关系是：

\[
\text{produce}(grad) \prec \text{AllReduce}(grad) \prec \text{consume}(grad)
\]

箭头是**数据依赖**，不是“CPU 代码看起来写在前面”。同一 stream 内有执行顺序；跨 stream 应通过事件、stream wait 或框架的同步接口建立依赖。`cudaStreamWaitEvent()` 让目标 stream 的后续工作等待事件，不是让调用它的 CPU 线程等待事件完成。[^cuda-stream]

![[图片/SVG/8_8_8_21_1.svg|900]]

图中 compute stream 在生产完成后可以执行**不访问 `grad` 的独立工作**。它读取规约结果以前仍然要等 `reduced`。省略这次等待不是性能优化，而是允许数据竞争。

### 2.1 同一 stream 的正确性与代价

把生产、AllReduce、消费全放在同一 stream，依赖容易表达；但同一 stream 内后续计算不能越过前面的 collective。跨 stream 的目的，是让真正无依赖的工作获得并发机会，不是让依赖本身消失。

跨 stream 安全性至少包含两份账：**执行顺序**和**缓冲区生命周期**。最后一个 GPU 使用者结束前，不能复用或释放内存。双缓冲时，每个槽位都要有自己的使用完成条件；不要仅因为本轮 CPU 提交结束就覆盖上轮缓冲。

### 2.2 别把 H2D 的条件套到 NCCL 上

Pinned host memory 是讨论 host↔device 异步拷贝的重要条件，但 GPU↔GPU 的 NCCL 通信不因此普遍要求一个用户提供的 pinned host buffer。也不能把 NCCL 一概视为“独立 copy engine 搬数据”：常见实现路径运行 GPU 通信 kernel，会与计算竞争 SM、HBM 或互连资源；具体版本和平台还可能提供不同的卸载/执行路径。性能判断必须来自所用路径的 trace。[^nccl-overview][^nccl-perf]

默认 stream 也不能笼统理解为“和一切 stream 都同步”。legacy default stream、per-thread default stream、以 `cudaStreamNonBlocking` 创建的 stream，其隐式同步规则不同。新代码使用显式 stream 和依赖，诊断时记录实际创建方式。[^cuda-stream]

## 3. CUDA/NCCL 代码：只借用资源，显式表达等待

下面三个 C++/CUDA 代码块按顺序放入同一个 `.cu` 文件。它们组成**可嵌入现有 NCCL 程序的函数**，不是包含 rendezvous、设备分配和 communicator 初始化的独立应用。使用 C++17；指针与句柄全部是借用，不转移所有权。

调用前由外层 RAII 对象管理设备内存、stream、event 和 communicator。约束如下：`grad`、`scratch` 是不重叠的本设备显存，容量均至少为 `n` 个 `float`；`n > 0`；`world > 0`；设备已选定；所有 rank 以相同顺序调用同规格操作。这里使用常规 blocking communicator，**不放在尚未结束的 NCCL group 内**。

### 3.1 错误要在提交点检查

错误检查帮助区分“没有成功提交”与“成功提交后卡住”。抛异常并不自动恢复其他 rank；跨 rank 的失败处理由外层任务管理器负责。CUDA 的后续同步也可能暴露先前的异步错误，因此不能只检查一次返回码。

```cpp
#include <cuda_runtime.h>
#include <nccl.h>
#include <cstddef>
#include <stdexcept>
#include <string>

inline void cuda_check(cudaError_t rc) {
    if (rc != cudaSuccess) {
        throw std::runtime_error(cudaGetErrorString(rc));
    }
}

inline void nccl_check(ncclResult_t rc) {
    if (rc != ncclSuccess) {
        throw std::runtime_error(ncclGetErrorString(rc));
    }
}
```

这段只处理错误传播，没有多执行主体，不需要人为添加时序图。`nccl_check()` 特意不接受 `ncclInProgress`，因为下面的函数不适用于 nonblocking communicator；不要把它直接复制到另一种初始化配置中。

### 3.2 用两个小 kernel 表达“产生”和“消费”

`fill_value()` 既用于产生梯度示意值，也用于独立写 `scratch`；`scale_value()` 是结果消费的简化版本。它们没有读取未初始化的 `scratch`。网格步进允许同一组 launch 参数处理不同长度。

```cpp
__global__ void fill_value(float* out, std::size_t n, float value) {
    const auto stride = static_cast<std::size_t>(blockDim.x) * gridDim.x;
    auto i = static_cast<std::size_t>(blockIdx.x) * blockDim.x + threadIdx.x;
    for (; i < n; i += stride) {
        out[i] = value;
    }
}

__global__ void scale_value(float* data, std::size_t n, float factor) {
    const auto stride = static_cast<std::size_t>(blockDim.x) * gridDim.x;
    auto i = static_cast<std::size_t>(blockIdx.x) * blockDim.x + threadIdx.x;
    for (; i < n; i += stride) {
        data[i] *= factor;
    }
}
```

这些只是显存读写教学 kernel，不代表真实 backward 或 optimizer 的性能特征。尤其 `fill_value(scratch)` 会消耗 HBM 带宽，和通信重叠后不一定更快。

### 3.3 提交函数：只在真正的消费点等待

生产事件连接 compute→comm；规约事件连接 comm→compute。`finished` 只表示本函数在 compute stream 上的尾部完成条件，外层在复用缓冲或释放资源前需要正确等待它。下面保留独立工作在等待之前，以免无意把流水线串行化。[^nccl-stream][^cuda-stream]

```cpp
void enqueue_bucket(float* grad, float* scratch, std::size_t n,
                    int rank, int world, ncclComm_t comm,
                    cudaStream_t compute, cudaStream_t communication,
                    cudaEvent_t produced, cudaEvent_t reduced,
                    cudaEvent_t finished) {
    fill_value<<<128, 256, 0, compute>>>(grad, n, static_cast<float>(rank + 1));
    cuda_check(cudaGetLastError());
    cuda_check(cudaEventRecord(produced, compute));
    cuda_check(cudaStreamWaitEvent(communication, produced, 0));
    nccl_check(ncclAllReduce(grad, grad, n, ncclFloat, ncclSum,
                            comm, communication));
    cuda_check(cudaEventRecord(reduced, communication));
    fill_value<<<128, 256, 0, compute>>>(scratch, n, 3.0F);
    cuda_check(cudaGetLastError());
    cuda_check(cudaStreamWaitEvent(compute, reduced, 0));
    scale_value<<<128, 256, 0, compute>>>(grad, n, 1.0F / world);
    cuda_check(cudaGetLastError());
    cuda_check(cudaEventRecord(finished, compute));
}
```

![[图片/SVG/8_8_8_21_1.svg|900]]

时序图揭示的是：**CPU 已经离开函数时，GPU 可能还在等其他 rank 的输入。** 计算 stream 的等待由设备依赖解除，不需要 CPU 持续投递“唤醒”动作。

检查结果时先保证 `finished` 已完成，再把 `grad` 拷到 host 检查。对于精确可表示的小 rank 数，期望每个元素接近 `(world + 1) / 2`，比较时保留浮点容差。不要在热路径里逐元素 D2H；正确性模式与性能模式应分开运行。

## 4. Group 的作用，以及它为什么会缩小 overlap 窗口

`ncclGroupStart()` / `ncclGroupEnd()` 用于聚合操作，也常用于单个 CPU 线程管理多个 GPU 时协调提交。**Group 不是“把所有等待取消”。** Group 内某个 NCCL 调用返回时，操作未必已经进入 CUDA stream；只有外层 group 按其同步/非阻塞约定成功完成提交后，才能把后续 CUDA 事件当作该组的完成边界。不要在未结束的 group 中等待那些尚未入队的工作。[^nccl-group]

![[图片/SVG/8_8_8_21_2.svg|900]]

### 4.1 一个 group 混用多条 stream

NCCL 官方说明：在同一个 group 中使用多条 stream，会引入这些参与 stream 之间的同步关系。操作需要等相关 stream 的前置工作，相关 stream 后续工作也不能随意越过该组。这可能把原本较独立的流水线汇合到同一道关口。这里说的是**参与该组的 stream**，不是无条件同步整个设备上的每一条 stream。[^nccl-stream]

设计时分别检查：为了减少 host launch 开销而合批，是否让本可提前启动的小操作等待了另一个慢生产者？合批变快的是提交部分，付出的可能是等待窗口。

### 4.2 Nonblocking 的两阶段观察

图右侧将 nonblocking 场景简化为 `ncclInProgress → 查询进展 → ncclSuccess → CUDA 完成事件`。真实程序还要处理错误码、超时、退出与 communicator 生命周期。`ncclCommGetAsyncError()` 一方面用于相应 API 的进展查询，也用于检查异步通信错误；它不能替代对输出缓冲区的 CUDA 完成依赖。[^nccl-comm]

不要无限轮询，不要在 fatal CUDA/NCCL 错误后继续拿旧输出训练，也不要把“重试同一个 collective”当成默认恢复协议。

## 5. 从“有重叠”到“有收益”：先算关键路径

定义同一工作范围内，单独计算耗时为 \(C\)，单独通信耗时为 \(M\)。忽略启动、依赖和资源竞争时，串行耗时是 \(C+M\)，完全重叠的理想下界是 \(\max(C,M)\)。这是**简化模型**，不是 NCCL 给出的性能保证。

实际联合运行可写成：

\[
T_{joint}=\max(C',M')+T_{unhidden}+T_{orchestration}
\]

其中 \(C'\)、\(M'\) 是并发后各自的耗时，可能大于单独运行的值；\(T_{unhidden}\) 表示未能覆盖的前后段或依赖气泡。需要避免重复计数：分段时让这些时间区间互不重叠。

![[图片/SVG/8_8_8_21_3.svg|900]]

图中的三组数完全是构造例子：串行 `8 + 6 = 14 ms`，理想并发 `8 ms`，争用严重时并发变成 `15 ms`。最后一种虽然同时存在计算和通信，却比串行更慢。

### 5.1 四个条件缺一不可

| 条件 | 直接检查什么 | 不满足时的表现 |
|---|---|---|
| 数据独立 | 计算是否读写正在通信的 buffer | 必须等待，不能硬做 overlap |
| 提交及时 | CPU 是否提前入队；是否被 Python、数据加载或同步阻塞 | GPU 空白区，通信启动偏晚 |
| 资源有余量 | SM、HBM、PCIe/NVLink、NIC 是否争用 | 单段 kernel 变长，整体反而变慢 |
| rank 进度可配合 | 最晚 rank 何时到达同一 collective | 早到 rank 的通信区间变长 |

这些检查是排查顺序，不是把所有性能问题都归到网络。数据来源慢导致 rank 晚到，应该回到 [[8.7 DataLoader 与 GPU 空闲归因]] 的 producer 路径，而非首先改 NCCL 环境变量。

### 5.2 Bucket 与 chunk 不在同一层

DDP bucket 是框架聚合梯度、触发一次 collective 的单位；NCCL 的内部 chunk/channel 是执行某次 collective 时的数据切分与并行组织。两者相互影响，但 `bucket_cap_mb` 并不等于设置 NCCL 的一个 chunk。

小 bucket 可以早发，但可能增加 collective 次数和固定开销；大 bucket 可以摊薄固定开销，却要等更多梯度就绪。调 bucket 的最终目标是缩短 step 的关键路径，不是让单次大 AllReduce 的带宽数字最大。这一过程在下一篇用 reducer 时间线展开。

### 5.3 只把模型用于该模型能回答的问题

环形点对点传输、均衡负载、忽略拓扑差异的 AllReduce，可粗略写为：

\[
T_{AR}\approx2(N-1)\alpha+\frac{2(N-1)}{N}\frac{S}{B}
\]

这里 \(S\) 是每 rank 完整输入的字节数，\(\alpha\) 是模型中的每阶段固定开销，\(B\) 是有效传输速率。它帮助理解小消息看延迟、大消息看带宽；**不能据此断言真实 NCCL 必选 Ring，也不能直接预测 NVLS、网络内规约或多层拓扑的结果**。公式中的总字节系数与 nccl-tests 的标准带宽归一化关系见下一节。[^tests-perf]

## 6. nccl-tests：先建立通信基线

### 6.1 先记录能复现实验的环境

同一个命令的结果可能受到 GPU/NIC 拓扑、库版本、进程绑核、容器权限、频率和后台负载影响。以下命令用于采集设备与版本，不会替你证明 RDMA 路径已启用；实际路径还要看 NCCL 日志及设备计数器。[^nccl-network]

```bash
nvidia-smi
nvidia-smi topo -m
nvcc --version
ibv_devinfo
```

`ibv_devinfo` 需要相应 RDMA 用户态工具，没有 RDMA 设备时不应把它的失败当作单机 NVLink 测试失败。记录软件包版本及实际加载库路径；只记录 `nvcc` 版本不足以说明 PyTorch 或 nccl-tests 动态加载了哪一版 NCCL。

### 6.2 编译：单进程与 MPI 不是同一种构建

在自己的环境中克隆官方仓库，固定到选定的 tag/commit，保存 `git rev-parse HEAD`。路径变量必须替换为真实的 CUDA/NCCL 安装目录。官方构建支持 `CUDA_HOME`、`NCCL_HOME`，跨进程/节点测试使用 MPI 构建。[^tests-readme]

```bash
git clone https://github.com/NVIDIA/nccl-tests.git
cd nccl-tests
git rev-parse HEAD
make -j CUDA_HOME=/usr/local/cuda NCCL_HOME=/opt/nccl
./build/all_reduce_perf -b 8 -e 256M -f 2 -g 2 -w 10 -n 50 -c 1
```

这里 `-g 2` 是一个测试线程管理两张 GPU，**不是两个进程**。从 8 字节按倍率 2 扫到 256 MiB，预热 10 次、测量 50 次，开启正确性检查。正式归档需同时保存原始 stdout、stderr、测试 commit 和完整环境；这里不伪造一份“典型输出”。

多机前先重新以 MPI 模式构建。下面是 **Open MPI 形式的两节点、每节点两 rank、每 rank 一张 GPU** 示例；其他 MPI 或 Slurm 环境请使用其自己的启动方式。`host-a`、`host-b` 是占位名称，不是固定机器。

```bash
make clean
make -j MPI=1 MPI_HOME=/opt/openmpi \
    CUDA_HOME=/usr/local/cuda NCCL_HOME=/opt/nccl
mpirun -np 4 --host host-a:2,host-b:2 \
    ./build/all_reduce_perf -b 8 -e 256M -f 2 -g 1 -w 10 -n 50 -c 1
```

MPI 的启动、CPU 绑定、GPU 可见性和动态库路径要在各节点一致验证。不要给每个 rank 都设只包含 GPU0 的同一 `CUDA_VISIBLE_DEVICES` 后，又期待自动使用该节点两张卡。总体 GPU rank 数来自**进程数 × 每进程测试线程数 × 每线程 GPU 数**，不能只看 `-g`。[^tests-readme]

### 6.3 正确性与规模要先于峰值

读输出时，先看列头：`size`、`count`、`type` 描述数据规格，`time` 的单位以该版本表头为准，`algbw` 与 `busbw` 使用 GB/s。若时间列标为 `(us)`，换算成秒应乘以 `10^-6`，不能把该列数值直接当成毫秒或秒。

先确认进程/rank 数正确、无数据校验错误，再从单节点两卡扩到全节点、双节点、目标规模。对 NCCL 性能输出分别看 out-of-place 与 in-place 栏，不把两种模式混成一个值；`#wrong` 等校验结果应符合当前测试版本的成功要求。显存使用不只有单个 `-e` 对应的缓冲，扩大规模前留出余量。

仅测一个 1 GiB AllReduce，不能代表一个由几十个小 bucket 组成的 backward。基线应覆盖实际应用会发出的 collective 类型、dtype 和 size 分布。对于 FSDP，补测 `all_gather_perf` 与 `reduce_scatter_perf`，并对齐它们的完整张量/每 rank 分片口径。[^tests-readme][^tests-perf]

## 7. algbw、busbw 与物理链路：同一个数的三种边界

NCCL tests 定义：

\[
\operatorname{algbw}=\frac{S}{t},\quad
\operatorname{busbw}_{AR}=\operatorname{algbw}\cdot\frac{2(N-1)}{N}
\]

AllGather、ReduceScatter 的换算系数为 \((N-1)/N\)。对这两类操作，文档中的 \(S\) 是**完整聚合数组**的字节数，而不是 API 中单 rank 的 sendcount/recvcount 对应字节数。不要差一个 world size。[^tests-perf]

![[图片/SVG/8_8_8_21_4.svg|900]]

### 7.1 一组可以手算的例子

假设 8 个 rank，每 rank AllReduce 的输入为 256 MiB，测得一次操作用时 2.00 ms：

\[
S=256\times2^{20}=268{,}435{,}456\text{ B}
\]
\[
\operatorname{algbw}=134.217728\text{ GB/s}
\]
\[
\operatorname{busbw}=134.217728\times1.75
=234.881024\text{ GB/s}
\]

这里 MiB 是二进制容量单位，GB/s 按十进制 \(10^9\) 换算。**以上都是假设输入下的算术结果，不是某型号 GPU 的成绩。**

### 7.2 为什么不能据此说“网卡跑了 235 GB/s”

`busbw` 是从操作时间和大小计算的 collective 归一化指标，不是抓取某块 NIC 的 TX/RX counter 得出的值。多 GPU、多轨、层级路径、NVLink 和网络内规约，会让“单张 NIC 的某方向带宽”与这个归一化指标不是同一口径。对硬件峰值作比较时，应先明确瓶颈域、方向、算法/卸载路径与聚合范围。[^tests-perf][^nccl-perf]

端口 counter 要用采样间隔内的增量，确认单位是字节、包还是设备规定的数据单位，并排除其他业务流量。不要把设备标称双向聚合带宽和某个单向结果比较，也不要把八张卡的总吞吐与单卡指标直接相除。

## 8. 测量范围：host 提交、设备通信、训练关键路径

### 8.1 三个计时器回答三个问题

![[图片/SVG/8_8_8_21_5.svg|900]]

| 测量范围 | 方法 | 适合回答的问题 |
|---|---|---|
| Host 提交 | CPU 时钟包围调用，不等 GPU | API/调度提交是否昂贵 |
| 设备侧通信区间 | 在正确 stream 上记录 CUDA start/stop event | 该位置的 collective 连同设备侧等待用了多久 |
| 完整工作窗口 | 预热后统一边界，完成所有相关 GPU 工作，比较各 rank | 实际 step/窗口是否缩短，慢 rank 在哪里 |

通信 event 区间可能包括等待其他 rank 的时间。它不是“纯链路线上传输时间”。早到 rank 的 NCCL kernel 持续很久，既可能是网络慢，也可能是别的 rank 很晚才提交同一 collective。

### 8.2 用 CUDA event 测单个提交窗口

下面仍是借用资源的片段：`start`、`stop` 必须以**启用计时**的 event 创建；`grad` 已就绪，所有 rank 正在执行相同测试，没有未完成 group，`communication` 是该 NCCL 操作使用的 stream。输入准备与预热在计时范围外，避免把首次初始化混进样本。

```cpp
cuda_check(cudaEventRecord(start, communication));
nccl_check(ncclAllReduce(grad, grad, n, ncclFloat, ncclSum,
                        comm, communication));
cuda_check(cudaEventRecord(stop, communication));

cuda_check(cudaEventSynchronize(stop));
float milliseconds = 0.0F;
cuda_check(cudaEventElapsedTime(&milliseconds, start, stop));
```

![[图片/SVG/8_8_8_21_5.svg|900]]

图中 host 的等待发生在 `cudaEventSynchronize(stop)`，不是 `ncclAllReduce()` 返回处。这里为了简单等待单个样本；**生产级诊断还需异步错误检查和任务超时管理**，不能把这一小段当成完整容错循环。大量重复测量时，每次强制同步也会改变流水线结构，所以应同时测批量窗口。

跨 stream 测 end-to-end 时，结束 event 必须位于**已等待通信完成的消费 stream**之后。只在 compute stream 的最后一个独立 kernel 后放 stop，却未把 comm stream 汇入该边界，会漏计仍在进行的通信。

### 8.3 分布式统计也要说明边界

对于一次严格配对的测试轮次，可以查看各 rank 的耗时及其中最大值。对一段多 step 窗口，可在窗口前对齐、窗口后完成设备工作，再以最慢 rank 的窗口时间计算总体样本吞吐。两种统计都不是任意混在一起的“P99”。若要逐 step P99，应保存逐步样本、rank 和 collective 标识，明确预热剔除、样本数与聚合规则。

不要把独立的单 rank P99 再取最大值，就称作跨 rank 配对样本的 P99；它们的统计对象不同。这里的原则和 [[8.7 DataLoader 与 GPU 空闲归因]] 中区分设备空闲区、CPU 供给等待一样：先确定观测范围，再解释数值。

## 9. Nsight Systems：用 trace 验证“谁在等谁”

下面用短测试窗口捕获 CUDA、NVTX 和 OS runtime 活动。实际可用参数以安装版本 `nsys profile --help` 为准；输出路径应唯一，避免多个 rank 覆盖同一文件。[^nsys]

```bash
nsys profile --trace=cuda,nvtx,osrt --sample=none \
    -o nccl-single-node \
    ./build/all_reduce_perf -b 16M -e 16M -g 2 -w 5 -n 20 -c 1
```

这条命令启动并观测测试进程，并不替代 baseline；profiler、详细日志、正确性检查都可能扰动时间。先留一份未开启重型观测的性能结果，再做短窗口 trace。

读 trace 时沿同一轮数据依赖追踪：CPU 提交、生产 kernel、comm stream 的前置依赖、通信 kernel、消费等待解除、optimizer。然后横向比较各 rank，找到**第一个偏离正常进度的位置**。

| Trace 现象 | 可以提出的假设 | 下一步证据 |
|---|---|---|
| NCCL API 很晚才出现 | CPU、Python、DataLoader 或梯度 ready 晚 | CPU 栈、前置算子、输入批次时间 |
| API 已提交，设备执行晚 | stream 前置依赖或 GPU 资源排队 | event/wait 和 compute kernel 占用 |
| 部分 rank 通信长，另一 rank 提交晚 | 到达偏斜，不一定是 fabric | 同一 collective 的跨 rank 时间线 |
| 所有 rank 都及时提交且通信慢 | 路径/链路/拥塞或算法选择问题 | NET/GRAPH 日志、NIC/switch counter |
| 并发后 GEMM 与通信同时变长 | 资源竞争 | 单独/联合三组对照、HBM/SM 指标 |

这是**归因假设表**，不是仅凭一个 profiler 截图就能下的定论。

## 10. 故障诊断：从最早错误开始，而非从最后一个 timeout 开始

![[图片/SVG/8_8_8_21_6.svg|900]]

### 10.1 第一层：程序是否提交了同一件事

核对各 rank 的 communicator/group、collective 顺序、count、dtype、reduce op、root（有 root 的操作）、P2P 对端与参与集合。某个 rank 少跑一轮、提前异常退出，或者把 AllReduce 和 AllGather 交叉提交，剩余 rank 的超时可以是后果。NCCL 的通信契约不能由“每个 rank 的代码看着差不多”替代。[^nccl-overview][^nccl-group]

日志关联至少保留：作业 ID、host、PID、global/local rank、step、逻辑 collective 序号、类型和大小。先查 OOM、illegal memory access、设备错误或 Python 异常，再解释后续通信超时。

### 10.2 第二层：初始化与实际 transport

用详细日志检查 communicator 初始化、拓扑和 transport 选择。以下设置用于短诊断窗口；日志文件名同时带 host 与 PID，以免跨 rank 覆盖。[^nccl-env]

```bash
export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=INIT,NET,GRAPH,COLL
export NCCL_DEBUG_FILE=/tmp/nccl.%h.%p.log
```

这些变量必须在启动测试进程前设置；多节点启动器是否把环境传给远端进程，需要单独核验。日志输出并不自动证明最佳路径已经使用，尤其要辨别是否出现预期网络插件或 verbs 设备、是否发生回退。

`NCCL_SOCKET_IFNAME` 选择 socket 网络接口，`NCCL_IB_HCA` 选择 IB/RoCE verbs HCA；**它们不是同一个开关**。Bootstrap 可达和 RDMA 数据路径正常也不是同一个测试。精确筛选语法、前缀与排除规则查当前环境变量文档，不抄与本机接口名不符的模板。[^nccl-env][^nccl-network]

### 10.3 第三层：主机与 fabric 证据

| 排查域 | 收集的证据 | 不应直接做的事 |
|---|---|---|
| 设备可见性与权限 | GPU、RDMA 设备、容器映射、版本 | 一看到报错就重装全部软件 |
| 共享内存与内存锁定 | `/dev/shm`、memlock、日志具体错误 | 无依据无限加大资源配置 |
| GPU↔NIC 路径 | 拓扑、NUMA、PCIe、GDR 是否启用 | 不审查平台便关闭 ACS/IOMMU |
| 单链路与对端 | 独立带宽/连通测试、速率、错误计数 | 把 socket 可 ping 当 RDMA 已正常 |
| Fabric 拥塞 | 同期 PFC/ECN/CNP/drop、队列与端口变化 | 只凭某个非零 counter 判断本轮拥塞 |

主机与网络排查应遵循 NVIDIA 的兼容性和排障说明，并结合具体 NIC/交换机的计数器定义。某些系统设置涉及隔离和安全，不能把它们写成适用于所有机器的“一键加速”。[^nccl-network]

### 10.4 二分实验，而不是万能参数包

在隔离实验里，分别测试单机与跨机、指定 HCA 与自动选择、禁用某条 transport 与默认路径。例如 `NCCL_IB_DISABLE=1` 可用于验证故障是否依赖 IB/RoCE 数据路径，但它可能回退到更慢的网络路径；`NCCL_P2P_DISABLE=1` 也只是对照手段。变量定义来自官方文档，实验解释仍需要日志证明真正改变了哪条路径。[^nccl-env]

一次只改一个变量，记录前后日志、吞吐、错误和 topology。实验结束恢复 baseline。固定 algorithm/protocol、增加并行度或提高 stream priority 都不是通用优化；调一个孤立吞吐数字也可能破坏训练中的 overlap。[^nccl-perf]

### 10.5 恢复与测量要分开设计

若已遇到 fatal CUDA 错误、communicator 失败或输出完整性无法确认，应停止使用相关结果，由进程/作业管理策略协同退出并从已验证的 checkpoint 恢复。`ncclCommAbort()` 等资源处置接口不等于模型状态恢复。特定版本的高级恢复 API 需要单独设计成员关系和状态一致性协议，不在这份基础实验中默认启用。[^nccl-comm]

持久化点的含义回到 [[8.6 Checkpoint 同步异步分片]]：通信完成只说明本轮数据操作的某个完成条件，不能代替可恢复的一致 checkpoint。

## 11. 一套可交付的 Benchmark Matrix

以下是实验设计建议，不是任何型号硬件的预期成绩。先完成正确性，再做性能矩阵。

| 维度 | 起步取值 | 目的 |
|---|---|---|
| Collective | AllReduce；再加 AllGather / ReduceScatter | 对应 DDP 与 FSDP 的实际操作 |
| 消息大小 | 小消息扫描 + 实际 bucket/group 大小附近 | 分离固定开销与带宽段 |
| 规模 | 单节点两卡 → 单节点全卡 → 双节点 → 目标规模 | 定位跨越哪一级开始退化 |
| 数据类型 | 与训练一致的 FP32/BF16 等支持类型 | 不用不同字节量的工作假装对比 |
| 执行模式 | 通信单独、计算单独、联合执行 | 验证净 overlap 收益 |
| 进程布局 | 每 rank 一卡；明确 CPU/NUMA/NIC 亲和 | 排除错误绑定 |
| 观测模式 | 低扰动 baseline；短窗口诊断 | 区分性能结果和定位证据 |

每个实验单元留下版本、完整命令、rank→GPU→NIC 映射、原始输出、至少一轮重复对照和解释。应用层再补充 samples/s 或 tokens/s、同步边界清楚的 step 延迟、显存峰值与正确性。**没有现场结果就保留空表，不填“经验值”冒充实测。**

## 12. 自测：能回答这些问题，才算学会使用异步

**问题一：`ncclAllReduce()` 返回后，另一个 stream 马上读取输出，为什么偶尔出错？**

返回说明 host 提交阶段完成，不是任意 stream 上的消费者都已经安全。先连生产→通信依赖，再连通信→消费依赖，同时保持 buffer 生命周期。只在 CPU 源码上排先后不够。

**问题二：把独立计算移到通信前面的同一 stream，算 overlap 吗？**

不是。它们仍在同一执行序列里。需要不同执行队列、无数据依赖，以及实际硬件资源允许；最后用联合窗口是否缩短判定收益。

**问题三：8 rank、256 MiB、2 ms，能否声称单张 NIC 达到了 234.88 GB/s？**

不能。这只是 AllReduce 的 busbw 换算结果。识别物理端口带宽要测对应端口、方向和时间区间，不能把归一化 collective 指标当计数器。

**问题四：一个 rank 的 NCCL kernel 占了 30 ms，应优先判网络堵塞吗？**

不应。先比对同一 collective 的 rank 到达时间及前面的错误。它可能在等一个很晚才完成输入或 backward 的 peer。只有进度和依赖证据排除后，才向链路和 fabric 二分。

**问题五：`ncclCommGetAsyncError()` 返回 `ncclSuccess`，能立刻释放输出吗？**

不能把它当作统一的 CUDA buffer 完成判据。按照所调用 API 的进展约定处理，再以正确 stream/event 的设备完成条件管理最后一个使用者。

> [!success] 验收产物
> 一张明确等待位置的 stream 依赖图；一份有正确性检查的 nccl-tests 原始记录；一张 CPU 提交、CUDA 通信和完整工作窗口的对账表；一次有假设、有单变量对照、有恢复 baseline 的排障记录。没有 GPU 时可先完成前两项中的设计与手算，不能声称已经得到运行成绩。
