# 8.21 NCCL 异步执行与性能：CUDA Stream、Overlap、nccl-tests 与故障诊断

> [!abstract] 本篇的主线
> **提交得快，不等于 GPU 开始得早；通信结束得早，不等于消费者开始得早；通信与计算同时出现，也不等于整个 step 更短。** 先建立生产、通信、消费之间的依赖，再把 CPU 提交、GPU 执行、跨 rank 到达和最终工作窗口放到同一条证据链上。

本篇是原笔记的**重整增强版**：保留异步语义、stream/event、group、nccl-tests、带宽口径和故障诊断，重点增加第 3—5 节的时间线对账及第 8 节的可运行诊断实验。跨服务的 KV 传输如何把这套方法延伸到队列、通知与调度，见 [[9.10 跨层性能归因：CPU、NUMA、PCIe、NIC、Switch、RDMA 与 NVMe 的 P99]]。

> [!info] 版本与证据边界
> 核对日期为 **2026-09-19**。NCCL stream/group 文档页面标识为 **2.31.2**；工具与框架应记录实际加载版本，不把网页版本当成本机版本。Python 实验代码通过语法检查，但制作环境没有可用 CUDA GPU，因此**没有 GPU 实测成绩**。本文所有带毫秒数值的时间条和对照表均标为“构造样本”；它们用于检查计算与因果推理，不能冒充 Nsight 实测截图。实验流程产生的 `.nsys-rep` 和 JSONL 才属于运行环境的实测证据。

## 1. 从接口返回到业务完成，中间有几道边界？

### 1.1 三种“完成”不能互换

普通成功的 NCCL 调用通常负责把操作提交到指定 CUDA stream，设备工作异步进行。CPU 返回、设备结果可用、所有 rank 完成工作窗口是不同边界。正确性依赖 stream/event 或框架提供的同步契约，而非 CPU 源码中的先后顺序。[^streams]

| 观察层 | 记录的事件 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| Host | API 进入、返回 | 本次调用占用 CPU 的跨度 | 输出已完成、GPU 没有等待 |
| 提交/运行时 | CUDA launch、外层 group 提交完成 | 工作已经提交到相关执行队列 | Kernel 已运行完、对端已匹配 |
| GPU | Kernel 开始、结束；正确依赖后的 event | 指定执行区间或此前 stream 工作完成 | 纯网络传输耗时、整个作业完成 |
| 多 rank 工作 | 配对 step 的各 rank 完成 | 这一轮的慢 rank 和整体进度 | 下一轮、请求响应、checkpoint 完成 |

`config.blocking = 0` 是另一维度：它影响某些操作的 host 进展方式。遇到 `ncclInProgress`，要按对应 API 的约定查询进展；`ncclCommGetAsyncError()` 返回 `ncclSuccess` 不构成任意显存缓冲区的统一释放条件。[^comm]

### 1.2 CUDA event、RNIC CQE、框架通知不是同一种东西

CUDA event 记录 stream 中的进度；RNIC CQE 表达某个工作请求的完成语义；框架通知可能进一步表达多个分片和多个 worker 都已满足某个条件。它们可以通过协议连接，但不能仅因都叫“done”就互相替代。

尤其要分开 **NCCL collective** 与 **NIXL/UCX 等传输接口**。后者可能走 GPUDirect RDMA，没有用户所期待的 NCCL collective kernel；反过来，一个 NCCL kernel 的持续时间也不等于某张 RNIC 的纯线上传输时间。GPU 可见性与外部 DMA 的契约继续见 [[8.12 GPUDirect RDMA]]。

## 2. 正确的依赖图：生产 → 通信 → 消费

假设 `grad` 在 compute stream 中产生，communication stream 执行原地 AllReduce，compute stream 最后再消费 `grad`。必须建立：

$$
\operatorname{produce}(grad)\prec\operatorname{AllReduce}(grad)\prec\operatorname{consume}(grad)
$$

同一 stream 内的顺序不能自动扩展为跨 stream 的顺序。`cudaStreamWaitEvent()` 给目标 stream 的后续工作建立等待，不是让调用它的 CPU 线程睡眠直到事件完成。基础语义见 [[8.11 cudaMemcpy 与 CUDA Stream]]。[^cuda-stream]

### 2.1 用借用句柄表达边界，不转移所有权

下面是**可嵌入既有 NCCL 应用的 C++17 片段**，不是独立程序。外层 RAII 对象持有设备缓冲、stream、event、communicator，直到最后一个 GPU 使用者完成。`grad` 至少包含 `n > 0` 个 `float`，当前设备正确，所有 rank 按相同顺序提交相同规格；communicator 使用普通 blocking 配置，调用点不在未结束的 group 内。

先定义错误传播。同步与提交都可能暴露 CUDA 异步错误；抛异常不等于协同终止其他 rank，跨进程恢复由外层管理器处理。

```cpp
#include <cuda_runtime.h>
#include <nccl.h>
#include <cstddef>
#include <stdexcept>

inline void check_cuda(cudaError_t result) {
    if (result != cudaSuccess) {
        throw std::runtime_error(cudaGetErrorString(result));
    }
}
inline void check_nccl(ncclResult_t result) {
    if (result != ncclSuccess) {
        throw std::runtime_error(ncclGetErrorString(result));
    }
}
```

这段只是错误传播，没有异步执行过程。下面的函数只连接生产到通信，**不偷偷同步整个设备**。调用前，生产者已经把写入 `grad` 的 kernel 提交到 `compute`；`produced` 和 `reduced` 的外层拥有者必须防止跨轮次复用造成错误关联。

```cpp
void enqueue_reduce(float* grad, std::size_t n, ncclComm_t comm,
                    cudaStream_t compute, cudaStream_t communication,
                    cudaEvent_t produced, cudaEvent_t reduced) {
    check_cuda(cudaEventRecord(produced, compute));
    check_cuda(cudaStreamWaitEvent(communication, produced, 0));
    check_nccl(ncclAllReduce(grad, grad, n, ncclFloat, ncclSum,
                             comm, communication));
    check_cuda(cudaEventRecord(reduced, communication));
}
```

![[图片/SVG/8_8_8_21_9.svg|900]]

图的上半部分说明：CPU 提交函数返回后，comm stream 可能仍在等待生产者，或者已经在等待对端；箭头表示依赖，不表示 CPU 一直阻塞。

独立计算必须使用不与 `grad` 冲突的数据。它提交到 compute stream 后，再插入下面的消费者等待；消费者 kernel 随后也必须提交到 `compute`。这两行的顺序决定等待是否覆盖了本可以并发的工作。

```cpp
// 此前已在 compute 上提交不访问 grad 的独立 kernel。
check_cuda(cudaStreamWaitEvent(compute, reduced, 0));
// 此后再向 compute 提交读取或覆盖 grad 的消费者 kernel。
```

同一张图中“独立工作 → 等待 reduced → 消费”是这个片段的执行顺序。等待应放在**真正使用结果的最晚合法位置**，而不是一提交通信就把所有后续计算堵住。外层最后还要记录消费者完成事件，再决定复用/释放资源。

### 2.2 Group 与 buffer 生命周期是两类额外约束

`ncclGroupStart()` / `ncclGroupEnd()` 可以聚合操作；单个 host 线程管理多张 GPU 时也常需要 group 协调。group 内某次 API 返回不保证该次操作已经单独入队。应在外层 group 按其约定完成提交后，再安排依赖这些操作的 CUDA 事件；不能在尚未结束的 group 中等待尚未提交的工作。[^groups]

group 跨多条 stream 时，会引入参与 stream 之间的同步关系。合批减少调用/launch 开销，也可能使早就绪操作等待较慢生产者。一个 group 还可能对应一个聚合 kernel，因此分析时不能强制假定“一次 NCCL API ↔ 一个 GPU kernel”。[^streams][^groups]

最后一个使用者未完成前，不得因为 host 提交已返回就复用 buffer。双缓冲要逐槽位维护状态，而不是让两轮操作共用一个含糊的“完成标记”。默认 stream 的 legacy/per-thread/nonblocking 规则也不同；新实验尽量显式记录 stream 创建方式，避免靠隐式同步维持正确性。[^cuda-stream]

## 3. 真实 trace 应如何落到一组可对账的时间戳？

### 3.1 先把“提交延迟”拆成三个名字

把所有时间都叫 latency 会丢失因果。建议至少保留以下字段；其中 `APP_*` 是**建议增加的应用埋点名，不是 NCCL 原生事件**。

| 字段 | 建议来源 | 定义与限制 |
|---|---|---|
| `APP_ENQUEUE` / `APP_DEQUEUE` | 框架队列、NVTX + 结构化日志 | 软件队列等待；没有埋点就不能从 GPU 空白反推 |
| `API_BEGIN` / `API_END` | NCCL/PyTorch API trace、CPU 单调时钟 | 调用在 host 上的跨度，可能包括准备、锁竞争、提交 |
| `LAUNCH_BEGIN` / `LAUNCH_END` | CUDA runtime/driver trace | GPU launch API，不一定与外层 NCCL API 一一对应 |
| `PRODUCE_DONE` | 生产 kernel/event 与依赖图 | 本轮输入在设备上就绪；不是“CPU 提交生产完成” |
| `KERNEL_BEGIN` / `KERNEL_END` | GPU kernel activity | 通信 kernel 驻留跨度，含其内部等待/推进 |
| `OTHER_DEPS_DONE` | 独立计算与其他依赖节点 | 消费者除通信以外的前置条件何时满足 |
| `CONSUME_BEGIN` / `STEP_DONE` | 消费者 kernel、汇合后的 event | 是否真正缩短关键路径 |

Nsight Systems 的 CUDA kernel execution 报告区分 API、排队和 kernel 时间。**Kernel 有可能在 launch API 返回以前已经开始执行**，因此 API 时间与 kernel 时间可重叠，不能无条件相加成总时间。正的 `KERNEL_BEGIN − LAUNCH_END` 可以作为提交后等待跨度，但它不自动等于调度器的无效开销。[^nsys-analysis]

“输入 ready → API 开始”的距离也不一定是故障：框架可能有意等 bucket 合批，或者 host 与 GPU 不在同一可直接相减的时钟域。先核对关联对象和时钟映射，再解释差值。

### 3.2 一条完整数值时间线：为什么 0.10 ms、4 ms、7 ms 都可能正确？

![[图片/SVG/8_8_8_21_7.svg|900]]

**构造样本，单位 ms；所有 GPU/CPU 事件假设已映射到同一 host 的可比时间轴。** 本例使用直接 NCCL 调用、无 group、无 CUDA Graph，仅分析一条已明确关联的操作。

| 主体 / 边界 | 开始 | 结束 | 解释 |
|---|---:|---:|---|
| Host 的 NCCL API | 0.20 | 0.30 | CPU 调用占用 0.10 ms |
| GPU 生产输入 | 0.00 | 1.00 | 数据依赖到 1.00 才满足 |
| GPU 通信 kernel | 1.20 | 5.20 | 设备区间为 4.00 ms，不是纯线速时间 |
| GPU 独立计算 | 1.00 | 6.00 | 不访问通信中的 buffer |
| GPU 消费结果 | 6.00 | 7.00 | 通信早已结束，消费不再暴露通信等待 |

于是三种口径分别为：

$$
T_{API}=0.30-0.20=0.10\text{ ms}
$$
$$
T_{comm\_kernel}=5.20-1.20=4.00\text{ ms},\quad T_{step}=7.00\text{ ms}
$$

从外层 API 返回到 kernel 启动的 0.90 ms，不能全部叫“launch overhead”。已知生产者在 1.00 才完成，在本例的依赖图中，0.30—1.00 的 0.70 ms 是合法的前置依赖等待；1.00—1.20 的 0.20 ms 还需要 CUDA launch、运行时和资源证据解释。**仅凭这张简化时间线，不能把余下 0.20 ms 精确判给 GPU 调度器。**

### 3.3 GPU 的“等待”有三种不同形态

第一种是 **stream 等待尚未满足的事件**：该 stream 的消费者还不能执行，但别的 stream 可以有用工作。第二种是 **kernel 已驻留却在等对端、协议或数据**：时间线上有 NCCL activity，甚至占用 SM，不能把它当有效传输的同义词。第三种是 **所有可执行工作都缺失导致的设备空闲**：这才更接近“GPU 在等供给”。三者需要依赖图、kernel 活动与资源观测联合区分。[^streams][^nsys-guide]

因此“GPU utilization 很高”不直接证明没有通信等待；“某条 stream 是空白”也不直接证明整张卡空闲。供给侧的诊断接着看 [[8.7 DataLoader 与 GPU 空闲归因]]。

### 3.4 跨 rank：早到者的长 kernel，可能是晚到者造成的

对同一 `run + process_group_epoch + step + collective_seq`，比较所有参与 rank 的输入就绪与提交时间。若 rank 0—6 早到，rank 7 因 CPU 数据处理或前序 kernel 晚到，早到 rank 的 NCCL 区间可能被拉长。不能因为七张卡都出现长 NCCL kernel，就把 fabric 当成七份独立证据。

需要确认的是“最早的异常在哪一个前驱节点”，不是“哪个等待节点画得最长”。跨 host 的裸 CPU 时间戳不能直接相减；没有有界时钟同步时，应先比较本地持续时间及消息因果，不能凭多机图上的视觉对齐计算微秒级单程延迟。

## 4. “传输快了一倍，整个 step 没改善”的严格解释

### 4.1 用关键路径计算，而不是把每段时间相加

在一个简化模型中，独立计算在时刻 $C$ 完成，通信在 $S$ 开始、持续 $N$，消费者持续 $D$，并且没有其他前驱、调度门槛和资源相互干扰，则：

$$
T_{step}=\max(C,S+N)+D
$$

通信在该消费者前暴露的等待是：

$$
T_{exposed}=\max(0,S+N-C)
$$

这两个式子是**指定依赖图的模型**，不是任意 DDP/FSDP 工作负载的通用性能公式。存在多 bucket、多消费者和流水并行时，应在完整 DAG 上求关键路径。

把上一节的 $C=6,S=1.2,N=4,D=1$ 代入，得到 7 ms。假设其他条件全部不变，把通信缩短为 2 ms：

$$
\max(6,1.2+2)+1=7\text{ ms}
$$

节省的两毫秒落在已有的重叠窗口中。**它释放了通信资源和余量，但没有改变这条 step 的最长依赖链。** 这不代表优化毫无价值，只代表“单步延迟下降”不是该样本获得的收益；高负载吞吐、尾延迟和容量仍要另测。

### 4.2 四组反事实，把“更快”与“更早”分开

![[图片/SVG/8_8_8_21_8.svg|900]]

以下都是构造对照，并不声称存在一个能保持所有其他条件不变的万能 NCCL 参数。

| 对照 | 独立计算结束 C | 通信区间 | 消费区间 | Step | 结论 |
|---|---:|---|---|---:|---|
| A 基线 | 6.0 | 1.2—5.2 | 6—7 | 7.0 | 通信已被隐藏 |
| B 仅通信减半 | 6.0 | 1.2—3.2 | 6—7 | 7.0 | 局部加速不改变关键路径 |
| C 通信短，但晚提交 | 6.0 | 5.2—7.2 | 7.2—8.2 | 8.2 | 启动变晚抵消通信加速 |
| D 通信短，但计算受争用 | 8.0 | 1.2—3.2 | 8—9 | 9.0 | 通信资源占用方式使计算退化 |

D 中的因果必须由实际 A/B 对照支持，不能看到计算变慢就断言一定是 NCCL 争用。独立测计算、独立测通信、联合运行三组是必要的起点；再根据 SM、HBM、PCIe/NVLink 和 NIC 证据细分。NCCL 的具体执行路径与调优边界见官方性能说明及 [[8.20 NCCL 拓扑与数据路径：PCIe、NVLink、NVSwitch、RDMA 与 GPU-NIC Affinity]]。[^perf]

### 4.3 调度门槛可以吃掉已经实现的加速

如果消费者还要等调度器在 $G$ 时刻发车，模型变成：

$$
T_{start}=\max(C,S+N,G)
$$

例如 $G=8$，基线通信在 5.2 完成，优化后在 3.2 完成，消费者却都在 8 开始。KV 传输场景中的完成轮询、worker 汇合、调度批次、显存容量准入，正是这种额外门槛。第 9.10 篇会把每一道门都绑定到请求和批次，而不是笼统地归到“网络”。

### 4.4 六种“局部变快、整体不变”的证据要求

| 机制 | 应看到的证据 | 不能省略的对照 |
|---|---|---|
| 通信已被隐藏 | 完成提前，消费者开始不变 | 完整依赖图、独立计算结束点 |
| 提交/合批变晚 | API 或 group 提交时间后移 | 同样 workload、同样 bucket 字节分布 |
| 资源争用 | 联合运行中计算或通信单段变长 | 计算单独 / 通信单独 / 联合三组 |
| rank 到达偏斜 | 同一 collective 的最后一个 rank 晚到 | 各 rank 的前序生产与 CPU 时间线 |
| 完成发布或调度等待 | transport 完成提前，调度恢复不变 | 完成观察、框架上报、消费者 launch 三段 |
| 测试或统计口径变化 | 只有微基准 GB/s 改善，业务分布不匹配 | 相同到达负载、样本队列和失败口径 |

“从 64 MiB 改成 32 MiB 后更快”不是保持通信工作量不变的优化；“平均更快但 P99 不变”也可能只是优化没有触及尾部请求。用统计之前，先核对比较的究竟是不是同一项工作。

## 5. 读 Nsight：从彩色条变成可审查的证据

![[图片/SVG/8_8_8_21_10.svg|900]]

### 5.1 建议的关联键与采集范围

应用侧记录 `run_id、rank、process_group_epoch、step、bucket/collective_seq、op、count、dtype`。rank 重启或 process group 重建后，epoch 必须变化，不能把复用的序号拼成一条假时间线。GPU 活动关联还要保留进程、设备、context、stream 与 CUDA correlation ID；具体字段来自当前版本的导出模式。

NVTX range 用于标记调用和逻辑窗口，**range 结束是 host 代码离开标记，不自动等于 GPU 完成**。通过 CUDA API/activity 的关联追到 kernel，最后再找到消费方。遇到 group 融合、一对多 launch 或 CUDA Graph replay，必须允许多对多关系，不能按时间最近原则强行配对。[^nsys-guide]

新的 Nsight Systems 版本可以提供更细 NCCL tracing，但功能、支持的 NCCL 版本和参数会变化。基础方案先使用 `cuda,nvtx,osrt`；启用高级 NCCL tracing 前，核对本机帮助和兼容性，且不要把两种 trace 的 CPU 时间精度视为完全相同。[^nsys-guide]

### 5.2 两个不能直接相减的东西

一是不同主机的单调时钟。二是不同 GPU 上各自记录的 CUDA event 时间。CUDA event elapsed time 用于相容设备/事件范围内的持续时间，不是一个可跨 GPU 全局定位的墙钟时间戳。跨域关联依赖 profiler 的时钟映射、同步策略及误差说明，而不是“单位都叫 ms”。[^events][^nsys-guide]

若只能证实 `KERNEL_BEGIN ≥ PRODUCE_DONE`，还没有识别 driver launch 与具体资源竞争，就应把剩余区间标为“未分解等待”。明确未知比把所有缝隙涂成“网络慢”更有价值。

### 5.3 小心观测器改变被观测系统

先保存未开启重型 tracing 的基线；再用短窗口定位。逐 step 同步、逐 kernel profiler、过多日志、逐请求同步 D2H 都可能改变 overlap。Nsight Compute 的 replay/串行化等机制适合分析单 kernel 资源行为，不能不加区分地用它的窗口推断生产程序的并发收益。[^ncu]

导出时先运行 `nsys stats --help-reports`，用本版本列出的 CUDA kernel execution 报告。需要 SQLite 时，先检查 `.schema` 和实际列名，不复制未经验证的固定 SQL schema。输出只有每类 kernel 的累计时间时，**不能重建逐 step 的关键路径**。

## 6. nccl-tests：建立通信基线，但不替代应用时间线

### 6.1 环境与路径必须先留下记录

记录 GPU UUID、rank→GPU→NIC 映射、CPU/NUMA 位置、PCIe 链路、CUDA/NCCL 实际加载版本、NCCL 插件、频率与后台负载。下面命令只读设备信息，不证明 GPUDirect 已正确启用。[^network]

```bash
nvidia-smi
nvidia-smi topo -m
nvcc --version
ibv_devinfo
```

`nvcc` 的版本不等于 PyTorch 实际加载的 CUDA/NCCL 版本。没有 RDMA 设备时，`ibv_devinfo` 失败也不代表单机 NVLink 测试失败。CPU 绑核正确不等于所有内存、NIC 与 GPU 都已局部访问。

### 6.2 构建与测试要固定版本和规模

在官方 nccl-tests 仓库选择并记录实际 commit；下面使用当前 checkout，不假定 `HEAD` 是某个特定 release。`NCCL_HOME` 应替换为本机实际路径。[^tests]

```bash
git clone https://github.com/NVIDIA/nccl-tests.git
cd nccl-tests
git rev-parse HEAD
make -j CUDA_HOME=/usr/local/cuda NCCL_HOME=/opt/nccl
./build/all_reduce_perf -b 8 -e 256M -f 2 -g 2 -w 10 -n 50 -c 1
```

`-g 2` 是每个测试线程使用两张 GPU，不是两进程。总体 rank 数取决于进程数、测试线程数、每线程 GPU 数。跨机使用 MPI 构建和对应启动器，明确每 rank 一卡的映射；不能让所有 rank 都看到同一个 GPU0 而期待自动获得正确布局。

先验证数据正确性、in-place/out-of-place 区别和规模，再扫描实际 workload 的 size/dtype。DDP 的 bucket 与 NCCL 内部 channel/chunk 不是同一层；FSDP 应额外覆盖 AllGather、ReduceScatter。单次大 AllReduce 的成绩不能代表由许多小操作组成的 backward。

### 6.3 algbw、busbw、端口 counter 三种口径

对 AllReduce，nccl-tests 的定义为：[^tests-perf]

$$
\operatorname{algbw}=S/t,\qquad
\operatorname{busbw}=\operatorname{algbw}\cdot2(N-1)/N
$$

其中 $S$ 为每 rank 完整输入的字节数。AllGather/ReduceScatter 的归一化系数为 $(N-1)/N$，文档中的 size 口径按完整聚合数组理解，不能不经换算套用 API 的单 rank count。

构造例：8 rank、256 MiB、2 ms，得到 `algbw = 134.217728 GB/s`，`busbw = 234.881024 GB/s`。MiB 按 $2^{20}$ 字节，GB/s 按 $10^9$ 字节/秒。**这不是单张 NIC 跑到了 235 GB/s。** 归一化带宽不是物理端口观测，聚合方向、多轨、NVLink 和算法路径都会改变物理解释。

计数器必须用同一端口、同一方向、同一窗口的增量，先确认是否包含 RDMA 流量。具体 mlx5 RDMA 与普通 Ethernet vport counter 的区别，在第 9.10 篇的 KV 案例中给出。

## 7. 三种计时器应同时存在

Host 提交计时不等待 GPU，适合找调用开销；CUDA event 计时要在正确 stream 或正确汇合边界上；业务窗口要覆盖所有真正依赖的设备工作。只在 compute stream 上记录一个 stop，而不让它等待内部 NCCL stream，会漏计尚未完成的通信。

下面直接 NCCL 片段的 `start/stop` 必须启用 event timing，输入已经就绪，所有 rank 规格匹配且 group 已结束。同步 stop 只为了获得本样本值，不应被机械地插入生产热路径。[^events][^streams]

```cpp
check_cuda(cudaEventRecord(start, communication));
check_nccl(ncclAllReduce(grad, grad, n, ncclFloat, ncclSum,
                         comm, communication));
check_cuda(cudaEventRecord(stop, communication));
check_cuda(cudaEventSynchronize(stop));
float elapsed_ms = 0.0F;
check_cuda(cudaEventElapsedTime(&elapsed_ms, start, stop));
```

![[图片/SVG/8_8_8_21_9.svg|900]]

图中 host 真正等待设备结果发生在最后的同步边界，而不是 `ncclAllReduce()` 返回处。start/stop 区间可能包含 peer 等待、host 没及时提交后续工作等空隙；它仍不是纯 wire time。

对于配对的 step，可以保留每个 rank 的时长，再对同一 step 求最大值形成分布；不能把每个 rank 独立计算出的 P99 取最大值，就当成配对 step 最大耗时的 P99。不同 rank 的窗口没有共同边界时，还需先解决测量对象不一致的问题。

## 8. 最小实测实验：两张 GPU 生成自己的时间线

### 8.1 实验目的与前提

实验比较 `serial`、`overlap`、`late_rank` 三种依赖安排。使用 PyTorch 的 NCCL backend，是为了省去手写 rendezvous 和设备资源管理，**不是把用户当前 stream 当作 ProcessGroupNCCL 内部通信 stream**。`dist.all_reduce(..., async_op=True)` 返回 Work；在常规 CUDA collective 语义下，`work.wait()` 给当前 CUDA stream 建立消费依赖，不能把它的 CPU 返回当成设备已经完成。相关阻塞/超时配置会影响 host 行为，运行时应记录环境。[^torch-dist]

前提：至少两张可见 NVIDIA GPU，兼容的驱动、CUDA 与启用 NCCL 的 PyTorch，`torchrun` 可用。每 rank 使用不同的 `LOCAL_RANK`，所有 rank 的参数相同。此实验没有触碰磁盘或修改设备配置；首次运行仍应选择空闲实验设备。

**把下面编号 A—F 的 Python 代码块按顺序拼成 `nccl_timeline.py`。** 代码在笔记中按职责拆开，下载包不另放 `.py`，以保持只交付 Markdown 与 SVG。

**A．参数和设备检查。** 不提供 `LOCAL_RANK` 或缺少 NCCL 时直接停止，避免悄悄回退到 CPU/Gloo。参数固定后，三种模式保持相同的通信字节和 GEMM 工作量。

```python
import argparse
import json
import os
import time
from datetime import timedelta
from pathlib import Path
import torch
import torch.distributed as dist

parser = argparse.ArgumentParser()
parser.add_argument('--mode', choices=['serial', 'overlap', 'late_rank'], default='overlap')
parser.add_argument('--steps', type=int, default=20)
parser.add_argument('--warmup', type=int, default=5)
parser.add_argument('--mib', type=int, default=32)
parser.add_argument('--gemms', type=int, default=6)
parser.add_argument('--late-ms', type=float, default=5.0)
args = parser.parse_args()
if min(args.steps, args.mib, args.gemms) <= 0 or args.warmup < 0 or args.late_ms < 0:
    raise ValueError('invalid experiment size')
local_rank = int(os.environ['LOCAL_RANK'])
if not torch.cuda.is_available() or not dist.is_nccl_available():
    raise RuntimeError('CUDA and the NCCL backend are required')
if not 0 <= local_rank < torch.cuda.device_count():
    raise RuntimeError('LOCAL_RANK does not map to a visible GPU')
```

**B．一次性初始化。** 一进程一卡，输入与独立计算缓冲完全分开；计时 event 在预热前创建，不把创建成本混入被测调用。这里始终使用默认 compute stream。

```python

# One process owns one GPU; keep the default compute stream throughout.
torch.cuda.set_device(local_rank)
dist.init_process_group('nccl', timeout=timedelta(seconds=120))
rank, world = dist.get_rank(), dist.get_world_size()
if world < 2:
    raise RuntimeError('run with at least two ranks')
run_id = os.environ.get('RUN_ID', 'nccl-timeline')
x = torch.empty(args.mib * 1024 * 1024 // 4, device='cuda', dtype=torch.float32)
a = torch.randn((1024, 1024), device='cuda')
b = torch.randn_like(a)
c = torch.empty_like(a)
begin, end = (torch.cuda.Event(enable_timing=True) for _ in range(2))
rows = []

```

**C．生产与异步提交。** `late_rank` 的 host 等待放在输入提交之后、AllReduce 之前，制造到达偏斜。`submit_ms` 只包围外层 API；serial 模式提前建立消费者等待。下面函数会在 D 块继续。

```python
def iteration(step: int, measured: bool) -> None:
    label = f'{run_id}/rank={rank}/step={step}/mode={args.mode}'
    torch.cuda.nvtx.range_push(label)
    wall_begin = time.perf_counter_ns()
    begin.record()
    x.fill_(float(rank + 1))
    if measured and args.mode == 'late_rank' and rank == world - 1:
        time.sleep(args.late_ms / 1000.0)
    torch.cuda.nvtx.range_push('all_reduce_submit')
    submit_begin = time.perf_counter_ns()
    work = dist.all_reduce(x, async_op=True)
    submit_end = time.perf_counter_ns()
    torch.cuda.nvtx.range_pop()
    if args.mode == 'serial':
        work.wait()
```

**D．独立计算与汇合。** 保持函数体缩进，紧接 C 块。overlap 模式将独立 GEMM 放到等待前；两种模式都在消费 `x` 前汇合通信。event 终点覆盖消费者，最后同步只服务于本轮诊断。

```python
    torch.cuda.nvtx.range_push('independent_gemm_submit')
    for _ in range(args.gemms):
        torch.mm(a, b, out=c)
    torch.cuda.nvtx.range_pop()
    if args.mode != 'serial':
        work.wait()
    x.mul_(1.0 / world)
    end.record()
    end.synchronize()  # Diagnostic boundary, NOT a throughput benchmark.
    wall_end = time.perf_counter_ns()
    torch.cuda.nvtx.range_pop()
    if measured:
        rows.append({'run_id': run_id, 'rank': rank, 'step': step,
                     'mode': args.mode, 'submit_ms': (submit_end-submit_begin)/1e6,
                     'joined_gpu_ms': begin.elapsed_time(end),
                     'local_wall_ms': (wall_end-wall_begin)/1e6})

```

**E．预热、测量、正确性。** barrier 只放在预热后，不放在每轮 step 前。每轮仍有诊断同步，真实流水吞吐需要另测。完整 D2H 正确性检查在所有测量之后，避免进入热路径。`try` 在 F 块继续。

```python
try:
    for step in range(args.warmup):
        iteration(step, False)
    dist.barrier()
    torch.cuda.synchronize()
    for step in range(args.steps):
        iteration(step, True)
    # Copy/check only AFTER measurement; each element should be (world+1)/2.
    expected = (world + 1) / 2.0
    torch.testing.assert_close(x.cpu(), torch.full((x.numel(),), expected))
    metadata = {'torch': torch.__version__, 'cuda': torch.version.cuda,
                'nccl': torch.cuda.nccl.version(), 'rank': rank, 'world': world,
                'gpu': torch.cuda.get_device_name(local_rank), 'args': vars(args)}
```

**F．归档与清理。** 紧接 E 块、保持缩进；记录实际框架/CUDA/NCCL 版本，每 rank 独立输出。最终销毁 process group；这不是包含故障恢复与生产取消处理的完整运行器。

```python
    output = Path(f'{run_id}.{args.mode}.rank{rank}.jsonl')
    with output.open('w', encoding='utf-8') as stream:
        stream.write(json.dumps({'metadata': metadata}) + '\n')
        for row in rows:
            stream.write(json.dumps(row) + '\n')
    print(f'rank {rank}: correctness PASS; {output}', flush=True)
finally:
    dist.destroy_process_group()
```

![[图片/SVG/8_8_8_21_9.svg|900]]

图的下半部分对应实验：默认 compute stream 产生 `x`，ProcessGroupNCCL 在内部通信路径中规约，独立 GEMM 只使用 `a/b/c`；`work.wait()` 连接回消费者，`end.synchronize()` 才给 host 一个完整诊断边界。GPU 上的通信 kernel 应通过 trace 查找，而不是凭创建的某个 stream 名字猜测。

### 8.2 先无 profiler 跑三组，再抓短 trace

`RUN_ID` 只使用简单文件名字符，不包含目录分隔符；每种模式产生独立的 rank JSONL。`late_rank` 有意让最后一个 rank 的 host 在提交前等待 5 ms，用于观察到达偏斜，不代表网络注入。

```bash
export RUN_ID=nccl-demo-001
torchrun --standalone --nproc-per-node=2 nccl_timeline.py --mode serial
torchrun --standalone --nproc-per-node=2 nccl_timeline.py --mode overlap
torchrun --standalone --nproc-per-node=2 nccl_timeline.py --mode late_rank
```

抓 trace 时，可让 torchrun 启动每个 rank 各自的 profiler 包装器。先核对本机 `torchrun --help` 与 `nsys profile --help`；以下形式让输出路径带 rank，避免覆盖。

```bash
torchrun --standalone --nproc-per-node=2 --no-python \
  bash -lc 'nsys profile --trace=cuda,nvtx,osrt --sample=none \
  -o "${RUN_ID}.overlap.rank${RANK}" \
  python nccl_timeline.py --mode overlap --steps 10'
```

不要把单机两卡实验宣称为“已验证跨机 RDMA”。多机实验还需自己的启动、网卡映射和链路取证。矩阵乘法与通信是否真正并发取决于资源和运行时；本实验保证依赖表达与测量边界，**不承诺 overlap 模式一定更快**。

### 8.3 输出该怎样解读？

| 产物 / 字段 | 含义 | 不可替代的证据 |
|---|---|---|
| `submit_ms` | 本地 `all_reduce` 的 CPU 调用跨度 | 不能替代内部 NCCL kernel 时间 |
| `joined_gpu_ms` | 默认 stream 起点到已汇合消费者终点的 GPU event 区间 | 可能包含生产、依赖等待及 host 提交空隙 |
| `local_wall_ms` | 本轮 host 起点到设备同步返回 | 包含本地调度与同步开销，不是纯 GPU 时间 |
| `.nsys-rep` | 调用、GPU activity、NVTX 的时间线 | 才能判断计算与内部通信的重叠和等待位置 |
| 正确性检查 | 规约后每元素接近 `(world+1)/2` | 不能证明任意真实模型或失败恢复均正确 |

本实验**每次 iteration 都同步**，适合解释单轮依赖，不能作为生产流水吞吐结论。正式性能评估应回到真实应用的多 step 窗口，保留正常队列深度，只在窗口边界完成必要同步。样本应去除预热，保留所有 rank，并报告错误、超时、profile 开销和重复窗口波动。

## 9. 故障诊断：从最早的偏离开始

先核对 communicator、collective 顺序、count、dtype、op、参与 rank；然后查 OOM、CUDA illegal access、进程提前退出。后续 NCCL timeout 可能只是最早错误的传播，而不是起因。[^groups][^comm]

短窗口诊断可开启下面日志，文件名包含 host 和 PID；日志过多会扰动性能，定位结束后应恢复基线。[^env]

```bash
export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=INIT,NET,GRAPH,COLL
export NCCL_DEBUG_FILE=/tmp/nccl.%h.%p.log
```

`NCCL_SOCKET_IFNAME` 与 `NCCL_IB_HCA` 分别选择 socket 接口和 verbs HCA，不是同一个设置。Bootstrap 可达不证明 RDMA 数据路径正常；某个网络插件被加载也不证明所有传输都走了预期最优路径。结合日志、设备计数与拓扑核对实际路径。[^env][^network]

| 第一次偏离的位置 | 首要假设 | 下一项证据 |
|---|---|---|
| 输入 ready 之前 | 数据供给、前序计算、内存分配 | CPU 栈、DataLoader、生产 kernel |
| ready 之后，API 之前 | 框架排队、合批、host 调度 | 应用队列埋点、group 边界 |
| 已提交，GPU 尚未开始 | 前置依赖、资源、launch 路径 | CUDA correlation、stream waits |
| GPU 通信长 | rank 偏斜、通信路径、资源争用 | 对端同轮时间线、NIC/switch、三组对照 |
| 通信完成，消费者迟迟不启动 | 其他依赖或调度门槛 | 消费者就绪、调度、launch 时间 |

禁用 IB/P2P 等开关只用于授权隔离环境的单变量二分，不是推荐永久配置。不要无依据关闭 ACS/IOMMU、修改共享 fabric 的 PFC/ECN。`ncclCommAbort()` 是资源/通信处置的一部分，不会自动恢复模型状态；可靠恢复依赖已验证的一致 checkpoint，见 [[8.6 Checkpoint 同步异步分片]]。

## 10. 最后的验收：不是“峰值带宽提高了”

一份可审查的性能结果至少同时包含：固定 workload 和到达负载；完整版本与 rank/GPU/NIC 映射；正确性与失败率；低扰动性能窗口；具有请求/step 标识的短 trace；同样条件的 A→B→A 或重复对照。

对通信单独、计算单独、联合运行分别测量；应用侧报告 samples/s 或 tokens/s、定义清楚的 step/请求延迟与尾部。若只改善了通信微基准，就只声明微基准改善，不扩大为训练/推理收益。若没有足够时钟或队列证据，就保留未分解等待。

> [!question] 三个检验理解的问题
> **通信 4 ms→2 ms，step 为什么仍为 7 ms？** 因为消费者还要等到 6 ms 的独立计算，节省落在已重叠区间。
>
> **NCCL API 已返回，为什么 GPU 还没有执行？** 可能有输入依赖、参与 group 的其他 stream、launch 路径或资源等待；必须逐边界检查。
>
> **NCCL kernel 很长而 NIC 没满，是否足以证明 CPU 慢？** 不足。peer 到达、协议推进、GPU/互连争用、计数器口径和采样粒度都仍需排查。
