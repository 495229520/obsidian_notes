# NCCL 架构与 Collective Communication：Ring、Tree、AllReduce、NVLink 与 RDMA

> [!abstract] 这一篇要解决什么
> 已经理解 [[8.11 cudaMemcpy 与 CUDA Stream]] 的异步执行、[[8.12 GPUDirect RDMA]] 的 NIC↔显存传输之后，还缺一层：**许多 GPU 怎样共同完成一个张量运算，而不是只把字节从 A 搬到 B？**
> 本篇把 Collective 的数学语义、Ring / Tree 的通信计划、NVLink / RDMA 的承载关系分开，再用字节账和实验把它们接起来。

> [!info] 阅读口径
> 内部实现固定参考 **NCCL `v2.27.7-1`**，不称其为最新版本。公共接口和部署警告同时核对了 2026-09-11 可访问的 NVIDIA 文档；在线文档会更新。文中的四 rank 推演、带宽算例均是**教学模型，不是实测数据**。硬件、版本和插件相关结论会明确限定范围。[^version]

## 1. 先拆开五层：NCCL 不是一种网线，也不是一个 RDMA 动词

一次 `ncclAllReduce` 可以从五个不同问题理解：

| 层 | 回答的问题 | 本篇的例子 |
| --- | --- | --- |
| Collective 语义 | 所有参与者最终应该拿到什么？ | 每个 rank 得到逐元素求和结果 |
| Algorithm | 谁在什么阶段把哪部分数据交给谁？ | Ring、Tree，以及其他硬件适配算法 |
| Runtime / Protocol | 如何切分工作、并发推进、判断数据可读？ | Channel、Chunk、Simple / LL / LL128 |
| Transport | 一个逻辑邻居之间怎样实现传输？ | P2P、SHM、NET，或支持的专用路径 |
| 物理互联 | 字节真正穿过哪些器件？ | NVLink、NVSwitch、PCIe、NIC、IB / RoCE fabric |

**AllReduce 是计算契约；Ring 是调度方案；RDMA 是一种数据传输能力。** 三者不能互相替代。Ring 的一条逻辑边可以落在 NVLink，也可以落在跨机网络，不能看到“Ring”就推断线上报文走 TCP。NCCL 的 GPU 计算、分块转发和网络推进也不是简单地给每次通信包一层 `ibv_post_send`。[^ring-src][^net-src]

![[图片/SVG/8_8_18_1.svg|900]]

图中同一条语义请求向下展开为不同承载路径。反过来，单独知道“机器有 NVLink 和 RDMA”并不能确定本次 AllReduce 采用了什么算法、用了几条 Channel，或是否经过主机中转。

这里的分层还是工程排障的坐标系：结果不对，先查语义和调用顺序；消息很小却慢，查启动、依赖和协议；大消息上不去，继续追实际数据路径与共享带宽。运行时细节接 [[8.19 NCCL 运行时：Communicator、Channel、Chunk、Protocol 与 Proxy|8.19 NCCL 运行时]]，物理路径接 [[8.20 NCCL 拓扑与数据路径：PCIe、NVLink、NVSwitch、RDMA 与 GPU-NIC Affinity|8.20 NCCL 拓扑与数据路径]]。

## 2. Collective：先把输入、输出和 rank 的含义写对

### 2.1 rank 是 Communicator 中的逻辑身份

设一个 communicator 包含 $P$ 个参与者，rank 取 $0,1,\ldots,P-1$。基线中的常规部署是每个 rank 关联一张 CUDA GPU；一个进程可以管理一个或多个 GPU，**进程数、GPU 数、rank 数不应不加条件地画等号**。[^comm]

需要同时记录四个标识：全局 rank、节点内 local rank、当前进程可见的 CUDA device ordinal、物理 GPU UUID / PCI bus ID。`CUDA_VISIBLE_DEVICES` 可能重排可见 ordinal；“rank 3”不等于“物理 GPU 3”。有 root 参数的操作，其 root 是 **communicator rank**，不是物理卡号。[^collectives]

### 2.2 核心操作的形状

下面用总向量 $M$ 字节表示归约类输入，用 $M/P$ 表示一个等长分片；元素个数由字节数除以 datatype 大小得到。

| 操作 | 各 rank 的输入 | 各 rank 的输出 | 关键约束 |
| --- | --- | --- | --- |
| AllReduce | 各有一份 $M$ 字节向量 | 各有一份 $M$ 字节归约结果 | 全员参与，逻辑元素一一对应 |
| ReduceScatter | 各有 $M$ 字节输入 | rank $r$ 得到结果的第 $r$ 个分片 | API 的 `recvcount` 是每个 rank 接收的元素数 |
| AllGather | 各有 $M/P$ 字节分片 | 各得到按 rank 排列的 $M$ 字节拼接结果 | API 的 `sendcount` 是每个 rank 的元素数 |
| Reduce | 各有一份输入 | 只有 root 得到完整归约结果 | root 参数需要一致 |
| Broadcast | root 提供输入 | 全员得到 root 的数据 | 不是把每个人的输入都拼起来 |
| Send / Recv | 指定发送和接收端 | 指定对端收到对应数据 | 属于点到点语义，不是全员归约 |

表中展示的是理解本组笔记所需的核心接口，不是所有 NCCL 版本的完整 API 清单。AllGather 的输出按 rank 排列，ReduceScatter 的输出分片也与 rank 相关；不能用“最终大家数据一样”概括所有 collective。[^collectives]

### 2.3 AllReduce 的数学契约

令 rank $r$ 的输入为 $x_r[j]$，SUM AllReduce 要求：

$$
y_r[j]=\sum_{k=0}^{P-1}x_k[j],\qquad\forall r,j.
$$

不同 rank 提供的是同一逻辑位置的不同贡献，不是不同大小的任意字节串。各参与者必须匹配操作、数据类型、数量和调用次序；有 root 的操作还要匹配 root。错配不是“性能差一点”，而可能挂起、报错或产生错误结果。[^collectives][^groups]

> [!warning] 两个容易混淆的“相同”
> **数学意义相同，不等于浮点结果逐位相同。** 不同归约顺序可能改变浮点舍入。验证不能总用 `memcmp` 替代数值误差检查。与此同时，同一个实际 collective 的各 rank 仍应满足其约定输出；不能把持续的异常差异都归咎于浮点误差。数值判断应依据数据类型、归约规模和业务误差预算。

### 2.4 ReduceScatter + AllGather：语义分解，不是强制实现流程

先将各输入逐元素归约，只把最终结果分片分配给各 rank；再交换这些已归约分片，每个 rank 都能拼回完整结果。这解释了：

$$
\operatorname{AllReduce}(x)\equiv
\operatorname{AllGather}(\operatorname{ReduceScatter}(x)).
$$

这个等价关系是**输出契约层面**的。实际 NCCL 可以在设备内核中把阶段连接处的归约、写回和发送融合，不需要应用先调用一次 `ncclReduceScatter`、等所有 GPU 同步，再调用一次 `ncclAllGather`。[^collectives][^ring-src]

## 3. 四个 rank 推演 Ring：不要只背“绕两圈”

### 3.1 固定本节的教学约定

逻辑环为 $0\rightarrow1\rightarrow2\rightarrow3\rightarrow0$。每个 rank 的输入按位置切成四块 $C_0,C_1,C_2,C_3$。使用下标表示块号，上标表示“已有谁的贡献”，例如 $C_0^{1,2}$ 表示第 0 块已叠加 rank 1、2 的输入。

本节安排 ReduceScatter 结束时 rank $r$ 保留最终 $C_r$。这是一种方便推演的编号方式；实现可以选择不同环顺序和不同起始块，但仍需满足相同输出契约。

### 3.2 ReduceScatter 的三轮

第 $s$ 轮，$s=0,1,2$，rank $r$：

$$
\text{发送块号}=(r-s-1)\bmod4,\qquad
\text{接收块号}=(r-s-2)\bmod4.
$$

接收端将收到的部分和与自己对应块相加。所有 rank 同时发送和接收，下面只列每一轮**发送出去的块**：

| 轮次 | rank 0 → 1 | rank 1 → 2 | rank 2 → 3 | rank 3 → 0 |
| --- | --- | --- | --- | --- |
| RS-1 | $C_3^{0}$ | $C_0^{1}$ | $C_1^{2}$ | $C_2^{3}$ |
| RS-2 | $C_2^{3,0}$ | $C_3^{0,1}$ | $C_0^{1,2}$ | $C_1^{2,3}$ |
| RS-3 | $C_1^{2,3,0}$ | $C_2^{3,0,1}$ | $C_3^{0,1,2}$ | $C_0^{1,2,3}$ |
| 最后一次接收并归约后 | rank 0 持有完整 $C_0$ | rank 1 持有完整 $C_1$ | rank 2 持有完整 $C_2$ | rank 3 持有完整 $C_3$ |

跟踪 $C_0$ 内的一个元素：四个 rank 的贡献分别为 $1,10,100,1000$。rank 1 发出 $10$，rank 2 归约为 $110$，rank 3 归约为 $1110$，rank 0 最终归约为 $1111$。每条边不是重复发送整个向量，而是在并行推进不同块。

![[图片/SVG/8_8_18_2.svg|900]]

图上半部分跟踪一个块，下半部分显示完成 ReduceScatter 后的持有关系及 AllGather 的扩散。**追踪单块是为了看依赖，不代表其他块在旁边空等。**

### 3.3 AllGather 的三轮

归约已结束，这三轮只复制和转发完整结果块，不再把本地原始输入重复加进去。

| 状态 | rank 0 已拥有 | rank 1 已拥有 | rank 2 已拥有 | rank 3 已拥有 |
| --- | --- | --- | --- | --- |
| AG 前 | $C_0$ | $C_1$ | $C_2$ | $C_3$ |
| AG-1 后 | $C_0,C_3$ | $C_1,C_0$ | $C_2,C_1$ | $C_3,C_2$ |
| AG-2 后 | $C_0,C_3,C_2$ | $C_1,C_0,C_3$ | $C_2,C_1,C_0$ | $C_3,C_2,C_1$ |
| AG-3 后 | 全部四块 | 全部四块 | 全部四块 | 全部四块 |

“已拥有”的表内顺序表示传播过程；实际输出缓冲区仍按原始块偏移写回，不是按到达顺序随意拼接。

### 3.4 对照源码：概念阶段在实现里可以融合

在固定版本的 `src/device/all_reduce.h` 中，`runRing` 可以沿下面的 primitive 名称阅读：

| Primitive | 阅读时对应的职责 |
| --- | --- |
| `directSend` | 把本轮起始数据交给后继 |
| `directRecvReduceDirectSend` | 收到部分和，合并本地贡献并继续转发 |
| `directRecvReduceCopyDirectSend` | 形成一个最终归约块，写输出，同时开始向后传播 |
| `directRecvCopyDirectSend` | 复制已归约结果并继续转发 |
| `directRecv` | 接收最后缺失的结果块 |

这里的 `Direct` 是内部 primitive 名称，**不能仅凭函数名证明当前网络使用了 GPUDirect RDMA 或直接注册了用户缓冲区**；还要结合 transport、连接 flags、内存注册与缓冲区路径。[^ring-src][^net-src]

源码中的 `ncclCollCbdPart`、`channelCount`、`chunkCount`、`loopCount` 把上面的数学分块映射到实际并行工作。尾部不足一个完整循环时还会调整分块和对齐。因此真实代码并非“每次永远固定四等分”的循环翻译。

## 4. 字节账：一张卡到底发送了多少？

### 4.1 明确单位和统计边界

设 $M$ 为**每个 rank 的完整输入向量字节数**，不是所有 rank 输入的总和。环内每阶段 $P-1$ 轮，每轮每个 rank 发送 $M/P$ 字节，忽略尾部对齐、协议 flag、报文头等额外开销。

$$
V_{\mathrm{tx,RS}}=\frac{P-1}{P}M,
\qquad
V_{\mathrm{tx,AG}}=\frac{P-1}{P}M.
$$

所以：

$$
\boxed{V_{\mathrm{tx,rank}}=2\frac{P-1}{P}M}
$$

每个 rank 接收同样多；**收发合计**为 $4(P-1)M/P$。把全体 rank 的发送量相加，得到 $2(P-1)M$。这三个统计口径都正确，但不是同一个指标。[^perf]

![[图片/SVG/8_8_18_4.svg|900]]

图中每个完整长条是 $M$；8 个格中的 7 个表示一次阶段发送 $7M/8$。它没有把接收量再算进单向发送带宽。

### 4.2 一个可手算的例子

【教学算例】$P=8$，每个 rank 输入 $M=1\,\mathrm{GiB}$：ReduceScatter 发送 $0.875\,\mathrm{GiB}$，AllGather 再发送 $0.875\,\mathrm{GiB}$，合计发送 $1.75\,\mathrm{GiB}$、接收 $1.75\,\mathrm{GiB}$。

假设这条抽象链路的**有效单向**载荷带宽为 $25\,\mathrm{GiB/s}$，只计算串行链路传输项：

$$
T_{\mathrm{bytes}}=\frac{1.75\,\mathrm{GiB}}{25\,\mathrm{GiB/s}}
=0.07\,\mathrm{s}=70\,\mathrm{ms}.
$$

这不是某代 GPU 或 NIC 的预期成绩；它只是验证单位和公式的题目。若硬件文档使用十进制 GB/s，必须先统一单位，不能把 GiB 和 GB 当成同一个数字。

### 4.3 延迟项解释为什么 Ring 并非总是最优

用 $\alpha$ 表示每个依赖阶段的等效启动成本，$B$ 表示模型中的单向有效带宽，得到一个简化模型：

$$
T_{\mathrm{ring}}\approx 2(P-1)\alpha
+2\frac{P-1}{P}\frac{M}{B}
+T_{\mathrm{reduce/memory}}.
$$

这个模型刻意省略复杂重叠、共享链路争用、不同 Channel 的工作差异和内核调度。**它用于解释趋势，不用于承诺真实时延**：小 $M$ 时启动和依赖阶段显眼；大 $M$ 时持续搬运和内存处理占比增加。更多 rank 不是免费增加算力，也会改变同步等待和路径。

不要把 $T_{\mathrm{reduce/memory}}$ 看成一项必然与网络完全串行相加的实测成本；真实流水线可能重叠，最终取决于关键路径。其价值是提醒：NCCL 通信内核同样要消耗 GPU 执行与内存资源。

## 5. Tree：减少依赖深度，不是简单地“所有数据都挤到一张卡”

### 5.1 先理解单树，再理解双树

一棵归约树把子节点的部分结果逐层合并到根，再沿树分发完整结果。平衡树的依赖深度随 $\log P$ 增长；与长 Ring 相比，这有利于降低小消息的依赖延迟。但朴素单树会让内部节点承担更多转发工作，根附近也可能成为热点。[^double-tree]

NCCL 的经典优化是 **complementary double binary trees**：把数据分给两棵互补树，让一棵树中的内部节点尽可能在另一棵树中承担叶子角色，从而改善负载均衡。这里的“根”是算法内部角色；AllReduce 公共 API 本身没有一个应用指定的 root。[^double-tree]

![[图片/SVG/8_8_18_3.svg|900]]

图展示四个 rank 的一种互补关系，颜色表达内部节点与叶子角色；它是双树思想示意，**不是声称 NCCL 在任意机器上都生成图中的编号和边**。真实建树还要适配节点内连接与跨节点层次。

### 5.2 不要把教科书公式贴到 NCCL 双树上

若人为规定“每层都等完整 $M$ 字节收完才能启动下一层”，可以写出朴素整向量树的估算：

$$
T_{\mathrm{naive\ tree}}\approx
2\lceil\log_2 P\rceil\left(\alpha+\frac{M}{B}\right).
$$

**这个公式不等于 NCCL Tree 的性能公式。** 双树、切块、收发并行、归约与分发流水化都会打破这个串行假设。固定版本源码中，`runTreeUpDown` 和 `runTreeSplit` 的组织方式就不同；后者可把 GPU 线程分组承担上行归约和下行广播。[^ring-src]

因此，面试里只说“Tree 带宽一定比 Ring 差、消息超过某个固定大小就切 Ring”不够严谨。更可靠的表达是：Ring 和 Tree 在依赖深度、负载分配、拓扑映射、内核成本上存在取舍；选择还与 Protocol、硬件和消息形状一起决定。

### 5.3 Ring / Tree 不是整个 NCCL 算法空间

支持的系统可能使用 NVLS / NVLSTree 等 NVLink SHARP 路径，或通过 collective-network 能力进行分层、卸载。**NVSwitch 的普通转发能力与支持条件下的归约卸载是两件事**，不能说“有 NVSwitch 就不需要 GPU 执行 NCCL 内核”。实际启用由硬件、版本、注册方式和运行时选择共同决定。[^algo-env]

本组三篇先建立最通用的 Ring / Tree / 传统 NET proxy 心智模型，不覆盖所有新版 device API、GPU-initiated networking 或硬件专用算法。阅读新功能时，应先判断它改变了五层中的哪一层，而不是把全部旧模型一律否定。

## 6. NVLink、NVSwitch 与 RDMA 分别提供什么

NVLink / NVSwitch 主要回答 GPU 域内的高速可达和交换问题；PCIe 连接 GPU、CPU 根复合体与 NIC；RDMA fabric 回答 NIC 之间的远端传输问题。经典多机训练中，一次 AllReduce 可以同时使用节点内 NVLink 和节点间 RDMA，并且每一段都有独立的容量与拥塞边界。[^gdr][^net-src]

这里的“节点内”是典型部署描述，不是 NVLink 技术永久的物理边界；多节点 NVLink 系统需要按实际 NVLink domain 理解。不要把“单机等于 NVLink，多机等于 RDMA”当作通用定律。[^algo-env]

对于从高性能存储过来的读者，尤其要记住三个边界：

- **RDMA 完成不等于整个 Collective 完成。** 它可能只是某个 Channel 中某一段数据的传输完成，后面仍有归约、转发或写回。
- **GDR 不等于 NCCL 内部没有任何数据复制。** NIC 可以直接访问显存，但应用缓冲区和 NCCL 内部显存缓冲区仍可能不同。
- **Collective 完成不等于数据已经持久化。** 这不是 WAL、fsync 或 checkpoint commit 的替代品；[[8.6 Checkpoint 同步异步分片]] 的一致性与持久化边界仍要单独建立。

## 7. 怎样读 nccl-tests 的成绩，而不是被数字骗了

### 7.1 `algbw` 与 `busbw`

对 AllReduce，`nccl-tests` 使用：

$$
\mathrm{algbw}=M/T,\qquad
\mathrm{busbw}=\mathrm{algbw}\times\frac{2(P-1)}{P}.
$$

`algbw` 帮你估算业务张量完成时间；`busbw` 用 collective 对应的流量因子做归一化。它**不是 NIC port counter 直接测出的物理线速**，也不意味着所有字节都走了同一根线。多级互联、共享端口和硬件卸载下，更不能把它无条件对标一张 NIC 的标称带宽。[^perf]

ReduceScatter 和 AllGather 的归一化因子为 $(P-1)/P$，但相应 $M$ 的口径要按测试说明取总输入或总输出，不能直接拿 `recvcount` / `sendcount` 当总字节数。读取延迟时也必须看当前输出表头的单位，不能从旧截图记忆是 μs 还是 ms。

### 7.2 API 返回时间不是 GPU 完成时间

把 CPU 调用 `ncclAllReduce` 前后的两次时钟相减，通常测到的是主机提交成本及可能的主机等待，不是完整 collective。需要区分 CUDA event 设备时间、主机墙钟时间、所有 rank 的整体完成与框架 step time。CUDA Graph、warmup 和调用聚合也会改变测量口径。[^streams][^tests]

同样，默认输出的平均时间不是 P99。要研究尾延迟，应在所用版本支持的逐次计时机制或自行设计的采样中保留分布、样本量、异常 rank 和采样开销；不能把 20 次运行的一个均值写成“P99”。

## 8. 实验：从单机正确性到算法选择，不急着改所有开关

### 8.1 准备和最小基线

本节需要真实 NVIDIA GPU、可用 CUDA / NCCL，以及已经编译好的 `nccl-tests`；**本笔记没有执行这些 GPU 实验**。编译使用项目 README 中与环境匹配的 `CUDA_HOME` / `NCCL_HOME`；跨进程、跨节点测试还需以 `MPI=1` 构建，并记录测试仓库 commit。[^tests]

以下是**单进程、两张可见 GPU**的 size sweep。在已清除旧调优变量的测试 shell 中运行，先确认可见 GPU 数与可用显存足够：

```bash
./build/all_reduce_perf \
  -b 8 -e 256M -f 2 -g 2 \
  -w 5 -n 20 -c 1
```

`-b/-e` 给出扫描范围，`-f 2` 每次翻倍，`-g 2` 是每线程使用两张卡，不是两台机器；`-w` 的预热不计入正常计时，`-c 1` 保留结果校验。此处 `256M` 是工具的 MiB 口径。预热次数只是实验起点，不是保证稳态的常数。

### 8.2 一次只限制一种算法

在独立进程中临时限制算法，其他消息参数保持不变；这是一组定位实验，不是生产配置建议：

```bash
NCCL_ALGO=Ring ./build/all_reduce_perf \
  -b 8 -e 256M -f 2 -g 2 -w 5 -n 20 -c 1

NCCL_ALGO=Tree ./build/all_reduce_perf \
  -b 8 -e 256M -f 2 -g 2 -w 5 -n 20 -c 1
```

自动选择、仅 Ring、仅 Tree 三组都要保留。限制算法后，运行时还可能调整 Protocol 和 Channel，所以这不是严格隔离所有内部变量的微实验；需要日志帮助解释。如果平台或操作没有可用组合，应记录失败原因，而不是继续把更多开关强行打开。[^algo-env]

若需要追调用时序，按下一篇的 Stream / Event 图看“提交→等待→完成”；本段 shell 命令自身没有额外需要绘制的分布式协议时序。

### 8.3 记录表与可证伪的问题

| 必记条件 | 结果列 | 这一列回答什么 |
| --- | --- | --- |
| GPU UUID、节点数、rank 映射 | correctness / 错误位置 | 实验先正确了吗？ |
| CUDA / driver / NCCL / tests commit | 初始化时间、首轮时间 | 冷启动是否被混进稳态？ |
| $M$、dtype、operation、in/out-of-place | time、algbw、busbw | 比较的是同一个问题吗？ |
| 默认 / Ring / Tree、实际协议与通道信息 | 多次独立运行差异 | 算法约束是否真的改变选择？ |
| 单机 / 跨机、NIC / NVLink / PCIe 路径 | 节点与链路计数器 | 瓶颈是否确实落在推测的路径？ |

建议带着三个问题做实验：小消息是否更受启动和依赖影响？增加 rank 后哪个 size 区间最先变差？单机良好、跨机变差时，是单 NIC 饱和、GDR / NUMA 路径问题，还是某个 rank 更晚进入 collective？不能仅凭一张带宽曲线把这几种原因合并。

## 9. 接到训练、推理和存储：哪些问题仍在 NCCL 之外

一个框架可以把多个小梯度合并成 bucket 再做归约：调用次数减少，但 bucket 必须等更多数据准备好。过小的 bucket 可能增加启动成本；过大的 bucket 可能推迟通信，缩短与后向计算的重叠窗口。这是**数据就绪时间与通信吞吐的共同优化**，不是只比较某次 AllReduce 的带宽。

同一节点做 [[8.17 万卡集群分布式 Checkpoint 极致加速实践（MegaScale & DeepSeek 方案）|分布式 Checkpoint]] 时，网络写存储和训练通信可能竞争 NIC、PCIe、CPU、内存带宽；因此“单独 nccl-tests 很快”不是业务共载仍然很快的证明。这里可建立一个可检验的假设：在固定计算负载下引入受控 checkpoint 流量，记录 step time 和对应链路利用率是否共同变化。未经这样的对照，不把相关性当作已确认原因。

对 [[8.16 PD 分离（Prefill-Decode Disaggregation）下的 KV Cache 网络传输架构|PD 分离的 KV Cache 传输]] 也一样：很多传输是按请求动态形成的点到点数据流，不能因为“都在 GPU 间传数据”就强行改成所有 rank 共同 AllReduce。

## 10. 自测：能够讲清这些，才算把算法层接起来

**问：八张卡每张 1 GiB，Ring AllReduce 是每张卡发送 8 GiB 吗？**  
不是。在等分、忽略额外开销的模型里，每张卡发送 $2\times7/8\times1=1.75$ GiB，接收同样多。8 GiB 是全体输入字节总和，不是单 rank 网络发送量。

**问：ReduceScatter 已算出完整的全局和，为什么还需要 AllGather？**  
全局结果已经形成，但它分散在不同 rank 上。每个 rank 只持有一个最终分片；AllGather 让全员拿到完整向量。需要分片结果的上层算法则可以停在 ReduceScatter，不必恢复全量。

**问：Tree 的算法根就是 rank 0 吗？**  
不应这样假设。AllReduce API 没有 root 参数，内部树的根和边由算法与拓扑安排，可以存在多棵树和多个 Channel。

**问：有 NVSwitch，跨机就不需要 NIC 了吗？**  
在经典 NVLink 域内 + RDMA 跨域部署中仍需要 NIC / fabric。若系统采用多节点 NVLink，应按其真实域边界分析，而不是套“机箱边界”定律。

**问：为什么加通道后 AllReduce 变快，训练 step 反而可能变慢？**  
这是资源竞争假设：通信可能占用更多 GPU 执行与内存资源，挤压计算，或使后续同步更不均匀。应比较端到端 step 和 GPU 时间线，不能仅用通信微基准评价业务最优点。
