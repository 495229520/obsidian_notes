# MLPerf Storage

> [[8.7 DataLoader 与 GPU 空闲归因]] 把「GPU 为什么空」讲成了机制，但那是定性的。真到选型、验收、对比两套存储时，你需要一个**可比较的数**：这套存储能喂饱几张 H100？MLPerf Storage（MLCommons 的存储基准）就是把 8.7 那道题变成一张标准考卷。它有一个漂亮的设计：**把真 GPU 从回路里拿掉，用 `sleep` 冒充算力**——于是测出来的纯粹是「存储 + 主机数据面」把数据喂到位的能力，与你手上有没有 GPU、是什么型号无关。考卷的判分线就是 8.7 的空泡：**AU（加速器利用率）≥ 90%**（CosmoFlow 放宽到 70%）等价于「空泡 < 10%」。
>
> 本篇继续用那个负载串讲：**8 卡 ResNet-50 类小文件训练 + 周期 checkpoint**。只不过这次不看某一次运行，而是问「这套存储在这类负载下能撑到几张卡」。

前置：[[8.7 DataLoader 与 GPU 空闲归因]]（空泡与 AU、三段流水线）、[[8.6 Checkpoint 同步异步分片]]（checkpoint 负载已进 v2.0 考卷）、[[9.1 fio Benchmark Matrix]]（可复现负载与「测量对象」的纪律）。

---

## 1. 它回答什么问题：把空泡变成一个数

传统存储 benchmark（[[9.1 fio Benchmark Matrix]]）回答「这块盘能跑多少 IOPS / 多少 GB/s」。但 AI 训练不关心裸 IOPS，关心的是**在真实访问模式下，存储能不能让加速器不挨饿**。MLPerf Storage 直接测这个，报两个量【事实】：

- **支持的加速器数**：在给定负载与 AU 门槛下，这套存储能同时喂饱多少张（模拟的）加速器；
- **聚合吞吐**：达到那个规模时的总带宽（GiB/s）。

一句话：它把 [[8.7 DataLoader 与 GPU 空闲归因]] 的 AU 从「一次运行的诊断量」升格成「一套存储的容量指标」。**AU 是判分线，加速器数是分数。**

---

## 2. 关键设计：拿掉 GPU，用 sleep 模拟算力

MLPerf Storage 底层是 **DLIO**（Deep Learning I/O benchmark）【事实】。它的核心把戏在下图①：不跑真的神经网络，而是**用一段 `sleep` 冒充「GPU 算一个 batch」的耗时**——这个耗时是按真实加速器（A100 / H100）在该模型上的实测算力标定的。

![MLPerf Storage 全景：① 模拟加速器回路——读一个 batch（真打存储）→ sleep 模拟算力 → 循环，两条时间线对比「存储跟得上（wait≈0，compute 背靠背，AU≈99%）」与「存储跟不上（每轮先等 batch 再算，wait 累积，AU<90%）」，并给出 AU=busy÷(busy+wait) 的定义；② 三类负载 = 三种存储画像——3D-Unet 大样本带宽墙门槛90%、ResNet-50 小样本元数据+IOPS墙门槛90%、CosmoFlow 中样本门槛70%，各附示例提交量级；③ 扩展曲线——加卡直到 AU 跌破90%门槛，前一档即支持卡数 N*，标注加卡→聚合需求↑→存储/主机饱和→wait↑→AU↓；④ checkpoint 负载（v2.0 新增）测写/读 B/W 与时长，N-rank 齐射为 incast 突发；底部为测量陷阱——数据集必须大于主机内存否则第二 epoch 页缓存作弊、主机 CPU/RAM 是隐藏变量、AU 是某配置下的一个点不能跨配置搬](../../图片/SVG/mlperf-storage-AU与加速器扩展.svg)

这个设计为什么诚实【设计】：

- **隔离出被测对象**。真训练里，GPU 慢、通信慢、存储慢都会拉低利用率，混在一起没法归因（正是 [[8.7 DataLoader 与 GPU 空闲归因]] §5 要三刀切的原因）。把 GPU 换成确定性的 `sleep`，计算段的时长就成了已知常数，于是**唯一的变量就是存储 + 主机能不能在这段时间里把下一个 batch 备好**。测出来的 AU 干干净净只反映数据面。
- **可复现、可比较**。真 GPU 有型号差异、驱动差异、功耗墙；`sleep` 没有。两家厂商用同一个 DLIO 配置跑，数字才可比。
- **不需要一屋子 GPU 去测存储**。这是工程上的大便利：你可以用一台没有 GPU 的机器，模拟出「128 张 H100 的数据需求」去压存储。

回路的每一轮就是 8.7 那条流水线的消费端：`读 batch（真 IO）→ sleep（算力）→ 循环`。存储跟得上，`sleep` 背靠背、`wait≈0`、AU≈99%；跟不上，每轮开头先卡一段 `wait`（空泡），AU 掉下去（对照上图①两条时间线）。**AU = busy ÷ (busy + wait)**，就是 8.7 的空泡公式换了归一化。

## 3. 三类负载 = 三种存储画像

考卷不止一道题。MLPerf Storage 用几个代表性模型，各自压存储的不同软肋（下图②，样本尺寸为量级、随数据集实现有别【量级/前提】）：

| 负载 | 样本尺寸 | 压的墙 | AU 门槛 | 示例提交量级 |
| --- | --- | --- | --- | --- |
| **3D-Unet**（医学影像） | ~140 MB 级（大） | 顺序**带宽** | 90% | 8 卡 ~23 GiB/s @ 99% |
| **ResNet-50**（ImageNet） | ~110 KB 级（小 JPEG） | **元数据 + 随机 IOPS** | 90% | 128 卡 ~24 GiB/s @ 99.6% |
| **CosmoFlow**（宇宙学） | ~2 MB 级（中） | 中间地带 | **70%** | 8 卡 ~4.3 GiB/s @ ~75% |

三道题压三种能力，把 [[8.7 DataLoader 与 GPU 空闲归因]] §2 那张「三段各吃一种资源」的表实测了一遍【事实】：

- **3D-Unet 是带宽题**：样本大、顺序读，瓶颈在能不能持续拉出足够 GiB/s。这类负载 GDS 直读（[[8.2 GDS 与 cuFile]]）真能加分。
- **ResNet-50 是元数据题**：海量小文件，瓶颈在 `open`/`stat` 的元数据 QPS 与随机小读（[[7.2 元数据路径瓶颈]]）。注意它虽然聚合带宽和 3D-Unet 差不多，却能支持**多得多的卡**——因为单卡的数据速率需求低，存储的软肋是「每秒能处理多少个小文件请求」而非「每秒多少字节」。
- **CosmoFlow 门槛为什么只有 70%**【前提】：它的模拟算力相对更快（`sleep` 更短），数据更难「藏进计算背后」——同样的存储，留给预取的时间窗更窄，90% 门槛不现实，于是标准把它定在 70%。**这提醒一件事：门槛是负载属性，报结论必须连门槛一起报。**

## 4. 扩展曲线：加卡为什么会把 AU 压垮

MLPerf Storage 的测法是**加卡加到 AU 跌破门槛**（下图③）：从少数模拟加速器起步，逐步增加并发的加速器数，每张卡都在独立地跑「读 batch → sleep」的回路，一起打同一套存储。曲线一开始平在 99% 附近，到某个 N* 突然膝盖式下跌——**前一档就是「支持的加速器数」**。

这条曲线把本章的因果链完整地展开了一遍【因果】：

```text
加卡(N↑)
  → 聚合数据需求↑          （N 张卡每秒要 N 份 batch）
  → 存储/主机某处先饱和     （元数据 QPS 墙 / 带宽墙 / CPU 解码墙 / 网卡墙）
  → 每轮取 batch 的 wait↑   （请求排队,尾延迟被抬高）
  → 预取队列撑不住,抽干     （8.7 §3:队列吸收方差,补不了均值）
  → AU↓                     （空泡占比上升,跌破门槛）
```

先饱和的是哪一堵墙，取决于负载（§3）和你的系统：小文件负载先撞元数据/网络往返的墙，大文件负载先撞带宽墙，主机弱的先撞 CPU 解码墙。**这正是为什么 MLPerf Storage 比裸 fio 更有意义**——它不是问「峰值带宽多少」，而是问「在真实访问模式下，哪堵墙先塌、塌在几张卡」。膝点的位置就是这套系统喂养能力的上限。

尾延迟在这里是主角而不是配角【因果】：AU 掉不是因为平均带宽不够（平均可能还有余量），而是因为**加卡后请求排队、单次取数的 p99 被拉高**，超过了队列存货能撑的时间，于是空泡。这条线索直接引向 [[9.5 p99 毛刺定位]]——扩展曲线的膝点，本质是尾延迟随并发上升的拐点。

## 5. checkpoint 负载：v2.0 把 8.6 也搬上了考卷

v2.0（2025）新增了 **checkpoint 工作负载**，针对大模型在 scale-out 系统上的存档/恢复【事实】。它测的东西和喂数据正交（下图④）：

| 方向 | 指标 | 对应 8.6 的哪一段 |
| --- | --- | --- |
| 写 | 写 B/W（GiB/s）+ 写时长（s） | [[8.6 Checkpoint 同步异步分片]] 的落盘：停算与 goodput 扣分 |
| 读 | 读 B/W + 读时长 | 恢复路径：故障后要停多久才能续训 |

为什么它是**另一类**能力，而不是喂数据的延伸【设计】：

- 喂数据是**持续、稳态**的小-中块读；checkpoint 是**突发、一次性**的大块写（和随后的大块读）。一套存储可能很擅长持续喂、却扛不住突发写，反之亦然。
- checkpoint 写是 8.6 §4 的 **N-rank 齐射**——多个 rank 同一时刻把各自的分片砸向存储，是典型的 incast 突发（[[4.7 PFC ECN 与 DCQCN]]）。这考的是聚合写带宽和突发下的尾延迟，与「每秒能处理多少小文件请求」是两回事。

所以 v2.0 的考卷实际上有两张脸：一张问「能喂饱几张卡」（§1–4），一张问「存档/恢复要停多久」（本节）。选型时两张都要看——它们可能指向不同的系统设计。

## 6. 测量陷阱：AU 高 ≠ 你的存储强

这是本篇最该带走的部分。一个数字要有意义，前提得对（下图底部）：

**① 数据集必须大于主机内存**【前提】。否则第二个 epoch 大面积命中页缓存（[[1.2 Page Cache 命中与未命中]] §3、[[8.7 DataLoader 与 GPU 空闲归因]] §4①），测出来的是 DRAM 带宽而不是存储——AU 虚高。MLPerf Storage 明确要求数据集规模远超客户端内存来堵这个洞。**自检信号**：如果你自己拿 DLIO 跑，第二个 epoch 突然飙上去，就是页缓存在作弊。

**② 主机是隐藏变量**【前提】。AU 反映的是「存储 + 主机数据面」的合力，不是存储单独的成绩。主机的 CPU（解码能力）、内存（页缓存 + 预取缓冲）、网卡数都会影响 AU——**一台胖主机会美化存储**。所以比较两份提交前，要先对齐主机口径：几台客户端、每台多少 RAM、什么网络。这和 [[9.4 eBPF biolatency biosnoop]] 反复讲的「口径不同的数字不能直接相减」是同一条纪律。

**③ AU 是某配置下的一个点**【事实】。换数据集、换模拟的加速器型号、换主机数，膝点都会移动。一份提交说「支持 128 卡」，只在它那套配置下成立，不能直接搬到你的环境。**读一份提交，四个字段必须对齐**（下图④右）：支持的加速器数 @ 目标 AU、聚合 GiB/s、主机/客户端/网络口径、数据集是否大于内存。缺一项，数字不可比。

## 7. Modern C++：最小 emulated-accelerator 回路

把 §2 的回路写出来，直接复用 [[8.7 DataLoader 与 GPU 空闲归因]] §6 的 `DataLoader`——这段代码就是 DLIO「模拟加速器」的最小核：

```cpp
#include <chrono>
#include <cstdint>
#include <thread>

// 模拟一个加速器:读 batch(真 IO)→ sleep(算力)→ 循环;统计 busy/wait 算 AU
class EmulatedAccelerator {
public:
    using clock = std::chrono::steady_clock;

    // compute = 真加速器在该模型上算一个 batch 的标定耗时(A100/H100 实测)
    explicit EmulatedAccelerator(std::chrono::microseconds compute)
        : compute_{compute} {}

    // loader 来自 8.7;返回本 step 是否成功取到 batch
    bool step(DataLoader& loader) {
        const auto t0 = clock::now();
        auto batch = loader.next();               // 队列空则阻塞 —— 这段就是 wait(空泡)
        const auto t1 = clock::now();
        if (!batch) return false;                 // 数据源耗尽,epoch 结束

        std::this_thread::sleep_for(compute_);    // 用 sleep 冒充 GPU kernel(DLIO 的核心)
        const auto t2 = clock::now();

        wait_ += t1 - t0;                         // 等 batch 的时间 = 空泡
        busy_ += t2 - t1;                         // 模拟算力的时间 = 有效 busy
        return true;
    }

    // AU = busy /(busy + wait);门槛依负载:ResNet-50/3D-Unet 0.90,CosmoFlow 0.70
    double accelerator_utilization() const {
        const auto total = busy_ + wait_;
        if (total.count() == 0) return 1.0;
        return static_cast<double>(busy_.count())
             / static_cast<double>(total.count());
    }

private:
    std::chrono::microseconds compute_;
    clock::duration busy_{0};
    clock::duration wait_{0};
};
```

**逐段讲解**：

- **`sleep_for(compute_)` 是整个方法论的支点**：它把「计算段耗时」变成一个确定的已知量，于是 `wait_`（阻塞在 `loader.next()` 上的时间）就纯粹反映数据面跟不跟得上。这正是 §2 说的「隔离出被测对象」；
- **`wait_` 的来源**：`loader.next()` 在预取队列空时阻塞（[[8.7 DataLoader 与 GPU 空闲归因]] §6 的 `pop`），阻塞多久就是空泡多久。真 GPU 里这段是「SM 空转等 H2D」，这里被 `steady_clock` 精确捕捉；
- **`steady_clock` 而非 `system_clock`**：算时间差要用单调时钟，不受 NTP 校准影响——和 [[9.4 eBPF biolatency biosnoop]] §4.2 用 `bpf_ktime_get_ns()` 同一个道理；
- **怎么扩展成扩展曲线（§4）**：跑 N 个 `EmulatedAccelerator`（各持一个独立数据流）并发打同一套存储，取所有卡 AU 的最小值；从小到大扫 N，找到最后一个「min(AU) ≥ 门槛」的 N，就是「支持的加速器数」。加卡→聚合需求↑→某卡先饿→min(AU) 先破线，曲线的膝点自然浮现。

这段代码的价值不在跑分，而在于：**它让你能用手上的机器，本地复现 8.7 的空泡归因实验**——把 `compute_` 设成你的 GPU 实测值，接上真实数据源，`accelerator_utilization()` 就是你这套存储在这个负载下的自测 AU。

## 8. 陷阱与误区

> [!warning] 常见错误
> 1. **拿 AU 高当存储强**：AU 是「存储 + 主机」的合力，胖主机会美化存储（§6②）；比较前先对齐主机口径。
> 2. **数据集小于内存就跑**：第二 epoch 页缓存作弊，测的是 DRAM（§6①、[[1.2 Page Cache 命中与未命中]]）——第二 epoch 突然变快就是信号。
> 3. **跨配置搬结论**：「支持 128 卡」只在它那套数据集/加速器型号/主机数下成立（§6③）——换环境要重测。
> 4. **报结论不报门槛**：CosmoFlow 是 70%、ResNet-50/3D-Unet 是 90%（§3）——门槛是负载属性，脱离门槛的 AU 没意义。
> 5. **把裸 fio 峰值当喂养能力**：fio 测峰值带宽，MLPerf 测「真实访问模式下哪堵墙先塌」（§4）——小文件负载的墙在元数据不在带宽。
> 6. **忽略 checkpoint 是另一类能力**：喂数据强不代表突发写强（§5）——两张考卷要分别看。
> 7. **误以为它需要真 GPU**：核心恰恰是用 `sleep` 拿掉 GPU（§2）——所以能用无 GPU 的机器压存储。

## 9. 关键结论

| 结论 | 性质 |
| --- | --- |
| MLPerf Storage 把 8.7 的 AU 从诊断量升格为容量指标：报「支持几张卡 + 聚合 GiB/s」 | 事实 |
| 核心设计：拿掉真 GPU，用 sleep（DLIO）冒充算力 → 隔离出「存储 + 主机数据面」这个被测对象 | 设计 |
| AU = busy ÷ (busy + wait)，就是 8.7 空泡公式的归一化；门槛 90%（CosmoFlow 70%） | 事实 |
| 三类负载压三种墙：3D-Unet 带宽、ResNet-50 元数据/IOPS、CosmoFlow 中间地带 | 事实 |
| 扩展曲线膝点 = 喂养上限：加卡→需求↑→某墙饱和→wait↑→队列抽干→AU↓ | 因果 |
| v2.0 新增 checkpoint 负载（写/读 B/W + 时长）：突发能力与喂数据能力正交（接 8.6） | 事实 |
| AU 高 ≠ 存储强：数据集须 > 内存、主机是隐藏变量、结论不可跨配置搬 | 前提 |
| 读一份提交先对齐四个字段：加速器数@AU、聚合带宽、主机/网络口径、数据集 vs 内存 | 方法论 |
