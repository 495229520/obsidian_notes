# NCCL 拓扑与数据路径：PCIe、NVLink、NVSwitch、RDMA 与 GPU-NIC Affinity

> [!abstract] 这一篇把 NCCL 落到机器和机房
> [[8.18 NCCL 架构与 Collective Communication：Ring、Tree、AllReduce、NVLink 与 RDMA|8.18]] 告诉你算法需要多少通信，[[8.19 NCCL 运行时：Communicator、Channel、Chunk、Protocol 与 Proxy|8.19]] 告诉你谁推进它。本篇继续追问：**一个 rank 的数据经过哪张 GPU、哪段 PCIe、哪块 NIC、哪条 rail？哪一段共享资源决定了实际速度？**
> 目标不是记住拓扑缩写，而是建立“设备身份 → 物理可达 → 运行时选路 → 计数器与对照实验”的证据链。

> [!info] 适用边界
> 内部机制以 NCCL **`v2.27.7-1`** 的传统 host API / NET 路径为基线，部署检查核对至 2026-09-11 可访问的 NVIDIA 文档。拓扑图、400 Gb/s 算例、主机名和网卡名均为**教学示意**，不是你的机器信息或已经执行的测试。多节点 NVLink、C2C、虚拟机和不同网络插件必须按自己的支持条件解读。[^version]

## 1. 三张图：物理拓扑、逻辑拓扑、实际数据路径

| 图的层次 | 主要证据 | 能证明什么 | 不能单独证明什么 |
| --- | --- | --- | --- |
| 物理 / 系统拓扑 | `nvidia-smi topo`、PCIe 树、NUMA、设备 UUID | 操作系统暴露的设备关系与能力 | 某次 NCCL 一定用了这条路径 |
| Collective 逻辑拓扑 | NCCL Ring / Tree / Channel 相关信息 | 算法的参与者和逻辑邻接 | 每条逻辑边都只有一跳物理链路 |
| 实际数据路径 | transport / 注册日志、性能 trace、设备计数器、A/B | 某配置下实际工作的链路与资源 | 没有对照就推断唯一根因 |

一条逻辑边“rank 0 → rank 5”可能经过源 GPU、另一张中转 GPU、PCIe、NIC、交换网络、远端 NIC 和目的 GPU。**逻辑邻居不等于物理直连邻居。** 拓扑优化正是在满足算法契约的前提下，给这些逻辑边寻找合适的物理实现。[^net-src][^paths]

反过来，两张 GPU 之间显示高速 NVLink 可达，也不代表各自到某张 NIC 的路径一样快。需要把 GPU↔GPU 和 GPU↔NIC 两类关系分开看。

## 2. 先认识两种 fabric：GPU 域与网络域

![[图片/SVG/8_8_20_1.svg|900]]

图示是一个双 NUMA、四 GPU、两 NIC 的教学节点：GPU 之间可通过 NVLink / NVSwitch 域互通，NIC 则分别挂在对应 PCIe 分支。**同一张卡同时有 GPU 域和 PCIe / 网络域的关系，两个方向不必共享相同的“最近邻”。**

### 2.1 设备和路径角色

| 对象 | 在本篇中的角色 | 常见误区 |
| --- | --- | --- |
| GPU / HBM | 张量的生产、归约、存储与消费位置 | “显存带宽就是跨 GPU 带宽” |
| NVLink | 支持 GPU 高速互联的链路体系 | “一定永远只在单机机箱内” |
| NVSwitch | NVLink 域内交换，支持能力依代际与系统而定 | “等同于以太网交换机” |
| PCIe Switch | 同一 PCIe 层次内的设备连接与转发 | “挂了多个 x16 设备就有无限上联带宽” |
| Root Complex / Host Bridge | PCIe 层次与主机体系连接 | “经过 CPU 根端口就等于 CPU 执行 memcpy” |
| NUMA / CPU 互联 | 主机计算、内存与跨节点路径 | “绑了 GPU 就自动绑好了所有 CPU 内存” |
| RDMA NIC | 主机或 GPU 缓冲区与远端 fabric 的传输端点 | “NET/IB 就必然直接读写显存” |
| IB / RoCE fabric | NIC 之间的网络交换、容量与拥塞域 | “和 GPU 域有同样的带宽与时延” |

GPU 内部带宽、NVLink 域带宽、PCIe 带宽和 NIC 端口带宽属于不同资源，比较时必须写明方向、单位、共享范围和流量是否经过该资源。[[8.1 GPU 内存层次与数据搬运]] 的内存层次知识在这里成为端到端路径上的多个容量约束。

### 2.2 不把拓扑建议写成支持定义

GPU 与 NIC 同一 PCIe switch 往往是有利的局部结构，但**GPUDirect RDMA 的定义并不是“只能同一 switch”**。支持性和性能取决于 GPU / NIC / driver、根复合体、路由、地址转换和平台限制；某些跨 host bridge 或 C2C 路径也有对应能力与限制。允许某个距离等级的配置，不能创造硬件本来没有的可达性。[^gdr][^env]

普通 PCIe 节点与带 CPU-GPU C2C 互联的平台也不是一回事。某些名称看起来相同的 `PHB` 路径，背后可能有不同的实际互联；应保留机器型号和平台拓扑文档，不只保存一个字母标签。

## 3. `nvidia-smi topo -m`：标签是路径类别，不是带宽排名表

### 3.1 GPU-GPU 矩阵常见图例

下面按 NVIDIA-SMI 文档解释；具体输出和功能以安装的驱动版本为准。[^smi]

| 标签 | 基本含义 | 工程解读 |
| --- | --- | --- |
| `X` | 自身 | 对角线，不是一次传输成绩 |
| `PIX` | 最多经过单个 PCIe bridge / switch 的关系 | 仍要检查实际 lane width、speed 与共享上联 |
| `PXB` | 经过多个 PCIe bridge，而不经过 host bridge | 不代表无限带宽或无争用 |
| `PHB` | 经过 PCIe host bridge，通常与 CPU 相关 | 经过 host bridge 不自动等于 host staging |
| `NODE` | 同一 NUMA 节点内经过多个 host bridge 的路径 | 与跨 NUMA 的 `SYS` 区分 |
| `SYS` | 经过 PCIe 以及 NUMA 节点间的 CPU 互联 | 路径更复杂，但性能与支持不能只靠标签判死刑 |
| `NV#` | 由 `#` 条 NVLink 构成的连接表示 | `#` 不是 GB/s，也不是交换机数量 |

“PCIe bridge”是系统枚举的连接层级用语，不应机械理解成一块独立零售交换芯片。矩阵描述的是路径关系，**不是测量出的延迟 / 带宽矩阵**。

### 3.2 为什么还要看 `topo -mp`

存在 NVLink 时，GPU↔GPU 的主矩阵容易把注意力吸引到 `NV#`；而到 NIC 的路径可能由 PCIe 分支决定。`topo -mp` 只显示 PCIe 关系，有助于把 GPU 域与 PCIe 域拆开观察。P2P capability 检查回答驱动报告的可访问性，仍需实际读写正确性与带宽测试交叉验证。[^smi][^gpu-trouble]

## 4. 四种路径：读日志时必须知道它们哪里不同

### 4.1 GPU↔GPU P2P

在可用且被选择的情况下，GPU 之间可通过 NVLink 或 PCIe peer access 访问数据。它不需要绕到外部 RDMA fabric；但这不意味着所有节点内 GPU 对都一定支持 P2P，也不意味着一个 P2P 能力检查已经验证了每种内存访问模式和完整正确性。[^gpu-trouble]

### 4.2 GDR 网络路径：NIC 访问显存

源 GPU 缓冲区 → 源端 PCIe / 支持的本地互联 → NIC → IB / RoCE fabric → 远端 NIC → 远端 GPU 缓冲区。主机仍参与控制与进度，但大块 payload 不必先落主机 DRAM。[^gdr][^net-src]

这里的“GPU 缓冲区”可能是 NCCL 内部通信缓冲区，也可能是满足注册与算法条件的应用缓冲区。**绕过主机中转与直接使用应用原始缓冲区，是两个独立问题。** 不能仅凭出现 `GDR` 就写“整个应用零复制”。

### 4.3 Host staging：仍可能使用 RDMA 网络

如果某条路径需要主机中转，可抽象为：源 GPU → 源 pinned host buffer → NIC → fabric → NIC → 远端 pinned host buffer → 远端 GPU。GPU↔host 的搬运和访问方式依具体实现而定，未必是 CPU 逐字节复制，但占用了额外的主机缓冲、内存与本地互联资源。[^net-src][^gdr]

因此，**“用了 RDMA”和“没有经过主机 DRAM”不是同义句**。一个 verbs 传输完全可以针对 host MR 工作。注册失败也要区分层次：直接执行某次不被支持的 GPU MR 注册可以报错；上层 NCCL 在不同选择条件下也可能使用另一种 transport 或 staging 路径，不能用“注册 API 不会自动回退”推出“整个通信库不可能回退”。

![[图片/SVG/8_8_20_2.svg|900]]

图中上路省去了两侧 host staging；虚线只表示主机控制与进度，不是 payload 必经边。下路有额外中转，但 fabric 部分仍可由 RDMA NIC 承担。

### 4.4 PXN：先经另一张 GPU，再使用它附近的 NIC

PXN 的核心是利用 NVLink 和中间 GPU，访问非本 GPU 局部的 NIC。某个 rank 的数据可以先走 GPU 域，到更适合目标 rail 或聚合传输的 GPU，再经对应 NIC 发往远端。它改变的是物理实现，不是把应用 rank 永久迁移到另一张卡。[^pxn]

为什么多走一跳反而可能更好？这是路径成本比较：新增的 NVLink 转发成本，可能小于原本跨 host bridge / NUMA 的代价；也可能改善网络 rail 对齐或流量聚合。**不是每台机器、每种消息都获益**。中转 GPU 的执行和内存资源、目标 NIC 容量、其他流量也可能成为新的瓶颈。

![[图片/SVG/8_8_20_3.svg|900]]

图的上半部分比较“局部距离最短”与“先在 GPU 域中转”；下半部分强调共享出口。PXN 不能把一张网卡变成两张，也不会自动消除交换网络的过订阅。

## 5. GPU-NIC Affinity：至少同时检查五种亲和关系

### 5.1 Rank ↔ GPU：身份必须稳定

先确认每个 rank 对应的 GPU UUID 与 bus ID。不同节点的 `GPU0` 不是同一物理槽位名称的跨机保证；容器的可见 GPU 顺序也可能不同。出现“只有某个 rank 慢”时，必须能追溯到那一张物理 GPU 和它的 NIC 路径。

### 5.2 GPU ↔ NIC：距离和共享边

检查 GPU 到 NIC 是否经过相同 switch、host bridge、跨 NUMA 互联，及路径上的 PCIe negotiated speed / width。还要看多设备是否共享同一上联。一个很近的 NIC，如果同时被大量 GPU 占满，也未必是全局最优出口。

### 5.3 Proxy CPU ↔ GPU / NIC：数据直达仍有控制开销

[[8.19 NCCL 运行时：Communicator、Channel、Chunk、Protocol 与 Proxy|8.19]] 已说明传统 NET 进度需要 CPU 参与。CPU affinity 应考虑调度器给出的 cpuset、NUMA 距离、忙核竞争和后台线程。进程被绑核不等于其所有内存自动绑定，NUMA 分配还受到分配时机、内存策略和具体缓冲区实现影响。[^affinity]

### 5.4 NIC ↔ Fabric rail：节点局部最优不等于集群最优

在 rail-optimized 网络里，不同 NIC 可能连接不同交换域，跨 rail 的代价或可用带宽与同 rail 不同。只在每台机器上独立选择“最近的 NIC”，可能让逻辑 Ring / Tree 在节点之间反复跨 rail。应把两端 NIC 与交换机端口的映射一起保存。[^env][^pxn]

`NCCL_CROSS_NIC` 是约束跨节点算法使用 NIC 的一个入口，但正确值取决于网络是否 rail-optimized，不是“0 永远快、1 永远快”二选一口诀。不同物理 NIC 是否共享 PCIe 或 fabric 上联也必须核对。

### 5.5 业务 ↔ 通信资源：最后看整个作业

多个 communicator、训练通信、[[8.6 Checkpoint 同步异步分片|Checkpoint]] 和 [[8.16 PD 分离（Prefill-Decode Disaggregation）下的 KV Cache 网络传输架构|KV Cache 传输]] 可能共享相同出口。最佳单作业映射不保证最佳共载结果。若目标是端到端 step time 或推理尾延迟，应把通信微基准视为底层参照，而不是最终优化目标。

## 6. 用“路径上的割边”估算瓶颈，不把标称带宽相加

### 6.1 最简单的容量约束

把数据路径画成图。对资源边 $e$，令 $V_e$ 为本次工作实际经过该边的字节量，$B_e$ 为对应统计方向上的有效可用带宽，则至少有：

$$
T\ge\max_e\frac{V_e}{B_e}.
$$

这是容量下界，不含所有依赖、同步和执行成本。$V_e$ 还取决于实际算法、Channel、分层方式和中转路径：**不能把整个作业的输入字节数不加区分地代到每一条边上**。

如果多条 flow 共享一条 NIC 上联，总吞吐受这条共享边限制。两张 NIC 的标称速率可以相加，只是说明两个端口的名义总容量；若它们共享不足的 PCIe uplink、fabric 上联或 GPU 访问路径，端到端可用容量仍不能达到那个和。

### 6.2 四 GPU 共享一个 400 Gb/s 出口

【教学上界】假设四张 GPU 的对应跨机流量都经过同一 **400 Gb/s** 单向 NIC 出口，十进制单位下：

$$
400\ \mathrm{Gb/s}\div8=50\ \mathrm{GB/s}.
$$

这只是端口名义比特率换算，应用 payload 的有效带宽还要扣除各层开销。若理想公平分成四路，每路最多约 12.5 GB/s 的名义份额；它不是某次 NCCL 的实测带宽，更不是保证公平调度。

假设经过这个出口的总 payload 是 8 GB，则仅名义容量下界为 $8/50=0.16$ s。若计算出某条真实 PCIe 共享边的容量下界更高，应以更慢的约束为参照。这个方法比“有四张快 GPU，所以网络吞吐乘四”更可靠。

### 6.3 多 rail 的三问

端口数增加前，问：这些端口是否有独立的本地注入能力？fabric 是否允许并行且不在下一级重新汇入拥挤的共享上联？运行时是否真的分散了流量，而不是依然集中使用一个出口？三个问题缺一，就不能把多 rail 当成已获得的线性扩展。

## 7. 第一组命令：只读采集设备身份与拓扑

这些命令在 Linux 上运行，分别需要 NVIDIA driver 工具、`pciutils`、`numactl`、`rdma-core` / 相关用户工具；容器内可见性与权限不足时应记录限制。它们是采集命令，不修改设备配置。[^smi][^gpu-trouble][^net-trouble]

### 7.1 GPU 和 PCIe 视图

```bash
nvidia-smi --query-gpu=index,uuid,pci.bus_id --format=csv
nvidia-smi topo -m
nvidia-smi topo -mp
nvidia-smi nvlink -s
lspci -tv
numactl --hardware
```

第一条把逻辑卡号连到持久身份；随后分别采集 GPU 域、PCIe 域、NVLink 状态和 CPU / 内存 NUMA。`lspci -tv` 是结构概览，若怀疑某段 PCIe 降速或 lane width 异常，需要再对确切设备和其上游 bridge 查看详细能力与协商结果，而不是从树形缩进猜带宽。

### 7.2 RDMA 设备与 NUMA

```bash
ibv_devices
ibv_devinfo
rdma link show
rdma statistic
```

先从真实输出解析 HCA 名、端口、link layer 和状态，不预设每个机器都叫 `mlx5_0`。`NET/IB` 中的 IB 名称可以表示通用 verbs 路径，不能直接据此认定物理链路一定是 InfiniBand 而不是 RoCE。

确认 HCA 确实叫 `mlx5_0` 后，才运行下面的路径查询；名称不同就替换：

```bash
readlink -f /sys/class/infiniband/mlx5_0/device
cat /sys/class/infiniband/mlx5_0/device/numa_node
```

它们将 HCA 名连到 PCIe 设备和 NUMA 信息。`numa_node` 为 `-1` 时是系统未给出有效节点信息，不是“距离所有 CPU 都为零”。一份可用于复盘的映射表应包含：host、global rank、local rank、CUDA ordinal、GPU UUID、GPU bus ID、HCA / port、NIC bus ID、CPU set、NUMA / rail。

### 7.3 亲和检查不要只看父进程

记录作业真正生效的 CPU 限制，例如 `/proc/<pid>/status` 中的 `Cpus_allowed_list`；必要时逐线程检查 `/proc/<pid>/task/<tid>/status`。相关线程可能与父进程不同，容器 cpuset / cgroup 也会限制可调范围。CPU affinity 和 host buffer 的内存位置要分别核对。[^affinity]

## 8. 第二组命令：记录 NCCL 选路，而不是先强迫它选路

### 8.1 单机日志基线

在未保留旧强制算法 / 协议参数的测试环境中，先运行与机器匹配的最小测试。下面仍假设两张可见 GPU，且 `nccl-tests` 已编译：

```bash
mkdir -p logs
NCCL_DEBUG=INFO \
NCCL_DEBUG_SUBSYS=INIT,GRAPH,NET,COLL,TUNING,ENV \
NCCL_DEBUG_FILE="$PWD/logs/nccl.%h.%p.log" \
./build/all_reduce_perf -b 8 -e 256M -f 2 -g 2 -w 5 -n 20 -c 1
```

`%h` / `%p` 用主机名和 PID 分开日志，避免不同进程覆盖同一个文件；每次独立实验最好再使用不同目录。调试日志会产生开销，**用于定位的详细日志运行与用于最终成绩的低日志运行要区分**。[^logging][^tests]

不是所有 INFO 版本都会打印你想看的全部 per-operation 选择。若信息不足，应按该版本的日志 / profiler 能力深入，不能凭“没找到 GDR 字符串”直接断言已回退。

### 8.2 跨机 MPI 模板

以下模板面向常见 Open MPI 启动方式，假设 `node-a`、`node-b` 各分配四张 GPU、每节点四个进程、每进程一张卡，全部节点的二进制路径和运行库可访问。主机名、slot 与设备可见性必须替换并核对；调度集群应优先遵循其作业启动方式。[^tests][^mpi]

```bash
mpirun -np 8 -H node-a:4,node-b:4 \
  --map-by ppr:4:node --bind-to none \
  -x NCCL_DEBUG=INFO \
  -x NCCL_DEBUG_SUBSYS=INIT,GRAPH,NET \
  -x 'NCCL_DEBUG_FILE=/tmp/nccl.%h.%p.log' \
  ./build/all_reduce_perf -b 8 -e 256M -f 2 -g 1 -w 5 -n 20 -c 1
```

这里 `--bind-to none` 是为了避免一个未知默认绑定掩盖最初的可运行性检查，**不是生产亲和推荐**。完成基线后，应在分配给作业的 CPU 集合内进行有记录的绑定实验。日志分别落在各机器的 `/tmp`，需要汇集所有节点，不能只读发起端。

### 8.3 两类接口过滤器不要混用

| 变量 | 选择对象 | 精确匹配示例 | 不能保证 |
| --- | --- | --- | --- |
| `NCCL_SOCKET_IFNAME` | IP 网络接口 | `'=eth0'` | verbs payload 必然通过同名 HCA |
| `NCCL_IB_HCA` | RDMA HCA 和端口 | `'=mlx5_0:1,mlx5_1:1'` | 每个 rank 都固定绑定它最近的一块 NIC |

前导 `=` 表示精确匹配，避免 `mlx5_1` 同时匹配 `mlx5_10` 等前缀。这里仅展示稳定的 HCA / port 过滤形式，不引入更新版本才可能支持的其他语法。**过滤器缩小候选范围，不替代真实 GPU↔NIC↔rail 映射。**[^env]

### 8.4 按三个问题提取日志

先看网络实现是什么（内部 IB / Socket，还是具体插件）；再看 GPU 访问和注册是否可用、对应连接是否使用了期望路径；最后把 Channel / rank / device / HCA 信息连到系统拓扑。**“某种能力可用”与“这条边实际用了它”不能合并成同一句话。**[^logging]

`NCCL_TOPO_DUMP_FILE` 可用于记录 NCCL 发现的拓扑；多进程时要为各进程构造独立路径。不要把 `NCCL_DEBUG_FILE` 对 `%h/%p` 的展开规则擅自推广到所有其他文件变量。也不要把一台机器导出的拓扑 XML 硬塞给另一种机器，来“修复”不存在的物理连接。[^env]

## 9. GDR 可用性：四道门逐一检查

### 9.1 内存注册与驱动组合

NCCL 需要 GPU 内存与 NIC 访问之间的支持路径。传统方案常涉及 `nvidia-peermem`；符合条件的 kernel、GPU driver 和 NIC 栈也可使用 DMA-BUF。**`nvidia-peermem` 未加载，不足以单独证明所有平台都无法使用 GDR；同样，仅加载了模块也不能证明当前连接确实直接访问显存。**[^gpu-trouble]

若怀疑注册资源不足，需要区分 host pinned memory 限制、GPU 内存注册、映射资源和设备能力；不要把所有失败都归结为同一种 `memlock` 问题。保存具体错误、内存类型和申请规模，再对照平台文档。

### 9.2 PCIe P2P、IOMMU 与 ACS

这些机制关系到 DMA 地址翻译、隔离与路由。特别是 Linux 裸机上的 PCIe GPU P2P，当前 NVIDIA 指南对 IOMMU translated 模式有明确的支持 / 正确性限制；即便某个 P2P capability 显示可访问，也不能据此跳过系统模式检查。[^gpu-trouble]

安全的起点是只读确认启动参数、实际 IOMMU 模式、相关 bridge 的 ACS 状态、以及虚拟化方式，再按该平台支持矩阵由管理员处理。**不应在共享机器、虚拟机或生产节点上盲目套用遍历全部 bridge 的 `setpci` 写入脚本**：隔离要求与裸机性能配置不是同一个目标。对虚拟机尤其不能把“关闭 ACS”当成通用修复。

### 9.3 容器和 `/sys` 可见性

GPU 设备可见、CUDA 能运行，不代表 NIC、相关权限和真实 PCIe 拓扑全部暴露给进程。NCCL 依赖系统拓扑信息；虚拟拓扑、缺失挂载或设备隔离可能导致识别和选路与预期不同。先比较容器内外可见的设备身份与路径，再考虑调参。[^gpu-trouble]

### 9.4 用对照实验确认，而不是只查配置

如果 host-memory RDMA 测试正常、GPU-memory RDMA 明显异常，应优先缩小到注册、GPU-NIC 路径和可见性，而不是直接重写交换机配置。反过来，两种内存路径都差时，应继续查端口、fabric、拥塞和共享容量。低层测试通过也不能替代 NCCL 调用与计算依赖的正确性。[^net-trouble]

## 10. 排障阶梯：每次只增加一个复杂度

![[图片/SVG/8_8_20_4.svg|900]]

这张图的方向是“验证条件逐渐变复杂”，不是暗示前一层快就能证明后一层一定快。先拿到最窄的可复现条件，再决定应该去 GPU、主机、NIC 还是 fabric 查证。

| 阶段 | 最小实验 | 重点观察 | 它能排除的范围 |
| --- | --- | --- | --- |
| 0：语义与身份 | 对齐各 rank 的调用序号、count、dtype、GPU UUID | 全员是否按预期参与 | 避免把软件错配当链路故障 |
| 1：单机 GPU 对 | P2P 正确性、单对带宽 | pair 之间是否异常不均 | 局部 GPU / PCIe / NVLink 问题 |
| 2：两节点单卡 | 一个 GPU / NIC 路径参与网络 collective | host / GPU MR、实际端口、时延 | 最小跨机传输边界 |
| 3：单节点多卡 | 多 GPU 同时通信 | 本地共享链路与 GPU 域 | 节点内并行竞争 |
| 4：两节点多卡 | 增加每节点 rank 数 | 多 NIC 利用率、rail、Proxy 调度 | 注入带宽与全局映射 |
| 5：真实业务共载 | 保持通信参数，引入真实计算 / IO | step time、尾延迟、各资源计数器 | 微基准与业务差距 |

NVIDIA 的当前 GPU 排障建议使用 `simpleP2P` 验证相应 GPU peer 访问正确性，使用 `nvbandwidth` 测量 GPU 传输带宽。具体测试 case 要覆盖你关心的访问方式；“一个 sample 通过”不等于所有路径已验证。[^gpu-trouble][^nvbandwidth]

网络侧可用 `ib_write_bw` / `ib_write_lat` 等工具对比 host memory 与 GPU memory；GPU 和 DMA-BUF 参数取决于 **perftest 的构建能力**，先检查本机 `--help`，不要假定所有安装都支持同一组选项。RoCE 还需要把 NIC 与交换机侧 PFC、ECN、CNP、drop、队列占用变化按时间关联；只看一个累计非零计数没有足够归因能力。[^net-trouble]

## 11. 四组有限范围的 A/B：每个开关都必须回答一个问题

这些实验在隔离、可重启的测试作业中做；先保存自动基线，只改变一个目标因素，保留 correctness，并查看实际路径是否按预期改变。

| 对照 | 想验证的假设 | 解释限制 |
| --- | --- | --- |
| 自动 vs `NCCL_P2P_DISABLE=1` | 节点内 P2P 路径是否与问题有关？ | 回退会同时改变其他开销，变好只缩小范围，不等于已找到根因 |
| 自动 vs 禁止 GDR 的受控配置 | GPU↔NIC 直接路径是否关键？ | classic PCIe 与 C2C 平台的覆盖规则不同，要核对日志 |
| 自动 vs `NCCL_PXN_DISABLE=1` | 中转 GPU / 非局部 NIC 是否影响路径？ | 没有实际用 PXN 时，开关可能不改变结果 |
| 自动 vs 限定一块真实 HCA | 是否某个端口 / rail 异常，或存在共享注入瓶颈？ | 少一块卡也减少总容量，不能只比较单个带宽值 |

为避免 C2C 特例覆盖 `LOC` 阈值，在本文固定版本的传统路径上构造禁用 GDR 对照时，需要同时核对 `NCCL_NET_GDR_LEVEL=LOC` 与 `NCCL_NET_GDR_C2C=0`；**它们仍不是绕过插件行为核验的理由**。先证明实际传输改变，再解释成绩。禁止 GDR 不等于禁止 RDMA 网络，可能只是 NIC 改为访问 host buffer。[^env]

同理，`NCCL_IB_DISABLE=1` 主要排除内部 IB/verbs 路径，不能忽视外部 network plugin；需要明确使用 Socket 的对照时应核验 `NCCL_NET=Socket` 与实际日志，并先确认 IP 网络可达。不要让一个失败的 TCP 配置被误解成“RDMA 是唯一可用网络”。[^env]

**不要把本节的排障开关永久留在作业环境里。** 它们的价值是缩小问题空间，不是取代运行时的正常选择。

## 12. 症状到证据：避免过早归因

**单机很快，跨机很慢。** 候选包括错误 HCA / rail、host staging、GPU-NIC 路径、共享注入容量、fabric 拥塞和对端更晚进入 collective。先做两节点单卡，再增加每节点 GPU 数；不要第一步就认定 PFC 设置错误。

**两节点单卡很好，多卡跨机上不去。** 重点检查每 NIC 真实流量是否均衡、PCIe 上联是否共享、rail 是否一致、Proxy CPU 是否受限，以及多个 GPU 是否竞争同一个出口。多 rail 性能不能只用总端口数解释。

**平均带宽正常，但业务 P99 高。** 记录每次通信的时间分布、慢 rank 和同时间的资源状态。PFC pause、ECN mark 或 drop 的增量可能提供线索，但尾延迟也可能来自 CPU 抢占、计算就绪不齐或周期性 IO 共载。需要时间相关和对照，而不是单个计数器阈值。

**日志里有 `IB`，但怀疑没有 GDR。** 先区分网络实现和内存目标；`IB` 是 transport 证据，不是 GPU MR 使用证据。查看注册、连接信息，再以 host / GPU 路径与相关 A/B 交叉确认。

**设成“更远也允许 GDR”后崩溃。** 距离阈值不创造硬件支持和正确性保证，应恢复已验证配置，保存首发错误并核对平台限制；不是继续增加 timeout 就能把不支持路径变成正确路径。

## 13. 可交付的工程产出

完成本篇实验后，应该能提交一份有证据的复盘，而不是只给一张截图：**一张 rank↔GPU↔NIC↔rail 映射表，一张标出共享边的真实拓扑图，一套固定版本和消息口径的基线，一组只改一个目标因素的 A/B，以及说明哪些假设已被支持、哪些仍未排除的结论。**

若把这个能力接到 [[8.17 万卡集群分布式 Checkpoint 极致加速实践（MegaScale & DeepSeek 方案）|Checkpoint 数据路径]]，应进一步回答：存储流量和 collective 在哪条 PCIe 或 NIC 上交汇？哪些指标分别代表局部带宽、全局作业等待、持久化完成？只有把这些边界写清，才能讨论训练通信与存储共载的整体优化。

## 14. 自测

**问：GPU0 到 GPU1 是 `NV#`，所以 GPU0 用 GPU1 旁边的 NIC 一定慢吗？**  
不一定。PXN 可以利用快速 GPU 域接到更合适的 NIC；额外一跳与原路径、rail 和共享容量之间需要实际比较。

**问：经过 CPU host bridge 就是 CPU memcpy 吗？**  
不是。它可能是设备事务的路由路径；是否落 host DRAM、是否由 CPU 指令复制，还要看 transport 和 buffer 路径。

**问：两块 400 Gb/s NIC 就保证 100 GB/s 的业务带宽吗？**  
不保证。100 GB/s 只是两个端口的十进制名义速率之和，未考虑线缆 / 协议开销、本地注入、共享 PCIe、fabric 割边以及实际负载分配。

**问：`nvidia-peermem` 不在 `lsmod` 中，如何下结论？**  
不能直接下“无 GDR”结论。先确认是否走受支持的 DMA-BUF 路径，再核验当前连接和实验；模块存在同样不是启用证明。

**问：怎样证明某次调优真的修复了 GPU-NIC affinity？**  
需要同时看到实际 rank / GPU / NIC 关系或路径变化、对应瓶颈指标变化、可重复的性能改善，并保持正确性；仅设置环境变量并看到一次成绩上涨还不够。
