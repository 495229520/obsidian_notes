# 8.22 PyTorch Distributed：ProcessGroupNCCL、DDP、FSDP 与通信计算重叠

> [!abstract] 先抓住两条不同的流水线
> **DDP：梯度逐渐产生 → bucket 就绪 → 梯度 AllReduce → 本地 optimizer。**
> **FSDP：参数分片 → 按需 AllGather → 层计算 → 梯度 ReduceScatter → 分片 optimizer。**
> 两者都可以经过 ProcessGroupNCCL，但框架决定的通信内容、启动时间、内存生命周期完全不同。学习目标不是记住几个包装器，而是能从一段训练代码推导通信序列、等待点、显存峰值和 step 关键路径。

[[8.21 NCCL 异步执行与性能：CUDA Stream、Overlap、nccl-tests 与故障诊断]] 解释了底层提交与完成，本篇解释是谁、在什么时候提交这些 collective。CUDA 基础可回看 [[8.11 cudaMemcpy 与 CUDA Stream]]；跨机设备路径由 [[8.12 GPUDirect RDMA]] 衔接。

**版本口径。** 核对日期为 2026-09-11；本文使用显式 PyTorch 2.14 文档和当日可访问的 FSDP2 官方教程。FSDP2 示例使用 `torch.distributed.fsdp.fully_shard`，不会把 FSDP1 的参数直接搬到 FSDP2。代码经过静态语法检查，但当前制作环境没有 CUDA GPU，**未声称完成多 GPU 运行、吞吐测试或数值一致性验收**。图中时间和容量关系是模型示意，数值例题均标明假设。

## 1. 把 Python 调用拆成六层

![[图片/SVG/8_8_8_22_1.svg|900]]

| 层 | 职责 | 不负责什么 |
|---|---|---|
| Launcher / rendezvous | 启动进程，分配 rank 信息，让参与者找到彼此 | 不替代数据通信算法 |
| DDP / FSDP / autograd | 决定哪些张量、何时参与通信 | 不直接配置交换机队列 |
| `torch.distributed` / c10d | collective 接口、process group 与 backend 分发 | 不保证任何调用都同步到 CPU |
| `ProcessGroupNCCL` / Work | 把 CUDA 张量操作提交给 NCCL，管理相关 stream 依赖与工作状态 | 不等于 optimizer，也不替你分数据集 |
| NCCL / CUDA | communicator、设备侧通信与 stream 执行 | 不知道 loss 的业务含义 |
| GPU / NVLink / NIC / Fabric | 实际计算、内存与跨设备传输资源 | 不修复 rank 的错误调用顺序 |

这是功能分层，不是声称每一层都是一个独立线程。`ProcessGroupNCCL` 使用通信 stream 与当前计算 stream 之间的依赖来提交操作；具体内部对象和源码函数会随版本变化。设计理解以当前文档与对应版本源码为准。[^dist][^ddp-design]

### 1.1 Rank、local rank、world size

`rank` 是某个分布式组内的进程编号；`world_size` 是参与进程数；launcher 提供的 `LOCAL_RANK` 通常用于选择当前节点可见设备中的 GPU。一个节点可以有 local rank 0，另一个节点也可以有 local rank 0，它们的 global rank 不同。

本文采用**每进程一张 CUDA GPU**的常用模式。先 `torch.cuda.set_device(local_rank)`，再初始化/使用 NCCL backend；GPU ordinal 是进程可见设备列表中的编号，不一定等于宿主机的物理编号。用日志记录 global rank→host→local rank→GPU UUID，比只打印一个 `cuda:0` 更有用。[^dist]

Rendezvous 常使用 `MASTER_ADDR`、`MASTER_PORT`、`RANK`、`WORLD_SIZE` 等环境信息。这里的“master”地址帮助建组，**不意味着之后所有梯度都通过 rank0 的 CPU 中转**。

### 1.2 ProcessGroup 不是简单的一条网卡连接

组定义参与者与通信上下文。一个程序可以创建多个组；框架内部还可能按设备、操作和缓存策略维护底层资源。不要把一个 Python ProcessGroup 想成始终只有某个固定 QP，也不要推导“多建组必然多一倍网络带宽”。组创建和 collective 使用顺序还要在参与 rank 之间保持一致。[^dist]

## 2. `async_op=True`、`Work.wait()` 与跨 stream 使用

### 2.1 三个容易误读的接口

对 CUDA/NCCL，`dist.all_reduce(t, async_op=True)` 返回 Work。默认、未显式指定超时的 NCCL `Work.wait()`，核心作用是让**当前 CUDA stream**等待这项通信，而不是普遍保证 CPU 等到整个 GPU 操作结束。显式传入 timeout、开启 `TORCH_NCCL_BLOCKING_WAIT`、调用 NCCL barrier 等，可能有不同的 CPU 阻塞行为。CPU backend 的行为也不能照搬这个结论。[^dist][^torch-nccl-env]

| 操作 | 应该怎样理解 |
|---|---|
| `async_op=True` | 取得 Work，允许 host 继续安排工作；依赖还要正确建立 |
| `work.wait()` | 在当前 CUDA stream 上接入完成依赖；CPU 阻塞行为取决于 backend/配置/timeout |
| `work.is_completed()` / Future 状态 | 按对应 backend 和 API 的文档解释，不能泛化为任意 stream 的 buffer 安全证明 |
| `torch.cuda.synchronize()` | CPU 等待设备工作；适合明确的测量边界，不应随手塞满训练热路径 |

`async_op=False` 也不等于“CUDA 上一切都完成，CPU 现在可以任意读取显存”。普通同步形式会安排正确的当前 stream 使用语义，但跨 stream 消费仍要处理依赖。[^dist]

### 2.2 示例：在实际消费者所在 stream 上调用 wait

以下片段在进程组已经初始化、设备已选定之后运行。生产 `x` 和提交 all-reduce 均发生在当前 stream；consumer stream 先安排独立的 scratch 写入，再为 `x` 接入 Work 完成依赖。原地 all-reduce 尚未完成时，不从别处修改 `x`。

```python
import torch
import torch.distributed as dist

rank = dist.get_rank()
world = dist.get_world_size()
x = torch.full((1024,), float(rank + 1), device="cuda")
work = dist.all_reduce(x, op=dist.ReduceOp.SUM, async_op=True)
consumer = torch.cuda.Stream()

with torch.cuda.stream(consumer):
    scratch = torch.empty_like(x)
    scratch.fill_(3.0)            # 独立数据，可先提交
    work.wait()                 # 让 consumer 后续工作等待通信
    x.mul_(1.0 / world)
    x.record_stream(consumer)    # allocator 生命周期，不是同步原语
    done = torch.cuda.Event()
    done.record()

done.synchronize()              # 仅为本次正确性检查建立 CPU 完成边界
expected = torch.full_like(x, (world + 1) / 2.0)
torch.testing.assert_close(x, expected)
```

![[图片/SVG/8_8_8_22_2.svg|900]]

图里有两种完全不同的“等”：`work.wait()` 建立 consumer stream 的设备依赖，`done.synchronize()` 在检查处让 CPU 等待。**默认 stream 上调用了 wait，并不自动保护后来随便换的一条 stream。** 若要从已同步的原 stream 转到新 stream，另一种正确办法是在新 stream 上显式等待原 stream 的相关工作。[^dist]

### 2.3 `record_stream()` 为什么不能替代 wait

PyTorch caching allocator 需要知道一块 tensor storage 还被哪些 stream 使用，避免提前复用这块内存。`record_stream()` 解决这个生命周期问题；它并不会等待通信，也不会建立数据读写依赖。[^record-stream]

上一段故意保留 `x` 的 Python 引用直到完成，以便容易验证；`record_stream(consumer)` 进一步表达跨 stream 使用意图。在更复杂代码里，既需要执行依赖，也需要生命周期管理，不能二选一。`scratch` 在 consumer 中分配和使用，因此不需要额外把同一 stream 再登记一遍。

## 3. DDP：同步的是梯度，输入切分由你负责

DDP 的常规数据并行模式中，各 rank 保存完整模型副本，运行不同的数据分片。默认梯度同步后，各 rank 使用一致的优化算法与状态执行本地更新。DDP 不负责把输入 batch 自动切到不同 GPU；真实数据训练需要 sampler 或等价的数据分配逻辑。[^ddp-api]

### 3.1 一个 step 的顺序

`forward → loss → backward` 看似一个简单调用链，内部却可以逐步得到不同参数的梯度。DDP reducer 通过 autograd hooks 获知梯度 ready；一个 bucket 所需梯度齐备后，可以提交异步 AllReduce，让其与剩余 backward 计算重叠。最后必须保证同步结果对 optimizer 可用。[^ddp-design]

这不是“每个参数一算完立即单发一个网络包”，也不是“整个 backward 完成后才统一通信”。框架的 bucket 把梯度 ready 的细粒度事件与 NCCL 的 collective 粒度连接起来。

### 3.2 参数为何不会每 step 都完整广播一次

通常 DDP 构造时会进行必要的参数/状态同步；之后参数不靠每步重新广播来保持一致，而是依靠对应梯度的归约和相同的本地更新。Buffer 同步、用户额外 collective、特殊通信 hook 等另有行为，不能把“参数不每步广播”扩大为“DDP 每步除了 AllReduce 什么通信都没有”。[^ddp-api]

对于标准配置、相同 local batch 大小、loss 为 local mean 的情况，DDP 的平均梯度对应参与 rank 的平均。若各 rank 有效样本数不同，简单 rank 平均不一定等于全局样本平均；梯度累积、token mask 和 uneven input 都需要重新核对权重。

### 3.3 `DistributedSampler` 是数据语义的一部分

真实数据集通常按 rank/world size 分片，训练 epoch 变化时调用 sampler 的 `set_epoch(epoch)` 使 shuffle 按新的 epoch 一致推进。还要明确是否 padding、丢弃尾批次，以及所有 rank 是否拥有兼容的训练步数。数据切分错误可能造成重复训练，也可能导致某些 rank 先结束而其他 rank 仍等待 collective。[^ddp-api]

本篇后面的最小程序直接在 GPU 上创建 rank-specific 合成输入，**不包含 DataLoader，因此不能用于证明真实数据加载性能**。真实输入链路的空闲归因见 [[8.7 DataLoader 与 GPU 空闲归因]]。

## 4. DDP 的关键：bucket ready 不等于随意发包

![[图片/SVG/8_8_8_22_3.svg|900]]

### 4.1 为什么必须保持 bucket 序号顺序

不同 rank 的局部梯度就绪时间可以不同，但 collective 的对应关系不能不同。PyTorch 的 DDP 设计文档说明 reducer 按一致的 bucket 索引次序发起规约，而不是每个 rank 完全按自己看到的 ready 先后顺序任意发送。否则同一位置的 collective 可能对应不同梯度。[^ddp-design]

因此，“bucket2 本地已 ready，但还在等 bucket1”可能是正确性约束。排障时应识别是哪一个更早的 bucket 或 rank 延迟了顺序，不要直接把强制一致顺序当作 bug。

### 4.2 一个可手算的排队模型

为了理解暴露在 backward 尾部的通信，定义以下**简化模型**：所有 rank 使用相同 bucket 顺序；同一通信资源一次服务一个 bucket；忽略复杂流水线内部细节。

\[
r_i=\max_k r_{k,i},\quad
s_i=\max(r_i,f_{i-1}),\quad
f_i=s_i+c_i
\]

其中 \(r_{k,i}\) 是 rank \(k\) 的 bucket \(i\) 就绪时间，\(c_i\) 是该模型中的服务时间。若最后一段 backward 计算结束于 \(B\)，简化通信尾部为：

\[
T_{tail}=\max(0,f_{last}-B)
\]

这不是对 NCCL 每个 packet 的精确仿真；它强调**最晚到达者、前序排队和尾部暴露**。实际 collective 可以在 rank 全部到达前发生部分进展，并行争用也会改变 \(c_i\)。

构造例子：三个 bucket 的聚合 ready 时间是 `2、5、8 ms`，各需 `3 ms`，则完成时间为 `5、8、11 ms`。Backward 计算在 `8 ms` 结束时，尾部暴露 `3 ms`。如果改成到 `8 ms` 才发送的大 bucket，即使其总通信缩短到 `7 ms`，完成时间也要到 `15 ms`。单次 collective 更快，不代表 step 更快。

### 4.3 调 bucket：寻找当前模型的折中点

| 更小 bucket | 更大 bucket |
|---|---|
| 更早具备发送条件 | 固定提交/启动开销更容易摊薄 |
| 更多 collective，可能吃掉 CPU/GPU 调度预算 | 需等待更多参数梯度 ready |
| 小消息带宽利用率可能差 | 晚启动时更容易留下长通信尾部 |

`bucket_cap_mb` 是 DDP 层面的容量控制，文档以 MiB 说明。Bucket 实际布局还与参数顺序、dtype、初始迭代及 reducer 重建等实现行为有关，不要把设置值当成 trace 中每一个 collective 的精确大小。多跑稳定迭代后再分析。[^ddp-api][^ddp-design]

把调参结果同时写成 `bucket 设置 → collective 数/size → 第一次启动 → 通信尾部 → step 吞吐`，比只有一列 `algbw` 更能解释原因。

## 5. DDP 的几个工程开关，各自解决不同问题

`gradient_as_bucket_view=True` 让梯度成为 bucket storage 的 view，可减少梯度存储复制与内存需求；但 view 有别名约束，例如不能照搬对 `.grad` 调用 `detach_()` 的代码。它解决的不是“让网络带宽翻倍”。[^ddp-api]

`find_unused_parameters=True` 用于适合它的未使用参数场景，并引入相应的图遍历与管理开销。`static_graph=True` 需要训练图及使用/未使用参数集合等满足其契约。不要不检查模型就把它们当性能 preset。动态图、条件分支、重入 backward 或编译场景必须按具体版本核验。[^ddp-api]

### 5.1 梯度累积的 `no_sync()` 要覆盖 forward

假设 `ddp`、`optimizer`、`loss_fn` 已就绪，`micro_batches` 包含同样大小的 K 个微批次，各 rank 的 K 一致。以下替换普通训练 step，而不是叠加在每微批次都清零梯度的循环外。

```python
from contextlib import nullcontext

K = len(micro_batches)
assert K > 0
optimizer.zero_grad(set_to_none=True)
for i, (inputs, targets) in enumerate(micro_batches):
    context = ddp.no_sync() if i < K - 1 else nullcontext()
    with context:                      # forward 与 backward 都在里面
        outputs = ddp(inputs)
        loss = loss_fn(outputs, targets) / K
        loss.backward()
optimizer.step()
```

![[图片/SVG/8_8_8_22_6.svg|900]]

图下方展示前 K−1 个微批次只做本地梯度累积，最后一个同步微批次再把累积结果接入通信。只把 `backward()` 放在 `no_sync()` 内、forward 放在外面，不符合文档对这个上下文的要求。[^ddp-api]

除以 K 的前提是等权微批次、相同有效样本数以及对应的 loss reduction。若最后一个微批次较小，或者各样本 token 数不同，需要按真实有效样本/token 权重计算，而不是机械 `/K`。

### 5.2 自定义通信 hook 不是只改一个算子

DDP `register_comm_hook()` 需要返回符合契约的 `Future[Tensor]`，结果形状要与 bucket 对应。自定义 hook 中的 bucket 梯度没有被预先除以 world size；若目标仍是标准平均梯度，就要自己实现正确的平均语义。压缩与量化还需检查误差、残差状态、收敛和开销。[^ddp-api]

先用原生 DDP 建立正确性和性能基线，再实验 hook。不要同时改 bucket、AMP、压缩和 optimizer，然后把变化全部归因于网络。

## 6. FSDP：降低常驻状态，换取按需通信

### 6.1 FSDP1 与 FSDP2 不混用术语和参数

本文采用 FSDP2 主线；核对时的官方教程把 FSDP1 作为旧方案并给出迁移背景。旧项目仍可能使用 FSDP1，因此读源码时先确认版本和 API，而不是凭“FSDP”三个字猜行为。[^fsdp-tutorial]

| 项 | FSDP1（旧项目常见） | 本文 FSDP2 |
|---|---|---|
| 入口 | `FullyShardedDataParallel` 包装器 | `fully_shard(module, ...)` |
| 参数表示 | 扁平化参数相关设计 | 保留逐参数组织，以 DTensor 表示分片 |
| 分组方式 | 包装边界 / auto-wrap 策略等 | 按模块自底向上调用 `fully_shard` |
| 前向后处理 | ShardingStrategy 等配置 | `reshard_after_forward` |
| 混合精度 | 旧 `MixedPrecision` 配置 | `MixedPrecisionPolicy` / `mp_policy` |
| 累积期间关梯度同步 | `no_sync()` 相关接口 | `set_requires_gradient_sync(False)` |

表是迁移索引，不是声称每个旧参数都有一对一对应的新参数。FSDP2 的 group 是框架将参数组成 collective 的单位，也不是 DDP 的 gradient bucket。[^fsdp-api]

### 6.2 四种状态，看几何比背名词更容易

![[图片/SVG/8_8_8_22_4.svg|900]]

以四个 rank 为例，平时各自保存参数、梯度和 optimizer 状态的一个分片。某层计算前，把这层参数的各分片 AllGather 成当前 rank 所需的完整参数；计算后按策略释放临时完整表示；backward 得到完整梯度后通过 ReduceScatter 让各 rank 得到自己的已归约梯度分片。Optimizer 只更新本 rank 负责的分片。[^fsdp-api][^fsdp-tutorial]

**AllGather 不会把四个 rank 的输入 batch 合成一个 batch。** 它在这里聚合的是参数分片。**ReduceScatter 也不是“随便丢掉其他梯度”**，而是先完成匹配位置的规约，再按分片规则分配结果。

### 6.3 `reshard_after_forward` 决定是否需要 backward 再聚合

设为 `True`，前向后释放完整参数，backward 需要再次 AllGather；设为 `False`，保留完整参数以避免那次聚合，但占用更高显存。核对时 PyTorch 2.14 的默认 `None` 会对非根模块采用 True，对根模块采用 False。本文实验显式使用 True，避免把默认策略隐含在推导里。[^fsdp-api]

一次 `fully_shard(module)` 将该模块中尚未被子模块分组接管的参数组成通信组。因此应**先处理子模块，再处理根模块**。只对整个模型调用一次，可能留下很大的通信单元和很晚的重叠窗口；但过细分组又会产生大量小 collective。[^fsdp-api][^fsdp-tutorial]

## 7. FSDP 的内存账与通信账，要用不同的字节变量

### 7.1 总显存绝不是 DDP 的 1/N

定义：\(P\) 为未分片的常驻参数状态字节数，\(G\) 为梯度状态字节数，\(O\) 为 optimizer 状态字节数，\(A\) 为本 rank 激活，\(U_{live}\) 为同时存活的临时完整参数/相关临时工作空间。

对理想均匀分片，可用下面的**估算模型**理解容量：

\[
M_{FSDP}\approx\frac{P+G+O}{N}+A+U_{live}+M_{comm}+M_{other}
\]

这个模型故意单列激活、通信 buffer 和 allocator/运行时等其他开销。参数 padding、混合精度副本、共享参数、optimizer 具体实现都会改变各项；不要以 `P×某个固定倍数` 代替所有模型的真实内存清单。

构造例子：常驻状态为 48 GiB，8 rank 分片得到 6 GiB；每 rank 激活 10 GiB，当前/预取的临时完整参数 4 GiB，其他开销暂按 2 GiB 估计，总量约为 **22 GiB，而不是 6 GiB**。这些是帮助查账的假设，不是显存预测工具。

### 7.2 为什么 FSDP 可能更省显存，却传更多字节

把传输参数的完整字节量记作 \(W\)，传输梯度的完整字节量记作 \(R\)。两者可因通信 dtype 不同而不同。只考虑一个均衡分片组、点对点 ring 型字节模型、无额外重算或额外 collective 的情形，每 rank 的**发送量**近似为：

\[
V_{DDP}\approx2\frac{N-1}{N}R
\]
\[
V_{FSDP,true}\approx2\frac{N-1}{N}W+\frac{N-1}{N}R
\]

第二式对应两次参数 AllGather（forward/backward）和一次梯度 ReduceScatter。当 \(W=R\) 时，模型内的 FSDP 发送量约为 DDP 的 1.5 倍。若前向后保留参数，少一次 AllGather；根模块策略、混合精度、HSDP、activation checkpointing 和分组方式都会改变账目。这个推导结合了 FSDP 生命周期与 nccl-tests 的字节口径。[^fsdp-api][^tests-perf]

它不是实际 NIC counter 的预测，也不是说 FSDP 总会慢 50%。省出的显存可能支持更大的 local batch，通信也可能被计算覆盖；必须用相同工作负载下的容量、吞吐和收敛结果作比较。

### 7.3 Activation checkpointing 与 FSDP 是不同轴

Activation checkpointing 通过少保存中间激活、backward 重算来改变 \(A\) 与计算量；FSDP 改变参数/梯度/optimizer 分片和通信。两者结合后，额外执行的 forward 路径可能改变 hook 触发、参数聚合与 overlap，需要检查具体组合，而不是只把两种理论节省比例相乘。本文不提供未经验证的组合配置；先分别建立 baseline。

## 8. FSDP 的 overlap：预取下一组参数，不能凭空隐藏第一组

![[图片/SVG/8_8_8_22_5.svg|900]]

### 8.1 前向：AG(i+1) 与 Compute(i)

参数组 i 已 AllGather 后才能计算 i；计算 i 时，可以提前准备组 i+1。预取越及时，下一组计算前等待越少。第一组通常没有前一层计算来覆盖，因此仍有启动气泡；可以研究更早 unshard 的位置，但要检查输入准备、显存和 stream 依赖。[^fsdp-tutorial]

FSDP2 有框架的隐式预取，也提供按模块设置 forward/backward prefetch 的接口。CPU 能否及时运行到相应位置、模块边界是否合适、launch 是否成为瓶颈，决定图中的理想窗口能否出现。仅看到开关名中有 `prefetch`，不能保证有效重叠。

### 8.2 反向：参数聚合、梯度散发与剩余计算

Backward 的计算方向通常与 forward 相反。某组的计算需要参数就绪，产生梯度后可以启动 ReduceScatter，与其他组的 backward 计算重叠。此时参数 AllGather 和梯度 ReduceScatter 还可能争用通信资源。

一个容易画错的地方是：**不同 CUDA stream 不等于 AG 和 RS 在线路上天然并发。** 核对的 PyTorch 2.14 FSDP2 文档说明，默认 AG/RS 虽在不同 CUDA stream，仍可经过同一个 process group / NCCL communicator，因此通信会在该上下文中串行服务。文档新增的 `set_separate_reduce_scatter_group()` 是实验性接口，提供分离的组以争取通信间并发，要求相关 rank 一致调用，并且仍受网络能力约束。本文基线不启用它。[^fsdp-api]

图中的通信 lane 因而画成顺序服务，强调**通信与计算**的重叠，而不是默认画出未经证明的两种 collective 同时满速。

### 8.3 预取深度会变成显存峰值

若某时刻当前组和接下来两组的完整参数都保留在显存，\(U_{live}\) 就包含三组的相应状态。预取过深可能提升平均 GPU 活跃度，却触发 OOM 或挤压 batch 大小。

对于 forward 按顺序执行的 `model.blocks`，下列片段在所有 `fully_shard` 调用完成后、训练开始前设置一组前瞻预取。反向使用相反的模块顺序。它是替换/扩展实验配置，不必加到最小 baseline 上。[^fsdp-tutorial]

```python
blocks = list(model.blocks)
for current, following in zip(blocks, blocks[1:]):
    current.set_modules_to_forward_prefetch([following])

reverse_blocks = list(reversed(blocks))
for current, following in zip(reverse_blocks, reverse_blocks[1:]):
    current.set_modules_to_backward_prefetch([following])
```

![[图片/SVG/8_8_8_22_5.svg|900]]

配置代码本身没有设备等待，但图展示它改变的执行窗口与同时存活参数组。应用于有分支、共享模块、不同执行顺序的模型前，要重新定义真正的下一组，不能照搬这个线性列表。

### 8.4 混合精度与 offload 不免费

FSDP2 `MixedPrecisionPolicy` 可以分别选择参数计算/AllGather dtype 与梯度 reduction dtype，例如参数 BF16、梯度规约 FP32。这样 \(W\) 与 \(R\) 不再相等。CPU offload 还会把参数分片 H2D、梯度分片 D2H 及 CPU optimizer 工作加入路径，容量下降可能换来 PCIe 和主机瓶颈。[^fsdp-api]

这时应接回 [[8.10 Host Device Memory 与 Pinned Memory]] 的主机缓冲管理，但仍不能把 pinned memory 误认为所有 GPU collective 的统一前提。

## 9. 可组合实验：同一模型选择 DDP 或 FSDP2

下面 **9.1–9.6 的六个 Python 代码块顺序拼接为 `train_dist.py`**。不包含上面的独立片段，也不需要新增依赖于项目私有代码的模块。程序使用 CUDA、NCCL 和有 FSDP2 API 的 PyTorch；请先检查本机版本。这个程序面向机制验证：合成输入常驻 GPU、FP32、小型 MLP，无 DataLoader、AMP、编译、checkpoint 或真实语料。

同一运行内，每个 rank 使用相同初始化种子构建完整模型，然后才分片；数据种子使用 rank 偏移。FSDP2 不能被当作“自动把所有 rank 随机初始化修成同一模型”的工具。[^fsdp-tutorial]

### 9.1 定义模型：模块边界可被 FSDP 识别

每个 block 是一个 Linear/GELU 单元，适合展示自底向上分组。没有 dropout 和复杂分支，便于检查执行顺序与消除无关变量。

```python
import argparse
import json
import os
import time
from datetime import timedelta

import torch
import torch.distributed as dist
from torch import nn
from torch.nn.parallel import DistributedDataParallel as DDP

class ToyNet(nn.Module):
    def __init__(self, width: int, depth: int):
        super().__init__()
        self.blocks = nn.ModuleList([
            nn.Sequential(nn.Linear(width, width), nn.GELU())
            for _ in range(depth)
        ])
        self.head = nn.Linear(width, 8)

    def forward(self, x):
        for block in self.blocks:
            x = block(x)
        return self.head(x)
```

这段是模型定义而非训练，不单独产生跨 rank 时序。分组过小/过大是否合适仍需实际测量；本例的层宽和深度不是性能推荐值。

### 9.2 选择并行策略：optimizer 必须看到最终参数

FSDP2 先逐 block 分片，再让 root 管理剩余参数（这里包括 head），显式使用 `reshard_after_forward=True`。DDP 分支让 `bucket_cap_mb` 可实验。两条分支都返回模型，随后才构建 optimizer。[^fsdp-api][^ddp-api]

```python
def wrap_model(model, args, local_rank: int, world: int):
    if args.mode == "ddp":
        return DDP(model, device_ids=[local_rank],
                   bucket_cap_mb=args.bucket_mb,
                   gradient_as_bucket_view=True)
    from torch.distributed.device_mesh import init_device_mesh
    from torch.distributed.fsdp import fully_shard
    mesh = init_device_mesh("cuda", (world,))
    for block in model.blocks:
        fully_shard(block, mesh=mesh, reshard_after_forward=True)
    fully_shard(model, mesh=mesh, reshard_after_forward=True)
    return model


def train_step(model, optimizer, x, target):
    optimizer.zero_grad(set_to_none=True)
    output = model(x)
    loss = (output - target).square().mean()
    loss.backward()
    optimizer.step()
    return loss.detach()
```

本节末尾图 6 中，同一个 `loss.backward()` 会进入两条不同的通信生命周期。**不要在 `train_step()` 里额外手工 AllReduce 一遍模型梯度**，DDP/FSDP 已经负责各自的同步协议。`detach()` 返回日志用 tensor，不在热路径 `.item()`，避免逐步隐含 host 同步。

### 9.3 初始化与预热：消除首次分配的干扰

先验证 CUDA 与设备映射，初始化进程组后创建模型和输入。timeout 是这个小实验的失败退出预算，不是调快网络的参数。预热会初始化 optimizer 状态并让部分框架路径进入稳定状态；仍应观察 trace 判断预热是否足够。

```python
def run(args):
    if not torch.cuda.is_available():
        raise RuntimeError("This experiment requires CUDA GPUs and NCCL.")
    local_rank = int(os.environ["LOCAL_RANK"])
    if not 0 <= local_rank < torch.cuda.device_count():
        raise RuntimeError("LOCAL_RANK exceeds visible CUDA device count.")
    torch.cuda.set_device(local_rank)
    device = torch.device("cuda", local_rank)
    dist.init_process_group("nccl", timeout=timedelta(minutes=5))
    rank, world = dist.get_rank(), dist.get_world_size()
    torch.manual_seed(1234)
    model = ToyNet(args.width, args.depth).to(device)
    model = wrap_model(model, args, local_rank, world)
    optimizer = torch.optim.AdamW(model.parameters(), lr=1e-3)
    torch.manual_seed(9000 + rank)
    x = torch.randn(args.batch, args.width, device=device)
    target = torch.randn(args.batch, 8, device=device)
    for _ in range(args.warmup):
        train_step(model, optimizer, x, target)
    dist.barrier()
    torch.cuda.synchronize()
    torch.cuda.reset_peak_memory_stats()
```

这一段末尾的 barrier 和设备同步是**测量窗口之前的边界**，不是每个训练 step 都要插入的操作。初始化时会让每张 GPU 临时装入完整模型，所以这个示例不能用于本来就无法完整放入单卡的超大模型；那需要另外设计 meta 初始化、分片加载和 checkpoint 恢复路径。

### 9.4 计时与跨 rank 汇总：不漏掉在飞 GPU 工作

下面代码仍属于 `run()` 函数，保留四空格缩进。连续执行多个 step 后才同步设备；使用各 rank 窗口耗时的最大值计算总样本吞吐，不把 rank0 自己的提交耗时当全局成绩。

```python
    start = time.perf_counter()
    for _ in range(args.steps):
        last_loss = train_step(model, optimizer, x, target)
    torch.cuda.synchronize()
    elapsed = time.perf_counter() - start
    peak_gib = torch.cuda.max_memory_allocated() / (1024 ** 3)
    stats = torch.tensor([elapsed, peak_gib], dtype=torch.float64,
                         device=device)
    dist.all_reduce(stats, op=dist.ReduceOp.MAX)
    worst_seconds, worst_peak_gib = stats.tolist()
    mean_loss = last_loss.clone()
    dist.all_reduce(mean_loss, op=dist.ReduceOp.SUM)
    mean_loss.div_(world)
    if rank == 0:
        print(json.dumps({
            "mode": args.mode, "world_size": world,
            "global_batch": args.batch * world,
            "window_seconds_max_rank": worst_seconds,
            "mean_step_ms": worst_seconds * 1000 / args.steps,
            "samples_per_s": args.steps * args.batch * world / worst_seconds,
            "peak_allocated_gib_max_rank": worst_peak_gib,
            "last_loss_rank_mean": mean_loss.item(),
            "torch": torch.__version__, "cuda_build": torch.version.cuda,
            "nccl": str(torch.cuda.nccl.version()),
        }, ensure_ascii=False))
```

汇总统计的 AllReduce 发生在计时窗口之后，不计入训练 step 吞吐。`stats.tolist()` 在这里完成 host 取值，不能挪进每一步热循环。`max_memory_allocated()` 是 PyTorch allocator 的已分配峰值，不等于整张 GPU 的全部显存使用；还应记录 reserved、设备总使用及 NCCL 等非 allocator 可见开销，诊断时不要只看一个数。

输出中的 `mean_step_ms` 是**多 step 窗口的均值口径**，不是每步 P50/P99；多个 rank 的峰值也可能出现在不同瞬间。保留字段名中的范围，避免后续报告误用。

### 9.5 参数校验：让实验设置显式可记录

默认规模只为便于启动。以 `--mode` 切换 DDP/FSDP2，所有进程通过同一 launcher 接收一致参数；`bucket-mb` 只影响 DDP，FSDP2 的分组通过模块边界控制。

```python
def parse_args():
    parser = argparse.ArgumentParser()
    parser.add_argument("--mode", choices=["ddp", "fsdp2"], required=True)
    parser.add_argument("--width", type=int, default=1024)
    parser.add_argument("--depth", type=int, default=8)
    parser.add_argument("--batch", type=int, default=64)
    parser.add_argument("--steps", type=int, default=30)
    parser.add_argument("--warmup", type=int, default=5)
    parser.add_argument("--bucket-mb", type=float, default=25.0)
    args = parser.parse_args()
    for name in ("width", "depth", "batch", "steps", "warmup", "bucket_mb"):
        if getattr(args, name) <= 0:
            parser.error(f"{name} must be positive")
    return args
```

这里要求 warmup 至少一次，以便这个教学程序不把 optimizer 状态首次分配留到计时段；正式实验仍须增加重复次数并验证稳定性。

### 9.6 入口与退出：正常收尾，不宣称自动容错

在正常路径中销毁进程组。某个 rank 发生 fatal 错误时，其他进程是否退出由 launcher、超时及作业管理策略共同决定；`finally` 不构成分布式事务回滚，也不让损坏的训练状态自动恢复。[^dist]

```python
if __name__ == "__main__":
    args = parse_args()
    try:
        run(args)
    finally:
        if dist.is_initialized():
            dist.destroy_process_group()
```

![[图片/SVG/8_8_8_22_6.svg|900]]

图中的最后一步是所有 rank 的资源收尾，不是仅 rank0 打印后就可以安全忽略其他进程。

### 9.7 启动方式与结果边界

单节点两 GPU 时分别运行以下命令，不要同时争抢同两张卡。两次实验使用相同模型、相同 local/global batch、相同精度和步数，输出保存为不同文件；根据显存容量调整规模。[^dist]

```bash
torchrun --standalone --nproc_per_node=2 train_dist.py \
    --mode ddp --bucket-mb 25 --steps 50

torchrun --standalone --nproc_per_node=2 train_dist.py \
    --mode fsdp2 --steps 50
```

该程序没有验证 DDP/FSDP 的逐参数数值一致性，只验证了能构造训练、运行并测量的路径。正式正确性验收应固定种子和有效全局 batch，采用小模型与单进程参考计算比对 loss、梯度及若干更新后的参数，使用恰当容差，并明确并行规约的浮点差异。FSDP 参数比对/保存需使用匹配版本的聚合或 distributed checkpoint 方式，**不能拿一个 rank 的 shard 与完整参数逐元素比较**。

## 10. 性能观测：从训练函数到真正的通信尾部

### 10.1 先看整体，再看组成

一次实验至少记录稳定窗口吞吐、有效 global batch、精度、模型规模、分组/预取配置、allocator 与设备显存峰值。需要 tail latency 时另做逐 step 配对采样，而不是从窗口平均倒推出 P99。

接着读 trace：DDP 关注 bucket ready 和 AllReduce 启动是否被 backward 覆盖；FSDP 关注每组参数是否提前就绪、首个 AG 的等待、反向 AG/RS 排队和同时存活的完整参数组。最底层 collective 慢时，再接入 [[8.21 NCCL 异步执行与性能：CUDA Stream、Overlap、nccl-tests 与故障诊断]] 的 nccl-tests、NCCL 日志与 fabric 证据。

### 10.2 一个短窗口 profiler 片段

这段在模型与输入已经初始化且预热之后，**单独作为诊断实验**运行，不与上一节的无 profiler 计时混为一个成绩。每 rank 导出独立 trace 文件，避免覆盖。`record_shapes`、memory profile、stack 等更重配置按需要逐步开启。[^profiler]

```python
from torch.profiler import profile, ProfilerActivity, record_function

with profile(activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
             record_shapes=False, profile_memory=False,
             with_stack=False) as prof:
    for _ in range(5):
        with record_function("train_step"):
            train_step(model, optimizer, x, target)
        prof.step()
    torch.cuda.synchronize()
prof.export_chrome_trace(f"trace-rank{dist.get_rank()}.json")
```

![[图片/SVG/8_8_8_22_6.svg|900]]

图中的 compute/collective 时间段是你需要在 trace 中对应的对象。不要把 CPU 上 `loss.backward()` 的返回长度当成全部 GPU backward+communication 时间；也不要把所有 NCCL kernel 时长相加就当作“通信导致的 step 延迟”，因为它们可能与计算重叠。

### 10.3 六种现象的排查方向

| 现象 | 优先假设 | 对照实验 |
|---|---|---|
| nccl-tests 正常，DDP 尾部很长 | bucket 就绪/启动晚，或 rank 计算偏斜 | bucket 大小、ready 时间与 rank trace |
| FSDP 每层计算前都有空白 | AG 未及时预取，分组或 CPU launch 问题 | 模块边界、单步预取、CPU 时间线 |
| 开预取后更快但 OOM | 同时存活的完整参数组增多 | 预取深度与 live group/显存对账 |
| GPU 利用率高但 samples/s 下降 | 计算/通信争用或额外工作增加 | 独立与联合测量，固定有效工作量 |
| 少数 rank 先出现 Python/OOM 错误 | collective timeout 是连带后果 | 找同一 step 最早错误，而非最大 timeout |
| 单机正常，跨机才退化 | NIC 亲和、路径回退、fabric 或 rank 分配 | NCCL NET/GRAPH 日志与网络 baseline |

这是调查路径，不是根据一项指标自动分类根因的规则。尤其 `GPU utilization` 不能直接替代有效训练吞吐。

## 11. ProcessGroupNCCL 故障诊断：把证据绑定到同一个 collective

### 11.1 Flight recorder 类记录要显式启用容量

核对版本提供了一组 `TORCH_NCCL_*` 环境变量。以下为短诊断窗口示例，不是长期性能配置；在所有相关进程启动前设置，并保证日志/转储路径不会被覆盖。[^torch-nccl-env]

```bash
export NCCL_DEBUG=INFO
export NCCL_DEBUG_FILE=/tmp/nccl.%h.%p.log
export TORCH_DISTRIBUTED_DEBUG=DETAIL
export TORCH_NCCL_TRACE_BUFFER_SIZE=20000
export TORCH_NCCL_DUMP_ON_TIMEOUT=1
export TORCH_NCCL_DESYNC_DEBUG=1
```

`TORCH_NCCL_DUMP_ON_TIMEOUT` 需要非零 `TORCH_NCCL_TRACE_BUFFER_SIZE` 才有相应记录可转储；buffer 大小描述记录容量，不是网络 buffer 字节数。详细一致性检查和 trace 会增加开销，记录后关掉再测 baseline。[^torch-nccl-env][^dist]

可选的 timing、CPP stack、monitoring 与 heartbeat 相关变量也有各自开销及版本语义。不要把 `TORCH_NCCL_ASYNC_ERROR_HANDLING` 的整数值当作所有版本一致的布尔开关，更不要随意关闭错误处理只求任务“不退出”。

### 11.2 找的是“第一个不一致”，不是“最后一个等待者”

收集每 rank 的 step、collective sequence、op、dtype、numel、process group 标识和最早异常。若 rank3 在 backward 前 OOM，其他 rank 等待 rank3 进入 AllReduce，最后表现成 watchdog timeout；增加 timeout 无法补回缺失的梯度。

如果 type/count/order 不匹配，先修程序协议。若同一 collective 全部匹配且及时进入，再沿 CUDA stream、GPU 设备、NCCL 路径、NIC 和 fabric 排查。序号在不同 process group 内可能有各自语境，不能不分组混排日志。[^dist][^ddp-design][^torch-nccl-env]

### 11.3 Uneven input、额外 collective 与 checkpoint

DDP 的 join 机制可以帮助处理特定的 uneven input 场景，但不能推导为“任意代码里的额外 collective 都会被自动匹配”。例如训练中显式加的统计 AllReduce、其他模块的通信，都要遵守参与集合和次数的契约；按当前 join 文档选择一致的退出行为。[^ddp-api]

FSDP 的 checkpoint 是分片状态的一致保存问题，不是只让 rank0 随手保存它手里的本地 shard。保存、加载、重新分片与 world size 改变应使用匹配版本的 distributed checkpoint/state-dict 流程，并验证 optimizer 状态和恢复后的更新。持久化语义接 [[8.6 Checkpoint 同步异步分片]]，实际大规模路径接 [[8.17 万卡集群分布式 Checkpoint 极致加速实践（MegaScale & DeepSeek 方案）]]。[^fsdp-tutorial]

## 12. 选择与实验矩阵：不要为了省显存而忽略吞吐

| 决策问题 | 起步方向 | 必须同时测什么 |
|---|---|---|
| 完整模型状态能装入每 rank，想先建立通信基线 | 先做 DDP baseline | 数值、全局 batch、通信尾部与吞吐 |
| 参数/梯度/optimizer 状态挤占容量 | 对照 FSDP2 | 分片状态、临时完整参数、激活及总峰值 |
| 激活才是主因 | 另做 activation checkpointing 等实验 | 重算开销、组合后的参数聚合次数 |
| FSDP 有大量 AG 等待 | 调模块分组与预取 | waiting gap、live groups、显存峰值 |
| 跨节点才出问题 | 回到底层 NCCL 与 fabric | 基线、路径、rank 亲和和端口证据 |

上表是本文建议的实验顺序，不是岗位或所有模型的固定配方。每个配置至少有一次正确性验证、稳定窗口测量、短 trace 和相同条件的复测。

DDP 可扫描若干 bucket 容量；FSDP2 扫描根级/块级/小组级模块边界、`reshard_after_forward` 与预取深度。比较时先固定 world size、有效 global batch、精度、输入和 optimizer，再单独研究 FSDP 省出的内存允许增加 batch 后的收益。**这两类比较要分开报告**，不把工作量变化伪装成纯系统加速。

## 13. 自测与工程验收

**问题一：把 `all_reduce(..., async_op=True)` 改成异步以后训练一定更快吗？**

不一定。依赖可能使消费仍需立即等待；调用者可能没安排独立计算；GPU/网络资源可能竞争；或者慢 rank 根本没及时进入同一 collective。先明确等待位置，再比较完整窗口。

**问题二：DDP 的 bucket ready 顺序不同，为什么不能各 rank 谁先好就先发？**

collective 序列必须对应相同逻辑数据。DDP 按一致 bucket 索引顺序启动，局部 ready 只是条件之一；随意发会破坏匹配关系。

**问题三：FSDP 把状态分成八份，显存为何没有变成八分之一？**

激活通常仍由本 rank 承担，当前与预取组的完整参数临时同时存在，还有通信 workspace 和 allocator/设备开销。分片的是特定状态，而不是整张卡上所有对象。

**问题四：`fully_shard(root)` 和先逐 block 分片再处理 root 有什么不同？**

每次调用定义尚未分组参数的通信单元。只处理 root 往往形成大单元；逐 block 分组能提供更细的聚合/释放时机和潜在 overlap，但增加 collective 数量。选择应由 trace 与显存峰值验证。

**问题五：为何 FSDP forward 后释放参数，会增加 backward 通信？**

反向计算需要对应参数。完整表示释放以后，只剩 local shard，就要再次聚合；保留完整表示可以省这次通信，却延长显存生命周期。

**问题六：一条 AG stream、一条 RS stream，就能保证两种通信同时在线路上进行吗？**

不能。核对版本的默认 FSDP2 配置可能经过同一 NCCL communicator，通信之间仍串行。分离 process group 是额外、版本相关的实验，并且并发仍受网络与依赖约束。

**问题七：为什么示例先 `fully_shard`，后创建 optimizer？**

optimizer 应引用完成分片转换后的参数表示及相应本地状态，而不是在转换前固定另一组参数对象。按照官方初始化顺序建立清晰的所有权与状态边界。

> [!success] 验收标准
> 能从训练代码画出 DDP 的 bucket 时间线和 FSDP 的参数生命周期；能解释 Work.wait 的等待主体；能给出对齐全局 batch 的 DDP/FSDP2 实验、正确性比较与显存账；能把 timeout 追溯到最早出错的 rank/step，而不是直接调大超时。GPU 不可用时，先完成代码与模型推导，将运行栏明确标为未验证。
