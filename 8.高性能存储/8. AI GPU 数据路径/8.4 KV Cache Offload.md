# KV Cache Offload

> 前几篇解决「训练数据怎么喂进 GPU」;本篇换到推理侧,主角是一种奇特的数据:**KV Cache——GPU 自己算出来、还要反复用、大到显存装不下的中间状态**。贯穿负载定下:一个 70B 级 LLM 聊天服务,支持 32k 上下文,用户多轮对话、共享长 system prompt。算一笔账就会发现它是存储问题:每 token 的 KV 是几百 KiB,一条 32k 会话约 10 GiB——几个并发会话就吃穿 HBM。Offload 的思路对存储工程师毫不陌生:**给 GPU 造一套 page cache**——HBM 之下垫主机内存、再垫 NVMe,按块管理、按需换入换出。第 1 章的缓存层次、第 8 章的搬运账在这里合流;而所有决策都归结为一道不等式:**取回时间 < 重算时间,offload 才有意义**。本篇把这道不等式的每一项拆开算。

前置：[[8.1 GPU 内存层次与数据搬运]]（HBM/PCIe/DRAM/NVMe 的带宽阶梯——决策不等式的分母来源）、[[1.2 Page Cache 命中与未命中]]（缓存层次思想的原型）、[[8.3 Bounce Buffer vs 直读]]（KV 正是「GPU 直接消费的字节」——直读的典型客户）。

## 1. KV Cache 是什么,为什么这么大

Transformer 自回归推理分两相【事实】：

- **prefill（预填充）**：把整段 prompt 一次算完,产出两样东西——第一个输出 token,以及**每层每个 token 的 K/V 向量**（后续注意力要反复查询的「上下文记忆」）。计算密集,延迟即 **TTFT**（time to first token）;
- **decode（解码）**：逐 token 生成,每步都要读**全部历史 KV**。访存密集,每步延迟即 **TBT**（time between tokens）。

KV 不能丢的原因【事实】：没有它,每生成一个 token 都要把整段上下文重算一遍——KV Cache 是「用显存换算力」的经典空间换时间。它的体积公式：

$$
Bytes_{token} = 2 \times L \times H_{kv} \times D_{head} \times B_{dtype}
$$

代入贯穿负载（70B 级、80 层、GQA 8 组 KV 头、head_dim 128、FP16）【量级】：

$$
2 \times 80 \times 8 \times 128 \times 2 = 320\ KiB/token
$$

即 **~320 KiB/token,32k 上下文一条会话 ~10 GiB**。一张 80 GB 的卡,模型权重占去大半,剩余 HBM 只够同时挂几条长会话——**并发数被 KV 容量卡死,而不是被算力卡死**【事实】。这就是 offload 的第一动机:把「显存容量」从并发瓶颈里摘出去。

第二动机更划算【事实】：多轮对话与共享 system prompt 让**不同请求的前缀 KV 完全相同**（相同 token 序列 → 相同 KV,确定性计算）——前缀缓存（prefix caching）命中一次,就省掉一整段 prefill 的算力。缓存的价值从「本会话续命」升级为「跨请求复用」,这正是 [[8.5 LMCache 与 Mooncake]] 把它做成集群资源的出发点。

## 2. 分层与调度:给 GPU 造 page cache

![KV Cache 分层 offload 全景:左侧为体积账——每 token 320 KiB、32k 会话 10 GiB、HBM 只够几条并发,与分层金字塔 HBM 数 TB/s、主机 DRAM 经 PCIe 约 25 GB/s、本地 NVMe 几 GB/s、远端集群池 25 GB/s 量级,逐层容量变大带宽变小;右侧为决策不等式——取回时间等于体积除以层带宽,重算时间随上下文长度超线性增长,32k 时重算秒级而 DRAM 取回亚秒级,结论是越长的上下文越值得缓存;底部为 paged 块管理与流水线预取——按 block 切块、LRU 逐层下沉、命中时边取边算逐层流水掩盖传输](../../图片/SVG/kvcache-分层offload决策.svg)

层次表(贯穿负载口径)【量级】:

| 层 | 带宽(到 HBM) | 容量 | 取回 10 GiB 耗时 |
| --- | --- | --- | --- |
| HBM 本层 | 数 TB/s | 几十 GB(与权重争) | ~0(命中即用) |
| 主机 DRAM(经 PCIe Gen4 x16) | ~25 GB/s([[8.1 GPU 内存层次与数据搬运]] 健康值) | 数百 GB~TB | **~0.4 s** |
| 本地 NVMe | 几 GB/s(单盘)~几十(阵列) | 几十 TB | ~1.5 s(7 GB/s) |
| 远端池(RDMA 200 Gb/s) | ~25 GB/s | 集群级 | ~0.4 s + 往返开销([[8.5 LMCache 与 Mooncake]]) |

对面的分子——**重算成本**【事实/量级】:prefill 的计算量随上下文长度**超线性**增长(线性的 FFN + 平方的注意力),70B 级模型 32k 上下文的 prefill 在旗舰卡上是**秒级到十秒级**。于是决策不等式两边都摆上了数:

$$
T_{fetch} = \frac{Bytes_{KV}}{BW_{tier}} \quad vs \quad T_{recompute}(n) \sim O(n^{1.x})
$$

三条结构性结论直接掉出来【事实】:

1. **上下文越长,offload 越划算**:取回时间随体积线性涨,重算时间超线性涨——32k 时 DRAM 取回(0.4 s)对重算(秒~十秒级)是 5~20 倍的赢面;短 prompt(几百 token)则重算反而快,不值得占缓存;
2. **层的选择就是不等式里代哪个分母**:DRAM 层几乎总赢;NVMe 层对长上下文仍赢,对中短上下文开始输——**每层有自己的盈亏平衡上下文长度**,这就是分层水位线的定法;
3. TTFT 的构成变了【事实】:命中时 TTFT = 取回 + 增量 prefill(新增部分),未命中 = 全量 prefill——**缓存命中率直接改写 TTFT 分布**:p50 由命中路径决定,p99 由未命中和取回慢尾决定。吞吐-延迟-容量在此闭环:offload 释放 HBM → 并发(batch)↑ → 吞吐↑;但取回流量占用 PCIe → 与权重加载/激活搬运争带宽 → TBT 可能变差——**收益在容量维,代价在带宽维**【取舍】。

工程形态与 OS 教科书逐条对得上【事实】:按块管理(paged attention 的 block,典型十几 token 一块【实现】——解决变长会话的显存碎片,机制即分页);LRU/LFU 逐层下沉(eviction);**流水线取回**(边取边算:第 N 层注意力计算时预取第 N+1 层的 KV——传输被计算掩盖,同 [[8.3 Bounce Buffer vs 直读]] §4 的重叠思想);pinned 中转池([[8.1 GPU 内存层次与数据搬运]] 军规)。**KV offload 引擎 = 一个为张量定制的多级 page cache**,第 1 章白学不了一点。

## 3. 全路径对账:一次「前缀命中在 DRAM」的请求

贯穿负载里最常见的路径——多轮对话第 N 轮,前 24k token 的 KV 在主机 DRAM,新输入 500 token:

| 步骤 | 发生什么 | 层级 | 等待点 | 拷贝 |
| --- | --- | --- | --- | --- |
| ① 调度器查索引 | 按前缀 token 序列哈希查块索引,命中 24k(1500 块) | CPU | 微秒级(内存哈希) | 无 |
| ② HBM 腾位 | 需要 7.5 GiB 空闲:可能触发别的会话 KV 下沉(evict) | HBM/PCIe | **W1:evict 与 fetch 争 PCIe——写下沉与读取回同管道** | D2H 一次 DMA |
| ③ 流水线取回 | 1500 块按层序 DMA 上卡,与 ④ 重叠 | PCIe | **W2:~0.3 s 传输,被 ④ 部分掩盖** | H2D:pinned 池 → HBM,每块 1 次 DMA |
| ④ 增量 prefill | 只算新 500 token(对着逐层就位的历史 KV) | GPU | W3:百 ms 级计算 | 无 |
| ⑤ 首 token 出 | TTFT = max(W2 尾段, W4) + 采样 | — | — | — |
| ⑥ decode 逐 token | 每步读全部 24.5k KV(已全在 HBM) | HBM | TBT 由 HBM 带宽决定 | 无 |

对照未命中路径:全量 prefill 24.5k ≈ 秒级到十秒级——**命中把 TTFT 砍掉一个量级,代价是 W1/W2 的 PCIe 流量**【事实】。尾延迟的形状也定了【实践】:p99 的三大来源是「未命中的长 prompt」「evict 风暴期的 W1」「NVMe 层慢取回」——排障先把 TTFT 按命中层分桶,再看每桶的分布。

## 4. Modern C++:决策不等式与分层索引的骨架

把 §2 的决策写成代码——这正是 offload 引擎调度器的核心判断:

```cpp
#include <chrono>
#include <cstdint>
#include <optional>

using Sec = std::chrono::duration<double>;

struct Tier {                      // 一层缓存:DRAM / NVMe / 远端池
    double fetch_gbps;             // 到 HBM 的有效带宽(实测值,勿用理论值,8.1 §5)
    Sec    base_latency;           // 首字节前的固定开销(NVMe/网络往返)
};

struct KvSegment {                 // 一段可复用的前缀 KV
    std::uint64_t bytes;           // = tokens × 320 KiB(贯穿负载口径)
    std::uint32_t tokens;
};

// 重算成本模型:随长度超线性(系数由本机型实测标定,不硬编码论文数字)
Sec recompute_cost(std::uint32_t tokens);

// 决策不等式:取回赢过重算才值得从该层取;否则宁可重算并考虑逐出该段
std::optional<Sec> worth_fetching(const KvSegment& seg, const Tier& tier) {
    const Sec fetch = tier.base_latency +
                      Sec{static_cast<double>(seg.bytes) / (tier.fetch_gbps * 1e9)};
    if (fetch < recompute_cost(seg.tokens)) return fetch;   // 返回预计 TTFT 贡献
    return std::nullopt;                                    // 该层已无收益:短段/慢层
}
```

读码要点【事实/实践】:

1. `base_latency` 是 NVMe/远端层输给 DRAM 层的主因——小段(短前缀)被固定开销吃掉,所以**每层的盈亏平衡点是「段长」的函数**,不是常数;
2. 两个成本模型都要**实测标定**:带宽用 8.1 §5 的口径,重算曲线跑几个长度点拟合——照抄别人硬件的系数,不等式两边都是错的;
3. 真实引擎在此之上叠调度:命中的段流水线取回(§3 的 W2/W4 重叠)、未过线的段按 LRU 下沉——骨架不变,都是这道不等式的批量版。

## 5. 排障清单:症状 → 判定 → 处置

| 症状 | 先看什么 | 典型根因 | 处置方向 |
| --- | --- | --- | --- |
| TTFT p99 远差于 p50 | TTFT 按「命中层」分桶的分布 | 未命中长 prompt + NVMe 层慢取回混在尾部 | 提高 DRAM 层容量/命中率;长前缀预取;短段别下沉 NVMe |
| 开 offload 后 TBT 变差 | PCIe 利用率;evict/fetch 流量时间线 | 取回流量与 decode 的权重/激活搬运争 PCIe(§2 结论 3) | 取回限速/错峰;evict 批量化;拓扑上取回走独立路径 |
| 命中率高但 TTFT 没降 | W2 是否被 W4 掩盖:流水线取回生效否 | 整段取完才开始算(无重叠) | 开启逐层流水预取;块粒度过大导致头部等待 |
| HBM 明明有空,并发仍上不去 | 块碎片;evict 水位线配置 | 块管理碎片或水位线过保守 | 调 block 大小;检查逐出策略触发阈值 |
| 短请求变慢 | 短前缀是否也走了缓存索引/下层取回 | 固定开销吃掉小段收益(§4 要点 1) | 设最小段长门槛,短段直接重算 |
| 多实例命中率远低于预期 | 各实例缓存是否独立(无共享) | 单机缓存,请求被负载均衡打散 | 前缀亲和路由;或上集群级缓存池([[8.5 LMCache 与 Mooncake]]) |

## 6. 陷阱与误区

> [!warning] 常见错误
> 1. **把 KV Cache 当普通张量管理**:它是「按块换入换出的缓存层次」——不做分页与逐出,长会话直接 OOM;这是存储问题,不是模型问题。
> 2. **决策只看带宽不看固定开销**:NVMe/远端层的往返开销让短段取回稳输重算——盈亏平衡点是段长的函数。
> 3. **忽略 evict 与 fetch 同管道**:PCIe 是双向但共享的,下沉风暴期间取回变慢,TTFT 毛刺——W1 是隐藏等待点。
> 4. **拿论文/别家的重算-取回系数直接用**:两边都依赖本机型实测;不等式的意义在方法,数字必须自己标定。
> 5. **只报平均 TTFT**:命中与未命中是两个分布,平均值谁也不代表——按命中层分桶是最低要求([[9.5 p99 毛刺定位]] 同款教训)。
> 6. **offload 收益只算命中省的算力**:还要减去 PCIe 争用给 TBT 的伤害、pinned 池占用的主存——容量维的收益,带宽维的代价,总账才是真账。

## 7. 关键结论

| 结论 | 性质 |
| --- | --- |
| KV Cache = GPU 算出、反复读、装不下的中间状态;~320 KiB/token(70B 级 GQA 口径),32k 会话 ~10 GiB——并发被容量卡死是 offload 第一动机 | 事实/量级 |
| 前缀确定性 → 跨请求复用:命中一次省一整段 prefill——缓存价值从续命升级为算力复用 | 事实 |
| 一切决策归于不等式:取回时间(体积/层带宽+固定开销) < 重算时间(超线性)——上下文越长越值得缓存,每层有自己的盈亏平衡段长 | 事实 |
| offload 引擎 = 为张量定制的多级 page cache:分块(paged)、逐出(LRU)、预取(逐层流水掩盖传输)——第 1 章思想全数回流 | 事实 |
| TTFT 分布被命中率改写:p50 看命中路径,p99 看未命中+慢层取回+evict 风暴——按命中层分桶是排障第一步 | 实践结论 |
| 收益在容量维(HBM 释放→并发→吞吐),代价在带宽维(PCIe 争用→TBT)——总账评估,单指标必偏 | 取舍 |
| 成本模型必须本机实测标定:带宽用实测健康值,重算曲线自己拟合 | 实践结论 |
| 单机缓存的天花板是命中率被负载均衡打散——集群化(池化+亲和调度)是下一篇 | 伏笔 |
