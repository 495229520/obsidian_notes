# GDS 兼容性、约束与回退路径

> [[8.2 GDS 与 cuFile]] 用一句话预警过：**GDS 有静默回退（compat mode），不核对计数器的性能测试都可能在测一条假路径**。本篇把这句话展开成体系——直通路径不是一个开关，而是**一条前提链：驱动、文件系统、IO 形状、拓扑、资源，五道闸门全过才走直通；任何一道失败，cuFile 不报错，悄悄换到经主存的回退路径，API 返回值一模一样**。会用 GDS 的标志不是能写出 cuFileRead，而是三件事：说得出每道闸门背后的 OS 机制（为什么页缓存缓存不了显存、文件系统凭什么要「支持」）；分得清三种结果（直通 / 静默回退 / 硬失败）各自怎么观测；以及把回退从「库替你兜底的意外」改造成「自己设计的显式路径」。

前置：[[8.2 GDS 与 cuFile]]（机制与验伪三步——本篇全程引用）、[[1.3 Buffered IO 与 O_DIRECT]]（O_DIRECT 的对齐义务与页缓存取舍）、[[8.3 Bounce Buffer vs 直读]]（回退路径的正面形态：做对的 bounce）。

---

## 1. 名词与背景：直通路径为什么这么挑剔

先把「挑剔」还原成机制——每道闸门背后是一个具体的 OS/硬件事实，不是 NVIDIA 故意设卡：

- **页缓存为什么必须绕开**【事实】：页缓存缓存的是**主存页**（[[1.2 Page Cache 命中与未命中]]），而 GDS 的 DMA 目的地是显存——数据根本不落主存，「缓存」无从谈起。所以直通强制 O_DIRECT，也就继承了它的全部义务：偏移、长度、缓冲区 4 KiB 对齐，自己负责预读（[[1.3 Buffered IO 与 O_DIRECT]]）；
- **文件系统为什么要「支持」**【实现】：`nvidia-fs.ko` 的工作方式是在块层把 DMA 目的地从主存页换成显存的 BAR1 地址（[[8.2 GDS 与 cuFile]] §1）。这要求文件系统能把「文件偏移」直通地翻译成「块设备地址」交给 NVMe 驱动——本地 ext4/xfs 的 O_DIRECT 路径可以；FUSE、NFS 这类路径上数据要过用户态进程或网络协议栈，没有可替换的块层 DMA，直通无从下手，只有专门适配过的分布式文件系统（Lustre、GPFS、WekaFS 等）例外；
- **IOMMU 为什么碍事**【实现】：直通是网卡/盘对 GPU 的 P2P DMA，IOMMU 的地址翻译层与 P2P 路径的交互是已知雷区——gdscheck 建议 disabled 或 passthrough；
- **BAR1 为什么是资源**【实现】：`cuFileBufRegister` 把显存缓冲区映射进 BAR1 窗口供设备 DMA；窗口是有限的，注册也有毫秒级成本（与 [[4.4 内存注册与零拷贝]] 的 MR、[[8.1 GPU 内存层次与数据搬运]] 的 pinned 同一军规：预注册 + 池化）。

一句话总结【事实】：**直通路径 = 一条跨文件系统、块层、PCIe 拓扑、GPU 驱动的合作链**；链上每个环节都有自己说「不」的理由，而 cuFile 的产品选择是：谁说「不」都不惊动你。

## 2. 五道闸门：一次 cuFileRead 的判定链

![[图片/SVG/8_8_13_1.svg|900]]

| 闸门 | 判什么 | 失败的典型原因 | 核对手段 |
| --- | --- | --- | --- |
| ① 驱动 | `nvidia-fs.ko` 已加载、cuFile 驱动会话打开成功 | 内核升级后模块没重编；容器里缺设备节点 | `gdscheck.py -p` 第一屏 |
| ② 文件系统 | 目标文件所在 FS 支持直通 | 文件在 NFS/FUSE/overlayfs 上；ext4 挂载参数与 O_DIRECT 冲突（如 `data=journal` 模式下 O_DIRECT 不可用【实现】） | gdscheck 支持矩阵 + `mount` 查挂载参数 |
| ③ IO 形状 | fd 带 O_DIRECT；偏移/长度/缓冲区 4 KiB 对齐 | 忘开 O_DIRECT；变长记录导致尾部不对齐 | 代码审查 + strace 看 open flags |
| ④ 拓扑/IOMMU | GPU↔盘 PIX/PXB；IOMMU off/passthrough | 插错槽（SYS）；云主机默认开 IOMMU | `nvidia-smi topo -m`；gdscheck 的 IOMMU 行 |
| ⑤ 资源 | BAR1 有余量、`cuFileBufRegister` 成功 | 注册过多缓冲；消费级卡 BAR1 小 | `nvidia-smi -q` 的 BAR1 Memory Usage |

三种结果的分类要背下来【事实】：

1. **直通成功**：返回字节数，`/proc/driver/nvidia-fs/stats` 计数器随字节数增长；
2. **静默回退（compat mode）**：返回值与直通**完全一样**，计数器纹丝不动——最危险的一种，所有性能对比实验的头号假阳性来源（[[8.2 GDS 与 cuFile]] §3）;
3. **硬失败**：返回负值（`-EINVAL` 最常见：没开 O_DIRECT 或没对齐）——反而最好处理，错误可见、当场能修。

## 3. 回退掉到哪：compat mode 的真实路径与价格

compat mode 内部做的事【实现】：放弃块层 DMA 改写，退回「普通 POSIX 读进主存中转缓冲 + H2D 拷贝进显存」——**就是 [[8.3 Bounce Buffer vs 直读]] 的 bounce 路径，但由库内部代办、你无法调优**。对账：

| | 直通 | compat 回退 |
| --- | --- | --- |
| 主存总线穿越 | 0 次 | ≥2 次/字节（盘 DMA 落主存 + GPU DMA 读出） |
| CPU 参与 | 提交命令 | 中转调度 + 可能的缓冲拷贝 |
| 主存占用 | 0 | 库内部 bounce 池 |
| 对同机其他负载 | 无影响 | **抢主存带宽**——[[8.3 Bounce Buffer vs 直读]] §2.2 的总线耦合：别的流跟着慢 |
| 可观测性 | 计数器增长 | 只有「计数器不涨」这一条负证据 |

两个必须知道的控制点【实现】：

- 环境变量 `CUFILE_FORCE_COMPAT_MODE=true` 可以**强制**回退——这是做 A/B 对照实验的正规工具（直通组 vs 强制回退组，变量唯一）；
- `cufile.json`（cuFile 的配置文件，可用 `CUFILE_ENV_PATH_JSON` 指定路径）里的 `allow_compat_mode` 可以**关掉**回退——关掉后条件不满足直接报错。**生产建议关掉**【实践】：宁可启动时显式失败并走自己设计的回退（§4），也不要跑在一条「以为是直通、实际是 bounce」的路径上——性能悬崖静默发生是最贵的故障形态。

典型故障案例（形态值得记住）【实践】：某训练集群例行升级内核，`nvidia-fs.ko` 未随内核重编，重启后所有节点静默回退——**没有任何报错**，checkpoint 加载时间翻倍、主机 CPU 利用率上涨、DataLoader 吞吐下降（主存带宽被抢，[[8.7 DataLoader 与 GPU 空闲归因]] 的归因链）。监控里最先报警的是「GPU 空闲率」，离根因隔了四层。若当初 `allow_compat_mode` 为 false，故障会在重启后第一次 open 时以明确错误暴露。

## 4. 把回退变成显式设计：接口 + 探测 + 有界队列

依赖库的静默兜底，等于把「跑哪条路」的决策权交给运行环境;工程上应当反过来——**启动时探测一次，显式选择路径，运行时持续自证**。这一节给出 Modern C++ 骨架，并把并发与背压的对应关系说清。

### 4.1 路径抽象与启动探测

两条路径藏在同一个接口后面：直通用 cuFile（[[8.2 GDS 与 cuFile]] §5 的三层 RAII），回退用**自己做对的 bounce**（O_DIRECT 读进 pinned 环 + 异步 H2D，[[8.3 Bounce Buffer vs 直读]] §4）——比库的 compat 强在可调优、可观测：

```cpp
#include <cstddef>
#include <memory>
#include <span>

// 统一读接口:上层只关心「把文件的这一段放进显存」
class GpuFileReader {
public:
    virtual ~GpuFileReader() = default;
    // 把 [off, off+len) 读到显存 dst;返回实际字节数,负值为错误
    virtual ssize_t read(void* dev_dst, std::size_t len, off_t off) = 0;
    // 自证:这条路径当前是否真在直通(GDS 实现查 nvidia-fs 计数器增量)
    virtual bool verified_direct() const = 0;
};

class GdsReader final : public GpuFileReader { /* 8.2 §5 的三层 RAII */ };
class BounceReader final : public GpuFileReader { /* 8.3 §4 的 pinned 环 + H2D */ };

// 启动时探测一次,显式选路——不把决策留给库的静默兜底
std::unique_ptr<GpuFileReader> make_reader(const char* path) {
    if (auto gds = GdsReader::try_create(path))   // 内部:driver open +
        return gds;                               // 试注册小缓冲 + 试读一页,
                                                  // 任何一步失败即放弃
    return std::make_unique<BounceReader>(path);  // 显式回退:自己的 bounce
}
```

**关键点**：

- `try_create` 把 §2 的五道闸门在**启动期**全部趟一遍（driver open、handle register、小缓冲注册、试读 4 KiB 并核对计数器增量）——失败发生在部署时而不是流量高峰;
- `verified_direct()` 让「验伪」成为接口的一部分：监控定期调用，直通路径退化立刻报警，而不是等 p99 图形出卖它;
- 选择在构造期做一次、之后零分支——数据路径上不再有「试试直通不行再回退」的运行时抖动。

### 4.2 队列与背压：为什么这直接决定存储延迟

单笔 cuFileRead 是同步阻塞调用【实现】；直通路径的吞吐靠**多线程并发提交**撑起来（与 [[2.3 iodepth 与提交完成路径]] 的 iodepth 思想同源：盘的并行度要靠在途 IO 数喂饱）。于是 IO 子系统的形状就是标准的 C++ 生产者-消费者：

```cpp
#include <condition_variable>
#include <cstdint>
#include <deque>
#include <mutex>
#include <optional>

struct IoRequest {
    void* dev_dst;
    std::size_t len;
    off_t off;
};

// 有界提交队列:满即拒绝——背压点在这里,而不是在 OOM 里
class BoundedIoQueue {
public:
    explicit BoundedIoQueue(std::size_t cap) : cap_{cap} {}

    // 生产者(上层业务线程):队列满返回 false,调用方决定等待/降级/拒绝
    bool try_push(IoRequest req) {
        std::lock_guard lk{mu_};
        if (q_.size() >= cap_) return false;   // 背压信号:显式、立即、可数
        q_.push_back(req);
        cv_.notify_one();
        return true;
    }

    // 消费者(IO 工作线程,每人一套 pinned/显存注册缓冲,零共享)
    std::optional<IoRequest> pop() {
        std::unique_lock lk{mu_};
        cv_.wait(lk, [this] { return !q_.empty() || closed_; });
        if (q_.empty()) return std::nullopt;
        IoRequest r = q_.front();
        q_.pop_front();
        return r;
    }

    void close() {
        { std::lock_guard lk{mu_}; closed_ = true; }
        cv_.notify_all();
    }

private:
    std::mutex mu_;
    std::condition_variable cv_;
    std::deque<IoRequest> q_;
    std::size_t cap_;
    bool closed_ = false;
};
```

**这段代码与存储延迟的因果链**【事实/实践】：

1. **队列深度 = 在途上限 L**：Little 定律（[[7.18 Backpressure 与过载保护]] §1）说 L = λ·W——容量 cap 定死后，到达率超过消费能力时 `try_push` 开始返回 false，等待被推回上游，**延迟的上涨发生在可观测、可决策的地方**；换成无界队列，同样的过载变成「延迟无限涨 + 内存无限涨」，最后以 OOM 或全员超时爆发;
2. **回退路径的消费能力更低**：compat/bounce 每笔 IO 多一段主存中转与 CPU 参与——同样的 cap 与 λ，W 直接变差。这就是「静默回退伤延迟」的微观机制：**不是哪一笔 IO 慢了一点，是整条队列的服务率掉了一档，排队延迟按非线性放大**（利用率 80% → 95% 时排队延迟急剧拉升，[[7.18 Backpressure 与过载保护]] §1 的曲线）;
3. **每工作线程独立缓冲、零共享**：`cuFileBufRegister` 的注册缓冲、bounce 的 pinned 环都按线程私有分配——与 [[4.18 多线程下 QP 使用模型]] 模型 C 同一军规：并发靠分区 + 归属，不靠共享 + 锁。队列是唯一被多线程触碰的结构，把并发面积压缩到一个点;
4. **可见性交接是现成的**：`mutex`/`condition_variable` 自带 happens-before——生产者填好 `IoRequest` 再 push，消费者 pop 到后读它，中间不需要任何额外屏障;真正要小心的交接在 GPU 侧：H2D 用 `cudaMemcpyAsync` 提交后，**必须经 stream/event 同步后才能通知计算 kernel 消费**——跨设备的 happens-before 只能靠 CUDA API 传递（[[8.12 GPUDirect RDMA]] §4.2 同一条纪律）。

## 5. 排障清单：症状 → 原因 → 检查

| 症状 | 常见原因 | 检查动作 |
| --- | --- | --- |
| GDS 组与对照组数字几乎一样 | 两组都在 compat 路径 | `/proc/driver/nvidia-fs/stats` 计数器增量——每轮实验必做（[[8.2 GDS 与 cuFile]] §4 第③步） |
| 升级内核/驱动后吞吐掉一半、CPU 上涨 | `nvidia-fs.ko` 未随内核重编，全体静默回退 | `gdscheck.py -p`；生产关 `allow_compat_mode` 让它显式失败 |
| `cuFileRead` 返回 -22 | 没开 O_DIRECT；偏移/长度/缓冲未 4 KiB 对齐 | strace 看 open flags；打印三元组核对对齐 |
| 换了个目录就静默变慢 | 新目录在 NFS/overlayfs 上（容器里最常见） | `df -T` + `mount` 看文件真实所在的文件系统 |
| 开 IOMMU 的云主机上各种失败 | P2P DMA 与 IOMMU 翻译冲突 | gdscheck 的 IOMMU 行；按建议设 passthrough/关闭 |
| 注册缓冲到一定数量后开始失败 | BAR1 窗口耗尽 | `nvidia-smi -q` 看 BAR1 占用；缩池、复用、换卡 |
| p99 有毫秒级周期尖刺 | 数据路径上临时 `cuFileBufRegister` | 火焰图搜注册调用；预注册 + 池化 |
| 上层偶发「提交失败」 | 有界队列满——这是背压在工作，不是 bug | 看拒绝率与队列等待时间；扩消费能力或做准入降级（[[7.18 Backpressure 与过载保护]] §4） |

## 6. 陷阱与误区

> [!warning] 常见错误
> 1. **把「跑通了」当「跑对了」**：compat 兜底让任何环境都能「成功」运行——直通与否只有计数器能证明，返回值证明不了任何事。
> 2. **生产环境保留默认的静默回退**：性能悬崖无声发生，监控从「GPU 空闲率」这类四手指标倒查回来要几个小时——关 `allow_compat_mode`，让失败发生在启动期。
> 3. **对比实验不用 `CUFILE_FORCE_COMPAT_MODE` 做对照**：自己搭的「非 GDS 组」往往与 compat 路径实现不同，变量不唯一;强制回退才是干净的对照组。
> 4. **把回退路径外包给库**：compat 的 bounce 你不能调优、不能观测;显式的 BounceReader（O_DIRECT + pinned 环 + 双缓冲）稳态能打满 PCIe（[[8.3 Bounce Buffer vs 直读]] §4），是完全不同档次的「回退」。
> 5. **用无界队列「扛住」IO 高峰**：无界队列不是接纳负载，是把过载转成延迟与内存增长（[[7.18 Backpressure 与过载保护]] §4.1）——有界 + 快速拒绝才是对延迟负责的写法。
> 6. **忽略文件系统这道闸门的动态性**：同一程序、同一机器，数据挪个目录（本地盘 → NFS）直通就没了——路径核对要进部署清单，不能只在开发机上验一次。

## 7. 关键结论

| 结论 | 性质 |
| --- | --- |
| 直通不是开关而是前提链：驱动、文件系统、IO 形状、拓扑/IOMMU、BAR1 资源五道闸门，全过才直通 | 事实 |
| 每道闸门背后是 OS 机制：页缓存只缓存主存页故必须 O_DIRECT;FS 要能把偏移直通翻译成块地址,FUSE/NFS 无从直通 | 事实 / 实现 |
| 三种结果：直通（计数器涨）、静默回退（返回值一样、计数器不动——头号陷阱）、硬失败（EINVAL,最好处理） | 事实 |
| compat 回退 = 库代办的 bounce：主存穿越回账、CPU 回场、还抢同机其他负载的主存带宽 | 事实 |
| `CUFILE_FORCE_COMPAT_MODE` 是干净对照组;`allow_compat_mode=false` 让生产失败显式化——两个控制点各有正用 | 实现 / 实践 |
| 工程形态：启动期探测选路（接口 + try_create）+ 运行期自证（verified_direct 进监控）——决策权不留给运行环境 | 实践结论 |
| 吞吐靠多线程并发提交（iodepth 思想）;有界队列即背压点：服务率掉档时排队延迟非线性放大,这就是回退伤延迟的微观机制 | 事实 / 实践 |
| 队列内的可见性交接由 mutex/cv 自带;跨设备交接必须经 CUDA stream/event——与 GDR 同一条纪律 | 事实 |
