## 2. 一个索引包含哪些对象

### 2.1 持久化身份与进程内对象分开

| 对象 | 内容与职责 | 不应该放进去的东西 |
| --- | --- | --- |
| `BPlusTreeHeaderPage` | 索引的 `root_page_id_` 入口信息 | 当前线程的 guard、BPM mutex |
| `BPlusTreePage` 基部 | 节点类型、size、max_size | frame pin count 与替换器历史 |
| Internal Page | 有序 separator 与 child page ID | 子节点进程内地址 |
| Leaf Page | 有序 key、RID、next page ID、tombstone 元数据 | 每条记录都必然完整存放在叶页这一假设 |
| `BPlusTree` 对象 | 比较器、BPM 访问入口、header page ID、配置 | 不能代替磁盘页关系的永久指针树 |
| `Context` | 本次操作的 guard 集合和根页标识 | 不是自动回滚日志，也不是磁盘页结构 |

当前 BusTub 叶页 value 是 **RID**，它定位真实 tuple；内部页 value 是 **`page_id_t`**，它定位子索引页。两个模板都叫 ValueType，不代表二者语义相同。[1][2]

### 2.2 用 guard 把“身份”变为“临时可访问的字节”

访问一个节点应沿 page ID 通过 BPM 取得合适的 guard，再把其数据解释为对应页类型。这个转换不意味着申请了一个新的 C++ 节点，也不意味着可以把该指针保存到 guard 之外。[2]

**读取页字段需要读权限；移动条目、改 size、改 sibling link 或 tombstones 都需要写权限。** 对 `ReadPageGuard` 得到的视图强行去 const 并修改，不是“优化”，而是绕开同步协议。

树中的关系由 page ID 保持；frame 会被淘汰和复用。不要把 `frame_id_t`、`LeafPage *` 或 `shared_ptr<LeafPage>` 写成磁盘上的 child pointer。

## 3. Page Layout：先弄清每一个槽位的含义

### 3.1 通用页头与索引入口页不是同一回事

当前基部声明三个字段：4 字节 `page_type_`、4 字节 `size_`、4 字节 `max_size_`，头部口径为 12 字节。叶页在其后增加 `next_page_id_`，其头部宏为 16 字节。[2]

Header Page 则是**独立的索引入口页**，持有根页号。它不是“每个 B+Tree 节点都要带的共同页头”。当前基部没有 `parent_page_id_`；向上找到父页可以依赖 `Context` 中仍然持有的路径，而不是凭空假定有一个持久化 parent 字段。

### 3.2 Internal Page：size 数的是 child slots，不是有效 key 的个数

统一采用 0-based 编号，设内部页 `size = n`：

| 数组位置 | `key_array_` | `page_id_array_` |
| --- | --- | --- |
| 0 | 无效 dummy key，不参与比较 | C0，最左子树 |
| 1 | S1 | C1 |
| … | … | … |
| n−1 | S(n−1) | C(n−1) |

因此共有 **n 个 child page ID、n−1 个有效 separator**。源码注释中还会用“m 个 key、m+1 个 child”描述抽象树，两种计数口径可以同时成立，前提是不把 m 和 `GetSize()` 混为一个量。[2]

在当前节点继承的键范围内：C0 负责小于 S1 的部分，Ci 负责 `[Si, S(i+1))`，最后一个 child 负责最后的上界以内的其余部分。**等于 separator 的 key 走右侧 child。**

dummy key 不是最小整数，不需要拿它与搜索 key 比较；它只是为“所有 child 都有一个对应数组位置”而保留的无效键槽。把它设成 0 然后参与搜索，会在负数或其他 key 类型下暴露错误。

### 3.3 Leaf Page：物理条目、逻辑条目与链表指针

叶页的 key 与 RID 一一对应，`size_` 描述物理数组中的条目数；其中部分槽位可能被 tombstone 标为逻辑删除。当前快照还包含 `num_tombstones_` 与保存**物理下标**的 `tombstones_` 数组。[2]

`next_page_id_` 用于叶页的正向有序扫描；它不证明两个叶页在磁盘上相邻，也不能代替树上的 parent separator。DDIA 第 3 章明确区分了逻辑键序和物理磁盘布局。[4]

### 3.4 容量公式与真实对象布局

当前源码给出的名义容量公式可写成：

$$
C_{internal}=\left\lfloor\frac{P-12}{sizeof(KeyType)+sizeof(page\_id\_t)}\right\rfloor
$$

$$
C_{leaf}=\left\lfloor\frac{P-16-sizeof(size\_t)-k\cdot sizeof(size\_t)}{sizeof(KeyType)+sizeof(RID)}\right\rfloor
$$

其中 P 是 `BUSTUB_PAGE_SIZE`，k 是实际采用的 tombstone 容量。模板参数为负值时，当前宏使用默认 tombstone 数，不能把负数直接放进容量计算。[2]

例如**只作名义算术示例**：P=8192，KeyType 为 8 字节，page ID 为 4 字节，RID 为 8 字节，size_t 为 8 字节，k=2，则内部容量为 681，叶页容量为 509。这不是对所有编译器、类型组合都做过 `sizeof(Page)` 验证的结论。

编译实际类型时必须核对 ABI padding、alignment、数组容量与配置 `max_size`。添加字段会占掉原本留给条目的空间。尤其不能把 vector、string、mutex、智能指针等具有进程内资源语义的对象直接加进页镜像；课程要求页内增加的字段遵循简单可构造类型等限制。[1]

源码的数组是课程给定的页格式；本篇不擅自把它们改成 vector。下面独立搜索示例里的 vector 是**页外教学数据**，不是建议修改这些页成员。

## 4. 不变量：先决定 separator 是边界，还是严格的右子树最小值

基础检查条件是：有效键排序；叶页键与 RID 对齐；内部 child 数比有效 separator 数多一；所有叶页深度相同；非根节点满足所选容量规则；从树上遍历得到的叶序与 sibling 链一致。

### 4.1 Separator 可以是合法边界，不一定是仍然存在的记录

对相邻非空子树 L、R，合法分隔键 S 可满足：

`max(L) < S <= min(R)`。

它的职责是隔开两个范围，**不一定永远等于 `min(R)`**。Lecture 08 特别指出，内部 guide post 可能已经不再存在于叶页中。[3]

例如左侧最大 key 为 10，右侧原来是 `[20,30,40]`，separator=20。删掉 20 后，右侧变成 `[30,40]`，保留 separator=20 仍然能正确路由。

这件事决定并发算法能否在叶页“不发生结构变化”时释放父锁：若约定 separator 必须始终等于右子树最小值，删除最小 key 就可能需要上改，即使叶页没有 underflow。[7]

### 4.2 借位之后不能继续沿用失效边界

若把右页最小 key=20 借给左页，左页最大 key 就变成 20，原 separator=20 不再满足“左侧严格小于”。这时必须调整父分隔键。

因此，“删除后有时可以保留旧 separator”绝不是“separator 不需要维护”。**是否发生跨边界移动，是两个场景的根本差异。** 对包含全 tombstone 的叶页，还应按物理结构和已维护的范围判据处理，不能对空的 live 集合生造 `min()`。

## 5. Search：内部 upper bound，叶页 lower bound

### 5.1 内部节点在找 child，叶节点在找 entry

内部页在有效 separator `S1...S(n−1)` 中找**第一个大于 target 的 separator**。若它是 Sj，走 C(j−1)；若不存在，走最后一个 child。相当于在跳过 dummy 的范围执行 upper bound，再回退一个 child 位置。

叶页找**第一个不小于 target 的物理 key**，相当于 lower bound。点查还要检查“没有越过 size、key 相等、该槽位不是 tombstone”。范围起点查找则不要求相等，可能需要继续跨页找到第一个有效条目。

| 条件 | 处理 |
| --- | --- |
| target 小于所有 separator | C0 |
| target 等于 Sj | Cj，不是 C(j−1) |
| target 大于所有 separator | 最后一个 child |
| leaf lower bound == size | 该页无候选；扫描可能继续下一页 |
| 物理 key 相等但有 tombstone | 点查未找到有效记录；扫描跳过 |

当前 `GenericComparator` 采用比较结果，而不是可以直接当作 STL strict-less 的布尔函数；对其结果应使用 `< 0`、`== 0`、`> 0` 等判断。把返回 −1/0/1 的比较器不加包装当 bool，会把“较大”也转换为 true。不要用未经证明符合 key 编码规则的 `memcmp` 替代它。[2]

### 5.2 独立 C++17 边界模型

以下代码全部拼在一起可运行。它用整数表达排序，故意让 dummy=999，证明内部搜索不依赖 dummy 的值；不涉及页锁，因此不额外画时序图。

```cpp
#include <algorithm>
#include <cassert>
#include <cstddef>
#include <iostream>
#include <optional>
#include <stdexcept>
#include <vector>

// 参数是普通 C++ 容器，仅模拟页内搜索，不是可序列化的 BusTub Page。
// keys[0] 是 dummy，keys[1..] 是严格递增的 separator。
std::size_t RouteChild(const std::vector<int> &keys, int target) {
  if (keys.empty()) throw std::invalid_argument("no child slot");
  const auto pos = std::upper_bound(keys.begin() + 1, keys.end(), target);
  // 至少有 dummy；pos >= begin()+1，所以减 1 不会下溢。
  return static_cast<std::size_t>(pos - keys.begin() - 1);
}
std::size_t LeafLowerBound(const std::vector<int> &keys, int target) {
  return static_cast<std::size_t>(
      std::lower_bound(keys.begin(), keys.end(), target) - keys.begin());
}
```

tombstone 判断是物理下标成员测试；即便 key 在数组中，结果也可以是“不存在”。这个模型不实现 tombstone 队列更新。

```cpp
// tombstones 保存物理槽号；本例线性检查它们以突出正确性。
std::optional<std::size_t> FindLive(const std::vector<int> &keys,
                                  const std::vector<std::size_t> &tombstones,
                                  int target) {
  const auto slot = LeafLowerBound(keys, target);
  if (slot == keys.size() || keys[slot] != target) return std::nullopt;
  if (std::find(tombstones.begin(), tombstones.end(), slot) != tombstones.end()) {
    return std::nullopt;
  }
  return slot;
}
```

测试覆盖等号归右、只有一个 child、空叶、越界、逻辑删除，并对 10,000 个 key 与直接区间判定比较。

```cpp
int main() {
  const std::vector<int> internal{999, 20, 40}; // dummy 故意不按排序放置。
  assert(RouteChild(internal, -1) == 0);
  assert(RouteChild(internal, 20) == 1);        // 等号归右子树。
  assert(RouteChild(internal, 39) == 1);
  assert(RouteChild(internal, 40) == 2);
  assert(RouteChild(std::vector<int>{0}, 100) == 0);
  assert(LeafLowerBound({}, 7) == 0);
  assert(LeafLowerBound({10, 20, 30}, 21) == 2);
  assert(!FindLive({10, 20, 30}, {1}, 20));    // 物理存在，逻辑已删除。
  assert(FindLive({10, 20, 30}, {1}, 30) == 2);
  assert(!FindLive({10, 20, 30}, {}, 99));
  bool rejected = false;
  try { (void)RouteChild({}, 7); }
  catch (const std::invalid_argument &) { rejected = true; }
  assert(rejected);
  for (int key = -5000; key < 5000; ++key) {
    const std::size_t expected = key < 20 ? 0 : (key < 40 ? 1 : 2);
    assert(RouteChild(internal, key) == expected);
  }
  std::cout << "page_search: PASS (10000 routing checks)\n";
}
```


## 6. Insert：本地插入与向父传播是两个层次

### 6.1 非满叶页的路径

先定位目标叶页、二分找到位置；有效同名 key 已存在则返回 false，不新增记录。插入位置之后的 key 与 RID 必须同步右移，再写入新 entry 并更新 size。向右平移应从尾部开始，避免覆盖尚未搬走的元素。

若叶页有 tombstone，还要调整所有受平移影响的下标；若同名 key 只是逻辑删除，应按重新插入的语义恢复有效记录和新的 RID，而不是产生两个相同的物理 key。当前公开 tombstone 测试明确检查重新插入后的 RID 与 tombstone 清除。[5]

### 6.2 把三个容量概念写在纸上

| 名称 | 含义 |
| --- | --- |
| C | 页内固定数组能容纳的物理槽位总数 |
| M / max_size | 传给页初始化/索引构造的配置值，不得超过合法容量 |
| split 阈值 | 本实现选择何时执行分裂；不必与“写第 C+1 项”是同一时刻 |

Spring 2026 项目**推荐但不强制**：叶页插入后 size 达到 max_size 就分裂；内部页在插入前 size 已达 max_size 时处理分裂。[1] 对叶页，采用这个约定时，普通插入要保持不分裂，插入前需要 `size + 1 < M`；不能机械写成“只要 size < M 就绝对 safe”。

`GetMinSize()` 的固定快照仍是待实现函数，其注释允许根据设计取 ceil 或 floor。[2] 奇偶容量、内部 child 计数、根例外和分裂时机必须作为一套规则验证，不能从三篇不同年份教程分别抄一个公式。

### 6.3 绝不能先越界写，再说下一步会分裂

如果当前 size 已等于物理容量 C，把新条目直接写入 index=C 是越界；随后马上 split 也不能补救已经发生的内存破坏。

可以采用预先分裂、在合法槽位内分发条目等策略；需要工作页/大缓冲时遵守项目的 BPM 分配约束。**下面“合并后共有五项”的纸上序列只是逻辑重排，不要求把五项先写入容量四的真实页数组。**

## 7. Split：叶页 copy-up，内部页 push-up

### 7.1 叶页分裂的具体变换

以下采用教学模型：不启用 tombstone；叶页稳定最大条目数为 4，最少为 2；待插入记录把逻辑有序序列变为 `[10,20,30,40,50]`。这个“允许到五项再从逻辑序列分发”的模型不同于课程推荐的叶页达到 M 即分裂，目的是把结构变化单独讲清。

将其分为 L=`[10,20]`、R=`[30,40,50]`，向父页提交 `(separator=30, right_page_id=R)`。**30 留在右叶页，同时作为边界复制到父页**。如果把 30 从叶页删除，它对应的真实索引记录就丢了。

叶链更新应保存旧 next：R.next=old_next，再令 L.next=R；并发可见顺序还受 latch 协议保护，不能认为两次赋值天然构成原子结构变化。[3]

### 7.2 内部页分裂的具体变换

用 `(key, child)` 的逻辑配对书写，但底层仍是分离数组：

`[(⊥,C0),(20,C1),(40,C2),(60,C3),(80,C4)]`。

选择 40 作为提升键，结果为：

| 位置 | 结果 |
| --- | --- |
| 左内部页 | `[(⊥,C0),(20,C1)]` |
| 向父提升 | `40`，以及新右内部页的 page ID |
| 右内部页 | `[(⊥,C2),(60,C3),(80,C4)]` |

**C2 必须保留下来成为右页的 child[0]；40 不再是右页的有效 separator。** 它分隔的是左右两个新内部页，不能继续按一个普通 key/child 对照搬而误删 C2。[3]

![[图片/SVG/8_6_6_24_2.svg|900]]

图上半展示叶页提升键仍然是一条叶记录，下半展示内部页提升键只留在父层，而它原来的 child 成为右页的最左 child。两者名称只差 copy 与 push，但数组操作完全不同。

### 7.3 父页必须按旧 child 的位置插入

父页接受的不是“在所有 key 中再猜一个位置”，而是“旧 child 在父页中的索引 j 已知，把新右 child 插到 j+1，并在对应位置加入新的 separator”。这样把结构变换与路径身份直接关联。

若父页仍有容量，插入后结束。若父页也需要分裂，把新的 `(separator, right_page_id)` 继续往上交。`Context.write_set_` 可保存仍然被保护的祖先，便于找到真正的父页。[1][2]

**向上改已经持锁的父页，不等于持有子页后再向上补锁。** 后一种行为可能违背锁顺序，详见 6.25。

### 7.4 根分裂与首次插入

空树第一次插入需要分配叶页、初始化、写入记录并发布 root page ID。根分裂需要分配新根，让其 child[0] 指向旧根/左半，child[1] 指向新右页，separator 为本次提升键，再更新 Header Page 的根号。

新根在读者能够从入口访问前，其必要字段必须初始化完成。并发下必须保护 header 与旧根的关系；只把 `root_page_id` 改成 atomic，不能自动保证旧根仍然是正确入口。

这里的“发布”是内存结构在 latch 协议下变为可访问；**它不是多个磁盘页已经原子持久化**。多页 split 的恢复问题应接到 [[8.高性能存储/6. 存储引擎/6.4 Torn Write 与 Checksum|Torn Write 与 Checksum]] 与 WAL，而不归结为“把父页最后 flush 就够了”。[4]

## 8. Delete：先区分删除、借位、合并与回收

本节先使用 **k=0、立即物理删除**的模型，tombstone 版本在第 10 节加入。定位不到有效 key 时不应改 size、挪动数组或删除父指针。

物理删除后，把后续 key/RID 同步左移并减少 size。若仍满足最小占用且无需维护更强的 separator 约束，局部操作结束；否则查看同一父页下的相邻 sibling。[3]

**叶链上的 next 不一定与当前页共享直接父节点。** 借位或合并需要基于持有的父页找到合法兄弟，不能拿到 next 就随意从另一个父节点的子树搬记录。

### 8.1 Leaf redistribution：只搬叶记录，再改父边界

设两页稳定最少 2 项：

| 情况 | 变换前 | 变换后与父 separator |
| --- | --- | --- |
| 右页向左借 | L=`[10,20,30]`，R=`[40]`，S=40 | L=`[10,20]`，R=`[30,40]`，S 改成 30 |
| 左页向右借 | L=`[10]`，R=`[20,30,40]`，S=20 | L=`[10,20]`，R=`[30,40]`，S 改成 30 |

借出者要能少一项后仍满足最小占用；不是“兄弟不为空就能借”。搬一项时 key 与 RID 不可拆开，双方 size 和父 separator 要在同一次受保护的变换中对应一致。

### 8.2 Internal redistribution：parent separator 要参与旋转

从右内部页借最左 child 给左页：把旧 parent separator 作为该 child 在左页尾部的 key；右页原来的第一个有效 separator 升为新的 parent separator；右页新的 child[0] 对应 key 置为无效。

例如父 separator=20：

- L=`[(⊥,C0),(10,C1)]`；R=`[(⊥,C2),(30,C3),(40,C4)]`；
- 借位后 L=`[(⊥,C0),(10,C1),(20,C2)]`；
- R=`[(⊥,C3),(40,C4)]`；父 separator=30。

反向从左页借最后一个 child 给右页：左页最后一个有效 key 升到父页；旧 parent separator 下沉为右页原 child[0] 的有效 key；搬来的 child 成为新的右页 child[0]。[3]

两种方向都可记为：**child 过边界，separator 经父页旋转。** 不能把内部借位当作“复制邻居第一个 key/value 就完成”。

### 8.3 Leaf merge：父 separator 不作为叶记录插入

若借位不可行且合并后的物理条目数可以放入接收页，把右页记录按序接到左页，并令 L.next=R.next；在父页删除指向 R 的 child slot 及相应 separator。

例如 L=`[10]`、R=`[20,30]`，父 separator=20，合并结果是 `[10,20,30]`，**不是 `[10,20,20,30]`**。父 key 只是路标，R 中已经有那条真实记录。

“从父页中删除 R”与“R 已经可以回收”是两步。仍有引用、guard、pin 或后台 I/O 使用的页不能被直接复用。

### 8.4 Internal merge：父 separator 必须下沉

内部页合并则不同。L=`[(⊥,C0),(10,C1)]`、R=`[(⊥,C2),(40,C3)]`，父 separator=30。结果应是：

`[(⊥,C0),(10,C1),(30,C2),(40,C3)]`。

如果忽略父 separator，C1 与 C2 之间没有正确路标；如果把 R 的 dummy 原样当成有效 key 追加，结果同样错误。这里仍然有 4 个 child、3 个有效 key。[3]

### 8.5 父页 underflow 与根收缩

移除一个 child 之后，父页 size 减一；若低于该类节点的最小占用，继续向上做借位或合并。

根是例外：**内部根只剩一个 child 时可以把该 child 发布为新根**，高度减一；k=0 的叶根删到没有条目时，入口可以变为 `INVALID_PAGE_ID`。不要把所有根都强行套进普通内部节点的“至少半满”规则。

对有 tombstone 的树，逻辑空不必等于物理空；当前公开测试专门检查所有 key 逻辑删除后 `Begin().IsEnd()` 为 true，同时还可能保留物理页和 tombstones。[5] 不能只看 live_count=0 就随意提前清掉所有延迟删除信息。

## 9. 一个结构操作怎样安全结束

完成 split/merge 之前，要确认本次需要的页和 guard 可以获得。如果边改页边获取资源，后续分配失败、兄弟锁获取失败或 I/O 出错，已经部分完成的变换不能通过简单 `return false` 撤销。

这是工程设计问题，典型方向是：**在公开可见修改前取得必要资源；或者建立可回滚的临时状态与恢复协议。** 当前 `Context` 只是追踪 guard，不会自动记录旧字节或 undo 信息。[2]

显式删页时要检查 BPM 的 `DeletePage` 结果。被 pin 的页删除失败，不应“先忽略、以后也不管”，否则可能泄漏或错误复用。更一般的并发回收需要 retired/deferred-free 等机制；这些不是本次骨架已自动提供的功能。

析构 guard 会释放访问权，但通常不等于立即把所有脏字节持久化。不要把 C++ 的作用域结束与数据库操作持久化混淆。

## 10. Tombstone buffer：删除的 key 不一定立即离开数组

### 10.1 三个计数分别是什么

设 k 为延迟删除容量：`size` 是物理条目数，`num_tombstones` 是仍在缓冲中的逻辑删除数；在每个槽位最多一个 tombstone 的前提下，`live_count = size - num_tombstones`。[1][2]

tombstone 记录**物理下标**，不是 key 本身、RID 或删除时间戳。`KeyAt(i)` 必须返回该物理下标上的 key，不因其被删除而隐藏；`GetValue` 与 iterator 则必须过滤删除状态。[1]

k=0 时立即物理删除。k>0 时，缓冲还能容纳新删除就先追加；已有 k 个待删除项、再有新删除需要进入时，先处理最旧项以腾出空间，最终保持最多 k 项。不能为方便而每次删除都清空缓冲。[1][5]

**阈值口径说明**：课程正文关于“缓冲有 k 项时处理最旧删除”的表述，容易被读成“刚凑齐 k 项便立即清掉一项”。本文的例子按固定源码的公开测试解释：允许保留 k 项，在接纳下一次删除时腾出空间。这个边界以对应学期的测试和澄清为准；不能把两种触发点无提示地混在同一实现里。[1][5]

### 10.2 一次具体的下标重映射

设物理数组 `[10,20,30,40]`，k=2。队列从左到右是最旧到最新：

| 操作 | 物理 key 数组 | tombstone 物理下标 | 逻辑有效 key |
| --- | --- | --- | --- |
| 初始 | `[10,20,30,40]` | `[]` | `[10,20,30,40]` |
| 删除 20 | 不变 | `[1]` | `[10,30,40]` |
| 删除 40 | 不变 | `[1,3]` | `[10,30]` |
| 再删除 10 | 先物理删除最旧的 20，得 `[10,30,40]` | 原 40 从 3 改到 2；追加 10 的 0，得 `[2,0]` | `[30]` |

第 3 次删除后不能留下 `[3,0]`：下标 3 已不在当前数组中。也不能先向容量为 k 的真实 tombstone 数组写入第 k+1 项，再做清理。

重复 Remove 一个仍为 tombstone 的 key，不应重复入队；否则 live_count、FIFO 次序和后续下标变换都会失真。

### 10.3 数组变化时的规则

| 结构操作 | 对 tombstone 下标的影响 |
| --- | --- |
| 在 i 处插入物理 entry | 原下标 >=i 的 tombstone 加一 |
| 物理删除 i | 移除 i 对应的 tombstone；原下标 >i 的减一 |
| 以 b 为边界分裂 | 左半下标保留；右半原下标减 b；各半保留本地删除相对次序 |
| 右页整体接到左页 | 右页下标加接入偏移；还要处理合并后的删除次序和容量 |
| 跨页借位 | 被搬 entry 的 tombstone 状态一起迁移；两页发生位移处都要重映射 |
| 重新插入逻辑删除的 key | 取消该条目的删除标记，更新其有效 RID；不能留下重复 key |

这是处理步骤的框架，不是允许忽略操作中再次触发物理删除的简化算法。每执行一次实际删除，后续待处理下标都要基于新布局。

### 10.4 合并后的删除次序不是随意拼接

Spring 2026 说明明确约定：把 donor 的条目并入 recipient 时，**donor 的待删除操作视作比 recipient 更晚**；因此需要先处理 recipient 的较旧删除，再轮到 donor 的删除。[1]

这个相对次序是课程契约，不要求你证明两个页上的真实墙钟时间。把两边 tombstones 按“当前物理下标大小”排序，会丢掉删除年龄；把 donor 队列放在 recipient 前面，也会颠倒约定。

拆分则把原队列按条目归属投影到左右页，不能因为右页是新分配的，就把右页全部标成最新。边界 separator 仍用于路由，可以对应一个被 tombstone 标记的物理 key；点查是否返回它由叶页可见性判断，而不是依靠内部 guide post 判断。

### 10.5 Tombstone 不等于 MVCC

这里保留的是“最近删除的槽位”，不是多事务可见的历史版本链。没有事务时间戳、快照规则和冲突处理，不能因为数组里留着旧 key 就说实现了 MVCC。已有 [[8.高性能存储/6. 存储引擎/6.15 Snapshot 与 Sequence Number|Snapshot 与 Sequence Number]] 可用于对照版本可见性，但不是本实验 tombstone 机制的别名。

## 11. Iterator：跨页游标同时也是一个资源持有者

### 11.1 最小状态不只是 `(page_id, slot)`

游标通常需要当前叶页的 page ID、物理槽位、使该页仍可访问的读 guard，以及获取下一页所需的 BPM 入口。默认/end 状态不能被解引用。[2]

本篇使用通常的 **past-the-end** 语义：`IsEnd()` 为 true 时没有可解引用的 entry。项目正文的 `isEnd` 说明把它描述成“指向最后一项”，措辞不够严密；固定头文件的方法名是 `IsEnd()`，公开测试也用空树 `Begin().IsEnd()==true`。不要据字面把最后一条有效记录漏掉。[1][2][5]

### 11.2 Begin、Begin(key) 与自增

`Begin()` 从根下降到最左叶页，从 slot=0 开始跳过 tombstones；若该页没有有效 entry，继续 next 页，直到找到有效项或结束。

`Begin(key)` 先路由到候选叶页，用 lower bound 找起始槽，再执行同样的“跳 tombstone、跨页、判末尾”过程。只有在页内找不到 key 时直接返回 End，会漏掉后面叶页的合法范围结果。

`operator++()` 先移动到本页下一物理槽，再跳过删除项；耗尽本页后读取 next page ID，转移 guard 并从新页开头继续。一个新页也可能全是 tombstone，所以跨页逻辑需要能循环，不是只写一次 if。

### 11.3 解引用结果包含引用：`auto` 不保证复制

固定源码签名是：`operator*() -> std::pair<const KeyType &, const ValueType &>`。[2]

pair 对象按值返回，但它的两个成员仍引用页里的 key/RID。**`auto entry = *iter` 只是复制了一个装引用的 pair，并没有深拷贝记录。** structured binding 同样不应被想当然地当成深拷贝。

如果需要在 `++iter`、销毁 iterator 或释放 guard 之后使用结果，应分别构造 KeyType 和 ValueType 的值副本。否则即使内存没有释放，frame 被复用也可能令旧引用指向完全不同的数据。

### 11.4 move、copy 与 guard 转移

若 iterator 内嵌 move-only PageGuard，其复制语义必须显式设计。不能复制一个裸指针，却误以为复制出来的 iterator 同时持有 pin；也不能复制 guard 内部计数而不真正取得使用权。

自己定义析构函数可能影响隐式移动成员函数的生成，必要时显式处理 move/copy；不要到“返回 iterator 编译失败”时只为了通过编译把 guard 去掉。[6]

当前结构只提供向右 next，因此本篇按正向扫描讲解；不冒称自动满足随机访问或双向 STL iterator 的全部要求。

### 11.5 非并发扫描与并发扫描的交接条件不同

无结构并发时，可以在保存 next page ID 后释放当前 guard，再取得下一页以减少同时 pin 的数量，但必须维持索引对象与页不被外部删除的前提。

允许并发 merge/reclaim 后，中间的解锁窗口可能使 next 被移除；反过来，一直持当前叶页、阻塞等待 sibling 又可能死锁。需要 no-wait/restart 或更完整的扫描协议，详见 6.25。Spring 2026 P2 明确说未测试 thread-safe leaf scans，**这只是测试覆盖范围，不是这些并发情形不存在**。[1][7]

## 12. 先做结构校验器，再做大量随机测试

### 12.1 每次操作后检查什么

| 检查 | 能抓到的典型错误 |
| --- | --- |
| 每页 physical size 不超过真实容量 | 先越界再 split |
| 有效键序与 key/RID 一一对应 | 平移方向错，只搬 key 没搬 RID |
| 内部 n child / n−1 separator；child[0] 存在 | split 时把最左 child 一起丢掉 |
| 每个 child 的键符合父范围 | upper/lower bound 用错、borrow 后 separator 未更新 |
| 所有叶深度相同 | 根收缩/父传播不完整 |
| 递归叶序等于 next 链叶序；链无环 | split/merge 后 next 指针遗留 |
| tombstone 下标有效、无重复、次序正确 | 插入/删除后忘记重映射 |
| 全部 live entry 与参考有序映射相同 | 点查跳过/多报、tombstone 复活处理错 |
| 操作结束 guard 与 pin 无泄漏 | 小缓冲池下逐渐无可用 frame |

key/RID 对照不能只看 key 集合。测试 reinsert 时要改变 RID，否则“复活了旧 RID”可能蒙混过关。

### 12.2 小容量比大数据量更快暴露 bug

先把 leaf/internal max_size 设成很小的合法值，系统枚举奇偶容量。用递增、递减、交错插入强迫两侧分裂，再删除到触发两方向 borrow、merge、内部传播与根收缩。[1]

随机测试用 `std::map` 等有序参考模型对比**逻辑内容**，另用独立校验器检查**物理结构和 tombstone 次序**。参考 map 不知道 tombstone 何时应该被物理清除，不能单独证明延迟删除满足课程契约。

缩小 BPM 让已修改页被淘汰后重新读入，能检测 dirty/写回问题；这验证同一运行中的回写重读，并不自动证明重新打开数据库或断电恢复正确。当前教学后端与索引初始化路径的重启语义要另行审查。

### 12.3 官方测试与工具入口

项目列出 insert、delete、sequential_scale、concurrent 测试；固定源码另有 `b_plus_tree_tombstone_test.cpp`，其中测试带 `DISABLED_` 前缀。[1][5]

```bash

cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --target b_plus_tree_insert_test b_plus_tree_delete_test -j2
./build/test/b_plus_tree_insert_test --gtest_also_run_disabled_tests

```

先用 `--gtest_list_tests` 检查目标实际包含哪些测试，再决定运行筛选器。不要只记录命令退出码而漏看 “0 tests”。`b_plus_tree_printer` 可帮助观察 split/merge，但一张看起来正确的树图不能替代 guard 生命周期与并发测试。

## 13. 最容易写错的实现清单

**内部搜索从 slot0 开始；把 n 当有效 key 数；叶分裂提升键后删掉该叶记录；内部分裂丢失右页 child0；借位只搬记录不改 parent separator；内部合并忘记拉下 parent key；把 next 当作必然同父的 sibling；忽略 tombstone 下标移动；把逻辑空当作物理空；把 iterator 的 pair-of-references 当深拷贝。**

这些错误很多不会立即产生 segfault，而会表现为“某个边界 key 偶尔查不到”“扫描结果少一项”“重载一个页后树坏了”。用可追踪的小容量操作序列，比一开始只跑百万次压测更容易定位。
