# B+ tree vs LSM

> 第 6 章到此讲的都是 out-of-place 路线:不改旧数据,永远追加([[6.1 WAL 与 Crash Consistency]] → [[6.5 Bitcask 模型]] → [[6.6 LSM-tree 三种放大]])。但数据库世界的另一半——MySQL/InnoDB、PostgreSQL、SQLite——站在对面的 **in-place** 路线上:B+ tree 把数据组织成盘上的页,更新就是**找到那一页、改掉、写回原处**。本篇把两条路线并排放好:先把 B+ tree 用 C++ 工程师的语言立起来,再沿六个维度对账。核心视角提前给出:**这是「共享可变结构 + 细粒度锁」与「不可变快照 + 单写者追加」两种并发哲学的盘上版本**——你在 C++ 里权衡过 mutex 保护的大结构与 copy-on-write 快照,就已经权衡过一次 B+ tree 与 LSM。

前置:[[6.6 LSM-tree 三种放大]] + [[6.7 Compaction 策略]](LSM 侧的全部机制)、[[6.4 Torn Write 与 Checksum]](B+ tree 的 torn page 命门)、[[1.2 Page Cache 命中与未命中]](buffer pool 与页缓存的双缓存问题)。

## 1. B+ tree 五分钟:盘上的页式有序索引

结构【事实】:数据切成固定大小的**页**(page,InnoDB 默认 16 KiB【实现】),页即树节点。内部节点只存 key 与子页指针,叶子节点存整行数据,叶子间串成有序链表。扇出巨大——16 KiB 页放几百个 key,**亿级数据 3~4 层**【量级】:顶两层常驻内存,一次点查通常只有 1 次盘 IO。

读写路径【事实】:

- **读**:从根逐层二分下降到叶子页——O(log_扇出 N) 次页访问,内节点几乎必然缓存命中;
- **写**:下降到叶子页,**原地修改页内容**,页写回由 **buffer pool**(引擎自管的页缓存)延迟执行;崩溃安全靠 WAL 兜底——先记日志再改页,[[6.1 WAL 与 Crash Consistency]] 的协议原样适用【事实】;
- **页满分裂**:插入无处容身时叶子页一分为二、父节点加指针,分裂可能逐层向上传播——这是 B+ tree 写延迟毛刺的经典来源【实践】。

两个 in-place 特有的命门【事实】:

1. **torn page**:16 KiB 的页写到一半掉电,盘上留下半新半旧——盘只保证扇区级原子性。InnoDB 用 doublewrite buffer(每页先写副本再写原位)、PostgreSQL 用 full-page write(checkpoint 后首次改页把整页塞进 WAL)兜底【实现】,细节见 [[6.4 Torn Write 与 Checksum]]——这笔额外写就是 B+ tree 自己的写放大;
2. **双缓存**:buffer pool 与 OS page cache 各存一份页([[1.2 Page Cache 命中与未命中]]),内存花两遍——所以数据库标配 O_DIRECT 绕开 page cache,自己全权管缓存([[1.3 Buffered IO 与 O_DIRECT]])【实现】。

## 2. 并发哲学:同一道 C++ 选择题的两个答案

这是两条路线差异的根,先于一切性能对比【事实】。

**B+ tree = 共享可变结构 + 细粒度锁**。所有线程读写同一棵树,正确性靠页级 latch:下降时锁父页→锁子页→确认子页不分裂后放父页,一路交替——这就是 C++ 并发课里的 **hand-over-hand locking(锁耦合)**,教科书场景就是链表/树【事实】。麻烦也全是熟面孔:锁粒度与并发度的权衡、分裂时要向上回头加锁引出的死锁风险、根页成为所有路径共享的热点——工业实现靠乐观下降、版本号验证(OLC)等手段压锁开销【实现】,但「读写互相阻塞」的本性只能缓解,不能消除。

**LSM = 不可变快照 + 单写者追加**。盘上文件不可变,读端拿一份文件清单的快照(引用计数持有,≈ `shared_ptr<const T>`)随便读,永不加锁;写端只有顺序追加与「生成新文件后原子替换清单」——清单替换又是 [[5.5 Multipath 与故障切换]] §4 那个 `atomic<shared_ptr>` 发布模式【事实】。并发模型简单到近乎无聊,代价在别处:重建不可变文件的成本,就是 [[6.6 LSM-tree 三种放大]] 的写放大。

两种哲学各用十行 Modern C++ 写出骨架,差异一目了然:

```cpp
#include <atomic>
#include <memory>
#include <mutex>

// B+ tree 的并发骨架:共享可变,hand-over-hand 锁耦合下降
struct Page { std::mutex latch; /* keys, children ... */ };

void descend(Page& parent, Page& child) {
    std::unique_lock parent_lk{parent.latch};
    std::unique_lock child_lk{child.latch};   // 先锁子
    parent_lk.unlock();                        // 确认子页安全后才放父——一路交替到叶子
    // ... 在 child_lk 保护下原地修改页内容
}   // 读写互相阻塞;分裂要回头向上加锁——死锁风险的来源

// LSM 的并发骨架:不可变快照 + 原子发布(与 5.5 的路径表同一个模式)
struct FileList;   // 不可变:SSTable 清单,一旦发布不再修改

class Version {
public:
    std::shared_ptr<const FileList> snapshot() const {   // 读端:无锁,随便共享
        return files_.load(std::memory_order_acquire);
    }
    void install(std::shared_ptr<const FileList> next) { // 写端:flush/compaction 完成后整体替换
        files_.store(std::move(next), std::memory_order_release);
    }
private:
    std::atomic<std::shared_ptr<const FileList>> files_;  // C++20
};
```

一句话对齐【事实】:**B+ tree 把复杂度花在「怎么安全地共享可变状态」,LSM 把复杂度花在「怎么摊销重建不可变状态」**——与你在 C++ 里「mutex 细化」vs「copy-on-write 快照」的选择完全同构,连各自的失败模式(锁竞争 vs 重建风暴)都一一对应。

## 3. 六个维度对账

![B+ tree 与 LSM 六维对比:左列 B+ tree——页式有序树,写路径为下降到叶子页原地改、WAL 兜底、buffer pool 延迟写回,盘上呈随机页写,标注锁耦合并发、torn page 用 doublewrite 兜底、页半满碎片;右列 LSM——写路径为 WAL 顺序追加加 memtable,后台 flush 与 compaction 逐层归并,盘上呈大块顺序写,标注不可变快照无锁读、写放大由 compaction 支付、墓碑与旧版本占空间;中部对账条逐项比较写路径、点查、扫描、放大形状、并发模型、故障脾气;底部结论——B+ 把成本付在前台每次写,LSM 把成本攒给后台分期付](../../图片/SVG/btree-lsm-原地改与追加对比.svg)

| 维度 | B+ tree | LSM |
| --- | --- | --- |
| 写路径 | 随机页写(16 KiB 粒度)+WAL;改 100 B 也要整页写回 | 顺序追加 + 后台归并;前台永远是 append |
| 写放大形状 | **页粒度放大**:小改动 ÷ 整页写 + doublewrite,离散毛刺(分裂/checkpoint 风暴) | **归并放大**:2+T×(L−1),连续后台带宽 |
| 点查 | 稳定 1 次盘 IO(内节点常驻),**延迟方差小** | 多结构探测,靠 bloom+缓存压住,L0 堆积时恶化 |
| 范围扫描 | 叶子链表顺序走,天然有序、局部性好 | 多 run 归并迭代 + 跳墓碑,删除密集时 CPU 账重([[6.7 Compaction 策略]] §4) |
| 并发模型 | 锁耦合,读写互相阻塞,热点页竞争 | 快照读无锁,写并发好;代价转移给 compaction |
| 空间 | 页半满碎片(稳态填充率 ~2/3【量级】) | 旧版本+墓碑,SA 由策略决定 |
| 崩溃恢复 | WAL redo+undo,毫 checkpoint 距离决定恢复时长 | WAL 重放 memtable 即可,SSTable 不可变天然安全 |
| 对 SSD | 随机小页写抬高设备 WAF([[3.5 GC 写放大与 Over-Provisioning]]) | 大块顺序写,设备 WAF ≈ 1 |

两条最容易被忽略的结论【事实/实践】:

1. **B+ tree 也有写放大**,只是形状不同:整页写 + doublewrite + 分裂,对「小值随机更新」负载,页粒度放大(16 KiB / 100 B = 160 倍单次)未必输给 LSM 的归并放大——**两边都在付,付法不同:B+ 前台按次付清,LSM 后台分期**;
2. **延迟形状比均值更能区分两者**:B+ tree 点查方差小但写有分裂/checkpoint 毛刺;LSM 写路径极稳但读方差大、且有 stall 悬崖。选型先问业务对哪一侧的尾延迟敏感([[9.5 p99 毛刺定位]])。

## 4. 选型决策与判定线索

决策表【实践】:

| 负载特征 | 倾向 | 理由 |
| --- | --- | --- |
| 读多写少、点查为主、要稳定读延迟 | B+ tree | 1 次 IO 的点查 + 小方差 |
| 写重/高速摄取(日志、时序、消息) | LSM | 前台纯顺序追加,写并发模型简单 |
| 大范围扫描 + 频繁删除 | B+ tree | LSM 的墓碑扫描税太重 |
| 闪存寿命/写带宽敏感,值小且随机更新 | 视两层放大实测 | B+ 页粒度放大 vs LSM 归并放大,谁小听数据的 |
| 需要事务的成熟生态(二级索引、约束) | B+ tree 系 | InnoDB/PostgreSQL 生态数十年沉淀【事实】 |
| 存储与计算按核规划、自建引擎 | LSM 系 | RocksDB 可嵌入、旋钮全暴露([[6.9 RocksDB 关键路径]]) |

拿到一个陌生系统,判定它是哪派、病在哪的**排障清单**【实践】:

| 线索 | 指向 | 下一步 |
| --- | --- | --- |
| iostat 大量小尺寸随机写(数十 KiB 级) | B+ tree 刷脏页 | 查 checkpoint 频率与 buffer pool 命中率;写毛刺对 checkpoint 时刻 |
| iostat 持续大块顺序写远超业务写入 | LSM compaction | 走 [[6.6 LSM-tree 三种放大]] §5 的 WA 排障线 |
| 写延迟周期性尖刺,间隔固定 | B+ checkpoint/刷脏风暴 | 拉长 checkpoint 距离(恢复时间变长【取舍】)、平滑刷脏速率 |
| 写延迟突然掉到零再恢复 | LSM write stall | 走 [[6.7 Compaction 策略]] §5 的欠账排障线 |
| 读 p99 随运行时间缓慢劣化 | LSM 层结构失衡/L0 堆积 | 查每层 Size 与 L0 文件数 |
| 空间占用 ≈ 逻辑量 × 1.5 且删除后不回落 | B+ 页碎片或 LSM 墓碑 | B+:重建索引/OPTIMIZE;LSM:等墓碑沉底或手动 compaction |
| 同机双缓存内存吃紧 | B+ 引擎没开 O_DIRECT | buffer pool 与 page cache 二选一,别双份([[1.3 Buffered IO 与 O_DIRECT]]) |

## 5. 陷阱与误区

> [!warning] 常见错误
> 1. **「LSM 写快 B+ 读快」当万能结论**:形状不对——B+ 的写毛刺在分裂与 checkpoint,LSM 的读恶化在 L0 与墓碑;必须按负载与尾延迟目标细算,均值对比几乎无信息量。
> 2. **以为 B+ tree 没有写放大**:整页写 + doublewrite/full-page write + 分裂,小值随机更新时单次放大可达百倍量级——它只是没有「后台欠账」形态,不是没有放大。
> 3. **对比测试一边稳态一边空库**:LSM 空库(无层无欠账)必胜,B+ 空库(无碎片无分裂)也必胜——两边都要灌到稳态([[6.7 Compaction 策略]] §6、[[3.6 空盘与稳态性能]])。
> 4. **忽略生态成本**:引擎对比常被二级索引、备份工具、复制方案的成熟度决定,而不是存储结构本身——结构选型是工程选型的子集。
> 5. **在 LSM 上跑「频繁更新同一小集合 + 大范围扫描」**:最坏组合——版本堆积 + 墓碑扫描税;这类负载是 B+ tree 的主场。
> 6. **把 mmap 型 B+ 引擎(如 LMDB 风格)当免费午餐**:省了 buffer pool 但把刷脏时机交给了内核([[1.5 mmap 读路径]]),写延迟不可控——嵌入式只读/读多场景才是它的舒适区【取舍】。

## 6. 关键结论

| 结论 | 性质 |
| --- | --- |
| B+ tree = in-place:页式有序树,原地改页 + WAL 兜底 + buffer pool 延迟写回;LSM = out-of-place:追加 + 归并 | 事实 |
| 并发哲学是根本分歧:共享可变+锁耦合(hand-over-hand) vs 不可变快照+单写者——mutex 细化 vs copy-on-write 的盘上版本 | 事实 |
| 两边都有写放大,付法不同:B+ 页粒度前台按次付(整页+doublewrite+分裂),LSM 归并后台分期付 | 事实 |
| 点查:B+ 稳定 1 IO 方差小;LSM 多结构探测靠 bloom/缓存压制。扫描:B+ 叶链天然有序;LSM 归并+墓碑税 | 事实 |
| 延迟形状比均值更能区分两者:B+ 毛刺在分裂/checkpoint,LSM 毛刺在 stall,读劣化在 L0 | 实践结论 |
| 对 SSD:LSM 顺序写把设备 WAF 压到 ~1;B+ 随机页写抬高设备层放大——两层放大都要进账本 | 事实 |
| torn page 是 in-place 特有命门,doublewrite/full-page write 兜底,本身构成额外写放大 | 事实 |
| 选型判据:读写比、点查/扫描比、删除密度、尾延迟在哪侧敏感、生态需求——结构对比只是工程选型的子集 | 实践结论 |
