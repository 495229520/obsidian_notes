# Snapshot 与 Sequence Number

> 写在不断发生，读却想要一个静止的世界。存储引擎的答案不是加一把大锁，而是给每次写盖一个递增的号（Sequence Number），读的时候只认"号 ≤ 某个值"的数据（Snapshot）。这套多版本机制让读路径几乎不碰锁——它是 [[6.9 RocksDB 关键路径]] 里读延迟稳定的前提，也是 [[6.7 Compaction 策略]] 判断"旧数据什么时候能真正删掉"的唯一依据。本篇把它翻译成你熟悉的 C++ 并发语言：原子计数器、release/acquire 发布、epoch 式内存回收。

前置：[[6.9 RocksDB 关键路径]]（写路径与读路径全景）、[[6.11 MemTable Immutable 与 SST 生命周期]]（数据在引擎里的三种形态）。

---

## 1. 问题：读写并发时，读到底读到什么

先不谈存储，用一个 C++ 工程师熟悉的场景。你维护一个进程内的 `std::map<std::string, std::string>`，多个线程持续写；现在要做一次全量导出（备份、统计、迁移都算），导出要跑几分钟。三种做法：

| 做法 | 导出看到什么 | 代价 |
| --- | --- | --- |
| `std::shared_mutex` 大读写锁 | 一个完全静止的 map | 导出多久，写就停多久——线上不可接受 |
| 不加锁直接遍历 | 一半新一半旧，甚至迭代器失效崩溃 | 数据不一致 / UB |
| **多版本**：写产生新版本，读固定在旧版本 | 开始导出那一刻的完整世界 | 旧版本占内存，要有人回收 |

第三种思路你可能已经用过：读线程 `std::shared_ptr<const State>` 拿住当前状态，写线程 copy-on-write 换一个新 `State` 再原子替换指针——读者手里的旧对象由引用计数保活，读全程无锁。RCU 也是同一族思想。

**MVCC（Multi-Version Concurrency Control，多版本并发控制）**就是把这个思想做到"每个 key"的粒度：写不覆盖旧值，而是追加一个带版本号的新值；读声明"我要看 X 时刻的世界"，只取版本号不超过 X 的数据。由此得到的读语义叫**快照隔离（snapshot isolation）**：一次读（或一个迭代器的整个生命周期）看到的是某个时间点上完整、自洽的数据库状态，不多也不少。

LSM 引擎（[[6.11 MemTable Immutable 与 SST 生命周期]]）天然适合 MVCC：SST 文件本来就不可变，"追加新版本"就是它唯一会做的事。

## 2. Sequence Number：给每一次写盖递增的章

**Sequence Number（序列号，下称 seq）**是引擎内部一个全局单调递增的 64 位计数器，每个写操作（Put/Delete/Merge）分配一个号。它定义了全库唯一的写入全序——"谁先谁后"从此有了裁判。

**【实现】** RocksDB/LevelDB 把 seq 直接编进 key。引擎内部真正存储和排序的不是用户 key，而是 **internal key**：

```text
internal key = user_key + 8 字节尾部（seq << 8 | type）
```

seq 占 56 位，低 8 位的 type 标记这条记录是 Put、Delete 还是 Merge。于是同一个 user_key 的多个版本是引擎里**并存的多条记录**：

| 引擎里实际存的记录 | 含义 |
| --- | --- |
| `(k1, seq=12, Delete)` | 第 12 号写：删除 k1（墓碑） |
| `(k1, seq=9, Put) → "v2"` | 第 9 号写：k1 = "v2" |
| `(k1, seq=5, Put) → "v1"` | 第 5 号写：k1 = "v1" |

**墓碑（tombstone）**：SST 是不可变文件，删除没法原地抹掉旧记录，只能追加一条"此 key 已删除"的标记。旧值的物理清除是后台 compaction 的事（第 4 节）。

排序规则【实现】：user_key **升序**、seq **降序**——同一个 key 的记录里，最新版本排在最前面。这样读某个版本只需一次 `seek`（二分定位）加向后扫几步，不用把所有版本翻一遍。

### 2.1 谁来分配号：写路径的串行点

分配 seq 必须串行——两个写不能拿到同一个号，号的顺序还得和 WAL 里的落盘顺序一致。RocksDB 的做法【实现】：并发写线程先组队（[[6.2 Group Commit]] 的 write group），队长（leader）一次性为整批分配一段连续区间，比如当前 `last_sequence = 100`，本批 30 条操作，则占用 101–130，队长写完 WAL 后把 `last_sequence` 一次推到 130。

对应到 C++ 的直觉：如果每条写都对一个 `std::atomic<uint64_t>` 做 `fetch_add`，多核下这条 cache line 会在核间乒乓（[[0.1]] 一族的伪共享/争用问题同源）；合批之后，串行点每批只被摸一次，争用被摊薄。**seq 分配点是整个写路径唯一的全局串行点，它的争用程度直接决定写延迟的下限**。

### 2.2 内存可见性：先写数据，再发布号

`last_sequence` 同时也是读者的"可见性水位"：不带快照的读默认取当前 `last_sequence` 当作自己的快照。于是有一个必须做对的顺序问题——**数据要先就位，号才能发布**：

```cpp
// 写者（write group 的 leader）：
insert_into_memtable(batch);                               // ① 整批数据先写进 memtable
last_sequence_.store(new_seq, std::memory_order_release);  // ② 然后才发布新水位

// 读者（任意线程）：
uint64_t snap = last_sequence_.load(std::memory_order_acquire);  // 与 ② 构成同步
// 此后按 snap 查询：凡 seq <= snap 的记录，保证已完整可见
```

这就是 C++ 内存模型里标准的**发布模式**：release 写与 acquire 读配对，保证读者拿到新水位时，水位之下的所有写入对它可见。顺序反过来会怎样：读者先看到 `last_sequence = 130`，再去 memtable 里找 seq=125 的记录——找不到，或者只看到半个 batch，快照隔离"完整世界"的承诺当场破产。

**【事实】** 这对 release/acquire 不是锦上添花而是全部家当：RocksDB 的 memtable 是无锁并发跳表（InlineSkipList），读者查询**不加任何锁**。读路径的低延迟正是拿这一条换来的——没有锁，就只能靠原子发布保证可见性。

## 3. Snapshot：一次 O(1) 的"拍照"

**Snapshot（快照）**不是数据拷贝，只是一个被记住的 seq。`GetSnapshot()` 做的全部事情【实现】：

1. 在 DB mutex 保护下读当前 `last_sequence`；
2. 把这个号包成节点挂进**活跃快照链表**；
3. 返回句柄。`ReleaseSnapshot()` 把节点摘下来。

不复制任何数据，代价与库大小无关——拿一个快照是 μs 级甚至更快的操作【量级】。"拍照"拍下的只是一个数字，照片的内容靠多版本数据本身保存。

可见性规则一句话：**在所有 seq ≤ snapshot_seq 的版本里，取该 key 最新的一条；若那条是墓碑，则 key 不存在。**

![[图片/SVG/8_6_6_15_1.svg|900]]

落到读路径（[[6.9 RocksDB 关键路径]]）：`Get(key, snapshot)` 构造查找键 `(key, snapshot_seq)`，在 memtable → immutable → 各层 SST 里 seek"第一条排序不小于它的记录"——因为 seq 降序，命中的正是"≤ 快照号的最新版本"。

两个容易忽略的事实【事实】：

- **迭代器隐式持有快照**。创建 iterator 时若不显式传 snapshot，引擎自动取当时的 `last_sequence`——所以一个活了 8 小时的 iterator 就是一个活了 8 小时的 snapshot，代价见第 5 节；
- **快照不持久化**。它只是内存链表里的一个号，进程退出即失效。要"跨重启的一致数据副本"得用 Checkpoint/备份机制，那是另一套东西。

## 4. 生命周期：最老的快照决定谁能被回收

旧版本和墓碑不能永远留着，物理清除由 compaction（后台归并整理，[[6.7 Compaction 策略]]）执行。但 compaction 不能随便删——某个旧版本可能正被一个活跃快照需要着。规则【实现】：

- 同一 key 的两个相邻版本之间**没有任何活跃快照的号落在中间**时，旧的那个才允许丢弃（没有任何读者会再看到它）；
- 墓碑更苛刻：除了满足上一条，还要**沉到最底层**——确认更低层不存在同 key 的旧值——才能连墓碑本身一起消失。否则删了墓碑，被它盖住的旧值会"诈尸"。

活跃快照链表里**最小的那个号（oldest snapshot）就是全局回收边界**：它之前的世界必须完整保留。

这套机制你在 C++ 无锁编程里见过，对照着记：

| 存储引擎 | C++ 并发对应物 |
| --- | --- |
| 活跃快照链表 | epoch-based reclamation 的活跃 epoch 注册表 |
| oldest snapshot | 最小活跃 epoch / RCU 的 grace period 边界 |
| compaction 丢弃旧版本 | 所有读者退出临界区后，retire list 延迟回收 |
| 忘记 `ReleaseSnapshot` | `shared_ptr` 循环引用式泄漏：对象永远等不到析构 |

两边解决的是同一个问题：**读者不加锁，写者就不知道什么时候能安全地回收旧东西，只能让读者显式注册存在感，回收以"最老的活跃读者"为界。**

## 5. 为什么影响存储延迟

**（1）读端无锁，p99 才平。** 如果用读写锁，一次几百 ms 的范围扫描会把所有写者挡在门外，写者攒成队列，锁释放瞬间惊群——延迟毛刺的教科书成因（lock convoy）。MVCC 下读者只做一次 acquire load，写者永远不等读者，两边互不放大。

**（2）写端串行点被合批摊薄。** seq 分配 + WAL 追加是串行的，但以 batch 为单位串行（第 2.1 节）——单点争用从"每操作一次"降到"每批一次"，这是 LSM 写吞吐的结构性优势之一。

**（3）长快照的三笔账【取舍】【量级】：**

- **空间放大**：oldest snapshot 之后的所有旧版本、墓碑都不能回收，写得越快涨得越快；
- **读放大**：迭代器 `Next()` 要逐条跳过不可见版本和墓碑——每跳一条是一次 key 比较加潜在 cache miss。一个 key 攒了 1 万个待回收版本时，`Seek` 到它的邻居可能要先扫过这 1 万条（RocksDB 的 iterator 统计里 `skipped_internal_keys` 就是量这个的）；
- **compaction 空转**：数据被反复读出、归并、写回，却因为快照卡着删不掉——写放大白白增加。

**故障案例（经典）**：备份程序创建 iterator 后因为下游卡住挂了 8 小时。症状三联：磁盘使用量持续上涨、大量 Delete 后空间不降、范围扫描 p99 缓慢爬升。三个症状同源——都是 oldest snapshot 不动导致的版本堆积。排查抓手【实现】：DB 属性 `rocksdb.num-snapshots`（活跃快照数）与 `rocksdb.oldest-snapshot-time`（最老快照年龄），任何"空间不回收"的工单先查这两个。

## 6. Modern C++：一个能跑的迷你 MVCC

用 80 行把上面所有概念串起来：internal key 排序、seq 发布、RAII 快照、回收边界。

```cpp
#include <atomic>
#include <cstdint>
#include <map>
#include <mutex>
#include <optional>
#include <print>
#include <set>
#include <string>

// internal key：user_key 升序、seq 降序 —— 同 key 的最新版本排在最前
struct InternalKey {
    std::string user_key;
    uint64_t seq;
    bool is_delete;
    bool operator<(const InternalKey& o) const {
        if (user_key != o.user_key) return user_key < o.user_key;
        return seq > o.seq;                     // 注意方向：seq 大的在前
    }
};

class MiniMvcc {
public:
    // RAII 快照：构造即注册进活跃集合，析构即注销 —— 不可能忘记 Release
    class Snapshot {
    public:
        explicit Snapshot(MiniMvcc& db) : db_(db) {
            std::lock_guard lk(db_.snap_mu_);   // 真实引擎同样在 DB mutex 下做，
            seq_ = db_.last_seq_.load(std::memory_order_acquire);
            db_.active_.insert(seq_);           // 否则读号与注册之间会插进回收
        }
        ~Snapshot() {
            std::lock_guard lk(db_.snap_mu_);
            db_.active_.erase(db_.active_.find(seq_));
        }
        Snapshot(const Snapshot&) = delete;
        Snapshot& operator=(const Snapshot&) = delete;
        [[nodiscard]] uint64_t seq() const { return seq_; }
    private:
        MiniMvcc& db_;
        uint64_t seq_{};
    };

    void put(std::string key, std::string value) { write(std::move(key), std::move(value), false); }
    void del(std::string key)                    { write(std::move(key), {}, true); }  // 墓碑

    std::optional<std::string> get(const std::string& key, const Snapshot& snap) const {
        std::lock_guard lk(data_mu_);
        // 定位 (key, snap.seq)：因 seq 降序，第一条 seq <= snap 的记录即快照下最新版本
        auto it = data_.lower_bound(InternalKey{key, snap.seq(), false});
        if (it == data_.end() || it->first.user_key != key || it->first.is_delete)
            return std::nullopt;                // 没有可见版本，或最新可见版本是墓碑
        return it->second;
    }

    // compaction 的回收边界：这个号之前的世界必须完整保留
    [[nodiscard]] uint64_t oldest_visible_seq() const {
        std::lock_guard lk(snap_mu_);
        return active_.empty() ? last_seq_.load(std::memory_order_relaxed)
                               : *active_.begin();
    }

private:
    void write(std::string key, std::string value, bool is_delete) {
        std::lock_guard lk(write_mu_);          // 写串行：对应 write group 的 leader
        const uint64_t seq = last_seq_.load(std::memory_order_relaxed) + 1;
        {
            std::lock_guard dlk(data_mu_);
            data_.emplace(InternalKey{std::move(key), seq, is_delete}, std::move(value));
        }
        last_seq_.store(seq, std::memory_order_release);  // 数据就位后才发布水位
    }

    mutable std::mutex write_mu_, data_mu_, snap_mu_;
    std::map<InternalKey, std::string> data_;
    std::multiset<uint64_t> active_;            // 活跃快照号（可重复）
    std::atomic<uint64_t> last_seq_{0};
};

int main() {
    MiniMvcc db;
    db.put("k1", "v1");                         // seq=1
    MiniMvcc::Snapshot old_view{db};            // 拍照：seq=1
    db.put("k1", "v2");                         // seq=2
    db.del("k1");                               // seq=3，墓碑
    MiniMvcc::Snapshot new_view{db};            // 拍照：seq=3

    std::println("old view: {}", db.get("k1", old_view).value_or("<not found>"));  // v1
    std::println("new view: {}", db.get("k1", new_view).value_or("<not found>"));  // <not found>
    std::println("GC 边界 seq = {}", db.oldest_visible_seq());                     // 1
    return 0;
}
```

```bash
g++ -std=c++23 -Wall -Wextra -fsanitize=thread -o mini_mvcc mini_mvcc.cpp && ./mini_mvcc
```

与真实引擎的差距，也是继续深挖的路标：玩具用 `data_mu_` 保护 `std::map`，RocksDB 用无锁跳表让读者彻底免锁（此时第 2.2 节的 release/acquire 从"多一层保险"变成"唯一保证"）；玩具没有 WAL（崩了全丢，见 [[6.17 Recovery 路径]]）；`oldest_visible_seq()` 只算了边界，真正按边界搬走旧版本的是 compaction。

## 7. 陷阱与误区

> [!warning] 常见错误
> 1. **把 Snapshot 当数据备份**：它只是"一个号 + 一个链表节点"，不含数据；DB 关闭即失效。持久副本用 Checkpoint/备份工具。
> 2. **忘记 ReleaseSnapshot / iterator 长期不销毁**：空间上涨、Delete 不释放、扫描变慢——三症状同源，先查 `rocksdb.num-snapshots`。用 RAII 包装快照（如上例），让"忘记释放"在语言层面不可能发生。
> 3. **以为 Delete 之后空间马上回来**：删除只是写入墓碑；大量删除后磁盘占用短期不降反升是正常现象，回收要等 compaction 把墓碑沉底。
> 4. **把 seq 当时间戳**：它只是单调递增的逻辑序号，与墙上时钟无关，跨实例比较没有意义。
> 5. **在自己的 C++ 服务里遇到"读长写频"就上 `shared_mutex`**：先想想本篇——读路径去锁（MVCC/RCU/COW + 原子发布）通常比调锁参数收益大一个量级，代价是要设计版本回收。
> 6. **快照数量当免费资源**：每个快照都在压低回收边界；高频拍快照的场景（如每秒一次的增量导出）要监控版本堆积速度。

## 8. 关键结论

| 结论 | 性质 |
| --- | --- |
| seq 是全局单调写序号，编进 internal key（seq<<8\|type），同 key 多版本并存、seq 降序排列 | 事实 / 实现 |
| Snapshot = 记住一个 seq 并注册进活跃链表，O(1)、不拷贝数据、不持久化 | 事实 |
| 可见性规则：取 seq ≤ snapshot 的最新版本，墓碑即不存在 | 事实 |
| 写路径先插 memtable、后 release 发布 last_sequence，读者 acquire 读——无锁 memtable 下这是可见性的唯一保证 | 实现 |
| seq 分配是写路径唯一全局串行点，靠 write group 合批摊薄 | 实现 / 取舍 |
| oldest snapshot 是回收边界，机制同 epoch-based reclamation：读者注册存在感，回收看最老读者 | 事实 / 类比 |
| 长快照三代价：空间放大、迭代器跳版本（读放大）、compaction 空转 | 取舍 / 量级 |
| 读端无锁使读写互不放大延迟；这是 MVCC 对 p99 的核心贡献 | 事实 |
