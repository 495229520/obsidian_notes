# Compaction 策略

> [[6.6 LSM-tree 三种放大]] 收尾于一个三角：写放大、读放大、空间放大不可同时最优，compaction 策略是在三角里挑位置的旋钮。本篇把这个旋钮拆开：**compaction 到底在做什么（多路归并）、两大流派（leveled 与 tiered）各自把哪种放大压到最低、以及它作为一个「与前台抢资源的后台流水线」怎么调度**。第三部分最重要——compaction 的本质是一条跑在盘上的生产者-消费者流水线，你在 C++ 里对有界队列、消费者跟不上、限流让路做过的所有决策，这里一个不少地重演，只是队列换成了 SSTable、消费者换成了盘带宽。

前置：[[6.6 LSM-tree 三种放大]]（三角与背压链——本篇全程使用其术语）、[[1.7 块层与 blk-mq]]（后台 IO 与前台 IO 在设备队列相遇的地方）。

## 1. compaction 在做什么：一次多路归并

机制本身朴素【事实】：挑出若干个 key 范围重叠的 SSTable（跨层或同层），**多路归并**成新的有序文件——同 key 只保留最新版本，沉到最底层的墓碑丢弃，写出新文件后原子替换元数据、删除旧文件。输入输出都是顺序大块 IO，这是 LSM 对盘最友好的部分【事实】。

核心就是「K 个有序流合并」，Modern C++ 二十行能写出骨架——理解它，compaction 的成本结构就一目了然：

```cpp
#include <queue>
#include <ranges>
#include <span>
#include <vector>

struct Entry { std::string_view key; std::uint64_t seq; std::string_view value; };
using Run = std::span<const Entry>;   // 一个 SSTable 的有序视图（真实实现是文件迭代器）

// K 路归并:堆里放各 run 的游标,每次弹出全局最小 key
std::vector<Entry> merge_runs(std::span<const Run> runs) {
    struct Cursor { const Entry* it; const Entry* end; int run_idx; };
    auto newer = [](const Cursor& a, const Cursor& b) {   // key 相同时 seq 大(新)者优先
        return a.it->key != b.it->key ? a.it->key > b.it->key
                                      : a.it->seq < b.it->seq;
    };
    std::priority_queue<Cursor, std::vector<Cursor>, decltype(newer)> heap(newer);
    for (auto [i, r] : std::views::enumerate(runs))
        if (!r.empty()) heap.push({r.data(), r.data() + r.size(), static_cast<int>(i)});

    std::vector<Entry> out;
    std::string last_key;
    while (!heap.empty()) {
        Cursor c = heap.top(); heap.pop();
        if (c.it->key != last_key) {          // 同 key 只留第一次弹出的(最新版本)
            last_key = c.it->key;
            out.push_back(*c.it);             // 真实实现:墓碑到达最底层时在此丢弃
        }
        if (++c.it != c.end) heap.push(c);
    }
    return out;
}
```

三个读码要点，直接对应生产系统的成本【事实】：

1. CPU 成本 = O(N log K)：K 是并发归并的 run 数——tiered 的 K 大，CPU 账更重；
2. IO 成本 = 输入全读 + 输出全写：**这就是写放大的物理现场**——归并了多少邻居字节，就放大了多少；
3. 「同 key 留最新、底层丢墓碑」一行,决定了空间什么时候真正回收——[[6.6 LSM-tree 三种放大]] §5 排障清单里「删了数据盘不缩」的答案在这里。

## 2. 两大流派：leveled 与 tiered 各压哪个角

差别只有一个问题【事实】：**一层里允许几份有序 run？**

![Leveled 与 Tiered 两种 compaction 策略对比及背压链：左上 leveled——每层仅一份全局有序 run，新数据下沉时必须与目标层 T 倍体量的重叠数据归并重写，读一层只探一个文件，标注写放大高、读/空间放大低；右上 tiered——每层攒 K 份 run 才整体合并写入下一层，下沉只重写自己，读一层要探 K 份 run，标注写放大低、读/空间放大高；中部为 RocksDB 混合布局——L0 用 tiered 吸收突发、L1 起 leveled 保读延迟；底部为背压水位线——pending compaction 欠账推高 L0 文件数，触发 slowdown 注入写延迟、再触顶 stop 停写，旁注 rate limiter 给后台 IO 限流让路前台读](../../图片/SVG/compaction-leveled与tiered背压链.svg)

| | **leveled** | **tiered**（size-tiered / universal） |
| --- | --- | --- |
| 每层 run 数 | 1 份，全局有序、文件不重叠 | 攒 K 份大小相近的 run 再整体合并 |
| 下沉动作 | 我的文件 + 目标层**所有重叠文件**一起重写 | K 份 run 合并成 1 份写入下层，**不碰下层已有数据** |
| 写放大 | 高:每下沉一层重写 ~T 遍,总 WA ≈ T×层数【量级】 | 低:每字节每层只写一次,总 WA ≈ 层数【量级】 |
| 读放大 | 低：每层最多探 1 个文件 | 高：每层要探 K 份 run |
| 空间放大 | 低（~1 + 1/T）:旧版本存活短 | 高（可达 ~2x）：K 份 run 里旧版本长期并存,合并瞬间还要双份空间【量级】 |
| 适合 | 读多、空间紧、点查延迟敏感 | 写重、摄取型（日志/时序/批量导入） |

两个都不是终点,工业默认是**杂交**【实现】：RocksDB 的 L0 天然是 tiered（memtable 倾倒,文件重叠,先攒着），L1 起 leveled——**用 tiered 的低写放大吸收突发写,用 leveled 的低读放大保住稳态读**。另有极端简化的 FIFO（只按时间淘汰整文件,零归并,WA=1）,适合纯时序、只查近期的负载【实现】。

选型直觉可以压成一句话【实践】：**leveled 是「每次都把房间整理到位」,tiered 是「攒一堆再大扫除」**——前者时刻整洁但每次收纳都要挪动一堆已归位的东西,后者收纳快但找东西要翻好几堆。

## 3. 调度：一条与前台抢盘的后台流水线

策略决定「归并什么」,调度决定「什么时候、用多少资源归并」——生产事故几乎都出在后者【实践】。

把全链画成流水线,每段都是有界缓冲【事实】：

```text
前台写 → [memtable] → flush 线程 → [L0 文件] → compaction 线程池 → [L1..Ln]
              ↑                          ↑                    ↑
         写满即冻结               文件数即水位          pending bytes 即欠账
```

三个调度事实【事实/实现】：

1. **compaction 是欠账驱动的**：每层有目标容量,超出部分就是「欠账」（RocksDB 的 pending compaction bytes）；调度器按欠账优先级挑任务派给线程池。欠账是**领先指标**——它开始爬坡时 stall 还没发生,是最好的告警信号；
2. **背压是二级水位线**：欠账传导到 L0 文件数与 memtable 数,触发 slowdown（对每笔写注入毫秒级延迟）→ stop（停写）。这与 [[6.6 LSM-tree 三种放大]] §3 同一条链,本篇视角是「怎么不触发它」：**长期解只有一个——让 compaction 的消化速率 ≥ 前台写入速率 × WA**。消化不掉时,slowdown 早触发比 stop 晚触发好——平滑的慢优于悬崖式的停【取舍】；
3. **后台 IO 必须限速让路**：compaction 的大块顺序读写与前台读共享同一设备队列（[[1.7 块层与 blk-mq]]）,不限速时前台读排在几 MB 的 compaction 写后面,p99 直接上天（[[9.5 p99 毛刺定位]]）。rate limiter 的两难:限太狠 → 欠账涨 → stall;不限 → 读毛刺【取舍】。这与网络 QoS 的「后台流让路交互流」同构——甚至解法都一样:令牌桶。

C++ 对照一次讲透【事实】：这就是你写过的多级 bounded-queue 流水线——消费者（compaction）吞吐不足时,你面对同样的菜单:加消费者线程（但盘带宽是硬顶）、加大缓冲（欠账更深,只是推迟爆炸）、生产者限流（slowdown）、丢弃(FIFO 策略整文件淘汰)。LSM 没有发明新问题,它只是把这道题从内存搬到了盘上,让每个错误决策都以小时级的欠账偿还周期呈现。

## 4. 删除与墓碑：compaction 的暗账

删除在 LSM 里格外拧巴,值得单独一节【事实】：

- **delete 是写入**：追加一个墓碑,老版本一个字节都没少;
- **墓碑必须沉到最底层才能消失**——中途丢弃会让更深层的旧值「复活」;
- **扫描为墓碑付费**：迭代器要逐个读出并跳过墓碑。删除密集的区间,一次 scan 可能跳过百万墓碑才凑出几行结果——CPU 满、盘不忙、结果空,是墓碑风暴的标准指纹【实践】;
- 大批量删除的正解【实现】:range tombstone（一条记录表达整个区间删除）,或直接按文件淘汰(drop 整个 SSTable/分区),绕开逐 key 墓碑。

## 5. 排障清单：症状 → 判定 → 处置

| 症状 | 先看什么 | 典型根因 | 处置方向 |
| --- | --- | --- | --- |
| 写吞吐锯齿/周期性停顿 | stall 计数、L0 文件数、slowdown/stop 触发日志 | compaction 消化率 < 写入率 × WA | 增 compaction 线程与限速额度;写入侧削峰;根治=降 WA(换 tiered/加大 memtable 攒批) |
| pending compaction bytes 持续爬坡不回落 | 每层欠账分布;compaction 线程利用率;盘带宽余量 | 线程不够(CPU 侧)或 rate limiter 掐太死(IO 侧) | 先分清 CPU 瓶颈还是 IO 瓶颈:线程满载→加线程;盘带宽打满→只能降写入或扩容 |
| 前台读 p99 与 compaction 活跃期同步抖动 | iostat 的队列深度与 await([[9.2 iostat 指标解读]]);compaction IO 速率 | 后台大块 IO 未限速,与前台读争设备队列 | 收紧 rate limiter;compaction 错峰;确认底层盘队列没有被塞满([[1.7 块层与 blk-mq]]) |
| scan 慢、CPU 高、盘闲 | 迭代器 skipped/tombstone 计数 | 墓碑风暴 | range delete 替代逐 key 删;对该区间手动 compaction;业务侧改「按分区整体淘汰」 |
| 磁盘占用周期性尖峰 | 单次 compaction 的输入总字节 | 大 compaction 输入输出并存 | 限制单次 compaction 规模;容量按峰值预留([[6.6 LSM-tree 三种放大]] §5) |
| 导入大批数据后读性能长期未恢复 | 每层 Size 分布是否收敛到金字塔形 | 突发写把层结构冲乱,欠账要按小时级消化 | 导入用 bulk load 直接生成底层 SSTable 绕过 compaction【实现】;或导入后主动 full compaction |

## 6. 陷阱与误区

> [!warning] 常见错误
> 1. **用「加大缓冲」响应 stall**：调高 L0 阈值/加大 memtable 只是把欠账上限调大——爆炸推迟且更猛。先算消化率 ≥ 写入率 × WA 是否成立,不成立什么参数都救不了。
> 2. **关掉/调松 rate limiter 求快**：compaction 确实快了,前台读 p99 替你付账——后台永远要给前台让路,这条不因「欠账着急」而豁免。
> 3. **把 stall 当引擎 bug 绕过**：stall 是背压的最后一级,绕过它(比如无限调高阈值)等于拆掉保险丝,读延迟与恢复时间无界膨胀。
> 4. **对删除密集负载选 leveled 并期待空间立刻回落**:墓碑沉底要穿过每一层,回收有小时级滞后——容量规划要按「删除生效前」的峰值算。
> 5. **基准测试只跑到 compaction 欠账形成之前**：前 10 分钟的成绩是 memtable 和空 L0 的成绩;跑到欠账稳态,吞吐常见腰斩——与 [[3.6 空盘与稳态性能]] 同一教训。
> 6. **忽视 compaction 的 CPU 账**：K 路归并 + 压缩 + CRC,tiered 大 K 时 CPU 可能先于盘成为瓶颈——「盘不忙但欠账涨」时先查线程利用率。

## 7. 关键结论

| 结论 | 性质 |
| --- | --- |
| compaction = 多路归并:同 key 留最新、墓碑沉底才消失;输入全读+输出全写就是写放大的物理现场 | 事实 |
| 流派差异只有一个问题:每层几份 run——leveled(1 份)压读/空间放大,tiered(K 份)压写放大 | 事实 |
| WA 量级:leveled ≈ T×层数,tiered ≈ 层数;工业默认杂交:L0 tiered 吸突发,L1+ leveled 保读 | 量级/实现 |
| 调度三要素:欠账驱动(pending bytes 是领先指标)、二级水位线背压、后台 IO 限速让路 | 事实/实现 |
| 稳态成立条件只有一条:compaction 消化率 ≥ 写入率 × WA;不成立时任何参数都只是推迟爆炸 | 事实 |
| 与 C++ 多级有界队列流水线同构:加消费者/加缓冲/限流/丢弃,同一张决策菜单 | 实践结论 |
| 删除是写入,墓碑要沉底;扫描为墓碑付费——大批删除用 range tombstone 或整文件淘汰 | 事实/实现 |
| 基准必须跑到欠账稳态;容量必须按 compaction 峰值并存预留 | 实践结论 |
