# Bloom Filter 与 Block Cache

> [[6.6 LSM-tree 三种放大]] 讲清了 LSM 的账：用读放大换写放大——一次点查最坏要探 memtable、每个 L0 文件、再加每层一个文件，十几次探测里每次都可能是一趟盘 IO。[[6.9 RocksDB 关键路径]] §3 提到文件内有「三道闸」挡在盘前面，本篇把其中两大主力拆开讲透：**bloom filter** 治「不在」——用一次几百纳秒的内存查询，替读请求回答「这个 key 肯定不在这个文件里」，把绝大多数无谓探测挡在用户态；**block cache** 治「在」——把解压后的热数据块留在内存，让真正要读的数据不必次次下盘。两件武器的分工可以一句话记住：**bloom 决定要不要去盘上找，cache 决定去了之后快不快**。理解它们，也就理解了一次读请求在「应用 → 引擎 → 内核 → 硬件」四层之间的完整流转：每一层是一道闸，每往下穿一道，延迟涨一到两个数量级。

前置：[[6.6 LSM-tree 三种放大]]（为什么读放大是 LSM 必须治理的病）、[[6.9 RocksDB 关键路径]]（这两道闸在整条读路径中的位置）、[[1.2 Page Cache 命中与未命中]]（第三道闸——内核页缓存的机制）。

## 1. 问题定标：一次点查 miss 有多贵

先量化「不治理会怎样」。SST 文件内部按块组织【实现】（RocksDB 的 BlockBasedTable）：数据切成 **data block**（目标大小默认 4 KiB，落盘前通常压缩），另有 **index block**（记每个 data block 的 key 范围，用于定位）和 **filter block**（bloom filter 本体）。没有任何缓存和过滤时，在一个 SST 里找一个 key 至少要：读 index block（一趟盘 IO）→ 二分定位 → 读 data block（又一趟盘 IO）→ 解压 → 块内找 key。

把这个成本乘上探测次数【事实】：查一个**不存在**的 key（点查 miss——缓存系统「先查库再回填」模式下的常态流量），要把 memtable、所有 L0 文件、L1 以下每层一个文件全探一遍才能死心。假设 L0 有 6 个文件、共 6 层，就是十几次探测、最坏几十趟盘 IO——每趟 NVMe 上约百 μs 量级（[[0.7 性能指标 IOPS 带宽 延迟 P99]]），机械盘上是 ms 级。**一次业务查询几毫秒全花在证明「这个 key 不存在」上**，这就是要治理的对象。

两件武器在端到端路径中的位置先钉住【事实】：bloom filter 和 block cache 都是**引擎在用户态自己实现的机制**，工作在 VFS 之上——它们的全部使命，就是让读请求根本不发起系统调用。

## 2. Bloom Filter：用 1% 的谎换 99% 的盘 IO

### 2.1 原理：一个只会说「不在」的证人

Bloom filter 是一种**概率型集合成员测试**结构【事实】。构造与查询都极简单：

- 一个 m 位的位数组，初始全 0；k 个独立哈希函数；
- **插入** key：算 k 个哈希值，把对应的 k 个位全置 1；
- **查询** key：算同样 k 个哈希，检查 k 个位——**只要有一个是 0，key 肯定没插入过**（插入时必然会置 1）；**全是 1，则 key 可能在**——也可能是别的 key 恰好把这几位都置过 1。

所以它的回答不对称【事实】：说「不在」绝对可靠（**无假阴性**）；说「在」只是「可能在」（**有假阳性**）。假阳率由参数决定：

$$
p \approx \left(1 - e^{-kn/m}\right)^{k}, \qquad k_{\text{opt}} = \frac{m}{n}\ln 2
$$

其中 n 是插入的 key 数，m/n 就是常说的 **bits per key**。工程上记两个锚点就够【实现】：**10 bits/key（k≈7）→ 假阳率约 1%**；再往上边际收益递减（加到 16 bits/key 也只是降到 0.1% 量级），RocksDB 默认推荐值就是 10。

一个直觉例子：把 1000 个用户名插入 10000 位的过滤器。查一个从没插过的名字，它有约 99% 的概率直接回答「肯定不在」——代价只是 7 次哈希和 7 次位读取，纯 CPU、纯内存、几百纳秒。

### 2.2 为什么 bloom 和 LSM 是天作之合

Bloom filter 有个著名短板：**不支持删除**（把位清 0 会误伤共享这些位的其他 key）。但在 LSM 里这个短板不存在【事实】：SST 文件**不可变**（[[6.11 MemTable Immutable 与 SST 生命周期]]），flush/compaction 生成文件时对文件里的全部 key 一次性建好 filter，存进 filter block，从此不增不删不改——文件死了 filter 跟着一起火化。**不可变文件 + 一次性构建**，恰好绕开了 bloom 的所有弱点。

使用侧【实现】：filter block 随文件打开加载后常驻内存（或放进 block cache，见 §5），每次探测一个 SST 前先问它——「肯定不在」则整个文件跳过，index block 和 data block 一个字节都不用碰。对照 §1 的账：L0 的 6 次探测里，bloom 把其中 5.94 次变成了纯内存操作。

### 2.3 边界：bloom 管不了的流量

三类流量 bloom 无能为力，判断一个负载「值不值得配 bloom」就看这三条【事实/取舍】：

1. **范围扫描**：`Seek(start)` + `Next()` 问的是「这个区间里有什么」，没有具体 key 可哈希——bloom 完全失效（前缀场景可用 prefix bloom 折中：对 key 前缀建 filter，能挡掉「该前缀不在此文件」的探测【实现】）;
2. **查的 key 大多真实存在**：bloom 只在「不在」时省钱；命中流量该读的盘一次不少;
3. **假阳性的那 1%**：穿透后照常走完 index + data block 的全套流程，白花一趟盘 IO——1% 听着小，乘上百万 QPS 就是每秒一万次无谓 IO，容量规划要把它算进去。

## 3. Block Cache：把热块留在解压后的内存

### 3.1 定义与结构

**Block cache 是引擎在用户态自管的数据块缓存**【实现】：缓存单位不是 key-value，而是整个**解压后的 data block**。RocksDB 的默认实现是分片 LRU（LRUCache）：

- **为什么缓存块而不是 kv**：SST 按块读盘（读一个 key 至少读回整块），块级缓存天然利用局部性——相邻 key 大概率同块；且块是不可变文件的切片，缓存失效规则简单（文件作废块随之作废）；
- **为什么分片（shard）**：这是多线程的老问题——一把大锁保护整个 LRU 链表，高并发下锁争用会把「纳秒级命中」拖成「微秒级排队」。按 key 哈希分成若干 shard（2 的幂个），每片独立加锁，争用摊薄。**shard 锁是读路径上第一个真正的等待点**：命中很快，但热点 shard 上多线程会排队【实现】；
- **容量显式可控**：这是它与页缓存最大的差别——引擎能精确决定「花多少内存、缓存什么、pin 住什么」。默认值只有数十 MiB 量级（版本相关），生产必须按负载显式配置【实现】。

### 3.2 两级缓存：block cache 与页缓存的分工

关键认知：**block cache 不是唯一的缓存，它下面还垫着内核的页缓存**。默认 buffered IO 下（[[1.3 Buffered IO 与 O_DIRECT]]），一次点查命中某个 SST 的完整穿闸顺序是【事实】：

![[图片/SVG/8_6_13_1.svg|900]]

逐闸把**等待点**和**数据拷贝**报清楚（这就是一次读请求在四层之间的流转）【事实】：

1. **bloom filter**（用户态，~百 ns）：纯 CPU，无拷贝，无等待；
2. **block cache**（用户态，~μs）：shard 锁可能排队；命中**零额外拷贝**——返回的是指向缓存块的引用（带引用计数，块在使用期间不会被逐出），块内二分找 key 即毕；
3. **页缓存**（内核，~十 μs）：block cache miss 后引擎发起 `pread` 读压缩块——**系统调用陷入内核**，第一个真正的模式切换。页缓存命中则**CPU 拷贝一次**（页缓存 → 用户缓冲区），回到用户态后**解压一次**（又一次读写整块的 CPU 操作），装入 block cache；
4. **盘**（硬件，~百 μs NVMe）：页缓存也 miss，线程**睡眠等待**——让出 CPU、两次上下文切换，设备用 **DMA** 把数据搬进页缓存（不占 CPU，[[1.8 一次 read write 全路径图]]），中断唤醒后继续第 3 步的拷贝与解压。

所以一次「双 miss」的读 = 1 次 DMA + 1 次 CPU 拷贝 + 1 次解压 + 1 次睡眠等待；而设计良好的热点读 = 0 次系统调用、0 次拷贝。**读延迟优化的全部内容，就是让探测停在越早的闸口**。

两级缓存的内容不同构成了一对取舍【取舍】：

| | block cache（引擎） | 页缓存（内核） |
| --- | --- | --- |
| 存什么 | **解压后**的块 | **压缩后**的文件页 |
| 命中代价 | 最低（免解压） | 要 1 次拷贝 + 1 次解压 |
| 内存密度 | 低（同样数据占更多内存） | 高（压缩形态） |
| 可控性 | 精确（容量/优先级/pin） | 只能 `fadvise` 施加影响（[[1.6 readahead 与 posix_fadvise]]） |

同一个块可能**两级各驻留一份**（解压版在 block cache、压缩版在页缓存）——内存被重复占用。容量规划必须把两级加在一起算；激进方案是 `O_DIRECT` 绕过页缓存 + 把省下的内存全给 block cache，只留一级（[[6.9 RocksDB 关键路径]] §3）【实现】。

### 3.3 index/filter block 也要排队

容易忽略的一点【实现】：index block 和 filter block 本身也是块，也要有地方住。RocksDB 提供两种方式——住在堆里由 `max_open_files` 间接管理（默认），或 `cache_index_and_filter_blocks=true` 让它们进 block cache 统一记账。后者内存账更诚实，但引入新风险：**index/filter 被普通数据块挤出去**后，下一次探测该文件要先下盘把 filter 读回来——「为了判断要不要读盘，先读一次盘」，p99 直接起飞。所以配套开关是把它们放进**高优先级池**并 pin 住 L0 的（`pin_l0_filter_and_index_blocks_in_cache`）【实现】。

## 4. 对 p99 的影响：缓存是尾延迟机器

平均延迟看命中率，尾延迟看 miss 的分布【事实】。几个典型的「平均很好、p99 很差」模式：

1. **compaction 换文件引发的 miss 突刺**：block cache 按「文件 + 块偏移」索引，compaction 把热数据从旧文件搬进新文件后，旧文件的缓存块全部作废——**数据还是那些数据，缓存却冷了**，直到读流量把新文件的块重新填热。表现为每轮 compaction 完成后 p99 周期性抬头（[[9.5 p99 毛刺定位]] 的经典指纹之一）【实践】；
2. **扫描污染**：一次大范围 scan 把海量一次性块灌进 cache，把真正的热点块挤出去。对策：scan 用 `ReadOptions::fill_cache=false`，读了不回填【实现】；
3. **冷启动**：重启后两级缓存全空（页缓存还可能被别的进程占着），恢复期每个读都是 §3.2 的全程穿闸——预热完成前 SLO 是另一套曲线【实践】。

## 5. Modern C++：手写一个 bloom filter

把 §2.1 落成能编译、能测假阳率的最小实现。用 double hashing 从两个哈希值合成 k 个（工程标准做法，省去维护 k 个独立哈希函数）【实现】：

```cpp
#include <cstdint>
#include <functional>
#include <print>
#include <string>
#include <string_view>
#include <vector>

class BloomFilter {
public:
    // bits_per_key=10, k=7 → 假阳率约 1%
    BloomFilter(std::size_t expected_keys, std::size_t bits_per_key = 10)
        : nbits_(std::max<std::size_t>(64, expected_keys * bits_per_key)),
          k_(static_cast<std::size_t>(bits_per_key * 0.69) | 1),   // ≈ ln2 · m/n
          bits_(nbits_ / 64 + 1) {}

    void add(std::string_view key) {
        auto [h1, h2] = hash2(key);
        for (std::size_t i = 0; i < k_; ++i) {
            std::size_t bit = (h1 + i * h2) % nbits_;      // double hashing
            bits_[bit / 64] |= 1ULL << (bit % 64);
        }
    }

    [[nodiscard]] bool may_contain(std::string_view key) const {
        auto [h1, h2] = hash2(key);
        for (std::size_t i = 0; i < k_; ++i) {
            std::size_t bit = (h1 + i * h2) % nbits_;
            if (!(bits_[bit / 64] & 1ULL << (bit % 64))) return false;  // 肯定不在
        }
        return true;                                        // 可能在
    }

private:
    static std::pair<std::uint64_t, std::uint64_t> hash2(std::string_view key) {
        std::uint64_t h = std::hash<std::string_view>{}(key);
        return {h, h * 0x9E3779B97F4A7C15ULL | 1};          // 演示用；生产用独立哈希
    }

    std::size_t nbits_, k_;
    std::vector<std::uint64_t> bits_;
};

int main() {
    constexpr int n = 100'000;
    BloomFilter bf(n);
    for (int i = 0; i < n; ++i) bf.add("key-" + std::to_string(i));

    int false_positive = 0;
    for (int i = n; i < 2 * n; ++i)                         // 全是没插过的 key
        if (bf.may_contain("key-" + std::to_string(i))) ++false_positive;
    std::println("false positive rate = {:.2f}%", 100.0 * false_positive / n);
}   // 预期输出 ≈ 1%
```

RocksDB 侧只需两行配置就能启用同款机制【实现】：

```cpp
rocksdb::BlockBasedTableOptions t;
t.filter_policy.reset(rocksdb::NewBloomFilterPolicy(10.0));      // 10 bits/key
t.block_cache = rocksdb::NewLRUCache(8ULL << 30);                // 8 GiB block cache
opt.table_factory.reset(rocksdb::NewBlockBasedTableFactory(t));
```

## 6. 观测与对照实验

引擎把两道闸的效果都记了账【实现】：

```bash
# bloom 的战果：挡掉了多少次探测（应用内读 statistics）
#   rocksdb.bloom.filter.useful      —— 「肯定不在」生效次数
# block cache 的命中账：
#   rocksdb.block.cache.hit / miss   —— 命中率 = hit / (hit+miss)
# 当前内存占用：
#   db->GetProperty("rocksdb.block-cache-usage", &v);

# 系统侧交叉验证：引擎侧 miss 应与盘上随机读对得上
iostat -x 5        # r/s 高而 rMB/s 低 = 典型的小块随机读（cache miss 流量）
```

一组对照实验（变量只动一个）【实践】：用 `db_bench` 灌数据后跑 `readrandom`，查询集偏向不存在的 key——

- `-bloom_bits=10` vs `-bloom_bits=0`：关掉 bloom 后 `iostat` 的 r/s 应上涨一个量级、QPS 相应崩塌——直接量出 §2 的价值；
- 固定 bloom，把 block cache 从 64 MiB 调到数 GiB：命中率与 p50 改善，但注意观察**总内存**（RSS + 页缓存）——验证 §3.2 的两级记账。

## 7. 陷阱与误区

> [!warning] 常见错误
> 1. **给纯 scan 负载配 bloom**：范围扫描不查具体 key，filter 一次都用不上，白花每文件 10 bits/key 的内存（§2.3）——先分析负载再配武器。
> 2. **bits/key 盲目加大**：10 → 1%，再往上是指数递减的收益换线性增长的内存；点查 miss 流量不大时，这些内存给 block cache 收益高得多。
> 3. **只算 block cache、忘了页缓存**：机器内存 = memtable + block cache + 页缓存 + 进程其他开销;把 block cache 配到机器内存边缘,页缓存被挤没,所有 block cache miss 都直接砸盘——命中率没变,miss 代价翻了一个量级。
> 4. **index/filter 进 cache 却不 pin**：热点数据把 filter 挤出去,出现「为了免一次 IO,先多一次 IO」的倒挂,p99 无规律尖刺（§3.3）。
> 5. **把 compaction 后的 p99 尖刺当成盘故障**：那是缓存按文件失效的机制性抖动（§4）,指纹是尖刺与 compaction 完成时刻对齐——先对时间线,再怀疑硬件。
> 6. **用命中率平均值做容量结论**：99% 命中率下,如果 miss 集中在同一类请求(比如全走盘的冷分区),那类请求的 p99 就是纯盘延迟——看分布,别看均值。

## 8. 关键结论

| 结论 | 性质 |
| --- | --- |
| 点查 miss 是读放大的最坏情况：每层都要探到底才能证明「不存在」——这是 bloom 要治的病 | 事实 |
| bloom 无假阴性、有假阳性：10 bits/key ≈ 1% 假阳率，一次几百 ns 的内存查询换一趟盘 IO | 事实 |
| SST 不可变 + 构建一次性，恰好绕开 bloom 不支持删除的短板——LSM 与 bloom 天然契合 | 事实 |
| bloom 对范围扫描无效、对「key 大多存在」的流量无收益——配置前先看负载形状 | 事实/取舍 |
| block cache 缓存解压后的块，分片 LRU；shard 锁是命中路径上的第一个等待点 | 实现 |
| 读路径四道闸的延迟阶梯：百 ns（bloom）→ μs（block cache）→ 十 μs + 拷贝解压（页缓存）→ 百 μs + 睡眠（盘）；优化 = 让探测止步更早 | 事实 |
| 两级缓存内容不同：解压块 vs 压缩块，同一数据可能两份驻留——容量规划两级合并算 | 事实/取舍 |
| 缓存是尾延迟机器：compaction 换文件、scan 污染、冷启动都以 p99 尖刺形式暴露 | 实践结论 |
