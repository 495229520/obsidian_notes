# LSM-tree 三种放大

> [[6.1 WAL 与 Crash Consistency]] 末尾埋了一句账：WAL 提升小写吞吐，「代价是读放大/空间由别的机制收拾」。本篇兑现这句话。[[6.5 Bitcask 模型]] 把「日志即数据库」推到极致——写永远是顺序追加，快得没道理；但日志会无限膨胀、读要靠全量内存索引。LSM-tree（Log-Structured Merge-tree）是这条路线的完全体：**把日志切成一段段排好序的不可变文件，分层摆放，后台不断归并**。它没有消灭「原地更新做不到的事」的成本，而是把成本改名成三种「放大」分期偿还——写放大、读放大、空间放大。本篇先把结构立起来，再给三种放大逐个记账，最后落到一份能上手的排障清单：当引擎变慢时，先判断是哪种放大在收账。

前置：[[6.1 WAL 与 Crash Consistency]]（memtable 崩溃安全的地基）、[[6.5 Bitcask 模型]]（日志即数据库的前身）、[[1.2 Page Cache 命中与未命中]]（读放大的「次数」贵不贵取决于它）、[[3.5 GC 写放大与 Over-Provisioning]]（设备内部还有一层放大，两层相乘）。

## 1. 结构五分钟：LSM 是「排好序的日志」的堆叠

一条写入的一生【事实】：

1. **WAL 追加 + fdatasync**——崩溃安全由 [[6.1 WAL 与 Crash Consistency]] 的协议保证；
2. 写进内存的 **memtable**（有序结构，典型实现是并发跳表【实现】）——到这里就向客户端确认了，**写路径没有任何盘上随机写**；
3. memtable 写满（RocksDB 默认 64 MiB【实现】）→ 整体冻结为 immutable memtable，后台**顺序刷盘**成一个 **SSTable**（Sorted String Table：按 key 排序的不可变文件，自带块索引与 bloom filter）；
4. 新 SSTable 落在 **L0** 层；后台 **compaction** 线程把低层文件与高层文件**归并重写**，逐层下沉：L1、L2……每层容量约是上一层的 T 倍（放大系数/fanout，默认 T≈10【实现】），最底层存着绝大部分数据。

两条铁律撑起整个设计【事实】：

- **盘上文件不可变**：更新 = 追加新版本，删除 = 追加墓碑（tombstone）——同一个 key 的多个版本可能同时躺在 memtable、L0、L3 里，**新层永远压过旧层**；
- **L0 特殊**：它是 memtable 的直接倾倒区，文件之间 key 范围互相重叠；L1 起每层内部全局有序、文件互不重叠——查一层只需定位一个文件。

给 C++ 工程师的一句话定位【事实】：LSM 把「共享可变的大结构 + 细粒度锁」问题改写成了「**单写者顺序追加 + 不可变快照共享**」——SSTable 之于 LSM，就像 `shared_ptr<const T>` 快照之于并发程序：不可变，所以读端无锁、随便共享；代价是「修改」变成了「重建一份新的」，而重建的成本就是本篇的主角。

## 2. 三种放大：同一笔债的三种还法

「放大（amplification）」都定义成比值【事实】：

![LSM-tree 结构与三种放大全景：中央为写路径——WAL 追加、memtable、冻结刷盘为 L0 SSTable、逐层 compaction 归并下沉到 L1/L2，写路径旁标注同一字节被反复重写的位置构成写放大；左侧读路径自上而下探测 memtable、L0 各文件、L1、L2，每层一次探测构成读放大，标注 bloom filter 与 block cache 两道减免；右侧同一 key 的多个旧版本与墓碑分布在各层尚未回收，构成空间放大；底部为放大三角——三者不可同时最优，compaction 策略是分配旋钮](../../图片/SVG/lsm-三种放大全景.svg)

### 2.1 写放大（Write Amplification, WA）

$$
WA = \frac{W_{disk}}{W_{user}}
$$

即：盘上实际写入字节 ÷ 用户逻辑写入字节。

同一个字节的用户数据会被写多少遍【事实】：WAL 一遍 + flush 成 L0 一遍 + **每下沉一层，被 compaction 连同邻居重写约 T 遍**（要与目标层 T 倍体量的重叠数据归并）。层数 L 的 leveled compaction 粗账：

$$
WA \approx 2 + T \times (L - 1)
$$

T=10、4~5 层时 WA 落在 **10~30 的量级**【量级】。后果有两层：

- **带宽账**：盘的写带宽被 compaction 吃掉 WA 分之（WA−1）——业务写 100 MB/s，盘上可能真跑 2 GB/s；
- **寿命账**：这还只是应用层。SSD 内部 FTL 的 GC 还有一层设备级 WAF（[[3.5 GC 写放大与 Over-Provisioning]]），**两层相乘**才是闪存的真实磨损【事实】。好消息是 LSM 的写全是大块顺序写，恰好是让设备级 WAF 趋近 1 的访问模式（[[3.4 SSD FTL 与地址映射]]）——两层放大之间存在互补，这是 LSM 与 SSD 天生一对的原因。

### 2.2 读放大（Read Amplification, RA）

$$
RA = N_{probe}
$$

即：一次逻辑读需要探测的结构数。

点查一个 key，最坏要按新→旧探测：memtable → immutable memtable → **L0 的每一个文件**（重叠，无法跳过）→ L1 一个文件 → …… → 最底层一个文件【事实】。两道减免【实现】：

- **bloom filter**：每文件一个，~10 bits/key 时假阳性率 ~1%【量级】——把「key 不在此文件」的探测从一次读 IO 降为一次内存查询。**只救点查，救不了范围扫描**——scan 必须对每层真正开迭代器做多路归并；
- **block cache / page cache**：探测次数不等于盘 IO 次数，命中缓存的探测是纳秒级（[[1.2 Page Cache 命中与未命中]]）。RA 的疼痛程度 = 探测次数 × 缓存未命中率——同一个 RA，缓存冷热能差出两个数量级。

### 2.3 空间放大（Space Amplification, SA）

$$
SA = \frac{S_{disk}}{S_{logical}}
$$

即：盘上实际占用 ÷ 逻辑数据量。

来源就是「不可变 + 追加」的直接后果【事实】：被新版本覆盖的旧值、已删除但墓碑还没沉到底层的 key，都在等 compaction 回收。leveled 下大头数据在最底层，SA 温和（~1.1x 量级）；tiered 下同层多份 run 并存，SA 可以摸到 2x（[[6.7 Compaction 策略]]）【量级】。另有一笔临时账：一次大 compaction 进行中，输入文件与输出文件短暂并存——**磁盘要留出这笔峰值余量，否则满盘时 compaction 自己先写不动**，陷入「越满越删不掉」的死锁【实践】。

### 2.4 三角关系：不可同时最优

三种放大互相顶着【事实/设计空间结论】：压 WA（少归并）→ run 变多 → RA、SA 上升；压 RA（勤归并成单份有序）→ 重写变多 → WA 上升；压 SA（激进回收）→ 同样多写。**compaction 策略就是在三角里挑位置的旋钮**——具体怎么挑是 [[6.7 Compaction 策略]] 的主题。这与多线程程序里「吞吐-延迟-内存占用」的三角同构：你可以移动痛点，不能消灭它。

## 3. 背压：写太快时，LSM 怎么让你慢下来

放大不是静态账本，它有一条动态的**背压链**【事实/实现】：

```text
用户写 → memtable 满? → immutable memtable 攒太多? → L0 文件数超阈值? → compaction 欠账太多?
              ↓（任一环节积压）
        slowdown（人为给每笔写注入延迟）→ stop（写入完全暂停，即 write stall）
```

机制与 C++ 有界队列的 `try_push` 满员完全同构：LSM 是一条**多级流水线**（memtable → flush → L0 → compaction），每级都是有界缓冲；下游（compaction 的盘带宽）跟不上时，压力逐级回传，最终由引擎**主动掐住前台写**——RocksDB 的 slowdown/stop 双阈值（L0 默认 20 个文件减速、36 个停写【实现】）就是两级水位线。没有这个机制会怎样：L0 无限堆积 → RA 无限涨 → 读先死——**stall 不是 bug，是引擎在保护读延迟**【事实】。但对上层应用，stall 表现为写延迟从 μs 突跳到秒级的毛刺——p99 排查绕不开它（[[9.5 p99 毛刺定位]]）。

一并想清楚 OS 层的资源竞争【事实】：compaction 的大块读写与前台读走**同一个设备队列**（[[1.7 块层与 blk-mq]]），不限速的 compaction 会把前台读的 p99 顶上天。所以工业引擎都带 rate limiter 给后台 IO 限流【实现】——这与网络里「后台流量让路前台流量」的流控是同一件事。

## 4. 把三种放大量出来

放大是可测量的，不是玄学【实践】：

```bash
# 写放大：盘上真实写速率 ÷ 业务逻辑写速率
iostat -x 5              # 看数据盘的 wMB/s（9.2）
# 与应用侧统计的逻辑写入字节对比；RocksDB 直接给现成账本：
# DB::GetProperty("rocksdb.stats") 里的 Cumulative WAL/Flush/Compact 写字节

# 读放大：探测次数与缓存命中
# rocksdb.stats 的 block cache hit/miss、每层 read 计数
# 系统侧交叉验证：业务 QPS 不变但盘上 r/s 上涨 = RA 恶化或缓存变冷

# 空间放大：盘占用 ÷ 逻辑量
du -s <db_dir>           # 对比估算的 key×value 逻辑量
# rocksdb.stats 每层 Size 列：底层占比越低，SA 越差
```

## 5. 排障清单：症状 → 判定 → 处置

| 症状 | 先看什么 | 典型根因 | 处置方向 |
| --- | --- | --- | --- |
| 写延迟周期性突跳到 ms/秒级，吞吐锯齿 | 引擎 stall 计数器、L0 文件数、pending compaction bytes | 背压链触顶：compaction 追不上写入 | 加大 compaction 并发/带宽；提高 slowdown 阈值只是把毛刺换成更狠的 stop【取舍】；根治靠降 WA（[[6.7 Compaction 策略]]） |
| 盘写带宽远大于业务写入（几倍到几十倍） | iostat wMB/s ÷ 业务字节速率 | 写放大过高：层数多/放大系数不当/value 大 | 换 tiered 类策略、key-value 分离（大 value 单独存）、确认 WAL 与数据是否重复刷 |
| 点查 p99 缓慢爬升，QPS 没变 | L0 文件数、bloom 假阳率、block cache 命中率 | L0 堆积（每个文件都要探测）或缓存变冷 | 催 compaction 清 L0；bloom bits 加大；查缓存是否被 scan 污染 |
| 范围扫描慢且 CPU 高、盘不忙 | 迭代器统计里 skipped keys / tombstone 数 | 扫描区间堆满墓碑：删除只是写墓碑，扫描要逐个跳过 | 对删除密集区间手动触发 compaction；用 range delete 代替逐 key 删【实现】 |
| 删了大量数据，盘占用不降 | 每层 Size 分布、墓碑所在层 | 墓碑没沉底：只有到最底层墓碑才能真正消失 | 等待/手动 full compaction；确认没有长事务快照钉住旧版本 |
| 磁盘快满时性能雪崩 | 剩余空间 vs 最大单次 compaction 峰值需求 | compaction 需要输入输出并存的临时空间 | 永远给 LSM 盘留峰值余量；满盘前告警而不是满盘后处理【实践】 |

排查心法【实践】：**先分清是哪种放大在收账**——写带宽异常查 WA，读延迟异常查 RA，容量异常查 SA；三者的仪表盘互相独立，混在一起看只会得出「引擎变慢了」这种无法行动的结论。

## 6. 陷阱与误区

> [!warning] 常见错误
> 1. **「LSM 写快」理解成「写便宜」**：前台写路径快（顺序追加），总成本没降——盘上每字节要被重写 WA 遍，账单由后台带宽与闪存寿命支付。
> 2. **把 delete 当释放空间**：delete 是一次写入（墓碑）；空间要等墓碑沉到最底层才回收，删除风暴反而让盘占用先涨后跌。
> 3. **忽略 L0 的特殊性**：L0 文件互相重叠，是读放大的最大变量；「L0 文件数」是 LSM 最值得盯的单一指标之一。
> 4. **测试用空库跑读写**：层没长起来、compaction 没欠账，放大全部不在位——LSM 必须灌到稳态再测（与 [[3.6 空盘与稳态性能]] 的 SSD 稳态是同一层教训的两个楼层）。
> 5. **只调参不记账**：每个旋钮都在三角里挪位置——调之前先测三个放大的基线，否则「优化」只是把没在监控上的那个放大调爆了。
> 6. **忘了设备还有一层放大**：应用 WA × 设备 WAF 才是闪存真实磨损；顺序大块写是把第二层压到 1 的关键（[[3.5 GC 写放大与 Over-Provisioning]]）。

## 7. 关键结论

| 结论 | 性质 |
| --- | --- |
| LSM = 排好序的不可变日志段分层归并：更新即追加、删除即墓碑、新层压旧层 | 事实 |
| 不可变换来的并发红利：读端共享快照无锁（≈ shared_ptr<const> 快照），写端单写者顺序追加 | 事实 |
| 写放大 ≈ 2 + T×(L−1)，量级 10~30；与 SSD 内部 WAF 两层相乘才是真实磨损，但顺序写恰好把设备层压到 ~1 | 事实/量级 |
| 读放大 = 按新→旧逐结构探测，L0 逐文件；bloom 救点查不救扫描，缓存决定探测的单价 | 事实 |
| 空间放大 = 旧版本 + 未沉底的墓碑；compaction 还需要输入输出并存的峰值余量 | 事实 |
| 三种放大不可同时最优；compaction 策略是三角里的位置旋钮 | 设计空间结论 |
| write stall 是逐级回传的显式背压（≈ 有界队列 try_push 满员），保护的是读延迟；slowdown/stop 是两级水位线 | 事实 |
| 排障先分账:写带宽异常→WA、读延迟异常→RA、容量异常→SA，三块仪表盘独立 | 实践结论 |
