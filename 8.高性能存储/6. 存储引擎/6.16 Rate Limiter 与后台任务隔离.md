# Rate Limiter 与后台任务资源隔离

> LSM 引擎的日常：前台线程在写几 KB 的 WAL，后台线程在搬几百 MB 的 compaction。盘只有一块，队列是共享的——不加管制，后台的大块 IO 会把前台的小 IO 压在队尾，p99 直接起飞。Rate Limiter 给后台流量套一只令牌桶，本质是让后台线程在资源不足时睡到 condition_variable 上——一次教科书级的自我背压。本篇从"共享队列为什么放大延迟"讲起，走到令牌桶实现、线程池优先级、内核 QoS 的边界，最后回答一个反直觉的问题：限太紧和限太松，为什么殊途同归都打到前台延迟。

前置：[[6.14 Write Stall]]（限太紧的下场）、[[6.7 Compaction 策略]]（后台流量从哪来）。

---

## 1. 背景：谁在抢盘

先把三类流量讲清楚（没学过存储也能看懂的版本）：

- **前台 IO**：用户线程发起、别人正在等结果的 IO。写路径上是 WAL 追加（每次 KB 级，常带 fsync）；读路径上是缓存未命中后的 SST 读（4KB～几十 KB）。
- **Flush**：内存写缓冲（MemTable）满了之后，后台线程把它整体写成一个磁盘文件（SST）——一次几十 MB 的顺序写。见 [[6.11 MemTable Immutable 与 SST 生命周期]]。
- **Compaction**：后台线程持续地把多层 SST 读进来、归并去重、再写出去。它的总流量常是用户写入量的几倍到几十倍（写放大，[[6.6 LSM-tree 三种放大]]）。

| 流量 | 发起者 | 单次大小 | 延迟敏感度 |
| --- | --- | --- | --- |
| WAL 写 / 读未命中 | 用户线程 | KB 级 | **极敏感**：直接坐在请求的关键路径上 |
| Flush | 后台 HIGH 线程池 | 几十 MB | 中：拖久了 MemTable 释放不掉 → write stall |
| Compaction | 后台 LOW 线程池 | GB 级、持续 | 低：慢点没关系，但长期落后会积债 |

矛盾一句话：**延迟最敏感的流量最小，量最大的流量最不敏感，而它们共享同一个设备。**

## 2. 队列视角：延迟 = 排队 + 服务

用 C++ 的直觉建模。想象一个单 worker 的线程池，任务队列里混着 1ms 的小任务和 500ms 的大任务：小任务自己只要 1ms，但排在一个大任务后面就是 501ms——**队头阻塞（head-of-line blocking）**。你的第一反应一定是"长短任务分池"，这个直觉完全正确，且正是本篇全部内容的纲领。

盘就是那个 worker。一个 IO 从引擎出发要排的队：内核块层（blk-mq）→ NVMe 提交队列 → 设备内部调度。前台的 4KB 读排在几十条 compaction 的 1MB 写后面时，它的延迟由队里那些写决定，与它自己的"服务时间"无关。**【量级】** NVMe 上 4KB 读空载约百 μs 量级；被大块写队列压住时可以到 ms 级——一个数量级以上的差距。SSD 还有第二重放大：大量写会触发盘内 GC，进一步抬高读延迟（介质背景见 [[3.4 SSD FTL 与地址映射]]）。

由此得出限速器的位置选择【事实】：**必须在 IO 进入队列之前拦截**。一旦 IO 已经下发，没有任何机制能把它从队列里撤回来。所以 Rate Limiter 长在存储引擎的用户态代码里——发 IO 之前先"申请配额"——而不是寄希望于内核事后调度。

## 3. Rate Limiter：一只令牌桶 + 一个条件变量

**令牌桶（token bucket）**：桶里装的是"本周期允许写的字节数"，按固定速率补充；要写盘先取令牌，不够就睡，等下个周期。它限制的是**平均速率**，同时允许周期内的小突发。

RocksDB 的 `GenericRateLimiter` 就是这个模型【实现】：

- 创建：`NewGenericRateLimiter(bytes_per_second, refill_period_us /*默认 100ms*/, fairness /*默认 10*/)`；
- 后台线程每次写文件前调用 `Request(bytes, priority)`：配额够就扣掉直接走；不够就把自己挂进等待队列，**睡在条件变量上**；
- 每个 refill 周期补一次配额，按序唤醒等待者；
- 两级优先级：Flush 走 `IO_HIGH`，compaction 走 `IO_LOW`。HIGH 优先放行，但 LOW 有约 1/fairness 的概率插队——防止 compaction 被彻底饿死（饿死的代价见第 7 节）；
- **WAL 等前台写不经过它**【事实】：默认模式只对后台流量收费。前台的限速是另一套机制（write stall，[[6.14 Write Stall]]），两者分工明确：rate limiter 管后台"别抢"，write stall 管前台"别灌"。

它只管引擎自己发出的字节——对同盘其他进程、对内核页缓存的回写都无感知。这个"只管自己"的边界在第 6 节展开。

## 4. Modern C++：令牌桶的最小实现

把"背压"三个字落成 40 行代码——你会发现它和"有界队列满了阻塞生产者"是同一个东西：

```cpp
#include <algorithm>
#include <chrono>
#include <condition_variable>
#include <cstdint>
#include <mutex>

// 教学版令牌桶：单优先级。后台线程写盘前调用 request(bytes)。
class TokenBucketLimiter {
public:
    TokenBucketLimiter(int64_t bytes_per_sec, std::chrono::milliseconds refill_period)
        : period_(refill_period),
          quota_per_period_(bytes_per_sec * refill_period.count() / 1000),
          available_(quota_per_period_),
          next_refill_(std::chrono::steady_clock::now() + period_) {}

    // 背压的全部秘密：资源不足时，生产者睡在条件变量上
    void request(int64_t bytes) {
        // 单次申请不得超过一个周期的配额，否则永远等不满（真实实现按此拆分大 IO）
        bytes = std::min(bytes, quota_per_period_);
        std::unique_lock lk(mu_);
        refill_locked();
        while (available_ < bytes) {              // 谓词循环：防虚假唤醒
            cv_.wait_until(lk, next_refill_);     // 定时醒来补桶，而不是无限期睡
            refill_locked();
        }
        available_ -= bytes;
    }

private:
    void refill_locked() {
        const auto now = std::chrono::steady_clock::now();
        while (now >= next_refill_) {             // 补齐错过的周期
            available_ = quota_per_period_;       // 不跨周期累积：突发上限 = 单周期配额
            next_refill_ += period_;
            cv_.notify_all();
        }
    }

    std::mutex mu_;
    std::condition_variable cv_;
    const std::chrono::milliseconds period_;
    const int64_t quota_per_period_;
    int64_t available_;
    std::chrono::steady_clock::time_point next_refill_;
};
```

几个值得停下来看的点：

- **`wait_until` 而不是 `sleep`**：睡眠的线程对"提前有配额了""进程要关闭了"都无反应；条件变量既能定时醒来补桶，又能被 notify 打断——限速器要的正是这种"可打断的等待"；
- **谓词循环**：醒来不等于配额够（虚假唤醒、被别人抢先），必须回到 `while` 再查——条件变量的铁律；
- **大请求拆分**：一次 `request(1GB)` 若不拆，桶永远补不到那么满，线程死等。真实实现【实现】把大 IO 按单周期配额切块逐次申请，RocksDB 还让等待者排 FIFO 队列、队首优先，保证公平；
- **背压的定义**：下游（盘）消化不动时，压力沿着调用链反向传导，最终让上游（compaction 线程）停下来。手段就三种——阻塞（本例）、丢弃、降级。存储引擎选阻塞，因为后台任务不能丢也不能降质。

## 5. 线程池隔离：Flush 和 Compaction 为什么分池

RocksDB 维护两个后台线程池【实现】：HIGH 池跑 flush，LOW 池跑 compaction（总并发由 `max_background_jobs` 控制）。为什么不是一个池加任务优先级？

因为**任务一旦开始执行就不可抢占**。假设单池 4 线程全被 compaction 占着（每个要跑几分钟），此时 flush 任务就算优先级再高也只能干等——而 flush 等不起：MemTable 释放不掉，写路径很快触发 write stall，前台直接受伤。物理分池保证 flush 永远有线程可用。

这和 C++ 服务开发的纪律一字不差：**不要把长任务和延迟敏感任务扔进同一个线程池**——优先级解决"谁先开始"，解决不了"开始了的让不让路"。

CPU 也要隔离【取舍】：compaction 不只是 IO，归并比较、压缩、CRC 都吃 CPU。线程数开太多，即使 IO 限住了，前台线程也会在 CPU 调度上被挤（上下文切换、cache 污染）。所以线程数上限和字节限速是两个独立的旋钮，都得设。

## 6. 内核层的 QoS：能帮什么，帮不了什么

引擎的 rate limiter 只管自己。同一块盘上还有别的进程、还有页缓存回写，这些要靠内核手段：

- **cgroup v2 `io.max` / `io.cost`**【实现】：对一个 cgroup 硬限 IOPS/带宽，或按权重分配设备时间——容器化部署里给整个 DB 实例划预算的标准做法；
- **wbt（writeback throttling）**【实现】：内核对 buffered write 的回写流量自动节流，保护同队列的读延迟；
- **ionice**：只对 bfq 这类调度器生效；NVMe 默认调度器是 `none`（多队列直通），此时 ionice 基本无效【事实】——老经验在新硬件上失灵的典型。

但内核有一个天然盲区【事实】：它只看得见 bio，分不清"这个写来自 compaction 还是来自用户请求"——同一个进程内部的流量分类，只有引擎自己知道。**这就是引擎必须自带 rate limiter 的根本理由：QoS 的粒度取决于"谁知道流量的身份"，而身份信息在用户态。**内核 QoS 与引擎限速是互补关系，不是替代关系。

## 7. 背压闭环：太松与太紧殊途同归

Rate limiter 不是越紧越好——它两头都连着前台延迟，只是路径和时间尺度不同：

- **太松**：compaction 全速跑 → 设备队列被大块写填满 → 前台读写排队 → **p99 立刻毛刺**。特征：`iostat` 的 `aqu-sz`（平均队列深度）随 compaction 波动，读延迟曲线和 compaction 流量曲线同相位（[[9.5 p99 毛刺定位]]）；
- **太紧**：compaction 产出跟不上写入 → 债务堆积（`pending_compaction_bytes` 上涨、L0 文件数上涨）→ 触发引擎自保 → **write stall 让前台写降速甚至停写**（[[6.14 Write Stall]]）。特征：限速后一段时间内一切安好，然后 stall 计数（`rocksdb.stall.micros`）陡增——延迟爆发是滞后的。

一句话【取舍】：**rate limiter 把"设备排队"换成"引擎债务"。前者即刻打 p99，后者延迟引爆。调参的目标不是消灭某一头，而是找到债务稳定（pending_compaction_bytes 有界且不趋势上涨）前提下的最低限速。**

对照实验（`db_bench` 即可复现形状）：固定写入负载，`rate_limiter_bytes_per_sec` 取三档——不限 / 盘实测混合带宽的 50% / 10%，各跑 30 分钟。观测三条曲线：前台读 p99、`pending_compaction_bytes`、stall 时间。预期形状：不限 → 读 p99 跟着 compaction 波形起伏；太紧 → 前期平滑随后 stall 陡增；合适 → 两条曲线都平。注意变量控制：换限速档位时要清库重灌，否则上一轮欠的债会污染下一轮。

自动调参【实现】：`NewGenericRateLimiter` 的 `auto_tuned=true` 会根据桶的实际利用率在设定区间内动态调整速率——思路就是上面实验的自动化版：盯着"桶被打满的频率"这个背压信号做反馈控制。

## 8. 陷阱与误区

> [!warning] 常见错误
> 1. **用 `sleep` 做限速**：粒度粗、不响应提前可用的配额、进程关闭时醒不过来。条件变量 + `wait_until` + 谓词循环才是正解。
> 2. **把 rate limiter 当全局 QoS**：它只管引擎自己的后台字节。同盘邻居、页缓存回写要靠 cgroup io.max / wbt；容器混部场景两层都要设。
> 3. **限速值直接抄盘的标称带宽**：标称值是纯顺序大块的理想工况；compaction 读写混合 + 前台随机读并存时，有效带宽低得多。以"债务是否稳定"为准绳倒推，而不是从纸面参数出发。
> 4. **只限 IO 不限 CPU**：compaction 的压缩和归并吃 CPU，字节限住了、线程数没限，前台照样被挤。两个旋钮独立。
> 5. **一个线程池混跑长短任务**：优先级管不了已开始的任务。物理分池——存储引擎如此，你自己的 C++ 服务也如此。
> 6. **只看平均带宽做容量规划**：均值看起来只用了 40%，p99 已经在毛刺——问题在队列深度和突发，观测要看分位数和 `aqu-sz`，不是均值。

## 9. 关键结论

| 结论 | 性质 |
| --- | --- |
| 前台小 IO 延迟敏感、后台大 IO 流量巨大，共享同一设备队列——队头阻塞是延迟放大的机制 | 事实 |
| 限速必须发生在 IO 下发之前；已入队的 IO 无法撤回，故 rate limiter 位于引擎用户态 | 事实 |
| 令牌桶 = 周期补配额 + 配额不足睡条件变量；背压 = 让生产者阻塞的反向传导 | 实现 |
| Flush 走 HIGH、compaction 走 LOW，fairness 防饿死；WAL 前台写不经过 rate limiter | 实现 |
| 长任务与延迟敏感任务必须物理分池：优先级决定谁先开始，决定不了已开始的让路 | 事实 / 工程纪律 |
| 内核只见 bio 不见语义，进程内流量分类只能在用户态做——引擎限速与内核 QoS 互补 | 事实 |
| 限太松即刻打 p99（排队），限太紧延迟引爆（债务 → write stall）；目标是债务稳定下的最低限速 | 取舍 |
| NVMe 默认 none 调度器下 ionice 无效；容器场景用 cgroup v2 io.max / io.cost | 事实 |
