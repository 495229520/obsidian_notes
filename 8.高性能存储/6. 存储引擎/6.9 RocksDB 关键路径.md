# RocksDB 关键路径

> [[6.6 LSM-tree 三种放大]] 把模型与账本立起来了，本篇把它落到工业引擎：一笔 `Put` 与一笔 `Get` 在 RocksDB 里的完整关键路径——哪些线程参与、在哪一步等待、哪些数据结构改变状态。先校准一个经常被忽略的事实【事实】：**RocksDB 是嵌入式库，不是服务**——它没有自己的进程与网络端口，所有前台工作都发生在**你的线程**里，后台 flush/compaction 线程也是在你的进程里创建的。这意味着两件事：关键路径上没有 RPC，只有函数调用与盘 IO；以及 compaction 烧的 CPU、抢的盘带宽，都直接记在你的进程账上。

前置：[[6.6 LSM-tree 三种放大]]（结构与背压链）、[[6.1 WAL 与 Crash Consistency]]（提交点协议）、[[6.2 Group Commit]]（fsync 摊薄，本篇写路径的第②步是它的工业实现）、[[1.2 Page Cache 命中与未命中]]（读路径的单价）、[[1.4 fsync fdatasync 与持久化语义]]（`sync` 选项的语义地基）。

## 1. 全景：三类线程与六个数据结构

![RocksDB 写读关键路径全景：左列为写路径六步——WriteBatch、write group 合并、WAL 追加与可选 fdatasync、memtable 跳表插入即确认、冻结 immutable 后台 flush 为 L0、compaction 线程池逐层下沉，并有 write stall 双水位背压箭头指回前台；右列为读路径六步——取 Version 引用、探测 memtable 与 immutable、L0 逐文件、L1 起每层二分一个文件、文件内 bloom filter 与 block cache 过滤、按序列号合并返回；底部为 Version/MANIFEST 的文件集 MVCC 说明](../../图片/SVG/rocksdb-写读关键路径.svg)

| 参与者 | 谁 | 干什么 |
| --- | --- | --- |
| 前台线程 | **你的**业务线程 | 执行 `Put`/`Get` 的全部同步工作 |
| flush 线程 | 后台（高优先级池） | immutable memtable → L0 SST |
| compaction 线程池 | 后台（低优先级池） | 逐层归并下沉，偿还 [[6.6 LSM-tree 三种放大]] 的债 |

| 数据结构 | 是什么 | 状态变化 |
| --- | --- | --- |
| **WriteBatch** | 一组 key-value 操作的序列化缓冲，原子性的单位 | 前台构造，写完即弃 |
| **WAL** | 顺序追加的日志文件（[[6.1 WAL 与 Crash Consistency]] 的协议） | 追加 → memtable 落盘后整文件作废 |
| **memtable** | 内存有序结构，默认**并发跳表**（skiplist）【实现】 | 活跃 → 写满冻结为 immutable → flush 后释放 |
| **SST 文件** | 不可变排序文件：数据块 + 块索引 + bloom filter | 只有创建与删除，**没有修改** |
| **Version / MANIFEST** | 当前「SST 文件集合」的元数据快照及其变更日志 | 每次 flush/compaction 原子切换一个新 Version |
| **sequence number** | 全局递增的写序号，每条记录携带 | 只增；快照 = 记住一个序号 |

**Version 是理解 RocksDB 并发模型的钥匙**【事实】：SST 不可变，因此「数据库当前长什么样」被表示为一个不可变的文件清单（Version）；flush/compaction 完成时构造新 Version、**原子替换 current 指针**，旧 Version 靠引用计数存活到最后一个读者离开——这就是 [[6.6 LSM-tree 三种放大]] 里 `shared_ptr<const T>` 快照类比的工程实体，变更记录顺序追加进 MANIFEST（本身也是一个 WAL）。**读者从不加表级锁，写者从不阻塞读者**。

## 2. 写路径：六步，只有一步碰盘

一笔 `Put(k, v)` 的前台旅程【事实/实现】：

1. **构造 WriteBatch**：k/v 序列化进内存缓冲——纯内存；
2. **加入 write group**：并发写线程排队，队首成为 **leader**，把队列里所有线程的 WriteBatch **合并成一个大 batch**；follower 原地等待——这是 [[6.2 Group Commit]] 的工业实现：N 个线程的 fsync 摊薄成 1 次；
3. **WAL 追加（+可选 sync）**：leader 把合并 batch 顺序 `write()` 进 WAL；`WriteOptions::sync` 决定是否在此处 `fdatasync`——**写路径唯一的盘上等待点**；
4. **插入 memtable**：并发跳表按 `key + seq` 插入（默认允许组内并行插入【实现】）；
5. **确认**：leader 唤醒 followers，各自返回——此时数据只在 WAL（可能只在页缓存）+ memtable；
6. **异步余波**：memtable 写满（默认 64 MiB【实现】）→ 冻结为 immutable，切一张新 memtable 与新 WAL；flush 线程把 immutable 顺序写成 L0 SST，提交新 Version，作废旧 WAL；compaction 线程池随后逐层下沉。

`sync` 的三档语义要背下来【取舍】：

| 配置 | 崩溃丢失窗口 | 延迟 |
| --- | --- | --- |
| `sync=false`（**默认**） | 进程崩不丢（WAL 在页缓存，内核还在）；**掉电/内核崩丢最近若干秒** | μs 级 |
| `sync=true` | 提交点 = fdatasync 完成，掉电不丢 | 加一次盘 flush，几十 μs~ms |
| 关 WAL | 崩溃丢整个 memtable | 最快 |

默认值不是持久化承诺——**RocksDB 默认把「掉电丢秒级数据」这个决定替你做了**，语义对不对要回到 [[6.1 WAL 与 Crash Consistency]] 的提交点定义自己判断；验证手段是 [[6.10 崩溃注入测试]]。

**前台等待点对账**：②的排队（锁+组队）、③的 fdatasync（可选）、以及 [[6.6 LSM-tree 三种放大]] §3 的 **write stall**——L0 文件数触水位（默认 20 减速 / 36 停写【实现】）、immutable 攒太多、pending compaction bytes 超限，三个水位任何一个触发，前台写被人为注入延迟或挂起。**stall 发生在第②步之前**，所以它的指纹是「写延迟从 μs 突跳到 ms/s，且与 value 大小无关」（[[9.5 p99 毛刺定位]]）。

## 3. 读路径：探测序列 + 两级缓存

一笔 `Get(k)` 的旅程【事实】：

1. **取 current Version**（引用计数 +1）——此后整个读操作看到一致的文件集，与并发 flush/compaction 互不干扰；
2. **memtable → immutable memtable**：跳表查找，纯内存；命中即按 seq 判断可见性返回；
3. **L0 逐文件探测**（新→旧）：L0 文件 key 范围互相重叠，**每个都要查**——L0 文件数直接加进读放大；
4. **L1 及以下每层至多一个文件**：层内有序不重叠，版本元数据里二分定位；
5. **文件内三道闸**【实现】：
   - **bloom filter**（常驻内存）：~1% 假阳率挡掉「不在此文件」的探测——一次内存查询替代一次盘 IO；
   - **block cache**（RocksDB 自管的解压后块缓存）：命中则纳秒级；
   - miss → **盘读**：定位数据块 `pread`，默认 buffered IO——还有第二级机会命中**页缓存**（存的是压缩块）；两级都 miss 才真正到盘（[[1.2 Page Cache 命中与未命中]]）；
6. **合并可见性**：找到的记录按 seq 与快照比较，墓碑视为「已删除」返回 NotFound。

两级缓存的取舍【取舍】：block cache 存解压块（省 CPU、内存密度低），页缓存存压缩块（密度高、每次命中要解压）；同一份数据可能两边各占一份内存——**容量规划要把两级加在一起算**，激进方案是 `O_DIRECT` + 大 block cache 只留一级【实现】。

范围扫描（`NewIterator`）与点查的差别：bloom 失效、每层各开一个游标做**多路归并**、逐 key 跳墓碑——[[6.6 LSM-tree 三种放大]] 排障清单里「扫描慢且 CPU 高」的根因就在这一步。**迭代器与快照都会钉住旧 Version**：长期持有的迭代器让已 compaction 掉的旧文件删不掉，盘占用只涨不跌【实践】。

## 4. 与 OS 的三处关键互动

RocksDB 的性能形状由三处 OS 交互决定，全部是前几章讲过的机制【事实】：

1. **WAL：顺序小写 + fdatasync**——[[1.4 fsync fdatasync 与持久化语义]] 的全部结论适用；group commit 把「每笔一刷」摊薄成「每组一刷」，盘越慢收益越大（[[6.2 Group Commit]]）；
2. **SST 读写与页缓存共处**：flush/compaction 是大块顺序写，读是随机 `pread`；compaction 的输入输出会冲刷页缓存里的热数据（缓存污染），可用 `fadvise` 提示丢弃【实现】（[[1.6 readahead 与 posix_fadvise]]）；
3. **后台 IO 与前台抢同一个设备队列**：compaction 不限速会把前台读的 p99 顶上天——rate limiter 给后台 IO 限流，本质与网络 QoS 同型（[[1.7 块层与 blk-mq]]、[[6.6 LSM-tree 三种放大]] §3）。

## 5. Modern C++：把关键路径跑一遍

RocksDB 原生 C++ API，RAII 贴合得很自然；下面的最小程序把 §2/§3 的路径逐个触发：

```cpp
#include <rocksdb/db.h>
#include <rocksdb/options.h>
#include <rocksdb/write_batch.h>

#include <cassert>
#include <memory>
#include <print>
#include <string>

int main() {
    rocksdb::Options opt;
    opt.create_if_missing = true;

    rocksdb::DB* raw = nullptr;
    rocksdb::Status s = rocksdb::DB::Open(opt, "/tmp/rocksdb-demo", &raw);
    assert(s.ok());
    std::unique_ptr<rocksdb::DB> db{raw};          // RAII：析构时关库、停后台线程

    // 写路径：WriteBatch = 原子单位；两条 Put 要么都在要么都不在
    rocksdb::WriteBatch batch;
    batch.Put("user:1", "alice");
    batch.Put("user:1:quota", "100");
    rocksdb::WriteOptions wo;
    wo.sync = true;                                 // §2 第③步的 fdatasync：提交点在这里
    s = db->Write(wo, &batch);                      // 排队 → 组提交 → WAL → memtable
    assert(s.ok());

    // 读路径：快照 = 记住一个 sequence number，读到一致视图
    rocksdb::ReadOptions ro;
    const rocksdb::Snapshot* snap = db->GetSnapshot();
    ro.snapshot = snap;
    std::string v;
    s = db->Get(ro, "user:1", &v);                  // memtable → L0… → bloom → cache → 盘
    std::println("user:1 = {}", s.ok() ? v : "miss");

    // 迭代器：多路归并；unique_ptr 保证及时释放——否则钉住旧 Version
    {
        std::unique_ptr<rocksdb::Iterator> it{db->NewIterator(ro)};
        for (it->SeekToFirst(); it->Valid(); it->Next())
            std::println("{} -> {}", it->key().ToString(), it->value().ToString());
    }
    db->ReleaseSnapshot(snap);                      // 快照同理：不释放，旧版本文件删不掉
}
```

**关键点**：

- `WriteOptions::sync` 是每笔写自己的持久化决定——同一个库里可以混用（重要事务 `sync=true`，可重放数据默认档）；
- 迭代器与快照的生命周期就是「钉住旧 Version 的时长」，用 RAII 块作用域把它压到最短；
- `Status` 必须逐个检查：fsync 的 EIO 会从这里冒出来，处理原则见 [[6.3 fsyncgate 与 EIO 处理]]。

## 7. 陷阱与误区

> [!warning] 常见错误
> 1. **把默认配置当持久化承诺**：`sync=false` 下掉电丢最近秒级的「已确认」写入——语义要自己选，并用 [[6.10 崩溃注入测试]] 验证。
> 2. **长期持有迭代器/快照**：钉住旧 Version → 已归并的旧文件删不掉 → 盘占用与空间放大悄悄上涨。
> 3. **只给 block cache 做容量规划**：buffered IO 下页缓存还存着压缩块，两级缓存加起来才是真实内存占用。
> 4. **忘了自己是宿主**：RocksDB 的后台线程在你的进程里抢 CPU 与盘带宽；容器配额、线程池大小、rate limiter 要与业务负载一起规划。
> 5. **用大 value 直灌**：MB 级 value 让 memtable 秒满、compaction 反复搬运大字节——写放大账单爆炸；大 value 考虑 key-value 分离（BlobDB 类方案【实现】）。
> 6. **stall 时盲调水位**：把 slowdown/stop 阈值调高只是推迟并加重停写；根治是提高 compaction 供给或降低写放大（[[6.7 Compaction 策略]]）。

## 8. 关键结论

| 结论 | 性质 |
| --- | --- |
| RocksDB 是嵌入式库：前台路径在业务线程里执行，后台线程的 CPU/IO 记在宿主进程账上 | 事实 |
| 写路径六步只有 WAL 一步碰盘；组提交（write group leader/follower）把 N 线程的 fsync 摊成 1 次 | 事实 |
| `sync` 三档 = 三种崩溃丢失窗口；默认 `sync=false` 掉电丢秒级——持久化语义是选项不是默认赠品 | 事实 / 取舍 |
| memtable → immutable → L0 SST → 逐层下沉；文件不可变，「当前状态」= Version 文件清单的原子替换 + 引用计数 | 事实 |
| 读路径 = 新→旧探测序列；L0 逐文件、L1+ 每层一个；bloom 与两级缓存决定探测单价 | 事实 |
| 迭代器/快照钉住旧 Version：生命周期 = 空间放大与文件回收的延迟 | 事实 / 实践 |
| write stall 是显式背压，指纹为「写延迟突跳且与数据量无关」；水位在 L0 文件数/immutable 数/欠账字节上 | 事实 |
| 两级缓存（block cache 解压块 + 页缓存压缩块）内存要合并核算；O_DIRECT 是收成一级的手段 | 取舍 |
