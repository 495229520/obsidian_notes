# 通信协议选择：Eager、Rendezvous 与 RMA

> 小消息首先要少付固定成本，大消息首先要避免为全部 payload 付出不必要的复制和缓冲成本。但决定协议的不是一个“消息大小开关”：注册是否命中、接收是否就绪、credit 是否充足、完成语义和进展线程是否可用，都可能改变选择。

**最重要的分类。** Eager / Rendezvous 描述“何时发送主体数据、何时匹配或协商接收资源”；RMA 描述“如何访问远端内存”。它们**不是互斥的三种协议**。Rendezvous 可以用 RMA READ 或 WRITE 搬数据，也可以退回消息分片；Eager 也不必然意味着端到端都用 CPU 拷贝。[^tag][^ucx]

**前置知识。** [[4.5 Send Recv 与 RDMA Read Write]] 给出通信操作；[[4.31 libfabric 与 OFI 编程模型]] 给出能力、MR、progress 与完成合同。本篇把两者接到协议状态机和性能决策上。

**版本与测量范围。** 机制讨论面向主机内存上的消息通信；具体 provider 示例固定到 **libfabric 2.7.0 的 RxM 手册**，UCX FAQ 仅用于跨栈对照，核对日期为 **2026-09-19**。下文的微秒、纳秒、缓冲容量和流水时长均为**明确声明的教学假设或计算结果，不是本机、用户集群或某品牌网卡的实测参数**。

## 1. 两条轴：协议决策与数据搬运

| 层次 | 问题 | 常见选项 |
|---|---|---|
| 匹配与资源策略 | 主体数据能否先发？接收位置何时确定？ | Eager、Rendezvous、分段中间协议 |
| 数据操作 | 数据怎样从源到目标？谁发起？ | SEND/RECV、RMA READ、RMA WRITE |
| 内存路径 | payload 要经过哪些缓冲？ | copy、bounce buffer、已注册内存、设备内存路径 |
| 完成与回收 | 源缓冲、目标 slot、业务请求何时结束？ | 本地完成、目标可见、消费确认、持久化确认 |

例如，“Rendezvous + RMA READ”意味着发送方先公布可读的源区域，接收方准备好目标后主动拉取。RMA 是搬运机制，Rendezvous 是安排这次搬运的协议。一个 `fi_send` 也可能在 provider 内部从 Eager 切换为 Rendezvous；应用没有调用 `fi_read`，不代表 provider 内部没有使用 RMA。[^rxm]

UCX 官方协议诊断的示例中也同时出现 eager zero-copy 与 rendezvous zero-copy read。这只是“两个维度可以组合”的证据，示例中的阈值不应移植为其他机器的参数。[^ucx]

## 2. 三条时间线：Eager、拉取式 Rendezvous、推送式 Rendezvous

![[图片/SVG/8_4_4_32_1.svg|900]]

图中向下是时间，横向箭头是消息或数据操作；等待区标明谁尚不能进入 bulk 传输或释放缓冲。RTS、CTS、FIN、DONE、CONSUMED 都是**本篇协议示意名，不是 libfabric 标准 API**。

### 2.1 Eager：先发送主体数据，把缓冲风险留在接收侧

发送方在协议允许的窗口内直接发 header 和 payload，不等待每条消息都取得专属接收位置。接收侧可能已经有匹配的应用缓冲，也可能先由 provider/上层运行时放到 unexpected 缓冲，等应用补上接收请求后再匹配或搬运。[^tag]

这里有两个不能混为一谈的“recv”：一是硬件或 provider 为协议准备的接收资源，二是上层应用声明的最终接收对象。应用尚未发布最终接收对象，不等于 NIC 没有任何接收资源；反之，底层有接收队列，也不等于应用拥有无限 unexpected 空间。

**为什么对小消息有利？** 它省去逐消息的前置就绪握手。即使多做一次小拷贝，节省的控制路径、往返等待和调度固定成本仍可能更多。

**主要代价是什么？** 在接收延迟、incast 或流量突发时，payload 会占用 unexpected 缓冲和内存带宽；如果不用 credit 或背压限制，瓶颈会从网络变成接收侧内存与调度。不能把“Eager”解释为“不等任何条件、一定立即完成”。

### 2.2 拉取式 Rendezvous：接收者决定何时取数据

一个简化、可审计的流程是：发送方先保持源缓冲稳定并准备可读注册区，通过 RTS 提供请求标识、长度和访问元数据；接收方完成匹配、准备目标缓冲后发起 RMA READ；READ 在接收方完成并满足所需可见性后，接收方回复 DONE，发送方据此释放源数据或撤销临时访问资格。

这时 **READ 的发起者是接收数据的一端，大数据流向却是发送源数据的一端 → 接收端**。做带宽或 incast 归因时，不能把请求方向当作 payload 方向。

源 MR 必须持续有效直到不再可能发生合法或在途访问。READ 结束让接收方可以消费目标数据，但发送方需要某种确认才知道对端不再读取源区域；没有“读方知道”就自动让“被读方知道”的魔法。[^rma][^mr]

### 2.3 推送式 Rendezvous：目标就绪后才放行写入

发送方先发 RTS，接收方匹配后提供 CTS，携带目标 slot、长度、epoch、地址与 key 等信息。发送方执行 WRITE。接下来必须建立**数据先可见、通知后可消费**的保证，再用 FIN、remote CQ data 或其他受支持机制通知目标；目标完成业务消费后返还 CONSUMED/credit。

在 libfabric 中，不能把“普通本地 WRITE CQE + 随后发一个 FIN”当成所有 provider 都成立的证明。可以选择 provider 实际支持的 delivery 完成与通知组合，或其他有明确顺序和可见性保证的协议；不同 endpoint、多 rail 或独立控制通道之间的先后关系尤其不能凭提交顺序猜。[^completion][^getinfo]

**握手不是固定两个 RTT。** RTS 是否已有元数据、目标是否预注册、通知是否合并、pull 还是 push、何时给应用报告完成，都会改变往返次数。比较时必须先画出关键路径，不能直接套“Rendezvous = 2 RTT”。

## 3. 小消息：把固定成本拆开，才知道该优化哪里

在固定路径、无明显排队的一小段尺寸区间内，可以先拟合：

$$
T(n) \approx \alpha + \beta n
$$

其中 $\alpha$ 是与 payload 大小弱相关的启动成本，$\beta$ 是该区间的有效每字节代价。这是分析近似，不承诺真实曲线全程线性。

| 成本 | 一条消息通常只付有限次数的工作 | 可验证的优化方向 |
|---|---|---|
| 应用和调度 | 请求状态、线程交接、锁、队列访问 | 减少跨线程交接，明确 endpoint 所有者 |
| 提交 | API 分派、描述符构造、门铃或底层发送调用 | 批量提交，减少每条消息的固定工作 |
| 匹配与控制 | tag/请求查找、credit、通知 | 合并控制消息、复用会话、减少额外握手 |
| 完成回收 | CQ 读取、状态表访问、回调 | 批量读取，有界调度，避免每条单独唤醒 |
| 数据搬运 | 实际复制、DMA、内存读取 | 小消息要比较复制代价与启动代价，而非只追求“零拷贝” |

[[4.16 Inline Batching 与 Doorbell 优化]] 解释为什么固定成本可以通过 inline 和批量摊薄。但 OFI 的 inject、硬件 inline 和上层 Eager 仍不是同一个概念：**一个限制源缓冲接管方式，一个描述硬件提交机制，一个决定何时发主体数据。**

例如 `fi_inject` 在满足大小限制时可以让调用者及时复用源缓冲，但它不是对端业务完成的通知。普通 `FI_INJECT_COMPLETE` 完成标志又与 `fi_inject` 函数不同，前者描述 CQ 完成时机，不能把两者的大小约束直接互换。[^msg][^completion]

## 4. 大消息：注册成本、复制成本与复用次数必须一起算

### 4.1 冷注册与热注册不能只测其中一种

冷路径可能包括首次访问、页和映射准备、注册资源创建、地址转换相关工作；热路径可能只查到已有 MR 或复用长生命周期注册池。具体组成依赖系统、内存类型与 provider，不能给所有 RNIC 填同一条常数。MR 的权限与释放边界见 [[4.4 内存注册与零拷贝]] 和 [[4.12 rkey lkey 生命周期]]。

如果一次注册被复用 $N$ 次，一种最简单的摊销模型是：

$$
C_{\text{reg/msg}} \approx
\frac{T_{\text{reg}}+T_{\text{dereg}}}{N}
+ T_{\text{lookup}}
$$

若依赖注册缓存，则可进一步写成条件期望：

$$
E[C_{\text{reg}}]
= h C_{\text{hit}} + (1-h) C_{\text{miss}}
$$

这里 $h$ 是**本次工作集与访问模式下**的命中率，不是 provider 永久属性。不断循环同一地址可能让 benchmark 看起来很好，却不能代表每次创建新大缓冲的应用。

### 4.2 零拷贝不等于零成本

跳过 bounce copy 可以省内存带宽，但仍可能有注册、映射、DMA、协议控制、队列等待和完成处理。反过来，长期注册池可能消除大部分逐消息注册成本，使 Rendezvous 的交叉点向更小消息移动。

还要明确哪些注册成本真在**关键路径**上：提前注册的目标池不应每条消息重复收费；若注册与其他工作有可验证的重叠，也不应直接把所有阶段耗时相加。下节先采用串行相加的简化模型，随后再讨论流水。

## 5. 阈值推导：先统一完成边界，再寻找交点

![[图片/SVG/8_4_4_32_2.svg|900]]

图中三条线完全来自下面的教学公式。颜色区分协议与冷/热条件，不表示任何特定厂商数据。

### 5.1 完整一点的比较模型

把 Eager 和 Rendezvous 的端到端耗时写为：

$$
T_E(n)=a_E+b_E n+Q_E(n,u)
$$

$$
T_R(n)=a_R+H+R_s(n)+R_t(n)+b_R n+Q_R(n,u)
$$

$H$ 是前置控制关键路径，$R_s,R_t$ 是本次真正发生在关键路径上的两端注册成本，$Q$ 是随负载状态 $u$ 改变的排队与调度。$b_E,b_R$ 吸收有效传输和该路径每字节复制的代价。

**只有完成边界相同，比较才公平。** 不能把 Eager 的“发送方源缓冲可复用”与 Rendezvous 的“接收方已消费 payload”相减。下列算例统一为“接收端 payload 可供应用读取”，并忽略负载排队。

### 5.2 线性区间内的候选交叉点

在一定尺寸范围内，将握手与注册近似合入常数 $A_R$，可写：

$$
T_E=A_E+b_E n,\qquad T_R=A_R+b_R n
$$

若 $b_E>b_R$ 且 $A_R>A_E$，则：

$$
n^*=\frac{A_R-A_E}{b_E-b_R}
$$

不能忽略其他情况：斜率相同且截距不同可能全程由同一路径占优；得到负交点不代表应配置负阈值；分母符号改变、非线性注册成本或排队出现时，应回到区间拟合和有效范围检查。

### 5.3 一个可复算的假设算例

设定单位为 **$n$：字节，$T$：微秒**：

$$
T_E = 1.0 + 0.00010n
$$

$$
T_{R,cold} = 5.0 + 0.00004n,
\qquad T_{R,warm} = 2.5 + 0.00004n
$$

这里 Eager 的每字节代价为 `0.10 ns/B`，Rendezvous 为 `0.04 ns/B`。两个交点分别为约 **66,667 B = 65.1 KiB** 和 **25,000 B = 24.4 KiB**。这些数仅说明“复用注册资源会改变交点”，不是建议把库的阈值设为 65 KiB。

| 消息大小 | Eager，μs | Rendezvous 冷，μs | Rendezvous 热，μs |
|---|---:|---:|---:|
| 4 KiB | 1.410 | 5.164 | 2.664 |
| 32 KiB | 4.277 | 6.311 | 3.811 |
| 64 KiB | 7.554 | 7.621 | 5.121 |
| 128 KiB | 14.107 | 10.243 | 7.743 |

下面是纯计算脚本，不包含网络操作。显式写单位是为了避免把 ns 与 μs 差一千倍，或把十进制 kB 与二进制 KiB 混用。

```python
# 教学参数，不是测量数据；n 使用字节，时间使用微秒。
a_e, a_r_cold, a_r_warm = 1.0, 5.0, 2.5
b_e, b_r = 0.00010, 0.00004
assert b_e > b_r
for label, a_r in [("cold", a_r_cold), ("warm", a_r_warm)]:
    n_star = (a_r - a_e) / (b_e - b_r)
    print(f"{label}: {n_star:.1f} B = {n_star / 1024:.2f} KiB")
```

### 5.4 最终选择是带约束的优化，不是交点填配置

可以把工程问题写成：在 CPU、注册资源、unexpected 内存、控制消息延迟及正确性预算均满足时，选择在目标负载下延迟或吞吐最合适的协议。

例如，单对单下 Eager 更快，却使多发送者情况下的 unexpected 队列持续增长，那么它就不是可接受选择。反过来，过早切 Rendezvous 可能让控制处理和 progress 占满 CPU。若系统支持自适应选择，还需要滞回或稳定窗口，避免在交点附近随噪声反复切换。

## 6. 接收缓冲与 credit：真正限制 Eager 的常常不是带宽

![[图片/SVG/8_4_4_32_3.svg|900]]

图上将发送方可重用的源缓冲和接收方可重用的 slot 分开计数。**local completion 回收本地资源，CONSUMED 回收目标槽位；它们不能共用一个计数器。**

### 6.1 对固定 slot 预留模型做一次容量计算

假设有 $P$ 个发送者，每个最多持有 $D$ 个接收 credit，每个 slot 可承载 $S_E$ 字节的 Eager payload，则：

$$
M_{\text{payload reserve}}=P\,D\,S_E
$$

实际内存还包括消息头、对齐、队列元数据、预置 recv 与控制缓冲。这个式子是**固定 slot 预留上界模型**，不是所有实现的即时物理驻留量。动态共享池应按全局获批字节数和真实分配方式另算。

教学例：$P=64,D=8$。若 $S_E=16\ \text{KiB}$，payload 预留为 **8 MiB**；阈值对应的 slot 增到 $64\ \text{KiB}$，就是 **32 MiB**。仅改变一个“消息大小阈值”，接收端 payload 预算就扩大四倍。

### 6.2 credit 应返回给哪个状态转换

一个简化接收 slot 状态机是：`FREE → RESERVED → RECEIVING → READY → CONSUMING → FREE`。最后一步才返还应用消费 credit；若还存在 DMA、读者或重传引用，就不能提前进入 FREE。

同时区分三类窗口：本地发送队列资源、对端协议接收资源、应用允许占用的目标缓冲。网络层流控解决不了应用持有一块数据几十毫秒不释放的问题。[[4.17 Retry RNR 与 Timeout]] 解释的是其中一类底层等待，不应替代完整的应用流控。

### 6.3 给控制通道留出独立进展空间

假设所有数据 credit 都用完，而返还 credit 的消息又必须先获取同一池的 credit，协议可能形成循环等待。可行的设计方向是保留控制缓冲与控制发送预算，或提供不依赖耗尽的数据窗口的返还机制。

这不是让控制消息“无限优先”：还要限制控制消息速率、合并确认并避免数据饥饿。应把控制消息最大延迟和每轮调度预算写进验收条件。

## 7. 分块与流水：减少启动次数和增加重叠之间的平衡

![[图片/SVG/8_4_4_32_4.svg|900]]

图中每个编号都是同一个逻辑块在不同阶段的位置。只有当各阶段确实可以独立推进时，斜着交错的条带才对应真实重叠；画出多条彩条不等于已经获得并行。

### 7.1 一个可计算的三阶段模型

把大小为 $n$ 的消息切成 $K=\lceil n/c\rceil$ 块，每块大小约为 $c$。假设每块经历准备、网络、消费三个阶段，服务时间分别为 $p,q,r$；每个阶段串行处理自己的工作，但不同阶段使用可重叠的资源。

理想情况下：

$$
T_{\text{pipeline}}
\approx T_{\text{setup}}+p+q+r+(K-1)\max(p,q,r)
$$

不重叠时则近似：

$$
T_{\text{serial}}
\approx T_{\text{setup}}+K(p+q+r)
$$

教学例：$K=4,p=2,q=3,r=1\ \mu s$，忽略 setup，则理想流水耗时 **15 μs**，串行耗时 **24 μs**。图中的条长按此假设比例绘制，不是设备 trace。

这些公式假定各块大小一致；最后一块较小时须使用它的实际阶段时间。若准备和消费共用同一个繁忙 CPU 核，或 DMA 与内存复制竞争同一条受限链路，则简单的 $\max$ 模型会过于乐观。

### 7.2 “准备”阶段究竟包含什么

它可能包括填充源缓冲、获取已注册 slot、序列化、分片元数据或某些注册工作，但**不能一边假定整块 MR 早已注册，一边又把每个 chunk 的注册当作新的可重叠收益**。

若整个大区域只注册一次，则注册是 setup；若每个块单独注册，必须等该块所有访问安全结束后才注销。注册粒度、块粒度和回收粒度可以不同，但必须画出引用关系，不能因为下一个 chunk 已发送就注销前一个仍在途的 MR。

### 7.3 chunk size 与 in-flight window 联合选择

chunk 太小，每字节分摊的 header、CQ、状态与调度成本会上升；chunk 太大，首块就绪时间增加、缓冲占用扩大，小请求更容易被大块工作阻塞。

设最多允许 $W$ 块在途，有效带宽为 $B$，从占用一个 slot 到可再次使用该 credit 的周期为 $L_{\text{credit}}$，则一个填满管线的量级条件是：

$$
Wc \gtrsim B L_{\text{credit}}
$$

左边单位是字节，右边也是字节。这里的 $L_{\text{credit}}$ 可能包含接收端消费与确认，**不一定等于线上的 RTT**。窗口还必须受 MR、slot、CQ、操作深度和内存预算限制；满足上述式子只是必要的容量直觉，不是吞吐达标证明。

教学例：$B=25\ \text{GB/s}$、$L_{\text{credit}}=8\ \mu s$，需要约 200,000 B 的循环窗口；若 $c=64\ \text{KiB}$，则 $W\ge4$ 才覆盖这个量级。改变消费者速度后必须重算，不能永远沿用网络空载 RTT。

### 7.4 分块不是把一次写拆成多个写就结束

至少要有请求 ID、epoch、总长、offset、块长度和完成状态。先检查范围，再检查重复、重叠和缺块；业务提交点只能在本协议要求的全部块可见并验证通过之后出现。

重复写同样字节在某些设计下可以幂等，但“递增计数器”“追加日志”“触发一次业务动作”一般不能仅靠重写达到幂等。跨 endpoint 或多 rail 的完成也不能凭最后一个 CQE 就宣布所有块都安全。对应的顺序与恢复基础见 [[4.13 RDMA 操作顺序性]] 和 [[4.19 RDMA 故障恢复与连接重建]]。

## 8. 一个具体实现：RxM 为什么不是只有一个阈值

本节仅针对所核对的 **libfabric 2.7.0 `ofi_rxm`**，不是所有 OFI provider 的通用调优接口。RxM 的实现说明区分：

| 尺寸区间或参数 | 作用 | 不应误读为 |
|---|---|---|
| `FI_OFI_RXM_BUFFER_SIZE` | 内部发送缓冲相关设置，影响 Eager 和 inject 大小边界 | NIC 的固定 MTU，或任意 provider 的 Eager 参数 |
| Eager 以上的中间区间 | 可以采用 SAR，即分段与重组 | “一过 Eager 阈值就必然执行一次 RDMA” |
| `FI_OFI_RXM_SAR_LIMIT` | 超过相应 SAR 范围转入 Rendezvous | 跨机器永远最优的常数 |

因此可能存在 **Eager → SAR → Rendezvous** 的多段选择，而非一个交点切换两个理想直线。参数名称、默认值、取值约束与实际 provider 组合应以本机版本输出和对应手册为准。首次连接、内部 MR 缓存和资源状态也会影响测量。[^rxm]

查询时先确认实际运行的 provider 链，再看暴露的参数；以下只是发现命令，不替用户修改环境变量：

```bash
fi_info --version
fi_info -p 'verbs;ofi_rxm' -t FI_EP_RDM -v
fi_info -e | grep -E 'RXM|LOG_LEVEL|LOG_PROV'
```

对 RxM 调参之前，先完成 [[4.31 libfabric 与 OFI 编程模型]] 的正确性和 progress 验证。只看到某个环境变量存在，不代表实际流量一定走到了它管理的路径。[^info]

UCX 可用 `ucx_info -cf` 查看配置说明，并在相应协议框架支持下通过 `UCX_PROTO_INFO=y` 查看协议选择信息；这些是 **UCX/UCP 应用的诊断手段**，不是 libfabric 程序的开关，也不要把 FAQ 的示例阈值直接复制进 OFI。[^ucx]

## 9. Benchmark：必须让实验能区分原因

只画“消息大小—带宽”不足以解释协议。沿用 [[4.30 RoCE Benchmark Matrix：Message Size、QP 数、Flow 数、Incast、NUMA、Multi-Rail、PFC、ECN 与 P99]] 的单轴、配对与回归思路，先完成下面的小矩阵。

| 实验轴 | 至少做的对照 | 它帮助排除什么混淆 |
|---|---|---|
| 消息大小 | 粗扫描，再在每个拐点两侧密集取点 | 不能只用 2 的幂恰好跳过阈值 |
| 注册状态 | 长期注册池、同址缓存命中、轮换地址/工作集 | 把热 MR 成本误当冷分配成本 |
| 接收时机 | 提前发布、受控延迟发布 | unexpected 复制与协议等待被平均值隐藏 |
| 并发形态 | 单对单、固定总负载的多发送者、受控 incast | 只在低负载下较快却不满足内存预算 |
| chunk / window | 固定一个扫描另一个，再选交互点 | 把增加在途字节的收益全归因于 chunk |
| progress | 固定核轮询、不同有界预算、受控暂停恢复 | 误把调度空隙解释为网络时延 |
| 内存与拓扑 | CPU/NIC 本地 NUMA 对照远端 NUMA | 复制和 DMA 路径改变而协议被背锅 |
| 终点语义 | 相同的目标可读或消费确认边界 | 把源缓冲完成和端到端完成进行比较 |

### 9.1 一次运行至少保存三组信息

**身份和输入：** 二进制与版本、完整 provider、设备与 NUMA、内存类型、消息大小分布、实际 offered load、窗口、chunk、注册策略、接收发布策略、背景流量。

**性能和资源：** 完成吞吐、有效 payload 带宽、单请求样本与 P50/P95/P99、CPU 时间或 cycles/message、注册/注销次数与耗时、在途字节、unexpected 高水位、实际 credit 等待。

**正确性和失败：** 提交成功/未接受/异步失败分开计数，缺块和重复、内容校验、超时、重试、资源残留。尾延迟只统计成功请求时，必须同时报告错误率和超时率，不能把最慢请求删掉后宣称 P99 改善。

### 9.2 协议归因要有证据等级

| 证据 | 可以支持什么 | 仍缺什么 |
|---|---|---|
| 曲线上有拐点 | 存在某种路径、缓存或资源变化的候选 | 不能单独证明切了 Eager/Rendezvous |
| 生效配置与版本 | 协议边界的预期位置 | 不能证明实际请求没有被其他条件分流 |
| provider 的协议诊断或固定版本源码路径 | 请求选择了哪条内部路径 | 仍需解释硬件与排队成本 |
| 同窗口的资源、调用与性能观测 | 将选择结果与成本关联 | 仍要通过配对实验排除漂移 |

调试日志和 tracing 本身会改变时延；建议短时诊断运行用于确认路径，性能运行保持同样配置但关闭昂贵追踪，并保留二者关联。不能把没有采到的注册缓存命中率填成零。

## 10. 失败路径：协议没有回收设计就不算完成

| 失败位置 | 尚未确定的事情 | 需要的协议动作 |
|---|---|---|
| RTS 发出后超时 | 对端是否已创建临时资源 | request ID / epoch、过期清理与重连后的旧请求隔离 |
| CTS 已下发但 bulk 未完成 | 已分配 slot 是否仍会被写入 | 停止新访问，确认在途操作被隔离后才复用 |
| 部分 chunk 完成后失败 | 哪些范围有效、哪些可重试 | 块级账目、完整性检查、明确的提交点 |
| FIN/DONE 丢失或确认超时 | 数据可能成功，但一端尚不知道 | 可查询状态、幂等控制消息和有界重试 |
| 接收进程重启 | 原 key、地址和 slot 是否属于旧代 | epoch 更新、旧授权撤销与缓冲隔离 |
| credit 返还延迟 | 网络拥塞还是消费者慢 | 分开观察数据完成时间与业务消费时间 |

Rendezvous 的“握手”主要解决本次传输的匹配和资源就绪，不自动提供 exactly-once 业务语义。RMA 的 one-sided 也不免除超时、半完成与重启状态裁决。具体错误必须结合所选通信层的保证，不把教学状态机当作硬件自动提供的事务。

## 11. 五道自测题与推理要点

**1．为什么大消息通常更值得考虑 Rendezvous，但不能写“越大一定越好”？** 握手和注册启动成本可被大 payload 摊薄，直接放到最终缓冲可节省复制和 unexpected 空间；但冷注册、错误的 progress 调度、低并发或不利拓扑仍会改变结果，且内存预算和完成边界必须一致。

**2．注册缓存命中率从很低变到很高，阈值一定怎样变化？** 在其他成本不变、Rendezvous 启动项下降且其每字节成本更低的线性模型里，交点向小消息移动。若同时改变缓存工作集、内存路径或排队，就不能只凭命中率下结论。

**3．本地 WRITE 已完成，可否立即把目标 slot 发给下一个请求？** 不可以仅凭这一事件决定。目标仍可能正在消费，或者此次完成不足以保证目标可见；slot 必须按目标拥有权和消费确认协议回收。

**4．把 1 MiB 消息切成 16 个 64 KiB 块，一定能获得流水收益吗？** 不一定。需要可重叠的阶段、足够但受控的窗口、独立的进展资源和正确的回收。若串行处理所有块只增加 16 份开销，甚至会更慢。

**5．如何验证“Rendezvous 握手导致延迟台阶”而非“注册缓存 miss”？** 固定同一 provider 和协议选择，做预注册/冷注册配对；再固定注册条件，观察接收发布时机和协议诊断。只有把这两个变量拆开，才能把台阶归到握手或注册，而不是从一张吞吐图猜。

## 12. 最后的选择顺序

先定应用语义和缓冲拥有权，再验证 provider 能力与完成保证；随后建立正确的 Eager / Rendezvous 路径，测量冷/热注册和接收就绪条件；最后在缓冲、CPU、尾延迟约束下选择阈值，并扫描 chunk 与 window。

**不要从一个环境变量开始设计协议。** 阈值是测量和约束的结果，不是正确性、进展与生命周期的替代品。
