# Inline、Batching 与 Doorbell 优化

> [[4.15 Signaled Unsignaled WR]] 砍掉了"每条完成的成本"，本篇砍"每次提交的成本"。小消息发送的固定开销有三笔：**一次 doorbell MMIO、网卡取 WQE 的一次 DMA 读、网卡取数据的又一次 DMA 读——消息只有几十字节时，这三笔 PCIe 账远大于数据在网线上的时间**。三个手法各砍一笔：inline 把数据拷进 WQE、省掉取数的 DMA；postlist 把一批 WR 链成链表一次提交、把 N 次门铃摊成 1 次；signaled 节奏（上一篇）把 CQE 也除以 N。这些优化全部只动"数据怎么进网卡"的路径，对端看到的语义一个比特都不变。

前置：[[4.15 Signaled Unsignaled WR]]（批的另一半：回收节奏）、[[0.4 PCIe BAR MMIO 与 MSI-X]]（MMIO 与 posted write——doorbell 的物理载体）、[[0.1 CPU Cache Cache Line 与内存屏障]]（WQE 就位与门铃的先后为什么需要屏障）。

## 1. 先拆账：一次小消息发送到底花在哪

先把名词说直白。**doorbell（门铃）**：网卡把自己的一小段寄存器通过 PCIe BAR 映射进进程地址空间（MMIO，[[0.4 PCIe BAR MMIO 与 MSI-X]]），软件往这个地址写一个值，就等于敲门告诉网卡"队列里有新活了"。**DMA 读**：网卡自己发起 PCIe 读，把主存里的内容（WQE、数据）拉到卡上——CPU 不参与，但一来一回是完整的 PCIe 往返。

一次普通 SEND/WRITE 的提交路径（[[4.3 QP WQE CQ 状态机]] §3 的前四站），按"谁在付钱"记账【事实/量级】：

| 步骤 | 是什么 | 量级 |
| --- | --- | --- |
| ① 填 WQE | 普通用户态内存写 | ~ns，可忽略 |
| ② doorbell | uncached MMIO store，穿过 PCIe | 每次固定成本，几十至几百 ns |
| ③ 网卡 DMA 读 WQE | PCIe 读往返 ×1 | 数百 ns |
| ④ 网卡 DMA 读 data buffer | PCIe 读往返 ×2（按 lkey 查表取数，[[4.4 内存注册与零拷贝]]） | 数百 ns |
| ⑤ 分段封包上线 | 网卡硬件流水 | 64 B 消息在 100 Gbps 线上只占约 5 ns |

结论一眼可见：**小消息的延迟大头在②③④这三笔 PCIe 账，不在网线**。而且②③④是每条消息的固定成本——消息率（Mpps）的天花板由它们决定，跟链路带宽关系不大。三个手法与三笔账一一对应：

## 2. IBV_SEND_INLINE：数据搭 WQE 的车

**定义【事实】**：`send_flags` 带上 `IBV_SEND_INLINE`，`ibv_post_send` 内部由 **CPU 把数据拷进 WQE 本体**；网卡取 WQE 时（③）数据已经捎带在里面，第④步整个消失。

由此推出的五条细则，每条都有直接的工程后果：

1. **buffer 立即解锁【事实】**：数据在 `post_send` 返回前已离开你的 buffer，所有权不再移交网卡——post 返回即可改写/释放。[[4.15 Signaled Unsignaled WR]] 的 buffer 账对 inline WR 当场销账，这是小消息栈上临时 buffer 能直接发的原因；
2. **lkey 不被检查【事实】**：网卡不再按 lkey 取数，inline 的 buffer 甚至**可以不在任何注册过的 MR 里**。但注意：同一条代码路径若可能回退到非 inline（超长时），回退分支仍需要合法 lkey；
3. **只对 SEND 与 RDMA WRITE 有意义【事实】**：READ/ATOMIC 的数据流向是回程的，没有"捎带"可言；
4. **上限是 `max_inline_data`【事实/实现】**：创建 QP 时在 `ibv_qp_init_attr.cap.max_inline_data` 里**请求**，设备在返回的 cap 里给出**实际值**——两者可以不同，实际值是设备与 WQE 布局决定的，常见几十到几百字节量级（以创建返回为准，不要写死）。超限的 inline post 直接报错；
5. **方向要想清楚【取舍】**：inline 是**用一次 CPU 拷贝换一次 PCIe DMA 往返**——与"零拷贝"的方向相反。消息越大，CPU 拷贝越亏、PCIe 往返占比越低，交叉点在自己的机器上用 `ib_write_lat` 扫出来（§5）。

**语义不变【事实】**：inline 只改数据进网卡的方式。线上的包、对端网卡与对端软件的行为、可靠性保证，全部与非 inline 一致——对端根本无从得知你是否 inline。

## 3. Postlist 与门铃合并：N 次 MMIO 摊成 1 次

`ibv_post_send` 的第二个参数本来就是**链表**：`ibv_send_wr.next` 把一批 WR 串起来，一次调用全部提交。主流 provider 的实现里，**一次调用只在链表末尾敲一次门铃**【实现】——这就是 postlist（perftest 的 `-l/--post_list` 参数名的出处）。

为什么敲一次就够【实现】？门铃写的不是"来了几条"，而是**"生产者指针指到哪了"**——SQ 是环形队列，网卡拿到新的队尾位置，就会把上次位置到新位置之间的所有 WQE 依次取走。所以最后一次门铃天然覆盖整批。这与 NVMe 的 SQ tail doorbell 是同一个形状（[[3.2 Queue Pair 与 Doorbell]]），门铃协议在两个世界里完全同构。

配套的两个细节：

- **屏障由 verbs 内部负责【实现】**：门铃必须在所有 WQE 内容对设备可见之后到达（否则网卡取到写了一半的 WQE）。`ibv_post_send` 内部已经含有这道写屏障——应用层**不需要**手工加 `std::atomic_thread_fence`；只有绕开 verbs 自己写驱动的人才碰这个问题（[[0.1 CPU Cache Cache Line 与内存屏障]]）；
- **批与回收对齐【实践】**：批尾那条 WR 顺手标 `IBV_SEND_SIGNALED`，让"门铃单位 = 回收单位"——一批一次门铃、一条 CQE，两本账用同一个节奏（[[4.15 Signaled Unsignaled WR]] §4）。

**代价【取舍】**：门铃在链表末尾才响，批内靠前的 WR 白等了"凑批"的时间。吞吐型路径（复制流、日志下刷）随便攒；延迟敏感路径（前台请求）**不要手工攒批**——有几条发几条，攒批留给本来就成批到达的活。

厂商还有更激进的一档【实现】：mlx5 的 BlueFlame 把小 WQE 直接通过 write-combining MMIO 写进网卡，连③的 WQE DMA 读都省掉。这是 provider 内部依据消息大小自动选择的路径，应用层无感知，知道它存在即可——也是"为什么同型号网卡小消息延迟出奇地低"的常见答案。

## 4. 测量：把三个手法各自的收益钉死

原则沿用 [[4.9 ibv_perftest 基准实验]]：一次只动一个变量。

| 实验 | 命令对照 | 观察指标 | 预期形状 |
| --- | --- | --- | --- |
| inline 交叉点 | `ib_write_lat -s <size>`，`--inline_size 0` vs 默认，size 从 8 B 扫到 1 KB | 单向延迟 | 小消息 inline 明显更低；随 size 增大差距收窄直至反超——交叉点就是你代码里该设的 inline 阈值 |
| 门铃摊薄 | `ib_write_bw -s 8 -l 1` vs `-l 32` | Mpps 与发送侧 CPU | 消息率上升、单核 Mpps 上升；带宽不变（8 B 远不到线速） |
| CQE 节奏 | 同上加 `--cq-mod 1` vs `--cq-mod 16` | Mpps 与 CPU | 与 [[4.15 Signaled Unsignaled WR]] §4 的 1/N 收益对上 |

注意两个口径陷阱【实践】：perftest 的延迟类工具**默认开启小消息 inline**（`--inline_size` 控制，默认值随版本变化）——对比前先把它显式固定；在 soft-RoCE（rxe）上做这组实验没有意义——rxe 没有真实的 PCIe 门铃与 DMA，量的全是内核软件路径（[[4.8 soft-RoCE 边界]]）。

## 5. 实践模板（Modern C++）

攒一批小消息、inline + postlist + 批尾 signaled 一次提交：

```cpp
#include <infiniband/verbs.h>

#include <cstdint>
#include <span>
#include <stdexcept>
#include <system_error>
#include <vector>

// 一批 = 一次 post_send = 一次门铃 = 一条 CQE（批尾 signaled）。
// wr 内部指针在 flush 时才互相链接，所以 vector 扩容不影响正确性。
class BatchSender {
public:
    BatchSender(ibv_qp& qp, std::uint32_t max_inline)
        : qp_{&qp}, max_inline_{max_inline} {}   // max_inline 用创建 QP 返回的实际值

    // inline 的 msg 在 flush 返回后即可失效；
    // 超限走非 inline 的，必须活到本批 CQE 被收割（4.15 的 buffer 账）
    void add(std::span<const std::byte> msg, std::uint32_t lkey) {
        ibv_sge sge{};
        sge.addr   = reinterpret_cast<std::uintptr_t>(msg.data());
        sge.length = static_cast<std::uint32_t>(msg.size());
        sge.lkey   = lkey;                       // inline 不查 lkey，但回退分支需要
        sges_.push_back(sge);

        ibv_send_wr wr{};
        wr.opcode     = IBV_WR_SEND;
        wr.send_flags = sge.length <= max_inline_ ? IBV_SEND_INLINE : 0;
        wrs_.push_back(wr);
    }

    // first_seq：本批第一条的序号，接 4.15 SendRing 的水位记账
    void flush(std::uint64_t first_seq) {
        if (wrs_.empty())
            return;
        for (std::size_t i = 0; i < wrs_.size(); ++i) {
            wrs_[i].wr_id   = first_seq + i;
            wrs_[i].sg_list = &sges_[i];
            wrs_[i].num_sge = 1;
            wrs_[i].next    = i + 1 < wrs_.size() ? &wrs_[i + 1] : nullptr;
        }
        wrs_.back().send_flags |= IBV_SEND_SIGNALED;

        ibv_send_wr* bad = nullptr;
        if (int rc = ibv_post_send(qp_, wrs_.data(), &bad); rc != 0) {
            // 部分成功：bad 之前的 WR 已经入队，在途账必须记到 bad 为止，
            // 不能把整批当失败重发——否则入队的那部分会被发两遍
            const auto posted = static_cast<std::size_t>(bad - wrs_.data());
            wrs_.clear();
            sges_.clear();
            throw std::system_error{rc, std::system_category(),
                                    "ibv_post_send（已入队 " +
                                        std::to_string(posted) + " 条）"};
        }
        wrs_.clear();
        sges_.clear();
    }

private:
    ibv_qp* qp_;
    std::uint32_t max_inline_;
    std::vector<ibv_send_wr> wrs_;
    std::vector<ibv_sge> sges_;
};
```

## 6. 排障清单：症状 → 原因 → 检查

| 症状 | 常见原因 | 检查动作 |
| --- | --- | --- |
| 带 `IBV_SEND_INLINE` 的 post 返回错误 | 消息长度超过 `max_inline_data` **实际值** | 打印创建 QP 返回的 `cap.max_inline_data`（不是你请求的值）；超限分支回退非 inline |
| inline 打开了但延迟没降 | 阈值取了请求值而非实际值导致从未生效；或瓶颈本来在网络/对端 | 同上核对实际 cap；用 §4 实验一确认本机收益形状 |
| 大消息吞吐反而下降 | inline 的 CPU 拷贝成本压过 PCIe 收益 | 只对小于交叉点的消息 inline；交叉点实测（§4） |
| 回退非 inline 路径报 `IBV_WC_LOC_PROT_ERR` | inline 时没人查 lkey 掩盖了坏 lkey，回退后暴露 | 回退分支必须携带合法 lkey / buffer 在 MR 内（[[4.4 内存注册与零拷贝]]） |
| 小消息 Mpps 上不去，发送核 CPU 打满 | 每条一次门铃 + 每条一条 CQE | postlist（`-l`）与 `--cq-mod` 一起上；对照 §4 实验二、三 |
| 上了 postlist 后 p99 变差 | 凑批等待 + 突发批注入放大排队 | 批加"限时又限量"两条上限；延迟敏感路径不攒批（§3 取舍） |
| 整批 post 失败后消息重复送达 | 部分成功当整批失败重发（`bad_wr` 之前的已入队） | 按 `bad_wr` 位置切分：之前的只记账，之后的才重发（§5 代码注释） |
| 在 rxe 上测不出任何差异 | soft-RoCE 没有真实 PCIe 路径，这些优化作用的层不存在 | 换真网卡测；rxe 只用来验证功能与语义（[[4.8 soft-RoCE 边界]]） |
| 偶发发出改了一半的数据（非 inline） | buffer 在 CQE 收割前被复用——不是屏障问题 | 回到 [[4.15 Signaled Unsignaled WR]] 的 buffer 账；verbs 内部屏障已保证 WQE 与门铃的顺序，不要往应用里加 fence 掩盖问题 |

## 7. 陷阱与误区

> [!warning] 常见错误
> 1. **把 inline 当"零拷贝"**：方向恰好相反——inline 是**多**一次 CPU 拷贝，省的是网卡的 DMA 读。RDMA 的零拷贝叙事（[[4.4 内存注册与零拷贝]]）说的是跳过内核协议栈拷贝，两码事。
> 2. **拿请求值当 `max_inline_data`**：请求 256 可能拿到 0（设备不支持）也可能拿到更大值；一切以创建 QP 返回的 cap 为准。
> 3. **忽略 `bad_wr` 的部分成功语义**：postlist 失败时之前的 WR 已入队，整批重发 = 重复消息。这是 postlist 相对逐条 post 唯一新增的错误处理负担。
> 4. **在延迟敏感路径手工攒批**：postlist 是吞吐工具。为了摊一次几十 ns 的门铃，让前台请求多等几微秒的凑批时间，是亏本买卖。
> 5. **给 verbs 应用手工加内存屏障**："WQE 先就位、门铃后响"由 `ibv_post_send` 内部保证；应用层的 fence 既无必要，还会掩盖真正的 bug（多半是 buffer 提前复用）。
> 6. **用 soft-RoCE 的数据外推硬件行为**：rxe 上门铃与 DMA 都是模拟的，inline/postlist 的数字没有参考价值。

## 8. 关键结论

| 结论 | 性质 |
| --- | --- |
| 小消息的成本大头是三笔 PCIe 固定账：doorbell MMIO、WQE DMA 读、数据 DMA 读——Mpps 天花板由它们决定，与带宽无关 | 事实 / 量级 |
| inline = CPU 拷贝换数据 DMA：buffer 立即解锁、lkey 不查、仅 SEND/WRITE、上限以创建返回的 cap 为准 | 事实 |
| inline 与 postlist 都只改提交路径，对端可见语义一个比特不变 | 事实 |
| 门铃写的是生产者指针，最后一响覆盖整批——postlist 因此把 N 次 MMIO 摊成 1 次；与 NVMe tail doorbell 同构 | 实现 |
| 屏障由 verbs 内部负责，应用不加 fence；BlueFlame 类捷径由 provider 自动选择 | 实现 |
| 批 = 门铃单位 = 回收单位（批尾 signaled）：与 4.15 的节奏对齐成一套 | 实践结论 |
| 吞吐路径攒批、延迟路径不攒；inline 阈值与收益必须在真硬件上实测 | 取舍 |
