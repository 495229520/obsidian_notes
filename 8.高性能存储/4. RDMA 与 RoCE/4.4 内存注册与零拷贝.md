# 内存注册与零拷贝

> **注册缓存缓存的是“仍然成立的 DMA 映射及其资源”，不是“这个地址曾经注册成功”的历史记录。** 一个可复用的 MR 必须同时满足：底层分配仍是同一代、设备与 PD 仍是同一代、区间与注册语义兼容、条目没有进入失效流程。释放 MR 则还需要证明：没有新的借用、没有在途 DMA、没有未撤销的远端授权，且后端已经允许回收。

本篇保留“虚拟地址 → 注册 → 零拷贝 → 生命周期”的主线，把注册缓存细化为可实现的契约。[[4.12 rkey lkey 生命周期]] 负责另一半：**注册还活着时，某个对象的远端授权为什么可能已经过期，以及怎样撤销它。**

> [!info] 口径与版本
> 【接口】表示 rdma-core 手册规定的行为；【实现】表示指明版本的实现；【设计】表示本篇提出的保守工程方案，不是声称 UCX 或所有 RNIC 都这样实现。基础路径以 Linux 用户态、普通主机内存、显式 MR、RC 为主。ODP、DMA-BUF、GPU 内存和特殊 provider 必须单独核对能力，不能直接套用全部 pin、回调或失效假设。

## 1. 先澄清：注册究竟登记了什么

CPU 指针是虚拟地址。CPU 通过进程页表访问内存；RNIC 发起 DMA 时，依赖自己的内存访问权限与地址翻译，以及平台的 DMA/IOMMU 映射。**CPU 的虚拟地址、设备看到的 IOVA、物理地址不应画成无条件相等。**

普通长期注册的核心工作可以分成三部分：建立底层页面的稳定引用；为设备建立地址翻译；建立关联 PD、范围、权限的访问凭据。Linux 将 RDMA 的长期 DMA pin 与普通短期 DIO pin 区分；带 MMU notifier 或可重放设备缺页的路径又有不同同步方式。不能把“所有 RDMA 都永久钉页”当成定义。[^pin]

`ibv_reg_mr(pd, addr, length, access)` 返回 MR。`lkey` 用于本端 SGE，`rkey` 用于远端发起的 RDMA/Atomic。`REMOTE_WRITE` 或 `REMOTE_ATOMIC` 要求同时具有 `LOCAL_WRITE`；本地读访问默认允许。`ibv_reg_mr_iova` 还允许指定设备访问时的基址，因此 descriptor 里的地址未必等于应用的 CPU 指针。[^reg]

![[图片/SVG/8_4_4_4_1_rcache.svg|900]]

图中有两条独立链：**所有权链**保证底层内存活着；**授权链**决定设备现在还能访问哪里。命中地址区间只完成了查找，不等于这两条链都成立。

### 1.1 零拷贝不是零成本，也不是免检查

零拷贝通常省掉中间缓冲的 CPU 数据搬运；数据仍要经过内存系统、PCIe 或设备互连，提交与完成也仍有固定开销。实际收益取决于所省的拷贝、消息大小、注册能否摊销和拓扑，不能把某个 TCP 路径的“省两次拷贝”推广成所有路径的固定数字。

MR 注册/注销涉及资源管理，不应在没有测量的情况下承诺固定微秒或毫秒数。可先建立成本模型【设计】：

\[
T_{cached}=T_{lookup}+T_{lease}+(1-h)T_{reg}+T_{transfer}+T_{completion}+T_{maintenance}
\]

这里 `h` 是有效命中率；`T_maintenance` 是按请求摊销的失效与回收成本。只统计“地址查到了”而不统计权限不兼容、失效命中、注册等待，不是有效命中率。

## 2. 必须拆开的四种生命周期

| 对象 | 身份例子 | 何时结束 | 不能替代的保证 |
| --- | --- | --- | --- |
| 底层分配 backing allocation | `(allocation_id, allocation_epoch)` | 真正释放、重映射或设备分配销毁 | VA 相同不代表同一分配 |
| MR / 注册条目 | `(context_epoch, pd_epoch, registration_id)` | 注册后端确认注销 | `shared_ptr` 活着不代表 MR 仍有效 |
| 池内逻辑对象 / slot | `(object_id, object_generation)` | 对象交还、换用途、授权边界改变 | 整个池没有 free，也可能发生逻辑 ABA |
| 远端授权 grant | `(owner_incarnation, session_epoch, grant_id, generation)` | 完成撤销与排空 | MR 仍有效不代表旧 grant 仍有效 |

**池内 slot 每次借还，不必让整个池的注册缓存失效。** 注册缓存的 generation 标识底层分配；slot 的 generation 标识业务对象。混用两者，要么丢失 ABA 防护，要么每次借还都重新注册，失去缓存意义。

## 3. 缓存键：地址是检索条件，分配身份才是正确性条件

### 3.1 一个保守的键空间

下面是设计字段，不是 UCX 的实际结构体布局：

| 字段组 | 至少区分什么 | 省略后的故障 |
| --- | --- | --- |
| 设备域 | context 实例 ID、重建 epoch、provider / 注册路径 | 重连设备后复用旧 lkey；多 NIC 误命中 |
| 保护域 | PD 实例 ID + 生命周期 epoch；必要时租户域 | PD 指针地址复用；跨隔离域命中 |
| 内存身份 | Host / GPU / DMA-BUF；allocation ID + epoch | 同 VA 的不同底层分配误命中 |
| 注册范围 | 归一化后的半开区间 `[start,end)` | 只比较起点而忽略越界 |
| 地址语义 | CPU VA 与设备 IOVA 的映射、zero-based 模式 | 把偏移当绝对地址提交 |
| 注册语义 | ODP、relaxed ordering、必要 access flags 等 | 属性不同的 MR 被当成同一个 |

键中的 context、PD、allocation 标识应来自受控对象管理器，**不能直接用可复用的裸指针值充当永久身份**。DMA-BUF 的 fd 数字也可能复用；只缓存 fd 数字不足以证明底层对象没变。

### 3.2 命中判据不是 `map.find(addr)`

一个条目覆盖请求区间，还必须逐项通过：

1. 查找与增加借用引用处在同一个线性化点，条目仍是 `READY/IDLE`。
2. backing 身份与 epoch 相同；没有已发布的失效事件或 tombstone。
3. context / PD / 隔离域、内存类型与 IOVA 语义一致。
4. 请求区间完全被注册区间覆盖；没有算术溢出。
5. access 足够，其他影响语义的 flags 兼容。

区间检查先验证 `length` 不溢出，再计算终点。普通 `ibv_reg_mr` 允许非页对齐用户地址；缓存向页边界扩展是实现策略，**不代表可以擅自覆盖邻接分配或扩大远端授权范围**。扩展注册必须拥有整个扩展区间的有效 backing 和相应授权策略。

### 3.3 权限超集能不能复用

在同一信任域、后端允许且其他语义相同时，`available_access` 覆盖 `requested_access` 可以作为命中条件；但“请求只读，命中了可写 MR”意味着这个 MR 的 rkey 可能仍有写权限。**descriptor 里写 `READ_ONLY` 不会自动收窄 RNIC 的权限。**

安全敏感场景应按权限分桶、使用独立 MR，或在大 MR 上创建受限 MW。ODP、zero-based、relaxed ordering 等也不能一律按“位越多越兼容”处理。没有明确的兼容性证明时，采用精确匹配。

## 4. 引用计数：至少需要三本账

| 账本 | 加引用的时刻 | 减引用的时刻 | 常见误判 |
| --- | --- | --- | --- |
| `lease_refs` | 查找成功，允许应用持有/准备提交 | 应用归还该 lease | 应用不再使用 ≠ RNIC 不再使用 |
| `wr_refs` | 提交前预留；为成功提交的 WR 保留 | 对应完成/已证明安全的 teardown 结算 | `post_send` 返回成功 ≠ 完成 |
| `grant_refs` | descriptor 可能对外发布之前 | grant 的撤销状态机真正结束 | 本端 CQ 空 ≠ 远端没有单边访问 |

另外记录 `bound_mw`、正在进行的注册/注销操作、等待者和元数据引用。**容器引用、C++ 对象引用、设备使用引用、远端授权引用不可混成一个没有定义的 `use_count()`。**

`grant_refs` 是授权账本，不是远端每条 WRITE 的计数器。普通远端 WRITE 不会自动给内存所有者产生一条可用于计数的本地接收 CQE。持有 grant 的对端可以将来再提交，因此即使当前估计没有远端 DMA，也不能随意回收。

![[图片/SVG/8_4_4_4_2_refs.svg|900]]

时间轴说明了“lease 已归还但 WR 未完成”的窗口。引用必须先保留再提交；否则另一个线程可能已经把 MR 注销，随后才执行加引用。

### 4.1 提交失败必须按实际接受的前缀结算

`ibv_post_send` 可提交一串 WR；遇到可立即检测的错误时停止，并通过 `bad_wr` 返回失败位置。成功提交的前缀仍在途，不能因为整个调用返回错误就全部减引用。[^post]

【设计】先为候选 WR 预留账目，提交后只撤销未提交的后缀；成功前缀由完成路径释放。也可逐个提交简化最小实验，但不要把逐个提交的假设带到批量版本里。`bad_wr` 的语义和后端特殊快速提交接口必须分别核对。

### 4.2 完成的三个边界

**本端 DMA 结束**、**远端内存可见**、**远端业务已消费**是不同的契约。普通非 inline 源/目的缓冲必须遵守 WR 完成后的复用规则；inline SEND/WRITE 的源数据已复制进 WQE，是源缓冲可在成功提交后复用的特殊情况，并不缩短远端目标 MR 的授权寿命。[^post]

为了让第一版账本可验证，先全部使用 signaled WR，逐个按请求 ID 结算。优化为 unsignaled 后，必须依据同一 SQ、操作种类、排序与必要 fence 条件建立完成水位；**一个 QP 的 CQE 不是其他 QP 的全局排空证明**。RDMA READ、Atomic 和写后通知的顺序问题转到 [[4.13 RDMA 操作顺序性]] 核对，不把“后面任意一个 signaled CQE”当万能栅栏。

出现错误 CQE 时，只使用该状态下有效的字段。手册规定非成功完成仅保证 `wr_id/status/qp_num/vendor_err` 有效；不要从失败 CQE 的无效 opcode 或长度推断应该释放哪一代资源。[^cq]

## 5. 地址复用与失效通知：先关入口，再谈销毁

### 5.1 两类 ABA 必须分别测试

**物理映射 ABA：** `mmap A → reg(A) → munmap A → mmap B at same VA`。新 CPU 指针数值不变，但缓存的 MR 可能仍代表旧底层分配。pin 是内核页面引用，不会替应用维持“这个 VA 仍然代表原来的业务对象”。

**池内逻辑 ABA：** 大池一直不释放；slot 先给请求 X，再给请求 Y。整个 MR 映射完全正确，但远端 X 保存的旧 rkey + 地址仍可能写到 Y。注册缓存对此未必有任何可见事件，应由 [[4.12 rkey lkey 生命周期]] 的对象 generation 与硬件授权边界处理。

![[图片/SVG/8_4_4_4_3_aba.svg|900]]

上半图改变的是 backing；下半图改变的是对象用途。前者需要注册缓存失效，后者需要 grant 失效，不能互相替代。

### 5.2 通知从哪里来

| 事件源 | 能观察什么 | 不能直接保证什么 |
| --- | --- | --- |
| 自己的 allocator / 内存池 | 分配、释放、slot 复用、owner token | 外部绕过该 allocator 的操作 |
| 内存管理 hook | 覆盖范围内的 free / unmap / memory-type-free | 所有 allocator、直接 syscall、所有 GPU 路径均被覆盖 |
| 驱动级 MMU notifier | 地址映射相关变化，与驱动协作 | 用户态任意 MR 自动具备相同同步语义 |
| GPU / DMA-BUF 对应生命周期机制 | 特定设备内存或导出对象的变化 | Host free hook 足以保护设备分配 |

【实现】UCX `v1.19.0` 的 rcache 接口明确包含 `UCM_EVENT_VM_UNMAPPED`、`UCM_EVENT_MEM_TYPE_FREE`、注册/注销回调、region 引用计数与失效完成回调。它还规定：失效完成回调不能执行可能重新访问 rcache 的操作。这里能学到的是事件、引用、回调的分离；不能据此断言“任意用户 free 都已安全地阻塞到 DMA 完成”。[^ucx]

### 5.3 同步失效，异步回收

【设计】失效回调的第一阶段必须与查找/提交入口同步：发布 tombstone 或增加失效序号，将匹配条目标成 `INVALIDATING`，从可命中索引删除，阻止新 lease 与新 grant。然后把撤销、排空、注销交给允许调用后端的工作线程。

**从索引摘除，不等于可以马上 free。** 队列里仍要持有条目和 backing 的强所有权；旧借用者可能还在结束操作。耗时等待不应发生在 allocator 锁、注册缓存全局锁或 provider 回调内部，否则可能等待那个被自己阻塞的 CQ/progress 线程。

> [!warning] 异步通知不自动解决生命周期
> 若调用者已经允许底层内存真实释放/复用，后台线程稍后才收到事件，就无法倒退时间保护此前的 DMA。需要受控的 deferred-free、明确的 pre-release 协议，或有已验证同步保证的驱动机制。无法保证时，缓存应拒绝这类外部内存，改用受控预注册池或受控的非缓存注册租约。仅关闭缓存也不能允许用户在 DMA 期间 free。

### 5.4 注册正在进行时收到失效怎么办

需要防止“旧注册晚返回，再被重新插入缓存”：

| 时间 | 注册线程 | 失效/所有者线程 |
| --- | --- | --- |
| t0 | 持有 backing；创建 `REGISTERING` 占位，记录 allocation epoch 与失效序号 | 仍禁止物理释放 |
| t1 | 锁外调用注册后端 | 发布失效；占位条目进入不可发布状态 |
| t2 | 注册成功返回 | 不等待全局锁里的后端操作 |
| t3 | 重取锁，复核身份、序号、状态 | 旧 epoch 永不恢复为可命中 |
| t4 | 若不匹配，把新得到的 MR 送回收队列，不发布给等待者 | 后端注销确认后才释放 backing |

同一区间并发 miss 使用 single-flight 占位与等待者通知，避免重复注册。等待者被唤醒后仍重新验证，不直接信任“有人刚刚注册成功”。重叠区间的合并/拆分也要遵守同样的发布规则；第一版允许不合并，优先证明正确性。

## 6. 可检查的缓存状态机

| 当前状态 | 事件 / 守卫 | 动作 | 下一状态 |
| --- | --- | --- | --- |
| `ABSENT` | 可持有稳定 backing，额度足够 | 建占位，记录身份和失效序号 | `REGISTERING` |
| `REGISTERING` | 注册成功且复核通过 | 原子发布到索引，唤醒等待者 | `READY` |
| `REGISTERING` | 注册失败 | 记录失败，通知等待者；处理部分资源 | `DEAD` 或 `QUARANTINED` |
| `REGISTERING` | 期间发生失效 | 禁止发布；成功返回的 MR 也必须回收 | `INVALIDATING` |
| `READY` | 所有业务引用归零且无保留 grant | 加入可淘汰集合，仍可重新命中 | `IDLE` |
| `IDLE` | 合法 acquire | 从空闲集合移出并增加 lease | `READY` |
| `READY/IDLE` | 失效或选为淘汰对象 | 关入口、移出索引；持有 backing | `INVALIDATING` |
| `INVALIDATING` | tombstone 可见，新提交入口已关闭 | 撤销 grant，排空/终止旧访问 | `DRAINING` |
| `DRAINING` | 下方注销谓词成立 | 将注销任务交给唯一回收者 | `DEREGISTERING` |
| `DEREGISTERING` | 后端确认注销成功 | 清 MR 句柄；按所有权策略释放 backing | `DEAD` |
| 任一退出阶段 | 超时、撤销失败、设备状态不明 | 保留内存与账本，阻止复用，告警 | `QUARANTINED` |

`IDLE` 是性能状态，`INVALIDATING` 是单向正确性边界。**同一 registration_id 一旦失效，就不能靠新引用把它复活；新注册产生新身份。**

图中的回收门由多个独立条件组成。LRU 决定“先尝试谁”，不能越过安全门。

### 6.1 注销谓词：代码审查可以逐项核对

**本节的保守守卫用于“缓存父 MR，先退休子 grant / MW”这条路线。** 父 MR 的完整 rkey 不对外发布，因而可以先把所有子授权结清，再注销父 MR。若独立普通 MR 的 `dereg` 本身就是撤销动作，应由唯一 retirement 对象持有尚未结束的授权和 backing，排空后执行注销，成功后再结清该授权；不能同时要求“grant 已撤销才能 dereg”和“只有 dereg 才能撤销 grant”。两条路线的守卫差异见 [[4.12 rkey lkey 生命周期]] §5.4。

下方三个 C++17 代码块依次拼接即为完整的纯逻辑测试程序；**它不调用 verbs，不模拟真实硬件时序**。生产中的字段需要在同一同步协议下读取；这里用值对象隔离检查逻辑。

```cpp
#include <cstdint>
#include <iostream>
#include <stdexcept>

enum class CacheState { Ready, Idle, Draining, Deregistering,
                        Dead, Quarantined };
struct EntryView {
    CacheState state{CacheState::Ready};
    bool indexed{true}, backing_owned{true}, backing_current{true};
    std::uint64_t lease_refs{}, wr_refs{}, grant_refs{};
    std::uint64_t bound_mw{}, backend_ops{};
    bool no_future_remote{false}, transport_quiesced{false};
};

bool can_acquire(const EntryView& e) {
    return (e.state == CacheState::Ready || e.state == CacheState::Idle)
        && e.indexed && e.backing_owned && e.backing_current;
}
bool may_deregister(const EntryView& e) {
    return e.state == CacheState::Draining && !e.indexed
        && e.backing_owned && e.lease_refs == 0 && e.wr_refs == 0
        && e.grant_refs == 0 && e.bound_mw == 0 && e.backend_ops == 0
        && e.no_future_remote && e.transport_quiesced;
}
```

`no_future_remote` 是“已撤销相关硬件权限，或已消除所有可访问路径”的证据；`transport_quiesced` 是“已经接受的访问也结束或被证明终止”的证据。**二者不是定时器到期后随手置位的布尔变量。** 对从未对外授权的本地 MR，前者可以由“从未发布过 rkey”这一可审计事实满足；后者仍须结清本端 WR。

## 7. 淘汰、资源预算与 RAII 的真实边界

### 7.1 只把安全候选交给 LRU

同时限制注册区域数、注册字节、空闲字节、隔离字节与后端任务数。`registered_bytes` 应说明是 MR 范围之和还是去重后的物理页估计；重叠 MR 会让二者不同，不能把两项直接相减。硬件翻译表和系统 pin 资源也不只是一个字节计数。

达到高水位后，选择空闲候选，先原子摘除再回收，尝试降到低水位。只要有本地 WR、未撤销 grant、绑定 MW 或后端操作，就跳过该条目。**没有可安全淘汰的条目时返回背压，而不是突破上限继续无限注册。** 超大且一次性使用的区域可以采用“不进入长期缓存”的受控租约，避免扫描污染。

### 7.2 析构顺序不能证明没有 DMA

RAII 适合表达：PD/context 比 MR 活得久，MR 比 backing 的实际释放活得久；请求持有注册资源直到完成。但是析构函数不能代替撤销协议，也不能用一次失败的 `ibv_dereg_mr` 后继续 free。手册规定，仍绑定 MW 时注销 MR 会失败；注销函数也有错误返回。[^reg]

【设计】提供显式 `close_async()` 或 `retire()`：先关入口和排空，成功注销后才进入已关闭状态。失败时把包含 MR 与 backing 的完整资源包移入 quarantine；析构仅处理已证明安全的对象。需要 fail-stop 的程序可选择终止进程并走设备/进程清理流程，但不能捕获错误后继续运行并复用那块内存。

这里的“backing_owned”必须是对真正分配的所有权，不是随手给外部指针套一个空 deleter 的 `shared_ptr`。

## 8. 边界扩展：ODP、fork、GPU 与大页

**ODP：** 改变按需映射与缺页机制，不取消授权生命周期、对象 generation 或在途访问约束。是否完全免预 pin、哪些资源计费、首次访问代价如何，取决于具体路径；不要承诺“注册瞬间返回、永不占资源”。[^reg][^pin]

**fork：** fork/COW 与已注册内存的交互需要核对内核、rdma-core 和 provider。受控进程模型可禁止 fork；需要 fork 的程序应按 `ibv_fork_init` 等接口文档设计，而不是假定所有平台都统一执行某条 `MADV_DONTFORK` 路径。即使 fork 安全，缓存失效和 DMA 生命周期仍须正确。[^fork]

**GPU / DMA-BUF：** Host VA 的缓存键不能直接推广到 GPU 分配；显存 context、allocation ID、导出对象、注册机制和失效回调都可能影响身份。`ibv_reg_dmabuf_mr` 明确有 offset、length、IOVA 与 fd 参数。具体 peer-memory / DMA-BUF 能力须以设备环境验证为准；本篇不把“装了某个模块就一定支持”当结论。[^reg]

**大页：** 大页可能减少翻译条目、改善注册成本，但实际收益还取决于物理布局和 provider。它不会自动解决授权过宽、slot 复用或失效通知问题。

## 9. 最小故障注入与观测清单

| 编号 | 注入场景 | 必须观察到的结果 |
| --- | --- | --- |
| C1 | lease 归还，WR 故意不完成 | 禁止注销；`wr_refs` 保留 |
| C2 | 同 VA 换 allocation epoch | 查找 miss / stale reject，不返回旧 MR |
| C3 | 注册后端暂停，期间触发 invalidate | 注册返回后禁止发布；只有一次安全回收 |
| C4 | 多线程相同区间同时 miss | single-flight 或可解释的去重；无资源泄漏 |
| C5 | 五个 WR 中第三个提交失败 | 已接受前缀保持在途；后缀正确回滚 |
| C6 | MR 没有本端 WR，但 grant 仍存在 | 不进入可复用状态 |
| C7 | 绑定 MW 时尝试关闭 | 先处理 MW；不因 dereg 失败而 free |
| C8 | 失效回调内触发 allocator 重入 | 不出现锁递归死锁或缓存复活 |
| C9 | 空闲条目不足，达到容量上限 | 背压/拒绝，不侵占在途条目 |
| C10 | 设备丢失、CQ 错误或排空超时 | quarantine；不凭超时猜测安全 |
| C11 | 重复完成通知或重复 put | 请求账本至多结算一次，无下溢 |
| C12 | MR/PD 指针数值复用 | epoch 不匹配，旧条目不命中 |

上表是实验验收条件，不是声称已在 RNIC 上执行。下列纯逻辑用例验证 §6 的守卫：

```cpp
int checks = 0;
void expect(bool ok) {
    if (!ok) throw std::runtime_error("cache guard failed");
    ++checks;
}
EntryView drainable() {
    EntryView e;
    e.state = CacheState::Draining;
    e.indexed = false;
    e.no_future_remote = e.transport_quiesced = true;
    return e;
}
void test_refs() {
    auto e = drainable();
    expect(may_deregister(e));
    ++e.lease_refs; expect(!may_deregister(e)); --e.lease_refs;
    ++e.wr_refs; expect(!may_deregister(e)); --e.wr_refs;
    ++e.grant_refs; expect(!may_deregister(e)); --e.grant_refs;
    ++e.bound_mw; expect(!may_deregister(e)); --e.bound_mw;
    ++e.backend_ops; expect(!may_deregister(e)); --e.backend_ops;
    expect(may_deregister(e));
}
```

这里逐一打开一道“尚未结清”的条件，确认回收门关闭。验证的是逻辑必要条件；真实 `wr_refs/grant_refs` 是否漏记，还要靠请求账本与并发测试。

```cpp
int main() {
    test_refs();
    auto e = drainable();
    e.indexed = true; expect(!may_deregister(e));
    e = drainable(); e.no_future_remote = false;
    expect(!may_deregister(e));
    e = drainable(); e.transport_quiesced = false;
    expect(!may_deregister(e));
    e = drainable(); e.backing_owned = false;
    expect(!may_deregister(e));
    e = drainable(); e.state = CacheState::Quarantined;
    expect(!may_deregister(e)); expect(!can_acquire(e));
    e = EntryView{}; expect(can_acquire(e));
    e.backing_current = false; expect(!can_acquire(e));
    e = EntryView{}; e.state = CacheState::Idle;
    expect(can_acquire(e));
    e = drainable(); expect(!can_acquire(e));
    std::cout << "cache guards: " << checks << " checks passed\n";
}
```

这些代码没有跨线程调用或真实等待，因此不把它们画成伪时序图；真实等待点已在图 2、图 4 中标出。把三块代码按序保存为 `cache_guard.cpp`，使用 `g++ -std=c++17 -Wall -Wextra -Werror -pedantic cache_guard.cpp -o cache_guard` 编译即可。

观测至少包括：有效命中率、miss 原因、注册/注销延迟分布、注册字节口径、空闲/在途/隔离资源、失效队列积压、重复提交/完成、stale backing 拒绝数。日志关联 `allocation_id/epoch → registration_id → wr_id → grant_id`；rkey 和地址按环境进行脱敏，不把完整授权信息写进广泛可读的日志。

## 10. 回到源码：怎样读 UCX 而不照抄一个哈希表

固定阅读版本：**UCX `v1.19.0`，`src/ucs/memory/rcache.h`**。本次核对的 header blob 为 `a1cdc24cdb3695e152f7b5da472adb1034f7af44`。[^ucx]

先看 `ucs_rcache_region`：引用计数包含“仍在页表中”的额外引用。再看 `ucs_rcache_get` / `region_hold` / `region_put`：获取与归还是显式契约。最后看 `region_invalidate` 及其 completion callback：失效与最终释放不是同一时刻。`max_regions/max_size/max_unreleased` 则提示了容量、区域数和待释放资源需要分别考虑。

这些字段足以说明“缓存索引持有资源”与“使用者仍引用资源”是两层。**它们没有自动提供本篇的远端 grant 协议，也不能证明某个自定义 allocator 已被 UCM 完整覆盖。** 移植时应逐项回答：事件从哪里来、谁持有 backing、在途引用是谁释放、回调能否重入、失败后谁负责隔离。

## 11. 最后记住的六条不变量

| 不变量 | 审查问题 |
| --- | --- |
| 地址相同不等于分配相同 | 键中有没有稳定身份与 epoch？ |
| 命中与加引用必须原子化 | invalidate 能否插在两者之间？ |
| 失效条目不得复活 | 注册晚返回会不会重新 publish？ |
| 零业务引用不等于没有 DMA | WR、grant、MW、后端操作是否分别结算？ |
| 超时只能进入故障处理 | 有没有“超时即 free”的路径？ |
| 复用必须有完整证据链 | 软件关入口、硬件撤销、在途排空是否全部落实？ |
