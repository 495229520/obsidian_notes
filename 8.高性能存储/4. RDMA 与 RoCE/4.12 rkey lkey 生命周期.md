# rkey / lkey 生命周期

> **generation 解决“这还是不是那一次授权”；硬件撤销解决“旧授权还能不能驱动 DMA”；排空解决“已经接受的 DMA 是否已经结束”。三个问题必须分别回答。** 增加一个 generation 字段，并不会让 RNIC 自动拒绝携带旧 rkey 的 WRITE。

[[4.4 内存注册与零拷贝]] 把注册缓存分成 backing、MR、逻辑对象与 grant 四种生命周期。本篇把后两种落实成**状态、事件、守卫、证据与失败去向**，重点回答：什么时候拒绝旧 descriptor，什么时候可以复用 buffer，连接重建后哪些东西必须重新确认。

> [!info] 适用范围与标记
> 【接口】是 rdma-core 手册中的语义；【实现】明确给出阅读版本；【设计】是本文的保守协议模型，不是通用 verbs 已经内置的功能。基础对象是 RC 上的普通 MR；Memory Window、内核 fast-registration MR 和特殊 provider 必须单独核对能力。文中的 `freeze / drain / retire` 是系统设计动作，不是同名 verbs API。

## 1. 三种标识：不要把 rkey 当成 generation

| 标识 | 谁创建 / 谁检查 | 说明 |
| --- | --- | --- |
| `lkey` | 注册后端；本端 RNIC 校验本端 SGE | 关联本端注册资源与访问权限，不是跨进程对象 ID |
| `rkey` | 注册 / MW 后端；目标 RNIC 校验远端访问 | 与地址范围、权限、保护域及相应对象类型共同约束访问 |
| 软件 `generation / epoch` | 应用协议；应用提交入口检查 | 标识分配代次、对象代次或会话代次，不能假定硬件检查 |

lkey/rkey 是接口暴露的 32 位值。某些设备内部会把 key 分成表项索引与版本位，但这不是可以跨 provider 编码依赖的通用布局，**也不构成“永不重复”的保证**。普通 MR 应使用注册接口实际返回的 key；Type 2 MW 的 bind WR 则包含应用按该类型规则设置的 `bind_mw.rkey`。不要把不同接口混成“总由后端自动轮换”，也不要自行推定 key 永不重复。[^reg][^mw][^post]

远端 WRITE 的 verbs WR 包含 `remote_addr` 与 `rkey`；本地 SGE 则包含 `addr/length/lkey`。下面定义的软件 generation 不在普通 RDMA WRITE 的目标内存校验字段中。[^post]

![[图片/SVG/8_4_4_12_1_identity.svg|900]]

图中软件门和硬件门是串联而非替代关系。软件门可以拒绝过期任务；已经绕过软件门的旧 descriptor，必须由仍有效的硬件隔离或撤销机制约束。

### 1.1 lkey：完成之前，注册资源必须存在

非 inline WR 使用本端 SGE 时，请求必须持有对应注册资源与 backing，直到完成账本可以证明设备不再使用。`ibv_post_send` 成功表示提交被接受，不表示 DMA 完成。inline SEND/WRITE 的源数据复制进 WQE，源 buffer 可按接口规定在提交返回后复用，但远端目标授权仍有自己的寿命。[^post]

一条错误 CQE 也不能靠随意读取字段来回收对象：非成功状态下，手册只保证 `wr_id/status/qp_num/vendor_err` 有效。请求 ID 必须映射到明确的请求对象及其资源代次，不能依赖错误 CQE 中无保证的字段。[^cq]

### 1.2 rkey：普通 MR 的有效性不随会话自然消失

普通 MR 关联 PD，而不是应用定义的某次逻辑会话。销毁 QP 不等于注销同一 PD 中仍存在的 MR。新 QP 与旧 MR 的保护域、范围和权限匹配时，**应用若把旧 descriptor 再交给新 QP 提交新的 WR，可能仍被硬件接受**。[^reg][^post]

这与“旧 QP 的迟到网络包自动变成新 QP 的合法包”不是一回事。旧连接的传输状态与报文校验有自己的规则；这里要防的是应用重试队列、远端元数据缓存或旧回调在**新连接上重新提交旧授权**。

rkey 不是密码学认证令牌；PD、连接隔离和权限位也不能替代加密与对端身份认证。本文假设控制面能验证对端身份和元数据完整性；不把“同一局域网”当作该假设的证明。

## 2. Descriptor 契约：身份、范围、权限缺一不可

### 2.1 分清每一种代次

| 字段 | 变化事件 | 防止什么 |
| --- | --- | --- |
| `owner_incarnation` | 所有者进程 / 服务实例重新开始 | 重启后计数从零开始，与历史授权撞号 |
| `session_epoch` | 重新建立一条逻辑数据面会话 | 新连接误接纳旧连接的任务或 descriptor |
| `object_id + generation` | slot 换用途、对象释放后重借、授权边界改变 | 同地址、同 MR 下的逻辑 ABA |
| `grant_id` | 每一次独立授权发布 | 同一对象被多次授权时，ACK / 回调串到另一份授权 |
| `domain_epoch` | 相关设备 / PD / 内存访问域重建 | 在新的访问域里沿用旧的本地注册或远端元数据 |

`allocation_epoch` 属于 [[4.4 内存注册与零拷贝]] 的 backing 身份，不要拿 slot 的 generation 代替它。大池一直活着时，backing 可以不变，而同一 slot 已经借还了很多代。

【设计】一个完整授权由下列字段组成：协议版本、上述身份元组、设备访问基址 `base_iova`、可访问长度、rkey 和 rights。基址未必是 CPU 虚拟地址，尤其不能在 IOVA / zero-based 路径中直接强制使用 CPU 指针。[^reg]

### 2.2 发布和接收的协议要求

发布方必须在 descriptor **可能被任何接收者看到之前**登记 grant 引用。发送失败或等待 ACK 超时不能证明“远端从未收到”，因此 `PUBLISHING` 也是可能有外部授权副本的状态。

接收方必须把 descriptor 与本地保存的**权威控制面记录**比较，不能只比较消息内部两个同样过期的字段。网络编码应逐字段规定位宽、字节序、版本和长度；不要 `memcpy` 一个含 padding 的 C++ 结构体充当协议。

generation 计数不能静默回绕。达到上限时应拒绝继续使用该身份空间，并在安全退休旧授权后更换 incarnation / 对象命名空间；新进程也不能无条件把 incarnation 重置成常量。生产中可使用可靠的持久序号或足够强的唯一实例标识，但“随机”不等于可以忽略碰撞与认证设计。

### 2.3 把地址复用写成具体例子

【示例】同一池内 slot 17，地址 `A`、MR 和 rkey 均未变化：

| 时刻 | 当前身份 | 旧 descriptor 的处理 |
| --- | --- | --- |
| t0 | `(owner O, session 41, object 17, generation 8, grant 90)` | 活跃授权可提交 |
| t1 | grant 90 进入 `QUIESCING` | 即使 generation 仍为 8，也禁止新提交 |
| t2 | 撤销与排空证据齐全；generation 8 退休 | 旧 descriptor 永久退休 |
| t3 | 新一代 generation 9、grant 91 已完成发布 | 旧 generation 8 不得匹配新对象 |
| t4 | 连接重建为 session 42 | 即使对象仍是 generation 9，也须重新授权与激活 |

**状态检查不能被 generation 检查代替。** 一个“代次还没变但已暂停”的对象，同样必须拒绝提交。

## 3. 所有者状态机：每一步都要带证据

### 3.1 状态转换表

| 当前状态 | 事件与守卫 | 必须执行的动作 / 证据 | 下一状态 |
| --- | --- | --- | --- |
| `UNREGISTERED` | backing 稳定，注册成功 | 记录资源身份；尚未对外发布 | `LOCAL_READY` |
| `LOCAL_READY` | 创建新 grant；权限与范围合法 | 先保留 grant 引用，再启动发布 / MW bind | `PUBLISHING` |
| `PUBLISHING` | 注册 / bind 已可用，接收者确认本次身份 | 完成权威元数据激活；允许接收方开提交门 | `ACTIVE` |
| `PUBLISHING/ACTIVE` | 释放、换用途、重连、撤权 | 先关新发布与新提交；冻结本次授权身份 | `QUIESCING` |
| `QUIESCING` | 所有使用者关门且旧请求排空，或有强制隔离证据 | 核对每个 QP / 使用者的结束证据；启动适用的硬件撤销 | `REVOKING` |
| `REVOKING` | 撤销完成且此前访问已结束 | 标记旧 grant 永不再用；结清该 grant 引用 | `RETIRED` |
| `RETIRED` | backing / MR 仍可保留，需再次授权 | 为新 generation / 新 grant 建立新记录，不复活旧记录 | 新记录的 `LOCAL_READY` |
| 任一退出阶段 | 缺少排空证据、设备异常、撤销失败 | 保存 MR、backing、未结算账本；禁止复用 | `QUARANTINED` |

`RETIRED` 是 grant 的终点，未必是整个大池 MR 的终点。**旧 grant 的记录不能因为新一代已激活而改回 ACTIVE**；可以复用存储槽位，但必须换身份并隔离旧回调。

![[图片/SVG/8_4_4_12_2_states.svg|900]]

图中的 `QUARANTINED` 不是“等一会儿就自动成功”，而是缺少安全证明时的资源隔离状态。恢复必须补齐后端与传输证据，或者走明确的进程 / 设备故障清理方案。

### 3.2 接收方也有状态，不能只有一份 descriptor

接收方的最小状态是 `CACHED → ACTIVE → FROZEN → RETIRED`。`CACHED` 只表示收到元数据；必须确认当前会话、当前对象代次和对应授权可用，才能 `activate`。REVOKE、断连、域重建都先转 `FROZEN`，阻止新的 WR。旧请求结清后再转 `RETIRED`。

失败重连时可以保留旧元数据用于日志，但不能因为“缓存里找到了”就自动恢复 `ACTIVE`。激活必须来自新会话的权威记录。

### 3.3 一个可直接检查的入口条件

允许提交当且仅当：

\[
Ready(session)\land Active(grant)\land Match(identity)\land Match(hardware\ tuple)
\land Allowed(operation)\land InBounds(range)
\]

其中 `hardware tuple` 包括实际发布的基址、长度、rkey 与权限记录。软件 rights 与硬件 MR/MW 权限必须一致或更保守；给 descriptor 写上 `READ_ONLY` 并不会把一个可写 rkey 变成只读 rkey。

## 4. 检查与 post 之间也有竞态

只写 `if (generation == current_generation) post_send(...)` 不够：检查后另一个线程可以关闭 grant，随后旧线程仍把 WR 提交出去。

【设计】第一版使用**同一提交锁 / actor 串行域**覆盖“检查会话和 grant 状态 → 为请求登记资源引用 → `ibv_post_send` → 处理实际接受的前缀”。REVOKE 和重连在同一同步域关闭入口、记录已接受请求的截止水位。耗时排空不持有这把锁，CQ/progress 线程必须能继续前进。

高性能版本可以用 reservation token、序列锁式验证或有证明的无锁协议替换，但必须证明：每个与关闭竞态的提交，要么未被接受，要么已计入排空集合。**不能只把 mutex 换成 `atomic<bool>`，就声称线性化点仍然存在。**

多 QP / 多线程共享 grant 时，截止水位是每个相关 SQ 的集合。一个 QP 上的 signaled 完成不是其他 QP 的排空证明；unsignaled 的回收水位也必须按操作类型和排序条件推导。初版全部 signaled 更便于验证。有关 READ / Atomic / fence 的细节见 [[4.13 RDMA 操作顺序性]]。[^post]

### 4.1 请求与回调必须绑定旧资源，而不是“当前位置”

每个在途请求保存 grant 身份、使用的注册租约和唯一请求 ID。完成时结算该请求所持有的资源，不重新通过 `object_id` 查询“当前 generation”，否则旧 CQE 可能减掉新一代的引用。

重复 CQE 处理、重复 ACK 或重试回调都必须至多结算一次。可以在请求账本中做 `Pending → Completed/Failed` 的单向转移；“减引用后再标记完成”可能让重入回调重复扣减。

`ibv_post_send` 的链表提交失败还要区分接受前缀与未提交后缀，不能把整个批次都算成失败。这个引用保留规则由 [[4.4 内存注册与零拷贝]] §4.1 展开。[^post]

## 5. 权限撤销：先确定你信任哪一种保证

### 5.1 合作式关闭与硬件强制失效不同

| 保证级别 | 需要什么 | 不能声称什么 |
| --- | --- | --- |
| 合作式软件关闭 | 所有提交者严格执行冻结、代次检查与排空 ACK | 有 bug 或恶意对端绕过检查后，旧 rkey 必然失效 |
| 硬件权限撤销 | 适用 MR/MW key 失效成功，或所有可访问路径被有效隔离 | 已经接受的 DMA 必然被倒退取消 |
| 安全复用 | 禁止未来旧访问 **且** 已接受旧访问排空 / 终止 | 超时、TCP 断开或一个控制面 ACK 单独证明安全 |

把 generation 写入被 WRITE 的对象头，再在 CPU 上发现不匹配，通常只是**事后检测**：WRITE 可能已经覆盖了新对象。它不等价于在 RNIC 写内存之前拒绝访问。

### 5.2 正常撤销协议：推荐把每个等待点都记录下来

以“缓存大池 MR，按对象发布受限 MW”为例【设计】：先确认设备支持所需 MW 类型，并按接口要求配置父 MR 的可绑定属性及权限。父 MR 不允许 MW 绑定时，下面的协议不能直接使用。

1. 所有者把 grant 转为 `QUIESCING`，不再发布副本；发送带完整身份元组的 `REVOKE`。
2. 每个持有者在自己的提交同步域内冻结 grant，记录该 grant 在所有相关 QP 的提交截止水位。
3. 持有者持续收割完成，直到该截止之前的访问都已按明确完成语义结清。READ / Atomic、失败 QP、unsignaled 要使用各自正确的规则。
4. 持有者发送 `STOP_ACK(identity, cutoff, completion_evidence)`。这不是“收到 REVOKE”的 ACK，而是“已经停止新提交，且既有请求已结束”的 ACK。
5. 所有者核对所有授权持有者的身份与排空证据，然后执行适用的 MW 失效；检查成功完成，而不只检查 post 返回值。
6. 只有在旧访问排空、旧权限失效、相关回调 / 本地使用结清后，旧 grant 才进入 `RETIRED`，slot 才允许给新一代。

![[图片/SVG/8_4_4_12_3_revoke.svg|900]]

时间图的两个等待区不能合并：**远端等待既有 WR 完成，所有者等待硬件撤销完成**。将“发送 REVOKE”画成回收终点，会漏掉这两个窗口。

单条成功 invalidate CQE 表明相应失效动作完成，不能直接推导“所有其他 QP 上已经接受的访问都结束”。跨 QP 的排空必须额外建立；控制消息走独立 TCP / SEND 通道时，也不能凭“ACK 已到”猜测所有 RDMA 操作与它自动有序。

### 5.3 对端不响应：不能把超时写成 RETIRED

超时只触发强制路径：冻结授权、禁止重试队列恢复、隔离相关 QP / 访问域，并按设备与驱动支持的流程获得旧 DMA 已结束的证据。可能需要销毁所有相关访问路径、完成设备恢复，或保留资源直到更高层清理；不能假设一次 `QP→ERR` 或一个软件定时器就同时完成全部任务。

没有可验证的路径时，进入 `QUARANTINED`：保留 backing，拒绝分配器复用，限制隔离资源增长并告警。**泄漏式隔离是故障策略，不是健康状态下的正常回收算法。**

### 5.4 普通独立 MR：注销本身就是撤销，不要设计循环等待

如果没有 MW，且授权对象就是一块独立 MR，可以用成功的 `ibv_dereg_mr` 完成权限撤销。这里不能写成：“先等 grant 完全撤销，才能 dereg；又只有 dereg 才能撤销 grant”。应明确两个阶段：

| 阶段 | 普通独立 MR 路线 | 缓存父 MR + 子 MW 路线 |
| --- | --- | --- |
| 进入撤销操作的守卫 | 新提交已停止；已接受访问排空；本地引用清零；无绑定 MW；回收者独占管理资源 | 子 grant 的所有提交已停止且排空；允许提交 MW 失效 |
| 尚未完成的授权引用 | 转由唯一 `retirement` 对象持有，**不提前视作已退休** | 子 MW / grant 保持引用，直到失效完成 |
| 撤销完成证据 | `ibv_dereg_mr` 返回成功 | 适用失效操作的成功完成 |
| 之后允许的动作 | 清 MR 句柄、将 grant 记为 RETIRED，再按所有权释放 backing | 将子 grant 记为 RETIRED；父 MR 可继续留在缓存 |
| 后端失败 | 保留整个资源包并隔离；不得 free | 保留 grant、MW 与父 MR 引用并隔离 |

若采用合作式停止作为前置条件，该保证只针对遵守协议的提交者。不能信任对端时，必须先建立适用的硬件隔离 / 传输终止保证，并核对后端撤销与 DMA 同步语义，不把上表当恶意并发写入的通用防护证明。

缓存父 MR 的完整 rkey 应留在本端，不要同时向远端公开“受限 MW key”和“覆盖整个池的父 MR key”。否则失效一扇小窗，仍挡不住持有大门钥匙的旧访问。

## 6. 连接重建：新 QP 不等于新授权

连接流程可与 [[4.11 RDMA CM 与连接建立]] 对照，但 CM 建连成功只解决传输通道可用，不能替你激活历史 descriptor。

### 6.1 可检查的重连步骤

| 步骤 | 会话状态 / 必须动作 | 可检查条件 |
| --- | --- | --- |
| 检测断连或决定重建 | `READY → FROZEN`；先关提交门，再处理重试 | `can_submit == false` |
| 处理旧请求 | 旧请求保留原 session / generation；逐项完成、失败或隔离 | 不把旧引用转嫁给新请求 |
| 建立新会话 | 新 `session_epoch`；核对 owner incarnation | 新旧身份不同；尚未 `READY` |
| 重新交换元数据 | 接收新会话专属 descriptor，核对范围、rights 与资源域 | 旧 descriptor 不自动迁移 |
| 激活新授权 | 新 grant 达到协议激活条件，会话开门 | 只允许新权威记录提交 |
| 清理旧会话 | 撤销与排空旧 grant；隔离未能证明安全的资源 | 旧回调不能修改新会话状态 |

设备 / PD 未变时，**本地 MR 可以保留，远端 grant 仍须按新会话重发与激活**。设备或 PD 也被重建时，本地注册缓存的 context / PD epoch 同样失效，不能只换远端 rkey 表而留下旧 lkey。

![[图片/SVG/8_4_4_12_4_reconnect.svg|900]]

图中故意保持地址与 rkey 不变：这样才能检验“拒绝旧 descriptor”是否真正依赖新会话身份，而不是碰巧因为重新注册换了 key 才失败。

### 6.2 哪些错误必须在 post 之前拒绝

旧 owner incarnation、旧 session、旧 object generation、已冻结 grant、旧 domain epoch、被替换的 key 或范围，都应在提交门返回明确的 stale / closed / invalid 错误。不要为了“让 RNIC 帮忙检查”主动提交已知过期的 descriptor；这会把可恢复的软件状态错误变成完成错误，甚至影响 QP。

跨重连重试业务请求，需要新的授权与新的请求 ID，并由业务协议处理幂等 / 去重。更换 descriptor 不代表旧 WRITE 一定没生效；不能凭传输失败就无条件执行两次有副作用的操作。

## 7. 失效工具：对象类型、完成语义和限制

| 机制 | 可以依赖的作用 | 使用边界 |
| --- | --- | --- |
| `ibv_dereg_mr` | 成功注销普通 MR，释放相应注册资源 | 先满足生命周期前提；仍有绑定 MW 会失败；失败不得继续 free |
| `ibv_rereg_mr` | 修改 translation、PD 或 access 等指定属性 | **不是通用的“保证换新 rkey”接口**；错误码对应 MR 状态不同，按手册恢复 |
| Type 1 MW | 通过 `ibv_bind_mw` 绑定 MR 子范围与权限；零长度绑定可取消绑定 | 函数返回表示排入工作队列，不是 bind 已完成；不能误用 Type 2 规则 |
| Type 2 MW | 用 `IBV_WR_BIND_MW`；适用的 `LOCAL_INV` / `SEND_WITH_INV` 失效 | 查询能力；核对具体 Type 2 / QP 关联与 provider 限制；不能推广为任意普通 MR |
| `SEND_WITH_INV` | 在适用对象上通过接收端处理携带的失效 key | 核对成功状态、`IBV_WC_WITH_INV`、实际 `invalidated_rkey` 与预期 grant |
| 内核 fast-registration MR | 内核 ULP 可用注册 / 本地失效 WR 管理访问凭据 | 不是把内核 `IB_WR_REG_MR` 原样写进用户态 `ibv_post_send` 就可用 |

依据是 rdma-core 的 MR、rereg、MW、bind、post 与完成手册，而不是“所有 key 都能随意 invalidate”的概括。[^reg][^rereg][^mw][^bind][^post][^cq]

特别注意三个边界。第一，`ibv_rereg_mr` 不同错误可能表示旧 MR 仍有效、新属性已生效或 MR 不应再使用；恢复逻辑须按具体错误分类，不能统一“失败就继续用旧 key”。第二，MW bind 成功提交后，经独立通道发布新 key 之前应确认其生效；依赖同一 QP 排序的优化需要单独证明。第三，成功接收响应但没有期望的失效标志，不是“默认已经失效”。[^rereg][^bind][^cq]

## 8. 工业例子：Linux NVMe/RDMA 的资源结算思路

固定阅读版本是 **Linux `v6.12` 的 `drivers/nvme/host/rdma.c`**，不是宣称所有 NVMe-oF 实现都采用同一路径。[^nvme]

在该版本 `nvme_rdma_map_data()` 中，请求引用先设为 2，对应 send 与 recv completions；数据映射还区分无数据、完整性相关 MR、小写入 inline、特定 global-rkey 路径以及 `nvme_rdma_map_sg_fr()`。`nvme_rdma_post_send()` 可以将前置工作请求与 SEND 串接，并使用 signaled SEND。

因此可学习的是：**命令发送完成、响应处理、数据映射与密钥相关资源要共同结算**；不能只见 SEND CQE 就把整个请求的资源全部放回池。常见 FRWR 路线通过注册与失效工作请求管理短期访问凭据，但不能把“每个 IO 必然恰好两个额外 WQE”写成该驱动所有分支的固定事实。

回到自己的系统，先把“谁持有一次请求的最后一个资源引用”画出来，再优化注册成本。应用的 session / object generation 则仍是应用协议的一部分，不能凭这个驱动例子推导出硬件自动理解了业务对象代次。

## 9. C++17：把旧 descriptor 拒绝条件变成测试

下面代码块按顺序拼接是一个完整的**纯逻辑测试程序**，不调用 verbs，不模拟线程或 RNIC。示例的 `current` 表示经过认证与激活的权威记录；`d` 是待提交任务持有的副本。生产中的“检查 + 资源保留 + post”必须按 §4 串行化。

### 9.1 身份和快照类型

采用值类型是为了让状态检查可单元测试；并不把这些 C++ 结构体直接当作网络协议。

```cpp
#include <array>
#include <cstdint>
#include <iostream>
#include <limits>
#include <stdexcept>
#include <tuple>

using U64 = std::uint64_t;
using Owner = std::array<U64, 2>;
struct Identity {
    Owner owner{};
    U64 session{}, object{}, generation{}, grant{}, domain{};
};
struct Descriptor {
    Identity id;
    U64 base{}, length{};
    std::uint32_t rkey{}, rights{};
};
struct Session {
    Owner owner{};
    U64 epoch{};
    bool ready{};
};
enum class View { Cached, Active, Frozen, Retired };
constexpr std::uint32_t kRead = 1, kWrite = 2;
```

比较完整身份而不是只比较一个 generation：对象代次没变，会话仍然可能已经变了。

```cpp
bool same_identity(const Identity& a, const Identity& b) {
    return std::tie(a.owner, a.session, a.object, a.generation,
                    a.grant, a.domain)
        == std::tie(b.owner, b.session, b.object, b.generation,
                    b.grant, b.domain);
}
bool same_descriptor(const Descriptor& a, const Descriptor& b) {
    return same_identity(a.id, b.id) && a.base == b.base
        && a.length == b.length && a.rkey == b.rkey
        && a.rights == b.rights;
}
```

### 9.2 提交门：先身份，再权限，再安全算术

示例只覆盖普通 READ / WRITE 请求，明确拒绝零长度，Atomic 的长度、对齐等要求需另加规则。`base + length - 1` 通过减法验证，避免溢出；子区间也先减后比较。

```cpp
bool can_submit(const Descriptor& d, const Descriptor& current,
                const Session& s, View v, std::uint32_t need,
                U64 offset, U64 bytes) {
    constexpr auto max = std::numeric_limits<U64>::max();
    if (!s.ready || v != View::Active) return false;
    if (d.id.owner != s.owner || d.id.session != s.epoch)
        return false;
    if (!same_descriptor(d, current)) return false;
    if (need != kRead && need != kWrite) return false;
    if ((d.rights & need) != need) return false;
    if (d.length == 0 || d.base > max - (d.length - 1))
        return false;
    return bytes != 0 && offset <= d.length
        && bytes <= d.length - offset;
}
```

`same_descriptor()` 是对权威记录的一致性检查，不是密码学认证。攻击者若能篡改权威记录或绕过提交入口，本函数不能提供隔离；仍需硬件权限和可信控制面。

### 9.3 对过期身份逐项做反例测试

这一组测试故意不改变 rkey，只改变一个软件身份字段，以证明拒绝逻辑没有碰巧依赖硬件 key 变化。

```cpp
int checks = 0;
void expect(bool ok) {
    if (!ok) throw std::runtime_error("descriptor guard failed");
    ++checks;
}
Descriptor fresh() {
    return {{{1, 7}, 41, 17, 8, 90, 3}, 4096, 1024,
            0x12345678U, kRead | kWrite};
}
bool allowed(const Descriptor& d, const Descriptor& c,
             const Session& s, View v = View::Active) {
    return can_submit(d, c, s, v, kWrite, 0, 64);
}
void test_stale(const Descriptor& c, const Session& s) {
    auto d = c; --d.id.generation; expect(!allowed(d, c, s));
    d = c; --d.id.session; expect(!allowed(d, c, s));
    d = c; ++d.id.owner[0]; expect(!allowed(d, c, s));
    d = c; ++d.id.object; expect(!allowed(d, c, s));
    d = c; ++d.id.grant; expect(!allowed(d, c, s));
    d = c; ++d.id.domain; expect(!allowed(d, c, s));
    d = c; ++d.rkey; expect(!allowed(d, c, s));
    d = c; ++d.base; expect(!allowed(d, c, s));
    d = c; ++d.length; expect(!allowed(d, c, s));
}
```

重连测试保留原地址、原 key 和原对象代次，仅改变新会话和新授权编号。旧任务必须失败，新任务才能通过。

```cpp
void test_reconnect(const Descriptor& c, const Session& s) {
    auto next = c;
    auto ns = s;
    ++ns.epoch;
    next.id.session = ns.epoch;
    ++next.id.grant;
    expect(!allowed(c, next, ns));
    expect(allowed(next, next, ns));
    auto rebooted = ns;
    ++rebooted.owner[1];
    expect(!allowed(next, next, rebooted));
}
void test_ranges(Descriptor c, const Session& s) {
    expect(can_submit(c, c, s, View::Active, kRead, 960, 64));
    expect(!can_submit(c, c, s, View::Active, kRead, 961, 64));
    expect(!can_submit(c, c, s, View::Active, kRead, 0, 0));
    expect(!can_submit(c, c, s, View::Active, kWrite, 1025, 1));
    c.rights = kRead;
    expect(!allowed(c, c, s));
    c.base = std::numeric_limits<U64>::max() - 2;
    expect(!can_submit(c, c, s, View::Active, kRead, 0, 1));
}
```

### 9.4 所有者转换守卫：进入撤销与完成撤销分开检查

这里把证据绑定到完整 grant 身份。`all_gates_closed` 和 `old_dma_done` 必须由 §5 的控制协议与后端结算产生；测试中直接赋值只是构造输入，不能照搬成生产代码里收到任意 ACK 就置位。

```cpp
enum class GrantState { Active, Quiescing, Revoking,
                        Retired, Quarantined };
struct RevokeEvidence {
    Identity id;
    bool all_gates_closed{}, old_dma_done{};
    bool mechanism_ready{}, hardware_revoked{};
    U64 local_refs{};
};
bool drained(const Descriptor& c, const RevokeEvidence& e) {
    return same_identity(c.id, e.id) && e.all_gates_closed
        && e.old_dma_done && e.local_refs == 0;
}
bool can_start_revoke(GrantState state, const Descriptor& c,
                      const RevokeEvidence& e) {
    return state == GrantState::Quiescing && drained(c, e)
        && e.mechanism_ready;
}
bool can_finish_revoke(GrantState state, const Descriptor& c,
                       const RevokeEvidence& e) {
    return state == GrantState::Revoking && drained(c, e)
        && e.hardware_revoked;
}
```

`mechanism_ready` 表示所选后端动作的前提满足，例如普通 MR 注销前不存在绑定 MW；它不是硬件撤销已经完成。独立 MR 的退休对象在这个阶段仍持有 grant，注销成功才产生 `hardware_revoked` 证据，因而不会形成循环等待。

```cpp
void test_revocation() {
    const auto c = fresh();
    RevokeEvidence e{c.id, true, true, true, false, 0};
    expect(can_start_revoke(GrantState::Quiescing, c, e));
    expect(!can_start_revoke(GrantState::Active, c, e));
    expect(!can_finish_revoke(GrantState::Revoking, c, e));
    e.hardware_revoked = true;
    expect(can_finish_revoke(GrantState::Revoking, c, e));
    e.old_dma_done = false;
    expect(!can_finish_revoke(GrantState::Revoking, c, e));
    e.old_dma_done = true; e.all_gates_closed = false;
    expect(!can_finish_revoke(GrantState::Revoking, c, e));
    e.all_gates_closed = true; ++e.local_refs;
    expect(!can_finish_revoke(GrantState::Revoking, c, e));
    --e.local_refs; --e.id.generation;
    expect(!can_finish_revoke(GrantState::Revoking, c, e));
    e.id = c.id; --e.id.session;
    expect(!can_finish_revoke(GrantState::Revoking, c, e));
    e.id = c.id;
    expect(!can_finish_revoke(GrantState::Quarantined, c, e));
    e.mechanism_ready = false;
    expect(!can_start_revoke(GrantState::Quiescing, c, e));
}
```

反例包括：已经发起撤销但还没完成、硬件撤销已完成但旧 DMA 未排空、旧 generation / session 的证据迟到、以及隔离状态被误当成可退休。最终转换还应与证据核对处在同一同步域内，防止检查后记录已被替换。

最后检查被冻结、未激活、已退休、会话未就绪的对象，确认“身份完全相同”不能跳过状态门。

```cpp
int main() {
    const auto c = fresh();
    Session s{c.id.owner, c.id.session, true};
    expect(allowed(c, c, s));
    expect(!allowed(c, c, s, View::Cached));
    expect(!allowed(c, c, s, View::Frozen));
    expect(!allowed(c, c, s, View::Retired));
    auto closed = s; closed.ready = false;
    expect(!allowed(c, c, closed));
    test_stale(c, s);
    test_reconnect(c, s);
    test_ranges(c, s);
    test_revocation();
    expect(!can_submit(c, c, s, View::Active, 0, 0, 64));
    std::cout << "descriptor guards: " << checks << " checks passed\n";
}
```

这些代码只做快照上的纯计算，没有实际等待；真正跨线程、跨机器的等待点见撤销泳道图。编译方式：`g++ -std=c++17 -Wall -Wextra -Werror -pedantic descriptor_guard.cpp -o descriptor_guard`。

## 10. 必须保留的故障注入矩阵

| 编号 | 注入 | 期望的状态 / 断言 |
| --- | --- | --- |
| K1 | 同地址、同 key，generation 变更 | 旧副本在 post 前被拒绝 |
| K2 | 同对象、同 key，新 session | 旧任务不能沿新 QP 重新提交 |
| K3 | 所有者重启，计数从初值开始 | incarnation 不匹配，旧授权仍被拒绝 |
| K4 | 检查完成后立刻触发 REVOKE | 提交被阻止，或被计入关闭截止；无漏账 |
| K5 | grant 正在发布，发送 ACK 丢失 | 不直接判定无人持有；进入撤销 / 隔离 |
| K6 | 远端仅收到 REVOKE，旧 WRITE 仍未完成 | 不接受此时的“收到了”ACK 作为 STOP_ACK |
| K7 | grant 跨两个 QP，只排空一个 | 禁止退休 |
| K8 | post invalidate 成功，但完成尚未到 | 保持 REVOKING，不复用 slot |
| K9 | 旧 generation 的 ACK / CQE 延迟到达 | 只结算旧记录；新 generation 引用不变 |
| K10 | 重复 ACK、重复完成回调 | 至多结算一次，不发生计数下溢 |
| K11 | dereg 失败或仍有绑定 MW | 资源保留 / 隔离，不 free |
| K12 | 超时、CQ overrun、设备丢失 | 无安全证据则 QUARANTINED |
| K13 | 软件 rights 只读，底层 key 实际可写 | 审计失败；不能宣称硬件只读隔离 |
| K14 | descriptor 篡改长度、地址或越界运算 | post 前拒绝；无整数回绕 |
| K15 | 绕过软件门直接使用旧 key | 测的是硬件撤销 / 隔离，不把 generation 当防线 |
| K16 | 独立 MR 用 dereg 撤销 | retirement 持有资源直到成功；不存在 grant/dereg 循环等待 |

K1–K3、K8–K9、K14、K16 的部分守卫在上述纯逻辑测试中覆盖；其他条目要求真正的并发 / provider / 硬件环境，**此文不声称已经完成这些硬件实验**。破坏性失效实验应在独立 PD、独立 QP 和隔离测试内存上执行，不对生产缓冲发已知无效的请求。

日志至少关联 `owner/session/object/generation/grant/domain/request` 与转换前后状态、原因及完成证据；记录 stale 拒绝、冻结后提交、重复结算、撤销等待和隔离资源量。rkey 与地址按安全策略脱敏。

## 11. 六个不可妥协的断言

| 断言 | 违反后的典型故障 |
| --- | --- |
| ACTIVE 之外不能接纳新提交 | 暂停 / 退休过程仍有新 WR 漏入 |
| 身份检查与提交预留属于同一同步协议 | 通过检查的旧请求越过撤销边界 |
| generation 不被当作 RNIC 权限检查 | 旧 WRITE 已经造成破坏，软件才发现 |
| 旧 grant 退休需要“未来关闭 + 既往排空” | 撤权了但旧 DMA 仍在，或排空了却又提交 |
| 新连接必须重新激活权威 descriptor | 旧任务在新 QP 上合法使用旧 MR |
| 缺证据就隔离，不能猜测资源安全 | 异常恢复中的静默内存破坏 |
