# 交换机数据面与 RoCE 队列：Ingress、Egress、Shared Buffer、PFC、ECN 与 HOL Blocking

> 排查 RoCE 排队时，先给每个数字补上三个限定：哪个端口、哪个方向、哪个记账对象。“队列超过阈值”没有这三个限定，往往不足以说明问题。

[[4.20 RoCE Fabric 组网：Clos、Leaf-Spine、ECMP、LAG 与 Oversubscription]] 回答报文走哪条链路；本篇把其中一台交换机展开。[[4.7 PFC ECN 与 DCQCN]] 已经介绍协议角色，这里不重复推导 DCQCN 速率状态机，而是把每个机制放回交换机的 PG、Queue、缓冲和调度器上。

**适用边界**：正文采用 SAI/SONiC 文档描述的共享缓冲抽象解释机制。真实 ASIC 可能是共享内存、分布式缓冲、VOQ 或组合架构，检测与记账时点也可能不同。下面的图是教学模型，不是所有芯片的内部电路图。阈值示例不应直接作为生产配置；本轮没有运行真实交换机压测。

## 1. 六个经常被统称为“队列”的不同对象

| 对象 | 标识通常包含什么 | 它描述什么 | 不应与谁混淆 |
| --- | --- | --- | --- |
| RNIC SQ / RQ / CQ | 设备、QP 或 CQ 对象 | 工作请求和完成通知 | 交换机的包队列 |
| Ingress Priority Group，PG | 入端口 + PG 索引 | 接收方向的缓冲归属、共享额度、headroom | 出口调度队列 |
| Egress Queue | 出端口 + queue 索引/类型 | 等待从该出口发送的一类包 | 单个远端 QP |
| Buffer Pool | 芯片/实例 + pool 对象 | 一组使用者可分配的缓冲资源或额度 | 自动具有 FIFO 顺序的队列 |
| VOQ | 常包含入口、目标出口及类 | 将不同目的出口的等待相互分开 | 自动解决所有拥塞的机制 |
| PFC priority | 链路上的优先级 0–7 | MAC Control 帧所指示的暂停类别 | DSCP、任意 queue 编号或某条流 |

SAI 将 queue 的端口、索引、WRED、buffer 和 scheduler profile 定义为不同属性；QoS map 又单独定义 TC→Queue、TC→PG、PFC priority→Queue 等映射。对象在接口上就是分开的，不只是名字不同。[^queue][^qosmap]

理解 [[4.3 QP WQE CQ 状态机]] 有助于分清第一行：RNIC 的 CQE 告诉主机某个操作完成了；交换机的 queue watermark 告诉你一段时间内某个包队列的缓冲使用峰值。不能拿 CQ 深度替代交换机队列深度。

## 2. 一次转发：报文数据、元数据与两种记账视角

### 2.1 从输入到输出的逻辑依赖

把一帧报文进入交换机后的工作拆成五类，比画成“一个大 FIFO”更有用。

| 工作 | 需要哪些输入 | 产生什么结果 |
| --- | --- | --- |
| 解析与分类 | 入端口、报文头、trust/ACL/QoS 策略 | 内部 TC、颜色、转发所需字段等元数据 |
| 转发选择 | 目的地址、FIB、ECMP/LAG 与邻接 | 出端口或下一跳、报文修改信息 |
| 缓冲准入与记账 | 包长/cell、入口 PG、出口队列、pool/profile | 是否接纳、占用归到哪里 |
| 排队与拥塞处理 | 队列状态、ECN/WRED 策略、PFC 相关状态 | 标记、丢弃决策或流控触发 |
| 调度与发送 | 可服务队列、调度权重、整形、收到的暂停状态 | 选择下一包、发送、释放相应资源 |

这些动作可能流水化、并行化或分布在多个模块中。表格表达依赖关系，并不声称所有 ASIC 都严格按这五行顺序执行。教材 §3.5.2 的硬件转发流水线是理解这一点的起点；具体缓冲对象进一步以 SAI/SONiC 为准。[^book][^buffer]

![[图片/SVG/8_4_23_1.svg|900]]

图中实线表示逻辑转发方向，虚线表示对同一批报文的资源归属。共享缓冲里的数据可以由描述符或索引关联到队列；**画出 Ingress PG 和 Egress Queue，不等于每个包必须先复制进一个入口 FIFO，再完整复制进另一个出口 FIFO。**

### 2.2 一个包可以同时出现在两本“账”上

考虑入端口 A 收到一个 RoCE 数据包，最终将从出端口 D 发出。它的元数据可以同时包含：

```text
入口归属：(port A, PG_R)
出口归属：(port D, Q_R)
存储归属：某个 buffer pool 中分配的 cell / 描述符
```

入口视角问：“A 的这个 PG 占用了多少接收缓冲？”出口视角问：“D 的这个 Queue 还有多少数据等待发送？”这两个问题可能观察同一批物理存储，因此不能把入口计数与出口计数无条件相加，宣布芯片已经消耗两倍内存。SONiC 的缓冲设计明确说明 ingress 与 egress pool 可映射到同一 switch buffer。[^buffer]

是否同时计入、从哪里开始计入、发送到哪一步释放、watermark 包括 reserved 还是 shared，均需核对具体 counter 定义。图示的“一份包、两个视角”是用于防止误算的模型，不是对每个计数器实现的统一承诺。

### 2.3 Cut-through 不等于没有缓冲

即使允许在整帧到齐之前开始转发，出口也可能正忙、正在被 PFC 暂停，或受调度/整形限制。只要短区间内到达量大于服务量，就必须等待或丢弃。可见，“支持 cut-through”与“拥塞时不会排队”是两个不同命题；后者不能由前者推出。

## 3. DSCP、TC、PG、Queue 与 PFC priority：先画映射，再谈配置

### 3.1 同样的数字不意味着同样的对象

下面是一组**假设平台允许这些映射**的教学配置。数字刻意不全相同，用于强调命名空间的区别；它不是推荐值，也不保证任意 ASIC 可逐项自由映射。

| 流量 | 线上 DSCP | 内部 TC | 入端口 PG | 出端口 Queue | PFC 相关策略 |
| --- | ---: | ---: | ---: | ---: | --- |
| RoCE 数据 | 24 | 3 | 3 | 5 | 该链路以 priority 3 管理；接收 priority 3 的 PFC 时约束其映射队列 |
| CNP | 48 | 6 | 0 | 6 | 示例中不启用该类 PFC，另设调度保障 |
| 普通业务 | 0 | 0 | 0 | 0 | 示例为有损类 |

因此在这组假设下，“收到了 priority 3 的 PFC”并不等于“暂停编号 3 的出口 Queue”。应查询该端口的 `PFC_PRIORITY_TO_QUEUE` 映射；图中数据队列恰好是 Queue 5。PG 与 PFC priority 的关系也要核查，不能只凭索引猜测。[^qosmap]

从这一例子可以导出一份配置审查顺序：先确认线上标记，再确认 ingress trust，再看 TC→PG 与 TC→Queue，最后核对链路双方的 PFC 语义及相应 profile。只检查主机上“DSCP 设置了 24”，还没有检查完一跳。

### 3.2 DSCP 与 ECN 不是同一组位

IP 的相关 8 位字段中，DSCP 使用 6 位，ECN 使用 2 位。RFC 3168 给出的传统 ECN 编码为：`00` 是 Not-ECT，`10` 是 ECT(0)，`01` 是 ECT(1)，`11` 是 CE。本文只使用它解释 IP 层的拥塞标记，不把 RFC 中的 TCP 反馈流程搬到 RoCE 上。[^ecn]

假设需要 DSCP=24、ECN=ECT(0)，则整个 8 位字段的教学计算为：

```text
(24 << 2) | 2 = 98 = 0x62
```

但某个配置 API 要你填“DSCP”还是整个“Traffic Class/TOS 字节”，必须看该 API 文档。把 24 与 98 填反，可能同时改变分类与 ECN 能力位。报文镜像或硬件采样可以核实线上的值；普通主机抓包能否看到硬件卸载的 RoCE 数据，需要单独验证，不能把“抓不到”直接当作“没有流量”。

## 4. PFC：触发点在接收侧，执行点在上一跳的发送侧

### 4.1 先固定一个方向

设数据沿 `上游 U → 本机 S → 下游 D` 传输。

本篇共享缓冲模型中，S 接收 U 的数据时，相关 Ingress PG 的可接纳空间不足，会触发面向 U 的 PFC。**S 发出 PFC，要求 U 暂停该链路上相应优先级的发送；不是要求 U 的应用立即销毁 QP，也不是只暂停刚刚造成拥塞的那条流。**[^buffer][^qosmap]

另一方面，若 S 从 D 收到 PFC，S 的相关发送队列会受到约束。这是 S 的 **PFC Rx**；它反映 D 对 S 的背压请求，不直接等同于 S 自己的接收缓冲已溢出。SAI queue 的暂停状态和 PFC priority→Queue 映射正对应这一侧的行为。[^queue][^qosmap]

![[图片/SVG/8_4_23_2.svg|900]]

### 4.2 用方向表消除歧义

| 在 S 上看到的事件 | 谁要求谁减小接收压力？ | S 上要优先关联的状态 |
| --- | --- | --- |
| 向 U 发出 PFC，Tx 增长 | S 要求 U 暂停发送 | U→S 的入端口 PG、共享池/headroom，以及导致数据无法离开的出口 |
| 从 D 收到 PFC，Rx 增长 | D 要求 S 暂停发送 | S→D 出端口的相关 queue、调度/暂停状态 |
| S 同时出现 Rx 与其他口 Tx | 下游背压可能向更上游传播 | 两类事件的时间先后、映射关系、实际流量路径 |

这些是定位方向，不是根因判决。S 的 ingress 压力可能由下游暂停、内部资源限制或出口竞争引起；PFC Tx 计数高不能单独证明“上游发得不合理”。

PFC 是链路级控制。所谓“PFC 传播”，通常是上一跳因无法继续发送而再次积压，随后**自己生成新的 PFC**。不是同一个 PFC 帧被像 IP 包一样一路转发到最初发送者。

### 4.3 暂停与恢复还需要时间

对一个按“已用空间”定义的简化模型，触发暂停的水位高于允许恢复的水位，形成滞回，避免在边界附近频繁开关。PFC 本身带有暂停时间；恢复可以涉及新的流控消息、零暂停值或定时到期，具体发出策略由实现决定。不要把 XON 想成一个可靠、端到端、逐条流的应用层握手。

更重要的是：**NOS 中名为 `xoff` 的字段，不一定就是“已占用字节达到这个数时暂停”。** SONiC 的设计讨论包含按剩余 headroom、shared headroom pool 等方式解释的参数。配置前应先查语义，再谈大小关系。[^buffer]

## 5. ECN 与 CNP：出口标记，端点反馈

### 5.1 谁看队列，谁改包，谁调速

在本篇基线中，拥塞判断关联 Egress Queue 的占用及所附 profile；对可 ECN 标记的报文，交换机将 ECN 字段设为 CE。接收 RNIC 根据标记产生 CNP，发送 RNIC 根据反馈调整相应流的发送行为。交换机并不因为“标了 CE”就直接获得远端 QP 的速率控制权。[^ecn][^queue][^dcqcn]

这三个动作分别位于交换机、接收端和发送端。PFC 则沿相邻链路反向发送暂停请求。图中的两条反馈线路必须分开读：CE 先随数据往前走，CNP 再走返回路由；PFC 只控制相邻一跳。

### 5.2 “ECN 已开启”至少还缺四个验证

| 验证项 | 可检查的对象 | 可能的误判 |
| --- | --- | --- |
| 流量是否进入目标 queue | DSCP/TC 映射、queue 字节增量 | 配对了 profile，却没有包进入 |
| 数据是否可被 ECN 标记 | 实际 ECT 位、标记计数 | Not-ECT 与正常 ECN 流量混在一起解释 |
| 反馈是否到达发送端 | 接收端 CNP Tx、发送端 CNP Rx | 只看到交换机 CE 增长便宣布闭环完成 |
| 收到反馈后是否及时改变负载 | 发送速率、队列与时间相关性 | 有 CNP 计数就认定控制参数合适 |

SAI 的 Queue 对象可以附 WRED profile；具体 profile 如何启用 ECN、选用哪类阈值/颜色、是否采用瞬时或其他统计占用，需查实际平台。不能假定所有系统的 `K_min/K_max/P_max` 都具有相同默认值和边界行为。[^queue]

CNP 的服务保障也不等于“必须使用某个固定数字的高优先级队列”。目标是让反馈及时返回，并避免调度策略饿死其他必要流量；选择独立队列、严格优先级或其他保障方式，必须连同负载和设备能力一起验证。

## 6. Shared Buffer：共享的是资源，不是无限容量

### 6.1 三类额度与一个物理预算

| 概念 | 解决的问题 | 代价与边界 |
| --- | --- | --- |
| Reserved / minimum guarantee | 给指定使用者留出最低接纳能力 | 预留过多会压缩其他使用者可借的空间 |
| Shared pool / dynamic threshold | 空闲资源允许多个端口或队列按策略借用 | 可借额度可能随其他使用者占用变化 |
| Headroom | PFC 发出后继续吸收尚未停止到达的数据 | 需要按速率、时延、帧与 cell 口径预算 |

SONiC 文档区分独立 headroom 与 shared headroom pool：前者可为每个 `(port, PG)` 留出专用资源，后者由多个使用者共享一定的 headroom 预算。两者的 `size/xon/xoff` 关系并不相同。[^buffer]

因此计算实际容量时，先问：“这些名字是互不重叠的物理分区，还是对同一存储的多级逻辑约束？”只有确认不重叠，才可以直接相加。也不能把每个 PG 配置的最大额度都相加，认定硬件真的为每个 PG 私有保留了那么多内存。

### 6.2 动态阈值不是固定容量的另一个写法

一个教学模型可以写成 `某使用者可借额度 = α × 当前共享池空闲量`。若其他端口消耗了共享池，即使本端口的流量不变，它允许继续增长的空间也可能缩小。这解释了为什么“同样的流量，其他业务一启动就出现暂停”值得去查共享资源。

这个公式只表达动态共享的因果关系。实际设备可能将 alpha 编码成指数，叠加 reserved、最大值、cell 对齐或多级 pool 限制；不要把上述等式直接翻译成某款交换机的配置命令。[^buffer]

### 6.3 为什么“只要开更多无损类”会消耗预算

假设采用独立预留模型，32 个端口，每端口 4 个无损 PG，每个预留 100000 bytes headroom，那么仅这部分预留为：

```text
32 × 4 × 100000 = 12800000 bytes = 12.8 MB ≈ 12.21 MiB
```

这不是某个真实芯片的数值。它是一个预算检查：增加无损类可能按端口和 PG 数放大预留需求。采用 shared headroom 可以改变这种分配方式，但又要验证多个使用者同时触发时的需求，不能把“共享”理解为无条件省下所有最坏情况空间。

## 7. 不能把 ECN 与 PFC 画成同一个通用水位轴

### 7.1 原因不是数值不同，而是求和方向不同

把共享缓冲中仍驻留的业务字节简化成矩阵 `X[i,j]`：行 i 表示一个 ingress PG，列 j 表示一个 egress queue。忽略计数器口径差异时：

```text
Ingress PG i 的占用 I[i] = Σ_j X[i,j]   （一行）
Egress Queue j 的占用 E[j] = Σ_i X[i,j] （一列）
```

一个入口可以向多个出口发送；一个出口也可以接收多个入口的包。所以 `I[i]` 与 `E[j]` 不具有通用的一一对应关系。这个矩阵只是教学记账模型，但已经足以证明：**对两个不同的求和结果，只比较阈值数字，不能保证触发先后。**

![[图片/SVG/8_4_23_3.svg|900]]

### 7.2 用两组反例检查直觉

假设教学模型中的 ECN 阈值为 100 kB；Ingress PG 按“已用空间”定义的暂停水位为 160 kB。两个数都不是设备建议值。

**情况 A：一个入口向三个出口扇出。** 三个出口各驻留 60 kB，全部来自同一个 PG。此时该 PG 的占用是 180 kB，每个出口 queue 只有 60 kB。即使 `100 < 160`，入口仍可能先达到暂停条件，而三个出口都还没有达到 ECN 阈值。

**情况 B：三个入口向同一出口汇聚。** 每个 PG 各占 60 kB，全部去同一 queue。此时出口 queue 是 180 kB，每个 PG 只有 60 kB。出口可先产生 ECN 标记，而各 PG 尚未达到暂停水位。

这两组静态状态不模拟完整控制过程，也不保证真实 ASIC 会允许所有组合；它们用于检验“仅凭一个不等式就能覆盖所有流量矩阵”的推理是否成立。DCQCN 原论文 §4 也明确区分了 egress ECN 与 ingress PFC 的阈值对象。[^dcqcn]

### 7.3 如何理解 4.7 中的简化图

[[4.7 PFC ECN 与 DCQCN]] 的单队列示意可以帮助记住“希望反馈尽早介入，暂停吸收来不及抑制的突发”。落到硬件时，要把它展开为：

**标记所观察的对象 → 反馈传输/处理时延 → 发送速率改变 → 各 PG 与共享池在此期间的增长 → 是否仍有足够 headroom。**

可在同一计数对象、相同单位及明确定义的模型内比较 `XON` 与 `XOFF`。但不应把“ECN 配置为多少字节”与“某个 buffer profile 的 xoff 整数”直接拼成一个适用于所有平台的不等式。

## 8. 三个小计算：增长速度、停车空间、等待时间

### 8.1 队列每微秒会增加多少

对一段输入/输出近似恒定、缓冲未溢出的时间区间，若速率使用 bit/s，积压增长为：

```text
ΔB = max(0, ΣR_in − R_service) × Δt / 8
```

例如四路各 100 Gb/s 汇聚到一个 100 Gb/s 出口，持续 2 μs，则新增积压为：

```text
(400 − 100) × 10^9 × 2 × 10^-6 / 8
= 75000 bytes ≈ 73.24 KiB
```

式中的 `R_service` 是该队列此时获得的服务速率，不一定等于端口标称速率。整形、与其他队列竞争或收到 PFC，都可能改变它。暂停期间若服务速率为零，输入却未停，积压增长会更快。

### 8.2 Headroom 不是把端到端 BDP 整份复制过来

令 `T_stop` 表示本机决定发出暂停后，到受控上游的到达流量实际停止之间，需要计入的链路传播与响应时延。它涉及相邻链路，不是整个应用请求的端到端 RTT。一个基本预算模型为：

```text
H_required ≥ R_in × T_stop / 8 + B_extra
```

`B_extra` 用于模型尚未计入的不可中断帧、MAC/PHY/gearbox 流水线、cell 取整等余量。**某项已经包含在 `T_stop` 内，就不应又作为余量重复加一次。** 真实公式还可能考虑小包比例和硬件缓冲开销；SONiC 的设计列出了这些平台相关输入。[^buffer]

若只计算 400 Gb/s、2 μs 的速率×时延项：

```text
400 × 10^9 × 2 × 10^-6 / 8
= 100000 bytes = 100 kB ≈ 97.66 KiB
```

这不是“400G 一律配 100kB”。它没有给出设备的真实停止时延、cell 大小或额外余量。线缆长度、端口速率、MTU 或 gearbox 变化后，都应重新核对适用的 headroom profile，而非复用旧配置截图。

### 8.3 缓冲换来的还有时延

若出口队列有 512 KiB 数据排在某个包之前，并持续独占 100 Gb/s 的服务能力，则忽略其他开销的等待近似为：

```text
T_queue = 512 × 1024 × 8 / (100 × 10^9)
        ≈ 41.94 μs
```

在 400 Gb/s 服务能力下，相同积压约对应 10.49 μs。若只分到 25 Gb/s 服务，则约为 167.77 μs。若队列正被暂停，不能继续拿标称线速套这个除法，声称它会按有限的固定时间排空。

这也是为什么“吞吐还可以，但 P99 变差”应同时查持续积压与暂停。加大可用 buffer 可能减少某类丢弃，也可能让更深的队列存在更久；不能只看丢包率而不记录时延。

## 9. HOL Blocking：至少要区分两种机制

### 9.1 经典输入 FIFO 队头阻塞

构造一个最小模型：入口 FIFO 的头包去出口 D，而 D 暂时不能接收；它后面的包去空闲出口 E。如果调度只能检查 FIFO 头部，E 的包也不能前进。这就是经典的 Head-of-Line Blocking：受阻的是 D，受害者却包括去 E 的包。

VOQ 按目标出口等维度把等待拆开，调度器便有机会选择去 E 的可服务队列，而不必等 D 恢复。这个结论来自队列结构本身；它没有保证任意调度器都达到满吞吐，也没有增加 D 的服务能力。

![[图片/SVG/8_4_23_4.svg|900]]

### 9.2 PFC 优先级范围内的连带阻塞

再换一个模型：两条流 A→D 与 A→E 先共享一条上游链路，并且都映射到 priority 3。下游因去 D 的流量积压，对这条共享链路发出了 priority 3 的暂停。此时去 E 的流也可能无法经过这条链路，即使 E 的最终出口空闲。

这个受害关系来自**共享链路上暂停粒度比流粒度粗**。因此，改善芯片内部的 FIFO HOL，不会自动消除跨链路的 PFC 连带阻塞。只有先画出受害流与拥塞流共同经过哪条受控链路、用哪个 priority，才能准确地说明“谁拖住了谁”。[^qosmap][^queue]

### 9.3 不是所有排队都叫 HOL

| 情况 | 更准确的名称 | 哪种措施直接对准了问题 |
| --- | --- | --- |
| 所有包都去同一个满负荷出口 | 出口竞争 / 持续过载 | 减少输入、改变分布或增加真正的出口能力 |
| 头包去忙出口，后包去空闲出口却不能绕过 | 输入 FIFO HOL | VOQ/队列拆分与相应调度 |
| 同一暂停优先级上的不同流一起停 | PFC 连带阻塞 | 更细的隔离设计、端到端反馈、消除根因 |
| 高优先级长期占满服务，低优先级得不到机会 | 调度饥饿 | 调度保证、整形、重新分配业务类 |
| 多个资源互相等待且形成循环依赖 | 可能的死锁 | 检查依赖环和恢复机制，不只看平均负载 |

把所有症状都写成 HOL，会让“加 VOQ”“换队列”看起来像万能答案；这个表就是用来阻止这种过度归因。

## 10. 调度与拥塞传播：分类正确还不够

### 10.1 Queue 分开了，服务能力仍要分配

严格优先级先服务更高优先级的可发送队列；若高优先级长期有足够负载占满端口，低优先级可能缺少服务。加权或 deficit 类调度按配置和算法分配机会，但也不等于为每个 QP 保证相同吞吐。SAI 将 scheduler profile 与 queue 绑定，说明队列归属和服务策略是独立配置维度。[^queue]

因此给 CNP 一个单独队列后，还要回答：这个队列能否被错误的大流量占用？数据类和其他控制类获得什么最低服务？收到 PFC 后，调度器把哪些队列视为不可发送？这些问题不能由 DSCP 数字本身回答。

### 10.2 拥塞树怎样形成

设下游 D 暂停 S 的数据类。S 的相关出口不能继续发送，但其他入口短时间内还在收包；这些包继续占用各自的 ingress PG 与共享缓冲。S 随后可能向多个上游发出新的暂停。重复这一过程，最初的出口问题就可能扩展成一棵背压树。

这是沿资源依赖传播的推论，不要求最初就存在物理环。**出现拥塞树不等于已经死锁。** 要诊断死锁，需要确认缺少进展并存在相应循环依赖或设备定义的持续暂停条件。

### 10.3 Watchdog 不是无损保证的加强版

Watchdog 的检测与恢复应分别核查：怎样判定持续暂停、观察窗口多长、恢复期间是否仍保持无损、哪些队列会受影响。SAI 的持续暂停状态用于观察相关 queue 是否在轮询区间内始终没有恢复或前进；接口中存在这种状态，不等于设备自动完成恢复，也不能替代对根因的检查。若某项恢复配置允许丢弃报文，就不能把该区间继续解释为全程无损。[^queue]

即使部署启用了 PFC，也仍可能因为物理错误、分类不一致、headroom 不足、共享资源耗尽或恢复动作而丢包。应用侧如何处理超时、重试和 QP 错误，要回到 [[4.17 Retry RNR 与 Timeout]] 与 [[4.19 RDMA 故障恢复与连接重建]]。特别是 RNR 表示接收资源方面的传输条件，不能直接当作交换机 ECN 的同义词。

## 11. 观测：把“计数器涨了”改写成可检查的路径

### 11.1 最小观测集合

| 指标 | 关联对象 | 能支持的判断 | 单独不能证明什么 |
| --- | --- | --- | --- |
| 端口收发字节与错误 | 物理端口、方向、时间窗 | 负载分布和物理异常线索 | 每条 QP 的情况 |
| Egress queue watermark | 出端口 + queue | 曾出现多少指定口径的积压 | 当前仍有相同积压 |
| Ingress PG shared watermark | 入端口 + PG | 入口共享资源使用峰值 | 等同于某个出口 queue |
| PG headroom watermark | 入端口 + PG | 指定 headroom 区的使用峰值 | “非零就丢包”或“一定安全” |
| PFC Tx / Rx / 暂停时长 | 端口 + priority + 方向 | 背压方向与持续程度 | 根因在本机还是下游 |
| ECN 标记与丢弃 | queue/profile 或平台定义对象 | 是否在目标类触发标记/丢弃 | 接收端一定发送了 CNP |
| CNP Tx / Rx | 对应 RNIC 与方向 | 反馈的产生与到达 | 调速足够快、参数合适 |
| 应用吞吐、延迟、完成与错误 | 业务和操作类型 | 用户可见影响 | 自动归因到网络某一层 |

SONiC 设计中的三个可直接核查的 SAI 名称分别是：

```text
入口 PG headroom：SAI_INGRESS_PRIORITY_GROUP_STAT_XOFF_ROOM_WATERMARK_BYTES
入口 PG shared： SAI_INGRESS_PRIORITY_GROUP_STAT_SHARED_WATERMARK_BYTES
出口 queue shared：SAI_QUEUE_STAT_SHARED_WATERMARK_BYTES
```

它们属于三个独立的统计对象。CLI 与 telemetry 路径会随 NOS 版本变化，采集时用平台实际接口查询这些对象，不伪造一套适用于所有交换机的 `show` 命令。[^watermark]

### 11.2 Watermark 是一个窗口内的峰值

记录 watermark 时，应同时记录时间、上次清零位置、是否被采集器周期读取清零、当前值来自硬件还是软件累计、是否是 persistent 视图。否则，一组“实验前很高、实验后也很高”的数字可能只是历史峰值残留。

计数器相减也有条件：两次快照须对应同一对象与计数生命周期，期间没有复位、清零或回绕。多个设备时钟未对齐时，不要从毫秒级采样硬推微秒级触发先后。用更细采样、设备时间戳或事件记录验证因果关系。[^watermark]

### 11.3 两个症状相近、方向不同的案例

**案例 A：目的主机出口发生 Incast。** 若观察到目的出口 queue 积压和 ECN 标记增加，随后对应入端口 PG/headroom 上升并产生 PFC Tx，同时发送 RNIC 收到 CNP，可形成“汇聚造成服务不足，反馈与暂停随后介入”的证据链。它仍需要检查接收端与出口服务能力，而不能仅凭 Incast 标签忽略主机瓶颈。

**案例 B：下游先暂停了本机。** 若先看到面向下游的端口 PFC Rx 增加、相关发送 queue 长时间不可服务，随后本机多个入口 PG 增长并向上游发出 PFC Tx，更应沿下游继续定位。此时本机可能是拥塞传播的中间节点；直接增大本机 buffer，未必消除最初的停顿。

两个案例都是待验证的因果假设，不是根据一张静态计数器截图就能确定的结论。

## 12. 实验：复现“拥塞流拖住无关流”，而不是只跑满端口

### 12.1 先明确共享哪段路径

在隔离测试网中准备两条业务：拥塞流 C 发往接收端 D，受害流 V 发往接收端 E。让两者在分叉前经过同一条待观察链路，初始映射到同一 PFC priority；分叉后 E 的出口保持有余量。

基础发流入口可以使用 [[4.20 RoCE Fabric 组网：Clos、Leaf-Spine、ECMP、LAG 与 Oversubscription]] 的 perftest 模板。多发送端测试需要按工具的连接模型启动独立会话或实例，并为控制连接分配互不冲突的端口；一个只接受一对测试端的实例，不会自动变成多客户端 Incast 服务。启动前核对本机工具帮助和版本。

| 实验 | 与上一轮相比只改变什么 | 要保存的观测 | 支持或反驳什么 |
| --- | --- | --- | --- |
| A：仅 V | 不制造拥塞 | V 的吞吐/延迟、路径与 queue 基线 | 受害流本来是否正常 |
| B：V + C，同 priority | 对 D 施加受控汇聚负载 | 共享链路 PFC、D/E queue、相关 PG | E 有余量时 V 是否仍受影响 |
| C：业务类隔离对照 | 在能力允许时分开相关映射 | 完整映射、调度、共享池及 V 的变化 | 暂停范围是否是主要耦合来源 |
| D：改变突发长度 | 路径与类保持不变 | watermark、CE、CNP、暂停与恢复时长 | 反馈时间与暂存空间的关系 |

C 阶段不是“换一个 DSCP 即可隔离”。只有新的 DSCP 被正确映射到不同的暂停/队列资源，并配有适当调度和缓冲策略，对照才成立；若仍共享 PG、pool 或服务瓶颈，影响可能继续存在。

### 12.2 每一轮的记录模板

```text
设备/NOS/ASIC/固件版本：
端口与业务路径；速率、MTU、GID 类型：
DSCP/PCP → TC → PG / Queue → PFC priority 映射：
ECN 与 buffer profile 的对象、单位和参数语义：
发送端数量、目的端、QP 数、消息大小、突发与持续时间：
预热、重复次数、采样周期、计数器清零边界：
PFC Tx/Rx/暂停时长、PG/Queue watermark、ECN/CNP/丢弃：
V 与 C 的吞吐、延迟口径、完成与错误：
与基线相比的变化；支持的假设；尚未排除的解释：
```

这个模板要求保留反例：例如 V 的性能没有变化，就应写清这次拓扑与映射没有观察到预想的连带阻塞，而不是把测试调整到“必须出现教材现象”才算成功。

### 12.3 安全与可验证边界

预先约定停止条件，例如持续暂停、超出预设错误上限或管理面失联。具备带外管理与回滚记录后再进行有风险的配置对照；不在生产集群中临时停用 PFC 来“证明原理”。

软件交换机或自写 FIFO/VOQ 仿真可以验证第 7、9 节的逻辑模型，不能证明真实 ASIC 的 headroom 足够、每个 cell 的记账方式或 400G 下的突发容忍度。实际硬件数据尚未获得时，应把结论保留为设计假设。

## 13. 自测：给每句话补上作用对象

**问：PFC 从哪个方向发，暂停谁？** 接收侧遇到相关压力时，向相邻上游反向发出；上游在这条链路上约束指定 priority 映射到的发送流量。不是暂停单个 QP，也不是转发一个端到端 PAUSE。

**问：同一个包为什么可能同时占用 PG 和 Queue 的账？** PG 描述它从哪类入口到达，Queue 描述它等待从哪类出口发出；在共享缓冲模型中，两种归属可能观察同一份物理存储。

**问：ECN=100kB、XOFF=160kB，能否保证先 ECN？** 不能。第 7 节扇出例中，一个 PG 占 180kB、三个出口各 60kB，就足以推翻仅比较数字的论证；此外还须确认 `xoff` 的真实参数语义。

**问：为什么 400G 的 headroom 不能直接照搬 100G 配置？** 相同停止时延内，速率×时延项变为四倍；实际余量还受帧长、流水线和 cell 等因素影响。需要平台公式，而不是只按线速乘四后就宣布安全。

**问：VOQ 能否解决 PFC 的所有 HOL？** 不能。它可以拆开内部不同目的出口的等待；共享链路上同一 priority 被暂停时，不同目的流仍可能一起停。

**问：PFC 很多但没有丢包，是否说明网络健康？** 不能。还要看暂停持续时间、受害业务、端到端反馈、应用时延与是否发生恢复动作。“无丢包”不是“无排队、无饥饿、无故障”的同义词。
