# 4.24 RoCE Fabric 故障诊断：PFC Storm、Pause Propagation、ECN/CNP、丢包与拥塞定位

> **排障要回答的是：哪一方向、哪一优先级、哪一跳停止了前进，停止之前发生了什么。** “PFC 很多”“CNP 在涨”“链路是 UP”都不足以单独给出根因。

本篇承接 [[4.7 PFC ECN 与 DCQCN]] 的反馈机制，把重点放在证据采集、故障分型、逐跳追踪和恢复验证。QP 错误码与重试边界见 [[4.17 Retry RNR 与 Timeout]]；确认故障之后如何处理旧请求、重建连接，交给 [[4.19 RDMA 故障恢复与连接重建]]，不在这里重复实现。

> [!info] 来源与适用边界
> 本次未能取得本项目 Sources 中可读的教材文件；没有引用未读教材或编造页码。本文依据文末官方文档、上游源码和明确标注的工程推导。Linux 命令面向 Ubuntu/Linux 的硬件 RoCE 环境；交换机命令**仅以 Cumulus Linux 5.9 为例**。计数器是否存在、计数范围和更新周期要以现场驱动、固件及 ASIC 文档为准。所有案例数字与示意曲线均非实测结果。

## 1. 先给故障划定边界，不先改 PFC 参数

建立一条故障记录：发生时刻与时区、影响的业务及 p99/SLO、源/目的设备、操作类型、方向、QP/连接、数据优先级、经过的交换端口，以及最近的配置变更。保存正常窗口作对照，否则一个累计多年的错误计数没有诊断价值。

**请求发起方不一定是大流量发送方。** RDMA WRITE 的主要数据从 requester 到 responder；RDMA READ 的大块响应反方向返回。画拓扑时先用实际字节方向确定“上游/下游”，不要直接套用业务中的 client/server 角色。操作语义可回看 [[4.5 Send Recv 与 RDMA Read Write]]。

建议先把问题缩成一个可证伪的句子，例如：“A→B 的 WRITE 在跨 Leaf 路径上吞吐下降，同一优先级的 A→C 也变慢；B→A 暂未复现。”这比“RDMA 网络不稳定”更容易设计对照实验。

| 分界问题 | 要保存的证据 | 能缩小的范围 |
|---|---|---|
| 所有作业还是少数设备？ | 受影响和未受影响的设备对、消息尺寸、时间窗 | 全局策略、局部端口、单一应用 |
| 单向还是双向？ | 分方向的应用完成字节、NIC TX/RX 字节 | 发端注入、收端吸收、反向控制路径 |
| 同 Leaf 正常、跨 Leaf 异常？ | 保持端点和负载可比的路径对照 | 上联、ECMP 成员、路径 QoS |
| 换 rail 后恢复？ | 各 rail 的实际端口字节、QP 选择与拓扑 | NIC/PCIe/网络共同故障域 |
| 业务慢但网络并不忙？ | CQ 进展、RQ 补充、线程状态、PCIe/内存压力 | 主机或应用，而非 Fabric 容量 |

最后一个问题与 [[4.25 RDMA Multi-Rail 与拓扑感知：NUMA、PCIe Root、Multi-NIC、路径选择与负载均衡]] 相接：换网卡同时也可能换了 NUMA/PCIe 路径，不能把“换 rail 有效”直接解释为“交换机有故障”。

## 2. 数据、PFC、CNP 是三条不同的路径

![[图片/SVG/8_4_4_24_1.svg|900]]

图中实线表示数据方向，红色反向箭头表示**一跳一跳重新产生的 PFC**，蓝色长回路表示接收端返回发送端的 CNP。PFC 控制帧不是被路由器沿原路径转发的端到端报文；传播的是缓冲耗尽和暂停造成的背压。CNP 则要通过实际可达的回程到达原数据发送端。[^C1]

### 2.1 RX/TX 必须以正在读取的本端口为准

以支持这些字段的 mlx5 物理端口为例：

| 本端口指标 | 本端在做什么 | 下一步往哪里查 |
|---|---|---|
| `rx_prio3_pause` 增加 | 收到对端对 priority 3 的暂停请求 | 沿本端数据 TX 方向查对端为什么要求暂停 |
| `tx_prio3_pause` 增加 | 向对端发出 priority 3 暂停请求 | 查本端接收吸收能力、相关 PG/队列及下游阻塞 |
| `rx_prio3_pause_duration` 增加 | 本端该优先级的发送被暂停 | 与吞吐、队列进展和受影响优先级对齐 |
| `tx_prio3_pause_duration` 增加 | 本端累计发送了暂停时长 | 不等同于已经测到对端实际停发了这么久 |

这里的 `3` 只是字段命名示例，**不是 RoCE 必须使用 priority 3**。字段名、单位与物理/vPort 作用域来自 Linux mlx5 文档；该文档将 pause duration 标为微秒。[^K1]

一个节点收到 PFC，首先说明它是当前暂停链上的**受影响方**，不是已经证明它制造拥塞。反过来，一个节点发出 PFC，也可能只是替更下游的阻塞传递背压。

### 2.2 如何沿 Pause Propagation 找到停止前进的位置

从业务受害端出发，记录本端 `RX pause`；在链路对端核对相同优先级的 `TX pause`。随后查对端内部与该流关联的入口 PG、出口 TC、占用/水位和出队进展。如果出口又在收到下一跳 PFC，就继续沿数据方向追踪；如果不再收到下一跳 PFC，却持续无法吸收/转发，则在这一跳继续拆分原因。

“最后不再收到 PFC 的位置”只是**候选边界**：出口 oversubscription、接收 NIC 到 PCIe 的写入瓶颈、调度器限速、优先级映射错误，都可能在这里表现为停滞。需要用负载变化和分层计数器进一步区分。

用 1 秒采样数据不能证明几微秒内的严格先后关系。跨设备时钟偏差、非同时读出的计数器和 watermark 的保留周期都会影响因果判断；必要时使用经批准的高分辨率遥测或镜像捕获，并注明其观测盲区。

## 3. 不把所有暂停都叫 PFC Storm

| 现象 | 最少还需要什么证据 | 不能直接下的结论 |
|---|---|---|
| 正常拥塞反馈 | 负载上升后标记/反馈增加，业务仍持续前进，降载后恢复 | “有 CNP 就是故障” |
| 短时 PFC 兜底 | 暂停短暂、可恢复，与突发及队列水位相关 | “出现一次 PFC 就必须关掉 PFC” |
| PFC storm / 长时间暂停 | 持续暂停或频繁续期、队列进展显著下降、影响范围扩散 | “pause 包数超过某固定值就是 storm” |
| Pause propagation | 多条相邻链路同优先级背压，传播方向与队列依赖相符 | “最多 pause 的交换机就是起点” |
| PFC 引起的 HOL | 无共同目的的流因共享被暂停优先级而变慢 | “每一个受害流本身都发送过量” |
| 真正循环等待死锁 | 能画出资源依赖环，各环节互相等待且缺少恢复进展 | “watchdog 显示 DEADLOCK 就证明了拓扑环” |
| watchdog 保护动作 | 事件、受影响端口/TC、丢包和恢复时间对齐 | “保护动作之后丢包一定来自线缆” |

**Storm 是现象描述；循环等待是机制判断。** 没有依赖环证据时，报告写“持续 PFC 阻塞，watchdog 触发”，比写“确认 PFC deadlock”更准确。

Cumulus Linux 5.9 的 watchdog 检测长时间暂停，保护阶段会改变受影响 TC 的 PFC 处理并丢弃相关新到达流量；其状态字段包含 `DEADLOCK`。这是特定实现的检测/恢复状态，不是对所有平台的统一定义，也不是“无损仍然被保证”。[^C2]

## 4. 用同一窗口的计数器增量建立证据链

![[图片/SVG/8_4_4_24_2.svg|900]]

这张图用于组织观测，不是规定所有故障必定按图中的时间顺序发生。微突发可能早于一次完整反馈；持续阻塞也可能在平均端口利用率不高时发生。

### 4.1 先区分 Counter、Gauge 与 Watermark

单调累计计数器才适合计算 `ΔC = C_after − C_before`。出现设备重置、计数器清零、回绕或作用域变化时，把该窗口标记为无效，不能把负增量改成零掩盖问题。速率的分母使用**实际采样间隔**，而不是预期的 `sleep 1`。

对于已确认单位为微秒、表示本优先级实际停发时间的 RX pause duration，可估计暂停占比：

$$
P_{pause,p}=\frac{\Delta D_{rx,p}}{10^6\,\Delta t_s}.
$$

例如一段实际 2 秒的窗口增加 600,000 微秒，则该优先级停发占比约 30%。这是**计算示例**；不能把多个优先级的占比相加当成整端口停发占比，也不能未经确认把 TX duration 代入同一解释。算出超过 100% 时先检查计数语义、作用域与窗口，而不是强行截断。

当前队列占用是 Gauge；最大水位是 Watermark，可能保留了更早的历史峰值。另如 mlx5 的 `outbound_pci_stalled_rd` / `outbound_pci_stalled_wr` 是最近周期的百分比指标，不是可以再差分的累计字节数。[^K1]

### 4.2 按故障层级保留哪些字段

| 证据层 | 示例字段或数据 | 使用时的限制 |
|---|---|---|
| 物理链路 | CRC/FCS、不可纠正错误、link down、协商速率 | 已纠正 FEC 错误不等于已经丢了同样数量的报文 |
| PFC | 每优先级 RX/TX pause 与 duration | 方向、优先级、单位、实际采样窗口必须明确 |
| 交换机缓冲 | ingress PG 占用/峰值、egress TC 出队、discard | ingress 与 egress 不一定共用同一记账对象 |
| ECN 反馈 | 出口 CE 标记、收端 NP、发端 RP | 不能要求各层包数一一相等 |
| 传输层 | retry、timeout、sequence error、RNR、CQ 错误 | 错误类别不等同于故障发生的位置 |
| 主机吸收 | PCIe stall、内存带宽、NUMA、CQ/RQ 进展 | 可能向网络反向施加背压 |
| 业务 | 成功完成字节、请求 p99、错误/重试、结果正确性 | 端口字节含协议开销或重传，不能代替有效吞吐 |

Linux mlx5 文档区分 ring、vPort、物理端口与设备指标。一些普通 Ethernet vPort 字节字段不含 RDMA，而 `*_vport_rdma_unicast_bytes` 专门统计 RDMA。先确认自己观测的是哪条数据路径，不能因为普通 netdev 统计很低就断言 NIC 没在传 RDMA。[^K1]

## 5. ECN/CNP 排障：逐段验证，而不是只看“CNP 有无”

把闭环拆成五个观测位置：**交换机标记 → 接收 NIC 看见 CE → 接收 NIC 发 CNP → 原发送 NIC 处理 CNP → 注入速率/队列随之改变**。

Linux 上游 mlx5 RDMA 源码定义了 `np_ecn_marked_roce_packets`、`np_cnp_sent`、`rp_cnp_handled`、`rp_cnp_ignored` 等字段。只有硬件/驱动实际暴露它们时才读取；缺少文件是“不支持或未暴露”，不是“计数为零”。[^K2]

| 对照结果 | 优先验证的假设 | 用什么排除其他解释 |
|---|---|---|
| 出口队列持续拥塞，但没有 CE | ECN 未启用、映射到错误 TC、包不是 ECT、阈值/观测对象错误 | 核对真实报文标记、TC 映射、同窗口出队和标记计数 |
| 交换机 CE 增加，目标收端 NP 不增加 | 数据尚未到收端、丢包、观察错 NIC、CE 被改写或计数口径不同 | 按端点/端口核对流量，用受控镜像补证 |
| NP 收到 CE，但 CNP 不符合预期 | NP 配置、计数范围、反馈节流/合并 | 不用“CE 数必须等于 CNP 数”作为判定式 |
| 收端发送 CNP，发端处理数不增加 | 回程可达性、CNP QoS、丢弃/限速、观察错发端 | 核对回程端口、优先级、丢弃及 RP ignored |
| RP 已处理 CNP，但仍大量 PFC | 反馈过晚、突发过大、参数不合适或接收吸收受限 | 同时观察注入速率、反馈延迟、PG/TC 与主机压力 |

这张表是**排除顺序**，不是仅靠两个计数器即可自动定位的软件算法。不同来源的聚合范围可能不同；反馈可能节流；一次采样可能错过短事件。RP handled 增长也不自动证明最终速率调节幅度足够。

### 5.1 DSCP、PCP、TC、PFC priority 不能混成一个数字

核对从报文到队列的完整映射：IP DSCP / VLAN PCP → 端口 trust 与分类规则 → switch priority → 出口 TC / 入口 PG → PFC 使能集合。数据报文和 CNP 都要检查，且每个端口都可能有不同策略。

IP DS 字段包含 6 位 DSCP 和 2 位 ECN。例如**仅用于解释编码**：DSCP=26、ECN=ECT(0)=2 时，8 位字段值为 `(26 << 2) | 2 = 106`。这不表示现场应设 106，也不表示 TC/PFC priority 是 26；把“完整 traffic class/TOS 字节”与“DSCP 值”混填是常见的排查方向。RFC 3168 解释 IP ECN，并不定义 RoCE CNP。[^R1]

Cumulus 5.9 文档给出的示例映射使用 data DSCP 26、CNP DSCP 48，并为控制流安排不同队列。它们是该配置示例，不是 RoCE 标准为所有厂商规定的号码。实际目标是让反馈获得足够及时的服务，防止控制流和被暂停数据一起长期失去前进能力。[^C1]

### 5.2 不把 ingress XOFF 与 egress ECN 当成同一个队列阈值

“让 ECN 比 PFC 更早发挥作用”是设计意图；**并不总能直接用两个配置里的字节数比较来证明**。在分别按 ingress PG 和 egress TC 记账、使用 shared pool 或动态阈值的 ASIC 上，先找到各参数对应的对象、动态共享规则和实际占用轨迹。[^C1]

用于思考 headroom 的简化量纲式是：

$$
H \gtrsim R_{ingress}\,t_{stop} + H_{packetization} + H_{implementation}.
$$

这里 `t_stop` 包含检测/发出暂停、传播、对端反应和在途数据到达的有效时间预算；后两项代表报文粒度与实现余量。**这是工程预算模型，不是交换机配置公式。** 假设 400 Gb/s 的输入在额外 2 μs 内维持满速，仅这部分就在途约 100,000 B，还未包含其余余量；不得把此数直接复制为 XOFF/headroom。

同理，端到端反馈生效之前的排队增量取决于 `∫ max(输入速率−服务速率, 0) dt`。即使平均输入小于出口速率，多个发送者同一时刻突发也可能耗尽反馈余量。

## 6. Linux 主机的只读采证流程

### 6.1 先保存设备映射和版本

下面只查询状态。接口名必须替换成现场已确认的 RoCE netdev；RDMA 设备名、netdev、PCI BDF 是不同命名空间。先看 `rdma link show` 的映射，再解释后续统计。RDMA/连接基础见 [[4.11 RDMA CM 与连接建立]]。

```bash
IFACE=enp65s0f0    # 示例名：先按 rdma link show 的实际映射替换
uname -r
rdma link show
ibv_devinfo
ip -details link show dev "$IFACE"
ethtool -i "$IFACE"
ethtool "$IFACE"
```

这些命令的目的不是一次看出根因，而是固定“本次到底测了谁”。同一服务器升级固件、更换网卡或切换容器设备之后，名字相似不代表数据源相同。保存版本输出，不依赖记忆中的默认行为。

### 6.2 完整保存两个统计快照，再离线筛选

把下面一段作为独立 Bash 片段使用。它只在本地建立采证目录，不清零设备计数器，也不修改链路配置。要求当前账户具有查询权限；失败会显式停止，不把权限错误误写成零值。

```bash
set -euo pipefail
IFACE=enp65s0f0
OUT="$(mktemp -d "${TMPDIR:-/tmp}/roce-evidence.XXXXXX")"
for phase in before after; do
    date --iso-8601=ns > "$OUT/$phase.begin"
    cat /proc/uptime > "$OUT/$phase.uptime.begin"
    ethtool -S "$IFACE" > "$OUT/$phase.ethtool.txt"
    ip -s -s link show dev "$IFACE" > "$OUT/$phase.link.txt"
    cat /proc/uptime > "$OUT/$phase.uptime.end"
    date --iso-8601=ns > "$OUT/$phase.end"
    if [ "$phase" = before ]; then sleep 2; fi
done
printf 'Evidence directory: %s\n' "$OUT"
```

前后时间戳说明查询并非原子快照；`/proc/uptime` 可帮助发现墙上时钟调整。`sleep 2` 只是留出观察间隔，统计窗口还包含命令运行时间。细粒度实验应给每个数据源分别记时间，跨主机还需记录时钟同步误差。

保存**完整** `ethtool -S`，而不是一开始就只保存 `grep pause`：否则后续可能已经丢掉 CRC、discard、PCIe 或其他反证。只读命令也会引入观测开销，不应在生产环境无上限地高频循环。

### 6.3 RDMA 硬件计数器：先枚举，后解释

下面列出一个指定 HCA/port 实际暴露的文件，不假设所有主机支持同样的计数器。替换 `DEV`、`PORT` 后再运行；目录缺失时报错，不伪造空白健康报告。

```bash
set -euo pipefail
DEV=mlx5_0
PORT=1
ROOT="/sys/class/infiniband/$DEV/ports/$PORT/hw_counters"
if [ ! -d "$ROOT" ]; then
    printf 'Hardware counters not exposed: %s\n' "$ROOT" >&2
    exit 1
fi
for file in "$ROOT"/*; do
    [ -f "$file" ] || continue
    printf '%s=' "${file##*/}"
    cat "$file"
done
```

输出后再按 §5 的 NP/RP 角色对照。`local_ack_timeout_err`、`packet_seq_err`、`req_transport_retries_exceeded` 与 `req_rnr_retries_exceeded` 在上游 mlx5 源码中属于不同类别，不能把所有 `err` 统一计为“物理丢包”。[^K2]

## 7. 交换机侧：用真实队列和逐端口证据对齐

以下是 **Cumulus Linux 5.9 NVUE 的只读查询例子**，只用于已经确认使用该版本命令体系的设备。`swp16` 要换成实际物理口；其他 NOS 使用其官方等价查询，不要跨厂商照抄。[^C1][^C2]

```bash
nv show qos roce
nv show interface swp16 qos roce status
nv show interface swp16 qos roce counters
nv show interface swp16 qos pfc-watchdog
```

分别用来核对总体 RoCE profile、该口的数据/CNP 映射、队列与反馈计数、watchdog 状态。不要只抄一个“PFC enabled=true”：同一页的 ingress PG、egress TC、当前占用、峰值和丢弃更接近实际故障位置。

需要抓包时，先说明**在哪里能看见什么**。普通主机 `tcpdump` 没抓到硬件卸载的 RoCE 报文，不足以证明网络没有发送；交换机镜像可能采样、丢包或无法完整呈现控制帧。抓包与 NIC/交换机计数器应互相补证，不能相互替代。

## 8. 现场分流：先保留证据，再做最小范围干预

![[图片/SVG/8_4_4_24_3.svg|900]]

**物理错误先查物理层。** 若 CRC/不可纠正错误/link flap 在故障窗口增长，先定位具体端口、模块、链路训练/协商问题；不要用增加 retry 或调低 ECN 阈值“修复”物理损坏。反过来，仅 FEC 已纠正计数增长时，应查链路余量和趋势，不直接等同于业务丢包。

**持续暂停先沿数据方向追踪。** 确认相关优先级确实被停发，关联 PG/TC 的占用与出队。接收主机 PCIe/内存吸收不足也可能让背压进入 Fabric；链路利用率低不排除这一类停滞。

**只有 RNR 时先看接收资源。** SEND 和 WRITE with Immediate 的接收资源语义，与普通 RDMA WRITE 不同。接收方 RQ 补充不及时不能靠增加 Fabric 带宽解决；具体语义和重试终止条件见 [[4.17 Retry RNR 与 Timeout]]。

**发生 watchdog 后分别验证安全性与可用性。** 保护动作可能通过丢包打破持续阻塞；随后仍要检查重传是否恢复、QP 是否进入错误、业务是否存在结果不确定的请求。端口恢复转发不等于业务自动恢复一致性。

### 8.1 三个教学病例：用反证约束结论

以下均为**假设场景**，不是实际观测报告。

| 场景 | 观测组合 | 可检验的解释 | 下一项有区分力的实验 |
|---|---|---|---|
| A：只有某路径慢 | 对应 TC 的 CE 很少，入口 PG 峰值高，PFC 持续；相邻路径正常 | 分类/映射/ECN profile 或路径容量有差异 | 保持端点、尺寸、并发不变，核对两路径的实际 QoS 和出口成员 |
| B：接收主机发 PFC | 收端 TX pause 与 PCIe stall 同窗上升，多个发送端 RX pause；交换出口自身无持续饱和 | 收端吸收能力受限，背压向外传播 | 保持网络不变，改变收端 NUMA/内存负载或使用健康收端对照 |
| C：没有明显 PFC 但反复 retry | 单条物理链路错误增加，ECN/CNP 不显著 | 损坏/训练/模块等物理问题，而非拥塞控制不足 | 在维护窗口替换已定位链路部件，验证错误与 retry 同时消失 |

病例 B 中“PCIe stall 与 pause 同时上升”仍只是强相关。需要对照实验、真实拓扑和方向一致性，才能排除其他共同原因。

### 8.2 分级处置，不先做全网开关实验

| 阶段 | 建议动作 | 必须保留的约束 |
|---|---|---|
| 保全现场 | 保存端点、交换端口、优先级、时间窗、版本与配置快照 | 不先 clear counters / 重启设备 |
| 降低影响 | 在业务许可内降低注入、限制 incast 并发或暂停特定作业 | 有责任人、观察窗口和撤销方式 |
| 隔离故障域 | 经审批隔离已定位端口/设备或切换健康路径 | 不把整个无损域一并关掉 |
| 校正配置 | 逐项修复已证实的 QoS/缓冲/反馈差异 | 保存原值，一次只改一类变量 |
| 恢复与复验 | 验证有效吞吐、p99、错误、pause 和重试共同恢复 | 还要验证业务正确性，不能只跑带宽 |

不要把“全网关闭 PFC”“禁用 watchdog”“无限加大超时”作为默认第一步。存在 ECN-only 的 lossy RoCE 部署，但它需要与 NIC 恢复能力、流量和服务目标一起验证，不是事故现场把既有 lossless profile 拆掉就完成迁移。[^C1]

## 9. 把知识变成一个受控实验报告

先用 [[4.9 ibv_perftest 基准实验]] 建立**单对端、低并发、可持续前进**的基线，再在隔离测试环境逐级增加发送者并发或消息突发。固定其他条件，分别保留正常、拥塞、恢复三个窗口；没有可控交换机/硬件遥测时，不声称已经复现硬件 PFC 行为。

| 实验组 | 只改变什么 | 应提交的证据 |
|---|---|---|
| 单对端基线 | 不改变网络配置 | goodput、消息尺寸、QP 数、各端口计数增量 |
| 有界 incast | 分级增加发送者数量 | 出口队列、NP/RP、pause、业务完成进展 |
| 接收端对照 | 改变 CPU/内存本地性或受控主机负载 | NUMA/PCIe 与网络计数的方向关联 |
| 健康路径对照 | 改变一条已知路径或 rail | 实际设备选择、端口字节、路径 QoS |
| 恢复验证 | 回到原负载和配置 | 恢复耗时、是否遗留 QP 错误、结果正确性 |

不要以软件 RXE 的结果证明交换 ASIC/PFC/硬件拥塞控制行为，边界见 [[4.8 soft-RoCE 边界]]。也不要默认主机 `tc netem` 一定作用在硬件卸载的 verbs 数据路径上；故障注入必须先证明它确实覆盖目标流量。

报告至少附一张真实端口拓扑、一组相同窗口的计数器增量、一条有反证的根因论证、一次可撤销的修复和一次业务级复验。若无法取得某类证据，写“未观测”，不要写“无异常”。

## 10. 自测：能否用一句话解释关键边界

**为什么 RX pause 高不说明本机发得太多？** 它先说明本端被对端要求停发；对端可能拥塞，也可能把更下游的背压传来。

**为什么不能把 CE、CNP、RP handled 做成严格相等校验？** 反馈可能节流或合并，各计数器的范围与更新时间也可能不同。

**为什么“没有丢包”不能证明 Fabric 健康？** 持续暂停或 HOL 可以让业务失去前进能力，而丢弃计数仍不明显。

**为什么不能仅靠 K_ECN < XOFF 验证配置？** 两个参数可能属于不同 ingress/egress 记账对象和共享缓冲规则，数值可比性尚未成立。

**怎么区分 Fabric 问题与主机吸收瓶颈？** 沿暂停方向追到候选边界，再用队列、物理错误、PCIe/NUMA 与受控端点对照验证。
