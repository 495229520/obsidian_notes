# PCP、Interactive Proof 与 SNARK-STARK：从局部验证到可验证计算

> [!abstract] 本篇到哪里就停
> 目标是看懂这条知识链：**计算声明 → 随机化验证 → 结构化证明 → 承诺与密码学编译 → 可部署的简洁论证 → zkML**。它不是一条所有协议都必须依次经过的实现流水线，而是一张认知地图。
>
> 能解释“为什么不是随便抽查几个原始字节”“证明绑定了哪个模型和哪种计算语义”“零知识并非验证正确性的同义词”，就达到本篇目标。**不证明 PCP theorem，不推导椭圆曲线配对，不实现承诺或证明系统。** 高性能网络与存储仍然是主线。

## 1. 从“数据没变”到“计算关系成立”，究竟多问了什么？

设服务端返回一个结果 $y$，声称它来自输入 $x$ 上的计算 $f$。客户端真正想问的是：

$$
y=f(x)\ ?
$$

重新运行一次 $f$ 可以检查结果，却失去了外包计算的部分意义。可验证计算研究的是：服务端除了给出结果，还给出可检查的证明或论证，使验证者不必照原样重算全部工作。**代价转移到哪里、是否真比重算划算，必须另外核算。**[^stark][^thaler]

先把几种问题分开。下表是本文用于系统讨论的分类，不是说它们无法组合。

| 我想确认的东西 | 典型问题 | 单靠它不能证明 |
|---|---|---|
| 内容标识与完整性 | 这些字节是否匹配可信的 Hash / Merkle root？ | 它们是不是正确程序的计算结果 |
| 远端持有或可取回性 | 远端是否按协议持有数据，或满足可恢复条件？ | 它是否正确执行过某个任意程序 |
| 可验证计算 | 给定输入和程序约束，结果关系是否成立？ | 输入来自真实世界、模型判断符合事实 |
| 零知识 | 验证时能否不额外泄露约定的私有见证？ | 公开输入和公开输出本身没有泄露信息 |

例如，对一个错误答案计算 SHA-256，仍然能得到完全正确的摘要。Hash 忠实标识这个答案的字节，不替你判断答案与输入之间的计算关系。

### 1.1 三个符号足够理解后面的故事

把要检查的关系写成：

$$
R(s,w)=1
$$

其中，$s$ 是 **statement（公开语句）**，可以包含输入、输出、程序标识和承诺；$w$ 是 **witness（见证）**，可以包含私有输入、中间值或执行轨迹；$\pi$ 是证明者生成、验证者检查的证明对象。验证者通常运行某种 `Verify(public_parameters, s, π)`，而不是读取整个 $w$。这是关系层面的抽象，不是一个可直接调用的统一 API。[^groth16][^artemis]

“接受证明”应读作：**在该协议的安全定义、参数和假设下，有理由接受它所编码的关系**。它不自动证明“服务端昨天在某一块真实 GPU 上执行了这段代码”。验证数学关系和证明物理执行历史，是不同的声明。

![[图片/SVG/PCP-局部验证与密码学编译.svg|900]]

图中的分支不是严格的历史谱系。Interactive Proof、PCP、IOP 提供不同的验证模型；承诺与适用的密码学变换，把其中一些模型转成实际通信协议。SNARK/STARK 也不是两个互斥的“椭圆曲线箱子”和“哈希箱子”。[^thaler][^stark]

## 2. Interactive Proof：验证者为什么需要随机挑战？

**Interactive Proof（交互式证明，IP）**让证明者 Prover 与验证者 Verifier 交换消息。验证者不一定亲自做完全部计算，但可以根据自己的随机数提出挑战，检查回答之间的一致性。随机性的重要之处是：证明者不能提前只为一个完全可预测的检查点编好答案。[^thaler]

先记住三个安全属性，它们回答不同的问题。

| 属性 | 直觉 | 不要误读成 |
|---|---|---|
| Completeness，完备性 | 声明为真、双方按协议执行时，应能通过 | 所有网络故障或实现错误都不会造成失败 |
| Soundness，可靠性 | 声明为假时，作弊者很难让验证者接受 | 每个实现都绝无漏洞、每次随机检查都必然抓到 |
| Zero-Knowledge，零知识 | 可用模拟等安全定义刻画“不额外泄露见证” | 验证者不知道公开语句，或输出没有信息量 |

再区分两个常被统称为“证明”的术语：**proof** 的可靠性通常针对计算能力不受限的作弊证明者；**argument** 则依赖密码学假设，限制作弊者的计算能力。实际 SNARK 的字母 A 是 Argument，这个区别不是营销措辞。[^thaler]

**Argument of Knowledge（知识论证）**还带有知识性要求：在相应定义下，成功证明者的行为应支持提取出一个满足关系的见证。这里的“知道”是数学安全定义中的概念，不是证明者必须把私有数据发给验证者，也不是心理学意义上的理解。[^groth16]

> [!important] “零知识”是一条额外轴
> 可以只要求计算可验证而不要求见证保密；也可以选择满足零知识的具体证明系统。不要因为名字含有 SNARK、STARK 或“证明”，就默认整个应用已经隐私安全。公开的 $s$、输出以及应用的访问模式仍需要各自评估。

## 3. PCP：少量查询的对象，是特殊构造的证明，不是原始文件

### 3.1 先反驳一个很自然的误解

一份含 $N=1{,}000{,}000$ 个位置的原始记录中，只有一个位置错误。均匀、无放回地抽查 $q=10$ 个位置，命中这个错误位置的概率为：

$$
P(\text{命中})=\frac{q}{N}=10^{-5}=0.001\%
$$

这个简单计数反例已经说明：**没有额外结构时，抽几个字节不可能自动变成强正确性保证。** 它不是 PCP 定理的用法。

PCP 是 **Probabilistically Checkable Proof（概率可检查证明）**。验证者查询的是为验证任务特别构造的证明编码；它的局部检查，与“声明是真是假”之间有全局可靠性关系。关键工作在于证明表示和检查规则如何构造，而不是把抽样次数写成一个很小的常数。[^pcp]

![[图片/SVG/PCP-固定证明与抽样约束.svg|900]]

图中的红色约束只表达“错误声明无法通过任意伪造证明躲过足够多的检查”的机制直觉，不是某一种 PCP 编码的真实矩阵，也不声称每个错误原始字节都会扩散成固定数量的错误格子。

### 3.2 定理只认一行，不做证明

PCP 定理的经典表述之一是：

$$
\mathrm{NP}=\mathrm{PCP}(O(\log n),O(1))
$$

在标准模型中，对长度为 $n$ 的输入，存在多项式时间验证者，使用 $O(\log n)$ 个随机比特、只查询证明中常数个比特，即可达到常数级可靠性界。这里采用原论文中“真命题可总被接受，假命题至少以 $1/2$ 概率被拒绝”的表述来理解。[^pcp]

真正值得记住的是量词：

$$
\begin{aligned}
\text{声明为真：}&\quad \exists\pi,\ \Pr_r[V^\pi(s;r)=1]=1,\\
\text{声明为假：}&\quad \forall\pi,\ \Pr_r[V^\pi(s;r)=1]\le\tfrac12.
\end{aligned}
$$

**证明 $\pi$ 必须先固定，之后才由验证者选择随机数 $r$。** 不能允许证明者看到每次查询位置以后，再临时改写那些位置来应付本轮检查。[^pcp]

这不意味着“对一个真命题的合法证明随便翻转一位，验证者也一定以常数概率发现”。定理的 soundness 针对的是**假声明下的所有伪造证明**，不是对任意微小存储损坏都作同一个保证。

### 3.3 三个“常数查询”没有承诺的事情

第一，常数指**对证明的查询次数**，不意味着不读公开输入，不意味着验证者总体只做常数工作。第二，定理是存在性与复杂度结果，不是开箱即用的工程实现或性能承诺。第三，把错误率降得更小，通常要重复检查或使用具体协议的安全参数；不能把常数次数理解成免费获得任意安全等级。[^pcp]

对上述固定证明、每次使用独立新随机数且每轮错误接受率最多 $1/2$ 的模型，连续 $k$ 轮都误接受的概率最多 $2^{-k}$。这是这个模型中的重复放大，不是任何 SNARK 的参数计算公式，更不是原始文件抽样的通用结论。

## 4. 承诺：把“证明早已固定”落到真实通信里

### 4.1 Merkle root 可以固定内容，但不能单独证明计算正确

理想 PCP 允许验证者随机访问一份已固定的证明。现实中，证明可能保存在远端，验证者也不希望下载全部内容。一个重要的桥梁是 **commitment（承诺）**：证明者先提交承诺，再回答挑战对应的 opening（打开证明）。[^thaler]

以 Merkle 向量承诺作直觉模型：证明者先构造有固定编码和位置规则的叶子向量，发送 root；验证者之后选位置；证明者返回叶子及认证路径。验证者既检查“返回值确实属于先前承诺的向量”，也检查“这些返回值满足本轮验证谓词”。两者缺一不可。[^thaler]

| 层次 | 检查的东西 | 独自缺少什么 |
|---|---|---|
| 承诺与 opening | 这些局部值是否来自先前固定的对象 | 局部值之间是否满足计算约束 |
| 局部代数或一致性检查 | 打开的值是否满足本轮规则 | 对端是否每轮换一份对象来迎合挑战 |
| 完整协议 | 对象绑定、挑战、检查与安全归约 | 仍要依赖具体模型、参数和实现正确性 |

Merkle root 不能取代 PCP / IOP 的验证规则；如果只验证路径，得到的是“这个值属于那个树”，不是“整个计算正确”。二叉 Merkle 树的认证路径还要携带相应的兄弟节点哈希，因此“少查几个位置”也不等于零通信。

### 4.2 Binding 与 Hiding 不是同一个性质

**Binding（绑定性）**限制证明者把同一承诺打开成不一致的内容；**Hiding（隐藏性）**限制承诺泄露其内容。一个普通确定性 Hash 并不自动提供隐藏性：对只有“是/否”两个可能值的秘密，观察者可以自己计算两个摘要后比对。需要隐藏时，必须采用满足对应安全定义的承诺方案，而不是只给 Hash 改名。[^thaler]

**Polynomial Commitment（多项式承诺）**允许先承诺一个多项式，再证明它在挑战点 $z$ 上的求值满足 $p(z)=v$。这是现代证明系统的一类重要工具，但“一次求值正确”仍不等于“任意程序已经被验证”：程序约束必须先被正确映射进被检查的关系。不同方案的设置、假设、打开成本和知识性保证可能不同。[^plonk][^artemis]

### 4.3 IOP 与 Fiat–Shamir 放在什么位置？

**IOP（Interactive Oracle Proof，交互式预言机证明）**把交互轮次与对大消息的局部查询结合起来。在实现中，可以用承诺固定这些大对象。基于多项式与编码的 IOP 是理解 STARK 的重要入口，但不需要在本篇深入它的形式化定义。[^stark][^fri]

对于满足相应条件的 public-coin 协议，**Fiat–Shamir** 用哈希导出的挑战替代验证者现场发送的随机挑战。示意写作：

$$
c_i=H(\text{domain}\parallel s\parallel\text{commitments}\parallel\text{transcript prefix})
$$

这不是可直接照抄的协议实现。需要规范编码、语句绑定、域分离以及适用的安全分析；随机预言机等假设也必须说明。**不能把任意交互协议里的随机数换成 Hash，就宣称获得安全的非交互零知识证明。**[^thaler][^plonk]

## 5. 一个小例子：随机代数检查，不等于随机挑几个结果元素

用矩阵乘法认识这个差别。服务端声称 $C=AB$，验证者选随机向量 $r$，比较：

$$
A(Br)\stackrel{?}{=}Cr
$$

这就是 Freivalds 检查的核心形式。对稠密 $n\times n$ 矩阵，三次矩阵向量乘法只需 $O(n^2)$ 运算，而朴素重算矩阵乘法是 $O(n^3)$。但验证者仍需要访问相应矩阵；它不是“不读取输入”的通用远程验证协议，也不是 PCP 定理的证明。[^freivalds]

下面在有限域 $\mathbb F_{101}$ 中构造一个错误的 $C$。代码**穷举**四个二进制挑战，目的是看清漏检与检出的机制，不是实现生产用随机挑战。

```python
from itertools import product

MODULUS = 101
A = [[1, 2], [3, 4]]
B = [[2, 0], [1, 2]]
# 正确的 AB 是 [[4, 4], [10, 8]]；这里故意改错一个值。
C_BAD = [[5, 4], [10, 8]]

def matvec(matrix: list[list[int]], vector: tuple[int, ...]) -> tuple[int, ...]:
    if not matrix or any(len(row) != len(vector) for row in matrix):
        raise ValueError("矩阵列数必须与向量维数一致")
    return tuple(
        sum(value * entry for value, entry in zip(row, vector)) % MODULUS
        for row in matrix
    )

for challenge in product((0, 1), repeat=2):
    accepted = matvec(A, matvec(B, challenge)) == matvec(C_BAD, challenge)
    print(challenge, "通过" if accepted else "拒绝")
```

这是一段单执行主体的纯计算枚举，没有线程等待或网络交互，因此不画时序图。输出为：

```text
(0, 0) 通过
(0, 1) 通过
(1, 0) 拒绝
(1, 1) 拒绝
```

为什么会这样？这里只有第一列引入了误差；挑战向量的第一项为 0 时，这次线性组合恰好把误差抹掉，为 1 时则能暴露它。随机检查不是逐个挑输出元素，而是用结构化关系把结果投影到一个较便宜的检查上。

对**先固定**且满足 $AB\ne C$ 的矩阵，在域上独立均匀选择二进制挑战向量，标准分析给出单轮误接受率不超过 $1/2$。不过“模 101 正确”只代表有限域关系正确：整数结果相差 101 的倍数可能在这个域里相同。要证明整数范围或浮点语义，必须增加相应编码与约束，不能省略。[^freivalds]

> [!note] 此例只建立一个直觉
> 随机代数检查能比原样重算便宜，但这里没有隐藏矩阵，没有构造简洁非交互证明，也没有省掉读取矩阵的成本。它不是 SNARK、不是完整 zkML 协议。

## 6. SNARK 与 STARK：认识属性，不背两个刻板印象

### 6.1 SNARK 的每个词都需要限定范围

**SNARK = Succinct Non-interactive Argument of Knowledge。** “简洁”通常约束证明大小与验证成本相对于被证明计算的增长；仍可能依赖安全参数、公开输入长度等。“非交互”说明在线证明可以一次发送，不意味着完全没有公共参数、预处理或设置阶段。[^groth16][^plonk]

**STARK = Scalable Transparent Argument of Knowledge。** 透明性强调不需要带秘密陷门的可信设置，而不是“不需要公共参数”或“不依赖任何安全假设”。常见 STARK 技术路线使用执行轨迹、代数约束、编码、哈希承诺以及低度测试；是否零知识，仍要看具体构造及配置。[^stark]

以下只比较三个有代表性的原始构造，不把一篇论文的性质强加给整个术语家族。

| 代表构造 | 认知锚点 | 设置与假设的关键边界 |
|---|---|---|
| Groth16 | 配对型预处理 SNARK，原构造证明包含三个群元素 | 通常采用电路相关的可信设置；验证还要处理公开输入，不能据此说总成本永远是常数 |
| 原始 PLONK | 通用、可更新 SRS 的 SNARK 路线 | “通用且可更新”不等于没有可信设置假设；不能把所有 SNARK 都说成每个电路独立重做仪式 |
| STARK 代表路线 | 透明、基于哈希与编码的可扩展论证 | 不需要秘密陷门设置；公开参数、哈希与编译假设仍然存在 |

第一行以 Groth 2016、第二行以原始 PLONK、第三行以 STARK 原论文为口径，不覆盖全部后续变体。[^groth16][^plonk][^stark]

“SNARK 就是配对”“STARK 是完全不属于 SNARK 的另一类”“所有 SNARK 都有可信设置”，都过于粗糙。名称强调的属性不同，实践中存在重叠和多种实例化；理解一个系统时应直接询问其承诺方案、设置、证明大小、验证成本、知识性与零知识保证。

### 6.2 FRI 只需知道负责哪一块

**FRI（Fast Reed–Solomon Interactive Oracle Proofs of Proximity）**检验给定函数或数据是否接近低次数多项式所对应的 Reed–Solomon 码字。它是低度邻近性测试的重要构件，不是单独拿来就能证明任意程序的完整协议。计算约束、轨迹绑定与安全编译必须在外层配合。[^fri]

一条常见的 STARK 认知路径是：执行轨迹 → 代数约束（常见为 AIR）→ 编码与组合检查 → 承诺与 FRI 等测试 → 在适用条件下非交互化。这里的箭头是机制概览，不是让你照图实现密码协议。[^stark][^fri]

### 6.3 “后量子”也不是无限承诺

基于哈希的 STARK 路线避免了典型配对型方案所依赖的离散对数问题，原论文讨论了后量子安全性。但实际保证还依赖哈希、安全参数、量子攻击模型以及整个协议的分析；不能把“使用 Hash”简化成“量子计算永远无法攻击”。[^stark]

## 7. zkML：证明“哪一个模型、对哪一个输入、执行哪一种语义”？

**zkML** 可以把机器学习推理等计算表达成可证明关系，并在具体构造中隐藏模型、输入或其他见证。它最值得系统工程师追问的不是“证明用了多酷的算法”，而是**公开语句到底绑定了什么**。模型与输入的承诺，正是 commit-and-prove 工作关注的重要问题。[^artemis]

### 7.1 一份足够具体的声明合同

下面是教学用的关系设计，不对应某个现成框架 API。假设输入和模型需要保密，可以把公开语句与私有见证组织为：

$$
\begin{aligned}
s &= (C_W,C_x,y,\text{program ID},q,\text{request context}),\\
w &= (W,x,\rho_W,\rho_x,\text{trace}).
\end{aligned}
$$

验证关系至少需要约束：

$$
\mathrm{Commit}(W;\rho_W)=C_W,\qquad
\mathrm{Commit}(x;\rho_x)=C_x,\qquad
\mathrm{Eval}_{q}(W,x)=y.
$$

$C_W$ 绑定指定模型，$C_x$ 绑定指定输入，$\rho$ 表示承诺所需的随机性；$q$ 表示数值与执行语义合同。这里使用隐藏承诺只是一个选项；如果输入本来就是公开的，可以直接把它放进语句，不必机械地隐藏一切。具体承诺方案和证明系统必须共同满足需要的安全定义。[^artemis]

尤其要防止这个逻辑漏洞：若只证明“**存在某个** $W$，使 $\mathrm{Eval}(W,x)=y$”，却没有将 $W$ 绑定到用户指定的模型，那么它不能证明“这个结果来自我要求的模型”。验证者还需要从可信渠道确认 $C_W$ 对应哪一个模型版本；攻击者自己挑的 root 不会凭空获得业务身份。

### 7.2 为什么不能一句话写成“等同于真实 GPU 浮点推理”？

许多证明系统工作在有限域上。机器学习部署则可能包含 FP16/BF16、舍入、饱和、量化、非线性函数、查表以及随机采样。把推理转为可证明约束，需要明确这些语义如何表示。zkLLM 等研究对量化、重缩放及非算术运算进行了专门处理，不能把这些步骤当成“自动等价”。[^zkllm]

一份可审查的合同至少应说清：模型参数与图结构；输入形状与布局；预处理或 tokenizer 版本；量化尺度、舍入与范围约束；非线性算子的实现或近似；输出的定义。随机采样若属于声明的一部分，还要绑定种子及采样规则。以上是本文提出的工程检查项，并不是断言所有 zkML 系统都已实现这些约束。

**证明编码后的量化关系正确，不自动证明与任意 CUDA kernel 的逐位浮点结果一致。** 这种等价性只有在双方语义被明确建模和论证后才能主张。有限域中的模运算回绕，也不能靠普通类型声明来避免。[^zkllm]

### 7.3 它能证明与不能证明的边界

| 验证通过后，可以在合同与安全假设内接受 | 单靠该证明不能推出 |
|---|---|
| 结果满足指定程序关系 | 模型输出符合现实事实或没有幻觉 |
| 见证中的模型匹配指定承诺 | 模型的训练数据合法、可信且没有偏差 |
| 输入匹配指定承诺或公开值 | 传感器读数来自真实场景而非伪造输入 |
| 关系符合约定的数值语义 | 与未纳入合同的浮点实现天然一致 |
| 具体零知识协议按定义保护私有见证 | 公开输出不会泄露信息、接口不存在侧信道 |
| 语句中绑定了请求上下文 | 服务端确实在某块 GPU、某地点或某时刻执行 |

这些限制直接来自“验证的是关系”这一抽象。可信执行环境与远程证明则更侧重平台身份、状态和测量值；二者可以组合，但不能互相冒充。对 AIDC 而言，安全传输、密钥管理、完整性、平台可信与可验证计算是不同层次的问题。

## 8. “验证很快”不等于“系统总成本很低”

证明者通常要准备见证、构造或处理轨迹、执行代数或哈希等工作，具体成本取决于系统。不同构造可能把时间花在多项式运算、多标量乘法、哈希、查表或内存搬运上；不能把某个方案的热点当作所有证明系统的热点。[^groth16][^plonk][^stark][^zkllm]

从 Infra 角度，做评估时应分别记录：原始推理时间 $T_{infer}$、见证准备时间 $T_{witness}$、证明时间 $T_{prove}$、验证时间 $T_{verify}$、证明字节数、CPU/GPU 峰值内存、模型/批量/数值语义和安全参数。这是本文建议的测量口径，不是实测结果。

需要特别追问：预处理是否摊销？公开输入读取和 Hash 是否计入？内存与数据传输是否计入？证明覆盖的是完整模型还是一个算子？两组数字是否使用同样的安全等级和语义？**验证者便宜，可以伴随证明者昂贵；这本来就是部分方案选择的权衡。**

如果完整性需求只是“Checkpoint 读回后有没有损坏”，不应直接跳到 SNARK。先把可信摘要、对象版本、校验与修复链做对；只有需求真的变成“我要验证某个外包计算关系”，才值得再评估证明系统。

## 9. 认知级自测：能回答这些问题就够了

**问：PCP 为什么可以只查很少的位置？**  
因为它查询的是为真假验证专门构造的证明，并依赖局部检查与全局可靠性之间的结构；不是原始数据随便抽样。定理的查询界也不是整个输入处理成本。

**问：Merkle proof 为什么不等于计算证明？**  
它证明被打开的值与已承诺内容相符；还需要检查这些值是否满足计算约束，并证明整套协议有可靠性。

**问：SNARK 的零知识和可信设置是固定的吗？**  
不是。零知识是额外的安全性质；设置方式依具体构造而异，应查看具体方案，而不是凭缩写判断。

**问：zkML 为什么需要模型承诺？**  
因为“存在某个模型产生结果”弱于“指定版本的模型产生结果”。承诺、公开语句和验证关系必须一起绑定目标。

**问：证明成功意味着实际在哪台 GPU 上算过吗？**  
一般不能。数学关系成立，不等同于物理执行历史、地点或时间的证明。

**问：现在应该投入什么工程时间？**  
本篇只要求理解词汇、识别语句与性能口径。除非工作任务明确涉及可验证计算，否则不安排实现 PCP、SNARK 或 zkML 的练习，不挤占 Hash / Integrity、网络与存储数据路径的学习。

> [!summary] 一句话串起知识链
> **随机化降低检查成本，结构化证明支撑局部可靠性，承诺固定被查询对象，密码学论证把这些机制变成可通信的协议；zkML 再把“指定模型上的指定计算”放进那份被验证的关系。**
