# Multipath 与故障切换

> 贯穿案例走到运维侧：GPU 节点通过 NVMe-oF 挂上了存储节点的盘（[[5.1 NVMe-oF 架构]]），但一根网线、一台交换机、一个 target 端口，任何一个抖一下，几十台 GPU 的训练就一起停——[[5.1 NVMe-oF 架构]] §6 已经警告过：远端盘不是快速 EIO，是 **hang**。Multipath 的思路很朴素：同一个 namespace 走两条独立的路，一条断了切另一条。本篇讲这件事在 NVMe 里怎么做：路径状态怎么同步（ANA）、切换窗口里在途 IO 归谁、以及为什么这套机制的每一环——无锁选路、在途请求重排、剩余路径的背压——都能在 C++ 多线程程序里找到同构物。

前置：[[5.1 NVMe-oF 架构]]（subsystem/controller/namespace 三层）、[[1.7 块层与 blk-mq]]（bio 与 request 的分界，切换发生在 bio 层）、[[3.3 Admin Queue 与 IO Queue]]（AEN 异步事件走 Admin 队列）。

---

## 1. 故障是常态：单路径的死法清单

一条 host→盘的路串着六七个部件【事实】：host 网卡 → 网线 → 交换机 → 网线 → target 网卡 → target 软件 → 盘。规模一上来，「所有部件同时健康」才是小概率事件——这与多线程程序的直觉一致：**单点资源就是单点故障**，一个线程死锁，所有等它的任务全部冻结。

死法分两类，检测难度天差地别【实践】：

| 死法 | 例子 | 检测方式 | 检测耗时 |
| --- | --- | --- | --- |
| **有信号的死** | 网卡 link down、TCP RST、RDMA QP 进 error 态（[[4.3 QP WQE CQ 状态机]]） | 事件上报，立刻知道 | ms 级 |
| **无信号的死** | 交换机静默丢包、target 进程 hang 住不回包 | 只能靠超时兜底 | **秒级**（见 §5） |

第二类是尾延迟的真正来源：对端没说自己死了，你只能等一个超时来「宣判」。这与 `std::future::wait_for` 的处境相同——没有带外信号时，超时是唯一的故障判据【事实】。

## 2. 硬件前提：一个 namespace，多个 controller

多路径不是 host 单方面能做的，target 侧要先把「同一块盘从多个门进」做出来【事实】：

- subsystem 声明支持多 controller（Identify 数据里的 **CMIC/NMIC** 位）；
- target 在两个独立端口（最好走两张网卡、两台交换机）各暴露一个 fabric port；
- host 对同一个 subsystem NQN `nvme connect` 两次（不同地址），得到**两个 controller 实例**——[[5.1 NVMe-oF 架构]] §3 的「一 host 一 controller」在多路径下变成「一 host 一路径一 controller」;
- 两个 controller 看到的 namespace 靠全局唯一 ID（NGUID/UUID）判定为同一块盘。

host 内核（`CONFIG_NVME_MULTIPATH`，现代发行版默认开【实现】）把两条路**合并成一个块设备**：

```bash
nvme connect -t rdma -a 192.168.1.10 -s 4420 -n nqn.2026-07.io.lab:jbof16   # 路径 A
nvme connect -t rdma -a 192.168.2.10 -s 4420 -n nqn.2026-07.io.lab:jbof16   # 路径 B

nvme list-subsys
# nvme-subsys0 - NQN=nqn.2026-07.io.lab:jbof16
#  +- nvme0 rdma traddr=192.168.1.10 live optimized
#  +- nvme1 rdma traddr=192.168.2.10 live non-optimized
```

应用只看到一个 `/dev/nvme0n1`；每条路径各自的「影子设备」是隐藏的 `nvme0c0n1`、`nvme0c1n1`【实现】。选路发生在 bio 层：blk-mq 之上先挑路径，挑完才进对应 controller 的每核队列（[[1.7 块层与 blk-mq]]）——这个位置选得很讲究，§5 会看到它决定了重试的干净程度。

> 历史包袱一句话【事实】：SCSI 时代用 `dm-multipath`（用户态 `multipathd` 守护进程探测 + device-mapper 拼设备）。NVMe 原生多路径把这套搬进内核、直接消费 ANA 协议，路径事件不再绕道用户态——检测到切换的链路短了一大截。本章只讲原生方案。

## 3. ANA：路径状态机与「谁通知谁」

两条路不是对等的：target 可能是双控制器存储阵列，盘物理上挂在控制器 1 后面，从控制器 2 进要走一次内部转发。NVMe 用 **ANA（Asymmetric Namespace Access）** 把这件事标准化【事实】——每条路径对每组 namespace 处于五种状态之一：

| ANA 状态 | 含义 | 选路器的态度 |
| --- | --- | --- |
| optimized | 最优路，直达 | 首选 |
| non-optimized | 能走但绕远（内部转发） | 备胎，optimized 全灭才用 |
| inaccessible | 此路不通（但 controller 活着） | 不选 |
| persistent loss | 永久失联 | 不选，也别等了 |
| change | 状态切换中 | 稍后重查 |

状态同步是教科书级的**事件驱动 + 拉取确认**【事实】：target 状态变了 → 通过 Admin 队列发 **AEN 异步事件**（[[3.3 Admin Queue 与 IO Queue]]）→ host 收到后**主动读 ANA log page** 拿全量新状态 → 更新本地路径表。AEN 只说「变了」，不说「变成什么」——通知与数据分离，避免事件本身携带会过期的状态。这就是 C++ 里 `condition_variable` 的正确用法：**唤醒不传值，醒来后重新检查谓词**；直接把状态塞进通知里，就会遇到通知乱序到达时的版本混乱。

## 4. 选路：每次 IO 都要过的无锁热路径

路径表是典型的**读端极热、写端极冷**共享数据【事实】：每笔 IO 都要查（百万次/秒量级），改动只在故障与恢复时发生（天级）。给它上 `std::shared_mutex` 都嫌贵——读端原子操作在核间弹缓存行。内核的答案是 **RCU/SRCU**：读端零锁零原子写，写端复制-修改-发布，等所有旧读者离开再回收旧表【实现】。

用 Modern C++ 写出同构物（C++20 `std::atomic<std::shared_ptr>`，语义等价、性能弱于 RCU 但形状相同）：

```cpp
struct PathSet;  // 不可变：一旦发布，内容不再修改

class PathTable {
public:
    // IO 热路径：每笔 IO 调用。acquire 保证拿到的 PathSet 已完整构造
    std::shared_ptr<const PathSet> snapshot() const {
        return paths_.load(std::memory_order_acquire);
    }
    // 冷路径：仅故障/恢复时调用。复制旧表→改→整体发布，旧表由 shared_ptr 自然回收
    void publish(std::shared_ptr<const PathSet> next) {
        paths_.store(std::move(next), std::memory_order_release);
    }
private:
    std::atomic<std::shared_ptr<const PathSet>> paths_;
};
```

release/acquire 配对在这里不是仪式【事实】：没有它，选路线程可能拿到新指针、却读到 PathSet 未初始化的字段——指针可见不等于指针指向的内容可见。内核 RCU 的 `rcu_assign_pointer`/`rcu_dereference` 做的是完全同一件事。

拿到路径表后按 **iopolicy** 挑【实现】：

| iopolicy | 规则 | C++ 同构物 | 适用 |
| --- | --- | --- | --- |
| `numa`（默认） | 选与提交 CPU 同 NUMA 节点的路径 | 线程亲和性/数据局部性 | 路径质量差异大 |
| `round-robin` | 轮转 | 无状态均摊 | 两条 optimized 想同时吃满 |
| `queue-depth` | 选在途 IO 最少的路 | least-loaded 调度 | 路径快慢会漂移时自适应 |

`queue-depth` 的在途计数是每路径一个原子计数器【实现】——又一次「宁可每路径一个计数器，不要全局一把锁」，与 [[5.6 SPDK 用户态驱动]] 的每核私有化是同一条设计公理。

## 5. 故障切换全时序:尾延迟从哪来

核心一节。一条路死掉之后发生什么，直接决定应用看到的 p99：

![Multipath 故障切换全景：上半部分为拓扑——host 的 native multipath 在 bio 层选路，经两条独立 fabric（网卡/交换机各自独立）连接 target 的两个 controller，汇聚到同一个 namespace，路径 A 标注 ANA optimized、路径 B 标注 non-optimized；下半部分为故障切换时间线——正常期 IO 走 A，t0 链路断，检测窗口分 link 事件 ms 级与 KATO 兜底秒级两种，随后摘除路径、在途 IO 以 bio 形态 requeue 到 B，后台每隔 reconnect_delay 重连 A，ctrl_loss_tmo 到期才放弃；时间线下方标注受害 IO 的尾延迟构成](../../图片/SVG/nvmeof-multipath故障切换.svg)

四个阶段【事实/实现】：

| 阶段 | 发生什么 | 耗时 |
| --- | --- | --- |
| ① 检测 | link down/QP error → 立刻；静默死 → 等 keep-alive 超时（KATO，Linux 默认 5 s） | **ms 到秒级——整个切换的大头** |
| ② 摘除 | controller 标记为失联，从路径表 publish 掉（§4 的写端） | μs 级 |
| ③ 重排 | 该路径上所有在途 bio 收回，重新走一遍选路 → 提交到路径 B | μs 级（好在 bio 层干净，见下） |
| ④ 后台重连 | 每 `reconnect_delay`（默认 10 s）试一次重建路径 A，`ctrl_loss_tmo`（默认 600 s）内不放弃；连上后路径回表 | 不挡 IO |

于是受害 IO 的延迟 = 检测窗口 + μs 级重排 + 在 B 上正常执行【事实】。**检测窗口贡献了 99% 的疼痛**——这就是为什么调优多路径基本等于调 KATO 与探测灵敏度，而不是调切换本身（更快的检测 = 更频繁的心跳 = 更容易误判抖动为死亡,这个两难在 [[10.6 健康检查与故障摘除]] 展开）。

**在途 IO 为什么能安全重发**【事实】：两点缺一不可。

1. **重发单位是 bio**：multipath 挂在 blk-mq 之上，收回的是「读 LBA X 长度 L」这个意图，不是已经填好的 SQE——换条路重新生成命令即可，没有半截状态要清理。对比一下：如果切换做在驱动层，就得处理「SQE 已写入、doorbell 已敲、CQE 生死未卜」的烂摊子。**在最抽象的层次做重试**，与 C++ 里「重投任务对象，而不是恢复执行到一半的栈帧」同一个道理。
2. **块读写是幂等的**：读重发无副作用；写重发把同一数据再写同一 LBA，结果不变。危险的是「原路径的写其实已落盘、新路径又写一次」中间被第三方写插入的情形——块层假设单 writer，这正是 [[5.1 NVMe-oF 架构]] §6「裸 namespace 不能多 host 共写」军规的另一面【事实】。

C++ 对照：这相当于线程池里一个 worker 猝死,它队列里的**任务对象**（值语义、无外部副作用）被收回重投给别的 worker——任务可重投的前提是幂等或恰好一次执行由上层保证。存储把这个前提做进了块语义里。

## 6. 背压：切换之后，剩下的路要扛双倍

切换成功不等于回到从前【实践】。两条 optimized 路各扛 50% 流量时，一条死掉，另一条瞬间 100%：

- 在途窗口翻倍 → 排队论说延迟随利用率非线性上升，利用率越接近饱和越陡【事实】;
- 若单路容量本来就只按 50% 规划,剩余那条直接进饱和区，p99 爆炸——故障切换「成功」，SLO 却挂了;
- blk-mq 的背压照常起作用（[[1.7 块层与 blk-mq]]）：路径 B 的队列满 → tag 拿不到 → 提交者睡眠——压力最终传导回应用的 io_uring 恒满窗（[[2.3 iodepth 与提交完成路径]]）。

这就是线程池的 **N-1 容量规划**：8 线程的池按 8 线程满载规划容量，死一个线程就雪崩;按 7 线程规划,死一个才只是变慢。多路径的军规相同【实践】：**容量按 N-1 条路径规划，多出来的是冗余，不是免费带宽**。诱惑在于平时两条路都能跑——把冗余当容量用掉的系统，第一次故障切换就是第一次过载测试。

## 7. 陷阱与误区

> [!warning] 常见错误
> 1. **两条路径共享物理部件**：两个 fabric port 插同一张双口网卡、上同一台交换机——拓扑上两条路，故障域里一条。冗余要沿着故障域画，不是沿着 IP 画。
> 2. **把冗余带宽当容量**：平时双路跑满很爽，切换即过载（§6）。
> 3. **只测拔线，不测静默死**：link down 是 ms 级检测的「善良故障」；真正伤 p99 的是 hang 而不断的路径——故障注入要覆盖丢包与假死（[[9.6 故障注入矩阵]]）。
> 4. **应用超时 < 检测窗口**：应用 1 s 超时、KATO 5 s——每次路径抖动应用先崩。超时预算必须从盘往上逐层加余量。
> 5. **忘了 ANA 是 target 说了算**：host 只消费状态。target 侧升级/倒换时 ANA 状态翻转，host「无故」切路——排查时先看 ANA log 再怀疑网络。
> 6. **误判涡轮**:检测调得越激进，网络抖动越容易被当成死亡，切换风暴自己制造尾延迟——检测灵敏度与误判率是同一个旋钮的两端（[[10.6 健康检查与故障摘除]]）。

## 8. 关键结论

| 结论 | 性质 |
| --- | --- |
| 多路径 = 同一 namespace（NGUID 判同）经多个 controller 可达；host 内核合并为单一块设备，选路在 bio 层 | 事实 |
| 故障分「有信号」（ms 级检测）与「静默」（等 KATO 兜底，秒级）——检测窗口是切换延迟的绝对大头 | 事实 |
| ANA 五态由 target 维护，AEN 通知「变了」+ host 拉 log 确认「变成什么」——通知与状态分离，同 condition_variable 的谓词重查 | 事实 |
| 路径表读极热写极冷 → 内核用 RCU；C++ 同构物是 atomic<shared_ptr> 的 acquire 读 + 复制发布——指针可见 ≠ 内容可见，屏障不能省 | 事实 |
| 在途 IO 以 bio 为单位收回重投,可行前提 = 在最抽象层重试 + 块读写幂等 | 事实 |
| 切换后剩余路径负载翻倍，延迟按排队论非线性上涨——容量按 N-1 规划，冗余不是免费带宽 | 实践结论 |
| 检测灵敏度与误判率是同一旋钮的两端：没有免费的快切换 | 取舍 |
| 应用超时预算必须覆盖检测窗口，否则多路径救了盘、救不了应用 | 实践结论 |
