# 内核态 vs 用户态路径

> 同一条 NVMe 命令、同一块盘,软件可以走两条路:内核路径([[1.8 一次 read write 全路径图]] 的那条)与 SPDK 用户态路径([[5.6 SPDK 用户态驱动]])。本篇把两条路摆在一起逐步对账——每一步花多少、删掉的是什么、删不掉的是什么。核心视角依然是 C++ 线程模型:**这场对比本质上是四个并发问题的四次选边**——通知用睡眠还是自旋、边界要不要陷入、队列共享还是分片、背压隐式还是显式。看懂这四次选边,也就看懂了「为什么有的系统愿意烧一整个核换 10 μs」。

前置:[[5.6 SPDK 用户态驱动]](用户态路径的机制)、[[1.7 块层与 blk-mq]] + [[1.8 一次 read write 全路径图]](内核路径的机制)、[[2.4 polling 与 registered buffers]](夹在中间的 io_uring)。

## 1. 两条路径,逐步对账

以本地盘 O_DIRECT 随机读 4 KiB 为例(NVMe-oF 下两条路的差异同构,只是网络段替换了 PCIe 段):

![内核态与用户态 IO 路径对比:左列内核路径八步——io_uring 提交经 syscall 陷入、VFS 与 blk-mq 每核队列、nvme 驱动填 SQE 敲 doorbell、盘执行 DMA、MSI-X 中断与 softirq、唤醒调度、返回用户态,每步标注量级开销;右列 SPDK 路径五步——应用函数调用、bdev 到 qpair 填 SQE、写 doorbell、盘执行 DMA、reactor 轮询 CQ phase bit 命中后原地回调,全程零陷入零中断零唤醒;两列中「盘执行」用同色标出为共同不变项,右列旁以虚线框列出被删除的四项:syscall、中断、唤醒调度、共享队列;底部为取舍条:烧核换延迟、独占换共享、显式背压换隐式背压](../../图片/SVG/spdk-内核态用户态路径对比.svg)

| 阶段 | 内核路径 | 开销【量级】 | SPDK 路径 | 开销【量级】 |
| --- | --- | --- | --- | --- |
| 提交入口 | `io_uring_enter` 陷入内核 | 百 ns 级/次 | 普通函数调用 | ns 级 |
| 请求成形 | VFS 检查 → bio → blk-mq 每核队列 → 取 tag → request | ~μs 级 | bdev → 本核独占 qpair,直接填 SQE | 百 ns 级 |
| 命令下发 | 驱动填 SQE、敲 doorbell | 百 ns 级 | 同样的 SQE + doorbell(同一份硬件协议) | 百 ns 级 |
| **盘执行** | DMA 搬数据、写 CQE | **几十 μs——两边完全相同** | 同左 | 同左 |
| 完成通知 | MSI-X 中断 → ISR → softirq 里收 CQE | μs 级 | reactor 下一圈轮询看见 phase bit | 百 ns 内 |
| 交还应用 | 唤醒等待任务 → 调度器排队 → 上核 → 陷出 | μs 级 + **抖动(见 §4)** | 原地调用完成回调 | ns 级 |

三个读账要点【事实】:

1. **盘不变,软件在盘两侧的「包装」变了**:硬件协议(SQE/doorbell/CQE/phase bit,[[3.2 Queue Pair 与 Doorbell]])两边一个字节都不差,差的全是软件送命令和取结果的方式;
2. 单笔 4 KiB 读,内核软件开销约占总延迟的一成——**平均延迟上 SPDK 赢得不多**;它真正赢的是 §3 的 IOPS/核与 §4 的尾延迟;
3. 表中每一行,都对应下面 §2 的一次「选边」。

## 2. 四次选边:并发设计的老问题,系统级的新答案

### 选边一:通知——睡眠等待还是忙等轮询

两条路径的分歧根源,就是 C++ 里这两段代码的分歧【事实】:

```cpp
// 内核路径的骨架:等待者睡在条件变量上,完成方(中断)负责唤醒
std::mutex m;
std::condition_variable cv;
bool done = false;

void wait_completion() {
    std::unique_lock lk(m);
    cv.wait(lk, [&] { return done; });  // 让出 CPU;醒来要过调度器,μs 级 + 抖动
}

// SPDK 路径的骨架:等待者自旋在共享内存的标志上,完成方只管写内存
std::atomic<bool> done_flag{false};

void poll_completion() {
    while (!done_flag.load(std::memory_order_acquire)) { /* 烧核 */ }
    // 反应 ns 级;acquire 与完成方的 release 写配对
}
```

中断就是系统级的 `notify_one`:它打断当前执行、走一段固定开销的处理路径(ISR/softirq)、把等待者塞回运行队列。轮询就是系统级的自旋 acquire 读:完成方(盘的 DMA 写 CQE + 翻 phase bit)相当于 release store,等待方下一圈就看见【事实】。选边规则与 C++ 中完全一致【实践】:**事件稀疏选睡眠(省 CPU),事件密集选自旋(省唤醒)**——存储 target 每核每秒几十万事件,密集侧的极端,所以 SPDK 选轮询;笔记本上偶尔读文件,稀疏侧的极端,所以通用内核选中断。

### 选边二:边界——每笔 IO 要不要陷入内核

syscall 单次只有百 ns 级【量级】,贵在乘法与间接伤害:每秒百万笔 IO × 提交/完成两次陷入,再算上模式切换对流水线与缓存的扰动,几个核就没了。C++ 对照:这就是**批处理均摊锁开销**的思路推到极限——io_uring 靠共享内存环把「多笔 IO 一次陷入」做到内核接口上([[2.1 SQ CQ 模型]]),SPDK 更进一步,把陷入次数直接归零:硬件接口(BAR、队列内存)已经 mmap 在进程里,「进内核」这个动作失去了存在的理由【事实】。

### 选边三:队列——共享仲裁还是按核分片

内核块层要服务所有进程、所有设备,队列天然共享,共享就要仲裁:tag 分配、限流、调度器,即便 blk-mq 已按核分了软件队列([[1.7 块层与 blk-mq]]),路径上仍有跨核可写的共享状态在弹缓存行。SPDK 的回答见 [[5.6 SPDK 用户态驱动]] §3:资源彻底按核私有,跨核只传消息——代价是**放弃通用性**,设备被一个进程独占,不再有「所有人都能 open 这块盘」【取舍】。这就是 C++ 里「全局锁保护的共享池」与「thread-local 池 + 消息」的取舍,答案取决于你是图书馆还是专机。

### 选边四:背压——队列满时睡给你看还是返回给你看

内核:tag 耗尽,提交线程被移出运行队列,应用只观察到「变慢」——背压隐式、免费、不可编程。SPDK:`-ENOMEM` 返回值,应用必须自己接、自己决策——背压显式、麻烦、可编程([[5.6 SPDK 用户态驱动]] §5)。有界队列 `push` 与 `try_push` 之争的系统级版本【事实】。对延迟敏感系统,显式是刚需:「满了之后谁慢下来、丢谁的请求」是业务决策,隐式背压把它锁死成「先来的都等着」【取舍】。

## 3. 内存可见性:两条路径都免不了的那部分

容易误会成「用户态路径连内存屏障都省了」。恰恰相反【事实】:

- **省掉的**是特权级切换(syscall/中断)与调度(唤醒/迁移)——这些是**软件强加的**开销;
- **省不掉的**是缓存一致性与内存序——盘的 DMA 写要对轮询核可见、SQE 要先于 doorbell 到达设备、跨核消息要 release/acquire 配对([[5.6 SPDK 用户态驱动]] §4)。这些由硬件的一致性协议收费,**与代码跑在哪个特权级无关**。

一句话立住这个认知:**内核态/用户态是权限边界,不是内存模型边界**【事实】。C++ 程序员的直觉在这里完全平移:把临界区从一个函数挪到另一个函数,锁和屏障该要还得要;SPDK 把驱动逻辑从内核挪进进程,acquire/release 一个都没少写,少写的只是「进出内核」这个昂贵的仪式。

## 4. 量级账:平均延迟、IOPS/核、尾延迟

三笔账分开算,结论各不相同【量级】:

| 维度 | 内核路径 | SPDK 路径 | 差距来源 |
| --- | --- | --- | --- |
| 单笔平均延迟(几十 μs 的 NAND 盘) | 盘 + 约 5~10 μs 软件 | 盘 + 1 μs 内软件 | 对 NAND 盘只差一成;盘越快(新介质 μs 级)差距占比越大 |
| IOPS/核 | 每笔摊 syscall+中断+调度,单核封顶早 | 单核轮询可达数百万 IOPS【实现,SPDK 官方基准量级】 | 乘法效应:百万 × 每笔省的 μs = 省出整数个核 |
| 尾延迟 p99/p999 | 受调度抖动支配 | 逼近盘本身的分布 | 见下 |

尾延迟一行最值得展开【事实】:内核路径的完成要经过「唤醒 + 调度」,而这一步的耗时不取决于你,取决于**当时核上在跑谁**——被抢占的任务、softirq 风暴、CPU 从省电的 idle 深睡态(C-state)里爬出来的毫秒级惊跳、NUMA 错位的唤醒……每一项都会给个别 IO 加上几十 μs 到 ms 级的罕见毛刺,它们几乎不动平均值,却直接写进 p999([[9.5 p99 毛刺定位]])。SPDK 的绑核轮询把「完成路径上有没有调度器」这个随机变量整个删掉了——**轮询买到的与其说是快,不如说是确定性**【事实/实践】。这对上层 SLO 的意义见 [[9.7 SLO 与性能回归]]。

## 5. 中间态:io_uring 站在两者之间

两条路不是二选一,内核自己也在向轮询侧移动([[2.4 polling 与 registered buffers]])【事实】:

| 机制 | 借了用户态路径的哪一招 | 还留着内核的什么 |
| --- | --- | --- |
| io_uring 共享环 | 队列放共享内存,批量提交摊薄陷入 | 请求仍走块层 |
| SQPOLL | 内核线程轮询提交环,提交侧零 syscall | 多烧一个内核线程 |
| IOPOLL(`hipri`) | 完成侧轮询 CQ,不走中断 | 仍在内核里轮询,仍有共享块层 |

于是选型是一条谱系而不是一道墙【实践】:通用应用 → io_uring 默认;延迟敏感但要文件系统 → io_uring + 轮询选项;存储即主业、独占设备、按核规划 CPU → SPDK。判据始终是 §2 的四次选边里,你有没有资格选贵的那边:**独占得起设备吗?烧得起核吗?接得住显式背压吗?**

## 6. 陷阱与误区

> [!warning] 常见错误
> 1. **拿平均延迟为 SPDK 立项**:NAND 盘上平均只差一成,说服力最弱;立项论据应当是 IOPS/核(省机器)或 p999(SLO),见 §4。
> 2. **以为用户态省掉了内存屏障**:省的是特权级与调度,不是缓存一致性——屏障一个不少(§3)。
> 3. **用 50% 利用率的场景选了轮询**:事件稀疏时轮询是纯浪费,还挤占同机其他负载;选边一要按事件密度选(§2)。
> 4. **测内核路径时不关调度噪声就下结论**:没隔核、没关深度 C-state 测出来的 p999 是调度器的成绩单,不是 IO 栈的([[9.5 p99 毛刺定位]])。
> 5. **忘了 SPDK 的账里要计整核成本**:「延迟降了 8 μs」的另一面是「这个核再也干不了别的」——对比要按「每核交付的 IOPS × 延迟分布」算总账。
> 6. **把 io_uring IOPOLL 当 SPDK 平替**:IOPOLL 删了中断,但 syscall 边界、块层共享结构还在;它是谱系的中点,不是终点(§5)。

## 7. 关键结论

| 结论 | 性质 |
| --- | --- |
| 硬件协议两边完全相同,差异全在软件包装——对比的是「送命令/取结果」的方式,不是盘 | 事实 |
| 四次选边概括全部差异:通知(睡眠 vs 自旋)、边界(陷入 vs 零陷入)、队列(共享仲裁 vs 按核分片)、背压(隐式 vs 显式) | 事实 |
| 中断 = 系统级 notify_one,轮询 = 系统级自旋 acquire 读;按事件密度选边,与 C++ 中同一判据 | 事实 |
| 内核态/用户态是权限边界不是内存模型边界:省得掉 syscall 与调度,省不掉 acquire/release 与缓存一致性 | 事实 |
| NAND 盘上平均延迟只差约一成;SPDK 的真实收益是 IOPS/核(乘法效应)与 p999(删掉调度这个随机变量) | 量级 |
| 轮询买到的核心商品是确定性:完成路径上不再有调度器 | 事实/实践 |
| io_uring(SQPOLL/IOPOLL)是谱系中点:借共享环与轮询,留块层与 syscall 边界 | 事实 |
| 选型判据 = 有没有资格选贵的一边:独占得起设备、烧得起核、接得住显式背压 | 取舍 |
