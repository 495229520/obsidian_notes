# NVMe-oF 端到端数据路径：Host、RDMA Fabric、Target Reactor、bdev 与 NVMe

[[5.19 RDMA Transport 数据路径]] 把命令、数据、完成映射到了 RDMA 操作。本篇继续向两端展开：应用提交之后，哪个线程推进请求？数据在哪块内存停留？网卡完成、SSD 完成、应用完成是不是同一件事？只有把这些边界分开，才能判断瓶颈属于网络、Target 软件，还是后端存储。

> [!abstract] 本篇的主路径
> **Host → NVMe/RDMA → RoCE Fabric → SPDK NVMe-oF Target → 本地 PCIe NVMe bdev → SSD**。Host 分别讨论 Linux 内核 initiator 和 SPDK initiator；Target 基线采用轮询模式、普通 NVMe bdev、无额外 RAID/加密/文件系统层。变体单独标注，不混画成一条路径。
>
> 实现锚点为 **SPDK `v25.09` 的 `lib/nvmf/rdma.c`**，不是“最新版本”声明；官方在线文档核对日期为 **2026-09-11**。当前文档、旧示例和本机二进制可能不一致，RPC、trace 名称与参数以所用版本的源码和 `--help` 为准。本文没有在真实 RDMA/NVMe 硬件上执行性能实验；算例均为推导，不是实测结果。[^rdma-src][^target]

## 1. 先固定软件栈：Host 和 Target 可以走不同路径

| 位置 | Linux 内核路径 | 本篇的 SPDK 路径 |
|---|---|---|
| Host 提交 | 应用 → io_uring 等接口 → 块层 → `nvme-rdma` | 应用 → SPDK NVMe 库 → RDMA transport |
| Host 完成 | 内核驱动处理完成，再交还应用 | 应用所在的执行上下文持续推进完成轮询 |
| Target 前端 | 内核 `nvmet-rdma` | SPDK NVMe-oF RDMA transport |
| Target 本地 PCIe 后端 | 内核块层、NVMe 驱动 | bdev NVMe 模块 → SPDK NVMe 驱动 → PCIe NVMe 队列 |
| 可见的块设备 | 通常有内核 `/dev/nvme…` 节点 | 被用户态驱动接管的本地 PCIe 设备不经过普通内核块 I/O 路径 |

表中的两列是**对照**，不是每个请求都必须依次通过的层。尤其不能把主路径写成 `SPDK nvmf → 普通 NVMe bdev → blk-mq → SSD`：直接访问本地 PCIe 控制器时，SPDK 自己管理 NVMe 队列与完成处理；换成内核文件/块设备支持的 bdev，才需要重新画出内核那一段。[[5.7 内核态 vs 用户态路径]] 给出两类路径的成本差异，[[5.13 SPDK NVMe Driver]] 解释用户态驱动怎样推进命令。[^nvme][^blk-mq][^bdev]

**控制面也不要塞进每个 I/O。** Discovery、Connect、Subsystem/Namespace 配置、内存池准备和队列建立属于建链与管理工作。正常稳态读写复用已有连接和资源；异常重连时才重新进入相应控制流程。Namespace 到 bdev 的映射需要保留，但并非每笔 I/O 都去运行一次 discovery。[^target]

## 2. 对象地图：四种“队列”不能互相代称

![[图片/SVG/8_5_5_24_1.svg|900]]

图上半回答“谁推进命令”，下半回答“谁访问数据”。CPU 负责状态机和提交，不代表每个 payload 字节都要由 CPU 拷贝；反过来，payload 由 DMA 搬运，也不代表 CPU、内存控制器和 PCIe 不会成为瓶颈。

| 对象 | 它组织什么 | 不能据此推出什么 |
|---|---|---|
| Host 的 NVMe-oF I/O qpair | 一条连接上的命令与完成语义 | 不等于 Target 后端 SSD 的某一条硬件 qpair |
| RDMA QP 的 SQ / RQ | 发送工作请求 / 双边接收缓冲 | RDMA SQ 不是 SSD 的 NVMe SQ |
| RDMA CQ | 已完成的 verbs 工作请求 | 可以共享；不能假定每条 QP 独占一个 CQ |
| NVMe-oF poll group | 一组连接的 I/O 推进上下文 | 多个连接不意味着多个操作系统线程 |
| `spdk_thread` | 轻量级线程、消息、poller、线程局部上下文 | 不恒等于一个操作系统线程或一个固定 CPU |
| Reactor | 在逻辑核上执行、轮询 SPDK 线程的运行环境 | 把进程 CPU 掩码变大，不保证热点连接自动均摊 |
| bdev I/O channel | 当前线程访问 bdev 的上下文 | 不是统一规定的一对一硬件队列映射 |
| 后端 NVMe SQ / CQ | SSD 命令提交环 / 完成环 | CQE 表示该 NVMe 命令完成，不代表 Host 已收到结果 |

SPDK 的原则是让请求数据归属明确的线程，尽量在同一上下文内推进普通 I/O，跨线程协作用消息或模块规定的机制。`spdk_thread` 可以由不同执行线程承载，但不能被多个线程同时随意轮询；动态调度与迁移也意味着“thread-per-core”是组织方法，不是永久不变的编号等式。RDMA transport 的 CQ 共享范围还要看设备与 poller 的划分，不能把多 RNIC 场景简化成全进程唯一 CQ。[^concurrency][^target-pg][^rdma-src]

理解所有权先读 [[5.11 Reactor Thread 与 Poller]] 与 [[5.12 无锁 thread-per-core 模型]]；本篇要增加的判断是：**资源由谁拥有，与硬件挂在哪个 NUMA 节点，是两个独立问题。**

## 3. 一次 NVMe 写：Target 用 RDMA READ 拉取数据

以下是 **out-of-capsule 写**：数据不随命令 SEND 一起携带，Host 提供可供 Target 访问的数据区域。`keyed SGL` 表达地址、长度、访问 key；具体注册方式可能使用内核快速注册机制，也可能复用用户态注册池，不能统一写成“每个 I/O 都调用一次 `ibv_reg_mr`”。[^rdma-src][^host-rdma]

| 步骤 | 执行主体与事件 | 数据位置 / 可以推进的条件 |
|---|---|---|
| W1 | Host 准备 NVMe Write 命令与访问描述；发送 command capsule | payload 仍在 Host 的有效缓冲区；映射和访问权限必须有效 |
| W2 | Target RNIC 接收 SEND；CPU 轮询到接收完成并解析请求 | 命令缓冲已收到；请求对象和数据缓冲仍可能需要等待 |
| W3 | Target 提交 **RDMA READ** | Target 是 READ 发起者；数据方向却是 Host → Target |
| W4 | RNIC 把读取结果放入 Target 数据缓冲；Target 观察对应完成 | 数据已经可供后端使用，才推进普通后端写 |
| W5 | Target 提交 bdev 写；NVMe 模块建立后端命令 | SSD 通过 DMA 读取 Target 缓冲，再按设备语义处理写入 |
| W6 | Target 观察后端 NVMe 完成，经 bdev 回调回到请求状态机 | 此时完成的是后端操作，不是 Host 应用已经返回 |
| W7 | Target 发送 response capsule；Host 处理响应并完成 I/O | Host 获得 NVMe 状态，按接口约定结束本次缓冲区占用 |

**NVMe Write 和 RDMA WRITE 不是同一个方向命名体系。** 前者以块设备操作命名；后者以 RDMA 发起者对远端内存做什么命名。这里 Target 为写盘而读取 Host 内存，所以使用 RDMA READ。[^rdma-src]

### 小写为什么可能没有 W3–W4？

当连接参数、命令布局和实现支持 **in-capsule data** 时，部分写数据可随 command capsule 的 SEND 到达 Target，省去单独的远程拉取。不能仅凭“4 KiB 小”就判断走这条路径；需要检查 transport 的 in-capsule 配置、协商结果和 trace。省掉一次数据操作，也可能提高接收缓冲的预留成本。[^target][^rdma-src]

## 4. 一次 NVMe 读：先读 SSD，再 RDMA WRITE 回 Host

![[图片/SVG/8_5_5_24_2.svg|900]]

这张图以三个执行位置对照读写依赖，箭头顺序是语义依赖，不是按微秒比例绘制。WRITE/READ 的名字保留 RDMA 发起者视角。

读路径可按四个阶段记忆：**Host 发读命令 → Target 从后端读到本地缓冲 → Target 用 RDMA WRITE 放到 Host 缓冲 → Target 返回 NVMe response**。后端读完成之前，普通路径不能把尚未就绪的数据作为有效结果发给 Host。[^rdma-src]

这里有两个完成边界必须单独理解：

- **数据到达不等于应用得到完成。** 普通 RDMA WRITE 并不自动替应用完成一个 NVMe 请求；Host transport 仍要处理 NVMe response、状态与缓冲区生命周期。
- **数据与响应需要正确排序。** 正常实现必须保证 Host 按 NVMe 完成语义消费数据时，所需数据已经可见。这个结论依赖 transport 的 WR 提交顺序、QP 语义与平台 DMA/内存可见性处理，不能扩大为“任意 QP、任意 RDMA READ/WRITE 和 SEND 都无条件按完成顺序可见”。[^rdma-src][^host-rdma]

### 把路径读回源码，而不是背一张图

在固定的 SPDK `v25.09` 源码中，可以沿以下结构查找实现；函数和状态名用于定位，不能把不同 release 的示例日志逐字混用。[^rdma-src]

| 文件 / 接口 | 本篇对应的问题 |
|---|---|
| `lib/nvmf/rdma.c` | 命令接收、请求状态迁移、数据 RDMA 操作、发送完成与资源回收 |
| `RDMA_REQUEST_STATE_NEED_BUFFER` | 为什么命令已收到，却还不能进入后端 |
| `RDMA_REQUEST_STATE_EXECUTING / EXECUTED` | 后端执行前后，状态机停在哪 |
| `RDMA_REQUEST_STATE_DATA_TRANSFER_TO_HOST_PENDING` | 读数据回传为什么还在等 transport 资源 |
| `RDMA_REQUEST_STATE_COMPLETING / COMPLETED` | 响应在途与请求对象可回收之间的区别 |
| `lib/nvmf/ctrlr_bdev.c` | Namespace 读写命令如何交给 bdev |
| `module/bdev/nvme/bdev_nvme.c` | 普通 NVMe bdev 如何访问 NVMe 驱动 |
| `spdk_nvme_ns_cmd_read* / write*` | 异步提交；返回值与完成回调不是一回事 |
| `spdk_nvme_qpair_process_completions` | 推进后端完成；“设备做完”和“CPU 看到”之间可能有间隔 |

阅读驱动 API 时，先辨别同步返回是“提交是否被接受”还是“操作已经完成”。SPDK NVMe 驱动是由调用者推进的库，不会凭空另起一个后台线程替应用收割所有完成。[^nvme]

## 5. 数据缓冲区：零拷贝不等于不经过内存

本篇普通读写路径的逻辑搬运如下：

```text
NVMe 写：Host buffer ──RDMA──> Target buffer ──SSD DMA 读取──> SSD
NVMe 读：SSD ──SSD DMA 写入──> Target buffer ──RDMA──> Host buffer
```

这不是“网卡把数据直接写进 NAND”。同一个 Target 缓冲区能够先给一个 DMA 参与者使用，再给另一个使用，才有机会避免中间 payload 的 CPU memcpy。注册、DMA 地址映射、IOMMU、对齐、散布聚集布局和模块约束仍然存在。[[5.9 SPDK 环境与 HugePage]] 与 [[5.10 VFIO UIO 与设备绑定]] 负责解释内存和设备访问条件。[^target-pg][^nvme]

| 资源 | 至少需要覆盖的有效期 | 提前复用的风险 |
|---|---|---|
| Host 写源缓冲 | Target 可能读取数据的整个期间 | Target 读到被下一笔写覆盖的内容 |
| Host 读目标缓冲 | 接收数据与请求完成所需期间 | 新请求与旧的远程写入冲突 |
| Host MR / key / 映射 | 远程访问仍可能发生的期间 | 访问错误，或错误地暴露了已复用的数据区域 |
| Target 数据缓冲 | 后端 DMA 与 transport 数据 WR 对它的访问全部结束 | 两个 DMA 参与者踩同一块已复用内存 |
| Target response / request 对象 | transport 发送生命周期与实现回收条件满足 | 新命令覆盖仍在发送的响应或状态 |

**错误路径比成功路径更严格。** 超时只是观察者停止等待，不自动证明所有 DMA 都已停止。断连、QP 错误、失效和清理过程需要把仍在途的访问收束，再释放资源。仅凭一个本地 SEND CQE，也不能认定远端 SSD 已持久化。[^rdma-src][^host-rdma]

零拷贝还要注明范围：buffered I/O 的应用/页缓存边界、加密压缩、校验转换、对齐修复、某些 bdev 和 bounce buffer，都可能引入额外 CPU 工作或数据拷贝。不要把基本路径的性质传播到所有插件组合；SPDK 的 `bdev zcopy` API 与“这条路径未做中间 payload memcpy”也不是同一个术语层次。[^bdev][^bdev-module]

## 6. Reactor 为什么会在“异步系统”里拖慢每一层？

一次请求等 RDMA 或 SSD 时，Reactor 可以推进其他请求，而不是为这一笔 I/O 睡眠等待。这提高了重叠度，却没有消除等待。网卡 CQE 和 NVMe CQE 已经在内存里，所属 poller 长时间没获得执行机会，请求依然不会向上完成。[^concurrency][^nvme]

因此，读到一次很长的“后端完成延迟”，需要区分至少三段：**提交前等待、设备与链路执行、完成产生后到软件观察之间的等待**。只量提交到回调，通常不能把最后一段剔除，也就不能直接命名为“NAND 服务时间”。

可能造成推进不均衡的因素包括单条热连接、单个 poll group 集中过多工作、过长的回调、与系统任务竞争 CPU、完成批处理和调度迁移。判断时需要线程/poller 统计与采样，而不是看到 CPU 100% 就断言饱和：一个空闲轮询线程也能长期占满逻辑核。[^concurrency][^rpc]

[[5.23 Target CPU NUMA NIC SSD 亲和性]] 的拓扑检查在这里仍适用，但要分别确认 **Reactor 的 CPU、缓冲区实际物理位置、RNIC、SSD**。CPU 与内存一起搬到另一个节点时，CPU 未必远程访存；可能远程的是两次设备 DMA。若 NIC 与 SSD 分属不同节点，也不存在只改一个 CPU 掩码就让所有路径都本地化的通用答案。

## 7. 端到端的背压：不是一个 QD 管到底

| 等待位置 | 资源不足时会发生什么 | 应收集的证据 |
|---|---|---|
| Host 提交侧 | 应用在途数、块层 tag 或 initiator 请求资源受限 | 实际达到的 QD、提交时延、Host 线程调度 |
| Target 接收侧 | 接收对象、请求对象或数据缓冲不足 | 请求状态停留、池水位、接收补充情况 |
| RDMA 数据传输 | 发送深度、在途 RDMA READ 能力或其他 transport 资源受限 | QP 能力与实际配置、pending 状态、RDMA 统计 |
| bdev / NVMe 后端 | channel、请求资源、后端队列或介质服务受限 | bdev 分布、后端完成分布、设备状态 |
| 返回 Host | 数据回传或 response 发送资源、CQ 推进受限 | 回传 pending、完成处理间隔、Host 收割延迟 |

SPDK 特意把“接收命令的对象”和“完整请求对象”拆开，是因为接收与发送完成的观察顺序、资源复用时机并不总能简单配对。读源码时要找 pending 队列与恢复推进的位置，而不仅仅看主流程分支。[^rdma-src]

NVMe 大块写使用 Target 发起的 RDMA READ，因而要检查 READ 并发能力，但不能给所有 RNIC 写一个固定上限。类似地，RNR 指向双边接收资源问题；网络丢包重试、远程访问错误和 RNR 是不同证据，不能统称“RDMA 慢”。把 QD 从 32 改到 256，可能只是把等待从 Host 搬到了 Target，甚至延长缓冲占用并放大尾延迟。[^host-rdma][^rdma-src]

## 8. 算清容量预算，再解释性能曲线

以下是**理想化算例**，只约束量纲与资源预算，不替代硬件测试：

| 假设 | 推导 | 能说明什么 |
|---|---|---|
| 4 KiB，100 万 IOPS | `4096 × 10^6 = 4.096 GB/s = 32.768 Gbit/s` | 单方向 payload 需求；还没有命令、响应与链路开销 |
| 100 Gbit/s 线速 | `100×10^9 / 8 / 4096 ≈ 305 万 IOPS` | 把全部线速用于 payload 的乐观上界，不是可交付 IOPS |
| 一核 3 GHz，100 万 IOPS | `3×10^9 / 10^6 = 3000 cycles/I/O` | 该核每 I/O 的理想周期预算；不是测出的指令数 |
| 稳态 100 万 IOPS，平均延迟 100 μs | `L = λE[W] = 100` | 平均在途数；不能把 P99 代入 Little 定律 |
| Target 每秒转发 B 字节 payload | 普通路径有约 `2B` 的逻辑 DMA 数据搬运量 | RNIC 与 SSD 两次搬运；不是精确 DRAM PMU 字节数 |

最后一行必须保留“逻辑”二字：缓存、DDIO、内存控制器实现、额外拷贝与读写方向都会影响实际计数。PCIe 也要按链路、方向与共享上行分别核算，不能把网络全双工吞吐和某条 PCIe 单向能力直接混加。

优化应沿曲线定位：小 I/O 更容易暴露每请求 CPU 成本；大 I/O 更容易暴露带宽和数据并发窗口；高 QD 下的非线性增长提示排队，但仍需找出具体队列。此处的“容易”是待验证假设，不是硬件归因结论。

## 9. 实验闭环：把总路径逐段替换，不做分位数减法

先复用 [[9.1 fio Benchmark Matrix]] 的负载合同，再做下面的对照。每次保留块大小、读写比、地址范围、热身/稳态条件，并同时报告实际 IOPS 与在途量。

| 组别 | 路径 | 用途与局限 |
|---|---|---|
| A | Target 本机 SPDK NVMe 工具 → 同一 SSD | 提供用户态驱动与盘的本地参照；不是远端测试中的后端原位分布 |
| B | Target 本机 bdev 测试 → 同一 NVMe bdev | 检查 bdev 组合；工作线程和负载模型可能不同 |
| C | 远端 NVMe/RDMA → Target malloc bdev | 去掉真实 SSD；malloc 的内存操作与缓存行为不等于“纯网络” |
| D | 远端 NVMe/RDMA → 同一真实 NVMe bdev | 完整路径；与 C 比较用于缩小嫌疑，不用于相减得到 SSD P99 |

**真实 PCIe SSD 被 SPDK 接管时，不要同时对同一设备运行内核 fio。** 若切换驱动以建立另一类基线，应在隔离实验中记录切换、配置和设备状态变化；它已不是同一软件栈内的单变量实验。配置和接管过程见 [[5.10 VFIO UIO 与设备绑定]]、[[5.14 JSON-RPC 控制方式]]，这里不重复自动绑定设备的危险命令。

### 9.1 先确认当前 Target 暴露的对象

下面在 SPDK 源码根目录执行，`RPC_SOCK` 必须填当前实验实例的管理 socket。先读取方法表，避免把在线文档中某个版本才有的 RPC 当作本机能力；随后保存配置视图，方便核对 Namespace 到 bdev 的实际映射。[^rpc]

```bash
: "${RPC_SOCK:?请设置实验 Target 的 RPC socket 路径}"
python3 scripts/rpc.py -s "$RPC_SOCK" rpc_get_methods
python3 scripts/rpc.py -s "$RPC_SOCK" spdk_get_version
python3 scripts/rpc.py -s "$RPC_SOCK" nvmf_get_subsystems
python3 scripts/rpc.py -s "$RPC_SOCK" bdev_get_bdevs
```

这些是管理查询，不是用来测每笔 I/O 的计时器；不要高频循环 JSON-RPC，把监控本身变成干扰源。

### 9.2 Host 上的只读端到端基线

`DEV` 是已经连接的**实验远端 namespace** 对应的块设备。运行前核对 NQN、序列号和容量，确保不是系统盘或业务盘；即使只读也会干扰线上服务。以下测的是 **Linux Host + SPDK Target**，不是全用户态 Host。`--readonly` 是第二道防误写保护。[^fio]

```bash
: "${DEV:?请设置已核对的实验远端块设备}"
test -b "$DEV" || { echo "DEV 不是块设备" >&2; exit 1; }
RUN="nvmeof-$(date -u +%Y%m%dT%H%M%SZ)"
fio --name=e2e --filename="$DEV" --readonly --rw=randread \
    --ioengine=io_uring --direct=1 --bs=4k --iodepth=1 --numjobs=1 \
    --time_based=1 --ramp_time=15 --runtime=60 \
    --lat_percentiles=1 --percentile_list=50:95:99:99.9 \
    --output-format=json+ --output="$RUN.json"
```

随后在隔离窗口扫描 QD 和块大小；修改参数前复制一份带 run ID 的配置。QD=1 只能减少该 job 自己形成的并发，不能消除别的租户、设备内部任务、系统调度与共享链路排队。写路径实验仅在明确可丢弃的数据区域进行，还要单独验证数据与 Flush/FUA 语义，不能把只读模板改成写操作后直接用于业务盘。

### 9.3 怎样把结果收回到证据？

至少交付一张拓扑图、一份对象/队列映射、固定版本与配置、同窗口的 Host 分布和 Target trace、一次可逆的对照实验。若只在 Soft-RoCE 或虚拟机中跑通，应写“功能验证”，不能据此给物理 RNIC、交换机或 SSD 的性能下结论。

逐请求归因、双时钟域处理、trace 名称核对与 P99 的统计限制，继续看 [[9.10 跨层性能归因：CPU、NUMA、PCIe、NIC、Switch、RDMA 与 NVMe 的 P99]]；这篇负责解释为什么慢，不是再列一遍组件。

## 10. 完成、持久化、超时：三个不同问题

**普通 NVMe Write 完成，不应直接翻译成“已经进入 NAND”。** 需要结合设备易失性缓存、FUA、Flush、断电保护能力，以及 bdev 是否保留了上层要求的语义。Transport 负责传递命令和结果，不自动增强持久性。更不能把文件系统 `fsync` 简化为单条网络 WRITE；它还可能包含元数据与排序要求。[^nvme-spec][^ctrlr-bdev]

如果 Target 已完成写入，但 response 丢失或连接中断，Host 看到超时也不能反推出“写没发生”。重试策略必须保留顺序、去重或上层幂等约束；与其他并发写重叠时，盲目重试不是无害的。连接恢复与错误上报边界见 [[5.21 Controller Loss Timeout]] 和 [[5.22 网络故障与 Target 故障差异]]。

> [!question] 自测：能否脱离图回答？
> **1. 写盘为什么发 RDMA READ？** 因为 Target 要读取 Host 内存中的写数据，RDMA 操作按发起者视角命名。
>
> **2. Target CPU 100% 能否证明 CPU 是瓶颈？** 不能。需区分空轮询和有用工作，并看 poller 推进、排队与同负载下的干预结果。
>
> **3. Host 已完成，Target 的 request 一定回池了吗？** 不一定。两端完成的观察时间不同，Target 仍可能等待本地发送完成和回收条件。
>
> **4. 远端 P99 减本地 P99 是网络开销吗？** 不是。既不是同一批逐请求可加样本，又有不同负载与测量边界。
>
> **5. “端到端零拷贝”应怎样表述？** 指明入口、后端、数据路径和缓冲条件；普通 payload 可避免中间 CPU 拷贝，但仍有 DMA、内存访问、协议处理和资源生命周期。
