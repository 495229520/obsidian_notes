# Target CPU/NUMA/NIC/SSD 亲和性

> [[5.12 无锁 thread-per-core 模型]] 讲了 SPDK 把数据按核分家、跨核只发消息，但它回避了一个问题：**到底选哪些核？** 核不是抽象编号——在双插槽服务器上，每个核、每根内存条、每张网卡、每块 SSD 都有「户口」（属于某个 NUMA 节点，[[0.5 NUMA CPU 亲和性与内存亲和性]]）。NVMe-oF target 是一台「数据转发机」：数据从网卡进来、在内存落脚、被 SSD 取走。如果这三方不在同一个节点，每一笔 IO 的数据都要横穿两颗 CPU 之间的互联（Intel 叫 UPI），带宽被互联限死、延迟随互联拥塞抖动——**跨 NUMA 是 NVMe-oF p99 上升的高发根因，而且症状极像「网络问题」，不掌握本篇的排查法会在错误的方向浪费很多天**。本篇讲怎么查户口、怎么对齐、错位长什么样、以及怎么用对照实验验证。

前置：[[0.5 NUMA CPU 亲和性与内存亲和性]]（NUMA、绑核、首触碰）、[[3.8 PCIe 拓扑与 NUMA]]（设备户口怎么查）、[[5.11 Reactor Thread 与 Poller]]（reactor 是什么）、[[5.9 SPDK 环境与 HugePage]]（大页内存从哪来）。

## 1. 背景：target 上的一笔写 IO，数据在谁手里过

先用直白话把角色摆齐【事实】：

- **NIC**（网卡）：数据的入口。它通过 DMA（设备直接读写内存、不经过 CPU）把收到的数据放进内存；
- **Reactor 核**：SPDK 的工作线程，每核一个，轮询网卡与盘的完成事件（[[5.11 Reactor Thread 与 Poller]]）；
- **HugePage 内存**：SPDK 的数据缓冲区所在（[[5.9 SPDK 环境与 HugePage]]），数据在这里落脚；
- **NVMe SSD**：数据的出口，同样用 DMA 从内存把数据取走写入闪存。

一笔写 IO 的数据流【事实】：

```text
NIC 收包 --DMA--> 内存缓冲 <--CPU 读写（协议处理/校验）
                     |
                     +--DMA--> NVMe SSD 落盘
```

核心观察：**数据必须在内存里落脚一次，而这块内存的物理位置，决定了 NIC、CPU、SSD 三方各自访问它的距离**。NUMA 机器上「距离」不是修辞：本地节点访存走本节点内存控制器；远端访存要横穿 UPI 互联，延迟大约多几十到一百纳秒【量级】，更要命的是 UPI 总带宽有限、且被所有跨节点流量（包括其他进程的）共享【事实】。

单次访存多 ~100 ns 听起来无所谓——但 DMA 是按数据量计费的【事实】：跑 10 GB/s 的写流量，如果每字节都要过两次 UPI（网卡跨节点写 + SSD 跨节点读），互联上就压着 20 GB/s，直逼一条 UPI 链路的实际可用带宽——**上限先于盘和网卡到来**。

## 2. 查户口：每个角色的 NUMA 位置怎么看

对齐的第一步永远是查证，不是猜测【实践】。四个角色四条命令：

```bash
# ① 机器有几个节点、每节点哪些核、多少内存
numactl --hardware

# ② NIC 的户口（-1 表示单节点机器或固件没报）
cat /sys/class/net/eth0/device/numa_node

# ③ NVMe SSD 的户口
cat /sys/block/nvme0n1/device/device/numa_node

# ④ 每个节点已预留的 HugePage 数量
cat /sys/devices/system/node/node*/hugepages/hugepages-2048kB/nr_hugepages
```

设备的户口由它插在哪个 PCIe 插槽决定——每个插槽的通道物理上连着某一颗 CPU（[[3.8 PCIe 拓扑与 NUMA]]）。所以**户口是硬件事实，软件改不了；软件能改的是另外三样：线程跑在哪、内存从哪个节点分、以及买机器时设备插在哪**【事实】。

## 3. 对齐与错位：一张图看清

![[图片/SVG/8_5_23_1.svg|900]]

左图（对齐）：NIC、reactor 核、HugePage、SSD 全在 node0——网卡 DMA 写本地内存，CPU 本地访存，SSD 从本地内存 DMA 读走，**数据路径 0 次穿越 UPI**。

右图（错位）：reactor 与内存落在 node1，而 NIC 和 SSD 在 node0——同一笔数据**两次横穿 UPI**（网卡跨节点写入 + SSD 跨节点读出），reactor 的每次访存还都是远端。三种典型错位【实践】：

| 错位方式 | 成因 | 隐蔽程度 |
| --- | --- | --- |
| reactor 圈错节点 | `-m` 掩码随手写，或不知道核编号与节点的映射 | 低——对照 `numactl --hardware` 一眼看出 |
| **HugePage 在错误节点** | 用了不分节点的全局参数预留；或首触碰发生在错误节点的线程上（[[0.5 NUMA CPU 亲和性与内存亲和性]] §4） | **高——CPU 掩码完全正确，症状却一模一样** |
| NIC 与 SSD 天生不同节点 | 采购/插槽布局没考虑数据路径 | 无法软件消除，只能选择让谁近（§5） |

## 4. SPDK 怎么把亲和性做出来

SPDK 的 thread-per-core 模型天然适合亲和化——每个 reactor 绑死一个核，数据属地化到核，只要「核圈对了、内存分对了」，整条路径就对了【实现】：

```bash
# ① reactor 只跑在 node0 的核上（假设 node0 = 核 0-15，避开核 0 留给系统）
spdk_tgt -m 0xFFFE

# ② HugePage 按节点预留（node0 上 8 GiB 的 2 MiB 大页）
echo 4096 > /sys/devices/system/node/node0/hugepages/hugepages-2048kB/nr_hugepages
```

三个实现细节【实现】：

- **内存分配带节点参数**：SPDK 的数据缓冲分配接口有带 socket id 的变体（继承自 DPDK 的按节点内存池），模块内部按「分配者所在节点」就近取内存——前提是那个节点上真的预留了大页，否则静默跨节点分配，回到错位状态；
- **传输方式影响 CPU 参与度**：TCP transport 下协议栈处理与数据拷贝都靠 CPU，跨节点的每字节都要 CPU 远端访存，错位代价最大；RDMA transport 下网卡直接 DMA 进目标缓冲（[[5.19 RDMA Transport 数据路径]]），CPU 不摸数据，错位代价主要落在两次 DMA 穿越 UPI 上——**错位都疼，但疼的位置不同**；
- **中断亲和只在内核路径存在**：SPDK 轮询模式没有数据面中断（[[5.6 SPDK 用户态驱动]]）；但若 target 用内核 NVMe/TCP（非 SPDK），网卡中断与 RSS 队列的亲和性就成了同样重要的变量——原则一致：处理某条连接的核、收该连接包的队列、中断落点，三者同节点。

**双节点机器的部署模式：两个岛**【实践】。node0 的盘配 node0 的核与内存、node1 的盘配 node1 的核与内存，两组 reactor 各管各的，互不跨界——这是 [[5.12 无锁 thread-per-core 模型]]「数据落户」思想在 NUMA 尺度的放大版。代价也同款：一个岛忙、另一个岛闲时，闲核不能帮忙（帮忙 = 跨节点访存，把省下的又花回去）——**属地化换确定性，牺牲全局利用率**【取舍】。

## 5. NIC 与 SSD 不同节点：让谁近？

买来的机器网卡在 node0、一半盘在 node1，怎么办？先画数据路径再算账【实践】：

- TCP 模式下一笔写的数据要经内存中转，**网络侧摸内存的次数多于盘侧**（收包落内存、CPU 协议处理读写、盘只来取一次）——reactor 与内存**跟着 NIC 走**，把仅有的一次穿越留给「SSD 跨节点读」；
- RDMA 模式下 CPU 不摸数据，账变成「网卡 DMA 写」对「SSD DMA 读」二选一，差距缩小——此时更值得做的是把两类盘分别岛化（§4），只让天生错位的那部分盘认命；
- 这是**取舍不是定理**【取舍】：不同负载（读多还是写多）、不同传输方式，账都要重算。方法是不变的：数每字节过 UPI 的次数，选次数少的方案。

## 6. 跨 NUMA 的症状与定位

错位的症状像极了「网络不稳」，这正是它危险的地方【实践】：

| 症状 | 错位的指纹 | 与真网络问题的区分 |
| --- | --- | --- |
| 带宽上不去，卡在一个「不像盘也不像网卡」的数字 | 上限 = UPI 可用带宽 | 网卡计数器与盘各自都没饱和，但吞吐死顶 |
| 平均延迟小涨、p99 大涨 | 互联被其他流量挤占时抖动 | TCP 重传为零、网络 RTT 正常（[[5.4 延迟分解方法论]] 的分段排除法） |
| 单核 CPU 利用率异常高 | 远端访存让同样的活多花时钟周期 | perf 显示 CPU 在等内存而不是在算 |

定位命令【实现】：

```bash
# 进程的内存页实际落在哪个节点(N0/N1 列)
numastat -p $(pgrep spdk_tgt)

# 跨节点流量是否在涨:other_node 计数持续上升 = 有人在跨界访存
numastat

# reactor 线程真的跑在预期的核上吗
ps -eLo pid,tid,psr,comm | grep reactor
```

**对照实验矩阵**（验收必做，[[0.8 Benchmark 基本方法]]）【实践】：固定负载（如 4K randwrite QD32），NIC 固定在 node0，跑四组：

| 组 | reactor | HugePage | 预期 |
| --- | --- | --- | --- |
| A（全对齐） | node0 | node0 | 基线：最高带宽、最平 p99 |
| B（核错位） | node1 | node0 | CPU 远端访存：延迟上涨 |
| C（内存错位） | node0 | node1 | 两次 DMA 穿越：带宽上限下降 |
| D（全错位） | node1 | node1 | 对照 §3 右图：最差 |

四组数据在手，「本机上跨 NUMA 值多少钱」就从传说变成了实测数字——以后排查毛刺时可以直接对号。

## 7. Modern C++：亲手量出本地与远端的差价

不依赖 SPDK 也能把 NUMA 差价量出来：**让内存固定在 node0（由首触碰保证），分别用 node0 和 node1 的核去读它**。绑核用 RAII 封装，失败即抛，不留半配置状态【实现】：

```cpp
#include <pthread.h>
#include <chrono>
#include <numeric>
#include <print>
#include <stdexcept>
#include <thread>
#include <vector>

// RAII:构造即把当前线程绑到指定核,失败抛异常(Linux)
class CpuPin {
public:
    explicit CpuPin(int cpu) {
        cpu_set_t set;
        CPU_ZERO(&set);
        CPU_SET(cpu, &set);
        if (pthread_setaffinity_np(pthread_self(), sizeof(set), &set) != 0)
            throw std::runtime_error{"setaffinity failed"};
    }
};

// 在 cpu 上顺序扫一遍 buf,返回 GB/s
double sweep_gbps(int cpu, const std::vector<std::uint64_t>& buf) {
    CpuPin pin{cpu};
    auto t0 = std::chrono::steady_clock::now();
    auto sum = std::accumulate(buf.begin(), buf.end(), std::uint64_t{0});
    std::chrono::duration<double> dt = std::chrono::steady_clock::now() - t0;
    [[maybe_unused]] volatile auto sink = sum;   // 防止整段被优化掉
    return static_cast<double>(buf.size() * sizeof(std::uint64_t)) / dt.count() / 1e9;
}

int main() {
    constexpr std::size_t kWords = 512 << 20 >> 3;      // 512 MiB,远大于 LLC
    std::vector<std::uint64_t> buf;
    {
        CpuPin pin{2};                 // node0 的核先触碰 → 物理页落在 node0
        buf.assign(kWords, 1);
    }
    std::println("local  (cpu2,  node0): {:.1f} GB/s", sweep_gbps(2, buf));
    std::println("remote (cpu18, node1): {:.1f} GB/s", sweep_gbps(18, buf));
}
```

**关键点**：

- **首触碰决定页的户口**：`buf.assign` 发生在绑核 node0 的作用域里，物理页因此落在 node0——这一行挪到绑核之外，整个实验就测了个寂寞（这正是 §3 表中最隐蔽的错位在实验里的重演）；
- 核编号 2 / 18 要换成你机器上 `numactl --hardware` 给出的两个节点各一个核；单节点机器上两行结果应当几乎一样；
- 缓冲必须远大于 LLC（末级缓存），否则测的是缓存不是内存；
- 典型双路机器上远端带宽低 20%~50%、延迟高几十纳秒【量级】——具体数字以实测为准，这个程序就是给你拿数字的。

## 8. 陷阱与误区

> [!warning] 常见错误
> 1. **只对齐 CPU，忘了内存**：`-m` 掩码正确但 HugePage 预留用了全局参数，或首触碰发生在错误节点——户口对了一半，症状一点不少。查证用 `numastat -p`，不要用「我配了」当证据。
> 2. **把核编号当成连续拓扑**：核 0-15 未必都在 node0——编号可能按节点交错，超线程的兄弟核编号还可能隔了一整段。掩码写之前先看 `lscpu -e` 或 `numactl --hardware`。
> 3. **虚拟机/云主机上按 `-1` 户口硬调**：`numa_node` 读出 -1 说明拓扑没暴露，此时所有绑定都是安慰剂——先确认平台暴露了 NUMA 拓扑再动手。
> 4. **忽略 core 0 与系统噪声**：内核 housekeeping、中断默认落在低编号核上；reactor 圈进 core 0，等于给数据面请了个不定期抖动的邻居（[[9.5 p99 毛刺定位]]）。
> 5. **岛化后用全局利用率评估容量**：两个岛各 50% 负载 ≠ 可以砍一半核——岛之间不能互相帮忙，容量按每个岛单独规划（与 [[5.5 Multipath 与故障切换]] 的 N-1 规划同理）。
> 6. **调优后不做对照验证**：亲和性配置无声生效也无声失效（重启、掩码漂移、irqbalance 改回中断）。§6 的四组对照实验要进回归，不是一次性仪式（[[9.7 SLO 与性能回归]]）。

## 9. 关键结论

| 结论 | 性质 |
| --- | --- |
| target 是数据转发机：数据在内存落脚一次，内存位置决定 NIC、CPU、SSD 三方的访问距离 | 事实 |
| 设备户口由 PCIe 插槽决定，软件改不了；软件能改的是线程落点与内存分配节点 | 事实 |
| 全对齐 = 数据路径 0 次穿越 UPI；典型错位让每字节过两次互联，上限从盘/网卡变成 UPI | 事实 |
| 最隐蔽的错位是内存：CPU 掩码正确 + HugePage/首触碰在错误节点，症状与全错位相同 | 实践结论 |
| TCP 模式错位疼在 CPU 远端访存，RDMA 模式疼在 DMA 穿越——传输方式决定「跟 NIC 走还是分岛」的账 | 取舍 |
| 跨 NUMA 症状像网络问题：吞吐死顶但网卡与盘都没饱和、重传为零而 p99 上涨——用 numastat 而不是抓包定位 | 实践结论 |
| 岛化（每节点一组 reactor+盘+内存）换确定性，代价是闲核不能跨岛帮忙——容量按岛规划 | 取舍 |
| 亲和性收益必须用对照实验量化：同负载跑对齐/错位矩阵，拿到本机的「跨 NUMA 价格表」 | 实践结论 |
