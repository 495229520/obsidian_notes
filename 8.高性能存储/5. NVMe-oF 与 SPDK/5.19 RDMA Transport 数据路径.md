# NVMe-oF RDMA Transport 数据路径

> 队列建好了（[[5.18 Queue 建立过程]]），[[5.2 Transport TCP vs RDMA]] 也给过六阶段的对账结论——本篇把 RDMA transport 这一侧放大到命令级：一笔 IO 的**命令**装进什么消息、**数据**由谁搬、搬到哪。答案先行：**命令与完成走双边 SEND（小消息、天然要通知），数据由 target 发起单边 RDMA READ/WRITE（大块、对端 CPU 零参与）**——[[4.5 Send Recv 与 RDMA Read Write]] §6 说的「控制走双边、数据走单边」组合拳，NVMe-oF 就是它的工业标准版。读完你应该能指着路径上任何一步说出：这一步谁在出 CPU、有没有拷贝、慢了先查什么。

前置：[[5.2 Transport TCP vs RDMA]]（对照组）、[[5.18 Queue 建立过程]]（队列 ↔ QP 怎么建成的）、[[4.5 Send Recv 与 RDMA Read Write]]（双边/单边语义）、[[4.4 内存注册与零拷贝]]（rkey 从哪来）。

---

## 1. 先把名词说清楚

面向第一次接触的读者，三个词先给直白定义：

- **capsule（胶囊）**：NVMe-oF 给命令套的「信封」。本地 NVMe 的命令是内存环里一个 64 字节的 SQE（[[3.2 Queue Pair 与 Doorbell]]）；网络上没有共享内存环，就把这 64 字节装进一条消息发过去——装命令的叫 command capsule，装 16 字节完成项（CQE）的叫 response capsule【事实】；
- **keyed SGL**：SQE 里「数据在哪」的描述符。本地盘用物理地址（PRP/SGL）；物理地址对远端机器毫无意义，所以 fabric 上换成三元组 **（远端虚拟地址 raddr，长度，rkey）**【事实】。rkey 是 [[4.4 内存注册与零拷贝]] 里的「带权限的钥匙」——拿着它，target 的网卡才能直接读写 host 的那段内存；
- **FRWR（Fast Registration Work Request，快速注册）**：把「注册一段内存、领一把 rkey」做成一条发到 QP 发送队列的工作请求，跟数据操作一起流水化执行【实现】。为什么需要它：每笔 IO 的数据页（O_DIRECT 下就是用户 buffer 的页）都不一样，不能提前注册；而慢路径 `ibv_reg_mr` 走系统调用、按 IO 调用太贵。O_DIRECT 提交时页已被内核钉住，FRWR 只是把「这些页 ↔ 一把新 rkey」的映射写进网卡，μs 级【量级】。

一个先建立的全局感：**RDMA transport 没有发明任何新机制**——它做的只是把 [[5.1 NVMe-oF 架构]] 定义的 capsule 和数据搬运，逐项映射到 [[4.5 Send Recv 与 RDMA Read Write]] 的五类操作上。

图中 A 区是映射表的图形版：

| NVMe 队列概念 | Verbs 对象 | 备注 |
| --- | --- | --- |
| 一条 NVMe 队列（SQ+CQ） | 一条 RC QP + CQ | 每队列独占，深度在 CM 建连时预告（[[5.18 Queue 建立过程]] §2、[[4.11 RDMA CM 与连接建立]]） |
| 命令/完成 capsule | SEND / RECV 双边消息 | 接收方按队列深度**预挂满 RECV**——深度就是信用（credit），RQ 空则 RNR（[[4.17 Retry RNR 与 Timeout]]） |
| 数据缓冲 | MR + rkey | host 每 IO 用 FRWR 现场注册 bio 页，rkey 装进 keyed SGL |
| doorbell | （无对应物） | 没有共享寄存器可写；SEND 到达本身就是提交通知 |

### 读路径：一笔 4 KiB 随机读的九步（图中 B 区）

前提：host 侧 O_DIRECT（buffered IO 的差异见 §6 陷阱 1）。

| 步 | 谁 | 做什么 | CPU / 拷贝 |
| --- | --- | --- | --- |
| ① | host 软件 | bio → capsule（SQE），FRWR 注册 bio 页领 rkey，rkey 装进 keyed SGL | host CPU 出场第 1 次；无数据拷贝 |
| ② | host RNIC | `post_send` 后网卡 DMA 读走 WQE 与 capsule，SEND 上线 | CPU 提交后退场 |
| ③ | target RNIC | SEND 命中预挂的 RECV，capsule 直落缓冲，出 CQE | 无 CPU 参与传输本身 |
| ④ | target 软件 | 解析 capsule → 查 subsystem/namespace 表 → 提交本地盘（bdev → blk-mq）；盘把数据 DMA 进 target 缓冲 | **延迟大头（几十 μs）**；target CPU 只处理命令 |
| ⑤ | target 软件 | `post_send`：**RDMA WRITE**（落点 = capsule 里的 raddr+rkey）紧跟 **SEND**（response capsule） | target CPU 只发命令，不搬字节 |
| ⑥ | target RNIC | WRITE 与 SEND 依序上线——同 QP 保序：response 到达时数据必已写完（[[4.13 RDMA 操作顺序性]]） | — |
| ⑦ | host RNIC | 校验 rkey → 数据 **DMA 直写 host 的 bio 页** | **零拷贝：host CPU 全程不碰数据** |
| ⑧ | host RNIC | response capsule 命中 RECV → CQE；若用 SEND with Invalidate，顺带远程失效 rkey（[[4.12 rkey lkey 生命周期]]） | — |
| ⑨ | host 软件 | 中断/轮询收割 CQE → 确认 rkey 已失效 → 完成 bio → 唤醒应用 | host CPU 出场第 2 次 |

图中虚线框就是判断准则的图形化：**从 ② 到 ⑧，两端 CPU 都不碰数据字节**——这正是与 TCP transport 最大的结构性差异（[[5.20 TCP Transport 数据路径]]：host 接收侧每字节一次 CPU 拷贝）。

## 3. 写路径：没有 R2T，「许可」内化为 target 自主拉取

写方向（图中 C 区）四步【事实】：

1. **CapsuleCmd（SEND）**：keyed SGL 携带数据区的 rkey——数据本身留在 host 内存原地不动；
2. **target 发 RDMA READ** 把数据拉到自己的缓冲：拉取时机由 target 的缓冲水位与盘的节奏决定（[[4.5 Send Recv 与 RDMA Read Write]] §4）；
3. **落盘**：缓冲页组 bio 提交本地 blk-mq；持久化语义取决于 Flush/FUA 链（[[3.11 NVMe Flush 与 FUA]]），transport 不改变它；
4. **CapsuleResp（SEND）** 回完成。

与 TCP 写路径对照【事实】：TCP 需要 target 显式回 **R2T** 许可、host 的 io 线程再被调度起来发数据——一个软件往返、两次调度点（[[5.2 Transport TCP vs RDMA]] §4）；RDMA 把这个往返做进了硬件：READ 本身就是「我准备好了，来拿」的动作，host 软件全程不知情。

两条写路径的限制条件：

- **在途 READ 有硬闸门**【事实】：target 能同时发起的 READ 数受 QP 的 `rd_atomic` 参数约束（CM 建连时协商，典型上限 16，[[4.11 RDMA CM 与连接建立]]）。大块写带宽上不去、网络与盘都不饱和时，先查这里——症状酷似「网络慢」，根因是并发窗口；
- **小写优化：in-capsule data**【实现】：数据直接塞进 CapsuleCmd 随 SEND 同行，READ 整个消失。上限由 target 通告（Identify 的 IOCCSZ，[[5.18 Queue 建立过程]] §4），内核 target 默认 KiB 级、可配。代价是 target 要按「深度 × in-capsule 上限」预留接收缓冲——内存换往返【取舍】。

## 4. 成本对账：快在哪、每 IO 付什么

零拷贝不是免费的，账要算全（图中 D 区）：

| 项 | 读 | 写 | 说明 |
| --- | --- | --- | --- |
| 数据面 CPU 拷贝 | 两端 0 次 | 两端 0 次 | 盘 DMA ↔ 缓冲 ↔ 网卡 DMA，全程硬件搬运【事实】 |
| 每 IO verbs 开销 | 1 FRWR + 1 invalidate + host 1 SEND + target 1 WRITE + 1 SEND | 同左（WRITE 换 READ） | 每条消息还要消耗/补充一个 RECV【实现】 |
| 注册/失效 | 每 IO 一次 | 每 IO 一次 | **高 IOPS 下的隐形瓶颈**：百万 IOPS = 每秒百万次注册+失效；预注册池是消解方向（[[4.4 内存注册与零拷贝]] §6）【取舍】 |
| 完成处理 | CQE 收割：中断或轮询 | 同左 | signaled 频率可调（[[4.15 Signaled Unsignaled WR]]）；内核态保留中断+唤醒，SPDK 轮询归零（[[5.7 内核态 vs 用户态路径]]） |

延迟量级【量级】：机房内 SEND 单程 1–2 μs，FRWR ~1 μs，盘服务几十 μs——加总即 [[5.1 NVMe-oF 架构]]「远程 ≈ 本地 + ~10 μs 内」设计目标的构成。**这个目标成立的前提**：RDMA 网卡 + 近无损网络 + O_DIRECT，三者少一个都要重新算账（[[5.2 Transport TCP vs RDMA]] §1）。

## 5. 排障清单：症状 → 嫌疑 → 检查

| 症状 | 首要嫌疑 | 检查动作 |
| --- | --- | --- |
| `nvme connect` 失败/卡住 | 端口没监听、ACL 拒绝、CM 参数不合 | `nvme discover` 是否能看到 subsystem；target 侧 configfs 软链（[[5.3 Host 与 Target]] §3）；`dmesg` 里 CM 拒绝码（[[4.11 RDMA CM 与连接建立]]） |
| IO 报错、队列反复重建 | rkey 失效时序、长度越界，QP 进 ERR | `dmesg` 里 wc status（`REM_ACCESS_ERR` 等对照 [[4.5 Send Recv 与 RDMA Read Write]] §8 排障表）；rkey 生命周期核对 [[4.12 rkey lkey 生命周期]] |
| 4K IOPS 上不去，CPU 不饱和 | 中断亲和错位、signaled 每条都出 CQE、FRWR 速率 | `cat /proc/interrupts \| grep mlx` 看中断是否集中在错误核；`mpstat -P ALL`；对照 `ib_send_bw`/`ib_write_bw`（无注册无盘的上限，[[4.9 ibv_perftest 基准实验]]） |
| 大块写带宽低，读正常 | `rd_atomic` 闸门卡住 target 的 READ 并发 | 核对两端 `max_qp_rd_atomic`/`max_dest_rd_atomic`；`ibv_devinfo -v` 查设备上限 |
| p99 尖刺，p50 正常 | 网络拥塞（PFC 风暴、incast）、QP 状态被挤出网卡缓存 | `ethtool -S <网卡> \| grep -iE 'pfc\|pause\|ecn\|discard'`；连接总数账（host × subsystem × 核数，[[5.3 Host 与 Target]] §2）；归因流程走 [[5.4 延迟分解方法论]] §4 签名表 |
| IO 无限 hang | 队列断连进入重连循环 | `nvme list-subsys`（state 是否 connecting）、`cat /sys/class/nvme/nvme*/state`——行为与参数见 [[5.21 Controller Loss Timeout]] |

## 6. 陷阱与误区

> [!warning] 常见错误
> 1. **以为「RDMA transport = 应用零拷贝」**：零拷贝说的是 transport 两端；buffered IO 下应用 buffer → page cache 的 CPU 拷贝照旧存在（[[1.3 Buffered IO 与 O_DIRECT]]）。想要端到端零拷贝，O_DIRECT 是前提。
> 2. **拿 perftest 数字外推存储性能**：`ib_write_bw` 既不做每 IO 注册、后面也没有盘——它测的是网卡上限，不是 NVMe-oF 上限。中间差的正是 §4 的每 IO 成本。
> 3. **写带宽低先怪网络**：`rd_atomic` 闸门的症状与网络拥塞几乎一样；先核对参数再抓包。
> 4. **忽略 RECV 补充**：深度即信用——收割线程停摆、RECV 不回补，对端 SEND 直接 RNR，重试耗尽连接崩（[[4.17 Retry RNR 与 Timeout]]）。
> 5. **rkey 用完不失效**：完成后不 invalidate，窗口期内持有旧 rkey 的对端仍可写这段内存——正确性问题而不只是性能问题（[[4.12 rkey lkey 生命周期]]）。
> 6. **只在空载下验证**：注册速率、CQ 收割、QP 缓存的问题全都只在高 IOPS/高连接数下现形；验收要按目标负载压。

## 7. 关键结论

| 结论 | 性质 |
| --- | --- |
| RDMA transport = 「控制走双边、数据走单边」组合拳的工业标准版：命令/完成走 SEND，数据由 target 发起 READ/WRITE | 事实 |
| keyed SGL 用（raddr, len, rkey）取代物理地址描述数据；host 每 IO 用 FRWR 现场注册 bio 页 | 事实 / 实现 |
| 读：target 发 WRITE 直写 host bio 页；写：target 发 READ 自主拉取——没有 R2T 软件往返 | 事实 |
| 同 QP 保序保证 response 到达时数据必已落位——完成通知不需要额外同步 | 事实 |
| 数据面两端 CPU 拷贝 0 次；代价移到控制面：每 IO 一次注册 + 一次失效，高 IOPS 下是隐形瓶颈 | 事实 / 取舍 |
| in-capsule data 用 target 内存换掉小写的 READ 往返；上限由 IOCCSZ 通告 | 取舍 |
| 写带宽受 rd_atomic 闸门约束，症状像网络慢——排障先查参数再抓包 | 实践结论 |
| 「远程 ≈ 本地 + ~10 μs」成立前提：RDMA 网卡 + 近无损网络 + O_DIRECT；差值构成 = SEND 往返 + 注册 + 收割 | 量级 / 前提 |
