# 自定义最小 bdev 模块

> [[5.8 SPDK bdev 与 perf]] 站在**使用者**一侧：同一个 bdevperf，底下换成真盘、内存假盘、远端盘都照跑，当时把这归功于"统一块设备抽象"。本篇换到**作者**一侧，把黑盒拆开：亲手实现一个最小的 bdev 模块（一个 RAM 盘），看看统一抽象在实现侧到底是什么——答案小得出奇：**一张函数表、一次注册、三条契约**。写完你会明白 NVMe / Malloc / AIO / NVMe-oF 这些后端不过是同一接口的不同实现，即运行期多态的 C 语言写法（手写虚函数表）；也会明白为什么说"能扩展数据路径"是从"会跑 perf"到"做存储引擎"的分水岭：拦截、改写、堆叠 IO 的合法入口，就是这张函数表。

前置：[[5.8 SPDK bdev 与 perf]]（bdev 是什么、怎么压测）、[[5.11 Reactor Thread 与 Poller]]（事件循环——你的代码将寄宿其中）、[[5.12 无锁 thread-per-core 模型]]（io_channel 契约的出处）、[[5.13 SPDK NVMe Driver]]（真盘后端在函数表下面做的事）。

---

## 1. 接口全景：三个结构体，三种身份

bdev 框架与模块之间的全部约定装在三个结构体里【事实】，与 C++ 对象模型逐项对应：

| 结构体 | 身份 | C++ 对应物 |
| --- | --- | --- |
| `spdk_bdev_module` | 一**类**后端（"malloc 这种盘"）：起名 + 初始化/退出钩子 | 类 / 插件 |
| `spdk_bdev` | 一**块**盘的实例：名字、块大小 `blocklen`、块数 `blockcnt`、上下文指针 | 对象 |
| `spdk_bdev_fn_table` | 这类盘的**行为**：函数指针表 | 虚函数表 |

`fn_table` 必填四项：`submit_request`（热路径：每笔 IO 进来走这里）、`get_io_channel`（给调用线程发一条私有通道）、`io_type_supported`（回答"你支持 FLUSH/UNMAP 吗"）、`destruct`（拆除实例）。**框架负责其余一切**：全局名字表、按名字打开、bdev_io 对象池、边界检查与大 IO 切分、统计、RPC 曝光（[[5.14 JSON-RPC 控制方式]]）。

![[图片/SVG/8_5_15_1.svg|900]]

图里唯一需要预习的概念是 **io_device / io_channel**（[[5.12 无锁 thread-per-core 模型]] 机制在框架里的名字）【事实】：`spdk_io_device_register` 登记的不是一个对象，而是"每线程私有上下文的**制造方法**"（create/destroy 回调 + 大小）；某线程第一次 `spdk_get_io_channel` 时，框架**在那个线程上**调用 create 回调，造出仅供该线程使用的一份上下文。于是模块的每线程状态天然免锁——不是靠纪律，是靠"每线程各造一份"的构造方式。

## 2. bdev_io 的生命周期：你只借用，不曾拥有

`submit_request(ch, bdev_io)` 递给你的 `spdk_bdev_io` 是框架从对象池分配的（池耗尽向上返回 `-ENOMEM`，背压链同 [[5.6 SPDK 用户态驱动]] §5）。你需要的一切都在里面：

```c
bdev_io->type                 // READ / WRITE / FLUSH / UNMAP / RESET ...
bdev_io->u.bdev.offset_blocks // 起始块号(框架已做过越界检查)
bdev_io->u.bdev.num_blocks    // 块数
bdev_io->u.bdev.iovs, iovcnt  // 数据缓冲(散列表,可能不止一段)
```

三条铁律【事实/契约】：

1. **每个 bdev_io 恰好 complete 一次**：`spdk_bdev_io_complete(io, status)`。忘了调 = 这笔 IO 永久悬挂（上层 qd 被吃掉一格）；调两次 = 释放后使用，断言或损坏；
2. **完成可以异步**：`submit_request` 里立刻完成（同步）与先返回、之后某圈轮询里再完成（异步）都合法——但 `submit_request` 本身**不许阻塞**（它跑在 reactor 上，[[5.11 Reactor Thread 与 Poller]] 军规）；
3. **complete 即失效**：调用后 bdev_io 归还池子，不得留存指针；读方向的数据必须在 complete **之前**填进 iovs。

读路径还有个小机关【实现】：上层可能先不给缓冲（零拷贝路径的钩子），所以读 IO 要先 `spdk_bdev_io_get_buf(io, 回调, 长度)`——缓冲就绪后框架回调你，届时 iovs 保证可用。写路径无此步，缓冲必然已带着数据到场。

## 3. 最小模块：一个 RAM 盘的完整骨架

下面是可工作的最小实现（结构对照 SPDK 源码 `module/bdev/null` 与 `module/bdev/malloc`，构建方式见 §4；SPDK 是 C 框架，按本库惯例在边界内用 Modern C++/RAII【实现】）：

```cpp
#include "spdk/bdev_module.h"
#include "spdk/env.h"
#include <cstring>
#include <memory>
#include <vector>

namespace {

// ---------- 模块（这"类"后端）:进程内唯一 ----------
int mymalloc_module_init();
void mymalloc_module_fini();

spdk_bdev_module g_module = [] {
    spdk_bdev_module m{};
    m.name        = "mymalloc";
    m.module_init = mymalloc_module_init;   // 框架启动时回调
    m.module_fini = mymalloc_module_fini;   // 进程退出时回调
    return m;
}();

int g_io_device_tag;   // 只作 io_device 的注册地址用,无内容

// ---------- 实例（一块盘） ----------
struct MyDisk {
    spdk_bdev bdev{};                 // 框架按指针持有 → 实例地址不可搬移
    std::vector<std::byte> data;      // "介质"本体
};

// ---------- fn_table 四件套 ----------
int mymalloc_destruct(void* ctx) {
    delete static_cast<MyDisk*>(ctx);         // 与 create 处的 release 配对
    return 0;                                  // 0 = 同步拆除完成
}

spdk_io_channel* mymalloc_get_io_channel(void* /*ctx*/) {
    return spdk_get_io_channel(&g_io_device_tag);
}

bool mymalloc_io_type_supported(void* /*ctx*/, spdk_bdev_io_type t) {
    return t == SPDK_BDEV_IO_TYPE_READ || t == SPDK_BDEV_IO_TYPE_WRITE ||
           t == SPDK_BDEV_IO_TYPE_FLUSH;      // 数据常驻内存:FLUSH 是空操作
}

// 读写共用的搬运:块号换算字节偏移,逐段 iov 拷贝
void do_copy(MyDisk& disk, spdk_bdev_io* io, bool is_read) {
    const auto blk = disk.bdev.blocklen;
    auto* cursor   = disk.data.data() + io->u.bdev.offset_blocks * blk;
    for (int i = 0; i < io->u.bdev.iovcnt; ++i) {
        auto& v = io->u.bdev.iovs[i];
        is_read ? std::memcpy(v.iov_base, cursor, v.iov_len)
                : std::memcpy(cursor, v.iov_base, v.iov_len);
        cursor += v.iov_len;
    }
    spdk_bdev_io_complete(io, SPDK_BDEV_IO_STATUS_SUCCESS);
}

void read_buf_ready(spdk_io_channel*, spdk_bdev_io* io, bool ok) {
    if (!ok) { spdk_bdev_io_complete(io, SPDK_BDEV_IO_STATUS_FAILED); return; }
    do_copy(*static_cast<MyDisk*>(io->bdev->ctxt), io, /*is_read=*/true);
}

void mymalloc_submit_request(spdk_io_channel*, spdk_bdev_io* io) {
    auto& disk = *static_cast<MyDisk*>(io->bdev->ctxt);
    switch (io->type) {
    case SPDK_BDEV_IO_TYPE_READ:              // 读:先确保缓冲就绪(§2)
        spdk_bdev_io_get_buf(io, read_buf_ready,
                             io->u.bdev.num_blocks * disk.bdev.blocklen);
        return;
    case SPDK_BDEV_IO_TYPE_WRITE:
        do_copy(disk, io, /*is_read=*/false);
        return;
    case SPDK_BDEV_IO_TYPE_FLUSH:             // 无易失缓存可刷(对照 3.11)
        spdk_bdev_io_complete(io, SPDK_BDEV_IO_STATUS_SUCCESS);
        return;
    default:                                   // io_type_supported 已把过关,
        spdk_bdev_io_complete(io, SPDK_BDEV_IO_STATUS_FAILED);  // 兜底而已
    }
}

const spdk_bdev_fn_table g_fn_table = [] {
    spdk_bdev_fn_table t{};
    t.destruct          = mymalloc_destruct;
    t.submit_request    = mymalloc_submit_request;
    t.io_type_supported = mymalloc_io_type_supported;
    t.get_io_channel    = mymalloc_get_io_channel;
    return t;
}();

// ---------- 注册:把一块 32 MiB 的盘挂进框架 ----------
int mymalloc_module_init() {
    // 本模块无每线程状态:上下文大小 0,创建/销毁回调即空实现
    spdk_io_device_register(
        &g_io_device_tag, [](void*, void*) { return 0; },
        [](void*, void*) {}, 0, "mymalloc");

    auto disk = std::make_unique<MyDisk>();
    disk->data.resize(std::size_t{32} * 1024 * 1024);
    disk->bdev.name         = const_cast<char*>("mymalloc0");
    disk->bdev.product_name = const_cast<char*>("mymalloc disk");
    disk->bdev.blocklen     = 512;
    disk->bdev.blockcnt     = disk->data.size() / 512;
    disk->bdev.ctxt         = disk.get();
    disk->bdev.fn_table     = &g_fn_table;
    disk->bdev.module       = &g_module;
    if (spdk_bdev_register(&disk->bdev) != 0) return -1;
    disk.release();          // 所有权移交框架,destruct 时收回(RAII 闭环)
    return 0;
}

void mymalloc_module_fini() {
    spdk_io_device_unregister(&g_io_device_tag, nullptr);
}

}  // namespace

SPDK_BDEV_MODULE_REGISTER(mymalloc, &g_module)   // main 之前挂入模块链表
```

值得回读的四处设计：

- **所有权闭环**：`make_unique` 造、`release()` 交给框架、`destruct` 里 `delete` 收回——跨 C 边界的 RAII 只能这样"手动接力"，把配对点写清楚是唯一防线【实践】；
- **`data` 是跨线程共享的，却不加锁**——这不是疏漏【事实/前提】：并发写同一字节只在上层发出**重叠 LBA 的并发 IO** 时发生，而块设备语义本就不承诺重叠在途 IO 的顺序（真盘也一样，[[3.1 NVMe 命令模型]]）。语义不要求，实现就不必付锁的钱——官方 malloc bdev 同理；
- **FLUSH 返回成功而非不支持**：内容常驻内存，"没有易失缓存可刷"时成功是诚实语义（对照 [[3.11 NVMe Flush 与 FUA]] 里 FLUSH 的本义）；
- **框架已做过的事不必重做**：越界检查、切分、统计都发生在 `submit_request` 之前/之外——模块只写"后端本职"。

## 4. 构建与测试：先证明"对"，再谈"快"

**构建**【实现】：SPDK 源码树自带树外模块模板 `test/external_code/`（含 Makefile：把你的模块 `.o` 与 bdev 框架库、一个测试应用链接成整体），照抄骨架最省事；图更省事也可把源文件加进树内 `module/bdev/` 的构建列表重编，让 bdevperf 直接带上你的模块。路径与库清单随版本变化，以源码树为准。

**第一步永远是正确性**——bdevperf 的 `verify` 模式写入带校验图样的数据再读回比对：

```bash
# module_init 已自动建好 mymalloc0,bdevperf 对所有已注册 bdev 开跑
sudo ./build/examples/bdevperf -q 32 -o 4096 -w verify -t 30
# 通过后再跑性能口径:
sudo ./build/examples/bdevperf -q 32 -o 4096 -w randread  -t 30
sudo ./build/examples/bdevperf -q 32 -o 4096 -w randwrite -t 30
```

verify 失败几乎总是三类 bug 之一【实践】：字节偏移算错（块号 × blocklen 处漏乘/错乘）、iov 游标推进错（多段缓冲只拷了第一段）、读路径没走 `get_buf` 就碰 iovs。

**对照实验（控制变量：同参数、同核数，只换 bdev）**：

| 对照组 | 量到的东西 | 预期关系 |
| --- | --- | --- |
| Null bdev（不搬数据，直接完成） | bdev 框架自身开销的上限读数 | 最快【事实】 |
| 官方 Malloc bdev | 框架 + 一次 memcpy | 居中 |
| 你的 mymalloc0 | 框架 + 你的实现 | **应贴近 Malloc**；明显更慢 → `submit_request` 里有多余的拷贝/分配/日志 |

这是 [[5.8 SPDK bdev 与 perf]] "分层对账"方法论对自己代码的回射：**你的模块开销 = mymalloc 读数 − Null 读数**。

**进阶实验（理解异步完成契约）**：把 `do_copy` 里的 `spdk_bdev_io_complete` 挪出去——IO 先挂到自己的待完成列表，注册一个 poller 在**下一圈**统一完成。预期：吞吐基本不变，qd=1 平均延迟增加约一个轮询圈的量（亚 μs~μs 级【量级】）。做完这个改造，你就掌握了真实后端（NVMe、网络）的骨架：submit 只发起，完成永远在后面某圈轮询里到达——[[5.13 SPDK NVMe Driver]] §4 的结构在模块层的重演。

## 5. 陷阱与故障定位

> [!warning] 常见错误
> 1. **忘调 `spdk_bdev_io_complete`**（哪怕只有一条错误分支漏掉）：上层 qd 被永久吃掉一格，压测越跑越慢直至挂死——最常见也最难肉眼看出的 bug。
> 2. **complete 两次 / complete 后再摸 bdev_io**：释放后使用，触发断言是好运，静默损坏是常态。
> 3. **在 `submit_request` 里阻塞**（同步文件 IO、锁、sleep）：整核冻结，本核所有 bdev 全部停摆——症状之一是 RPC 也无响应（[[5.14 JSON-RPC 控制方式]] §2 的健康探针反向应用）。
> 4. **把每线程该分的状态塞成全局可写共享**（计数器、缓存、空闲链表）：数据竞争。规矩是进 io_channel 上下文，每线程一份（§1）。
> 5. **读路径跳过 `spdk_bdev_io_get_buf`**：本地 bdevperf 恰好总带缓冲，测试全绿；接到 NVMe-oF target 下面立刻崩——"在我机器上是好的"的经典来源。
> 6. **`io_type_supported` 撒谎**：声明支持 UNMAP 却在 submit 里走 default 失败分支,上层(如文件系统逻辑)会把它当真实 IO 错误处理,而不是优雅降级。

| 症状 | 首查 | 原因与处置 |
| --- | --- | --- |
| bdevperf 卡住不出结果 | 两次 `bdev_get_iostat` 差值是否为零 | 十有八九是陷阱 1：审计 `submit_request` 每条路径是否都通向 complete |
| 断言 / segfault 在 complete 附近 | 该 io 是否被完成两次 | 陷阱 2：给每条分支加日志或断点，找到双完成的路径 |
| verify 失败 | offset/iov 换算 | §4 的三类 bug；用 `-o 512 -q 1` 最小化后单步 |
| 整核 100% 却零 IOPS，RPC 也不应答 | `gdb -p` 看该 reactor 栈 | 陷阱 3：栈顶就是阻塞元凶 |
| 单核对多核结果不一致 / 偶发错 | 模块里的全局可写状态 | 陷阱 4：搬进 channel 上下文或走 send_msg |
| 只在 NVMe-oF 下崩 | 读路径 iovs 来源 | 陷阱 5：补 get_buf |
| `spdk_bdev_register` 返回失败 | 名字是否重复、blocklen 是否为 0 | 名字表冲突或几何没填全 |

## 6. 关键结论

| 结论 | 性质 |
| --- | --- |
| bdev 统一抽象的实现侧 = module（类）+ bdev（实例）+ fn_table（虚函数表）：运行期多态的 C 写法；上层因此不知道也不必知道下面是真盘还是内存 | 事实 |
| 框架包办名字表、io 池、边界检查、切分、统计与 RPC 曝光；模块只写四个函数——其中唯一热路径是 submit_request | 事实 |
| bdev_io 契约三条：恰好完成一次、完成可异步但提交不许阻塞、complete 即失效；读路径先 get_buf 再碰 iovs | 事实 / 契约 |
| io_channel = "每线程上下文的制造方法"：create 回调保证在目标线程执行,免锁靠构造方式不靠纪律 | 事实 |
| 共享 data 不加锁是对的：块设备语义不承诺重叠在途 IO 的顺序——语义不要求的钱不必付 | 事实 / 前提 |
| 测试次序:verify 证对 → Null/Malloc/自制三方对照量开销 → 异步完成改造理解真实后端骨架 | 方法 |
| 跨 C 边界的 RAII 是手动接力:make_unique → release 交框架 → destruct 收回;配对点必须显式写清 | 实践结论 |
| vbdev 堆叠 = 把"后端干活"换成"转发给下层 bdev",转发前后加逻辑即 crypto/delay/QoS——与内核 device-mapper 同构 | 事实 |
