# NUMA、CPU 亲和性与内存亲和性

> NUMA 优化的目标不是“把进程绑住”这么简单，而是让**执行线程、物理内存页和 PCIe 设备处在同一个局部性域**，使高频数据路径尽量不经过跨 Socket 互联。

前置：[[0.4 PCIe BAR MMIO 与 MSI-X]]。本篇先建立 NUMA、CPU 亲和性和内存亲和性的基础模型；设备侧 PCIe 拓扑见 [[3.8 PCIe 拓扑与 NUMA]]，NVMe-oF Target 的工程落地见 [[5.23 Target CPU NUMA NIC SSD 亲和性]]。

## 1. 先从一台“不是所有内存都一样近”的机器说起

在单路或简单桌面机器上，我们容易形成一种直觉：CPU 访问任意内存地址，代价大致相同。这类模型称为 **UMA（Uniform Memory Access，统一内存访问）**。

多路服务器不是这样。每颗 CPU Socket 通常拥有自己的：

- CPU 核心与末级缓存；
- 内存控制器；
- 本地 DIMM 内存；
- 一部分 PCIe Root Complex，以及挂在其下的 NIC、NVMe SSD、GPU 等设备。

不同 Socket 之间通过 Intel UPI、AMD Infinity Fabric 等片间互联连接。某个核心访问本 Socket 的内存，可以直接经过本地内存控制器；访问另一 Socket 的内存，则必须经过跨 Socket 互联。

这就是 **NUMA（Non-Uniform Memory Access，非统一内存访问）**：

> 同一个物理地址空间对所有 CPU 可见，但访问代价取决于“执行 CPU”和“物理页所在节点”之间的拓扑距离。

可以把双路服务器想象成两间相连的仓库：

- 在本仓库取货，是本地内存访问；
- 穿过连接通道去另一间仓库取货，是远端内存访问；
- 通道不但增加路程，还是多个核心和设备共享的资源，因此负载高时更容易排队。

### 1.1 核心术语

| 术语 | 含义 | 容易混淆的点 |
| --- | --- | --- |
| Socket | 一颗物理 CPU 封装 | 一颗 Socket 内通常有多个 Core |
| Core | 物理执行核心 | 开启 SMT 后，一个 Core 可对应多个逻辑 CPU |
| Logical CPU | Linux 调度器可见的 CPU 编号 | `CPU 8` 不一定等于第 8 个物理核心 |
| NUMA node | 一组拓扑上接近的 CPU 与内存 | 常与 Socket 对应，但不能永远假定一一对应 |
| Local memory | 对当前执行 CPU 所在节点而言的本地内存 | “本地”是相对访问者而言的 |
| Remote memory | 位于其他 NUMA 节点的内存 | 功能完全正确，只是代价和资源路径不同 |
| NUMA distance | 固件提供的节点间相对距离 | 是相对权重，不是纳秒数，不能跨机器直接比较 |

查看机器的真实映射，不要凭 CPU 编号猜拓扑：

```bash
lscpu -e=CPU,CORE,SOCKET,NODE,ONLINE
numactl --hardware
lstopo-no-graphics
```

`numactl --hardware` 会输出节点包含的 CPU、空闲内存和 distance 矩阵。distance 中较小的值表示更近，但具体数值由平台固件提供，不能把某个固定值解释成固定延迟。

## 2. 一次访问究竟由哪三个“位置”决定

![[图片/SVG/8_0_5_2.svg|900]]

理解 NUMA 性能时，必须同时追踪三个位置：

1. **线程在哪里执行**：当前被调度到哪个逻辑 CPU、哪个 NUMA node；
2. **物理页在哪里**：虚拟地址背后的物理页实际分配在哪个 NUMA node；
3. **设备在哪里**：NIC、NVMe SSD 等 PCIe 设备离哪个 NUMA node 最近。

这三个位置彼此独立：

- 把线程钉到 node 0，不会自动把已经分配在 node 1 的物理页搬过来；
- 把内存绑定到 node 0，不会自动限制线程只能在 node 0 运行；
- 线程和内存都在 node 0，也不代表挂在 node 1 的 NVMe 能进行本地 DMA。

因此，NUMA 调优的基本目标可以写成：

```text
线程所在节点 = 内存页所在节点 = 高频访问设备所在节点
```

这不是要求整台机器的所有对象都集中到一个节点，而是让**每条数据路径在各自节点内形成闭环**。双路存储服务器通常会在两个节点各运行一套 worker、buffer pool 和设备队列，而不是让所有流量都挤到一侧。

## 3. CPU 亲和性：限制线程可以在哪里运行

### 3.1 什么是 CPU 亲和性

**CPU 亲和性（CPU affinity）** 是一个 CPU 集合，表示某个线程允许在哪些逻辑 CPU 上运行。Linux 调度器只能在该集合内选择执行位置。

未设置亲和性时，调度器可以为了负载均衡迁移线程。迁移本身不一定错误，但对延迟敏感的数据面线程可能带来：

- 私有缓存和部分共享缓存中的热数据失效；
- 从本地内存访问变成远端内存访问；
- poller、队列和中断处理核之间的局部性被破坏；
- 每次迁移成本不稳定，表现为尾延迟毛刺。

常用操作：

```bash
# 查看进程主线程的亲和掩码
taskset -pc <pid>

# 启动时只允许程序在 CPU 2、3 上运行
taskset -c 2,3 ./app

# 查看某进程每个线程当前在哪个 CPU 上
ps -L -p <pid> -o pid,tid,psr,comm

# 查看某个具体线程的允许 CPU 列表
grep Cpus_allowed_list /proc/<pid>/task/<tid>/status
```

> [!important] CPU 亲和性以线程为单位
> Linux 调度实体是线程。多线程程序只检查主线程的 `taskset -pc <pid>`，可能漏掉其他 worker 的亲和性。排障时应检查 `/proc/<pid>/task/<tid>/status`。

### 3.2 CPU 亲和性不等于独占 CPU

“只能在 CPU 4 运行”和“CPU 4 只运行我”是两件事：

- affinity 只限制当前线程的可运行范围；
- 其他进程、内核线程和中断仍可能使用同一个 CPU；
- 真正隔离还需要 cpuset/cgroup、systemd CPUAffinity、Kubernetes CPU Manager 或启动参数等机制配合。

对 busy-poll 数据面，还应检查是否把两个繁忙 poller 放在同一物理核心的 SMT siblings 上：

```bash
lscpu -e=CPU,CORE,SOCKET,NODE
```

SMT 线程共享部分核心资源。是否使用 SMT 要以实际负载测试为准，而不是把“逻辑 CPU 数量”直接当作“独立核心数量”。

### 3.3 按 CPU 绑定与按 NUMA node 绑定

```bash
# 精确绑定逻辑 CPU
numactl --physcpubind=2,3 ./app

# 允许在 node 0 的所有 CPU 上运行
numactl --cpunodebind=0 ./app
```

- `--physcpubind` 适合固定 poller 与队列的一一映射；
- `--cpunodebind` 只保证不跨 node，仍允许在线程所属节点内部迁移。

## 4. 内存亲和性：决定物理页优先在哪里分配

### 4.1 虚拟地址不等于物理页已经分配

调用 `mmap` 或内存分配器获得地址时，程序通常先得到一段虚拟地址空间。匿名页的物理内存往往在第一次发生缺页异常时才真正分配。

Linux 默认常采用 **first-touch（首次触碰）** 策略：

> 哪个线程第一次写入某个页，内核通常就优先从该线程当前所在 NUMA node 为这个页分配物理内存。

这里有三个关键字：

- **第一次**：后续把线程钉到别处，不会自动改变已有物理页的位置；
- **写入**：只预留地址不等于完成物理分配；
- **页粒度**：同一大块 buffer 中的不同页可以落在不同节点。

### 4.2 一个非常典型的错位事故

![[图片/SVG/8_0_5_3.svg|900]]

错误不在 `std::vector`，而在初始化时机：很多容器构造、`resize`、清零和预热操作都会触碰内存。下图把反模式与正确顺序并排对照。

可记为一句话：**先钉核，再分配；谁使用，谁首次写入。**

### 4.3 常见内存策略

| 策略 | 含义 | 适用场景 | 主要取舍 |
| --- | --- | --- | --- |
| default / first-touch | 首次触碰者所在节点优先 | 线程与数据天然分片的普通程序 | 初始化线程错了就会整体错位 |
| bind | 只从指定节点集合分配 | 延迟敏感、要求位置确定的数据面 | 指定节点内存不足时可能分配失败 |
| preferred | 优先指定节点，必要时回退 | 希望局部性好，但不能因本地内存不足失败 | 回退后会出现远端页 |
| local | 从执行线程当前节点分配 | worker 已可靠钉核的场景 | 线程迁移会改变后续页的分配位置 |
| interleave | 在多个节点间轮流分配页 | 需要聚合多路内存带宽的大型顺序工作集 | 单线程会持续访问一部分远端页，延迟敏感路径通常不合适 |

用 `numactl` 控制新进程的 CPU 与后续内存分配：

```bash
# 线程和内存都在 node 0
numactl --cpunodebind=0 --membind=0 ./app

# CPU 在 node 0，故意把内存放到 node 1，用于对照实验
numactl --cpunodebind=0 --membind=1 ./app

# 大型吞吐型工作集在 node 0、1 交错分配
numactl --interleave=0,1 ./app
```

> [!warning] 内存策略主要影响之后发生的页分配
> 程序已经触碰过的页不会因为后来执行一次 `taskset` 或修改 affinity 就自动搬家。已有页的迁移需要 `migratepages`、`move_pages`、带迁移标志的 `mbind` 等额外机制，并且迁移本身有成本。

### 4.4 自动 NUMA 平衡不是“永远免费修好”

Linux 的 automatic NUMA balancing 可以采样访问并迁移任务或页面，适合没有显式管理局部性的通用负载。但对固定队列、固定设备和 busy-poll worker：

- 采样与页迁移会引入额外工作；
- 它只能根据观测逐渐纠偏，不等于从一开始就布局正确；
- 设备 DMA、线程和中断的整体关系，仍需要应用或编排系统显式安排。

查看是否开启：

```bash
cat /proc/sys/kernel/numa_balancing
```

基准测试要记录该设置，并确保所有对照轮次保持一致；不要为了调参而在生产机上随意修改全局设置。

## 5. 设备亲和性：DMA 也有本地与跨节点之分

NIC、NVMe SSD 等 PCIe 设备通常挂在某个 Socket 的 Root Complex 下，因此也有一个“最近的 NUMA node”。

```bash
# NVMe 控制器的 NUMA 节点
cat /sys/class/nvme/nvme0/device/numa_node

# 网卡对应 PCI 设备的 NUMA 节点
readlink -f /sys/class/net/eth0/device
cat /sys/class/net/eth0/device/numa_node

# 从整机视角查看 CPU、内存和 PCIe 设备的层级关系
lstopo-no-graphics
```

`numa_node` 为 `-1` 通常表示内核或固件没有提供明确局部性，或者平台没有可区分的 NUMA 归属；不能简单解释成“设备故障”。

以“NVMe 读数据后通过 NIC 发出”为例，理想路径是设备、buffer、worker 同节点闭环；若 buffer 在 node 1，设备仍然可以完成 DMA，但流量可能需要经过跨 Socket 互联。结果是：功能完全正常，数据校验也正确，却多占用一条共享链路。

设备亲和性还包括完成路径：

- NIC/NVMe 的 MSI-X 中断落在哪些 CPU；
- 软件队列由哪个 worker 轮询；
- 完成事件是否需要跨节点唤醒另一个线程。

```bash
# 查看中断计数落在哪些逻辑 CPU
grep -Ei 'nvme|eth0|mlx|ice|ixgbe' /proc/interrupts
```

中断“平均分散”不一定正确。对局部性敏感的队列，目标通常是**中断或 poller、队列、buffer、设备处于同一节点**。

## 6. 为什么平均值变化不大，p99 却可能明显变坏

一次存储 IO 的延迟可以粗略拆成：

$$
T_{\mathrm{io}} = T_{\mathrm{device}} + T_{\mathrm{dma}} + T_{\mathrm{cpu}} + T_{\mathrm{queue}}
$$

跨 NUMA 不只是给每个请求增加一个固定常数，它还会改变共享资源的竞争状态：

1. 远端访存增加 CPU 等待时间；
2. 跨节点 DMA 与远端访存共同占用 Socket 间互联；
3. 线程迁移造成缓存冷却，单次服务时间出现波动；
4. 服务时间稍微增加后，队列可能开始积压；
5. 高并发下，排队时间的增长会放大到尾延迟。

因此常见现象是：

- 平均延迟只增加一点；
- 吞吐在低负载下看起来正常；
- 一到高负载，p99/p999 先恶化；
- 互联上还有其他流量时，毛刺具有随机性或周期性。

混合布局还可能产生双峰分布：一部分请求访问本地页，另一部分请求访问远端页。平均值会把两类请求“揉平”，而分位数能更早暴露问题。

### 6.1 NUMA 错位的典型观测签名

| 现象 | 为什么值得怀疑 NUMA |
| --- | --- |
| 吞吐下降、CPU 占用上升，但设备并未饱和 | CPU 周期和带宽花在远端搬运，而非设备服务上 |
| 同一命令重复运行，结果时好时坏 | 线程落点、first-touch 线程或中断落点不稳定 |
| 平均延迟尚可，p99 周期性尖刺 | 迁移、缓存冷却或跨节点互联竞争放大尾部 |
| 单路很快，启用另一 Socket 的线程后反而变慢 | 新增线程引入远端访问或争抢互联，而非增加本地并行度 |
| 应用慢，但 `iostat` 的设备延迟正常 | 时间可能耗在设备之外的内存、调度和完成路径 |

这些现象只是线索，不能单凭一个指标下结论。最可靠的方法是做“只改变 NUMA 位置”的受控对照实验。

## 7. 观测工具：先回答“谁在哪儿”

### 7.1 静态拓扑

```bash
# CPU、Core、Socket、Node 映射
lscpu -e=CPU,CORE,SOCKET,NODE

# 节点 CPU、容量、空闲内存和距离
numactl --hardware

# CPU、缓存、内存控制器和 PCIe 设备树
lstopo-no-graphics

# 某 PCIe 设备的 NUMA 节点
cat /sys/bus/pci/devices/0000:5e:00.0/numa_node
```

### 7.2 运行时线程位置

```bash
# 每个线程最近一次运行所在的 CPU
ps -L -p <pid> -o pid,tid,psr,comm

# 允许 CPU 集合
grep Cpus_allowed_list /proc/<pid>/task/<tid>/status

# 每个 CPU 的利用率，结合 lscpu 映射回 NUMA node
mpstat -P ALL 1
```

### 7.3 运行时内存位置

```bash
# 全机 NUMA 统计
numastat

# 指定进程各节点内存分布
numastat -p <pid>

# 逐映射查看页分布与内存策略
cat /proc/<pid>/numa_maps
```

读 `numastat -p` 时，重点不是追求所有“remote/miss”字段永远为零，而是判断：

- 高频数据 buffer 是否主要位于预期节点；
- 计数是否随压测快速增长；
- 位置变化是否与吞吐、CPU 和 p99 变化同步。

`numa_miss` 增长也可能表示首选节点内存不足后的回退，因此还要同时检查各节点剩余内存，不能直接断言是代码错误。

> [!tip] 推荐的排障顺序
> 先用 `lscpu`、`numactl -H`、`lstopo` 建立拓扑图；再查线程 affinity、内存页位置和设备 `numa_node`；最后才调整绑定。没有位置证据就直接“到处绑核”，很容易把负载绑到错误节点。

## 8. 对照实验一：只改变内存所在节点

下面的最小程序申请匿名映射、逐页触碰，再反复扫描内存。它不是替代 STREAM 的精密带宽测试，而是帮助观察**同一 CPU 访问本地内存与远端内存的相对差异**。

```cpp
#include <sys/mman.h>
#include <unistd.h>

#include <chrono>
#include <cstddef>
#include <cstdint>
#include <iostream>
#include <span>
#include <stdexcept>

class Mapping {
public:
    explicit Mapping(std::size_t bytes) : bytes_{bytes} {
        void* raw = ::mmap(nullptr, bytes_, PROT_READ | PROT_WRITE,
                           MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
        if (raw == MAP_FAILED) {
            throw std::runtime_error{"mmap failed"};
        }
        data_ = static_cast<std::uint64_t*>(raw);
    }

    ~Mapping() {
        if (data_ != nullptr) {
            ::munmap(data_, bytes_);
        }
    }

    Mapping(const Mapping&) = delete;
    Mapping& operator=(const Mapping&) = delete;

    [[nodiscard]] std::span<std::uint64_t> words() const {
        return {data_, bytes_ / sizeof(std::uint64_t)};
    }

private:
    std::uint64_t* data_{nullptr};
    std::size_t bytes_{};
};

int main() {
    constexpr std::size_t bytes = 1ULL << 30;  // 1 GiB
    constexpr int rounds = 8;

    Mapping mapping{bytes};
    auto data = mapping.words();

    const long page_size = ::sysconf(_SC_PAGESIZE);
    if (page_size <= 0) {
        throw std::runtime_error{"cannot query page size"};
    }

    const auto words_per_page =
        static_cast<std::size_t>(page_size) / sizeof(std::uint64_t);

    // 逐页写入，显式触发 first-touch。
    for (std::size_t i = 0; i < data.size(); i += words_per_page) {
        data[i] = i;
    }

    std::uint64_t checksum = 0;
    constexpr std::size_t words_per_cache_line = 64 / sizeof(std::uint64_t);

    const auto begin = std::chrono::steady_clock::now();
    for (int round = 0; round < rounds; ++round) {
        for (std::size_t i = 0; i < data.size(); i += words_per_cache_line) {
            ++data[i];
            checksum += data[i];
        }
    }
    const auto end = std::chrono::steady_clock::now();

    const std::chrono::duration<double> elapsed = end - begin;
    std::cout << "elapsed_s=" << elapsed.count()
              << " checksum=" << checksum << '\n';
}
```

编译并在双 NUMA 节点机器上运行：

```bash
g++ -O2 -std=c++20 -Wall -Wextra -pedantic numa_mem_probe.cpp -o numa_mem_probe

# A：CPU 与内存都在 node 0
numactl --cpunodebind=0 --membind=0 ./numa_mem_probe

# B：CPU 仍在 node 0，只把内存放到 node 1
numactl --cpunodebind=0 --membind=1 ./numa_mem_probe
```

### 8.1 实验必须控制的变量

- 两轮使用相同 CPU 集合、数据规模、编译选项和系统设置；
- 工作集应明显大于末级缓存，否则测到的是缓存而不是 DRAM；
- 先确认机器确实有 node 0 和 node 1；
- 避免其他高带宽任务同时运行；
- 每种布局重复多轮，比较中位数和尾部，不只看单次结果；
- 同时记录 `numastat -p`，确认页确实落在预期节点；
- 不要预设固定倍率，差异取决于 CPU、内存频率、互联、访问模式和系统负载。

> [!note] 这个程序输出的 `elapsed_s` 用于相对比较
> 它每个缓存行只显式修改一个整数，真实内存事务还受缓存行填充、写分配和回写影响，因此不要把它换算成硬件的“精确峰值带宽”。正式带宽验收应使用经过校准的 STREAM、Intel MLC 或平台对应工具。

## 9. 对照实验二：只改变 NVMe 数据路径的位置

假设 `/dev/nvme0n1` 的控制器属于 node 0：

```bash
cat /sys/class/nvme/nvme0/device/numa_node

# A：线程与内存靠近设备
numactl --cpunodebind=0 --membind=0 \
  fio --name=local --filename=/dev/nvme0n1 \
      --rw=randread --bs=4k --iodepth=32 --direct=1 \
      --runtime=60 --time_based --output=local.json --output-format=json

# B：线程与内存放到另一个节点，其他参数不变
numactl --cpunodebind=1 --membind=1 \
  fio --name=remote --filename=/dev/nvme0n1 \
      --rw=randread --bs=4k --iodepth=32 --direct=1 \
      --runtime=60 --time_based --output=remote.json --output-format=json
```

对比：

- IOPS 与带宽；
- 平均完成延迟；
- p95、p99、p999；
- 每单位 IOPS 消耗的 CPU；
- `/proc/interrupts` 中完成中断的位置；
- `numastat -p` 中内存页分布。

> [!warning] 这是裸设备读测试
> 确认设备上没有需要保护的数据，并保持只读负载。若不能确认，应改用专门的测试盘或测试文件。不要把示例中的设备名直接复制到生产环境执行。

若远端轮出现“CPU 成本增加、p99 上升、设备却未更忙”，就形成了支持 NUMA 错位的证据链。若两轮没有明显差异，也可能是工作负载太轻、瓶颈在设备内部，或者平台互联足以覆盖当前流量；“没有测出差异”不等于 NUMA 原理不存在。

## 10. 从反模式到正确模式

### 10.1 反模式：只绑线程，不管内存

钉核反而把“偶尔本地、偶尔远端”变成了“永远远端”。所以 CPU affinity 不能脱离 first-touch 单独讨论（见 §4.2 反模式）。

### 10.2 反模式：所有 worker 共享一个跨节点 buffer pool

共享池可能由任意线程补充和初始化，页位置逐渐混杂。对每个请求而言，本地或远端变得不可预测，p99 比平均值更容易恶化。

更合适的方式是：

- 每个 NUMA node 拥有独立 buffer pool；
- node 内 worker 只从本地池获取 buffer；
- 跨节点移交尽量传递小型描述符，而不是搬运大块 payload；
- 必须跨节点时，在架构上显式计入互联带宽和延迟预算。

### 10.3 反模式：为了“均衡”把中断平均撒到所有 CPU

设备位于 node 0，却把一半队列中断放到 node 1，会让完成路径穿过节点边界。中断亲和性的目标不是视觉上的平均，而是与队列和 worker 的拓扑一致。

### 10.4 正确模式：每个 Socket 建立数据面闭环

![[图片/SVG/8_0_5_4.svg|900]]

每个 Socket 各自 `NIC ↔ worker ↔ buffer pool ↔ NVMe`。这类设计的代价是资源池分片：一侧繁忙时，另一侧的空闲资源不一定能无成本借用。NUMA 亲和性本质上是**可预测延迟与全局资源利用率之间的取舍**。

## 11. Hugepage、DPDK 与 SPDK 中的额外注意点

高性能存储数据面经常使用 Hugepage、DPDK 和 SPDK。此时 first-touch 原理仍重要，但还要考虑 Hugepage 是按 NUMA node 预留和分配的：

```bash
# 查看每个节点的 Hugepage 状态
for node in /sys/devices/system/node/node*; do
  echo "$node"
  grep -H . "$node"/hugepages/hugepages-*/{nr_hugepages,free_hugepages} 2>/dev/null
done
```

常见故障是：

- worker 和设备在 node 1；
- Hugepage 却只在 node 0 预留；
- 应用可以启动，但数据 buffer 被迫远端访问，或者本地 Hugepage 分配失败。

工程上应同步检查：

1. 设备属于哪个 node；
2. poller/lcore 属于哪个 node；
3. 每个 node 预留了多少 Hugepage；
4. DPDK/SPDK 的每 Socket 内存配置是否与设备分组一致。

具体 Target 线程、NIC 和 SSD 的组合策略在 [[5.23 Target CPU NUMA NIC SSD 亲和性]] 展开。

### 12.1 启动前

## 13. 常见误区

> [!warning] 误区一：线程绑在 node 0，内存自然就在 node 0
> affinity 只约束调度位置，不会自动迁移已经存在的页。必须检查 first-touch 和实际页分布。

> [!warning] 误区二：NUMA 优化就是把所有线程绑到一个 Socket
> 这样可能浪费另一 Socket 的 CPU、内存带宽和设备。正确目标通常是每个 Socket 各自形成局部数据路径。

> [!warning] 误区三：`numa_node = -1` 表示设备坏了
> 它通常只表示没有可用的 NUMA 归属信息。需要结合平台拓扑判断。

> [!warning] 误区四：interleave 一定比本地分配快
> interleave 可以聚合多节点内存带宽，但也会制造远端访问。它更适合带宽型大工作集，不是低延迟 IO buffer 的默认答案。

> [!warning] 误区五：只要平均延迟没变，NUMA 就没问题
> NUMA 错位首先可能表现在 CPU 效率、p99/p999 和负载升高后的排队，而不是空载平均值。

> [!warning] 误区六：绑定越细越好
> 过度绑定会降低调度器处理突发负载的空间，还可能造成热点和资源碎片。只对已识别的关键数据路径做有证据的约束。

## 14. 故障案例：功能正常，p99 却随流量上升

### 14.1 现象

一台双路 NVMe-oF Target：

- NIC 和 NVMe 都挂在 node 0；
- poller 已绑定到 node 0；
- 平均延迟基本正常；
- 压力升高后 p99 明显恶化，CPU/IOPS 也比同型节点高。

### 14.2 容易走错的方向

- 怀疑 SSD 固件；
- 增加队列深度；
- 添加更多 poller；
- 只检查 CPU affinity，看到线程在 node 0 就结束排查。

这些动作可能进一步加深排队，却没有回答 buffer 在哪里。

### 14.3 证据链

见图 4 中部：`numastat -p` 页位置 → 管理线程 first-touch 根因 → poller 远端访存 → 高负载 p99 放大。

### 14.4 修复

- 按 node 拆分 buffer pool；
- poller 先钉核，再由 poller 所在节点初始化本地 pool；
- node 0 的设备只使用 node 0 的 buffer；
- 用相同压测参数复测，并同时比较页分布、CPU/IOPS 和 p99。

这个案例说明：**CPU 亲和性正确只是必要条件，不是充分条件。**

## 15. 关键结论

| 结论 | 性质 |
| --- | --- |
| NUMA 的“非统一”来自拓扑：执行 CPU 到不同物理页的访问路径不同 | 事实 |
| CPU affinity、内存策略和设备归属是三个独立维度 | 事实 |
| first-touch 决定匿名页常见的初始位置，因此应先钉核，再由使用者初始化 | 事实 → 实践结论 |
| CPU affinity 只限制可运行 CPU，不会自动迁移内存，也不等于独占 CPU | 事实 |
| 理想数据路径是线程、内存页、设备和完成处理位于同一 NUMA node | 实践结论 |
| 跨节点互联是共享资源，轻载时可能无感，高负载时会通过排队放大 p99 | 原理 → 实践结论 |
| interleave、严格 bind 与本地分片各有取舍，不存在适合所有负载的绑定方案 | 取舍 |
| 最可靠的诊断方式是固定其他变量，只改变 CPU/内存节点做对照实验 | 方法论 |
