# CXL 内存池化与异构分层存储（CXL.mem / CXL.cache）

> CXL 的关键价值不是把“远端内存伪装成本地 DRAM”，而是把内存扩展、池化和共享纳入 **load/store + 缓存一致性 + 操作系统内存管理** 的统一模型。性能上仍然存在拓扑距离：本地 DRAM 是 Top-tier，CXL 内存通常是更慢但容量更大的 Bottom-tier；系统是否有效，取决于页面能否稳定地“热留 DRAM、冷落 CXL”。

前置知识：[[0.1 CPU Cache Cache Line 与内存屏障]]、[[0.2 虚拟内存 Page Table 与 TLB]]、[[0.4 PCIe BAR MMIO 与 MSI-X]]、[[0.5 NUMA CPU 亲和性与内存亲和性]]。已有 [[0.9 CXL 与 DPU SmartNIC 认知速记]] 只负责建立位置感，本篇继续追踪协议分工、地址解码、内存资源形态和 Linux 页面迁移闭环。

> [!info] 版本边界
> - 截至 2026-08，CXL Consortium 已公开 CXL 4.0；它把链路速率从 64 GT/s 提升到 128 GT/s，并增强 bundled ports 与内存 RAS。
> - 本篇的系统模型以长期稳定的 `CXL.io / CXL.cache / CXL.mem` 分工为主；池化从 CXL 2.0 开始进入标准，跨计算域的共享与 fabric 能力在 CXL 3.x 显著扩展。
> - Linux 具体接口、DAMON/DAMOS action、DAX 转换和内存热插拔能力依赖内核、发行版、固件及平台验证结果。文中的命令用于检查，不应把“规范支持”直接等同于“当前机器可用”。

## 1. CXL 先解决哪三个系统问题

传统服务器把 CPU、DDR 通道和 DIMM 插槽绑定在同一主板上。这种形态简单，但有三个结构性问题。

| 问题 | 传统做法的限制 | CXL 提供的方向 |
| --- | --- | --- |
| 容量墙 | 单 Socket 的内存通道、插槽和可寻址容量有限 | 通过 Type-3 设备扩展 Host-Managed Device Memory |
| 资源碎片 | 某台机器内存空闲，另一台机器却因内存不足被迫扩容 | 通过 switch + Fabric Manager 把内存容量做成可重新分配的池 |
| 异构介质 | DRAM、持久内存、设备侧内存具有不同延迟、带宽和成本 | 以统一地址空间暴露多个性能层级，再由 OS 或应用放置数据 |

CXL 因此不只是一条“更快的 PCIe”。它同时改变了两层边界：

1. **硬件边界**：设备内存不再只能通过驱动发命令、再由 DMA 成批搬运；CPU 可以通过 `CXL.mem` 对设备内存执行缓存一致的 load/store。
2. **资源边界**：内存容量可以与 CPU 解耦，形成扩展、池化乃至共享资源；但分配、隔离、故障域和一致性仍需要控制面管理。

> [!important] CXL 内存不是 NVMe，也不是每次访问都触发“换页”
> 当 CXL 容量被映射为 System RAM 后，CPU 对驻留在 CXL 页上的普通 load/store 直接走 CXL 数据路径。页面迁移只在放置策略决定“换层”时发生，不是每次内存访问都发生。

## 2. 三个协议分别负责什么

> **图 1：CXL 三协议、Type-1/2/3 设备与扩展/池化/共享边界**

![[图片/SVG/8_0_10_1.svg|900]]

### 2.1 CXL.io：发现、配置和非内存 I/O

`CXL.io` 与 PCIe 的配置/I/O 机制相近，负责设备枚举、初始化、配置空间、寄存器访问、邮箱命令、错误与中断等控制路径。它回答的是：

> “这是什么设备、有哪些能力、怎样配置和管理它？”

`CXL.io` 不是主要的数据内存语义。普通寄存器或 mailbox 访问走 `.io`；CPU 对设备内存的缓存一致访问走 `.mem`；设备对主机内存的缓存一致访问走 `.cache`。

### 2.2 CXL.cache：设备缓存 Host 内存

`CXL.cache` 允许设备一致地访问并缓存主机内存。典型方向是：

```text
加速器 / SmartNIC  →  Host DRAM
```

设备可以把主机内存中的缓存行保留在自己的 cache 中；当 CPU 与设备都可能读写同一缓存行时，CXL coherence 协议负责 snoop、所有权与失效关系。它适合需要细粒度共享主机数据结构的加速器，而不只是传统的“设备发 DMA、CPU 手工同步所有权”。

### 2.3 CXL.mem：Host 访问设备内存

`CXL.mem` 允许 CPU 一致地访问并缓存设备提供的 Host-Managed Device Memory（HDM）。典型方向是：

```text
CPU load/store  →  Type-2 / Type-3 设备内存
```

操作系统先把一段 Host Physical Address（HPA）路由到 CXL 设备。进程仍然从虚拟地址出发，经页表和 TLB 得到 HPA；随后 CXL Host Bridge、switch 和 HDM Decoder 把请求送到设备侧地址。也就是说，CXL 没有绕过虚拟内存，只是给物理地址空间增加了一种新后端。

### 2.4 最容易说反的一句话

> [!warning] `.cache` 不是“拿 CXL 内存当 CPU 的额外缓存”
> - `CXL.cache`：**设备**缓存并一致地访问 **Host 内存**。
> - `CXL.mem`：**Host CPU**缓存并一致地访问 **设备内存**。
>
> CPU 当然可能把 `CXL.mem` 返回的缓存行放进自己的 CPU Cache，但协议名称描述的是事务方向和一致性角色，而不是“这块介质叫什么缓存”。

## 3. Type-1 / Type-2 / Type-3 如何组合协议

| 设备类型 | 必需协议 | 是否提供 HDM | 典型设备 | 核心用途 |
| --- | --- | --- | --- | --- |
| Type-1 | `CXL.io + CXL.cache` | 否 | SmartNIC、无本地大容量内存的加速器 | 设备一致地访问 Host DRAM |
| Type-2 | `CXL.io + CXL.cache + CXL.mem` | 可提供 | GPU、FPGA、带 HBM/本地内存的加速器 | CPU 与设备共享两侧内存，并保持一致性 |
| Type-3 | `CXL.io + CXL.mem` | 是 | DRAM/持久内存扩展器 | 给 CPU 增加字节可寻址容量 |

本篇讨论的内存扩展与分层，主角是 **Type-3**。它通常没有通用计算核心，却可以向主机暴露易失或持久容量。Linux 常把它建模成一个 CPU-less NUMA node：节点有内存，没有可调度 CPU。

Type-2 也能暴露设备内存，但它的设计问题还包括设备自身执行、双向一致性和加速器内存管理；不能把 Type-2 简化为“更贵的 Type-3”。

## 4. 从一条物理地址追到 CXL 介质

### 4.1 地址链

一次 `CXL.mem` 访问可按下面的地址链理解：

```text
进程虚拟地址 VA
    ↓ 页表 / TLB
Host Physical Address, HPA
    ↓ Root / Switch / Endpoint HDM Decoder
Device Physical Address, DPA
    ↓ 设备控制器
DRAM / 持久介质中的目标位置
```

其中：

- **HPA** 属于主机物理地址空间，页表最终指向它；
- **HDM Decoder** 定义某段 HPA 应转发到哪个端口、设备和 DPA 范围；
- **CXL Region** 是 Linux 把一组 decoder 配成可用地址映射后的逻辑内存区域；
- 多设备 region 可以做 interleave，把相邻粒度的数据条带化到多个 memdev，以聚合容量或带宽，但也会扩大故障影响面。

这和 [[0.4 PCIe BAR MMIO 与 MSI-X]] 中的 BAR/MMIO 不同：BAR 主要给 CPU 访问设备寄存器窗口；HDM decoder 则把主机物理内存地址路由到设备内存。

### 4.2 Linux 把 CXL Region 暴露成两种主要形态

| 形态 | 用户看到什么 | 分配者 | 是否适合透明分层 |
| --- | --- | --- | --- |
| Device DAX | `/dev/daxN.Y`，应用通过 `mmap()` 直接映射 | 应用或专用 runtime | 否；应用显式管理地址与生命周期 |
| System RAM | 经 `dax_kmem` 和 memory hotplug 加入 page allocator | Linux 页分配器、NUMA 策略 | 是；普通匿名页、页缓存等可落到该节点 |

“透明”只表示应用不必改用块 I/O API；运维与内核仍必须正确完成 decoder、region、DAX、memory hotplug、NUMA node 和 memory tier 的配置。

> [!note] DAX 映射与 System RAM 不是同一层抽象
> `/dev/daxN.Y` 让应用直接决定怎样使用容量；System RAM 则把容量交给 Linux 通用页分配器。前者位置可控，后者更透明，但页面放置与迁移策略会直接决定性能。

## 5. 内存扩展、池化与共享不是同一件事

| 资源形态 | 同一时刻的主要拥有者 | 控制面动作 | 数据面语义 | 成熟度心智模型 |
| --- | --- | --- | --- | --- |
| 扩展（Expansion） | 单 Host | 启用本机直连 Type-3 容量 | Host 对设备内存 load/store | 第一代落地最直接 |
| 池化（Pooling） | 一段容量通常绑定给一个 Host | Fabric Manager 盘点、切片、绑定/解绑 Logical Device | 绑定后作为该 Host 的专用内存 | CXL 2.0 引入 switch + pooling |
| 共享（Sharing） | 多个 Host / 设备可访问同一资源范围 | 建立共享域、权限、地址与故障管理 | 需要额外定义一致性、同步和生命周期 | CXL 3.x 扩展 fine-grained sharing / fabric |

### 5.1 Pool 的本质是“库存可调度”，不是“所有主机同时读写”

可以把池化看成一组可切分的内存库存：

1. Fabric Manager 发现 switch、端口、Logical Device 和容量；
2. 控制面为 Host A 绑定一段容量，为 Host B 绑定另一段；
3. Host 只枚举和使用绑定给自己的逻辑设备；
4. 解绑前必须处理页面下线、数据清理、租户隔离和设备状态。

因此“池化”首先解决的是利用率和容量调度。它通常依靠**空间隔离**避免多主并发修改同一范围。

### 5.2 Shared Memory 还多出一整套分布式正确性问题

真正共享同一物理范围时，不能只说“大家都能 load/store”就结束。系统还需要回答：

- 哪些参与者处于同一 coherence domain；
- 原子操作、锁和内存序在跨 Host 场景中的边界；
- 某个 Host 崩溃后，谁回收锁、引用和内存所有权；
- 热拔、链路错误、poison 和持久介质故障如何传播；
- 多租户之间怎样做访问控制、清零和审计。

> [!important] Pooling ≠ Sharing
> 池化是“从公共库存中分配专用切片”；共享是“多个计算域同时访问同一数据”。后者不自动等价于 POSIX shared memory，更不自动提供数据库事务或分布式锁语义。

## 6. 延迟量级：为什么常说 200–300 ns，但不能把它当协议常数

### 6.1 先建立坐标系

下面只给工程量级，测试结果会随 CPU、CXL 控制器、内存介质、链路宽度、retimer/switch、NUMA 拓扑、并发度和测量方法显著变化。

| 路径 | 常见量级 | 读法 |
| --- | ---: | --- |
| 本地 DRAM | 约 80–120 ns | 最快的主存层，仍远慢于 LLC |
| 跨 Socket NUMA DRAM | 约 120–200+ ns | 多经过片间互联，并与其他流量竞争 |
| 直连 CXL Type-3 DRAM | **低数百 ns**；约 200–300 ns 可作规划点 | 真实系统研究覆盖约 140–410 ns，不能只背一个数 |
| 经 switch / retimer 的 CXL 内存 | 直连基础上继续增加 | 取决于跳数、交换与排队，而非只看协议代际 |
| NVMe 随机读 | 约 10–100 μs | 比 CXL 内存再慢约两个数量级 |

可把一次 CXL 访问拆成：

```text
T_CXL
= T_CPU/LLC miss
+ T_host bridge
+ T_link + T_retimer/switch
+ T_device controller
+ T_media
+ T_queueing
```

协议公布的 GT/s 只约束链路传输能力，不能消掉控制器、介质和排队延迟。负载升高后，平均延迟和 p99 还可能因队列拥塞快速上升。

### 6.2 为什么“延迟更高”不代表“带宽一定很差”

延迟是一个依赖链上的等待时间；带宽取决于系统能同时保留多少 outstanding request，以及链路、控制器和介质能否并行服务。

一个有用的上界模型是：

```text
BW_observed ≤ min(
    BW_link_payload,
    BW_device_media,
    BW_controller,
    MLP × cache_line_size / latency
)
```

- **MLP（Memory-Level Parallelism）低**：指针追逐、哈希冲突链等存在长依赖链，下一次地址要等上一次返回，性能更接近延迟受限。
- **MLP 高**：大数组扫描、向量化分析、批量预取能同时发出很多 miss，更可能利用 CXL 的聚合带宽。
- **多设备 interleave**：可能叠加多条链路和多个内存控制器的带宽，但热点条带、switch oversubscription 和 Host 端入口仍可能成为瓶颈。

CXL 2.0、3.x、4.0 的公开链路速率依次可到 32、64、128 GT/s。它们是每 lane 的原始传输速率；有效载荷带宽还受 lane 数、flit/协议开销、读写方向、设备实现和工作负载影响，不能直接把 GT/s 当成应用可用 GB/s。

> [!tip] CXL 既可以是容量层，也可以是带宽扩展器
> “DRAM 放热页、CXL 放冷页”是最常见模型；对可并行的带宽型负载，也可能把一部分页主动分散到 CXL，利用 DDR + CXL 的聚合带宽。两种目标不同：前者最小化慢访问，后者最大化并行通道，不能用同一套静态比例套所有负载。

## 7. Linux 如何把 DRAM 与 CXL 组织成 Memory Tiers

> **图 2：CXL Region 进入 Linux 页分配器，以及 AutoNUMA / DAMON 的观察—决策—迁移闭环**

![[图片/SVG/8_0_10_2.svg|900]]

### 7.1 Top-tier 与 Bottom-tier

典型两层系统可以抽象为：

```text
Top-tier:    CPU-attached DRAM，低延迟、高带宽、容量较小
Bottom-tier: CXL-attached memory，延迟更高、容量更大、成本/可组合性更好
```

Linux 把不同内存资源表示为不同 NUMA node，再把性能接近的节点组成 `memory_tierN`。节点属于哪个 tier，不应只靠“它有没有 CPU”猜测；内核需要性能坐标来排序。

### 7.2 HMAT / CDAT 决定系统是否真正理解“谁更快”

- **SRAT**：描述 proximity domain 与 CPU/内存/Generic Port 的亲和关系；
- **HMAT**：提供 CPU 到内存或 CXL Host Bridge 的延迟与带宽信息；
- **CDAT**：由 CXL 设备提供设备侧容量的性能坐标；
- Linux 将这些信息组合成 access coordinates，供 memory tier 与 demotion path 使用。

检查 tier：

```bash
for tier in /sys/devices/virtual/memory_tiering/memory_tier*; do
    printf '%s: ' "$tier"
    cat "$tier/nodelist"
done
```

> [!warning] 没有 HMAT/CDAT，不代表内核会自动猜对
> 当前 Linux 文档明确提醒：在线内存节点默认可能先进入 DRAM tier；若明显更慢的 CXL node 与 DRAM 被分到同一 tier，应先检查固件表和 access coordinates，而不是马上调页面迁移阈值。

### 7.3 初始放置仍然受 first-touch 与 mempolicy 影响

把 CXL 加入 System RAM 后，普通分配仍然受 [[0.5 NUMA CPU 亲和性与内存亲和性]] 中的规则影响：

- first-touch 决定匿名页第一次落在哪个节点；
- `mbind()`、`set_mempolicy()`、`numactl --membind/--preferred/--interleave` 可以表达静态策略；
- AutoNUMA 或 DAMOS 只能在观测之后纠偏，无法抵消一个持续错误的初始化和线程布局；
- 页面已被 pin、mlock、设备长期 DMA 或属于某些不可迁移类别时，自动迁移可能失败或被跳过。

## 8. AutoNUMA：用 Hinting Fault 发现热页

### 8.1 两种 NUMA Balancing 模式

`kernel.numa_balancing` 是位掩码：

| 值 | 模式 | 目标 |
| ---: | --- | --- |
| `0` | Disabled | 关闭自动 NUMA balancing |
| `1` | Normal | 在传统 NUMA 节点之间减少远端访问 |
| `2` | Memory Tiering | 把热页放到更快的 memory tier |
| `3` | `1 OR 2` | 同时启用 Normal 与 Tiering |

读取当前设置：

```bash
sysctl kernel.numa_balancing
sysctl kernel.numa_balancing_promote_rate_limit_MBps
```

### 8.2 观察机制

AutoNUMA 会周期性地让部分映射暂时不可直接命中，随后在访问时产生 **NUMA hinting fault**。内核利用 fault 记录“哪个任务、哪个 CPU/节点正在访问这页”，再决定是否迁移。

简化逻辑：

```text
采样页映射
  → 访问触发 hinting fault
  → 判断访问者与页面位置 / tier
  → 热页从慢层 promote 到快层
  → 更新统计并等待下一轮
```

这种机制的优点是应用无感；代价是 unmap、fault、页复制和 TLB 失效都不是免费的。已经通过绑核和显式 mempolicy 做好稳定布局的负载，开启 AutoNUMA 反而可能增加抖动。

### 8.3 Promotion 与 Demotion 要分开理解

- **热页提升（promotion）**：Memory Tiering 模式通过 hinting fault 识别 CXL 中的热页，并尝试迁移到快层；`numa_balancing_promote_rate_limit_MBps` 限制每节点提升吞吐，避免迁移占满链路和内存带宽。
- **冷页降级（demotion）**：内存压力触发 `vmscan` reclaim；启用 `/sys/kernel/mm/numa/demotion_enabled` 后，回收路径可优先把页迁到下一层 NUMA node，而不是立刻 swap/zswap。

```bash
cat /sys/kernel/mm/numa/demotion_enabled
```

因此不要把“AutoNUMA”理解成一个完全对称的冷热搬运线程。热页识别、快层 headroom、reclaim 水位和 demotion path 共同组成实际闭环。

## 9. DAMON / DAMOS：把观测与策略显式分开

### 9.1 DAMON 本身首先是观测器

DAMON（Data Access MONitor）按 `sampling interval` 采样访问，再按 `aggregation interval` 汇总。为了避免工作集越大、监控成本无限增长，它把访问模式相近的相邻页合并成 region，只在 region 内抽样，并根据访问差异自适应 split/merge。

它输出的核心信息是：

- region 地址范围与大小；
- 访问次数 `nr_accesses`；
- 当前访问模式持续时间 `age`；
- 采样与聚合窗口下的统计误差。

所以 DAMON 给的是**有界开销的近似热度图**，不是逐次访问的精确 trace。

### 9.2 真正执行迁移的是 DAMOS scheme

DAMOS（DAMON-based Operation Schemes）把“什么 region 算热/冷”与“采取什么动作”组合起来，并支持 quota、watermark、filter 与 action interval。较新的内核接口提供：

- `migrate_hot`：把匹配的热 region/page 迁往指定快节点；
- `migrate_cold`：把匹配的冷 region/page 迁往指定慢节点；
- `target_nid` 或多个加权 `migrate_dests`：指定目标节点；
- quota：限制时间或字节预算，避免迁移风暴。

> [!warning] 不要把所有 DAMON 模块都叫“CXL 分层”
> - `DAMON_RECLAIM` 主要把冷页 page out，目标可能是 swap；
> - `DAMON_LRU_SORT` 主要调整 LRU 热冷位置；
> - 只有配置了适合的 DAMOS migration action 和目标 node，才是在 DRAM/CXL 之间直接迁移。

### 9.3 AutoNUMA 与 DAMON 的取舍

| 维度 | AutoNUMA / Memory Tiering | DAMON + DAMOS |
| --- | --- | --- |
| 热度信号 | Hinting fault，围绕页与访问者关系 | region-based sampling，带频率和 age |
| 默认目标 | 通用、应用透明的局部性与热页提升 | 可编程的数据访问策略 |
| 冷页路径 | 主要结合 reclaim / demotion | 可显式配置 `migrate_cold` |
| 控制粒度 | 内核内置启发式与少量 sysctl | pattern、quota、watermark、filter、目标 node |
| 主要风险 | fault 开销、与显式绑核策略冲突 | 参数复杂、采样误差、策略配置不当 |
| 适合场景 | 通用 workload，先获得合理默认值 | 大内存服务、需要可观测和可审计策略的场景 |

## 10. 页面迁移什么时候值得做

迁移一个页并不是“修改页表指针”这么简单，通常包括：隔离源页、在目标节点分配新页、复制数据、处理并发访问、更新 PTE、执行必要的 TLB shootdown，再回收旧页。

可以用下面的不等式判断一次提升是否值得：

```text
未来收益
≈ N_future_access × (L_CXL - L_DRAM)

迁移成本
≈ page_size / migration_bandwidth
 + 页面隔离与分配
 + PTE 更新与 TLB shootdown
 + 对应用和链路的干扰

只有：未来收益 > 迁移成本 + 安全余量，才应该迁移
```

这解释了几个工程原则：

1. **要看持续热度，不只看一次 fault**：否则页会在两层间 ping-pong。
2. **设置迟滞（hysteresis）**：提升阈值高于降级阈值，并加入 cooldown/age。
3. **为快层保留 headroom**：DRAM 塞满后，即使发现热页也没有目标空间；TPP 的核心贡献之一就是主动 demotion，为新热页和 promotion 留余量。
4. **限制迁移吞吐**：迁移本身消耗 DRAM、CXL 链路和 CPU；平均吞吐可能提高，p99 却可能恶化。
5. **区分 4 KiB 与大页**：大 folio/THP 一次搬得更多，若只有少量子页热，会产生迁移放大；拆分与合并又有额外成本。

> [!tip] 页面温度不是页面的永久属性
> 同一页会随请求阶段、批处理窗口、模型层和 compaction 周期变热或变冷。分层策略是反馈控制系统，不是一次离线分类。

## 11. 哪些工作负载适合 CXL 分层

| 工作负载特征 | 适配度 | 原因与策略 |
| --- | --- | --- |
| 大容量服务，工作集有稳定热冷分布 | 高 | 热集放 DRAM，冷集放 CXL，容量收益明显 |
| In-memory DB / KV cache，有大量低频对象 | 高 | 可按访问热度提升，保留 DRAM 给索引和活跃对象 |
| 分析扫描、向量化处理，MLP 高 | 中到高 | 可把 CXL 当带宽扩展器，评估 interleave 比例 |
| AI CPU 侧 KV Cache / embedding 冷层 | 中到高 | 比 NVMe 更接近内存语义，但不能替代 HBM 热路径 |
| 指针追逐、随机依赖链、MLP≈1 | 低到中 | 直接暴露 CXL 延迟，必须确保关键节点留在 DRAM |
| 热集快速振荡 | 低 | 迁移决策落后于 workload，容易 ping-pong |
| 硬实时或极端 p99 敏感 | 低 | hinting fault、reclaim 和后台迁移带来不可预测干扰 |
| 大量 pinned / mlocked / 长期 DMA 页 | 低 | 页面不可迁移或迁移受限，透明策略难以收敛 |

对 AI Infra 最重要的定位是：CXL 适合作为 **HBM/DRAM 与 NVMe 之间的容量层、共享池或 CPU 侧缓存层**。它不能凭协议名称消除 GPU 访问路径、CPU-GPU 拷贝、NUMA 拓扑和软件 runtime 的约束。

## 12. Linux 观察与实验路径

### 12.1 先确认硬件、decoder、DAX 与 NUMA 拓扑

```bash
# 内核与 PCI/CXL 设备
uname -r
lspci -nn | grep -i -E 'cxl|memory'
ls -l /sys/bus/cxl/devices/

# cxl-cli / daxctl 通常来自 ndctl 工具套件
cxl list
daxctl list

# CPU、内存节点与距离
numactl --hardware
lstopo-no-graphics
lsmem
```

### 12.2 再确认 CXL 是否已经进入 page allocator 和正确 tier

```bash
# 查看各 memory tier 包含哪些 NUMA node
for tier in /sys/devices/virtual/memory_tiering/memory_tier*; do
    printf '%s: ' "$tier"
    cat "$tier/nodelist"
done

# 查看自动分层开关
sysctl kernel.numa_balancing
sysctl kernel.numa_balancing_promote_rate_limit_MBps
cat /sys/kernel/mm/numa/demotion_enabled

# 查看节点级与进程级 NUMA 分配
numastat -m
numastat -p <pid>
```

某个路径不存在，不等于命令“写错了”；也可能是内核配置、驱动、固件、设备形态或发行版没有提供相应能力。

### 12.3 观察迁移，而不是只看最终吞吐

```bash
# 先确认当前内核有哪些迁移 tracepoint
perf list 'migrate:*'

# 示例：记录系统范围内的页面迁移事件
sudo perf record -a -e migrate:mm_migrate_pages -- sleep 30
sudo perf script
```

还应同步观察：

- 应用 p50 / p99 / p999 延迟与吞吐；
- local/remote/CXL 实际访问比例；
- IPC、LLC miss、memory stall；
- promotion/demotion 字节数、失败数和迁移速率；
- DRAM headroom、reclaim、swap/zswap；
- CXL 链路、switch 端口和设备控制器拥塞计数器（若平台提供）。

### 12.4 最小对照矩阵

| 组别 | CPU 策略 | 内存策略 | 自动迁移 | 要回答的问题 |
| --- | --- | --- | --- | --- |
| A | 固定本地 CPU | DRAM only | 关 | 理想快层基线 |
| B | 同 A | CXL only | 关 | 纯 CXL 延迟/带宽上限 |
| C | 同 A | DRAM+CXL interleave | 关 | 聚合带宽是否抵消慢延迟 |
| D | 同 A | 允许两层 | AutoNUMA tiering | 通用策略能否收敛 |
| E | 同 A | 允许两层 | DAMON/DAMOS | 自定义阈值、quota 是否更稳 |

启动静态绑定实验的形式：

```bash
# 示例 node 编号必须先由 numactl --hardware 确认
numactl --cpunodebind=<cpu_node> --membind=<dram_node> ./workload
numactl --cpunodebind=<cpu_node> --membind=<cxl_node>  ./workload
numactl --cpunodebind=<cpu_node> --interleave=<dram_node>,<cxl_node> ./workload
```

每组至少记录预热阶段、稳态阶段和压力/回收阶段。只跑一次均值无法看出迁移扰动和 CXL 队列造成的尾延迟。

## 13. 常见误区与故障边界

### 13.1 把 NUMA distance 当成纳秒

`numactl --hardware` 的 distance 是固件给出的相对权重，不是测量延迟。真正的 200–300 ns 应由目标平台上的 pointer-chasing latency benchmark 验证。

### 13.2 看到 CPU-less node 就断言它一定是 Bottom-tier

内存 tier 依赖 HMAT/CDAT 和 access coordinates。固件缺失或错误时，CXL 与 DRAM 可能被归到同一 tier，自动 demotion path 随之错误。

### 13.3 只测 STREAM 就宣布 CXL“和 DRAM 一样快”

STREAM 主要测可并行带宽；指针追逐、锁、索引树和 page-table-heavy workload 更容易暴露延迟。必须同时测 latency、bandwidth、MLP 敏感性和尾延迟。

### 13.4 认为 System RAM 配好后应用就完全不用关心

透明分层可以减少代码改动，但 first-touch、mempolicy、线程亲和性、pinning、THP、page cache、cgroup/cpuset 和业务阶段仍会影响页面位置。

### 13.5 迁移越积极越好

过度 promotion/demotion 会复制大量数据、挤占链路、触发 TLB shootdown，并造成 p99 毛刺。策略必须有 quota、rate limit、age 和 hysteresis。

### 13.6 把内存池化当成无状态资源绑定

解绑或热拔前，必须先把页面迁出/下线，处理持久数据、poison、引用、DMA 和租户清理。CXL 4.0 等后续版本强化 RAS，不代表操作系统可以忽略故障与生命周期协议。

### 13.7 规范能力等于平台能力

CPU Host Bridge、BIOS/ACPI、switch、retimer、Type-3 设备、内核、`cxl-cli`、DAX、memory hotplug 和监控工具必须共同工作。任一层不完整，都可能只能枚举设备而无法形成可用 System RAM 或 memory tier。

## 14. 系统级总结

1. **协议分工**：`CXL.io` 管发现与控制，`CXL.cache` 让设备一致地缓存 Host 内存，`CXL.mem` 让 Host 一致地访问设备内存。
2. **设备分工**：Type-1 侧重 `.cache`，Type-2 同时拥有 `.cache/.mem`，Type-3 用 `.mem` 做内存扩展。
3. **资源形态**：扩展是一机一设备；池化是容量库存的动态切片与绑定；共享才是多计算域同时访问，正确性要求更高。
4. **性能坐标**：CXL 内存通常落在低数百纳秒，约 200–300 ns 是代表性规划点而非规范保证；带宽取决于 lane、控制器、介质、MLP 和拓扑拥塞。
5. **Linux 闭环**：CXL Region 经 DAX 转为 System RAM 后成为 NUMA node；HMAT/CDAT 决定 tier；AutoNUMA 侧重热页 promotion，reclaim/demotion 负责冷页下沉，DAMON+DAMOS 提供可编程的观察和迁移策略。
6. **真正的优化目标**：不是让所有页都留在 DRAM，而是在可接受的迁移成本和尾延迟下，把有限快层留给最有价值的访问。
