# Interrupt、Busy Polling 与 Context Switch

> **中断用“事件到达后通知 CPU”节省空闲算力；忙轮询用“CPU 主动反复检查”换取更短、更稳定的发现延迟；混合模式则试图在两者之间动态折中。**

---

## 1. 为什么完成通知会影响数据路径性能

一次异步 I/O 可以粗略分成两半：

1. **提交路径**：软件把请求描述符写入提交队列，再通过 doorbell 等方式通知设备；
2. **完成路径**：设备完成 DMA 后更新完成队列，软件发现完成项并处理结果。

这里研究的是第二步：**设备已经做完工作以后，CPU 怎样知道？**

> **图 1：同一份设备完成状态，可以通过不同通知策略被 CPU 发现。**

![[图片/SVG/8_0_6_1.svg|900]]

如果设备本身已经很快，那么“设备完成”到“软件开始处理完成项”之间的这段等待，可能成为端到端延迟的重要组成部分。因此高性能存储不仅关心 SSD 有多快，还关心：

- 完成通知是否需要进入内核；
- 线程是否会睡眠和再次被唤醒；
- 是否发生调度和上下文切换；
- 完成队列、线程和设备是否位于合适的 CPU / NUMA 节点；
- 为降低延迟消耗了多少 CPU。

> [!important] 本章的核心矛盾
> **Interrupt 优先节省 CPU，Busy Polling 优先降低发现延迟。不存在脱离负载、硬件和 SLO 的“永远最优方案”。**

## 2. 先建立三个基本概念

### 2.1 Interrupt：有事再叫我

**中断（Interrupt）**可以理解为设备向 CPU 发送的一次异步通知：

> “刚才提交的工作已经完成，请来处理完成队列。”

等待期间，原来的线程可以睡眠，CPU 可以运行其他任务或进入更深的空闲状态。设备完成后，硬件中断让 CPU 转入相应的中断处理路径。

简化流程与「中断 / 特权级切换 / 上下文切换」三者区分见下图。

> **图 2：中断完成路径泳道 · 三者不是同一件事 · Context Switch 直接/间接成本**

![[图片/SVG/8_0_6_2.svg|900]]

它的优势是**空闲时几乎不需要持续检查**；代价是完成路径可能增加中断处理、线程唤醒、调度等待和缓存重新变热等步骤。

### 2.2 Busy Polling：我一直看着

**忙轮询（Busy Polling）**是指 CPU 不主动睡眠，而是在循环中反复检查完成队列或状态位：

```cpp
while (!stop_requested) {
    const auto completed = poll_completions();
    process(completed);
}
```

这段伪代码表达的是轮询思想，不代表可以忽略真实设备 API 的内存顺序、批处理和错误处理要求。

轮询的目标不是让设备更快，而是缩短「设备已经完成 → 软件发现完成」这一段**完成发现延迟**。CQ 内存结构、poll 循环与发现延迟对比见下图。

> **图 3：Busy Polling 轮询主机 DRAM 中的完成队列 · 空轮询比率 R_useful**

![[图片/SVG/8_0_6_3.svg|900]]

### 2.3 Context Switch：CPU 换一个执行者

**上下文切换（Context Switch）**是指调度器把某个逻辑 CPU 的执行权从一个可调度实体切换给另一个。需要保存旧任务并恢复新任务的执行现场，例如：

- 程序计数器；
- 栈指针和通用寄存器；
- 调度状态；
- 与体系结构和任务相关的其他状态。

上下文切换有两类常见来源：

| 类型 | 含义 | 典型原因 |
|:---|:---|:---|
| **自愿切换** | 线程主动进入不能继续运行的状态 | 阻塞 I/O、等待锁、条件变量、主动睡眠 |
| **非自愿切换** | 线程仍想运行，但被调度器换下 | 时间片耗尽、更高优先级任务就绪、CPU 竞争 |

目标笔记关注的是：**中断等待模型经常伴随“睡眠 → 唤醒 → 重新调度”，而忙轮询试图让固定线程持续运行，从而减少这类切换。**

> [!warning] 中断、内核态切换、上下文切换不是同一件事
> - **中断发生**：CPU 暂停当前指令流，进入中断处理入口；
> - **用户态 / 内核态切换**：CPU 的特权级和执行路径发生变化；
> - **上下文切换**：调度器真正换成另一个线程或进程运行。
>
> 一次中断可能最终唤醒另一个线程并触发上下文切换，也可能处理完后直接返回原任务。不能把“发生中断”简单等同于“必然发生一次上下文切换”。

## 3. 中断路径：硬中断、延后处理与批量化

### 3.1 为什么硬中断处理必须尽量短

硬中断到达后，CPU 需要快速确认中断来源并处理最紧急的工作。如果在硬中断上下文里执行大量业务逻辑，会延迟其他中断和正常任务。

因此 Linux 驱动通常遵循这样的思想：

1. **立即完成少量、必须完成的工作**；
2. **把较重的处理延后**；
3. **一次批量处理多个完成项**，摊薄固定开销。

不同子系统的具体机制不同，不能把网络和存储的实现名称混用，但“快速响应 + 延后处理 + 批量化”是共同思路。

### 3.2 NAPI 是网络类比，不是存储接口

NAPI 属于 Linux **网络收包路径**。典型过程：网卡收包 → 硬中断调度 NAPI 并暂时抑制重复中断 → 在 softirq 等上下文按 budget 批量 poll → 队列清空后重新启用中断。

它展示了一个重要的**混合思想**：
- 低负载时，让中断快速通知“有新工作”；
- 高负载时，转为按预算批量轮询，避免每个事件都产生一次中断；
- 工作清空后，再回到中断等待。

> [!note]
> NAPI 可以帮助理解“中断与轮询如何协作”，但 NVMe 完成队列、SPDK poller 和 `io_uring` IOPOLL 都有自己的接口与约束，不能把它们直接称为 NAPI。

### 3.3 中断合并：少叫几次，一次多处理

设备或驱动可以采用 **Interrupt Coalescing（中断合并）**：积累一定数量的完成或等待一个短窗口后再产生中断。

| 合并程度 | 好处 | 代价 |
|:---|:---|:---|
| 较弱 | 单个完成更快被通知 | 中断频率更高，CPU 开销更大 |
| 较强 | 每次中断可批量处理更多完成 | 首批完成可能等待更久，尾延迟可能上升 |

因此中断模式也不是一个固定点，而是一条“CPU 开销—通知延迟”可调曲线。

## 4. Busy Polling 到底在轮询什么

### 4.1 轮询对象通常是完成队列

以队列式设备为例，设备通过 DMA 写回数据和完成队列项（Completion Queue Entry，CQE）。轮询线程反复检查 CQ 的生产进度、phase bit、owner bit 或库暴露的完成接口，发现新完成后再回收描述符并推进队列。

设备 DMA 写数据缓冲 → DMA 写 CQE 并翻 phase bit → poller `load` 下一槽 P 位发现完成 → 处理并回收。轮询线程看到“完成标志”以后，还必须能够正确看到设备先前写入的数据。这与 DMA 一致性、驱动协议和内存顺序有关，前置知识见 [[0.1 CPU Cache Cache Line 与内存屏障]]；结构示意见图 3。

### 4.2 为什么轮询可能降低延迟

中断等待路径中，完成后的软件处理可能要等待：

- 中断投递和处理；
- 延后处理阶段；
- 等待线程被标记为可运行；
- 调度器选择该线程；
- 线程在目标 CPU 上恢复运行。

轮询线程若已在正确的 CPU 上运行，只需在下一次检查时发现完成项，因而通常能减少唤醒和调度造成的等待与抖动。

> [!important]
> 轮询主要优化的是**软件发现完成的路径**。如果瓶颈在介质、PCIe 带宽、队列拥塞、锁竞争或跨 NUMA 访问，单纯改成轮询不一定有效。

### 4.3 为什么轮询会“烧 CPU”

当完成队列为空时，轮询循环仍在执行 load、分支和循环控制。对操作系统来说，这个线程不是 idle，而是持续处于 runnable / running 状态，因此：

- 一个逻辑 CPU 可能长期接近满占用；
- CPU 难以进入深度休眠状态，功耗和温度可能上升；
- 轮询线程会与同核上的其他任务竞争执行资源；
- 若轮询的数据位于远端 NUMA 节点，还会持续制造跨节点访问；
- 错误的多线程共享轮询还可能造成 cache line 抖动。

所以“CPU 使用率高”对于专用 poller 可能是预期现象，关键是确认这些 CPU 周期是否换来了需要的吞吐和尾延迟。

### 4.4 空轮询与有效轮询

可以把 poller 的工作粗略分为：

- **有效轮询**：这一次检查取得了完成项；
- **空轮询**：检查后没有任何完成项。

一个有用的观察指标是：

$$
R_{useful} = \frac{N_{poll\_with\_work}}{N_{poll\_total}}
$$

如果 CPU 长期满载，而绝大多数轮询都没有工作，说明当前负载可能不足以证明永久忙轮询是合理的，应考虑混合或中断模式。

## 5. Context Switch 的成本不只是“保存几个寄存器”

### 5.1 直接成本

一次调度切换可能包含：

1. 进入内核调度路径；
2. 保存当前任务状态；
3. 运行调度器并选择下一个任务；
4. 恢复新任务状态；
5. 返回新任务继续执行。

### 5.2 间接成本往往更重要

切换之后，新任务的工作集未必还在当前核心最热的缓存中，因此还可能出现：

- 指令缓存和数据缓存命中率下降；
- TLB 状态受影响；
- 分支预测器需要重新适应；
- 线程迁移到其他 CPU 后发生更明显的缓存冷启动；
- 共享队列和锁的 cache line 在核心之间移动。

这解释了为什么“测一次切换需要多少时间”不能完全代表它对真实数据路径的影响。

### 5.3 不要背诵固定纳秒数

上下文切换成本受以下因素影响：

- CPU 微架构和频率；
- 同进程线程还是不同进程；
- 是否切换地址空间；
- 工作集大小与缓存状态；
- 是否发生 CPU migration；
- 系统负载、调度策略与内核版本；
- 安全缓解机制和虚拟化环境。

> [!warning]
> “一次上下文切换固定等于某个纳秒数”不是可移植结论。正确做法是：**在目标机器、目标负载和目标绑核策略下测量，并同时观察缓存、迁移和尾延迟。**

## 6. 三种完成通知模型对比

| 维度 | Interrupt | Busy Polling | Hybrid / Adaptive |
|:---|:---|:---|:---|
| 空闲 CPU 消耗 | 低 | 高 | 介于两者之间 |
| 完成发现延迟 | 受中断、唤醒和调度影响 | 通常更短、更稳定 | 短等待可接近轮询，长空闲可接近中断 |
| 低负载效率 | 高 | 容易大量空转 | 通常较好 |
| 持续高负载 | 中断频率可能很高 | 容易批量收割完成 | 可根据繁忙程度调整 |
| 功耗 | 较低 | 较高 | 可控折中 |
| 实现与调优 | 相对常规 | 需要专核、绑核和队列所有权 | 状态切换策略更复杂 |
| 多租户环境 | 通常更友好 | 容易抢占共享 CPU | 取决于资源隔离 |
| 典型场景 | 通用服务器、低占空比任务 | 专用低延迟数据面 | 负载变化明显的服务 |

### 6.1 混合模式的常见策略

一种直观策略是：**完成暂时没到时先短暂轮询；仍无结果则阻塞，等待中断唤醒**（见图 1 右侧 Hybrid 列）。

也可以根据近期负载动态切换：

- 队列持续繁忙：延长轮询或保持 poll mode；
- 多次空轮询：缩短轮询窗口，转入等待；
- 新一轮突发到达：由中断重新唤醒处理路径。

混合模式的关键不是某个固定自旋时长，而是让策略匹配**到达间隔分布、CPU 预算和延迟 SLO**。

## 7. 为什么 thread-per-core 倾向 Busy Polling

### 7.1 基本模型

thread-per-core 通常让一个工作线程固定在一个 CPU core 上，并让它拥有一组本地资源（见图 4 上半）：

线程持续执行事件循环：

```cpp
while (!stop_requested) {
    poll_storage_completions();
    poll_network_completions();
    run_local_tasks();
    flush_submissions();
}
```

SPDK 的 reactor / poller 模型就是这种思想的代表之一。

### 7.2 它为什么有效

| 设计 | 可能带来的收益 |
|:---|:---|
| 线程固定到核心 | 减少 CPU migration，保持缓存和 TLB 局部性 |
| 队列由单线程拥有 | 热路径可减少共享锁和原子竞争 |
| 持续轮询 | 减少睡眠、唤醒和调度切换 |
| 批量处理完成 | 摊薄 MMIO、doorbell、函数调用等固定成本 |
| 消息传递代替共享写 | 降低多个核心反复修改同一 cache line 的概率 |

### 7.3 它没有消灭所有上下文切换

thread-per-core 只是减少热路径中的调度干扰，不代表完全没有切换。以下情况仍可能抢占 poller：

- poller 没有正确绑核；
- 同一 CPU 上还有普通任务或内核线程；
- 设备 IRQ 被投递到 poller 所在核心；
- 发生缺页、阻塞系统调用或等待锁；
- 调度策略、cgroup 配额或虚拟机 steal time 产生干扰。

因此专用轮询核心通常还需要配合：

- CPU affinity；
- IRQ affinity；
- NUMA 内存和设备亲和；
- 避免热路径阻塞；
- 合理的核心隔离与资源预算。

这些拓扑问题与 [[0.5 NUMA CPU 亲和性与内存亲和性]] 直接相关。

### 7.4 为什么不是所有程序都该 thread-per-core

如果负载稀疏、核心昂贵、业务经常执行阻塞操作，或者多个租户必须共享 CPU，那么永久占用一个核心可能得不偿失。thread-per-core 更适合：

- 请求或完成持续到达；
- 延迟和抖动比单核利用率更重要；
- 队列能够清晰分片；
- 可以为数据面预留核心；
- 热路径可以设计成非阻塞。

## 8. 在 io_uring、SPDK 与 RDMA 中如何体现

### 8.1 io_uring：IOPOLL 与 SQPOLL 不要混淆

| 机制 | 轮询对象 | 主要减少什么 |
|:---|:---|:---|
| `IORING_SETUP_IOPOLL` | **I/O 完成状态** | 用轮询完成替代通常的中断完成路径，降低完成发现延迟 |
| `IORING_SETUP_SQPOLL` | **Submission Queue** | 由内核线程轮询提交队列，减少应用提交时进入内核的需要 |

二者分别回答不同问题：

```text
SQPOLL: 应用提交后，内核怎样发现新 SQE？
IOPOLL: 设备完成后，软件怎样发现完成状态？
```

> [!warning]
> - IOPOLL 依赖文件类型、文件系统和块设备支持，通常还涉及 direct I/O 等约束；
> - SQPOLL 会使用内核轮询线程，也需要考虑 CPU 亲和和空闲行为；
> - 开启某个 flag 不代表工作负载必然更快，必须核对 API 约束并实测。

深入用法见 [[2.7 SQPOLL 与 IOPOLL]]，registered buffers 与完成轮询的配合见 [[2.4 polling 与 registered buffers]]。

### 8.2 SPDK：把轮询放到用户态数据面

SPDK 常见设计是：

- 用户态驱动直接操作队列；
- 每个 reactor 绑定核心；
- poller 在所属 SPDK thread 上反复执行；
- 通过消息传递协调跨核工作；
- 热路径尽量避免中断、阻塞和共享锁。

其收益来自一整套协同设计，而不是“写一个 `while (true)`”本身：设备队列、内存、线程、NUMA 和消息所有权必须共同匹配。

### 8.3 RDMA CQ：轮询完成队列

RDMA 数据面经常让线程轮询 Completion Queue（CQ），及时收割 Work Completion。基本取舍与存储 CQ 相似：

- 持续高负载、低延迟：poll CQ 常见；
- 稀疏事件或控制面：事件通知可节省 CPU；
- CQ 与 poller 的核心、NUMA 和 NIC 亲和性会影响效果。

> [!note]
> NVMe CQ、RDMA CQ 和软件环形队列在结构上都可能表现为“生产者写完成、消费者推进队头”，但它们的字段、内存语义和 API 并不相同。类比用于理解，编程时必须遵循各自规范。

## 9. 什么时候应该退回中断模型

满足以下特征时，应优先考虑中断或混合模型，而不是永久忙轮询：

1. **事件稀疏**：大多数 poll 都没有工作；
2. **CPU 核心紧张**：无法为数据面预留专核；
3. **多租户共享**：poller 会挤压其他服务的 CPU 配额；
4. **功耗优先**：系统需要频繁进入低功耗状态；
5. **延迟目标宽松**：业务不需要为很小的完成发现延迟支付整核成本；
6. **热路径会阻塞**：轮询线程仍频繁等待锁、缺页或执行阻塞调用；
7. **负载变化很大**：峰值适合轮询，但长时间低谷更适合休眠。

## 10. 对照实验：不要凭感觉选择

### 10.1 实验目标

比较同一工作负载在以下模式下的差异：

- A：Interrupt；
- B：Busy Polling；
- C：Hybrid / Adaptive（若软件栈支持）。

### 10.2 必须控制的变量

| 变量 | 控制要求 |
|:---|:---|
| 设备与固件 | 使用同一设备和相同配置 |
| I/O 类型 | 读写比例、顺序 / 随机、块大小保持一致 |
| 并发度 | 线程数、队列数、queue depth 保持一致 |
| 数据路径 | direct / buffered、文件系统和库版本保持一致 |
| CPU | 相同绑核、频率策略和 SMT 策略 |
| NUMA | 内存、设备和 poller 位于相同拓扑策略下 |
| IRQ | 记录 IRQ affinity，避免中断随机干扰实验核 |
| 实验阶段 | 相同预热、稳态时长和重复次数 |

实验方法继续参考 [[0.8 Benchmark 基本方法]]。

### 10.3 同时观察四类指标

| 类别 | 指标示例 | 要回答的问题 |
|:---|:---|:---|
| 业务结果 | IOPS、带宽 | 做成了多少工作？ |
| 延迟 | average、p50、p99、最大值 | 完成发现是否更快、更稳定？ |
| CPU 成本 | CPU 利用率、cycles、instructions | 为性能花了多少 CPU？ |
| 调度与中断 | context-switches、cpu-migrations、IRQ / softirq 计数 | 路径是否真的减少了切换和中断？ |

> [!important]
> 如果轮询让 p99 下降，但额外占满多个核心，结论不能只写“轮询更快”，而应写成：**在给定负载和绑核条件下，轮询用多少 CPU 成本换来了多少吞吐或尾延迟改善。**

### 10.4 可直接运行的 Linux 观察脚本

下面的脚本不改变系统配置，只采集指定进程的 CPU、调度和全局中断计数。它适合包在你的 `fio`、存储服务或测试程序外面运行。

```bash
#!/usr/bin/env bash
set -euo pipefail

if [[ $# -lt 2 ]]; then
    printf 'usage: %s <pid> <seconds>\n' "$0" >&2
    exit 1
fi

pid="$1"
duration="$2"

printf '%s\n' '=== process counters ==='
perf stat \
    -e task-clock,context-switches,cpu-migrations,cycles,instructions \
    -p "$pid" \
    -- sleep "$duration"

printf '%s\n' '=== per-thread scheduling sample ==='
pidstat -w -t -p "$pid" 1 3

printf '%s\n' '=== interrupt snapshots ==='
grep -E '(^ *CPU|nvme|mlx|eth|virtio)' /proc/interrupts || true
printf '%s\n' '=== softirq snapshots ==='
grep -E '(^ *CPU|NET_RX|NET_TX|BLOCK|IRQ_POLL)' /proc/softirqs || true
```

工具解释：

- `perf stat`：观察任务时钟、上下文切换、CPU migration、cycles 和 instructions；
- `pidstat -w -t`：区分每个线程的自愿 / 非自愿上下文切换；
- `/proc/interrupts`：查看各 CPU 上的硬中断计数和设备分布；
- `/proc/softirqs`：查看软中断类别在各 CPU 上的累计计数。

> [!note]
> `/proc` 中是累计计数。严谨实验应保存测试前后快照并计算差值，而不是只看某一时刻的绝对值。生产环境运行 `perf` 还可能受权限策略限制。

## 11. 故障案例：轮询已经开启，P99 反而变差

### 11.1 现象

某存储服务从中断模式切换到 busy polling 后：

- poller 所在 CPU 长期繁忙；
- 平均延迟变化不大；
- p99 周期性升高；
- context switches 和 cpu migrations 仍然存在。

### 11.2 容易出现的错误判断

> “轮询理论上不睡眠，所以一定不是调度问题；应该继续增加 poller 数量。”

这可能进一步增加核心竞争和共享队列争用。

### 11.3 排查顺序

1. **检查线程亲和性**：poller 是否在多个 CPU 之间迁移；
2. **检查同核任务**：是否还有普通 worker、内核线程或其他进程共享该 CPU；
3. **检查 IRQ affinity**：NVMe / NIC 中断是否仍投递到 poller 核；
4. **检查 NUMA**：队列内存和设备是否位于远端节点；
5. **检查热路径阻塞**：是否等待互斥锁、分配内存、发生缺页或调用阻塞接口；
6. **检查队列所有权**：多个 poller 是否同时争用同一 CQ 或共享状态；
7. **检查空轮询比例**：负载是否根本不足以支撑永久轮询。

### 11.4 可能根因

假设观测到：

- poller 被固定在 CPU 4；
- 设备 IRQ 也集中在 CPU 4；
- poller 偶尔被中断处理和其他内核工作打断；
- 完成批次积压后，少量请求形成尾延迟尖峰。

此时问题不是“busy polling 原理失效”，而是**轮询核心没有真正隔离，数据路径和中断路径仍在争抢同一个 CPU**。

### 11.5 修复与验证

- 把相关 IRQ 调整到合适的 housekeeping CPU，或按队列重新规划亲和性；
- 确保 poller、队列内存和设备 NUMA 对齐；
- 避免 poller 热路径中的阻塞操作；
- 重新执行 A/B 实验，并同时比较 p99、迁移、切换、中断差值和 CPU 成本。

> [!warning]
> IRQ affinity 的调整会影响整机其他负载。生产环境必须先记录原配置，并在受控实验中逐项修改，不能机械照抄 CPU 编号。

## 12. 常见误区

### 误区一：CPU 100% 就说明程序有问题

对专用 busy poller，CPU 持续繁忙可能是设计结果。真正要问的是：

- 是否跑在预留核心；
- 是否取得足够的吞吐或延迟收益；
- 空轮询比例是否可接受；
- 是否影响其他租户和功耗目标。

### 误区二：Busy Polling 能消灭所有系统调用

轮询的是某个特定阶段。初始化、内存注册、控制面、错误处理或其他路径仍可能进入内核。`io_uring` 的 IOPOLL 与 SQPOLL 也分别优化不同阶段。

### 误区三：没有上下文切换就一定低延迟

即使调度切换很少，仍可能受到以下因素影响：

- cache miss / TLB miss；
- NUMA 远端访问；
- 设备队列拥塞；
- PCIe 或内存带宽竞争；
- SMT sibling 干扰；
- 中断和固件行为。

### 误区四：轮询线程越多越好

poller 数量超过硬件队列和可用核心后，可能引入共享 CQ 竞争、cache line 抖动和调度干扰。应根据队列分片、核心预算和实际扩展曲线决定。

### 误区五：只看平均延迟

中断、调度和批处理经常影响的是抖动与尾部。平均值相近时，p99 仍可能完全不同。指标定义见 [[0.7 性能指标 IOPS 带宽 延迟 P99]]。

## 13. 关键结论

1. **Interrupt 是“被动通知”**：空闲 CPU 成本低，但完成处理可能经过中断、唤醒和调度路径；
2. **Busy Polling 是“主动发现”**：用持续 CPU 时间换取更短、更稳定的完成发现延迟；
3. **中断不等于上下文切换**：两者可能关联，但属于不同机制；
4. **Context Switch 的成本包含直接调度成本和缓存局部性损失**，不能背诵固定数字；
5. **NAPI 是网络中的中断—轮询混合机制**，只能类比，不能冒充存储接口；
6. **thread-per-core 通过绑核、单线程队列所有权和非阻塞 poll loop 减少热路径干扰**；
7. **IOPOLL 轮询 I/O 完成，SQPOLL 轮询提交队列**，二者优化的不是同一阶段；
8. **低负载、CPU 紧张、多租户或功耗优先时，应考虑中断或自适应混合模式**；
9. **最终选择必须用 IOPS、p99、CPU、context switches、migrations 和 IRQ 差值共同验证。**
