# 4.6 语法错误与错误恢复

Parser 除了识别合法输入，还需要说明错误，并在可能时继续分析后续代码。恢复的目的是获得更多可靠诊断，不是证明错误程序已经变正确。

## 1. 错误发生位置与检测位置可能不同

| 情况 | 典型处理阶段 |
|---|---|
| 字符串没有结束引号 | 词法分析 |
| 两个二元运算符相邻，缺少操作数 | 语法分析 |
| 调用一个不可调用的整数变量 | 语义分析 |
| 运算写错但仍满足语言规则 | 可能需要测试或进一步分析发现 |

阶段是职责划分，不保证实现按同样边界报错，也不意味着所有语义问题都能静态判定。

例如前一行漏写分号，Parser 可能直到下一行的类型关键字才发现无法继续。报告指向下一行，不代表真正的笔误就在那个 Token 上。

一次遗漏还可能破坏后续声明的识别，产生一串“变量未声明”等级联错误。因此诊断应优先说明最早发现的结构问题，避免恢复过程制造大量误导信息。

## 2. 恐慌模式：找到可继续分析的位置

恐慌模式（Panic Mode）通常放弃损坏的局部结构，跳过一段 Token，直到能与外层分析重新衔接。

基本步骤是：报告错误；退出或弹出不再有效的分析上下文；跳过不适合继续处理的 Token；在同步点恢复。

同步点取决于所在结构。常用分号、右括号、右花括号，也可以根据 FIRST/FOLLOW 等集合选择合适的 Token，并非只能使用定界符。是否消费同步 Token，由恢复函数与调用者的约定决定。

## 3. 一个按语句恢复的例子

假设语句以分号结束，表达式只支持二元加法，输入为：

```text
print(1 + + 2); print(3);
```

采用“本条语句损坏就跳到语句末尾”的策略：

| 步骤 | 行为 |
|---|---|
| 读到第二个 `+` | 当前期待操作数，报告错误 |
| 放弃当前 print 语句 | 返回能够处理下一条语句的分析层次 |
| 跳过损坏部分 | 跟踪当前括号层次，越过 `+ 2)` |
| 到达当前语句分号 | 消费分号，结束本次恢复 |
| 继续分析 | 正常处理 `print(3);` |

这不是自动把第一条语句修正为 `print(1 + 2)`。可以为它生成错误节点，也可以跳过它，但必须保留“本次编译存在错误”的状态。

不能机械地遇到第一个分号就停：若分号位于嵌套结构内部，它可能不是当前外层语句的边界。恢复也应正确处理 EOF，并保证消费输入或退出当前上下文，避免在同一 Token 上无限报错。

## 4. 错误产生式与局部修复

| 策略 | 做法 | 代价或风险 |
|---|---|---|
| 恐慌模式 | 跳过损坏结构，在同步点继续 | 被跳过部分的其他错误可能漏报 |
| 错误产生式 | 显式识别某些常见错误形式，给出针对性诊断 | 新规则可能引入歧义或分析冲突 |
| 局部修复 | 尝试插入、删除或替换少量 Token | 合法修复不一定符合作者意图 |

例如用额外规则识别缺少乘号的 `5 x`，可以给出“是否漏写乘号”的提示。这不代表语言规范正式允许省略乘号：错误分支可以仅为诊断而存在，并继续将输入标为错误。

如果直接加入宽泛的 $E\to EE$，`5 x + y` 可能出现新的分组歧义，不能只看它是否接纳了一个错误例子。

## 5. 编辑距离不能决定程序员意图

输入 `1 + 2 ) * 3` 可以做一次编辑得到不同合法表达式：

| 修改 | 结果 | 值 |
|---|---|---|
| 删除右括号 | `1 + 2 * 3` | 7 |
| 在开头插入左括号 | `(1 + 2) * 3` | 9 |
| 在 2 前插入左括号 | `1 + (2) * 3` | 7 |

修改次数相同，含义却不同。因此，寻找最小编辑距离不能代替对意图的判断。修复建议可以交给用户选择；编译器也可以在内部做有限恢复，但必须区分“用于继续分析的假设”和“用户确认的正确程序”。

## 6. 恢复后的状态管理

对表驱动 LR 分析器，恢复可能包含退栈、移进专门的错误符号、丢弃前瞻 Token；递归下降则可以通过返回错误结果和专门的跳过函数恢复。算法不同，恢复位置和保留的信息也会不同。

后续检查应识别错误节点，尽量避免对同一损坏结构反复报错。解析流程到达文件末尾，甚至解析函数返回“完成”，也不能代替错误计数判断。

具体诊断次数取决于恢复规则。验证恢复行为时，应检查：第一条错误是否清楚、能否继续识别后续正确语句、是否出现级联错误，以及是否能够终止。
