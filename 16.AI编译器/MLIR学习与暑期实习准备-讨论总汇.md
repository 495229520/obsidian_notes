# MLIR 学习、Lab 与暑期实习准备：讨论总汇

> 整理日期：2026-10-21（北京时间）  
> 目标时间：2027 年 3 月前后申请暑期实习；具体批次、届别和到岗条件以招聘公告为准。  
> 文档性质：本轮讨论的决策记录与执行建议。课程设计、时间预算和求职判断均不等于已验证结果。

## 1. 当前最重要的结论

1. **MLIR／AI 编译器值得作为一个求职方向尝试，但不需要现在就押上全部学习时间。** 先用四周形成一个独立修改、带测试的 Pass，再依据实际进展决定投入。
2. **完整培养路线与实习投递门槛分开。** 几百小时的长期计划不是申请实习前必须完成的清单。
3. **2027 年 3 月前的目标是一项能讲透的编译器项目。** 优先完成少量算子、校验、Lowering、CPU 执行和测试；不把 NPU 实机、完整量化、自研内存规划器或工业 PR 同时列为必修。
4. **现阶段无需新增硬件。** 使用已有主机和 SSD，先完成 CPU 开发与实验；真实加速器需求出现后再考虑借用、租用或购买。
5. **Lab 有学习和简历价值，但价值来自独立贡献。** 运行脚本、复现教程、独立扩展、工业缺陷修复，分别能证明不同层次的能力。
6. **存在对应实习岗位，但不能保证录用。** 当前尚未通过独立代码和面试检查评估你的编译器能力；应通过项目里程碑和投递反馈来判断，而非依赖保证。

## 2. 你的起点、诉求与现实约束

### 2.1 已有基础与兴趣

- 有 C++、Linux 学习基础，并有机器人／数据中台相关工程经历。
- 对 MLIR、张量优化、Lowering、硬件映射、片上内存及数据搬运感兴趣。
- 希望学习服务于实习和就业，而不是只积累课程数量。
- 曾尝试观看 TPU-MLIR 分享，但其中默认的编译器和 MLIR 基础过多，导致理解困难。
- 零碎时间适合概念预习；实际写 Pass、调试 Lowering 和分析内存，需要连续操作时间。

不能据此默认已经熟练掌握编译原理、Python、线性代数、深度学习、CUDA 或所有系统工程技术。这些应按实验所需逐项补齐。

### 2.2 时间与选择风险

你担心投入数月后仍然没有投递机会，也担心长期计划把自己锁在一个方向。你提出的近期约束是：即使 2026 年不实习，2027 年 3 月也要开始申请暑期实习。

从 2026-10-21 到 2027 年 3 月初约有 19 周；若 11 月中旬才正式投入，约有 15 周。这是日历窗口，不是可全部用于编译器学习的时间。

**处理原则：限制初期专项投入，保留通用求职准备，用阶段成果决定后续投入。** 如果已经开始学习，可以把现有成果计入里程碑，无需等到某个日期重新开始。

## 3. 付费课程的评审结论

以下归纳来自用户提供的 Pro 分析及本轮讨论，不是对授课质量、全部作业或课后服务的独立审计。

### 3.1 值得保留的内容

原课程更偏 TPU-MLIR 工具链、量化和 NPU 部署实践。其有价值的主题包括：

- 从模型前端到 Top／Tpu、Lowering、LayerGroup 和模型产物的整体流程。
- DMA、局部存储、算子分组与内存编排。
- INT8 校准、敏感层分析、混合精度回退与 Profiling。
- 真实设备部署，以及推理、预处理、后处理的流水线组织。

### 3.2 原六个 Lab 分别证明什么

| 原课程 Lab | 课纲中的任务 | 主要能力证据 |
| --- | --- | --- |
| Lab1 | 手写冗余算子消除 Pass | 开始实现编译器变换 |
| Lab2 | ResNet50 CPU／NPU 对比 | 配环境、运行模型、测量 |
| Lab3 | ONNX→MLIR→BModel | 理解转换流程；研发深度取决于是否改源码 |
| Lab4 | 量化、精度分析与回退 | 模型适配和量化调试 |
| Lab5 | YOLO 视频流水线 | 并发、队列、部署工程 |
| Lab6 | Qwen 聊天机器人 | 大模型部署闭环 |

只有 Lab1 在所提供课纲中明确写了手写编译器 Pass。不能因此断言其他实验没有源码开发，但需要查看完整任务书才能确认。

例如，Lab3 如果要求保存各阶段 IR、定位对应 Pass、修改转换规则并补回归测试，就能提供研发训练；只运行转换命令则主要证明工具使用能力。

### 3.3 需要补齐的基础

| 基础 | 为什么需要 |
| --- | --- |
| IR、SSA、定义与使用、基本块、支配关系 | 看懂程序表示与值的可用范围 |
| Operation、Value、Region、Block、Type、Attribute | 看懂 MLIR 对象与 C++ API |
| 算子语义、Verifier、Trait、Interface | 判断合法输入与可实施的变换 |
| 副作用、别名、变换合法性 | 避免优化破坏程序语义 |
| tensor、linalg、scf、memref | 连接张量计算、循环和实际存储 |
| Bufferization、所有权与释放责任 | 理解复制、复用和内存生命周期 |
| lit、FileCheck、数值回归 | 同时验证 IR 结构与执行结果 |

### 3.4 是否值得付费

目前缺少价格、完整作业、批改样例、教师反馈与设备资源细节，不能直接下购买结论。应索取：

1. 完整 Lab1 任务书与学生作业样例。
2. 基础课和 Lowering／LayerGroup 的试听。
3. 是否审查学生自己的 Pass、转换代码及测试。
4. NPU 型号、SDK、工具版本、模型规格。
5. 机时、排队情况、访问期限及结课后复现条件。
6. 价格、课时单位与课外投入要求。

公开文档串讲和现成脚本的价值有限；稳定设备资源、源码级排错和持续代码评审，才可能构成值得付费的服务。

Pro 文本还指出：BF16 是浮点格式而非校准算法；“XLA 局限于谷歌生态”的表述过于笼统；课纲时长相加为 84 但单位不明，不能直接当作 84 小时。上述属于课纲表述核查项，不能单独据此否定授课质量。

## 4. Lab 的来源：哪些是公开依据，哪些是教学设计

**这套 Lab 是参考公开技术体系、结合课纲后重新组织的教学方案，不是某个培训班原版作业集，也不是已经全部实现并跑通的成熟课程。**

| 内容 | 来源与状态 |
| --- | --- |
| TPU-MLIR 流程、量化、LayerGroup、NPU 部署 | 来自课纲主题，并有公开工业项目支撑 |
| Dialect、Verifier、重写、Lowering、LLVM 执行 | 有官方教程、源码和测试 |
| Bufferization、分块与融合 | 有官方机制和示例；具体任务重新组织 |
| MiniNN 名称、四类算子、小型网络、受限 ONNX 导入器 | 教学设计，需要实际实现与验证 |
| 64 KiB 教学容量、独立内存规划器与检查器 | 简化的自定义实验，不代表真实硬件 |
| 工业缺陷修复或优化 PR | 后期选题方向；问题尚未复现前不能当作确定任务 |
| 各 Lab 小时数 | 主动学习预算估计，不是实测完成时间 |

每个进入正式执行的 Lab，应补齐六项内容：参考仓库、固定版本、源码或测试位置、可运行基线、个人修改范围、验收命令与标准。只有题目和时间估计，还不能称为准备完成的任务书。

## 5. 可依托的公开项目与材料

### 5.1 官方 Toy：核心主线参考

- [官方教程](https://mlir.llvm.org/docs/Tutorials/Toy/)
- [GitHub 源码](https://github.com/llvm/llvm-project/tree/main/mlir/examples/toy)

覆盖自定义操作、Dialect、模式重写、Interface、形状推导、分阶段 Lowering 与 LLVM 代码生成。建议先完成 IR 基础，再读懂并修改一段 Toy 实现。

Toy 的示范路径包含 Affine Lowering；它不等于我们设计的 ONNX→MiniNN→Linalg 路线。MiniNN 是利用这些机制开展的独立综合练习，不能称为 Toy 官方实验。

### 5.2 MLIR For Beginners：辅助理解 C++ 实现

- [j2kun/mlir-tutorial](https://github.com/j2kun/mlir-tutorial)

配套文章包括构建、运行与测试 Lowering、第一个 Pass、TableGen、Dialect、Trait、折叠、Verifier、Canonicalizer、Dialect Conversion、LLVM Lowering、数据流分析与 PDLL。

建议围绕当前问题选读，不必与 Toy 同时完整学两遍。运行时使用该仓库要求的依赖；不要默认不同教程可共用任意 LLVM 版本。

### 5.3 官方 Transform Dialect：优化阶段参考

- [官方教程](https://mlir.llvm.org/docs/Tutorials/transform/)

包含组合已有变换、扩展新的 Transform 操作和独立工程接入。官方要求先具备 MLIR 基础。先复现示例，再增加尾块尺寸、不同参数、正确性对照与性能测量。

### 5.4 Bufferization 与测试材料

- [Bufferization](https://mlir.llvm.org/docs/Bufferization/)
- [Dialect Conversion](https://mlir.llvm.org/docs/DialectConversion/)
- [MLIR Testing Guide](https://mlir.llvm.org/getting_started/TestingGuide/)
- [Understanding the IR Structure](https://mlir.llvm.org/docs/Tutorials/UnderstandingTheIRStructure/)
- [LLVM Programmer’s Manual](https://llvm.org/docs/ProgrammersManual/)

Bufferization 解决 tensor 到 memref 的转换、别名和原地更新等问题；教学片上内存规划器是另一层练习，不能混为一谈。One-Shot Bufferize 本身不负责缓冲区释放，需要配套释放流程或明确外部所有权。

### 5.5 TPU-MLIR：后期工业案例

- [sophgo/tpu-mlir](https://github.com/sophgo/tpu-mlir)

这是面向算能 TPU 的真实编译器项目，但不是零基础分周作业仓库。顺序应是：跑通一个受支持例子、跟踪一个操作、建立最小复现，再选择范围明确的问题修改。

不提前保证存在适合初学者的 LayerGroup 缺陷，也不保证优化一定有收益。选题需要源码阅读和基线实验。

### 5.6 资料范围控制

近期以 Toy 为主、MLIR For Beginners 为补充；优化阶段加入 Transform／Bufferization；后期再进入 TPU-MLIR。暂不同时铺开 TVM、IREE、Triton、Torch-MLIR 等多个大型工程。

## 6. 长期路线与 MiniNN 项目

长期顺序为：通用 MLIR 基础 → 小型 CPU 编译闭环 → 优化与内存分析 → 工业编译器源码实践 → 按岗位需要进行硬件专项。

### 6.1 MiniNN 的初始边界

- 静态形状、二维张量、FP32。
- Constant、MatMul、Add、ReLU。
- Add 初期采用等形状相加；不支持的广播明确报错。
- 长期完整链路：受限 ONNX → MiniNN → Linalg 等标准方言 → 缓冲区与循环 → LLVM → CPU。
- 自己实现算子语义、校验、必要转换、测试和错误诊断；复用上游基础设施和代码生成。

原示例网络：1×16 输入乘 16×32 权重，加偏置并 ReLU，再乘 32×8 权重得到 1×8 输出。若使用通常的一维偏置，需显式支持广播或在构图时变成受支持的形状，不能悄悄超出等形状 Add 的定义。

此前讨论记录的环境基线是 LLVM／MLIR 20.1.8 与 TPU-MLIR v1.30.2、BM1684X 目标。它们用于区分上游教学工程和厂商工程，并非推荐追逐最新版本，也不表示当前机器已经验证成功。不同项目各自固定依赖，实际执行前检查构建与运行条件。

### 6.4 后期选修

| 选修 | 内容 | 原版估计 |
| --- | --- | --- |
| N1 | 真实 NPU 小模型精度、设备时间与端到端时间对照 | 12—20 小时 |
| N2 | YOLO 视频流水线、有界队列、吞吐／延迟／丢帧 | 16—24 小时 |
| N3 | Attention、KV Cache、受支持 LLM 部署 | 20—36 小时 |

估计以已有匹配硬件、工具和受支持示例为前提。编译器研发优先考虑 N4；机器人边缘部署可优先 N1／N2。N3 需分别测量 prefill 与 decode，不能只报告“能聊天”。这些均可放在首次实习投递之后。

## 7. 面向 2027 年 3 月的精简执行计划

### 7.1 最小项目交付

以一个小型、基于 MLIR 的张量编译器为主项目：

1. 只支持少量静态 FP32 算子，可先直接输入自定义 MLIR，省去 ONNX 前端。
2. 自己实现操作校验与关键 Lowering。
3. 复用上游机制完成 CPU 执行。
4. 与独立参考实现进行数值对照。
5. 覆盖错误形状、不支持输入和必要边界条件。
6. 深入讲清一次自己定位的缺陷，或一项真实测量的优化。

### 7.2 明确移出投递前必修

- ONNX 前端。
- 完整量化 IR、整数内核和混合精度 Lowering。
- NPU 实机和 GPU 专项。
- 独立片上内存规划器。
- 必须被上游合并的工业 PR。
- 完整 YOLO／Qwen 应用。

如进度充裕，可择一扩展；不同时加回所有项目。

### 7.3 日历检查点

| 时间 | 预期结果 | 决策 |
| --- | --- | --- |
| 2026-10-21—11 月上旬 | 保留 C++、Linux、算法、已有项目准备；少量 MLIR 预习 | 已有成果可直接计入，不重启路线 |
| 11 月中旬—12 月上旬 | 跑通公开示例，独立改一个 Pass，补正反测试 | 判断理解进展与兴趣 |
| 12 月中旬—2027 年 1 月中旬 | 少量算子的 CPU 闭环，有数值与错误测试 | 形成第一版简历；困难则减算子和功能 |
| 1 月中旬—2 月中旬 | 深入一个缺陷或优化；整理复现和讲解 | 停止扩张范围，补基础 |
| 2 月起—3 月 | 关注岗位、核对资格、按开放时间投递 | 边投边完善，不等整套课程毕业 |

以上是检查节点，不是保证完成的工期。“3 月投递”是个人目标，不是所有公司的统一开放日期。

### 7.4 四周试行机制

前四周建议每周投入约 8—12 小时 MLIR 专项，保留其他求职准备。四周后检查：

- 能否解释一个小 IR，并独立修改一条规则？
- 遇到错误时，能否开始缩小问题，而非完全依赖外部答案？
- 是否愿意继续阅读源码、调试和验证？

进展慢时先区分基础、环境、任务范围和投入时间的问题。必要时缩小任务或降低优先级，不因为已投入时间而被迫继续。四周未完成某个目标，不自动等于不适合这个方向。

| AMD 9700X＋48GB 主机 | LLVM／MLIR 构建、C++ 开发、CPU 实验 | 主力开发机，不需先升级 |
| 已购 2TB SSD | WSL、源码、构建、模型、容器 | 安装并确认空间及路径 |
| GTX970 | 日常显示 | 不为主线换卡 |
| MacBook Air | 阅读、编辑、小实验、SSH | 继续使用 |
| i7＋16GB＋GTX1660S Ubuntu 机器 | 备用原生 Linux 环境 | 不需先升级 |
| NPU 开发板 | 后期真实设备部署与性能测量 | 暂不买 |

配置建议：

- WSL 虚拟磁盘放新 SSD；源码和构建目录放 WSL 内部 Linux 文件系统。
- 检查 WSL2 内存配置：官方默认上限为 Windows 总内存的 50%；48GB 主机默认约 24GB。可视 Windows 占用考虑约 32GB，并非课程硬性要求。
- 初期构建所需工具与本机目标，采用适当的 Release／assertions 配置，限制编译与链接并发。
- 先记录一次最小构建的峰值内存、磁盘与耗时，再决定是否升级。

CPU 项目不要求购买显卡。TPU-MLIR 的源码和受支持模拟流程能否运行，取决于匹配依赖；模拟器功能验证不能证明实机性能。真实 NPU 延迟、吞吐、功耗和 DMA 重叠需要匹配硬件。BM1684X 目标不能由任意“带 NPU 的开发板”替代。

## 9. Lab 的简历价值与写法

### 9.1 不同成果的证据强度

| 成果 | 简历价值 |
| --- | --- |
| 配环境、看 IR、原样运行教程 | 必要基础，通常不单列项目 |
| 简单加零消除 Pass | 可写项目细节，独立成项目偏薄 |
| 自定义操作、校验、Lowering | 核心开发能力证据 |
| 模型／IR 到 CPU 执行闭环 | 可作为主要项目 |
| 有独立验证的分块、融合或内存优化 | 适合深入面试 |
| 工业项目中可复现的问题修复 | 有测试与评审记录时更有说服力 |
| 按脚本部署 YOLO／Qwen | 主要证明部署能力 |

### 9.2 项目进入简历的五个条件

1. 明确自己写的代码和复用的上游部分。
2. 有实际运行结果与独立参考对照。
3. 有负测试、错误诊断和边界条件。
4. 至少深入解决一个问题，能说明原因与取舍。
5. 能现场解释并修改：形状或使用关系变了，能判断变换是否合法。

AI 可以辅助编码，但不能替代对语义、失败条件和调试过程的掌握。

### 9.3 推荐的最终项目组织

- **项目 A：基于 MLIR 的小型张量编译器。** 描述支持范围、操作校验、转换链、CPU 执行、测试及个人贡献。若没有 ONNX 前端，不写支持 ONNX。
- **项目 B：TPU-MLIR 的具体修复或扩展。** 这是后续可选增强，围绕一个明确问题展示复现、定位、补丁与测试；不影响先投实习。

不要把十几个 Lab 编号全部堆在简历中。复现教程如实标注来源；PR 未合并就写未合并或评审中；不要把上游已有功能写成自己实现。

性能结果须有真实设备、输入、精度、线程数、计时范围、预热和重复测量条件。教学规划峰值下降只能写规划空间改善；模拟器通过只能写功能验证，不能写真实 NPU 加速。
