# AI 컴파일러 및 NPU 학습 계획

MLIR과 NPU 컴파일러 개발을 위한 개인 학습 계획이다. 주요 학습 과제는 MLIR 기반 텐서 컴파일, 타일링과 연산 융합, 온칩 메모리 계획, 실제 컴파일러 코드의 개선이다. C++, Python, 컴파일러 이론은 과제 수행에 필요한 범위부터 보완한다. IR/SSA와 MLIR 기초를 이해한 뒤, 범위가 작고 재현 가능한 프로젝트를 완성하고 실제 컴파일러 코드 분석으로 넘어간다.

> [!info] 계획과 완료 기록
> 학습 진도와 상세 실험 기록은 Trellis 작업에서 관리한다. 이 문서에는 별도의 완료 체크리스트를 두지 않는다. 프로젝트 B는 사용할 저장소, 타깃, 검증 환경을 정한 뒤 시작한다.

컴파일러 학습 시작일은 2026년 10월 18일이다. C++ 숙련, 알고리즘 문제 풀이, 다른 과목의 수료를 기다리지 않는다. xv6/QEMU는 이번 로드맵에서 제외한다. 기존 C++, Linux, 알고리즘 및 로봇·데이터 플랫폼 프로젝트 자료를 필요할 때 활용하고, 스토리지·GPU·RDMA 자료도 문제 해결에 필요한 부분만 찾아본다.

## 프로젝트와 오픈소스 기반

| 프로젝트 | 활용 기반 | 직접 구현할 부분 | 1차 산출물 |
|---|---|---|---|
| A: MLIR 기반 텐서 컴파일 및 메모리 계획 실험 시스템 | [LLVM/MLIR standalone](https://github.com/llvm/llvm-project/tree/llvmorg-20.1.8/mlir/examples/standalone), LLVM 20.1.8 | MatMul/Add/ReLU의 ODS 정의와 Verifier, C++ 재작성 및 로워링, 타일링·융합, 생존 기간 분석과 교육용 온칩 메모리 계획 | 독립 저장소, 실행 테스트, 최적화 전후 비교, 재현 명령 |
| B: MLIR/NPU 컴파일러의 자원 계획 또는 진단 개선 | 접근 가능한 공개 컴파일러나 SDK를 선정한 뒤 버전 고정 | 실제 실행 경로의 C++ 정책 또는 진단 수정, 독립 회귀 입력, 기능 및 계획 결과 비교 | 수정 전 기준 결과, 패치, 실행 경로 근거, 검증 결과와 한계 |

개인 저장소 이름은 `mini-npu-compiler-lab`, `mlir-resource-planning-study` 등을 사용할 수 있다. 각 Lab은 순차적으로 구현해야 한다. 오픈소스는 프레임워크와 예제를 제공하지만 이 계획 전체에 대응하는 완성된 정답 묶음은 없다.

프로젝트 A는 $Y=\operatorname{ReLU}(AB+C)$에서 시작한다. 정적 형상의 2차원 f32 텐서를 사용하며, C와 AB의 형상은 같아야 한다. 초기 버전은 브로드캐스팅을 지원하지 않는다. 먼저 CPU 기계어로 변환해 정확하게 실행한 뒤 최적화를 추가한다. 온칩 메모리 계획은 교육용 장치 모델과 CPU 재실행으로 검증하고, 용량·할당·데이터 전송량을 기록한다.

프로젝트 B는 모델 입력 → 상위 수준 IR → 타깃별 IR → 연산 그룹화·자원 계획 → 실행 산출물의 경로부터 확인한다. 이 경로와 명칭은 선택한 도구에 맞춰 구체화한다. 작은 그래프와 양자화 결과를 검증한 다음 소스를 수정한다. 시뮬레이터가 제공되면 기능 검증에 활용할 수 있으나, 실제 칩의 지연 시간·처리량·전력은 해당 하드웨어에서 측정해야 한다.

### 프로젝트 B를 이력서에 기재하는 기준

L7의 첫 과제로는 기본값이 비활성화된 교육용 메모리 예산 상한을 검토할 수 있다. 이를 통해 실행 경로 추적, 용량 산정 기준, 타일 분할 탐색, 실패 시 대체 경로를 연습한다. 옵션 추가, 인자 전달, 로그 출력만으로는 개발 기여를 충분히 설명하기 어렵다.

최종적으로는 유효한 타일 분할 후보 선택, 자원 부족 원인을 특정하는 진단과 회귀 테스트, 실제 계획·정확성 오류 수정, 가중치 상주 또는 버퍼 재사용 정책 중 한 가지를 목표로 한다. 수정 전후의 결과와 비용을 함께 제시한다. 성능 개선이 관찰되지 않았다면 그대로 기록한다. 업스트림 PR 병합은 필수 조건이 아니다.

구현 가능성은 소스 분석과 실험으로 판단한다. L7 기본 범위를 넘어가는 작업 시간은 별도로 산정한다. 지원 시점까지 실질적인 패치를 만들지 못했다면 프로젝트 A를 우선 제시한다. 소스 코드를 읽은 경험을 실제 제품 개발 성과로 기재하지 않는다.

### 입문 자료와 학습 순서

첫 주에는 Mac에서 컴파일 과정과 AST/IR → SSA·기본 블록·CFG → MLIR의 Operation·Value·Region·Block → Dialect·Type·Attribute 순서로 학습한다. 읽은 뒤에는 짧은 IR에 주석을 달거나 예제를 손으로 추적한다. 영상 시청 시간만으로 이해도를 판단하지 않는다.

[MLIR Beginner-Friendly Tutorial](https://github.com/AlexandreSinger/mlir-beginner-friendly-tutorial)의 [1편](https://youtu.be/Uno_XhtkT5E)을 먼저 보고, [IR 구조 튜토리얼](https://mlir.llvm.org/docs/Tutorials/UnderstandingTheIRStructure/)로 개념을 확인한다. Toy [1장](https://mlir.llvm.org/docs/Tutorials/Toy/Ch-1/)과 [2장](https://mlir.llvm.org/docs/Tutorials/Toy/Ch-2/)에서는 AST에서 MLIR로 변환하는 과정과 Dialect 예제를 읽는다. 둘째 주에는 [3장의 재작성](https://mlir.llvm.org/docs/Tutorials/Toy/Ch-3/)과 Beginner-Friendly [2편](https://youtu.be/l0O4Vbc3l5c)의 로워링 설명을 선별해 읽는다.

첫 2주에는 Beginner-Friendly의 Demo 0 빌드 절차를 생략한다. 해당 LLVM 서브모듈은 프로젝트 A의 20.1.8과 별개이므로 실제 실행 시 버전을 확인한다. 읽기와 수기 IR 작성은 실행 검증으로 간주하지 않는다. 전체 컴파일러 이론 과정이나 파서 구현을 입문 전제 조건으로 두지 않는다.

### 수학·알고리즘은 실험에 맞춰 보완

수학 및 알고리즘 기초를 단계별 참고 자료로 활용한다. 첫날은 행렬 곱의 형상과 ReLU를 읽고, 둘째 주에는 행렬 참조 구현과 함께 레이아웃·부동소수점 오차를 학습한다. 이후 의존성, 인덱스, 마지막 타일의 경계, 생존 기간, 양자화를 해당 Lab에서 보완한다. 초기 MatMul/Add/ReLU 추론 컴파일러에 미적분이나 자동 미분을 선수 과목으로 요구하지 않는다.

| 적용 단계 | 함께 학습할 내용 | 간단한 이해도 확인 |
|---|---|---|
| L0–L1 | 행렬 곱, 형상, 레이아웃, 허용 오차, SSA | 작은 행렬을 손으로 계산하고 참조 결과와 비교 |
| L2–L3 | 연산 의미, 인덱스 매핑, 버퍼와 소유권 | 잘못된 입력 거부와 CPU 실행 결과 확인 |
| L4 | 타일 경계, 의존성, 리덕션과 융합 | 나누어떨어지지 않는 크기에서도 정확성 확인 |
| L5 | 생존 기간, 구간 중첩, 정렬과 용량 | 버퍼 충돌 검사와 CPU 재실행 |
| L6–L7 | 양자화, 자원 제약, 탐색과 진단 | 작은 입력의 오차 및 변경 전후 동작 비교 |

표는 단계별 참고 자료다. 실제 일정과 완료 여부는 Trellis 작업에 기록한다.

[Groverkss/mlir-tutor](https://github.com/Groverkss/mlir-tutor)의 1·2·4장에서는 빈칸을 채우며 ODS, 로워링, 루프, 타일링·융합을 연습할 수 있다. ## 투입 시간과 단계별 산출물

컴파일러 학습의 잠정 투입량은 하루 4–5시간, 주 6일이며 나머지 하루는 조정용으로 둔다. xv6를 제외했다고 일일 투입량을 자동으로 늘리지 않는다. 2주 후 실제 투입 시간과 검증 결과로 조정한다.

장기 학습·구현 시간의 추정치는 직접 학습·구현하는 시간 386–530시간, 중간값 458시간이다. 주간 가용 시간에서 15%를 조정 여유로 두면 약 20.4–25.5시간/주이며, 약 15–26주, 중간값 약 20주에 해당한다. 각 단계의 검증을 통과한 뒤 다음 단계로 진행한다. 프로젝트 B는 대상을 정한 뒤 예상 시간과 검증 조건을 다시 산정한다.

| 단계 | 산출물 |
|---|---|
| L0–L1 | 행렬 참조 구현, 빌드 가능한 프로젝트, 첫 제한적 Pass |
| L2–L3 | Dialect, 로워링, 실제 CPU 실행 및 회귀 테스트 |
| L4 | 타일링·융합과 전후 비교, 프로젝트 A 초판 공개 |
| L5 | 생존 기간 분석, 온칩 메모리 계획, 검사·재실행으로 A 보완 |
| L6–L7 | 선정한 타깃의 변환·양자화·기능 검증, B의 실질적 패치 |

L2 중에 후보 NPU 도구의 환경과 작은 그래프를 미리 확인하며, 투입 시간은 L6/L7 예산에 포함한다. 수업이나 인턴으로 시간이 줄면 A의 재현 가능한 산출물을 우선 확보하고 B는 실제 완료 범위에 맞춘다.

첫 주에는 Mac에서 IR/SSA와 짧은 MLIR 예제를 이해한다. 둘째 주에는 행렬 참조 구현, 독립 NumPy 비교, 경계 테스트, Pass·재작성·로워링 읽기를 진행한다. LLVM 빌드, standalone 프로젝트, 첫 C++ Pass는 셋째 주 이후로 배치한다. 시작 전에 9700X PC의 WSL2 Ubuntu와 실제 가용 자원을 확인한다. L0 완료는 실제 프로젝트 검증을 통과해야 인정한다. 후속 단계의 주 단위 일정은 2주 회고 후 다시 산정하며, 입문 읽기는 기존 L0/L1 예산에 포함한다.

첫 주에는 Mac으로 학습하고 SSD를 구매했다는 이유로 전체 LLVM/MLIR 설치를 앞당기지 않는다. 이후 WSL 가상 디스크는 새 SSD에 두고 소스·빌드 디렉터리는 WSL 내부 Linux 파일 시스템에 둔다. 프로젝트 A에 필요한 환경부터 준비한다. WSL의 실제 가용 메모리와 디스크를 확인한다. 100–150GB는 전체 로드맵의 디스크 계획 여유분이며, 입문 최소 요구량이나 실측 사용량이 아니다. 이번 단계에서는 Apple Neural Engine을 NPU 타깃으로 삼지 않는다.

학습 자료와 오픈소스 도구는 무료로 확보할 수 있으며 기존 장비로 시작한다. 2TB SSD는 구매한 상태이며 실제 지출액은 별도로 기록한다. 현재 GPU나 추가 장비 구매 계획은 없다. 전기요금과 기존 구독료는 별도로 계산한다.

### GPU 임대를 검토할 시점

L0–L3의 IR/SSA, Dialect, Pass, CPU 실행은 기존 장비로 수행한다. L4의 타일링·융합을 마친 뒤 GPU 실험 질문을 정리하고, 이 계획에서는 L5 메모리 계획까지 검증한 후 첫 단기 임대를 검토한다. GPU는 선택 과제이며 NPU 컴파일러 학습이 GPU 임대를 자동으로 요구하지는 않는다.

임대 전에 프로젝트 A를 직접 실행하고 타일링·융합·데이터 재사용·버퍼 생존 기간을 설명할 수 있어야 한다. 다음 항목도 준비한다.

- 독립 CPU/NumPy 참조 구현, 수치 허용 오차, 비정방 행렬·마지막 타일 등 경계 테스트.
- 타일 크기에 따른 GPU 실행 시간 비교처럼 명확한 실험 가설과 기준 결과.
- 입력과 배치 스크립트, 워밍업·동기화·측정 구간·반복 횟수, GPU와 도구 버전의 호환성 확인.

먼저 짧게 임대해 환경과 정확성을 확인한 뒤 측정을 모아서 수행하고, 사용 후 과금 인스턴스를 중지한다. 학습 시간 추정치상 L0–L5 완료까지는 약 3–5개월이지만 실제 검증에 따라 진행한다. 이 기간은 지출을 검토하는 시점의 예시이며 반드시 임대해야 하는 기한이 아니다.

### GPU 구매를 다시 검토할 조건

단기 임대를 활용하며 4–6주간 사용 기록을 남긴다. GPU 코드를 자주 디버깅하고 임대·전송 과정이 학습을 반복해서 방해하며 필요한 아키텍처와 VRAM이 정해졌다면, 임대료와 GPU 구매비·전원 및 케이스 호환·전기요금을 비교한다. 간헐적 실험은 단기 임대를 유지한다. 단계 완료만으로 구매를 결정하지 않는다. 실제 NPU 성능은 대응하는 NPU 자원으로 측정해야 한다.

### 선택형 클라우드 실험 예산

고정 요금이나 환산 금액을 제시하지 않고, 실제 이용 가능한 서비스의 견적을 원화(KRW) 기준으로 확인한다. GPU 종류, 지역, 부가세, 스토리지, 데이터 전송, 중지 후 남는 자원의 요금을 구분한다.

| 예산 항목 | 산정 방법 |
|---|---|
| 컴퓨팅 | 실제 시간당 단가 × 과금 대상 실행 시간 |
| 스토리지·전송 | 보관 기간, 용량, 외부 전송량에 따른 실제 요금 |
| 첫 실험 지출 한도 | 환경 검증에 필요한 시간과 견적을 확인한 뒤 사전 설정 |
| 실제 NPU 사용 | 타깃 모델, SDK, 접근 권한 및 별도 견적 확인 |

설치·컴파일·디버깅 시간도 과금 대상에 포함될 수 있다. 코드와 테스트는 가능한 한 로컬에서 준비한다. 무료 자원이나 특정 장치 접근 권한이 이미 확보됐다고 가정하지 않는다.

## 이력서에 넣을 프로젝트 선택

| 지원 분야와 완료 상태 | 프로젝트 구성 |
|---|---|
| AI/NPU 컴파일 최적화, B에 실질적 C++ 수정과 회귀 테스트가 있음 | A, B, 기존 로봇·데이터 플랫폼 프로젝트 |
| 지원 시점의 B가 소스 읽기·변환 실행 단계에 머묾 | A와 기존 로봇·데이터 플랫폼 프로젝트의 검증된 성과 우선, 세 번째 프로젝트를 억지로 추가하지 않음 |
| 일반 C++/Linux 인턴 | 기존 로봇·데이터 플랫폼 프로젝트 우선, 직무에 따라 A 또는 완료한 B 선택 |

기존 프로젝트도 실제로 완성한 기능, 본인의 기여, 검증 결과만 기재한다. RPC, 코루틴, 모든 동시성 모델을 이미 구현했다고 전제하지 않는다. 프로젝트 수를 맞추느라 지원을 늦추지 않는다.

완료 성과로 기재하려면 본인이 작성한 핵심 코드를 제시하고, 새로운 입력·제약에 대응하며, 다른 사람이 설명대로 재현하고, 실패 사례 하나와 수정 과정을 설명할 수 있어야 한다. 튜토리얼 재현만 했다면 학습 경험으로 구분한다.

## 상세 설계와 검증 기록의 관리

설계, 도구 버전, 실습별 과제, 첫 2주 일정과 검증 기록은 Trellis 작업에서 관리한다. 계획이 바뀌면 해당 작업을 먼저 갱신하고 이 문서에도 반영한다. 실험을 실행하지 않았다면 완료로 표시하지 않는다.

관련 기준은 수학·알고리즘 기초와 MLIR 학습 및 실습 계획 정리를 함께 확인한다. 이 문서의 장기 투입 계획과 실습 계획 정리의 4주 시범 학습·최소 프로젝트 범위는 목적이 다르므로 시간 예산을 합산하지 않는다.
