# AI 컴파일러 5개월 학습 로드맵

01–03 문서를 종합해 앞으로 4–5개월 동안 실행할 계획으로 정리했다. 목표는 두 가지다. MLIR/LLVM 기반 AI 컴파일러의 기초를 익히고, 직접 설계·구현·검증한 소형 텐서 컴파일러 하나를 GitHub에 공개한다. 모든 분야를 다루지 않으며, 국내 컴파일러 직무 채용 공고에서 반복해서 요구하는 역량 중 입문자가 5개월 안에 증명할 수 있는 부분을 우선한다.

> [!info] 기존 문서와의 관계
> - 이 문서는 **2026년 10월 26일–2027년 3월 말 실행 계획**이다. 01–03은 세부 근거와 참고 자료로 유지한다.
> - 01의 L0–L7(386–530시간)과 03의 L0–L15(204시간)는 번호 체계가 다르다. 이 문서는 혼동을 피하려고 **P0–P5 단계**라는 새 번호를 쓴다.
> - 01의 프로젝트 B(실제 NPU 컴파일러 패치), 03 §6.4의 N1–N4, GPU 임대는 이번 5개월 범위에서 제외하고 §8의 후속 과제로 둔다.
> - 진도와 실험 기록은 기존 방식대로 Trellis 작업에서 관리한다. 이 문서에는 완료 체크를 하지 않는다.

## 3. 범위와 시간 예산

### 3.1 5개월 뒤의 완료 기준

1. 짧은 MLIR을 보고 Operation·Value·Region·Block, SSA 정의·사용, Dialect 간 변환 단계를 설명할 수 있다.
2. 공개 저장소 `mininn-mlir`(이름은 바꿔도 된다)에서 사용자 정의 Dialect의 `MatMul → Add → ReLU` 그래프를 CPU에서 실행하고 NumPy 결과와 일치시킨다.
3. 잘못된 형상과 미지원 입력을 Verifier가 거부하며, lit/FileCheck 테스트로 확인한다.
4. 타일링·융합 하나를 정확성 테스트와 측정 조건을 갖춰 설명할 수 있다.
5. 교육용 메모리 계획기가 버퍼 생존 기간을 분석해 고정 용량 안에 배치하고, 독립 검사기와 CPU 재실행으로 검증된다.
6. 다른 사람이 README의 명령만 따라 빌드·테스트를 재현할 수 있다.

5번은 일정이 밀리면 가장 먼저 줄인다(§5 P4 참고). 1–4번과 6번이 지원 시작의 최소 조건이다.

| 주 | 할 일 |
|---|---|

| W1 | 연구실 PC의 OS, 계정 권한, 원격 접속 정책, 가용 디스크를 확인한다(§7). |
| W2 | 연구실 PC에서 LLVM/MLIR 20.1.8을 빌드하고(§7.2), 최대 메모리·디스크·소요 시간을 기록한다. `check-mlir`의 일부 또는 Toy 예제(`toyc-ch1`~)를 실행한다. |

- **수학(02):** §2.1 행렬 곱 원소 공식, §2.2 형상·스트라이드·오프셋, §2.4 절대·상대 오차와 `atol + rtol·|ref|` 판정.

### P1. MLIR 핵심과 첫 Pass (W3–W6, 65시간)

| 주 | 할 일 |
|---|---|
| W3 | Toy Ch3(패턴 재작성, DRR·C++ 패턴), Ch4(Interface, 형상 추론, 인라이닝)를 실행하며 읽는다. Beginner-Friendly 2편의 로워링 설명을 함께 본다. |
| W4 | Toy Ch5(Affine 부분 로워링), Ch6(LLVM 로워링·JIT)를 실행하고 IR을 단계별로 저장해 비교한다. LLVM 스타일 C++(`StringRef`, `ArrayRef`, `SmallVector`, `isa/cast/dyn_cast`, `LogicalResult`, 소유권)을 정리한다. |
| W5 | standalone 예제를 복사해 개인 저장소 뼈대를 만든다. ODS/TableGen으로 연산 하나를 정의하고, out-of-tree 빌드와 `lit` 테스트를 돌린다. |
| W6 | **첫 Pass**를 직접 작성한다. 예: `relu(relu(x)) → relu(x)`, `x + 0 → x` 같은 재작성 패턴. 변환해야 하는 입력과 **변환하면 안 되는 반례**(형상이 다른 경우, 결과를 여러 곳에서 쓰는 경우)를 FileCheck로 테스트한다. |

- **수학(02):** §2.5 그래프·의존성, §5 DFS·작업 목록(worklist).
- **W6 점검(03 §7.4의 4주 시범 학습):**
  - 짧은 IR을 설명하고 규칙 하나를 독립적으로 수정할 수 있는가?
  - 빌드·테스트 오류의 원인을 외부 답에만 의존하지 않고 좁혀 갈 수 있는가?
  - 소스 읽기와 디버깅을 계속할 의향이 있는가?
  - 진도가 느리면 원인을 기초, 환경, 범위, 투입 시간 중에서 구분하고 P2 범위를 줄인다(예: Add 제외, MatMul+ReLU만 지원).

### P2. MiniNN 컴파일러 v0.1: CPU 실행까지 (W7–W11, 90시간)

03 §6.1·§7.1의 최소 프로젝트 범위를 구현한다. 지원 범위는 **정적 형상, 2차원, f32, Constant·MatMul·Add·ReLU, 브로드캐스팅 없음**이다.

목표 입력 형태는 다음과 같다(설계 예시이며 문법은 구현하면서 정한다).

```mlir
func.func @forward(%a: tensor<4x8xf32>, %b: tensor<8x16xf32>,
                   %r: tensor<4x16xf32>) -> tensor<4x16xf32> {
  %0 = mininn.matmul %a, %b : (tensor<4x8xf32>, tensor<8x16xf32>) -> tensor<4x16xf32>
  %1 = mininn.add %0, %r : tensor<4x16xf32>
  %2 = mininn.relu %1 : tensor<4x16xf32>
  return %2 : tensor<4x16xf32>
}
```

| 주 | 할 일 | 산출물 |
|---|---|---|
| W7 | `mininn` Dialect와 네 연산의 ODS 정의, Verifier(랭크 2, `A.cols == B.rows`, Add 입력 형상 일치, f32만 허용) | 정상·오류 입력 lit 테스트(`-verify-diagnostics`, `expected-error`) |
| W8 | Dialect Conversion으로 `mininn → linalg`(`linalg.matmul`, 원소별 `linalg.generic`/`linalg.map`) 로워링. MatMul 누산 대상의 `linalg.fill` 0 초기화를 설명한다. | 변환 후 `mininn` 연산이 남지 않는지 확인하는 FileCheck |
| W9 | One-Shot Bufferize(함수 경계 포함) → 루프 → LLVM 로워링 파이프라인을 `mininn-opt`에 등록한다. 복사가 생기는 이유와 할당·해제 책임을 기록한다. | IR 단계별 덤프와 설명 |
| W10 | CPU 실행: `mlir-runner`/`mlir-cpu-runner`(20.1.8에 있는 이름 확인) 또는 C++ 드라이버와 ExecutionEngine. 무작위 입력 몇 세트와 경계 형상으로 NumPy와 비교하는 스크립트 | `tests/e2e/` 수치 회귀 테스트 |
| W11 | 정리 및 **v0.1 공개**: README(지원 범위, 미지원 기능, 빌드·테스트 명령, 파이프라인 그림), 직접 작성한 부분과 재사용한 부분 구분 | GitHub 릴리스 v0.1 |

- **수학(02):** §3.1–§3.2 연산 의미와 접근 매핑(`(i,j,k)→(i,k)` 등), parallel·reduction 반복 유형, ReLU를 누산 중간에 넣으면 안 되는 이유.
- **검증 기준:** `ReLU(AB+R)`이 `[3,5]×[5,2]` 같은 비정방 형상에서도 NumPy와 일치한다. 잘못된 형상 세 가지 이상을 Verifier가 거부한다. 처음부터 다시 빌드해 테스트가 모두 통과한다.
- **디버깅 기록:** 이 단계에서 겪은 결함 하나(예: 누산 대상을 초기화하지 않은 결과 오류, 버퍼 별칭 문제)를 증상 → 최소 재현 → 원인 → 수정 → 회귀 테스트 순서로 `docs/debug-log.md`에 남긴다. 이 기록을 면접 설명의 중심으로 쓴다.

공고의 "타일링, 연산자 융합", "중위 수준 최적화"에 대응하는 단계다.

| 주 | 할 일 |
|---|---|

### 6.3 이력서 항목 형식

수치는 실제로 측정한 값만 넣는다. 아래 `[ ]`는 채울 자리다.

```text
MiniNN: MLIR 기반 소형 텐서 컴파일러 (개인, 2026.11–2027.03)  github.com/[계정]/mininn-mlir
- MatMul/Add/ReLU용 MLIR Dialect와 형상 Verifier를 ODS·C++로 구현하고,
  Linalg → Bufferization → LLVM으로 로워링해 CPU에서 실행. NumPy 참조와 [ ]개 형상 조합에서 일치 검증
- Linalg 타일링과 생산자·소비자 융합을 적용하고, 나누어떨어지지 않는 타일 경계 테스트 추가.
  [CPU 모델, 입력 크기, 반복 조건]에서 [측정 결과]
- 버퍼 생존 구간 분석과 고정 용량([ ]KiB) 교육용 메모리 계획기·독립 검사기 구현, 계획상 최대 사용량 [ ] → [ ]
- [직접 찾은 결함 한 줄: 증상 → 원인 → 수정 → 회귀 테스트]
```

SK하이닉스 인턴 항목은 별도로 쓰고, 보안 범위 안에서 본인이 맡은 C++ 작업, 리뷰를 받은 방식, 배운 점을 기재한다. 컴파일러 직무와 직접 관련이 없어도 "엔지니어 지도하에 실무 C++ 코드 작성·리뷰"는 공고의 "C++ 능숙", "프로덕션 소프트웨어" 항목에 대응한다.

### 6.4 면접에서 설명할 질문

1. MLIR은 왜 여러 Dialect를 거쳐 단계적으로 로워링하는가? 각 단계에서 사라지는 정보는 무엇인가?
2. Verifier로 거부해야 하는 입력과 변환 Pass가 처리해야 하는 입력을 어떻게 구분했는가?
3. 패턴 재작성이 적용되면 안 되는 반례를 하나 들고, 테스트로 어떻게 막았는가?
4. Linalg MatMul의 indexing map과 iterator type은 무엇이고, 타일링에 어떻게 쓰이는가?
5. 융합이 데이터 이동을 줄이는 이유와 중복 계산·임시 버퍼 증가로 손해가 되는 경우는?

7. Bufferization에서 복사가 생기는 이유와 버퍼 해제 책임은 어디에 있는가?
8. 메모리 계획기의 탐욕 배치가 최적이 아닌 예를 들 수 있는가? 용량 초과 시 실제 컴파일러는 어떤 대안을 쓰는가(타일 크기 축소, 재계산, 외부 메모리로 내보내기)?
9. 직접 겪은 가장 어려운 버그를 처음 증상부터 설명하라.

### 7.2 LLVM/MLIR 20.1.8 빌드 기준

```bash
git clone --depth 1 --branch llvmorg-20.1.8 https://github.com/llvm/llvm-project.git
cmake -S llvm-project/llvm -B build-20 -G Ninja \
  -DLLVM_ENABLE_PROJECTS=mlir \
  -DLLVM_TARGETS_TO_BUILD=Native \
  -DCMAKE_BUILD_TYPE=Release \
  -DLLVM_ENABLE_ASSERTIONS=ON \
  -DLLVM_INSTALL_UTILS=ON \
  -DLLVM_ENABLE_LLD=ON \
  -DLLVM_CCACHE_BUILD=ON \
  -DLLVM_PARALLEL_LINK_JOBS=4
ninja -C build-20
```

- `LLVM_INSTALL_UTILS=ON`은 out-of-tree 프로젝트에서 `FileCheck`·`lit`를 쓰기 위한 설정이다. `lld`·`ccache`가 설치되어 있지 않으면 해당 옵션을 뺀다.
- 컴파일은 16스레드로 충분하다. 링크 단계의 메모리 사용이 크므로 링크 병렬도를 4에서 시작하고, 실제 최대 메모리를 보고 조정한다.
- 빌드 시간, 최대 메모리, 빌드 디렉터리 크기를 W2에 실측해 Trellis에 기록한다. 3TB는 LLVM 빌드 몇 개와 측정 데이터에 충분하지만 실제 여유 공간은 다른 사용자 데이터를 고려해 확인한다.
- 측정(P3) 때는 다른 작업이 없는 시간대를 고르고 CPU 주파수 설정과 스레드 수를 기록한다.

GPU·NPU 장비 구매와 클라우드 임대는 이번 5개월 동안 필요하지 않다(01 §장비와 비용, 03 §8).

## 8. 이번 범위 밖의 후속 과제

v1.0을 공개한 뒤 지원 직무에 맞춰 **하나만** 고른다(03 §7.2).

| 후속 과제 | 연결되는 공고 요구 | 규모 |
|---|---|---|
| 제한적 ONNX 임포터(Python, `onnx` 패키지로 MiniNN MLIR 텍스트 생성) | 퓨리오사AI Front-end의 PyTorch·ONNX, 그래프 수준 최적화 | 15–20시간 |
| 브로드캐스팅 편향 Add, Softmax 등 연산 확장 | 그래프 컴파일러 일반 | 15–25시간 |
| INT8 수치 시뮬레이션(02 §4.5) | 양자화, 모바일·엣지 NPU | 15–20시간 |
| 공개 컴파일러(IREE, torch-mlir 등)에서 연산 하나 추적 후 작은 수정·테스트 | 01의 프로젝트 B, "프로덕션 소프트웨어" | 20–40시간 이상 |
| CUDA/Triton 또는 SIMD 커널 | 딥엑스·리벨리온 우대 사항 | 별도 계획 필요 |

## 9. 점검 시점과 지원 시작

| 시점 | 확인할 결과 | 판단 |
|---|---|---|
| W2 말 (11/8) | 빌드 성공과 실측값, C++·NumPy 참조 구현 | 빌드가 안 되면 환경 문제를 먼저 해결하고 P1을 1주 미룬다 |
| W6 말 (12/6) | 첫 Pass와 반례 테스트, 4주 시범 학습 점검(§5 P1) | 계속·범위 축소·투입량 조정 중 결정 |
| W11 말 (1/10) | v0.1: CPU 실행과 수치·오류 테스트 | 인턴 공고(하이퍼엑셀 인턴 등) 지원 검토 시작 |
| W15 말 (2/7) | v0.2: 타일링·융합과 측정 | P4를 전체로 할지 축소할지 결정 |
| W20 말 (3/14) | v1.0, 이력서·면접 준비 | 신입 공고 본격 지원, §8 후속 과제 선택 |

- 03 §10.3대로 **모든 단계를 마쳐야 지원할 수 있는 것은 아니다.** v0.1과 설명할 수 있는 디버깅 사례 하나가 있으면 인턴 지원을 검토한다.
- 지원할 때마다 공고 원문의 자격·우대 항목을 §2.1 표와 대조해 부족한 부분을 기록한다. 공고 피드백이 계획보다 우선한다.
- 컴파일러 공고만 보지 않고 C++ 시스템 소프트웨어, 반도체 SW 직무도 함께 검토한다(03 §10.3).

## 10. 이번 계획의 한계

- 공고 요약은 2026년 10월 22일 기준이며 게시일을 확인할 수 없는 공고가 섞여 있다. 일부 공고는 이미 마감됐을 수 있다.
- 300시간과 주차 배분은 예상치다. W2와 W6 점검에서 실제 투입 시간과 진도로 다시 산정한다.
- 연구실 PC의 OS, 접속 정책, 빌드 시간은 아직 확인하지 않았다.
- 이 계획을 마쳐도 실제 NPU 백엔드나 프로덕션 컴파일러 개발 경험을 대신하지는 않는다. 포트폴리오는 기초와 독립 구현 능력의 근거로 제시한다.
