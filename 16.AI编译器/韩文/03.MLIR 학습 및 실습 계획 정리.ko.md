# MLIR 학습 및 실습 계획 정리

MLIR 입문부터 소형 텐서 컴파일러 구현까지의 학습 범위와 실습 계획을 정리했다. 실습별 시간은 예상치이며, 실행·검증을 마친 결과와 구분한다.

## 1. 주요 결론

1. **MLIR/AI 컴파일러를 지원 분야로 검토하되 처음부터 모든 학습 시간을 투입하지 않는다.** 우선 4주 동안 직접 수정하고 테스트한 Pass 하나를 만든 뒤 실제 진도에 따라 투입량을 결정한다.
2. **장기 학습 로드맵과 인턴 지원 전 최소 요건을 구분한다.** 수백 시간의 전체 계획을 모두 마쳐야 지원할 수 있는 것은 아니다.
3. **단기 목표는 본인이 충분히 설명할 수 있는 컴파일러 프로젝트 하나다.** 소수 연산, 검증, 로워링, CPU 실행, 테스트를 우선한다. 실제 NPU, 전체 양자화, 자체 메모리 계획기, 실제 컴파일러 PR을 동시에 필수 과제로 두지 않는다.
4. **현 단계에는 추가 장비 구매가 필요하지 않다.** 기존 PC와 SSD로 CPU 개발·실험부터 수행하고 가속기가 필요한 과제가 생기면 대여·임대·구매를 검토한다.
5. **Lab의 포트폴리오 가치는 직접 수행한 기여에서 나온다.** 스크립트 실행, 튜토리얼 재현, 독립 확장, 실제 결함 수정은 각각 다른 수준의 역량을 보여 준다.
6. **지원 가능성은 프로젝트 결과와 채용 공고로 판단한다.** 독립 코딩과 면접을 통해 컴파일러 역량을 평가한 상태는 아니다. 채용이나 합격을 보장할 수 없으며, 단계별 산출물과 지원 피드백을 근거로 판단한다.

## 2. 출발점·목표·제약

### 2.1 기존 경험과 관심사

- C++·Linux 학습 경험과 로봇·데이터 플랫폼 관련 개발 경험이 있다.
- MLIR, 텐서 최적화, 로워링, 하드웨어 매핑, 온칩 메모리, 데이터 전송에 관심이 있다.
- 강의 수강 수보다 인턴·취업에 연결되는 학습을 원한다.
- 기존 NPU 컴파일러 발표를 따라가려 했으나 컴파일러·MLIR 기초를 많이 전제해 이해에 어려움이 있었다.
- 짧은 시간에는 개념 예습이 가능하지만 Pass 작성, 로워링 디버깅, 메모리 분석에는 연속된 작업 시간이 필요하다.

이 경험만으로 컴파일러 이론, Python, 선형대수, 딥러닝, CUDA, 모든 시스템 기술에 이미 숙련됐다고 판단하지 않는다. 실험에 필요한 항목부터 확인하고 보완한다.

### 2.2 시간과 진로 선택의 위험

장기 계획에 몇 달을 투자하기 전에 학습 범위와 우선순위를 점검한다. 먼저 4주 동안 작은 Pass를 직접 수정하고 테스트하면서 필요한 기초, 실제 진도, 지속할 의향을 확인한다.

초기 전문 학습 투입량을 제한하고 일반적인 취업 준비를 유지하며 단계별 결과로 이후 투입량을 결정한다. 이미 학습을 시작했다면 기존 결과를 마일스톤에 반영한다. 특정 날짜에 처음부터 다시 시작할 필요는 없다.

## 3. 유료 교육과정 검토

교육과정을 검토할 때는 아래 학습 주제와 과제 기준을 살펴본다. 강의 개요만으로 수업 품질, 전체 과제의 깊이, 수강 후 지원을 판단하지 않는다.

### 3.1 유지할 학습 주제

검토한 과정은 NPU 도구 체인, 양자화, 배포 실습에 비중이 있었다. 유지할 주제는 다음과 같다.

- 모델 프런트엔드부터 상위·타깃별 IR, 로워링, 연산 그룹화, 실행 산출물까지의 전체 흐름.
- DMA, 로컬 메모리, 연산 그룹화, 메모리 배치·관리.
- INT8 캘리브레이션, 민감 계층 분석, 혼합 정밀도 폴백, 프로파일링.
- 실제 장치 배포와 전처리·추론·후처리 파이프라인 구성.

### 3.2 6개 실습 유형이 보여 주는 역량

| 실습 | 과제 범위 | 확인할 역량 |
|---|---|---|
| Lab1 | 불필요한 연산을 제거하는 Pass 직접 구현 | 컴파일러 변환 구현 |
| Lab2 | ResNet50의 CPU/NPU 실행 비교 | 환경 구성, 모델 실행, 측정 |
| Lab3 | ONNX → MLIR → 타깃 실행 산출물 | 변환 흐름 이해. 개발 깊이는 소스 수정 여부에 따라 달라짐 |
| Lab4 | 양자화, 정확도 분석, 폴백 | 모델 적합화와 양자화 디버깅 |
| Lab5 | 객체 탐지 영상 파이프라인 | 동시성, 큐, 배포 엔지니어링 |
| Lab6 | 지원되는 공개 LLM의 대화형 추론 배포 | LLM 배포 전 과정 |

컴파일러 Pass를 직접 구현하는 과제는 Lab1이다. 다른 실습도 실행 명령만 따라 하는지, 소스 수정과 테스트까지 요구하는지 과제 명세에서 확인한다. 위 표는 학습 설계 예시이며 특정 교육기관의 과제 목록이 아니다.

예를 들어 Lab3에서 단계별 IR 보관, 담당 Pass 식별, 변환 규칙 수정, 회귀 테스트를 요구한다면 개발 훈련이 된다. 변환 명령만 실행한다면 주로 도구 사용 능력을 보여 준다.

### 3.3 보완할 기초

| 기초 | 필요한 이유 |
|---|---|
| IR, SSA, 정의·사용, 기본 블록, 지배 관계 | 프로그램 표현과 값의 유효 범위 이해 |
| Operation, Value, Region, Block, Type, Attribute | MLIR 객체와 C++ API 이해 |

| Bufferization, 소유권, 해제 책임 | 복사·재사용·메모리 생존 기간 이해 |
| lit, FileCheck, 수치 회귀 테스트 | IR 구조와 실행 결과 검증 |

수학·연산의 세부 범위는 수학 및 알고리즘 기초를 참고한다.

### 3.4 수강료 지출 판단

가격, 전체 과제, 첨삭 예시, 강사 피드백, 장치 자원이 확인되지 않았으므로 구매 결론을 내리지 않는다. 다음 자료를 요청해 비교한다.

1. Lab1 전체 명세와 수강생 과제 예시.
2. 기초 및 로워링·연산 그룹화 수업의 샘플.
3. 수강생이 작성한 Pass·변환 코드·테스트의 리뷰 여부.
4. NPU 모델, SDK, 도구 버전, 모델 사양.
5. 사용 가능 시간, 대기 방식, 접근 기간, 수료 후 재현 조건.
6. 수강료, 수업 시간 단위, 수업 외 예상 투입량.

공개 문서 설명이나 준비된 스크립트 실행만으로는 서비스의 가치를 판단하기 어렵다. 안정적인 장치 접근, 소스 수준 디버깅, 지속적인 코드 리뷰가 제공되는지 확인한다.

BF16은 캘리브레이션 알고리즘이 아니라 부동소수점 형식이다. XLA의 적용 범위는 실제 프레임워크와 백엔드를 기준으로 확인한다. 강의 분량도 숫자의 합계만 보지 말고 시간인지 차시인지 단위를 확인해야 한다.

## 4. Lab의 근거와 교육용 설계 구분

아래 실습은 공개 기술 자료를 참고해 설계한 학습 계획이다. 공식 튜토리얼에 있는 기능과 직접 구현해야 할 교육용 과제를 구분한다. 전체 실습을 실행·검증한 상태는 아니다.

| 내용 | 근거와 상태 |
|---|---|
| NPU 변환, 양자화, 연산 그룹화, 배포 | 강의 주제에서 일반화. 구체적인 구현은 선정한 도구에서 확인 |
| Dialect, Verifier, 재작성, 로워링, LLVM 실행 | 공식 튜토리얼·소스·테스트 존재 |
| Bufferization, 타일링·융합 | 공식 메커니즘과 예제 존재. 실습 구성은 별도 설계 |
| MiniNN 이름, 네 종류 연산, 소형 네트워크, 제한적 ONNX 임포터 | 직접 구현·검증할 교육용 설계 |
| 64KiB 교육용 용량, 독립 메모리 계획기·검사기 | 단순화한 자체 실험. 실제 하드웨어를 의미하지 않음 |
| 실제 결함 수정·최적화 PR | 후반 주제 후보. 재현 전에는 확정 과제가 아님 |
| Lab별 시간 | 직접 학습·작업하는 시간의 추정치. 실측 완료 시간이 아님 |

실행에 들어가는 Lab에는 참고 저장소, 고정 버전, 소스·테스트 위치, 실행 가능한 기준 예제, 본인 수정 범위, 검증 명령·기준을 갖춘다. 제목과 시간 추정만으로 준비가 끝난 과제 명세라고 부르지 않는다.

## 5. 공개 프로젝트와 참고 자료

### 5.1 공식 Toy: 핵심 참고 자료

- [공식 튜토리얼](https://mlir.llvm.org/docs/Tutorials/Toy/)
- [GitHub 소스](https://github.com/llvm/llvm-project/tree/main/mlir/examples/toy)

사용자 정의 연산, Dialect, 패턴 재작성, Interface, 형상 추론, 단계별 로워링, LLVM 코드 생성을 다룬다. IR 기초를 먼저 익힌 뒤 Toy 구현 일부를 이해하고 수정한다.

Toy 예제 경로에는 Affine 로워링이 포함된다. 여기서 설계한 ONNX → MiniNN → Linalg와 같은 경로는 아니다. MiniNN은 이러한 메커니즘을 활용한 독립 종합 실습이며 Toy 공식 과제로 부르지 않는다.

### 5.2 MLIR For Beginners: C++ 구현 보조 자료

- [j2kun/mlir-tutorial](https://github.com/j2kun/mlir-tutorial)

빌드, 로워링 실행·테스트, 첫 Pass, TableGen, Dialect, Trait, 폴딩, Verifier, Canonicalizer, Dialect Conversion, LLVM 로워링, 데이터 흐름 분석, PDLL을 다룬다.

현재 문제에 맞춰 선별해서 읽고 Toy와 동시에 전체 과정을 두 번 진행하지 않는다. 실행 시 해당 저장소의 의존성을 사용한다. 서로 다른 튜토리얼이 임의의 LLVM 버전을 함께 사용할 수 있다고 가정하지 않는다.

### 5.3 공식 Transform Dialect: 최적화 참고 자료

- [공식 튜토리얼](https://mlir.llvm.org/docs/Tutorials/transform/)

기존 변환 조합, 새로운 Transform 연산 확장, 독립 프로젝트 연결을 다룬다. MLIR 기초를 갖춘 뒤 예제를 재현하고, 나누어떨어지지 않는 크기·다른 파라미터·정확성 비교·성능 측정을 추가한다.

### 5.4 Bufferization과 테스트 자료

- [Bufferization](https://mlir.llvm.org/docs/Bufferization/)
- [Dialect Conversion](https://mlir.llvm.org/docs/DialectConversion/)
- [MLIR Testing Guide](https://mlir.llvm.org/getting_started/TestingGuide/)
- [Understanding the IR Structure](https://mlir.llvm.org/docs/Tutorials/UnderstandingTheIRStructure/)
- [LLVM Programmer’s Manual](https://llvm.org/docs/ProgrammersManual/)

Bufferization은 tensor에서 memref로의 변환, 별칭, 제자리 갱신 등을 다룬다. 교육용 온칩 메모리 계획기는 다른 계층의 실습이므로 구분한다. One-Shot Bufferize 자체는 버퍼 해제를 담당하지 않는다. 해제 절차를 연결하거나 외부 소유권을 명확히 해야 한다.

### 5.5 후반 실제 컴파일러 사례 선정

특정 업체의 컴파일러를 필수 대상으로 고정하지 않는다. 공개 소스 또는 합법적으로 접근 가능한 SDK 중에서 코드·의존성·실행 환경·테스트를 확인할 수 있는 대상을 선정한다. 저장소, 라이선스, 버전, 타깃 하드웨어를 기록한다.

지원 예제 실행 → 연산 하나 추적 → 최소 재현 입력 작성 → 범위가 명확한 문제 수정 순서로 진행한다. 초보자에게 적합한 연산 그룹화 결함이 반드시 존재하거나 최적화가 반드시 성능을 개선한다고 보장하지 않는다. 주제 선정에는 소스 분석과 기준 실험이 필요하다.

### 5.6 자료 범위 제한

초기에는 Toy를 주 자료로, MLIR For Beginners를 보조 자료로 사용한다. 최적화 단계에서 Transform·Bufferization을 추가하고 이후 선정한 컴파일러를 분석한다. 여러 대형 컴파일러·GPU 프레임워크를 동시에 시작하지 않는다.

## 6. 장기 로드맵과 MiniNN 프로젝트

일반 MLIR 기초 → 소형 CPU 컴파일·실행 전 과정 → 최적화·메모리 분석 → 실제 컴파일러 소스 수정 → 지원 직무에 필요한 하드웨어 심화 순서로 진행한다.

### 6.1 MiniNN의 초기 범위

- 정적 형상, 2차원 텐서, FP32.
- Constant, MatMul, Add, ReLU.
- 초기 Add는 동일 형상 입력만 허용하고 지원하지 않는 브로드캐스팅은 오류로 처리.
- 장기 변환 경로: 제한적 ONNX → MiniNN → Linalg 등 표준 Dialect → 버퍼·루프 → LLVM → CPU.
- 연산 의미, 검증, 필요한 변환, 테스트, 오류 진단은 직접 구현하고 상위 프로젝트의 인프라·코드 생성은 재사용.

원래 예제 네트워크는 1×16 입력에 16×32 가중치를 곱하고 편향과 ReLU를 적용한 다음, 32×8 가중치를 곱해 1×8 출력을 만든다. 일반적인 1차원 편향을 사용하려면 브로드캐스팅을 명시적으로 지원하거나 그래프 구성 시 지원 형상으로 변환해야 한다. 동일 형상 Add의 범위를 암묵적으로 넘기지 않는다.

### 6.2 16개 실습으로 구성한 기본 계획

다음 시간은 학습과 구현에 필요한 예상치다. 도구 설치, 빌드 대기, 환경 문제 해결에 걸리는 시간은 별도로 잡는다. NPU 관련 과제는 대상 도구와 장치를 정한 뒤 다시 산정한다.

### 6.3 Trellis 통합 논의의 확장 범위

이전 통합안은 A에 CPU 컴파일, 최적화, 교육용 메모리 계획과 독립 검사를, B에 실제 컴파일러 수정과 검증을 포함했다. 이에 따라 기본 계획의 204시간보다 큰 386–530시간 예산이 산정됐다.

| 확장 단계 | 범위 | 예상 시간 |
|---|---|---:|
| L0 | 참조 계산·환경 | 32–44 |
| L1 | SSA·재작성·테스트 | 36–48 |
| L2 | Dialect·로워링 | 50–66 |
| L3 | Bufferization·CPU 실행 | 44–58 |
| L4 | 타일링·융합 | 50–70 |
| L5 | 메모리 계획·검사·재실행 | 60–84 |
| L6 | NPU 변환·양자화·시뮬레이션 환경 | 36–50 |
| L7 | 실제 컴파일러 패치 | 60–84 |
| 공개 준비 | 재현·문서·결과 정리 | 18–26 |

두 계획은 L 번호가 가리키는 과제가 다르므로 혼용하지 않는다. 확장 계획 전체를 단기 목표로 삼지 말고, 다음 절의 최소 프로젝트 범위부터 완성한다. 학습 계획의 장기 예산과 이 문서의 시범 학습 시간을 더하지 않는다.

교육용 프로젝트의 기준 버전은 LLVM/MLIR 20.1.8이다. NPU 프로젝트는 저장소·SDK·타깃 선정 후 버전을 별도로 고정하고 실행 조건을 확인한다. 최신 버전을 무조건 따라가거나 현재 장비에서 이미 실행 검증이 끝났다고 가정하지 않는다. NPU 관련 단계인 확장 계획의 L6·L7과 기본 계획의 L14에 필요한 시간은 실제 도구를 정한 뒤 재산정한다.

### 6.4 후반 선택 과제

| 과제 | 내용 | 예상 시간 |
|---|---|---|
| N1 | 실제 NPU 소형 모델의 정확도, 장치 시간, 종단 간 시간 비교 | 12–20시간 |
| N2 | 객체 탐지 영상 파이프라인, 유한 용량 큐, 처리량·지연·프레임 손실 | 16–24시간 |
| N3 | Attention, KV cache, 지원되는 LLM 배포 | 20–36시간 |
| N4 | 실제 컴파일러 연산 추가·수정과 테스트 | 20–40시간 이상 |

추정은 대응 하드웨어·도구·지원 예제를 확보한 상태를 전제로 한다. 컴파일러 개발은 N4를, 로봇 엣지 배포는 N1/N2를 우선 검토한다. N3는 prefill과 decode를 별도로 측정하며 대화 가능 여부만 보고하지 않는다. 모두 최소 프로젝트를 완성한 뒤 진행해도 된다.

## 7. 소형 컴파일러부터 완성하는 단기 계획

### 7.1 최소 프로젝트 산출물

주 프로젝트는 소형 MLIR 기반 텐서 컴파일러 하나로 제한한다.

1. 소수의 정적 FP32 연산만 지원한다. 사용자 정의 MLIR을 직접 입력해 ONNX 프런트엔드를 생략해도 된다.
2. 연산 검증과 핵심 로워링을 직접 구현한다.
3. 상위 프로젝트의 메커니즘을 재사용해 CPU에서 실행한다.
4. 독립 참조 구현과 수치를 비교한다.
5. 잘못된 형상, 미지원 입력, 필요한 경계 조건을 테스트한다.
6. 직접 찾은 결함 하나 또는 실측한 최적화 하나를 깊이 설명한다.

### 7.2 첫 프로젝트에서 제외할 범위

- ONNX 프런트엔드.
- 전체 양자화 IR, 정수 커널, 혼합 정밀도 로워링.
- 실제 NPU 및 GPU 심화 과제.
- 독립 온칩 메모리 계획기.
- 업스트림 병합이 완료된 실제 컴파일러 PR.
- 완성형 영상·LLM 애플리케이션.

시간이 남으면 하나만 확장한다. 모든 항목을 한꺼번에 되돌려 넣지 않는다.

### 7.3 일정 점검 시점

| 시기 | 기대 결과 | 판단 |
|---|---|---|
| 2026년 10월 21일–11월 초 | C++·Linux·알고리즘·기존 프로젝트 준비 유지, 소량 MLIR 예습 | 기존 결과 반영, 처음부터 다시 시작하지 않음 |
| 11월 중순–12월 초 | 공개 예제 실행, 독립 Pass 수정, 정상·오류 입력 테스트 | 이해 진도와 관심 확인 |
| 12월 중순–2027년 1월 중순 | 소수 연산의 CPU 실행 전 과정, 수치·오류 테스트 | 구현·검증 결과 정리. 어려우면 연산·기능 축소 |
| 1월 중순–2월 중순 | 결함 또는 최적화 하나 심화, 재현·설명 정리 | 범위 확장 중단, 기초 보완 |

표의 날짜는 학습 진도를 점검하기 위한 기준이다. 완료를 보장하는 일정이 아니므로 실제 결과에 따라 범위를 조정한다.

### 7.4 4주 시범 학습

첫 4주에는 주 8–12시간을 MLIR에 배정하고 다른 취업 준비를 유지한다. 4주 뒤 다음을 점검한다.

- 짧은 IR을 설명하고 규칙 하나를 독립적으로 수정할 수 있는가?
- 오류가 나면 외부 답에만 의존하지 않고 원인을 좁히기 시작할 수 있는가?
- 소스 읽기, 디버깅, 검증을 계속할 의향이 있는가?

진도가 느리면 기초, 환경, 범위, 투입 시간 중 원인을 구분한다. 필요하면 범위를 줄이거나 우선순위를 낮춘다. 이미 투자한 시간 때문에 계속할 필요는 없다. 4주 목표 미달만으로 이 분야에 적합하지 않다고 판단하지 않는다.

## 8. 장비: 현재 추가 구매 불필요

다음은 논의에서 기록한 최신 구성이다. 원격으로 장비를 검사하거나 설치 완료를 확인한 결과는 아니다.

| 장비 | 용도 | 현재 조치 |
|---|---|---|
| AMD 9700X + 48GB PC | LLVM/MLIR 빌드, C++ 개발, CPU 실험 | 주 개발 장비. 사전 업그레이드 불필요 |
| 구매한 2TB SSD | WSL, 소스, 빌드, 모델, 컨테이너 | 설치 후 공간·경로 확인 |
| GTX970 | 일반 화면 출력 | 주 과제를 위해 교체하지 않음 |
| MacBook Air | 읽기, 편집, 작은 실험, SSH | 계속 사용 |
| i7 + 16GB + GTX1660S Ubuntu | 예비 네이티브 Linux 환경 | 사전 업그레이드 불필요 |
| NPU 개발 보드 | 후반 실제 배포·성능 측정 | 구매 보류 |

환경 구성 시 다음을 확인한다.

- WSL 가상 디스크는 새 SSD에, 소스·빌드는 WSL 내부 Linux 파일 시스템에 둔다.
- WSL2 메모리 설정을 확인한다. 메모리 상한을 호스트 메모리의 50%로 잡으면 48GB PC에서 약 24GB다. Windows 사용량에 따라 약 32GB 설정을 검토할 수 있으나 필수 요구는 아니다. 실제 가용량을 확인한다.
- 필요한 도구와 호스트 타깃부터 빌드하고 Release·assertions 구성을 선택한다. 컴파일·링크 병렬도를 제한한다.
- 최소 빌드의 최대 메모리 사용량, 디스크, 소요 시간을 측정한 뒤 업그레이드를 결정한다.

CPU 프로젝트에는 GPU 구매가 필요하지 않다. NPU 컴파일러 소스와 시뮬레이터 실행 가능 여부는 의존성과 지원 환경에 달려 있다. 시뮬레이터의 기능 검증은 실제 장치 성능을 증명하지 않는다. 실제 NPU 지연·처리량·전력·DMA 중첩은 대응 하드웨어가 필요하다. NPU가 있다는 이유만으로 아무 개발 보드나 타깃 장치를 대체할 수는 없다.

## 9. Lab의 이력서 가치와 작성 기준

### 9.1 결과별로 입증하는 역량

| 결과 | 이력서에서의 의미 |
|---|---|
| 환경 구성, IR 읽기, 튜토리얼 그대로 실행 | 필요한 기초. 보통 단독 프로젝트로 기재하지 않음 |
| 단순한 0 더하기 제거 Pass | 프로젝트의 세부 항목. 단독 프로젝트로는 범위가 작음 |
| 사용자 정의 연산·검증·로워링 | 핵심 개발 역량의 근거 |
| 모델/IR부터 CPU 실행까지 완성 | 주요 프로젝트로 제시 가능 |
| 독립 검증을 갖춘 타일링·융합·메모리 최적화 | 기술 면접에서 심화 설명 가능 |
| 실제 프로젝트의 재현 가능한 결함 수정 | 테스트·리뷰 기록과 함께 제시하면 기여 설명에 유리 |
| 스크립트 기반 비전/LLM 배포 | 주로 배포 역량 입증 |

### 9.2 이력서 기재 전 확인할 다섯 가지

1. 직접 작성한 코드와 상위 프로젝트에서 재사용한 부분을 구분한다.
2. 실제 실행 결과와 독립 참조 비교가 있다.
3. 오류 입력 테스트, 오류 진단, 경계 조건을 다룬다.
4. 문제 하나를 깊이 해결하고 원인·선택의 이유·비용을 설명한다.
5. 현장에서 형상이나 사용 관계가 바뀌어도 변환 적법성을 판단하고 설명·수정할 수 있다.

AI는 코딩을 보조할 수 있지만 연산 의미, 실패 조건, 디버깅 과정의 이해를 대신하지 않는다.

### 9.3 최종 프로젝트 구성

- **프로젝트 A: MLIR 기반 소형 텐서 컴파일러.** 지원 범위, 연산 검증, 변환 경로, CPU 실행, 테스트, 개인 기여를 기술한다. ONNX 프런트엔드가 없으면 ONNX 지원을 기재하지 않는다.
- **프로젝트 B: 선정한 MLIR/NPU 컴파일러의 구체적인 수정·확장.** 후속 선택 과제다. 하나의 문제를 중심으로 재현·원인 분석·패치·테스트를 제시하며, B 완료를 첫 인턴 지원의 전제 조건으로 삼지 않는다.

수십 개 Lab 번호를 이력서에 나열하지 않는다. 튜토리얼 재현은 출처를 밝히고, PR이 병합되지 않았다면 미병합 또는 리뷰 중이라고 쓴다. 기존 기능을 본인 구현으로 기재하지 않는다.

성능 결과에는 실제 장치, 입력, 정밀도, 스레드 수, 측정 구간, 워밍업, 반복 측정 조건을 제시한다. 교육용 계획기의 최대 사용량 감소는 계획상 메모리 사용량 개선으로 표현한다. 시뮬레이터 통과는 기능 검증이며 실제 NPU 가속 성과로 기재하지 않는다.

## 10. 지원 분야와 공고 확인

### 10.1 검토할 직무

| 분야 | 로드맵과의 관련성 | 추가 준비 |
|---|---|---|
| MLIR/AI 컴파일러 인턴 | 직접 관련 | C++, 컴파일러·모델 기초, 독립 디버깅 |
| 그래프 최적화·로워링·메모리 계획 신입 | 방향상 관련 | 심화 문제와 실제 코드 수정 |
| GPU 연산·컴파일 최적화 | 일부 기초만 포함 | GPU 아키텍처, CUDA/Triton, 실제 장치 분석 |
| LLVM 코드 생성 백엔드 | 현재 범위 제한적 | 명령어 선택, 레지스터 할당, 명령어 스케줄링 |

공고 검색에는 AI 컴파일러, 그래프 컴파일러, 컴파일러 개발, MLIR, 추론 최적화 등의 키워드를 활용하고 담당 업무를 항목별로 대조한다. 직무 이름에 AI가 있다고 이 기술 스택을 반드시 요구하는 것은 아니다.

### 10.2 채용 공고를 읽는 기준

지원할 때는 공식 채용 공고의 요구 사항을 본인의 결과물과 대조한다. 아래 표는 확인 기준이며 특정 기업의 채용 여부를 나타내지는 않는다.

| 확인 항목 | 준비 자료와의 대응 |
|---|---|
| C/C++, 자료구조·알고리즘 | 직접 구현한 코드와 문제 해결 과정 |
| LLVM/MLIR 또는 모델 컴파일 경험 | Dialect, Pass, 로워링, 테스트 결과 |
| 양자화·아키텍처·성능 분석 | 실제로 수행한 실험과 측정 조건 |
| 인턴·신입·경력 구분 | 학력과 경력 조건을 개별 대조 |
| 포트폴리오·전형 방식 | 저장소, 재현 절차, 기술 설명, 공고가 요구하는 서류 |

위 표는 공고 검토용 기준이며 모든 기업의 공통 요건이 아니다. 경력·시니어 직무의 요구를 입문 프로젝트의 최소 기준으로 삼지 않는다. 공고의 존재, 지원 자격 충족, 합격 가능성은 각각 따로 확인한다.

### 10.3 지원을 시작할 시점

- 기초 Pass만 있다면 결과를 보완하며 공고 요구를 확인한다.
- CPU 실행 전 과정, 독립 테스트, 충분히 설명할 수정 사례 하나가 있으면 관련 인턴 지원을 검토한다.
- 이후 심화 최적화나 실제 컴파일러 수정이 생기면 이력서를 갱신한다. 이를 모두 마쳐야 첫 지원을 하는 것은 아니다.

인턴 경험의 유무만으로 가능성을 판단하지 않는다. 기존 로봇 프로젝트와 새 컴파일러 프로젝트에서 직접 구현한 기능, 해결한 문제, 검증 결과를 구체적으로 정리한다.

기존 경험과 맞는 C++ 시스템, 시스템 소프트웨어, 로봇 플랫폼 직무도 함께 검토한다. 별도 준비가 필요하지만 하나의 분야에만 의존하는 위험을 줄일 수 있다.

## 11. 판단의 적용 범위

- 독립 MLIR 코딩과 면접 역량 평가는 아직 수행하지 않았다.
- 전체 MiniNN·메모리 계획 Lab이 구현·검증됐다고 주장할 수 없다.
- 구체적 결함을 정하기 전에는 PR 내용이나 업스트림 수용을 약속하지 않는다.
- 실측 없이 속도 향상, 메모리 감소율, 하드웨어 용량을 단정하지 않는다.
- 가격·서비스 상세가 없으면 유료 과정 구매 결론을 내리지 않는다.
- 대응 환경을 검증하지 않으면 업체 시뮬레이터 실행을 보장하지 않는다.
- 자격·일정을 확인하지 않으면 특정 공고에 지원 가능하다고 단정하지 않는다.
- 수백 시간 예산은 장기 범위이며 단기 지원 전 의무 목록으로 사용하지 않는다.
