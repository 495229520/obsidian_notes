# MLIR 学习与实践计划整理

本文整理了从 MLIR 入门到实现小型张量编译器的学习范围与实践计划。各项实验的时间均为估算，应与已经执行、验证的结果区分。

## 1. 主要结论

1. **可以考虑 MLIR／AI 编译器方向，但一开始不必投入全部学习时间。** 先用四周独立修改一个 Pass，并为它编写测试，再根据实际进度决定后续投入。
2. **长期学习路线与申请实习前的最低要求分开。** 不必完成数百小时的全部计划才开始申请。
3. **短期目标是完成一个自己能讲清楚的编译器项目。** 优先实现少量算子、校验、Lowering、CPU 执行与测试。不同时把真实 NPU、完整量化、自研内存规划器和实际编译器 PR 列为必做项。
4. **现阶段不需要购买额外设备。** 先用已有 PC 和 SSD 进行 CPU 开发与实验，等到具体任务需要加速器时，再考虑借用、租用或购买。
5. **Lab 的作品集价值来自自己的实际贡献。** 运行脚本、复现教程、独立扩展、修复实际缺陷，分别体现不同层次的能力。
6. **是否适合申请，要结合项目结果与招聘公告判断。** 目前还没有通过独立编码和面试评估编译器能力，不能保证录用或通过选拔，应依据阶段成果和申请反馈判断。

## 2. 起点、目标与约束

### 2.1 已有经验与兴趣

- 有 C++、Linux 学习经验，以及机器人、数据平台相关开发经验。
- 对 MLIR、张量优化、Lowering、硬件映射、片上内存和数据搬运感兴趣。
- 希望学习能服务于实习与就业，而不只是增加课程数量。
- 曾尝试跟进 NPU 编译器技术分享，但其中默认掌握的编译器和 MLIR 基础较多，理解存在困难。
- 短时间可以预习概念，但编写 Pass、调试 Lowering、分析内存，需要连续的工作时间。

不能仅凭这些经历，就认定已经熟练掌握编译器理论、Python、线性代数、深度学习、CUDA 和全部系统技术。应先检查实验需要哪些基础，再逐项补充。

### 2.2 时间投入与方向选择的风险

在为长期计划投入数月之前，先检查学习范围和优先级。用四周独立修改并测试一个小 Pass，了解需要补充的基础、实际进度，以及自己是否愿意继续。

初期控制专业方向的投入，保留一般求职准备，再根据阶段结果决定后续投入。如果已经开始学习，就把已有成果计入里程碑，没有必要等到某个日期重新开始。

## 3. 付费课程评估

评估课程时，可以参考以下学习主题与作业标准。不能仅凭课程大纲判断授课质量、全部作业的深度和课后支持。

### 3.1 保留的学习主题

所评估课程偏重 NPU 工具链、量化与部署实践。可以保留以下主题：

- 从模型前端到高层 IR、目标相关 IR、Lowering、算子分组和执行产物的完整流程。
- DMA、局部内存、算子分组、内存布局与管理。
- INT8 校准、敏感层分析、混合精度回退与性能剖析。
- 实际设备部署，以及预处理、推理、后处理流水线的构建。

### 3.2 六类实验分别体现的能力

| 实验   | 作业范围                     | 检查的能力                |
| ---- | ------------------------ | -------------------- |
| Lab1 | 独立实现消除无用运算的 Pass         | 编译器变换实现              |
| Lab2 | 比较 ResNet50 的 CPU／NPU 执行 | 环境配置、模型运行、测量         |
| Lab3 | ONNX → MLIR → 目标执行产物     | 理解转换流程；开发深度取决于是否修改源码 |
| Lab4 | 量化、精度分析、回退               | 模型适配与量化调试            |
| Lab5 | 目标检测视频流水线                | 并发、队列、部署工程           |
| Lab6 | 对受支持的开源 LLM 部署交互式推理      | LLM 部署全流程            |

其中明确要求直接实现编译器 Pass 的是 Lab1。其他实验也要从作业说明中确认：是只执行给定命令，还是要求修改源码并编写测试。上表是学习设计示例，不代表某家培训机构的实际作业清单。

例如，Lab3 如果要求保存各阶段 IR、找出负责转换的 Pass、修改变换规则并添加回归测试，就能形成开发训练。如果只是运行转换命令，主要体现的是工具使用能力。

### 3.3 需要补充的基础

| 基础 | 作用 |
|---|---|
| IR、SSA、定义与使用、基本块、支配关系 | 理解程序表示和值的有效范围 |
| Operation、Value、Region、Block、Type、Attribute | 理解 MLIR 对象与 C++ API |
| 算子语义、Verifier、Trait、Interface | 判断输入是否合法、变换是否可行 |
| 副作用、别名、变换合法性 | 避免优化改变程序语义 |
| tensor、linalg、scf、memref | 连接张量计算、循环与实际存储空间 |
| Bufferization、所有权、释放责任 | 理解复制、复用与内存生命周期 |
| lit、FileCheck、数值回归测试 | 验证 IR 结构和执行结果 |

数学与算子的具体范围，可参考数学与算法基础笔记。

### 3.4 如何判断是否值得支付学费

目前尚未确认价格、完整作业、批改示例、教师反馈和设备资源，因此不作购买结论。应索取以下资料进行比较：

1. Lab1 的完整说明与学员作业示例。
2. 基础、Lowering、算子分组课程的样例。
3. 是否审查学员编写的 Pass、变换代码与测试。
4. NPU 型号、SDK、工具版本和模型规格。
5. 可用时长、排队方式、访问期限，以及结课后能否复现。
6. 学费、课时单位、课外预计投入时间。

仅讲解公开文档或运行预制脚本，难以判断服务价值。应确认是否提供稳定的设备访问、源码级调试指导和持续代码审查。

BF16 是浮点格式，不是校准算法。XLA 的适用范围应结合实际框架和后端确认。课程总量也不能只看数字之和，要明确单位究竟是小时还是课次。

## 4. 区分 Lab 的依据与教学设计

以下实验参考公开技术资料设计。应区分官方教程已有的机制与需要自行实现的教学任务，目前并未完成全部实验的执行与验证。

| 内容 | 依据与状态 |
|---|---|
| NPU 转换、量化、算子分组、部署 | 从课程主题中提炼；具体实现要在选定工具中确认 |
| Dialect、Verifier、重写、Lowering、LLVM 执行 | 有官方教程、源码和测试 |
| Bufferization、分块与融合 | 有官方机制与示例；实验安排需单独设计 |
| MiniNN 名称、四类算子、小型网络、受限 ONNX 导入器 | 需要自行实现和验证的教学设计 |
| 64KiB 教学容量、独立内存规划器与检查器 | 简化的自建实验，不代表真实硬件 |
| 实际缺陷修复、优化 PR | 后期选题候选；复现之前不能认定为确定作业 |
| 各 Lab 的时间 | 学习和实际操作的估算，不是实测完成时间 |

准备执行的 Lab，应包含参考仓库、固定版本、源码与测试位置、可运行的基准示例、自己的修改范围，以及验证命令和标准。只有标题和时间估算，还不能算准备完成的实验说明。

## 5. 开源项目与参考资料

### 5.1 官方 Toy：主要参考资料

- [官方教程](https://mlir.llvm.org/docs/Tutorials/Toy/)
- [GitHub 源码](https://github.com/llvm/llvm-project/tree/main/mlir/examples/toy)

内容涵盖自定义算子、Dialect、模式重写、Interface、形状推断、分阶段 Lowering 和 LLVM 代码生成。先掌握 IR 基础，再理解并修改 Toy 的部分实现。

Toy 的示例路径包含 Affine Lowering，与这里设计的 ONNX → MiniNN → Linalg 路径不同。MiniNN 是利用这些机制设计的独立综合实验，不能称为 Toy 官方作业。

### 5.2 MLIR For Beginners：C++ 实现的辅助资料

- [j2kun/mlir-tutorial](https://github.com/j2kun/mlir-tutorial)

内容包括构建、Lowering 执行与测试、首个 Pass、TableGen、Dialect、Trait、折叠、Verifier、Canonicalizer、Dialect Conversion、LLVM Lowering、数据流分析和 PDLL。

根据当前问题选择性阅读，不要与 Toy 同时完整学习两遍。执行时使用对应仓库要求的依赖，不能假设不同教程可以随意共用某个 LLVM 版本。

### 5.3 官方 Transform Dialect：优化参考资料

- [官方教程](https://mlir.llvm.org/docs/Tutorials/transform/)

内容涵盖已有变换的组合、新 Transform 算子的扩展，以及独立项目集成。掌握 MLIR 基础后复现示例，再补充不能整除的尺寸、不同参数、正确性对比和性能测量。

### 5.4 Bufferization 与测试资料

- [Bufferization](https://mlir.llvm.org/docs/Bufferization/)
- [Dialect Conversion](https://mlir.llvm.org/docs/DialectConversion/)
- [MLIR Testing Guide](https://mlir.llvm.org/getting_started/TestingGuide/)
- [Understanding the IR Structure](https://mlir.llvm.org/docs/Tutorials/UnderstandingTheIRStructure/)
- [LLVM Programmer’s Manual](https://llvm.org/docs/ProgrammersManual/)

Bufferization 涉及 tensor 到 memref 的转换、别名和原地更新等内容。教学用片上内存规划器属于另一层的实验，要分别理解。One-Shot Bufferize 本身不负责释放缓冲区，需要接入释放流程，或明确由外部负责所有权管理。

### 5.5 后期实际编译器案例的选择

不把某家厂商的编译器固定为必选对象。从开源项目或有权访问的 SDK 中，选择能够确认代码、依赖、执行环境和测试的对象，并记录仓库、许可证、版本与目标硬件。

按照“运行受支持的示例 → 跟踪一个算子 → 编写最小复现输入 → 修改边界明确的问题”推进。不能保证一定存在适合初学者的算子分组缺陷，也不能保证优化一定提升性能。选题需要源码分析和基准实验。

### 5.6 限制资料范围

初期以 Toy 为主，MLIR For Beginners 为辅。进入优化阶段后补充 Transform 和 Bufferization，再分析选定的编译器。不要同时开始多个大型编译器或 GPU 框架。

## 6. 长期路线与 MiniNN 项目

按照“通用 MLIR 基础 → 小型 CPU 编译与执行全流程 → 优化与内存分析 → 实际编译器源码修改 → 目标岗位需要的硬件知识”推进。

### 6.1 MiniNN 的初始范围

- 静态形状、二维张量、FP32。
- Constant、MatMul、Add、ReLU。
- 初期 Add 只允许相同形状的输入；不支持的广播应报错。
- 长期转换路径：受限 ONNX → MiniNN → Linalg 等标准 Dialect → 缓冲区与循环 → LLVM → CPU。
- 自行实现算子语义、校验、必要变换、测试和错误诊断；复用上游基础设施与代码生成机制。

原示例网络先将 1×16 输入与 16×32 权重相乘，加入偏置并应用 ReLU，再乘以 32×8 权重，得到 1×8 输出。若使用常见的一维偏置，需要明确支持广播，或在构图时转换为受支持的形状，不能默默超出“相同形状 Add”的范围。

### 6.3 Trellis 整合方案的扩展范围

此前的整合方案为项目 A 加入 CPU 编译、优化、教学内存规划与独立检查，为项目 B 加入实际编译器修改与验证。因此，估算为 386–530 小时，比基础计划的 204 小时更多。

| 扩展阶段 | 范围 | 估算小时数 |
|---|---|---:|
| L0 | 参考计算与环境 | 32–44 |
| L1 | SSA、重写、测试 | 36–48 |
| L2 | Dialect、Lowering | 50–66 |
| L3 | Bufferization、CPU 执行 | 44–58 |
| L4 | 分块与融合 | 50–70 |
| L5 | 内存规划、检查与重新执行 | 60–84 |
| L6 | NPU 转换、量化与模拟环境 | 36–50 |
| L7 | 实际编译器补丁 | 60–84 |
| 发布准备 | 复现、文档与结果整理 | 18–26 |

两套方案中，L 编号对应的任务不同，不能混用。不要把整个扩展计划当成短期目标，先完成下一节中的最小项目范围。学习计划中的长期预算与本文的试学时间不能相加。

教学项目以 LLVM／MLIR 20.1.8 为基准。NPU 项目要在确定仓库、SDK 和目标后，分别固定版本并确认执行条件。不必追随最新版本，也不能假设已经在现有设备上完成验证。扩展计划 L6、L7 与基础计划 L14 所需的 NPU 相关时间，应在选定实际工具后重新估算。

### 6.4 后期选修任务

| 任务 | 内容 | 时间估算 |
|---|---|---|
| N1 | 比较真实 NPU 小模型的正确性、设备耗时与端到端耗时 | 12–20 小时 |
| N2 | 目标检测视频流水线、有界队列、吞吐量、延迟与丢帧 | 16–24 小时 |
| N3 | Attention、KV cache、受支持 LLM 的部署 | 20–36 小时 |
| N4 | 实际编译器算子的新增、修改与测试 | 20–40 小时以上 |

估算以已经具备对应硬件、工具和受支持示例为前提。编译器开发优先考虑 N4，机器人边缘部署优先考虑 N1／N2。N3 分别测量 prefill 与 decode，不能只报告是否能对话。这些任务都可以放在最小项目完成后。

## 7. 从完成小型编译器开始的短期计划

### 7.1 最小项目产物

主项目只保留一个基于 MLIR 的小型张量编译器。

1. 仅支持少量静态 FP32 算子。可以直接输入自定义 MLIR，省略 ONNX 前端。
2. 自行实现算子校验与核心 Lowering。
3. 复用上游机制，在 CPU 上执行。
4. 与独立参考实现进行数值对比。
5. 测试错误形状、不支持的输入和必要边界条件。
6. 能详细解释一个自己发现的缺陷，或一项经过实测的优化。

### 7.2 第一个项目排除的范围

- ONNX 前端。
- 完整量化 IR、整数内核、混合精度 Lowering。
- 真实 NPU 与 GPU 深入任务。
- 独立片上内存规划器。
- 已被上游合并的实际编译器 PR。
- 完整的视频或 LLM 应用。

有余力时只扩展一项，不要一次把所有任务重新加回来。

### 7.3 学习进度检查时间点

| 时期 | 预期结果 | 判断 |
|---|---|---|
| 2026 年 10 月 21 日至 11 月初 | 保持 C++、Linux、算法和已有项目准备，少量预习 MLIR | 计入已有成果，不从头开始 |
| 11 月中旬至 12 月初 | 运行公开示例，独立修改 Pass，测试正常与错误输入 | 检查理解进度与兴趣 |
| 12 月中旬至 2027 年 1 月中旬 | 完成少量算子的 CPU 执行全流程，开展数值与错误测试 | 整理实现和验证结果；困难较大时缩减算子与功能 |
| 1 月中旬至 2 月中旬 | 深入一个缺陷或优化，整理复现与说明 | 停止扩大范围，补充基础 |

表中的日期用于检查学习进度，不保证届时完成，应根据实际结果调整范围。

### 7.4 四周试学

前四周每周给 MLIR 分配 8–12 小时，并保持其他求职准备。四周后检查：

- 能否解释一段简短 IR，并独立修改一条规则？
- 遇到错误时，能否开始缩小原因范围，而不是完全依赖外部答案？
- 是否愿意继续阅读源码、调试和验证？

进度慢时，区分原因来自基础、环境、范围还是投入时间。必要时缩小范围或降低优先级，不必因为已经投入时间就继续。四周未达标，也不能直接判定自己不适合这个领域。

|---|---|---|
| AMD 9700X＋48GB PC | LLVM／MLIR 构建、C++ 开发、CPU 实验 | 主开发机，无需预先升级 |
| 已购买的 2TB SSD | WSL、源码、构建、模型、容器 | 安装后确认空间与路径 |
| GTX970 | 一般显示输出 | 不为主项目更换 |
| MacBook Air | 阅读、编辑、小型实验、SSH | 继续使用 |
| i7＋16GB＋GTX1660S Ubuntu | 备用原生 Linux 环境 | 无需预先升级 |
| NPU 开发板 | 后期真实部署与性能测量 | 暂缓购买 |

配置环境时检查：

- WSL 虚拟磁盘放在新 SSD，源码与构建目录放在 WSL 内部的 Linux 文件系统。
- 检查 WSL2 内存设置。若上限取宿主机内存的 50%，48GB PC 对应约 24GB。可根据 Windows 内存占用考虑约 32GB 的配置，但这不是硬性要求，要确认实际可用量。
- 先构建需要的工具与宿主目标，选择 Release＋assertions 配置，并限制编译与链接并行度。
- 测量最小构建的峰值内存、磁盘占用和耗时后，再决定是否升级。

CPU 项目不需要购买 GPU。NPU 编译器源码和模拟器能否运行，取决于依赖及支持环境。模拟器的功能验证不能证明真实设备性能。实际 NPU 的延迟、吞吐量、功耗和 DMA 重叠需要对应硬件，不能因为某块开发板带 NPU，就认为它能替代任意目标设备。

## 9. Lab 的简历价值与填写标准

### 9.1 不同结果能证明什么能力

| 结果 | 简历中的意义 |
|---|---|
| 配置环境、阅读 IR、原样运行教程 | 必要基础，通常不单独作为项目 |
| 简单的加零消除 Pass | 项目细节，单独成项的范围偏小 |
| 自定义算子、校验、Lowering | 核心开发能力的依据 |
| 从模型／IR 到 CPU 执行全流程 | 可作为主要项目展示 |
| 有独立验证的分块、融合与内存优化 | 可在技术面试中深入说明 |
| 实际项目中可复现的缺陷修复 | 配合测试、审查记录，更容易说明贡献 |
| 基于脚本的视觉／LLM 部署 | 主要证明部署能力 |

### 9.2 写入简历前检查五件事

1. 区分自己编写的代码与复用上游的部分。
2. 有实际执行结果和独立参考对比。
3. 覆盖错误输入测试、错误诊断与边界条件。
4. 深入解决一个问题，能解释原因、选择依据和代价。
5. 当场改变形状或使用关系时，仍能判断变换合法性，并解释和修改实现。

AI 可以辅助编码，但不能代替对算子语义、失败条件和调试过程的理解。

### 9.3 最终项目组合

- **项目 A：基于 MLIR 的小型张量编译器。** 说明支持范围、算子校验、转换路径、CPU 执行、测试和个人贡献。没有 ONNX 前端，就不要声称支持 ONNX。
- **项目 B：对选定 MLIR／NPU 编译器的具体修改或扩展。** 作为后续选修，围绕一个问题展示复现、原因分析、补丁和测试，不把完成 B 作为首次申请实习的前提。

不要在简历中堆砌几十个 Lab 编号。复现教程要说明来源；PR 尚未合并，就如实写未合并或审查中，不把已有功能算作自己的实现。

性能结果应说明实际设备、输入、精度、线程数、测量范围、预热与重复测量条件。教学规划器的峰值使用量下降，应表述为规划层面的内存用量改善。通过模拟器属于功能验证，不能写成真实 NPU 加速成果。

## 10. 申请方向与招聘公告检查

### 10.1 可以考察的岗位

| 方向 | 与路线的关系 | 额外准备 |
|---|---|---|
| MLIR／AI 编译器实习 | 直接相关 | C++、编译器与模型基础、独立调试 |
| 图优化、Lowering、内存规划初级岗位 | 方向相关 | 深入解决问题与实际源码修改 |
| GPU 算子与编译优化 | 仅覆盖部分基础 | GPU 架构、CUDA／Triton、真实设备分析 |
| LLVM 代码生成后端 | 当前覆盖有限 | 指令选择、寄存器分配、指令调度 |

搜索公告时，可以使用 AI 编译器、图编译器、编译器开发、MLIR、推理优化等关键词，再逐项核对工作职责。岗位名称中有 AI，不代表一定要求这套技术栈。

### 10.2 阅读招聘公告的标准

申请时，把官方公告的要求与自己的成果逐项对照。下表用于检查，不表示某家企业正在招聘。

| 检查项 | 对应准备材料 |
|---|---|
| C／C++、数据结构与算法 | 自己实现的代码和问题解决过程 |
| LLVM／MLIR 或模型编译经验 | Dialect、Pass、Lowering、测试结果 |
| 量化、架构与性能分析 | 实际完成的实验和测量条件 |
| 实习、应届、社招的区分 | 分别核对学历与经验要求 |
| 作品集与选拔方式 | 仓库、复现步骤、技术说明、公告要求的材料 |

这些是公告检查标准，不是所有企业的统一要求。不要把资深岗位的要求当作入门项目最低标准。岗位是否存在、是否符合资格、能否通过选拔，需要分别判断。

### 10.3 何时开始申请

- 只有基础 Pass 时，继续完善结果，同时检查岗位要求。
- 具备 CPU 执行全流程、独立测试和一个能充分说明的修改案例后，可以考虑相关实习。
- 后续完成深入优化或实际编译器修改，再更新简历，不必全部做完才首次申请。

不能只凭有没有实习经历判断机会。应把已有机器人项目和新编译器项目中亲自实现的功能、解决的问题、验证结果写具体。

也可以同时考察与既有经验匹配的 C++ 系统、系统软件、机器人平台岗位。这些方向仍需单独准备，但可以降低只依赖一个方向的风险。
