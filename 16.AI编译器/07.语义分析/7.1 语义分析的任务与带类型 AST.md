# 7.1 语义分析的任务与带类型 AST

Parser 确认程序符合文法，语义分析进一步检查名称、类型和继承等静态约束，并给 AST 补充后续编译需要的信息。它不负责证明程序的业务逻辑正确，也不能排除所有运行时错误。

## 1. 语法合法之后还缺什么

```cool
let y: String <- "abc" in y + 3
```

这个表达式的结构合法，y 也能找到声明，但 COOL 的加法要求两个操作数都是 Int，因此类型检查失败。

另一个表达式 `let y: Int in x + 3` 是否错误，取决于外层有没有可见的 x：查不到时是名称错误，查到 String 时是加法类型错误，查到 Int 则可以通过。不能只看局部片段就断言 x 未声明。

| 检查 | 所需信息 |
|---|---|
| 标识符是否可用 | 声明、作用域与名称绑定 |
| 赋值、运算是否相容 | 表达式类型、声明类型、子类型关系 |
| 方法调用是否合法 | 接收者类型、参数数量、方法签名 |
| 类是否合法 | 类名集合、父类关系、成员与重写规则 |

“必须有可见声明”不等于“声明必须写在使用之前”。COOL 类名允许前向引用，属性在整个类中可见，相关实现见 [[7.4 类、继承与多趟语义分析]]。

## 2. 为什么不全部写进 CFG

CFG 擅长描述嵌套结构，任意名称的声明与使用匹配还需要跨位置的信息。形式语言中的同序复制语言

$$L=\{wcw\mid w\in\Sigma^*\}$$

在 Σ 至少有两个字符、c 是额外分隔符时不是上下文无关语言。它可用来说明无界名称匹配中的一种限制，但不是实际程序全部语义约束的完整模型。

把 w 压栈后只能逆序弹出，是帮助理解的直觉，不是证明任意下推自动机都做不到的完整证明。反序复制 wcwᴿ 可以由 CFG 描述，单字符字母表下的 aⁿcaⁿ 也可以。

有些简单类型限制确实可以写进文法；将名称与类型统一交给单独的数据结构和规则检查，通常更容易维护。Parser 中也可以执行语义动作，因此阶段分工不要求实现必须完全隔离。

## 3. 语义分析输出什么

| AST 注解 | 例子 |
|---|---|
| 表达式静态类型 | 加法节点标为 Int |
| 使用与声明的关联 | 某处 x 指向内层 let 的声明节点 |
| 方法签名信息 | 接收者能调用哪个签名、返回类型是什么 |
| 诊断位置 | 未声明名字或不相容初始化式的源码范围 |

动态方法调用的静态签名已经确定，不代表运行时实现已经固定；实际执行哪个重写方法仍可能由对象动态类型决定。

类型信息可写入 AST，也可保存在节点索引到信息的旁表中。两种方式都能形成逻辑上的带类型 AST。检查失败后可以保留部分注解供诊断使用，但不能把“遍历完成”当作“程序合法”。
