# 7.5 类型、静态检查与可靠性

入门时，可以把类型理解为对值及其可用操作的约束。Int 支持规定的整数运算，String 支持字符串接口。具体能做什么，以语言规则为准，不能只看底层位宽相同。

## 1. 静态类型和动态类型

假设 Dog 继承 Animal：

```cool
let pet: Animal <- new Dog in pet
```

| 对象 | 类型 |
|---|---|
| 初始化表达式 new Dog 的静态类型 | Dog |
| 正文中变量引用 pet 的静态类型 | Animal |
| 本次运行中 pet 保存的对象的动态类型 | Dog |

静态类型由检查规则推导；动态类型是运行时实际对象所属的类。编译器知道 pet 可以容纳 Animal 子类，不代表总能据此把每次 pet 引用都推导为 Dog。

## 2. 检查和推导如何配合

类型推导计算表达式的类型；类型检查验证它是否满足使用位置的约束。

在 COOL 中，程序员声明属性、形参、返回值和 let 变量的类型，编译器仍要推导加法、调用和分支等表达式的类型。因此“有显式类型声明”不等于“不需要类型推导”。

例如先推导初始化式为 Dog，再验证 Dog 是否符合 Animal。反过来，知道变量要求 Animal，并不能把任意初始化式直接标成 Animal 而跳过检查。

## 3. 静态检查与运行时检查

静态类型系统主要在运行前验证约束；动态类型系统主要在执行操作时检查值。静态作用域与动态作用域讨论的是名字绑定，两者应分开。

静态类型语言仍可能需要运行时检查，例如对空对象调用方法。动态类型语言也可以编译成机器码，“动态类型”并不等于“只能解释执行”。

机器指令会按指定方式解释位模式，但硬件也有不同指令、权限和异常机制，不能笼统地说“底层完全不区分类型、完全不会检查”。源语言的类型约束通常仍需编译器或运行时实现。

## 4. 可靠性承诺什么

在 COOL 的普通类类型情形，若一个良类型表达式正常求值得到非 void 对象，则对象动态类型应符合表达式静态类型：

$$T_{dynamic}\le T_{static}.$$

这只是可靠性的一项直观表述；完整论证还依赖运行时环境、语言求值规则以及 SELF_TYPE 等特殊情况。不能把这个不等式当成所有类型系统唯一的可靠性定义。

类型可靠不等于不会除零、不发生对 void 的分派、不出现没有匹配分支的 case，也不保证程序终止或业务结果正确。应看语言具体承诺排除哪些错误。

## 5. 可靠性与精度

Int 符合 Object。把整数字面量只标成 Object 虽然是一个宽泛上界，却会丢失 Int 信息，使 `1 + 2` 无法满足加法要求。

所以检查器应按规则尽量保留精确类型。宽化成 Object 后仍可以使用 Object 的接口，并不是所有操作都不能做。

静态检查也可能拒绝某些运行时实际安全的程序。SELF_TYPE 就是在不直接执行程序的前提下保留接收者相关类型信息的一种机制，见 [[7.11 SELF_TYPE 与精确返回类型]]。
