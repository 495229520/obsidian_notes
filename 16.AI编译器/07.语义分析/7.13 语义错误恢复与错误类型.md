# 7.13 语义错误恢复与错误类型

语义分析已经拥有 AST，遇到一个坏表达式后通常可以继续访问其他子树。需要解决的问题是：给出错节点什么检查结果，才能减少派生报错，同时保留独立错误？

## 1. 为什么 Object 可能引发级联诊断

假设外层没有 x：

```cool
let y: Int <- x + 2 in y + 3
```

若将所有出错节点都恢复成 Object，可能依次报告：x 未声明、Object 不能参与加法、初始化式 Object 不符合 Int。后两条可能都源于第一处错误。

具体报错数量取决于实现。例如 Add 报错后仍按 Int 恢复，就不一定再触发初始化错误。因此不能把某个示例的次数当成所有编译器的固定行为。

## 2. 专门的错误占位

一种做法是给失败结果标记 ErrorType。原笔记用 No_type 表示类似的恢复占位；实际代码中名称和职责必须先说明。

尤其要区分：有些 COOL 实验框架用 No_type 表示“没有初始化表达式”的内部类型。缺省初值与“已发现错误”不是同一件事，不能仅凭名称就混用。

采用错误占位时，可约定：

- 在相容性检查中，遇到已知错误结果时抑制由它派生的重复诊断。
- Add 的一侧为错误占位时，不再把这一侧报告为普通类型不匹配；另一侧仍单独检查。
- 父节点可传播错误占位，或在明确规则下恢复为预期类型，同时保留已发生错误的状态。

## 3. 底部类型只是其中一种模型

若将内部占位记为 ⊥，可为恢复计算定义：

$$\bot\le T,\qquad lub(\bot,T)=T.$$

这让失败初值不再重复触发“不能初始化 Int”，也让其他合法分支的信息可以继续传播。它是诊断恢复约定，不是说错误表达式真的有合法的运行时值。

不要把 ⊥ 当成用户类塞进普通父类树。它与所有正常类型的关系需要单独处理；SELF_TYPE、方法查找、LUB 等辅助函数也要识别它。实现也可以选择显式错误状态，而不是数学上的共同底部。

## 4. 重新检查例子

| 位置 | 恢复处理 |
|---|---|
| x | 报告未声明，返回错误占位 |
| x + 2 | 检查右侧 2，抑制由 x 引发的重复类型错误 |
| let 初始化 | 不重复报告同一失败初值的相容问题 |
| 正文 y + 3 | y 仍按声明类型 Int 登记，正常检查正文 |

若正文另有未声明的 z，仍应报告。不能看到任何错误占位就跳过整个父节点的其余子树。

## 5. 恢复的边界

继承环或不存在的父类可能破坏后续分析的基础，应先停止相关阶段或建立专门恢复结构。局部类型错误则通常可以在有效的类图上继续检查。

每条诊断保留源码位置；退出局部作用域时恢复环境；最终是否成功依据错误状态或错误计数判断。某个节点恢复出了 Int，甚至整棵 AST 遍历结束，都不表示错误程序已被修正，也不应直接生成可执行程序。
