# 3.3 词法规格与匹配规则

正则表达式说明哪些字符串属于某一类，但 Lexer 还需要决定边界、同长度冲突和匹配后的动作。本篇讲选择规则；扫描程序怎样实现这些规则，见 [[3.7 表驱动 Lexer 的实现]]。

## 1. 一套简化规格

下面的规则用于教学，不是某种真实语言的完整词法。顺序越靠前，同长度匹配时优先级越高。

| 顺序 | 规则 | 模式 | 匹配后的动作 |
|---|---|---|---|
| 1 | IF | `"if"` | 输出 IF |
| 2 | ID | `[a-zA-Z][a-zA-Z0-9]*` | 输出 ID，保留名称 |
| 3 | INT | `[0-9]+` | 输出 INT，转换或保留数值文本 |
| 4 | EQ | 两个连续等号 | 输出 EQ |
| 5 | ASSIGN | 一个等号 | 输出 ASSIGN |
| 6 | 标点 | `(`、`)`、`;` 等各自的规则 | 输出对应类别 |
| 7 | WS | `(' '|'\t'|'\n'|'\r')+` | 跳过，更新源码位置 |
| 8 | ERROR | 任意单个字符 | 报错并前进一个字符 |

各条普通 Token 规则必须至少消费一个字符。若规则可以匹配空串，而动作又不推进输入，扫描器可能永远停在同一位置。

## 2. 先比较长度，再比较优先级

从当前未处理位置出发，考虑所有规则能匹配的前缀：

1. 选择最长的匹配前缀。
2. 长度相同时，选择优先级最高的规则。
3. 执行该规则动作，从匹配末尾开始处理下一个 Token。

| 输入片段 | 候选 | 最终选择 |
|---|---|---|
| `if` | IF 长度 2，ID 长度 2 | IF，同长度按顺序 |
| `if8` | IF 长度 2，ID 长度 3 | ID，长度先于优先级 |
| 两个等号 | ASSIGN 长度 1，EQ 长度 2 | EQ |
| `foo123` | ID 可以匹配多个前缀 | 选择整个 `foo123` |
| `@`（本例） | 只有 ERROR | 报错并消费这个字符 |

关键词优先，不意味着见到关键字前缀就立刻返回。最长匹配也不是寻找整段输入的“最佳切分”：它只决定当前位置的最长合法前缀，不保证后面的字符仍能被合法切分。

## 3. 一个完整切分例子

```text
输入：if8 == 12;
输出：ID("if8"), EQ, INT(12), SEMICOLON, EOF
```

`if8` 整体比 `if` 更长，选 ID；空格匹配 WS 后跳过；两个等号形成 EQ；`12` 形成 INT；分号形成标点 Token。

这只是切分。整串是否构成合法语句，以及 if8 是否已声明，不由这一组词法规则判断。

## 4. 空白、注释与错误恢复

匹配后跳过是一种动作，不代表扫描器没有识别它。即使不向 Parser 输出空白和注释，也要更新行号、列号或源码偏移。

本例同时包含回车和换行，避免读取 CRLF 文件时把回车误判为非法字符。对于缩进具有语法意义的语言，空白还可能参与产生缩进相关 Token，不能直接套用“全部丢弃”。

ERROR 规则只匹配任意单个字符，且优先级最低。这样，合法的一字符 Token 在同长度比较中胜出，较长合法 Token 也能胜出。不要把错误兜底写成任意长度字符序列，否则它可能凭长度抢走正常输入。

未闭合字符串、未结束注释等错误通常需要专门处理：应报告构造从哪里开始、为什么不完整，再按约定恢复。简单地逐字符报错不一定能给出有用诊断。

COOL 的任意深度嵌套注释还需要记录嵌套深度，不能只靠有限状态表示全部层数。正则规则和 DFA 是本章的基础模型，实际 Lexer 可以配合计数器或专门代码。

## 5. 生成时与运行时如何分工

生成器可以把每条规则的 NFA 接受状态标上规则编号；子集构造后，为每个 DFA 状态预先选好最高优先级的接受规则。

运行时仍需继续扫描并寻找最后接受位置，才能实现最长匹配。因此，“规则优先级已在生成时确定”不能替代运行时的最长匹配逻辑。
