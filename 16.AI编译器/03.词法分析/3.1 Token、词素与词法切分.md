# 3.1 Token、词素与词法切分

词法分析器（Lexer）接收字符序列，把它切成词素并确定类别，再交给语法分析器。它要回答两个问题：这一段在哪里结束？这一段是什么？

## 1. 类别、词素和 Token 对象

以 `if (count < 12)` 为例：

| 原始片段（词素） | 类别 | 可携带的信息 |
|---|---|---|
| `if` | IF | 源码位置 |
| `(` | LPAREN | 源码位置 |
| `count` | ID | 名称或字符串表索引 |
| `<` | LT | 源码位置 |
| `12` | INTEGER | 数值 12、原始拼写 |
| `)` | RPAREN | 源码位置 |

- Token 类别描述一类合法片段，例如标识符、整数或某个运算符。
- Lexeme（词素）是源码中实际出现的字符片段，例如 `count`、`12`。
- 实现中的 Token 通常包含类别、属性和源码范围，不必每次复制整个词素。

课程里写成 `<ID, "count">` 是一种简化表示。整数属性可以保存转换后的数值，标识符属性可以保存名称索引。源码位置用于后续报错，不能因为丢弃空白就丢掉位置追踪。

上述例子的空格通常被跳过，Parser 收到 IF、LPAREN、ID、LT、INTEGER、RPAREN，最后再收到 EOF。EOF 是输入结束标记，不是源文件里实际写出的字符。

## 2. Lexer 不负责哪些判断

`count` 是否声明、类型是否允许比较，由语义分析处理；括号和表达式能否组成合法语句，由语法分析处理。

例如，缺少分号通常不妨碍每个字符组成合法 Token，所以它通常是语法错误。`my-var` 也可能被正常切成 ID、减号、ID，不能仅凭作者想把它当变量名就认定词法切分失败。

词法规则取决于语言。本章示例采用“字母开头，后接字母或数字”的简化标识符规则，不是 C++ 或 COOL 的完整规范。

## 3. 向前看与词素边界

读到一个等号时，需要检查后面是否还有等号，才能区分赋值符号 \= 和比较符号 \==。读到标识符的第一个字符后，则要继续读取全部合法后续字符。

因此要区分：

- 读取一个可能很长的 Token，例如长标识符。
- 为确定边界而额外探测后面的输入，有时还需要回退。

不能笼统地说所有 Token 都只需向前看一个字符。例如，单点与三点运算符需要继续探测；通用最长匹配的回退机制见 [[3.7 表驱动 Lexer 的实现]]。

## 4. 关键字和标识符

若 `if` 是保留字，拼写相同的词素应当分类为 IF，不能用作普通变量名。但 `if8` 应当整体识别为标识符，不能因为前两个字符是关键字就提前结束。

常见实现有两种：

1. 把关键字和标识符都写成规则，通过最长匹配和规则优先级选择。
2. 先读取完整标识符，再查询关键字表，确定最终类别。

两者都必须先确认完整词素边界。具体匹配政策见 [[3.3 词法规格与匹配规则]]。

## 5. 语言设计如何影响词法分析

| 原文例子 | 难点 | 应记住的结论 |
|---|---|---|
| 早期 Fortran 的 `DO 5 I = 1,25` 与 `DO 5 I = 1.25` | 忽略空格后，前者是循环，后者可作为对 DO5I 的赋值；要读到后面的标点才区分 | 早期词素的解释可能依赖较远的字符 |
| PL/I 允许关键字用作名称 | 同一拼写在不同语句位置具有不同作用 | 关键字不一定是保留字，分类可能需要语法上下文 |
| C++ 嵌套模板中的 `>>` | 按普通最长匹配得到右移 Token，但模板结束需要两个右尖括号 | C++11 起在相应模板上下文中按两个 `>` 处理，不能把所有 `>>` 都拆开 |

这几个例子用于说明词法与语法的边界，不必背下完整历史语句。实际编译器可以由 Parser 解释上下文相关 Token，不一定要求 Lexer 独自完成判断。
