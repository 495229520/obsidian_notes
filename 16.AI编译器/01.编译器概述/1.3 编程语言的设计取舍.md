# 1.3 编程语言的设计取舍

语言设计围绕使用场景做选择。评价一种语言，需要同时看它如何表达问题、允许哪些操作，以及实现和使用这些功能的成本。

## 1. 为什么需要不同的语言

| 使用场景 | 关注的问题 | 代表例子 |
|---|---|---|
| 系统编程 | 内存布局、资源生命周期、与操作系统和硬件交互 | C、C++ |
| 科学计算 | 数组、数值运算及其优化 | Fortran |
| 数据库查询 | 用简洁规则表达筛选、连接和聚合 | SQL |
| 脚本与数据处理 | 开发速度、交互使用、库的组合 | Python |

这些是常见用途，不是语言只能用于这些场景。

一些设计选择会改变成本分配：

- 自动内存管理减少手动回收工作，但可能引入运行时开销；显式管理提供控制，也增加错误风险。RAII、所有权检查等机制提供其他选择。
- 静态检查可以提前发现问题，但类型系统和规则也需要学习；把检查留到运行时会改变开发体验和运行成本。
- 高层抽象可以减少代码量。实现能否消除抽象开销，要看语言规则、编译器和具体用法，不能简单认为抽象越高就越慢。

## 2. 声明式表达给实现留下选择空间

SQL 是领域特定语言（DSL）。一条查询可以说明需要哪些行、怎样分组、返回哪些列，而不指定逐行遍历还是索引查找。

例如，“按类别汇总金额”表达了所需结果；数据库查询优化器再根据索引、统计信息和成本估计选择执行计划。相同查询在不同数据和索引条件下，可以采用不同计划。

这与编译器的关系是：程序表示保留了某种语义，实现可以在符合语义的前提下选择执行方法。张量编译也利用这种空间，例如保留矩阵乘法这一操作后，再选择分块、数据布局和目标指令。

声明式与命令式不是互斥的语言标签。同一套软件可以用 C++ 控制流程，再用 SQL 描述查询；同一种语言也可以支持多种表达方式。

## 3. 为什么旧语言演进的同时，还会出现新语言

成熟语言的变化受到旧代码、工具、库和使用习惯的约束。改变一条规则，可能让已有程序失效，也可能增加迁移和培训成本。

新语言较少受到既有代码的限制，可以重新选择类型系统、内存管理和语法规则。但采用新语言仍需承担：

- 学习语言、标准库和工具的成本。
- 迁移既有代码、对接其他语言的成本。
- 补齐库、调试器和部署支持的成本。

因此，语言设计有优势并不等于会被广泛采用。它带来的收益需要足以抵消这些成本。沿用熟悉的语法，可以降低其中一部分学习负担。

## 4. 怎样评价一种语言

| 维度 | 具体要问的问题 |
|---|---|
| 表达能力 | 目标领域的问题是否容易写清楚？ |
| 可读性与维护性 | 别人能否理解、调试和修改代码？ |
| 安全性与可靠性 | 哪些错误可以提前阻止，哪些需要运行时处理？ |
| 性能与可预测性 | 速度、内存和延迟是否符合需求？ |
| 可移植性与互操作性 | 能否部署到目标平台，与现有系统配合？ |
| 工具和生态 | 所需库、构建、调试和分析工具是否可用？ |

流行程度可以反映实际采用情况，但不能代替上述评价。大量旧代码、特定平台要求或成熟库，都可能让一门语言长期保有用户。

对编译器学习而言，还可以继续追问：这项语言特性要求前端检查什么？需要怎样的 IR？哪些成本能在编译期消除，哪些需要运行时支持？
